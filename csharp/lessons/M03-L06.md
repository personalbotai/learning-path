### 1. Konsep & Arsitektur Mendalam

Struktur data standar dalam .NET seperti `List<T>`, `Dictionary<TKey, TValue>`, dan `Queue<T>` dirancang untuk eksekusi single-threaded dengan performa maksimal. Ketika diakses secara paralel oleh multiple threads, struktur data ini akan mengalami:
1. **Race Conditions**: Kerusakan integritas internal state (misalnya modifikasi pointer `_size` atau referensi node secara bersamaan).
2. **Data Corruption**: *Torn reads/writes* pada 64-bit value di arsitektur 32-bit atau pembacaan array saat proses *resizing* internal belum selesai.
3. **Infinite Loops**: Pada `Dictionary<TKey, TValue>` non-thread-safe, tabrakan hash (*hash collision bucket chain*) yang dimodifikasi secara konkuren dapat membentuk *cyclic linked-list*, menyebabkan thread mengalami CPU spinning 100% tanpa henti.

Pendekatan naif untuk mengatasi masalah ini adalah *coarse-grained locking* menggunakan statement `lock (_syncRoot)` pada setiap operasi pembacaan dan penulisan. Pendekatan ini memiliki penalti performa yang fatal:
* **Lock Contention**: Thread terpaksa masuk ke status *blocking/waiting*, memicu context switching pada kernel thread yang mahal (~ribuan siklus CPU).
* **Convoy Effect**: Kumpulan thread antre menunggu satu resource, menurunkan *throughput* sistem ke batas konkurensi $O(1)$.
* **Cache Invalidation**: Penggunaan lock memaksa flush cache CPU berulang kali (L1/L2/L3 cache coherence traffic).

Untuk menyelesaikan masalah ini, .NET menyediakan namespace `System.Collections.Concurrent` yang dibangun di atas kombinasi arsitektur **Fine-Grained Locking** dan **Lock-Free Programming (Hardware Atomic Primitives)**.

```
+-------------------------------------------------------------------------------+
|                      System.Collections.Concurrent                             |
+-------------------------------------------------------------------------------+
|  ConcurrentDictionary<TKey, TValue> | - Striped Locks (Bucket-level Locking)  |
|                                      | - Lock-Free Volatile Reads             |
+--------------------------------------+----------------------------------------+
|  ConcurrentQueue<T>                  | - Lock-Free Segment Array              |
|                                      | - Interlocked.CompareExchange (CAS)    |
+--------------------------------------+----------------------------------------+
|  ConcurrentStack<T>                  | - Lock-Free Treiber Stack (CAS)        |
+--------------------------------------+----------------------------------------+
|  ConcurrentBag<T>                    | - Work-Stealing Pattern                |
|                                      | - Thread-Local Queues (Affinity)       |
+--------------------------------------+----------------------------------------+
|  BlockingCollection<T>               | - Producer-Consumer Pipeline Wrapper   |
|                                      | - Bounded Capacity & SemaphoreSlim     |
+-------------------------------------------------------------------------------+
```

### 2. Implementasi & Contoh Kasus Nyata

Contoh kasus di bawah mengimplementasikan *High-Throughput In-Memory Metric Aggregator* yang menerima jutaan event dari berbagai thread dan mendistribusikannya ke background worker menggunakan `ConcurrentDictionary` dan `BlockingCollection`.

```csharp
using System;
using System.Collections.Concurrent;
using System.Threading;
using System.Threading.Tasks;

public sealed class MetricEvent
{
    public required string MetricName { get; init; }
    public double Value { get; init; }
    public DateTime TimestampUtc { get; init; }
}

public sealed class MetricAggregator : IDisposable
{
    // 1. ConcurrentDictionary: Lock-free reads, striped-lock writes
    private readonly ConcurrentDictionary<string, MetricStatistics> _metrics = new(
        concurrencyLevel: Environment.ProcessorCount * 2,
        capacity: 1000
    );

    // 2. BlockingCollection: Bounded Producer-Consumer queue untuk offloading I/O
    private readonly BlockingCollection<MetricEvent> _processingQueue = new(boundedCapacity: 50_000);
    private readonly CancellationTokenSource _cts = new();
    private readonly Task _backgroundWorker;

    public MetricAggregator()
    {
        _backgroundWorker = Task.Run(ProcessEventsAsync);
    }

    public void TrackMetric(string name, double value)
    {
        var metricEvent = new MetricEvent
        {
            MetricName = name,
            Value = value,
            TimestampUtc = DateTime.UtcNow
        };

        // TryAdd mencegah starvation: menolak data atau menerapkan backpressure jika antrean penuh
        if (!_processingQueue.TryAdd(metricEvent, 100))
        {
            Console.WriteLine($"[Warning] Queue saturated. Dropping event: {name}");
            return;
        }

        // Atomic In-Memory Update menggunakan AddOrUpdate
        _metrics.AddOrUpdate(
            key: name,
            addValueFactory: static k => new MetricStatistics(1, 0, 0),
            updateValueFactory: static (k, current) => current.Record(1)
        );
    }

    private void ProcessEventsAsync()
    {
        // GetConsumingEnumerable menangani pemblokiran thread secara efisien saat buffer kosong
        foreach (var metric in _processingQueue.GetConsumingEnumerable(_cts.Token))
        {
            // Simulasi aggregasi lanjutan atau flushing ke persistent storage
            _metrics.AddOrUpdate(
                metric.MetricName,
                addValueFactory: static _ => new MetricStatistics(1, 1, 1),
                updateValueFactory: static (_, existing) => existing.Record(existing.Count + 1)
            );
        }
    }

    public bool TryGetMetric(string name, out MetricStatistics stats)
    {
        // Operasi baca sepenuhnya LOCK-FREE
        return _metrics.TryGetValue(name, out stats!);
    }

    public void Dispose()
    {
        _processingQueue.CompleteAdding();
        _cts.Cancel();
        try { _backgroundWorker.Wait(2000); } catch (AggregateException) { }
        _processingQueue.Dispose();
        _cts.Dispose();
    }
}

// Immutable Record untuk menghindari mutating state di dalam collection secara tidak terkendali
public sealed record MetricStatistics(long Count, double Min, double Max)
{
    public MetricStatistics Record(long newCount) => this with { Count = newCount };
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **`ConcurrentDictionary<TKey, TValue>` (Lock Striping & Volatile Read)**:
   * **Write Path**: Tidak menggunakan satu lock global. Runtime membagi collection ke dalam array table buckets dan array objek synchronization locks terpisah yang disebut *Lock Stripes*. Secara default, jumlah lock sebanding dengan `Environment.ProcessorCount * 4`. Operasi tulis hanya mengunci *stripe* yang sesuai dengan hash key `(hash % locks.Length)`. Thread yang menulis ke hash berbeda dapat dieksekusi secara paralel.
   * **Read Path**: `TryGetValue` bersifat 100% *Lock-Free*. Node-node dalam bucket diimplementasikan sebagai linked-list dengan pointer `volatile`. Ketika pembaca membaca linked-list saat thread lain sedang melakukan write/insert, read operation dipastikan membaca state lama atau state baru secara atomik tanpa tersangkut lock.

2. **`ConcurrentQueue<T>` (Segmented Lock-Free FIFO)**:
   * Berhenti menggunakan single linked-list per-node karena alokasi GC yang terlalu intensif.
   * Diimplementasikan sebagai linked-list dari **Segments** (array berukuran 32 item yang melipatgandakan ukuran hingga cap tertentu).
   * Operasi `Enqueue` dan `TryDequeue` menggunakan instruksi CPU atomic: `Interlocked.CompareExchange` (pada level assembly x86/x64: `LOCK CMPXCHG`). Head dan Tail pointer digeser tanpa pernah menggunakan lock kernel.

3. **`ConcurrentBag<T>` (Work-Stealing Architecture)**:
   * Mengalokasikan sub-queue per-thread menggunakan `ThreadLocal`.
   * Saat Thread A memanggil `Add()`, item diletakkan di queue lokal milik Thread A.
   * Saat Thread A memanggil `TryTake()`, item diambil dari queue lokalnya sendiri (LIFO - tanpa locking).
   * Jika queue lokal Thread A kosong, Thread A akan mencoba "mencuri" (*steal*) item dari queue lokal milik Thread B menggunakan strategi FIFO dengan fine-grained lock per-queue.

#### Alokasi Memori / Resource
* **Overhead Struktural**: `ConcurrentDictionary` membutuhkan memori awal yang jauh lebih besar dibanding `Dictionary` biasa karena overhead alokasi array `tables` internal, bucket array, dan array objek lock ($N$ buah `object` instances yang dialokasikan di Heap).
* **False Sharing**: Desain internal concurrent collections menerapkan *padding* (sering kali 64 bytes, setara ukuran CPU Cache Line) pada index pointer untuk mencegah fenomena cache-line bouncing antar core CPU.

#### Trade-offs
* **Snapshot Isolation vs Throughput**: Method seperti `Count`, `IsEmpty`, atau enumerasi (`foreach`) pada concurrent collections bukan operasi $O(1)$ yang murah. Method `Count` pada `ConcurrentDictionary` harus mengakuisisi **seluruh** lock stripes yang ada, memblokir seluruh operasi write, mengambil snapshot, lalu melepaskan semua lock. Jangan pernah mengecek `collection.Count > 0` di loop kritis.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Pre-size Concurrency Level**: Selalu berikan konfigurasi `concurrencyLevel` dan `capacity` pada konstruktor `ConcurrentDictionary` jika estimasi beban kerja diketahui. Ini mencegah alokasi ulang array lock stripes dan resize bucket table.
* **Gunakan ValueFactory yang Idempotent**: Delegate pada `GetOrAdd` atau `AddOrUpdate` dieksekusi **di luar lock** (pada beberapa implementasi) untuk mencegah deadlocks. Ini berarti delegasi Anda bisa dieksekusi lebih dari satu kali jika terjadi race condition, meski hanya ada satu hasil yang disimpan.

```csharp
// BENAR: Factory delegate bersifat idempotent (murni komputasi atau pure allocation)
var val = dict.GetOrAdd(key, k => new HeavyObject(k));

// Lebih baik lagi: Gunakan Lazy<T> jika inisialisasi object memicu side-effect (I/O, database)
var val2 = dict.GetOrAdd(key, k => new Lazy<HeavyObject>(() => new HeavyObject(k))).Value;
```

#### Don'ts
* **Check-Then-Act Anti-Pattern**: Menjalankan pengecekan terpisah sebelum mutasi akan merusak thread-safety:
  ```csharp
  // SALAH FATAL: Race condition terjadi antara ContainsKey dan Indexer setter
  if (!concurrentDict.ContainsKey(key)) {
      concurrentDict[key] = value; 
  }

  // BENAR: Gunakan atomic TryAdd
  concurrentDict.TryAdd(key, value);
  ```
* **Menyimpan Mutable Reference Types**: Menyimpan class dengan property yang dapat dimodifikasi (`item.Status = "Updated"`) di dalam concurrent collection tidak membuat object tersebut otomatis thread-safe. Collection hanya menjamin referensi ke object tersebut yang thread-safe. Gunakan `immutable record` atau thread-safe models.
* **Menggunakan `ConcurrentBag` untuk Operasi Antrean Standar**: `ConcurrentBag` sangat lambat jika thread yang melakukan `Add` berbeda dengan thread yang melakukan `Take` (karena terjadi kontensi *work-stealing* terus-menerus). Gunakan `ConcurrentQueue` untuk skenario Producer-Consumer standar.

#### Edge Cases
* **Iterasi Enumerator**: Enumerasi melalui `GetEnumerator()` pada `ConcurrentQueue` atau `ConcurrentDictionary` merepresentasikan **momentary snapshot** dari data pada saat enumerator dibuat. Iterasi tidak akan melempar `InvalidOperationException: Collection was modified`, tetapi tidak dijamin mencerminkan data yang baru saja dimasukkan selama loop berjalan.

1. **Analisis Memory Leaks pada Thread-Local ConcurrentBag**:
   Buatlah sebuah prototype di mana Anda menggunakan `ConcurrentBag<T>` dalam konteks eksekusi banyak short-lived threads (misalnya membuat instance `new Thread(...)` secara manual ribuan kali, bukan thread-pool). Amati melalui Visual Studio Diagnostic Tools / DotMemory: Apa yang terjadi pada alokasi memori internal sub-queue `ConcurrentBag` ketika thread mati? Mengapa hal ini tidak terjadi pada `ConcurrentQueue`?
2. **Implementasi Token Bucket Rate Limiter**:
   Rancang algoritma Rate Limiter in-memory yang thread-safe menggunakan `ConcurrentDictionary<string, (long LastTimestamp, int Tokens)>` dengan operasi update token atomik tanpa menggunakan satupun keyword `lock`. Manfaatkan `Interlocked.CompareExchange` atau `AddOrUpdate` dengan skema CAS (*Compare-And-Swap*).
