### 1. Konsep & Arsitektur Mendalam

Sistem keamanan pada ASP.NET Core memisahkan dua konsep fundamental: **Autentikasi** (*Authentication/AuthN* - "Siapa Anda?") dan **Otorisasi** (*Authorization/AuthZ* - "Apa yang boleh Anda lakukan?").

```
Incoming HTTP Request
        │
        ▼
┌───────────────────────────────┐
│   AuthenticationMiddleware    │ ◄── Mengeksekusi IAuthenticationHandler
└───────────────┬───────────────┘     Membaca Bearer Token / Cookies
                │                     Menghasilkan ClaimsPrincipal ──► HttpContext.User
                ▼
┌───────────────────────────────┐
│   AuthorizationMiddleware     │ ◄── Mengevaluasi IAuthorizationPolicyProvider
└───────────────┬───────────────┘     Menjalankan IAuthorizationHandler
                │                     Memvalidasi Requirements terhadap HttpContext.User
                ▼
      Endpoint / Controller
```

#### Identitas Berbasis Klaim (Claim-Based Identity)
ASP.NET Core merepresentasikan entitas pemanggil menggunakan model hierarki:
- **`Claim`**: Pasangan *key-value* formal yang menyatakan fakta tentang subjek (misal: `sub: 12345`, `role: Admin`, `department: IT`).
- **`ClaimsIdentity`**: Paspor digital yang berisi kumpulan `Claim` serta informasi mengenai algoritma autentikasi yang digunakan.
- **`ClaimsPrincipal`**: Pemegang satu atau lebih `ClaimsIdentity`. Di runtime, objek ini diikat pada `HttpContext.User`.

#### JSON Web Token (JWT) & OAuth 2.0 / OpenID Connect (OIDC)
- **OAuth 2.0**: Protokol delegasi wewenang (*authorization framework*). Pengguna memberikan izin kepada aplikasi pihak ketiga untuk mengakses sumber daya atas nama mereka via *Access Token* tanpa membagikan kredensial asli.
- **OpenID Connect (OIDC)**: Lapisan identitas (*identity layer*) di atas OAuth 2.0 yang memperkenalkan *ID Token* untuk membuktikan identitas pengguna.
- **JWT (RFC 7519)**: Format token ringkas, *self-contained*, dan aman secara kriptografis yang terdiri atas Header, Payload, dan Signature (`Base64UrlEncoded(Header).Base64UrlEncoded(Payload).Signature`). Karena bersifat *self-contained*, API backend dapat memvalidasi identitas pengguna secara terdistribusi tanpa perlu melakukan *database lookup* pada setiap *request*.

#### Evolusi: Dari RBAC Menuju Policy-Based Authorization
Model lama berbasis *Role-Based Access Control* (RBAC) seperti `[Authorize(Roles = "Admin")]` bersifat kaku dan sering mengarah ke anti-pattern *role explosion*. ASP.NET Core memecahkan ini dengan **Policy-Based Authorization**, yang memecah logika akses menjadi:
1. **Policy**: Kumpulan dari satu atau lebih *requirements*.
2. **Requirement (`IAuthorizationRequirement`)**: Definisi data/aturan abstrak yang harus dipenuhi.
3. **Handler (`AuthorizationHandler<T>`)**: Unit logika yang mengevaluasi konteks (`ClaimsPrincipal`, resource target) untuk menentukan apakah *requirement* terpenuhi (`context.Succeed()`).

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan konfigurasi modern berbasis ASP.NET Core (.NET 8/9 Minimal API) menggunakan JWT Bearer dengan validasi ketat, serta pembuatan custom policy requirement untuk otorisasi berbasis hak akses dinamis (*Permission/Scope Requirement*).

#### Program.cs
```csharp
using System.Security.Claims;
using System.Text;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.AspNetCore.Authorization;
using Microsoft.IdentityModel.Tokens;

var builder = WebApplication.CreateBuilder(args);

// 1. Konfigurasi Autentikasi JWT
var jwtIssuer = builder.Configuration["Jwt:Issuer"] ?? "https://auth.internal.corp";
var jwtAudience = builder.Configuration["Jwt:Audience"] ?? "api://gateway";
var jwtSigningKey = builder.Configuration["Jwt:Key"] ?? "kunci-rahasia-minimum-32-karakter-harus-panjang!";

builder.Services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{
    // Hindari pemetaan legacy ClaimTypes (misal: "sub" berubah menjadi ClaimTypes.NameIdentifier)
    options.MapInboundClaims = false;
    
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidIssuer = jwtIssuer,
        ValidateAudience = true,
        ValidAudience = jwtAudience,
        ValidateIssuerSigningKey = true,
        IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwtSigningKey)),
        ValidateLifetime = true,
        // Matikan default 5 menit clock skew untuk API dengan kepatuhan waktu presisi
        ClockSkew = TimeSpan.Zero,
        RoleClaimType = "roles",
        NameClaimType = "sub"
    };
});

// 2. Registrasi Custom Authorization Requirement & Handler
builder.Services.AddSingleton<IAuthorizationHandler, MinimumTenureHandler>();

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("RequireEngineeringStaff", policy =>
    {
        policy.RequireAuthenticatedUser();
        policy.RequireClaim("department", "Engineering");
        policy.Requirements.Add(new MinimumTenureRequirement(monthsRequired: 6));
    });

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

// 3. Endpoint Terproteksi
app.MapGet("/api/secure/infra-config", (ClaimsPrincipal user) =>
{
    var subject = user.FindFirst("sub")?.Value;
    return Results.Ok(new
    {
        Message = "Akses konfigurasi infrastruktur diberikan.",
        RequestedBy = subject
    });
})
.RequireAuthorization("RequireEngineeringStaff");

app.Run();

// --- Domain Authorization Models & Handlers ---

public record MinimumTenureRequirement(int MonthsRequired) : IAuthorizationRequirement;

public class MinimumTenureHandler : AuthorizationHandler<MinimumTenureRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, 
        MinimumTenureRequirement requirement)
    {
        // Cari klaim 'employment_date' format YYYY-MM-DD
        var employmentDateClaim = context.User.FindFirst("employment_date");
        if (employmentDateClaim is null)
        {
            return Task.CompletedTask; // Gagal implisit: Jangan panggil context.Succeed()
        }

        if (DateTime.TryParse(employmentDateClaim.Value, out var employmentDate))
        {
            var calculatedMonths = ((DateTime.UtcNow.Year - employmentDate.Year) * 12) 
                                   + DateTime.UtcNow.Month - employmentDate.Month;

            if (calculatedMonths >= requirement.MonthsRequired)
            {
                context.Succeed(requirement);
            }
        }

        return Task.CompletedTask;
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Pipeline
1. **Header Parsing**: `AuthenticationMiddleware` membaca header `Authorization: Bearer <token>`.
2. **Eksekusi Token Handler**: Di .NET 8+, default *token handler* telah beralih dari `JwtSecurityTokenHandler` ke **`JsonWebTokenHandler`**. Token di-parse langsung menggunakan struktur low-allocation berbasis `ReadOnlySpan<byte>`.
3. **Kriptografi & Validasi**:
   - Signature token divalidasi menggunakan implementasi kriptografi native OS (Windows CNG atau Linux OpenSSL via binding `System.Security.Cryptography`).
   - Validasi `nbf` (*not before*) dan `exp` (*expiration*) dievaluasi terhadap `DateTime.UtcNow` ditambah parameter `ClockSkew`.
4. **Pemberian Context**: Jika valid, seluruh payload dikonversi menjadi kumpulan instance `Claim`, dibungkus ke dalam `ClaimsIdentity` (dengan parameter `AuthenticationType = "Bearer"`), lalu disematkan ke `HttpContext.User`.
5. **Evaluasi Kebijakan**: Saat eksekusi mencapai `AuthorizationMiddleware`, middleware memanggil `IAuthorizationService.AuthorizeAsync`. Jika salah satu requirement gagal (tidak ada handler yang memanggil `context.Succeed()`), ASP.NET Core membatalkan pipeline dan mengembalikan `403 Forbidden` (jika user terautentikasi) atau `401 Unauthorized` (jika user anonim).

#### Alokasi Memori & Resource
- `JsonWebTokenHandler` menghindari alokasi memori berlebih dengan tidak langsung membuat representasi JSON Object Tree untuk seluruh payload. Pembacaan header dan claims penting dilakukan dengan pemindaian biner string terindeks.
- Namun, pembuatan `ClaimsPrincipal`, `ClaimsIdentity`, dan array `Claim[]` pada setiap HTTP request tetap membebani *Garbage Collector (GC)* pada throughput tinggi. Oleh karena itu, jangan memasukkan terlalu banyak data arbitrary/metadata ke dalam JWT payload.

#### Trade-offs Desain
| Pendekatan | Kelebihan | Kekurangan |
| :--- | :--- | :--- |
| **Stateless JWT** | Sangat scalable, zero-latency (tidak butuh I/O database untuk verifikasi). | Pencabutan izin (*instant revocation*) mustahil dilakukan tanpa distributed blacklist/cache. |
| **Reference Token (Opaque)** | Dapat dicabut kapan saja (*real-time revocation*), payload token sangat kecil. | Membutuhkan I/O round-trip (Redis/Database atau token introspection endpoint) di setiap request. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Asymmetric Keys (RS256/ES256) untuk OAuth/SSO**: Gunakan *private key* hanya di Identity Provider (IdP) untuk *signing*, dan distribusikan *public key* (via JWKS endpoint) ke seluruh resource API untuk *verification*.
- **Set `MapInboundClaims = false`**: Matikan pemetaan default runtime .NET. Secara default, .NET memetakan `sub` menjadi `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier` yang menyebabkan overhead alokasi string dan ketidaksesuaian schema JWT standar modern.
- **Set `ClockSkew = TimeSpan.Zero`**: Default clock skew ASP.NET Core adalah 5 menit. Artinya token yang kedaluwarsa tetap valid hingga 5 menit ke depan jika parameter ini tidak di-override secara eksplisit.

#### Don'ts
- **Menyimpan Secret/PII di dalam Payload**: JWT hanya di-*encode* menggunakan Base64Url, **bukan dienkripsi**. Siapa pun yang memiliki akses ke string token dapat membaca isi klaim tanpa perlu mengetahui *signing key*.
- **Menaruh Authorization Logic di Controller Action Body**: Jangan lakukan pemeriksaan manual berulang seperti `if (!User.IsInRole("Admin")) return Forbid();`. Gunakan *Custom Policies* dan *Requirements* agar logika otorisasi dapat diuji secara terisolasi (*unit-testable*) dan reusable.
- **Menggunakan Symmetric Key yang Lemah**: Kunci simetris (HMAC-SHA256) di bawah 256-bit (32 karakter) rentan terhadap serangan brute-force secara *offline*.

#### Edge Cases
- **Token Invalidation saat Pergantian Role/Permission**: Jika role user diubah di database, JWT lama yang masih aktif akan tetap valid hingga masa `exp` tercapai. Gunakan short-lived access tokens (5–15 menit) digabungkan dengan mekanisme *refresh token rotation*, atau gunakan *SecurityStamp* validation.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Resource-Based Authorization**:
   Buat sebuah endpoint dokumen `DELETE /api/documents/{id}` menggunakan `IAuthorizationService.AuthorizeAsync(User, document, "MustBeDocumentOwnerPolicy")`. Buat handler turunan `AuthorizationHandler<TRequirement, TResource>` yang memverifikasi apakah klaim `sub` pada token cocok dengan properti `OwnerId` dari objek dokumen yang di-query dari database.
2. **Integrasi Key Rotation dengan JWKS Mock**:
   Ubah konfigurasi JWT Bearer Anda agar tidak menggunakan `IssuerSigningKey` statis lokal. Konfigurasikan opsi `ConfigurationManager<OpenIdConnectConfiguration>` untuk membaca metadata dari endpoint mock `.well-known/openid-configuration` yang mengekspos *JSON Web Key Set* (JWKS). Uji coba pergantian key tanpa me-restart aplikasi API Anda.
