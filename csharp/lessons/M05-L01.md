## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Pada era awal .NET Framework, eksekusi paralel dan konkuren dikelola langsung menggunakan kelas `System.Threading.Thread`. Model ini merepresentasikan pemetaan 1:1 antara thread terkelola (*managed thread*) dengan OS Thread (kernel thread). Pendekatan ini memiliki *cost* yang sangat mahal:
- **Alokasi Memori Stack:** Setiap OS thread secara *default* memesan memori sebesar 1 MB untuk stack-nya (pada arsitektur Windows x64).
- **Context Switching Overhead:** Pergantian konteks thread pada tingkat kernel membutuhkan penyimpanan dan pemulihan register CPU, penggantian *page table*, dan invalidasi cache CPU (L1/L2/L3 cache misses).

```
[ Pendekatan Klasik: Thread ]
Caller Thread ---> Blocked / Waiting --------------------------> Resume
                      \                                         /
                       -> [Dedicated OS Thread (1MB Stack)] ---/

[ Pendekatan TAP: Asynchronous Non-Blocking ]
Caller Thread ---> Dispatches I/O -> Thread Bebas ke ThreadPool
                     | (Tidak ada thread menunggu)
                     | [Hardware / OS Kernel IOCP / epoll]
                     v
Completion ------> ThreadPool Worker mengambil Continuation via State Machine
```

Untuk mengatasi keterbatasan skalabilitas ini, arsitektur .NET berevolusi melalui beberapa fase:
1. **APM (Asynchronous Programming Model):** Pola `BeginInvoke`/`EndInvoke` dan antarmuka `IAsyncResult`.
2. **EAP (Event-based Asynchronous Pattern):** Pola `MethodAsync` dengan event `MethodCompleted`.
3. **TAP (Task-based Asynchronous Pattern):** Diperkenalkan pada .NET 4.0 dan disempurnakan dengan *keyword* `async`/`await` pada C# 5.0.

TAP memisahkan konsep komputasi konkuren dari thread fisik menggunakan abstraksi **`Task`** dan **`Task<TResult>`**. `Task` merepresentasikan sebuah *promise* atau *future*—sebuah operasi yang sedang berjalan atau akan selesai di masa depan.

Perbedaan fundamental:
- **CPU-Bound Work:** TAP mendelegasikan eksekusi ke antrean terkelola (*managed work-stealing queue*) di dalam **CLR ThreadPool**, mengeliminasi biaya alokasi OS thread baru secara berulang.
- **I/O-Bound Work:** TAP tidak menahan thread sama sekali. Operasi I/O (network, disk, database) mendaftarkan callback ke tingkat kernel OS melalui **I/O Completion Ports (IOCP)** di Windows atau **epoll/kqueue** di Linux/macOS. Thread pemanggil langsung dibebaskan kembali ke ThreadPool. Ketika operasi I/O tuntas pada level hardware, interrupt kernel akan memicu ThreadPool untuk menjadwalkan kelanjutan (*continuation*) task tersebut.

### 2. Implementasi & Contoh Kasus Nyata

Kode di bawah ini membandingkan pendekatan raw OS `Thread` vs pendekatan modern TAP untuk skenario paralelisme CPU dan non-blocking I/O.

```csharp
using System.Diagnostics;

namespace ConcurrencyDeepDive;

public class Program
{
    public static async Task Main(string[] args)
    {
        Console.WriteLine($"Main Thread ID: {Environment.CurrentManagedThreadId}");
        
        // 1. Eksekusi Thread Manual (Pola Usang / Anti-Pattern untuk Operasi I/O)
        ExecuteWithDedicatedThread();

        // 2. Eksekusi TAP (Modern, Non-blocking, Composable)
        using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
        try
        {
            var result = await ProcessDataPipelineAsync("https://api.github.com", cts.Token);
            Console.WriteLine($"Pipeline Result: {result}");
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine("Pipeline dibatalkan karena timeout.");
        }
    }

    // Pendekatan Klasik: Alokasi dedicated thread, synchronous blocking
    private static void ExecuteWithDedicatedThread()
    {
        // Masalah: Mengalokasikan 1MB kernel stack dan thread pool tidak bisa me-reuse resource ini
        var thread = new Thread(() =>
        {
            Console.WriteLine($"Dedicated Thread ID: {Environment.CurrentManagedThreadId}");
            // Simulasi blocking call (ThreadState = WaitSleepJoin)
            // OS Thread tertahan secara pasif tanpa melakukan komputasi nyata
            Thread.Sleep(500); 
        })
        {
            IsBackground = true,
            Name = "ManualWorkerThread",
            Priority = ThreadPriority.Normal
        };

        thread.Start();
        thread.Join(); // Blocking thread pemanggil sampai worker selesai
    }

    // Pendekatan Modern TAP: I/O non-blocking + offloading CPU-bound secara terkontrol
    private static async Task<int> ProcessDataPipelineAsync(string url, CancellationToken cancellationToken)
    {
        using var httpClient = new HttpClient();
        httpClient.DefaultRequestHeaders.UserAgent.ParseAdd("DotNet-DeepDive-Client");

        Console.WriteLine($"[I/O Start] Thread ID: {Environment.CurrentManagedThreadId}");

        // TRUE ASYNC (I/O-Bound): Tidak ada thread yang diblokir saat menunggu respons network
        var response = await httpClient.GetStringAsync(url, cancellationToken);

        Console.WriteLine($"[I/O Resume] Thread ID: {Environment.CurrentManagedThreadId}");

        // TASK DELEGATION (CPU-Bound): Offload transformasi data berat ke ThreadPool
        int computedMetric = await Task.Run(() =>
        {
            Console.WriteLine($"[CPU-Bound] ThreadPool Thread ID: {Environment.CurrentManagedThreadId}");
            
            // Simulasi komputasi intensif (e.g. Parsing, Hashing, Image Processing)
            int checksum = 0;
            for (int i = 0; i < response.Length; i++)
            {
                cancellationToken.ThrowIfCancellationRequested();
                checksum ^= response[i];
            }
            return checksum;
        }, cancellationToken);

        return computedMetric;
    }
}
```

#### Komponen Kritis Kode:
- `Thread.Sleep` memblokir thread kernel, menahannya dari mengerjakan task lain.
- `GetStringAsync` mengembalikan kontrol langsung ke caller saat I/O request diserahkan ke socket OS. Thread asal bebas melayani request lain.
- `Task.Run` secara eksplisit memanfaatkan *Hill-Climbing algorithm* milik .NET ThreadPool untuk menjadwalkan pekerjaan CPU-bound tanpa membuat thread fisik baru.
- `CancellationToken` mengalir secara kooperatif, memungkinkan penghentian pipeline tanpa *thread aborting* yang destruktif.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Roslyn State Machine Generation
Ketika compiler Roslyn mendeteksi *keyword* `async`, ia merombak method tersebut menjadi struktur data berbasis **State Machine** yang mengimplementasikan antarmuka internal `IAsyncStateMachine`.

1. **Transformasi Kode:** Method dipecah menjadi beberapa *state* berbasis titik jeda (`await`).
2. **`MoveNext()` Execution:** Saat `await` dipanggil pada objek *awaitable* (misal `Task`), method `GetAwaiter()` dieksekusi. Jika task belum selesai (`IsCompleted == false`), sistem mendaftarkan *continuation callback* via `awaiter.UnsafeOnCompleted(Action)`.
3. **Yielding:** Eksekusi keluar dari method pemanggil, dan thread dikembalikan ke pool.
4. **Resumption:** Ketika sinyal penyelesaian tiba, ThreadPool menjadwalkan `MoveNext()` untuk dieksekusi kembali, memulihkan lokal variabel yang tersimpan di dalam struct/class state machine dan melompat ke *state* berikutnya.

#### Alokasi Memori / Resource
| Karakteristik | `System.Threading.Thread` | `Task` / TAP |
| :--- | :--- | :--- |
| **Alokasi Memori** | ~1 MB (Reserved Virtual Memory Stack) | ~72 - 144 bytes per objek `Task` di Managed Heap |
| **Kernel Handles** | Membuat OS Thread Handle baru | Menggunakan kembali handle yang sudah ada di ThreadPool |
| **Optimasi Zero-Alloc** | Mustahil | Menggunakan `ValueTask<T>` untuk operasi sinkron yang sering terjadi |
| **Context Switch** | Mahal (User Mode $\leftrightarrow$ Kernel Mode) | Ringan (Kooperatif di tingkat Managed Runtime) |

#### ThreadPool Mechanics & Work-Stealing Algorithm
ThreadPool .NET mengelola dua lapis antrean:
- **Global Queue:** Antrean *FIFO* untuk task yang dijadwalkan dari thread di luar ThreadPool (atau via `ThreadPool.QueueUserWorkItem`).
- **Local Work-Stealing Queue:** Setiap worker thread memiliki antrean lokal bertipe *deque* (double-ended queue). Worker thread memasukkan dan mengambil task miliknya dari *ujung depan (LIFO)* untuk meminimalkan *cache thrashing*. Jika antrean lokal kosong, worker thread akan "mencuri" (*steal*) task dari *ujung belakang (FIFO)* antrean thread lain.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan TAP untuk Operasi Asinkron & I/O:** Selalu gunakan `Task`/`ValueTask` untuk network, file, dan database operations.
- **Gunakan `ConfigureAwait(false)` pada Non-UI Library:** Mencegah overhead pemulihan `SynchronizationContext` yang tidak dibutuhkan pada library core atau backend API.
- **Selalu Meneruskan `CancellationToken`:** Menjamin *resource cancellation* berjalan secara konsisten dan responsif sepanjang call-stack.
- **Gunakan `ValueTask<T>` pada Hot Path:** Jika sebuah method sering kali selesai secara sinkron (misal: mengambil data dari cache in-memory), gunakan `ValueTask<T>` untuk menghindari alokasi heap `Task<T>`.

#### Don'ts
- **Hindari Sync-over-Async (`.Result` atau `.Wait()`):** 
  ```csharp
  // FATAL: Menyebabkan ThreadPool Starvation dan Deadlock (pada UI Context / ASP.NET klasik)
  var data = GetDataAsync().Result; 
  ```
- **Hindari `async void`:** Kecuali pada *event handlers* UI. Method `async void` tidak dapat di-*catch* oleh blok `try-catch` pemanggil dan exception yang tidak tertangani akan langsung meruntuhkan (*crash*) proses aplikasi.
- **Jangan Menggunakan Raw `Thread` Tanpa Alasan Khusus:** Hindari `new Thread().Start()` untuk pekerjaan latar belakang biasa.

#### Edge Cases
- **Kapan Raw `Thread` Masih Diperlukan?**
  Gunakan raw `Thread` hanya jika Anda membutuhkan kontrol tingkat rendah seperti:
  1. Thread dengan prioritas non-standar (`ThreadPriority.Highest`).
  2. Thread yang harus berjalan di mode Single-Threaded Apartment (`ApartmentState.STA`) untuk berinteraksi dengan komponen legacy COM.
  3. *Long-running operation* yang berjalan terus-menerus selama masa hidup aplikasi dan akan memonopoli ThreadPool worker thread jika dijalankan via TAP (alternatif: `Task.Factory.StartNew` dengan opsi `TaskCreationOptions.LongRunning`).

### 5. Tantangan Eksplorasi Mandiri

1. **Dekomposisi State Machine:**
   Kompilasi sebuah method `async Task<int> FetchDataAsync()` sederhana. Buka assembly hasilnya menggunakan alat decompiler seperti **ILSpy** atau **sharplab.io**. Identifikasi struct `IAsyncStateMachine`, perhatikan implementasi field `state`, dan amati bagaimana lokal variabel dinaikkan (*lifted*) ke field struct.

2. **Simulasi ThreadPool Starvation:**
   Buat console app sederhana yang mengonfigurasi batas minimal dan maksimal thread pool ke angka rendah: `ThreadPool.SetMinThreads(2, 2); ThreadPool.SetMaxThreads(4, 4);`.
   Jalankan 20 `Task.Run()` yang di dalamnya memanggil method async dengan pola anti-pattern: `.Wait()` atau `.Result`. Amati bagaimana throughput aplikasi terhenti total dan bandingkan perilakunya saat seluruh method diubah menjadi full `await`.
