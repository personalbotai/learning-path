### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa perangkat lunak modern, skema basis data relasional harus berevolusi secara deterministik seiring berjalannya siklus hidup aplikasi. Entity Framework Core (EF Core) menyelesaikan masalah sinkronisasi antara *domain model* (C# POCO classes) dan skema database relasional melalui mekanisme **Migrations**.

```
[ Domain Entities & DbContext ] 
              │
              ▼  (Kompilasi & Refleksi Skema)
   [ Target IModel Graph ] 
              │
              ├─────── [ ModelSnapshot.cs ] (Skema Sebelumnya)
              ▼
   [ Model Differ Engine ] ────────► Menghasilkan List<MigrationOperation>
              │
              ▼
   [ xxx_MigrationName.cs ] (Up() & Down()) + Update ModelSnapshot
              │
              ▼ (Translasi ke SQL Dialect via Provider)
  [ Transaksi DDL + INSERT __EFMigrationsHistory ] ──► [ RDBMS Engine ]
```

Arsitektur EF Core Migrations bertumpu pada tiga pilar utama:

1. **`ModelSnapshot` (`IModel` Metadata Graph):**
   Setiap kali migrasi baru dibuat, EF Core memperbarui berkas `*ModelSnapshot.cs`. Berkas ini berisi representasi deklaratif C# dari metadata skema database saat migrasi terakhir dibuat. EF Core **tidak pernah** melakukan *reverse engineering* ke database fisik saat membuat migrasi baru; melainkan, mesin *Model Differ* membandingkan struktur *current compile-time model* (yang dikonfigurasi via atribut dan `OnModelCreating`) langsung terhadap `ModelSnapshot`.

2. **Migration Operations (`MigrationBuilder`):**
   Selisih (*diff*) antara snapshot dan model saat ini diubah menjadi serangkaian operasi abstrak tingkat tinggi (`MigrationOperation`) seperti `CreateTableOperation`, `AddColumnOperation`, atau `AlterColumnOperation`. Operasi ini didefinisikan secara simetris dalam metode `Up()` (aplikasi perubahan) dan `Down()` (pembatalan perubahan/*rollback*).

3. **Database Metadata Storage (`__EFMigrationsHistory`):**
   Untuk mengetahui status skema di tingkat fisik, RDBMS menyimpan tabel sistem `__EFMigrationsHistory` (standarnya berisi kolom `MigrationId` dan `ProductVersion`). Ketika instruksi migrasi dijalankan, EF Core membandingkan daftar riwayat di tabel ini dengan rakitan assembly migrasi untuk mengeksekusi migrasi yang belum terpasang secara transaksional.

#### Strategi Seeding Data
EF Core mendukung tiga paradigma *data seeding*:
*   **Model Seed Data (`HasData`):** Data dikaitkan langsung ke konfigurasi entitas dan dilacak oleh *Model Differ*. Cocok untuk data statis/lookup (master role, status). Nilai kunci (*primary key*) **wajib deterministik** dan eksplisit.
*   **Custom Migration Operations (`migrationBuilder.InsertData` / `.Sql`):** Disisipkan langsung ke berkas migrasi tertentu untuk migrasi data historis atau transformasi skema yang membutuhkan pemindahan data (*data-motion*).
*   **Runtime Initialization / Custom Seeder:** Dijalankan secara independen melalui *worker* atau modul `Program.cs` saat bootstrap aplikasi, ideal untuk data dinamis, mock data lingkungan development, atau payload berukuran besar.

### 2. Implementasi & Contoh Kasus Nyata

Contoh kasus berikut mengimplementasikan evolusi skema modul perbankan sederhana: pembuatan entitas `Account`, relasi audit `Transaction`, konfigurasi tipe data presisi, implementasi *idempotent seed data*, serta penanganan *data-motion migration*.

#### Definisi Entitas & DbContext Configuration

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace CoreBanking.Infrastructure;

public enum AccountStatus
{
    Inactive = 0,
    Active = 1,
    Suspended = 2
}

public sealed class Account
{
    public Guid Id { get; set; }
    public string AccountNumber { get; set; } = string.Empty;
    public decimal Balance { get; set; }
    public AccountStatus Status { get; set; }
    public DateTime CreatedAtUtc { get; set; }
    
    // Concurrency Token untuk mencegah double-spending/race condition
    public byte[] RowVersion { get; set; } = null!;
    
    public ICollection<TransactionRecord> Transactions { get; set; } = new List<TransactionRecord>();
}

public sealed class TransactionRecord
{
    public long Id { get; set; }
    public Guid AccountId { get; set; }
    public Account Account { get; set; } = null!;
    public decimal Amount { get; set; }
    public DateTime TimestampUtc { get; set; }
}

public sealed class BankingDbContext : DbContext
{
    public BankingDbContext(DbContextOptions<BankingDbContext> options) : base(options) { }

    public DbSet<Account> Accounts => Set<Account>();
    public DbSet<TransactionRecord> Transactions => Set<TransactionRecord>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfiguration(new AccountConfiguration());
        modelBuilder.ApplyConfiguration(new TransactionConfiguration());
    }
}

public sealed class AccountConfiguration : IEntityTypeConfiguration<Account>
{
    public void Configure(EntityTypeBuilder<Account> builder)
    {
        builder.ToTable("Accounts", "banking");

        builder.HasKey(a => a.Id);

        builder.Property(a => a.AccountNumber)
            .IsRequired()
            .HasMaxLength(32)
            .IsUnicode(false);

        builder.HasIndex(a => a.AccountNumber)
            .IsUnique();

        builder.Property(a => a.Balance)
            .HasPrecision(18, 4);

        builder.Property(a => a.RowVersion)
            .IsRowVersion();

        // Data Seeding via HasData (Kunci PK & DateTime HARUS Statis/Deterministik)
        builder.HasData(
            new Account
            {
                Id = Guid.Parse("a0000000-0000-0000-0000-000000000001"),
                AccountNumber = "SYS-SETTLEMENT-001",
                Balance = 1_000_000_000.0000m,
                Status = AccountStatus.Active,
                CreatedAtUtc = new DateTime(2024, 1, 1, 0, 0, 0, DateTimeKind.Utc)
            }
        );
    }
}

public sealed class TransactionConfiguration : IEntityTypeConfiguration<TransactionRecord>
{
    public void Configure(EntityTypeBuilder<TransactionRecord> builder)
    {
        builder.ToTable("Transactions", "banking");

        builder.HasKey(t => t.Id);

        builder.Property(t => t.Amount)
            .HasPrecision(18, 4);

        builder.HasOne(t => t.Account)
            .WithMany(a => a.Transactions)
            .HasForeignKey(t => t.AccountId)
            .OnDelete(DeleteBehavior.Restrict);
    }
}
```

#### Custom Migration: Data Motion & Schema Mutation

Skenario: Kolom `AccountNumber` awalnya nullable, kemudian diubah menjadi `NOT NULL` dengan *business rule* bahwa data lama yang kosong harus diisi kode akun transisi otomatis sebelum batasan non-null diterapkan.

```csharp
using Microsoft.EntityFrameworkCore.Migrations;

namespace CoreBanking.Infrastructure.Migrations;

public partial class EnforceAccountNumberNotNull : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        // 1. Data-Motion: Update record yang melanggar integritas data terlebih dahulu via RAW SQL
        migrationBuilder.Sql(
            @"UPDATE banking.""Accounts"" 
              SET ""AccountNumber"" = 'MIGRATED-' || SUBSTRING(""Id""::text, 1, 8) 
              WHERE ""AccountNumber"" IS NULL OR ""AccountNumber"" = '';",
            suppressTransaction: false
        );

        // 2. Skema Mutasi: Terapkan constraint NOT NULL setelah data bersih
        migrationBuilder.AlterColumn<string>(
            name: "AccountNumber",
            schema: "banking",
            table: "Accounts",
            type: "character varying(32)",
            maxLength: 32,
            nullable: false,
            oldClrType: typeof(string),
            oldType: "character varying(32)",
            oldMaxLength: 32,
            oldNullable: true);
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AlterColumn<string>(
            name: "AccountNumber",
            schema: "banking",
            table: "Accounts",
            type: "character varying(32)",
            maxLength: 32,
            nullable: true,
            oldClrType: typeof(string),
            oldType: "character varying(32)",
            oldMaxLength: 32);
    }
}
```

#### CLI Operations & Script Generation (Terminal)

```bash
# 1. Menambahkan migrasi baru
dotnet ef migrations add EnforceAccountNumberNotNull -o Infrastructure/Migrations

# 2. Menghasilkan skrip SQL Idempotent untuk pipeline CI/CD (Production Ready)
dotnet ef migrations script --idempotent -o scripts/deploy-migration.sql

# 3. Menerapkan migrasi ke database lokal (Dev Mode Only)
dotnet ef database update
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Model Comparison Pipeline:**
   Saat menjalankan `dotnet ef migrations add`, EF Core membuat instance dari `DbContext` (memanfaatkan `IDesignTimeDbContextFactory` jika tersedia). Mesin `IMigrationsModelDiffer` mengiterasi setiap entitas, relasi, indeks, dan anotasi di *Target Model* dan membandingkannya secara struktural dengan model di `ModelSnapshot`. Hasil perbandingannya adalah pohon perubahan (*directed graph*) yang disortir secara topologis untuk menghormati batasan *Foreign Key*.
2. **Translasi Dialect Provider:**
   Objek `MigrationOperation` diteruskan ke `IMigrationsSqlGenerator` yang diimplementasikan spesifik oleh provider database (misal: `NpgsqlMigrationsSqlGenerator` atau `SqlServerMigrationsSqlGenerator`). Mesin ini memetakan operasi abstrak C# menjadi sintaks DDL RDBMS spesifik.
3. **Idempotency Guard via SQL Block:**
   Bila dihasilkan menggunakan argumen `--idempotent`, provider akan membungkus setiap operasi migrasi dalam blok logika kondisional RDBMS:
   ```sql
   IF NOT EXISTS (
       SELECT 1 FROM [__EFMigrationsHistory] 
       WHERE [MigrationId] = N'20240328100000_EnforceAccountNumberNotNull'
   )
   BEGIN
       -- Operasi DDL dieksekusi di sini
       INSERT INTO [__EFMigrationsHistory] ([MigrationId], [ProductVersion])
       VALUES (N'20240328100000_EnforceAccountNumberNotNull', N'8.0.0');
   END;
   ```

#### Alokasi Memori & Resource
*   **Compile-time Metadata Cost:** Snapshot model dapat berukuran ribuan baris kode C#. Model ini dikompilasi oleh compiler C# (Roslyn) ke dalam dynamic assembly saat tools migrations berjalan, mengonsumsi CPU dan memory overhead pada fase build lokal/CI.
*   **Connection Lifecycle:** Migrasi database secara default membungkus seluruh set batch DDL migrasi ke dalam **satu transaksi database fisik tunggal** (`TransactionScope` atau manual `BeginTransaction()`), mengunci skema (*exclusive DDL lock* pada Postgres / SQL Server) sampai seluruh statement selesai atau di-rollback otomatis jika timbul *runtime exception*.

#### Trade-offs: `Database.Migrate()` vs SQL Bundles/Scripts
| Metrik | `Database.Migrate()` saat Startup | Skrip SQL Idempotent / Migration Bundles |
| :--- | :--- | :--- |
| **Eksekusi** | Otomatis di method `Program.cs` | Dijalankan terpisah di pipeline CD / DBA |
| **Keamanan Skalabilitas** | **Berbahaya** (terjadi race condition jika multi-replica pod k8s aktif bersamaan) | **Tinggi** (terisolasi dari instance runtime aplikasi) |
| **Hak Akses DB** | Akun DB aplikasi butuh hak akses `DDLAdmin` (Pelanggaran *Principle of Least Privilege*) | Akun aplikasi cukup `DML` (`SELECT, INSERT, UPDATE, DELETE`). Pipeline CD menggunakan kredensial `DDL`. |
| **Dukungan Zero-Downtime** | Sangat sulit diverifikasi otomatis | Mudah diinspeksi DBA sebelum deployment |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Deterministik Seed Data:** Selalu gunakan ID hardcoded (`Guid.Parse(...)` atau konstanta integer) dan tanggal statis pada `HasData()`.
- **Gunakan Migration Bundles (`dotnet ef migrations bundle`):** Hasilkan executable self-contained biner tunggal untuk diterapkan oleh pipeline deployment tanpa perlu .NET SDK di runner production.
- **Kombinasikan Data Motion & Schema Mutation:** Lakukan mutasi skema secara bertahap menggunakan pola *Expand and Contract*: buat kolom baru -> salin data -> hapus kolom lama pada migrasi terpisah.

#### Don'ts
- **JANGAN Menggunakan Nilai Non-Deterministik pada `HasData`:**
  ```csharp
  // FATAL: Setiap kali menjalankan 'dotnet ef migrations add', 
  // EF Core akan menganggap data berubah dan menghasilkan migration UpdateData palsu!
  builder.HasData(new Account { 
      Id = Guid.NewGuid(), 
      CreatedAtUtc = DateTime.UtcNow 
  });
  ```
- **JANGAN Memanggil `context.Database.Migrate()` di Lingkungan Multi-Instance:**
  Ketika 5 pod Kubernetes menyala bersamaan, migrasi skema yang sama akan dieksekusi secara paralel. Jika database engine tidak mendukung DDL transaksional atomik (seperti MySQL lama) atau terjadi *deadlock* pada tabel `__EFMigrationsHistory`, database akan mengalami *corruption* atau kegagalan startup.
- **JANGAN Mengubah Berkas Migrasi yang Sudah Terdistribusi ke Production:**
  Jika migrasi sudah terpasang di production, jangan mengubah metode `Up()` pada berkas tersebut secara manual. Buat migrasi baru untuk membetulkan kesalahan tersebut.

#### Edge Cases
*   **PostgreSQL Enums / Extensions:** Jika model memanfaatkan fitur database eksternal seperti `CREATE EXTENSION "uuid-ossp"` atau custom PostgreSQL Enum type, `HasData` dan Model Differ tidak dapat mendeteksi perubahan state internal enum secara otomatis. Eksekusi `migrationBuilder.Sql()` secara manual wajib dilakukan di awal file migrasi.
*   **Breaking Column Rename:** Secara default, jika properti di-rename di C#, EF Core dapat menafsirkannya sebagai `DropColumn` lalu `AddColumn`. **Hal ini menghapus seluruh data yang sudah ada di kolom tersebut.** Periksa selalu file migrasi yang dihasilkan: jika terdapat `migrationBuilder.DropColumn` untuk kolom yang seharusnya di-rename, gantilah dengan `migrationBuilder.RenameColumn`.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis File Migration Diff:**
   Buat entitas `Customer` dengan properti `FullName`. Buat migrasi pertama. Selanjutnya, ganti properti `FullName` menjadi dua properti: `FirstName` dan `LastName`. Jalankan `dotnet ef migrations add SplitCustomerName`. Amati file C# migrasi yang terbuat. Apakah EF Core menghapus `FullName` dan data di dalamnya? Modifikasi file migrasi tersebut menggunakan `migrationBuilder.Sql()` agar data nama lama terbagi (*split*) ke `FirstName` dan `LastName` sebelum kolom `FullName` dihapus!
2. **Simulasi Distributed Migration Lock:**
   Jalankan dua instance terminal secara paralel. Tulis *script* sederhana yang memanggil `context.Database.Migrate()` bersamaan dengan jeda waktu panjang di dalam *custom transaction* (`Thread.Sleep` di dalam raw SQL `pg_sleep` / `WAITFOR DELAY`). Analisis respons RDBMS terhadap *schema lock* dan amati apa yang terjadi pada entri `__EFMigrationsHistory`.
