## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum C# 2.0 memperkenalkan Generics, abstraksi data mengandalkan tipe universal `System.Object`. Pendekatan ini memiliki dua kelemahan mendasar:
1. **Kehilangan Type Safety**: Kompilator tidak dapat memvalidasi tipe data saat *compile-time*, memaksa pengecekan terjadi saat *runtime* melalui *explicit casting*, yang rentan memicu `InvalidCastException`.
2. **Penurunan Performa (Boxing & Unboxing)**: Tipe nilai (*value types*) yang dilewatkan ke parameter `object` harus dialokasikan ke *managed heap* (*boxing*) dan diekstraksi kembali (*unboxing*), memicu tekanan berlebih pada Garbage Collector (GC).

C# Generics memecahkan masalah ini dengan menyediakan mekanisme **Reified Generics** (Generik Terwujud). Berbeda dengan Java yang menggunakan *Type Erasure* (informasi tipe dihapus oleh kompilator dan diganti `Object` di *bytecode*), .NET CLR (*Common Language Runtime*) mempertahankan metadata generik secara penuh hingga *runtime*.

```
[C# Source Code] 
       │
       ▼ (Roslyn Compiler)
[IL Code with Generic Metadata]  --> `List<!T>`, `class Repo<T>`
       │
       ▼ (CLR JIT Compiler)
 ┌─────┴────────────────────────┐
 │                              │
 ▼ (T = Reference Type)         ▼ (T = Value Type)
[Shared Machine Code]          [Specialized Native Code per Type]
(Semua pointer berukuran sama)   (Ukuran struct unik: int vs double)
```

#### Peran Generic Constraints (`where`)
Secara default, parameter tipe `T` diperlakukan sebagai tipe yang tidak diketahui dengan kemampuan setara `System.Object`. Kompilator melarang pemanggilan metode spesifik, pembuatan instansiasi via operator `new`, atau operasi pembanding aritmatika pada `T`.

*Constraints* (Batasan) memberitahu kompilator mengenai kapabilitas minimum yang harus dimiliki oleh tipe argumen yang diinjeksikan. Menggunakan klausa `where T : class` secara eksplisit membatasi `T` hanya untuk **Reference Types** (kelas, *interface*, delegate, atau array), dan bukan *value types* (`struct`, `enum`, tipe primitif seperti `int`, `DateTime`).

Keuntungan penerapan `where T : class`:
- Kompilator mengizinkan perbandingan langsung dengan `null` (`if (entity == null)`).
- Menjamin *memory representation* dari `T` selalu berupa *managed pointer* / referensi (4 byte pada arsitektur x86, 8 byte pada x64), yang krusial untuk optimasi JIT compiler.
- Mencegah *value type* terbungkus secara tidak sengaja (*boxing*) dalam skenario arsitektur tertentu.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi arsitektur Enterprise Repository Pattern yang memanfaatkan Generic Interfaces, Generic Classes, dan *multiple constraints* bertingkat (`class`, antarmuka domain, dan `new()`).

```csharp
using System;
using System.Collections.Concurrent;
using System.Collections.Generic;
using System.Linq;

// 1. Domain Abstractions
public interface IIdentifiable<TId>
{
    TId Id { get; }
}

public interface IAuditable
{
    DateTime CreatedAtUtc { get; }
    void MarkUpdated();
}

// 2. Generic Contract dengan Multiple Constraints
public interface IRepository<TEntity, TId> 
    where TEntity : class, IIdentifiable<TId>, IAuditable, new()
    where TId : IEquatable<TId>
{
    TEntity? GetById(TId id);
    void Add(TEntity entity);
    void Remove(TId id);
    IEnumerable<TEntity> Find(Func<TEntity, bool> predicate);
}

// 3. Implementasi Generic In-Memory Repository yang Thread-Safe
public class InMemoryRepository<TEntity, TId> : IRepository<TEntity, TId>
    where TEntity : class, IIdentifiable<TId>, IAuditable, new()
    where TId : IEquatable<TId>
{
    private readonly ConcurrentDictionary<TId, TEntity> _storage = new();

    public TEntity? GetById(TId id)
    {
        // Guard clause untuk argumen bernilai null
        ArgumentNullException.ThrowIfNull(id);

        _storage.TryGetValue(id, out var entity);
        return entity;
    }

    public void Add(TEntity entity)
    {
        ArgumentNullException.ThrowIfNull(entity);

        // Constraints memastikan entity memiliki method MarkUpdated() dan interface IAuditable
        entity.MarkUpdated();

        if (!_storage.TryAdd(entity.Id, entity))
        {
            throw new InvalidOperationException($"Entitas dengan Id '{entity.Id}' sudah terdaftar.");
        }
    }

    public void Remove(TId id)
    {
        ArgumentNullException.ThrowIfNull(id);
        _storage.TryRemove(id, out _);
    }

    public IEnumerable<TEntity> Find(Func<TEntity, bool> predicate)
    {
        ArgumentNullException.ThrowIfNull(predicate);
        return _storage.Values.Where(predicate);
    }

    // Pemanfaatan constraint `new()` untuk factory method
    public TEntity CreateBlankEntity(TId id)
    {
        var instance = new TEntity(); // Valid karena constraint new()
        return instance;
    }
}

// 4. Implementasi Domain Nyata
public sealed class UserAccount : IIdentifiable<Guid>, IAuditable
{
    public Guid Id { get; init; } = Guid.NewGuid();
    public string Username { get; set; } = string.Empty;
    public DateTime CreatedAtUtc { get; private set; } = DateTime.UtcNow;
    public DateTime? UpdatedAtUtc { get; private set; }

    public void MarkUpdated()
    {
        UpdatedAtUtc = DateTime.UtcNow;
    }
}

// 5. Eksekusi Program
public static class Program
{
    public static void Main()
    {
        IRepository<UserAccount, Guid> repository = new InMemoryRepository<UserAccount, Guid>();

        var user = new UserAccount { Username = "alex_dev" };
        repository.Add(user);

        var retrieved = repository.GetById(user.Id);
        Console.WriteLine($"User Ditemukan: {retrieved?.Username}, UpdatedAt: {retrieved?.UpdatedAtUtc}");

        // Baris berikut akan memicu Compile-Time Error jika uncommented:
        // IRepository<int, Guid> invalidRepo; 
        // CS0701: 'int' is not a reference type as required by constraint 'class'
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Code Sharing vs Monomorphization
Ketika kode C# dikompilasi menjadi Intermediate Language (IL), generic types mempertahankan instruksi generic formal, misalnya `ldfld !0 class MyGeneric::field`. CLR JIT (*Just-In-Time*) compiler mengeksekusinya secara berbeda tergantung tipenya:

- **Reference Types (`where T : class`)**: CLR menerapkan strategi **Code Sharing**. Karena seluruh pointer objek managed pada memori memiliki representasi fisik identik (alamat memori 32-bit atau 64-bit), JIT hanya memproduksi **satu salinan native machine code** untuk semua tipe referensi (`List<string>`, `List<UserAccount>`, dll.). Pemanggilan metode dilakukan dengan menyisipkan pointer `MethodTable` secara implisit ke dalam *execution frame*.
- **Value Types (`where T : struct`)**: CLR melakukan **Specialization/Monomorphization**. JIT menghasilkan kode biner baru untuk setiap `struct` berbeda secara terpisah karena ukuran dan struktur byte-nya unik (misalnya: `int` 4-byte vs `Guid` 16-byte).

#### Alokasi Memori / Resource
- **Instruksi `callvirt` vs `call`**: Constraint `where T : class, IInterface` menginstruksikan kompilator untuk menggunakan opcode `constrained. callvirt` dalam IL. Tanpa constraint interface, memanggil metode abstrak atau interface akan memerlukan *boxing* jika diaplikasikan pada struct. Namun, dengan constraint eksplisit `class`, *call site* dioptimalkan langsung pada *Virtual Method Table* (VMT) objek kelas tanpa alokasi temporer.
- **Nullability Context**: Jika Nullable Reference Types (NRT) diaktifkan, constraint `where T : class` secara bawaan mengartikan `T` sebagai non-nullable (`T : class`), sedangkan `where T : class?` secara eksplisit memperbolehkan tipe referensi bernilai null.

#### Trade-offs
- **Kelebihan Code Sharing**: Mengurangi *footprint* memori instruksi mesin (*instruction cache/L1i cache miss*) karena native binary digunakan bersama-sama oleh berbagai representasi `T : class`.
- **Kekurangan**: Terjadi *indirection overhead* minimal saat runtime karena CLR harus mengekstrak konteks tipe spesifik lewat argumen tersembunyi (*Generic Context Token*) untuk operasi-operasi yang bergantung pada tipe statis (seperti `typeof(T)` atau `static` field dari generic class).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Constraint Teringkas**: Hanya tetapkan batasan yang mutlak dibutuhkan oleh fungsionalitas di dalam kelas/metode generik. Jangan membatasi ke tipe kelas konkrit jika kontrak antarmuka (`interface`) sudah mencukupi.
- **Manfaatkan `EqualityComparer<T>.Default`**: Ketika membandingkan kesetaraan identitas objek dalam generik tanpa batasan kelas dasar konkrit, gunakan `EqualityComparer<T>.Default.Equals(a, b)` daripada operator `==`, karena operator `==` pada generic yang hanya dibatasi `where T : class` akan melakukan perbandingan referensi (*reference equality*), mengabaikan *override* operator kesetaraan yang mungkin dimiliki tipe konkretnya.
- **Kombinasikan dengan `notnull` jika Relevan**: Jika Anda tidak ingin tipe referensi tersebut mengizinkan instansiasi bernilai *nullable*, pertimbangkan kombinasi `where T : class, notnull`.

#### Don'ts
- **Hindari Type-Checking Manual di Dalam Generic Method**:
  ```csharp
  // BAD: Anti-pattern merusak fungsi generik
  public void Process<T>(T item) where T : class
  {
      if (item is Order order) { /* implementasi khusus */ }
      else if (item is Customer cust) { /* implementasi khusus */ }
  }
  ```
  *Solusi*: Gunakan polymorphism atau ekstrak operasi ke antarmuka atau pola *Strategy/Visitor*.
- **Jangan Mengabaikan GC Pressure**: Meskipun `where T : class` menghindari *boxing*, pembuatan instance via `new T()` (jika ditambahkan constraint `new()`) menggunakan *Activator* secara implisit pada versi framework lama atau pemanggilan *parameterless constructor* dinamik yang mengalokasikan objek baru ke Large Object Heap (LOH) / Gen 0 Heap. Pertimbangkan implementasi *Object Pooling* untuk tipe referensi siklus hidup pendek.

#### Edge Cases
- **Operator `==` pada `where T : class`**:
  ```csharp
  public bool AreEqual<T>(T a, T b) where T : class
  {
      return a == b; // PERINGATAN: Membandingkan Identity Memory Reference!
  }
  
  string s1 = new string("test".ToCharArray());
  string s2 = new string("test".ToCharArray());
  Console.WriteLine(AreEqual(s1, s2)); // FALSE! Meskipun string meng-override operator ==
  ```
  *Penyebab*: Compiler mengikat operator `==` pada *compile-time* ke representasi `System.Object`, sehingga mengeksekusi *reference equality*, bukan *overloaded equality operator* dari kelas turunan.

### 5. Tantangan Eksplorasi Mandiri

1. **Inspeksi Metadata Intermediate Language (IL)**:
   Buat kelas generik sederhana `TestClass<T>` dengan dua metode: satu dibatasi `where T : class` dan satu tanpa batasan. Kompilasi dan periksa perbedaan instruksi IL pada kedua metode menggunakan CLI tool `ildasm` atau [SharpLab.io](https://sharplab.io). Amati keberadaan opcode `constrained.` dan bagaimana kompilator menangani pemanggilan metode `ToString()`.

2. **Dilema Reference Equality vs Value Equality**:
   Ubah metode `AreEqual<T>` pada bab *Edge Cases* di atas agar dapat melakukan perbandingan nilai (*value equality*) yang benar untuk tipe referensi apa pun (seperti `string`, kelas turunan yang menerapkan `IEquatable<T>`), tanpa melakukan *boxing* dan tanpa kehilangan keamanan tipe. (*Petunjuk: Pelajari `IEqualityComparer<T>` dan `IEquatable<T>` constraint*).
