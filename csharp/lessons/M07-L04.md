## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Middleware Pipeline di ASP.NET Core adalah implementasi dari pola desain *Chain of Responsibility* dan *Russian Doll Model* (model boneka bersarang). Setiap komponen middleware berada di antara request yang masuk dari client dan endpoint target (Controller/Minimal API), serta memproses response saat bergerak keluar.

```
       Request ---> [ Middleware 1 ] ---> [ Middleware 2 ] ---> [ Endpoint ]
                         │                       │                     │
      Response <--- [ Middleware 1 ] <--- [ Middleware 2 ] <------------┘
```

Secara fundamental, arsitektur ini dirancang untuk:
1. **Separation of Concerns (SoC)**: Mengisolasi aspek cross-cutting (seperti autentikasi, logging, kompresi, dan CORS) dari domain logic aplikasi.
2. **Short-circuiting**: Memberikan kapabilitas pada middleware tertentu untuk menghentikan aliran pipeline tanpa memanggil komponen berikutnya (misalnya, middleware autentikasi menolak request token tidak valid dan langsung mengembalikan HTTP 401).
3. **Branching (Percabangan)**: Memungkinkan jalur eksekusi terpisah berbasis path URL atau predikat kondisional (`Map` dan `MapWhen`).

Inti dari pipeline ini direpresentasikan oleh tipe delegasi:
```csharp
public delegate Task RequestDelegate(HttpContext context);
```

Setiap middleware bertindak sebagai fungsi tingkat tinggi (higher-order function) dengan signature:
```csharp
Func<RequestDelegate, RequestDelegate>
```
Fungsi ini menerima `RequestDelegate` berikutnya dalam antrean dan mengembalikan `RequestDelegate` baru yang membungkus logika middleware itu sendiri. Pipeline dievaluasi secara rekursif saat inisialisasi aplikasi (`builder.Build()`) dan menghasilkan satu pointer fungsi terpadu (`RequestDelegate`) yang langsung dipanggil oleh web server (misalnya Kestrel) untuk setiap request HTTP yang masuk.

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi production-ready dari dua variasi middleware:
1. **Convention-based Middleware**: Injeksi Correlation ID dan audit latency.
2. **Factory-based (`IMiddleware`)**: Memungkinkan resolusi scoped service secara murni via Dependency Injection (DI) container.

```csharp
using System.Diagnostics;
using Microsoft.Extensions.Primitives;

// 1. Convention-based Middleware untuk Correlation ID & Performance Metrics
public sealed class RequestCorrelationMiddleware
{
    private const string CorrelationHeaderKey = "X-Correlation-ID";
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestCorrelationMiddleware> _logger;

    // RequestDelegate DI-inject SEKALI saat aplikasi bootstrapping (Singleton lifecycle)
    public RequestCorrelationMiddleware(RequestDelegate next, ILogger<RequestCorrelationMiddleware> logger)
    {
        _next = next ?? throw new ArgumentNullException(nameof(next));
        _logger = logger ?? throw new ArgumentNullException(nameof(logger));
    }

    // Scoped dependencies HARUS di-inject pada method InvokeAsync, BUKAN di constructor!
    public async Task InvokeAsync(HttpContext context)
    {
        // 1. Ekstrak atau buat Correlation ID baru
        if (!context.Request.Headers.TryGetValue(CorrelationHeaderKey, out StringValues correlationId) ||
            StringValues.IsNullOrEmpty(correlationId))
        {
            correlationId = Guid.NewGuid().ToString("N");
        }

        context.Items[CorrelationHeaderKey] = correlationId.ToString();

        // 2. Tambahkan Correlation ID ke Response Header sebelum body mulai ditulis
        context.Response.OnStarting(() =>
        {
            context.Response.Headers[CorrelationHeaderKey] = correlationId;
            return Task.CompletedTask;
        });

        var stopwatch = Stopwatch.StartNew();

        using (_logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = correlationId.ToString() }))
        {
            _logger.LogInformation("Memulai pemrosesan HTTP {Method} {Path}", context.Request.Method, context.Request.Path);

            try
            {
                // Panggil middleware berikutnya dalam pipeline
                await _next(context);
            }
            finally
            {
                stopwatch.Stop();
                _logger.LogInformation(
                    "Selesai memproses HTTP {Method} {Path} dalam {ElapsedMilliseconds} ms dengan Status {StatusCode}",
                    context.Request.Method,
                    context.Request.Path,
                    stopwatch.ElapsedMilliseconds,
                    context.Response.StatusCode);
            }
        }
    }
}

// 2. Extension Method untuk perakitan pipeline yang clean & idiomatik
public static class PipelineExtensions
{
    public static IApplicationBuilder UseRequestCorrelation(this IApplicationBuilder builder)
    {
        return builder.UseMiddleware<RequestCorrelationMiddleware>();
    }
}

// 3. Konfigurasi Entry Point Aplikasi (Program.cs)
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddEndpointsApiExplorer();

var app = builder.Build();

// Urutan pendaftaran (ORDER OF REGISTRATION) SANGAT KRUSIAL:
// Middleware penanganan exception ditaruh paling luar (paling awal)
app.Use(async (context, next) =>
{
    try
    {
        await next(context);
    }
    catch (Exception ex)
    {
        var logger = context.RequestServices.GetRequiredService<ILogger<Program>>();
        logger.LogError(ex, "Unhandled exception tertangkap di root pipeline.");

        if (!context.Response.HasStarted)
        {
            context.Response.StatusCode = StatusCodes.Status500InternalServerError;
            context.Response.ContentType = "application/json";
            await context.Response.WriteAsync("{\"error\":\"Internal Server Error\"}");
        }
    }
});

// Pasang Custom Middleware Correlation
app.UseRequestCorrelation();

// Contoh Branching Pipeline (Hanya dieksekusi jika path diawali "/internal")
app.Map("/internal", internalApp =>
{
    internalApp.Use(async (context, next) =>
    {
        if (!context.Request.Headers.ContainsKey("X-Internal-Secret"))
        {
            context.Response.StatusCode = StatusCodes.Status403Forbidden;
            return; // Short-circuiting! Pipeline downstream tidak dipanggil
        }
        await next(context);
    });

    internalApp.Run(async context =>
    {
        await context.Response.WriteAsync("Akses area internal diizinkan.");
    });
});

app.MapGet("/api/data", () => Results.Ok(new { Message = "Payload berhasil diproses." }));

app.Run();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Penyusunan Delegasi
Ketika memanggil method seperti `app.Use(...)` atau `app.UseMiddleware<T>()`, Anda sebenarnya mendaftarkan delegasi ke dalam internal koleksi `List<Func<RequestDelegate, RequestDelegate>>` pada instance `IApplicationBuilder`.

Saat `app.Build()` dieksekusi:
1. Pipeline dibalik dari belakang (*reverse traversal*).
2. Titik terminasi default (biasanya mengembalikan 404 Not Found) dijadikan delegasi ekor (`tail`).
3. Setiap delegasi middleware membungkus delegasi berikutnya:
   $$\text{Pipeline} = M_1(M_2(M_3(\dots(Tail))))$$
4. Hasil akhirnya berupa delegasi tunggal `RequestDelegate`. Kestrel memanggil delegate entry-point ini secara langsung untuk setiap HTTP request tanpa overhead runtime scanning atau `MethodInfo.Invoke` reflection.

#### Alokasi Memori & Resource
- **Convention Middleware Singleton Trap**: Middleware konvensional diinstansiasi **sekali saja** saat build (`Application Lifetime`). Jika Anda meng-inject Scoped Service (seperti Entity Framework `DbContext`) ke dalam *constructor* middleware konvensional, service tersebut akan berubah menjadi *Captive Dependency* (bertahan selamanya sebagai singleton palsu) yang memicu race condition multi-threading dan kebocoran memori.
- **Factory-Based Middleware (`IMiddleware`)**: Menggunakan `IMiddlewareFactory`. Interface ini mengizinkan middleware di-resolve via DI per request (Scoped). Pendekatan ini aman untuk scoped dependency, namun menimbulkan sedikit overhead alokasi memori GC (Gen 0) per request karena objek middleware diinstansiasi ulang.
- **`HttpContext` Lifetime**: Dikelola via Object Pooling oleh Kestrel (`DefaultHttpContextPool`). Setelah `InvokeAsync` selesai sepenuhnya dan response stream di-flush, objek `HttpContext` di-reset dan dikembalikan ke pool. Jangan menyimpan referensi ke `HttpContext` di luar execution stack middleware!

#### Trade-offs
- Menumpuk terlalu banyak middleware meningkatkan kedalaman stack trace (`async/await` state machine) dan berpotensi menambah latency CPU.
- `app.Map` memutus linearitas: sekali pipeline di-*branch*, request tersebut tidak dapat kembali ke pipeline utama (berbeda dengan `app.UseWhen` yang dapat bergabung kembali ke pipeline utama setelah eksekusi percabangan).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `context.Response.OnStarting`** saat memodifikasi response header di middleware jika ada kemungkinan middleware downstream telah menulis response body.
- **Inject Scoped Dependency ke method `InvokeAsync`**: Parameter method `InvokeAsync` dievaluasi oleh ASP.NET Core Activator per request dan mendukung injeksi dependensi Scoped secara otomatis:
  ```csharp
  public async Task InvokeAsync(HttpContext context, AppDbContext dbContext) // AMAN
  ```
- **Jaga Urutan Pipeline**: Urutan baku yang direkomendasikan adalah:
  1. Exception Handler / Diagnostics
  2. HSTS / HTTPS Redirection
  3. Static Files
  4. Routing (`app.UseRouting()`)
  5. CORS
  6. Authentication
  7. Authorization
  8. Custom Domain Middleware
  9. Endpoints (`app.MapControllers()`, dsb.)

#### Don'ts
- **DILARANG mengubah Header setelah Response Dimulai**:
  ```csharp
  await _next(context);
  // BAHAYA! Jika body sudah di-stream, Response.HasStarted bernilai true.
  // Kode di bawah ini akan melempar InvalidOperationException:
  context.Response.Headers["X-Custom"] = "Value"; 
  ```
- **DILARANG menggunakan `async void`**: Selalu gunakan `Task` sebagai return type dari method `InvokeAsync`. `async void` akan mematikan proses jika terjadi exception (unhandled process crash).
- **Hindari Blocking Calls**: Jangan panggil `.Result`, `.Wait()`, atau `.GetAwaiter().GetResult()` pada operasi asynchronous di middleware. Hal ini menyebabkan ThreadPool starvation pada server ber-concurrency tinggi.

#### Edge Cases
- **Client Disconnection (`OperationCanceledException`)**: Selalu operasikan `context.RequestAborted` ke operasi async (misalnya I/O database atau query jaringan) agar thread langsung dibatalkan saat client menutup koneksi socket secara prematur:
  ```csharp
  await dbContext.Users.ToListAsync(context.RequestAborted);
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Anti-Tampering Request Payload:**
   Rancang sebuah Middleware yang menghitung SHA256 checksum dari `HttpRequest.Body` yang masuk, mencocokkannya dengan header `X-Payload-Signature`, dan melakukan short-circuit dengan HTTP 400 jika payload tidak identik. *Petunjuk:* Waspadai konsumsi stream; body stream ASP.NET Core secara default non-rewindable, pelajari penggunaan `context.Request.EnableBuffering()` dan reset stream pointer (`Seek(0, SeekOrigin.Begin)`).
2. **Reverse Engineer Pipeline Assembly:**
   Telusuri implementasi internal `IApplicationBuilder.Build()` pada repositori sumber `dotnet/aspnetcore`. Analisis mengapa framework menggunakan loop `Reverse()` dan delegasi terangkai alih-alih linked list iteration biasa saat runtime. Catat dampaknya terhadap optimasi compiler JIT.
