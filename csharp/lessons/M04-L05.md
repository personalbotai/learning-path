### 1. Konsep & Arsitektur Mendalam

Perbedaan fundamental antara **LINQ to Objects** (`IEnumerable<T>`) dan **LINQ to Entities/IQueryable** (`IQueryable<T>`) terletak pada **bagaimana kode dipahami oleh compiler dan di mana komputasi tersebut dieksekusi**.

```
[ Lambda Expression: x => x.Age > 18 ]
           │
           ├─ Assigned to Func<T, bool> (IEnumerable) 
           │       │
           │       ▼
           │  [ IL Bytecode: Executed in CLR Memory ] 
           │  (LINQ to Objects: CPU + RAM lokal)
           │
           └─ Assigned to Expression<Func<T, bool>> (IQueryable)
                   │
                   ▼
              [ Abstract Syntax Tree (AST) Data Structure ]
                   │
                   ▼ (Parsed by IQueryProvider / Visitor)
              [ External Query: e.g., T-SQL "WHERE [Age] > 18" ]
              (Database Engine / Remote Execution)
```

#### A. LINQ to Objects (`IEnumerable<T>`)
`IEnumerable<T>` merepresentasikan sekumpulan data in-memory yang dapat diiterasi secara sekuensial.
- **Karakteristik Tipe**: Menerima delegasi executable, biasanya berakar pada `Func<T, TResult>` atau `Action<T>`.
- **Eksekusi**: Kode lambda di-compile langsung menjadi **CIL (Common Intermediate Language)** bytecode saat compile-time. CLR mengeksekusi instruksi ini langsung di CPU dan RAM aplikasi.
- **Opasitas (Opaque Delegate)**: Bagi runtime, sebuah `Func<T, bool>` adalah sebuah *black box*. Runtime hanya tahu cara memanggil method tersebut dengan passing input dan menerima output. Runtime tidak bisa menginspeksi struktur internal dari kondisi di dalam delegasi tersebut.

#### B. LINQ Providers & Expression Trees (`IQueryable<T>`)
`IQueryable<T>` diturunkan dari `IEnumerable<T>`, namun dirancang untuk mengeksekusi query terhadap data store eksternal (seperti SQL Server, PostgreSQL, CosmosDB, atau Web API).
- **Karakteristik Tipe**: Menerima **Expression Tree** (`Expression<Func<T, TResult>>`).
- **Eksekusi**: Lambda expression **tidak di-compile** menjadi executable IL bytecode. Compiler menghasilkan instruksi instansiasi kelas-kelas yang membentuk struktur pohon sintaksis abstrak (**Abstract Syntax Tree / AST**).
- **Transparansi**: Kode diperlakukan sebagai **data**. Komponen `IQueryProvider` dapat membedah AST ini (mengidentifikasi parameter, operasi logika, pemanggilan fungsi, dan konstanta), lalu menerjemahkannya (*transpile*) menjadi bahasa native target (misalnya SQL: `WHERE Age > 18`).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh yang mengilustrasikan perbedaan antara eksekusi delegasi langsung (`Func`) dan parsing Expression Tree (`Expression`) secara programmatic:

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Linq.Expressions;

public record User(int Id, string Name, int Age, bool IsActive);

public class Program
{
    public static void Main()
    {
        // -------------------------------------------------------------
        // KASUS 1: LINQ to Objects (IEnumerable<T> & Func<T, bool>)
        // -------------------------------------------------------------
        var users = new List<User>
        {
            new(1, "Alice", 24, true),
            new(2, "Bob", 17, true),
            new(3, "Charlie", 30, false)
        };

        // Lambda otomatis di-compile menjadi delegate Func<User, bool>
        Func<User, bool> inMemoryFilter = u => u.Age >= 18 && u.IsActive;

        // Eksekusi terjadi di CLR: Iterasi melalui memory list via Yield Return
        IEnumerable<User> adultActiveUsers = users.Where(inMemoryFilter);
        
        Console.WriteLine($"[IEnumerable] Total matches: {adultActiveUsers.Count()}");

        // -------------------------------------------------------------
        // KASUS 2: Expression Trees (IQueryable<T> & Expression<Func<T, bool>>)
        // -------------------------------------------------------------
        // Lambda yang SAMA, tetapi compiler memproduksinya sebagai metadata AST
        Expression<Func<User, bool>> expressionFilter = u => u.Age >= 18 && u.IsActive;

        // Membedah AST (Bagaimana EF Core / IQueryProvider membaca kode Anda)
        Console.WriteLine("\n[Expression Tree Inspection]");
        Console.WriteLine($"Body Type: {expressionFilter.Body.GetType().Name}"); // BinaryExpression
        Console.WriteLine($"Node Type: {expressionFilter.Body.NodeType}");         // AndAlso (&&)

        if (expressionFilter.Body is BinaryExpression andAlso)
        {
            // Sub-tree Kiri (u.Age >= 18)
            var left = (BinaryExpression)andAlso.Left;
            var leftProp = (MemberExpression)left.Left;
            var leftConst = (ConstantExpression)left.Right;
            Console.WriteLine($" Left Condition : {leftProp.Member.Name} {left.NodeType} {leftConst.Value}");

            // Sub-tree Kanan (u.IsActive)
            var right = (MemberExpression)andAlso.Right;
            Console.WriteLine($" Right Condition: {right.Member.Name} == true");
        }

        // -------------------------------------------------------------
        // KASUS 3: Compiling Expression dynamically at runtime
        // -------------------------------------------------------------
        // Expression Tree bisa di-compile kembali menjadi CIL delegate secara on-the-fly
        Func<User, bool> compiledDelegate = expressionFilter.Compile();
        bool isAliceValid = compiledDelegate(users[0]);
        Console.WriteLine($"\n[Dynamic Execution] Alice valid? {isAliceValid}");
    }
}
```

#### Cara Kerja `ExpressionVisitor`
Di dalam framework ORM (seperti Entity Framework Core), provider mengimplementasikan pattern `ExpressionVisitor` untuk menelusuri setiap node (*leaf* dan *branch*) dari AST di atas, lalu memetakan node C# tersebut ke padanan sintaksis SQL (misal: Node `AndAlso` diterjemahkan menjadi operator `AND` SQL).

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Pembangkitan Kode oleh C# Compiler (Roslyn)**:
   - Saat mendeklarasikan `Func<T, bool> f = x => x.Active;`, Roslyn menghasilkan sebuah private synthetic method di dalam class, lalu membuat instansiasi delegasi yang menunjuk langsung ke method tersebut.
   - Saat mendeklarasikan `Expression<Func<T, bool>> e = x => x.Active;`, Roslyn mengubah seluruh ekspresi lambda menjadi serangkaian pemanggilan factory method statis dari namespace `System.Linq.Expressions`:
     ```csharp
     ParameterExpression param = Expression.Parameter(typeof(User), "x");
     MemberExpression prop = Expression.Property(param, "Active");
     Expression<Func<User, bool>> e = Expression.Lambda<Func<User, bool>>(prop, param);
     ```

2. **Deferred Execution**:
   - `IEnumerable<T>`: Menggunakan compiler-generated state machine (`IEnumerator<T>`) dengan pola *pull-based* (`MoveNext()` / `Current`). Iterasi ditunda sampai collection di-*consume* (`foreach`, `.ToList()`).
   - `IQueryable<T>`: Mengekspos property `Provider` (`IQueryProvider`) dan `Expression`. Ketika `.GetEnumerator()` dipanggil, query provider mengevaluasi seluruh struktur AST, membuat payload eksternal (misal: SQL script), mengirimkannya melalui I/O socket, memetakan data tabular mentah menjadi objek C#, barulah yield objek satu per satu.

#### Alokasi Memori / Resource
- **Delegate (`Func`)**: Alokasi sangat rendah. Jika tidak melakukan closure (*capturing variable* dari scope lokal), Roslyn akan meng-cache instance delegasi tersebut sebagai static singleton.
- **Expression Tree**: Berat di heap memory. Membangun representasi pohon sintaksis membutuhkan alokasi puluhan hingga ratusan objek node (`ParameterExpression`, `BinaryExpression`, dsb.).
- **Dynamic Compilation (`Expression.Compile()`)**: Operasi ini menginstansiasi dynamic method menggunakan `Reflection.Emit`. Ini menghasilkan runtime overhead yang masif (CPU-bound) dan mengalokasikan executable memory yang perlu di-cleanup oleh runtime.

#### Trade-offs
| Parameter | `IEnumerable<T>` / `Func<T>` | `IQueryable<T>` / `Expression<T>` |
| :--- | :--- | :--- |
| **Lokasi Eksekusi** | RAM & CPU Aplikasi Lokal | Remote Server (Database / API Engine) |
| **Batas Filter Data** | Mengambil seluruh record data ke RAM lalu difilter | Memfilter record di database, hanya data relevan yang dikirim |
| **Kemampuan Bahasa** | 100% fitur C# (RegEx, method pihak ketiga, pointers) | Terbatas pada fungsionalitas yang didukung `IQueryProvider` target |
| **Compile Cost** | Cepat, langsung menjadi binary IL | Kompleks; pembentukan AST saat inisialisasi memerlukan overhead alokasi |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Terapkan Filter Sejauh Mungkin pada `IQueryable`**:
  ```csharp
  // BENAR: Filter dijalankan oleh Database Engine
  var adults = dbContext.Users
      .Where(u => u.Age >= 18) // Masih IQueryable
      .Take(50)                // SQL: TOP(50) / LIMIT 50
      .ToList();
  ```
- **Gunakan `.Select()` untuk Proyeksi Data**: Batasi kolom yang ditarik dari storage untuk menghemat I/O network dan heap allocation.
  ```csharp
  // Mengurangi footprint memori secara dramatis
  var userDtos = dbContext.Users
      .Where(u => u.IsActive)
      .Select(u => new UserDto(u.Id, u.Name))
      .ToList();
  ```

#### Don'ts
- **Premature Materialization (Overfetching)**:
  Jangan memanggil method materialisasi seperti `.ToList()`, `.ToArray()`, atau `.AsEnumerable()` sebelum logika filtering selesai didefinisikan.
  ```csharp
  // FATAL: Mengunduh 1.000.000 row dari DB ke RAM, lalu memfilter 10 row via CPU lokal!
  var filteredUsers = dbContext.Users
      .ToList() // Titik patah: IQueryable berubah menjadi IEnumerable (In-Memory)
      .Where(u => u.Age > 60)
      .Take(10);
  ```
- **Memanggil Method C# Lokal di dalam `IQueryable`**:
  `IQueryProvider` tidak dapat menerjemahkan algoritma lokal Anda ke dalam SQL, yang akan memicu `InvalidOperationException` pada runtime jika EF Core tidak mendukung client evaluation untuk konteks tersebut.
  ```csharp
  // RUNTIME ERROR: CustomEncrypt() tidak dapat diterjemahkan ke SQL
  var user = dbContext.Users
      .Where(u => CustomEncrypt(u.Email) == encryptedEmail)
      .FirstOrDefault();
  ```

#### Edge Cases & Pitfalls
- **Accidental Type Poisoning (`IEnumerable` Infection)**:
  Jika sebuah helper method menerima `IEnumerable<T>`, passing `IQueryable<T>` ke dalamnya akan menyebabkan compiler memilih ekstensi LINQ to Objects secara diam-diam.
  ```csharp
  public static IEnumerable<User> ApplyFilter(IEnumerable<User> query) 
      => query.Where(u => u.Age > 18); // Ini mengeksekusi Func<User, bool> di RAM!
  ```
- **Kompilasi Ulang Expression yang Berulang-ulang**:
  Hindari memanggil `expression.Compile()` di dalam loop atau high-throughput pipeline tanpa caching, karena setiap panggilan akan melakukan emisi MSIL dinamis dan menekan memori CLR.

### 5. Tantangan Eksplorasi Mandiri

1. **Membuat SQL Translator Sederhana Menggunakan `ExpressionVisitor`**:
   Buat subclass dari `ExpressionVisitor` yang menerima `Expression<Func<User, bool>>`, kunjungi node `BinaryExpression`, dan generate string representasi SQL kustom (misal: mengubah ekspresi `u => u.Age > 20 && u.IsActive == true` menjadi string `"Age > 20 AND IsActive = 1"`).
2. **Benchmark Overhead Expression Compilation vs Native Delegate**:
   Gunakan **BenchmarkDotNet** untuk membandingkan performa antara:
   - Pemanggilan langsung delegasi: `Func<int, bool> fn = x => x > 50;`
   - Mengeksekusi lambda via `.Compile()` di setiap iterasi.
   - Mengompilasi expression satu kali (*cached compiled expression*), lalu mengeksekusi delegate yang dihasilkan berkali-kali. Amati perbedaan CPU time dan *Gen 0/1/2 GC Allocations*.
