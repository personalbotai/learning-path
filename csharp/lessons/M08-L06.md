### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur data enterprise, integritas data bergantung pada transaksi atomik dan mekanisme resolusi konflik yang presisi. Ketika aplikasi C# berkomunikasi dengan RDBMS melalui ADO.NET atau Entity Framework Core (EF Core), pemahaman mendalam tentang siklus hidup transaksi, titik pemulihan parsial (*savepoints*), dan konkurensi menjadi krusial.

#### Transaksi Database & Isolation Levels
Secara default, setiap pemanggilan `SaveChangesAsync()` dalam EF Core membungkus semua modifikasi yang terdeteksi oleh `ChangeTracker` ke dalam satu transaksi implisit. Namun, alur bisnis kompleks sering kali membutuhkan transaksi eksplisit (`IDbContextTransaction`) untuk mengoordinasikan beberapa operasi lintas repositori atau batch processing.

Setiap transaksi dieksekusi dengan tingkat isolasi (*Isolation Level*) tertentu yang mendikte bagaimana RDBMS mengisolasi modifikasi data dari transaksi lain:
1. **Read Uncommitted**: Membaca transaksi yang belum di-*commit* (*dirty reads*).
2. **Read Committed** (Default pada SQL Server & PostgreSQL): Mencegah *dirty reads* menggunakan pembacaan berbasis *shared lock* atau *row-versioning*.
3. **Repeatable Read**: Menjamin bahwa data yang dibaca tidak akan berubah selama transaksi berlangsung (*shared locks* ditahan hingga selesai), mencegah *non-repeatable reads*.
4. **Serializable**: Isolasi penuh dengan penguncian rentang (*range locking*), mencegah *phantom reads*, tetapi memicu penalti performa ekstrem dan risiko *deadlock*.
5. **Snapshot**: Menggunakan *multiversion concurrency control* (MVCC) di penyimpanan `tempdb`/undo-log untuk membaca representasi data yang konsisten tanpa mengunci baris.

```
+-------------------------------------------------------------------------+
|                              TRANSACTION                                |
|  [BEGIN TRAN]                                                           |
|       |                                                                 |
|       v                                                                 |
|   Operasi 1: Update Saldo Akun                                          |
|       |                                                                 |
|       +-----> [CREATE SAVEPOINT "Sp_BonusApplied"]                      |
|       |              |                                                  |
|       |              v                                                  |
|       |         Operasi 2: Klaim Reward Eksternal (Berisiko Gagal)      |
|       |              |                                                  |
|       |       [FAILED] ---> [ROLLBACK TO "Sp_BonusApplied"]             |
|       v                                                                 |
|   Operasi 3: Log Riwayat Transaksi                                      |
|       |                                                                 |
|  [COMMIT TRAN]                                                          |
+-------------------------------------------------------------------------+
```

#### Savepoints: Transaksi Parsial
*Savepoint* adalah penanda (*marker*) di dalam scope transaksi aktif yang memungkinkan pembatalan (*rollback*) sebagian operasi tanpa membatalkan seluruh transaksi. Diperkenalkan secara formal ke EF Core pada versi 5.0, fitur ini sangat berguna saat mengeksekusi sub-langkah non-kritis (misal: pemberian cashback atau pencatatan metrik pihak ketiga) yang jika gagal, tidak boleh membatalkan keseluruhan transaksi bisnis utama.

#### Concurrency Control: Optimistic vs. Pessimistic
Konkurensi terjadi saat dua atau lebih thread/proses mengakses dan memodifikasi data yang sama secara bersamaan.
*   **Pessimistic Concurrency**: Mengunci baris data di level database secara eksplisit menggunakan sintaks seperti `SELECT ... FOR UPDATE` atau *table hints* (`UPDLOCK`, `XLOCK`). Pendekatan ini aman dari konflik, namun memperbesar peluang *deadlock* dan menghambat skalabilitas sistem.
*   **Optimistic Concurrency**: Mengizinkan modifikasi terjadi tanpa penguncian langsung. Sebelum perubahan di-*commit*, sistem memvalidasi apakah data telah diubah oleh pihak lain sejak data tersebut pertama kali dibaca. Di EF Core, hal ini diimplementasikan menggunakan **Concurrency Token** atau kolom penanda versi seperti `byte[] RowVersion` (SQL Server `ROWVERSION` atau PostgreSQL `xmin`).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh skenario e-commerce: Memproses checkout pesanan dengan penyesuaian stok, penerapan kupon diskon menggunakan *savepoint*, dan resolusi konflik konkurensi stok produk.

#### Definisi Entitas & Model

```csharp
using System.ComponentModel.DataAnnotations;
using Microsoft.EntityFrameworkCore;

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
    public int Stock { get; set; }

    // Concurrency Token: Otomatis di-update oleh DB engine saat ada UPDATE baris
    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}

public class Order
{
    public int Id { get; set; }
    public int ProductId { get; set; }
    public int Quantity { get; set; }
    public decimal FinalAmount { get; set; }
    public bool DiscountApplied { get; set; }
}

public class AppDbContext : DbContext
{
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Order> Orders => Set<Order>();

    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Product>()
            .Property(p => p.RowVersion)
            .IsRowVersion(); // Mengonfigurasi atribut Concurrency Token secara eksplisit
    }
}
```

#### Eksekusi Transaksi, SavePoint, dan Penanganan Konflik

```csharp
using Microsoft.EntityFrameworkCore;
using System.Data;

public class CheckoutService
{
    private readonly AppDbContext _context;

    public CheckoutService(AppDbContext context)
    {
        _context = context;
    }

    public async Task<bool> ProcessCheckoutAsync(int productId, int quantity, bool applyBonusCoupon)
    {
        const int maxRetry = 3;
        int currentAttempt = 0;

        while (currentAttempt < maxRetry)
        {
            currentAttempt++;
            
            // 1. Inisialisasi Transaksi Eksplisit dengan Isolation Level tertentu
            await using var transaction = await _context.Database.BeginTransactionAsync(IsolationLevel.ReadCommitted);

            try
            {
                var product = await _context.Products.FirstOrDefaultAsync(p => p.Id == productId);
                if (product == null || product.Stock < quantity)
                {
                    throw new InvalidOperationException("Stok tidak mencukupi atau produk tidak ditemukan.");
                }

                // Kurangi stok
                product.Stock -= quantity;
                decimal totalAmount = product.Price * quantity;
                bool discountApplied = false;

                // 2. Pembuatan Savepoint sebelum operasi yang berisiko gagal
                await transaction.CreateSavepointAsync("BeforeBonusProcessing");

                try
                {
                    if (applyBonusCoupon)
                    {
                        // Simulasi operasi bisnis kupon berisiko (misal evaluasi limit eksternal)
                        totalAmount = ApplyCouponLogic(totalAmount);
                        discountApplied = true;
                    }
                }
                catch (CouponException)
                {
                    // Rollback HANYA modifikasi kupon ke batas Savepoint
                    await transaction.RollbackToSavepointAsync("BeforeBonusProcessing");
                    discountApplied = false;
                    // Transaksi utama tetap berjalan tanpa diskon
                }

                var order = new Order
                {
                    ProductId = productId,
                    Quantity = quantity,
                    FinalAmount = totalAmount,
                    DiscountApplied = discountApplied
                };

                _context.Orders.Add(order);

                // 3. Commit seluruh entitas ke Database
                await _context.SaveChangesAsync();
                await transaction.CommitAsync();

                return true;
            }
            catch (DbUpdateConcurrencyException ex)
            {
                // Rollback transaksi lokal jika terjadi kegagalan konkurensi
                await transaction.RollbackAsync();

                if (currentAttempt >= maxRetry)
                {
                    throw new ApplicationException("Gagal menyelesaikan checkout karena perebutan sumber daya (konkurensi). Coba lagi nanti.", ex);
                }

                // Resolusi Konflik: Database Wins / Client Wins / Merging
                foreach (var entry in ex.Entries)
                {
                    if (entry.Entity is Product)
                    {
                        // Nilai yang ada di DB saat ini (modifikasi pihak lain)
                        var databaseValues = await entry.GetDatabaseValuesAsync();
                        
                        if (databaseValues == null)
                        {
                            throw new InvalidOperationException("Produk telah dihapus oleh transaksi lain.");
                        }

                        // Refresh original values dengan snapshot terbaru dari database untuk mencoba kembali
                        entry.OriginalValues.SetValues(databaseValues);
                    }
                }

                // Delay eksponensial (Jitter) sebelum retry untuk meredakan contention
                await Task.Delay(TimeSpan.FromMilliseconds(50 * currentAttempt));
            }
            catch (Exception)
            {
                await transaction.RollbackAsync();
                throw;
            }
        }

        return false;
    }

    private decimal ApplyCouponLogic(decimal currentTotal)
    {
        // Simulasi error validasi kupon pihak ketiga
        throw new CouponException("Layanan kupon gagal memvalidasi.");
    }
}

public class CouponException : Exception
{
    public CouponException(string message) : base(message) { }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Transaksi dan Wire Protocol
Ketika `BeginTransactionAsync()` dipanggil, runtime .NET mengirimkan instruksi protokol TDS (Tabular Data Stream pada SQL Server) atau extended query message (PostgreSQL) berupa perintah `BEGIN TRANSACTION`.

Pada eksekusi `CreateSavepointAsync("SpName")`, EF Core memancarkan raw SQL:
```sql
SAVE TRANSACTION SpName; -- Pada SQL Server
-- atau
SAVEPOINT SpName;         -- Pada PostgreSQL
```
Panggilan `RollbackToSavepointAsync` tidak menutup soket transaksi database. Mesin database hanya memundurkan log pointer transaksi (LSU - *Log Sequence Unit*) ke status saat savepoint didefinisikan, mempertahankan semua *exclusive lock* pada operasi sebelum savepoint.

#### Mekanisme Deteksi Concurrency Conflict
Saat `RowVersion` dipetakan sebagai Concurrency Token, EF Core mengubah pernyataan SQL `UPDATE` internal menjadi:
```sql
UPDATE [Products]
SET [Stock] = @p0
WHERE [Id] = @p1 AND [RowVersion] = @p2; -- @p2 adalah OriginalValue dari RowVersion
SELECT [RowVersion] FROM [Products] WHERE @@ROWCOUNT = 1 AND [Id] = @p1;
```
Di balik layar:
1. `ChangeTracker` mencatat `OriginalValues["RowVersion"]` saat entitas pertama kali dimuat ke dalam memori.
2. Saat `SaveChangesAsync` dipanggil, EF Core menyertakan `OriginalValues["RowVersion"]` dalam klausa `WHERE`.
3. Mesin RDBMS mengeksekusi instruksi: jika ada proses lain yang telah meng-*update* baris tersebut, nilai `RowVersion` di tabel berubah. Akibatnya, klausa `WHERE` menghasilkan kecocokan nol baris (`@@ROWCOUNT = 0`).
4. EF Core mengevaluasi bahwa mutasi baris yang diharapkan bernilai 1 ternyata 0. EF Core menginterpretasikan ini sebagai pelanggaran data dan melempar `DbUpdateConcurrencyException`.

#### Alokasi Memori dan Resource Lock Manager
*   **Koneksi Database:** Transaksi eksplisit menahan instans koneksi fisik (`DbConnection`) dari connection pool selama durasi blok transaksi. Koneksi tidak dilepas hingga `DisposeAsync()` atau `CommitAsync()` / `RollbackAsync()` tuntas.
*   **Database Lock Manager:** Penggunaan transaksi yang lama dengan isolasi tinggi mengalokasikan slot memori pada *Lock Manager* database untuk melacak *Row-level locks*, *Page locks*, hingga berisiko mengalami *Lock Escalation* (berubah menjadi *Table Lock* penuh), yang melumpuhkan throughput sistem.

### 4. Best Practices & Common Pitfalls

#### Do's
*   **Jaga Transaksi Singkat dan Padat**: Tarik data (*read-only*) sebelum membuka transaksi. Mulai transaksi hanya sebelum serangkaian operasi tulis dieksekusi.
*   **Gunakan Optimistic Concurrency untuk Sistem Web**: Optimistic Concurrency tidak membebani RDBMS dengan lock berdurasi panjang, sehingga ideal untuk aplikasi cloud yang menggunakan REST API stateless.
*   **Terapkan Exponential Backoff + Jitter**: Saat menangani `DbUpdateConcurrencyException`, jangan langsung mencoba kembali secara simultan. Berikan random delay agar request lain dapat menyelesaikan transaksinya tanpa deadlock berulang.

#### Don'ts
*   **I/O Operasi Eksternal di dalam Transaksi**: Sangat dilarang memanggil HTTP Client, mengirim pesan ke broker (Kafka/RabbitMQ), atau operasi I/O lambat lainnya di dalam blok transaksi database. Jika pemanggilan HTTP timeout (misal 30 detik), koneksi DB tertahan dan tabel terkunci selama durasi tersebut.
*   **Mengabaikan `ChangeTracker` State pasca Rollback**: Melakukan `RollbackAsync()` di level database **tidak** otomatis membalikkan state objek dalam `ChangeTracker` di memori aplikasi. Jika instans `DbContext` yang sama dipakai kembali tanpa penataan ulang, state entitas di memori menjadi *desynchronized* dengan database. Buang konteks tersebut (*dispose*) atau buat konteks baru.
*   **Mencampur `TransactionScope` tanpa Memahami Eskalasi DTC**: `System.Transactions.TransactionScope` secara otomatis dapat melakukan eskalasi dari transaksi lokal ke Distributed Transaction Coordinator (MSDTC) jika membuka dua koneksi database berbeda, yang kerap memicu crash pada arsitektur microservices berbasis Linux/Docker.

#### Edge Cases
*   **Nested Transactions vs Savepoints**: Sebagian besar RDBMS tidak mendukung nesting transaksi sebenarnya (`BEGIN TRAN` ganda pada satu koneksi). EF Core mengatasi ini dengan memetakan panggilan transaksi bersarang menjadi `Savepoints` secara virtual. Ketahuilah keterbatasan database target Anda.

### 5. Tantangan Eksplorasi Mandiri

1.  **Simulasi Race Condition Tingkat Tinggi:**
    Buat skrip *console application* yang melakukan `Task.WhenAll` terhadap 50 thread konkuren yang mencoba memotong stok dari 1 entitas `Product` (stok awal = 20, tiap thread memotong 1). Implementasikan penanganan `DbUpdateConcurrencyException` menggunakan teknik resolusi *Merging Logic* (baca stok terbaru di database, validasi apakah masih mencukupi, lalu potong kembali) dan buktikan stok akhir tepat bernilai 0 tanpa ada *lost update*.

2.  **Audit Lock Escallation & Profiling:**
    Gunakan *SQL Server Profiler*, *Extended Events*, atau `pg_stat_activity` pada PostgreSQL untuk mengamati locking behavior. Bandingkan jenis lock yang terbentuk pada transaksi dengan isolasi `ReadCommitted` vs `Serializable` ketika menjalankan batch update sebanyak 10.000 baris. Perhatikan kapan lock eskalasi terjadi dari *Row Lock* (`RID`/`KEY`) ke *Exclusive Table Lock* (`X`).
