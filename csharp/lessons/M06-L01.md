## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Manajemen memori pada .NET CLR (*Common Language Runtime*) beroperasi secara otomatis, namun pemahaman terhadap mekanisme internalnya sangat krusial untuk membangun aplikasi dengan *throughput* tinggi dan latensi rendah. Memori virtual proses pada .NET dibagi ke dalam dua struktur utama: **Stack** dan **Heap**.

```
+------------------------------------------------------------------------+
|                          VIRTUAL MEMORY PROCESS                        |
+------------------------------------------------------------------------+
|  [ Thread 1 Stack ]  [ Thread 2 Stack ]   ...   [ Managed Heap ]       |
|  - Stack Frame 1     - Stack Frame 1            +--------------------+ |
|    - Local Vars        - Local Vars             | Gen 0 (Ephemeral)  | |
|    - Eval Stack        - Eval Stack             | Gen 1 (Buffer)     | |
|  - Stack Frame 2     - Stack Frame 2            | Gen 2 (Long-lived) | |
|                                                 | LOH (>= 85,000 B)  | |
|                                                 | POH (Pinned)       | |
|                                                 +--------------------+ |
+------------------------------------------------------------------------+
```

#### The Stack
Stack bersifat *per-thread*, dialokasikan secara otomatis saat *thread* dibuat dan memiliki ukuran *default* 1 MB (pada arsitektur Windows x64).
- **Mekanisme**: Bekerja dengan prinsip LIFO (*Last In, First Out*). Alokasi dan dealokasi memori dilakukan semata-mata dengan menggeser pointer register CPU (`RSP` pada x64).
- **Karakteristik**: Memiliki kompleksitas alokasi $O(1)$ dan dealokasi $O(1)$. Tidak ada fragmentasi, tidak ada keterlibatan Garbage Collector (GC).
- **Data yang disimpan**: *Value types* primitif (`int`, `bool`, `double`), *structs* (kecuali di-*box* atau bagian dari objek *heap*), dan pointer alamat memori (referensi) ke objek di Managed Heap.

#### The Managed Heap
Managed Heap bersifat *shared* untuk semua *thread* dalam sebuah *AppDomain*. CLR mengelola alokasi objek referensi (`class`, string, array, dan boxed value types) melalui pointer alokasi bertahap (*bump-pointer allocation*). Karena alokasi bersifat dinamis, pembersihan memori membutuhkan intervensi Garbage Collector (GC).

#### Generational Garbage Collection
GC pada .NET berlandaskan **Weak Generational Hypothesis**:
1. Mayoritas objek berumur sangat pendek (sering kali mati segera setelah dibuat).
2. Objek yang tua cenderung bertahan lebih lama daripada objek yang baru.
3. Mengumpulkan memori dari sebagian kecil *heap* (generasi muda) jauh lebih cepat daripada memindai keseluruhan memori (*full sweep*).

Managed Heap dibagi menjadi generasi-generasi berikut:

- **Generation 0 (Gen 0)**:
  Ruang penampungan pertama untuk objek-objek kecil yang baru dialokasikan (*ephemeral*). Ukurannya relatif kecil (beberapa megabyte). GC pada Gen 0 terjadi sangat sering dan memakan waktu sub-milidetik.
- **Generation 1 (Gen 1)**:
  Berfungsi sebagai zona penyangga (*buffer*) antara objek berumur pendek dan panjang. Objek yang selamat (*survive*) dari siklus GC Gen 0 akan dipromosikan ke Gen 1.
- **Generation 2 (Gen 2)**:
  Menyimpan objek berumur panjang (misalnya *singleton*, *static references*, objek *cache*, thread pools). GC pada Gen 2 dikenal sebagai **Full GC**, yang menginspeksi seluruh generasi (Gen 0, 1, dan 2). Proses ini paling mahal dari sisi siklus CPU dan latensi.
- **Large Object Heap (LOH)**:
  Objek berukuran $\ge 85.000$ byte langsung dialokasikan di LOH. LOH dikumpulkan bersamaan dengan Gen 2. Secara historis, LOH tidak dikompaksi (*non-compacted*) secara *default* karena biaya penyalinan memori yang tinggi, sehingga rentan terhadap fragmentasi.
- **Pinned Object Heap (POH)**:
  Diperkenalkan pada .NET 5, segmen khusus untuk menampung objek yang dialokasikan dalam status *pinned* (alamat memori tidak boleh dipindah oleh GC), mencegah fragmentasi pada Gen 0/1/2.

### 2. Implementasi & Contoh Kasus Nyata

Kode berikut mendemonstrasikan bagaimana siklus hidup variabel, pemindahan generasi objek, serta perbedaan mutasi memori antara Stack dan Managed Heap terjadi di .NET modern.

```csharp
using System;
using System.Diagnostics;

namespace MemoryArchitectureDemo
{
    // Struct: Dialokasikan di Stack jika digunakan sebagai variabel lokal
    public readonly struct PointValue
    {
        public readonly int X;
        public readonly int Y;

        public PointValue(int x, int y) => (X, Y) = (x, y);
    }

    // Class: Objek selalu dialokasikan di Managed Heap
    public sealed class CustomerNode
    {
        public int Id { get; set; }
        public string Name { get; set; }

        public CustomerNode(int id, string name) => (Id, Name) = (id, name);
    }

    public static class Program
    {
        public static void Main()
        {
            Console.WriteLine($"=== GC Generations Lifecycle & Profiling ===");

            // 1. Stack Allocation (Value Type)
            PointValue point = new PointValue(10, 20); 
            // 'point' berada langsung di stack frame method Main. Tidak memicu GC.

            // 2. Heap Allocation (Gen 0)
            CustomerNode shortLived = new CustomerNode(101, "Alice");
            Console.WriteLine($"Generasi awal shortLived: Gen {GC.GetGeneration(shortLived)}"); // Gen 0

            // Catat metrik GC sebelum beban kerja
            int gen0Before = GC.CollectionCount(0);
            int gen1Before = GC.CollectionCount(1);
            int gen2Before = GC.CollectionCount(2);

            // 3. Simulasi beban kerja: Objek short-lived mati, objek referensi bertahan
            CustomerNode longLived = new CustomerNode(999, "Database-Cache-Root");

            // Mengisi Gen 0 untuk memicu GC ephemeral
            for (int i = 0; i < 50_000; i++)
            {
                // Objek teralokasi di Gen 0 dan langsung kehilangan root referensinya
                var temp = new CustomerNode(i, "Transient");
            }

            // Objek 'longLived' diakses kembali agar root-nya tetap hidup
            Console.WriteLine($"Generasi longLived pasca-alokasi massal: Gen {GC.GetGeneration(longLived)}");

            // Memaksa satu siklus pengumpulan Gen 0
            GC.Collect(0, GCCollectionMode.Forced);
            Console.WriteLine($"Generasi longLived pasca GC Gen 0: Gen {GC.GetGeneration(longLived)}"); // Naik ke Gen 1

            // Memaksa pengumpulan hingga Gen 1
            GC.Collect(1, GCCollectionMode.Forced);
            Console.WriteLine($"Generasi longLived pasca GC Gen 1: Gen {GC.GetGeneration(longLived)}"); // Naik ke Gen 2

            // Menampilkan statistik koleksi yang terjadi
            Console.WriteLine("\n=== Statistik Frekuensi GC ===");
            Console.WriteLine($"Gen 0 Delta: {GC.CollectionCount(0) - gen0Before}");
            Console.WriteLine($"Gen 1 Delta: {GC.CollectionCount(1) - gen1Before}");
            Console.WriteLine($"Gen 2 Delta: {GC.CollectionCount(2) - gen2Before}");

            // Menjaga referensi agar tidak dioptimasi/dihapus oleh JIT sebelum baris ini
            GC.KeepAlive(point);
            GC.KeepAlive(longLived);
        }
    }
}
```

#### Penjelasan Alur Eksekusi:
1. `PointValue point`: Dialokasikan langsung di *Stack Frame* fungsi `Main`. Begitu `Main` selesai dieksekusi, pointer stack bergeser dan memori langsung bebas tanpa melibatkan GC.
2. `shortLived` dan `longLived`: Dialokasikan pada Gen 0 Managed Heap. Alamat memorinya dipegang oleh variabel referensi lokal di stack.
3. Saat *loop* 50.000 iterasi berjalan, alokasi objek memicu batas ambang (*budget threshold*) Gen 0. GC berjalan secara otomatis.
4. Objek `longLived` yang masih memiliki GC Root (karena dipanggil kembali di baris bawahnya) berhasil bertahan hidup (*survive*), sehingga metadata header-nya diperbarui dan posisinya dipromosikan bertahap: **Gen 0 $\rightarrow$ Gen 1 $\rightarrow$ Gen 2**.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Fase Siklus Garbage Collection
Ketika batas alokasi terlampaui pada suatu generasi, GC menghentikan sementara thread aplikasi (*Stop-The-World* / Safe-Points, kecuali pada konfigurasi Background GC) dan menjalankan 3 fase:

```
[ Phase 1: MARK ]
GC Roots (Stack, Registers, Statics) 
   │
   ├──> Objek A (Hidup) ──> Objek B (Hidup)
   └──> Objek C (Hidup)
   [ Objek D, E tidak terjangkau -> SAMPAH ]

[ Phase 2: SWEEP / RECLAIM ]
Mengidentifikasi slot memori dari Objek D & E sebagai ruang kosong.

[ Phase 3: COMPACT (Opsional)]
Memindahkan Objek A, B, C agar berdampingan.
Menyesuaikan pointer referensi agar tidak terjadi fragmentasi.
```

1. **Mark Phase (Penandaan)**:
   GC menelusuri seluruh **GC Roots**:
   - Register CPU aktif.
   - Variabel lokal bertipe referensi pada *Stack frame* yang sedang aktif.
   - Variabel `static`.
   - Tabel *Finalization Queue* dan *GCHandle*.
   Setiap objek yang terjangkau ditandai (*marked*) pada bit array metadata internal (*Mark Table*). Objek yang tidak memiliki rute keterjangkauan dianggap sampah (*garbage*).

2. **Plan & Sweep Phase (Penyapuan)**:
   GC menganalisis efisiensi kompresi. Jika fragmentasi terdeteksi tinggi, fase pemadatan (*compaction*) dijadwalkan. Jika tidak, blok memori objek mati langsung ditandai sebagai *free list* untuk digunakan kembali oleh alokasi berikutnya.

3. **Compact Phase (Pemadatan)**:
   Objek-objek yang bertahan digeser secara fisik di memori agar berdampingan (*contiguous*). Pointer alokasi (*allocation pointer*) disetel ulang. Semua referensi di *stack* dan di dalam objek lain yang merujuk ke memori tersebut diperbarui (*pointer fixing*) ke alamat baru.

#### Card Tables & Generational Cross-References
Bagaimana GC bisa mengumpulkan Gen 0 tanpa memindai seluruh Gen 2 untuk mencari tahu apakah ada objek lama yang mereferensikan objek baru?
CLR menggunakan **Card Table**:
- Memori dibagi menjadi "kartu-kartu" (masing-masing bernilai 512 byte).
- Setiap kali Anda menulis kode `oldObj.Child = newObj;`, JIT compiler menyisipkan **Card Table Write Barrier**.
- Bit untuk *card* tersebut ditandai (*dirtied*).
- Saat GC Gen 0 berjalan, engine GC hanya memindai *dirty cards* pada Gen 2, bukan seluruh ruang Gen 2.

#### Trade-offs: Server GC vs Workstation GC
- **Workstation GC**: Dioptimalkan untuk responsivitas UI dan latensi rendah. Menggunakan satu GC thread bersama thread aplikasi, memiliki jeda *Stop-the-World* yang minimal namun throughput pengolahan data lebih lambat.
- **Server GC**: Dioptimalkan untuk *throughput* tinggi pada aplikasi backend (ASP.NET Core). Managed Heap dipartisi berdasarkan jumlah logical CPU core; setiap core memiliki dedicated heap (Gen 0, 1, 2) dan dedicated GC thread. Dampaknya: alokasi memori paralel sangat cepat, namun konsumsi total memori proses (*working set*) menjadi jauh lebih tinggi.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Value Types yang Ringkas dan Tepat Sasaran**: Manfaatkan `readonly struct` untuk data kecil ($\le 16$ byte) yang bersifat *immutable* guna menghindari pembebanan pada Heap.
- **Manfaatkan Memory Pooling**: Gunakan `ArrayPool<T>.Shared` untuk buffer array temporer yang sering dibuat dan dihancurkan. Ini mencegah *churn* pada Gen 0 dan mencegah lonjakan alokasi ke LOH.
- **Gunakan `Span<T>` dan `ReadOnlySpan<T>`**: Memungkinkan operasi *slicing* pada memori stack, array, atau native string tanpa mengalokasikan string/substring baru di heap.

#### Don'ts
- **Menghindari Mid-Life Crisis**: Situasi di mana objek sementara (*short-lived*) tidak sempat mati di Gen 0 karena GC terlambat berjalan, sehingga dipromosikan ke Gen 1 atau Gen 2. Objek ini membebani siklus Full GC. Hindari menahan objek sementara ke scope yang terlalu luas.
- **Jangan Memanggil `GC.Collect()` Secara Manual di Production**: CLR memiliki algoritma otomatis untuk menghitung *budget* generasi secara heuristik berdasarkan karakteristik beban kerja. Memanggil `GC.Collect()` merusak pola adaptif engine tersebut dan sering kali memicu penalti latensi yang parah.
- **Hindari Memory Leak Melalui Event Handler & Static Fields**: Menempelkan event handler pada publisher yang berumur panjang (misal: *static event*) dari subscriber berumur pendek membuat objek subscriber tersebut tidak bisa di-GC karena GC Roots terus menganggapnya hidup.

#### Edge Cases
- **Boxing/Unboxing**: Mengoper `struct` ke parameter bertipe `object` atau *interface* memaksa CLR membungkus *value type* tersebut ke dalam instance baru di Heap (Gen 0).
  ```csharp
  int value = 42;
  // Menghasilkan alokasi heap tersembunyi karena boxing:
  Console.WriteLine(string.Format("Angka: {0}", value)); 
  ```
- **LOH Fragmentation**: Mengalokasikan array berukuran besar ($\ge 85.000$ byte) secara berulang dengan ukuran bervariasi dapat menyebabkan fragmentasi LOH. Jika LOH terfragmentasi, CLR akan gagal mendapatkan blok memori yang kontinu meskipun memori bebas total masih cukup, memicu `OutOfMemoryException`.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Alokasi Memori dengan BenchmarkDotNet**:
   - Buat sebuah proyek console baru dan pasang library `BenchmarkDotNet`.
   - Bandingkan performa dan alokasi memori antara pemrosesan string menggunakan konkatenasi standar (`+`), `StringBuilder`, dan manipulasi berbasis `ReadOnlySpan<char>`.
   - Amati kolom `Allocated`, `Gen 0`, `Gen 1`, dan `Gen 2` pada laporan *benchmark*.

2. **Deteksi Mid-Life Crisis dengan Dotnet Counters**:
   - Jalankan perintah CLI: `dotnet-counters monitor -p <PID> --counters System.Runtime`.
   - Tulis skrip loop yang mengalokasikan objek berukuran sedang (misal: byte array 40 KB) dan tahan referensinya selama 50 milidetik sebelum dilepas.
   - Amati bagaimana `GC Cumulative Allocation Rate` dan rasio kenaikan koleksi `Gen 1 / Gen 2 Collections` berfluktuasi secara real-time.
