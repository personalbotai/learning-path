### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur *distributed systems* dan *container orchestration* (seperti Kubernetes), aplikasi tidak lagi dipandang sebagai entitas statis. Runtime orkestrator memerlukan sinyal deterministik untuk mengetahui:
1. Kapan aplikasi harus menerima trafik jaringan? (*Readiness*)
2. Kapan proses aplikasi macet (*deadlock/hang*) dan harus di-*restart*? (*Liveness*)
3. Bagaimana performa internal runtime dan domain aplikasi bekerja dari waktu ke waktu? (*Metrics*)

```
               [ Orchestrator / K8s ]
                     |          |
         Liveness    |          | Readiness
         (/health/live)         (/health/ready)
                     v          v
   +-------------------------------------------------------+
   | ASP.NET Core Runtime Host                             |
   |                                                       |
   |  +-------------------------------------------------+  |
   |  | HealthCheck Middleware                          |  |
   |  |   -> IHealthCheck (Tags: "live") -> Fast Check  |  |
   |  |   -> IHealthCheck (Tags: "ready") -> DB / Broker|  |
   |  +-------------------------------------------------+  |
   |                                                       |
   |  +-------------------------------------------------+  |
   |  | System.Diagnostics.Metrics (OpenTelemetry API)  |  |
   |  |   -> Meter ("OrderService")                     |  |
   |  |        -> Counter<long> ("orders-created")      |  |
   |  |        -> Histogram<double> ("processing-time") |  |
   |  +-------------------------------------------------+  |
   +---------------------------|---------------------------+
                               | (Scrape / Push)
                               v
                  [ Prometheus / OTEL Collector ]
```

#### Health Checks Architecture
.NET menyediakan abstraksi `IHealthCheck` via paket `Microsoft.Extensions.Diagnostics.HealthChecks`. Arsitekturnya berpusat pada `HealthCheckService`, sebuah *singleton/hosted service* yang mengeksekusi kumpulan registrasi `HealthCheckRegistration`.
- **Liveness Probe**: Memvalidasi integritas internal proses ASP.NET Core (misal: apakah CLR masih responsif, tidak ada fatal *deadlock* thread pool). Liveness **tidak boleh** bergantung pada dependensi eksternal (seperti SQL Server atau Redis).
- **Readiness Probe**: Memvalidasi apakah aplikasi siap memproses *request* (misal: koneksi database sudah terbentuk, migrasi skema selesai, cache lokal sudah terisi). Jika gagal, orkestrator akan mencabut pod dari *service endpoint* tanpa mematikan proses.

#### Metrics Architecture (`System.Diagnostics.Metrics`)
Sejak .NET 6, arsitektur metrik distandarisasi menggunakan API `System.Diagnostics.Metrics`, menggantikan `PerformanceCounters` (Windows-only) dan `EventCounters`. Arsitektur ini sepenuhnya selaras dengan spesifikasi OpenTelemetry:
- **`Meter`**: Namespace logis untuk instrumen (analog dengan `ILoggerFactory` atau `ActivitySource`).
- **Instruments**:
  - `Counter<T>` / `UpDownCounter<T>`: Nilai monotonik meningkat (misal: total HTTP requests, alokasi memori aktif).
  - `Histogram<T>`: Distribusi statistik nilai (misal: latensi eksekusi *database query*, ukuran payload).
  - `ObservableGauge<T>`: Pengambilan sampel asinkron non-blocking terhadap nilai saat ini (misal: ukuran connection pool aktif saat di-*scrape*).
- **Decoupled Architecture**: `Meter` tidak mengetahui ke mana data dikirim. Data hanya dikonsumsi jika ada `MeterListener` (misal: OpenTelemetry .NET SDK Prometheus Exporter) yang aktif mendengarkan.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi Health Checks berbasis tag (memisahkan Liveness dan Readiness) serta pelacakan metrik kustom menggunakan `System.Diagnostics.Metrics`.

```csharp
// Program.cs
using System.Diagnostics.Metrics;
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Microsoft.Extensions.Diagnostics.HealthChecks;
using System.Text.Json;

var builder = WebApplication.CreateBuilder(args);

// 1. Registrasi Metrics (Domain & Infrastructure)
builder.Services.AddSingleton<OrderMetrics>();

// 2. Registrasi Health Checks dengan Tags
builder.Services.AddHealthChecks()
    // Liveness: Sangat ringan, cek proses internal
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    // Readiness: Cek infrastruktur eksternal (Database, Cache)
    .AddCheck<DatabaseHealthCheck>("sql_database", 
        failureStatus: HealthStatus.Unhealthy, 
        tags: ["ready"], 
        timeout: TimeSpan.FromSeconds(3));

var app = builder.Build();

// Mapping Endpoints Health Check
// Liveness: /health/live -> hanya mengeksekusi tag "live"
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live"),
    ResponseWriter = WriteHealthResponse
});

// Readiness: /health/ready -> mengeksekusi tag "ready"
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready"),
    ResponseWriter = WriteHealthResponse
});

// Minimal API Bisnis yang merekam Metrik
app.MapPost("/orders", async (OrderRequest request, OrderMetrics metrics) =>
{
    var stopwatch = System.Diagnostics.Stopwatch.StartNew();
    
    // Simulasi pemrosesan order
    await Task.Delay(Random.Shared.Next(50, 150));
    
    stopwatch.Stop();

    // Rekam instrumen metrics
    metrics.OrderCreated(request.Category, stopwatch.Elapsed.TotalMilliseconds);

    return Results.Created($"/orders/{Guid.NewGuid()}", request);
});

app.Run();

// -------------------------------------------------------------
// Definisi Metrik Domain
// -------------------------------------------------------------
public sealed class OrderMetrics
{
    private const string MeterName = "ECommerce.Sales";
    private readonly Meter _meter;
    private readonly Counter<long> _orderCounter;
    private readonly Histogram<double> _orderProcessingDuration;

    public OrderMetrics(IMeterFactory meterFactory)
    {
        // IMeterFactory (.NET 8+) memastikan lifecycle Meter terikat pada DI scope yang benar
        _meter = meterFactory.Create(MeterName);
        
        _orderCounter = _meter.CreateCounter<long>(
            name: "sales.orders.created", 
            unit: "{order}", 
            description: "Total jumlah pesanan yang berhasil diproses");

        _orderProcessingDuration = _meter.CreateHistogram<double>(
            name: "sales.orders.duration", 
            unit: "ms", 
            description: "Durasi pemrosesan pesanan dalam milidetik");
    }

    public void OrderCreated(string category, double durationMs)
    {
        // TagList mengoptimalkan alokasi heap saat menambahkan dimensi data
        var tags = new TagList
        {
            { "category", category },
            { "environment", Environment.GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT") ?? "Production" }
        };

        _orderCounter.Add(1, tags);
        _orderProcessingDuration.Record(durationMs, tags);
    }
}

// -------------------------------------------------------------
// Custom Readiness Health Check
// -------------------------------------------------------------
public sealed class DatabaseHealthCheck : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, 
        CancellationToken cancellationToken = default)
    {
        try
        {
            // Simulasi ping/query: "SELECT 1" menggunakan CancellationToken
            await Task.Delay(40, cancellationToken); 
            
            // Mengirim data diagnostik terstruktur jika diperlukan
            var data = new Dictionary<string, object>
            {
                { "latency_ms", 40 },
                { "active_connections", 12 }
            };

            return HealthCheckResult.Healthy("Database SQL Server responsif.", data);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            return HealthCheckResult.Unhealthy("Pemeriksaan database mengalami timeout.");
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("Koneksi database gagal terhubung.", ex);
        }
    }
}

public record OrderRequest(string Category, decimal Amount);

// Serializer JSON terstruktur untuk orkestrator/monitoring agent
internal static class HealthResponseFormatter
{
    public static Task WriteHealthResponse(HttpContext context, HealthReport report)
    {
        context.Response.ContentType = "application/json";
        
        var payload = new
        {
            status = report.Status.ToString(),
            totalDurationMs = report.TotalDuration.TotalMilliseconds,
            checks = report.Entries.Select(e => new
            {
                name = e.Key,
                status = e.Value.Status.ToString(),
                description = e.Value.Description,
                durationMs = e.Value.Duration.TotalMilliseconds,
                data = e.Value.Data,
                error = e.Value.Exception?.Message
            })
        };

        return context.Response.WriteAsync(JsonSerializer.Serialize(payload, new JsonSerializerOptions 
        { 
            PropertyNamingPolicy = JsonNamingPolicy.CamelCase, 
            WriteIndented = true 
        }));
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **HealthCheck Execution**: `DefaultHealthCheckService` mengiterasi setiap `HealthCheckRegistration`. Pemeriksaan dieksekusi secara asinkron. Jika dikonfigurasi, middleware menjalankan seluruh health check terdaftar secara paralel via `Task.WhenAll`. Setiap check dibungkus batas waktu internal (`timeout`) yang memicu pembatalan `CancellationToken` jika dependensi gagal merespons tepat waktu.
- **Metrics Emission**: Saat `_orderCounter.Add(1, tags)` dieksekusi:
  1. Engine runtime mengecek apakah ada `MeterListener` yang aktif berlangganan pada instrumen tersebut.
  2. Jika **tidak ada listener**, overhead operasi ini mendekati *zero-cost* (hanya berupa pengecekan pointer null/boolean flag sederhana di memori).
  3. Jika **ada listener** (misal OpenTelemetry), instrumen mengevaluasi nilai dan menyalurkannya langsung ke agregator in-memory milik listener secara *thread-safe* menggunakan instruksi atomik (interlocked operations).

#### Alokasi Memori / Resource
- **TagList vs Dictionary/Object Array**: Pada .NET modern, gunakan struct `System.Diagnostics.TagList`. `TagList` mengalokasikan array hingga 8 pasangan *key-value* langsung di stack (menggunakan *inline buffer* internal), sehingga tidak memicu alokasi heap (`0 B allocations`) untuk dimensi metrik standar.
- **Health Checks Polling Overhead**: Health check endpoint yang terlalu sering di-scrape oleh orkestrator dapat memicu degradasi performa jika membuka *physical connection* baru terus-menerus. Gunakan connection pooling bawaan client driver (misal: Npgsql, Microsoft.Data.SqlClient).

#### Trade-offs
- **Fail-Fast vs Cascade Failure**: Menempatkan dependency checks (DB, Third-party API) di endpoint *Liveness* adalah anti-pattern berat. Jika database mengalami network hiccup selama 10 detik, Liveness probe gagal, Kubernetes me-restart pod. Semua pod me-restart secara bersamaan (*crash-looping* massal) dan memicu *thundering herd problem* ke database saat kembali aktif.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Pisahkan Liveness dan Readiness**: Liveness harus selalu bernilai 200 OK selama thread CLR masih bernapas. Delegasikan semua pengecekan downstream I/O ke Readiness.
- **Terapkan Strict Timeout**: Selalu tentukan batas waktu maksimum pada health check eksternal (misal: maksimum 2-3 detik). Database yang menggantung tidak boleh menahan health check service hingga HTTP client timeout.
- **Manfaatkan `IMeterFactory`**: Hindari instansiasi `new Meter(...)` secara statis di sembarang tempat. Gunakan `IMeterFactory` melalui Dependency Injection agar meter terikat pada lifecycle runtime host dan mudah di-mock dalam unit test.

#### Don'ts
- **Don't Cause High Cardinality di Metrics**:
  ```csharp
  // KESALAHAN FATAL: Memasukkan User ID, GUID, Email, atau Order ID ke Tags
  var badTags = new TagList { { "user_id", userId.ToString() } };
  _orderCounter.Add(1, badTags); 
  ```
  Setiap kombinasi unik dari label/tag akan membuat deret waktu (*time-series*) baru di database metrik (Prometheus/Datadog). Ribuan nilai unik akan menghabiskan memori TSDB (*Out Of Memory*). Gunakan tag hanya untuk nilai dengan batas variasi yang rendah (*low-cardinality*) seperti `status_code`, `payment_method`, atau `region`.

#### Edge Cases
- **Database Connection Pool Starvation**: Health check mengeksekusi query `SELECT 1`. Namun, jika connection pool aplikasi habis akibat beban trafik tinggi, health check akan masuk antrean tunggu pool (*pool starvation*), memicu timeout, dan salah diidentifikasi sebagai database mati padahal hanya pool lokal yang jenuh.
  - *Mitigasi*: Berikan bobot status `HealthStatus.Degraded` alih-alih `HealthStatus.Unhealthy` pada kondisi saturasi koneksi.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Health Check Caching dengan Dekorasinya**:
   Buat custom decorator untuk `IHealthCheck` yang meng-cache status hasil eksekusi (misalnya selama 15 detik). Jika ada 3 node orkestrator yang me-request probe `/health/ready` hampir bersamaan, query fisik ke dependensi eksternal hanya dilakukan satu kali.
2. **Kustomisasi ObservableGauge untuk CLR Memory Profiling**:
   Gunakan `_meter.CreateObservableGauge` untuk memonitor ukuran *Large Object Heap* (LOH) dan frekuensi *Garbage Collection Gen 2* secara asinkron tanpa membebani eksekusi thread request reguler. Bandingkan performanya terhadap pembacaan manual via `GC.GetGCMemoryInfo()`.
