### 1. Konsep & Arsitektur Mendalam

Sebelum adanya *Task-based Asynchronous Pattern* (TAP) dengan kata kunci `async` dan `await` di C# 5.0, pemrograman asinkron bergantung pada pola rumit seperti APM (*Asynchronous Programming Model* via `Begin`/`End`) dan EAP (*Event-based Asynchronous Pattern*). Pola-pola ini memecah alur kontrol (*control flow*), menyulitkan penanganan eksepsi, dan memicu *callback hell*.

`async` dan `await` bukan fitur runtime murni, melainkan fitur compiler tingkat tinggi (sintaksis gula) yang didukung oleh CLR (*Common Language Runtime*). Fitur ini dirancang untuk memecahkan masalah esensial: **efisiensi utilisasi thread pada operasi terikat I/O (*I/O-bound*) dan latensi tinggi**.

```
[ Thread Pool Worker ] ──> Eksekusi baris sebelum await
                                 │
                                 ▼
                     await Task.Delay() / I/O Read
                                 │
                   ┌─────────────┴─────────────┐
                   ▼                           ▼
      (Selesai Sinkron?)             (Operasi Menunggu/Pending)
                   │                           │
                   ├─ YES ──> Lanjut eksekusi  ├─ NO ──> Return Task belum selesai
                   │          tanpa yield.     │         Thread Worker KEMBALI ke Pool!
                   │                           │         (Bebas memproses request lain)
                   │                           ▼
                   │                I/O Completion Port (IOCP)
                   │                memicu callback via OS kernel
                   │                           │
                   │                           ▼
                   └─────────────────> [ Resume di MoveNext() ]
                                       Ambil thread worker baru / sync context
```

#### Paradigma Non-Blocking I/O
Ketika thread memanggil operasi I/O sinkron (misalnya `FileStream.Read` atau `HttpClient.Send`), thread tersebut masuk ke status *kernel wait* (*blocked*). Setiap thread di .NET memakan memori stack sekitar 1 MB secara default (di Windows x64) serta beban *context-switching* di level kernel CPU. Jika 1.000 thread melakukan I/O sinkron secara bersamaan, aplikasi mengonsumsi ~1 GB memori hanya untuk stack thread yang menganggur (*idle*), memicu *thread pool starvation*.

Dengan `async` dan `await`:
1. Saat compiler mendeteksi `await`, ia membagi metode menjadi beberapa segmen kelanjutan (*continuation*).
2. Jika operasi yang di-`await` belum selesai, thread saat ini dilepaskan (*yield*) kembali ke `ThreadPool` untuk melayani pekerjaan lain.
3. Operasi I/O di tingkat OS didaftarkan ke IOCP (*I/O Completion Ports* di Windows) atau `epoll`/`io_uring` di Linux. Tidak ada thread aktif yang menunggu di memori aplikasi.
4. Ketika I/O selesai, hardware interrupt memberi sinyal ke OS kernel, OS kernel memberitahu runtime via IOCP thread, dan runtime menjadwalkan eksekusi kelanjutan metode tersebut ke `ThreadPool` (atau *SynchronizationContext* yang sesuai).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi layanan pengambilan data multi-sumber dengan agregasi paralel dan penanganan *cancellation*.

```csharp
using System;
using System.IO;
using System.Net.Http;
using System.Text.Json;
using System.Threading;
using System.Threading.Tasks;

public sealed record UserProfile(int Id, string Username, string Email);

public sealed class UserProfileService
{
    private readonly HttpClient _httpClient;

    public UserProfileService(HttpClient httpClient)
    {
        _httpClient = httpClient ?? throw new ArgumentNullException(nameof(httpClient));
    }

    public async Task<UserProfile> FetchUserProfileAsync(int userId, CancellationToken cancellationToken = default)
    {
        // 1. Validasi input - dijalankan secara sinkron sebelum ada penundaan
        if (userId <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(userId), "User ID harus bernilai positif.");
        }

        string endpoint = $"https://jsonplaceholder.typicode.com/users/{userId}";

        // 2. Operasi I/O pertama: Mengambil HTTP Response Headers secara streaming
        // Gunakan HttpCompletionOption.ResponseHeadersRead untuk mencegah buffering seluruh payload ke memori
        using HttpResponseMessage response = await _httpClient.GetAsync(
            endpoint, 
            HttpCompletionOption.ResponseHeadersRead, 
            cancellationToken
        ).ConfigureAwait(false);

        response.EnsureSuccessStatusCode();

        // 3. Operasi I/O kedua: Membaca stream respons secara asinkron
        await using Stream contentStream = await response.Content
            .ReadAsStreamAsync(cancellationToken)
            .ConfigureAwait(false);

        // 4. Deserialisasi stream JSON non-blocking langsung dari network stream buffer
        var options = new JsonSerializerOptions { PropertyNameCaseInsensitive = true };
        
        UserProfile? profile = await JsonSerializer.DeserializeAsync<UserProfile>(
            contentStream, 
            options, 
            cancellationToken
        ).ConfigureAwait(false);

        return profile ?? throw new InvalidOperationException("Payload user tidak valid atau kosong.");
    }
}

public class Program
{
    public static async Task Main()
    {
        using var httpClient = new HttpClient();
        var service = new UserProfileService(httpClient);
        using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));

        try
        {
            Console.WriteLine($"[Thread: {Environment.CurrentManagedThreadId}] Memulai fetch profile...");
            UserProfile profile = await service.FetchUserProfileAsync(1, cts.Token);
            Console.WriteLine($"[Thread: {Environment.CurrentManagedThreadId}] Sukses: {profile.Username} ({profile.Email})");
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine("Permintaan dibatalkan karena timeout.");
        }
        catch (HttpRequestException ex)
        {
            Console.WriteLine($"HTTP Error: {ex.Message}");
        }
    }
}
```

#### Penjelasan Komponen Kunci:
- **`HttpCompletionOption.ResponseHeadersRead`**: Menginstruksikan `HttpClient` untuk menyelesaikan Task segera setelah header HTTP diterima, tanpa memblokir menunggu payload body diunduh seluruhnya.
- **`ConfigureAwait(false)`**: Memberitahu state machine bahwa kelanjutan metode (*continuation*) tidak memerlukan pemulihan konteks asal (*SynchronizationContext* / *TaskScheduler*). Mengurangi overhead context dispatch dan mencegah deadlocks pada aplikasi non-console.
- **`await using`**: Mengimplementasikan `IAsyncDisposable`. Pembersihan unmanaged resources (seperti flush stream network) dilakukan secara asinkron tanpa memblokir thread.

### 3. Cara Kerja di Balik Layar (Under the Hood)

Ketika Anda menambahkan modifier `async` pada metode, compiler Roslyn membongkar (*lowering*) metode tersebut secara radikal menjadi sebuah `struct` yang mengimplementasikan antarmuka runtime internal: `IAsyncStateMachine`.

#### Anatomi Roslyn Transformation
Sebuah metode sederhana:
```csharp
public async Task<int> CalculateAsync()
{
    int a = 10;
    await Task.Delay(100);
    return a + 5;
}
```

Ditransformasikan oleh compiler ke struktur konseptual berikut:

```csharp
[StructLayout(LayoutKind.Auto)]
private struct <CalculateAsync>d__0 : IAsyncStateMachine
{
    public int <>1__state;
    public AsyncTaskMethodBuilder<int> <>t__builder;
    
    // Variabel lokal 'a' diangkat (hoisted) menjadi field struct
    public int <a>5__1;
    
    private TaskAwaiter <>u__1;

    public void MoveNext()
    {
        int num = <>1__state;
        int result;
        try
        {
            TaskAwaiter awaiter;
            if (num != 0)
            {
                // Bagian awal metode
                <a>5__1 = 10;
                awaiter = Task.Delay(100).GetAwaiter();
                
                if (!awaiter.IsCompleted)
                {
                    // STATE 0: Menandai bahwa eksekusi sedang yield pada awaiter pertama
                    num = (<>1__state = 0);
                    <>u__1 = awaiter;
                    
                    // Mendaftarkan struct ini ke builder untuk dipanggil kembali saat awaiter selesai
                    <>t__builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
                    return; // THREAD KELUAR DARI METODE DI SINI!
                }
            }
            else
            {
                // STATE RESUMPTION: Dipanggil kembali ketika Task.Delay selesai
                awaiter = <>u__1;
                <>u__1 = default;
                num = (<>1__state = -1);
            }

            // Mendapatkan hasil dari awaiter (atau melempar exception jika ada kegagalan)
            awaiter.GetResult();
            
            // Eksekusi kode setelah await
            result = <a>5__1 + 5;
        }
        catch (Exception exception)
        {
            <>1__state = -2;
            <>t__builder.SetException(exception);
            return;
        }

        <>1__state = -2;
        <>t__builder.SetResult(result);
    }

    public void SetStateMachine(IAsyncStateMachine stateMachine) =>
        <>t__builder.SetStateMachine(stateMachine);
}
```

#### Eksekusi & Runtime Flow
1. **Inisialisasi**: State machine dimulai pada `<>1__state = -1`. Compiler mengeksekusi metode secara sinkron sampai titik `await` pertama tercapai.
2. **Synchronous Fast Path**: Method builder memeriksa `awaiter.IsCompleted`. Jika task sudah berstatus selesai (misalnya hasil cache atau `Task.FromResult`), tidak ada alokasi heap atau thread-switch. Eksekusi berlanjut langsung ke baris berikutnya secara sinkron.
3. **Suspension (Yielding)**: Jika `IsCompleted == false`, status diubah (`<>1__state = 0`), dan builder memanggil `AwaitUnsafeOnCompleted`.
4. **Resumption**: Ketika operasi asinkron selesai, subsistem CLR memanggil `MoveNext()`. Berdasarkan nilai `state` yang tersimpan, alur melompat ke label eksekusi yang sesuai untuk membaca hasil `GetResult()`.

#### Alokasi Memori & Lifting (Boxing)
- **Local Variable Hoisting**: Setiap variabel lokal yang hidup melintasi batas `await` (seperti variabel `a`) harus disimpan di field struct state machine agar nilainya tidak hilang saat stack frame metode dihancurkan saat proses yielding.
- **Stack-to-Heap Boxing**: State machine Roslyn awalnya dibuat sebagai `struct` di stack thread. Jika operasi selesai secara sinkron, **nol alokasi memori heap** terjadi. Namun, jika operasi tertunda (*pending*), `AsyncTaskMethodBuilder` terpaksa melakukan boxing terhadap struct state machine ini ke GC Heap (`IAsyncStateMachineBox<T>`) agar kelanjutannya dapat direferensikan oleh callback Task.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `ValueTask<T>` untuk metode yang sering selesai secara sinkron**: Jika metode membaca dari cache in-memory 95% dari waktu eksekusi dan hanya 5% lewat jaringan, `ValueTask<T>` menghilangkan alokasi objek `Task<T>` di heap pada jalur sinkron.
- **Selalu forward `CancellationToken`**: Pastikan token pembatalan diteruskan ke seluruh rantai panggilan asinkron terdalam (seperti I/O sockets, stream reads, dan query database).
- **Gunakan `ConfigureAwait(false)` pada Non-UI Frameworks/Libraries**: Mengabaikan capture context (`SynchronizationContext`) menurunkan alokasi dan meningkatkan performa throughput aplikasi backend (ASP.NET Core sudah tidak memiliki SynchronizationContext, tetapi library class tetap wajib menggunakannya untuk portabilitas).

#### Don'ts
- **Hindari `async void`**: 
  Metode `async void` hanya diperuntukkan bagi Event Handlers GUI. Eksepsi yang terjadi di dalam `async void` tidak dapat ditangkap oleh blok `try-catch` di luar pemanggil dan akan langsung mengeksekusi `AppDomain.UnhandledException`, yang secara default **mematikan seluruh proses aplikasi**. Selalu gunakan `async Task`.
- **Hindari Sync-Over-Async (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`)**:
  Memanggil properti result secara sinkron memblokir thread pemanggil. Di runtime dengan SynchronizationContext (seperti .NET Framework MVC lama, WPF, WinForms), hal ini menyebabkan **Deadlock** karena thread yang diblokir sedang menunggu task selesai, sedangkan continuation task tersebut mencoba mengakses thread yang sedang diblokir tersebut. Di runtime modern (ASP.NET Core), pola ini menyebabkan *ThreadPool starvation*.

#### Edge Cases: Exception Handling & Unobserved Exceptions
Ketika beberapa operasi di-`await` via `Task.WhenAll`, jika dua atau lebih task melempar exception:
```csharp
Task task1 = Task.FromException(new InvalidOperationException());
Task task2 = Task.FromException(new ArgumentException());

try 
{
    await Task.WhenAll(task1, task2);
}
catch (Exception ex)
{
    // AWAS: 'ex' HANYA akan merefleksikan exception PERTAMA (InvalidOperationException)!
    // ArgumentException akan tertelan kecuali membaca Task.WhenAll().Exception.InnerExceptions
}
```
`await` mengekstrak exception tunggal pertama dari `AggregateException` untuk menjaga ergonomi kode. Jika Anda memerlukan visibilitas seluruh kegagalan, simpan referensi `Task` dari `Task.WhenAll` dan periksa properti `.Exception`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Sharplab.io**: 
   Kunjungi [sharplab.io](https://sharplab.io). Tulis fungsi `async Task<string> GetDataAsync()` yang memiliki dua `await` terpisah dengan satu variabel lokal di antaranya. Beralihlah ke mode *Release* dan periksa bagaimana Roslyn mengonversi variabel lokal tersebut menjadi field dari `struct` internal, serta bagaimana switch-case diatur di dalam `MoveNext()`.
2. **Deteksi Boxing Overhead**:
   Buat dua metode: satu mengembalikan `Task<int>` dan satu mengembalikan `ValueTask<int>`. Keduanya langsung mengembalikan `42` tanpa melakukan await I/O. Gunakan **BenchmarkDotNet** untuk mengukur alokasi heap (GC Gen 0) antara keduanya. Amati mengapa `ValueTask` menghasilkan 0 bytes allocation.
3. **Eksperimen Custom Awaiter**:
   Pelajari bahwa C# tidak membatasi `await` hanya untuk `Task`. Anda bisa meng-`await` tipe apa pun selama tipe tersebut memiliki metode `GetAwaiter()` yang mengembalikan objek dengan antarmuka/pola:
   - `bool IsCompleted { get; }`
   - `void OnCompleted(Action continuation)`
   - `T GetResult()`
   Implementasikan custom awaiter sederhana untuk `TimeSpan` sehingga Anda bisa menulis: `await TimeSpan.FromSeconds(2);`.
