## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

SOLID adalah akronim dari lima prinsip desain berorientasi objek yang diperkenalkan oleh Robert C. Martin (Uncle Bob): **Single Responsibility Principle (SRP)**, **Open/Closed Principle (OCP)**, **Liskov Substitution Principle (LSP)**, **Interface Segregation Principle (ISP)**, dan **Dependency Inversion Principle (DIP)**. 

Di ekosistem modern C# dan .NET Core/.NET 8+, prinsip-prinsip ini bukan sekadar dogma teoretis, melainkan fondasi arsitektur modular, *testable*, dan *maintainable*. Prinsip ini memandu pemisahan *concern* saat berhadapan dengan *Dependency Injection (DI)* bawaan runtime .NET, *generic variance*, serta siklus hidup kompilasi IL (*Intermediate Language*) dan JIT (*Just-In-Time*).

```
   +-------------------------------------------------------+
   |                High-Level Policy (DIP)                |
   |              e.g., OrderProcessingService             |
   +-------------------------------------------------------+
                              |
                              v  (Depends on Abstraction)
   +-------------------------------------------------------+
   |             Abstractions / Interfaces (ISP)           |
   |           IPaymentProcessor, IInventoryClient         |
   +-------------------------------------------------------+
          ^                                        ^
          | (Subtype substitutability: LSP)        | (Extensible: OCP)
   +--------------------+                    +---------------------+
   | CreditCardPayment  |                    | CryptoPayment       |
   |  (Single Task: SRP)|                    |  (Single Task: SRP) |
   +--------------------+                    +---------------------+
```

#### S — Single Responsibility Principle (SRP)
Sebuah *class* atau modul harus memiliki tepat satu alasan untuk berubah (*one reason to change*). Dalam arsitektur internal CLR, mematuhi SRP menghasilkan *class* berukuran kecil dengan kohesi tinggi. Hal ini memudahkan compiler dan JIT melakukan *inlining* metode-metode kecil dan mengurangi *coupling* antardomain model.

#### O — Open/Closed Principle (OCP)
Entitas perangkat lunak harus terbuka untuk ekstensi (*open for extension*), namun tertutup untuk modifikasi (*closed for modification*). Dalam C#, hal ini dicapai melalui polimorfisme (antarmuka/`interface` dan *abstract base class*). Penambahan fitur baru dilakukan dengan menambahkan tipe data baru, bukan mengubah instruksi logika bercabang (`switch`/`if-else`) yang sudah teruji di basis kode eksisting.

#### L — Liskov Substitution Principle (LSP)
Objek dari superclass harus dapat digantikan oleh objek dari subclass tanpa merusak kebenaran (*correctness*) eksekusi program. Kontrak perilaku (*behavioral contract*) harus dipatuhi: *preconditions* tidak boleh diperketat, dan *postconditions* tidak boleh diperlemah di turunan. Melempar `NotImplementedException` pada implementasi turunan adalah indikasi utama pelanggaran fatal terhadap LSP.

#### I — Interface Segregation Principle (ISP)
Klien tidak boleh dipaksa bergantung pada *interface* yang tidak digunakannya. Daripada membuat satu *interface* monolitik yang membengkak (*fat interface*), buatlah antarmuka yang terfokus dan modular. Di C#, hal ini didukung oleh komposisi antarmuka berganda (contoh: `IReadOnlyCollection<T>`, `IDisposable`).

#### D — Dependency Inversion Principle (DIP)
Modul tingkat tinggi (*high-level modules*) tidak boleh bergantung pada modul tingkat rendah (*low-level modules*). Keduanya harus bergantung pada abstraksi. Selain itu, abstraksi tidak boleh bergantung pada detail; detail harus bergantung pada abstraksi. Dalam C#, DIP direalisasikan via *Inversion of Control (IoC)* container seperti `Microsoft.Extensions.DependencyInjection`.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sistem pemrosesan pesanan *e-commerce* dengan validasi stok, eksekusi pembayaran multi-kanal, dan notifikasi pelanggan.

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.DependencyInjection;

namespace SolidInCSharp;

// --- DOMAIN MODELS ---
public readonly record struct Money(decimal Amount, string Currency);
public sealed record Order(Guid Id, string CustomerEmail, Money TotalAmount);

// ============================================================================
// 1. SINGLE RESPONSIBILITY & INTERFACE SEGREGATION PRINCIPLE
// Interface dibuat kecil, spesifik, dan memisahkan concern masing-masing.
// ============================================================================

public interface IPaymentGateway
{
    ValueTask<bool> ProcessPaymentAsync(Money amount, CancellationToken cancellationToken = default);
}

public interface INotificationSender
{
    ValueTask SendInvoiceAsync(string recipientEmail, Guid orderId, CancellationToken cancellationToken = default);
}

public interface IStockValidator
{
    ValueTask<bool> HasSufficientStockAsync(Guid orderId, CancellationToken cancellationToken = default);
}

// ============================================================================
// 2. OPEN/CLOSED & LISKOV SUBSTITUTION PRINCIPLE
// Implementasi baru dapat ditambahkan tanpa memodifikasi OrderProcessor.
// Subtipe mematuhi kontrak invariant tanpa melempar NotImplementedException.
// ============================================================================

public sealed class StripePaymentGateway : IPaymentGateway
{
    public async ValueTask<bool> ProcessPaymentAsync(Money amount, CancellationToken cancellationToken = default)
    {
        // I/O non-blocking ke Stripe API
        await Task.Yield(); 
        Console.WriteLine($"[Stripe] Successfully processed {amount.Amount} {amount.Currency}");
        return true;
    }
}

public sealed class BankTransferPaymentGateway : IPaymentGateway
{
    public async ValueTask<bool> ProcessPaymentAsync(Money amount, CancellationToken cancellationToken = default)
    {
        // Validasi dan reservasi mutasi bank
        await Task.Yield();
        Console.WriteLine($"[BankTransfer] Settled transaction: {amount.Amount} {amount.Currency}");
        return true;
    }
}

public sealed class EmailNotificationSender : INotificationSender
{
    public async ValueTask SendInvoiceAsync(string recipientEmail, Guid orderId, CancellationToken cancellationToken = default)
    {
        await Task.Yield();
        Console.WriteLine($"[Email] Sent confirmation invoice for order {orderId} to {recipientEmail}");
    }
}

public sealed class DatabaseStockValidator : IStockValidator
{
    public async ValueTask<bool> HasSufficientStockAsync(Guid orderId, CancellationToken cancellationToken = default)
    {
        await Task.Yield();
        return true; // Asumsi stok selalu tersedia untuk demo
    }
}

// ============================================================================
// 3. DEPENDENCY INVERSION PRINCIPLE (HIGH-LEVEL ORCHESTRATOR)
// OrderProcessor hanya bergantung pada abstraksi, bukan implementasi konkret.
// ============================================================================

public sealed class OrderProcessor
{
    private readonly IStockValidator _stockValidator;
    private readonly IPaymentGateway _paymentGateway;
    private readonly INotificationSender _notificationSender;

    // Dependensi di-inject via Constructor Injection
    public OrderProcessor(
        IStockValidator stockValidator,
        IPaymentGateway paymentGateway,
        INotificationSender notificationSender)
    {
        _stockValidator = stockValidator ?? throw new ArgumentNullException(nameof(stockValidator));
        _paymentGateway = paymentGateway ?? throw new ArgumentNullException(nameof(paymentGateway));
        _notificationSender = notificationSender ?? throw new ArgumentNullException(nameof(notificationSender));
    }

    public async ValueTask<bool> CheckoutAsync(Order order, CancellationToken cancellationToken = default)
    {
        if (!await _stockValidator.HasSufficientStockAsync(order.Id, cancellationToken))
        {
            Console.WriteLine($"[OrderProcessor] Stock shortage for order: {order.Id}");
            return false;
        }

        bool paymentSuccess = await _paymentGateway.ProcessPaymentAsync(order.TotalAmount, cancellationToken);
        if (!paymentSuccess)
        {
            Console.WriteLine($"[OrderProcessor] Payment rejected for order: {order.Id}");
            return false;
        }

        await _notificationSender.SendInvoiceAsync(order.CustomerEmail, order.Id, cancellationToken);
        return true;
    }
}

// ============================================================================
// ENTRY POINT & WIRING VIA IoC CONTAINER
// ============================================================================

public static class Program
{
    public static async Task Main()
    {
        var services = new ServiceCollection();

        // Registrasi Service (Inversion of Control Wiring)
        services.AddScoped<IStockValidator, DatabaseStockValidator>();
        services.AddScoped<INotificationSender, EmailNotificationSender>();
        
        // Polimorfisme OCP: Cukup ganti registrasi di bawah ini tanpa menyentuh OrderProcessor
        services.AddScoped<IPaymentGateway, StripePaymentGateway>();
        
        services.AddScoped<OrderProcessor>();

        using ServiceProvider provider = services.BuildServiceProvider();
        using IServiceScope scope = provider.CreateScope();

        var processor = scope.ServiceProvider.GetRequiredService<OrderProcessor>();

        var testOrder = new Order(
            Id: Guid.NewGuid(),
            CustomerEmail: "architect@enterprise.io",
            TotalAmount: new Money(149.99m, "USD")
        );

        bool success = await processor.CheckoutAsync(testOrder);
        Console.WriteLine($"Checkout Success: {success}");
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: VTable vs. Interface Method Table (IMT)
Saat Anda menggunakan abstraksi interface untuk memenuhi prinsip OCP, DIP, dan LSP:
- Pemanggilan metode pada `class` konkret non-virtual diubah oleh compiler C# menjadi instruksi IL `call`. JIT dapat menautkan target fungsi ini secara statis dan melakukan *inlining*.
- Pemanggilan metode berbasis interface dieksekusi melalui instruksi IL `callvirt`. CLR runtime tidak dapat secara langsung melompat ke alamat memori fungsi karena ia tidak tahu tipe konkretnya pada fase kompilasi.
- .NET runtime menggunakan mekanisme **Interface Dispatch**. Di dalam struktur internal tipe CLR (*MethodTable*), terdapat **Interface Method Table (IMT)** berukuran tetap (umumnya 27 slot pada CoreCLR). Slot IMT menangani konflik hash interface ID. Jika terjadi konflik (*collision*), runtime memicu mekanisme *stub invocation* atau melompat ke *Interface Dispatch Stubs*.
- **JIT Devirtualization & PGO**: Pada .NET modern (dengan *Tiered Compilation* dan *Dynamic PGO*), jika JIT mendeteksi bahwa call-site antarmuka bersifat *monomorphic* (hanya satu tipe konkret yang dieksekusi di lapangan, misalnya `StripePaymentGateway`), JIT akan mengubah *indirect call* tersebut menjadi perbandingan tipe sederhana (*type guard*) dan *direct call*, bahkan melakukan *inline* penuh pada method target. Jika *megamorphic* (banyak implementasi bergantian), performa bergantung penuh pada IMT lookup.

```
       IL: callvirt IPaymentGateway::ProcessPaymentAsync
                           |
                           v
              +--------------------------+
              | Interface Dispatch Stub  |
              +--------------------------+
               /                        \
    (Monomorphic Fast Path)     (Monomorphic Fail / Megamorphic)
              |                                  |
              v                                  v
    +-------------------+              +-------------------+
    | Direct JIT Inline |              |    Lookup IMT     |
    | (Zero Indirection)|              | (Hash/Stub Table) |
    +-------------------+              +-------------------+
                                                 |
                                                 v
                                       +-------------------+
                                       | Target Executable |
                                       | Machine Code      |
                                       +-------------------+
```

#### Alokasi Memori / Resource
- **Boxing Overhead**: Jika sebuah struct (value type) mengimplementasikan interface untuk mematuhi LSP atau ISP, meneruskan struct tersebut ke parameter interface (contoh: `IPaymentGateway gateway = new ValueTypeGateway();`) akan memaksa CLR mengalokasikan memori di Managed Heap (**Boxing**). Oleh karena itu, *contract components* dalam pola SOLID umumnya diimplementasikan sebagai `class` atau dipanggil via generic constraints (`where T : IPaymentGateway`) untuk mempertahankan sifat zero-allocation struct.
- **Closure Allocation**: Pendelegasian tanggung jawab (SRP) yang dipecah ke lambda expressions atau delegates di dalam pipeline dapat menghasilkan *closure allocation* jika ada variabel dari scope luar yang ditangkap (*captured*).

#### Trade-offs
- **Arsitektur vs. CPU Cache**: Desain SOLID memecah struktur monolitik menjadi banyak class/interface independen. Hal ini meningkatkan *indirection pointer* di heap memory, yang berpotensi menyebabkan *CPU cache misses* (L1/L2/L3) jika dibandingkan dengan pemrosesan *data-oriented design* (DOD) berurutan dalam array contiguous memory.
- **Cognitive Overhead**: Terlalu ekstrem menerapkan SRP dan ISP pada modul trivial dapat menyebabkan *Interface-itis* (ledakan jumlah file interface yang membingungkan alur navigasi debug).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Constructor Injection untuk Dependensi Wajib**: Buat dependensi eksplisit melalui konstruktor privat/internal. Cegah instansiasi parsial atau *invalid states*.
- **Defensive Null Checks**: Gunakan *guard clauses* (contoh: `ArgumentNullException.ThrowIfNull(service)`) di dalam konstruktor.
- **Pecah Interface Berdasarkan Domain Client (ISP)**: Rancang interface dari perspektif modul yang mengonsumsinya (*consumer-driven*), bukan modul yang memproduksinya.
- **Gunakan Value-Type Records untuk Data & Classes untuk Behavior**: Pisahkan data transfer object murni dari service berlogika kompleks untuk mempermudah pemenuhan SRP.

#### Don'ts
- **Service Locator Anti-Pattern**: Mengoper `IServiceProvider` langsung ke dalam *business logic* untuk mengambil *dependency* di tengah jalan. Hal ini mengaburkan dependensi dan melanggar DIP.
- **Interface Soup (1:1 Abstraction)**: Menambahkan antarmuka (misal `IOrder`, `IOrderData`) untuk setiap entitas tanpa adanya kebutuhan polimorfisme atau isolasi unit testing. Ini bukan SOLID, melainkan *over-engineering*.
- **Temporal Coupling**: Mengabstraksikan interface yang mengharuskan pemanggilan berurutan tanpa validasi, misal: `Init()`, lalu `Process()`, lalu `Close()`. Ini membocorkan *implementation details* ke abstraksi.

#### Edge Cases
- **LSP Violation via Type Checking**: Menggunakan `if (payment is StripePaymentGateway stripe)` di dalam orchestrator merupakan tanda eksplisit kebocoran LSP. Polimorfisme harus menangani logika internal, bukan branching manual di pemanggil.
- **Exceptions as Flow Control**: Subclass melempar exception khusus (misal: `PlatformNotSupportedException`) pada metode interface tertentu. Ini melanggar substitutability LSP. Tangani via fitur kemampuan (contoh: pattern `CanProcess()` atau `bool TryProcess()`).

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Codebase Bermasalah (LSP & ISP Violation)**:
   Analisis interface monolitik berikut:
   ```csharp
   public interface IFileManager
   {
       void Read();
       void Write();
       void Compress();
       void Encrypt();
   }
   ```
   Rancang ulang interface tersebut menjadi modul-modul yang patuh terhadap ISP dan LSP untuk kasus `ReadOnlyStream` yang tidak memiliki kapabilitas Write atau Compress!
2. **JIT Tiering & Inlining Inspection**:
   Tulis program konsol yang memanggil fungsi via interface dalam *loop* 1.000.000 kali. Gunakan *tool* seperti `BenchmarkDotNet` dengan mode Disassembly Diagnoser (`[DisassemblyDiagnoser]`) untuk melihat apakah JIT compiler di mesin Anda melakukan *devirtualization* terhadap target antarmuka tersebut!
3. **Circular Dependency Trap pada DIP**:
   Buat dua class `ServiceA` dan `ServiceB` yang saling membutuhkan via constructor injection. Telusuri bagaimana `Microsoft.Extensions.DependencyInjection` melempar `InvalidOperationException` dan perbaiki arsitekturnya dengan mengekstraksi dependensi bersama ke class/interface ketiga yang patuh terhadap SRP.
