## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara fundamental, aplikasi ASP.NET Core modern bukanlah entitas magis yang di-host oleh *web server* monolitik seperti IIS di era .NET Framework (`System.Web`). ASP.NET Core pada dasarnya adalah **aplikasi konsol biasa** yang menginisiasi dan menjalankan *web server* di dalam prosesnya sendiri.

Tiga pilar utama dalam arsitektur *bootstrapping* ASP.NET Core adalah:

1.  **Hosting Model (Generic Host & WebApplicationBuilder)**: 
    Sejak .NET 6, `WebApplicationBuilder` membungkus `Generic Host` (`IHostBuilder`). Host bertanggung jawab atas manajemen *lifetime* aplikasi, *Dependency Injection* (DI), *Configuration*, dan *Logging*. Host ini menyatukan infrastruktur aplikasi web dan non-web (seperti *worker services*) ke dalam satu model standar.
2.  **Kestrel Web Server**: 
    Kestrel adalah *cross-platform, event-driven, asynchronous I/O web server* bawaan ASP.NET Core. Kestrel dirancang untuk *throughput* ekstrem. Ia bisa berjalan sebagai *edge server* (langsung menghadap internet) atau di belakang *Reverse Proxy* (seperti Nginx, HAProxy, IIS, atau YARP).
3.  **Startup Pipeline (Middleware)**: 
    Setelah Host terbangun, aplikasi mengonfigurasi *HTTP request pipeline*. Pipeline ini menggunakan pola *Chain of Responsibility* (sering disebut arsitektur *Russian Doll*). Setiap *request* masuk akan melewati serangkaian komponen (Middleware) yang dapat memodifikasi *request*, meneruskannya ke middleware berikutnya, dan memodifikasi *response* saat kembali.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan *Top-level statements* (.NET 6+) yang mendemonstrasikan konfigurasi Kestrel secara eksplisit dan pembuatan *middleware pipeline* kustom.

```csharp
using Microsoft.AspNetCore.Server.Kestrel.Core;
using System.Diagnostics;

// 1. Inisialisasi WebApplicationBuilder (Membangun Host)
var builder = WebApplication.CreateBuilder(args);

// 2. Konfigurasi Kestrel secara eksplisit (Under the hood tuning)
builder.WebHost.ConfigureKestrel(options =>
{
    // Membatasi ukuran body request untuk mencegah serangan DoS
    options.Limits.MaxRequestBodySize = 10 * 1024 * 1024; // 10 MB
    
    // Mengatur koneksi maksimum yang diizinkan
    options.Limits.MaxConcurrentConnections = 100;
    
    // Konfigurasi endpoint spesifik
    options.ListenAnyIP(5000); // HTTP
    // options.ListenAnyIP(5001, listenOptions => listenOptions.UseHttps()); // HTTPS
});

// Registrasi Dependency Injection (Services)
builder.Services.AddSingleton<IRequestTracker, RequestTracker>();

// 3. Build Host menjadi WebApplication
var app = builder.Build();

// 4. Konfigurasi Startup Pipeline (Middleware)

// Middleware 1: Global Exception Handler & Logging (Paling luar)
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    try
    {
        // Meneruskan request ke middleware selanjutnya
        await next(context); 
    }
    catch (Exception ex)
    {
        context.Response.StatusCode = 500;
        await context.Response.WriteAsync("Terjadi kesalahan internal.");
        app.Logger.LogError(ex, "Unhandled exception");
    }
    finally
    {
        sw.Stop();
        app.Logger.LogInformation($"Request {context.Request.Path} selesai dalam {sw.ElapsedMilliseconds}ms");
    }
});

// Middleware 2: Security Headers (Memodifikasi Response)
app.Use(async (context, next) =>
{
    context.Response.Headers.Append("X-Content-Type-Options", "nosniff");
    context.Response.Headers.Append("X-Frame-Options", "DENY");
    await next(context);
});

// 5. Terminal Middleware (Endpoint akhir, tidak memanggil next())
app.MapGet("/", () => "Hello dari Kestrel Pipeline!");
app.MapGet("/heavy", async () => 
{
    await Task.Delay(1000); // Simulasi I/O bound work
    return "Heavy task selesai";
});

// 6. Jalankan Host (Blocking call yang menahan aplikasi tetap hidup)
app.Run();

// --- Dummy Service ---
public interface IRequestTracker { }
public class RequestTracker : IRequestTracker { }
```

**Penjelasan Kode:**
- `ConfigureKestrel`: Digunakan untuk melakukan *tuning* pada level transport jaringan. Sangat penting untuk skenario *high-traffic*.
- `app.Use(...)`: Mendaftarkan middleware. Pemanggilan `await next(context)` adalah kunci; kode sebelum `next` dieksekusi saat *request* masuk, kode setelah `next` dieksekusi saat *response* keluar.
- `app.MapGet(...)`: Adalah *Terminal Middleware* (Routing endpoint). Ia mengakhiri pipeline dan mulai mengembalikan *response* ke atas.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Saat `app.Run()` dipanggil, Kestrel mulai mendengarkan (*bind*) pada port yang ditentukan menggunakan *Socket transport* (sebelumnya menggunakan `libuv`). Kestrel menggunakan arsitektur *multiplexed I/O* berbasis *event-loop*. Saat *request* TCP masuk, Kestrel mem-parsing HTTP *headers* dan menyerahkan eksekusi pipeline ke .NET *Thread Pool*. Ini memungkinkan Kestrel menangani puluhan ribu koneksi konkuren dengan jumlah *thread* OS yang sangat sedikit.
- **Alokasi Memori / Resource**: 
  Rahasia performa Kestrel terletak pada penggunaan `System.IO.Pipelines` dan `MemoryPool<byte>`. Alih-alih mengalokasikan *buffer* array byte baru (`byte[]`) untuk setiap *request* (yang akan membebani *Garbage Collector* dan memicu fragmentasi *Large Object Heap*), Kestrel menggunakan memori *unmanaged* atau *pooled memory* secara *zero-copy*. Data dibaca langsung dari *socket* ke dalam *buffer* yang dipinjam, diproses, dan dikembalikan ke *pool*.
- **Trade-offs**: 
  - **In-Process vs Out-of-Process (IIS)**: Jika di-host di IIS, model *In-Process* (default) menjalankan Kestrel dan IIS dalam satu proses `w3wp.exe`, memberikan performa maksimal. Model *Out-of-Process* menjalankan Kestrel di `dotnet.exe` terpisah dan IIS bertindak murni sebagai *reverse proxy* via HTTP, yang menambah *overhead* jaringan internal (namun lebih aman jika aplikasi *crash*, tidak mematikan *worker process* IIS).

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Reverse Proxy di Production**: Meskipun Kestrel aman sebagai *edge server*, menggunakan Nginx/YARP/IIS di depannya sangat disarankan untuk *TLS termination*, *load balancing*, dan *caching* statis.
  - **Urutan Middleware Sangat Krusial**: Selalu letakkan middleware penanganan error (`UseExceptionHandler`) di urutan paling atas pipeline agar dapat menangkap *exception* dari middleware di bawahnya.
  - **Gunakan `appsettings.json` untuk Limit Kestrel**: Hindari *hardcode* limit Kestrel di kode. Gunakan konfigurasi agar mudah diubah oleh tim DevOps tanpa kompilasi ulang.
- **Don'ts**:
  - **JANGAN PERNAH melakukan Blocking Call di Middleware**: Menggunakan `.Wait()`, `.Result`, atau `Thread.Sleep()` di dalam pipeline akan memblokir *Thread Pool thread*. Ini menyebabkan *Thread Starvation* dan aplikasi akan hang di bawah beban tinggi. Selalu gunakan `await`.
  - **Jangan memodifikasi Response setelah `next()` jika body sudah ditulis**: Jika *Terminal Middleware* sudah mulai menulis ke *Response stream*, memodifikasi HTTP Headers di middleware sebelumnya (setelah `await next()`) akan melempar `InvalidOperationException: Headers are read-only, response has already started`.
- **Edge Cases**:
  - **Graceful Shutdown**: Saat aplikasi menerima sinyal SIGTERM (misal dari Kubernetes saat *pod* dimatikan), Kestrel akan berhenti menerima koneksi baru dan menunggu koneksi lama selesai. Pastikan Anda tidak memiliki *background task* yang berjalan tanpa memantau `CancellationToken` dari `IHostApplicationLifetime`.

### 5. Tantangan Eksplorasi Mandiri

1. Buatlah sebuah *Custom Middleware* berbasis kelas (mengimplementasikan `IMiddleware` atau konvensi `InvokeAsync`) yang membaca *header* `X-Api-Key`. Jika *header* tidak ada atau salah, kembalikan status `401 Unauthorized` tanpa memanggil `next()`.
2. Eksplorasi `IHostApplicationLifetime`. Buatlah sebuah *background service* sederhana, dan log pesan ke konsol tepat saat aplikasi mulai *shutting down* (menggunakan `ApplicationStopping.Register(...)`).
3. Konfigurasikan Kestrel untuk mendengarkan pada *Unix Domain Socket* (UDS) alih-alih TCP port, dan cari tahu mengapa UDS lebih cepat untuk komunikasi antar-proses (IPC) di lingkungan Linux/Docker.
