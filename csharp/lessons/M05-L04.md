### 1. Konsep & Arsitektur Mendalam

Dalam komputasi konkuren .NET modern, terminasi thread secara paksa (*preemptive cancellation*) seperti pemanggilan `Thread.Abort()` telah dihentikan secara permanen sejak .NET Core. Pendekatan preemptif merusak integritas *runtime* karena melempar `ThreadAbortException` di sembarang titik instruksi, berisiko mengunci memori secara permanen (*orphaned locks*), dan merusak konsistensi *internal application state*.

Sebagai gantinya, .NET mengadopsi model **Cooperative Cancellation**. Dalam paradigma ini, pembatalan operasi bergantung pada kerja sama sukarela antara pihak pemohon (*caller*) dan pihak pelaksana (*worker task*). Framework ini dibangun di atas dua entitas utama:

```
[ Caller / Controller ]
         |
         v
+--------------------------+
| CancellationTokenSource  | ---> Mengontrol state (Cancel, CancelAfter)
+--------------------------+      Mengelola alokasi callbacks & WaitHandle
         |
         | Menerbitkan (.Token)
         v
+--------------------------+
|    CancellationToken     | ---> Bersifat pasif (readonly struct)
+--------------------------+      Didistribusikan ke stack eksekusi
         |
         v
[ Worker / Task Receiver ]   ---> Melakukan Polling / Registrasi Callback
```

1. **`CancellationTokenSource` (CTS)**: Merupakan *reference type* (`class`) yang memegang kepemilikan siklus hidup sinyal. CTS adalah pihak yang memiliki otoritas untuk memicu pembatalan via `.Cancel()` atau mengatur pembatalan berbasis waktu via `.CancelAfter(TimeSpan)`.
2. **`CancellationToken` (CT)**: Merupakan *value type* (`readonly struct`) berukuran ringkas (setara satu pointer) yang diekspos oleh CTS. CT dibagikan ke seluruh rantai pemanggilan metode secara *read-only*. Karena berupa `struct`, membagikannya ke berbagai sub-metode tidak menghasilkan alokasi baru di GC Heap.

#### Mekanisme Deteksi Pembatalan
Kode pekerja mengonsumsi token melalui dua mekanisme:
- **Polling Model (Pull)**: Menginspeksi properti `token.IsCancellationRequested` secara berkala (cocok untuk CPU-bound loop), atau mengeksekusi `token.ThrowIfCancellationRequested()` yang akan melempar `OperationCanceledException` jika sinyal aktif.
- **Callback Registration Model (Push)**: Mendaftarkan delegasi melalui `token.Register(Action callback)`. Mekanisme ini umumnya digunakan untuk menjembatani API asynchronous lama (non-cancellable I/O) agar dapat dihentikan (misalnya: memutus socket TCP atau membatalkan stream secara paksa saat token terpicu).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem *worker pipeline* pemrosesan data paralel dengan mekanisme timeout terpusat, penggabungan token (*linked tokens*), dan pembersihan resource secara deterministik.

```csharp
using System;
using System.IO;
using System.Net.Http;
using System.Threading;
using System.Threading.Tasks;

public sealed class ResilientDataProcessor : IDisposable
{
    private readonly HttpClient _httpClient;
    private readonly CancellationTokenSource _masterCts = new();

    public ResilientDataProcessor(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    // Menggabungkan cancellation internal dengan cancellation eksternal caller
    public async Task ProcessPipelineAsync(string downloadUrl, Stream destination, CancellationToken callerToken = default)
    {
        // 1. Timeout lokal spesifik untuk operasi ini: 10 detik
        using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(10));

        // 2. Buat Linked Token Source untuk menggabungkan master runtime, timeout, dan caller token
        using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(
            _masterCts.Token, 
            timeoutCts.Token, 
            callerToken
        );

        CancellationToken combinedToken = linkedCts.Token;

        try
        {
            Console.WriteLine("[Pipeline] Memulai download stream...");
            
            // Mengirim token ke asynchronous I/O API bawaan runtime
            using var response = await _httpClient.GetAsync(
                downloadUrl, 
                HttpCompletionOption.ResponseHeadersRead, 
                combinedToken
            ).ConfigureAwait(false);

            response.EnsureSuccessStatusCode();

            await using var sourceStream = await response.Content.ReadAsStreamAsync(combinedToken)
                .ConfigureAwait(false);

            byte[] buffer = new byte[81920]; // 80 KB chunk
            int bytesRead;

            // 3. Polling dan I/O cancellation dalam loop pemrosesan data (CPU + I/O bound)
            while ((bytesRead = await sourceStream.ReadAsync(buffer.AsMemory(0, buffer.Length), combinedToken).ConfigureAwait(false)) > 0)
            {
                // Throw preemptif sebelum melakukan operasi berat di memory
                combinedToken.ThrowIfCancellationRequested();

                // Simulasi pemrosesan CPU-bound
                TransformChunkInMemory(buffer.AsSpan(0, bytesRead));

                await destination.WriteAsync(buffer.AsMemory(0, bytesRead), combinedToken)
                    .ConfigureAwait(false);
            }

            Console.WriteLine("[Pipeline] Selesai secara sukses.");
        }
        catch (OperationCanceledException ex) when (callerToken.IsCancellationRequested)
        {
            Console.WriteLine("[Pipeline] Dihentikan secara eksplisit oleh Caller.");
            throw; // Propagasi pembatalan caller
        }
        catch (OperationCanceledException ex) when (timeoutCts.IsCancellationRequested)
        {
            Console.WriteLine("[Pipeline] Dihentikan karena Timeout operasi (10s) terlampaui.");
            throw new TimeoutException("Operasi melebihi batas waktu 10 detik.", ex);
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine("[Pipeline] Dihentikan oleh Master Application Token.");
            throw;
        }
    }

    private static void TransformChunkInMemory(Span<byte> data)
    {
        // Mutasi in-place sederhana (Enkripsi/Transformasi bit)
        for (int i = 0; i < data.Length; i++)
        {
            data[i] = (byte)(data[i] ^ 0x5A);
        }
    }

    public void TriggerGlobalShutdown() => _masterCts.Cancel();

    public void Dispose()
    {
        _masterCts.Cancel();
        _masterCts.Dispose();
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Secara internal, `CancellationToken` hanyalah sebuah `struct` yang membungkus satu *reference field*:
```csharp
public readonly struct CancellationToken
{
    private readonly CancellationTokenSource? _source;
    // ...
}
```

Ketika `cts.Cancel()` dieksekusi:
1. State internal pada CTS diubah menggunakan operasi atomik `Interlocked.CompareExchange` dari status `NOT_CANCELED` (0) menjadi `CANCELED` (1).
2. Jika ada *wait handles* sinkronisasi OS yang diikatkan ke CTS via `.WaitHandle`, runtime akan memicu event OS tersebut.
3. Seluruh *callback* yang didaftarkan melalui `.Register()` akan dieksekusi secara serial (LIFO secara historis, namun tidak boleh diasumsikan urutannya).
4. Pemanggilan `ThrowIfCancellationRequested()` menguji boolean state tersebut; jika true, runtime melempar `OperationCanceledException(this)`.

#### Alokasi Memori / Resource
- **Callback Registration List**: Setiap kali `token.Register(...)` dipanggil, CTS mengalokasikan node internal (`CancellationCallbackInfo`). Jika mendaftar ribuan callback pada satu token berumur panjang, akan terjadi alokasi masif pada GC Large/Gen-0 Heap.
- **`CancellationTokenRegistration` Lifecycle**: Method `.Register()` mengembalikan *struct* `CancellationTokenRegistration`. Anda wajib memanggil `.Dispose()` atau `using` pada registrasi tersebut untuk melepaskan referensi delegasi dari CTS dan mencegah *memory leaks*.
- **Timer CTS**: Menggunakan `new CancellationTokenSource(TimeSpan)` secara implisit mengalokasikan objek `TimerQueueTimer` internal di level CLR. Jika CTS ini tidak pernah di-`Dispose()`, timer native akan menggantung hingga GC mengoleksinya via Finalizer thread.

#### Trade-offs: Polling vs Registration
| Polling (`IsCancellationRequested`) | Callback Registration (`Register`) |
| :--- | :--- |
| **Alokasi 0 byte** (hanya membaca field via referensi memory). | Memerlukan alokasi objek *callback context* & *registration node*. |
| Terikat langsung dengan CPU execution loop. | Mengharuskan eksekusi delegasi saat sinyal dipicu (dapat memicu context switch). |
| Hanya bisa membatalkan saat program kembali mencapai titik check. | Mampu menginterupsi pemanggilan I/O blocking secara asinkron. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Alirkan Token ke Level Terdalam**: Selalu teruskan `CancellationToken` ke semua method asynchronous (I/O, Database Query, Stream, Serialization). Jangan memutus rantai token.
- **Rethrow `OperationCanceledException`**: Biarkan exception bertipe pembatalan merambat naik ke pipeline utama runtime (Task/ASP.NET Core Middleware) agar status `Task` berakhir sebagai `TaskStatus.Canceled`, bukan `TaskStatus.Faulted`.
- **Dispose CTS yang Memiliki Timer**: Selalu letakkan `CancellationTokenSource` yang menggunakan timeout/linked tokens di dalam blok `using` atau pastikan `.Dispose()` terpanggil.

#### Don'ts
- **Menangkap Exception Secara Naif Tanpa Re-throw**:
  ```csharp
  // FATAL: Menelan status pembatalan, task dianggap sukses berjalan
  try {
      await worker.ExecuteAsync(token);
  } catch (Exception) { /* diam saja */ }
  ```
- **Menggunakan `CancellationToken.None` di Library**: Jangan gunakan `CancellationToken.None` di lapisan library/internal method. Sediakan parameter `CancellationToken cancellationToken = default` agar caller memiliki kebebasan menentukan token.
- **Melakukan Pekerjaan Berat di Dalam `.Register()`**: Delegasi callback dipanggil di thread yang memicu `.Cancel()`. Jika pemicunya adalah thread UI atau TaskPool worker penting, registrasi callback yang lambat akan memblokir thread tersebut (*blocking execution context*).

#### Edge Cases
- **Linked Token Source Cleanup**: `CancellationTokenSource.CreateLinkedTokenSource(t1, t2)` mendaftarkan callback ke `t1` dan `t2`. Jika `t1` berumur panjang (misalnya singleton application token), CTS linked akan tetap hidup di memori kecuali method `.Dispose()` pada objek linked dipanggil secara eksplisit.
- **Fast-path Race Condition**: Operasi I/O bisa saja berhasil selesai tepat beberapa milidetik *setelah* pembatalan terjadi. Kode harus mampu menangani validasi status konsistensi resource yang telah terlanjur dimutasi.
