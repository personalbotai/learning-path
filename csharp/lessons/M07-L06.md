## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Validasi adalah garis pertahanan pertama dalam aplikasi untuk memastikan integritas data sebelum diproses oleh *business logic* atau disimpan ke *database*. Dalam ekosistem C# dan ASP.NET Core, terdapat dua paradigma utama untuk melakukan validasi: **Data Annotations** dan **FluentValidation**.

**Data Annotations**
Merupakan bawaan dari .NET (`System.ComponentModel.DataAnnotations`). Pendekatan ini menggunakan *Attributes* yang ditempelkan langsung pada properti model. 
*   **Kelebihan:** Cepat diimplementasikan, bawaan *framework*, cocok untuk validasi sederhana (CRUD dasar).
*   **Kekurangan:** Melanggar *Single Responsibility Principle* (SRP) karena model data bercampur dengan logika validasi. Sangat sulit digunakan untuk validasi kondisional (misal: Field A wajib diisi jika Field B bernilai X) atau validasi lintas-properti.

**FluentValidation**
Merupakan *library* pihak ketiga yang menjadi standar industri (*de facto*) di ekosistem .NET modern. Menggunakan pola *Fluent Interface* untuk membangun aturan validasi secara terpisah dari model.
*   **Arsitektur:** Memisahkan model data (POCO) dari kelas validator (`AbstractValidator<T>`). Ini mematuhi SRP dan *Open/Closed Principle* (OCP).
*   **Kelebihan:** Mendukung validasi kompleks, kondisional (`When`), validasi bersarang (*nested*), lokalisasi pesan error yang mudah, dan sangat ramah terhadap *Unit Testing*.

Dalam arsitektur ASP.NET Core, proses validasi diintersepsi pada fase **Model Binding**. Sebelum *Controller Action* atau *Minimal API Endpoint* dieksekusi, *framework* akan menjalankan validator yang terdaftar, dan jika gagal, akan mengisi `ModelState` (pada MVC/Controllers) atau langsung mengembalikan respons `400 Bad Request`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah perbandingan dan implementasi modern menggunakan **FluentValidation** pada skenario registrasi pengguna, termasuk validasi kondisional dan *nested object*.

```csharp
using FluentValidation;
using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using Microsoft.Extensions.DependencyInjection;

// 1. Model Data (POCO - Bersih dari atribut validasi)
public class Address
{
    public string Street { get; set; } = string.Empty;
    public string ZipCode { get; set; } = string.Empty;
}

public class RegisterUserRequest
{
    public string Username { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
    public string Password { get; set; } = string.Empty;
    public bool HasPhysicalAddress { get; set; }
    public Address? Address { get; set; }
}

// 2. Validator untuk Nested Object
public class AddressValidator : AbstractValidator<Address>
{
    public AddressValidator()
    {
        RuleFor(x => x.Street).NotEmpty().WithMessage("Jalan tidak boleh kosong.");
        RuleFor(x => x.ZipCode)
            .NotEmpty()
            .Matches(@"^\d{5}$").WithMessage("Kode pos harus 5 digit angka.");
    }
}

// 3. Validator Utama dengan Logika Kompleks
public class RegisterUserRequestValidator : AbstractValidator<RegisterUserRequest>
{
    public RegisterUserRequestValidator()
    {
        RuleFor(x => x.Username)
            .NotEmpty()
            .MinimumLength(5).WithMessage("Username minimal 5 karakter.");

        RuleFor(x => x.Email)
            .NotEmpty()
            .EmailAddress().WithMessage("Format email tidak valid.");

        RuleFor(x => x.Password)
            .NotEmpty()
            .MinimumLength(8)
            .Must(ContainUppercase).WithMessage("Password harus mengandung huruf besar.");

        // Validasi Kondisional: Alamat wajib divalidasi HANYA JIKA HasPhysicalAddress = true
        When(x => x.HasPhysicalAddress, () =>
        {
            RuleFor(x => x.Address)
                .NotNull().WithMessage("Alamat wajib diisi jika memiliki alamat fisik.")
                .SetValidator(new AddressValidator()!); // Nested Validation
        });
    }

    // Custom Rule Logic
    private bool ContainUppercase(string password)
    {
        return !string.IsNullOrEmpty(password) && password.Any(char.IsUpper);
    }
}

// 4. Setup di Program.cs (Minimal API Example)
var builder = WebApplication.CreateBuilder(args);

// Registrasi Validator ke DI Container
builder.Services.AddScoped<IValidator<RegisterUserRequest>, RegisterUserRequestValidator>();

var app = builder.Build();

app.MapPost("/api/register", async (RegisterUserRequest request, IValidator<RegisterUserRequest> validator) =>
{
    // Eksekusi Validasi secara manual (atau gunakan Endpoint Filter untuk otomatisasi)
    var validationResult = await validator.ValidateAsync(request);

    if (!validationResult.IsValid)
    {
        // Mengembalikan format ProblemDetails standar RFC 7807
        return Results.ValidationProblem(validationResult.ToDictionary());
    }

    // Lanjut ke Business Logic...
    return Results.Ok(new { Message = "Registrasi Berhasil" });
});

app.Run();
```

**Penjelasan Kode:**
*   `AbstractValidator<T>`: Kelas dasar dari FluentValidation. Aturan didefinisikan di dalam konstruktor.
*   `RuleFor(x => x.Property)`: Menggunakan *Expression Trees* untuk menargetkan properti secara *type-safe*.
*   `When(...)`: Mengeksekusi blok aturan hanya jika kondisi terpenuhi (sangat sulit dilakukan dengan Data Annotations).
*   `SetValidator(...)`: Menggunakan validator lain untuk memvalidasi objek bersarang (*composition*).

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  *   **Data Annotations:** Mengandalkan *Reflection* (`System.Reflection`) pada saat *runtime*. ASP.NET Core memanggil `Validator.TryValidateObject` yang akan memindai metadata atribut pada kelas. Proses ini memiliki *overhead*, meskipun .NET melakukan *caching* pada metadata tersebut.
  *   **FluentValidation:** Saat kelas validator diinisialisasi, `RuleFor(x => x.Property)` membangun sebuah **Expression Tree** (`Expression<Func<T, TProperty>>`). *Expression tree* ini kemudian dikompilasi menjadi *delegate* (fungsi anonim yang sangat cepat dieksekusi) untuk membaca nilai properti tanpa menggunakan *Reflection* berulang kali.

- **Alokasi Memori / Resource**: 
  *   Jika validator FluentValidation tidak memiliki *state* (tidak menyimpan data spesifik *request* di level kelas), sangat disarankan mendaftarkannya sebagai **Singleton** di *Dependency Injection* (`AddSingleton`). Ini mencegah alokasi memori (instansiasi objek validator baru) pada setiap *request* HTTP, mengurangi tekanan pada *Garbage Collector* (GC).
  *   Jika validator membutuhkan layanan *Scoped* (misal: `DbContext` untuk validasi ke *database*), maka validator harus didaftarkan sebagai **Scoped** (`AddScoped`).

- **Trade-offs**: 
  *   Data Annotations lebih ringan dari segi ukuran *library* (karena bawaan), namun mengorbankan kebersihan arsitektur.
  *   FluentValidation menambah dependensi eksternal dan sedikit kurva belajar, namun memberikan skalabilitas kode yang masif untuk aplikasi *Enterprise*.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan FluentValidation untuk aplikasi skala menengah-besar.** Pisahkan folder `Validators` dari `Models`.
  - **Manfaatkan `FluentValidation.TestHelper`.** *Library* ini menyediakan *extension methods* seperti `ShouldHaveValidationErrorFor` yang membuat *Unit Testing* validasi menjadi sangat mudah dan ekspresif.
  - **Gunakan *Endpoint Filters* (Minimal API) atau *Action Filters* (MVC).** Jangan menulis boilerplate `if (!result.IsValid)` di setiap *endpoint*. Buat *middleware/filter* global untuk menangkap kegagalan validasi dan mengembalikan `400 Bad Request`.

- **Don'ts**:
  - **Jangan campur Data Annotations dan FluentValidation.** Pilih salah satu (idealnya FluentValidation). Mencampur keduanya akan membuat bingung tim *developer* di mana aturan validasi sebenarnya berada.
  - **Hindari validasi I/O (Database/Network) di dalam Validator jika memungkinkan.** Menggunakan `.MustAsync()` untuk mengecek apakah Email sudah ada di *database* memang bisa dilakukan, namun ini mengaburkan batas antara *Input Validation* (sintaksis) dan *Business Validation* (semantik). Validasi bisnis sebaiknya berada di *Domain Layer* atau *Service Layer*.

- **Edge Cases**:
  - **Asynchronous Validation Deadlocks:** Jika Anda menggunakan aturan asinkron (`MustAsync`), pastikan Anda memanggil `ValidateAsync()`, bukan `Validate()`. Memanggil metode sinkron pada validator yang memiliki aturan asinkron akan melempar `AsyncValidatorInvokedSynchronouslyException`.

### 5. Tantangan Eksplorasi Mandiri

1. **Buat Global Validation Filter:** Implementasikan `IEndpointFilter` pada Minimal API yang secara otomatis menginjeksi `IValidator<T>`, memvalidasi *request body*, dan mengembalikan `Results.ValidationProblem()` jika gagal, sehingga kode di dalam *endpoint* Anda bersih dari logika validasi.
2. **Eksplorasi Custom Reusable Validator:** Buat *Extension Method* kustom untuk `IRuleBuilder` (misalnya `.PasswordMustBeStrong()`) yang mengenkapsulasi logika pengecekan huruf besar, angka, dan simbol, lalu gunakan di beberapa kelas validator yang berbeda.
3. **Unit Testing:** Buat proyek xUnit, instal `FluentValidation.DependencyInjectionExtensions` dan `FluentValidation.TestHelper`, lalu tulis *test* untuk memastikan `AddressValidator` gagal jika `ZipCode` berisi huruf.
