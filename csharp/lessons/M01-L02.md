### 1. Konsep & Arsitektur Mendalam

Sistem tipe data dalam .NET Common Language Runtime (CLR) didesain dengan konsep *Unified Type System*. Semua tipe data, secara langsung maupun tidak langsung, bermuara pada akar hierarki yang sama: `System.Object`. Namun, CLR membagi semesta tipe data ke dalam dua kategori fundamental dengan perilaku alokasi dan siklus hidup yang sangat kontras: **Value Types** dan **Reference Types**.

```
                   System.Object
                         │
         ┌───────────────┴───────────────┐
         │                               │
  Reference Types                System.ValueType
  (Class, Interface,                     │
   Delegate, Array,                 Value Types
   String, Object)               (Struct, Enum,
                                  Primitives: int, bool, etc.)
```

#### Value Types (`System.ValueType`)
Value types merepresentasikan data mandiri yang memegang nilainya secara langsung (*in-line*). Ketika sebuah value type dialokasikan, ruang memori yang dipesan langsung menampung representasi biner dari data tersebut. Karakteristik utamanya meliputi:
- **Semantik Salin (Copy-by-value):** Operasi penugasan (`=`) menduplikasi seluruh isi bit dari variabel sumber ke variabel tujuan secara independen.
- **Hierarki:** Berakar dari abstract class `System.ValueType` (yang meng-override implementasi default `System.Object.Equals` dan `GetHashCode` menggunakan refleksi untuk perbandingan berbasis nilai/member-wise).
- **Subkategori:** Primitives (`byte`, `int`, `double`, dll.), `struct`, dan `enum`.

#### Reference Types (`System.Object`)
Reference types memisahkan data menjadi dua komponen: referensi (pointer ke lokasi memori) dan objek aktual itu sendiri (*payload instance*). Variabel hanya menyimpan alamat memori dari instance target.
- **Semantik Referensi (Copy-by-reference):** Operasi penugasan hanya menyalin alamat memori (pointer), bukan objek yang dirujuk. Kedua variabel akan menunjuk ke lokasi memori yang sama.
- **Overhead Instance:** Setiap instance pada managed heap selalu memiliki metadata tersembunyi:
  1. **MethodTable Pointer (TypeHandle):** Penunjuk ke metadata tipe data (ukuran: 4 byte di x86, 8 byte di x64) untuk *virtual method dispatch* dan *runtime type identification*.
  2. **SyncBlockIndex:** Integer 4-byte (diikuti padding per alignment) yang digunakan untuk sinkronisasi thread (`lock`) dan hash code generation default.
- **Subkategori:** `class`, `interface`, `delegate`, `record class`, `string`, dan seluruh jenis `array`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengilustrasikan perbedaan semantik mutasi memori, dampak komparasi, serta teknik optimasi modern menggunakan `readonly struct` dan passing parameter `in`/`ref`.

```csharp
using System;

// 1. Reference Type: Alokasi di Managed Heap, membutuhkan GC
public class GeoCoordinateClass
{
    public double Latitude { get; set; }
    public double Longitude { get; set; }

    public GeoCoordinateClass(double lat, double lon) => 
        (Latitude, Longitude) = (lat, lon);
}

// 2. Value Type: Alokasi in-line, immutable untuk mencegah bug side-effect
public readonly struct GeoCoordinateStruct : IEquatable<GeoCoordinateStruct>
{
    public double Latitude { get; }
    public double Longitude { get; }

    public GeoCoordinateStruct(double lat, double lon) => 
        (Latitude, Longitude) = (lat, lon);

    // Override bawaan ValueType untuk menghindari refleksi yang lambat
    public bool Equals(GeoCoordinateStruct other) =>
        Latitude.Equals(other.Latitude) && Longitude.Equals(other.Longitude);

    public override bool Equals(object? obj) =>
        obj is GeoCoordinateStruct other && Equals(other);

    public override int GetHashCode() =>
        HashCode.Combine(Latitude, Longitude);

    public static bool operator ==(GeoCoordinateStruct left, GeoCoordinateStruct right) =>
        left.Equals(right);

    public static bool operator !=(GeoCoordinateStruct left, GeoCoordinateStruct right) =>
        !left.Equals(right);
}

public class Program
{
    public static void Main()
    {
        // --- Demonstrasi Copy Semantics ---
        
        // Reference Type Behavior
        var refA = new GeoCoordinateClass(-6.2088, 106.8456); // Jakarta
        var refB = refA; // Menyalin pointer, bukan objek
        refB.Latitude = 0.0; // Mutasi via refB mengubah instance yang sama
        
        Console.WriteLine($"RefA Latitude: {refA.Latitude}"); // Output: 0.0 (Terkontaminasi)

        // Value Type Behavior
        var valA = new GeoCoordinateStruct(-6.2088, 106.8456);
        var valB = valA; // Bitwise copy dari seluruh struct
        // valB.Latitude = 0.0; // Error CS0200: Readonly struct tidak dapat dimutasi

        valB = new GeoCoordinateStruct(0.0, valB.Longitude);
        Console.WriteLine($"ValA Latitude: {valA.Latitude}"); // Output: -6.2088 (Tetap aman)

        // --- Demonstrasi Optimasi Passing Parameter ---
        double distance = CalculateDistance(in valA, in valB);
        Console.WriteLine($"Distance: {distance:F2}");
    }

    // Menggunakan modifier 'in' untuk menghindari penyalinan bitwise struct (pass-by-reference read-only)
    public static double CalculateDistance(in GeoCoordinateStruct p1, in GeoCoordinateStruct p2)
    {
        double dLat = p2.Latitude - p1.Latitude;
        double dLon = p2.Longitude - p1.Longitude;
        return Math.Sqrt(dLat * dLat + dLon * dLon);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Mitos "Value Types di Stack, Reference Types di Heap"
Pernyataan bahwa value type *selalu* berada di stack adalah keliru. Aturan alokasi memori yang benar ditentukan oleh **konteks deklarasi**:
- **Reference Type Instance:** Selalu dialokasikan di **Managed Heap** (Small Object Heap/Large Object Heap).
- **Value Type Instance:** Dialokasikan secara **in-line** di mana pun ia dideklarasikan:
  - Sebagai variabel lokal di dalam *method body* $\rightarrow$ Alokasi di **Execution Stack** (selama tidak tertangkap oleh lambda closure atau iterator block `yield`).
  - Sebagai *field* dari sebuah `class` $\rightarrow$ Alokasi menyatu di dalam body instance class tersebut di **Managed Heap**.
  - Sebagai elemen dari array (misal: `int[]`) $\rightarrow$ Alokasi contiguous di **Managed Heap**.

#### Eksekusi & Runtime: IL & Memory Overhead
Pada arsitektur 64-bit (x64):
- Sebuah instance reference type terkecil (seperti `new object()`) memakan alokasi heap sebesar **24 byte**:
  - `SyncBlockIndex`: 4 byte (+ 4 byte padding alignment = 8 byte).
  - `MethodTable Pointer`: 8 byte.
  - Payload data: 0 byte (tetap dibulatkan minimum 8 byte oleh memory alignment CLR).
- Sebuah struct dengan satu field `int` hanya memakan **4 byte** jika berada di stack atau ter-embed di struktur lain, tanpa *header overhead*.

#### Boxing dan Unboxing
Ketika value type diperlakukan sebagai reference type (misal: di-cast ke `object` atau interface non-generik):

```csharp
int x = 42;
object boxed = x;        // Boxing: IL opcode 'box'
int unboxed = (int)boxed; // Unboxing: IL opcode 'unbox_any'
```

- **`box`**: Runtime mengalokasikan memori baru di Managed Heap (lengkap dengan TypeHandle dan SyncBlockIndex), menyalin bitwise data dari value type ke payload heap tersebut, lalu mengembalikan referensinya. Hal ini memicu overhead alokasi memori dan beban ekstra pada Garbage Collector (GC).
- **`unbox_any`**: Runtime memeriksa apakah pointer yang diberikan valid dan MethodTable-nya cocok dengan tipe target. Jika valid, runtime mengembalikan pointer ke raw data di dalam heap instance, lalu menyalin nilainya kembali ke evaluation stack. Jika tipe tidak identik, dilemparkan `InvalidCastException`.

```
Stack                   Heap
┌──────┐                ┌───────────────────────┐
│ x=42 │                │ SyncBlockIndex (8B)   │
└──────┘                ├───────────────────────┤
┌──────────┐            │ MethodTable Ptr (8B)  │
│  boxed   ├───────────►├───────────────────────┤
│ (pointer)│            │ Data: 42 (int) (8B)   │
└──────────┘            └───────────────────────┘
```

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `readonly struct` untuk Value Types kustom:** Membuat struct dapat dimutasi (*mutable struct*) adalah sumber *bug* tersembunyi karena operasi copy implisit dapat menyebabkan modifikasi data diterapkan pada salinan sementara (*defensive copy*), bukan target asli.
- **Implementasikan `IEquatable<T>` pada `struct`:** Implementasi `System.ValueType.Equals` bawaan menggunakan refleksi untuk membandingkan field satu per satu. Dengan mengimplementasikan `IEquatable<T>`, Anda menghindari overhead refleksi dan boxing saat komparasi.
- **Pertimbangkan ukuran struct:** Pilih `struct` hanya jika data bersifat logis tunggal, immutable, memiliki masa hidup singkat, dan ukurannya relatif kecil (aturan umum: $\le$ 16 byte / sebanding dengan 2 pointer x64).

#### Don'ts
- **Jangan mengabstraksikan struct ke Interface secara berlebihan:** Mengoper struct ke parameter bertipe interface (misalnya `IComparable` atau `IDisposable`) menyebabkan proses **boxing implisit**, meniadakan seluruh efisiensi performa memory allocation dari struct.
- **Hindari penggunaan mutable struct pada collection:** Memodifikasi properti struct di dalam generic collection seperti `List<T>` akan menghasilkan compiler error atau kegagalan update nilai jika diakses via property indexer (`list[0].Prop = val` tidak mengubah nilai di list).

#### Edge Cases
- **Nullable Value Types (`Nullable<T>` atau `T?`):** Merupakan value type (bukan referensi) yang diimplementasikan sebagai:
  ```csharp
  public struct Nullable<T> where T : struct {
      internal bool hasValue;
      internal T value;
  }
  ```
  Runtime memberikan perlakuan khusus: `Nullable<T>` yang bernilai `null` saat di-box akan menghasilkan null reference murni, bukan referensi ke heap object.
- **`ref struct` (sejak C# 7.2):** Tipe data khusus (misalnya `Span<T>`) yang dijamin oleh compiler untuk **hanya hidup di stack**. Tidak dapat di-box, tidak dapat menjadi field dari class biasa, tidak dapat digunakan dalam async method (lintas `await`), dan tidak dapat masuk ke lambda closure.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi IL & Boxing Overhead:**
   Gunakan tools seperti [SharpLab.io](https://sharplab.io) atau `ildasm`. Tulis metode yang memanggil `String.Format("Angka: {0}", 123)` dibandingkan `String.Format("Angka: {0}", 123.ToString())`. Analisis apakah ada instruksi IL `box` pada keduanya dan jelaskan penyebabnya.

2. **Benchmarking Defensive Copying:**
   Gunakan library `BenchmarkDotNet`. Buat sebuah struct berukuran 64 byte (misal: 8 buah `long`). Bandingkan performa eksekusi iterasi pemanggilan method passing parameter reguler (`Method(MyStruct s)`), passing parameter `in` tanpa readonly (`Method(in MyNonReadonlyStruct s)`), dan passing parameter `in` dengan readonly struct (`Method(in MyReadonlyStruct s)`). Perhatikan bagaimana compiler membuat *defensive copy* jika struct tidak dideklarasikan sebagai `readonly`.
