### 1. Konsep & Arsitektur Mendalam

Struktur kendali (*control flow*) dalam C# telah berevolusi secara signifikan dari paradigma imperatif berbasis *statement* menuju paradigma deklaratif-fungsional berbasis *expression* dan *pattern matching*.

Pada arsitektur C# klasik (C# 1.0–6.0), percabangan didominasi oleh `if-else` bertingkat dan `switch statement`. `switch statement` awal memiliki keterbatasan struktural:
1. Hanya mengevaluasi tipe data primitif, `string`, dan `enum`.
2. Beroperasi murni berdasarkan kesetaraan nilai konstan (*constant equality*).
3. Bersifat *statement-based* yang mewajibkan mutasi variabel di luar lingkup kontrol flow, rentan terhadap *fall-through bugs* (sehingga mewajibkan instruksi `break`/`goto case`), dan menghasilkan *boilerplate* yang tinggi.

```
Paradigma Klasik (Imperatif)           Paradigma Modern (Deklaratif)
+-----------------------+              +-----------------------+
|  Statement-Based      |              |  Expression-Based     |
|  - Mutasi variabel    |     VS       |  - Return value murni |
|  - Branching manual   |              |  - Type & Shape match |
|  - Efek samping       |              |  - Exhaustive check   |
+-----------------------+              +-----------------------+
```

Mulai C# 7.0 hingga C# 11/12+, Microsoft memperkenalkan sistem **Pattern Matching** formal yang terintegrasi secara mendalam dengan Roslyn Compiler. Fitur ini mengubah cara kerja evaluasi data:
- **Dekonstruksi dan Pengujian Bentuk (*Shape Inspection*)**: Memeriksa bukan hanya nilai atau tipe, melainkan struktur internal objek (*Property Pattern*, *Positional Pattern*, *List Pattern*).
- **Ekspresi Deterministik**: `switch expression` (C# 8+) mengembalikan nilai secara langsung (*pure expression*), menjamin *immutability*, dan memicu *compiler warning* (`CS8509`) jika evaluasi pola tidak menyeluruh (*non-exhaustive pattern*).
- **Kombinator Logika Terbaca**: Integrasi kata kunci `and`, `or`, dan `not` menggantikan operator bitwise/boolean klasik pada level evaluasi tipe dan nilai langsung di dalam cabang logika.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skenario nyata: Engine pemrosesan transaksi pembayaran finansial terdistribusi yang harus memvalidasi berbagai skema transaksi (Kartu Kredit, QRIS, Transfer Bank, dan Kripto) dengan aturan diskon, penanganan *fraud*, serta audit berbasis payload.

```csharp
using System;

public abstract record PaymentTransaction(decimal Amount, string Currency);

public record CreditCardTx(
    decimal Amount, 
    string Currency, 
    string CardNumber, 
    int ExpiryYear, 
    bool Is3DSecure
) : PaymentTransaction(Amount, Currency);

public record QrisTx(
    decimal Amount, 
    string Currency, 
    string MerchantId, 
    int TimeoutSeconds
) : PaymentTransaction(Amount, Currency);

public record CryptoTx(
    decimal Amount, 
    string Currency, 
    string Network, 
    int Confirmations
) : PaymentTransaction(Amount, Currency);

public enum RiskTier { Low, Medium, High, Blocked }

public static class PaymentProcessor
{
    // 1. Relational & Logical Patterns (C# 9+)
    public static decimal CalculateFee(decimal amount) => amount switch
    {
        <= 0 => throw new ArgumentOutOfRangeException(nameof(amount), "Amount invalid."),
        > 0 and <= 50_000 => 1_500m,
        > 50_000 and <= 1_000_000 => 2_500m,
        > 1_000_000 and <= 10_000_000 => 5_000m,
        _ => amount * 0.001m // 0.1% untuk transaksi di atas 10 juta
    };

    // 2. Type, Property, and Positional Patterns dengan When Guards
    public static RiskTier EvaluateRisk(PaymentTransaction tx) => tx switch
    {
        // Property pattern mendalam + logical pattern
        CreditCardTx { Is3DSecure: false, Amount: > 5_000_000 } => RiskTier.High,
        CreditCardTx { ExpiryYear: var year } when year < DateTime.UtcNow.Year => RiskTier.Blocked,
        
        // Property pattern evaluasi multi-field
        QrisTx { TimeoutSeconds: < 30, Amount: > 2_000_000 } => RiskTier.Medium,
        
        // Relational check pada sub-tipe spesifik
        CryptoTx { Confirmations: < 3, Currency: "BTC" or "ETH" } => RiskTier.High,
        CryptoTx { Confirmations: >= 3 } => RiskTier.Low,
        
        // Pola penangkap default (Discard Pattern)
        _ => RiskTier.Low
    };

    // 3. List Pattern & Slice Pattern (C# 11+)
    // Menganalisis log riwayat status pemrosesan: misal ["INIT", "PENDING", "SUCCESS"]
    public static string AnalyzeAuditLog(string[] auditStates) => auditStates switch
    {
        // Mencocokkan array kosong
        [] => "Empty audit trail",
        
        // Tepat satu elemen dan bernilai spesifik
        ["FAILED"] => "Instantly failed transaction",
        
        // Dimulai dengan "INIT", diakhiri "SUCCESS", elemen tengah diabaikan via slice pattern (..)
        ["INIT", .., "SUCCESS"] => "Transaction completed smoothly",
        
        // Mengambil elemen terakhir menggunakan discarded slice & sub-pattern
        [.., "FRAUD_DETECTED" or "CHARGEBACK"] => "Flagged for manual review",
        
        // Pattern dengan capture variable pada elemen spesifik
        ["INIT", var intermediate, "FAILED"] => $"Failed after stage: {intermediate}",
        
        _ => "Non-standard execution path"
    };
}

public class Program
{
    public static void Main()
    {
        var cc = new CreditCardTx(7_500_000m, "IDR", "4111222233334444", 2026, false);
        var qris = new QrisTx(150_000m, "IDR", "MCH-001", 15);
        var crypto = new CryptoTx(0.5m, "BTC", "Mainnet", 2);

        Console.WriteLine($"CC Risk: {PaymentProcessor.EvaluateRisk(cc)}");          // Output: High
        Console.WriteLine($"Fee CC: {PaymentProcessor.CalculateFee(cc.Amount)}");    // Output: 5000
        Console.WriteLine($"QRIS Risk: {PaymentProcessor.EvaluateRisk(qris)}");      // Output: Low
        Console.WriteLine($"Crypto Risk: {PaymentProcessor.EvaluateRisk(crypto)}");  // Output: High

        string[] log1 = { "INIT", "AUTH", "SETTLED", "SUCCESS" };
        string[] log2 = { "INIT", "RISK_CHECK", "FAILED" };

        Console.WriteLine(PaymentProcessor.AnalyzeAuditLog(log1)); // Output: Transaction completed smoothly
        Console.WriteLine(PaymentProcessor.AnalyzeAuditLog(log2)); // Output: Failed after stage: RISK_CHECK
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Roslyn Lowering Engine)
Kompilator C# (Roslyn) tidak mengeksekusi *pattern matching* secara dinamis; ia menurunkannya (*lowering*) menjadi instruksi C# 1.0 / Common Intermediate Language (CIL) yang sangat teroptimasi sebelum mencapai JIT (Just-In-Time) compiler.

1. **Type & Property Patterns Lowering**:
   Ketika mengevaluasi `tx switch { CreditCardTx { Is3DSecure: false } => ... }`, Roslyn menghasilkan CIL yang setara dengan:
   ```csharp
   CreditCardTx creditCardTx = tx as CreditCardTx;
   if (creditCardTx != null && !creditCardTx.Is3DSecure) { ... }
   ```
   Instruksi IL yang digunakan adalah `isinst [Assembly]CreditCardTx`. Jika objek cocok, referensi ditempatkan di *evaluation stack*; jika tidak, nilai `null` di-*push*, menghindari pelemparan `InvalidCastException`.

2. **Decision Tree Optimization**:
   Jika terdapat puluhan cabang tipe data turunan, Roslyn menyusun algoritma *Decision Tree*. Alih-alih melakukan *linear checking* serangkaian `if-else` berturut-turut ($O(N)$), kompilator membagi cabang menggunakan uji tipe terkelompok atau mengabstraksikannya ke `switch` numerik berbasis *type token hash* ($O(1)$ hingga $O(\log N)$).

3. **Jump Tables & Lookup Tables**:
   Untuk *constant string pattern* atau *integer pattern*, Roslyn memetakan kasus ke instruksi CIL `switch`, yang oleh JIT dikonversi menjadi *Jump Table* berbasis tabel *address offset*. Jika nilai bersifat jarang (*sparse values*), kompilator menghasilkan struktur *binary search tree* via instruksi kondisional bersarang (`bgt`, `blt`, `beq`).

4. **List Patterns Lowering**:
   Pola `[.., "SUCCESS"]` di-compile menjadi:
   - Pengecekan *Length* / *Count* (misal: `auditStates.Length >= 1`).
   - Akses berbasis indeks langsung: `auditStates[auditStates.Length - 1] == "SUCCESS"`.
   Kompilator mengeliminasi alokasi *slice* array runtime; konstruksi `..` pada *pattern matching* bersifat *zero-allocation* karena murni dihitung lewat manipulasi indexer runtime `^1`.

#### Alokasi Memori / Resource
- **Stack-Allocated Evaluation**: Berbeda dengan *reflection*, *pattern matching* bebas alokasi heap (*zero-heap allocation*) pada level instruksi parsing tipe.
- **Boxing/Unboxing**: Waspadai pencocokan nilai *struct* primitif ke dalam tipe `object`. Mengevaluasi `object obj = 100; if (obj is int i)` memerlukan instruksi `unbox.any`. Namun, pengujian tipe murni via *relational pattern* langsung pada tipe konkret primitif tidak memicu *boxing*.

#### Trade-offs
- **Binary Size vs Execution Speed**: Strategi kompilasi *Decision Tree* dan *Jump Table* mengorbankan ukuran biner CIL yang lebih besar (*unrolled loops* dan *branch targets*) demi meminimalkan *branch mispredictions* pada CPU pipeline.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Manfaatkan Compiler Exhaustiveness Check**: Selalu gunakan `switch expression` untuk mengevaluasi tipe data diskrit seperti `enum` atau hirarki tertutup (`abstract record` / *discriminated unions pattern*). Jika sebuah *enum* baru ditambahkan, Roslyn memunculkan *warning* `CS8509` bahwa cabang belum lengkap.
- **Utamakan Property Pattern dibanding Deep Null-Checking**: Gantikan `if (order != null && order.Customer != null && order.Customer.Address != null)` dengan:
  ```csharp
  if (order is { Customer.Address: { } address }) { ... }
  ```
- **Kombinasikan Pattern Guards (`when`) Hanya untuk Logika Dinamis**: Gunakan sintaks *pattern matching* intrinsik (`and`, `or`, `>`, `<`) untuk batasan statis, dan simpan klausa `when` hanya jika memerlukan pemanggilan *method* eksternal atau evaluasi variabel dinamis di luar objek.

#### Don'ts
- **Hindari Side-Effects di dalam When Guards**:
  ```csharp
  // BAD: Menyebabkan state mutasi saat runtime melakukan evaluasi cabang
  case Order o when ModifyDatabase(o): 
  ```
  Urutan evaluasi antar *guard clauses* dapat diatur ulang atau dioptimalkan oleh JIT. Evaluasi harus bersifat *idempotent* dan *pure function*.
- **Hindari Pengurutan Cabang yang Tertutup (*Shadowed Patterns*)**:
  ```csharp
  // BAD: Kompilator akan memunculkan CS8120 karena cabang kedua unreachable
  case > 0: ...
  case > 100: ... // Error: Cabang ini tidak akan pernah dieksekusi!
  ```
  Selalu urutkan dari pola yang paling spesifik (*restrictive*) ke pola yang paling umum (*permissive*).

#### Edge Cases
- **Handling of `null`**: 
  - Pattern `{}` (empty property pattern) mencocokkan objek apa pun yang **tidak bernilai `null`**.
  - Pattern `_` (discard pattern) mencocokkan apa pun, **termasuk `null`**.
  Jika tidak berhati-hati, menempatkan wildcard `_` tanpa validasi `null` sebelumnya dapat meneruskan referensi null ke blok kode berikutnya.

### 5. Tantangan Eksplorasi Mandiri

1. **Reverse Compilation (IL Inspection)**:
   Buat sebuah metode dengan `switch expression` yang menggunakan *List Pattern* kompleks (misal: `[int first, .., > 100]`). Kompilasi menggunakan konfigurasi `Release`, lalu buka DLL menggunakan tools decompiler (seperti ILSpy, dotPeek, atau situs sharplab.io). Amati bagaimana Roslyn mengonversi *slice syntax* (`..`) menjadi instruksi CIL pengujian panjang array dan batas indeks tanpa melakukan alokasi array baru.
2. **State Machine Menggunakan Tuple Pattern**:
   Rancang sebuah Finite State Machine (FSM) untuk siklus hidup dokumen transaksi:
   - State: `Draft`, `Submitted`, `Approved`, `Rejected`, `Archived`.
   - Event: `Submit`, `Approve`, `Reject`, `Archive`.
   Implementasikan fungsi `Transition(State current, Event trigger) => (current, trigger) switch { ... }` yang menangani semua permutasi valid dan melempar `InvalidOperationException` untuk transisi ilegal dengan memanfaatkan *exhaustiveness checking*.
