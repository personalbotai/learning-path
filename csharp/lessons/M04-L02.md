### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur pemrosesan data berbasis C#, LINQ (*Language Integrated Query*) mentransformasi data collection melalui pipeline fungsional. Tiga operasi paling fundamental dalam pipeline ini adalah filtering (`Where`), projection (`Select`), dan ordering (`OrderBy`/`ThenBy`). Ketiganya diimplementasikan sebagai *extension methods* di dalam kelas statis `System.Linq.Enumerable` (untuk pemrosesan *in-memory* via `IEnumerable<T>`) dan `System.Linq.Queryable` (untuk pemrosesan *remote data source* via `IQueryable<T>`).

```
                [IEnumerable<TSource>]
                          │
                          ▼
             ┌─────────────────────────┐
             │ Where(predicate)        │ ◄── Streaming / Deferred
             └────────────┬────────────┘
                          ▼
             ┌─────────────────────────┐
             │ OrderBy(keySelector)    │ ◄── Non-Streaming / Buffering
             │ ThenBy(secondaryKey)    │     (Memerlukan seluruh data)
             └────────────┬────────────┘
                          ▼
             ┌─────────────────────────┐
             │ Select(selector)        │ ◄── Streaming / Deferred
             └────────────┬────────────┘
                          ▼
                 [Yield Result Pipeline]
```

#### Deferred Execution: Streaming vs. Non-Streaming
Arsitektur LINQ mengadopsi model evaluasi malas (*deferred/lazy execution*). Artinya, pendefinisian pipeline tidak mengeksekusi iterasi data sama sekali sampai enumerasi dipicu (misalnya melalui `foreach`, `.ToList()`, atau `.First()`). Namun, karakteristik eksekusi internal ketiga operator ini memiliki perbedaan mendasar:

1. **`Where` (Streaming Iterator):** Menggunakan generator pola `yield return`. Operator ini bertindak sebagai saringan: membaca satu elemen dari hulu (*upstream*), mengevaluasi delegate `Func<T, bool>`, dan jika `true`, langsung meneruskannya ke hilir (*downstream*) secara inkremental tanpa membebani memori dengan koleksi perantara.
2. **`Select` (Streaming Iterator):** Mengambil satu elemen, mentransformasikannya via `Func<TSource, TResult>`, dan langsung memancarkannya (*yield*). Kompleksitas memorinya adalah $O(1)$.
3. **`OrderBy` / `OrderByDescending` (Non-Streaming / Buffering):** Berbeda dengan `Where` dan `Select`, pengurutan **tidak dapat** dilakukan secara streaming. Algoritma sorting tidak bisa menentukan elemen mana yang berada di urutan pertama sebelum memeriksa *seluruh* elemen dalam sequence. Akibatnya, `OrderBy` memicu *pipeline stall*: ia membaca seluruh data dari upstream ke dalam buffer internal array sebelum elemen pertama dapat dihasilkan ke downstream.

#### Kontrak `IOrderedEnumerable<T>` dan Komposisi Hierarkis
Saat memanggil `OrderBy`, tipe return yang dihasilkan bukan sekadar `IEnumerable<T>`, melainkan `IOrderedEnumerable<T>`. Interface ini memperluas `IEnumerable<T>` dengan metode `CreateOrderedEnumerable`. Fitur ini memungkinkan chaining pengurutan sekunder via `.ThenBy()` tanpa merusak stabilitas urutan primer sebelumnya. Mengganti `.ThenBy()` dengan pemanggilan `.OrderBy()` kedua adalah kesalahan logika umum yang menghapus hasil sorting pertama dan mengulang proses alokasi buffer dari awal.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skenario audit finansial: memfilter transaksi bernilai tinggi atau anomali, mengurutkannya berdasarkan prioritas risiko dan tanggal secara presisi, lalu memproyeksikannya ke dalam DTO (*Data Transfer Object*) yang dioptimalkan untuk transmisi jaringan.

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

public enum TransactionStatus { Pending, Completed, Flagged, Rejected }

public readonly record struct Transaction(
    Guid Id,
    decimal Amount,
    TransactionStatus Status,
    DateTime Timestamp,
    string MerchantCategory
);

public readonly record struct TransactionAuditDto(
    Guid TransactionId,
    decimal Amount,
    string FormattedDate,
    bool RequiresUrgentReview
);

public class AuditEngine
{
    public static IEnumerable<TransactionAuditDto> ProcessHighRiskTransactions(
        IEnumerable<Transaction> source,
        decimal amountThreshold,
        DateTime cutoffDate)
    {
        ArgumentNullException.ThrowIfNull(source);

        // Definisi pipeline LINQ: Belum dieksekusi di sini (Deferred Execution)
        var auditPipeline = source
            // 1. FILTERING: Evaluasi predicate streaming
            .Where(tx => (tx.Status == TransactionStatus.Flagged || tx.Amount >= amountThreshold) 
                         && tx.Timestamp >= cutoffDate)
            
            // 2. ORDERING: Buffering & Stable Multi-Key Sort
            // Primary sort descending (nilai transaksi terbesar)
            .OrderByDescending(tx => tx.Amount)
            // Secondary sort ascending (transaksi tertua didahulukan)
            .ThenBy(tx => tx.Timestamp)
            
            // 3. PROJECTION: Transformasi bentuk domain model ke lightweight DTO
            .Select(tx => new TransactionAuditDto(
                TransactionId: tx.Id,
                Amount: tx.Amount,
                FormattedDate: tx.Timestamp.ToString("yyyy-MM-dd HH:mm:ss"),
                RequiresUrgentReview: tx.Status == TransactionStatus.Flagged && tx.Amount > 50_000m
            ));

        return auditPipeline;
    }
}

public class Program
{
    public static void Main()
    {
        var now = DateTime.UtcNow;
        var transactions = new List<Transaction>
        {
            new(Guid.NewGuid(), 12000m, TransactionStatus.Completed, now.AddHours(-1), "Retail"),
            new(Guid.NewGuid(), 75000m, TransactionStatus.Flagged,   now.AddHours(-5), "Crypto"),
            new(Guid.NewGuid(), 90000m, TransactionStatus.Completed, now.AddHours(-2), "WireTransfer"),
            new(Guid.NewGuid(), 75000m, TransactionStatus.Completed, now.AddHours(-3), "Luxury"),
            new(Guid.NewGuid(), 3000m,  TransactionStatus.Rejected,  now.AddHours(-4), "Retail")
        };

        // Konsumsi hasil pipeline (Eksekusi nyata dimulai di sini)
        IEnumerable<TransactionAuditDto> auditStream = AuditEngine.ProcessHighRiskTransactions(
            transactions, 
            amountThreshold: 50_000m, 
            cutoffDate: now.AddDays(-1)
        );

        foreach (var item in auditStream)
        {
            Console.WriteLine($"[AUDIT] ID: {item.TransactionId} | Amt: {item.Amount:C} | " +
                              $"Date: {item.FormattedDate} | Urgent: {item.RequiresUrgentReview}");
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: State Machine dan Iterator Optimization
Saat kode dikompilasi, C# Compiler dan .NET Runtime tidak menjalankan loop naif. Ada beberapa optimasi internal:

1. **Iterator Chains Folding:**
   Pada .NET Runtime modern (.NET Core 3.0+ hingga .NET 8/9), perangkaian `.Where().Where()` atau `.Where().Select()` dioptimalkan menggunakan tipe internal khusus seperti `WhereSelectEnumerableIterator<TSource, TResult>`. Alih-alih membuat dua *enumerator state machine* bertingkat di heap, runtime menggabungkan delegate filter dan proyeksi ke dalam satu iterator state machine tunggal, mereduksi *overhead stack frame call* dari method `MoveNext()`.

2. **Mekanisme Kerja `OrderBy` via `EnumerableSorter`:**
   Saat `MoveNext()` dipanggil pertama kali pada `IOrderedEnumerable<T>`:
   - `OrderBy` membuat salinan array internal (`Buffer<TElement>`) dari seluruh data upstream.
   - Menginstansiasi `EnumerableSorter<TElement, TKey>`.
   - Mengalokasikan array integer indeks berukuran $N$ (`int[] map = new int[count]`), di mana `map[i] = i`.
   - **Bukan elemen objeknya yang ditukar (swap), melainkan array indeks integer-nya.** Algoritma pengurutan internal menggunakan modifikasi *QuickSort* yang stabil (atau intro-sort berbasis indeks). 
   - Nilai komparasi di-*cache* untuk meminimalkan pemanggilan berulang ke `keySelector`.
   - Setelah array indeks terurut, iterator memancarkan objek asli dengan memetakan kembali `buffer[map[i]]`.

```
[Element Data]  --> [Obj_A, Obj_B, Obj_C, Obj_D]  (Tidak dipindah di memori)
Indeks Awal     --> [  0  ,   1  ,   2  ,   3  ]
                     │      │      │      │
Sort Komparasi       ▼      ▼      ▼      ▼
Indeks Terurut  --> [  2  ,   0  ,   3  ,   1  ]  (Swap hanya terjadi pada int[])
Yield Output    -->  Obj_C  Obj_A  Obj_D  Obj_B
```

#### Alokasi Memori & Garbage Collection (GC)
- **Delegate Allocations & Closures:** Jika predicate pada `.Where(x => x.Val > limit)` menangkap variabel lokal (`limit`), compiler menginstansiasi *display class* (closure) di managed heap. Jika query ini berada di jalur eksekusi frekuensi tinggi (*hot path*), alokasi closure ini memicu GC pressure (Gen 0).
- **OrderBy Memory Footprint:** Memerlukan $O(N)$ alokasi memori tambahan: 
  1. Array internal seukuran $N$ untuk mereferensikan elemen.
  2. Array integer seukuran $N$ untuk komparasi indeks.
  3. Array kunci hasil evaluasi `keySelector` untuk menghindari pemanggilan delegate berkali-kali selama sorting.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Urutkan Pipeline Secara Efisien (Filter Terlebih Dahulu):** Selalu posisikan `Where` sebelum `OrderBy`. Menyaring data dari 1.000.000 item menjadi 100 item berarti `OrderBy` hanya mengalokasikan memori dan menyortir 100 item alih-alih 1.000.000 item.
- **Gunakan Readonly Structs / Records untuk Projection:** Jika hasil proyeksi `Select` hanya digunakan sementara dalam scope lokal, proyeksikan ke `record struct` atau `ValueTuple` untuk mencegah alokasi heap dari instansiasi class anonim biasa.
- **Gunakan StringComparer Eksplisit:** Saat mengurutkan atau memfilter teks, selalu spesifikasikan `StringComparison` atau `IComparer<string>` (misal: `StringComparer.OrdinalIgnoreCase`) guna menghindari inkonsistensi budaya lokal (*culture-sensitive comparisons*) dan optimasi performa komparasi byte langsung.

#### Don'ts
- **Menghubungkan `OrderBy` Berturut-turut:** 
  ```csharp
  // SALAH: OrderBy kedua menghapus/menimpa efek pengurutan pertama sepenuhnya!
  var bad = list.OrderBy(x => x.Category).OrderBy(x => x.Price);

  // BENAR: Menjaga stabilitas hirarki pengurutan
  var good = list.OrderBy(x => x.Category).ThenBy(x => x.Price);
  ```
- **Multiple Enumeration:** Memanggil terminal method (seperti `.Count()`, `.Any()`, atau `foreach`) berulang kali pada variabel bertipe `IEnumerable<T>` yang memegang hasil `Where`/`Select` akan menyebabkan seluruh kalkulasi diulang dari elemen pertama:
  ```csharp
  var query = data.Where(HeavyCalculation);
  if (query.Any()) // Iterasi 1 dieksekusi
  {
      foreach (var item in query) { } // Iterasi 2 dieksekusi ULANG dari awal!
  }
  ```

#### Edge Cases
- **Null Keys dalam `OrderBy`:** Berdasarkan konvensi CLR, nilai `null` dianggap lebih kecil daripada nilai non-null. Pada `.OrderBy(x => x.NullableProperty)`, elemen dengan nilai `null` akan selalu ditaruh di indeks awal sequence.
- **Exception Terlambat (Late-surfacing Exceptions):** Exception logic di dalam `Where` atau `Select` (seperti `NullReferenceException` atau `DivideByZeroException`) tidak akan mematikan aplikasi saat pipeline didefinisikan, melainkan meledak saat koleksi mulai di-loop di bagian kode lain yang jauh dari titik deklarasi query.
