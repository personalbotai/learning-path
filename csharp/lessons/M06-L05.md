### 1. Konsep & Arsitektur Mendalam

Mengukur performa kode di runtime modern seperti .NET tidak sesederhana membungkus blok kode dengan `System.Diagnostics.Stopwatch`. Pengukuran naif rentan menghasilkan data bias akibat berbagai variabel runtime dan hardware:

1. **JIT Warmup & Tiered Compilation**: .NET menggunakan *Tiered Compilation* (Tier 0 / Quick JIT untuk startup cepat, kemudian Tier 1 / Optimized JIT setelah batas eksekusi tertentu terlampaui). Pengukuran manual sering kali secara tidak sengaja mengukur kode Tier 0 yang belum teroptimasi.
2. **Garbage Collection (GC) Interference**: Siklus GC yang terpicu secara acak di tengah pengujian dapat mendistorsi latensi eksekusi secara masif.
3. **Dead-Code Elimination**: Compiler (Roslyn) dan JIT compiler dapat mendeteksi variabel atau kalkulasi yang tidak digunakan, lalu menghapusnya secara otomatis dari instruksi assembly akhir (*dead-code elimination*).
4. **OS Thread Scheduling & CPU Throttling**: Mekanisme *CPU frequency scaling* (Turbo Boost, thermal throttling) dan *context switching* oleh OS scheduler menyebabkan variansi eksekusi antar iterasi.

**BenchmarkDotNet (BDN)** adalah framework benchmarking standar industri untuk .NET (digunakan langsung oleh tim internal Microsoft Runtime). BDN mengisolasi variabel-variabel di atas melalui arsitektur berbasis *isolated process harness*:

```
+-----------------------------------------------------------+
| Host Process (Orchestrator)                               |
| - Parse konfigurasi (Jobs, Diagnosers, Exporters)         |
| - Generate source code runner spesifik                    |
| - Compile runner via Roslyn/dotnet CLI (Release Mode)     |
+-----------------------------+-----------------------------+
                              | Spawns
                              v
+-----------------------------------------------------------+
| Worker Process (Benchmark Executor)                       |
| - Pilot Phase (Menentukan iterasi optimal)                |
| - Warmup Phase (Memaksa JIT Tier 1 / Dynamic PGO)         |
| - Target Phase (Eksekusi iterasi aktual)                  |
| - Overhead Evaluation (Mengurangi overhead BDN engine)    |
| - Diagnostics (EventPipe / ETW untuk alokasi memori & GC) |
+-----------------------------------------------------------+
```

BDN menggunakan pendekatan statistik non-parametrik dan parametrik (Confidence Intervals, Median, Standard Deviation) untuk menyaring *outliers* dan menyajikan metrik yang stabil secara deterministik.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Membandingkan performa parsing dan transformasi string: Naive Concatenation vs. `StringBuilder` vs. `string.Create` (berbasis `Span<T>`).

Tambahkan package via CLI:
```bash
dotnet add package BenchmarkDotNet
```

File: `StringFormattingBenchmark.cs`
```csharp
using System.Buffers;
using System.Text;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Order;

namespace Performance.Benchmarks;

[MemoryDiagnoser] // Mengaktifkan tracking alokasi memori (Gen 0/1/2 dan Allocated Bytes)
[Orderer(SummaryOrderPolicy.FastestToSlowest)] // Mengurutkan hasil dari yang tercepat
[RankColumn] // Memberikan label peringkat performa
public class StringFormattingBenchmark
{
    private string _prefix = null!;
    private int _id;
    private string _suffix = null!;

    [Params(10, 100)] // Menjalankan benchmark untuk berbagai skala input
    public int DataCount { get; set; }

    [GlobalSetup]
    public void Setup()
    {
        _prefix = "TRANSACTION_EVENT_LOG_PREFIX_";
        _id = 428942;
        _suffix = "_TERMINATED_NODE";
    }

    [Benchmark(Baseline = true)] // Menjadi titik acuan komparasi (Ratio 1.00)
    public string NaiveConcatenation()
    {
        string result = string.Empty;
        for (int i = 0; i < DataCount; i++)
        {
            // Menghasilkan alokasi string baru pada setiap iterasi loop (+ operator)
            result = _prefix + _id + "_" + i + _suffix;
        }
        return result; // Wajib me-return value untuk menghindari Dead-Code Elimination
    }

    [Benchmark]
    public string UsingStringBuilder()
    {
        var sb = new StringBuilder(128); // Pre-allocate initial capacity untuk menghindari resize array
        for (int i = 0; i < DataCount; i++)
        {
            sb.Clear();
            sb.Append(_prefix)
              .Append(_id)
              .Append('_')
              .Append(i)
              .Append(_suffix);
        }
        return sb.ToString();
    }

    [Benchmark]
    public string UsingStringCreateZeroAllocation()
    {
        string result = string.Empty;
        for (int i = 0; i < DataCount; i++)
        {
            int currentIteration = i;
            // Menghitung panjang target buffer di awal
            int totalLength = _prefix.Length + 6 + 1 + GetDigitCount(currentIteration) + _suffix.Length;

            // Alokasi memori langsung pada string buffer target tanpa copy intermediate object
            result = string.Create(totalLength, (_prefix, _id, currentIteration, _suffix), static (span, state) =>
            {
                state._prefix.AsSpan().CopyTo(span);
                int written = state._prefix.Length;

                state._id.TryFormat(span[written..], out int idChars);
                written += idChars;

                span[written++] = '_';

                state.currentIteration.TryFormat(span[written..], out int iterChars);
                written += iterChars;

                state._suffix.AsSpan().CopyTo(span[written..]);
            });
        }
        return result;
    }

    private static int GetDigitCount(int value)
    {
        if (value == 0) return 1;
        int count = 0;
        while (value > 0)
        {
            count++;
            value /= 10;
        }
        return count;
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  - BDN memisahkan siklus hidup ke dalam 4 stage: **Pilot** (menentukan berapa banyak iterasi loop per *operation invocation* agar resolusi timer CPU valid), **Warmup** (mengeksekusi kode berulang kali agar JIT mentransisikan method ke Tier 1 dan compiler melakukan optimasi inlining), **Overhead** (mengukur biaya iterasi loop kosong milik BDN sendiri), dan **Actual/Target Iteration** (eksekusi murni).
  - BDN secara otomatis mengubah priority process menjadi `High` dan mengaitkan thread eksekusi ke CPU Core tertentu (*Processor Affinity*) guna meminimalisir *cache invalidation* akibat core hopping.
- **Alokasi Memori / Resource**:
  - `[MemoryDiagnoser]` tidak menggunakan interceptor berbasis proxy. Di Windows, BDN memanfaatkan ETW (*Event Tracing for Windows*); di Linux/macOS, BDN menggunakan *EventPipe*.
  - BDN membaca metrik `GC.GetAllocatedBytesForCurrentThread()` sebelum dan sesudah eksekusi batch untuk menghitung alokasi heap managed per operasi secara absolut tanpa terdistorsi oleh alokasi thread background.
- **Trade-offs**:
  - Isolasi tinggi dan analisis statistik yang akurat menuntut waktu eksekusi yang lama (satu benchmark method dapat memakan waktu 30-90 detik untuk convergence).
  - BDN tidak didesain untuk profiling *end-to-end user scenario* (seperti HTTP pipeline kompleks), melainkan untuk *micro-benchmarking* dan *nano-benchmarking* pada level algoritma, alokasi memori, atau library method.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Kembalikan nilai (Return value)**: Selalu kembalikan hasil komputasi dari method `[Benchmark]` atau gunakan `BenchmarkDotNet.Engines.Consumer` jika return type adalah complex stream / enumerable. Ini mencegah Roslyn/JIT mengeliminasi method body karena dianggap *no-op*.
  - **Konfigurasi `Release`**: Pastikan aplikasi di-build dan di-run menggunakan `-c Release` dengan *debugger detached*. BDN akan melempar peringatan keras (*assertion error*) jika mendeteksi assembly `Debug` atau debugger aktif.
  - **Isolasi dependensi**: Gunakan `[GlobalSetup]` untuk inisialisasi data yang berat dan `[IterationSetup]` secara hati-hati (karena dapat menginterferensi timing jika run-time overhead-nya tinggi).

- **Don'ts**:
  - **Jangan gunakan alokasi di `[IterationSetup]`**: Pengalokasian memori pada fase ini dapat memicu GC di fase `[Benchmark]`, yang merusak metrik `Gen 0/1/2`.
  - **Jangan mengukur durasi mikro via loop manual di dalam method**:
    ```csharp
    // SALAH: Jangan looping manual untuk mengukur performa
    [Benchmark]
    public void BadBenchmark() {
        for(int i = 0; i < 10000; i++) DoWork();
    }

    // BENAR: Biarkan BDN yang menentukan jumlah invocations
    [Benchmark]
    public void GoodBenchmark() => DoWork();
    ```

- **Edge Cases & Compiler Tricks**:
  - **Constant Folding**: Jika benchmark menerima parameter konstan, JIT dapat mengevaluasi hasil komputasi pada saat kompilasi. Solusi: Gunakan `[Params]` atau field yang nilainya diisi saat runtime (`[GlobalSetup]`).

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Penalti Struct Boxing**:
   Buat sebuah class benchmark yang membandingkan performa sorting `List<int>` vs `List<object>` (di mana `int` mengalami proses *boxing/unboxing*). Analisis kolom `Allocated` pada output `[MemoryDiagnoser]` dan jelaskan mengapa terjadi degradasi throughput instruksi per cycle pada JIT.
2. **Cross-Runtime Comparison**:
   Konfigurasikan BDN Job menggunakan atribut `[SimpleJob]` untuk membandingkan eksekusi algoritma traversal data (misal: array vs. `ReadOnlySpan<T>`) di dua runtime berbeda: `.NET 8.0` dan `.NET 9.0`. Amati optimasi baru JIT (Dynamic PGO / Loop Unrolling) pada versi runtime terbaru.
