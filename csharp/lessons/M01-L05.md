### 1. Konsep & Arsitektur Mendalam

Dalam runtime .NET, manajemen memori berpusat pada garbage collector (GC). Secara historis, tipe data linear berurutan direpresentasikan oleh `T[]` (Array). Namun, dalam sistem dengan *throughput* tinggi, penggunaan array konvensional memicu masalah performa sistemik:
1. **GC Pressure**: Membuat subset (slicing) dari array menghasilkan alokasi array baru di *managed heap*, memicu siklus GC Gen 0/Gen 1 yang agresif.
2. **Fragmentasi Large Object Heap (LOH)**: Objek array berukuran $\ge 85.000$ byte langsung dialokasikan ke LOH, yang tidak dipadatkan secara default dan rentan terhadap fragmentasi memori.
3. **Rigiditas Sumber Memori**: Struktur data tidak dapat merepresentasikan data berurutan secara generik jika data tersebut berasal dari tumpukan memori lain (misalnya unmanaged memory dari C-library atau memori *stack frame* via `stackalloc`).

Untuk mengatasi masalah ini, .NET memperkenalkan arsitektur memori modern berbasis *zero-allocation abstractions*: `Span<T>`, `ReadOnlySpan<T>`, `Memory<T>`, dan `ReadOnlyMemory<T>`.

```
                    ┌─────────────────────────┐
                    │    Contiguous Memory    │
                    │  (Heap, Stack, Native)  │
                    └────────────┬────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       ┌──────────────────┐            ┌───────────────────┐
       │     Span<T>      │            │     Memory<T>     │
       │   (ref struct)   │            │ (standard struct) │
       ├──────────────────┤            ├───────────────────┤
       │ - Stack-only     │            │ - Heap-safe       │
       │ - Synchronous    │            │ - Async/Await OK  │
       │ - Ref pointer    │            │ - Wraps buffer    │
       └──────────────────┘            └─────────┬─────────┘
                                                 │ .Span
                                                 ▼
                                       ┌───────────────────┐
                                       │ Ephemeral Span<T> │
                                       └───────────────────┘
```

#### Arsitektur Array (`T[]`)
Array di C# adalah *reference type* yang diwarisi dari `System.Array`. Di balik layar, layout memori dari sebuah array pada managed heap terdiri dari:
- **Object Header** (8 byte pada sistem 64-bit): Menyimpan sync-block index untuk sinkronisasi thread dan hash code.
- **MethodTable Pointer** (8 byte): Menunjuk ke metadata tipe data di runtime.
- **Length** (4 byte, dialignasi ke 8 byte): Menyimpan panjang array.
- **Data Payload**: Elemen `T` yang berurutan secara contiguous.

#### Arsitektur `Span<T>`
`Span<T>` adalah `ref struct` (hanya dapat dialokasikan di *call stack* CPU). Di tingkat CoreCLR, `Span<T>` didefinisikan sebagai *by-ref-like type* yang merepresentasikan *fat pointer*:
- `ref T _pointer`: Managed interior pointer ke alamat awal data (bisa menunjuk ke heap, stack, atau native heap).
- `int _length`: Panjang segmen memori.

Karena `Span<T>` merupakan `ref struct`, Runtime Engine dan Roslyn compiler menegakkan aturan ketat: **`Span<T>` tidak boleh lolos ke managed heap**. Oleh karena itu, `Span<T>` tidak dapat dijadikan tipe generic parameter pada kelas biasa, tidak bisa dibox, tidak bisa menjadi field dari class biasa, dan tidak bisa masuk ke dalam state machine `async/await` atau *lambda closure*.

#### Arsitektur `Memory<T>`
Untuk skenario di mana referensi memori harus bertahan melintasi *heap context*—khususnya pada model pemrograman asinkron (`async/await`) atau disimpan sebagai *field* kelas—.NET menyediakan `Memory<T>`. 
`Memory<T>` adalah struct biasa (non-ref) yang membungkus:
- `object? _object`: Referensi ke `T[]`, `string`, atau instance `MemoryManager<T>`.
- `int _index`: Offset awal.
- `int _length`: Panjang segmen.

Ketika data perlu dimanipulasi atau dibaca secara efisien, metode `.Span` dipanggil untuk menghasilkan `Span<T>` sesaat (*ephemeral*) di dalam stack frame eksekusi saat itu.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi pemrosesan payload data (misalnya format logging terstruktur: `[TIMESTAMP] LEVEL: MESSAGE`) tanpa alokasi string baru melalui *zero-copy slicing*.

```csharp
using System;
using System.Buffers;
using System.Text;

public class LogProcessor
{
    // Simulasi payload raw string yang datang dari network stream
    private const string RawLog = "2026-03-30T10:14:00.123Z|CRITICAL|Database connection pool exhausted.";

    public static void Main()
    {
        // 1. Span-based Zero Allocation Parsing
        ParseLogZeroAlloc(RawLog);

        // 2. Stackalloc Memory dengan Span
        SpanFromStackMemory();

        // 3. Memory<T> untuk Operasi Asinkron
        ProcessLogAsync(RawLog.ToCharArray()).GetAwaiter().GetResult();
    }

    public static void ParseLogZeroAlloc(ReadOnlySpan<char> logLine)
    {
        // Mencari delimiter '|' pertama tanpa alokasi Substring()
        int firstPipe = logLine.IndexOf('|');
        if (firstPipe == -1) return;

        ReadOnlySpan<char> timestamp = logLine[..firstPipe]; // Zero-copy slicing
        ReadOnlySpan<char> remaining = logLine[(firstPipe + 1)..];

        int secondPipe = remaining.IndexOf('|');
        if (secondPipe == -1) return;

        ReadOnlySpan<char> level = remaining[..secondPipe];
        ReadOnlySpan<char> message = remaining[(secondPipe + 1)..];

        // Cetak segment langsung tanpa alokasi string
        Console.WriteLine($"[Zero-Alloc Slicing]");
        Console.WriteLine($"Timestamp : {timestamp}");
        Console.WriteLine($"Level     : {level}");
        Console.WriteLine($"Message   : {message}");
    }

    public static void SpanFromStackMemory()
    {
        // Alokasi memori langsung di Thread Call Stack (0 byte di Heap)
        Span<byte> buffer = stackalloc byte[16];
        for (int i = 0; i < buffer.Length; i++)
        {
            buffer[i] = (byte)(i * 2);
        }

        Console.WriteLine("\n[Stackalloc Span]");
        Console.WriteLine($"Length on Stack: {buffer.Length} bytes");
        Console.WriteLine($"First byte: {buffer[0]}, Last byte: {buffer[^1]}");
    }

    public static async System.Threading.Tasks.Task ProcessLogAsync(Memory<char> memoryBuffer)
    {
        Console.WriteLine("\n[Async Memory<T>]");
        
        // Memory<T> aman dilewatkan melintasi yield points async
        await System.Threading.Tasks.Task.Delay(10);

        // Proyeksikan ke Span saat ingin membaca/memproses secara sinkron
        ReadOnlySpan<char> span = memoryBuffer.Span;
        int levelEnd = span.IndexOf('|');
        
        Console.WriteLine($"Extracted asynchronously: {span[..levelEnd]}");
    }
}
```

#### Analisis Alur Eksekusi
1. `logLine[..firstPipe]`: Menggunakan C# range indexer pada `ReadOnlySpan<char>`, operasi ini tidak memanggil `string.Substring()` melainkan hanya menginstansiasi instance `ReadOnlySpan<char>` baru dengan pointer tergeser dan ukuran `Length` yang diperbarui.
2. `stackalloc byte[16]`: Runtime memajukan pointer stack frame (`ESP`/`RSP`) sebesar 16 byte. Data dibersihkan secara otomatis saat stack frame metode berakhir, tanpa intervensi GC.
3. `ProcessLogAsync(Memory<char>)`: Compiler mengubah metode ini menjadi state machine kelas tersembunyi. `Memory<char>` disimpan sebagai field di dalam state machine tersebut tanpa melanggar batasan CLR.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Bounds-Check Elimination (BCE)
Akses elemen array atau span (`data[i]`) biasanya menghasilkan instruksi assembly periksa batas (bounds-check):
```asm
cmp rdx, [rcx+8]   ; Bandingkan index (rdx) dengan Array/Span Length
jae ThrowIndexOutOfRangeException
```
JIT Compiler (.NET RyuJIT) menerapkan **Bounds-Check Elimination (BCE)**. Jika loop menggunakan pattern standar:
```csharp
for (int i = 0; i < span.Length; i++) {
    var val = span[i];
}
```
RyuJIT menganalisis bahwa `i` selalu berada dalam rentang `0` sampai `span.Length - 1`. Instruksi percabangan `cmp` dan `jae` akan dihilangkan seluruhnya dari loop body, menghasilkan instruksi raw pointer dereferencing yang setara dengan pointer aritmatika C/C++.

#### Alokasi Memori: Mekanika Interior Pointer
`Span<T>` memanfaatkan *Managed Pointer* (`ref T`). Tidak seperti pointer raw C (`T*`), jika pointer ini menunjuk ke elemen dalam objek di managed heap, GC Engine CoreCLR **mengetahui keberadaan pointer ini**. 

```
Managed Heap:
[ Object Header ][ MethodTable ][ Length ][ Elemen 0 ][ Elemen 1 ][ Elemen 2 ]
                                                ▲
                                                │
Stack Frame:                                    │
Span<T> { _pointer ─────────────────────────────┘ , _length = 2 }
```
Saat GC melakukan fase *Compacting* (memindahkan objek untuk mengurangi fragmentasi), GC akan melacak dan memperbarui alamat `_pointer` di dalam stack frame `Span<T>` secara atomik.

#### Trade-offs
| Metrik | `T[]` (Array) | `Span<T>` | `Memory<T>` |
| :--- | :--- | :--- | :--- |
| **Alokasi Heap** | Ya | Tidak pernah (Stack only) | Ya, jika membungkus array baru |
| **Dukungan Asinkron** | Ya | Tidak bisa menyeberang `await` | Ya |
| **Overhead Slicing** | $O(N)$ (alokasi baru & copy) | $O(1)$ (hanya update struct) | $O(1)$ (hanya update struct) |
| **Fleksibilitas Sumber Data**| Khusus Managed Heap | Stack, Heap, Native | Heap, Native (via custom manager)|

### 4. Best Practices & Common Pitfalls

#### Do's
- Gunakan `ReadOnlySpan<char>` sebagai parameter parser string alih-alih `string` biasa untuk menghindari alokasi substring yang masif.
- Gunakan `stackalloc` untuk buffer lokal berukuran kecil (di bawah 1 KB) yang sering dipakai dan dibuang.
- Gunakan `Memory<T>` atau `ReadOnlyMemory<T>` pada API interfaces publik untuk asynchronous processing (misal: `Stream.ReadAsync(Memory<byte>)`).
- Konversi `Memory<T>` ke `Span<T>` sesaat sebelum melakukan loop komputasi sinkron (`memory.Span`).

#### Don'ts
- **Jangan** pernah menggunakan `stackalloc` di dalam perulangan tak terbatas atau untuk ukuran buffer dinamis yang besar dari user input; hal ini memicu `StackOverflowException` fatal yang meruntuhkan proses secara instan.
- **Jangan** mencoba melakukan *box* terhadap `Span<T>` atau menyimpannya di koleksi generic klasik:
  ```csharp
  // KODE TIDAK VALID / ERROR KOMPILASI
  List<Span<byte>> invalidList; 
  object boxed = (object)mySpan;
  ```
- **Jangan** mengabaikan immutability. Gunakan `ReadOnlySpan<T>` dan `ReadOnlyMemory<T>` secara default kecuali memang ada kebutuhan mutasi inplace.

#### Edge Cases
- **Lifetime Safety**: Roslyn compiler menerapkan *escape analysis*. Anda tidak dapat mengembalikan `Span<T>` yang merujuk pada `stackalloc` lokal ke pemanggil metode:
  ```csharp
  public Span<byte> BrokenMethod()
  {
      Span<byte> buffer = stackalloc byte[10];
      return buffer; // CS8352: Cannot return local by reference
  }
  ```
- **Memory Pooling Concurrency**: Saat menggunakan `MemoryPool<T>.Shared.Rent()`, pastikan pemanggilan `Dispose()` dieksekusi dengan pola `try/finally`. Buffer yang di-rent tidak di-nol-kan secara default dan dapat menimbulkan kebocoran data jika dibaca sebelum di-overwrite.
