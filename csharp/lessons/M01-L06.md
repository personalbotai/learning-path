## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara default, parameter dalam C# dievaluasi secara **Pass-by-Value**. Ketika sebuah variabel dilewatkan ke dalam method:
- **Value Type (`struct`, `int`, `enum`)**: Runtime menduplikasi nilai biner (*bitwise copy*) langsung ke dalam *stack frame* method target.
- **Reference Type (`class`)**: Runtime menduplikasi *pointer reference* (alamat memori heap) ke dalam *stack frame* method target. Objek aslinya tidak digandakan, tetapi variabel penampung referensinya yang digandakan.

Untuk mengubah perilaku default ini dan mengoptimalkan performa (menghindari duplikasi payload memori besar), C# menyediakan beberapa *parameter modifier*:

| Modifier | State Awal Variabel Pemanggil | Harus Diisi di Dalam Method? | Akses di Dalam Method | Tujuan Utama |
|---|---|---|---|---|
| `ref` | Harus sudah diinisialisasi | Opsional | Read / Write | Memodifikasi variabel caller langsung di lokasi memorinya. |
| `out` | Boleh belum diinisialisasi | **Wajib** sebelum method exit | Write-only (sampai diinisialisasi) | Mengembalikan beberapa nilai (*multi-return*) seperti pola `TryParse`. |
| `in` | Harus sudah diinisialisasi | **Dilarang** (Read-Only) | Read-only | Optimasi: pass struct besar via reference tanpa alokasi salinan data. |
| `ref readonly` | Harus sudah diinisialisasi | **Dilarang** (Read-Only) | Read-only | Mirip `in`, tetapi menolak *defensive copying* pada tingkat compiler. |

#### Local Functions vs Lambda Expressions
Diperkenalkan pada C# 7.0, **Local Functions** adalah method privat yang dideklarasikan di dalam blok method lain. Berbeda dengan *lambda expression* (`Func<T>`, `Action<T>`):
1. **Zero Allocation**: Local function tidak memerlukan instansiasi delegate (`System.MulticastDelegate`) di heap.
2. **Inlineable**: JIT compiler dapat melakukan *inlining* secara agresif terhadap local function.
3. **Optimized Closures**: Saat menangkap (*capture*) variabel lokal sekitar, local function mengalokasikan struct closure di stack, bukan class closure di heap (selama tidak dikonversi ke delegate).
4. **Static Local Functions** (C# 8+): Menjamin secara *compile-time* bahwa fungsi tersebut tidak menangkap variabel lokal luar (`enclosing scope`), mencegah alokasi memori implisit secara permanen.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern yang menggabungkan `ref`, `out`, `in`, dan `static local function` untuk sistem pemrosesan transaksi berkinerja tinggi.

```csharp
using System;

public readonly struct TransactionPayload
{
    public readonly long TransactionId;
    public readonly decimal Amount;
    public readonly DateTime Timestamp;

    public TransactionPayload(long id, decimal amount)
    {
        TransactionId = id;
        Amount = amount;
        Timestamp = DateTime.UtcNow;
    }
}

public class PaymentProcessor
{
    // Menggunakan 'in' untuk menghindari copying struct berukuran 32 bytes pada tiap pemanggilan
    public bool Process(in TransactionPayload payload, ref decimal accountBalance, out string executionLog)
    {
        // Parameter 'out' wajib diberi nilai sebelum method berakhir pada semua branch logika
        if (payload.Amount <= 0)
        {
            executionLog = $"[FAILED] Invalid amount: {payload.Amount}";
            return false;
        }

        // Memanggil Static Local Function: Menghilangkan risiko memory leak & heap allocation
        if (!ValidateBalance(accountBalance, payload.Amount))
        {
            executionLog = $"[FAILED] Insufficient funds: {accountBalance} < {payload.Amount}";
            return false;
        }

        // Modifikasi langsung variabel pemanggil melalui 'ref'
        accountBalance -= payload.Amount;

        executionLog = $"[SUCCESS] TxID: {payload.TransactionId}, Remaining: {accountBalance}";
        return true;

        // Static Local Function: Terisolasi secara scope, tidak bisa membaca state 'payload' secara implisit
        static bool ValidateBalance(decimal currentBalance, decimal requiredAmount)
        {
            return currentBalance >= requiredAmount;
        }
    }
}

public class Program
{
    public static void Main()
    {
        var processor = new PaymentProcessor();
        var tx = new TransactionPayload(1001, 250.50m);
        decimal userBalance = 1000.00m;

        // Pemanggilan method menggunakan modifier yang eksplisit
        // Menggunakan out-variable declaration inline
        bool isSuccess = processor.Process(in tx, ref userBalance, out string log);

        Console.WriteLine($"Result: {isSuccess}");
        Console.WriteLine($"Log: {log}");
        Console.WriteLine($"New Balance in Caller: {userBalance}");
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Managed Pointer
Pada level **Intermediate Language (IL)**, tidak ada perbedaan biner mendasar antara `ref` dan `out`. Keduanya diterjemahkan menjadi **Managed Pointer** (`&` atau tipe `byref` di CLR metadata, contoh: `valuetype TransactionPayload&`).

```il
// IL Method Signature
.method public hidebysig instance bool 
Process(
    [in] valuetype TransactionPayload& payload, // 'in' diwakili oleh managed pointer + [in] attribute
    valuetype [System.Runtime]System.Decimal& accountBalance, // 'ref'
    [out] string& executionLog // 'out' diwakili oleh managed pointer + [out] attribute
) cil managed
```

- Ketika argumen bertanda `ref` atau `out` dipassing, alamat memori lokal pada stack frame caller dimuat menggunakan instruksi `ldloca` (*load local address*) alih-alih `ldloc` (*load local value*).
- **Aturan `out`**: Enforcing bahwa `out` harus diinisialisasi murni berasal dari verifikasi static analysis Roslyn (C# Compiler), bukan batasan level hardware CLR.

#### Local Function: Mangled Methods & Struct Closure
Saat kode C# di-compile, *local function* diubah menjadi method privat biasa di dalam tipe yang bersangkutan dengan nama yang di-*mangle*:
`<ParentMethodName>g__LocalFunctionName|Index_SubIndex(...)`.

Jika local function melakukan capturing terhadap variabel lokal method pembungkus:
1. **Local Function**: Roslyn membentuk closure menggunakan `struct` bernilai internal yang dilewatkan via `ref` ke generated method. Data tetap tinggal di stack frame.
2. **Lambda Expression (`Action`/`Func`)**: Roslyn harus membentuk closure berupa `class` heap object instance (`<>c__DisplayClass`), memicu alokasi memori GC (*Garbage Collection pressure*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `in` pada Readonly Struct Besar**: Gunakan `in` hanya jika ukuran `struct` melebihi `IntPtr.Size * 2` (16 bytes pada 64-bit) dan struct berstatus `readonly struct`.
- **Gunakan `static` pada Local Function**: Tambahkan modifier `static` pada local function secara default. Ini mencegah capturing variabel liar secara tidak sengaja.
- **Pola `out` untuk Parsing/Lookup**: Terapkan idiomatic .NET pattern `bool TryDoSomething(..., out T result)` untuk operasi yang rentan gagal daripada melempar Exception (*Exceptions should be exceptional*).

#### Don'ts
- **Menghindari `in` pada Non-Readonly Struct**:
  Jika struct **tidak** ditandai dengan keyword `readonly struct`, compiler C# akan membuat **Defensive Copy** (salinan memori penuh ke stack) setiap kali field atau method dari struct tersebut diakses di dalam fungsi target untuk menjamin invariabilitas data. Hal ini membalikkan tujuan optimasi menjadi degradasi performa.
- **Jangan Menggunakan `ref` / `out` sebagai Pengganti Objek Domain**: Jangan membuat method dengan 5 parameter `out`. Gunakan C# `record`, `tuple`, atau DTO class/struct untuk representasi data yang kompleks.

#### Edge Cases: Async & Iterators Limitations
Parameter bertipe `ref`, `out`, dan `in` **dilarang keras** digunakan pada method `async` atau method yang menggunakan `yield return` (Iterator).
- *Alasannya*: Operasi asinkron dan iterator memotong eksekusi method dan menyimpannya ke dalam heap (*state machine*). *Managed pointer* pada stack tidak dapat menjamin validitas alamat referensi melintasi jeda penundaan waktu eksekusi (*context switch/thread hopping*), karena stack frame aslinya mungkin telah di-unwind dan hancur.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Defensive Copying**: 
   Buat sebuah mutable `struct Vector3 { public double X, Y, Z; public double Magnitude() => Math.Sqrt(X*X + Y*Y + Z*Z); }`. Panggil method ini melewati argumen `in`. Gunakan tool seperti [SharpLab.io](https://sharplab.io) untuk melihat instruksi `ldloca` dan penyalinan memori yang di-generate compiler dalam mode Release. Ubah menjadi `readonly struct` dan bandingkan perbedaannya.
2. **Alokasi Heap Benchmark (Local Function vs Lambda)**: 
   Tulis perbandingan komparasi menggunakan `BenchmarkDotNet` antara eksekusi algoritma traversal pohon rekursif menggunakan `Local Function` versus `Func<T>` delegate closure. Amati metrik `Allocated Memory` di output benchmark.
