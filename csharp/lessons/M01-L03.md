## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, *NullReferenceException* (NRE) dikenal sebagai *"The Billion Dollar Mistake"*. Sebelum C# 8.0, semua *reference types* (seperti `string`, `class`, `interface`) secara implisit dapat bernilai `null`. Hal ini memaksa developer untuk terus-menerus melakukan pengecekan `if (obj != null)` di seluruh basis kode, atau mengambil risiko aplikasi *crash* di *runtime*.

Mulai C# 8.0, Microsoft memperkenalkan **Nullable Reference Types (NRT)**. Paradigma ini membalikkan keadaan: secara *default*, *reference types* dianggap **non-nullable** (tidak boleh null). Jika Anda ingin sebuah variabel bisa bernilai `null`, Anda harus mendeklarasikannya secara eksplisit menggunakan tanda tanya (`?`), misalnya `string?`.

Untuk mendukung penanganan `null` yang elegan, C# menyediakan serangkaian operator khusus:
1. **Null-Conditional Operator (`?.`)**: Mengakses *member* hanya jika objek tidak `null`. Jika `null`, evaluasi berhenti (*short-circuit*) dan mengembalikan `null`.
2. **Null-Coalescing Operator (`??`)**: Mengembalikan nilai sebelah kiri jika tidak `null`; jika `null`, mengembalikan nilai sebelah kanan.
3. **Null-Coalescing Assignment (`??=`)**: Menetapkan nilai sebelah kanan ke variabel sebelah kiri *hanya* jika variabel sebelah kiri bernilai `null`.
4. **Null-Forgiving Operator (`!`)**: Memberitahu *compiler* (Roslyn) untuk mengabaikan peringatan *nullability* karena developer menjamin nilainya tidak akan `null` saat *runtime*.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan fitur NRT dan operator *null-coalescing* dalam skenario sistem profil pengguna dan *lazy initialization*.

```csharp
#nullable enable // Mengaktifkan fitur NRT (biasanya diaktifkan di level .csproj)

using System;
using System.Collections.Generic;

public class UserProfile
{
    // Non-nullable: Wajib diinisialisasi melalui constructor
    public string Username { get; } 
    
    // Nullable: Boleh null, tidak wajib diisi
    public string? Bio { get; set; } 
    
    // Nullable list yang berisi elemen non-nullable
    private List<string>? _roles;

    public UserProfile(string username)
    {
        // Jika username null, akan memicu warning CS8618 saat kompilasi
        Username = username ?? throw new ArgumentNullException(nameof(username));
    }

    // Menggunakan Null-Coalescing Assignment (??=) untuk Lazy Loading
    public List<string> Roles
    {
        get
        {
            // Jika _roles null, inisialisasi list baru, lalu kembalikan _roles
            _roles ??= new List<string>();
            return _roles;
        }
    }

    public string GetDisplayBio()
    {
        // Menggunakan Null-Coalescing (??) untuk memberikan nilai default
        return Bio ?? "Pengguna ini belum menulis bio.";
    }
}

public class Program
{
    public static void Main()
    {
        var user = new UserProfile("john_doe");

        // 1. Null-Coalescing (??)
        Console.WriteLine(user.GetDisplayBio()); // Output: Pengguna ini belum menulis bio.

        // 2. Null-Conditional (?.) dipadukan dengan Null-Coalescing (??)
        // Jika user null, user?.Username menghasilkan null, lalu ?? menangkapnya.
        UserProfile? potentialUser = null;
        string nameToDisplay = potentialUser?.Username ?? "Guest";
        Console.WriteLine(nameToDisplay); // Output: Guest

        // 3. Null-Coalescing Assignment (??=)
        // Roles awalnya null, tapi property getter akan menginisialisasinya
        user.Roles.Add("Admin");
        Console.WriteLine($"Role count: {user.Roles.Count}"); // Output: Role count: 1

        // 4. Null-Forgiving (!)
        // Digunakan saat kita yakin 100% nilai tidak null, tapi compiler tidak tahu.
        // Contoh: Parsing dari eksternal API yang kita yakini strukturnya.
        string? externalData = GetDataFromApi();
        int length = externalData!.Length; // Hati-hati: Akan NRE di runtime jika externalData ternyata null!
    }

    private static string? GetDataFromApi() => "Data Valid";
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Sangat penting untuk dipahami bahwa **Nullable Reference Types adalah ilusi *compiler***. Di level CLR (*Common Language Runtime*) dan IL (*Intermediate Language*), `string` dan `string?` adalah entitas yang sama persis (`System.String`). *Compiler* Roslyn menggunakan *flow analysis* statis saat kompilasi untuk melacak *state* variabel (apakah *maybe-null* atau *not-null*) dan menghasilkan *warning* (CS8600-CS8655). Untuk *library*, *compiler* menyisipkan atribut `[Nullable]` pada *metadata* agar *assembly* lain tahu *contract nullability*-nya.
- **Alokasi Memori / Resource**: 
  Berbeda dengan *Nullable Value Types* (seperti `int?` yang dikompilasi menjadi `Nullable<int>` dan memakan memori ekstra untuk *flag boolean* `HasValue`), `string?` **tidak menambah *overhead* memori sama sekali**. Operator `??` dan `?.` dikompilasi menjadi instruksi *branching* IL yang sangat efisien (`brtrue.s` / `brfalse.s`), yang melakukan *short-circuit evaluation* (sisi kanan tidak dieksekusi jika sisi kiri sudah memenuhi syarat).
- **Trade-offs**: 
  Mengaktifkan NRT meningkatkan waktu kompilasi secara marjinal karena *compiler* harus melakukan *flow analysis* yang kompleks (melacak setiap cabang `if`, `switch`, dan penugasan variabel). Migrasi basis kode lama ke NRT juga membutuhkan usaha besar (*refactoring*).

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Aktifkan `<Nullable>enable</Nullable>` di file `.csproj` untuk seluruh proyek baru.
  - Gunakan `??=` untuk pola *Lazy Initialization* pada *property* atau *field* yang berat untuk dialokasikan.
  - Gunakan kombinasi `?.` dan `??` untuk menavigasi struktur objek yang dalam (JSON deserialization, DTOs) dengan aman.
- **Don'ts**:
  - **Jangan menyalahgunakan Null-Forgiving Operator (`!`)**. Menggunakan `!` hanya untuk "membungkam *compiler*" adalah anti-pattern. Jika Anda menggunakan `!`, tambahkan komentar mengapa Anda yakin itu tidak `null`.
  - Jangan mengabaikan *warning* CS8618 (*Non-nullable property must contain a non-null value when exiting constructor*). Gunakan *constructor injection* atau *keyword* `required` (C# 11+).
- **Edge Cases**:
  - **Deserialisasi JSON**: *Compiler* menganggap *property* `string Name { get; set; }` tidak akan `null`. Namun, jika *payload* JSON tidak memiliki *field* `Name`, *deserializer* (seperti `System.Text.Json`) mungkin akan mengisinya dengan `null` menggunakan *Reflection*, melewati pengecekan *compiler*. Ini bisa menyebabkan NRE di *runtime*. Solusinya: gunakan *constructor* berparameter untuk deserialisasi atau validasi manual.

### 5. Tantangan Eksplorasi Mandiri

1. Buat sebuah *class* dengan beberapa *property* bersarang (*nested objects*). Tulis sebuah *method* yang mencoba mengambil nilai terdalam menggunakan kombinasi `?.` dan berikan nilai *fallback* menggunakan `??`.
2. Buka situs [SharpLab.io](https://sharplab.io/), tulis kode yang menggunakan operator `??=`, lalu periksa hasil dekompilasi IL (*Intermediate Language*)-nya. Amati bagaimana *compiler* mengubah operator tersebut menjadi blok `if (x == null)`.
3. Simulasikan masalah deserialisasi JSON: Buat *class* dengan *property* non-nullable tanpa *constructor*, lalu *deserialize* dari JSON kosong (`"{}"`). Amati bagaimana NRT gagal melindungi Anda di *runtime* dan pikirkan cara memperbaikinya menggunakan *keyword* `required`.
