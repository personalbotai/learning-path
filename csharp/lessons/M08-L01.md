### 1. Konsep & Arsitektur Mendalam

Entity Framework Core (EF Core) adalah *Object-Relational Mapper* (ORM) modern untuk .NET yang mengabstraksi interaksi database relasional menggunakan objek CLR (*Common Language Runtime*). Dua komponen fundamental yang menggerakkan EF Core adalah **`DbContext`** dan **`DbSet<TEntity>`**.

```
+-------------------------------------------------------------+
|                         DbContext                           |
|  +-------------------------------------------------------+  |
|  | ChangeTracker | Model Metadata (IModel) | DatabaseFac.|  |
|  +-------------------------------------------------------+  |
|                                                             |
|   +-----------------------+     +-----------------------+   |
|   |   DbSet<Customer>     |     |     DbSet<Order>      |   |
|   |  (Repository Abstr.)  |     |  (Repository Abstr.)  |   |
|   +-----------+-----------+     +-----------+-----------+   |
+---------------|-----------------------------|---------------+
                | LINQ Translation            | State Tracking
                v                             v
+-------------------------------------------------------------+
|                      Relational Database                    |
+-------------------------------------------------------------+
```

#### Peran DbContext: Unit of Work
Secara arsitektural, `DbContext` adalah implementasi gabungan dari dua pola desain enterprise klasik (*Martin Fowler*):
1. **Unit of Work**: Mengelompokkan sekumpulan mutasi bisnis ke dalam satu transaksi logis. `DbContext` memelihara daftar entitas yang diubah, dihapus, atau ditambahkan, lalu meresolusi urutan pengeksekusian SQL secara atomik saat method `SaveChangesAsync()` dipanggil.
2. **Identity Map**: Memastikan setiap baris database yang dimuat hanya direpresentasikan oleh tepat satu *instance* objek di dalam memori untuk satu scope konteks. Hal ini mencegah inkonsistensi status objek dan duplikasi alokasi memori.

#### Peran DbSet<TEntity>: Repository Pattern
`DbSet<TEntity>` bertindak sebagai koleksi generik di dalam memori yang merepresentasikan tabel atau view dalam database. `DbSet<TEntity>` mengimplementasikan `IQueryable<T>`, yang memungkinkan penulisan kueri C# berbasis LINQ (*Language Integrated Query*). Kueri ini tidak dieksekusi secara instan, melainkan disusun ke dalam bentuk *Expression Tree* sebelum akhirnya diterjemahkan menjadi *raw SQL* oleh provider database terkait.

#### Code-First Entity Configuration: Fluent API vs Data Annotations
Dalam pendekatan Code-First, skema database diturunkan dari struktur kelas entitas. EF Core menyediakan dua mekanisme konfigurasi:
1. **Data Annotations**: Atribut deklaratif seperti `[Table]`, `[Key]`, `[MaxLength]`. Meskipun cepat, pendekatan ini mencemari entitas domain dengan dependensi infrastruktur, menyalahi prinsip *Persistence Ignorance* (Domain-Driven Design).
2. **Fluent API (`OnModelCreating`)**: Menggunakan `ModelBuilder` untuk mengonfigurasi skema secara imperatif/eksplisit. Fluent API memiliki prioritas konfigurasi tertinggi dan mendukung kapabilitas tingkat lanjut seperti penanganan *concurrency tokens*, *shadow properties*, *value converters*, serta konfigurasi relasi kompleks (misalnya *composite foreign keys*, *delete behaviors*).

Praktek industri modern memisahkan konfigurasi ini ke dalam kelas terisolasi menggunakan antarmuka `IEntityTypeConfiguration<TEntity>` guna menjaga keterbacaan kode (*Single Responsibility Principle*).

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Membangun sistem e-commerce dengan konfigurasi Code-First yang mematuhi Domain-Driven Design (DDD), memanfaatkan Fluent API terisolasi, enkapsulasi navigasi, dan *Value Objects*.

```csharp
using System;
using System.Collections.Generic;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace IndustrialEcommerce.Infrastructure
{
    // ==========================================
    // 1. DOMAIN MODELS (POCO / DDD Approach)
    // ==========================================
    public enum OrderStatus
    {
        Pending = 1,
        Processing = 2,
        Completed = 3,
        Cancelled = 4
    }

    public class Customer
    {
        public Guid Id { get; private set; }
        public string Email { get; private set; } = null!;
        public string FullName { get; private set; } = null!;
        public DateTime CreatedAtUtc { get; private set; }

        // Backing field encapsulation untuk relasi 1-to-Many
        private readonly List<Order> _orders = new();
        public IReadOnlyCollection<Order> Orders => _orders.AsReadOnly();

        private Customer() { } // Diperlukan oleh EF Core runtime via Reflection

        public Customer(string email, string fullName)
        {
            Id = Guid.NewGuid();
            Email = email ?? throw new ArgumentNullException(nameof(email));
            FullName = fullName ?? throw new ArgumentNullException(nameof(fullName));
            CreatedAtUtc = DateTime.UtcNow;
        }
    }

    public class Order
    {
        public Guid Id { get; private set; }
        public Guid CustomerId { get; private set; }
        public Customer Customer { get; private set; } = null!;
        public decimal TotalAmount { get; private set; }
        public OrderStatus Status { get; private set; }
        public byte[] RowVersion { get; private set; } = null!; // Concurrency Token

        private Order() { }

        public Order(Guid customerId, decimal totalAmount)
        {
            Id = Guid.NewGuid();
            CustomerId = customerId;
            TotalAmount = totalAmount;
            Status = OrderStatus.Pending;
        }

        public void MarkAsCompleted()
        {
            Status = OrderStatus.Completed;
        }
    }

    // ==========================================
    // 2. FLUENT ENTITY CONFIGURATIONS
    // ==========================================
    public sealed class CustomerConfiguration : IEntityTypeConfiguration<Customer>
    {
        public void Configure(EntityTypeBuilder<Customer> builder)
        {
            builder.ToTable("Customers", "sales");

            builder.HasKey(c => c.Id);

            builder.Property(c => c.Email)
                   .IsRequired()
                   .HasMaxLength(256)
                   .IsUnicode(false); // VARCHAR alih-alih NVARCHAR untuk efisiensi indeks

            builder.HasIndex(c => c.Email)
                   .IsUnique()
                   .HasDatabaseName("UX_Customers_Email");

            builder.Property(c => c.FullName)
                   .IsRequired()
                   .HasMaxLength(150);

            builder.Property(c => c.CreatedAtUtc)
                   .HasDefaultValueSql("SYSUTCDATETIME()");

            // Akses backing field privat secara eksplisit
            builder.Metadata
                   .FindNavigation(nameof(Customer.Orders))!
                   .SetPropertyAccessMode(PropertyAccessMode.Field);
        }
    }

    public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
    {
        public void Configure(EntityTypeBuilder<Order> builder)
        {
            builder.ToTable("Orders", "sales");

            builder.HasKey(o => o.Id);

            builder.Property(o => o.TotalAmount)
                   .HasPrecision(18, 4) // Menghindari pemotongan nilai mata uang (rounding precision)
                   .IsRequired();

            builder.Property(o => o.Status)
                   .HasConversion<string>() // Enum disimpan sebagai VARCHAR di database
                   .HasMaxLength(20)
                   .IsUnicode(false);

            // Optimistic Concurrency Token via RowVersion/Timestamp
            builder.Property(o => o.RowVersion)
                   .IsRowVersion();

            // Relasi One-to-Many
            builder.HasOne(o => o.Customer)
                   .WithMany(c => c.Orders)
                   .HasForeignKey(o => o.CustomerId)
                   .OnDelete(DeleteBehavior.Restrict); // Mencegah Cascade Delete tidak sengaja
        }
    }

    // ==========================================
    // 3. APPLICATION DB CONTEXT
    // ==========================================
    public class ApplicationDbContext : DbContext
    {
        public DbSet<Customer> Customers => Set<Customer>();
        public DbSet<Order> Orders => Set<Order>();

        public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
            : base(options)
        {
        }

        protected override void OnModelCreating(ModelBuilder modelBuilder)
        {
            base.OnModelCreating(modelBuilder);

            // Memindai seluruh konfigurasi di assembly secara otomatis
            modelBuilder.ApplyConfigurationsFromAssembly(typeof(ApplicationDbContext).Assembly);
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Model Building & Caching Engine**:
   Ketika `DbContext` pertama kali diinstansiasi, EF Core mengompilasi model data (`IModel`) dengan memicu `OnModelCreating()`. Proses ini menggunakan banyak komputasi refleksi. Untuk mengatasinya, EF Core mengimplementasikan `IModelCacheKeyFactory`. Model yang telah dikompilasi akan di-cache secara statis di memori runtime berbasis konfigurasi tipe konteks. Instansiasi `DbContext` berikutnya langsung membaca skema dari cache, menekan *startup overhead*.
2. **Metadata Snapshotting**:
   Ketika entitas dimuat dari database melalui query, EF Core membuat salinan data skalar (*snapshot*) di dalam `ChangeTracker`. Saat `SaveChangesAsync()` dipanggil, EF Core membandingkan nilai properti entitas saat ini dengan *snapshot* awal (mekanisme *DetectChanges*). Jika ditemukan delta, EF Core menyusun *Abstract Syntax Tree* (AST) untuk mutasi tersebut dan menghasilkan instruksi SQL (`UPDATE`, `INSERT`, `DELETE`) secara teroptimasi (termasuk teknik *batching* perintah).

#### Alokasi Memori / Resource
- **State Tracking Overhead**: Setiap entitas yang ditranslasikan ke dalam memori default-nya berstatus `EntityState.Unchanged` dan diikat oleh *Identity Map*. Jika query menarik 10.000 baris, memori menampung 10.000 objek CLR aktif ditambah 10.000 objek *snapshot* status di dalam memori CLR heap.
- **DbContext Lifecycle**: `DbContext` adalah objek yang **tidak aman untuk multi-threading** (*not thread-safe*). Ia didesain bervolume alokasi *short-lived* (*Scoped* pada container dependency injection ASP.NET Core). Berbagi satu *instance* `DbContext` ke beberapa thread secara simultan akan memicu `InvalidOperationException` akibat *race condition* pada `ChangeTracker` internal.

#### Trade-offs
- **Abstraksi vs Kontrol**: Code-First Fluent API menyembunyikan kompleksitas DDL SQL, namun mengaburkan optimasi fisik database (seperti alokasi *Fillfactor*, *Filegroup partition*, atau *Index Includes*) kecuali dikonfigurasi secara manual via migrasi kustom.
- **Change Tracking**: Pelacakan otomatis memudahkan penulisan logika, tetapi menaikkan konsumsi alokasi Gen-0/Gen-1 GC secara drastis saat menangani volume pembacaan data skala besar.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `ApplyConfigurationsFromAssembly`**: Hindari menumpuk ribuan baris konfigurasi relasi di dalam method `OnModelCreating`. Pecah setiap konfigurasi tabel ke kelas individual yang mengimplementasikan `IEntityTypeConfiguration<T>`.
- **Gunakan `AsNoTracking()` untuk Read-Only Query**: Jika data hanya digunakan untuk representasi UI/API tanpa intensi mutasi, matikan snapshot tracking:
  ```csharp
  var customers = await context.Customers
                               .AsNoTracking()
                               .Where(c => c.CreatedAtUtc > threshold)
                               .ToListAsync();
  ```
- **Spesifikasikan Presisi dan Tipe Data**: Definisikan tipe database non-default secara presisi (`HasPrecision(18,2)`, `.IsUnicode(false)`) untuk mencegah SQL Server menggunakan tipe data default yang boros alokasi (misalnya `NVARCHAR(MAX)` alih-alih `VARCHAR(n)`).

#### Don'ts
- **Jangan Menggunakan `DbContext` Lintas Thread (Parallelization Anti-pattern)**:
  ```csharp
  // KESALAHAN FATAL: Membaca paralel memakai satu instance context yang sama
  var task1 = context.Customers.ToListAsync();
  var task2 = context.Orders.ToListAsync();
  await Task.WhenAll(task1, task2); // Akan melempar InvalidOperationException
  ```
- **Jangan Mengabaikan Missing Backing Fields**: Membuka koleksi navigasi sebagai `public List<Order> Orders { get; set; }` memungkinkan kode luar memanipulasi koleksi tanpa lewat *business logic method* entitas, merusak integritas *encapsulation domain*.

#### Edge Cases & Pitfalls
- **N+1 Query Explosion**: Terjadi ketika relasi navigasi dibaca di dalam iterasi *loop* tanpa menyertakan `.Include()` (Eager Loading), menyebabkan EF Core mengeksekusi *roundtrip query* tambahan ke database sebanyak $N$ baris data.
- **Cascade Delete Loops**: Ketika mengonfigurasi relasi sirkular atau relasi pohon (*self-referencing*), pastikan menggunakan `DeleteBehavior.Restrict` atau `DeleteBehavior.NoAction`. Membiarkan `Cascade` pada SQL Server untuk skema jenis ini akan menghasilkan error migrasi: *"may cause cycles or multiple cascade paths"*.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Shadow Properties & Audit Log**:
   Implementasikan *shadow property* (properti yang ada di skema tabel database tetapi tidak dideklarasikan di kelas C#) bernama `LastModifiedUtc` dan `CreatedBy` pada seluruh entitas secara otomatis menggunakan refleksi di dalam `OnModelCreating`. Modifikasi `SaveChangesAsync` pada `DbContext` Anda agar secara otomatis menyuntikkan nilai timestamp ke *shadow property* tersebut setiap kali entitas dimutasi.
2. **Efisiensi Memory Profiling via Value Converters**:
   Buatlah sebuah *Strongly Typed ID* (misalnya struct `readonly record struct CustomerId(Guid Value)`) untuk menggantikan penggunaan primitif `Guid` polos pada entitas `Customer`. Konfigurasikan `ValueConverter` pada Fluent API agar EF Core dapat memetakan struct tersebut menjadi kolom `uniqueidentifier` di database dan verifikasi *impact* konversi terhadap *query translation* yang dihasilkan.
