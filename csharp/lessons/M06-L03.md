## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Pada sistem tradisional runtime .NET, setiap manipulasi data berbasis memori kontigu—seperti melakukan parsing teks (`string.Substring`) atau memproses *stream* jaringan (`byte[]`)—cenderung memicu alokasi objek baru di Managed Heap. Alokasi jangka pendek bervolume tinggi ini memberikan tekanan luar biasa pada Garbage Collector (GC), khususnya Generation 0, yang memicu siklus GC berkala dan menurunkan *throughput* serta meningkatkan latensi aplikasi (*GC pauses*).

Untuk mengatasi kendala ini, .NET memperkenalkan primitif representasi memori: `Span<T>`, `ReadOnlySpan<T>`, dan *object-pooling framework* berbasis buffer melalui `ArrayPool<T>`.

```
               +--------------------------------------------+
               |        Span<T> / ReadOnlySpan<T>           |
               |  (ref struct: { ref T _pointer, int _len })|
               +---------------------+----------------------+
                                     |
         +---------------------------+--------------------------+
         |                           |                          |
         v                           v                          v
+-----------------+         +-----------------+        +------------------+
|  Managed Heap   |         |   Call Stack    |        |  Unmanaged Heap  |
| (byte[], string)|         |   (stackalloc)  |        | (Native Memory)  |
+-----------------+         +-----------------+        +------------------+
```

#### Arsitektur Span<T> dan ReadOnlySpan<T>
`Span<T>` adalah `ref struct` yang merepresentasikan tampilan (*view*) berurutan terhadap blok memori kontigu sembarang jenis (Type-safe & Memory-safe). Di balik layar, struktur `Span<T>` pada runtime 64-bit hanya terdiri atas dua *field*:
1. `ref T _pointer`: Pointer terkelola (*managed pointer*) yang langsung menunjuk ke alamat elemen awal di memori.
2. `int _length`: Panjang segmen memori (4 byte).

Karena `Span<T>` dapat menunjuk ke:
- **Managed Heap**: `byte[]`, elemen `string` (melalui `ReadOnlySpan<char>`).
- **Stack**: Array lokal via operator `stackalloc`.
- **Native/Unmanaged Heap**: Memori yang dialokasikan via `Marshal.AllocHGlobal` atau `NativeMemory.Alloc`.

Maka seluruh operasi slicing (`span.Slice(start, length)`) hanya memodifikasi pointer referensi dan offset panjang data **tanpa melakukan penyalinan byte (*zero-copy*) dan tanpa mengalokasikan objek baru di GC heap**.

#### Arsitektur ArrayPool<T>
Jika data berukuran besar atau memiliki siklus hidup yang melintasi batas pemanggilan asinkron (`async/await`), alokasi stack tidak dapat digunakan. `ArrayPool<T>` menyelesaikan masalah ini dengan menyediakan mekanisme penyewaan (*rent*) buffer array yang sudah dialokasikan sebelumnya.

Runtime menyediakan implementasi bawaan berkinerja tinggi: `ArrayPool<T>.Shared`. Arsitekturnya mengandalkan struktur dua tingkat:
1. **Thread-Local Stacks (Per-Core Cache)**: Meminimalkan *thread contention* dan *lock overhead* saat thread yang sama sering meminjam dan mengembalikan array dengan ukuran umum (hingga 2 MB).
2. **Per-Core Locked Stacks (Global Pool)**: Berfungsi sebagai *fallback* ketika cache lokal per-thread kehabisan alokasi buffer.

### 2. Implementasi & Contoh Kasus Nyata

Contoh kasus di bawah mendemonstrasikan parser pesan protokol IoT berformat `ID:TIMESTAMP:PAYLOAD_HEX` (misal: `DEV42:1700000000:DEADBEEF`) tanpa alokasi memori heap sama sekali, dipadukan dengan `ArrayPool<byte>` untuk mendaur ulang buffer hasil decoding byte hex.

```csharp
using System;
using System.Buffers;
using System.Buffers.Binary;
using System.Text;

public readonly record struct TelemetryPayload(int DeviceId, long Timestamp, int PayloadLength);

public static class FastTelemetryParser
{
    // Menggunakan ReadOnlySpan<char> memastikan ZERO GC allocation saat slicing
    public static TelemetryPayload ParseTelemetry(ReadOnlySpan<char> rawMessage)
    {
        // 1. Ekstraksi Device ID (Format: DEVxx)
        int firstColon = rawMessage.IndexOf(':');
        if (firstColon == -1) 
            throw new FormatException("Format pesan tidak valid: delimiter pertama tidak ditemukan.");

        ReadOnlySpan<char> deviceSegment = rawMessage.Slice(0, firstColon);
        if (!deviceSegment.StartsWith("DEV"))
            throw new FormatException("Header device tidak valid.");

        // Parsing int langsung dari ReadOnlySpan<char> tanpa string allocation
        int deviceId = int.Parse(deviceSegment.Slice(3));

        // 2. Ekstraksi Timestamp
        ReadOnlySpan<char> remaining = rawMessage.Slice(firstColon + 1);
        int secondColon = remaining.IndexOf(':');
        if (secondColon == -1) 
            throw new FormatException("Format pesan tidak valid: delimiter kedua tidak ditemukan.");

        ReadOnlySpan<char> timestampSegment = remaining.Slice(0, secondColon);
        long timestamp = long.Parse(timestampSegment);

        // 3. Ekstraksi & Decode Hex Payload menggunakan ArrayPool
        ReadOnlySpan<char> hexPayloadSegment = remaining.Slice(secondColon + 1);
        int byteCount = hexPayloadSegment.Length / 2;

        // Sewa array dari ArrayPool<T>.Shared untuk menghindari Large Object Heap / SOH pressure
        byte[] rentedBuffer = ArrayPool<byte>.Shared.Rent(byteCount);

        try
        {
            // Buat span di atas buffer pinjaman
            Span<byte> destinationSpan = rentedBuffer.AsSpan(0, byteCount);

            // Decode string hex langsung ke destination span tanpa array allocation
            ConvertHexToBytes(hexPayloadSegment, destinationSpan);

            // Lakukan simulasi pemrosesan payload kontigu
            ProcessBinaryPayload(destinationSpan);

            return new TelemetryPayload(deviceId, timestamp, byteCount);
        }
        finally
        {
            // Wajib dikembalikan di block finally!
            // clearArray: false untuk byte data non-sensitif demi performa maksimal
            ArrayPool<byte>.Shared.Return(rentedBuffer, clearArray: false);
        }
    }

    private static void ConvertHexToBytes(ReadOnlySpan<char> hex, Span<byte> output)
    {
        for (int i = 0; i < output.Length; i++)
        {
            int highNibble = ConvertNibble(hex[i * 2]);
            int lowNibble = ConvertNibble(hex[i * 2 + 1]);
            output[i] = (byte)((highNibble << 4) | lowNibble);
        }
    }

    private static int ConvertNibble(char c) => c switch
    {
        >= '0' and <= '9' => c - '0',
        >= 'A' and <= 'F' => c - 'A' + 10,
        >= 'a' and <= 'f' => c - 'a' + 10,
        _ => throw new FormatException($"Karakter hex tidak valid: {c}")
    };

    private static void ProcessBinaryPayload(ReadOnlySpan<byte> payload)
    {
        // Operasi aman berbasis Span tanpa alokasi
        if (payload.Length >= 4)
        {
            // Contoh parsing big-endian 32-bit integer langsung dari span
            int header = BinaryPrimitives.ReadInt32BigEndian(payload);
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Karakteristik `ref struct`
- `Span<T>` dideklarasikan dengan modifier `ref struct`. Compiler C# dan runtime CLR memberlakukan *escape analysis rules* ketat: **instance `ref struct` hanya boleh hidup di stack eksekusi**.
- Ia **tidak boleh**:
  - Dibuat menjadi field dari class biasa (hanya boleh di `ref struct` lain).
  - Melakukan *boxing* ke `object` atau `ValueType`.
  - Mengimplementasikan antarmuka non-ref struct.
  - Digunakan di dalam method `async/await` melewati *suspension point* (karena state machine `async` meng-kompilasi variabel lokal ke dalam heap-allocated state class).
  - Digunakan di lambda expression yang meng-capture context, atau linq iterator block (`yield return`).
- Runtime memanfaatkan batasan ini untuk menjamin pointer yang ditunjuk oleh `Span<T>` tidak pernah merujuk ke frame stack yang telah di-pop (*preventing dangling pointers*).

#### Alokasi Memori / Resource
- **Bounds Checking Elimination**: JIT compiler (.NET Core 3.0+) mengoptimalkan loop yang menggunakan `Span<T>`. Jika panjang rentang loop dapat dibuktikan konstan atau terikat pada `span.Length`, JIT akan memangkas instruksi pengecekan batas array (*range-check elimination*) secara otomatis.
- **Tearing Prevention**: `Span<T>` adalah representasi 2-word (`ref pointer` + `int length`). Pengoperan `Span<T>` dalam multi-threaded environment tanpa sinkronisasi dapat memicu kondisi data race (tearing). Batasan *stack-only* mencegah span dishare lintas thread secara unsafe.
- **ArrayPool Bucket Fragmentation**: Saat Anda memanggil `ArrayPool<T>.Rent(minimumLength)`, pool tidak mengalokasikan ukuran persis. Pool mengalokasikan array dengan ukuran pembulatan kelipatan pangkat dua ($2^n$, misal: sewa 100 byte akan mengembalikan array berukuran 128 byte). 

#### Trade-offs
- **Kompleksitas API**: Mengganti alokasi string dengan `ReadOnlySpan<char>` mengharuskan developer meninggalkan method bawaan seperti `string.Split()`, `string.Replace()`, beralih ke pattern manual berbasis pointer/index atau library *low-level* seperti `Utf8Parser` / `Span APIs`.
- **Safety vs Overhead pada ArrayPool**: Membiarkan `clearArray: false` menyisakan data lama di dalam array (stale data). Jika disewakan ke caller lain, caller bisa membaca residu data transaksi sebelumnya jika tidak membaca sesuai panjang validasi (`rentedLength`).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan pola `rentedBuffer.AsSpan(0, requiredLength)`**: Ingat bahwa `ArrayPool.Rent(n)` mengembalikan array yang panjangnya $\ge n$. Selalu bungkus array sewaan ke dalam span sesuai dimensi data aktual agar tidak membaca index kosong.
- **Kombinasikan dengan `stackalloc` untuk buffer ultra-kecil**:
  ```csharp
  // Alokasi stack jika ukuran kecil (< 512 byte), fallback ke ArrayPool jika besar
  Span<byte> buffer = length <= 512 ? stackalloc byte[length] : ArrayPool<byte>.Shared.Rent(length);
  ```
- **Gunakan `Memory<T>` atau `ReadOnlyMemory<T>` jika harus melintasi batas `async/await`**:
  `Memory<T>` adalah struct biasa (bukan `ref struct`) yang hidup di heap atau stack, yang memiliki method `.Span` untuk diekstrak saat operasi sinkron dimulai kembali.

#### Don'ts
- **Jangan menggunakan buffer sewaan setelah dipanggil `Return()` (Use-After-Free equivalent)**:
  Setelah mengembalikan buffer ke `ArrayPool`, referensi lokal array tersebut tidak boleh dimutasi atau dibaca lagi, karena thread lain berpotensi sedang menulis ke buffer yang sama.
- **Jangan memanggil `Return()` dua kali (Double-Free pattern)**:
  Mengembalikan instance array yang sama dua kali ke `ArrayPool` akan merusak linked-list/stack internal pool dan menyebabkan race condition fatal pada runtime.

#### Edge Cases
- **Data Sensitif (Security Concern)**: Jika array sewaan memegang token JWT, password hash, atau private key, selalu panggil `ArrayPool<T>.Shared.Return(rentedBuffer, clearArray: true)`. Jika tidak, residu memori tersebut dapat diekspos ke thread lain dalam proses yang sama.
