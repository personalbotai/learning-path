### 1. Konsep & Arsitektur Mendalam

Event-Driven Architecture (EDA) adalah paradigma arsitektur perangkat lunak di mana komponen-komponen sistem berkomunikasi secara asinkron melalui pertukaran pesan (*events*). Berbeda dengan arsitektur sinkron berbasis Request-Response (seperti REST atau gRPC langsung), EDA memberikan *temporal decoupling* (pemancar dan penerima tidak perlu aktif pada waktu yang sama) serta *spatial decoupling* (pemancar tidak mengetahui lokasi fisik atau identitas absolut dari penerima).

Dalam ekosistem .NET, **MassTransit** bertindak sebagai *Service Bus Framework* tingkat tinggi yang mengabstraksi kompleksitas broker pesan seperti **RabbitMQ**, Azure Service Bus, atau Amazon SQS.

```
+-----------------------------------------------------------+
|                      MassTransit                          |
|  [Serialization] -> [Retry/CircuitBreaker] -> [Outbox]    |
+-----------------------------------------------------------+
                              |
                     AMQP 0-9-1 Protocol
                              v
+-----------------------------------------------------------+
|                        RabbitMQ                           |
|                                                           |
|   [OrderSubmitted Exchange] (Fanout/Topic)                |
|             |                                             |
|      +------+------+ (Exchange-to-Exchange Binding)       |
|      v             v                                      |
| [Billing Exchange] [Inventory Exchange]                   |
|      |             |                                      |
|      v             v                                      |
| [Billing Queue]    [Inventory Queue]                      |
+-----------------------------------------------------------+
```

#### Komponen Utama & Topologi RabbitMQ pada MassTransit

1. **Commands vs Events**:
   - **Command**: Instruksi imperatif yang ditujukan ke tepat satu penerima (Point-to-Point). Menggunakan `Send()` di MassTransit. Contoh: `SubmitOrder`.
   - **Event**: Notifikasi bahwa sesuatu telah terjadi di masa lalu. Bersifat broadcast (Publish-Subscribe) ke nol atau banyak penerima. Menggunakan `Publish()` di MassTransit. Contoh: `OrderSubmitted`.
2. **Topologi Exchange-to-Exchange (E2E)**:
   Secara *default*, MassTransit tidak mengikat *Queue* langsung ke *Exchange* tipe data. MassTransit membuat hierarki *Exchange-to-Exchange binding*:
   - MassTransit mendeteksi tipe .NET (misal: `Contracts.OrderSubmitted`).
   - Membuat `Fanout Exchange` dengan nama namespace tipe pesan tersebut.
   - Mengikat exchange pesan ke exchange milik *Queue* konsumen.
   - Memungkinkan dukungan pewarisan (*polymorphic dispatch*); jika pesan mengimplementasikan interface `IEvent`, MassTransit otomatis membuat rute binding untuk interface tersebut.
3. **Message Envelope**:
   MassTransit membungkus setiap *payload* ke dalam struktur envelope standar (mengacu pada spesifikasi interoperabilitas pesan). Envelope ini menyuntikkan metadata seperti `MessageId`, `CorrelationId`, `ConversationId`, `Host`, serta *telemetry baggage* untuk OpenTelemetry.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sistem E-Commerce. Ketika sebuah pesanan berhasil dibuat, diterbitkan event `OrderSubmitted`. Modul *Payment/Billing* mendengarkan event ini untuk melakukan penagihan, menggunakan Transactional Outbox Pattern agar terhindar dari kondisi *dual-write problem*.

#### 1. Definisi Kontrak (Class Library Independen)

Kontrak harus bersifat *immutable* dan bebas dari logika bisnis atau dependensi framework berat.

```csharp
// Contracts/OrderSubmitted.cs
namespace Contracts;

public record OrderSubmitted
{
    public required Guid OrderId { get; init; }
    public required Guid CustomerId { get; init; }
    public required decimal Amount { get; init; }
    public required DateTime TimestampUtc { get; init; }
}
```

#### 2. Implementasi Consumer

```csharp
// Consumers/OrderSubmittedConsumer.cs
using Contracts;
using MassTransit;
using Microsoft.Extensions.Logging;

namespace OrderService.Consumers;

public class OrderSubmittedConsumer(ILogger<OrderSubmittedConsumer> logger) 
    : IConsumer<OrderSubmitted>
{
    public async Task Consume(ConsumeContext<OrderSubmitted> context)
    {
        // CorrelationId otomatis dipropagasi oleh MassTransit
        var correlationId = context.CorrelationId ?? context.MessageId;
        
        logger.LogInformation(
            "Memproses tagihan untuk Order: {OrderId}, Amount: {Amount}, Correlation: {CorrelationId}",
            context.Message.OrderId,
            context.Message.Amount,
            correlationId
        );

        // Simulasi logika bisnis pemrosesan pembayaran
        if (context.Message.Amount <= 0)
        {
            throw new ArgumentException("Nilai transaksi tidak valid, tidak bisa memproses.");
        }

        await Task.Delay(100, context.CancellationToken); // Operasi I/O asinkron

        logger.LogInformation("Penagihan sukses untuk Order: {OrderId}", context.Message.OrderId);
    }
}

// Validasi Consumer Definition untuk konfigurasi lokal endpoint
public class OrderSubmittedConsumerDefinition : ConsumerDefinition<OrderSubmittedConsumer>
{
    public OrderSubmittedConsumerDefinition()
    {
        // Menentukan nama queue secara eksplisit daripada auto-generated
        EndpointName = "order-billing-service";
        
        // Membatasi konkurensi pada level consumer ini
        ConcurrentMessageLimit = 16;
    }

    protected override void ConfigureConsumer(
        IReceiveEndpointConfigurator endpointConfigurator,
        IConsumerConfigurator<OrderSubmittedConsumer> consumerConfigurator,
        IRegistrationContext context)
    {
        // Pasang Retry Policy spesifik untuk consumer ini
        endpointConfigurator.UseMessageRetry(r => 
            r.Incremental(3, TimeSpan.FromMilliseconds(200), TimeSpan.FromMilliseconds(500)));
    }
}
```

#### 3. Konfigurasi Host & Bus (Program.cs)

Menggunakan .NET 8 Web API / Worker Service dengan MassTransit dan Entity Framework Core Outbox.

```csharp
// Program.cs
using Contracts;
using MassTransit;
using Microsoft.EntityFrameworkCore;
using OrderService.Consumers;
using OrderService.Infrastructure;

var builder = WebApplication.CreateBuilder(args);

// 1. Registrasi Database Context untuk Transactional Outbox
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("Database")));

// 2. Registrasi MassTransit
builder.Services.AddMassTransit(x =>
{
    // Registrasi consumer dan definition-nya
    x.AddConsumer<OrderSubmittedConsumer, OrderSubmittedConsumerDefinition>();

    // Pasang Transactional Outbox (EF Core)
    x.AddEntityFrameworkOutbox<AppDbContext>(o =>
    {
        o.UsePostgres();
        o.UseBusOutbox(); // Alihkan IPublishEndpoint langsung ke tabel outbox
    });

    // Konfigurasi transport RabbitMQ
    x.UsingRabbitMq((context, cfg) =>
    {
        cfg.Host(builder.Configuration.GetValue<string>("RabbitMq:Host", "localhost"), "/", h =>
        {
            h.Username(builder.Configuration.GetValue<string>("RabbitMq:Username", "guest"));
            h.Password(builder.Configuration.GetValue<string>("RabbitMq:Password", "guest"));
        });

        // Konfigurasi Prefetch Count secara global
        cfg.PrefetchCount = 32;

        // Terapkan auto-konfigurasi endpoint berbasis ConsumerDefinition
        cfg.ConfigureEndpoints(context);
    });
});

var app = builder.Build();

// Endpoint untuk Trigger Event
app.MapPost("/orders", async (IPublishEndpoint publishEndpoint, AppDbContext dbContext) =>
{
    var orderId = Guid.NewGuid();

    // 1. Simpan entitas domain ke DB (bagian dari transaksi DB)
    // dbContext.Orders.Add(new Order { Id = orderId, ... });

    // 2. Publish event via Outbox (Pesan ditulis ke tabel Outbox, bukan langsung ke RabbitMQ)
    await publishEndpoint.Publish<OrderSubmitted>(new
    {
        OrderId = orderId,
        CustomerId = Guid.NewGuid(),
        Amount = 250_000m,
        TimestampUtc = DateTime.UtcNow
    });

    // 3. Commit transaksi secara atomik (Domain Entity + Outbox Message tersimpan bersamaan)
    await dbContext.SaveChangesAsync();

    return Results.Accepted($"/orders/{orderId}", new { OrderId = orderId });
});

app.Run();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Pipeline Arsitektur GreenPipes**: MassTransit dibangun di atas konsep *pipe-and-filter* internal bernama GreenPipes. Setiap pesan yang masuk ke `IReceiveEndpoint` melewati serangkaian middleware: Deserializer $\to$ Exception Handler $\to$ Retry Filter $\to$ Outbox Filter $\to$ Scoped Container Filter $\to$ Consumer Method.
2. **Channel Multiplexing (AMQP)**: MassTransit mempertahankan satu `IConnection` TCP tunggal ke RabbitMQ per aplikasi, namun membuka banyak `IModel` (AMQP Channel). Tiap *Receive Endpoint* (antrean) beroperasi di channel terisolasi untuk menghindari *bottleneck* sinkronisasi soket TCP.
3. **Dispatch Loop**: RabbitMQ Client menggunakan *push-model* (`BasicConsumer`). Pesan masuk ke *internal memory buffer* aplikasi. MassTransit memproses *buffer* tersebut menggunakan `Task.Run` atau `ThreadPool` thread worker secara non-blocking hingga batas konkurensi terpenuhi.

#### Alokasi Memori / Resource
- **Deserialisasi Streaming**: Default deserializer adalah `System.Text.Json`. MassTransit membaca byte array langsung dari frame AMQP via streaming memory, meminimalisir alokasi `byte[]` berlebih untuk mengurangi beban GC (Garbage Collection) pada Generasi 0/1.
- **Prefetch Count & Socket Throttling**: Properti `cfg.PrefetchCount` mengirim instruksi `basic.qos` ke broker. Jika Prefetch diatur ke 32, broker hanya akan mengirim maksimal 32 pesan yang belum di-ACK (Unacknowledged) ke memori lokal instans aplikasi ini. Tanpa prefetch limit, aplikasi bisa mengalami *Out of Memory (OOM)* akibat banjir pesan ke RAM.

#### Trade-offs
- **At-Least-Once Delivery**: RabbitMQ dan MassTransit menjamin pesan *pasti sampai minimal satu kali*, bukan *tepat satu kali* (exactly-once). Duplikasi pesan dapat terjadi ketika pesan selesai diproses namun jaringan mati tepat sebelum ACK dikirim ke broker.
- **Latensi vs Daya Tahan (Durability)**: Secara default, MassTransit mengonfigurasi exchange dan queue sebagai `Durable`, serta pesan sebagai `Persistent` (ditulis ke disk broker). Ini memberikan resiliensi data yang tinggi, namun menghasilkan *I/O disk overhead* pada node RabbitMQ dibandingkan pesan *transient* (in-memory only).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Interface atau Record Tipis untuk Kontrak**: Hanya sertakan data yang relevan. Jangan pernah menyertakan logika atau *rich domain model* (DDD Entity) ke dalam kontrak pesan.
- **Implementasi Idempotensi di Consumer**: Karena jaminan pengiriman adalah *at-least-once*, desain consumer agar aman dieksekusi berkali-kali untuk payload yang sama. Gunakan tabel *Inbox* (seperti MassTransit Outbox Inbox) atau verifikasi *state* transaksi pada basis data lokal sebelum memproses aksi efek samping.
- **Gunakan Transactional Outbox Pattern**: Hindari skenario memanggil `dbContext.SaveChangesAsync()` kemudian memanggil `publishEndpoint.Publish()`. Jika broker mati tepat setelah DB commit, event hilang selamanya (*Dual-write hazard*).

#### Don'ts
- **Jangan Melakukan Sinkronisasi Blocking di Consumer**: Menulis `Task.Wait()` atau `.Result` di dalam consumer menyebabkan ancaman thread-pool starvation, merusak throughput, dan dapat memicu *deadlock* pada pemrosesan pesan AMQP.
- **Jangan Mengabaikan Exception (Swallowing Exceptions)**: Menangkap semua exception menggunakan `try-catch` kosong di consumer membuat MassTransit mengira pesan sukses diproses, sehingga pesan akan di-ACK dan dihapus dari broker alih-alih masuk ke mekanisme *retry* atau *_error* queue.
- **Hindari Shared Database Antar Microservice**: Membaca basis data service lain secara langsung merusak esensi decoupling dari Event-Driven Architecture.

#### Edge Cases
- **Poison Messages**: Pesan yang gagal diproses berkali-kali melampaui batas *retry policy* akan dipindahkan secara otomatis oleh MassTransit ke antrean khusus bernama `<queue-name>_error`. Antrean ini harus dimonitor secara reguler; pesan yang ada di sana harus diinspeksi, diperbaiki bug aplikasinya, lalu dipindahkan kembali menggunakan *MassTransit Shovel / Move-Queue*.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Idempotent Consumer Manual**:
   Matikan ekstensi outbox bawaan, lalu rancang mekanisme idempotensi manual di dalam consumer menggunakan Redis `SET NX` atau tabel database `ConsumedMessages` berdasarkan `context.MessageId`. Simulasikan kegagalan jaringan setelah proses bisnis selesai namun sebelum ACK terkirim, lalu buktikan bahwa pemrosesan kedua kalinya tidak menimbulkan inkonsistensi data.

2. **Hierarki Pesan Polimorfik (Polymorphic Routing)**:
   Buat hierarki event:
   ```csharp
   public interface IOrderEvent { Guid OrderId { get; } }
   public record OrderCreated(...) : IOrderEvent;
   public record OrderCancelled(...) : IOrderEvent;
   ```
   Jalankan MassTransit, lalu periksa dashboard RabbitMQ Management Web UI. Analisis bagaimana MassTransit membuat topologi *Exchange-to-Exchange bindings* untuk `IOrderEvent`, `OrderCreated`, dan `OrderCancelled`. Cobalah membuat satu consumer terpisah yang hanya mendengarkan `IConsumer<IOrderEvent>` untuk mencatat audit log semua variasi event pesanan.
