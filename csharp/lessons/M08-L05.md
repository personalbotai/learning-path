## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam Object-Relational Mapping (ORM) seperti Entity Framework Core (EF Core), terdapat *impedance mismatch* antara paradigma berorientasi objek (Object Graph) dan model relasional (Tabel & Foreign Key). Ketika Anda memuat sebuah entitas dari database, EF Core tidak secara otomatis memuat entitas terkait (relasi) untuk mencegah penarikan data masif yang tidak disengaja. 

Untuk mengelola bagaimana dan kapan data relasional ditarik ke dalam memori, EF Core menyediakan tiga strategi utama:

1.  **Eager Loading (`Include`)**: Menarik entitas utama dan entitas terkait dalam satu *query* (atau *split queries*) ke database. Cocok ketika Anda tahu pasti data relasi akan digunakan.
2.  **Explicit Loading**: Menarik entitas terkait secara manual (on-demand) setelah entitas utama sudah berada di memori. Berguna untuk logika kondisional di mana relasi hanya dibutuhkan pada *state* tertentu.
3.  **Lazy Loading**: Menunda penarikan data relasi sampai *property* navigasi diakses pertama kali di dalam kode. Membutuhkan *proxy generation* di runtime.

Pemilihan strategi ini sangat krusial karena berdampak langsung pada jumlah *roundtrip* ke database (I/O bound) dan konsumsi memori aplikasi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan EF Core. Kita asumsikan domain model `Author` yang memiliki banyak `Book`.

```csharp
// Domain Models
public class Author
{
    public int Id { get; set; }
    public string Name { get; set; }
    
    // virtual keyword WAJIB untuk Lazy Loading, opsional untuk Eager/Explicit
    public virtual ICollection<Book> Books { get; set; } = new List<Book>();
}

public class Book
{
    public int Id { get; set; }
    public string Title { get; set; }
    public bool IsPublished { get; set; }
    public int AuthorId { get; set; }
    public virtual Author Author { get; set; }
}
```

**A. Eager Loading (Include & ThenInclude)**
```csharp
// Mengambil Author beserta Buku-bukunya dalam satu query (JOIN)
// Menggunakan Filtered Include (EF Core 5.0+) untuk membatasi data relasi
var authors = await _context.Authors
    .Include(a => a.Books.Where(b => b.IsPublished)) 
    .ToListAsync();

// Jika ada relasi bertingkat (misal Book punya Reviews)
var authorsWithReviews = await _context.Authors
    .Include(a => a.Books)
        .ThenInclude(b => b.Reviews)
    .ToListAsync();
```

**B. Explicit Loading**
```csharp
// 1. Load entitas utama saja
var author = await _context.Authors.FindAsync(1);

// 2. Logika kondisional: Hanya load buku jika author adalah VIP
if (author.IsVip)
{
    // Load Collection (One-to-Many)
    await _context.Entry(author)
        .Collection(a => a.Books)
        .Query() // Memungkinkan filtering tambahan sebelum di-load
        .Where(b => b.IsPublished)
        .LoadAsync();
}

var book = await _context.Books.FindAsync(1);
// Load Reference (Many-to-One / One-to-One)
await _context.Entry(book).Reference(b => b.Author).LoadAsync();
```

**C. Lazy Loading**
```csharp
// Setup di DbContext (Membutuhkan package Microsoft.EntityFrameworkCore.Proxies)
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    => optionsBuilder
        .UseLazyLoadingProxies()
        .UseSqlServer(myConnectionString);

// Penggunaan
var author = await _context.Authors.FindAsync(1); // Query 1: SELECT Author
Console.WriteLine(author.Name);

// Query 2 (SELECT Books) dieksekusi SECARA OTOMATIS tepat di baris ini
foreach (var book in author.Books) 
{
    Console.WriteLine(book.Title);
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**:
  - **Eager Loading**: EF Core menerjemahkan `.Include()` menjadi operasi `LEFT JOIN` atau `INNER JOIN` di SQL. Jika Anda melakukan `Include` pada banyak koleksi (One-to-Many), ini dapat menyebabkan **Cartesian Explosion** (duplikasi data di *result set*). EF Core mengatasi ini dengan fitur `.AsSplitQuery()` yang memecah satu *query* besar menjadi beberapa *query* kecil yang dieksekusi secara paralel/berurutan.
  - **Explicit Loading**: EF Core menggunakan *Change Tracker* untuk melacak entitas. Pemanggilan `.LoadAsync()` memicu eksekusi SQL `SELECT` terpisah yang difilter berdasarkan *Foreign Key* dari entitas yang sedang di-track.
  - **Lazy Loading**: Saat aplikasi berjalan, EF Core menggunakan *DynamicProxy* (biasanya dari Castle.Core) untuk membuat *class* turunan (proxy) dari entitas Anda secara *on-the-fly*. Proxy ini melakukan *override* pada *property* `virtual` dan menyuntikkan `ILazyLoader`. Saat *getter* dipanggil, proxy mengecek apakah data sudah ada; jika belum, ia memblokir *thread* (sinkron) dan melakukan *query* ke database.

- **Alokasi Memori / Resource**:
  - **Eager**: Memori dialokasikan di awal untuk seluruh *Object Graph*. Sangat efisien dari segi koneksi DB (sedikit *roundtrip*), namun berisiko *Out of Memory* (OOM) jika data relasi terlalu besar.
  - **Lazy/Explicit**: Memori awal kecil. Namun, setiap akses relasi membuka koneksi/mengeksekusi *command* ke DB, meningkatkan latensi jaringan dan beban CPU pada database server.

- **Trade-offs**: Eager Loading menukar penggunaan memori dan kompleksitas *query* (JOIN) demi kecepatan latensi jaringan. Lazy Loading menukar performa jaringan (*multiple roundtrips*) demi kemudahan penulisan kode dan penghematan memori awal.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Eager Loading sebagai default** untuk aplikasi web/API. Ini memberikan performa yang paling dapat diprediksi.
  - Gunakan `.AsSplitQuery()` jika Anda melakukan `.Include()` pada lebih dari satu *Collection* untuk menghindari *Cartesian Explosion*.
  - Gunakan **Explicit Loading** jika Anda membutuhkan agregasi tanpa menarik data. Contoh: `_context.Entry(author).Collection(a => a.Books).Query().CountAsync()`.

- **Don'ts**:
  - **HINDARI Lazy Loading di Web API**. Saat *serializer* (seperti JSON.NET atau System.Text.Json) mengubah objek menjadi JSON, ia akan membaca setiap *property*. Ini memicu Lazy Loading untuk *semua* relasi, menyebabkan *database meltdown* dan *circular reference exception*.
  - Jangan gunakan `.Include()` jika Anda hanya ingin melakukan proyeksi data menggunakan `.Select()`. EF Core cukup pintar untuk melakukan JOIN otomatis jika Anda memetakan relasi langsung di dalam `.Select()`.

- **Edge Cases (N+1 Query Problem)**:
  Ini adalah jebakan paling mematikan dari Lazy Loading.
  ```csharp
  var authors = _context.Authors.ToList(); // 1 Query
  foreach(var a in authors) {
      // Jika ada 100 author, loop ini akan memicu 100 Query tambahan! (Total 101 Queries)
      Console.WriteLine(a.Books.Count); 
  }
  ```
  *Solusi*: Gunakan Eager Loading (`.Include(a => a.Books)`) sebelum melakukan iterasi.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis SQL Log**: Aktifkan *Logging* pada DbContext Anda (gunakan `LogTo(Console.WriteLine)`). Buat *query* dengan tiga `.Include()` pada koleksi yang berbeda. Bandingkan SQL yang dihasilkan antara menggunakan `.AsSingleQuery()` (default) dan `.AsSplitQuery()`.
2. **Proyeksi vs Include**: Tulis sebuah *query* menggunakan `.Select(a => new { a.Name, BookCount = a.Books.Count })` tanpa menggunakan `.Include()`. Periksa log SQL-nya. Mengapa EF Core tidak memerlukan `.Include()` dalam kasus ini?
3. **Simulasi N+1**: Buat *seeder* untuk memasukkan 50 entitas utama dan masing-masing 10 entitas relasi. Gunakan Lazy Loading di dalam sebuah *loop*. Ukur waktu eksekusinya menggunakan `Stopwatch`, lalu refaktor menggunakan Eager Loading dan bandingkan selisih waktunya.
