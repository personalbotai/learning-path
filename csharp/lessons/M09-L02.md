### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur perangkat lunak enterprise (seperti *Clean Architecture* atau *Domain-Driven Design*), pemisahan antara logika domain dan mekanisme persistensi data adalah keharusan. Dua pola desain fundamental yang memfasilitasi abstraksi ini adalah **Repository Pattern** dan **Unit of Work (UoW) Pattern**.

```
[ Domain / Application Layer ]
              │
       (Depends on)
              ▼
   ┌─────────────────────┐       ┌──────────────────────┐
   │ IOrderRepository    │       │     IUnitOfWork      │
   └──────────┬──────────┘       └──────────┬───────────┘
              │ Implements                  │ Implements
              ▼                             ▼
┌────────────────────────────────────────────────────────┐
│ Persistence Layer (EF Core / Dapper)                   │
│  ┌───────────────────────┐  ┌───────────────────────┐  │
│  │ OrderRepository       │  │ UnitOfWork            │  │
│  │ (Encapsulates Queries)│  │ (Coordinates Commits) │  │
│  └──────────┬────────────┘  └──────────┬────────────┘  │
│             │                          │               │
│             └───────────┐  ┌───────────┘               │
│                         ▼  ▼                           │
│                   ┌──────────────┐                     │
│                   │  DbContext   │                     │
│                   └──────┬───────┘                     │
└──────────────────────────┼─────────────────────────────┘
                           ▼
                  [ Relational DB (SQL) ]
```

#### Repository Pattern
Secara konseptual, Repository bertindak seolah-olah seluruh koleksi data domain berada di dalam memori (in-memory collection). Fowler mendefinisikan Repository sebagai mediator antara lapisan domain dan pemetaan data (data mapping), yang menyembunyikan detail operasional database (SQL generation, HTTP API calls, atau Document queries).

Tujuan intinya bukan sekadar mem-bungkus (wrap) query database, melainkan:
- Mengisolasi domain dari teknologi persistensi spesifik (misal: migrasi dari EF Core ke Dapper, atau SQL Server ke PostgreSQL tanpa mengubah domain entity).
- Menyediakan *ubiquitous language* query bisnis (misal: alih-alih `context.Orders.Where(x => x.Status == 1 && x.CreatedAt > Date)`, Repository mengekspos `GetPendingOrdersFrom(DateTime date)`).

#### Unit of Work (UoW) Pattern
Ketika operasi bisnis melibatkan manipulasi beberapa Aggregate/Entity yang berbeda (misalnya: membuat `Order`, mengurangi `Stock`, dan mencatat `AuditLog`), seluruh mutasi ini harus berjalan secara atomik (*All-or-Nothing* - prinsip ACID).

Unit of Work bertugas:
1. Melacak seluruh perubahan state entitas selama siklus hidup satu transaksi bisnis (Insert, Update, Delete).
2. Mengoordinasikan penulisan perubahan ke storage secara atomik saat seluruh logika domain selesai dijalankan.

#### Paradoks EF Core: Apakah Perlu Membungkus `DbContext`?
Secara internal di runtime .NET:
- `DbContext` adalah implementasi nyata dari **Unit of Work**.
- `DbSet<T>` adalah implementasi nyata dari **Repository**.

Mengapa developer enterprise masih mengabstraksinya?
1. **Mencegah Leaky Abstraction**: Mengembalikan `IQueryable<T>` langsung ke Presentation/Controller layer berisiko mengeksekusi *deferred execution query* di luar kendali boundary transaksi atau memicu query N+1 yang tidak terpantau.
2. **Domain Encapsulation**: Membatasi pengembang agar hanya berinteraksi melalui *Aggregate Root*, mencegah mutasi langsung pada entitas relasi privat (*child entities*).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi idiomatik modern menggunakan C# (.NET 8/9), memanfaatkan *nullable reference types*, `CancellationToken`, dan menghindari anti-pattern generic repository yang diekspos secara mentah.

#### 1. Abstraksi Kontrak (Domain/Application Layer)

```csharp
namespace Domain.Contracts;

public interface IUnitOfWork : IAsyncDisposable
{
    Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);
    Task BeginTransactionAsync(CancellationToken cancellationToken = default);
    Task CommitTransactionAsync(CancellationToken cancellationToken = default);
    Task RollbackTransactionAsync(CancellationToken cancellationToken = default);
}

public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default);
    Task<IReadOnlyList<Order>> GetUnprocessedOrdersAsync(int batchSize, CancellationToken cancellationToken = default);
    Task AddAsync(Order order, CancellationToken cancellationToken = default);
    void Remove(Order order); // In-memory mark for deletion, actual delete handled by UoW
}
```

#### 2. Entitas Domain

```csharp
namespace Domain.Entities;

public sealed class Order
{
    public Guid Id { get; private set; }
    public string CustomerId { get; private set; }
    public decimal TotalAmount { get; private set; }
    public bool IsProcessed { get; private set; }

    // Private constructor untuk EF Core
    private Order() { CustomerId = null!; }

    public Order(Guid id, string customerId, decimal totalAmount)
    {
        Id = id;
        CustomerId = customerId ?? throw new ArgumentNullException(nameof(customerId));
        TotalAmount = totalAmount;
        IsProcessed = false;
    }

    public void MarkAsProcessed() => IsProcessed = true;
}
```

#### 3. Implementasi Konkrit (Infrastructure Layer)

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Storage;
using Domain.Contracts;
using Domain.Entities;

namespace Infrastructure.Persistence;

public sealed class ApplicationDbContext(DbContextOptions<ApplicationDbContext> options) 
    : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>(builder =>
        {
            builder.HasKey(o => o.Id);
            builder.Property(o => o.CustomerId).IsRequired().HasMaxLength(50);
            builder.Property(o => o.TotalAmount).HasPrecision(18, 2);
        });
    }
}

public sealed class UnitOfWork(ApplicationDbContext context) : IUnitOfWork
{
    private IDbContextTransaction? _currentTransaction;

    public async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
    {
        // Interceptor, audit logging, atau domain event dispatching dapat disisipkan di sini
        return await context.SaveChangesAsync(cancellationToken);
    }

    public async Task BeginTransactionAsync(CancellationToken cancellationToken = default)
    {
        if (_currentTransaction is not null) return;
        _currentTransaction = await context.Database.BeginTransactionAsync(cancellationToken);
    }

    public async Task CommitTransactionAsync(CancellationToken cancellationToken = default)
    {
        try
        {
            await context.SaveChangesAsync(cancellationToken);
            if (_currentTransaction is not null)
            {
                await _currentTransaction.CommitAsync(cancellationToken);
            }
        }
        catch
        {
            await RollbackTransactionAsync(cancellationToken);
            throw;
        }
        finally
        {
            if (_currentTransaction is not null)
            {
                await _currentTransaction.DisposeAsync();
                _currentTransaction = null;
            }
        }
    }

    public async Task RollbackTransactionAsync(CancellationToken cancellationToken = default)
    {
        if (_currentTransaction is null) return;

        await _currentTransaction.RollbackAsync(cancellationToken);
        await _currentTransaction.DisposeAsync();
        _currentTransaction = null;
    }

    public async ValueTask DisposeAsync()
    {
        if (_currentTransaction is not null)
        {
            await _currentTransaction.DisposeAsync();
        }
        await context.DisposeAsync();
    }
}

public sealed class OrderRepository(ApplicationDbContext context) : IOrderRepository
{
    public async Task<Order?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)
    {
        return await context.Orders.FindAsync([id], cancellationToken);
    }

    public async Task<IReadOnlyList<Order>> GetUnprocessedOrdersAsync(int batchSize, CancellationToken cancellationToken = default)
    {
        // Menghindari kebocoran IQueryable ke luar context, mengembalikan materialised data
        return await context.Orders
            .Where(o => !o.IsProcessed)
            .OrderBy(o => o.Id)
            .Take(batchSize)
            .AsNoTracking()
            .ToListAsync(cancellationToken);
    }

    public async Task AddAsync(Order order, CancellationToken cancellationToken = default)
    {
        await context.Orders.AddAsync(order, cancellationToken);
    }

    public void Remove(Order order)
    {
        context.Orders.Remove(order);
    }
}
```

#### 4. Penggunaan pada Application Layer (Service / Handler)

```csharp
namespace Application.Services;

public sealed class OrderProcessingService(
    IOrderRepository orderRepository,
    IUnitOfWork unitOfWork)
{
    public async Task ProcessOrdersAsync(CancellationToken ct)
    {
        await unitOfWork.BeginTransactionAsync(ct);
        try
        {
            var unprocessed = await orderRepository.GetUnprocessedOrdersAsync(10, ct);
            
            foreach (var order in unprocessed)
            {
                // Ambil entitas yang dilacak (tracked) oleh context
                var trackedOrder = await orderRepository.GetByIdAsync(order.Id, ct);
                trackedOrder?.MarkAsProcessed();
            }

            // Semua mutasi disimpan serempak via Unit of Work
            await unitOfWork.CommitTransactionAsync(ct);
        }
        catch
        {
            await unitOfWork.RollbackTransactionAsync(ct);
            throw;
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Change Tracking Engine
Saat Entity Framework Core bekerja di dalam pola Repository dan UoW:
1. **Identity Map & Snapshot Scanning**: Ketika entitas dimuat dari database melalui `OrderRepository.GetByIdAsync()`, runtime EF Core mencatat representasi nilai asli (original snapshot) di dalam struktur memori internal (`ChangeTracker`).
2. **Dirty Checking**: Saat `UnitOfWork.SaveChangesAsync()` dipanggil, EF Core memicu `ChangeTracker.DetectChanges()`. Runtime membandingkan state terkini dari objek pada Managed Heap terhadap snapshot aslinya.
3. **Topological Sort untuk SQL Batching**: EF Core menyusun *Dependency Graph* dari seluruh entitas yang berstatus `Added`, `Modified`, atau `Deleted`. Graf ini diurutkan secara topologis (topological sort) untuk memastikan perintah `INSERT`, `UPDATE`, dan `DELETE` dikirimkan ke DBMS tanpa melanggar batasan *Foreign Key Constraint*.

#### Alokasi Memori / Resource
- **State Tracking Overhead**: Setiap entitas yang dimuat secara default (tanpa `.AsNoTracking()`) menciptakan instance `EntityEntry` internal. Ini menggandakan konsumsi memori untuk data yang sama (data runtime + original snapshot).
- **DbContext Lifetime**: `DbContext` didesain untuk bersifat `Scoped` (hidup dan mati selama satu HTTP request atau background message execution). Jika UoW dan Repository didaftarkan sebagai `Singleton`, terjadi memory leak masif karena `ChangeTracker` tidak pernah membuang referensi objek, yang berujung pada degradasi komputasi linear saat `DetectChanges()` dievaluasi.

#### Trade-offs Arsitektur
| Keuntungan | Konsekuensi / Biaya |
| :--- | :--- |
| **Separasi Mutlak**: Domain layer murni terbebas dari dependensi paket pihak ketiga (`Microsoft.EntityFrameworkCore`). | **Boilerplate**: Menulis interface & class tambahan untuk setiap aggregate. |
| **Testability**: Sangat mudah melakukan mocking (`IOrderRepository` & `IUnitOfWork`) menggunakan framework seperti NSubstitute atau Moq. | **Feature Loss**: Menghambat penggunaan fitur canggih bawaan EF Core secara langsung (seperti `EF.Functions`, Compiled Queries, TagWith, Batch Delete via ExecuteDeleteAsync). |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Repository Berbasis Aggregate Root**: Jangan membuat repository untuk setiap tabel database. Buatlah hanya untuk entitas *Aggregate Root* (misal: `OrderRepository` mengelola `Order` sekaligus `OrderItem` privatnya).
- **Kembalikan `IReadOnlyList<T>` atau `Task<T?>`**: Selalu evaluasi query di dalam repository (`ToList`, `FirstOrDefault`) sebelum mengembalikannya ke service layer.
- **Daftarkan Dependency dengan Lifetime `Scoped`**:
  ```csharp
  services.AddScoped<IUnitOfWork, UnitOfWork>();
  services.AddScoped<IOrderRepository, OrderRepository>();
  ```

#### Don'ts
- **Anti-Pattern: Generic Repository dengan Bocoran Query Expression**:
  ```csharp
  // HINDARI INI!
  public interface IRepository<T> {
      IEnumerable<T> Find(Expression<Func<T, bool>> predicate); // Bocor!
      IQueryable<T> AsQueryable(); // Menghancurkan isolasi layer data!
  }
  ```
  *Alasan*: Mengekspos `Expression<Func<T, bool>>` atau `IQueryable` memungkinkan business logic bocor ke persistence layer, dan query kompleks dapat menyebabkan eksekusi query client-side yang tidak optimal.
- **Memanggil `SaveChangesAsync()` di Dalam Repository**:
  *Alasan*: Menyimpan state langsung di method repository (misal: `AddAsync` langsung `SaveChanges`) menghancurkan tujuan dari **Unit of Work**. Pola UoW menuntut persistensi dikoordinasikan secara atomik di akhir transaksi oleh caller.

#### Edge Cases
- **Detached Entities**: Jika menggunakan DTO yang diubah di luar scope lalu dikirim kembali ke Repository, entity tersebut tidak berada dalam context tracking. Anda harus meng-attach entitas secara eksplisit (`context.Orders.Update(order)`) atau mengambil entitas asli dari database sebelum memutasinya.
- **Deadlock Multi-DbContext**: Jika satu transaksi UoW melibatkan dua database berbeda (Distributed Transaction), EF Core's local transaction tidak mencukupi; Anda wajib memanfaatkan `System.Transactions.TransactionScope` dengan dukungan 2-Phase Commit (2PC).

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Generic Expression ke Specification Pattern**:
   Ambil Generic Repository yang menerima `Expression<Func<T, bool>>` dan refactor ke dalam **Specification Pattern** (`ISpecification<T>`). Pastikan query criteria diekapsulasi menjadi objek domain yang reusable (misal: `ExpiredOrdersSpecification`).
2. **Integrasi Transactional Outbox Pattern**:
   Modifikasi method `UnitOfWork.SaveChangesAsync()` agar sebelum menyimpan entitas domain, sistem secara otomatis mengekstraksi seluruh *Domain Events* yang tersimpan di dalam Aggregate Root, melakukan serialisasi menjadi JSON, dan menyimpannya ke tabel `OutboxMessages` dalam transaksi database yang sama (ACID).
