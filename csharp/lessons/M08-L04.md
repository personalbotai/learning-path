## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam Entity Framework Core (EF Core), **Change Tracker** adalah subsistem inti yang mengimplementasikan dua pola desain enterprise fundamental: **Identity Map** dan **Unit of Work**. 

Secara default, setiap kueri LINQ to Entities yang dieksekusi terhadap `DbSet<T>` dikonfigurasi sebagai **Tracking Query**. Artinya:
1. **Identity Map**: EF Core menjamin bahwa dalam satu instans `DbContext`, satu baris data unik pada database (ditentukan oleh Primary Key) hanya akan diwakili oleh tepat **satu instans objek** di memori C#.
2. **Snapshot Tracking**: Saat entitas dimaterialisasi dari *data reader*, EF Core mengambil salinan kondisi awal (*snapshot*) dari semua nilai properti entitas tersebut dan menyimpannya di dalam memori internal `ChangeTracker`. Ketika `DbContext.SaveChangesAsync()` dipanggil, EF Core membandingkan nilai instans entitas saat ini dengan *snapshot* tersebut (*dirty checking*) untuk menghasilkan *statement* SQL `UPDATE` yang spesifik pada kolom yang termodifikasi saja.

```
[Database Engine]
       │
 (SQL Result Set)
       ▼
[EF Core Materializer]
       │
       ├─► (Tracking: Default) ──► Simpan ref ke Identity Map ──► Buat Snapshot ──► Return Entity
       │                                                                                ▲
       └─► (AsNoTracking)      ─────────────────────────────────────────────────────────┘
                                  (Langsung bypass ChangeTracker & Snapshot)
```

#### Alasan Keberadaan `AsNoTracking`
Pada skenario *read-heavy* (seperti HTTP GET pada REST API, pembuatan report, atau microservices yang hanya membaca data), fitur pelacakan (*tracking*) menjadi *unnecessary overhead*. 
- Anda tidak berniat memanggil `.SaveChangesAsync()` untuk entitas tersebut.
- *Overhead* memori dialokasikan dua kali lipat (satu untuk objek yang Anda gunakan, satu untuk *snapshot* internal).
- *Overhead* CPU meningkat karena traversal dan pencatatan state di dalam `ChangeTracker`.

Operator `.AsNoTracking()` menginstruksikan EF Core untuk mem-bypass *Change Tracker* secara penuh: objek langsung dimaterialisasi dari ADO.NET `DbDataReader` dan diserahkan ke *caller* tanpa pencatatan *snapshot* atau registrasi *Identity Map*.

#### Varian: `AsNoTrackingWithIdentityResolution`
Pada `AsNoTracking()`, jika Anda melakukan `Include()` pada relasi *1-to-N* di mana entitas turunan merujuk kembali ke entitas induk yang sama, EF Core akan membuat **instans objek baru yang terduplikasi** di memori untuk setiap baris relasi. `AsNoTrackingWithIdentityResolution()` hadir (sejak EF Core 5.0) untuk mengatasi masalah ini: ia mempertahankan *Identity Map* sementara selama masa hidup kueri (sehingga kesamaan referensi objek tetap terjaga dan alokasi memori berkurang jika terdapat banyak duplikasi), tetapi tetap **tidak membuat snapshot** dan membuang state tracker setelah eksekusi kueri selesai.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah perbandingan implementasi antara *Tracking*, *AsNoTracking*, dan penanganan mutasi disconnected:

```csharp
using Microsoft.EntityFrameworkCore;

namespace TrackingVsNoTrackingDemo;

public class Customer
{
    public int Id { get; set; }
    public string FullName { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
    public List<Order> Orders { get; set; } = [];
}

public class Order
{
    public int Id { get; set; }
    public decimal TotalAmount { get; set; }
    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;
}

public class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();
}

public class CustomerService(AppDbContext context)
{
    // 1. READ-ONLY QUERY (Sangat Optimal: Tanpa Snapshot & Bypass Tracker)
    public async Task<List<CustomerDto>> GetCustomersReadOnlyAsync(CancellationToken ct = default)
    {
        return await context.Customers
            .AsNoTracking()
            .Where(c => c.Orders.Any())
            .Select(c => new CustomerDto(c.Id, c.FullName, c.Email))
            .ToListAsync(ct);
    }

    // 2. QUERY DENGAN IDENTITY RESOLUTION (Bypass Tracker tapi Mencegah Duplikasi Referensi Objek)
    public async Task<List<Order>> GetOrdersWithCustomerGraphAsync(CancellationToken ct = default)
    {
        // Jika 10 order dimiliki oleh 1 Customer yang sama:
        // AsNoTracking biasa: Membuat 10 instans Customer berbeda di memori C#.
        // AsNoTrackingWithIdentityResolution: Hanya 1 instans Customer yang di-referensikan 10 order.
        return await context.Orders
            .AsNoTrackingWithIdentityResolution()
            .Include(o => o.Customer)
            .ToListAsync(ct);
    }

    // 3. MUTATION QUERY (Wajib Tracking untuk Automatic Dirty Checking)
    public async Task UpdateCustomerEmailTrackingAsync(int customerId, string newEmail, CancellationToken ct = default)
    {
        // Default kueri: Tracking aktif
        var customer = await context.Customers.FirstOrDefaultAsync(c => c.Id == customerId, ct);
        
        if (customer is null) 
            throw new KeyNotFoundException($"Customer {customerId} not found.");

        // Modifikasi mutasi biasa
        customer.Email = newEmail;

        // EF Core ChangeTracker mendeteksi perbedaan Email antara Snapshot vs Objek saat ini.
        // Dihasilkan SQL: UPDATE Customers SET Email = @p0 WHERE Id = @p1;
        await context.SaveChangesAsync(ct);
    }

    // 4. COMMON PITFALL: AsNoTracking tapi mencoba SaveChanges
    public async Task BadUpdateExampleAsync(int customerId, string newEmail, CancellationToken ct = default)
    {
        var customer = await context.Customers
            .AsNoTracking()
            .FirstOrDefaultAsync(c => c.Id == customerId, ct);

        if (customer is null) return;

        customer.Email = newEmail;
        
        // BUG: Tidak ada SQL UPDATE yang dikirim ke database! 
        // ChangeTracker tidak mengetahui keberadaan entitas 'customer'.
        await context.SaveChangesAsync(ct); 
    }
}

public record CustomerDto(int Id, string FullName, string Email);
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Query Materialization Pipeline**: 
   - EF Core menyusun ekspresi kueri melalui *ShapedQueryCompilingExpressionVisitor*.
   - Saat reader ADO.NET (`DbDataReader`) mengeksekusi *command*, ia mengiterasi baris per baris.
   - Jika **Tracking Aktif**: EF Core memanggil `EntityMaterializerSource` untuk membuat instans entitas, lalu memasukkannya ke dalam `StateManager` (mesin inti di balik `ChangeTracker`). Di sini, instans di-bungkus dalam objek internal bernama `EntityEntry`.
   - Jika **`AsNoTracking` Aktif**: EF Core langsung mengeksekusi factory delegate untuk instansiasi entitas dan mengembalikan objek tersebut tanpa mengabari `StateManager`. Overhead wrapping `EntityEntry` ditiadakan.

#### Alokasi Memori / Resource
- **Snapshot Creation**: Pada tracking query, EF Core mengalokasikan array objek (`object[]`) di Gen 0/Gen 1 Heap untuk menyimpan nilai asli setiap kolom dari entitas. Jika Anda mengambil 10.000 baris entitas yang memiliki 20 properti, EF Core mengalokasikan minimal 200.000 referensi tambahan hanya untuk *snapshot state*.
- **Identity Map Dictionary**: Tracking query mempertahankan `Dictionary<EntityKey, EntityEntry>` di dalam memori context. Ini memperpanjang masa hidup pointer objek dan membebani GC (*Garbage Collector*) selama `DbContext` belum di-*dispose*.
- **`AsNoTracking` Memory Profile**: Mengeliminasi alokasi `object[]` snapshot dan entri *hash map* internal. Tekanan terhadap GC turun drastis, meminimalkan GC Gen 1/Gen 2 collections.

#### Trade-offs Matrix
| Fitur | Tracking (`Tracking`) | No-Tracking (`AsNoTracking`) | Identity Resolution (`AsNoTrackingWithIdentityResolution`) |
| :--- | :--- | :--- | :--- |
| **Kecepatan Pembacaan** | Paling lambat (Overhead tracking) | Paling Cepat | Cepat (Sedikit overhead hashing key) |
| **Alokasi Heap Memori** | Paling Tinggi (Objek + Snapshot) | Rendah (Hanya Objek) | Paling Rendah pada relasi redundant |
| **Kesesuaian Referensi Objek** | Terjamin (Identity Map) | Tidak Terjamin (Dapat duplikat) | Terjamin (Scope per kueri) |
| **Deteksi Perubahan Otomatis** | Ya (Via `SaveChanges`) | Tidak (Harus `Attach`/`Update`) | Tidak |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Terapkan Query Tracking Behavior Global jika Arsitektur Berbasis CQRS / Web API Stateless**:
   Jika sebagian besar operasi controller/endpoint Anda bersifat baca, Anda dapat mengubah default context menjadi no-tracking:
   ```csharp
   services.AddDbContext<AppDbContext>(options =>
       options.UseSqlServer(connectionString)
              .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking));
   ```
   Gunakan `.AsTracking()` secara eksplisit hanya saat data akan dimutasi.
2. **Gunakan Proyeksi (`Select`)**:
   Jika Anda melakukan proyeksi DTO menggunakan `.Select(x => new Dto { ... })`, EF Core **secara implisit menonaktifkan tracking** meskipun Anda tidak memanggil `.AsNoTracking()`, asalkan tipe proyeksi bukan tipe entitas yang dipetakan EF Core.

#### Don'ts
1. **Jangan Membaca Data Menggunakan `AsNoTracking` jika Anda Berencana Mengubahnya Langsung di Konteks yang Sama**:
   Memanggil `.AsNoTracking()` lalu mencoba memanggil `context.Update(entity)` akan menandai **seluruh** kolom sebagai `Modified`, bukan hanya kolom yang Anda ubah. Ini memaksa SQL mengeksekusi update pada seluruh kolom database (menimpa data yang mungkin diubah proses paralel lain dan menghancurkan efisiensi *index updating*).
2. **Jangan Asumsi `AsNoTracking()` Selalu Lebih Sedikit Memori pada Graph Kompleks**:
   Jika Anda mengeksekusi kueri dengan multiple `Include` (contoh: 1.000 item yang masing-masing merujuk ke Category yang sama dari 5 kategori yang ada), `AsNoTracking()` akan menginstansiasi 1.000 objek `Category` berbeda di heap. Gunakan `AsNoTrackingWithIdentityResolution()` untuk kasus relasi berganda ini.

#### Edge Cases
- **Disconnected Scenarios (REST API Update Lifecycle)**:
  Saat client mengirim payload JSON berupa entitas yang sebelumnya diambil secara `AsNoTracking`, `DbContext` tidak mengenalnya.
  ```csharp
  // Pendekatan Salah:
  context.Update(customerFromJson); // Semua kolom di-update!
  
  // Pendekatan Benar (Fetch with tracking first, lalu mutasi):
  var existingCustomer = await context.Customers.FindAsync(customerFromJson.Id);
  context.Entry(existingCustomer).CurrentValues.SetValues(customerFromJson);
  await context.SaveChangesAsync();
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Duplikasi Alokasi Heap**:
   Buat tabel `Departments` (1 baris) dan `Employees` (10.000 baris yang semuanya merujuk ke department tersebut). Jalankan dua kueri:
   - `context.Employees.Include(e => e.Department).AsNoTracking().ToList();`
   - `context.Employees.Include(e => e.Department).AsNoTrackingWithIdentityResolution().ToList();`
   
   Gunakan *assertion* `ReferenceEquals(employees[0].Department, employees[1].Department)` pada kedua hasil kueri tersebut. Buktikan kueri mana yang menghasilkan `true` dan kueri mana yang menghasilkan `false`, kemudian periksa memory footprint-nya via Visual Studio Diagnostic Tools atau dotMemory.

2. **Deteksi Perubahan Terputus (*Disconnected Property Patching*)**:
   Tulis sebuah ekstensi method yang menerima entitas hasil `AsNoTracking`, meng-attach entitas tersebut ke `DbContext`, lalu secara presisi hanya mengubah status satu kolom spesifik (misal: `IsActive`) menjadi `IsModified = true` tanpa harus me-load ulang entitas tersebut dari database melalui kueri tracking. Periksa query SQL mentah yang dihasilkan melalui `ToQueryString()` atau SQL Profiler.
