## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Domain-Driven Design (DDD) adalah pendekatan pengembangan perangkat lunak yang berfokus pada pemodelan domain bisnis yang kompleks. Dalam DDD, *Tactical Design* menyediakan *building blocks* untuk menerjemahkan aturan bisnis ke dalam kode. Tiga pilar utamanya adalah **Entities**, **Value Objects**, dan **Aggregates**.

*   **Entities (Entitas):** Objek yang didefinisikan oleh **identitas uniknya** (ID), bukan oleh atributnya. Entitas memiliki siklus hidup (dibuat, diubah, dihapus) dan bersifat *mutable* (dapat berubah). Contoh: `User`, `Order`. Dua entitas dianggap sama jika ID-nya sama, meskipun atribut lainnya berbeda.
*   **Value Objects (Objek Nilai):** Objek yang didefinisikan oleh **atributnya**, tanpa memiliki identitas unik. Value Object harus bersifat *immutable* (tidak dapat diubah setelah dibuat). Jika Anda perlu mengubah nilainya, Anda harus membuat instance baru. Contoh: `Money`, `Address`, `Email`. Dua Value Object dianggap sama jika semua propertinya bernilai sama (*structural equality*).
*   **Aggregates & Aggregate Roots (AR):** *Aggregate* adalah kluster dari Entitas dan Value Object yang diperlakukan sebagai satu kesatuan (*consistency boundary*). Setiap Aggregate memiliki satu **Aggregate Root**, yaitu entitas utama yang menjadi satu-satunya pintu masuk untuk berinteraksi dengan objek-objek di dalam Aggregate tersebut. AR bertanggung jawab untuk menjaga *invariants* (aturan bisnis yang harus selalu benar).

**Mengapa arsitektur ini penting?**
Tanpa batasan ini, aplikasi sering jatuh ke dalam *Anemic Domain Model* (kelas hanya berisi *getter/setter* tanpa logika bisnis) dan *Spaghetti Code* di mana status objek dapat diubah dari mana saja, menyebabkan inkonsistensi data dan *race conditions* saat transaksi database.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern di C# (menggunakan fitur C# 9+ seperti `record` dan *encapsulation* yang ketat) untuk domain pemesanan (*Order*).

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

// 1. VALUE OBJECT
// Menggunakan 'record' di C# sangat ideal untuk Value Object karena 
// secara otomatis menyediakan structural equality dan immutability.
public record Money(decimal Amount, string Currency)
{
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException("Cannot add different currencies.");
        return new Money(Amount + other.Amount, Currency);
    }
}

// 2. ENTITY (Child Entity di dalam Aggregate)
public class OrderItem
{
    public Guid Id { get; }
    public string ProductName { get; }
    public Money Price { get; }
    public int Quantity { get; private set; }

    // Internal constructor: Hanya Aggregate Root yang boleh membuat instance ini
    internal OrderItem(Guid id, string productName, Money price, int quantity)
    {
        if (quantity <= 0) throw new ArgumentException("Quantity must be > 0");
        
        Id = id;
        ProductName = productName;
        Price = price;
        Quantity = quantity;
    }

    internal void AddQuantity(int amount) => Quantity += amount;
}

// 3. AGGREGATE ROOT
public class Order
{
    public Guid Id { get; }
    public string CustomerId { get; }
    public DateTime CreatedAt { get; }
    
    // Encapsulation: Cegah modifikasi list dari luar (Oleh karena itu menggunakan IReadOnlyCollection)
    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();

    public Order(Guid id, string customerId)
    {
        Id = id;
        CustomerId = customerId;
        CreatedAt = DateTime.UtcNow;
    }

    // Perilaku Bisnis (Business Behavior) - Menjaga Invariants
    public void AddItem(string productName, Money price, int quantity)
    {
        var existingItem = _items.SingleOrDefault(i => i.ProductName == productName);
        
        if (existingItem != null)
        {
            existingItem.AddQuantity(quantity);
        }
        else
        {
            _items.Add(new OrderItem(Guid.NewGuid(), productName, price, quantity));
        }
    }

    // Kalkulasi dinamis berdasarkan state saat ini
    public Money CalculateTotal()
    {
        if (!_items.Any()) return new Money(0, "USD");

        var currency = _items.First().Price.Currency;
        var totalAmount = _items.Sum(i => i.Price.Amount * i.Quantity);
        
        return new Money(totalAmount, currency);
    }
}
```

**Penjelasan Kode:**
*   `Money` menggunakan `record`. Jika kita membandingkan `new Money(10, "USD") == new Money(10, "USD")`, hasilnya adalah `true`.
*   `OrderItem` adalah Entitas karena memiliki `Id`, tetapi konstruktor dan metode mutasinya ditandai `internal`. Ini mencegah layer aplikasi memanipulasinya secara langsung.
*   `Order` adalah Aggregate Root. Koleksi `_items` disembunyikan di balik `IReadOnlyCollection`. Satu-satunya cara menambah item adalah melalui metode `AddItem`, yang memastikan aturan bisnis (seperti menggabungkan kuantitas jika produk sama) dieksekusi dengan aman.

### 3. Cara Kerja di Balik Layar (Under the Hood)

*   **Eksekusi & Runtime:** 
    *   Saat menggunakan `record` untuk Value Object, *compiler* C# (Roslyn) di balik layar men-generate implementasi `IEquatable<T>`, meng-override `Equals()`, `GetHashCode()`, dan operator `==` / `!=`. Ini membebaskan developer dari menulis kode *boilerplate* untuk *structural equality*.
    *   Pada ORM seperti Entity Framework (EF) Core, Aggregate Root dilacak oleh *Change Tracker*. Karena koleksi `_items` dienkapsulasi, EF Core memerlukan konfigurasi khusus (menggunakan *backing field* `_items`) agar dapat melakukan materialisasi data dari database ke memori tanpa mem-bypass aturan bisnis.
*   **Alokasi Memori / Resource:** 
    *   `record class` (default dari `record`) dialokasikan di **Heap** (sebagai *reference type*), tetapi berperilaku seperti *value type* dalam hal komparasi. Jika performa sangat kritikal dan GC (*Garbage Collector*) *pressure* harus ditekan, Value Object dapat diimplementasikan sebagai `readonly record struct` (dialokasikan di **Stack**).
*   **Trade-offs:** 
    *   Menerapkan DDD membutuhkan lebih banyak kode di awal (abstraksi, enkapsulasi) dibandingkan pendekatan CRUD/Anemic biasa. Namun, seiring kompleksitas aplikasi meningkat, DDD menjaga kurva pemeliharaan (*maintenance curve*) tetap datar karena logika bisnis terpusat dan terisolasi.

### 4. Best Practices & Common Pitfalls

*   **Do's:**
    *   **Gunakan `record` untuk Value Objects.** Ini adalah fitur C# paling idiomatik untuk kebutuhan ini.
    *   **Rancang Aggregate sekecil mungkin.** Aggregate yang terlalu besar (misal: `Order` memuat seluruh `Customer` dan riwayat `Payment`) akan menyebabkan masalah performa memori dan konflik konkurensi di database.
    *   **Referensi Aggregate lain melalui ID.** Jangan gunakan referensi objek langsung. Contoh: `Order` memiliki `CustomerId` (string/Guid), bukan objek `Customer Customer`.
*   **Don'ts:**
    *   **Jangan gunakan *public setter* pada Entitas.** Gunakan metode dengan nama yang merepresentasikan *Ubiquitous Language* (bahasa bisnis). Alih-alih `order.Status = "Shipped"`, gunakan `order.MarkAsShipped()`.
    *   **Jangan injeksi Repository/Service ke dalam Entitas.** Entitas harus murni (*pure*) dan tidak bergantung pada infrastruktur (I/O, Database).
*   **Edge Cases:**
    *   **Konkurensi:** Jika dua user mencoba memodifikasi `Order` yang sama secara bersamaan, Aggregate Root harus memiliki mekanisme *Optimistic Concurrency* (misalnya properti `byte[] RowVersion` atau `int Version`) untuk mencegah *Lost Update*.

### 5. Tantangan Eksplorasi Mandiri

1.  **Integrasi ORM:** Implementasikan konfigurasi EF Core `IEntityTypeConfiguration<Order>` untuk memetakan *backing field* `_items` dan gunakan `OwnsOne` untuk memetakan Value Object `Money` ke dalam tabel yang sama dengan `Order` dan `OrderItem`.
2.  **Domain Events:** Modifikasi kelas `Order` agar mewarisi kelas dasar yang dapat menampung *Domain Events*. Buat agar metode `AddItem` memicu event `OrderItemAddedEvent`, lalu rancang mekanisme untuk mem-publish event tersebut sesaat sebelum transaksi database di-commit.
3.  **Record Structs:** Ubah `Money` menjadi `readonly record struct`. Lakukan *benchmarking* (menggunakan `BenchmarkDotNet`) untuk membandingkan alokasi memori antara `record class` dan `readonly record struct` saat membuat 10.000 instance `Money`.
