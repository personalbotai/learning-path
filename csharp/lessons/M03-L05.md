## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam pemrograman berorientasi objek, kita mengenal *Liskov Substitution Principle* (LSP), di mana tipe turunan (derived type) dapat menggantikan tipe dasar (base type). Namun, ketika berhadapan dengan Generics, aturan ini secara default tidak berlaku. Sebuah `List<Dog>` **bukanlah** turunan dari `List<Animal>`, meskipun `Dog` adalah turunan dari `Animal`. Perilaku default ini disebut **Invariance**.

Untuk mengatasi limitasi ini secara *type-safe*, C# (sejak versi 4.0) memperkenalkan **Variance** pada Generics yang secara eksklusif hanya berlaku untuk **Interface** dan **Delegate**. Variance terbagi menjadi dua:

1.  **Covariance (`out`)**: Memungkinkan Anda menggunakan tipe yang *lebih spesifik* (derived) daripada yang dideklarasikan. Digunakan ketika generic type parameter hanya bertindak sebagai **Producer** (mengembalikan data).
2.  **Contravariance (`in`)**: Memungkinkan Anda menggunakan tipe yang *lebih umum* (base) daripada yang dideklarasikan. Digunakan ketika generic type parameter hanya bertindak sebagai **Consumer** (menerima data sebagai argumen).

**Mengapa ini penting?**
Tanpa variance, polimorfisme pada koleksi dan delegasi akan sangat kaku, memaksa developer melakukan *casting* manual yang rawan `InvalidCastException` di runtime. Variance memindahkan beban validasi keamanan tipe (type safety) dari runtime ke compiler.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi yang mendemonstrasikan Invariance, Covariance, dan Contravariance.

```csharp
using System;
using System.Collections.Generic;

// 1. Hierarki Kelas Dasar
public class Animal { public string Name { get; set; } }
public class Dog : Animal { public void Bark() => Console.WriteLine("Woof!"); }
public class Cat : Animal { public void Meow() => Console.WriteLine("Meow!"); }

// 2. COVARIANCE (out) - Hanya memproduksi data
public interface IProducer<out T>
{
    T Produce(); 
    // void Consume(T item); // ERROR: T tidak bisa jadi parameter input jika ditandai 'out'
}

public class AnimalShelter : IProducer<Dog>
{
    public Dog Produce() => new Dog { Name = "Rex" };
}

// 3. CONTRAVARIANCE (in) - Hanya mengkonsumsi data
public interface IConsumer<in T>
{
    void Consume(T item);
    // T Produce(); // ERROR: T tidak bisa jadi return type jika ditandai 'in'
}

public class AnimalVet : IConsumer<Animal>
{
    public void Consume(Animal animal) => Console.WriteLine($"Treating {animal.Name}");
}

public class Program
{
    public static void Main()
    {
        // --- INVARIANCE (Default pada Class/Struct) ---
        List<Dog> dogs = new List<Dog>();
        // List<Animal> animals = dogs; // COMPILE ERROR! List<T> adalah invariant.
        
        // Mengapa Error? Jika diizinkan, kita bisa melakukan: animals.Add(new Cat()); 
        // Padahal 'animals' merujuk ke List<Dog>. Ini akan merusak type safety!

        // --- COVARIANCE (out) ---
        IProducer<Dog> dogProducer = new AnimalShelter();
        // Aman: Karena IProducer hanya MENGELUARKAN data, Dog pasti adalah Animal.
        IProducer<Animal> animalProducer = dogProducer; 
        Animal a = animalProducer.Produce();
        
        // Contoh di .NET BCL: IEnumerable<out T>
        IEnumerable<Dog> dogPack = new List<Dog> { new Dog { Name = "Buddy" } };
        IEnumerable<Animal> animalPack = dogPack; // Valid!

        // --- CONTRAVARIANCE (in) ---
        IConsumer<Animal> generalVet = new AnimalVet();
        // Aman: Vet yang bisa merawat Animal, pasti bisa merawat Dog.
        IConsumer<Dog> dogVet = generalVet; 
        dogVet.Consume(new Dog { Name = "Max" });

        // Contoh di .NET BCL: Action<in T>
        Action<Animal> feedAnimal = (anim) => Console.WriteLine($"Feeding {anim.Name}");
        Action<Dog> feedDog = feedAnimal; // Valid!
        feedDog(new Dog { Name = "Buster" });
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime (CLR)**: 
  Variance di C# diimplementasikan di level *Common Language Runtime* (CLR). Saat compiler C# melihat modifier `in` atau `out`, ia menyematkan metadata khusus (flag `+` untuk out, `-` untuk in) pada definisi IL (Intermediate Language) dari interface/delegate tersebut. CLR menggunakan metadata ini saat mengeksekusi instruksi `castclass` atau `isinst` untuk memvalidasi apakah konversi referensi aman dilakukan.
- **Alokasi Memori / Resource**: 
  Variance **tidak** menciptakan objek baru atau melakukan penyalinan memori. Konversi dari `IEnumerable<Dog>` ke `IEnumerable<Animal>` murni merupakan *reference conversion*. Pointer memori tetap menunjuk ke objek yang sama di Heap, hanya saja tipe referensinya (kacamatanya) yang berubah.
- **Trade-offs (Batasan Value Types)**: 
  Variance **HANYA** bekerja pada *Reference Types* (class). Variance **TIDAK** berlaku untuk *Value Types* (struct, int, enum). 
  *Alasan Arsitektural*: Reference types selalu memiliki ukuran memori yang sama (pointer 32-bit atau 64-bit), sehingga CLR bisa menggunakan referensi yang sama. Value types memiliki ukuran memori yang berbeda-beda dan memerlukan *boxing* jika di-cast ke tipe dasar (seperti `object`), yang akan mengubah representasi memori. Oleh karena itu, `IEnumerable<int>` **tidak bisa** di-cast menjadi `IEnumerable<object>`.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `out` (Covariance) untuk interface yang bersifat *Read-Only* (seperti `IReadOnlyList<out T>`, `IEnumerable<out T>`).
  - Gunakan `in` (Contravariance) untuk interface yang bertindak sebagai *Handler*, *Processor*, atau *Comparer* (seperti `IComparer<in T>`, `IEquatable<in T>`).
  - Ingat prinsip **PO-CI** (Producer `Out`, Consumer `In`).
- **Don'ts**:
  - Jangan mencoba menerapkan `in`/`out` pada deklarasi `class` atau `struct`. Variance hanya didukung pada `interface` dan `delegate`.
  - Jangan memaksakan penggunaan variance jika interface Anda perlu melakukan operasi baca *dan* tulis (seperti `IList<T>`). Biarkan tetap Invariant.
- **Edge Cases (Array Covariance Flaw)**:
  Sejak C# 1.0, Array mendukung covariance secara default (misal: `Animal[] arr = new Dog[5];`). Namun, ini adalah **desain yang cacat** (broken by design) karena jika Anda melakukan `arr[0] = new Cat();`, compiler akan mengizinkannya, tetapi program akan *crash* di runtime dengan `ArrayTypeMismatchException`. Generics variance (`in`/`out`) diciptakan untuk memperbaiki masalah ini dengan memaksakan validasi di level compiler (compile-time).

### 5. Tantangan Eksplorasi Mandiri

1. **Event Aggregator**: Buatlah sebuah sistem *Event/Message Bus* sederhana menggunakan interface `IEventHandler<in TEvent>`. Buktikan bahwa sebuah handler yang menerima `BaseEvent` dapat didaftarkan untuk menangani `SpecificEvent`.
2. **Delegate Variance**: Eksplorasi delegate bawaan C# yaitu `Func<in T, out TResult>`. Buatlah sebuah metode yang menerima delegate tersebut dan tunjukkan bagaimana Anda bisa memasukkan metode dengan parameter yang lebih umum (contravariance) dan return type yang lebih spesifik (covariance).
3. **Value Type Trap**: Cobalah buat `IEnumerable<int>` dan cast menjadi `IEnumerable<object>`. Amati error compiler yang terjadi dan tuliskan penjelasan singkat mengapa CLR menolak operasi tersebut berdasarkan konsep alokasi memori (boxing).
