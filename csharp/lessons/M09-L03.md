### 1. Konsep & Arsitektur Mendalam

#### Mengapa CQRS Diperlukan?
Dalam arsitektur tradisional berbasis CRUD, model data yang sama digunakan untuk membaca (*read*) dan menulis (*write*). Pola ini memicu masalah skalabilitas ketika aplikasi berkembang:
1. **Asimetri Beban Kerja:** Rasio pembacaan sistem umumnya jauh lebih tinggi daripada penulisan (misal: 95% read vs 5% write). Mengunci skema data yang sama untuk keduanya menimbulkan *bottleneck* penguncian baris/tabel (*row/table locking*) dan degradasi konkurensi.
2. **Konflik Impedansi Objek:** Operasi *write* memerlukan enkapsulasi logika bisnis, invariansi domain (*rich domain model*), dan normalisasi tinggi (3NF) guna mencegah anomali data. Sebaliknya, operasi *read* membutuhkan proyeksi data yang terdenormalisasi, pemrosesan cepat, dan transfer payload data (*DTO*) tanpa overhead domain behavior.

**CQRS (Command Query Responsibility Segregation)** memisahkan alur logika sistem ke dalam dua jalur independen:
- **Command:** Mengubah *state* sistem, tidak mengembalikan representasi *state* (kecuali ID referensi atau status sukses/gagal), dan divalidasi ketat terhadap aturan bisnis.
- **Query:** Mengambil data tanpa mengubah *state* (idempoten dan *side-effect free*), dioptimasi untuk kecepatan baca.

```
                    ┌──────────────┐
                    │ API / Client │
                    └──────┬───────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
      [Command Model]              [Query Model]
             │                           │
  - Validasi Domain          - DTO Projection (Dapper/EF NoTracking)
  - Business Rules/Invariants - Caching Strategy
  - UoW / DbContext (Write)  - Read Replica / Direct SQL
             │                           │
             ▼                           ▼
      ┌─────────────┐             ┌─────────────┐
      │ Primary DB  │════(Sync)══>│ Read Store  │
      └─────────────┘             └─────────────┘
```

#### Peran MediatR dalam In-Process CQRS
MediatR mengimplementasikan pola **Mediator**, **Command**, dan **Chain of Responsibility**. Alih-alih Controller berpasangan langsung (*tightly coupled*) dengan Service/Repository, Controller mengirimkan pesan (*Message*) ke Mediator. 

MediatR kemudian:
1. Melakukan resolusi tipe *handler* yang relevan via Dependency Injection (IoC).
2. Mengeksekusi rangkaian *pipeline behavior* (interceptor) untuk *cross-cutting concerns* (validasi, logging, metrik transaksi).
3. Meneruskan pesan ke *Handler* target.

Pemisahan ini menegakkan prinsip *Single Responsibility* (satu handler = satu use case) dan *Open/Closed Principle* (fitur baru cukup menambah handler baru tanpa mengubah kode yang ada).

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Pembuatan Akun Rekening Bank (**Command**) dan Pengambilan Saldo Rekening (**Query**) menggunakan .NET 8, C# 12, dan MediatR.

#### A. Kontrak & Pesan (Commands & Queries)
Gunakan `record` C# untuk memastikan pesan bersifat *immutable* (tidak dapat diubah setelah diinstansiasi).

```csharp
using MediatR;

namespace Banking.Application.Features.Accounts;

// Command: Membawa niat untuk mengubah state
public record CreateAccountCommand(
    Guid CustomerId, 
    string Currency, 
    decimal InitialDeposit
) : IRequest<Guid>; // Mengembalikan ID akun baru

// Query: Membawa parameter untuk mengambil data tanpa efek samping
public record GetAccountBalanceQuery(
    Guid AccountId
) : IRequest<AccountBalanceDto?>;

// DTO untuk Query
public record AccountBalanceDto(
    Guid AccountId, 
    decimal Balance, 
    string Currency, 
    DateTime LastUpdatedUtc
);
```

#### B. Pipeline Behavior (Cross-Cutting Concern: Logging & Validation)
Menggunakan generic middleware di level MediatR untuk memvalidasi perintah sebelum mencapai handler.

```csharp
using FluentValidation;
using MediatR;
using Microsoft.Extensions.Logging;

namespace Banking.Application.Behaviors;

public class ValidationPipelineBehavior<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators,
    ILogger<ValidationPipelineBehavior<TRequest, TResponse>> logger
) : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, 
        RequestHandlerDelegate<TResponse> next, 
        CancellationToken cancellationToken)
    {
        var context = new ValidationContext<TRequest>(request);

        var validationResults = await Task.WhenAll(
            validators.Select(v => v.ValidateAsync(context, cancellationToken))
        );

        var failures = validationResults
            .SelectMany(r => r.Errors)
            .Where(f => f != null)
            .ToList();

        if (failures.Count != 0)
        {
            logger.LogWarning("Validasi gagal untuk request {RequestType}", typeof(TRequest).Name);
            throw new ValidationException(failures);
        }

        return await next(); // Lanjut ke behavior berikutnya atau Handler
    }
}
```

#### C. Command Handler (Write Model: Enkapsulasi Domain)
```csharp
using MediatR;

namespace Banking.Application.Features.Accounts.Commands;

public class CreateAccountCommandHandler : IRequestHandler<CreateAccountCommand, Guid>
{
    // Dalam real-world: Inject UnitOfWork / EF DbContext / Aggregate Repository
    public async Task<Guid> Handle(CreateAccountCommand command, CancellationToken cancellationToken)
    {
        // 1. Eksekusi Invariant Bisnis
        if (command.InitialDeposit < 50_000)
        {
            throw new InvalidOperationException("Setoran awal minimum adalah Rp 50.000,-");
        }

        // 2. Buat Domain Entity / State Change
        var accountId = Guid.NewGuid();
        
        // Simulasi I/O penyimpanan ke Write Database
        await Task.Delay(20, cancellationToken); 

        return accountId;
    }
}
```

#### D. Query Handler (Read Model: Bypass Domain, Langsung ke DTO)
Query tidak boleh memuat Domain Entity lengkap; query membaca langsung dari database secara teroptimasi (misal via Dapper atau EF Core dengan `.AsNoTracking()`).

```csharp
using MediatR;

namespace Banking.Application.Features.Accounts.Queries;

public class GetAccountBalanceQueryHandler : IRequestHandler<GetAccountBalanceQuery, AccountBalanceDto?>
{
    public async Task<AccountBalanceDto?> Handle(GetAccountBalanceQuery query, CancellationToken cancellationToken)
    {
        // Query model mengabaikan validasi bisnis domain yang kompleks.
        // Langsung proyeksikan data dari read-store/database.
        await Task.Delay(10, cancellationToken); // Simulasi SQL Read (misal: via Dapper)

        return new AccountBalanceDto(
            AccountId: query.AccountId,
            Balance: 1_250_000m,
            Currency: "IDR",
            LastUpdatedUtc: DateTime.UtcNow
        );
    }
}
```

#### E. Wire-up Dependency Injection & Minimal API (.NET 8)
```csharp
using Banking.Application.Behaviors;
using Banking.Application.Features.Accounts;
using FluentValidation;
using MediatR;

var builder = WebApplication.CreateBuilder(args);

// Registrasi MediatR & Scanning Assembly
builder.Services.AddMediatR(cfg => {
    cfg.RegisterServicesFromAssembly(typeof(CreateAccountCommand).Assembly);
    cfg.AddOpenBehavior(typeof(ValidationPipelineBehavior<,>));
});

// Registrasi Validasi
builder.Services.AddValidatorsFromAssembly(typeof(CreateAccountCommand).Assembly);

var app = builder.Build();

// Endpoint Command
app.MapPost("/accounts", async (CreateAccountCommand cmd, ISender sender, CancellationToken ct) =>
{
    var accountId = await sender.Send(cmd, ct);
    return Results.Created($"/accounts/{accountId}", new { Id = accountId });
});

// Endpoint Query
app.MapGet("/accounts/{id:guid}/balance", async (Guid id, ISender sender, CancellationToken ct) =>
{
    var result = await sender.Send(new GetAccountBalanceQuery(id), ct);
    return result is not null ? Results.Ok(result) : Results.NotFound();
});

app.Run();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Resolusi Dynamic Dispatch
MediatR **tidak** menggunakan `dynamic` C# runtime yang memicu DLR (Dynamic Language Runtime) overhead saat pemanggilan pesan. MediatR bekerja dengan teknik **Compiled Expressions** dan Dependency Injection resolution:

1. **Service Registration:** Saat aplikasi startup (`AddMediatR`), library melakukan *scanning* reflection pada metadata assembly untuk memetakan pasangan:
   `IRequest<TResponse>` $\rightarrow$ `IRequestHandler<TRequest, TResponse>`.
2. **Handler Activation:** Interface `ISender.Send(request)` membungkus request ke dalam kelas wrapper generik internal (`RequestHandlerWrapperImpl<TResponse>`). Wrapper ini membuat delegasi eksekusi terkompilasi (*cached delegates*) yang mengikat instance `IRequestHandler` dari IoC Container, sehingga menghindari overhead scanning reflection pada setiap request HTTP yang masuk.
3. **Pipeline Construction:** Pipeline behavior dirangkai menggunakan teknik rekursif mirip konstruksi middleware ASP.NET Core:
   ```csharp
   // Representasi pseudo-code MediatR pipeline nesting:
   RequestHandlerDelegate<TResponse> executionDelegate = () => handler.Handle(request, ct);
   foreach (var behavior in behaviors.Reverse())
   {
       var currentNext = executionDelegate;
       executionDelegate = () => behavior.Handle(request, currentNext, ct);
   }
   return executionDelegate();
   ```

#### Alokasi Memori & Resource
- **Heap Allocations:** Setiap pengiriman pesan (`sender.Send(...)`) mengalokasikan:
  1. Instance objek Command/Query (reference type / class / record).
  2. Eksekusi state machine asynchronous `Task<TResponse>`.
  3. Instance delegasi closure untuk setiap layer dalam `IPipelineBehavior`.
- **Garbage Collection (GC):** Pada sistem throughput ekstrem (misal >50.000 RPS), alokasi instansiasi pesan yang terus-menerus akan memicu frekuensi GC Gen 0 meningkat. Oleh karena itu, hindari menaruh payload biner masif di dalam instance `IRequest`.
- **Lifetime Management:** Handler didaftarkan secara default sebagai `Transient` (atau mengikuti *Service Lifetime* yang diatur). Jika handler membutuhkan `DbContext`, maka dependensi handler otomatis terikat ke dalam `Scoped` lifecycle HTTP context yang sama.

#### Trade-offs
| Aspek | Monolithic Service Layer | CQRS dengan MediatR |
| :--- | :--- | :--- |
| **Keterbacaan Alur** | Eksplisit. Pemanggilan metode langsung mudah ditelusuri (*Go to Definition*). | Implisit. Terjadi indirection via broker; navigasi kode menuntut pencarian teks manual atau IDE plugin khusus. |
| **Performa Eksekusi** | Zero abstraction overhead, direct method invocation (paling cepat). | Tambahan latensi mikroskopis (~1-5 mikrodetik) akibat resolusi generic wrapper dan pipeline chain. |
| **Maintainability** | Service rentan menjadi *God Class* ribuan baris dengan lusinan dependensi konstruktor. | Handler tetap ramping (*Single Responsibility*), dependensi minim per use-case. |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Gunakan Record Type untuk Messages:** Record secara *native* menyediakan immutability dan *value-based equality*, memitigasi bahaya modifikasi state pesan di tengah eksekusi pipeline.
2. **Gunakan ISender, Bukan IMediator:** Injeksikan interface `ISender` ke dalam API endpoints/controllers jika Anda hanya butuh mengirim Command/Query. Interface `IMediator` mencakup fungsionalitas `IPublisher` (untuk *in-memory event broadcasting* via notifications) yang tidak selalu dibutuhkan oleh lapisan transport web.
3. **Bypass Domain Model pada Queries:** Di dalam Query Handler, hindari memuat entitas domain lengkap (misal `Account` aggregate). Eksekusi query langsung ke database menggunakan proyeksi SQL atau `.AsNoTracking().Select(...)` langsung ke DTO untuk menghemat alokasi memori dan siklus CPU.
4. **Sertakan Selalu `CancellationToken`:** Teruskan selalu token pembatalan dari layer controller/minimal API ke `ISender.Send(request, ct)` hingga ke layer database call untuk mencegah konsumsi resource tak terpakai akibat *client disconnected*.

#### Don'ts
1. **Handler-to-Handler Calling (Anti-Pattern):** Jangan pernah menyuntikkan `ISender` ke dalam suatu `IRequestHandler` untuk memanggil handler lain. Ini menciptakan kopling tersembunyi (*spaghetti orchestration*). Jika dua proses harus berbagi logika, pisahkan logika tersebut ke dalam Domain Service terpisah.
2. **Mencampur Konsep CQS dan Event-Driven Architecture:** MediatR `INotification` adalah *in-process broadcasting*, bukan pengganti message broker eksternal (seperti RabbitMQ, Azure Service Bus, atau Kafka). Kegagalan pada satu `INotificationHandler` default-nya dapat menghentikan eksekusi handler lainnya dalam thread yang sama.
3. **Anemic Command Handler:** Jangan menaruh seluruh aturan validasi dan logika mutasi state di dalam Command Handler. Tempatkan aturan mutasi pada *Domain Entity/Aggregate*, dan biarkan Command Handler bertindak sebagai orkestrator (koordinasi I/O, transaksi, dan persistence).

#### Edge Cases
- **Database Transaction Across Pipeline:** Jika menggunakan Transaction Pipeline Behavior, pastikan menangani situasi *nested transactions* atau isolasi koneksi jika handler mengeksekusi operasi baca-tulis multithreaded secara bersamaan.
- **Async Void Notifications:** Default implementation dari MediatR `Publish` mengeksekusi notification handlers secara sekuensial. Jika salah satu handler melempar `Exception`, handler berikutnya tidak akan dieksekusi kecuali dikonfigurasi strategi publikasi paralel (`PublishStrategy.ParallelNoWait` dsb.).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Generic Transactional Pipeline Behavior:**
   Buat sebuah `IPipelineBehavior<TRequest, TResponse>` yang memeriksa apakah `TRequest` mengimplementasikan antarmuka penanda `ITransactionalCommand`. Jika ya, bungkus eksekusi `next()` di dalam blok `IDbContextTransaction` menggunakan Entity Framework Core, lengkap dengan skema *automatic rollback* saat terjadi eksepsi.

2. **Implementasi In-Memory Caching Behavior untuk Query:**
   Buat interface `ICacheableQuery` yang memiliki properti `string CacheKey` dan `TimeSpan Expiration`. Buat generic pipeline behavior yang memanfaatkan `IMemoryCache` atau `IDistributedCache`: jika data sudah ada di cache, segera kembalikan data tersebut dan potong eksekusi rantai pipeline tanpa memanggil Handler database asli.
