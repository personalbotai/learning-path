## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Containerization pada ekosistem .NET telah berevolusi dari image monolitik berbasis Windows Server/Debian standar menuju runtime yang sangat ramping (*lean*), aman, dan dioptimalkan secara mikro. Di lingkungan produksi modern (seperti Kubernetes), ukuran container (*image footprint*) dan *attack surface* (vektor serangan keamanan) adalah metrik vital.

```
Evolusi Container Images .NET:
+-------------------------------------------------------------+
| Standard Linux (Debian/Ubuntu Full) ~200MB+ (Shell, APT)    | -> Rawan CVE, lambat ditarik
+-------------------------------------------------------------+
| Linux Slim / Alpine ~100MB (musl libc, isu kompatibilitas)  | -> Performa GC/PInvoke bervariasi
+-------------------------------------------------------------+
| Ubuntu Chiseled / Distroless ~45-50MB (glibc, NO Shell/APT) | -> Sangat aman, ultra-cepat, production-ready
+-------------------------------------------------------------+
```

#### Mengapa Bukan Alpine Biasa?
Secara historis, developer beralih ke Alpine Linux untuk mengecilkan ukuran image. Namun, Alpine menggunakan implementasi C standard library **musl libc**, sedangkan .NET CoreCLR dioptimalkan secara native untuk **glibc**. 
Perbedaan ini kerap memicu kendala:
1. **Performa Memory Allocator**: Alokator `musl` standar memiliki karakteristik konkurensi alokasi heap yang berbeda dan sering kali lebih lambat dibanding `glibc` (ptmalloc) untuk skenario *high-throughput multi-threaded*.
2. **Kompatibilitas Native Dependency**: Library pihak ketiga yang menggunakan *Platform Invoke* (P/Invoke) berbasis library C terkompilasi sering kali membutuhkan symlink manual atau bahkan crash jika dikompilasi khusus glibc.
3. **Globalisasi (ICU)**: Dukungan *International Components for Unicode* (ICU) di Alpine sering kali dipangkas, menyebabkan kalkulasi parsing tanggal/mata uang melempar runtime exception kecuali flag `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=true` diaktifkan.

#### Arsitektur Ubuntu Chiseled Images
Canonical dan Microsoft berkolaborasi menciptakan **Ubuntu Chiseled Images**. Konsep "chiseling" menggunakan tool `chisel` untuk mengekstrak hanya file biner, library dependensi tingkat rendah (seperti `glibc`, `libstdc++`, `zlib`, `openssl`), dan metadata lisensi langsung dari paket `.deb` Ubuntu resmi, **tanpa menyertakan package manager (`apt`, `dpkg`), shell (`bash`, `sh`), utilitas core (`ls`, `cat`), ataupun file konfigurasi yang tidak perlu**.

Karakteristik arsitektur Chiseled:
- **Zero Shell & Package Manager**: Mencegah penyerang yang berhasil mengeksekusi Remote Code Execution (RCE) melakukan *reverse shell* atau mengunduh malware via `curl`/`wget`.
- **Glibc Native**: Mempertahankan kestabilan alokasi memori runtime CoreCLR dan kompatibilitas native binary.
- **Rootless by Default**: Sejak .NET 8, container image Chiseled menjalankan aplikasi menggunakan akun non-root secara default (`$APP_UID` atau UID `1654`).
- **Appliance-like Model**: Container diperlakukan sebagai firmware/appliance yang immutabel.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern ASP.NET Core 8/9 menggunakan multi-stage build Dockerfile yang memanfaatkan **Ubuntu Chiseled runtime** dan konfigurasi non-root.

#### Struktur Proyek
```text
├── src/
│   └── OrderService/
│       ├── OrderService.csproj
│       └── Program.cs
├── .dockerignore
└── Dockerfile
```

#### `.dockerignore`
```dockerignore
**/.git
**/.vs
**/.vscode
**/bin
**/obj
**/*.user
Dockerfile*
docker-compose*
README.md
```

#### `OrderService.csproj`
```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <!-- Mencegah overhead pembuatan satellite assemblies yang tidak terpakai -->
    <InvariantGlobalization>false</InvariantGlobalization>
  </PropertyGroup>

</Project>
```

#### `Program.cs`
```csharp
using System.Net.Mime;

var builder = WebApplication.CreateBuilder(args);

// Port default ASP.NET Core 8+ di container non-root adalah 8080 (bukan 80)
builder.WebHost.ConfigureKestrel(options =>
{
    options.AddServerHeader = false; // Hardening: Sembunyikan banner Kestrel
});

builder.Services.AddHealthChecks();

var app = builder.Build();

app.UseHealthChecks("/healthz");

app.MapGet("/api/v1/orders", () => Results.Ok(new[]
{
    new { OrderId = Guid.NewGuid(), Amount = 150000m, Status = "Processed" },
    new { OrderId = Guid.NewGuid(), Amount = 450000m, Status = "Pending" }
}));

app.Run();
```

#### `Dockerfile` (Multi-Stage Production-Ready)
```dockerfile
# ----------------------------------------------------------------------
# Stage 1: Build & Publish via .NET SDK Environment
# ----------------------------------------------------------------------
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
ARG BUILD_CONFIGURATION=Release
WORKDIR /src

# Optimasi Layer Cache: Salin .csproj terlebih dahulu dan restore dependency
COPY ["src/OrderService/OrderService.csproj", "OrderService/"]
RUN dotnet restore "OrderService/OrderService.csproj"

# Salin sisa source code dan lakukan publish
COPY src/OrderService/ OrderService/
WORKDIR "/src/OrderService"
RUN dotnet publish "OrderService.csproj" \
    -c $BUILD_CONFIGURATION \
    -o /app/publish \
    --no-restore \
    /p:UseAppHost=false

# ----------------------------------------------------------------------
# Stage 2: Final Minimal Runtime via Chiseled Image
# ----------------------------------------------------------------------
# Gunakan image ASP.NET Chiseled resmi (Ubuntu-based, distroless)
FROM mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled AS final

WORKDIR /app
EXPOSE 8080

# Salin artifak hasil build dari Stage 1
COPY --from=build /app/publish .

# Terapkan Non-Root User yang sudah disediakan oleh base image (.NET 8+: UID 1654)
USER $APP_UID

# Jalankan DLL via dotnet runtime host
ENTRYPOINT ["dotnet", "OrderService.dll"]
```

#### Perintah Eksekusi
```bash
# Build image
docker build -t orderservice:chiseled -f Dockerfile .

# Jalankan container dengan resource constraint eksplisit
docker run -d \
  --name order-api \
  -p 8080:8080 \
  --memory="512m" \
  --cpus="1.0" \
  orderservice:chiseled

# Verifikasi status & user
docker top order-api
# Perhatikan bahwa process berjalan di bawah UID numerik (1654), bukan root (0)
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Chiseling & Kernel Isolation
- **Chiseling Process**: Saat canonical membangun image `aspnet:8.0-jammy-chiseled`, tool `chisel` membaca manifest slicing (misalnya `libc6_libs`, `libssl3_libs`). Hanya shared object files (`.so`) esensial yang diekstrak ke dalam root filesystem image. Akibatnya, syscall yang mengasumsikan keberadaan runtime environment Unix standar (seperti memanggil sub-process `/bin/sh -c`) akan langsung gagal dengan error `ENOENT` (No such file or directory).
- **CoreCLR Container Awareness**: CoreCLR secara native membaca Control Groups (**cgroups v1 & cgroups v2**) dari Linux kernel melalui path virtual `/sys/fs/cgroup`. Saat container diberi limit `--memory=512m`, runtime CoreCLR membaca file `memory.max` (cgroups v2) atau `memory.limit_in_bytes` (cgroups v1), **bukan** total RAM fisik host node.

#### Alokasi Memori / Resource: GC Heap Adaptation
- **Server GC vs Workstation GC**: Di dalam container dengan vCPU > 1, ASP.NET Core secara default menggunakan **Server GC**. Server GC mengalokasikan heap terpisah untuk setiap CPU core logical. Jika batas memori container kecil (misal: 256MB) tetapi berada di mesin host dengan 64-core, alokasi heap per-core awal dapat memicu *Out-Of-Memory (OOM) Killer* oleh kernel Linux sebelum aplikasi selesai inisialisasi.
- **Tuning Konfigurasi Runtime**:
  Pada environment dengan resource terbatas, CoreCLR menyediakan environment variable berikut:
  - `DOTNET_GCHeapHardLimitPercent`: Mengatur batas maksimum alokasi managed heap terhadap cgroup memory limit (misal: `75` untuk 75%). Sisanya disisakan untuk unmanaged heap, thread stack, dan JIT metadata.
  - `DOTNET_gcServer=0`: Memaksa *Workstation GC* jika container dialokasikan kurang dari 2 vCPU atau memori di bawah 256MB untuk memangkas overhead thread GC background.

#### Trade-offs
1. **Zero-In Container Debugging**: Developer tidak bisa melakukan `docker exec -it <container> /bin/bash` atau `curl localhost:8080` untuk troubleshooting jaringan internal di dalam container Chiseled. Troubleshooting harus beralih ke Kubernetes *ephemeral debug containers*, OpenTelemetry distributed tracing, atau .NET diagnostic tools remote (`dotnet-monitor`).
2. **Custom Native Dependencies**: Jika aplikasi bergantung pada binary native seperti SkiaSharp, wkhtmltopdf, atau native driver database lama, binary pendukung tersebut harus dimasukkan secara manual lewat multi-stage build ke direktori shared library (`/lib` atau `/usr/lib`), karena `apt-get install` tidak tersedia di runtime target.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Non-Root User Explicitly (`USER $APP_UID`)**: Hindari menjalankan proses sebagai PID root di dalam container. Jika terjadi eksploitasi container breakout, hak akses penyerang di host kernel akan dibatasi oleh UID unprivileged tersebut.
- **Gunakan Binding Port Non-Privileged (> 1024)**: Karena container berjalan sebagai non-root, aplikasi tidak dapat mengikat port privilege seperti port `80` atau `443`. Port standar modern ASP.NET Core adalah `8080` (HTTP) dan `8443` (HTTPS).
- **Manfaatkan `.dockerignore` Secara Agresif**: Jangan biarkan direktori `bin/` dan `obj/` lokal masuk ke dalam konteks build Docker. Hal ini mencegah konflik arsitektur binary kompilasi lokal host dengan arsitektur Linux container.

#### Don'ts
- **Jangan Menggunakan `dotnet run` di Production**: `dotnet run` membutuhkan .NET SDK lengkap, mengompilasi ulang kode, dan memakan memori berlipat ganda. Selalu jalankan hasil publikasi menggunakan `dotnet OrderService.dll`.
- **Jangan Mengabaikan ICU saat Parsing Multibahasa**: Jika menggunakan Chiseled regular (`aspnet:8.0-*-chiseled`), library ICU tidak disertakan untuk menjaga ukuran seminimal mungkin. Jika aplikasi membutuhkan sorting alfabet non-English atau formatting mata uang spesifik, gunakan tag **`-extra-chiseled`** (contoh: `mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled-extra`) yang menyertakan data ICU dan timezone.
- **Jangan Simpan Sensitive Configuration di Image Layer**: Jangan pernah meletakkan `appsettings.Production.json` dengan koneksi database atau API key di dalam Dockerfile `COPY`. Selalu injeksikan melalui Environment Variable, Kubernetes Secret, atau Azure Key Vault saat runtime.

#### Edge Cases: Penanganan Sertifikat SSL/TLS & Root CA Custom
Container Chiseled menyertakan sertifikat Mozilla Root CA default di `/etc/ssl/certs/ca-certificates.crt`. Jika API Anda perlu menghubungi internal enterprise proxy atau private microservice dengan Self-Signed Root CA:
```dockerfile
# Tambahkan CA privat Anda di stage SDK/Build lalu salin ke path sertifikat chiseled
FROM mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled AS final
WORKDIR /app
COPY --from=build /src/my-internal-ca.crt /usr/local/share/ca-certificates/
# Pada Chiseled, kita harus menyalin file yang sudah di-bundle jika tidak ada update-ca-certificates
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Komparasi Ukuran & CVE Image**:
   - Bangun aplikasi Web API yang sama menggunakan tiga base runtime image berbeda:
     1. `mcr.microsoft.com/dotnet/aspnet:8.0` (Debian regular)
     2. `mcr.microsoft.com/dotnet/aspnet:8.0-alpine` (Alpine Linux)
     3. `mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled` (Ubuntu Chiseled)
   - Jalankan `docker images` untuk membandingkan total byte size. Gunakan scanner kerentanan seperti `trivy image <nama-image>` untuk melihat perbedaan drastis jumlah CVE yang ditemukan di masing-masing image.

2. **Diagnostik Distroless Tanpa Shell**:
   - Jalankan container berbasis Chiseled. Buktikan bahwa perintah `docker exec -it <id> sh` akan ditolak oleh Docker engine.
   - Konfigurasikan file `dotnet-dump` atau buat *sidecar container* yang memanfaatkan shared Linux Process Namespace (`--pid=container:<target_container>`) untuk mengambil memory dump aplikasi ASP.NET Core yang sedang berjalan di dalam container Chiseled tanpa harus menginstal tool apapun di container aplikasi utama.
