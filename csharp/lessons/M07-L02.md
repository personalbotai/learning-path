### 1. Konsep & Arsitektur Mendalam

*Dependency Injection* (DI) adalah implementasi dari prinsip *Inversion of Control* (IoC), di mana pembuatan dan pengelolaan dependensi didelegasikan ke entitas eksternal—dalam ekosistem .NET, entitas ini adalah `Microsoft.Extensions.DependencyInjection` (sering disingkat MEDI).

Arsitektur DI Container di .NET dibangun di atas konsep graf dependensi hierarkis. Kontainer bertanggung jawab atas tiga hal: **Pendaftaran (*Registration*)**, **Resolusi (*Resolution*)**, dan **Masa Hidup (*Lifetime Management*)**.

Di .NET runtime, masa hidup objek dibagi menjadi tiga kategori utama melalui enum `ServiceLifetime`:

```
               [Root Container / IServiceProvider]
                               |
            +------------------+------------------+
            |                                     |
    [Singleton Service]                   [CreateScope()]
 (Hidup selama AppDomain)                         |
                                        [Child Scope Provider]
                                                  |
                                   +--------------+--------------+
                                   |                             |
                            [Scoped Service]             [Transient Service]
                         (1 per Scope context)         (Dibuat baru setiap request)
```

1. **Transient (`ServiceLifetime.Transient`)**:
   - Objek diinstansiasi setiap kali diminta oleh dependensi lain atau melalui `IServiceProvider.GetService()`.
   - Tidak terikat pada *scope*.
   - Ideal untuk dependensi *lightweight* dan *stateless*.

2. **Scoped (`ServiceLifetime.Scoped`)**:
   - Objek diinstansiasi **satu kali per scope**. Dalam ASP.NET Core, scope dibuat otomatis untuk setiap siklus HTTP Request.
   - Semua kelas yang meminta service ini dalam konteks request yang sama akan berbagi instance referensi memori yang sama.
   - Krusial untuk komponen yang membawa *state* per operasi bisnis, seperti Entity Framework Core `DbContext`.

3. **Singleton (`ServiceLifetime.Singleton`)**:
   - Objek hanya diinstansiasi **satu kali** (bisa secara *lazy* saat pertama kali diminta, atau *eager* saat aplikasi boot) dan dipakai bersama di seluruh aplikasi.
   - Hidup di *Root Provider* sampai aplikasi mati (*process termination*).
   - Wajib bersifat *thread-safe* karena akan diakses secara paralel oleh banyak thread sekaligus.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengilustrasikan perbedaan identitas objek (via `Guid`) di antara ketiga masa hidup dalam satu scope dan lintas scope.

```csharp
using System;
using Microsoft.Extensions.DependencyInjection;

// 1. Abstraksi dan Implementasi Marker Interface
public interface IOperation { Guid Id { get; } }
public interface ITransientOperation : IOperation { }
public interface IScopedOperation : IOperation { }
public interface ISingletonOperation : IOperation { }

public class OperationService : ITransientOperation, IScopedOperation, ISingletonOperation
{
    public Guid Id { get; } = Guid.NewGuid();
}

// Service Konsumen yang mengonsumsi ketiga varian
public class OperationConsumer
{
    public ITransientOperation Transient { get; }
    public IScopedOperation Scoped { get; }
    public ISingletonOperation Singleton { get; }

    public OperationConsumer(
        ITransientOperation transient,
        IScopedOperation scoped,
        ISingletonOperation singleton)
    {
        Transient = transient;
        Scoped = scoped;
        Singleton = singleton;
    }
}

public class Program
{
    public static void Main()
    {
        var services = new ServiceCollection();

        // Pendaftaran dependensi dengan lifetime yang berbeda
        services.AddTransient<ITransientOperation, OperationService>();
        services.AddScoped<IScopedOperation, OperationService>();
        services.AddSingleton<ISingletonOperation, OperationService>();
        
        services.AddTransient<OperationConsumer>();

        // Build ServiceProvider (Root Container)
        using ServiceProvider rootProvider = services.BuildServiceProvider(new ServiceProviderOptions
        {
            ValidateScopes = true, // Mencegah Captive Dependency saat startup
            ValidateOnBuild = true
        });

        Console.WriteLine("=== SIMULASI SCOPE 1 (e.g., HTTP Request 1) ===");
        using (IServiceScope scope1 = rootProvider.CreateScope())
        {
            var consumerA = scope1.ServiceProvider.GetRequiredService<OperationConsumer>();
            var consumerB = scope1.ServiceProvider.GetRequiredService<OperationConsumer>();

            Console.WriteLine($"[Consumer A] Transient: {consumerA.Transient.Id}");
            Console.WriteLine($"[Consumer B] Transient: {consumerB.Transient.Id} (Beda dengan A)");

            Console.WriteLine($"[Consumer A] Scoped:    {consumerA.Scoped.Id}");
            Console.WriteLine($"[Consumer B] Scoped:    {consumerB.Scoped.Id} (Sama persis dengan A)");

            Console.WriteLine($"[Consumer A] Singleton: {consumerA.Singleton.Id}");
        }

        Console.WriteLine("\n=== SIMULASI SCOPE 2 (e.g., HTTP Request 2) ===");
        using (IServiceScope scope2 = rootProvider.CreateScope())
        {
            var consumerC = scope2.ServiceProvider.GetRequiredService<OperationConsumer>();

            Console.WriteLine($"[Consumer C] Transient: {consumerC.Transient.Id} (Selalu Baru)");
            Console.WriteLine($"[Consumer C] Scoped:    {consumerC.Scoped.Id} (Baru dibanding Scope 1)");
            Console.WriteLine($"[Consumer C] Singleton: {consumerC.Singleton.Id} (Sama dengan Scope 1)");
        }
    }
}
```

#### Penjelasan Alur Eksekusi:
- **Transient**: `consumerA.Transient.Id != consumerB.Transient.Id`. Walaupun diminta di dalam scope yang sama, engine tetap memanggil *constructor* baru.
- **Scoped**: `consumerA.Scoped.Id == consumerB.Scoped.Id`. Karena masih dalam siklus `scope1`, engine mencari cache di dictionary lokal `scope1`. Begitu pindah ke `scope2`, instance baru dibuat.
- **Singleton**: Nilai `Id` Singleton identik di `Scope 1` dan `Scope 2` karena dicache pada level *Root Provider*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: *CallSite Engine*
Ketika `BuildServiceProvider()` dieksekusi, .NET tidak sekadar menyimpan koleksi dependensi. MEDI mengompilasi graf dependensi menjadi pohon panggilan (*CallSite Tree*):
- Engine membaca graf relasi dependensi untuk setiap tipe pendaftaran.
- Secara default, .NET menggunakan mekanisme **Dynamic Expression Compilation / ILEmit**:
  1. Resolusi awal menggunakan *reflection/runtime expression compilation* untuk menghemat waktu cold-start.
  2. Jika service diakses berulang kali (biasanya lebih dari 2 kali berturut-turut), .NET mengompilasi kode instansiasi menjadi IL dinamis (*Direct Dynamic Method Call*). Hasilnya, performa instansiasi setara dengan `new T()` manual.

#### Alokasi Memori & *Disposal Tracking*
Bagaimana kontainer menangani `IDisposable` atau `IAsyncDisposable`?
- **Root Tracking vs Scope Tracking**:
  Kontainer menyimpan referensi ke semua objek yang mengimplementasikan `IDisposable` dalam sebuah daftar pelacak (`List<IDisposable>`).
- **Scoped**: Objek Scoped yang dibuat dalam `IServiceScope` akan dilepaskan (*disposed*) segera ketika `scope.Dispose()` dipanggil. Memori objek kemudian dapat dipungut oleh Garbage Collector (GC).
- **Singleton**: Objek Singleton akan disimpan di *Root Scope*. Objek ini **tidak akan** dilepaskan oleh GC sampai seluruh aplikasi dimatikan dan Root Container di-dispose.
- **Bahaya Transient IDisposable**: Jika service *Transient* yang mengimplementasikan `IDisposable` di-resolve langsung dari **Root Provider** (bukan child scope), root provider akan menahan referensi objek tersebut ke dalam list internalnya. Akibatnya: **Memory Leak**, karena GC Root terus terhubung ke objek Transient tersebut sampai aplikasi terminate.

#### Trade-offs
| Lifetime | Kecepatan Resolusi | Beban Alokasi Memori | Kompleksitas Thread-Safety |
| :--- | :--- | :--- | :--- |
| **Transient** | Tinggi (tanpa lookup cache) | Tinggi (banyak alokasi objek baru di GC Gen 0) | Rendah (tidak dibagi antar thread) |
| **Scoped** | Sedang (cek cache per scope) | Terkontrol (dibersihkan di akhir scope) | Rendah jika diakses single-threaded request |
| **Singleton**| Sangat Cepat (pointer lookup) | Sangat Rendah (1 instance di heap) | **Tinggi** (wajib sinkronisasi thread) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Aktifkan `ValidateScopes`**: Selalu aktifkan `ValidateScopes` di lingkungan `Development` (aktif secara default di ASP.NET Core template). Fitur ini mendeteksi anomali masa hidup service sebelum aplikasi masuk ke mode *production*.
- **Desain Singleton sebagai Stateless atau Immutable**: Jika Singleton membutuhkan state internal, gunakan struktur data *lock-free* atau *thread-safe* seperti `ConcurrentDictionary<TKey, TValue>`.
- **Gunakan `IServiceScopeFactory` pada Background Tasks**: Pada `IHostedService` atau worker thread, selalu buat scope eksplisit menggunakan `IServiceScopeFactory.CreateScope()` sebelum menyelesaikan dependensi Scoped.

#### Don'ts
- **Hindari Captive Dependencies**: Kondisi saat service dengan lifetime yang lebih panjang mengonsumsi service dengan lifetime yang lebih pendek.
  *Contoh Dilarang:* Meng-inject `Scoped` service (seperti EF Core `DbContext`) ke dalam `Singleton` service. Akibatnya:
  1. Service Scoped berubah menjadi Singleton de facto (tidak pernah di-dispose).
  2. Akses konkurensi paralel memicu `InvalidOperationException: A second operation was started on this context instance before a previous operation completed`.
- **Jangan Menggunakan Service Locator Pattern**: Hindari meng-inject `IServiceProvider` ke dalam domain classes untuk memanggil `.GetService<T>()`. Ini menyembunyikan dependensi kelas, merusak *encapsulation*, dan mempersulit *unit testing*.

#### Edge Cases
- **Transient Memory Leak**: Memanggil `serviceProvider.GetRequiredService<MyTransientDisposable>()` dari Root Provider.
  *Solusi*: Jika butuh Transient Disposable, gunakan pola *Factory* (`Func<T>`) di mana kelas pemanggil memiliki kontrol penuh menggunakan blok `using`.
- **Resolusi Asinkron**: Instansiasi constructor di .NET bersifat sinkron. Hindari melakukan I/O blocking (seperti `.Result` atau `.Wait()`) di dalam constructor service yang didaftarkan ke DI. Gunakan pola *Asynchronous Initialization* terpisah.

1. **Simulasi Captive Dependency Trap**:
   - Buat satu service Singleton bernama `OrderProcessor` yang menerima `DatabaseContext` (daftarkan sebagai Scoped).
   - Jalankan aplikasi dengan flag `ValidateScopes = false` vs `ValidateScopes = true`. Amati kapan aplikasi melemparkan eksepsi: saat startup aplikasi atau saat method dijalankan?
2. **Implementasi Manual Memory Profiling**:
   - Daftarkan sebuah class `HeavyDisposableResource : IDisposable` sebagai `Transient` yang mengalokasikan array byte besar (`byte[1024 * 1024 * 10]`).
   - Buat loop sebanyak 100 kali yang me-resolve resource tersebut langsung dari `rootProvider` tanpa scope.
   - Amati pergerakan memori via Visual Studio Diagnostic Tools / `GC.GetTotalMemory()`. Buktikan bahwa memori tidak turun meskipun `GC.Collect()` dipanggil secara manual.
