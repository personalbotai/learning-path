## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, basis data relasional (RDBMS) dirancang dengan paradigma *Schema-on-Write*, di mana setiap data harus mematuhi skema tabular kaku (*Third Normal Form* / 3NF). Namun, evolusi arsitektur modern (seperti *event-driven systems*, integrasi *third-party API*, dan katalog produk multi-varian) menuntut fleksibilitas skema tanpa mengorbankan integritas transaksional ACID. SQL Modern menjembatani hal ini melalui fitur **Semi-Terstruktur (JSON in SQL)** yang distandarisasi pada ISO/IEC 9075:2016 (SQL:2016).

Implementasi JSON dalam SQL bervariasi antar-mesin basis data, namun PostgreSQL dan MySQL menjadi tolok ukur implementasi modern. Di PostgreSQL, terdapat perbedaan fundamental antara dua tipe data utama:

1. **`JSON` (Textual Storage):** 
   - Menyimpan representasi teks mentah persis seperti input (*whitespace*, urutan kunci, dan kunci duplikat dipertahankan).
   - *Parsing* sintaksis terjadi setiap kali data dibaca (*execution-time parsing*).
   - Efisien saat *insert*, tetapi sangat lambat untuk *query* dan traversal properti.

2. **`JSONB` (Deconstructed Binary Storage):**
   - Mendekonstruksi JSON string menjadi format biner terindeks saat proses *write*.
   - Menghapus *whitespace*, mengabaikan urutan kunci asli, dan menolak kunci duplikat (mengambil nilai terakhir).
   - Memiliki *overhead* CPU minor saat penulisan, tetapi menyediakan performa pencarian superior dan mendukung indexing struktural melalui **GIN (Generalized Inverted Index)**.

```
       JSON String Input: '{"b": 1, "a": 2}'
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
 [Type: JSON]          [Type: JSONB]
Textual Exact Copy     Parser & Binary Serialization
  - Simpan verbatim      - Sort keys: "a", "b"
  - Tanpa Indexing       - Hapus whitespace
                         - Kompilasi ke binary header & offsets
                         - Support GIN / B-Tree Index
```

### 2. Implementasi & Contoh Kasus Nyata

Contoh skenario berikut menggunakan dialek **PostgreSQL 14+**, mengimplementasikan tabel audit pesanan (*e-commerce order lifecycle*) yang menyimpan payload metadata transaksi yang fleksibel.

```sql
-- 1. Setup Skema Tabel dengan JSONB dan Validasi Constraint
CREATE TABLE customer_orders (
    order_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id INT NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    
    -- Memastikan metadata selalu berupa JSON Object, bukan Array atau Scalar
    CONSTRAINT chk_metadata_is_object CHECK (jsonb_typeof(metadata) = 'object')
);

-- 2. Inseri Data Kompleks (Objek bersarang, Array, dan Tipe Primitif)
INSERT INTO customer_orders (customer_id, total_amount, metadata) 
VALUES 
(
    101, 
    250000.00, 
    '{
        "source": "mobile_app",
        "device": {"os": "iOS", "version": "17.4"},
        "payment": {
            "gateway": "midtrans",
            "method": "qris",
            "settled": true
        },
        "tags": ["promo_ramadan", "first_order"]
    }'::jsonb
),
(
    102, 
    750000.00, 
    '{
        "source": "web_desktop",
        "device": {"os": "Linux", "browser": "Firefox"},
        "payment": {
            "gateway": "xendit",
            "method": "va_bca",
            "settled": false
        },
        "tags": ["corporate"]
    }'::jsonb
);

-- 3. Querying & Extraction
SELECT 
    order_id,
    -- Ekstraksi Field bersarang menghasilkan JSONB (->)
    metadata -> 'device' AS device_json,
    
    -- Ekstraksi Field bersarang menghasilkan TEXT (->>)
    metadata -> 'device' ->> 'os' AS device_os,
    
    -- Path traversal operator (#>>) untuk nested query tanpa chain operator
    metadata #>> '{payment, gateway}' AS payment_gateway,
    
    -- Boolean check ketersediaan kunci
    metadata ? 'tags' AS has_tags
FROM customer_orders
-- Filter menggunakan Containment Operator (@>)
-- Mencari dokumen yang mengandung subset JSON yang didefinisikan
WHERE metadata @> '{"payment": {"settled": true}}'::jsonb;

-- 4. Modifikasi Parsial Data JSONB (Tanpa Rewrite Seluruh Dokumen)
UPDATE customer_orders
SET metadata = jsonb_set(
    metadata, 
    '{payment,settled}', 
    'true'::jsonb, 
    false -- false = jangan insert jika key path tidak ditemukan
) || '{"updated_by": "webhook_worker"}'::jsonb -- Concat operator untuk merge data baru
WHERE metadata #>> '{payment, gateway}' = 'xendit';

-- 5. Transformasi Array JSONB ke Baris Relasional (Flattener)
SELECT 
    order_id,
    tag.value::text AS individual_tag
FROM customer_orders,
LATERAL jsonb_array_elements_text(metadata -> 'tags') AS tag;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Ketika data `JSONB` masuk, parser *engine* SQL membaca token secara leksikal dan membentuk pohon sintaksis abstrak (AST). Data kemudian diserialisasi ke dalam format biner yang terdiri dari:
1. **Header (32-bit integer):** Menyimpan metadata tipe data dan jumlah elemen.
2. **J-Entry Array:** Array metadata berukuran tetap untuk tiap elemen/kunci yang menyimpan *offset* memori dan flag tipe data (misal: *string*, *number*, *bool*, *null*).
3. **Variable-Length Data Storage:** Payload nilai asli yang disusun bersebelahan secara contiguous.

Karena adanya *J-Entry Array*, operasi penelusuran (`metadata -> 'device'`) tidak memindai teks karakter demi karakter ($O(N)$), melainkan menggunakan *binary search* pada daftar kunci yang telah diurutkan ($O(\log K)$ di mana $K$ adalah jumlah kunci dalam objek).

#### Alokasi Memori & TOAST (The Oversized-Attribute Storage Technique)
Di PostgreSQL, batas ukuran blok halaman data (*page*) adalah 8 KB. Jika dokumen JSONB membesar (melebihi ambang batas `TOAST_TUPLE_THRESHOLD`, biasanya 2 KB):
- Engine akan mencoba melakukan kompresi data (*algoritma PGLZ* atau *LZ4*).
- Jika masih melebihi batas, data JSONB dipindahkan keluar tabel utama ke tabel penyimpanan khusus (**TOAST Table**), menyisakan pointer 18-byte di baris utama.
- **Konsekuensi:** Pembacaan parsial (misal mengekstrak satu nilai integer dari dokumen JSONB sebesar 1 MB) tetap mengharuskan dekompresi dan rekonstruksi chunk TOAST di *buffer memory*, menyebabkan *overhead* I/O tersembunyi.

#### Mekanisme Indexing GIN (Generalized Inverted Index)
Ketika membuat index:
```sql
CREATE INDEX idx_orders_metadata ON customer_orders USING gin (metadata);
```
Mesin memecah dokumen JSONB menjadi pasangan `Path-Value` (*triples/tokens*). Jika dokumen berisi `{"payment": {"method": "qris"}}`, GIN index membuat posting list di mana token `'payment'.'method'.'qris'` memetakan langsung ke alamat fisik tuple (`TID`/`ctid`). Operator `@>` dapat langsung melompati pemindaian sekuensial (*Seq Scan*) dan melakukan *Bitmap Index Scan*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `jsonb_path_ops` untuk performa GIN maksimal:** Jika kueri dominan menggunakan operator containment `@>`, gunakan:
  ```sql
  CREATE INDEX idx_orders_fast ON customer_orders USING gin (metadata jsonb_path_ops);
  ```
  Ini hanya meng-hash keseluruhan path ekspresi, menghasilkan ukuran indeks hingga 60% lebih kecil dan pencarian lebih cepat dibandingkan default `jsonb_ops`.
- **Ekstrak field ke kolom komputasi/fungsional jika sering difilter:**
  ```sql
  CREATE INDEX idx_gateway ON customer_orders ((metadata #>> '{payment, gateway}'));
  ```
- **Terapkan validasi skema dasar** via CHECK constraints atau ekstensi `pg_jsonschema` untuk mencegah degenerasi data ("*Garbage in, Garbage out*").

#### Don'ts
- **Menghindari Foreign Key di dalam JSON:** Jangan menyimpan relasi kritis (seperti `user_id` atau `product_id`) murni di dalam JSONB jika integritas referensial dan kaskade (*CASCADE DELETE*) diperlukan. JSONB tidak mendukung deklarasi Foreign Key bawaan ke tabel lain.
- **Jangan gunakan JSONB untuk data tabel statis:** Normalisasi klasik (*3NF*) masih jauh lebih efisien dalam penggunaan memori dan kecepatan agregasi analitis (*column scans*) dibanding JSONB.
- **Hindari pola Write-Heavy Partial Update:** Melakukan pembaruan field kecil via `jsonb_set` pada baris TOAST besar akan memicu penulisan ulang seluruh dokumen di level WAL (Write-Ahead Logging), mengakibatkan *write amplification*.

#### Edge Cases
- **Perbedaan Tipe Data JSON vs SQL:** JSON hanya mengenal tipe numerik generik, sedangkan SQL membedakan `INTEGER`, `NUMERIC`, `DOUBLE PRECISION`. Konversi `metadata->>'amount'` menghasilkan `TEXT` yang harus di-*cast* secara eksplisit (`::numeric`) sebelum operasi aritmatika, jika tidak engine akan melempar error.
- **SQL NULL vs JSON Null:** 
  `SELECT '{"key": null}'::jsonb -> 'key';` menghasilkan JSON literal `null`.
  `SELECT '{"key": null}'::jsonb ->> 'key';` menghasilkan SQL `NULL`.
  Evaluasi boolean `IS NULL` akan menghasilkan nilai yang berbeda tergantung operator yang digunakan.

### 5. Tantangan Eksplorasi Mandiri

1. **Optimasi Ukuran Indeks:** Buat tabel dengan 100.000 baris data dummy berstruktur JSONB acak. Buat dua indeks berbeda: satu menggunakan default `jsonb_ops` dan satu lagi menggunakan `jsonb_path_ops`. Analisis perbedaan ukuran fisik keduanya via fungsi `pg_relation_size()`, serta bandingkan estimasi *cost* eksekusi kueri menggunakan `EXPLAIN ANALYZE`.
2. **Migrasi Pola EAV (Entity-Attribute-Value):** Ambil satu model data katalog produk dinamis berbasis EAV konvensional (`entity_id`, `attribute_name`, `attribute_value`). Tulis skrip migrasi SQL untuk mengubah relasi baris tersebut menjadi satu baris ber-skema `JSONB` per entitas, lalu ukur perbandingan latensi pemanggilan data produk beserta seluruh atributnya.
3. **Ekstraksi SQL/JSON Standard (SQL:2016):** Uji coba fungsionalitas fungsi standar ANSI seperti `JSON_TABLE()` (tersedia di MySQL 8.0 dan PostgreSQL 15+) untuk memetakan dokumen JSON bertingkat secara dinamis ke dalam representasi tabel virtual tanpa merusak relasi skema.
