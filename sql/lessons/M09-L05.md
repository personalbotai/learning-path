## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur *database management system* (RDBMS), performa sistem dibatasi oleh tiga sumber daya utama: I/O disk, CPU, dan *lock contention*. *Slow Query Log* adalah subsistem telemetri bawaan engine database yang mencatat *execution profile* dari kueri-kueri yang melampaui ambang batas latensi (*execution duration threshold*) atau tidak memanfaatkan indeks secara optimal.

Fungsi utama *Slow Query Log* bukan sekadar melacak "kueri yang berjalan lambat", melainkan menyediakan data agregat observabilitas untuk mendiagnosis degradasi performa:
1. **Pendeteksian Regresi Indeks**: Mengidentifikasi kueri yang beralih dari *index scan* ke *full table scan* akibat bertambahnya kardinalitas data.
2. **Lock Wait vs. CPU Time**: Membedakan apakah kueri lambat karena beban komputasi/bacaan halaman data (I/O) atau tertahan oleh *row-level locks* / *table metadata locks*.
3. **Capacity Planning**: Memberikan gambaran beban *workload* terhadap alokasi memori (*buffer pool* / *shared buffers*).

Secara arsitektur, database engine (seperti MySQL InnoDB atau PostgreSQL) menyisipkan instrumen timer presisi tinggi di siklus hidup eksekusi kueri:

```
[Client] 
   │ SQL Query
   ▼
[Parser & Planner/Optimizer]
   │ Execution Plan
   ▼
[Execution Engine] ◄── Timer Start (T_start = clock_gettime(CLOCK_MONOTONIC))
   │ (Iterasi Baris, Lock Acquisition, Disk/Buffer Read)
   ▼
[Execution Complete] ◄── Timer End (T_end)
   │ Elapsed = T_end - T_start
   ▼
[Evaluasi Threshold] ── (Elapsed > Threshold?) ──► YES ──► [Write to Slow Query Sink (File/Table)]
                                                    │
                                                    NO ──► [Discard Profiling Record]
```

Database engine modern memisahkan perhitungan metrik menjadi dua fase: durasi total kueri dan durasi perolehan kunci (*lock acquisition time*). Pemisahan ini krusial agar DBA dan Software Engineer tidak salah mengoptimasi kueri yang sebenarnya ringan tetapi terblokir oleh transaksi konkurensi lain yang berjalan lama (*long-running transaction*).

### 2. Implementasi & Contoh Kasus Nyata

Implementasi *Slow Query Logging* bervariasi bergantung pada engine database. Di bawah ini disajikan konfigurasi dan ekstraksi analitik untuk dua engine dominan: **MySQL/Percona (Slow Query Log native)** dan **PostgreSQL (`log_min_duration_statement` + `pg_stat_statements`)**.

#### A. MySQL / MariaDB (Runtime Configuration & Analysis)

```sql
-- 1. Mengaktifkan Slow Query Log secara dinamis di level global
SET GLOBAL slow_query_log = 'ON';

-- Tentukan lokasi file log (atau gunakan nilai default)
SET GLOBAL slow_query_log_file = '/var/log/mysql/mysql-slow.log';

-- Atur ambang batas dalam detik (mendukung presisi mikrodetik: 0.5 = 500ms)
SET GLOBAL long_query_time = 0.200000; -- 200 ms

-- Catat kueri yang tidak menggunakan indeks, terlepas dari durasi eksekusinya
SET GLOBAL log_queries_not_using_indexes = 'ON';

-- Batasi frekuensi log kueri non-indeks per menit agar disk I/O tidak jenuh
SET GLOBAL log_throttle_queries_not_using_indexes = 60;

-- Catat eksekusi admin commands (misal: OPTIMIZE, ANALYZE)
SET GLOBAL log_slow_admin_statements = 'ON';
```

Format rekaman yang dihasilkan pada `/var/log/mysql/mysql-slow.log`:
```text
# Time: 2023-10-27T08:14:02.123456Z
# User@Host: app_user[app] @ [10.0.1.25]  Id: 10423
# Query_time: 1.450231  Lock_time: 0.000102 Rows_sent: 10  Rows_examined: 2450000
SET timestamp=1698394442;
SELECT customer_id, SUM(amount) 
FROM orders 
WHERE created_at BETWEEN '2023-01-01' AND '2023-06-30' 
GROUP BY customer_id 
ORDER BY SUM(amount) DESC 
LIMIT 10;
```
*Analisis Metrik Penting:*
* `Query_time: 1.450231`: Kueri berjalan selama 1,45 detik.
* `Rows_sent: 10`: Hasil yang dikembalikan hanya 10 baris.
* `Rows_examined: 2450000`: Engine harus memindai 2,45 juta baris. Rasio `Rows_examined / Rows_sent` yang sangat tinggi (245.000 : 1) membuktikan ketiadaan *composite index* pada `(created_at, customer_id, amount)`.

#### B. PostgreSQL (Statistik Agregat Menggunakan `pg_stat_statements`)

PostgreSQL lebih mengedepankan pendekatan *in-memory shared ring buffer* via extension bawaan untuk observabilitas kueri, menghindari overhead penulisan berkas teks secara linear.

```sql
-- Tambahkan pg_stat_statements ke postgresql.conf (memerlukan restart server):
-- shared_preload_libraries = 'pg_stat_statements'
-- pg_stat_statements.track = top

-- Registrasi ekstensi di database target
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Atur logging teks berbasis ambang batas (alternatif slow log)
ALTER SYSTEM SET log_min_duration_statement = 250; -- Catat kueri > 250ms
SELECT pg_reload_conf();

-- Mengambil Top 5 kueri dengan akumulasi waktu komputasi tertinggi
SELECT 
    queryid,
    substring(query, 1, 60) AS short_query,
    calls,
    round(total_exec_time::numeric, 2) AS total_time_ms,
    round(mean_exec_time::numeric, 2) AS avg_time_ms,
    rows,
    shared_blks_hit,
    shared_blks_read
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Clock System Calls**: Engine database memanggil *monotonic clock* OS (seperti `clock_gettime(CLOCK_MONOTONIC)` di Linux) saat state kueri memasuki tahap eksekusi, tepat setelah parsing dan optimalisasi selesai. Penggunaan *monotonic clock* wajib guna mencegah anomali waktu jika terjadi penyesuaian NTP (*time drift*).
2. **Post-Execution Evaluation**: Ketika cursor execution loop selesai atau iterator mencapai EOF (End-of-File), engine membaca kembali *monotonic clock*.
   $$\Delta t = T_{end} - T_{start}$$
   Jika $\Delta t > \text{threshold}$, *record* slow log disiapkan ke thread-local buffer sebelum disalurkan ke subsistem I/O log.

#### Alokasi Memori & Log I/O Subsistem
- Pada **MySQL**, penulisan log ke file (`FILE` target) dilakukan secara sinkron oleh thread yang menjalankan kueri tersebut menggunakan operasi *unbuffered/buffered sequential write*. Jika target diubah ke `TABLE` (`mysql.slow_log`), engine melakukan *internal insert* ke tabel berbasis CSV atau MyISAM/InnoDB, yang mengonsumsi CPU dan alokasi memori tambahan.
- Pada **PostgreSQL (`pg_stat_statements`)**, informasi dicatat ke dalam *Shared Memory Ring Buffer* berukuran tetap (`pg_stat_statements.max`). Hash dari string kueri yang dinormalisasi digunakan sebagai *lookup key*. Operasi ini menggunakan *lightweight spinlocks* (`LWLock`) untuk meminimalkan *thread contention*.

#### Trade-offs
| Pendekatan | Kelebihan | Kelemahan |
| :--- | :--- | :--- |
| **Direct File Logging** (MySQL `slow_query_log`) | Menyimpan parameter riil secara utuh; mempermudah *reproduce* bug. | Disk I/O blocking; ukuran log dapat membengkak drastis (*uncontrolled disk space usage*). |
| **In-Memory Tracking** (Postgres `pg_stat_statements`) | *Zero/minimal disk write overhead*; normalisasi query otomatis; performa tinggi. | Parameter query diabstraksikan (`$1`, `$2`); detail variasi argumen hilang. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Aktifkan Microsecond Precision**: Gunakan nilai sub-detik untuk target latensi sistem OLTP, idealnya `0.1s` (100ms) hingga `0.5s` (500ms).
- **Gunakan Log Aggregator & Parser**: Jangan membaca raw file log secara langsung di server produksi. Manfaatkan tool seperti `pt-query-digest` (Percona Toolkit) atau *agent collector* (Datadog, Prometheus mysqld_exporter) untuk mengelompokkan kueri berdasarkan *fingerprint*.
- **Rotasikan Log File**: Pasangkan implementasi slow log berbasis file dengan utilitas `logrotate` untuk mencegah kehabisan kapasitas disk (*disk saturation*).

#### Don'ts
- **Hindari Mode `TABLE` pada MySQL di Traffic Tinggi**: Menyimpan slow log ke tabel bawaan `mysql.slow_log` menghasilkan *table locks* dan memicu efek bola salju (*cascading performance failure*). Gunakan format `FILE`.
- **Jangan Biarkan `log_queries_not_using_indexes` Aktif Tanpa Throttle**: Tabel kecil (misal: tabel referensi/konfigurasi berisi 5 baris) secara alami lebih cepat dibaca menggunakan *full table scan*. Kueri ini akan membanjiri log jika throttling tidak diaktifkan.
- **Jangan Matikan Slow Log di Lingkungan Produksi**: Persepsi bahwa slow log memperlambat database secara masif adalah keliru jika dikonfigurasi dengan batas ambang yang rasional. Peniadaan slow log membuat sistem kehilangan visibilitas performa.

#### Edge Cases & Pitfalls
- **The Lock Contention Illusion**: Kueri dengan metrik `Query_time: 15s` dan `Lock_time: 14.9s` sebenarnya selesai diproses dalam 0.1 detik. Mengoptimalkan indeks pada kueri ini tidak akan menyelesaikan masalah; akar masalahnya adalah transaksi lain yang menahan lock pada baris/tabel target.
- **Sensitive Data Leakage (PII)**: Raw slow query logs mencatat nilai literal (`WHERE password_hash = '...'` atau `WHERE ssn = '...'`). Berkas ini harus diatur izin aksesnya (`chmod 600`) atau engine harus dikonfigurasi untuk menyamarkan nilai literal jika mendukungnya (*query parameter redaction*).

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi CPU-Bound vs Lock-Bound**: 
   Jalankan sebuah transaksi yang membuka `BEGIN; UPDATE accounts SET balance = balance WHERE id = 1;` tanpa melakukan `COMMIT`. Pada terminal berbeda, jalankan transaksi pembaruan data yang sama dengan batas `long_query_time` rendah. Periksa rekaman log: bagaimana nilai `Query_time` dan `Lock_time` mencerminkan insiden *blocking* ini?
2. **Deep Profiling dengan `pt-query-digest`**:
   Kumpulkan sample file slow log sebesar 10MB dari database lokal Anda. Gunakan utilitas `pt-query-digest` untuk menghasilkan laporan distribusi *Ranked by 95% response time*, dan identifikasi *Variance-to-Mean Ratio (VMR)* dari kueri yang paling bermasalah.
3. **Analisis In-Memory Eviction PostgreSQL**:
   Pada PostgreSQL, set `pg_stat_statements.max = 100`. Generate 200 variasi kueri dinamis yang berbeda. Amati bagaimana engine melakukan evisi kueri terlama (*de-allocations*) melalui metrik internal view `pg_stat_statements_info`.
