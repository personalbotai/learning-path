## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Transaksi adalah unit kerja logis (*logical unit of work*) yang mengubah status sistem dari satu keadaan konsisten ke keadaan konsisten lainnya. Di dalam arsitektur basis data relasional (RDBMS), integritas transaksi dijamin oleh empat pilar: **ACID**.

```
+-------------------------------------------------------------------------+
|                              TRANSAKSI ACID                             |
+-------------------+------------------+------------------+---------------+
|     Atomicity     |   Consistency    |    Isolation     |  Durability   |
|   All-or-Nothing  | State Validity   | Concurrency Ctrl | Non-volatile  |
|     (WAL / Undo)  | (Constraints/FK) |  (MVCC / Locks)  |  (WAL / Redo) |
+-------------------+------------------+------------------+---------------+
```

#### Komponen Dasar ACID
1. **Atomicity (Semua atau Tidak Sama Sekali):** Seluruh mutasi data dalam transaksi dieksekusi tuntas atau dibatalkan seutuhnya (*rolled back*). Di balik layar, ini ditangani menggunakan *Undo Logs* atau *Write-Ahead Logging* (WAL).
2. **Consistency (Konsistensi):** Transaksi hanya membawa database dari satu kondisi valid ke kondisi valid lainnya sesuai *invariants*, aturan integritas (*Foreign Keys, Unique, Check Constraints*), dan logika bisnis sistem.
3. **Isolation (Isolasi):** Eksekusi transaksi konkuren tidak boleh saling menginterferensi. Standar ANSI SQL mendefinisikan 4 level isolasi:
   - *Read Uncommitted* (rentan *Dirty Read*, *Non-repeatable Read*, *Phantom Read*)
   - *Read Committed* (mencegah *Dirty Read*)
   - *Repeatable Read* (mencegah *Dirty Read* & *Non-repeatable Read*)
   - *Serializable* (mencegah semua anomali konkurensi melalui *Two-Phase Locking (2PL)* atau *Serializable Snapshot Isolation (SSI)*)
4. **Durability (Ketahanan):** Sekali transaksi dinyatakan *commit*, perubahannya bersifat permanen dan tahan terhadap crash/kegagalan daya. Diimplementasikan via penulisan *Redo Logs* ke disk secara sinkron (`fsync`).

---

#### Transaksi Lokal vs. Transaksi Terdistribusi
Pada *Single-node RDBMS*, koordinasi ACID ditangani oleh sebuah engine monolitik melalui *Lock Manager* dan *Log Manager*. Namun, ketika data dipecah ke beberapa node (*Sharding*, arsitektur *Microservices*, atau *Multi-Datacenter*), batas transaksi lokal terlampaui.

```
       [ Client / App Coordinator ]
              /            \
    Step 1: PREPARE      Step 1: PREPARE
            /                \
           v                  v
  [ Node A (Postgres) ]   [ Node B (Postgres) ]
     (Locks Acquired,        (Locks Acquired,
      WAL Flushed)            WAL Flushed)
            \                /
    Step 2: COMMIT       Step 2: COMMIT
             \              /
              v            v
           [ Consensus Selesai ]
```

Masalah utama dalam transaksi terdistribusi dirumuskan oleh **CAP Theorem** (Consistency, Availability, Partition Tolerance) dan **PACELC**:
- Tidak mungkin menjamin *Strict Consistency* dan *100% High Availability* ketika terjadi *Network Partition*.
- Dua pendekatan arsitektural utama untuk menangani konsistensi terdistribusi:
  1. **Two-Phase Commit (2PC):** Protokol sinkronik terdistribusi berbasis konsensus atomik. Koordinatorku bertanya apakah semua node siap (*Prepare Phase*), lalu menginstruksikan finalisasi (*Commit/Abort Phase*). Kelemahannya: *blocking protocol*, rentan terhadap kegagalan koordinator, dan *throughput* rendah.
  2. **Saga Pattern (Compensating Transactions):** Pendekatan asinkronik berbasis arsitektur *Event-Driven* atau orkestrasi, di mana setiap *sub-transaksi lokal* langsung di-*commit*. Jika sebuah langkah gagal, dijalankan transaksi kompensasi (*compensating action*) ke arah sebaliknya (menerapkan prinsip *Eventual Consistency* / BASE).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh praktis SQL:
1. Penanganan isolasi level tinggi pada transaksi lokal.
2. Mekanisme native **Two-Phase Commit (2PC)** menggunakan fitur `PREPARED TRANSACTION` yang didukung oleh mesin database seperti PostgreSQL.

#### Kasus A: Isolasi Ketat pada Transaksi Finansial Lokal
Menghindari anomali *Write Skew* atau *Race Condition* saat transfer saldo.

```sql
-- Node Database: Ledger
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 1. Validasi saldo pengirim dengan lock selektif (Pessimistic Locking)
SELECT balance 
FROM accounts 
WHERE account_id = 'ACC-001' 
FOR UPDATE;

-- 2. Kurangi saldo pengirim
UPDATE accounts 
SET balance = balance - 500000,
    updated_at = CURRENT_TIMESTAMP
WHERE account_id = 'ACC-001' AND balance >= 500000;

-- Pastikan operasi sebelumnya mengubah baris (rowcount = 1)
-- Jika balance tidak cukup, aplikasi melempar ROLLBACK;

-- 3. Tambahkan saldo penerima
UPDATE accounts 
SET balance = balance + 500000,
    updated_at = CURRENT_TIMESTAMP
WHERE account_id = 'ACC-002';

-- 4. Catat riwayat mutasi
INSERT INTO audit_logs (sender_id, receiver_id, amount, created_at)
VALUES ('ACC-001', 'ACC-002', 500000, CURRENT_TIMESTAMP);

COMMIT;
```

#### Kasus B: 2-Phase Commit (2PC) Antar Database secara Manual
Skenario: Koordinasi transfer dana antara Node Core Banking (`Node_A`) dan Node Dompet Digital/Wallet (`Node_B`).

```sql
-- ==========================================
-- PHASE 1: PREPARE PHASE
-- ==========================================

-- Eksekusi pada Node_A (Core Banking Engine)
BEGIN;
UPDATE core_accounts 
SET balance = balance - 100000 
WHERE account_id = 'USER-A' AND balance >= 100000;

-- Alih-alih COMMIT biasa, gunakan PREPARE TRANSACTION dengan Global Transaction ID (GTID)
PREPARE TRANSACTION 'gtid_tx_transfer_20260331_001_node_a';
-- Pada titik ini, Node_A telah menulis WAL ke disk, mengunci row terkait,
-- dan MENJAMIN bisa commit kapan saja, bahkan setelah crash.

-- Eksekusi pada Node_B (Wallet Engine)
BEGIN;
UPDATE wallet_balances 
SET balance = balance + 100000 
WHERE wallet_id = 'USER-B';

PREPARE TRANSACTION 'gtid_tx_transfer_20260331_001_node_b';
-- Node_B juga menjamin kesiapan untuk commit.

-- ==========================================
-- PHASE 2: COMMIT PHASE (Jika kedua PREPARE sukses)
-- Koordinator mengirim sinyal finalisasi:
-- ==========================================

-- Eksekusi di Node_A
COMMIT PREPARED 'gtid_tx_transfer_20260331_001_node_a';

-- Eksekusi di Node_B
COMMIT PREPARED 'gtid_tx_transfer_20260331_001_node_b';

-- ==========================================
-- SKENARIO KEGAGALAN: JIKA SALAH SATU GAGAL DI PHASE 1
-- Koordinator wajib membatalkan semua node yang sudah berstatus PREPARE:
-- ==========================================
-- ROLLBACK PREPARED 'gtid_tx_transfer_20260331_001_node_a';
-- ROLLBACK PREPARED 'gtid_tx_transfer_20260331_001_node_b';
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: WAL & Two-Phase Locking (2PL)
- **Write-Ahead Logging (WAL):** Database tidak langsung menulis data block ke tabel di disk saat `COMMIT`. RDBMS menulis data ke struktur linear append-only (WAL) dan memanggil sistem operasi `fsync()`. Data block di memori (*dirty pages*) baru di-*flush* ke data file utama secara asinkron saat proses *Checkpointer*.
- **2PC State Engine:** Saat perintah `PREPARE TRANSACTION` dieksekusi:
  1. Node melepaskan status transaksi dari koneksi client aktif (*detaching session*).
  2. Semua state transaksi (Locks, LSN - *Log Sequence Number*, Modifikasi Tuple) disimpan secara persisten ke disk (pada Postgres: direktori `pg_twophase`).
  3. Kunci data (*Exclusive Locks*) **tetap ditahan** dan tidak dilepas sampai ada perintah eksplisit `COMMIT PREPARED` atau `ROLLBACK PREPARED`.

#### Alokasi Memori & Resource
- **Lock Manager:** Tiap baris data yang diubah dalam transaksi dialokasikan pada tabel *in-memory hash lock*. Pada isolasi tinggi atau 2PC berdurasi panjang, hash table ini membesar, memicu eskalasi lock (*Lock Escalation*) atau *lock contention* tinggi.
- **MVCC (Multi-Version Concurrency Control):** Pada database seperti PostgreSQL, operasi `UPDATE` tidak menimpa data di tempat. Sistem membuat *tuple* baru dengan metadata header `xmin` (ID transaksi pembuat) dan menandai tuple lama dengan `xmax` (ID transaksi penghapus/pengubah). Buffer Pool menyimpan halaman-halaman ini hingga proses *Garbage Collection* (misalnya `VACUUM`) membersihkannya.

#### Trade-offs: 2PC vs. Saga
| Metrik | Two-Phase Commit (2PC) | Saga Pattern (BASE) |
| :--- | :--- | :--- |
| **Konsistensi** | *Immediate / Strong Consistency* | *Eventual Consistency* |
| **Latensi** | Tinggi (terhambat proses *sync I/O* + latensi jaringan) | Rendah (transaksi lokal independen) |
| **Availability** | Rendah (kegagalan 1 node memblokir transaksi lain) | Tinggi (kegagalan ditangani secara kompensasi) |
| **Locking Isolation** | Menahan lock fisik lintas node secara serentak | Tidak ada *distributed lock*, risiko isolasi bocor |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Jaga Durasi Transaksi Sesingkat Mungkin:** Hindari memproses manipulasi string berat, komputasi CPU, atau operasi I/O jaringan di antara `BEGIN` dan `COMMIT`.
- **Terapkan Urutan Akses Lock yang Deterministik:** Saat memperbarui beberapa baris sekaligus, urutkan selalu ID entitas (misal: `WHERE id IN (...) ORDER BY id ASC`) untuk mencegah *Deadlock* antar transaksi paralel.
- **Implementasikan Idempotency Key:** Pada transaksi terdistribusi atau Saga, setiap request mutasi wajib menyertakan UUID unik dari *client* guna menghindari eksekusi ganda saat *network retry*.

#### Don'ts
- **JANGAN Memanggil External Network Call (HTTP/gRPC/Third-party) di Dalam Blok Transaksi SQL:**
  ```sql
  -- ANTI-PATTERN:
  BEGIN;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
  -- Aplikasi memanggil API Stripe / Midtrans (memakan waktu 2 detik)
  -- LOCK tertahan selama 2 detik penuh, mematikan throughput throughput database!
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  COMMIT;
  ```
- **Jangan Biarkan *Orphan Prepared Transactions*:** Jika koordinator 2PC mati mendadak setelah fase *PREPARE*, transaksi berstatus *in-doubt* akan mengunci data selamanya, mencegah auto-vacuum dan memicu *bloat* tabel secara masif.

#### Edge Cases
- **Heuristic Completion pada 2PC:** Ketika node partisipan terputus koneksi dari koordinator untuk waktu yang sangat lama, partisipan dapat secara sepihak memutuskan untuk *Rollback* atau *Commit* (Heuristic Decision). Ini melanggar konsistensi data (*Split-Brain State*) dan membutuhkan intervensi data audit manual.
- **Phantom Reads pada MVCC:** Mesin database dengan MVCC default (`Read Committed`) tetap dapat membaca kemunculan baris baru yang disisipkan oleh transaksi lain di tengah eksekusinya sendiri. Gunakan `SERIALIZABLE` jika kalkulasi bergantung pada himpunan data dinamis (*range queries*).
