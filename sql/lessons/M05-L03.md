## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem SQL, `ALTER` dan `DROP` adalah bagian dari **Data Definition Language (DDL)**. Berbeda dengan DML (`INSERT`, `UPDATE`, `DELETE`) yang memanipulasi *data* di dalam tabel, DDL memanipulasi **Data Dictionary** atau **System Catalog**—yaitu metadata yang mendefinisikan struktur database itu sendiri.

Di lingkungan produksi yang dinamis, skema database tidak pernah statis. Kebutuhan bisnis yang berubah menuntut penambahan kolom baru, modifikasi tipe data, atau penghapusan entitas usang. Tantangan arsitektural utama dari modifikasi skema bukanlah sintaksnya, melainkan **Concurrency Control** dan **Availability**. 

Secara historis, operasi DDL akan mengunci seluruh tabel secara eksklusif (*Exclusive Table Lock*), memblokir semua operasi baca dan tulis. Namun, RDBMS modern (seperti PostgreSQL dan MySQL/InnoDB) telah mengimplementasikan **Online DDL**, yang memungkinkan modifikasi skema dilakukan di latar belakang dengan interupsi minimal terhadap *traffic* produksi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skrip migrasi skema yang umum digunakan di industri, mencakup penambahan, modifikasi, dan penghapusan objek.

```sql
-- ==========================================
-- 1. ALTER TABLE: Menambah Kolom Baru
-- ==========================================
-- Praktik terbaik: Gunakan DEFAULT yang konstan jika memungkinkan
ALTER TABLE users 
ADD COLUMN is_active BOOLEAN DEFAULT TRUE NOT NULL;

-- ==========================================
-- 2. ALTER TABLE: Memodifikasi Tipe Data & Constraint
-- ==========================================
-- PostgreSQL: Menggunakan klausa USING untuk konversi data eksplisit
ALTER TABLE users 
ALTER COLUMN phone_number TYPE VARCHAR(20) USING phone_number::VARCHAR,
ALTER COLUMN phone_number SET NOT NULL;

-- MySQL: Menggunakan klausa MODIFY
-- ALTER TABLE users MODIFY COLUMN phone_number VARCHAR(20) NOT NULL;

-- ==========================================
-- 3. ALTER TABLE: Menambah & Menghapus Index/Constraint
-- ==========================================
-- Menambah constraint unik
ALTER TABLE users 
ADD CONSTRAINT uq_users_email UNIQUE (email);

-- Menghapus constraint
ALTER TABLE users 
DROP CONSTRAINT uq_users_email;

-- ==========================================
-- 4. DROP: Menghapus Objek Database
-- ==========================================
-- Menghapus kolom (Hati-hati: Data di kolom ini akan hilang permanen)
ALTER TABLE users 
DROP COLUMN IF EXISTS phone_number;

-- Menghapus tabel secara aman
-- CASCADE (PostgreSQL) akan otomatis menghapus objek yang bergantung pada tabel ini (misal: Views)
DROP TABLE IF EXISTS old_audit_logs CASCADE;
```

**Penjelasan Implementasi:**
- `IF EXISTS`: Sangat krusial dalam skrip migrasi otomatis (CI/CD) agar eksekusi tidak gagal (*crash*) jika objek sudah tidak ada.
- `CASCADE`: Digunakan saat melakukan `DROP` untuk menangani *dependency*. Jika tabel `A` direferensikan oleh View `B`, melakukan `DROP TABLE A` akan gagal kecuali menggunakan `CASCADE` (yang juga akan menghapus View `B`).

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Saat perintah `ALTER` dieksekusi, RDBMS harus memperbarui *System Catalog*. Ada dua algoritma utama yang digunakan oleh *storage engine* (khususnya InnoDB di MySQL):
  1. **ALGORITHM=COPY**: Mesin membuat tabel sementara (*temp table*) dengan skema baru, menyalin semua data baris-demi-baris dari tabel lama, membangun ulang index, menukar (*swap*) nama tabel, lalu menghapus tabel lama. Ini memblokir operasi `WRITE`.
  2. **ALGORITHM=INPLACE**: Modifikasi dilakukan langsung pada file data asli tanpa menyalin seluruh tabel. Operasi DML (baca/tulis) tetap bisa berjalan bersamaan. Perubahan data selama DDL berlangsung dicatat dalam *Online Log* dan diaplikasikan di akhir proses.

- **Alokasi Memori / Resource**: 
  Operasi `COPY` sangat mahal. Jika Anda melakukan `ALTER` pada tabel berukuran 100GB, disk Anda memerlukan tambahan ruang kosong sebesar 100GB selama proses berlangsung. Selain itu, *Buffer Pool* (RAM) akan terbebani oleh proses pembacaan dan penulisan ulang data secara masif, yang dapat menggusur *cache* data panas (*hot data*).

- **Trade-offs**: 
  PostgreSQL menangani DDL secara transaksional berkat arsitektur MVCC (*Multi-Version Concurrency Control*). Anda bisa melakukan `ROLLBACK` pada perintah `ALTER` atau `DROP`. Sebaliknya, di MySQL, perintah DDL akan memicu **Implicit Commit**, artinya transaksi yang sedang berjalan akan otomatis di-commit dan DDL tidak bisa di-rollback.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Tools Migrasi**: Selalu gunakan *schema migration tools* seperti Flyway, Liquibase, atau Prisma Migrate untuk melacak versi skema.
  - **Pahami Lock yang Terjadi**: Sebelum menjalankan `ALTER` di tabel raksasa, cek dokumentasi RDBMS apakah operasi tersebut membutuhkan *Table Rewrite* atau hanya *Metadata Change*.
  - **Gunakan `CONCURRENTLY` untuk Index**: Di PostgreSQL, gunakan `CREATE INDEX CONCURRENTLY` agar pembuatan index tidak memblokir operasi *write*.

- **Don'ts**:
  - **Jangan Menjalankan DDL di Jam Sibuk**: Meskipun *Online DDL* didukung, proses ini memakan I/O disk dan CPU yang tinggi. Lakukan di *maintenance window* atau jam sepi.
  - **Jangan Gunakan `DROP ... CASCADE` Sembarangan**: Anda bisa secara tidak sengaja menghapus puluhan *Views* atau *Foreign Keys* krusial tanpa menyadarinya.
  - **Jangan Menambah Kolom dengan Default Dinamis**: Menambahkan kolom dengan `DEFAULT gen_random_uuid()` atau fungsi dinamis lainnya pada tabel besar akan memaksa *Table Rewrite* di hampir semua RDBMS.

- **Edge Cases**:
  - **Metadata Lock Contention**: Jika ada transaksi *Long-Running Query* (misal: *report* yang berjalan 2 jam) yang sedang membaca tabel `A`, dan Anda menjalankan `ALTER TABLE A`, perintah `ALTER` akan tertahan menunggu *Metadata Lock*. Parahnya, antrean ini akan memblokir semua *query* baru ke tabel `A` di belakangnya, menyebabkan *downtime* instan pada aplikasi.
