## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Perintah `INSERT` adalah bagian fundamental dari *Data Manipulation Language* (DML) dalam SQL yang bertanggung jawab untuk menambahkan *record* (baris) baru ke dalam sebuah tabel. Secara konseptual, `INSERT` bukan sekadar operasi penulisan data sederhana, melainkan sebuah transaksi kompleks yang berinteraksi dengan berbagai komponen *database engine*.

Ketika perintah `INSERT` dijalankan, *database* harus memastikan kepatuhan terhadap prinsip ACID (*Atomicity, Consistency, Isolation, Durability*). Ini berarti *database engine* akan melakukan validasi tipe data, memeriksa *constraints* (seperti `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`), dan mengeksekusi *triggers* (jika ada) sebelum data benar-benar disimpan. Jika salah satu validasi ini gagal, seluruh operasi `INSERT` akan di-*rollback* (dibatalkan) untuk menjaga konsistensi data.

Dalam arsitektur modern, operasi `INSERT` sangat dipengaruhi oleh desain skema. Tabel dengan banyak indeks (*indexes*) akan mengalami penalti performa saat `INSERT` karena *database* tidak hanya menulis data ke tabel utama (biasanya berupa *Clustered Index* atau *Heap*), tetapi juga harus memperbarui struktur data (seperti B-Tree) untuk setiap *Non-Clustered Index* yang terkait.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah berbagai variasi implementasi `INSERT` dari yang paling dasar hingga teknik tingkat lanjut yang sering digunakan di industri.

```sql
-- 1. Standard Single-Row Insert
-- Selalu sebutkan nama kolom secara eksplisit untuk mencegah error jika skema tabel berubah.
INSERT INTO users (username, email, status, created_at)
VALUES ('johndoe', 'john@example.com', 'active', CURRENT_TIMESTAMP);

-- 2. Bulk Insert (Multi-row)
-- Jauh lebih efisien daripada melakukan single insert berulang kali (mengurangi network round-trips).
INSERT INTO products (sku, name, price, stock)
VALUES 
    ('SKU-001', 'Mechanical Keyboard', 150.00, 50),
    ('SKU-002', 'Wireless Mouse', 45.50, 120),
    ('SKU-003', 'USB-C Hub', 30.00, 200);

-- 3. INSERT INTO ... SELECT (Data Migration / Aggregation)
-- Memasukkan data dari hasil query lain. Sangat berguna untuk proses ETL atau archiving.
INSERT INTO inactive_users_archive (user_id, username, archived_at)
SELECT id, username, CURRENT_TIMESTAMP
FROM users
WHERE last_login < CURRENT_DATE - INTERVAL '1 year';

-- 4. UPSERT (Insert or Update) - Sintaks PostgreSQL (ON CONFLICT) / MySQL (ON DUPLICATE KEY)
-- Menangani konflik jika data dengan Unique/Primary Key yang sama sudah ada.
INSERT INTO daily_page_views (page_url, view_count, last_viewed)
VALUES ('/home', 1, CURRENT_TIMESTAMP)
ON CONFLICT (page_url) 
DO UPDATE SET 
    view_count = daily_page_views.view_count + 1,
    last_viewed = EXCLUDED.last_viewed;

-- 5. INSERT dengan RETURNING (PostgreSQL / SQLite / Oracle)
-- Mengembalikan data yang baru saja di-insert, sangat berguna untuk mendapatkan Auto-Increment ID.
INSERT INTO orders (user_id, total_amount)
VALUES (105, 250.00)
RETURNING id, created_at;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  1. **Parser & Planner**: *Query* diurai untuk memvalidasi sintaks dan hak akses (*permissions*).
  2. **Constraint Checking**: *Execution engine* memverifikasi *constraints*. Untuk `FOREIGN KEY`, *engine* harus melakukan *lookup* (pencarian) ke tabel referensi.
  3. **Index Maintenance**: *Engine* menavigasi struktur B-Tree dari setiap indeks untuk menyisipkan *pointer* atau data baru.
- **Alokasi Memori / Resource**: 
  Data tidak langsung ditulis ke *hard drive*. *Database* menulis perubahan ke memori utama yang disebut **Buffer Pool** (atau *Shared Buffers*). Secara bersamaan, operasi ini dicatat secara sekuensial ke dalam **Write-Ahead Log (WAL)** atau *Redo Log*. WAL memastikan *Durability*; jika server mati mendadak, data di WAL akan di-*replay* saat *restart* untuk memulihkan data yang ada di *Buffer Pool* namun belum sempat di-*flush* ke *disk* (*checkpointing*).
- **Trade-offs**: 
  - **Page Splits**: Jika data dimasukkan ke dalam halaman memori (*page*) B-Tree yang sudah penuh, *database* harus melakukan *page split* (membelah halaman menjadi dua). Ini adalah operasi yang mahal secara komputasi (I/O intensif) dan menyebabkan fragmentasi.
  - **Read vs Write Performance**: Menambahkan indeks mempercepat `SELECT` tetapi memperlambat `INSERT`. Arsitek *database* harus menyeimbangkan *trade-off* ini berdasarkan rasio *read/write* aplikasi.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Bulk Inserts**: Saat memasukkan ratusan/ribuan baris, gunakan satu *query* `INSERT` dengan banyak `VALUES` (atau gunakan fitur `COPY` di PostgreSQL / `LOAD DATA` di MySQL) daripada melakukan *looping* di level aplikasi.
  - **Eksplisit Mendefinisikan Kolom**: Selalu gunakan `INSERT INTO table_name (col1, col2) VALUES (...)`.
  - **Gunakan Transaksi**: Bungkus beberapa operasi `INSERT` yang saling bergantung dalam blok `BEGIN ... COMMIT;` untuk memastikan integritas data.
- **Don'ts**:
  - **Menghindari N+1 Inserts**: Jangan pernah menaruh *query* `INSERT` tunggal di dalam *loop* `for/while` pada kode aplikasi (misal: Node.js, Python, Java). Ini akan membunuh performa karena *network latency* dan *transaction overhead*.
  - **Mengabaikan Tipe Data**: Jangan memasukkan *string* ke kolom numerik dengan harapan *database* akan melakukan *implicit casting*. Ini membuang siklus CPU dan berisiko memicu *error* tak terduga.
- **Edge Cases**:
  - **Sequence Gaps**: Jika sebuah `INSERT` gagal (misal karena pelanggaran *Unique Constraint*) atau transaksi di-*rollback*, nilai *Auto-Increment* / *Sequence* yang sudah di-*generate* tidak akan dikembalikan. Ini normal dan didesain demi performa (menghindari *locking* pada *sequence generator*). Jangan berasumsi ID akan selalu berurutan tanpa celah.

Bandingkan waktu eksekusi antara melakukan 100.000 *query* `INSERT` tunggal versus membaginya menjadi 100 *batch* di mana masing-masing *batch* berisi 1.000 baris (`Bulk Insert`).

3. Simulasikan skenario *Upsert* (`ON CONFLICT` / `ON DUPLICATE KEY`) pada tabel keranjang belanja (*shopping cart*), di mana jika *user* memasukkan produk yang sama, *quantity* produk tersebut akan bertambah, alih-alih membuat baris baru.
