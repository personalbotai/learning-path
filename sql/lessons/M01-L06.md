### 1. Konsep & Arsitektur Mendalam

Dalam model relasional murni (berdasarkan teori himpunan Codd), sebuah tabel merepresentasikan *unordered set of tuples*. RDBMS tidak menjamin urutan data baris yang disimpan di *disk* atau dikembalikan oleh query `SELECT` kecuali klausul `ORDER BY` dideklarasikan secara eksplisit. Ketiadaan `ORDER BY` membuat engine basis data bebas membaca data berdasarkan lokasi fisik blok penyimpanan (*Heap Scan*), status *cache/buffer pool*, atau konkurensi I/O—yang menghasilkan output non-deterministik.

```
+-----------------------------------------------------------------------+
| SQL Execution Pipeline (Simplified)                                   |
|                                                                       |
| FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT    |
+-----------------------------------------------------------------------+
                                                         |
                   +-------------------------------------+
                   v
    +------------------------------+
    | Ada Index yang Cocok?        |
    +------------------------------+
          |                  |
     (YA) |             (TIDAK)
          v                  v
+--------------------+   +----------------------------------------------+
| B-Tree Index Scan  |   | Materialize ke Buffer (work_mem/sort_buffer) |
| (Data sudah urut)  |   | -> Jalankan Algoritma Sort                   |
| Cost: Rendah       |   | -> Jika over: Spill ke Disk (Temporary File) |
+--------------------+   +----------------------------------------------+
```

Pagination adalah mekanisme membatasi jumlah data yang ditransmisikan dan ditampilkan ke pengguna atau sistem eksternal secara bertahap (*chunking*). Dua pendekatan dominan yang digunakan:

1. **Offset-based Pagination (`OFFSET ... LIMIT`)**:
   Kueri melompati $M$ baris pertama lalu mengambil $N$ baris berikutnya. Meskipun intuitif, pendekatan ini memiliki kompleksitas komputasi $O(M + N)$. Basis data harus membaca dan memproses seluruh $M$ baris sebelum membuangnya (*discard*), yang menyebabkan degradasi performa eksponensial seiring bertambahnya nilai *offset* (*deep pagination*).
2. **Keyset / Cursor-based Pagination**:
   Kueri mengeksploitasi struktur data indeks (B-Tree) dengan memanfaatkan nilai kolom terakhir dari halaman sebelumnya sebagai penanda filter (predikat `WHERE`). Kompleksitas komputasinya adalah $O(\log K + N)$, di mana $K$ adalah jumlah total baris pada indeks dan $N$ adalah jumlah data yang diambil. Pendekatan ini stabil terlepas dari seberapa dalam navigasi halaman dilakukan.

### 2. Implementasi & Contoh Kasus Nyata

Skenario berikut menggunakan skema pencatatan transaksi pembayaran e-commerce skala tinggi.

```sql
-- 1. SETUP SKEMA DAN INDEKS
CREATE TABLE transactions (
    id BIGSERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indeks komposit deterministik untuk optimasi pengurutan temporal
CREATE INDEX idx_transactions_user_created_id 
ON transactions (user_id, created_at DESC, id DESC);

-- Seeding data simulasi
INSERT INTO transactions (user_id, amount, status, created_at)
SELECT 
    (random() * 100)::INT,
    (random() * 1000)::NUMERIC(12, 2),
    CASE WHEN random() > 0.5 THEN 'SUCCESS' ELSE 'FAILED' END,
    NOW() - (g || ' minutes')::INTERVAL
FROM generate_series(1, 1000000) AS g;
```

#### Kasus A: Naive Offset Pagination (Anti-Pattern pada Skala Besar)
Kueri ini mencari riwayat transaksi `user_id = 42` pada halaman ke-501 (dengan ukuran halaman 20 baris).

```sql
-- Offset = (Page - 1) * Limit -> (501 - 1) * 20 = 10000
SELECT id, user_id, amount, status, created_at
FROM transactions
WHERE user_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 10000;
```
*Catatan Engine:* RDBMS harus memindai 10.020 baris, mengurutkannya, membuang 10.000 baris pertama di memori, dan mengembalikan 20 baris sisa.

#### Kasus B: Keyset (Cursor-Based) Pagination (Production-Ready)
Klien menyimpan `created_at` dan `id` dari *item terakhir* di halaman sebelumnya sebagai *cursor*.

```sql
-- Cursor didapat dari record terakhir halaman sebelumnya:
-- created_at: '2026-03-29 10:15:30.123456+00', id: 48921

SELECT id, user_id, amount, status, created_at
FROM transactions
WHERE user_id = 42
  AND (created_at, id) < ('2026-03-29 10:15:30.123456+00'::TIMESTAMPTZ, 48921) -- Row-value comparison
ORDER BY created_at DESC, id DESC
LIMIT 20;
```
*Catatan Engine:* Query Planner melakukan *Index Range Scan* langsung menuju posisi node B-Tree yang tepat, mengambil 20 baris secara sekuensial, dan langsung berhenti (*early exit*). Tidak ada baris yang dibaca sia-sia.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Algoritma Pengurutan
Ketika optimizer menerima kueri dengan `ORDER BY`:
1. **Index Scan / Backward Index Scan**: Jika indeks B-Tree yang mencakup kriteria `ORDER BY` tersedia, engine tidak menjalankan algoritma pengurutan. Node daun (*leaf pages*) B-Tree sudah saling terhubung dalam struktur *doubly-linked list*, sehingga engine cukup membaca *pointer* secara sekuensial maju atau mundur.
2. **Top-N Heapsort (Priority Queue)**: Jika kueri mengandung kombinasi `ORDER BY ... LIMIT N` tanpa indeks yang sesuai, engine mengalokasikan struktur data *bounded heap* (priority queue) berukuran $N$ di memori. Engine memindai seluruh tabel dan hanya mempertahankan $N$ elemen teringan/terberat. Kompleksitas: $O(M \log N)$, di mana $M$ adalah total baris yang lolos filter `WHERE`.
3. **External Merge Sort**: Jika data hasil seleksi tidak muat di memori dan $N$ tidak dibatasi (`LIMIT` besar atau tanpa `LIMIT`), engine beralih ke *quicksort* di memori hingga batas buffer tercapai, menuliskannya ke *disk* sebagai fragmen sementara (*temp run*), lalu menggabungkannya secara bertahap via *K-way merge*.

#### Alokasi Memori & Resource
- **PostgreSQL**: Dibatasi oleh parameter `work_mem`. Jika ukuran data hasil query melebihi `work_mem`, PostgreSQL beralih dari operasi `quicksort` di RAM ke `external merge sort` di disk (direktori `pgsql_tmp`). I/O disk sekunder ini memperlambat query hingga hitungan magnitudo.
- **MySQL (InnoDB)**: Menggunakan alokasi per-thread `sort_buffer_size`. Operasi pengurutan yang tidak menggunakan indeks dinamakan `filesort` (meskipun prosesnya bisa berlangsung murni di RAM jika ukurannya di bawah limit buffer).

#### Analisis Trade-offs

| Aspek | Offset-based Pagination | Keyset / Cursor Pagination |
| :--- | :--- | :--- |
| **Kompleksitas Waktu** | $O(M + N)$ — Menurun linear seiring bertambahnya halaman | $O(\log K + N)$ — Konstan stabil |
| **Navigasi UI** | Fleksibel: Bisa langsung loncat ke Page $X$ acak | Terbatas: Hanya navigasi maju (*Next*) / mundur (*Prev*) |
| **Integritas Data** | Rentan terhadap *Pagination Drift* (data terduplikasi/terlewat) | Imun terhadap *drift* saat ada konkurensi `INSERT`/`DELETE` |
| **Beban Indexing** | Minimal (cukup indeks filter dasar) | Wajib indeks komposit ketat mencakup kolom order + penentu deterministik |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Jadikan Pengurutan Deterministik (Tie-breaker)**: Pastikan kombinasi kolom `ORDER BY` bersifat unik. Jika mengurutkan berdasarkan data non-unik (misal: `created_at` atau `status`), selalu tambahkan *primary key* di akhir: `ORDER BY created_at DESC, id DESC`. Tanpa ini, RDBMS dapat mengembalikan urutan yang berbeda pada eksekusi berulang untuk entri dengan *timestamp* identik.
- **Perhatikan Urutan Kolom Indeks**: Buat indeks yang cocok persis dengan urutan klausa: `(equality_filters, range_filters, sort_columns)`.
- **Gunakan Explicit `NULLS FIRST` / `NULLS LAST`**: Engine SQL memperlakukan posisi `NULL` secara berbeda (PostgreSQL default: `NULLS LAST` untuk ASC, `NULLS FIRST` untuk DESC; MySQL: `NULL` selalu dianggap nilai paling rendah). Definisikan secara eksplisit untuk menjaga portabilitas logika kueri.

#### Don'ts
- **Menghindari Perhitungan Total Record yang Tidak Perlu**: Jangan menggabungkan pagination dengan `SELECT COUNT(*) OVER()` atau subquery count terpisah jika tidak mutlak dibutuhkan. `COUNT(*)` menuntut *Full Table/Index Scan*, melenyapkan keuntungan latensi rendah dari pagination.
- **Jangan Gunakan Deep OFFSET di API Publik**: Membuka parameter `?page=100000` di API REST publik memungkinkan serangan DoS berbasis konsumsi I/O disk dan RAM secara massif. Batasi nilai maksimum offset yang diperbolehkan di sisi API gateway/aplikasi.

#### Edge Cases
- **Pagination Drift**: Terjadi pada Offset Pagination. Jika user sedang membuka Halaman 1, lalu baris baru di-*insert* di urutan teratas oleh proses lain, data baris terakhir Halaman 1 akan terdorong ke posisi pertama Halaman 2. Ketika user mengklik Halaman 2, ia akan melihat baris duplikat tersebut. Keyset pagination mencegah anomali ini secara struktural.
- **Kondisi NULL pada Keyset Cursor**: Komparasi baris SQL seperti `(col1, col2) < (val1, val2)` akan menghasilkan status `UNKNOWN` jika salah satu kolom bernilai `NULL` (berdasarkan aturan Three-Valued Logic). Pastikan kolom cursor dideklarasikan sebagai `NOT NULL`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Rencana Eksekusi (EXPLAIN ANALYZE)**:
   Buat kueri `ORDER BY` pada tabel dengan $100.000$ baris tanpa indeks pada kolom target, lalu jalankan `EXPLAIN (ANALYZE, BUFFERS)`. Identifikasi jenis sort yang digunakan engine: apakah `quicksort`, `top-N heapsort`, atau `external merge`. Turunkan nilai session `work_mem` (PostgreSQL: `SET work_mem = '64kB';`) dan amati kapan engine mulai menggunakan disk temporer (*Spill to Disk*).
2. **Reverse Keyset Pagination**:
   Implementasikan kueri SQL untuk navigasi mundur (*Previous Page*) menggunakan cursor-based pagination. Perhatikan bagaimana tanda komparator (`<` vs `>`) dan arah `ORDER BY` harus dibalik pada tingkat SQL kueri, lalu bagaimana hasilnya perlu disusun ulang di lapisan aplikasi (*in-memory array reversal*).
3. **Simulasi Row-Value Constructor vs Tuple Comparison**:
   Tidak semua versi sistem database lawas mengoptimasi sintaks `(a, b) < (val_a, val_b)` secara efisien via B-Tree index scan. Tulis ulang kondisi keyset tersebut menggunakan logika boolean standar (`WHERE a < val_a OR (a = val_a AND b < val_b)`), lalu bandingkan execution plan dari kedua pendekatan tersebut pada database pilihanmu.
