## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

*Foreign Key* (FK) adalah konstrain referensial dalam model relasional yang memaksakan *referential integrity* antara dua tabel. Secara arsitektural, FK memastikan bahwa nilai pada satu atau sekumpulan kolom di tabel anak (*child/referencing table*) harus selalu merujuk secara valid ke entri *Primary Key* (PK) atau *Unique Key* yang ada di tabel induk (*parent/referenced table*), atau bernilai `NULL` (kecuali didefinisikan `NOT NULL`).

```
+------------------------+             +------------------------+
|      users (Parent)    |             |    profiles (Child)    |
+------------------------+             +------------------------+
| PK  id: BIGINT         |<---+        | PK  id: BIGINT         |
|     email: VARCHAR     |    +--------| FK  user_id: BIGINT    |
+------------------------+             |     bio: TEXT          |
                                       +------------------------+
   [DELETE parent row] ---> triggers ---> [CASCADE: DELETE child row]
```

Ketika operasi mutasi data (`DELETE` atau `UPDATE`) terjadi pada tabel induk, RDBMS harus mengeksekusi aturan konstrain yang telah ditentukan melalui *referential actions*:
*   **`RESTRICT` / `NO ACTION`**: Memblokir operasi penghapusan pada parent jika masih ada data anak yang merujuk padanya. Operasi digagalkan dan *transaction aborted*.
*   **`SET NULL`**: Mengubah nilai kolom FK pada baris anak menjadi `NULL` ketika baris parent dihapus.
*   **`CASCADE`**: Menginstruksikan RDBMS untuk secara otomatis mereplikasi aksi penghapusan parent ke seluruh baris anak yang berelasi secara rekursif.

#### Mengapa `ON DELETE CASCADE` Ada?
Fitur ini mengabstraksi pembersihan relasi dependensi siklus hidup data (*lifecycle containment*). Tanpa `ON DELETE CASCADE`, logika pembersihan data orphan (yatim) harus di-orchestrate manual oleh aplikasi melalui rentetan kueri `DELETE` individual di dalam satu transaksi, atau melalui *stored procedure*. `ON DELETE CASCADE` memindahkan tanggung jawab ini langsung ke *core database engine* secara atomik dan deterministik.

### 2. Implementasi & Contoh Kasus Nyata

Contoh skenario: Sistem *Multi-Tenant Software-as-a-Service* (SaaS), di mana sebuah `organization` menaungi banyak `projects`, dan setiap proyek memiliki entri `tasks`. Jika organisasi dihapus, seluruh proyek dan *task* di dalamnya harus musnah secara berjenjang (*cascading delete*).

```sql
-- 1. Setup Skema Database (PostgreSQL / ANSI SQL Compatible)
CREATE TABLE organizations (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE projects (
    id BIGSERIAL PRIMARY KEY,
    org_id BIGINT NOT NULL,
    title VARCHAR(150) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_projects_organization
        FOREIGN KEY (org_id)
        REFERENCES organizations(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- Index mutlak diperlukan pada Foreign Key column di child table!
CREATE INDEX idx_projects_org_id ON projects(org_id);

CREATE TABLE tasks (
    id BIGSERIAL PRIMARY KEY,
    project_id BIGINT NOT NULL,
    description TEXT NOT NULL,
    is_completed BOOLEAN DEFAULT FALSE,
    CONSTRAINT fk_tasks_project
        FOREIGN KEY (project_id)
        REFERENCES projects(id)
        ON DELETE CASCADE
);

CREATE INDEX idx_tasks_project_id ON tasks(project_id);

-- 2. Inisialisasi Data Uji
INSERT INTO organizations (id, name) VALUES (1, 'Acme Corp');

INSERT INTO projects (id, org_id, title) VALUES 
    (101, 1, 'Core API Gateway'),
    (102, 1, 'Frontend Dashboard');

INSERT INTO tasks (project_id, description) VALUES 
    (101, 'Implement JWT auth'),
    (101, 'Setup Rate Limiter'),
    (102, 'Design CSS System');

-- 3. Eksekusi Deletion pada Parent Teratas
-- Operasi ini memicu multi-level recursive cascade:
-- organizations(1) -> projects(101, 102) -> tasks(3 rows)
DELETE FROM organizations WHERE id = 1;

-- 4. Verifikasi Integritas
SELECT COUNT(*) FROM organizations WHERE id = 1; -- Hasil: 0
SELECT COUNT(*) FROM projects WHERE org_id = 1;  -- Hasil: 0
SELECT COUNT(*) FROM tasks;                      -- Hasil: 0 (Terhapus otomatis via CASCADE multi-level)
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
1. **Implicit Internal Trigger / Action Hook**: Saat parser dan query planner menerima perintah `DELETE FROM organizations WHERE id = 1`, engine melihat definisi dependensi katalog relasional (`pg_constraint` di PostgreSQL atau `INFORMATION_SCHEMA.KEY_COLUMN_USAGE` di MySQL/InnoDB).
2. **Cascading Traversal**: RDBMS membuat sub-perintah penghapusan internal secara implisit. Engine melakukan scan pada tabel anak (`projects`) untuk mencari record di mana `org_id = 1`. 
3. **Locking Mechanism**:
   * RDBMS memegang *Exclusive Lock* (`X-Lock`) pada baris parent yang dihapus.
   * Engine kemudian mengambil *Exclusive Lock* pada seluruh baris anak terkait di tabel `projects` dan `tasks`.
   * **Bahaya Tanpa Index**: Jika kolom `org_id` pada tabel anak tidak memiliki index B-Tree, engine terpaksa melakukan **Full Table Scan (Sequential Scan)** pada tabel anak. Dalam MySQL InnoDB, hal ini dapat meningkatkan eskalasi lock menjadi *Gap Lock* yang masif atau *Table Lock*, melumpuhkan konkurensi database (*lock contention*).

#### Alokasi Memori & Resource
* **Write-Ahead Logging (WAL) / Redo Log Amplification**: Satu operasi `DELETE` parent baris tunggal dapat memicu ribuan penghapusan baris anak. Engine harus mencatat seluruh *tombstone/deletion marker* baris anak ke dalam WAL/Redo log. Hal ini memicu lonjakan I/O disk yang drastis.
* **Undo Log Churn**: Setiap modifikasi baris anak harus mempertahankan salinan lama (*before-image*) di Undo Tablespace untuk mendukung isolasi transaksi *Multi-Version Concurrency Control* (MVCC) bagi pembaca konkuren lainnya.
* **Buffer Pool Contention**: Engine harus memuat seluruh *data pages* milik tabel anak yang terdampak ke dalam *Buffer Pool Memory*, mendepak halaman data aktif lainnya (*cache thrashing*).

#### Trade-offs Arsitektur
| Aspek | Sisi Positif | Sisi Negatif / Trade-off |
| :--- | :--- | :--- |
| **Konsistensi** | Integritas referensial dijamin 100% pada level engine. | Kehilangan fleksibilitas partisi logika bisnis. |
| **Kompleksitas Aplikasi**| Kode backend menjadi bersih tanpa boilerplate query cleanup. | Risiko latency transaksi yang tidak terprediksi (*unbounded latency*). |
| **Auditability** | Eksekusi atomik dalam single transaction boundary. | Penghapusan terjadi secara "senyap" (*silent deletion*), sulit dilacak di application audit log tanpa engine-level CDC (*Change Data Capture*). |

### 4. Best Practices & Common Pitfalls

#### Do's
* **Wajib Mengindeks Kolom Foreign Key**: Selalu buat indeks B-Tree pada kolom FK di tabel anak. Ketiadaan indeks pada FK adalah penyebab nomor satu degradasi performa transaksi deletion parent di level produksi.
* **Gunakan untuk *Compositional Entities***: Gunakan `ON DELETE CASCADE` hanya pada data yang eksistensinya tidak memiliki nilai independen tanpa parent-nya (contoh: `orders` -> `order_items`, `users` -> `user_auth_tokens`).
* **Tetapkan Batasan Waktu Transaksi**: Gunakan parameter `statement_timeout` untuk mencegah satu operasi penghapusan parent dengan jutaan baris anak menahan koneksi dan lock terlalu lama.

#### Don'ts
* **Jangan Gunakan pada Entitas Finansial / Audit**: Dilarang keras menerapkan `CASCADE` pada relasi data seperti `users` -> `invoices`, atau `accounts` -> `ledger_transactions`. Gunakan `ON DELETE RESTRICT` untuk memblokir penghapusan, atau gunakan pola *Soft Delete* (`deleted_at TIMESTAMP`).
* **Hindari Deep Nested Cascade (> 3 Level)**: Menghubungkan hierarki pohon penghapusan yang terlalu dalam (`A -> B -> C -> D -> E`) menyebabkan ketergantungan *locking tree* yang rumit dan rentan menimbulkan **Deadlock** dengan transaksi konkuren lainnya yang mencoba mengakses entitas anak secara paralel.

#### Edge Cases
* **Siklus Dependensi & Deadlocks**: Jika dua transaksi konkuren mengeksekusi penghapusan parent yang berbeda namun memiliki relasi silang anak yang saling tergantung, urutan penguncian baris internal (*lock acquisition order*) dapat saling bersilangan, menyebabkan deteksi deadlock seketika (`SQLSTATE 40P01`).
* **Triggers Explosion**: Jika tabel anak memiliki trigger `AFTER DELETE FOR EACH ROW`, menghapus 1 baris parent yang mencakup 10.000 baris anak via CASCADE akan memicu 10.000 eksekusi trigger anak dalam satu unit transaksi yang sama, berpotensi menabrak batas memori dan CPU.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Profiling Query Plan (The Hidden Scan Cost)**:
   * Buat tabel `parent` dengan 1.000 baris dan `child` dengan 1.000.000 baris menggunakan `generate_series()`.
   * Berikan foreign key `ON DELETE CASCADE` **tanpa** indeks pada kolom FK tabel `child`.
   * Jalankan `EXPLAIN (ANALYZE, BUFFERS) DELETE FROM parent WHERE id = 1;` dan catat metrik execution time serta buffer read.
   * Tambahkan B-Tree index pada kolom FK tersebut, jalankan ulang analisis query plan yang sama, lalu bandingkan perbedaan total *shared hits/reads* dan *execution time*-nya.
2. **Simulasi Deadlock pada Cascading Tree**:
   * Rancang skenario dua session konkuren menggunakan koneksi terpisah:
     * Transaksi A: Melakukan `DELETE FROM parent WHERE id = 1` (memicu cascade ke `child`).
     * Transaksi B: Menjalankan `UPDATE child SET value = ... WHERE parent_id = 1`.
   * Amati pesan galat deadlock yang dihasilkan engine dan telusuri graf dependensi lock yang terbentuk melalui view internal database engine Anda (`pg_locks` pada Postgres atau `performance_schema.data_locks` pada MySQL).
