## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam relational database engine (RDBMS) seperti PostgreSQL, MySQL, atau SQL Server, pemrosesan data pada klausa `WHERE` bertujuan untuk memfilter baris data (tuple) sedini mungkin sebelum masuk ke tahap eksekusi berikutnya (seperti *aggregation*, *sorting*, atau *projection*). Efisiensi filter ini ditentukan oleh konsep **SARGability** (*Search Argument Able*), yaitu kemampuan *query optimizer* untuk memanfaatkan struktur data indeks (umumnya B-Tree) secara langsung tanpa harus melakukan *Full Table Scan* (atau *Sequential Scan*).

#### Operator `IN` (Set Membership)
Operator `IN` mengevaluasi apakah nilai dari suatu ekspresi cocok dengan salah satu nilai dalam kumpulan daftar (*literal list*) atau hasil dari *subquery*.
- Secara semantik, `x IN (a, b, c)` setara dengan ekspresi disjungtif: `x = a OR x = b OR x = c`.
- Pada level arsitektur engine, *query optimizer* akan menimbang apakah ekspresi ini akan di-ekspansi menjadi kumpulan predikat `OR`, diubah menjadi *In-List Index Scan*, atau jika daftarnya sangat besar, dikonversi menjadi *Hash Semi-Join* virtual di memori.

#### Operator `BETWEEN` (Closed Range Interval)
Operator `BETWEEN` melakukan evaluasi rentang tertutup (inklusif):
$$\text{expression BETWEEN min AND max} \iff \text{expression} \ge \text{min AND expression} \le \text{max}$$
- Pada struktur indeks B-Tree, operator ini diterjemahkan menjadi operasi pencarian biner (*binary search*) untuk menemukan batas bawah (`min`), lalu menelusuri rantai *leaf nodes* indeks secara terurut hingga mencapai batas atas (`max`). Operasi ini sangat efisien (*B-Tree Range Scan*).

#### Operator `LIKE` (Pattern Matching)
Operator `LIKE` digunakan untuk pencarian pola string parsial menggunakan dua karakter *wildcard*:
- `%` (persen): merepresentasikan nol, satu, atau banyak karakter sembarang.
- `_` (garis bawah): merepresentasikan tepat satu karakter sembarang.
- SARGability dari `LIKE` sangat bergantung pada posisi *wildcard*:
  - **Prefix Match** (`'ABC%'`): Bersifat SARGable. Optimizer dapat menggunakan B-Tree layaknya rentang nilai: `x >= 'ABC' AND x < 'ABD'`.
  - **Infix/Suffix Match** (`'%ABC'` atau `'%ABC%'`): **Non-SARGable**. Karena karakter pertama tidak diketahui, B-Tree tidak dapat menentukan titik awal pencarian, memaksa engine melakukan *Full Scan* kecuali menggunakan indeks khusus seperti *Trigram Index* (GIN/GiST).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skema tabel e-commerce dan query operasional yang menggunakan operator `IN`, `BETWEEN`, dan `LIKE` secara tepat.

```sql
-- DDL Skema Contoh
CREATE TABLE products (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku VARCHAR(64) NOT NULL,
    category_id INT NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    metadata JSONB
);

CREATE INDEX idx_products_sku ON products(sku);
CREATE INDEX idx_products_category ON products(category_id);
CREATE INDEX idx_products_price ON products(price);
CREATE INDEX idx_products_created_at ON products(created_at);

-- 1. Penggunaan IN: Filter status diskrit & Subquery Sizing
SELECT product_id, sku, status 
FROM products
WHERE status IN ('ACTIVE', 'PENDING_APPROVAL', 'BACKORDER')
  AND category_id IN (101, 102, 108);

-- 2. Penggunaan BETWEEN: Filter Nilai Numerik (Inklusif)
SELECT product_id, sku, price 
FROM products
WHERE price BETWEEN 150000.00 AND 500000.00;

-- 3. Penggunaan LIKE: SARGable Prefix Match
-- Mencari SKU elektronik yang diawali 'ELEC-'
SELECT product_id, sku 
FROM products
WHERE sku LIKE 'ELEC-%';

-- 4. Penggunaan LIKE dengan Karakter ESCAPE
-- Mencari string literal yang mengandung karakter wildcard '%' atau '_'
-- Misalnya mencari SKU yang secara literal mengandung '_V2'
SELECT product_id, sku 
FROM products
WHERE sku LIKE '%!_V2' ESCAPE '!';
```

#### Analisis Penanganan Waktu (Date/Time)
Salah satu kesalahan umum adalah menggunakan `BETWEEN` untuk data bertipe `TIMESTAMP` / `TIMESTAMPTZ`.

```sql
-- SALAH (Anti-pattern pada rentang waktu):
-- Jika record bernilai '2023-12-31 14:30:00', data ini TIDAK akan terpanggil 
-- karena '2023-12-31' dievaluasi sebagai '2023-12-31 00:00:00'.
SELECT * FROM products 
WHERE created_at BETWEEN '2023-01-01' AND '2023-12-31';

-- BENAR (Menggunakan perbandingan eksplisit Half-Open Interval):
SELECT * FROM products 
WHERE created_at >= '2023-01-01 00:00:00' 
  AND created_at <  '2024-01-01 00:00:00';
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Ekspansi `IN` List**:
   - Jika daftar elemen `IN` kecil (misal: 3–5 elemen), optimizer PostgreSQL/MySQL mengubahnya menjadi *bitmap index scan* berulang atau node ekspresi `OR`.
   - Jika daftar elemen besar (ratusan hingga ribuan), query planner mentransformasikan list tersebut menjadi sebuah tabel konstanta in-memory (*Values Scan*) dan melakukan *Hash Semi-Join* terhadap tabel utama.
2. **Transformasi `BETWEEN`**:
   - Engine langsung men-desugar operator `BETWEEN` saat tahap parsing menjadi dua operator biner: `arg >= min AND arg <= max`.
3. **Automasi Translatasi `LIKE` Prefix**:
   - Pada pola `LIKE 'JKT%'`, optimizer dengan collation biner (`C` atau collation berbasis byte) mengubah ekspresi menjadi:
     `col >= 'JKT' AND col < 'JKU'`
   - Ini memungkinkan engine langsung melompat ke *leaf page* indeks target pada kompleksitas waktu $\mathcal{O}(\log N + K)$ (di mana $K$ adalah jumlah record yang cocok), alih-alih $\mathcal{O}(N)$ untuk memindai seluruh tabel.

#### Alokasi Memori / Resource
- **Collation Impact pada `LIKE`**: Komparasi string pada operator `LIKE` sangat dipengaruhi oleh *Collation* database (misal: `en_US.UTF-8` vs `C`/`POSIX`). Collation non-C memerlukan normalisasi string sesuai aturan Unicode (misalnya *case-folding* atau aksen), yang memakan siklus CPU signifikan per baris data jika terjadi *table scan*.
- **Memory Consumption pada `IN` List Raksasa**: Memberikan 10.000 ID ke dalam klausa `IN (...)` meningkatkan beban parsing query string, memakan alokasi *query cache/statement memory*, dan dapat melampaui batas *max packet size* atau alokasi *work_mem* saat membuat internal hash table.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Prefix Match**: Selalu posisikan wildcard di akhir (`string%`) jika menargetkan indeks B-Tree standar.
- **Tentukan Escape Karakter Secara Eksplisit**: Jika mencari data teks mentah dari input pengguna, selalu definisikan klausa `ESCAPE` untuk mencegah *wildcard injection*.
- **Pertimbangkan GIN/pg_trgm untuk Arbitrary Pattern**: Jika pencarian `LIKE '%keyword%'` mutlak diperlukan, gunakan indeks berbasis Trigram (seperti extension `pg_trgm` di PostgreSQL).

#### Don'ts
- **HINDARI `NOT IN` bila Dataset Mengandung `NULL`**:
  Ini adalah jebakan klasik dalam SQL **Three-Valued Logic (3VL)**.
  
  ```sql
  -- Jika subquery menghasilkan set: (1, 2, NULL)
  SELECT * FROM users WHERE user_id NOT IN (1, 2, NULL);
  ```
  Evaluasi logika:
  `user_id <> 1 AND user_id <> 2 AND user_id <> NULL`
  Karena perbandingan dengan `NULL` menghasilkan `UNKNOWN`, dan `TRUE AND UNKNOWN` bernilai `UNKNOWN`, maka **seluruh query tidak akan pernah mengembalikan baris apa pun**.
  *Solusi*: Gunakan `NOT EXISTS` atau filter `WHERE id IS NOT NULL` di subquery.
- **Jangan Gunakan `BETWEEN` untuk Batas Waktu**: Hindari `BETWEEN` pada kolom tanggal/waktu yang memiliki komponen jam, menit, dan detik. Selalu gunakan format rentang terbuka sebelah kanan: `>= Start AND < End`.

#### Edge Cases
- **Case-Insensitive Searching**:
  - MySQL secara default menggunakan collation case-insensitive (misal: `utf8mb4_general_ci`), sehingga `LIKE 'a%'` cocok dengan `'A'`.
  - PostgreSQL bersifat case-sensitive secara default (`LIKE` membedakan huruf besar/kecil). Gunakan operator `ILIKE` di PostgreSQL untuk case-insensitive, namun perhatikan bahwa `ILIKE 'abc%'` memerlukan indeks ekspresi khusus atau indeks berbasis trigram untuk bisa SARGable.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Three-Valued Logic pada `NOT IN`**:
   Buat tabel sementara `test_null` dengan kolom `val INT`, isi dengan data `1`, `2`, dan `NULL`. Jalankan query `SELECT * FROM generate_series(1, 3) g(id) WHERE id NOT IN (SELECT val FROM test_null);`. Amati hasilnya, lalu jelaskan mengapa outputnya kosong serta tulis ulang query tersebut menggunakan `NOT EXISTS`.
2. **Analisis Execution Plan pada `LIKE`**:
   Buat tabel dengan 100.000 data teks dummy pada PostgreSQL atau MySQL. Pasang indeks B-Tree pada kolom teks tersebut. Jalankan `EXPLAIN ANALYZE` untuk dua query:
   - `SELECT * FROM tbl WHERE col LIKE 'test%';`
   - `SELECT * FROM tbl WHERE col LIKE '%test%';`
   Perhatikan perbedaan tipe operasinya (*Index Scan* vs *Seq Scan/Full Table Scan*) serta perbedaan drastis pada waktu eksekusi (*execution time*).
