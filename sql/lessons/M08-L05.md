# 47. Composite Index & Covering Index

## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam optimasi database relasional, indeks tunggal (single-column index) seringkali tidak cukup untuk menangani *query* kompleks yang melibatkan banyak kondisi, pengurutan, dan agregasi. Di sinilah **Composite Index** dan **Covering Index** berperan krusial.

**Composite Index (Indeks Komposit)**
Adalah sebuah indeks B-Tree yang dibangun di atas dua atau lebih kolom dalam sebuah tabel. Arsitektur utamanya bergantung pada **Leftmost Prefix Rule** (Aturan Prefiks Paling Kiri). 
Bayangkan buku telepon: data diurutkan berdasarkan *Nama Belakang* terlebih dahulu, lalu *Nama Depan*. Anda bisa mencari orang dengan cepat jika Anda tahu *Nama Belakang*-nya, atau *Nama Belakang + Nama Depan*. Namun, Anda tidak bisa mencari dengan cepat jika hanya tahu *Nama Depan*-nya saja. Begitulah cara B-Tree pada Composite Index bekerja.

**Covering Index (Indeks Penutup)**
Ini bukanlah tipe indeks baru, melainkan sebuah **kondisi** di mana sebuah indeks (biasanya komposit) mengandung *semua* kolom yang dibutuhkan oleh sebuah *query* (baik di klausa `SELECT`, `WHERE`, `JOIN`, maupun `GROUP BY`). 
Mengapa ini penting? Karena ini mencegah **Table Lookup** (atau *Key/Bookmark Lookup*). Jika indeks sudah memiliki semua data yang diminta, *Execution Engine* tidak perlu lagi membaca tabel utama (Heap atau Clustered Index) di disk. Ini mengubah operasi *Random I/O* yang lambat menjadi *Sequential I/O* yang sangat cepat di dalam struktur indeks.

### 2. Implementasi & Contoh Kasus Nyata

Mari kita gunakan tabel `orders` pada sistem *e-commerce* dengan jutaan baris data.

```sql
-- Membuat tabel contoh
CREATE TABLE orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    order_date TIMESTAMP NOT NULL,
    total_amount DECIMAL(10,2) NOT NULL
);

-- 1. Membuat Composite Index standar
-- Diurutkan berdasarkan customer_id, lalu status
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);

-- 2. Membuat Covering Index menggunakan klausa INCLUDE (PostgreSQL / SQL Server)
-- customer_id dan status ada di struktur B-Tree (untuk pencarian)
-- order_date dan total_amount hanya disimpan di Leaf Node (untuk menutupi query)
CREATE INDEX idx_orders_covering ON orders (customer_id, status) 
INCLUDE (order_date, total_amount);
```

**Analisis Penggunaan Query:**

```sql
-- KASUS 1: Menggunakan Composite Index secara optimal (Index Seek)
SELECT order_id FROM orders 
WHERE customer_id = 105 AND status = 'SHIPPED';
-- Engine menggunakan idx_orders_cust_status karena memenuhi Leftmost Prefix.

-- KASUS 2: Gagal menggunakan Composite Index (Full Table Scan / Index Scan)
SELECT order_id FROM orders 
WHERE status = 'SHIPPED';
-- Engine TIDAK BISA menggunakan idx_orders_cust_status secara efisien karena 
-- kolom pertama (customer_id) tidak ada di klausa WHERE.

-- KASUS 3: Memanfaatkan Covering Index secara penuh (Index Only Scan)
SELECT order_date, total_amount 
FROM orders 
WHERE customer_id = 105 AND status = 'SHIPPED';
-- Engine menggunakan idx_orders_covering.
-- Karena order_date dan total_amount sudah ada di Leaf Node indeks (via INCLUDE),
-- engine TIDAK PERLU membaca tabel utama. Performa meningkat drastis.
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Saat *Query Optimizer* mem-parsing *query*, ia akan mengevaluasi *cost* (biaya I/O dan CPU). Jika *query* meminta kolom yang tidak ada di indeks, *engine* harus melakukan *Index Seek* untuk menemukan *pointer*, lalu melakukan *Key Lookup* ke *Clustered Index* (tabel utama) untuk mengambil kolom sisanya. Jika *Key Lookup* terlalu banyak (misal > 15% dari total baris), *Optimizer* seringkali menyerah dan memilih *Full Table Scan* karena *Random I/O* dari *Key Lookup* lebih mahal daripada *Sequential I/O* dari *Table Scan*. *Covering Index* mengeliminasi *Key Lookup* ini sepenuhnya (menghasilkan *Index Only Scan*).
- **Alokasi Memori / Resource**: 
  Setiap kolom yang ditambahkan ke *Composite Index* akan memperbesar ukuran *Non-Leaf Nodes* dan *Leaf Nodes* pada B-Tree. Semakin besar indeks, semakin banyak *page* memori yang dibutuhkan di *Buffer Pool* (RAM). Klausa `INCLUDE` adalah solusi brilian: kolom yang di-*include* tidak diurutkan dan tidak disimpan di *Non-Leaf Nodes*, melainkan hanya disisipkan sebagai "payload" di *Leaf Nodes*. Ini menghemat memori secara signifikan.
- **Trade-offs**: 
  *Covering Index* memberikan performa baca (READ) yang luar biasa cepat, namun memberikan penalti pada operasi tulis (INSERT/UPDATE/DELETE). Setiap kali data di tabel berubah, struktur B-Tree indeks juga harus diperbarui. Indeks yang terlalu "lebar" (banyak kolom) akan memperlambat proses mutasi data dan memakan ruang disk yang besar.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Urutkan kolom berdasarkan *Equality* lalu *Range***: Letakkan kolom yang dicari dengan operator `=` di urutan pertama indeks, lalu diikuti oleh kolom yang dicari dengan operator `>`, `<`, atau `BETWEEN`.
  - **Gunakan klausa `INCLUDE`**: Jika Anda hanya butuh menampilkan kolom di `SELECT` (bukan untuk di-filter di `WHERE` atau di-urutkan di `ORDER BY`), gunakan `INCLUDE` alih-alih menambahkannya ke dalam *Composite Index* utama.
  - **Perhatikan Kardinalitas**: Letakkan kolom dengan kardinalitas tinggi (nilai unik yang banyak, seperti `customer_id`) di sebelah kiri *Composite Index* dibandingkan kolom berkardinalitas rendah (seperti `status`).
- **Don'ts**:
  - **Jangan membuat indeks untuk semua kombinasi kolom**: Ini akan membunuh performa *write* database Anda. Analisis *query* yang paling sering dieksekusi atau paling lambat, dan buat indeks khusus untuk itu.
  - **Jangan melanggar SARGability**: Menggunakan fungsi pada kolom indeks (misal: `WHERE UPPER(status) = 'SHIPPED'`) akan membuat *Composite Index* tidak berguna.
- **Edge Cases**:
  - Jika Anda melakukan *Range Query* pada kolom pertama di *Composite Index* (misal: `WHERE customer_id > 100 AND status = 'SHIPPED'`), *engine* akan menggunakan indeks untuk mencari `customer_id`, tetapi **tidak bisa** menggunakan struktur B-Tree untuk mencari `status`. Kolom `status` hanya akan dievaluasi sebagai *residual predicate* (filter tambahan setelah data ditemukan).

### 5. Tantangan Eksplorasi Mandiri

1. Gunakan perintah `EXPLAIN ANALYZE` (PostgreSQL) atau aktifkan *Actual Execution Plan* (SQL Server) pada *query* yang tidak ter-*cover* penuh. Identifikasi operasi *Key Lookup* / *Bookmark Lookup* / *Heap Fetch* dan perhatikan berapa persentase *cost* yang dihabiskan di sana.
2. Rancang sebuah *Covering Index* untuk *query* berikut tanpa membuat ukuran indeks membengkak: `SELECT customer_name, email, last_login FROM users WHERE status = 'ACTIVE' ORDER BY created_at DESC LIMIT 50;` (Petunjuk: Pikirkan kombinasi *Composite* untuk `WHERE` + `ORDER BY`, dan `INCLUDE` untuk `SELECT`).
3. Lakukan *benchmark* (uji beban) perbandingan waktu eksekusi `INSERT` 1 juta baris data pada tabel tanpa indeks vs. tabel dengan 3 *Composite Index* yang lebar. Amati degradasi performanya.
