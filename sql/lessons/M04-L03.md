### 1. Konsep & Arsitektur Mendalam

Dalam aljabar relasional, operasi join menggabungkan dua relasi ($R$ dan $S$) berdasarkan predikat logika tertentu ($\theta$). Join standar (`INNER JOIN`) hanya menghasilkan relasi baru dari baris-baris yang memenuhi predikat evaluasi nilai kebenaran (*truth-value* `TRUE`). Namun, kebutuhan rekayasa data sering kali menuntut pemeliharaan baris yang tidak memiliki pasangan relasional. Di sinilah keluarga **Outer Join** digunakan.

```
       LEFT JOIN                 RIGHT JOIN              FULL OUTER JOIN
    +-----+                 +-----+                 +-----+       +-----+
    |  A  |                 |     |  B  |           |  A  |  A∩B  |  B  |
    +-----+                 +-----+                 +-----+       +-----+
 (Semua A + Match B)     (Semua B + Match A)        (Semua A + Semua B)
```

#### A. RIGHT OUTER JOIN
Secara semantik, `RIGHT JOIN` adalah pencerminan (*mirror*) dari `LEFT JOIN`. Jika relasi $R$ di-`RIGHT JOIN` dengan relasi $S$ atas kondisi $p$, maka query planner akan mempertahankan seluruh baris dari $S$ (relasi kanan/outer), dan mencocokkannya dengan baris dari $R$ (relasi kiri/inner). Jika tidak ada tupel di $R$ yang memenuhi predikat $p$, kolom-kolom turunan dari $R$ akan diisi dengan nilai `NULL`.

Secara relasional:
$$R \mathbin{\rtimes}_p S \equiv S \mathbin{\ltimes}_p R$$

Banyak Database Management System (DBMS) mengonversi `RIGHT JOIN` menjadi `LEFT JOIN` pada tahap *query normalization/canonicalization* di dalam query optimizer untuk menyederhanakan pohon eksekusi (*abstract syntax tree* / logical plan).

#### B. FULL OUTER JOIN
`FULL OUTER JOIN` mempertahankan integritas baris dari kedua belah relasi ($R$ dan $S$) secara simultan. Jika predikat join bernilai `TRUE`, baris digabungkan. Jika baris pada $R$ tidak memiliki pasangan di $S$, kolom $S$ bernilai `NULL`. Sebaliknya, jika baris pada $S$ tidak memiliki pasangan di $R$, kolom $R$ bernilai `NULL`.

Operasi ini merepresentasikan gabungan union dari *left outer join* dan *right outer join*:
$$R \mathbin{⟗}_p S \equiv (R \mathbin{\ltimes}_p S) \cup (R \mathbin{\rtimes}_p S)$$

Fitur ini kritikal pada kasus pelaporan konsolidasi, rekonsiliasi data keuangan, serta proses *data diffing/auditing*.

#### C. Arsitektur Engine SQLite & Kebutuhan Emulasi
Sebelum SQLite versi 3.39.0 (rilis pertengahan 2022), Virtual Database Engine (VDBE) dan Query Optimizer pada SQLite **hanya mendukung `INNER JOIN`, `CROSS JOIN`, dan `LEFT OUTER JOIN`**. Struktur loop parser SQLite didesain asimetris, di mana hanya loop terluar (*driving loop*) yang dapat memancarkan nilai `NULL` buatan (*pseudo-null-row* via opcode `NullRow`) untuk tabel di loop dalam.

Meskipun SQLite versi 3.39.0+ telah menambahkan dukungan asli (`native`) untuk `RIGHT` dan `FULL OUTER JOIN` dengan membalik urutan tabel secara internal dan melacak baris yang telah divisitasi (*visited bitmap*), pemahaman teknik **Emulasi Outer Join** wajib dikuasai engineer. Pola ini esensial ketika:
1. Beroperasi pada runtime SQLite legacy (Android OS lama, embedded systems, SQLite library terpasang di Python 3.9/3.10 default distro tertentu).
2. Memahami dekomposisi komputasi set (*relational set operation*) untuk optimasi performa mesin database.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: **Rekonsiliasi Sistem Pembayaran (Billing vs Payment Gateway)**.
Kita memiliki tabel `invoices` dan tabel `bank_transactions`. Kita ingin mengetahui:
- Tagihan yang sudah dibayar.
- Tagihan yang belum ada pembayarannya (*unpaid*).
- Pembayaran masuk yang tidak memiliki nomor tagihan terkait (*unmatched/orphaned payment*).

```sql
-- Skema Tabel
CREATE TABLE invoices (
    invoice_id VARCHAR(10) PRIMARY KEY,
    amount DECIMAL(10, 2),
    customer_id INT
);

CREATE TABLE bank_transactions (
    trx_id VARCHAR(10) PRIMARY KEY,
    invoice_ref VARCHAR(10),
    paid_amount DECIMAL(10, 2),
    settlement_date DATE
);

-- Mock Data
INSERT INTO invoices (invoice_id, amount, customer_id) VALUES
('INV-001', 100000.00, 101),
('INV-002', 250000.00, 102),
('INV-003', 500000.00, 103); -- Belum dibayar (Tidak ada di bank)

INSERT INTO bank_transactions (trx_id, invoice_ref, paid_amount, settlement_date) VALUES
('TRX-901', 'INV-001', 100000.00, '2023-10-01'),
('TRX-902', 'INV-002', 250000.00, '2023-10-02'),
('TRX-903', 'INV-999', 750000.00, '2023-10-03'); -- Orphaned payment (Tidak ada di invoices)
```

#### A. Sintaks Standar ANSI SQL (PostgreSQL, SQL Server, SQLite >= 3.39.0)

```sql
SELECT 
    i.invoice_id,
    i.amount,
    b.trx_id,
    b.invoice_ref,
    b.paid_amount
FROM invoices i
FULL OUTER JOIN bank_transactions b 
    ON i.invoice_id = b.invoice_ref;
```

#### B. Emulasi FULL OUTER JOIN di SQLite (< 3.39.0 atau Universal Pattern)

Untuk mengemulasikan `FULL OUTER JOIN`, kita menggunakan dekomposisi logika himpunan:
`FULL OUTER JOIN` = (`LEFT JOIN`) $\cup$ (`ANTI-JOIN` dari sisi kanan).

##### Teknik 1: Menggunakan `UNION` (Naive approach - Deduplikasi Otomatis)
Operator `UNION` otomatis menghapus duplikasi baris, sehingga menggabungkan `LEFT JOIN` dan pencerminan `LEFT JOIN` menghasilkan set yang identik dengan `FULL OUTER JOIN`.

```sql
-- Langkah 1: Ambil semua baris kiri beserta pasangannya
SELECT 
    i.invoice_id, i.amount, b.trx_id, b.invoice_ref, b.paid_amount
FROM invoices i
LEFT JOIN bank_transactions b ON i.invoice_id = b.invoice_ref

UNION -- UNION menghapus baris duplikat yang sama-sama beririsan (INNER JOIN match)

-- Langkah 2: Ambil semua baris kanan (dibalik menjadi LEFT JOIN)
SELECT 
    i.invoice_id, i.amount, b.trx_id, b.invoice_ref, b.paid_amount
FROM bank_transactions b
LEFT JOIN invoices i ON b.invoice_ref = i.invoice_id;
```

##### Teknik 2: Menggunakan `UNION ALL` + Anti-Join (High-Performance Pattern)
Operator `UNION` mewajibkan DBMS melakukan *distinct sort* atau *hash deduplication* di memori temporer yang sangat lambat untuk dataset besar. Pola idiomatik berikut jauh lebih efisien:

```sql
-- Bagian 1: Seluruh data kiri + kecocokan kanan (LEFT JOIN konvensional)
SELECT 
    i.invoice_id, 
    i.amount, 
    b.trx_id, 
    b.invoice_ref, 
    b.paid_amount
FROM invoices i
LEFT JOIN bank_transactions b ON i.invoice_id = b.invoice_ref

UNION ALL -- Lewati tahap deduplikasi memori, langsung gabungkan

-- Bagian 2: HANYA data kanan yang TIDAK punya pasangan di kiri (Anti-Join)
SELECT 
    i.invoice_id, 
    i.amount, 
    b.trx_id, 
    b.invoice_ref, 
    b.paid_amount
FROM bank_transactions b
LEFT JOIN invoices i ON b.invoice_ref = i.invoice_id
WHERE i.invoice_id IS NULL; -- Filter kunci Anti-Join
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Runtime Engine
1. **Physical Join Algorithms**:
   * **Hash Full Outer Join**: DBMS besar (Postgres, Oracle) membangun Hash Table di memori untuk salah satu tabel. Selama scanning tabel kedua, engine mencatat baris mana di Hash Table yang telah dicocokkan menggunakan pelacak bit (*match bit/bitmap*). Di akhir scan, seluruh entri hash table yang bit-nya belum aktif dipancarkan sebagai baris berpasangan `NULL`.
   * **Nested Loop (SQLite VDBE)**: SQLite berbasis Nested Loop Join. Pada implementasi emulasi `UNION ALL`, engine VDBE membuka kursor independen sebanyak dua kali:
     - Kursor 1: Melakukan full-scan pada `invoices`, melakukan b-tree lookup ke `bank_transactions`.
     - Kursor 2: Melakukan full-scan pada `bank_transactions`, melakukan b-tree lookup ke `invoices` dengan memvalidasi opcode `IsNull`.

#### B. Alokasi Memori & Resource Trade-offs
* **`UNION` vs `UNION ALL`**: 
  * Pada `UNION` biasa, SQLite harus mengalokasikan struktur data sementara (*ephemeral B-Tree table*) di disk/temp memory untuk membandingkan setiap tupel dengan seluruh tupel yang sudah dikeluarkan demi memastikan keunikan (*uniqueness*). Kompleksitas waktu: $\mathcal{O}(N \log N)$.
  * Pada `UNION ALL` + Anti-Join, memori dialokasikan secara *streaming* pipelined langsung ke kursor output tanpa pemilahan kesamaan (*deduplication sort*). Kompleksitas waktu: $\mathcal{O}(N + M)$.
* **Spill-to-Disk**: Jika memory budget (`PRAGMA temp_store` atau `work_mem`) terlampaui saat melakukan deduplikasi pada `UNION`, engine terpaksa mengeksekusi *External Merge Sort* yang memicu overhead I/O disk signifikan.

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Gunakan Indeks pada Kunci Evaluasi Kedua Belah Pihak**: Pastikan kedua kolom join memiliki indeks (B-Tree). Pada contoh di atas: `CREATE INDEX idx_trx_invref ON bank_transactions(invoice_ref);` adalah wajib agar subquery Anti-Join tidak berubah menjadi $\mathcal{O}(N \times M)$ Full Table Scan.
2. **Pilih `UNION ALL` + Anti-Join untuk Emulasi**: Selalu terapkan pola `UNION ALL` dengan predikat filter `WHERE foreign_key IS NULL` daripada mengandalkan overhead pembersihan `UNION`.
3. **Posisikan Predikat Filter dengan Benar**: Letakkan predikat filtering tabel spesifik di dalam klausa `ON`, bukan di `WHERE`, saat berhadapan dengan Outer Join untuk menghindari hilangnya status outer.

#### Don'ts:
1. **The Accidental INNER JOIN (WHERE clause trap)**:
   ```sql
   -- RUSAK: Mengubah FULL OUTER JOIN menjadi INNER JOIN secara diam-diam!
   SELECT *
   FROM invoices i
   FULL JOIN bank_transactions b ON i.invoice_id = b.invoice_ref
   WHERE b.settlement_date >= '2023-10-01'; 
   ```
   *Penyebab*: Ketika baris `invoices` tidak punya pasangan di `bank_transactions`, nilai `b.settlement_date` adalah `NULL`. Evaluasi `NULL >= '2023-10-01'` menghasilkan `UNKNOWN`, yang difilter keluar oleh klausa `WHERE`.
   *Solusi*: Pindahkan filter ke dalam klausa `ON` atau tambahkan penanganan eksplisit:
   ```sql
   ON i.invoice_id = b.invoice_ref AND b.settlement_date >= '2023-10-01'
   -- ATAU
   WHERE (b.settlement_date >= '2023-10-01' OR b.settlement_date IS NULL)
   ```

2. **Salah Memilih Kolom IS NULL pada Anti-Join**:
   Pada blok Anti-Join emulasi, pastikan kolom yang dicek `IS NULL` adalah kolom yang dideklarasikan `NOT NULL` atau kolom `PRIMARY KEY` dari tabel tujuan. Jika memeriksa kolom nullable biasa, Anda tidak bisa membedakan antara "baris memang tidak ada pasangannya" vs "baris ada, tapi datanya bernilai NULL".
