## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam SQL, fungsi agregasi tradisional (seperti `SUM`, `COUNT`, `AVG`) yang dikombinasikan dengan `GROUP BY` akan memadatkan (collapse) baris-baris data menjadi satu baris hasil per grup. Hal ini menghilangkan granularitas baris individual. 

**Window Functions** dan klausa **`OVER()`** hadir untuk memecahkan masalah ini. Konsep "Window" memungkinkan kita melakukan kalkulasi agregasi atau analitik pada sekumpulan baris yang saling berkaitan (window), *tanpa* menghilangkan identitas atau detail dari baris individual tersebut.

Klausa `OVER()` adalah jantung dari arsitektur ini. Ia mendefinisikan "jendela" (konteks baris) tempat fungsi beroperasi. `OVER()` dapat memecah data menjadi tiga dimensi kontrol:
1. **`PARTITION BY`**: Membagi result set ke dalam partisi-partisi logis (mirip `GROUP BY`, tapi tanpa collapsing).
2. **`ORDER BY`**: Menentukan urutan evaluasi baris di dalam setiap partisi.
3. **Window Frame (`ROWS` / `RANGE`)**: Mendefinisikan batas spesifik (subset) dari baris di dalam partisi yang akan dievaluasi relatif terhadap baris saat ini (Current Row).

Secara arsitektur, Window Functions sangat krusial untuk pemrosesan analitik (OLAP) karena menghilangkan kebutuhan akan *Self-Joins* atau *Correlated Subqueries* yang sangat mahal secara komputasi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan skenario data penjualan e-commerce untuk menghitung total per kategori, *running total* (total berjalan), dan *moving average* (rata-rata bergerak).

```sql
-- Menggunakan CTE (Common Table Expression) untuk simulasi data
WITH SalesData AS (
    SELECT 1 AS id, 'Laptop' AS category, '2023-10-01'::DATE AS sale_date, 1500 AS amount UNION ALL
    SELECT 2, 'Laptop', '2023-10-02', 1200 UNION ALL
    SELECT 3, 'Laptop', '2023-10-03', 1800 UNION ALL
    SELECT 4, 'Phone',  '2023-10-01', 800  UNION ALL
    SELECT 5, 'Phone',  '2023-10-02', 900  UNION ALL
    SELECT 6, 'Phone',  '2023-10-03', 850
)
SELECT 
    id,
    category,
    sale_date,
    amount,
    
    -- 1. Agregasi Standar dalam Window (Total per Kategori)
    SUM(amount) OVER(PARTITION BY category) AS total_category_sales,
    
    -- 2. Running Total (Akumulasi berdasar waktu per kategori)
    -- Default frame jika ada ORDER BY: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    SUM(amount) OVER(
        PARTITION BY category 
        ORDER BY sale_date
    ) AS running_total,
    
    -- 3. Moving Average (Rata-rata dari baris sebelumnya, baris saat ini, dan baris setelahnya)
    -- Menggunakan eksplisit Window Frame (ROWS)
    ROUND(AVG(amount) OVER(
        PARTITION BY category 
        ORDER BY sale_date 
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ), 2) AS moving_avg_3_days

FROM SalesData
ORDER BY category, sale_date;
```

**Penjelasan Kode:**
- `SUM(amount) OVER(PARTITION BY category)`: Menghitung total penjualan per kategori dan menempelkan hasilnya di setiap baris tanpa mengubah jumlah baris.
- `ORDER BY sale_date` di dalam `OVER()` memicu kalkulasi akumulatif (Running Total).
- `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING`: Membatasi jendela kalkulasi hanya pada 3 baris (kemarin, hari ini, besok) untuk menghasilkan *Moving Average*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime (Logical Query Processing)**: 
  Window functions dieksekusi sangat lambat dalam siklus pemrosesan kueri logis (Fase 5.5). Mereka dievaluasi *setelah* klausa `FROM`, `WHERE`, `GROUP BY`, dan `HAVING`, tetapi *sebelum* klausa `ORDER BY` final dan `LIMIT`/`OFFSET`. Inilah sebabnya Anda tidak bisa menggunakan Window Function di dalam klausa `WHERE`.
  Di tingkat *Execution Engine*, RDBMS biasanya menggunakan operator **Window Spool** dan **Sort**. Data diurutkan terlebih dahulu berdasarkan `PARTITION BY` dan `ORDER BY`, lalu di-spool (disimpan sementara) untuk dievaluasi per frame.
- **Alokasi Memori / Resource**: 
  Operasi `OVER()` sangat bergantung pada memori (RAM) karena membutuhkan operasi *Sorting* (kompleksitas $O(N \log N)$). Jika partisi terlalu besar untuk muat di *Work Memory* (seperti `work_mem` di PostgreSQL), *Execution Engine* akan melakukan *spilling* ke disk (TempDB / temporary files), yang secara drastis menurunkan performa (I/O bottleneck).
- **Trade-offs (`ROWS` vs `RANGE`)**: 
  Secara default, jika Anda menggunakan `ORDER BY` dalam `OVER()`, SQL menggunakan frame `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. `RANGE` membandingkan *nilai* dan menangani duplikat (ties) dengan memasukkan semua baris bernilai sama ke dalam frame. Ini membutuhkan memori ekstra. `ROWS` membandingkan *posisi fisik* baris, yang jauh lebih cepat dan hemat memori (kompleksitas $O(N)$).

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Selalu gunakan klausa `ROWS` secara eksplisit (misal: `ROWS UNBOUNDED PRECEDING`) alih-alih membiarkan default `RANGE` jika Anda tidak peduli dengan penanganan nilai duplikat (ties). Ini akan memberikan *performance boost* yang signifikan.
  - Lakukan *filtering* data sekuat mungkin di klausa `WHERE` atau di dalam CTE *sebelum* data masuk ke Window Function untuk mengurangi beban *Sorting* di memori.
- **Don'ts**:
  - Jangan mencoba meletakkan Window Function di klausa `WHERE`. Jika Anda perlu memfilter berdasarkan hasil Window Function (misal: mencari ranking 1), bungkus kueri tersebut dalam CTE atau Subquery.
  - Hindari `PARTITION BY` pada kolom dengan kardinalitas sangat rendah jika datasetnya masif, karena akan menciptakan partisi raksasa yang memicu *disk spill*.
- **Edge Cases**:
  - **Penanganan NULL**: Dalam `ORDER BY` di dalam `OVER()`, nilai `NULL` biasanya diurutkan di awal atau di akhir tergantung RDBMS (PostgreSQL default `NULLS LAST` untuk ASC, SQL Server `NULLS FIRST`). Gunakan `NULLS FIRST` atau `NULLS LAST` secara eksplisit untuk menghindari bug analitik.

### 5. Tantangan Eksplorasi Mandiri

1. **Top-N per Group Problem**: Buatlah sebuah kueri menggunakan `ROW_NUMBER()` atau `DENSE_RANK()` untuk mencari 3 produk dengan penjualan tertinggi di *setiap* kategori. Filter hasilnya menggunakan CTE.
2. **Analisis YoY/MoM**: Gunakan fungsi `LAG()` dikombinasikan dengan `OVER()` untuk menghitung persentase pertumbuhan penjualan bulan ini dibandingkan bulan sebelumnya (Month-over-Month Growth).
3. **Performance Tuning**: Buat tabel dengan 1 juta baris data acak. Jalankan kueri *Running Total* menggunakan default `RANGE` dan eksplisit `ROWS`. Analisis *Execution Plan* (menggunakan `EXPLAIN ANALYZE` atau setara) dan bandingkan penggunaan memori serta waktu eksekusinya.
