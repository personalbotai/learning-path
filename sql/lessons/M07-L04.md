### 1. Konsep & Arsitektur Mendalam

Fungsi peringkat (*ranking functions*) dalam SQL—terdiri dari `ROW_NUMBER()`, `RANK()`, dan `DENSE_RANK()`—merupakan subset inti dari **Window Functions** (diperkenalkan pada standar ANSI/ISO SQL:2003). Sebelum adanya window functions, operasi perankingan atau penentuan *Top-N per Category* memerlukan teknik *self-join* yang mahal, subquery korelatif, atau *procedural cursor* yang tidak efisien.

Fungsi-fungsi ini bekerja di atas set baris terisolasi yang disebut **Window Frame**, yang dikontrol oleh klausa `OVER (...)`. Evaluasi peringkat bergantung pada dua sub-klausa utama:
- `PARTITION BY`: Memecah *result set* menjadi kelompok-kelompok independen (serupa dengan `GROUP BY`, namun tidak menciutkan baris menjadi agregasi tunggal). Jika ditiadakan, seluruh *result set* dianggap sebagai satu partisi tunggal.
- `ORDER BY`: Menentukan determinasi nilai yang dijadikan tolok ukur urutan dalam setiap partisi. Urutan ini wajib eksplisit agar *engine* dapat menentukan komparasi logis antarnilai.

Perbedaan fundamental antara ketiga fungsi ini terletak pada bagaimana *engine* menangani kondisi **tie** (nilai komparasi yang identik):

| Fungsi | Perilaku terhadap Nilai Seri (*Tie*) | Sifat Urutan Angka | Contoh Output Seri (Nilai: 100, 100, 80) |
| :--- | :--- | :--- | :--- |
| `ROW_NUMBER()` | Mengabaikan nilai kembar; menetapkan integer unik berurutan secara arbitrer (atau non-deterministik jika sorting tidak unik). | Kontinu, selalu bertambah 1 | `1, 2, 3` |
| `RANK()` | Memberikan angka peringkat yang sama untuk nilai kembar, lalu melompati (*gap*) urutan berikutnya sesuai jumlah duplikasi. | Ada *gap* / diskontinu | `1, 1, 3` |
| `DENSE_RANK()` | Memberikan angka peringkat yang sama untuk nilai kembar tanpa melompati angka pada urutan berikutnya. | Kontinu, tanpa *gap* | `1, 1, 2` |

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sebuah platform analitik e-commerce membutuhkan laporan untuk:
1. Mendapatkan 2 transaksi bernilai tertinggi dari setiap kategori produk (*Top-N per group*).
2. Mengidentifikasi dan menduplikasi data transaksi ganda berdasarkan ID referensi eksternal.

Berikut skrip DDL, DML, dan query analisis menggunakan dialek PostgreSQL/ANSI SQL standar:

```sql
-- 1. Setup Tabel dan Data Transaksi
CREATE TABLE transactions (
    transaction_id INT PRIMARY KEY,
    category_id VARCHAR(10) NOT NULL,
    customer_id INT NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL
);

INSERT INTO transactions (transaction_id, category_id, customer_id, amount, created_at) VALUES
(101, 'ELECTRONICS', 1, 1500.00, '2023-10-01 10:00:00'),
(102, 'ELECTRONICS', 2, 1500.00, '2023-10-01 11:30:00'), -- Tie amount dengan ID 101
(103, 'ELECTRONICS', 3, 1200.00, '2023-10-01 14:00:00'),
(104, 'ELECTRONICS', 4,  900.00, '2023-10-02 09:15:00'),
(105, 'FASHION',     5,  300.00, '2023-10-02 10:00:00'),
(106, 'FASHION',     6,  300.00, '2023-10-02 11:00:00'), -- Tie amount dengan ID 105
(107, 'FASHION',     7,  250.00, '2023-10-02 12:00:00'),
(108, 'FASHION',     8,  100.00, '2023-10-02 13:00:00');

-- 2. Komparasi Visual: ROW_NUMBER vs RANK vs DENSE_RANK
SELECT 
    transaction_id,
    category_id,
    amount,
    ROW_NUMBER() OVER w AS row_num,
    RANK()       OVER w AS rank_num,
    DENSE_RANK() OVER w AS dense_rank_num
FROM transactions
WINDOW w AS (PARTITION BY category_id ORDER BY amount DESC, created_at ASC);

-- 3. Kasus Nyata: Mengambil Top-2 Transaksi Terbesar per Kategori (Menghindari Tie Trap)
-- Menggunakan DENSE_RANK dalam Common Table Expression (CTE)
WITH ranked_transactions AS (
    SELECT 
        transaction_id,
        category_id,
        customer_id,
        amount,
        created_at,
        DENSE_RANK() OVER (
            PARTITION BY category_id 
            ORDER BY amount DESC
        ) as price_tier
    FROM transactions
)
SELECT 
    transaction_id,
    category_id,
    amount,
    price_tier
FROM ranked_transactions
WHERE price_tier <= 2
ORDER BY category_id, price_tier ASC;

-- 4. Kasus Nyata: Deduplikasi Data (Mengambil hanya 1 baris terawal per nilai unik)
WITH duplicate_filter AS (
    SELECT 
        transaction_id,
        category_id,
        amount,
        created_at,
        ROW_NUMBER() OVER (
            PARTITION BY category_id, amount 
            ORDER BY created_at ASC, transaction_id ASC
        ) as dedupe_id
    FROM transactions
)
SELECT 
    transaction_id,
    category_id,
    amount,
    created_at
FROM duplicate_filter
WHERE dedupe_id = 1;
```

**Penjelasan Implementasi:**
- Klausa `WINDOW w AS (...)` digunakan untuk mencegah redundansi definisi window jika parameter `PARTITION BY` dan `ORDER BY` bernilai sama di beberapa fungsi select.
- CTE `ranked_transactions` wajib digunakan karena *Window Functions* tidak diizinkan dievaluasi langsung di dalam klausa `WHERE`.
- Dalam deduplikasi, `ROW_NUMBER()` mengunci determinasi record pertama dengan memanfaatkan `ORDER BY created_at ASC, transaction_id ASC` sebagai *tie-breaker*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Flow
RDBMS mengeksekusi window function pada tahap akhir pipeline query processing logis:
```text
FROM → JOIN → WHERE → GROUP BY → HAVING → WINDOW FUNCTIONS → SELECT → DISTINCT → ORDER BY → LIMIT
```
Karena window function dieksekusi setelah `WHERE` dan `HAVING`, optimizer SQL tidak bisa memfilter output window function sebelum seluruh partisi dihitung, kecuali dibungkus dalam subquery atau CTE.

Pada level Execution Engine (misal: PostgreSQL atau MySQL 8.0+):
1. **Sort Engine Node**: Query Planner menyuntikkan node `Sort` berdasarkan kunci `(PARTITION BY, ORDER BY)`.
2. **WindowAgg Node**: Stream baris yang telah tersortir dialirkan baris-per-baris (*streaming/pipeline-driven*) ke engine `WindowAgg`.
3. **Internal State Machine**:
   - `ROW_NUMBER()` memegang satu *counter* integer `64-bit`. Counter bertambah `+1` setiap baris baru dibaca. Ketika batas partisi berubah, counter direset ke `1`.
   - `RANK()` menyimpan dua nilai internal: `current_row_index` (absolut terhadap partisi) dan `current_rank`. Jika nilai kolom `ORDER BY` sama dengan baris sebelumnya, `current_rank` dipertahankan. Jika berbeda, `current_rank = current_row_index`.
   - `DENSE_RANK()` menyimpan `current_rank`. Nilai hanya bertambah `+1` jika ada transisi nilai kolom (*value edge-change detection*) dari baris sebelumnya.

#### Alokasi Memori & Resource
- Operasi ranking membutuhkan sorting. Sorting dieksekusi di memori kerja engine (seperti `work_mem` di Postgres atau buffer sort di database lain).
- **Spill to Disk**: Jika ukuran data partisi melebihi kuota memori, database beralih dari *in-memory Quicksort* ke *External Merge Sort* berbasis disk/temp file, menyebabkan latensi I/O melonjak drastis.
- Tidak seperti fungsi agregasi `SUM() OVER (...)` yang membutuhkan *frame accumulation buffer* besar, `ROW_NUMBER()`, `RANK()`, dan `DENSE_RANK()` adalah *peeking-window* statis; engine hanya perlu melacak baris saat ini dan baris sebelumnya (*sliding 1-row state*).

#### Trade-offs
- **Kompleksitas Komputasi**: Biaya didominasi oleh fase pengurutan: $\mathcal{O}(N \log N)$ untuk $N$ baris per partisi, diikuti oleh fase scanning linear $\mathcal{O}(N)$. 
- **Deterministic Risk**: Jika klausa `ORDER BY` pada `ROW_NUMBER()` tidak menghasilkan nilai yang unik secara mutlak (tidak memiliki *tie-breaker unique column*), urutan eksekusi bersifat non-deterministik antar-run query, terutama pada lingkungan pemrosesan paralel (*Parallel Query Workers*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Composite Index**: Buat indeks yang mencakup `(PARTITION BY_col, ORDER BY_col)` untuk meniadakan fase `Sort` eksplisit di runtime (*Sort Elision optimization*).
- **Sertakan Kolom Unique/Primary Key pada ORDER BY**: Saat menggunakan `ROW_NUMBER()`, pastikan terdapat kolom penentu akhir (misal `created_at, id`) agar hasil perankingan selalu stabil (*deterministic*).
- **Gunakan Subquery/CTE untuk Filtering**: Sadari bahwa filtering peringkat harus selalu melalui struktur turunan.

#### Don'ts
- **Hindari penggunaan `ROW_NUMBER()` untuk pagination tingkat lanjut tanpa filter indeks**: Membaca jutaan baris hanya untuk membuang peringkat selain 10-20 menghabiskan komputasi CPU dan memori sort secara masif.
- **Jangan gunakan window function di dalam klausa `WHERE` atau `HAVING`**:
  ```sql
  -- SINTAKS INVALID (Akan menghasilkan error: window functions are not allowed in WHERE)
  SELECT * FROM transactions WHERE ROW_NUMBER() OVER(ORDER BY amount DESC) <= 5;
  ```

#### Edge Cases
- **Penanganan `NULL` Values**: Dalam SQL standar, `NULL` bernilai sama di antara sesamanya untuk evaluasi peringkat. Pada PostgreSQL, default sorting menempatkan `NULL` sebagai nilai terbesar (`NULLS FIRST` pada `DESC`, `NULLS LAST` pada `ASC`). Selalu tentukan eksplisit:
  ```sql
  ORDER BY amount DESC NULLS LAST
  ```
- **Overlapping Partitioning**: Menjalankan beberapa window function dengan kombinasi `PARTITION BY` yang saling bertolak belakang dalam satu query akan memaksa database mengeksekusi beberapa kali *resort* data secara berulang (*Multiple Sort Nodes*).
