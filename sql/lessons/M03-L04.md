## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur *Relational Database Management System* (RDBMS), pemrosesan kueri SQL tidak dieksekusi secara linear sesuai urutan penulisan sintaksis (*lexical order*), melainkan melalui urutan pemrosesan logis (*logical query processing phase*). 

Klausa `HAVING` lahir karena batasan fundamental dari klausa `WHERE`. Klausa `WHERE` beroperasi pada tingkat baris (*tuple-level/row-level filtering*) sebelum operasi agregasi dilakukan. Pada fase `WHERE`, *relational engine* mengevaluasi baris per baris individual dari tabel virtual yang dihasilkan oleh fase `FROM` dan `JOIN`. Karena fungsi agregasi (seperti `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) membutuhkan sekumpulan baris untuk dihitung menjadi satu nilai ringkasan, mesin database belum memiliki nilai skalar agregat tersebut saat fase `WHERE` berjalan.

Urutan pemrosesan logis kueri standar ANSI SQL adalah sebagai berikut:
1. `FROM` & `JOIN` (Membentuk *cartesian product* dan evaluasi predikat `ON`)
2. `WHERE` (Memfilter baris individual)
3. `GROUP BY` (Mengelompokkan baris ke dalam *buckets/partitions*)
4. **`HAVING` (Memfilter hasil grup berdasarkan predikat agregasi)**
5. `SELECT` (Evaluasi ekspresi kolom, proyeksi)
6. `DISTINCT` (Menghapus duplikasi)
7. `ORDER BY` (Pengurutan data hasil)
8. `LIMIT` / `OFFSET` (Pembatasan set hasil akhir)

```
[Raw Rows] ──► WHERE ──► [Filtered Rows] ──► GROUP BY ──► [Aggregated Buckets] ──► HAVING ──► [Final Groups]
```

`HAVING` bertindak sebagai filter predikat fase kedua. Secara formal dalam aljabar relasional:
$$\sigma_{p_{agg}}(\gamma_{G, agg(A)}(R))$$
di mana relasi $R$ terlebih dahulu dikelompokkan dan diagregasikan oleh operator $\gamma$, lalu hasilnya difilter oleh operator seleksi $\sigma$ dengan predikat agregat $p_{agg}$.

Jika predikat diletakkan di `HAVING` tanpa melibatkan fungsi agregat (misalnya `HAVING status = 'ACTIVE'`), secara semantik kueri tetap valid, namun secara arsitektur ini membebani *execution engine* karena operasi pengelompokan (*grouping*) dilakukan pada data yang seharusnya bisa dibuang lebih awal di fase `WHERE`.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sistem deteksi anomali transaksi finansial (*fraud detection* sederhana). Kita ingin mencari merchant yang memiliki total volume transaksi sukses lebih dari Rp 50.000.000 dengan rata-rata transaksi di bawah Rp 500.000 (indikasi *micro-transactions structuring*) dalam rentang waktu kuartal terakhir.

```sql
-- 1. Setup Skema & Sample Data
CREATE TABLE merchants (
    merchant_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE transactions (
    transaction_id BIGINT PRIMARY KEY,
    merchant_id INT NOT NULL REFERENCES merchants(merchant_id),
    amount NUMERIC(15, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

-- Indexing untuk optimasi filter WHERE dan pengelompokan
CREATE INDEX idx_transactions_filter ON transactions (status, created_at, merchant_id) INCLUDE (amount);

-- 2. Kueri Analisis dengan Kombinasi WHERE dan HAVING
SELECT 
    m.merchant_id,
    m.name AS merchant_name,
    COUNT(t.transaction_id) AS total_transactions,
    SUM(t.amount) AS total_volume,
    ROUND(AVG(t.amount), 2) AS average_ticket_size
FROM 
    merchants m
JOIN 
    transactions t ON m.merchant_id = t.merchant_id
WHERE 
    -- Filter baris: Hanya evaluasi transaksi sukses dalam 90 hari terakhir
    t.status = 'SUCCESS'
    AND t.created_at >= NOW() - INTERVAL '90 days'
GROUP BY 
    m.merchant_id, 
    m.name
HAVING 
    -- Filter grup: Volume kumulatif tinggi, namun rata-rata nominal rendah
    SUM(t.amount) >= 50000000.00
    AND AVG(t.amount) < 500000.00
    AND COUNT(t.transaction_id) >= 100
ORDER BY 
    total_volume DESC;
```

**Penjelasan Kueri:**
1. **`WHERE t.status = 'SUCCESS' AND ...`**: Mengeliminasi transaksi berstatus *FAILED*, *PENDING*, atau di luar rentang waktu sebelum data dikirim ke operator agregasi. Mengurangi dimensi data masukan secara drastis.
2. **`GROUP BY m.merchant_id, m.name`**: Mempartisi data ke dalam *hash table* atau *sorted streams* berdasarkan merchant.
3. **`HAVING SUM(...) >= ... AND AVG(...) < ...`**: Mengevaluasi metrik agregat per merchant bucket. Hanya grup yang memenuhi ketiga kondisi kumulatif tersebut yang dipertahankan.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
Ketika *Query Optimizer* menerima kueri ber-agregasi dengan klausa `HAVING`, mesin database (seperti PostgreSQL, MySQL InnoDB, atau SQL Server) biasanya memilih salah satu dari dua algoritma fisik utama:

1. **Hash Aggregate**:
   - Optimizer membuat struktur data *in-memory hash table*.
   - *Key* hash adalah kolom-kolom `GROUP BY`.
   - *Value* hash menyimpan slot akumulator agregat (misalnya pointer ke `count_state`, `sum_state`).
   - Setiap baris yang lolos seleksi `WHERE` di-*hash*. Jika grup sudah ada, nilai akumulator diperbarui secara *in-place*. Jika belum, *entry* baru dialokasikan.
   - Setelah semua baris selesai diproses, mesin memindai *hash table* tersebut dan mengevaluasi ekspresi pada `HAVING`. Entri yang menghasilkan nilai boolean `FALSE` atau `UNKNOWN` (*NULL*) akan langsung di-drop dari memori.

2. **Stream/Group Aggregate (Sort-based)**:
   - Jika data sudah terurut berdasarkan kolom `GROUP BY` (misalnya via *B-Tree Index Scan*), mesin membaca baris secara sekuensial.
   - Akumulator menghitung nilai berjalan selama nilai kolom `GROUP BY` sama.
   - Begitu nilai kolom kunci berubah (*boundary crossing*), predikat `HAVING` langsung dievaluasi untuk grup yang baru saja selesai. Jika lolos, baris dikirim ke pipeline berikutnya (*pipelined execution*).

#### Alokasi Memori / Resource
- **Hash Table Spilling**: Jika kapasitas memori kerja database (misalnya `work_mem` di PostgreSQL atau *buffer pool* di database lain) tidak cukup menampung semua entri grup unik, agregasi beralih ke disk (*Hash Agg Spill to TempDB/External Sort*). 
- `HAVING` **tidak** mengurangi konsumsi memori pada tahap konstruksi agregasi. Memori dialokasikan untuk **semua** kombinasi unik `GROUP BY`, terlepas dari apakah grup tersebut nantinya akan dibuang oleh `HAVING`.

#### Predicate Pushdown Optimization
*Cost-Based Optimizer* (CBO) modern memiliki teknik transformasi predikat (*predicate pushdown*):
- Jika developer tidak sengaja meletakkan predikat non-agregat di `HAVING` (misal: `HAVING m.merchant_id = 10`), optimizer pintar akan secara otomatis memindahkan (*push down*) predikat tersebut ke fase `WHERE` sebelum kalkulasi eksekusi fisik dilakukan.
- Namun, jika predikat mengandung fungsi agregasi (misal: `HAVING COUNT(*) > 5`), predikat tersebut **tidak dapat di-push down**, memaksa evaluasi penuh seluruh grup data.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `WHERE` secara agresif**: Buang sebanyak mungkin baris individual sebelum masuk ke fase `GROUP BY` untuk meminimalkan beban komputasi CPU dan alokasi memori pada operator agregasi.
- **Kombinasikan Indeks dengan Kunci Pengelompokan**: Gunakan *Composite Index* yang mencakup kolom filter `WHERE` dan kolom pengelompokan `GROUP BY` untuk memungkinkan *Index-Only Scan* atau menghindari fase pengurutan (*Sort Elimination*).
- **Gunakan fungsi agregat yang deterministik**: Pastikan penanganan `NULL` pada kolom yang diagregasi dipahami dengan jelas (misal: `COUNT(kolom)` mengabaikan `NULL`, sedangkan `COUNT(*)` menghitung seluruh baris).

#### Don'ts
- **Menaruh kondisi skalar/baris di dalam `HAVING`**:
  ```sql
  -- ANTI-PATTERN: Menghabiskan resource memory & CPU untuk agregasi
  SELECT department_id, AVG(salary)
  FROM employees
  GROUP BY department_id
  HAVING department_id IN (1, 2, 3); -- Salah! Pindahkan ke WHERE

  -- BEST PRACTICE
  SELECT department_id, AVG(salary)
  FROM employees
  WHERE department_id IN (1, 2, 3)
  GROUP BY department_id;
  ```
- **Menggunakan Alias Kolom `SELECT` di `HAVING` (Tergantung Mesin SQL)**:
  Standar SQL melarang penggunaan alias kolom yang didefinisikan di `SELECT` pada klausa `HAVING` karena `HAVING` dievaluasi sebelum `SELECT`. Walaupun beberapa database (seperti MySQL) memperbolehkannya via ekstensi sintaks, PostgreSQL dan SQL Server akan melemparkan *error* sintaksis.

#### Edge Cases
- **`HAVING` tanpa `GROUP BY`**:
  Jika Anda menulis `HAVING` tanpa klausa `GROUP BY`, seluruh tabel diperlakukan sebagai satu grup tunggal:
  ```sql
  -- Mengembalikan 1 baris jika total baris > 1000, atau 0 baris jika tidak
  SELECT AVG(amount) 
  FROM transactions 
  HAVING COUNT(*) > 1000;
  ```
- **`NULL` dalam Hasil Agregasi**:
  Jika sebuah grup hanya berisi nilai `NULL` untuk kolom tertentu, `SUM(kolom)` atau `AVG(kolom)` akan menghasilkan `NULL`. Jika `HAVING SUM(amount) > 0` dievaluasi terhadap `NULL > 0`, hasilnya adalah `UNKNOWN` (Three-Valued Logic), yang berarti grup tersebut akan dieliminasi dari hasil akhir.
