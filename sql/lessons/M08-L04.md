## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Ketika sebuah *query* SQL dikirim ke Database Management System (DBMS), mesin database tidak langsung mengeksekusi instruksi tersebut secara mentah. SQL adalah bahasa deklaratif: pengguna mendefinisikan *apa* data yang diinginkan, bukan *bagaimana* algoritma untuk mengambilnya. Di sinilah peran subsistem inti database yang disebut **Query Optimizer**.

Proses evaluasi query melewati tahapan arsitektural berikut:
1. **Parser & Lexer**: Mengubah teks SQL menjadi *Abstract Syntax Tree* (AST) dan memvalidasi sintaksis.
2. **Catalog / Metadata Resolver**: Memvalidasi eksistensi tabel, kolom, hak akses, dan tipe data.
3. **Query Optimizer (RBO & CBO)**:
   - *Rule-Based Optimizer (RBO)*: Menerapkan aturan logis statis (misal: *push down predicate* agar filter dieksekusi sedini mungkin).
   - *Cost-Based Optimizer (CBO)*: Menghitung estimasi beban I/O, CPU, dan memori untuk berbagai alternatif rencana akses (*search space*). CBO memanfaatkan statistik tabel (seperti distribusi nilai via *histogram*, jumlah *row*, dan jumlah blok data).
4. **Execution Engine**: Menerima pohon rencana (*Physical Query Plan*) optimal dari CBO dan mengeksekusinya menggunakan operator-operator aljabar relasional (Scan, Filter, Hash, Sort, Join).

```
   SQL Query
       │
       ▼
 [ Parser/Lexer ] ──► AST
       │
       ▼
 [ Query Optimizer (CBO) ] ◄── Metadata & Statistics (Histograms, Page count)
       │
       ▼
 [ Execution Plan (Tree Nodes) ]
       │
       ▼
 [ Execution Engine ] ──► Disk / Buffer Pool ──► Result Set
```

Perintah `EXPLAIN` atau `EXPLAIN QUERY PLAN` (istilah spesifik pada SQLite, setara dengan `EXPLAIN` atau `EXPLAIN ANALYZE` pada PostgreSQL/MySQL) adalah instrumen diagnostik primer untuk menyingkap representasi internal *Physical Plan* yang dipilih oleh CBO sebelum atau sesudah query dieksekusi.

Memahami visualisasi eksekusi memampukan *engineer* untuk:
- Mengidentifikasi *Full Table Scan* (atau `SCAN TABLE` / `Seq Scan`) yang tidak diinginkan pada tabel berukuran besar.
- Mengetahui apakah indeks digunakan secara efektif (*Index Seek* vs *Index Scan*).
- Menilai algoritma Join yang dipilih (*Nested Loop*, *Hash Join*, atau *Sort-Merge Join*).
- Mengidentifikasi operasi berbiaya tinggi (*expensive operations*) seperti alokasi memori sementara untuk `Sort` atau *Disk Spill*.

### 2. Implementasi & Contoh Kasus Nyata

Sintaks visualisasi eksekusi bervariasi antar-database engine. Contoh berikut menggunakan dialek SQLite (`EXPLAIN QUERY PLAN`) dan kompatibilitas PostgreSQL (`EXPLAIN (ANALYZE, BUFFERS)`), mensimulasikan sistem e-commerce.

#### Setup Skema & Data
```sql
-- DDL Skema E-commerce
CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    country VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    order_date DATE NOT NULL,
    total_amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
);

-- Indeks strategis
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_date_status ON orders(order_date, status);
```

#### Kasus 1: Query Tanpa Filter Terindeks (SQLite & PostgreSQL)

```sql
-- SQLite: Cek rencana query
EXPLAIN QUERY PLAN
SELECT * FROM orders 
WHERE total_amount > 500.00;
```
**Output SQLite:**
```text
QUERY PLAN
`--SCAN orders
```
*Analisis:* `SCAN orders` menandakan *Full Table Scan*. Setiap halaman (*page*) tabel di disk/buffer harus dibaca karena tidak ada indeks pada `total_amount`.

---

#### Kasus 2: Pemanfaatan Indeks Komposit & Covering Index

```sql
-- Query mencari pesanan selesai pada tanggal tertentu
EXPLAIN QUERY PLAN
SELECT order_date, status 
FROM orders 
WHERE order_date = '2024-01-15' AND status = 'COMPLETED';
```
**Output SQLite:**
```text
QUERY PLAN
`--SEARCH orders USING COVERING INDEX idx_orders_date_status (order_date=? AND status=?)
```
*Analisis:* Database menggunakan operator `SEARCH` (bukan `SCAN`) melalui `idx_orders_date_status`. Kata kunci `COVERING INDEX` menunjukkan database sama sekali tidak perlu menyentuh tabel utama (*heap/table B-Tree*); semua data yang diminta tersedia langsung di daun (*leaf page*) indeks B-Tree.

#### Kasus 3: Relasi Join Kompleks (PostgreSQL Syntax: Rencana Riil vs Estimasi)

Dalam PostgreSQL, menambahkan parameter `ANALYZE` akan mengeksekusi query secara aktual untuk membandingkan estimasi CBO dengan metrik waktu nyata.

```sql
-- Eksekusi di PostgreSQL
EXPLAIN (ANALYZE, BUFFERS, COSTS)
SELECT 
    c.name,
    COUNT(o.id) AS total_orders,
    SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE c.country = 'ID'
GROUP BY c.id, c.name
ORDER BY total_spent DESC
LIMIT 10;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Volcano Iterator Model
Mayoritas mesin database relasional (termasuk SQLite, PostgreSQL, dan MySQL) mengimplementasikan **Volcano Iterator Model** (dikembangkan oleh Goetz Graefe). 

- Setiap simpul (*node*) pada execution plan adalah iterator yang mengimplementasikan antarmuka standar: `open()`, `next()`, dan `close()`.
- Operator induk (misalnya `Limit`) memanggil metode `next()` pada simpul anak (`Sort`).
- Simpul anak memanggil `next()` secara hierarkis ke bawah sampai ke simpul pemindaian fisik (`Index Scan` atau `Seq Scan`).
- Tuple/baris ditarik secara bertahap (*pull-based execution*), meminimalkan retensi memori secara global kecuali jika simpul tersebut membutuhkan *Pipeline Breakers* (seperti `Sort` atau `Hash Join` fase *Build*), yang harus memproses seluruh set data sebelum mengembalikan baris pertama.

#### Alokasi Memori & Resource
- **Hash Join**: Dibagi menjadi dua fase: *Build* dan *Probe*. Database membaca himpunan data yang lebih kecil (dalam contoh di atas: tabel `customers` setelah difilter `country = 'ID'`), menyusun *Hash Table* di memori RAM (misalnya `work_mem` di PostgreSQL). Kemudian, tabel `orders` dipindai dan dipetakan ke Hash Table tersebut (*Probe*).
- **Sort Operator**: Jika volume data melebihi kuota alokasi memori lokal (`work_mem` atau *cache size* mesin), database akan beralih dari algoritma pemilahan cepat berbasis memori (*Quicksort* atau *Top-N Heapsort*) ke *External Merge Sort*, yang memaksa penulisan fragmen sementara ke disk storage (*I/O Spill* pada direktori `tmp`).

#### Trade-offs
- **Index Seek vs Full Scan**: Indeks B-Tree memangkas kompleksitas pencarian dari $O(N)$ ke $O(\log N)$. Namun, jika predikat mencakup proporsi data yang signifikan (umumnya >15-20% dari total data), optimizer akan sengaja mengabaikan indeks dan memilih *Sequential Scan*. Hal ini terjadi karena *Random I/O* akibat *pointer dereferencing* dari indeks ke tabel heap jauh lebih mahal daripada *Sequential Read* blok-blok tabel secara berurutan.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Validasi Nilai Nyata dengan `EXPLAIN ANALYZE`**: Dalam fase *development*, gunakan opsi eksekusi aktual (`EXPLAIN ANALYZE` di Postgres/MySQL) untuk memvalidasi apakah estimasi CBO (`rows=...`) mendekati realitas (`actual rows=...`). Perbedaan eksponensial (misal: estimasi 1 baris, realita 1.000.000 baris) adalah alarm utama statistik database sudah usang (*stale statistics*).
- **Periksa Pipeline Breakers**: Awasi operator `Sort`, `Materialize`, atau `HashAggregate` pada query latensi rendah. Pastikan operasi sortir dibantu oleh urutan indeks yang ada untuk menghindari pemilahan manual di memori.
- **Rutin Jalankan `ANALYZE`**: Pastikan katalog metadata rutin diperbarui (`ANALYZE table_name;` atau VACUUM otomatis) agar optimizer memiliki histogram akurat.

#### Don'ts
- **Menjalankan `EXPLAIN ANALYZE` pada Operasi Mutasi Tanpa Transaksi**: Perintah `EXPLAIN ANALYZE DELETE FROM orders WHERE ...` akan **benar-benar menghapus data**. Jika ingin menguji query mutasi, bungkus dalam transaksi dan lakukan *rollback*:
  ```sql
  BEGIN;
  EXPLAIN ANALYZE DELETE FROM orders WHERE status = 'CANCELLED';
  ROLLBACK;
  ```
- **Mengabaikan implicit type casting**: Membandingkan tipe data kolom `VARCHAR` dengan parameter numerik tanpa casting manual sering kali menonaktifkan pemanfaatan B-Tree Index, memaksa *full scan*.

#### Edge Cases
- **Parameter Sniffing (Prepared Statements)**: Pada eksekusi *prepared statement*, query planner bisa membuat *generic plan* daripada *custom plan*. Hal ini dapat menghasilkan eksekusi yang lambat jika distribusi data sangat timpang (*skewed data*), karena optimizer mengasumsikan distribusi seragam.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Predicate Invalidation**: Buat query yang menggunakan fungsi pada kolom berindeks (misal: `WHERE UPPER(country) = 'ID'` atau `WHERE id + 1 = 100`). Jalankan `EXPLAIN QUERY PLAN`, amati perbedaannya dibanding filter tanpa manipulasi fungsi, dan selesaikan masalah tersebut menggunakan *functional index* (expression index).
2. **Simulasi Spill to Disk**: Konfigurasikan memori sesi lokal database Anda ke batas minimum (contoh di PostgreSQL: `SET work_mem = '64kB';`). Lakukan pengurutan (`ORDER BY`) pada tabel dengan ratusan ribu baris. Analisis output `EXPLAIN (ANALYZE, BUFFERS)` untuk menemukan metrik *Sort Method: external merge Disk*. Hitung dampak latensinya dibandingkan dengan alokasi memori yang memadai.
