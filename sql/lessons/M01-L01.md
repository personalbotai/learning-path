## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum era 1970-an, pengelolaan data didominasi oleh model **Hierarki** (contoh: IBM IMS) dan model **Jaringan** (CODASYL). Kedua model ini memiliki kelemahan mendasar: *tight physical coupling*. Pengembang aplikasi harus mengetahui secara persis bagaimana data disimpan di disk, termasuk struktur *pointer*, *offset*, dan jalur traversal fisik (*navigational access*). Jika struktur fisik file diubah (misalnya penambahan indeks), seluruh kode aplikasi yang mengakses data tersebut harus ditulis ulang.

```
Pendekatan Prosedural (CODASYL/Hierarki):
Aplikasi ---> Mengetahui Struktur Pointer Fisik File ---> Data di Disk
(Perubahan fisik merusak aplikasi)

Pendekatan Deklaratif Relasional (Codd):
Aplikasi ---> Query Deklaratif (SQL) ---> RDBMS Engine (Optimizer) ---> Data di Disk
(Physical Data Independence terjamin)
```

Pada tahun 1970, **Dr. Edgar F. Codd**, seorang ilmuwan komputer di IBM Research Laboratory, mempublikasikan *paper* monumental berjudul *"A Relational Model of Data for Large Shared Data Banks"*. Codd memperkenalkan dua prinsip revolusioner:

1. **Abstraksi Berbasis Matematika**: Data direpresentasikan murni sebagai relasi (*relation*), yang dalam terminologi matematika merupakan himpunan bagian dari perkalian Kartesian (*Cartesian product*) antar-domain atribut. Tidak ada *pointer* fisik yang diekspos ke pengguna.
2. **Physical Data Independence**: Struktur penyimpanan fisik (*access path*, alokasi blok disk, algoritma pengindeksan) terisolasi sepenuhnya dari representasi logis data.

#### Fondasi Model Relasional

Model relasional berdiri di atas dua pilar matematika:
* **Teori Himpunan (Set Theory)**: Relasi adalah himpunan tak terurut (*unordered sets*) dari tupel-tupel yang unik.
* **Logika Predikat Orde Pertama (First-Order Predicate Logic)**: Kriteria query diekspresikan sebagai predikat yang mengevaluasi apakah sebuah tupel memenuhi kondisi tertentu (menghasilkan nilai kebenaran: *True*, *False*, atau *Unknown*).

| Terminologi Matematika (Codd) | Terminologi RDBMS / SQL | Representasi Fisik |
| :--- | :--- | :--- |
| **Relation** | Table | File data / Heap / B-Tree Table |
| **Tuple** | Row / Record | Slotted-page tuple record |
| **Attribute** | Column / Field | Struct member / byte offset |
| **Domain** | Data Type + Constraints | Tipe data primitif (INT, VARCHAR, dll.) |

#### Aljabar Relasional (*Relational Algebra*)

SQL merupakan bahasa deklaratif yang mengimplementasikan operasi-operasi dasar Aljabar Relasional:
* **Selection ($\sigma$)**: Memfilter baris berdasarkan predikat (SQL: `WHERE`).
* **Projection ($\pi$)**: Memilih atribut tertentu (SQL: `SELECT column_list`).
* **Cartesian Product ($\times$)**: Kombinasi silang antar dua relasi (SQL: `CROSS JOIN`).
* **Union ($\cup$)**: Penggabungan himpunan dua relasi yang kompatibel (SQL: `UNION`).
* **Difference ($-$)**: Mengambil tupel yang ada di relasi $R$ tetapi tidak di relasi $S$ (SQL: `EXCEPT` / `MINUS`).
* **Join ($\bowtie$)**: Derivasi dari $\sigma(R \times S)$ berdasarkan predikat kesamaan nilai atribut (SQL: `INNER JOIN`).

#### Evolusi Menuju SQL

IBM mengembangkan proyek prototipe bernama **System R** (1974) untuk membuktikan kelayakan teori Codd. Donald D. Chamberlin dan Raymond F. Boyce merancang bahasa kueri bernama **SEQUEL** (*Structured English Query Language*), yang kemudian disingkat menjadi **SQL** (*Structured Query Language*) karena masalah merek dagang.

Perbedaan fundamental antara *Relational Model* murni dan *SQL*:
* **Set vs. Multiset (Bag)**: Relasi matematika tidak memperbolehkan duplikasi data. SQL secara default bekerja berbasis *multiset*, memperbolehkan duplikasi baris kecuali dinyatakan eksplisit dengan `DISTINCT` atau *primary key*.
* **NULL Handling**: Relasi Codd murni tidak mendefinisikan *null marker* secara fleksibel. SQL mengadopsi logika tiga nilai (*Three-Valued Logic* / 3VL): `TRUE`, `FALSE`, dan `UNKNOWN` untuk menangani *missing information*.

### 2. Implementasi & Contoh Kasus Nyata

Kode DDL dan DML ANSI-SQL berikut mengimplementasikan integritas relasional: *Entity Integrity* (Primary Key), *Referential Integrity* (Foreign Key), dan *Domain Integrity* (Data Type & Check Constraints).

```sql
-- DDL: Mendefinisikan Domain dan Relasi Logis
CREATE TABLE customers (
    customer_id   BIGINT GENERATED ALWAYS AS IDENTITY,
    email         VARCHAR(255) NOT NULL,
    full_name     VARCHAR(100) NOT NULL,
    created_at    TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    
    -- Entity Integrity: Menjamin keunikan tupel
    CONSTRAINT pk_customers PRIMARY KEY (customer_id),
    CONSTRAINT uq_customers_email UNIQUE (email)
);

CREATE TABLE orders (
    order_id      BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id   BIGINT NOT NULL,
    total_amount  NUMERIC(12, 2) NOT NULL,
    order_status  VARCHAR(20) NOT NULL,
    order_date    TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    
    CONSTRAINT pk_orders PRIMARY KEY (order_id),
    -- Referential Integrity: Menghubungkan relasi secara formal
    CONSTRAINT fk_orders_customers 
        FOREIGN KEY (customer_id) 
        REFERENCES customers (customer_id) 
        ON DELETE RESTRICT,
    -- Domain Integrity: Validasi nilai atribut pada tingkat basis data
    CONSTRAINT chk_orders_amount CHECK (total_amount >= 0.00),
    CONSTRAINT chk_orders_status CHECK (order_status IN ('PENDING', 'PAID', 'CANCELLED'))
);

-- DML: Memasukkan Data Sesuai Batasan Relasi
INSERT INTO customers (email, full_name) 
VALUES 
    ('alice@example.com', 'Alice Smith'),
    ('bob@example.com', 'Bob Johnson');

INSERT INTO orders (customer_id, total_amount, order_status)
VALUES 
    (1, 150.50, 'PAID'),
    (1, 45.00, 'PENDING');

-- Implementasi Aljabar Relasional dalam SQL:
-- Proyeksi (\pi), Seleksi (\sigma), dan Natural Join (\bowtie)
SELECT 
    c.customer_id,
    c.full_name,
    o.order_id,
    o.total_amount
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id -- Theta-Join / Equi-Join
WHERE o.order_status = 'PAID';                        -- Selection: \sigma_{status='PAID'}
```

#### Penjelasan Komponen Kunci:
1. `GENERATED ALWAYS AS IDENTITY`: Menjamin nilai unik untuk *surrogate primary key* tanpa bergantung pada *trigger* atau *sequence manual*.
2. `ON DELETE RESTRICT`: Menegakkan *Referential Integrity*. Mesin RDBMS menolak penghapusan baris pada tabel `customers` jika masih ada baris terkait pada tabel `orders`, mencegah terjadinya *orphan records*.
3. `CHECK (total_amount >= 0.00)`: Mengisolasi logika validasi bisnis tingkat domain ke dalam basis data, menjamin integritas data tidak bergantung sepenuhnya pada lapisan kode aplikasi.

### 3. Cara Kerja di Balik Layar (Under the Hood)

Ketika sebuah kueri SQL dikirimkan ke mesin RDBMS (misal: PostgreSQL, MySQL InnoDB), arsitektur *under-the-hood* bekerja memproses pernyataan deklaratif menjadi eksekusi fisik imperatif.

```
       Query SQL String
              │
              ▼
    ┌───────────────────┐
    │      Parser       │ ──> Menghasilkan Abstract Syntax Tree (AST)
    └───────────────────┘
              │
              ▼
    ┌───────────────────┐
    │ Analyzer/Catalog  │ ──> Validasi skema, hak akses, & tipe data
    └───────────────────┘
              │
              ▼
    ┌───────────────────┐
    │  Query Optimizer  │ ──> Cost-Based Optimizer (CBO)
    │       (CBO)       │     Mengubah Aljabar Relasional -> Physical Execution Plan
    └───────────────────┘
              │
              ▼
    ┌───────────────────┐
    │ Execution Engine  │ ──> Menggunakan Volcano Iterator Model (next())
    └───────────────────┘
              │
              ▼
    ┌───────────────────┐
    │ Buffer Pool / I/O │ ──> Membaca blok data/index dari disk ke RAM
    └───────────────────┘
```

#### 1. Eksekusi & Runtime: Volcano Iterator Model
Sebagian besar mesin relasional klasik mengimplementasikan pemrosesan kueri berbasis model iterator (juga dikenal sebagai *Volcano Model*). Setiap node dalam *execution plan* mengimplementasikan interface standar:
* `open()`: Menginisialisasi *state* operator.
* `next()`: Menghasilkan tupel tunggal berikutnya ke operator di atasnya (*pull-based processing*).
* `close()`: Membersihkan alokasi memori operator.

Contoh pada query `JOIN`: Node `Hash Join` memanggil `next()` pada tabel luar (*probe phase*) hanya setelah tabel dalam sepenuhnya dibaca ke dalam memori (*build phase*).

#### 2. Query Optimizer (Cost-Based Optimizer / CBO)
Optimizer mengonversi query deklaratif menjadi representasi pohon aljabar relasional, lalu menerapkan aturan ekuivalensi (misal: memindahkan operator `Selection` sedekat mungkin ke pembacaan disk—dikenal sebagai *Predicate Pushdown*). Optimizer menghitung estimasi biaya (*I/O cost* dan *CPU cost*) untuk puluhan permutasi eksekusi menggunakan statistik data (distribusi histogram nilai atribut).

#### 3. Alokasi Memori & Disk Storage (Slotted Page Architecture)
Tupel fisik tidak disimpan langsung sebagai baris teks berurutan, melainkan dalam struktur halaman memori/disk berukuran tetap (misal: 8 KB pada PostgreSQL, 16 KB pada MySQL InnoDB).

* Setiap halaman memiliki **Page Header** yang berisi metadata.
* **Line Pointers / Slot Array** tumbuh dari awal halaman ke arah dalam, menyimpan *offset* byte ke data baris sesungguhnya.
* **Tuple Storage** tumbuh dari akhir halaman ke arah luar (*reverse order*).
* Desain ini memungkinkan pengalamatan tupel menggunakan `Tuple ID (TID) / Item Pointer (ctid)` berupa kombinasi `(Block Number, Slot Index)`. Posisi baris fisik dapat berpindah di dalam satu blok (misal saat *defragmentation*) tanpa memutus referensi indeks eksternal.

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Normalisasi hingga minimal Third Normal Form (3NF)**: Reduksi redundansi struktural untuk mencegah *Insertion, Update,* dan *Deletion Anomalies*. Lakukan denormalisasi terkendali hanya untuk optimasi analitikal atau beban kerja pembacaan tinggi setelah terbukti adanya *bottleneck*.
2. **Definisikan Constraints Eksplisit di Level Basis Data**: Jangan mengandalkan integritas relasional hanya pada *application layer*. Validasi di aplikasi rentan gagal saat terjadi *race condition*, penggunaan *multi-client*, atau proses *data migration* ad-hoc.
3. **Pahami Three-Valued Logic (3VL)**: Nilai `NULL` merepresentasikan "tidak diketahui" (*unknown*), bukan angka nol atau string kosong. Operasi perbandingan seperti `NULL = NULL` menghasilkan evaluasi boolean `UNKNOWN`, bukan `TRUE`.

#### Don'ts
1. **Pola Desain EAV (Entity-Attribute-Value)**: Menyimpan skema dalam baris (`entity_id`, `attribute_name`, `value`) merusak model relasional. CBO tidak dapat memanfaatkan statistik kolom secara akurat, tipe data kehilangan integritas (*everything is string*), dan operasi `JOIN` menjadi eksponensial.
2. **Multi-Valued Attributes (Pelanggaran 1NF)**: Menyimpan data yang dipisahkan koma (*CSV-in-a-column*) seperti `tags = 'tech,sql,db'` menghancurkan indexing, mencegah penggunaan *foreign keys*, dan memaksa operasi `FULL TABLE SCAN` menggunakan operator string `LIKE '%sql%'`.
3. **Mengabaikan Karakteristik Multisets**: Melakukan `UNION` ketika sebenarnya membutuhkan `UNION ALL`. `UNION` memaksa mesin basis data melakukan operasi deduplikasi (melalui *Sort* atau *Hash Aggregate*) di memori/disk yang sangat membebani CPU dan memori.

#### Edge Cases
* **Outer Join dengan Predikat pada Klausul WHERE vs. ON**:
  Menempatkan predikat filter pada tabel kanan di dalam klausul `WHERE` pada `LEFT JOIN` secara implisit mengubah operasi menjadi `INNER JOIN`, karena nilai `NULL` yang digenerasi oleh tabel yang hilang akan dieliminasi oleh filter `WHERE`.
  
  ```sql
  -- BUG: LEFT JOIN bermutasi menjadi INNER JOIN karena o.order_status = 'PAID'
  -- mengeliminasi baris di mana customer tidak memiliki order (o.order_status IS NULL)
  SELECT c.customer_id, o.order_id
  FROM customers c
  LEFT JOIN orders o ON c.customer_id = o.customer_id
  WHERE o.order_status = 'PAID';

  -- BENAR: Menjaga semua customer tetap muncul, memfilter hanya order yang berelasi
  SELECT c.customer_id, o.order_id
  FROM customers c
  LEFT JOIN orders o ON c.customer_id = o.customer_id 
                    AND o.order_status = 'PAID';
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Dekonstruksi Execution Plan**:
   Jalankan perintah `EXPLAIN (ANALYZE, BUFFERS)` (pada PostgreSQL) atau `EXPLAIN FORMAT=JSON` (pada MySQL) untuk query `INNER JOIN` antara dua tabel di atas. Identifikasi node manakah yang mewakili implementasi fisik dari operasi seleksi ($\sigma$), proyeksi ($\pi$), dan join ($\bowtie$).
2. **Eksplorasi Anomali Tanpa Integritas Relasional**:
   Rancang sebuah tabel tunggal denormalisasi `orders_flat` yang menggabungkan seluruh informasi pelanggan dan pesanan. Simulasikan tiga anomali relasional klasik:
   * *Insertion Anomaly*: Bisakah Anda mencatat pelanggan baru yang belum pernah melakukan pemesanan tanpa mengisi nilai atribut pesanan dengan `NULL`?
   * *Deletion Anomaly*: Jika satu-satunya pesanan dari seorang pelanggan dihapus, apakah data profil pelanggan tersebut ikut terhapus secara permanen?
   * *Update Anomaly*: Ubah alamat email seorang pelanggan yang memiliki 10.000 riwayat transaksi. Berapa baris data yang harus dimutasi untuk menjaga konsistensi?
