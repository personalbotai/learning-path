## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Perintah `CREATE TABLE` adalah komponen inti dari *Data Definition Language* (DDL). Pernyataan ini bukan sekadar membuat representasi visual sebuah tabel, melainkan mendefinisikan *logical schema*, *physical layout*, serta *integrity constraints* dari data yang akan disimpan ke dalam storage engine (seperti InnoDB pada MySQL atau Heap Storage pada PostgreSQL).

Saat perintah `CREATE TABLE` dikirimkan ke database:
1. **Parser & Lexer**: Database engine mengurai query menjadi *Abstract Syntax Tree* (AST) untuk memverifikasi validitas sintaks.
2. **Catalog & Dictionary Update**: Engine mendaftarkan metadata tabel ke dalam *System Catalog* internal (misalnya `pg_class` & `pg_attribute` di PostgreSQL, atau *Data Dictionary* di MySQL 8.0). Metadata ini mencakup tipe data tiap kolom, urutan kolom, constraint, dan kolasi.
3. **Physical Allocation Handshake**: Storage engine menginisialisasi pointer disk atau file tablespace khusus (seperti file `.ibd` per tabel pada InnoDB jika opsi `innodb_file_per_table` aktif). Belum ada alokasi data block/page nyata untuk *record*, namun struktur b-tree untuk *Clustered Index* (Primary Key) sudah disiapkan di tingkat metadata.
4. **Metadata Lock (MDL)**: Engine mengakuisisi *exclusive lock* sementara pada catalog level guna menjamin tidak ada konkurensi operasi DDL/DML lain yang merusak konsistensi skema.

Konsep utama yang ditentukan saat pembuatan tabel:
- **Tipe Data & Ukuran Fisik**: Menentukan apakah sebuah kolom memiliki panjang tetap (*fixed-length*, misal `INT`, `CHAR`) atau dinamis (*variable-length*, misal `VARCHAR`, `TEXT`), yang berdampak langsung pada pemanfaatan page memory.
- **Constraints (Integritas Data)**: Menentukan validasi tingkat rendah yang dijalankan engine (misal `NOT NULL`, `CHECK`, `UNIQUE`, `FOREIGN KEY`) sebelum baris disimpan.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh pembuatan tabel modern berstandar enterprise (menggunakan dialek PostgreSQL/ANSI SQL modern) untuk entitas pesanan (*Order*) dengan auditing, integritas ketat, dan optimasi tipe data.

```sql
-- Pastikan extension pgcrypto/uuid tersedia jika menggunakan UUID v4
-- CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE orders (
    -- 1. Primary Key: Penggunaan BIGINT GENERATED ALWAYS AS IDENTITY (ANSI Standard modern)
    -- Lebih disukai dibanding tipe SERIAL non-standar.
    id BIGINT GENERATED ALWAYS AS IDENTITY,
    
    -- 2. UUID publik untuk eksposur API (mencegah enumerasi ID sequential di publik)
    order_uuid UUID NOT NULL DEFAULT gen_random_uuid(),
    
    -- 3. Foreign Key relasional
    customer_id BIGINT NOT NULL,
    
    -- 4. Variabel finansial: JANGAN PERNAH gunakan FLOAT/DOUBLE. 
    -- NUMERIC/DECIMAL menggunakan representasi fixed-point exact.
    total_amount NUMERIC(12, 4) NOT NULL,
    discount_amount NUMERIC(12, 4) NOT NULL DEFAULT 0.0000,
    
    -- 5. Tipe data terbatas & CHECK constraint untuk validasi status
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    
    -- 6. Audit timestamp menggunakan UTC eksplisit (TIMESTAMPTZ)
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- CONSTRAINT DEFINITIONS (Didefinisikan eksplisit dengan penamaan standar)
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT uq_orders_uuid UNIQUE (order_uuid),
    CONSTRAINT chk_orders_total_positive CHECK (total_amount >= 0),
    CONSTRAINT chk_orders_discount_valid CHECK (discount_amount >= 0 AND discount_amount <= total_amount),
    CONSTRAINT chk_orders_status_enum CHECK (status IN ('PENDING', 'PAID', 'SHIPPED', 'CANCELLED', 'REFUNDED')),
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) 
        REFERENCES customers (id) 
        ON DELETE RESTRICT 
        ON UPDATE CASCADE
);
```

#### Penjelasan Komponen Kunci:
- `GENERATED ALWAYS AS IDENTITY`: Mencegah modifikasi manual kolom primary key secara tidak sengaja, menggantikan implementasi `SERIAL` lama.
- `NUMERIC(12, 4)`: Mengalokasikan 12 digit presisi total dengan 4 digit di belakang koma. Engine menyimpannya dalam format biner terkompresi tanpa *floating-point rounding errors*.
- `TIMESTAMPTZ`: Menyimpan waktu dalam format epoch UTC. Engine mengonversi input berdasarkan zona waktu sesi, mencegah anomali *daylight saving* atau perpindahan server.
- Penamaan Constraint Eksplisit (`pk_`, `uq_`, `chk_`, `fk_`): Mempermudah debugging log saat constraint violation terjadi di application layer.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Setiap baris data (*tuple* atau *record*) yang masuk nantinya disimpan dalam struktur **Slotted Page** (berukuran default 8KB di PostgreSQL atau 16KB di MySQL/InnoDB).
- Header dari setiap page menyimpan pointer offset menuju tuple fisik di dasar page.
- Baris data terdiri dari: **Row Header** (metadata status transaksi MVCC, bitmask NULL), diikuti oleh kolom-kolom data fisik.

#### Alokasi Memori / Resource & CPU Alignment
Salah satu faktor performa yang jarang disadari developer adalah **Column Alignment Padding**:
- CPU modern membaca data dari RAM paling efisien dalam word boundary (kelipatan 2, 4, atau 8-byte).
- Jika sebuah kolom 2-byte (`SMALLINT`) diikuti oleh kolom 8-byte (`BIGINT`), engine (khususnya PostgreSQL) akan menyisipkan 6-byte kosong (*padding*) di dalam disk page agar `BIGINT` tepat berada di alignment boundary 8-byte.
- **Dampak Storage**: Menyusun kolom secara sembarangan dari tipe kecil ke besar secara acak dapat meningkatkan ukuran tabel di disk hingga 20-30% murni karena waste padding.

#### Trade-offs
- **Banyak Constraint vs Write Throughput**: Setiap kali ada `INSERT`, engine harus memvalidasi seluruh `CHECK` constraint, mengecek B-Tree index pada `UNIQUE` constraint, dan membaca foreign table pada `FOREIGN KEY`. Semakin ketat DDL, semakin tinggi overhead write latency.
- **NULL Bitmap Overhead**: Mengizinkan banyak kolom `NULLABLE` memaksa engine menyisipkan `NULL bitmap` di header baris. Sebaliknya, deklarasi `NOT NULL` yang ketat memungkinkan optimasi traversal byte oleh query executor.

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Urutkan Kolom Berdasarkan Alignment Boundary (PostgreSQL optimization)**: Tempatkan tipe data fixed 8-byte (`BIGINT`, `TIMESTAMPTZ`, `DOUBLE PRECISION`) di awal, diikuti tipe 4-byte (`INT`), 2-byte (`SMALLINT`), dan diakhiri dengan tipe dinamis (`VARCHAR`, `TEXT`, `JSONB`).
2. **Definisikan Nama Constraint Secara Eksplisit**: Hindari membiarkan sistem membuat nama acak seperti `orders_check_1`. Berikan nama semantik: `chk_orders_status`.
3. **Selalu Tentukan NOT NULL Jika Memungkinkan**: Kolom yang nullable memperlambat query optimizer dan menambah kompleksitas logika aplikasi (handling kondisi three-valued logic: `TRUE`, `FALSE`, `UNKNOWN`).

#### Don'ts:
1. **Jangan Gunakan FLOAT/DOUBLE untuk Uang**: Pembulatan biner IEEE 754 akan menyebabkan selisih desimal fraksional yang berakibat fatal pada pembukuan finansial. Gunakan `NUMERIC`/`DECIMAL`.
2. **Jangan Menggunakan VARCHAR(255) Sebagai 'Default Mental'**: Di beberapa engine lama, angka 255 memiliki arti historis. Di engine modern, gunakan panjang yang mencerminkan batasan bisnis riil, atau gunakan `TEXT` dengan `CHECK (length(col) <= N)` jika batasannya fleksibel.
3. **Hindari Composite Primary Key yang Terlalu Lebar**: Menggunakan 3 atau 4 kolom string sebagai Primary Key akan menduplikasi seluruh data tersebut ke setiap *Secondary Index*, menyebabkan pembengkakan memori (buffer pool exhaustion).

#### Edge Cases:
- **Circular Foreign Keys**: Membuat Tabel A yang memiliki FK ke Tabel B, sementara Tabel B memiliki FK ke Tabel A. Solusi: Buat tabel terlebih dahulu tanpa FK, lalu gunakan `ALTER TABLE ... ADD CONSTRAINT` dengan status `DEFERRABLE INITIALLY DEFERRED`.
- **Large Objects / TOAST / Off-page Storage**: Jika ukuran baris melebihi batas ukuran page (misalnya menyimpan string raksasa di `TEXT` atau dokumen di `JSONB`), engine akan memindahkan data tersebut ke area *Out-of-line storage* (TOAST di Postgres). Hal ini menurunkan performa scan tabel jika kolom tersebut sering diakses.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Kasus Column Padding**:
   Buat dua tabel identik dengan 10 juta baris dummy:
   - Tabel 1: Kolom diacak urutannya (`SMALLINT`, `BIGINT`, `SMALLINT`, `BIGINT`).
   - Tabel 2: Kolom diurutkan berdasarkan ukuran fisik (`BIGINT`, `BIGINT`, `SMALLINT`, `SMALLINT`).
   Gunakan query `pg_total_relation_size()` (Postgres) atau periksa ukuran file `.ibd` (MySQL). Amati perbedaan ukuran disk-nya.

2. **Forensik Engine Dictionary**:
   Eksekusi query `CREATE TABLE test_catalog (id INT);` lalu lakukan *reverse inspection* terhadap metadata internal database:
   - Di PostgreSQL: Jalankan `SELECT * FROM pg_class WHERE relname = 'test_catalog';` dan `SELECT * FROM pg_attribute WHERE attrelid = 'test_catalog'::regclass;`.
   - Analisis kolom apa saja yang digenerate oleh engine di balik layar (misal: `xmin`, `xmax`, `ctid`).
