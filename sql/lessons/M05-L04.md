## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

*Column constraints* (konstraint kolom) adalah aturan deklaratif yang diterapkan pada skema basis data relasional (RDBMS) untuk memastikan **Domain Integrity** dan **Entity Integrity**. Alih-alih membiarkan integritas data bergantung sepenuhnya pada validasi aplikasi (yang rentan terhadap *race condition*, *bug* rilis, atau *bypass* melalui skrip migrasi), *constraint* dieksekusi langsung oleh RDBMS *storage engine* pada layer terendah.

Secara arsitektural, tiga *constraint* inti yang sering digunakan bersamaan adalah:

1. **`UNIQUE` (Entity/Key Integrity)**:
   - **Konsep**: Menjamin bahwa tidak ada dua baris yang memiliki nilai identik pada satu atau kombinasi kolom (*composite*).
   - **Arsitektur Internal**: Menerapkan `UNIQUE` secara otomatis menginstruksikan database engine (seperti PostgreSQL atau MySQL InnoDB) untuk mengalokasikan struktur data indeks fisik (umumnya B-Tree). Validasi keunikan tidak dilakukan dengan *full table scan*, melainkan dengan *index lookup* logaritmik $\mathcal{O}(\log N)$.
   - **Perilaku `NULL`**: Mengacu pada standar ANSI SQL, nilai `NULL` merepresentasikan *unknown value*. Oleh karena itu, secara *default* `NULL != NULL`. Sebagian besar mesin database (PostgreSQL, MySQL) mengizinkan beberapa nilai `NULL` pada kolom `UNIQUE`, kecuali ditentukan lain menggunakan sintaks modern seperti `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15+).

2. **`CHECK` (Domain Integrity)**:
   - **Konsep**: Membatasi rentang atau format data melalui evaluasi ekspresi *boolean* deterministik.
   - **Arsitektur Internal**: RDBMS menyematkan ekspresi `CHECK` ke dalam *execution plan* mutasi data (`INSERT` / `UPDATE`). Sebelum sebuah *tuple* (baris) ditulis ke dalam *memory buffer* (PostgreSQL *shared buffers* atau InnoDB *buffer pool*) dan di-commit ke Write-Ahead Log (WAL), *expression evaluation engine* mengevaluasi predikat tersebut.
   - **Three-Valued Logic (3VL)**: Operasi `CHECK` lolos jika predikat bernilai `TRUE` **atau** `UNKNOWN` (hasil perbandingan dengan `NULL`). *Constraint* hanya akan melempar pelanggaran (*violation*) jika ekspresi secara eksplisit bernilai `FALSE`.

3. **`DEFAULT` (Data Synthesis/Fallback)**:
   - **Konsep**: Menyediakan nilai fallback ketika *statement* manipulasi data tidak menyertakan kolom terkait secara eksplisit.
   - **Arsitektur Internal**: Bukan merupakan mekanisme validasi, melainkan operasi *rewrite* pada fase parsing/perencanaan query (*query rewriter*). Nilai default bisa bersifat statis (literal, misal `'active'`) atau dinamis yang memanggil fungsi engine (misal `CURRENT_TIMESTAMP`, `gen_random_uuid()`).

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Merancang skema tabel akun finansial dan dompet digital (*e-wallet*) yang menuntut integritas data absolut.

```sql
-- Pastikan ekstensi UUID aktif jika menggunakan PostgreSQL
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- Enum status akun
CREATE TYPE account_status AS ENUM ('active', 'suspended', 'closed');

-- Pembuatan tabel dengan variasi UNIQUE, CHECK, dan DEFAULT
CREATE TABLE user_wallets (
    wallet_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- UNIQUE: Nomor rekening tidak boleh kembar
    account_number VARCHAR(20) NOT NULL,
    
    -- DEFAULT: Literal string, CHECK: Format string dengan regex (POSISIX)
    currency_code VARCHAR(3) DEFAULT 'IDR' NOT NULL,
    
    -- CHECK: Saldo riil tidak boleh bernilai negatif (mencegah overdraft yang tak diinginkan)
    balance NUMERIC(15, 2) DEFAULT 0.00 NOT NULL,
    
    -- CHECK: Hold balance tidak boleh melebihi total balance
    hold_balance NUMERIC(15, 2) DEFAULT 0.00 NOT NULL,
    
    status account_status DEFAULT 'active' NOT NULL,
    
    -- DEFAULT: Dinamis berbasis fungsi waktu sistem
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,

    -- Table-level UNIQUE: Satu user hanya boleh memiliki satu jenis currency tertentu
    user_id UUID NOT NULL,
    CONSTRAINT uq_user_currency UNIQUE (user_id, currency_code),

    -- Table-level CHECK: Menjamin hubungan multi-kolom yang valid
    CONSTRAINT chk_balances_logic CHECK (
        balance >= 0 AND 
        hold_balance >= 0 AND 
        hold_balance <= balance
    ),
    
    -- Table-level CHECK: Currency code harus 3 huruf kapital
    CONSTRAINT chk_currency_format CHECK (currency_code ~ '^[A-Z]{3}$')
);

-- Pengujian Constraint:
-- 1. Berhasil: Menggunakan DEFAULT untuk wallet_id, currency_code, balance, hold_balance, timestamps
INSERT INTO user_wallets (user_id, account_number)
VALUES ('a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11', 'ACC-IDR-0001');

-- 2. Gagal: CHECK Violation (hold_balance > balance)
-- Error: new row for relation "user_wallets" violates check constraint "chk_balances_logic"
INSERT INTO user_wallets (user_id, account_number, balance, hold_balance)
VALUES ('a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11', 'ACC-IDR-0002', 1000.00, 2000.00);

-- 3. Gagal: UNIQUE Violation (user_id dan currency_code 'IDR' sudah ada)
-- Error: duplicate key value violates unique constraint "uq_user_currency"
INSERT INTO user_wallets (user_id, account_number, currency_code)
VALUES ('a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11', 'ACC-IDR-0003', 'IDR');
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Query Parsing & Rewriting (`DEFAULT`)**:
   Saat `INSERT` dieksekusi tanpa kolom tertentu, *Query Parser/Rewriter* mendeteksi ketiadaan nilai pada *target list*. Mesin lalu menginjeksi ekspresi default dari katalog sistem (`pg_attribute.atthasdef` pada PG). Jika nilainya adalah fungsi volatil seperti `gen_random_uuid()`, fungsi tersebut dipanggil per baris secara dinamis.
2. **Evaluasi Pipeline Mutasi (`CHECK`)**:
   Sebelum baris baru ditulis ke tabel *heap*, baris dilewatkan melalui *Executor Engine*. Komponen *Constraint Enforcement* menjalankan *expression tree* dari `CHECK`. Komparasi dievaluasi dalam CPU cycle mikro. Jika salah satu node menghasilkan `FALSE`, transaksi langsung di-*abort* dan melempar *exception*, mencegah I/O penulisan yang sia-sia ke *disk*.
3. **Penyisipan Indeks & Deteksi Konflik (`UNIQUE`)**:
   Sebelum transaksi dinyatakan *committed*, *tuple pointer* harus dimasukkan ke dalam B-Tree index yang mendasari `UNIQUE`. Mesin melakukan penelusuran dari *root* ke *leaf page*. Jika sebuah kunci yang sama telah ada pada *leaf page* dan transaksi yang memasukkannya sudah berstatus *committed*, terjadi *abort* seketika (`duplicate key error`).

#### Alokasi Memori / Resource
- **Overhead B-Tree (untuk `UNIQUE`)**: 
  Setiap *constraint* `UNIQUE` membutuhkan alokasi memori fisik untuk indeks B-Tree. Operasi `INSERT` dan `UPDATE` memicu *Write Amplification*: RDBMS harus menulis ke *heap page* sekaligus menyeimbangkan (*rebalancing/page split*) struktur pohon B-Tree indeks tersebut. Indeks ini juga memakan porsi di *buffer pool/shared memory*.
- **CPU Bound (untuk `CHECK`)**:
  `CHECK` berbasis regex (seperti `~ '^[A-Z]{3}$'`) membutuhkan *CPU parsing clock* tambahan dibanding komparasi integer sederhana (`balance >= 0`).

#### Trade-offs
- **Integritas Database vs. Throughput Tulis**: 
  Menambahkan banyak *constraint* memperlambat *bulk insert* atau penulisan intensif (*high-concurrency writes*) karena adanya verifikasi ekspresi konstan dan mutasi struktur indeks B-Tree `UNIQUE`.
- Namun, menyerahkan tugas ini ke layer aplikasi mengakibatkan *race condition* murni. Memeriksa keunikan data di aplikasi (`SELECT EXISTS` lalu `INSERT`) rentan terhadap celah waktu transaksi konkuren (*Time-of-check to time-of-use / TOCTOU*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Beri Nama Eksplisit pada Constraint**: 
  Selalu gunakan format konvensi seperti `chk_<table>_<kolom>` atau `uq_<table>_<kolom>`. Jika terjadi kegagalan di layer database, *error log* akan langsung menunjukkan constraint mana yang dilanggar tanpa perlu menelusuri nama acak bawaan sistem (seperti `user_wallets_check1`).
- **Gunakan Partial Unique Index untuk Soft Deletes**: 
  Jika menggunakan pola *soft delete* (kolom `deleted_at`), constraint `UNIQUE` standar akan mencegah pengguna mendaftar ulang dengan email yang sama. Gunakan indeks unik bersyarat:
  ```sql
  CREATE UNIQUE INDEX uq_users_active_email ON users (email) WHERE deleted_at IS NULL;
  ```
- **Terapkan `NOT VALID` saat Migrasi Data Besar**:
  Ketika menambahkan `CHECK` constraint ke tabel berukuran jutaan baris, gunakan mode bertahap (di PostgreSQL):
  ```sql
  ALTER TABLE user_wallets ADD CONSTRAINT chk_balance_positive CHECK (balance >= 0) NOT VALID;
  ALTER TABLE user_wallets VALIDATE CONSTRAINT chk_balance_positive;
  ```
  Ini mencegah *exclusive table lock* yang lama saat validasi baris lama berlangsung.

#### Don'ts
- **Jangan Mengandalkan CHECK Tanpa Menyadari Three-Valued Logic (3VL)**:
  Contoh: `CHECK (discount_rate < 0.5)` akan **tetap lolos** jika `discount_rate` bernilai `NULL`, karena `NULL < 0.5` bernilai `UNKNOWN`. Jika kolom tidak boleh kosong, sandingkan selalu dengan `NOT NULL`.
- **Jangan Menggunakan Fungsi Non-Deterministik pada CHECK**:
  Constraint `CHECK (created_at <= CURRENT_DATE)` adalah anti-pattern berat. `CURRENT_DATE` berubah setiap hari; akibatnya, *dump-and-restore* database atau *in-place table rewrite* di masa depan akan gagal total karena data lama menjadi tidak valid secara retrospektif. Fungsi dalam `CHECK` harus **bersifat *IMMUTABLE***.

#### Edge Cases
- **Multi-column NULL pada UNIQUE**:
  Pada ANSI SQL standar, komposit `UNIQUE (a, b)` akan tetap membiarkan duplikasi baris jika salah satu atau kedua kolom bernilai `NULL` (`(1, NULL)` dan `(1, NULL)` dianggap unik pada sebagian besar engine).

### 5. Tantangan Eksplorasi Mandiri

1. **Jebakan Three-Valued Logic pada CHECK**:
   Buat sebuah tabel sementara `promo_codes` dengan kolom `code VARCHAR(10)` dan constraint `CHECK (LENGTH(code) >= 5)`. Lakukan `INSERT` data dengan nilai `code` diisi `NULL`. Amati apakah database melempar *error* atau membiarkannya lolos. Mengapa hal tersebut terjadi secara spesifikasi ANSI SQL? Bagaimana cara memitigasinya secara tepat?
2. **Simulasi Race Condition pada Validasi Aplikasi vs UNIQUE Constraint**:
   Buat tabel sederhana tanpa constraint: `CREATE TABLE accounts (email TEXT);`. Buka dua sesi terminal terpisah (*concurrent transactions*), jalankan query pengecekan `SELECT COUNT(*) FROM accounts WHERE email = 'test@example.com';`, lalu lakukan `INSERT` secara bersamaan di kedua terminal sebelum melakukan `COMMIT`. Amati hasilnya. Tambahkan constraint `UNIQUE`, ulangi prosesnya, dan amati bagaimana database menangani konkurensi melalui mekanisme *lock / index abort*.
