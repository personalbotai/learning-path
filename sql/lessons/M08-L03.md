## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis dan implementatif, mayoritas Relational Database Management System (RDBMS) modern seperti PostgreSQL, MySQL (InnoDB), dan Oracle menggunakan varian **$B^+$-Tree** ketika mendefinisikan indeks `B-TREE`. Perbedaan fundamentalnya terletak pada penyimpanan data: pada $B^+$-Tree, *data record* atau *Tuple Pointer* (cth: Row ID / TID) hanya disimpan di level terbawah (**Leaf Nodes**), sedangkan **Internal Nodes** (Root dan Branch) secara eksklusif hanya menyimpan *search keys* dan *child page pointers* sebagai rute pemandu.

Arsitektur ini didesain spesifik untuk meminimalkan operasi I/O disk atau SSD. RDBMS membaca dan menulis data dalam unit blok bernama **Page** (atau *Block*, default 8 KB di PostgreSQL, 16 KB di InnoDB). Struktur pohon multi-tingkat ini memiliki komponen struktural utama:

```
                      [ Root Node (Page 0) ]
                            /         \
          [ Branch Node (Page 1) ]   [ Branch Node (Page 2) ]
                 /            \             /            \
        [ Leaf Page A ] <---> [ Leaf Page B ] <---> [ Leaf Page C ]
          (TIDs/Data)           (TIDs/Data)           (TIDs/Data)
```

1. **Root Node**: Titik masuk evaluasi query. Selalu dipertahankan dalam memori (*Buffer Cache/Pool*).
2. **Internal/Branch Nodes**: Node perantara yang bertindak sebagai pemetaan rentang nilai (*router*). Memiliki nilai **Fan-out** yang besar (ratusan *child pointers* per page), memungkinkan pohon tetap dangkal (*height* biasanya hanya 3 sampai 4 tingkat untuk jutaan baris data).
3. **Leaf Nodes**: Node terminal. Menyimpan nilai kunci indeks terurut beserta pointer ke lokasi fisik tabel (Heap Tuple ID di PostgreSQL, atau *Clustered Primary Key* di InnoDB). Antar-leaf node saling terhubung menggunakan **Doubly Linked List** (pointer *previous* dan *next*), memungkinkan *range-scan* berjalan sekuensial pada kompleksitas $O(N)$ tanpa perlu menelusuri kembali pohon ke arah atas.

#### Anatomi Fisik di Dalam Satu Page
Di dalam blok memori satu Page berukuran 8 KB (Postgres), struktur internal terbagi menjadi:
* **PageHeaderData**: Metadata halaman (LSN, free space bounds, flag).
* **Linp / Line Pointers (ItemId)**: Array offset 4-byte yang menunjuk ke lokasi byte aktual dari setiap *Index Tuple* di dalam halaman.
* **Special Space**: Terletak di akhir halaman, menyimpan metadata spesifik B-Tree (identitas page tetangga kiri/kanan, tipe node: *root*, *leaf*, *internal*).
* **Index Tuples**: Kunci data terurut yang tumbuh dari akhir halaman ke arah atas, mendekati array Line Pointer.

Pencarian nilai di dalam satu node menggunakan algoritma **Binary Search** lokal langsung di dalam memori cache CPU melalui array *Line Pointer*.

### 2. Implementasi & Contoh Kasus Nyata

Mari kita buktikan struktur internal ini pada PostgreSQL menggunakan ekstensi bawaan `pageinspect` untuk mengintip representasi biner B-Tree langsung dari storage engine.

```sql
-- 1. Setup ekstensi untuk inspeksi level storage
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- 2. Buat tabel pengujian dan index B-Tree standar
DROP TABLE IF EXISTS customer_orders;
CREATE TABLE customer_orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id INT NOT NULL,
    total_amount NUMERIC(10, 2),
    created_at TIMESTAMPTZ DEFAULT clock_timestamp()
);

-- Buat B-Tree Index pada customer_id
CREATE INDEX idx_orders_customer_id ON customer_orders USING btree (customer_id);

-- 3. Populasi dataset sintetis (100.000 baris) untuk memicu pembentukan multi-level tree
INSERT INTO customer_orders (customer_id, total_amount)
SELECT 
    (random() * 50000)::INT,
    (random() * 1000)::NUMERIC(10, 2)
FROM generate_series(1, 100000);

-- Paksa storage engine menulis buffer ke disk & perbarui statistik
VACUUM ANALYZE customer_orders;

-- 4. Inspeksi Statistik Global B-Tree (Root level, Height, Block counts)
SELECT 
    level,          -- Tinggi pohon dari root (0 = root adalah leaf)
    index_size,     -- Total byte ukuran index
    root_blkno,     -- Nomor block/page di mana Root berada
    fastroot_blkno  -- Fast root (optimasi level)
FROM bt_metap('idx_orders_customer_id');

-- 5. Inspeksi isi internal dari Page Root (Melihat data routing key dan child pointer)
-- Ganti parameter block kedua dengan root_blkno dari query sebelumnya (misal: block 3)
SELECT 
    itemoffset,    -- Posisi tuple di dalam page
    ctid,          -- Pointer: (block_id, offset) yang menunjuk ke child page berikutnya
    data           -- Representasi hex dari value key
FROM bt_page_items('idx_orders_customer_id', 3)
LIMIT 5;

-- 6. Analisis Query: Evaluasi Index Scan vs Bitmap Index Scan
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM customer_orders
WHERE customer_id BETWEEN 1000 AND 1050;
```

**Penjelasan Alur Eksekusi Query (Step 6):**
* Execution Engine memanggil B-Tree search routine (`_bt_search`).
* Engine membaca Block 3 (Root Node), melakukan binary search pada nilai `1000`.
* Pointer dari Block 3 mengarahkan traversal ke Internal Block berikutnya hingga menemukan Leaf Block spesifik.
* Sesampainya di Leaf Block target, engine membaca baris pertama, kemudian mengeksekusi *sequential read* melintasi *leaf node link* (`next pointer`) hingga menemukan batas atas `1050`.
* Metrik `BUFFERS: shared hit=...` pada `EXPLAIN` membuktikan berapa banyak page berukuran 8 KB yang diakses dari shared memory untuk menyelesaikan traversal pohon tersebut.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Setiap pencarian B-Tree memiliki kompleksitas waktu teoritis:
$$\text{Cost} = O(h + \log_2(K))$$
Di mana $h$ adalah *tree height* (tinggi pohon) dan $K$ adalah jumlah record yang diekstrak pada range scan. 

Saat baris baru di-*insert*:
1. RDBMS melintasi pohon dari root ke leaf node yang tepat berdasarkan urutan sorting data.
2. Jika leaf page masih memiliki *free space* (berdasarkan *Fillfactor*), tuple langsung disisipkan di posisi biner yang tepat.
3. **Page Split**: Jika leaf page penuh (8 KB habis), engine mengeksekusi operasi split:
   * Mengalokasikan page baru.
   * Memindahkan 50% elemen dari page lama ke page baru.
   * Menambahkan *High Key* pada page lama dan menyisipkan entry baru di parent branch node.
   * Jika parent node juga penuh, split berlanjut secara rekursif ke atas hingga dapat menciptakan root node baru (menambah *tree height*).

#### Alokasi Memori / Resource
* **Fan-Out Factor**: Jika ukuran rata-rata kunci indeks + pointer adalah 16 byte, maka satu page 8 KB (dikurangi header) dapat memuat sekitar:
  $$\text{Fan-out} \approx \frac{8192 - 100}{16} \approx 500 \text{ pointers/node}$$
  Dengan Fan-out 500:
  * Level 1 (Root): $500^1 = 500$ pages.
  * Level 2 (Branches): $500^2 = 250.000$ pages.
  * Level 3 (Leaves): $500^3 = 125.000.000$ leaf pages $\approx 1 \text{ Miliar record}$.
  Itulah alasan mengapa tinggi B-Tree jarang sekali melebihi 3 atau 4 level, membatasi disk read maksimum menjadi 3-4 I/O per pencarian titik tunggal.
* **Buffer Cache Priming**: Root dan intermediate nodes memiliki access frequency sangat tinggi, sehingga hampir 100% menetap di RAM (Buffer Pool), mengeliminasi latensi fisik disk storage.

#### Trade-offs
* **Keuntungan**: Optimal untuk *point lookup* (`=`), *range queries* (`BETWEEN`, `<`, `>`), dan pengurutan (`ORDER BY`) tanpa butuh fase explicit sorting di memori.
* **Kerugian**: Write Amplification masif. Setiap operasi `INSERT`, `UPDATE`, atau `DELETE` memaksa index B-Tree diperbarui. Page split menghasilkan alokasi disk non-sekuensial dan memicu operasi WAL (Write-Ahead Log) tambahan.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Patuhi Leftmost Prefix Rule pada Composite Index**: Jika membuat indeks pada `(tenant_id, created_at, status)`, query filter wajib menyertakan `tenant_id` agar traversal pohon dari root dapat berjalan.
* **Gunakan Fillfactor untuk Tabel Bersifat Write-Heavy**: Turunkan fillfactor indeks (misal: default 90 menjadi 70-80 di PostgreSQL) untuk memberikan ruang bagi *in-page updates* dan mencegah frekuensi *page split* yang destruktif:
  ```sql
  ALTER INDEX idx_orders_customer_id SET (fillfactor = 75);
  REINDEX INDEX idx_orders_customer_id;
  ```
* **Index pada Kolom High-Cardinality**: B-Tree bekerja paling efisien saat nilai kolom memiliki variasi unik yang tinggi.

#### Don'ts
* **Jangan Menggunakan Random UUID v4 sebagai Index Key**: Memasukkan string random 128-bit merusak lokalitas cache. Nilai acak menyebabkan insert harus disebarkan ke sembarang leaf page secara sporadis, memaksa *page split* 50% terjadi di seluruh struktur pohon (menyebabkan *Index Bloat* ekstrem). Gunakan UUIDv7 (time-ordered) atau BIGSERIAL.
* **Jangan Bungkus Kolom Indeks dengan Fungsi (SARGability Issue)**:
  ```sql
  -- BURUK: Mengabaikan struktur B-Tree, memicu Table Scan
  SELECT * FROM customer_orders WHERE DATE(created_at) = '2023-10-01';

  -- BAIK: SARGable, memungkinkan B-Tree Range Scan
  SELECT * FROM customer_orders 
  WHERE created_at >= '2023-10-01 00:00:00Z' AND created_at < '2023-10-02 00:00:00Z';
  ```

#### Edge Cases
* **Index Bloat Akibat DELETE Masif**: Menghapus data tidak otomatis mengecilkan ukuran fisik file B-Tree di disk. Halaman leaf yang kosong hanya ditandai sebagai *reusable* untuk data baru di masa depan. Jika pola akses data tidak lagi mengisi rentang nilai tersebut, lakukan `REINDEX CONCURRENTLY` untuk merekonstruksi pohon secara *in-place* tanpa me-lock operasi baca/tulis tabel.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Fragmentasi Page Split (UUIDv4 vs UUIDv7/Sequential)**:
   Buat dua tabel terpisah: Tabel A menggunakan `gen_random_uuid()` (UUIDv4) sebagai primary key, dan Tabel B menggunakan `BIGSERIAL`. Masukkan 500.000 data ke masing-masing tabel. Gunakan query `pg_relation_size()` dan fungsi `bt_page_stats()` dari `pageinspect` untuk mengukur perbedaan ukuran file indeks, total free space per page, dan jumlah level kedalaman pohon (*tree height*).

2. **Deteksi Leftmost Prefix Failure via EXPLAIN**:
   Rancang sebuah *composite index* tiga kolom: `CREATE INDEX idx_test ON table(col_a, col_b, col_c)`. Tulis tiga variasi query:
   * Menggunakan filter `col_a` dan `col_b`.
   * Menggunakan filter `col_b` dan `col_c`.
   * Menggunakan filter `col_a` dan `col_c`.
   Jalankan `EXPLAIN (ANALYZE, BUFFERS)` untuk ketiga skenario dan identifikasi perbedaan antara strategi `Index Scan`, `Index Only Scan`, dan `Bitmap Index Scan`. Kapan traversal berhenti memanfaatkan B-Tree secara optimal?
