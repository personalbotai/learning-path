## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Mayoritas sistem RDBMS (PostgreSQL, MySQL, Oracle) menerapkan **Rigid / Static Typing**: tipe data terikat secara absolut pada *definisi kolom*. Jika kolom didefinisikan sebagai `INTEGER`, mesin database akan menolak eksekusi `INSERT` untuk data string atau floating-point tanpa konversi eksplisit.

SQLite mengadopsi paradigma yang fundamental berbeda: **Dynamic Type System** dengan mekanisme yang disebut **Type Affinity**. Pada SQLite standar, tipe data tidak terikat pada kolom, melainkan terikat pada **nilai itu sendiri** (*the value itself*). 

#### Storage Classes vs Column Affinity
Arsitektur pengetikan SQLite terbagi menjadi dua lapisan:

1. **Storage Classes (Representasi Fisik di Disk/Memory)**:
   - `NULL`: Nilai kosong.
   - `INTEGER`: Bilangan bulat bertanda (signed integer), disimpan dalam 1, 2, 3, 4, 6, atau 8 byte tergantung magnitudo nilai.
   - `REAL`: Bilangan pecahan floating-point 8-byte IEEE.
   - `TEXT`: String teks, disimpan menggunakan encoding database (UTF-8, UTF-16BE, atau UTF-16LE).
   - `BLOB`: Binary Large Object, disimpan persis seperti input byte mentah (raw bytes).

2. **Column Affinity (Preferensi Konversi Kolom)**:
   Affinity adalah "rekomendasi" atau preferensi tipe bagi SQLite Engine saat menyimpan data ke kolom tersebut. Kolom dengan affinity tertentu akan mencoba mengonversi (cast) nilai yang masuk ke storage class preferensinya, **namun tidak membatalkannya jika konversi gagal**.

SQLite mengklasifikasikan deklarasi tipe menjadi 5 affinity rules berdasarkan pola string nama tipe pada DDL:
- **`INTEGER`**: Jika tipe mengandung substring `"INT"` (e.g., `INT`, `BIGINT`, `TINYINT`, `INTEGER`).
- **`TEXT`**: Jika tipe mengandung substring `"CHAR"`, `"CLOB"`, atau `"TEXT"` (e.g., `VARCHAR(255)`, `TEXT`).
- **`BLOB`**: Jika tidak ada tipe yang didefinisikan atau mengandung `"BLOB"`.
- **`REAL`**: Jika tipe mengandung `"REAL"`, `"FLOA"`, atau `"DOUB"` (e.g., `REAL`, `FLOAT`, `DOUBLE PRECISION`).
- **`NUMERIC`**: Mencakup semua tipe lainnya (e.g., `NUMERIC`, `DECIMAL`, `BOOLEAN`, `DATE`, `DATETIME`). Tipe ini mencoba konversi ke `INTEGER` terlebih dahulu, lalu `REAL`, dan jika gagal mempertahankan `TEXT`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mendemonstrasikan bagaimana Type Affinity bekerja pada tabel konvensional, bagaimana fungsi introspeksi `typeof()` mengekspos storage class, dan bagaimana tabel `STRICT` (tersedia sejak SQLite v3.37.0) menegakkan static typing.

```sql
-- 1. Setup Tabel Standar dengan Berbagai Affinity
CREATE TABLE transactions (
    id INTEGER PRIMARY KEY,           -- INTEGER affinity
    reference_code VARCHAR(32),        -- TEXT affinity
    amount NUMERIC,                   -- NUMERIC affinity
    payload BLOB                      -- BLOB affinity
);

-- 2. Memasukkan Data dengan Tipe Campuran
-- SQLite akan menerapkan aturan Type Coercion sesuai affinity
INSERT INTO transactions (id, reference_code, amount, payload) VALUES
  (1, 'TXN-001', '500.50', X'DEADBEEF'),    -- '500.50' (TEXT) dikonversi ke REAL oleh NUMERIC affinity
  (2, 123456, 1000, 'Raw string'),          -- 123456 (INTEGER) dikonversi ke TEXT oleh TEXT affinity
  (3, 'TXN-003', 'InvalidNumber', 42);      -- 'InvalidNumber' gagal dikonversi ke angka, tetap disimpan sebagai TEXT

-- 3. Introspeksi Storage Class Aktual Menggunakan typeof()
SELECT 
    id,
    reference_code, 
    typeof(reference_code) AS ref_type,
    amount, 
    typeof(amount)         AS amount_type,
    payload, 
    typeof(payload)        AS payload_type
FROM transactions;

/* Output:
id | reference_code | ref_type | amount        | amount_type | payload     | payload_type
---+----------------+----------+---------------+-------------+-------------+-------------
1  | TXN-001        | text     | 500.5         | real        | <BLOB>      | blob
2  | 123456         | text     | 1000          | integer     | Raw string  | text
3  | TXN-003        | text     | InvalidNumber | text        | 42          | integer
*/

-- 4. Perbandingan Berbahaya (Affinity Comparison Pitfall)
-- String comparison vs Numeric comparison
SELECT 
    ('40' < '5') AS str_compare,   -- 1 (True), evaluasi leksikografis ('4' < '5')
    (40 < 5)     AS num_compare,   -- 0 (False), evaluasi numerik
    ('40' < 5)   AS mixed_compare; -- 0 (False), aturan SQLite: NUMERIC/INTEGER selalu < TEXT

-- 5. Solusi Modern: Mode STRICT (SQLite >= 3.37.0)
CREATE TABLE strict_accounts (
    account_id INT PRIMARY KEY,
    holder_name TEXT NOT NULL,
    balance REAL
) STRICT;

-- Berhasil: Tipe data cocok
INSERT INTO strict_accounts VALUES (101, 'Alice', 1500.75);

-- Gagal: Result code SQLITE_CONSTRAINT_DATATYPE
-- SQLite menolak memasukkan String acak ke kolom balance bertipe REAL
-- INSERT INTO strict_accounts VALUES (102, 'Bob', 'Seribu Rupiah');
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Record Format)
SQLite menyimpan data baris (row) dalam format B-Tree payload menggunakan struktur serialisasi khusus:

```text
[Header Size (varint)] | [Serial Type 1] | [Serial Type 2] | ... | [Data Value 1] | [Data Value 2] | ...
```

- **Serial Type**: Menentukan tipe dan panjang data secara deterministik.
  - `0`: NULL
  - `1`: 8-bit Two's complement integer (1 byte)
  - `2`: 16-bit Two's complement integer (2 bytes)
  - `3`: 24-bit Two's complement integer (3 bytes)
  - `4`: 32-bit Two's complement integer (4 bytes)
  - `5`: 48-bit Two's complement integer (6 bytes)
  - `6`: 64-bit Two's complement integer (8 bytes)
  - `7`: IEEE 754-2008 64-bit floating point (8 bytes)
  - `8`: Integer konstanta 0 (0 byte alokasi)
  - `9`: Integer konstanta 1 (0 byte alokasi)
  - `N >= 12 dan Genap`: BLOB dengan panjang `(N-12)/2` bytes.
  - `N >= 13 dan Ganjil`: String TEXT dengan panjang `(N-13)/2` bytes.

#### Alokasi Memori / Resource
Ketika sebuah integer dimasukkan (misal: angka `42`), SQLite tidak secara otomatis mengalokasikan 4 atau 8 byte seperti engine `INT4`/`INT8` pada PostgreSQL. SQLite memeriksa magnitudo angka tersebut di runtime dan menyimpannya menggunakan **Serial Type 1** (1 byte fisik di disk). Ini memberikan rasio kompresi disk yang tinggi tanpa overhead kompresi algoritma CPU yang mahal.

#### Trade-offs
- **Keuntungan**: Fleksibilitas skema sangat tinggi. Efisiensi disk ekstrem karena alokasi disk bersifat variabel per entitas nilai, bukan per deklarasi skema.
- **Kerugian**: Tidak adanya integritas tipe secara default dapat meloloskan korupsi data logis (misal: aplikasi client memasukkan string `"N/A"` ke dalam kolom numerik tanpa memicu error). Dynamic casting di runtime juga menambah sedikit overhead inspeksi byte header saat evaluasi operator query.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Tabel `STRICT` untuk Aplikasi Baru**: Jika menggunakan SQLite v3.37+, selalu tambahkan keyword `STRICT` pada DDL tabel finansial atau transaksional guna memastikan integritas tipe setara dengan PostgreSQL/MySQL.
- **Gunakan Tipe Standar SQLite**: Batasi penamaan tipe skema ke: `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, `ANY` (hanya pada mode `STRICT`).
- **Lakukan Casting Eksplisit pada Operasi Logika**: Saat membandingkan nilai dari parameter aplikasi dengan kolom SQLite, gunakan `CAST(column AS <TYPE>)` jika tidak yakin mengenai affinity kolom tujuan.

#### Don'ts
- **Jangan Percaya Limit Panjang Karakter**: Menulis `VARCHAR(50)` di SQLite **tidak membatasi** string menjadi 50 karakter. SQLite memetakan ini menjadi `TEXT` affinity dan dengan senang hati menerima string berukuran 10 MB tanpa error.
- **Jangan Menyimpan Format Tanggal Secara Implisit**: SQLite tidak memiliki storage class `DATETIME`. Gunakan string ISO-8601 (`TEXT`), Epoch unix timestamp (`INTEGER`), atau Julian day numbers (`REAL`). Lakukan standardisasi satu format di seluruh basis kode.

#### Edge Cases
- **Kolom `INTEGER PRIMARY KEY` (Rowid Alias)**: Kolom yang didefinisikan persis sebagai `INTEGER PRIMARY KEY` adalah alias langsung dari *64-bit signed rowid* mesin B-Tree internal SQLite. Namun, jika Anda mendeklarasikannya sebagai `INT PRIMARY KEY` (tanpa kata penuh `INTEGER`), SQLite **tidak** menjadikannya alias rowid, melainkan kolom biasa dengan INTEGER affinity. Akibatnya, perilaku auto-increment rowid tidak berlaku.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Binary Ordering Kolom Campuran**:
   Buat sebuah tabel sementara `CREATE TABLE mixed (val ANY);`. Masukkan 5 baris yang merepresentasikan masing-masing storage class (`NULL`, `10`, `3.14`, `'Hello'`, `X'FF'`). Jalankan query `SELECT val, typeof(val) FROM mixed ORDER BY val ASC;`. Pelajari aturan urutan preseden evaluasi sorting yang diterapkan SQLite terhadap storage classes yang berbeda.

2. **Benchmarking Transisi Skema ke Strict**:
   Tulis script SQL yang mengonversi tabel non-strict berisi 100.000 baris acak (dengan potensi dirty data teks pada kolom angka) ke format tabel `STRICT`. Tangani data error menggunakan fungsi `WHERE typeof(...) != '...'` sebelum data dimigrasikan dengan syntax `INSERT INTO ... SELECT`.
