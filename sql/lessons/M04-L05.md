## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

*Self Join* bukanlah tipe join ANSI-SQL yang terpisah (seperti `INNER`, `LEFT`, atau `FULL OUTER`), melainkan sebuah teknik operasional di mana sebuah tabel dihubungkan (*joined*) dengan dirinya sendiri. Kebutuhan ini muncul saat sebuah relasi entitas bersifat refleksif (*unary relationship*), di mana suatu baris data memiliki ketergantungan semantik terhadap baris lain di dalam tabel yang sama.

```
+-------------------------------------------------------------+
|                     Tabel: employees                        |
+----+-------------------+------------+-----------------------+
| id | name              | manager_id | ...                   |
+----+-------------------+------------+-----------------------+
|  1 | Alice (CEO)       | NULL       |                       |
|  2 | Bob (VP Eng)      | 1          | -----> Mereferensikan |
|  3 | Charlie (Dev Sr)  | 2          | -----> id pada tabel  |
+----+-------------------+------------+ -----> yang sama      |
```

Model hirarki seperti ini umumnya diimplementasikan menggunakan pola **Adjacency List Model**, di mana setiap record menyimpan referensi langsung (*foreign key*) ke *parent*-nya melalui kolom semacam `parent_id` atau `manager_id`.

#### Mengapa Self Join Dibutuhkan?
Di *relational engine*, data disimpan dalam tupel individual tanpa *pointer* memori persisten ke baris lain. Untuk menyandingkan atribut dari baris *child* (misal: nama staf) dengan atribut baris *parent* (misal: nama manajer) dalam satu *result set* tabular, kita harus menginstruksikan *query planner* untuk memperlakukan satu tabel fisik seolah-olah menjadi dua relasi logis yang independen.

Hal ini dilakukan melalui mekanisme **Table Aliasing**. Tanpa alias pembeda, *SQL parser* akan melempar kesalahan ambiguitas nama atribut (*ambiguous column reference*) saat membangun *Abstract Syntax Tree* (AST).

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Sistem manajemen organisasi perusahaan dan penentuan struktur pelaporan karyawan, termasuk mendeteksi *root* (pimpinan puncak) dan hierarki berjenjang (karyawan -> manajer -> direktur).

```sql
-- DDL & DML Setup
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    job_title VARCHAR(50) NOT NULL,
    manager_id INT NULL,
    CONSTRAINT fk_manager 
        FOREIGN KEY (manager_id) 
        REFERENCES employees(employee_id)
);

-- Indexing foreign key adalah syarat mutlak performa join
CREATE INDEX idx_employees_manager_id ON employees(manager_id);

INSERT INTO employees (employee_id, full_name, job_title, manager_id) VALUES
(1, 'Siti Rahma', 'Chief Executive Officer', NULL),
(2, 'Budi Santoso', 'VP of Engineering', 1),
(3, 'Dewi Lestari', 'VP of Product', 1),
(4, 'Eko Kurniawan', 'Engineering Manager', 2),
(5, 'Fajar Nugraha', 'Senior Backend Engineer', 4),
(6, 'Gita Gutawa', 'Product Manager', 3);
```

#### Query 1: Menampilkan Karyawan Beserta Manajer Langsungnya (1-Level Hierarchy)
Gunakan `LEFT JOIN` agar baris *root* (CEO) yang memiliki `manager_id = NULL` tidak tereliminasi dari hasil query.

```sql
SELECT 
    emp.employee_id AS staff_id,
    emp.full_name AS staff_name,
    emp.job_title AS staff_title,
    COALESCE(mgr.full_name, 'TOP LEVEL / NO MANAGER') AS direct_manager,
    mgr.job_title AS manager_title
FROM 
    employees emp
LEFT JOIN 
    employees mgr ON emp.manager_id = mgr.employee_id
ORDER BY 
    emp.employee_id;
```

#### Query 2: Multi-level Self Join (Karyawan -> Manajer -> Direktur)
Untuk hierarki fixed-depth (tingkat kedalaman statis), *self join* dapat di-*chain*.

```sql
SELECT 
    e.full_name AS employee,
    m.full_name AS direct_manager,
    d.full_name AS director
FROM 
    employees e
LEFT JOIN 
    employees m ON e.manager_id = m.employee_id
LEFT JOIN 
    employees d ON m.manager_id = d.employee_id
WHERE 
    e.job_title = 'Senior Backend Engineer';
```

#### Query 3: Menemukan Rekan Selevel (*Peers / Siblings*)
Mencari karyawan yang berbagi manajer yang sama tanpa menyertakan diri sendiri.

```sql
SELECT 
    e1.full_name AS employee_1,
    e2.full_name AS employee_2,
    mgr.full_name AS common_manager
FROM 
    employees e1
JOIN 
    employees e2 ON e1.manager_id = e2.manager_id 
                 AND e1.employee_id < e2.employee_id -- Menghilangkan matching ke diri sendiri & duplikasi reflektif (A-B vs B-A)
JOIN 
    employees mgr ON e1.manager_id = mgr.employee_id;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Bagi database engine (PostgreSQL, MySQL InnoDB, dsb.), `FROM employees emp JOIN employees mgr` tidak dianggap sebagai "satu tabel membaca dirinya". *Query Optimizer* memproyeksikan tabel fisik ini menjadi dua *Logical Scan Nodes* yang terpisah dalam *Execution Plan*.

```
                Hash Left Join (or Nested Loop)
               /                               \
     Seq Scan on employees emp       Index Scan on employees mgr
   (membaca baris bawahan)           (lookup via PK: mgr.employee_id)
```

1. **Logical Plan Expansion**: AST memetakan `emp` sebagai *outer relation* (driving table) dan `mgr` sebagai *inner relation*.
2. **Path Selection**: 
   - Jika tabel kecil: Engine memilih **Nested Loop Join**. Engine membaca satu baris dari `emp`, mengambil nilai `manager_id`, lalu melakukan *Index Unique Scan* pada B-Tree `employees.employee_id` untuk menemukan baris `mgr`.
   - Jika tabel besar dan melibatkan *filtering*: Engine mungkin menggunakan **Hash Join** dengan membangun *In-Memory Hash Table* dari relasi referensi (`mgr`), lalu men-*scan* relasi anak (`emp`) terhadap *hash keys*.

#### Alokasi Memori / Resource
- **Buffer Cache**: Karena kedua instans logis membaca tabel fisik yang sama, blok data (*pages*) yang berada di buffer pool memori diakses secara bersamaan (*shared hits*). Ini membuat *self join* cenderung menghasilkan I/O fisik yang lebih rendah dibanding join dua tabel fisik berukuran raksasa yang berbeda.
- **Working Memory**: Jika *Hash Join* terpilih, database mengalokasikan memori kerja (misal: `work_mem` di Postgres) untuk membangun *hash table* salah satu alias tabel.

#### Trade-offs: Adjacency List (Self Join) vs. Alternatives
- **Adjacency List (Self Join Biasa)**:
  - *Kelebihan*: Sangat hemat storage, integritas referensial dijamin kuat oleh `FOREIGN KEY`, mutasi struktur (pindah cabang) sangat murah (cukup *update* satu nilai `manager_id`).
  - *Kekurangan*: Terbatas pada relasi dengan kedalaman tetap (*fixed depth*). Jika kedalaman hirarki dinamis/arbitrer (misal: kedalaman $N$), penggunaan *Self Join* manual membutuhkan penulisan query $N$-kali `JOIN`. Untuk kedalaman dinamis, pendekatan harus beralih ke **Recursive CTE (`WITH RECURSIVE`)**, **Nested Sets**, atau **Closure Tables**.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Indeks Kolom Referensi**: Pastikan kolom penunjuk *parent* (`manager_id`) memiliki B-Tree Index. Tanpa ini, join akan berubah dari $O(N \log N)$ atau $O(N)$ menjadi $O(N^2)$ via *Double Sequential Scan*.
- **Gunakan LEFT JOIN untuk Root Handling**: Root hirarki umumnya memiliki nilai `parent_id IS NULL`. Penggunaan `INNER JOIN` secara tidak sengaja akan memfilter entitas teratas ini dan mengaburkan visualisasi pohon.
- **Beri Alias Semantik yang Ekspresif**: Hindari alias satu huruf generik seperti `a` dan `b`. Gunakan `emp` dan `mgr`, atau `child` dan `parent` untuk menjaga keterbacaan kode (*readability*).

#### Don'ts
- **Hindari Self Join Multitier Berlebihan**: Melakukan chain *self-join* lebih dari 3-4 tingkat (misal: `e JOIN m JOIN gm JOIN ggm`) adalah tanda *code smell*. Solusi ini kaku, rawan salah asusmsi kedalaman data, dan menurunkan performa planner secara eksponensial. Gunakan `WITH RECURSIVE` jika kedalaman > 2 tingkat.
- **Jangan Lupa Evaluasi Siklus (Cycle Detection)**: Jika tidak ada validasi di tingkat aplikasi atau *database trigger*, relasi hirarki bisa membentuk *circular loop* (A membawahi B, B membawahi C, C membawahi A).

#### Edge Cases
- **Self-referencing Root**: Sebagian arsitektur data menetapkan *root node* merujuk ke dirinya sendiri (`employee_id = 1, manager_id = 1`) alih-alih `NULL`. Pola ini berbahaya karena `INNER JOIN` akan terus berjalan, tetapi bisa memicu rekursi tanpa batas (*infinite loops*) jika berpindah ke implementasi *Hierarchical Queries*. Konsisten gunakan `NULL` untuk *top-level root*.

### 5. Tantangan Eksplorasi Mandiri

1. **Deteksi Daun Hirarki (*Leaf Nodes*)**:
   Tulis sebuah query SQL murni menggunakan teknik *Self Join* (tanpa subquery `WHERE NOT IN` atau `NOT EXISTS`) untuk mendeteksi semua karyawan yang **bukan merupakan manajer bagi siapa pun** (karyawan paling bawah / *leaf node*).
   
2. **Validasi Anomali Data (*Cycle Hunting*)**:
   Buat sebuah skenario data uji di mana terjadi relasi sirkular dua arah (Karyawan A adalah manajer dari Karyawan B, dan Karyawan B adalah manajer dari Karyawan A). Tulis query berbasis *Self Join* untuk mengekstrak anomali pasangan karyawan yang saling menjadi atasan satu sama lain tersebut.
