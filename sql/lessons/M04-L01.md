## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Relational Database Management System (RDBMS) berakar pada Aljabar Relasional karya Edgar F. Codd. Integritas data dan kemampuan menghubungkan entitas tanpa redundansi data merupakan inti dari model ini, yang diwujudkan melalui **Primary Key (PK)**, **Foreign Key (FK)**, dan operasi **INNER JOIN**.

```
[ orders ]                              [ customers ]
+----+-------------+--------+           +----+---------------+
| id | customer_id | amount |           | id | name          |
+----+-------------+--------+           +----+---------------+
| 1  | 101 (FK)----|--------+---------->| 101| Alice Smith   | (PK: B-Tree Index)
| 2  | 102 (FK)    |        |           | 102| Bob Johnson   |
+----+-------------+--------+           +----+---------------+
```

#### Primary Key (PK)
Primary Key adalah constraint yang menjamin keunikan identitas suatu baris (*entity integrity*). Karakteristik fundamental PK:
1. **Uniqueness**: Tidak boleh ada nilai duplikat pada kolom PK.
2. **Not Null**: Kolom PK secara implisit atau eksplisit berstatus `NOT NULL`.
3. **Underlying Structure**: RDBMS secara otomatis membuat struktur data indeks (hampir selalu bertipe **B-Tree**) di atas kolom PK. Pada *engine* tertentu (seperti MySQL/InnoDB), PK bertindak sebagai **Clustered Index**, di mana data baris fisik aktual disimpan langsung pada leaf node pohon B-Tree tersebut. Pada engine lain (seperti PostgreSQL), PK membentuk *unique index* terpisah (heap-organized table) yang mengarahkan pointer (TID/Tuple ID) ke storage heap file.

#### Foreign Key (FK) & Referential Integrity
Foreign Key adalah constraint yang memvalidasi bahwa nilai pada suatu kolom di child table harus merujuk pada nilai yang valid di kolom parent table (biasanya PK atau kolom dengan constraint `UNIQUE`). 

FK mengaktifkan *referential integrity enforcement* di level storage engine:
- Operasi `INSERT` atau `UPDATE` pada child table akan memicu lookup ke parent table index untuk memvalidasi keberadaan *key* tersebut.
- Operasi `DELETE` atau `UPDATE` pada parent table akan dibatasi atau dialirkan (*cascaded*) ke child table sesuai definisi policy: `RESTRICT`, `NO ACTION`, `CASCADE`, atau `SET NULL`.
- **Penting**: RDBMS **tidak secara otomatis** membuat indeks pada kolom FK (berbeda dengan PK). Tanpa indeks eksplisit pada FK, setiap operasi `DELETE`/`UPDATE` pada parent table yang memvalidasi child table dapat menyebabkan *Full Table Scan* pada child table.

#### INNER JOIN: Relational Calculus to Physical Engine
Secara matematis, `INNER JOIN` adalah perkalian kartesian (*Cartesian Product* atau cross join) dari dua relasi yang kemudian disaring menggunakan predikat seleksi (kondisi `ON`):
$$\mathcal{R} \bowtie_{\theta} \mathcal{S} = \sigma_{\theta}(\mathcal{R} \times \mathcal{S})$$

Namun, query execution engine tidak mengeksekusi operasi ini dengan mengalikan semua baris ($O(N \times M)$) karena inefisiensi memori dan CPU. Optimizer menganalisis metadata dan statistik katalog (histograms, page count) untuk memilih salah satu dari 3 algoritma eksekusi fisik utama:
1. **Nested Loop Join**: Mengiterasi outer table baris demi baris dan melakukan lookup ke inner table (sangat efisien jika inner table terindeks dan outer table kecil).
2. **Hash Join**: Membangun in-memory hash table dari tabel yang lebih kecil (build phase), kemudian memindai tabel yang lebih besar untuk mencocokkan hash key (probe phase). Efisien untuk volume data besar tanpa indeks yang terurut.
3. **Sort-Merge Join**: Mengurutkan kedua tabel berdasarkan join key (jika belum terurut via index) dan memindai keduanya secara paralel seperti merge-sort. Sangat efisien untuk dataset raksasa dengan ordering yang sudah terbentuk.

### 2. Implementasi & Contoh Kasus Nyata

Contoh implementasi skema e-commerce menggunakan PostgreSQL/standar ANSI-SQL:

```sql
-- 1. Buat Parent Table: customers
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY,
    email VARCHAR(255) NOT NULL,
    full_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    
    -- PK Constraint: Otomatis membuat Unique B-Tree Index
    CONSTRAINT pk_customers PRIMARY KEY (customer_id),
    CONSTRAINT uq_customers_email UNIQUE (email)
);

-- 2. Buat Child Table: orders
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id BIGINT NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL CHECK (total_amount >= 0),
    order_status VARCHAR(20) DEFAULT 'PENDING' NOT NULL,
    order_date TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    
    -- PK Constraint
    CONSTRAINT pk_orders PRIMARY KEY (order_id),
    
    -- FK Constraint dengan Enforcement Policy
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) 
        REFERENCES customers (customer_id)
        ON DELETE RESTRICT      -- Cegah hapus customer jika memiliki order
        ON UPDATE CASCADE       -- Ubah customer_id di order jika customer_id di parent berubah
);

-- 3. CRITICAL: Buat indeks manual untuk FK!
-- Tanpa ini, join dan validasi referensial akan sangat lambat pada skala jutaan row.
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

-- 4. Seed Data
INSERT INTO customers (email, full_name) VALUES
('ada@lovelace.org', 'Ada Lovelace'),
('alan@turing.ac.uk', 'Alan Turing'),
('grace@hopper.mil', 'Grace Hopper');

INSERT INTO orders (customer_id, total_amount, order_status) VALUES
(1, 150000.00, 'PAID'),
(1, 250000.00, 'SHIPPED'),
(2, 85000.00, 'PAID');
-- Customer ID 3 (Grace Hopper) sengaja tidak memiliki order.

-- 5. Query INNER JOIN idiomatik
SELECT 
    c.customer_id,
    c.full_name,
    o.order_id,
    o.total_amount,
    o.order_status
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_status = 'PAID'
ORDER BY o.total_amount DESC;
```

#### Analisis Hasil Eksekusi Query
Customer dengan ID 3 (`Grace Hopper`) dievaluasi bernilai `FALSE` pada predikat join (`c.customer_id = o.customer_id`) karena tidak terdapat baris yang bersesuaian di tabel `orders`. Secara semantik, `INNER JOIN` memfilter keluar baris tersebut, hanya menyisakan baris yang memiliki pasangan sah di kedua relasi.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Ketika query `INNER JOIN` diterima, engine melalui tahapan berikut:

```
Parser -> Rewriter -> Cost-Based Optimizer (CBO) -> Execution Engine
```

1. **Predikat Pushdown**: CBO mencoba memindahkan klausul `WHERE o.order_status = 'PAID'` sedekat mungkin ke disk scan. Alih-alih me-load seluruh baris `orders` lalu men-join baru memfilter, engine menyaring baris `orders` terlebih dahulu.
2. **Join Strategy Resolution**:
   - Jika `orders` memiliki $10^6$ baris dan `customers` hanya $10$ baris, CBO memilih **Hash Join**. Tabel `customers` di-load ke memory (`build side`), dan tabel `orders` yang difilter dipindai untuk mencocokkan bucket hash (`probe side`).
   - Jika kedua kolom `customer_id` didukung oleh B-Tree Index yang terurut, CBO dapat memilih **Merge Join** tanpa perlu melakukan sorting fisik tambahan di memori.

#### Alokasi Memori & Disk Spilling
- **Hash Join**: Menggunakan alokasi memori kerja (misal: `work_mem` di PostgreSQL atau `join_buffer_size` di MySQL). Jika in-memory hash table melebihi alokasi memori yang diizinkan, engine melakukan operasi **Batching** atau **Spilling to Disk** (menggunakan Temporary Disk Files). Hal ini menyebabkan degradasi I/O performa secara drastis (*high I/O wait*).
- **FK Validation Overhead**: Setiap kali `INSERT` dijalankan pada tabel `orders`, engine mengunci tuple terkait di `customers` (biasanya shared lock/`FOR KEY SHARE`) untuk memastikan customer tidak sedang dihapus di transaksi lain, lalu melakukan read B-Tree traversal ke index `pk_customers`.

#### Trade-offs
- **Integritas vs Write Throughput**: FK menjamin integritas data secara mutlak di layer penyimpanan ACID. Konsekuensinya, write throughput turun karena overhead pengecekan dependensi dan locking antar-tabel.
- **Normalisasi (Join) vs Denormalisasi**:
  - Menggunakan PK/FK (Normalized 3NF) menekan redundansi data dan mencegah update anomaly.
  - Membutuhkan eksekusi JOIN di runtime yang meningkatkan konsumsi CPU & memory bandwidth.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Selalu buat Index pada kolom Foreign Key**: RDBMS membuat index pada PK secara otomatis, tetapi **hampir tidak pernah** mengindeks FK secara otomatis.
- **Gunakan tipe data yang identik secara biner**: Pastikan tipe data `PK` dan `FK` sama persis (misal: keduanya `BIGINT`, bukan menggabungkan `INT` dan `BIGINT`, atau `VARCHAR(50)` dengan `VARCHAR(100)`). Perbedaan tipe data memicu *implicit type casting* yang menonaktifkan penggunaan index B-Tree (*Index Invalidation*).
- **Definisikan alias tabel secara jelas**: Gunakan alias singkat namun representatif (`c` untuk `customers`, `o` untuk `orders`) guna meningkatkan maintainability query.

#### Don'ts
- **Jangan gunakan Natural Join (`NATURAL INNER JOIN`)**: Fitur ini mencocokkan kolom dengan nama yang sama secara implisit. Jika ada perubahan skema (misal penambahan kolom `created_at` di kedua tabel), logika join akan rusak seketika secara diam-diam (*silent logical error*).
- **Hindari Join pada kolom Non-Indexed / Non-Unique**: Melakukan `INNER JOIN` pada kolom non-indeks atau non-kandidat key dapat memicu *Cartesian product explosion* yang melipatgandakan baris result set (*fan-out issue*) dan membebani alokasi memory server.
- **Jangan abaikan CASCADE policy**: Berhati-hati dengan `ON DELETE CASCADE`. Menghapus satu record di tabel root (misal `tenants` atau `organizations`) dapat menghapus jutaan row di tabel transaksional secara tidak sengaja dalam satu transaksi besar yang mengunci database.

#### Edge Cases
- **Handling NULL pada Foreign Key**: Kolom Foreign Key yang bernilai `NULL` lolos dari validasi referensial (kecuali jika diberi constraint `NOT NULL`). Dalam `INNER JOIN`, baris dengan `FK = NULL` **tidak akan pernah muncul** di hasil akhir karena perbandingan `NULL = NULL` dalam evaluasi boolean logika Three-Valued Logic (3VL) SQL menghasilkan status `UNKNOWN`.
- **FK Constraint Checking Order pada Batch Ingestion**: Saat memuat data skala besar (bulk insert), urutan insert harus dimulai dari parent ke child. Jika terpaksa acak (misal: circular dependency), gunakan `DEFERRABLE INITIALLY DEFERRED` constraint (pada engine yang mendukung seperti PostgreSQL) agar validasi ditunda hingga `COMMIT`.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan**:
   Jalankan perintah `EXPLAIN ANALYZE` pada query `INNER JOIN` di atas. Lakukan drop index pada `idx_orders_customer_id`, lalu jalankan kembali. Amati bagaimana query plan berubah (apakah engine beralih dari *Index Scan* ke *Seq Scan* atau mengubah algoritma join dari *Nested Loop* ke *Hash Join*).
2. **Simulasi Deadlock Foreign Key**:
   Buat dua sesi transaksi konkuren (`BEGIN`). Pada Sesi A, lakukan `DELETE` pada salah satu baris di parent table. Pada Sesi B, lakukan `INSERT` data baru pada child table yang mengarah ke parent row yang berbeda. Amati fenomena row-locking yang terjadi pada tingkat referensial.
3. **Mengatasi Fan-Out Effect**:
   Rancang skema di mana satu `customer` memiliki banyak `orders`, dan satu `order` memiliki banyak `order_items`. Tulis query `INNER JOIN` yang menggabungkan ketiganya untuk menghitung total belanja per customer tanpa mengalami bug duplikasi agregasi akibat relasi *one-to-many-to-many*.
