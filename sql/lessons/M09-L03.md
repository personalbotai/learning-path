## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

**SQL Injection (SQLi)** adalah kerentanan keamanan di mana input data dari pengguna diperlakukan sebagai kode instruksi oleh SQL Engine. Kerentanan ini berakar pada pelanggaran prinsip pemisahan antara **Control Plane (logika instruksi)** dan **Data Plane (nilai data)**.

```
Pendekatan Vulnerable (String Concatenation):
[ Client Input ] ──(Teks Mentah)──> [ SQL Parser & Compiler ] ──> [ Modifikasi AST ]
                                                                        │
                                                               ⚠️ Eksekusi Kode Tak Diinginkan

Pendekatan Parameterisasi (Prepared Statements):
[ Query Blueprint ] ───────────────> [ SQL Parser & Compiler ] ──> [ Fixed AST / Plan ]
                                                                        │
[ Client Input ]    ──(Wire Protocol)──────────────────────────────> [ Data Binding ]
                                                                        │
                                                               ✅ Aman: Evaluasi Murni Data
```

#### Anatomi Parsing SQL Engine
Ketika query dikirim ke Database Management System (DBMS) seperti PostgreSQL atau MySQL, engine melewati beberapa tahapan:
1. **Lexical & Syntactic Analysis (Parser):** Memecah string SQL menjadi token (*keywords*, *identifiers*, *operators*, *literals*) dan memvalidasi tata bahasa untuk menghasilkan **Abstract Syntax Tree (AST)**.
2. **Semantic Analysis:** Memeriksa keberadaan tabel, kolom, tipe data, dan hak akses.
3. **Query Optimizer:** Menganalisis statistik tabel untuk menentukan *Execution Plan* paling efisien (misal: *Index Scan* vs *Sequential Scan*).
4. **Executor:** Menjalankan plan terhadap storage engine.

Pada query dinamis berbasis konkatenasi string:
```sql
-- Input: admin' OR '1'='1
SELECT * FROM users WHERE username = 'admin' OR '1'='1' AND password = '...';
```
Karakter kutip tunggal (`'`) bertindak sebagai token delimiter penutup literal string. SQL Lexer memecah sisa input menjadi token logika (`OR`, `AND`, operator `=`). Akibatnya, **struktur AST berubah secara fundamental saat runtime**. Struktur kondisional yang seharusnya mengevaluasi satu akun berubah menjadi tautologi (`'1'='1'`), memotong evaluasi kata sandi.

#### Parameterisasi (Prepared Statement)
Parameterisasi memutus rantai eksploitasi ini dengan memisahkan kompilasi query dari injeksi data:
1. **Prepare Phase:** Query dikirim dengan penanda (*placeholder* seperti `?`, `$1`, atau `:name`). SQL Engine mem-parsing dan mengompilasi struktur query ke dalam AST permanen.
2. **Execute/Bind Phase:** Nilai parameter dikirim secara terpisah melalui protokol biner DBMS. Nilai-nilai ini langsung di-injeksi ke dalam slot memori eksekusi (data binding) tanpa pernah melewati parser atau lexer ulang. 

Meskipun nilai parameter mengandung `' OR '1'='1`, engine tetap memperlakukannya 100% sebagai nilai skalar string murni, bukan instruksi logika.

### 2. Implementasi & Contoh Kasus Nyata

Berikut perbandingan antara implementasi rentan dan aman pada level SQL murni (*Prepared Statements*) dan implementasi backend (Node.js/PostgreSQL driver).

#### A. Level SQL Engine (PostgreSQL Extended Protocol Simulation)

```sql
-- ============================================================================
-- 1. POLA RENTAN (Dynamic SQL Execution)
-- ============================================================================
-- Simulasi di dalam PL/pgSQL Function yang menyusun query via string concatenation:
CREATE OR REPLACE FUNCTION authenticate_vulnerable(p_user text) 
RETURNS TABLE(id int, username text) AS $$
BEGIN
    -- BAHAYA: String input langsung disambung ke command
    RETURN QUERY EXECUTE 
        'SELECT id, username FROM accounts WHERE username = ''' || p_user || '''';
END;
$$ LANGUAGE plpgsql;

-- Penyerang mengeksekusi payload:
-- SELECT * FROM authenticate_vulnerable('admin'' OR 1=1; --');


-- ============================================================================
-- 2. POLA AMAN: Native Engine-Level PREPARE (Parameterisasi)
-- ============================================================================
-- Tahap 1: Daftarkan query plan ke memory session dengan placeholder tipe data ($1)
PREPARE get_account_by_user (text) AS
    SELECT id, username, email, is_active 
    FROM accounts 
    WHERE username = $1;

-- Tahap 2: Eksekusi dengan menyuplai data murni
-- Meskipun input mengandung karakter berbahaya, input diperlakukan sebagai literal teks
EXECUTE get_account_by_user('admin'' OR ''1''=''1');

-- Tahap 3: Hapus statement dari session memory jika sudah selesai
DEALLOCATE get_account_by_user;
```

#### B. Level Aplikasi (Node.js + `pg` Driver)

```javascript
import pg from 'pg';
const { Pool } = pg;

const pool = new Pool({
  connectionString: process.env.DATABASE_URL
});

// ============================================================================
// ANTI-PATTERN: String Interpolation / Template Literals (SQLi Vulnerable)
// ============================================================================
async function unsafeLogin(userInputUsername) {
  // JANGAN LAKUKAN INI: Input digabungkan sebelum masuk ke database driver
  const query = `SELECT id, password_hash FROM users WHERE username = '${userInputUsername}'`;
  
  // Jika userInputUsername = "victim' --", sisa query akan terpotong
  const result = await pool.query(query);
  return result.rows[0];
}

// ============================================================================
// BEST PRACTICE: Parameterized Query (Extended Protocol)
// ============================================================================
async function safeLogin(userInputUsername) {
  // Query teks dan parameter dipisah. Driver mengirim keduanya dalam paket network berbeda
  const queryText = `
    SELECT id, password_hash, role 
    FROM users 
    WHERE username = $1 
      AND is_active = true
  `;
  
  const values = [userInputUsername];

  try {
    const result = await pool.query(queryText, values);
    return result.rows[0];
  } catch (err) {
    console.error('Database query failure:', err.message);
    throw err;
  }
}

// ============================================================================
// ADVANCED: Dynamic Column/Table Identifiers (Whitelist Pattern)
// Identifiers TIDAK BISA diparameterisasi dengan $1 / ?, harus divalidasi manual
// ============================================================================
async function fetchUsersSorted(sortByColumn, direction = 'ASC') {
  // 1. Whitelisting kolom yang sah
  const ALLOWED_COLUMNS = new Set(['created_at', 'username', 'email']);
  const ALLOWED_DIRECTIONS = new Set(['ASC', 'DESC']);

  const sanitizedSort = ALLOWED_COLUMNS.has(sortByColumn) ? sortByColumn : 'created_at';
  const sanitizedDirection = ALLOWED_DIRECTIONS.has(direction.toUpperCase()) ? direction.toUpperCase() : 'ASC';

  // 2. Format identifier secara eksplisit dan aman (bukan dari input mentah)
  // Untuk PostgreSQL, identifier dapat dibungkus double quotes setelah validasi
  const queryText = `
    SELECT id, username, email 
    FROM users 
    ORDER BY "${sanitizedSort}" ${sanitizedDirection} 
    LIMIT $1
  `;

  // Limit adalah value, sehingga aman menggunakan parameterized query
  const result = await pool.query(queryText, [10]);
  return result.rows;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Extended Query Protocol
Ketika menggunakan database modern (misalnya PostgreSQL) melalui driver modern, database tidak menjalankan mode *Simple Query Protocol* (mengirim 1 string SQL mentah lewat paket jaringan), melainkan **Extended Query Protocol**.

Proses ini dibagi menjadi beberapa frame jaringan independen:
1. **Parse:** Frontend mengirim string query dengan parameter token (e.g., `SELECT * FROM tbl WHERE id = $1`). Backend memvalidasi sintaksis dan menyimpan *Prepared Statement Object* tanpa data.
2. **Bind:** Frontend mengirim referensi nama prepared statement, daftar format kode (teks/biner), dan **array byte nilai parameter aktual**. Backend mengasosiasikan data ke dalam slot memori eksekutor.
3. **Describe:** Backend mengembalikan representasi metadata tipe kolom hasil.
4. **Execute:** Backend menjalankan query plan yang sudah terikat nilai parameter dan memompa hasilnya ke client.

Karena payload serangan berada di dalam langkah **Bind**, mesin parser database tidak pernah menyentuh payload tersebut.

#### Alokasi Memori / Resource
- **Session-scoped Statement Cache:** Di server, *prepared statement* disimpan dalam session backend memory pool (misalnya, Process Private Memory PostgreSQL / *TopMemoryContext*). Query plan dicache agar tidak perlu melalui tahap lexical parsing berulang kali.
- **Connection Pool Overhead:** Jika arsitektur backend menggunakan pooling (seperti PgBouncer dalam mode *Transaction Pooling*), server-side prepared statements bisa menimbulkan masalah (`ERROR: prepared statement does not exist`) karena koneksi fisik berganti antar-transaksi. Driver modern mengatasi ini dengan menggunakan *unnamed prepared statements* yang langsung di-bind dan di-destroy per transaksi, atau mengelola prepared statement secara lokal di client side.

#### Trade-offs: Generic Plan vs Custom Plan
Database optimizer menggunakan parameter data aktual untuk mengestimasi distribusi probabilitas baris (*cardinality estimation* via histogram statistik data):
- **Custom Plan:** Dihasilkan ketika engine mengetahui nilai pasti pada waktu kompilasi. Sangat optimal untuk query dengan data *skewed* (tidak merata).
- **Generic Plan:** Dihasilkan oleh prepared statement yang digeneralisasi agar dapat dieksekusi berulang kali dengan parameter apa pun tanpa kompilasi ulang.
- **Trade-off:** Parameterisasi terkadang dapat menyebabkan performa sub-optimal (*Plan Regression*) pada data yang memiliki distribusi sangat tidak merata, karena optimizer mengasumsikan rata-rata distribusi daripada menggunakan nilai parameter spesifik (pada PostgreSQL, engine akan mencoba custom plan 5 kali sebelum beralih permanen ke generic plan).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Parameterized Query Secara Default:** Perlakukan setiap variabel yang berasal dari luar (HTTP Request, Message Broker, file input) sebagai data tercemar (*tainted data*).
- **Terapkan Identifier Whitelisting:** Parameterisasi hanya berlaku untuk *Data Value/Literals*. Untuk nama tabel, nama kolom, atau kata kunci (`ASC`/`DESC`), gunakan mekanisme validasi ketat (*strict whitelist* atau enum check) dan database escape helper seperti `quote_ident()`.
- **Enforce Principle of Least Privilege (PoLP):** Konfigurasikan user database aplikasi agar tidak memiliki hak akses destruktif (`DROP TABLE`, `ALTER`) atau hak baca ke tabel sistem (`pg_catalog`, `information_schema`) yang tidak diperlukan.

#### Don'ts
- **Jangan Mengandalkan Blacklist atau Manual Sanitization:** Menghapus atau mereplace karakter kutip (`'`), komentar (`--`), atau semicolon (`;`) menggunakan regex aplikasi tidak aman. Penyerang dapat memanipulasi *character encoding* (seperti multibyte UTF-8 bypass, misal: GBK/Big5 di MySQL) untuk memunculkan kembali karakter kutip.
- **Jangan Melakukan Interpolasi String pada ORM:** Menggunakan ORM tidak otomatis menjamin imunitas jika pengembang menggunakan fitur raw query secara salah:
  ```javascript
  // FATAL: Menggunakan ORM tapi tetap melakukan konkatenasi manual
  await sequelize.query(`SELECT * FROM users WHERE name = '${req.body.name}'`);
  ```
- **Jangan Menggabungkan String di dalam Stored Procedure:** Penggunaan `EXECUTE` di dalam PL/pgSQL atau T-SQL tanpa klausul `USING` memicu kerentanan SQLi internal (Stored Procedure Injection).

#### Edge Cases
- **Second-Order SQL Injection:** Input jahat disimpan ke database secara aman melalui parameterisasi, namun di kemudian hari input tersebut dibaca dari tabel dan disambung (*concatenated*) secara dinamis ke dalam query kedua tanpa parameterisasi. Pertahanan parameterisasi harus konsisten di hulu dan hilir.
- **Kueri Array / Clause `IN` Dinamis:** Membuat query dinamis untuk jumlah elemen array yang tidak tetap sering memicu developer kembali ke konkatenasi string.
  ```sql
  -- Solusi PostgreSQL idiomatik untuk klausa IN yang diparameterisasi secara penuh:
  SELECT id, name FROM products WHERE id = ANY($1::int[]);
  -- Input $1 dikirim langsung sebagai array integer murni: [1, 2, 3, 4]
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Audit Protokol Jaringan Database:**
   Gunakan alat *packet analyzer* (seperti Wireshark atau tcpdump) atau logging DBMS lokal (`log_statement = 'all'` pada PostgreSQL). Bandingkan jejak paket antara eksekusi query biasa (string literal mentah) dengan eksekusi parameterized query (Extended Protocol). Perhatikan bagaimana format parameter dikirimkan pada tingkat soket TCP (`Parse`, `Bind`, `Execute`).

2. **Mitigasi Dynamic Query Builder:**
   Rancang sebuah fungsi di bahasa pemrograman pilihan Anda yang menerima filter dinamis dari URL query params (misal: `?filter_col=price&filter_op=gt&val=10000`). Buat query builder yang mampu mengabstraksikan filter tersebut secara aman tanpa ada celah manipulasi nama kolom, operator logika, ataupun nilainya. Identifikasi elemen mana yang harus divalidasi via *whitelist* dan elemen mana yang harus masuk ke *bind parameters*.
