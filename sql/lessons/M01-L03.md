## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Klausa `WHERE` merupakan implementasi dari operator seleksi (*selection operator*, dilambangkan dengan huruf Yunani $\sigma$) dalam aljabar relasional. Tujuan fundamentalnya adalah membatasi himpunan baris (*horizontal filtering*) yang dikembalikan oleh kueri berdasarkan suatu kondisi logika (*predicate*).

#### Urutan Eksekusi Logis (*Logical Query Processing*)
Salah satu kesalahan pemahaman paling umum adalah menganggap SQL dieksekusi secara linear sesuai urutan penulisannya. Dalam arsitektur RDBMS, klausa dievaluasi dalam tahapan logis tertentu:

```
1. FROM / JOIN      -> Membentuk cartesian product / working dataset
2. WHERE            -> Mengeliminasi baris berdasarkan predikat (3VL)
3. GROUP BY         -> Mengelompokkan data yang lolos filter
4. HAVING           -> Memfilter hasil agregasi kelompok
5. SELECT           -> Menentukan proyeksi kolom dan ekspresi
6. DISTINCT         -> Menghapus duplikasi baris
7. ORDER BY         -> Mengurutkan baris
8. LIMIT / OFFSET   -> Membatasi jumlah output
```

Karena klausa `WHERE` dievaluasi pada **Fase 2** (sebelum `SELECT` pada Fase 5), Anda **tidak dapat** menggunakan alias kolom (*alias name*) yang didefinisikan di `SELECT` dalam klausa `WHERE`, begitu pula Anda **tidak dapat** menggunakan fungsi agregasi (seperti `SUM()`, `COUNT()`) secara langsung di dalam `WHERE`.

#### Logika Tiga Nilai (*Three-Valued Logic / 3VL*)
SQL tidak mengadopsi logika boolean murni (*Two-Valued Logic: True/False*), melainkan *Three-Valued Logic* yang mencakup `TRUE`, `FALSE`, dan `UNKNOWN`. Nilai `UNKNOWN` muncul ketika melibatkan operasi pembanding dengan nilai `NULL` (yang merepresentasikan *missing* atau *inapplicable data*).

Klausa `WHERE` bekerja dengan aturan tegas: **hanya baris dengan hasil evaluasi predikat `TRUE` yang akan diteruskan ke tahap pemrosesan berikutnya**. Baris yang menghasilkan evaluasi `FALSE` atau `UNKNOWN` akan dieliminasi (*discarded*).

| Ekspresi (`A = NULL`) | Hasil Logika | Lolos Filter `WHERE`? |
| :--- | :--- | :--- |
| `'active' = 'active'` | `TRUE` | **Ya** |
| `'active' = 'banned'` | `FALSE` | **Tidak** |
| `'active' = NULL` | `UNKNOWN` | **Tidak** |
| `NULL = NULL` | `UNKNOWN` | **Tidak** |

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skema dan serangkaian skenario implementasi penyaringan data pada sistem *e-commerce*.

```sql
-- DDL & Sample Data
CREATE TABLE orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL, -- 'PENDING', 'PROCESSING', 'COMPLETED', 'CANCELLED'
    total_amount NUMERIC(12, 2) NOT NULL,
    discount_amount NUMERIC(12, 2) DEFAULT 0.00,
    shipped_at TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO orders (customer_id, status, total_amount, discount_amount, shipped_at, created_at)
VALUES 
    (101, 'COMPLETED', 150000.00, 10000.00, '2024-03-01 10:00:00+00', '2024-02-28 08:30:00+00'),
    (102, 'PENDING', 50000.00, 0.00, NULL, '2024-03-02 09:15:00+00'),
    (103, 'COMPLETED', 750000.00, 50000.00, '2024-03-03 14:00:00+00', '2024-03-02 11:00:00+00'),
    (104, 'CANCELLED', 200000.00, 0.00, NULL, '2024-03-03 16:45:00+00'),
    (105, 'PROCESSING', 300000.00, 15000.00, NULL, '2024-03-04 12:00:00+00');
```

#### Skenario 1: Predikat Majemuk & Presedensi Operator
Mengambil pesanan yang bernilai tinggi (`> 200000`) atau pesanan lama yang statusnya `PENDING`. Hati-hati dengan presedensi operator `AND` yang lebih tinggi daripada `OR`.

```sql
-- REKOMENDASI: Gunakan tanda kurung eksplisit untuk menghindari bug presedensi
SELECT 
    order_id, customer_id, status, total_amount 
FROM 
    orders
WHERE 
    status = 'PENDING' 
    OR (total_amount > 200000.00 AND status = 'COMPLETED');
```

#### Skenario 2: Penanganan NULL dengan Tepat
Mengambil data pesanan yang berstatus `COMPLETED` tetapi belum memiliki timestamp pengiriman (`shipped_at`).

```sql
-- Penggunaan IS NULL / IS NOT NULL wajib untuk evaluasi 3VL
SELECT 
    order_id, status, shipped_at
FROM 
    orders
WHERE 
    status = 'COMPLETED'
    AND shipped_at IS NULL; -- Jangan pernah: shipped_at = NULL
```

#### Skenario 3: Set Inclusion (`IN`) dan Range Filtering (`BETWEEN`)
Memfilter pesanan dengan ID pelanggan tertentu dalam rentang waktu terisolasi.

```sql
SELECT 
    order_id, customer_id, created_at
FROM 
    orders
WHERE 
    customer_id IN (101, 103, 107)
    AND created_at >= '2024-03-01 00:00:00+00' 
    AND created_at < '2024-03-04 00:00:00+00';
    -- Catatan: Penggunaan '>=' dan '<' lebih disarankan dibanding 'BETWEEN' 
    -- untuk timestamp guna menghindari insiden batas akhir milidetik.
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Predicate Pushdown & Scan Types
1. **Query Parsing & Optimization**: SQL diterjemahkan ke dalam *Abstract Syntax Tree* (AST), lalu *Cost-Based Optimizer* (CBO) menyusun rencana eksekusi (*Query Execution Plan*). CBO melakukan teknik optimasi bernama **Predicate Pushdown**, yaitu memindahkan evaluasi predikat `WHERE` sedekat mungkin ke sumber data fisik untuk mengurangi volume data yang dibaca dari memori atau *disk*.
2. **Access Methods**:
   - **Sequential Scan (Table Scan)**: RDBMS membaca halaman data (*pages/blocks*) secara sekuensial dari disk ke *Buffer Pool*. Setiap *tuple* (baris) dievaluasi terhadap predikat `WHERE`. Jika tidak cocok, tuple langsung diabaikan.
   - **Index Scan / Index Range Scan**: Jika kolom pada `WHERE` memiliki indeks (umumnya *B-Tree*), *execution engine* menelusuri struktur pohon dari *root* ke *leaf* dengan kompleksitas $O(\log N)$, mencari pointer fisik (`TID`/`RowID`), lalu hanya membaca halaman data yang relevan.

#### Alokasi Memori & CPU Resource
- Evaluasi predikat dilakukan pada level register CPU dan *cache line* saat halaman data sudah berada di memori (*Buffer Cache*). 
- Jika predikat melibatkan fungsi kompleks (misal: perbandingan ekspresi reguler `~` atau operasi kalkulasi matematis berat), penggunaan CPU cycles meningkat secara signifikan per tuple.

#### Trade-offs: Short-Circuit Evaluation
RDBMS modern menerapkan optimasi *short-circuiting* (contoh: pada `A AND B`, jika `A` bernilai `FALSE`, `B` tidak akan dievaluasi). Namun, perhatikan bahwa CBO berhak menentukan urutan evaluasi predikat mana yang diuji lebih dulu berdasarkan estimasi selektivitas (*selectivity cost*), bukan berdasarkan urutan penulisan kode Anda.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan SARGable Query (Search Argument Ready)**: Tulis predikat agar mesin basis data dapat menggunakan indeks B-Tree secara optimal.
  ```sql
  -- SARGable (Bagus: B-Tree Index Range Scan aktif)
  WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'
  ```
- **Gunakan Penandaan Explicit Parentheses**: Selalu bungkus grup logika `AND` dan `OR` dengan tanda kurung `()` untuk menghindari interpretasi ambigu atau bug urutan presedensi.
- **Cocokkan Tipe Data Predikat**: Hindari konversi tipe implisit (*implicit type casting*). Contoh: Membandingkan kolom `VARCHAR` dengan nilai literal integer `WHERE phone_number = 628123456` memaksa database mengubah seluruh kolom menjadi integer, menyebabkan *full table scan*.

#### Don'ts
- **Hindari Membungkus Kolom Terindeks dalam Fungsi (Non-SARGable)**:
  ```sql
  -- BURUK: Indeks pada 'created_at' diabaikan total, memicu Table Scan
  WHERE EXTRACT(YEAR FROM created_at) = 2024;
  
  -- BURUK: Indeks pada 'status' tidak dapat digunakan secara optimal
  WHERE LOWER(status) = 'completed'; 
  ```
- **Hindari Wildcard di Awal String**:
  ```sql
  -- BURUK: B-Tree tidak bisa mencari substring dari belakang/tengah
  WHERE customer_code LIKE '%XYZ';
  
  -- BAIK: Indeks tetap bekerja (prefix match)
  WHERE customer_code LIKE 'XYZ%';
  ```

#### Edge Cases
- **The Negation & NULL Trap**:
  Jika Anda mengeksekusi:
  ```sql
  SELECT * FROM orders WHERE status != 'CANCELLED';
  ```
  Baris di mana `status` bernilai `NULL` **tidak akan pernah muncul**, karena perbandingan `NULL != 'CANCELLED'` menghasilkan `UNKNOWN`. Jika Anda ingin menyertakan nilai `NULL`, Anda wajib menulisnya eksplisit:
  ```sql
  SELECT * FROM orders WHERE status != 'CANCELLED' OR status IS NULL;
  ```
- **Anti-pattern `IN` dengan Subquery bernilai NULL**:
  Jika subquery mengembalikan sekurang-kurangnya satu nilai `NULL`, ekspresi `NOT IN` akan selalu menghasilkan kumpulan data kosong (`EMPTY SET`) karena cara kerja logika 3VL: `x NOT IN (A, NULL)` dievaluasi menjadi `x != A AND x != NULL` $\rightarrow$ `TRUE AND UNKNOWN` $\rightarrow$ `UNKNOWN`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi SARGability via EXPLAIN**:
   Buat tabel dengan 100.000 baris acak yang memiliki indeks pada kolom bertipe `TIMESTAMP`. Bandingkan *Execution Plan* (menggunakan `EXPLAIN ANALYZE` di PostgreSQL atau `EXPLAIN` di MySQL) antara dua kueri berikut:
   - `SELECT * FROM test_table WHERE DATE(created_at) = CURRENT_DATE;`
   - `SELECT * FROM test_table WHERE created_at >= CURRENT_DATE AND created_at < CURRENT_DATE + INTERVAL '1 day';`
   Perhatikan perbedaan antara *Filter* vs *Index Cond*, serta estimasi `cost` dan *execution time*-nya.

2. **Teka-teki 3VL (Three-Valued Logic)**:
   Periksa kueri berikut tanpa menjalankannya di terminal terlebih dahulu. Apakah kueri ini akan mengembalikan baris yang memiliki nilai `val = NULL`?
   ```sql
   SELECT * FROM my_table WHERE val = NULL OR NOT(val = NULL);
   ```
   Jelaskan secara teoritis berdasarkan tabel kebenaran (*truth table*) logika 3VL mengapa hasilnya demikian!
