## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara arsitektural, subquery dalam SQL terbagi menjadi dua kategori fundamental: **Independent (Non-correlated) Subquery** dan **Correlated Subquery**.

```
Independent Subquery:
[Inner Query] Evaluasi 1x ───> Menghasilkan Result Set ───> [Outer Query] Evaluasi 1x

Correlated Subquery:
[Outer Query] Ambil Row_i ───> Oper Nilai ke Inner ───> [Inner Query] Evaluasi Row_i ───> Kembali ke Outer
       ^                                                                                      │
       └────────────────────────── Ulangi untuk setiap baris ─────────────────────────────────┘
```

#### Correlated Subquery
Correlated subquery adalah query bersarang (inner query) yang mereferensikan kolom dari query terluar (outer query). Tidak seperti independent subquery yang dieksekusi sekali di awal (*eager evaluation*), correlated subquery secara konseptual dieksekusi berulang kali—satu kali untuk setiap baris kandidat yang diproses oleh outer query. Karena ketergantungan variabel ini (*variable binding*), inner query tidak dapat dijalankan secara terisolasi tanpa konteks baris dari outer query.

#### Operator `EXISTS` vs `IN`
Operator `EXISTS` digunakan untuk menguji keberadaan (*existential qualification*) baris dalam subquery:
1. **Boolean Short-Circuiting**: `EXISTS` mengevaluasi kondisi ke `TRUE` segera setelah menemukan baris pertama yang memenuhi kualifikasi predikat. RDBMS tidak membaca keseluruhan result set subquery untuk baris tersebut.
2. **Three-Valued Logic (3VL) Handling**: `EXISTS` hanya mengembalikan nilai biner: `TRUE` atau `FALSE`. Jika subquery menghasilkan baris kosong atau baris yang hanya berisi `NULL`, `EXISTS` tetap menghasilkan `FALSE` atau `TRUE` (jika baris `NULL` ada). Ini berbeda secara fundamental dengan `IN`, yang beroperasi menggunakan logika tiga nilai (*True*, *False*, *Unknown*).

Ketika menggunakan `NOT IN`, jika subquery menghasilkan satu saja nilai `NULL`, seluruh ekspresi akan mengevaluasi ke `UNKNOWN` (atau dianggap `FALSE` pada klausa `WHERE`), menyebabkan query mengembalikan *empty set*. `NOT EXISTS` kebal terhadap anomali `NULL` ini.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Sistem E-Commerce dengan skema database pelanggan (`customers`) dan pesanan (`orders`).

```sql
-- DDL Skema Pengujian
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    country VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT REFERENCES customers(customer_id),
    order_date DATE NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL
);

-- Indeks penting untuk performa correlated subquery
CREATE INDEX idx_orders_customer_date ON orders(customer_id, order_date);
```

#### Kasus 1: Semi-Join Menggunakan `EXISTS`
Mencari pelanggan dari 'Indonesia' yang pernah melakukan transaksi dengan nilai di atas $1,000 pada tahun 2024.

```sql
SELECT c.customer_id, c.name
FROM customers c
WHERE c.country = 'Indonesia'
  AND EXISTS (
      -- Inner query terikat ke outer query via c.customer_id
      SELECT 1 
      FROM orders o
      WHERE o.customer_id = c.customer_id
        AND o.total_amount > 1000.00
        AND o.order_date >= '2024-01-01'
        AND o.order_date < '2025-01-01'
  );
```
*Catatan:* Konvensi `SELECT 1` digunakan karena `EXISTS` hanya memeriksa eksistensi tuple (*cardinality* $\ge 1$), bukan memproyeksikan payload data kolom.

#### Kasus 2: Anti-Join Menggunakan `NOT EXISTS`
Menemukan *churn risk*: pelanggan yang terdaftar tetapi tidak memiliki transaksi dalam kurun waktu 180 hari terakhir.

```sql
SELECT c.customer_id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.order_date >= CURRENT_DATE - INTERVAL '180 days'
);
```

#### Kasus 3: Correlated Subquery pada Proyeksi (`SELECT` Clause)
Mengambil detail pelanggan beserta nilai pesanan terakhir mereka.

```sql
SELECT 
    c.customer_id,
    c.name,
    (
        -- Correlated scalar subquery: Harus mengembalikan tepat 1 baris & 1 kolom
        SELECT o.total_amount
        FROM orders o
        WHERE o.customer_id = c.customer_id
        ORDER BY o.order_date DESC, o.order_id DESC
        LIMIT 1
    ) AS latest_order_amount
FROM customers c
WHERE c.country = 'Indonesia';
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Dari Nested Loop ke Query Unnesting
Secara konseptual, model komputasi correlated subquery adalah algoritma **Nested Loop Join**:
$$\mathcal{O}(N \times M)$$
di mana $N$ adalah jumlah baris outer query dan $M$ adalah jumlah baris inner query.

Namun, Query Optimizer modern (seperti pada PostgreSQL, MySQL 8.0+, Oracle) tidak mengeksekusinya secara naif. Engine menjalankan proses optimasi yang disebut **Subquery Unnesting / Flattening**:
1. Optimizer mendeteksi klausa `WHERE EXISTS (...)`.
2. Pola tersebut ditransformasikan secara logis menjadi representasi aljabar relasional **Semi-Join** ($\ltimes$).
3. Jika menggunakan `NOT EXISTS`, pola diubah menjadi **Anti-Join** ($\rhd$).
4. Planner kemudian dapat memilih algoritma join fisik yang jauh lebih efisien daripada Nested Loop, seperti **Hash Semi-Join** atau **Merge Semi-Join**:

```
                               QUERY PLAN (PostgreSQL EXPLAIN)
------------------------------------------------------------------------------------------
 Hash Semi Join  (cost=1.15..3.40 rows=5 width=36)
   Hash Cond: (c.customer_id = o.customer_id)
   ->  Seq Scan on customers c  (cost=0.00..2.10 rows=10 width=36)
         Filter: ((country)::text = 'Indonesia'::text)
   ->  Hash  (cost=1.10..1.10 rows=4 width=4)
         ->  Bitmap Heap Scan on orders o  (cost=0.15..1.10 rows=4 width=4)
               Recheck Cond: (total_amount > 1000.00)
               ...
```

#### Alokasi Memori / Resource
* **Short-Circuit Mechanism:** Pada level engine eksekusi (misal: *Volcano Iterator Model*), fungsi `ExecScan` yang menjalankan inner node akan langsung me-return status `FOUND` ke parent node pada *tuple scan* pertama yang valid. Evaluasi dihentikan seketika tanpa melakukan *materialization* sisa row.
* **WorkMem / Memory Footprint:** Jika optimizer melakukan unnesting menjadi Hash Semi-Join, memori kerja (`work_mem` di PostgreSQL atau `join_buffer_size` di MySQL) digunakan untuk membangun *hash table* dari relasi inner/outer. Jika ukuran dataset melebihi buffer memori, database akan men-tumpahkan (*spill*) partisi batch ke disk temporary space.

#### Trade-offs
* **Correlated Scalar Subquery (`SELECT`)**: Sangat sulit atau terkadang mustahil di-unnest oleh optimizer jika mengandung agregasi kompleks. Akibatnya, engine dipaksa kembali ke eksekusi naif *row-by-row iteration*, mengakibatkan degradasi performa drastis jika dataset outer besar ($N > 100,000$).
* **Projection Optimization**: RDBMS mengabaikan daftar ekspresi pada `SELECT` di dalam `EXISTS`. Statement `EXISTS (SELECT 1 ...)`, `EXISTS (SELECT * ...)`, maupun `EXISTS (SELECT 1/0 ...)` menghasilkan *abstract syntax tree* (AST) fisik yang sama karena engine membuang target list dan hanya memproses operator scan/filter.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan Composite Index untuk Foreign Key + Filter Subquery**: Pada correlated subquery, pastikan kolom yang menghubungkan outer dan inner table diindeks bersamaan dengan kondisi filter. Contoh: `CREATE INDEX idx_o_cust_amt ON orders(customer_id, total_amount)`.
* **Prioritaskan `EXISTS` daripada `DISTINCT + JOIN`**: Saat memeriksa eksistensi relasi *one-to-many*, menggunakan `JOIN` biasa mengharuskan penggunaan `DISTINCT` yang memicu operasi *Sort/Hash Unique* yang mahal di memori. `EXISTS` mempertahankan kardinalitas tabel utama tanpa menduplikasi baris.
* **Ubah Scalar Correlated Subquery ke Window Functions**: Jika membutuhkan data baris terbaru (Kasus 3), gunakan `ROW_NUMBER() OVER (PARTITION BY ...)` atau `LEFT JOIN LATERAL` yang lebih optimal diproses secara set-based.

#### Don'ts
* **Menghindari `NOT IN` pada Kolom yang Nullable**:
  ```sql
  -- BERBAHAYA: Jika orders.customer_id memiliki 1 saja nilai NULL, 
  -- query akan selalu menghasilkan 0 baris (empty set)!
  SELECT * FROM customers 
  WHERE customer_id NOT IN (SELECT customer_id FROM orders);
  
  -- AMAN & PERFORMAN: Menggunakan NOT EXISTS
  SELECT * FROM customers c
  WHERE NOT EXISTS (
      SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
  );
  ```
* **Menghitung Baris dengan `COUNT(*)` untuk Cek Eksistensi**:
  ```sql
  -- ANTI-PATTERN: Memaksa engine memindai SELURUH baris yang cocok
  WHERE (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) > 0

  -- IDIOMATIK: Short-circuit pada baris pertama
  WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)
  ```

#### Edge Cases
* **Outer-Reference Shadowing**: Jika nama kolom pada inner query dan outer query identik dan Anda lupa memberikan alias tabel, RDBMS akan memprioritaskan namespace lingkup terdalam (*innermost scope*).
  ```sql
  -- BUG SILENT: customer_id diambil dari scope `orders`, bukan `customers`
  -- Subquery menjadi NON-CORRELATED dan bernilai true jika ada order valid!
  SELECT * FROM customers c
  WHERE EXISTS (
      SELECT 1 FROM orders 
      WHERE customer_id = customer_id -- Identik dengan: orders.customer_id = orders.customer_id
  );
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Optimasi Unnesting**: Buat dua query setara: satu menggunakan `EXISTS` dan satu menggunakan `INNER JOIN` dengan `DISTINCT`. Jalankan `EXPLAIN (ANALYZE, BUFFERS)` pada PostgreSQL atau `EXPLAIN FORMAT=TREE` pada MySQL 8. Amati apakah query engine menghasilkan execution plan yang identik, dan bandingkan metrik *shared hit blocks* serta *execution time*.
2. **Refactoring Scalar Subquery**: Ambil contoh query pada **Kasus 3** (mengambil nilai pesanan terakhir pelanggan). Tulis ulang query tersebut menggunakan dua pendekatan berbeda:
   * Menggunakan PostgreSQL `LATERAL JOIN`.
   * Menggunakan Common Table Expression (CTE) yang dikombinasikan dengan Window Function `ROW_NUMBER()`.
   Bandingkan alokasi resource dan execution cost-nya terhadap volume data 500.000+ baris.
