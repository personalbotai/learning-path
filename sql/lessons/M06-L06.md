## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Recursive CTE (Common Table Expression) adalah mekanisme standardisasi SQL (SQL:1999) yang memungkinkan sebuah *named temporary result set* merujuk pada dirinya sendiri secara iteratif. Fitur ini hadir untuk menyelesaikan kelemahan fundamental model relasional murni: manipulasi data berbentuk hierarki (hierarchical trees) dan jejaring graf (graphs) yang memiliki kedalaman tak terdefinisi (*arbitrary depth*).

Sebelum adanya Recursive CTE, traversal hierarki pada skema *Adjacency List* (misal: kolom `parent_id`) membutuhkan prosedur tersimpan (*stored procedures*), kueri berulang dari *application layer*, atau denormalisasi skema seperti *Nested Sets* dan *Materialized Paths* yang memiliki *overhead* besar pada operasi penulisan (`INSERT`/`UPDATE`).

```
+-------------------------------------------------------------+
|                     WITH RECURSIVE cte AS (                 |
|                                                             |
|   [ Anchor Member ]       -> Basis evaluasi (Base case)     |
|          UNION ALL                                          |
|   [ Recursive Member ]    -> Evaluasi berulang (Induction)  |
|                                                             |
| ) SELECT * FROM cte;                                        |
+-------------------------------------------------------------+
```

Secara formal, arsitektur sintaksis Recursive CTE terdiri dari tiga komponen inti:
1. **Anchor Member**: Kueri non-rekursif yang dieksekusi tepat satu kali untuk menginisialisasi himpunan baris pertama (kondisi awal/dasar).
2. **Operator Penggabung**: Menggunakan `UNION ALL` (standar performa) atau `UNION` (dengan overhead eliminasi duplikasi implisit).
3. **Recursive Member**: Kueri yang mereferensikan nama CTE tersebut. Kueri ini dieksekusi berulang kali pada *subset* data hasil iterasi sebelumnya, bukan pada akumulasi keseluruhan data sebelumnya.

Evaluasi rekursi berhenti secara deterministik saat Recursive Member menghasilkan *empty set* (tidak ada baris baru yang dievaluasi), atau secara paksa saat mencapai *guard limit* (seperti `MAXRECURSION` di SQL Server atau batas alokasi memori di PostgreSQL/MySQL).

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan struktur pohon organisasi perusahaan (Adjacency List) dengan pelacakan tingkat kedalaman (*depth*), penjejakan jalur (*breadcrumbs path*), dan penanganan batas rekursi.

```sql
-- 1. Setup Skema & Data Sampel
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    manager_id INT REFERENCES employees(employee_id),
    department VARCHAR(50) NOT NULL
);

INSERT INTO employees (employee_id, name, manager_id, department) VALUES
(1, 'Siti Rahma', NULL, 'Executive'),          -- Top-level Node
(2, 'Budi Santoso', 1, 'Engineering'),         -- Level 1
(3, 'Dewi Lestari', 1, 'Product'),             -- Level 1
(4, 'Eko Kurniawan', 2, 'Engineering'),        -- Level 2 (Bawahan Budi)
(5, 'Rina Fitriani', 2, 'Engineering'),        -- Level 2 (Bawahan Budi)
(6, 'Fajar Nugraha', 4, 'Engineering');        -- Level 3 (Bawahan Eko)

-- 2. Kueri Rekursif: Hierarchical Traversal & Breadcrumbs Path
WITH RECURSIVE employee_hierarchy AS (
    -- ANCHOR MEMBER: Mengambil root node (Level 0)
    SELECT 
        employee_id,
        name,
        manager_id,
        department,
        0 AS depth_level,
        CAST(name AS TEXT) AS hierarchy_path
    FROM 
        employees
    WHERE 
        manager_id IS NULL

    UNION ALL

    -- RECURSIVE MEMBER: Melakukan self-join terhadap CTE
    SELECT 
        e.employee_id,
        e.name,
        e.manager_id,
        e.department,
        eh.depth_level + 1,
        eh.hierarchy_path || ' -> ' || e.name
    FROM 
        employees e
    INNER JOIN 
        employee_hierarchy eh ON e.manager_id = eh.employee_id
    WHERE 
        eh.depth_level < 10 -- Guard Clause untuk mitigasi unbounded recursion
)
-- 3. Mengambil hasil evaluasi
SELECT 
    employee_id,
    REPEAT('  ', depth_level) || name AS tree_structure,
    department,
    depth_level,
    hierarchy_path
FROM 
    employee_hierarchy
ORDER BY 
    hierarchy_path;
```

#### Penjelasan Komponen Kueri:
- **`CAST(name AS TEXT)` pada Anchor**: Wajib dilakukan untuk menyamakan tipe dan panjang alokasi data string. Jika tidak dikonversi ke tipe elastis (`TEXT`) atau `VARCHAR(n)` dengan alokasi besar, Recursive Member akan mengalami galat *truncation* atau *type mismatch* karena PostgreSQL/ANSI SQL menentukan skema kolom CTE berdasarkan *Anchor Member*.
- **`eh.depth_level + 1`**: Variabel akumulator untuk melacak kedalaman traversing secara inkremental pada runtime.
- **`eh.depth_level < 10`**: Guard condition logis untuk menjamin eksekusi berhenti sekalipun skema mengalami siklus sirkular (*cyclic reference*).

### 3. Cara Kerja di Balik Layar (Under the Hood)

Secara terminologi komputasi basis data, istilah "rekursi" pada SQL sebenarnya adalah **iterasi berbasis himpunan (*fixed-point iteration*)**.

```
[Anchor Member] 
      │
      ▼
┌──────────────┐     Recursive     ┌──────────────┐
│Working Table │ ────────────────> │ Intermediate │
└──────────────┘      Member       │    Table     │
      │                            └──────────────┘
      │ Append                            │
      ▼                                   │ Swap & Truncate
┌──────────────┐                          │
│ Result Table │ <────────────────────────┘
└──────────────┘
```

#### Eksekusi & Runtime Engine
1. **Inisialisasi Internal Buffers**: RDBMS (misalnya PostgreSQL atau MySQL 8.0) mengalokasikan dua struktur data internal berbasis memori sementara:
   - **Result Table**: Menyimpan seluruh akumulasi data yang akan dikembalikan ke klien.
   - **Working Table**: Hanya menyimpan baris hasil dari iterasi paling akhir ($R_{k}$).
   - **Intermediate Table**: Menampung output sementara saat Recursive Member dieksekusi.
2. **Tahap 1 (Inisiasi)**: *Anchor Member* dieksekusi. Output ditulis secara serentak ke **Result Table** dan **Working Table**.
3. **Tahap 2 (Looping Iteratif)**:
   - RDBMS menjalankan *Recursive Member*, menggunakan isi **Working Table** sebagai input relasi CTE.
   - Hasil kueri dimasukkan ke dalam **Intermediate Table**.
4. **Tahap 3 (State Check & Swap)**:
   - Jika **Intermediate Table** kosong ($\emptyset$), loop berhenti (*termination state*).
   - Jika memiliki data:
     - Seluruh baris di Intermediate Table disalin ke **Result Table**.
     - Data lama di **Working Table** di-evict (dibersihkan), lalu data dari **Intermediate Table** dipindahkan ke **Working Table**.
     - **Intermediate Table** dikosongkan.
     - Kembali ke **Tahap 2**.

#### Alokasi Memori & Resource
- Baris data pada *Working Table* dan *Intermediate Table* disimpan pada alokasi memori eksekusi lokal (contoh: `work_mem` di PostgreSQL).
- Jika skala pohon data melebar atau kedalaman hierarki masif, struktur data sementara ini dapat meluap (*spill*) dari RAM ke disk (membentuk *temp files* di subdirektori `pgsql_tmp`). Hal ini menurunkan performa dari $O(N)$ berbasis RAM menjadi operasi I/O-bound disk yang sangat lambat.

#### Trade-offs
- **Kelebihan**: Normalisasi data tetap terjaga (`3NF`), struktur tabel sederhana (*Adjacency List* fleksibel untuk operasi mutasi `INSERT`/`UPDATE`).
- **Kekurangan**: Kompleksitas komputasi pembacaan lebih tinggi dibandingkan skema *Closure Table* atau *Materialized Paths*. Operasi join berulang pada setiap iterasi membuat CPU consumption melonjak seiring kedalaman graf.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `UNION ALL` secara default**: Hindari `UNION` standar kecuali benar-benar diperlukan untuk menghilangkan entri ganda, karena `UNION` memaksa RDBMS melakukan operasi sorting/hashing yang membebani memori di setiap siklus iterasi.
- **Indeks Foreign Key Penentu Rekursi**: Berikan indeks B-Tree pada kolom relasi parent-child (`CREATE INDEX idx_emp_manager ON employees(manager_id)`). Tanpa indeks ini, RDBMS akan melakukan *Sequential Scan* penuh pada tabel relasi untuk **setiap iterasi**.
- **Definisikan Guard Limits**: Selalu gunakan pembatas kedalaman numerik atau gunakan klausa native seperti `SET max_sp_recursion_depth` (MySQL) atau klausa `CYCLE` (PostgreSQL 14+).

#### Don'ts
- **Menaruh Agregasi di Recursive Member**: Standar ANSI SQL melarang pemanggilan fungsi agregasi (`SUM()`, `COUNT()`), `DISTINCT`, `GROUP BY`, atau `LIMIT` di dalam *Recursive Member* secara langsung karena memutus kesinambungan aljabar relasional iterasi baris per baris.
- **Menggunakan Non-deterministic Join Criteria**: Menghubungkan Recursive Member menggunakan *non-equality operator* atau kondisi ambigu dapat menciptakan kompleksitas komputasi eksponensial ($O(2^n)$ alih-alih linear).

#### Edge Cases: Infinite Loops (Siklus Data)
Jika relasi data tidak murni hierarki (misal: Node A -> Node B -> Node A), CTE akan terjebak dalam *infinite execution loop* yang menguras memori server.

*Pola Penanganan Standar (PostgreSQL < 14 / Universal SQL Engine):*
```sql
-- Menggunakan Tracking Array untuk mendeteksi siklus
WITH RECURSIVE cycle_detector AS (
    SELECT 
        employee_id, 
        manager_id, 
        ARRAY[employee_id] AS visited_nodes,
        FALSE AS is_cycle
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT 
        e.employee_id, 
        e.manager_id,
        cd.visited_nodes || e.employee_id,
        e.employee_id = ANY(cd.visited_nodes) -- True jika ID sudah pernah dikunjungi
    FROM employees e
    JOIN cycle_detector cd ON e.manager_id = cd.employee_id
    WHERE NOT cd.is_cycle -- Memotong iterasi segera setelah siklus terdeteksi
)
SELECT * FROM cycle_detector WHERE is_cycle = TRUE;
```

### 5. Tantangan Eksplorasi Mandiri

1. **Bill of Materials (BOM) Explosion**:
   Buat skema perakitan manufaktur dengan relasi komponen: `parts (part_id, part_name)` dan `assembly (parent_part_id, child_part_id, quantity_required)`. Tulis Recursive CTE untuk menghitung total kuantitas komponen paling dasar (*leaf-nodes*) yang dibutuhkan untuk memproduksi satu unit produk akhir yang terdiri dari hierarki sub-assembly multi-level.

2. **Graph Shortest Path Discovery**:
   Implementasikan pemetaan rute penerbangan: `flights (origin, destination, cost)`. Gunakan Recursive CTE untuk mencari rute termurah antara dua kota tertentu, dengan syarat:
   - Hindari siklus (*infinite loop*).
   - Maksimal transfer/transit (*stops*) adalah 3 kali penerbangan.
   - Hasil harus diurutkan berdasarkan total akumulasi `cost` terendah.
