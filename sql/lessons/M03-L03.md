## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Klausul `GROUP BY` adalah fondasi pemrosesan analitik transaksional dalam SQL yang mengubah himpunan baris individual (*scalar rows*) menjadi baris ringkasan yang dikelompokkan (*aggregated rows*). Secara relasional, `GROUP BY` mempartisi tabel ke dalam partisi-partisi ekuivalen berdasarkan kesamaan nilai pada ekspresi penentu (kunci grup), lalu memetakan fungsi agregasi (seperti `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) ke dalam masing-masing partisi tersebut.

#### Posisi dalam Lifecycle Pemrosesan Query
Dalam siklus eksekusi logis SQL, pemrosesan dilakukan berurutan secara konseptual:
1. `FROM` & `JOIN`: Membentuk ruang sampel data (Cartesian product dengan filter join).
2. `WHERE`: Memangkas baris individual sebelum masuk ke agregator.
3. `GROUP BY`: Mempartisi baris yang lolos seleksi ke dalam ember-ember (*buckets*) nilai unik.
4. `HAVING`: Memfilter bucket/grup hasil agregasi.
5. `SELECT`: Menghitung ekspresi proyeksi dan fungsi agregat.
6. `DISTINCT`: Mengeliminasi baris keluaran duplikat.
7. `ORDER BY`: Mengurutkan himpunan data akhir.
8. `LIMIT` / `OFFSET`: Memangkas baris untuk presentasi.

Karena `GROUP BY` dievaluasi pada langkah ke-3 sedangkan `SELECT` pada langkah ke-5, atribut apa pun yang muncul di klausul `SELECT` harus memenuhi **Aturan Relasional Agregasi**: atribut tersebut harus berupa kolom yang tercantum di klausul `GROUP BY`, fungsi agregat, atau kolom yang secara fungsional bergantung secara langsung (*functionally dependent*, misalnya Primary Key) pada kolom `GROUP BY` (didukung di PostgreSQL dan MySQL mode `ONLY_FULL_GROUP_BY`).

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Analisis performa e-commerce untuk menghitung total pendapatan, rata-rata transaksi, dan jumlah pesanan unik per kategori serta status transaksi.

```sql
-- DDL & Dummy Data Setup
CREATE TABLE orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    category_id INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO orders (customer_id, category_id, status, total_amount, created_at)
VALUES 
    (101, 1, 'COMPLETED', 150000.00, NOW() - INTERVAL '2 days'),
    (102, 1, 'COMPLETED', 350000.00, NOW() - INTERVAL '1 day'),
    (103, 1, 'CANCELLED', 200000.00, NOW() - INTERVAL '1 day'),
    (101, 2, 'COMPLETED', 500000.00, NOW() - INTERVAL '3 days'),
    (104, 2, 'PENDING',   120000.00, NOW()),
    (105, 3, 'COMPLETED', 750000.00, NOW() - INTERVAL '4 days'),
    (102, 2, 'COMPLETED', 250000.00, NOW() - INTERVAL '2 hours');

-- Query Analisis Multi-Level Grouping dengan Filter Pra dan Pasca Agregasi
SELECT 
    category_id,
    status,
    COUNT(order_id) AS total_orders,
    COUNT(DISTINCT customer_id) AS unique_buyers,
    SUM(total_amount) AS gross_revenue,
    ROUND(AVG(total_amount), 2) AS average_order_value,
    MIN(total_amount) AS lowest_sale,
    MAX(total_amount) AS highest_sale
FROM orders
WHERE created_at >= NOW() - INTERVAL '30 days' -- Filter pra-agregasi (mengurangi beban memory)
GROUP BY 
    category_id, 
    status
HAVING 
    COUNT(order_id) >= 1                      -- Filter pasca-agregasi
ORDER BY 
    category_id ASC, 
    gross_revenue DESC;
```

#### Penjelasan Penting:
- `COUNT(order_id)` vs `COUNT(DISTINCT customer_id)`: Perhitungan non-distinct hanya membutuhkan inkremen register penghitung, sedangkan `DISTINCT` di dalam agregat memaksa engine membangun struktur memori sekunder (biasanya hash set terpisah) per bucket untuk memastikan deduplikasi nilai.
- Hubungan `WHERE` vs `HAVING`: `WHERE` menyaring baris sebelum masuk ke engine grouping (meringankan alokasi memori hashing/sorting), sedangkan `HAVING` diterapkan pada data yang sudah diagregasi.

### 3. Cara Kerja di Balik Layar (Under the Hood)

Ketika query planner (misalnya PostgreSQL Optimizer atau MySQL Query Optimizer) menerima perintah `GROUP BY`, ada dua strategi fisik utama yang dipilih untuk memproses data:

```
[Data Input Stream]
        │
        ├─── Evaluasi Biaya Cost-Based Optimizer (CBO)
        │
        ├─► Strategi A: HashAggregate (Hash Table In-Memory)
        │     • Masukkan key ke Hash Bucket
        │     • Update state agregat in-place
        │     • Spill ke Disk (Temporary Batch Files) jika work_mem habis
        │
        └─► Strategi B: GroupAggregate (Presorted Stream)
              • Membutuhkan index (B-Tree) atau Sort eksplisit sebelumnya
              • Baca baris sekuensial: jika key berganti, emit hasil & reset state
```

#### 1. HashAggregate
- **Mekanisme**: Engine mengalokasikan hash table di memori kerja (RAM, diatur oleh `work_mem` di Postgres atau `tmp_table_size` di MySQL). Engine membaca baris data baris demi baris, menghitung hash dari kolom-kolom `GROUP BY`, dan mencari bucket yang relevan.
- **Akumulator**: Nilai agregat (seperti pointer state `SUM` atau counter `COUNT`) disimpan langsung di dalam hash bucket. Jika hash key sudah ada, state diperbarui *in-place*. Jika belum ada, entri baru dialokasikan.
- **Resource Exhaustion**: Jika ukuran hash table melebihi kuota memori yang dialokasikan, engine melakukan *hash spill-to-disk*. PostgreSQL akan membagi data menjadi partisi-partisi batch dan menulisnya ke disk menggunakan temporary files, yang menurunkan throughput I/O secara drastis.

#### 2. GroupAggregate (Sort-Based)
- **Mekanisme**: Engine mengasumsikan atau memaksa data masuk dalam keadaan terurut berdasarkan kolom `GROUP BY`. Keterurutan ini didapat dari pembacaan B-Tree Index yang sudah ada atau melalui tahapan eksplisit `Sort node`.
- **Eksekusi Stream**: Engine cukup membandingkan nilai kolom grup pada baris saat ini dengan baris sebelumnya. Jika nilainya sama, state agregasi diakumulasi. Saat nilai berubah (*control break*), engine langsung memancarkan (*emit*) baris output dan mereset state agregat untuk grup baru.
- **Efisiensi Memori**: Penggunaan memori konstan ($O(1)$) untuk pelacakan grup, karena engine tidak perlu mempertahankan seluruh grup dalam memori sekaligus.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Manfaatkan Index Kolom Penentu**: Jika query sering melakukan `GROUP BY col_a, col_b`, buat komposit B-Tree index pada `(col_a, col_b)`. Ini memungkinkan database memilih `GroupAggregate` langsung lewat index scan tanpa perlu alokasi memori besar untuk *sort* atau *hash*.
- **Filter Agresif di `WHERE`**: Kurangi volume baris sedini mungkin. Memfilter 1 juta baris menjadi 10.000 baris menggunakan `WHERE` jauh lebih murah daripada mengelompokkan 1 juta baris lalu menyaringnya dengan `HAVING`.
- **Gunakan Functional Dependency**: Jika mengelompokkan berdasarkan entitas, cukup gunakan Primary Key entitas tersebut di `GROUP BY` alih-alih mendaftarkan semua kolom tabel (pada DB yang mendukung standard SQL:1999+).

#### Don'ts
- **Menyalahgunakan `HAVING` untuk Kondisi Non-Agregat**: Jangan menulis `HAVING status = 'COMPLETED'`. Kondisi ini memaksa baris yang tidak relevan ikut masuk ke tahap hashing/sorting. Gunakan `WHERE status = 'COMPLETED'`.
- **Kombinasi `GROUP BY` dan `COUNT(DISTINCT ...)` Skala Masif**: Operasi multi-distinct aggregation (misal: `COUNT(DISTINCT a), COUNT(DISTINCT b)`) menonaktifkan optimasi fast path hash table dan memicu *work memory explosion* atau multipass sort.

#### Edge Cases & Pitfalls
- **Semantik Nilai `NULL`**: Dalam standar ANSI SQL, nilai `NULL` tidak sama dengan `NULL` (`NULL = NULL` menghasilkan `UNKNOWN`). Namun, pada `GROUP BY`, semua nilai `NULL` dianggap setara secara partisi dan disatukan ke dalam satu grup tunggal.
- **Karakter Kolasi / Collation**: Grouping string peka terhadap konfigurasi kolasi database (misal: `utf8mb4_unicode_ci` vs `utf8mb4_bin`). Pada kolasi *case-insensitive*, nilai `'Admin'` dan `'admin'` akan dilebur menjadi satu grup yang sama, yang dapat memicu ketidakkonsistenan tampilan data jika tidak dipahami.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan**: Jalankan perintah `EXPLAIN ANALYZE` pada PostgreSQL atau `EXPLAIN FORMAT=TREE` pada MySQL untuk query di Bagian 2. Identifikasi apakah node yang digunakan bertipe `HashAggregate` atau `GroupAggregate`.
2. **Simulasi Memory Spilling**: Perkecil alokasi memori sementara (pada Postgres: jalankan `SET work_mem = '64kB';` dalam sesi lokal), kemudian jalankan agregasi pada tabel berukuran ratusan ribu baris dengan banyak key unik. Amati perubahan node planner menjadi sort spill-to-disk (misal: *External Sort* atau *Spill to disk on batches*).
3. **Optimasi B-Tree Pipeline**: Tambahkan index komposit `CREATE INDEX idx_orders_cat_status ON orders(category_id, status);`. Jalankan kembali query analisis dan amati apakah optimizer mengeliminasi pemrosesan hashing sepenuhnya demi pipeline `GroupAggregate`.
