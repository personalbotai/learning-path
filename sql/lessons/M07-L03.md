### 1. Konsep & Arsitektur Mendalam

*Window Functions* (fungsi jendela) pada SQL mengeksekusi kalkulasi analitik pada sekumpulan baris (*window*) yang memiliki relasi dengan baris saat ini (*current row*) tanpa mengompresi/mengagregasi baris-baris tersebut menjadi satu baris tunggal seperti halnya klausa `GROUP BY`.

Kekuatan analitik utama dari *window function* bertumpu pada sub-klausa di dalam `OVER()`:
1. **`PARTITION BY`**: Memecah result set menjadi partisi data independen.
2. **`ORDER BY`**: Menentukan urutan deterministik evaluasi baris dalam partisi.
3. **`ROWS` / `RANGE` (Window Framing)**: Membatasi *subset* dinamis dari baris-baris dalam partisi yang digunakan untuk menghitung nilai fungsi pada *current row*.

```
+-----------------------------------------------------------------------------------+
| PARTITION (Kategori A)                                                            |
|  [Row 1] -> UNBOUNDED PRECEDING                                                   |
|  [Row 2] -> 1 PRECEDING                                                           |
|  [Row 3] -> CURRENT ROW          <--- [FRAME: ROWS BETWEEN 2 PRECEDING AND CURRENT]
|  [Row 4] -> 1 FOLLOWING                                                           |
|  [Row 5] -> UNBOUNDED FOLLOWING                                                   |
+-----------------------------------------------------------------------------------+
```

#### Framing: `ROWS` vs `RANGE`
Banyak developer mengabaikan klausul *framing*, padahal definisi frame secara drastis mengubah hasil dan performa query:

*   **`ROWS` (Physical Framing)**: Bekerja berdasarkan hitungan baris fisik secara eksplisit.
    Contoh: `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` selalu mengevaluasi tepat maksimal dua baris fisik (baris sebelumnya dan baris saat ini), terlepas dari nilai datanya identik atau tidak.
*   **`RANGE` (Logical Framing)**: Bekerja berdasarkan nilai logis dari kolom yang di-*order*.
    Contoh: Jika ada baris dengan nilai duplikat (*ties*) pada kolom `ORDER BY`, `RANGE` akan memperlakukan semua baris duplikat tersebut sebagai satu kesatuan (*peer group*).
*   **Default Behavior (Jebakan Terbesar)**:
    Jika Anda menulis klausa `OVER (ORDER BY date_col)` tanpa mendeklarasikan frame, ANSI SQL menetapkan *default framing* sebagai:
    ```sql
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ```
    Artinya, jika terdapat nilai duplikat pada `date_col`, perhitungan akumulatif akan melompat dan menggabungkan semua nilai baris duplikat tersebut ke dalam *current row*, bukan berjalan murni baris demi baris.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Analisis arus kas (*cash flow*) harian dengan metrik *Cumulative Balance* (saldo berjalan) dan *7-Day Moving Average* (rata-rata bergerak 7 transaksi terakhir).

```sql
-- DDL & Data Dummy
CREATE TABLE bank_transactions (
    id SERIAL PRIMARY KEY,
    account_id INT NOT NULL,
    transaction_date DATE NOT NULL,
    amount NUMERIC(12, 2) NOT NULL
);

INSERT INTO bank_transactions (account_id, transaction_date, amount) VALUES
(101, '2026-03-01',  500.00),
(101, '2026-03-02', -100.00),
(101, '2026-03-02', -150.00), -- Tanggal kembar (Ties) untuk demonstrasi
(101, '2026-03-03',  300.00),
(101, '2026-03-04',  200.00),
(101, '2026-03-05', -50.00),
(101, '2026-03-06',  400.00),
(101, '2026-03-07', -100.00);

-- Query Analitik dengan ROWS Framing
SELECT 
    id,
    transaction_date,
    amount,
    
    -- 1. Default (Implicit RANGE): Hati-hati pada tanggal 2026-03-02
    SUM(amount) OVER (
        PARTITION BY account_id 
        ORDER BY transaction_date
    ) AS balance_implicit_range,

    -- 2. Explicit ROWS: Running Total murni baris-demi-baris
    SUM(amount) OVER (
        PARTITION BY account_id 
        ORDER BY transaction_date, id -- Deterministic tie-breaker
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_balance_strict,

    -- 3. Moving Average: Rolling window 3 transaksi terakhir (2 baris sebelumnya + current)
    AVG(amount) OVER (
        PARTITION BY account_id 
        ORDER BY transaction_date, id
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS rolling_avg_last_3_trans,

    -- 4. Centered Moving Average: 1 sebelum, current, 1 sesudah
    AVG(amount) OVER (
        PARTITION BY account_id 
        ORDER BY transaction_date, id
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ) AS centered_avg
FROM 
    bank_transactions
ORDER BY 
    account_id, transaction_date, id;
```

#### Analisis Hasil Query:
Pada tanggal `2026-03-02`, terdapat dua transaksi (`-100.00` dan `-150.00`).
*   `balance_implicit_range` akan menghasilkan nilai akumulatif yang langsung menjumlahkan keduanya (`500 - 100 - 150 = 250`) pada baris pertama di tanggal tersebut, karena sifat `RANGE` menggabungkan *peers*.
*   `running_balance_strict` dengan `ROWS` menghasilkan evaluasi sekuensial yang presisi: baris pertama menghasilkan `400.00` (`500 - 100`), dan baris kedua menghasilkan `250.00` (`400 - 150`).

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Ketika query planner (misalnya pada PostgreSQL engine) menerima fungsi jendela:
1. **Sort Engine Node**: Engine mengeksekusi operasi pengurutan via node `Sort` berdasarkan kunci `PARTITION BY` lalu `ORDER BY`. Jika indeks komposit yang relevan (`account_id, transaction_date`) sudah tersedia, engine melakukan *Index Scan* atau *Incremental Sort*, memangkas overhead pemilahan data.
2. **`WindowAgg` Operator**: Node eksekutor khusus yang membaca stream baris terurut.
   * Pada **`ROWS`**, engine mempertahankan *ring buffer* atau sliding pointer dengan ukuran tetap (*fixed boundary offset*). Untuk kalkulasi agregasi seperti `SUM` atau `AVG`, engine dapat menggunakan teknik *sliding window aggregation* ($O(1)$ amortized cost) dengan menambah baris baru yang masuk dan mengurangkan baris yang keluar dari frame.
   * Pada **`RANGE`**, engine wajib melakukan *look-ahead* untuk memeriksa apakah baris berikutnya bernilai sama (*peer check*). Engine tidak dapat langsung menghasilkan output sampai mendeteksi transisi nilai, yang meningkatkan operasi perbandingan (*comparisons*).

#### Alokasi Memori / Resource
*   Data window dialokasikan pada memori kerja engine (misal: `work_mem` di PostgreSQL).
*   Jika ukuran partisi dan data framing melebihi kapasitas memori yang dialokasikan, data tumpah (*spills*) dari memori ke disk menggunakan berkas temporer (*spill to disk / temporary files*). Hal ini menyebabkan degradasi performa I/O yang drastis (*external merge sort*).

#### Trade-offs: `ROWS` vs `RANGE`
| Karakteristik | `ROWS` | `RANGE` |
| :--- | :--- | :--- |
| **Operasi Boundary** | Berbasis offset indeks integer ($i - k$) | Evaluasi relasional logis nilai kolom |
| **Efisiensi Algoritma** | Sangat cepat ($O(N)$ waktu total) | Lebih lambat jika terdapat banyak duplikasi |
| **Deterministik** | Ya (jika sorting menggunakan tie-breaker) | Selalu mendistribusikan hasil sama pada *peer ties* |

### 4. Best Practices & Common Pitfalls

#### Do's
*   **Selalu spesifikasikan framing secara eksplisit**: Jangan biarkan engine menggunakan default `RANGE`. Selalu definisikan `ROWS BETWEEN ...` untuk kebutuhan akumulatif atau *rolling window*.
*   **Gunakan Deterministic Tie-Breaker**: Jika kolom `ORDER BY` mengandung data non-unik (seperti `DATE`), tambahkan primary key atau kolom unik sekunder:
    ```sql
    ORDER BY transaction_date ASC, id ASC
    ```
    Mencegah hasil perhitungan bergeser secara non-deterministik saat data dibaca ulang.
*   **Manfaatkan Window Clause Terpusat**: Jika beberapa metrik menggunakan frame yang identik, gunakan klausa `WINDOW` di akhir query untuk mereduksi duplikasi kode:
    ```sql
    SELECT 
        SUM(amount) OVER w,
        AVG(amount) OVER w
    FROM bank_transactions
    WINDOW w AS (PARTITION BY account_id ORDER BY transaction_date, id ROWS BETWEEN 6 PRECEDING AND CURRENT ROW);
    ```

#### Don'ts
*   **Jangan gunakan `UNBOUNDED FOLLOWING` jika tidak mutlak diperlukan**:
    ```sql
    -- ANTI-PATTERN: Memaksa engine mem-buffer seluruh partisi ke memori sebelum kalkulasi baris pertama
    SUM(amount) OVER (PARTITION BY account_id ORDER BY id ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING)
    ```
    Framing ini membalik arah evaluasi alami dan mencegah *pipelined/streaming execution*.

#### Edge Cases
*   **Partisi dengan Ukuran Frame Melampaui Jumlah Baris**:
    Jika Anda mendefinisikan `ROWS BETWEEN 5 PRECEDING AND CURRENT ROW` pada baris ke-2, engine tidak akan menghasilkan *error*. Engine secara dinamis memotong frame menjadi baris yang tersedia saja (`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`). Hal ini penting untuk validasi perhitungan rata-rata bergerak di awal partisi.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan (`EXPLAIN ANALYZE`)**:
   Buat tabel dengan 100.000 baris acak yang memiliki banyak duplikasi nilai tanggal. Eksekusi `SUM(val) OVER (ORDER BY date_col)` (default `RANGE`) lalu bandingkan CPU time dan memory consumption dengan `SUM(val) OVER (ORDER BY date_col ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`. Temukan perbedaannya pada node `WindowAgg`.

2. **Deteksi Lonjakan Volatilitas (Rolling StdDev)**:
   Buat query transaksi yang menghitung standar deviasi pergerakan harga (*volatility*) menggunakan fungsi agregat `STDDEV()` dengan kerangka jendela simetris: tepat 3 transaksi sebelum dan 3 transaksi setelah baris saat ini (`ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING`). Pastikan query menangani data awal dan akhir partisi secara anggun tanpa crash.
