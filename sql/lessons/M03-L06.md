## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Agregasi dalam Relational Database Management System (RDBMS) adalah proses mentransformasikan multiset data (baris jamak) menjadi skalar atau nilai rangkuman berdasarkan partisi tertentu. Meskipun secara sintaksis terlihat sederhana, operasi agregasi sering menjadi sumber *silent bugs* dan degradasi performa ekstrem di lingkungan produksi akibat perbedaan semantik ANSI SQL, penanganan nilai `NULL`, serta batas arsitektural *query execution engine*.

#### A. Semantik NULL dan Tiga Nilai Logika (Three-Valued Logic)
ANSI SQL mendefinisikan bahwa fungsi agregat standar—seperti `SUM()`, `AVG()`, `MIN()`, `MAX()`, dan `COUNT(ekspresi)`—mengeliminasi nilai `NULL` sebelum evaluasi dilakukan. Pengecualian tunggal ada pada `COUNT(*)`, yang mengevaluasi kardinalitas baris secara utuh tanpa memedulikan nilai tiap kolom.
- `COUNT(*)` vs `COUNT(col)`: `COUNT(*)` mengembalikan jumlah baris fisik yang memenuhi predikat filter. `COUNT(col)` mengembalikan jumlah baris di mana `col IS NOT NULL`.
- Bahaya `AVG()`: `AVG(col)` ekuivalen dengan `SUM(col) / COUNT(col)`, **bukan** `SUM(col) / COUNT(*)`. Jika ada baris dengan nilai `NULL`, pembagi (denominator) mengecil, menghasilkan rata-rata yang terdistorsi secara statistik.

#### B. Standar SQL dan Mode Skema: Fenomena Non-Aggregate Expressions
Standar ANSI SQL:1992 mewajibkan setiap kolom non-agregat di klausul `SELECT` harus diekspresikan secara eksplisit di klausul `GROUP BY`.
Standar ANSI SQL:1999 dan versi setelahnya memperlonggar aturan ini melalui konsep **Functional Dependency**: jika kolom pada klausul `GROUP BY` merepresentasikan Primary Key (PK) dari tabel, maka kolom lain dari tabel yang sama valid untuk dimuat di `SELECT` tanpa harus masuk `GROUP BY`.

Banyak *engine* lawas (seperti MySQL pra-5.7 tanpa `ONLY_FULL_GROUP_BY`) mengizinkan kueri ambigu dieksekusi:
```sql
-- Ilegal secara logika deterministik jika id bukan penentu unik untuk department:
SELECT department, employee_name, MAX(salary)
FROM employees
GROUP BY department;
```
Pada skenario non-deterministik tersebut, *engine* memilih nilai `employee_name` secara acak (*indeterminate value*) dari baris mana pun dalam grup, bukan baris pemilik `MAX(salary)`.

#### C. The Fan-Out Trap (Ledakan Kardinalitas Join)
Ketika melakukan agregasi terhadap data yang dihasilkan dari relasi *one-to-many* atau *many-to-many*, kardinalitas baris akan mengembang (*fan-out*). Jika developer menerapkan `SUM()` atau `COUNT()` langsung pada tabel induk setelah join dengan tabel anak jamak, data induk akan terduplikasi dan menghasilkan nilai agregat yang salah secara eksponensial.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skrip DDL dan skenario pengujian komprehensif (PostgreSQL 14+ / modern ANSI SQL) yang mereplikasi pitfall agregasi paling umum dan solusi korektifnya.

```sql
-- 1. Setup Skema Eksperimen
DROP TABLE IF EXISTS order_items CASCADE;
DROP TABLE IF EXISTS orders CASCADE;

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    shipping_cost NUMERIC(10, 2) NOT NULL,
    order_status VARCHAR(20) NOT NULL
);

CREATE TABLE order_items (
    item_id INT PRIMARY KEY,
    order_id INT NOT NULL REFERENCES orders(order_id),
    product_name VARCHAR(50) NOT NULL,
    quantity INT NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    discount_pct NUMERIC(5, 2) -- bernilai NULL jika tidak ada diskon
);

INSERT INTO orders (order_id, customer_id, shipping_cost, order_status) VALUES
(101, 1, 15000.00, 'COMPLETED'),
(102, 1, 20000.00, 'COMPLETED'),
(103, 2, 10000.00, 'PENDING');

INSERT INTO order_items (item_id, order_id, product_name, quantity, unit_price, discount_pct) VALUES
(1, 101, 'RAM DDR5 32GB', 2, 1500000.00, 0.10),
(2, 101, 'NVMe SSD 1TB',  1, 1200000.00, NULL),  -- NULL discount
(3, 102, 'Mechanical KB',  1,  800000.00, 0.05),
(4, 102, 'Gaming Mouse',   1,  500000.00, NULL);  -- NULL discount

-- ============================================================================
-- PITFALL 1: Perilaku Agregasi Terhadap NULL (Distorsi Statistik)
-- ============================================================================

-- SALAH: Menghitung rata-rata diskon secara naif
-- AVG() mengabaikan NULL, sehingga total diskon hanya dibagi 2 (bukan 4 item)
SELECT 
    AVG(discount_pct) AS naive_avg_discount,               -- Hasil: 0.075 (7.5%) -> BIAS
    AVG(COALESCE(discount_pct, 0.00)) AS correct_avg_discount -- Hasil: 0.0375 (3.75%) -> VALID
FROM order_items;

-- ============================================================================
-- PITFALL 2: The Fan-Out Trap (Join Duplikasi Agregat)
-- Menghitung total shipping_cost dan total revenue per customer
-- ============================================================================

-- SALAH: Join langsung menyebabkan baris orders terduplikasi sebanyak order_items
SELECT 
    o.customer_id,
    SUM(o.shipping_cost) AS corrupted_total_shipping, -- Duplikasi nilai shipping!
    SUM(oi.quantity * oi.unit_price) AS total_item_spend
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.order_status = 'COMPLETED'
GROUP BY o.customer_id;

-- BENAR: Menggunakan CTE/Subquery Pre-aggregation untuk mengisolasi dimensi kardinalitas
WITH aggregated_items AS (
    SELECT 
        order_id,
        SUM(quantity * unit_price) AS order_item_total
    FROM order_items
    GROUP BY order_id
)
SELECT 
    o.customer_id,
    SUM(o.shipping_cost) AS valid_total_shipping,
    SUM(ai.order_item_total) AS valid_total_item_spend
FROM orders o
JOIN aggregated_items ai ON o.order_id = ai.order_id
WHERE o.order_status = 'COMPLETED'
GROUP BY o.customer_id;

-- ============================================================================
-- PITFALL 3: Aggregation Filtering (WHERE vs. Conditional Aggregation)
-- Menghitung metrik agregat parsial tanpa memotong dataset utama
-- ============================================================================

-- Modern ANSI: Gunakan klausul FILTER (atau CASE WHEN jika pada MySQL/SQL Server)
SELECT 
    customer_id,
    COUNT(*) AS total_orders,
    -- FILTER clause (PostgreSQL/SQLite) jauh lebih optimal daripada subquery berulang
    COUNT(*) FILTER (WHERE order_status = 'COMPLETED') AS completed_orders,
    SUM(shipping_cost) FILTER (WHERE order_status = 'COMPLETED') AS completed_shipping_spend,
    -- Alternatif kompatibel semua RDBMS via Conditional Aggregation:
    SUM(CASE WHEN order_status = 'PENDING' THEN shipping_cost ELSE 0 END) AS pending_shipping_spend
FROM orders
GROUP BY customer_id;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Runtime: HashAggregate vs. GroupAggregate
Query Optimizer menerjemahkan agregasi menggunakan dua algoritma utama:

```
[GroupAggregate Engine Pipeline]
Data Input -> Sort Operator (O(N log N) jika tak berindeks) -> Stream Rows -> Aggregate on Value Change -> Output

[HashAggregate Engine Pipeline]
Data Input -> Compute Hash(Group Key) -> Insert to In-Memory Hash Table -> Spill to Disk if Full -> Read Bucket -> Output
```

1. **Sort GroupAggregate**:
   - Membutuhkan data yang sudah terurut berdasarkan kolom `GROUP BY`.
   - Mengonsumsi memori konstan $O(1)$ jika indeks B-Tree yang kompatibel telah tersedia, membaca data secara sekuensial (*streaming operator*).
   - Jika data belum terurut, *engine* menyuntikkan node `Sort` ($O(N \log N)$), yang sangat mahal pada *dataset* besar.
2. **HashAggregate**:
   - *Engine* mengalokasikan *hash table* di memori transient (misal: `work_mem` di PostgreSQL atau *Hash Space* di Oracle).
   - Kolom grup di-hash menjadi kunci, dan nilai akumulator disimpan di dalam *bucket*.
   - Kompleksitas waktu $O(N)$ rata-rata, tetapi mengonsumsi memori besar sebanding dengan kardinalitas grup (*distinct keys*).

#### B. Alokasi Memori & Disk Spilling
Jika memori yang dibutuhkan *HashAggregate* melebihi batas yang dikonfigurasi (misal: `work_mem` habis):
- Engine beralih ke mode **External Hash Aggregation** atau **Sort-Merge Spilling**.
- Partisi hash dialirkan ke disk (*temporary files* pada filesystem atau `tempdb`).
- Hal ini menimbulkan *Disk I/O bottleneck* masif yang menurunkan performa kueri hingga puluhan kali lipat.

#### C. Blocking vs. Pipelined Operators
Agregasi global (seperti `COUNT(*)`, `SUM()`) atau agregasi tanpa indeks pengurutan adalah **blocking operators**. Operator hilir (*downstream nodes*) tidak dapat menerima baris data pertama sampai baris data terakhir dari operator hulu (*upstream*) selesai dibaca dan diakumulasikan. Hal ini meniadakan efektivitas `LIMIT` pagination cepat pada skala data puluhan juta baris.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Eksplisitkan Karakteristik Kolom Nullable**: Selalu gunakan `COALESCE(col, 0)` di dalam fungsi agregasi jika entri kosong harus memiliki bobot matematis nol (seperti perhitungan rasio, audit saldo, atau rata-rata skor).
- **Gunakan Pre-Aggregation (Derived Tables/CTE)**: Ketika melakukan *join* antar tabel *parent-child* (relasi $1:N$), agregasikan tabel *child* terlebih dahulu sebelum dieksekusi dengan relasi *parent* untuk menghindari *Cartesian product explosion*.
- **Manfaatkan Indeks untuk Grouping (Index-Only Scan)**: Buat *composite index* yang mencakup kolom agregat dan filter (misal: `CREATE INDEX idx_orders_status_cust ON orders(order_status, customer_id, shipping_cost)`) agar database dapat mengeksekusi agregasi langsung dari B-Tree tanpa menyentuh *heap storage* tabel.
- **Aktifkan Strict SQL Mode**: Pastikan bendera database seperti `ONLY_FULL_GROUP_BY` (MySQL) selalu aktif di lingkungan dev maupun prod untuk mencegah interpretasi sintaks non-standar yang berpotensi menghasilkan *silent data corruption*.

#### Don'ts
- **Hindari `SELECT DISTINCT` untuk Memperbaiki Cartesian Join**: Menggunakan `SELECT DISTINCT` setelah agregasi salah kaprah adalah anti-pattern berat. Ini hanya menyamarkan gejala duplikasi dengan memaksakan operasi *sorting* sekunder di memori, bukan menyelesaikan akar masalah relasionalnya.
- **Hindari Tipe Data `FLOAT` / `REAL` untuk Agregasi Finansial**: Agregasi `SUM()` pada tipe *floating-point* rentan terhadap *binary representation error* (misal: `0.1 + 0.2 = 0.30000000000000004`). Gunakan `DECIMAL` / `NUMERIC`.
- **Jangan Menggunakan `HAVING` untuk Kondisi Non-Agregat**: Menempatkan filter baris biasa (seperti status atau tanggal) di dalam klausul `HAVING` memaksa *engine* membaca dan mengelompokkan seluruh tabel terlebih dahulu sebelum membuang datanya. Filter tersebut wajib berada di klausul `WHERE`.

#### Edge Cases
- **`SUM()` pada Tabel Kosong**: Operasi `SUM()` pada *dataset* berukuran nol (atau di mana seluruh baris terfilter oleh `WHERE`) menghasilkan `NULL`, **bukan** `0`. Aplikasi backend yang mem-parsing tipe data integer non-nullable akan mengalami *runtime exception* jika tidak dibungkus oleh `COALESCE(SUM(col), 0)`.
- **Integer Overflow pada Agregasi**: Mengagregasi kolom berformat `INT` (32-bit, batas maksimal $\sim 2.14$ miliar) pada jutaan baris data dapat memicu *integer overflow error*. Konversi tipe data akumulator menggunakan `SUM(col::BIGINT)` atau ubah tipe kolom skema dasar ke `BIGINT`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Rencana Eksekusi (Execution Plan)**:
   Buat tabel dengan 1.000.000 baris data dummy. Jalankan perintah agregasi `SELECT category, AVG(val) FROM t GROUP BY category`. Gunakan `EXPLAIN ANALYZE` (PostgreSQL) atau `EXPLAIN FORMAT=JSON` (MySQL). Amati kapan engine memilih operator `HashAggregate` versus `GroupAggregate`. Ubah parameter `work_mem` menjadi sangat kecil (misal: `64kB`) dan identifikasi apakah terjadi *disk spill* (ditandai dengan munculnya *temporary files written*).
   
2. **Dekonstruksi Silent Bug Multi-Join**:
   Tulis kueri yang menghubungkan tiga tabel hierarki: `users` (1) $\rightarrow$ `posts` (N) dan `users` (1) $\rightarrow$ `comments` (M). Hitung metrik agregat `total_posts` dan `total_comments` per user dalam satu kueri tunggal. Buktikan mengapa join langsung menghasilkan nilai yang salah (*cross-product fan-out*), lalu rancang solusi menggunakan dua pendekatan:
   - Menggunakan *Correlated Subqueries*.
   - Menggunakan *Multiple CTE Pre-Aggregations*.
   Bandingkan biaya eksekusi (*cost*) dari kedua pendekatan tersebut menggunakan profiler database Anda.
