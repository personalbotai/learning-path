### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur basis data relasional (RDBMS) standar sebelum diperkenalkannya SQL:2003 (ISO/IEC 9075-2:2003), tabel diperlakukan murni sebagai himpunan matematika nir-urut (*unordered sets*). Mengakses data dari baris lain—misalnya menghitung delta metrik antar hari atau mendeteksi transisi status sistem—mengharuskan *Self-Join* atau *Correlated Subquery*. Pendekatan ini memiliki kompleksitas komputasi $O(N^2)$ pada skenario terburuk dan membebani I/O *buffer pool* secara masif.

Fungsi *Window* navigasi baris—khususnya `LEAD` dan `LAG`—diperkenalkan untuk mengatasi masalah disparitas urutan fisik dan logika himpunan ini:
- **`LAG(expression, [offset], [default])`**: Mengambil nilai atribut dari $k$ baris *sebelum* baris saat ini (*current row*) di dalam partisi yang terurut.
- **`LEAD(expression, [offset], [default])`**: Mengambil nilai atribut dari $k$ baris *setelah* baris saat ini di dalam partisi yang terurut.

```
       Partisi Data (ORDER BY event_time)
+-------+-------------------------+-------------------------+
| Baris | Nilai Asli              | Evaluasi Window         |
+-------+-------------------------+-------------------------+
|   1   | [Tuple 1]               | LAG(val, 1) -> NULL     |
|   2   | [Tuple 2]               | LAG(val, 1) -> Tuple 1  |
|   3   | [Tuple 3] (Current Row) | LEAD(val, 1) -> Tuple 4 |
|   4   | [Tuple 4]               | LEAD(val, 1) -> Tuple 5 |
|   5   | [Tuple 5]               | LEAD(val, 1) -> NULL    |
+-------+-------------------------+-------------------------+
```

Secara arsitektural, `LEAD` dan `LAG` beroperasi pada tahap akhir pemrosesan query logika SQL:
$$\text{FROM} \rightarrow \text{WHERE} \rightarrow \text{GROUP BY} \rightarrow \text{HAVING} \rightarrow \mathbf{WINDOW} \rightarrow \text{SELECT} \rightarrow \text{DISTINCT} \rightarrow \text{ORDER BY} \rightarrow \text{LIMIT}$$

Karena dievaluasi pada tahap `WINDOW`, fungsi ini tidak memadatkan baris (*non-collapsing aggregation*) seperti `SUM()` agregat biasa. Setiap baris input mempertahankan identitasnya masing-masing, sementara *tuple buffer* di memori memungkinkan pengintipan (*lookahead* atau *lookbehind*) secara langsung tanpa pembacaan ulang blok disk.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Analisis sesi transpor logistik atau telemetri server. Kita perlu mendeteksi selisih waktu respons server (latensi antar *request*) dan memprediksi anomali nilai status berdasarkan metrik *request* selanjutnya.

```sql
-- DDL & Sample Data
CREATE TABLE server_metrics (
    server_id VARCHAR(10) NOT NULL,
    recorded_at TIMESTAMP NOT NULL,
    cpu_utilization NUMERIC(5, 2) NOT NULL,
    status_code INT NOT NULL,
    CONSTRAINT pk_server_metrics PRIMARY KEY (server_id, recorded_at)
);

INSERT INTO server_metrics (server_id, recorded_at, cpu_utilization, status_code) VALUES
('srv-alpha', '2026-03-30 08:00:00', 45.50, 200),
('srv-alpha', '2026-03-30 08:00:15', 48.00, 200),
('srv-alpha', '2026-03-30 08:00:30', 89.20, 500),
('srv-alpha', '2026-03-30 08:00:45', 92.10, 503),
('srv-alpha', '2026-03-30 08:01:00', 51.00, 200),
('srv-beta',  '2026-03-30 08:00:00', 12.00, 200),
('srv-beta',  '2026-03-30 08:00:20', 15.30, 200);

-- Implementasi Analisis Selisih & Prediksi Transisi
WITH TelemetryAnalysis AS (
    SELECT 
        server_id,
        recorded_at,
        cpu_utilization,
        status_code,
        -- Mengambil CPU utilization dari 1 tick sebelumnya (default fallback = nilai sendiri)
        LAG(cpu_utilization, 1, cpu_utilization) OVER w AS prev_cpu,
        -- Mengambil jeda waktu dari metrik sebelumnya dalam satuan detik
        EXTRACT(EPOCH FROM (
            recorded_at - LAG(recorded_at, 1) OVER w
        )) AS delta_seconds_from_prev,
        -- Mengintip status_code 1 tick di masa depan untuk deteksi kegagalan transisi
        LEAD(status_code, 1, 0) OVER w AS next_status_code
    FROM server_metrics
    WINDOW w AS (
        PARTITION BY server_id 
        ORDER BY recorded_at ASC
    )
)
SELECT 
    server_id,
    recorded_at,
    cpu_utilization,
    prev_cpu,
    ROUND((cpu_utilization - prev_cpu), 2) AS cpu_surge,
    delta_seconds_from_prev,
    status_code,
    next_status_code,
    CASE 
        WHEN status_code = 200 AND next_status_code >= 500 THEN 'WARNING: Cascading Failure Imminent'
        WHEN status_code >= 500 AND next_status_code = 200 THEN 'INFO: Recovery Detected'
        ELSE 'STABLE'
    END AS operational_health
FROM TelemetryAnalysis
ORDER BY server_id, recorded_at;
```

#### Penjelasan Komponen Kunci:
1. `WINDOW w AS (...)`: Klausa penamaan window untuk menjaga prinsip DRY (*Don't Repeat Yourself*). Memastikan fungsi `LAG` dan `LEAD` berbagi konteks partisi dan pengurutan yang identik, mencegah *multiple sort passes*.
2. `LAG(cpu_utilization, 1, cpu_utilization)`: Parameter ketiga adalah nilai *default fallback*. Jika dieksekusi pada baris pertama di dalam partisi (di mana baris sebelumnya tidak eksis), mesin query mengembalikan nilai `cpu_utilization` saat itu, bukan `NULL`.
3. `PARTITION BY server_id`: Memastikan pergeseran kursor pointer `LEAD`/`LAG` langsung terisolasi dan direset saat berganti server.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
Pada mesin query berbasis cost-based optimizer (seperti PostgreSQL, MySQL 8+, atau Oracle):
1. **Materialization & Sorting**: RDBMS memeriksa indeks. Jika ada *composite index* pada `(server_id, recorded_at)`, data dialirkan langsung. Jika tidak, engine mengeksekusi operasi `Sort` secara penuh pada memori kerja (`work_mem` di Postgres atau `sort_buffer_size` di MySQL).
2. **WindowAgg Node**: Mesin mengeksekusi operator `WindowAgg`. Berbeda dengan agregat berbingkai variabel (`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`), `LEAD` dan `LAG` mengoptimalkan pergerakan *tuple slot cursor*:
   - Untuk `LAG(offset)`: Mesin menyimpan cincin buffer siklis (*circular ring buffer*) berukuran `offset` elemen di memori.
   - Untuk `LEAD(offset)`: Mesin membaca baris *ahead-of-time* dari operator anak (*child node*) ke dalam *read-ahead buffer* sebanyak `offset` baris sebelum mengembalikan *current row* ke klien.

```
       Arsitektur Buffer Streaming Engine (WindowAgg)
  Pipeline: Data Stream ---> [ Read-Ahead Window Buffer ] ---> Evaluasi LEAD
                                  |
                                  v
                             [ Current Row ]
                                  |
                                  v
                             [ Ring Buffer ]           ---> Evaluasi LAG
```

#### Alokasi Memori / Resource
- Kompleksitas Waktu: $\mathcal{O}(N \log N)$ untuk tahap penyortiran awal data. Operasi pembacaan window itu sendiri adalah $\mathcal{O}(N)$, karena tiap *pointer* hanya bergerak maju (*forward cursor*).
- Kompleksitas Ruang: $\mathcal{O}(K)$, di mana $K$ adalah nilai parameter `offset`. Ruang memori sangat efisien karena engine tidak perlu memuat seluruh partisi ke dalam struktur data pohon, melainkan hanya membutuhkan sliding buffer kecil sebesar nilai offset. Namun, jika partisi tidak muat dalam memori kerja, eksekusi akan tumpah (*spill*) ke temporary disk/tempdb (*external merge sort*).

#### Trade-offs
- **LEAD/LAG vs Self-Join**: Menggunakan `LEFT JOIN` pada tabel yang sama membutuhkan overhead evaluasi predikat bersarang $\mathcal{O}(N \times M)$ atau indeks nested-loop, memakan memori join buffer yang jauh lebih besar. `LEAD`/`LAG` secara komparatif menghemat konsumsi I/O hingga 70-90% pada dataset masif.
- **Batasan Skala Frame**: `LEAD`/`LAG` secara konseptual mengekstraksi titik diskrit, bukan rentang akumulatif. Anda tidak dapat mendefinisikan *frame specification* seperti `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` di dalam deklarasi fungsi `LEAD`/`LAG`; sintaks SQL engine akan melempar *syntax error*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Index Covered Ordering**: Selalu dukung klausa `PARTITION BY col_a ORDER BY col_b` dengan *composite index* `(col_a, col_b)`. Ini memungkinkan engine menghilangkan tahapan `Sort` yang mahal dan beralih langsung ke mode streaming pipelined.
- **Manfaatkan Parameter Ketiga (Fallback Value)**: Selalu tentukan nilai default eksplisit (misal: `0`, `-1`, atau nilai kolom itu sendiri) untuk menghindari inkonsistensi kalkulasi akibat propagasi `NULL` (di mana operasi aritmatika `X - NULL` selalu menghasilkan `NULL`).
- **Gunakan Klausa `WINDOW` Terpusat**: Jika menggunakan kombinasi `LAG` dan `LEAD` lebih dari satu kali, standarisasi dengan klausa eksplisit `WINDOW w AS (...)` untuk menjamin penggunaan struktur *execution plan* tunggal.

#### Don'ts
- **Jangan Mengabaikan `ORDER BY`**: Menjalankan `LEAD` atau `LAG` tanpa klausa `ORDER BY` di dalam deklarasi `OVER()` adalah *anti-pattern* fatal. Data dalam basis data relasional pada dasarnya acak; tanpa urutan deterministik, hasil navigasi tetangga akan menjadi non-deterministik dan fluktuatif antar-query run.
- **Hindari Offset Berukuran Dinamis per Baris**: Parameter `offset` harus berupa konstanta skalar deterministik pada level kompilasi query plan. Jangan mencoba menyuntikkan subquery variabel dinamis ke dalam parameter `offset`.

#### Edge Cases
- **Partisi Berisi 1 Baris**: Ketika suatu partisi hanya memiliki satu baris data, baik `LAG` maupun `LEAD` akan langsung menghasilkan nilai *default fallback* (atau `NULL`). Sistem downstream harus siap menangani rasio degradasi komputasi berbasis *division by zero* jika selisih bernilai `0` atau `NULL`.
- **Nilai Asli Berupa `NULL`**: Jika data historis kolom target itu sendiri mengandung `NULL`, fungsi `LAG(val, 1, 0)` tidak dapat membedakan apakah nilai `NULL` berasal dari ketiadaan baris (batas partisi terlampaui) atau memang data pada baris sebelumnya bernilai `NULL`. Jika pembedaan ini krusial, gunakan predikat `LAG(col) IS NULL AND LAG(1) OVER (...) IS NOT NULL`.

### 5. Tantangan Eksplorasi Mandiri

1. **Deteksi *Session Timeout* Dinamis**:
   Diberikan tabel audit log yang menyimpan log klik pengguna (`user_id`, `event_time`). Tuliskan sebuah query yang mengelompokkan aktivitas ke dalam `session_id` baru setiap kali jeda antara interaksi saat ini dengan interaksi sebelumnya (`LAG`) melebihi batas waktu 30 menit. *(Petunjuk: Gabungkan `LAG` dengan fungsi kondisional `CASE` dan akumulasi `SUM() OVER ()`)*.

2. **Benchmarking Execution Plan**:
   Ambil tabel transaksi logistik dengan skala minimal 100.000 baris. Jalankan dua pendekatan untuk menghitung selisih metrik antar baris berurutan:
   - Pendekatan A: `LAG() OVER (PARTITION BY ... ORDER BY ...)`
   - Pendekatan B: `LEFT JOIN` pada dirinya sendiri menggunakan subquery baris terdekat.
   Analisis perbedaan metrik `Total Cost`, penggunaan `work_mem`, serta keberadaan node `WindowAgg` vs `Nested Loop/Hash Join` menggunakan perintah `EXPLAIN ANALYZE`.
