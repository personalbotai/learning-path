## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam SQL, `CASE WHEN` bukanlah sebuah *statement* kontrol alur (seperti `if-else` pada bahasa prosedural), melainkan sebuah **ekspresi skalar (scalar expression)**. Artinya, `CASE` dievaluasi untuk mengembalikan tepat satu nilai tunggal per baris pada saat *runtime*. 

Fitur ini diimplementasikan berdasarkan standar ANSI SQL dan berfungsi untuk memindahkan logika transformasi data dari *Application Layer* ke *Database Layer*. Hal ini sangat krusial untuk:
1. **Mengurangi Network I/O**: Memfilter dan mentransformasi data di dalam database jauh lebih efisien daripada menarik raw data ke memori aplikasi.
2. **Conditional Aggregation**: Memungkinkan pembuatan *pivot table* atau agregasi multi-dimensi dalam satu kali *table scan* (pemindaian tabel).

Terdapat dua format arsitektural dari `CASE`:
- **Simple CASE**: Membandingkan satu ekspresi dengan sekumpulan nilai unik (mirip `switch-case`). Hanya mendukung operasi *equality* (`=`).
- **Searched CASE**: Mengevaluasi sekumpulan ekspresi boolean (mirip `if-else if`). Mendukung operator kompleks (`>`, `<`, `LIKE`, `IS NULL`, `IN`).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan **Searched CASE** untuk berbagai skenario di industri.

```sql
-- Skenario: Database E-Commerce (Tabel: orders)

-- 1. Transformasi Data Sederhana (Data Categorization)
SELECT 
    order_id,
    customer_id,
    total_amount,
    CASE 
        WHEN total_amount >= 1000000 THEN 'VIP'
        WHEN total_amount >= 500000 THEN 'Regular'
        ELSE 'Basic' 
    END AS customer_tier
FROM orders;

-- 2. Conditional Aggregation (Pivoting Data) - SANGAT PENTING DI INDUSTRI
-- Menghitung jumlah pesanan berdasarkan status untuk setiap pelanggan dalam 1 query
SELECT 
    customer_id,
    COUNT(order_id) AS total_orders,
    SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS completed_count,
    SUM(CASE WHEN status = 'PENDING' THEN 1 ELSE 0 END) AS pending_count,
    SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END) AS cancelled_count
FROM orders
GROUP BY customer_id;

-- 3. Custom Sorting (ORDER BY)
-- Mengurutkan agar status 'PENDING' selalu muncul di atas, 
-- diikuti 'COMPLETED', lalu sisanya diurutkan berdasarkan tanggal.
SELECT order_id, status, created_at
FROM orders
ORDER BY 
    CASE status
        WHEN 'PENDING' THEN 1
        WHEN 'COMPLETED' THEN 2
        ELSE 3
    END ASC,
    created_at DESC;

-- 4. Conditional Update (Menghindari Multiple UPDATE Statements)
UPDATE inventory
SET stock = CASE 
    WHEN category = 'Electronics' THEN stock + 10
    WHEN category = 'Clothing' THEN stock + 50
    ELSE stock -- Penting: Jika tidak ada ELSE, nilai akan menjadi NULL
END
WHERE warehouse_id = 1;
```

**Penjelasan Implementasi:**
- Pada contoh ke-2 (*Conditional Aggregation*), kita mengubah baris data menjadi kolom (*pivot*). *Query Optimizer* hanya perlu melakukan satu kali *Full Table Scan* atau *Index Scan*, alih-alih kita harus melakukan tiga *query* terpisah dengan klausa `WHERE` yang berbeda.
- Pada contoh ke-4, `CASE` digunakan dalam `UPDATE` untuk menerapkan logika bisnis yang berbeda dalam satu transaksi atomik, mencegah *lock contention* yang lama pada tabel.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime (Short-Circuit Evaluation)**: 
  *Execution Engine* SQL mengevaluasi klausa `WHEN` secara sekuensial dari atas ke bawah. Begitu sebuah kondisi bernilai `TRUE`, *engine* akan langsung mengembalikan hasil tersebut dan **berhenti mengevaluasi** klausa `WHEN` di bawahnya (*short-circuiting*). Oleh karena itu, kondisi yang paling sering terjadi (*most probable*) atau paling ringan komputasinya harus diletakkan di urutan teratas untuk menghemat siklus CPU.
- **Alokasi Memori / Resource**: 
  Ekspresi `CASE` dievaluasi di memori selama fase *Projection* (jika di `SELECT`) atau fase *Sort* (jika di `ORDER BY`). Jika `CASE` memuat *subquery* (misal: `WHEN (SELECT count(*) FROM...) > 0`), ini akan memicu *Nested Loop* di belakang layar yang dapat menyebabkan lonjakan penggunaan memori dan CPU secara eksponensial per baris data.
- **Trade-offs (SARGability)**: 
  Menggunakan `CASE WHEN` di dalam klausa `WHERE` atau `JOIN ON` sering kali merusak **SARGability** (*Search Argument Able*). Artinya, *Query Optimizer* tidak dapat menggunakan B-Tree Index pada kolom tersebut dan terpaksa melakukan *Full Table Scan*.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Selalu gunakan klausa `ELSE`**. Jika `ELSE` dihilangkan dan tidak ada kondisi `WHEN` yang terpenuhi, SQL secara implisit akan mengembalikan `NULL`. Ini sering menjadi sumber *bug* tersembunyi.
  - Gunakan `CASE` untuk *Conditional Aggregation* guna menggantikan *multiple subqueries* atau *UNION ALL* saat membuat laporan analitik.
- **Don'ts**:
  - **Jangan gunakan `CASE` di klausa `WHERE` jika bisa dihindari**. 
    *Buruk:* `WHERE CASE WHEN status = 'A' THEN 1 ELSE 0 END = 1` (Index tidak terpakai).
    *Baik:* `WHERE status = 'A'` (Index terpakai).
  - Hindari *Nested CASE* (CASE di dalam CASE) yang terlalu dalam. Ini merusak *readability* dan menyulitkan *Query Optimizer* membuat *execution plan* yang optimal.
- **Edge Cases**:
  - **Penanganan NULL**: Ingat bahwa `NULL = NULL` bernilai *Unknown* (bukan True). Jangan pernah menggunakan *Simple CASE* untuk mengecek NULL.
    *Salah:* `CASE col WHEN NULL THEN...`
    *Benar:* `CASE WHEN col IS NULL THEN...`

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan**: Buatlah tabel dengan 1 juta baris yang memiliki indeks. Tulis dua *query* untuk memfilter data: satu menggunakan `CASE WHEN` di dalam `WHERE`, dan satu lagi menggunakan operator boolean standar (`AND/OR`). Gunakan `EXPLAIN ANALYZE` dan bandingkan *cost* serta penggunaan indeksnya.
2. **Dynamic Pivot**: Cobalah buat *query* agregasi kondisional (`SUM(CASE WHEN...)`) untuk menghitung total penjualan per bulan (Januari - Desember) sebagai kolom-kolom terpisah dari sebuah tabel transaksi yang hanya memiliki kolom `transaction_date` dan `amount`.
3. **Data Cleansing**: Gunakan `CASE WHEN` di dalam statement `UPDATE` untuk menormalisasi kolom nomor telepon (misalnya: mengubah awalan '08' menjadi '+628', membiarkan yang sudah '+62', dan menandai yang tidak valid dengan string 'INVALID'). Lakukan dalam satu *query* tunggal.
