## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara fundamental, **SQL View** adalah relasi virtual (*virtual table*) yang tidak menyimpan baris data fisik di media penyimpanan (berbeda dengan *Materialized View*). Sebuah View hanyalah kueri SQL terkompilasi yang tersimpan di dalam katalog sistem (*data dictionary* atau *system catalog* seperti `pg_views` pada PostgreSQL atau `information_schema.views`).

```
+-------------------------------------------------------------+
|                      Client Application                     |
+-------------------------------------------------------------+
                              |
                     SELECT * FROM v_orders
                              |
                              v
+-------------------------------------------------------------+
|                     Query Parser & Rewriter                 |
|  1. Identifikasi token 'v_orders' sebagai Relasi Virtual    |
|  2. Ambil definisi AST dari System Catalog                  |
|  3. View Inlining / Query Tree Expansion                    |
+-------------------------------------------------------------+
                              |
         AST Tergabung: SELECT ... FROM orders JOIN ...
                              |
                              v
+-------------------------------------------------------------+
|                   Cost-Based Optimizer (CBO)                |
|  - Predicate Pushdown (Filter sedini mungkin)               |
|  - Projection Pruning                                       |
|  - Join Elimination / Flattening                            |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                      Execution Engine                       |
|           Membaca data fisik dari Base Tables               |
+-------------------------------------------------------------+
```

Alasan utama arsitektur View diterapkan pada sistem basis data modern mencakup tiga pilar:
1. **Abstraksi dan Enkapsulasi Logika**: Mengisolasi skema normalisasi yang kompleks (misalnya relasi *many-to-many* dengan 5 *table joins*) dari lapisan aplikasi, menyajikan antarmuka tabular yang denormalized dan siap konsumsi.
2. **Keamanan & Kontrol Akses Berbutir Halus (*Fine-Grained Security*)**: Mengontrol akses data di tingkat kolom (memproyeksikan hanya kolom non-sensitif) dan baris (*Row-Level Filtering*, membatasi data berdasarkan `tenant_id` atau status aktif) tanpa memberikan *grant* langsung ke tabel dasar (*base table*).
3. **Penyelarasan Backward Compatibility**: Mempertahankan fungsionalitas aplikasi warisan (*legacy*) saat skema fisik tabel di-*refactor* (misal pemecahan satu tabel menjadi dua partisi vertikal).

Terdapat tiga klasifikasi utama View dalam RDBMS enterprise:
- **Standard View (Virtual)**: Diekspansi saat runtime oleh *Query Rewriter*. Nol konsumsi *disk* selain metadata.
- **Updatable View**: View yang mendukung operasi DML (`INSERT`, `UPDATE`, `DELETE`). Memerlukan pemetaan deterministik 1:1 ke baris tabel dasar (tidak boleh ada agregasi, `DISTINCT`, `GROUP BY`, atau `UNION`).
- **Materialized View**: Mengompilasi dan menyimpan (*persist*) hasil eksekusi kueri ke dalam *disk* fisik sebagai tabel terpisah. Membutuhkan mekanisme *refresh* eksplisit, cocok untuk kueri analitik (OLAP) yang berat.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menggunakan dialek PostgreSQL modern untuk skenario platform *Fintech/E-Commerce*.

```sql
-- 1. Setup Base Tables
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    tax_identifier VARCHAR(50) NOT NULL, -- Data sensitif
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT REFERENCES customers(customer_id),
    total_amount NUMERIC(15, 2) NOT NULL,
    order_status VARCHAR(20) NOT NULL,
    ordered_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 2. Standard View: Abstraksi & Data Masking (Menyembunyikan tax_identifier)
CREATE OR REPLACE VIEW v_active_customer_orders AS
SELECT 
    c.customer_id,
    c.full_name,
    c.email,
    o.order_id,
    o.total_amount,
    o.order_status,
    o.ordered_at
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE c.is_active = TRUE;

-- 3. Updatable View dengan WITH CHECK OPTION
-- Mencegah modifikasi data yang melanggar batasan WHERE clause dari view tersebut
CREATE OR REPLACE VIEW v_pending_orders AS
SELECT 
    order_id,
    customer_id,
    total_amount,
    order_status
FROM orders
WHERE order_status = 'PENDING'
WITH LOCAL CHECK OPTION;

-- 4. Materialized View: Agregasi Analitik untuk Reporting
CREATE MATERIALIZED VIEW mv_customer_spending_summary AS
SELECT 
    c.customer_id,
    c.full_name,
    COUNT(o.order_id) AS total_orders,
    COALESCE(SUM(o.total_amount), 0) AS lifetime_value,
    MAX(o.ordered_at) AS last_order_date
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.full_name
WITH DATA;

-- Materialized View membutuhkan indeks fisik untuk pembacaan optimal & Concurrent Refresh
CREATE UNIQUE INDEX idx_mv_cust_summary_id ON mv_customer_spending_summary(customer_id);

-- 5. Contoh Refresh Non-Blocking (Tanpa Exclusive Table Lock)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_customer_spending_summary;
```

#### Penjelasan Komponen Kunci:
- **`WITH LOCAL CHECK OPTION`**: Memaksa validasi integritas saat ada DML melalui View. Jika aplikasi menjalankan:
  ```sql
  UPDATE v_pending_orders SET order_status = 'CANCELLED' WHERE order_id = 1;
  ```
  Operasi akan ditolak oleh *runtime database engine* dengan *error violation*, karena status baru bertentangan dengan batasan kueri View (`order_status = 'PENDING'`).
- **`REFRESH MATERIALIZED VIEW CONCURRENTLY`**: Menggunakan teknik *differential update*. PostgreSQL membuat snapshot sementara, menghitung selisih (*diff*), dan menerapkan modifikasi baris via operasi `INSERT/UPDATE/DELETE` di bawah tingkat *lock* `SHARE UPDATE EXCLUSIVE`, sehingga operasi baca (`SELECT`) dari klien lain tidak terblokir.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Query Rewriting & Macro Expansion)
Ketika kueri `SELECT * FROM v_active_customer_orders WHERE total_amount > 1000000;` diterima:
1. **Parse Phase**: Parser membangun *Abstract Syntax Tree* (AST) dari kueri yang masuk.
2. **Rewrite Phase**: RDBMS memeriksa *system catalogs*. Menemukan bahwa target relasi adalah view, mesin mengambil teks definisi kueri view dan menginjeksinya (*View Inlining*) ke dalam AST pemanggil.
3. **Optimasi (Predicate Pushdown)**: Optimizer mengevaluasi predikat `WHERE total_amount > 1000000` dan langsung meneruskannya ke tingkat pemindaian indeks pada tabel `orders`, bukan mengeksekusi View secara terisolasi lalu memfilter hasilnya.

#### Alokasi Memori / Resource
- **Standard View**: Tidak memiliki alokasi memori khusus di luar *shared buffer* standar untuk metadata katalog. Saat dieksekusi, ia meminjam memori eksekusi kueri utama (`work_mem` pada PostgreSQL untuk sorting/hash joins).
- **Materialized View**: Mengalokasikan ruang disk nyata (Heap Storage, Data Pages, WAL entries). Ketika dimuat ke memori, ia menempati *buffer pool* persis seperti tabel biasa. 

#### Trade-offs
| Parameter | Standard View | Materialized View |
| :--- | :--- | :--- |
| **Konsistensi Data** | Real-time (ACID compliant langsung ke tabel dasar) | *Eventual/Stale* (bergantung frekuensi refresh) |
| **Beban Komputasi** | Beban tinggi pada saat kueri dijalankan (*CPU-bound*) | Beban dialihkan ke proses *refresh* (*I/O & Disk bound*) |
| **Biaya Penyimpanan** | 0 Byte untuk data (hanya teks SQL di katalog) | Duplikasi data tabel dasar di *disk storage* |
| **Dukungan Indeks** | Tidak dapat diindeks secara langsung | Mendukung B-Tree, Hash, BRIN, GIN secara native |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Definisikan Kolom Proyeksi Secara Eksplisit**: Hindari `CREATE VIEW v_foo AS SELECT * FROM base_table`. Jika ada perubahan urutan kolom atau penambahan kolom baru di tabel dasar, View tidak akan merefleksikannya secara otomatis atau berisiko *broken pointer metadata*.
- **Pahami Dependency Cascades**: Gunakan `ALTER VIEW` atau reka ulang dependensi secara terstruktur. Hati-hati saat menggunakan `DROP TABLE ... CASCADE` karena View yang bergantung akan terhapus otomatis secara senyap.
- **Buat Indeks Unik pada Materialized View**: Persyaratan absolut untuk mengizinkan `REFRESH CONCURRENTLY` adalah adanya minimal satu `UNIQUE INDEX` tanpa klausul `WHERE` (bukan *partial index*).

#### Don'ts
- **Hindari "View on View on View" (View Chaining)**: Menumpuk View di atas View lain secara bertingkat menciptakan *nested encapsulation hell*. Hal ini sering membingungkan *Cost-Based Optimizer* (CBO), mematikan peluang *join elimination*, dan memicu pembacaan berulang pada tabel yang sama (*redundant table scans*).
- **Jangan Mengabaikan Query Cost pada Updatable View**: Memperbarui tabel melalui view kompleks dengan *INSTEAD OF triggers* dapat menyembunyikan latensi operasi tulis dari pengembang aplikasi.

#### Edge Cases
- **Schema Drift**: Jika tipe data kolom di tabel dasar diubah menggunakan `ALTER TABLE ... ALTER COLUMN TYPE`, sejumlah database (seperti PostgreSQL) akan menolak operasi tersebut jika terdapat View yang bergantung pada kolom tersebut (`feature dependent objects exist`). Developer harus menghapus View terlebih dahulu, mengubah kolom, lalu membuat ulang View.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Optimizer pada Predicate Pushdown**:
   Buat sebuah View yang menggabungkan dua tabel berukuran besar (>500.000 baris) dengan agregasi `GROUP BY`. Jalankan `EXPLAIN (ANALYZE, BUFFERS)` pada kueri pemanggilan View menggunakan filter `WHERE` pada salah satu atribut non-agregat. Amati pada simpul eksekusi mana predikat tersebut dievaluasi: sebelum atau sesudah operasi *HashAggregate*?
2. **Implementasi Inverted DML via Triggers**:
   Buat sebuah View non-updatable (mengandung klausa `JOIN` antara tabel `orders` dan `order_items`). Implementasikan trigger `INSTEAD OF INSERT` pada View tersebut agar aplikasi dapat mengeksekusi instruksi `INSERT` tunggal ke dalam View, lalu pisahkan mutasi datanya secara transaksional ke kedua tabel dasar secara atomik.
