### 1. Konsep & Arsitektur Mendalam

Normalisasi database relasional adalah proses matematis dan struktural untuk mengorganisasi skema relasional guna meminimalkan **redundansi data** dan mengeliminasi **anomali anomali modifikasi** (insert, update, dan delete). Konsep ini berakar pada aljabar relasional yang dicetuskan oleh Edgar F. Codd.

Dalam sistem pemrosesan transaksi online (OLTP), integritas data adalah prioritas utama. Ketika data disimpan secara redundan di banyak baris atau tabel:
1. **Insert Anomaly**: Entitas anak tidak dapat dicatat tanpa keberadaan entitas induk (atau sebaliknya).
2. **Update Anomaly**: Perubahan satu atribut memerlukan pembaruan di ribuan baris. Jika satu baris gagal atau terlewat, database berada dalam status inkonsisten (*split-brain data state*).
3. **Delete Anomaly**: Menghapus data suatu transaksi secara tidak sengaja menghapus entitas domain penting yang melekat padanya.

Normalisasi bekerja melalui dekomposisi relasi (*lossless decomposition*) berdasarkan **Ketergantungan Fungsional** (*Functional Dependency / FD*):

```
+-------------------------------------------------------------------------------+
|                            Tingkatan Normalisasi                              |
+-------------------------------------------------------------------------------+
|  UNF   : Data mentah dengan multi-value dan repeating groups                  |
|   │                                                                           |
|   ▼                                                                           |
|  1NF   : Nilai skalar atomik, baris unik (Primary Key eksplisit)              |
|   │                                                                           |
|   ▼                                                                           |
|  2NF   : 1NF + Tidak ada Partial Dependency (semua atribut non-kunci          |
|   │      bergantung penuh pada SELURUH Primary Key komposit)                  |
|   ▼                                                                           |
|  3NF   : 2NF + Tidak ada Transitive Dependency (atribut non-kunci             |
|   │      TIDAK bergantung pada atribut non-kunci lainnya)                     |
|   ▼                                                                           |
|  BCNF  : Untuk setiap FD X -> Y, X HARUS berupa Superkey                      |
+-------------------------------------------------------------------------------+
```

* **First Normal Form (1NF)**: Setiap kolom harus memuat satu nilai atomik (bukan array, JSON tanpa indeks, atau daftar terpisah koma). Tidak boleh ada baris duplikat, sehingga harus ada Primary Key yang terdefinisi.
* **Second Normal Form (2NF)**: Memenuhi 1NF dan tidak memiliki *partial dependency*. Hal ini relevan ketika Primary Key berupa kunci komposit ($PK = \{A, B\}$). Atribut non-kunci tidak boleh hanya bergantung pada $A$ saja atau $B$ saja.
* **Third Normal Form (3NF)**: Memenuhi 2NF dan tidak memiliki *transitive dependency* ($A \to B$ dan $B \to C$, sehingga secara tidak langsung $A \to C$). Jika $C$ bukan atribut penentu langsung dari kunci kandidat, $C$ harus dipisahkan ke tabel relasi tersendiri.
* **Boyce-Codd Normal Form (BCNF)**: Varian ketat dari 3NF. BCNF menyatakan bahwa untuk setiap dependensi fungsional nontrivial $X \to Y$, penentunya ($X$) harus merupakan *superkey*. BCNF menyelesaikan anomali ketika tabel memiliki beberapa *overlapping composite candidate keys*.

### 2. Implementasi & Contoh Kasus Nyata

Studi Kasus: Sistem Manajemen Pesanan (*E-Commerce Order Management*).

#### Tahap 0: Bentuk Tidak Normal (UNF / Denormalized Bloat)
Perhatikan tabel tunggal yang bermasalah berikut:

```sql
-- ANTI-PATTERN: Tabel mentah yang memicu anomali insert, update, dan delete
CREATE TABLE orders_unnormalized (
    order_id INT,
    customer_id INT,
    customer_name VARCHAR(100),
    customer_city VARCHAR(50),
    product_ids VARCHAR(255),       -- Melanggar 1NF: multi-value (CSV)
    product_names VARCHAR(255),     -- Melanggar 1NF: multi-value (CSV)
    product_prices VARCHAR(255),    -- Melanggar 1NF: multi-value (CSV)
    order_date DATE,
    total_amount NUMERIC(12, 2)
);
```

#### Tahap 1, 2, dan 3: Transformasi Menuju 3NF / BCNF

Lakukan dekomposisi lossless menjadi skema relasional yang terisolasi dengan constraint integritas referensial yang ketat:

```sql
-- 1. Entitas Independen: Customers (Memenuhi 3NF/BCNF)
-- Menghilangkan dependensi transitif Customer Name/City dari Order
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    city VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 2. Entitas Independen: Products (Memenuhi 3NF/BCNF)
-- Menghilangkan duplikasi deskripsi dan harga produk dari pesanan
CREATE TABLE products (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku VARCHAR(64) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    current_price NUMERIC(12, 2) NOT NULL CHECK (current_price >= 0),
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);

-- 3. Entitas Transaksi: Orders (Memenuhi 3NF/BCNF)
-- Hanya menyimpan relasi langsung ke customer dan state transaksi
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_date TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    CONSTRAINT fk_orders_customer 
        FOREIGN KEY (customer_id) 
        REFERENCES customers(customer_id) 
        ON DELETE RESTRICT
);

-- 4. Entitas Relasi Item: Order Items (Memenuhi 1NF, 2NF, dan 3NF)
-- Menghilangkan Partial Dependency: harga item saat transaksi dicatat di sini
CREATE TABLE order_items (
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    -- Historical Price Capture (PENTING: Bukan transitive dependency melainkan state capture)
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    CONSTRAINT pk_order_items 
        PRIMARY KEY (order_id, product_id),
    CONSTRAINT fk_items_order 
        FOREIGN KEY (order_id) 
        REFERENCES orders(order_id) 
        ON DELETE CASCADE,
    CONSTRAINT fk_items_product 
        FOREIGN KEY (product_id) 
        REFERENCES products(product_id) 
        ON DELETE RESTRICT
);

-- Indexing foreign keys untuk mengoptimalkan operasi JOIN
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
```

#### Query Transaksional Konsisten (Read via JOIN)
```sql
SELECT 
    o.order_id,
    o.order_date,
    c.full_name AS customer_name,
    c.city,
    p.name AS product_name,
    oi.quantity,
    oi.unit_price,
    (oi.quantity * oi.unit_price) AS subtotal
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.order_id = 1001;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Query Planner & JOIN Operations
Ketika skema dinormalisasi, pembacaan data membutuhkan operasi `JOIN`. RDBMS Relational Engine (seperti PostgreSQL atau MySQL InnoDB) menggunakan Cost-Based Optimizer (CBO) untuk menentukan strategi eksekusi:
- **Nested Loop Join**: Digunakan saat satu sisi relasi memiliki baris yang sangat sedikit (misal: mencari 1 order via Primary Key) dan sisi lainnya memiliki indeks.
- **Hash Join**: Digunakan saat menggabungkan dataset besar yang tidak berurut. Engine membangun *in-memory hash table* dari tabel yang lebih kecil di `work_mem`, lalu memindai tabel kedua untuk pencocokan.
- **Merge Join**: Digunakan ketika kedua tabel sudah terurut berdasarkan join keys (misalnya via B-Tree index). Operasi ini membaca kedua tabel secara paralel dengan kompleksitas $O(N + M)$.

#### Alokasi Memori / Resource: Buffer Pool & Page Density
RDBMS membaca data dalam satuan blok disk yang disebut **Data Pages** (umumnya 8KB di PostgreSQL, 16KB di MySQL InnoDB).
- **Skema Denormalisasi (Tabel Lebar)**: Setiap baris berukuran besar karena memuat string teks berulang (nama kota, nama produk). Hasilnya: *Row density* rendah (hanya sedikit baris per page). Akibatnya, I/O disk tinggi dan *Buffer Pool Cache Hit Ratio* menurun drastis karena memori terbuang untuk menyimpan duplikasi data teks.
- **Skema Normalisasi (Tabel Ramping)**: Tabel transaksi hanya menyimpan tipe data numerik integer/bigint sebagai Foreign Key (4-8 byte). Ratusan baris muat dalam satu page 8KB. Efisiensi cache L1/L2 CPU dan Buffer Pool meningkat pesat untuk scan tabel.

#### Trade-offs: Throughput Tulis vs. Latensi Baca
```
+------------------------------------+---------------------------------------+
|          NORMALISASI (3NF)         |            DENORMALISASI              |
+------------------------------------+---------------------------------------+
| (+) Write performance tinggi       | (-) Write performance rendah          |
|     (row locks sempit, I/O kecil)  |     (lock lebar, write amplification) |
| (+) Konsistensi ACID terjamin      | (-) Risiko inkonsistensi data tinggi  |
| (-) Membutuhkan resource CPU/RAM   | (+) Read latency sangat rendah        |
|     untuk eksekusi JOIN            |     (Single table scan, no JOIN)      |
+------------------------------------+---------------------------------------+
```

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Rancang Normalisasi Maksimal pada Awal Perancangan (Design Time)**: Mulai skema konseptual selalu dari 3NF/BCNF. Denormalisasi hanya boleh dilakukan setelah pengujian performa sistem berbasis data metrik riil (*metrics-driven optimization*).
2. **Definisikan Foreign Key Explicitly**: Jangan berasumsi aplikasi layer akan menangani integritas data. Gunakan constraint `ON DELETE RESTRICT` atau `ON DELETE CASCADE` langsung di database engine.
3. **Capture State at Transaction Time**: Pahami perbedaan antara redundansi yang salah vs *snapshot historical data*. Menyimpan `unit_price` di `order_items` **bukan** redundansi dari `products.current_price`, melainkan mencatat status moneter pada titik waktu transaksi terjadi (*point-in-time invariant*).

#### Don'ts
1. **Anti-pattern CSV/Array dalam Kolom Relasional**: Menyimpan string seperti `"1,5,89"` di kolom teks untuk referensi ID. Ini menghancurkan indeks B-Tree, mencegah pembuatan Foreign Key constraint, dan memaksa full-table scan dengan fungsi `LIKE` atau regex.
2. **Premature Denormalization**: Menggabungkan tabel hanya karena takut "JOIN itu lambat". RDBMS modern mampu mengeksekusi jutaan JOIN terindeks per detik tanpa hambatan memori.
3. **Mengabaikan Surrogate vs Natural Key Relationship**: Terlalu bergantung pada natural key (seperti nama unik atau kode pos) yang dapat berubah di masa depan, alih-alih menggunakan surrogate identity key yang immutable.

#### Edge Cases
* **Polymorphic Associations**: Situasi di mana tabel `comments` harus merujuk ke tabel `posts` ATAU tabel `videos`. Menggunakan satu kolom `parent_id` dan `parent_type` melanggar integritas relasional karena Foreign Key engine tidak dapat memvalidasi dua target tabel sekaligus.  
  *Solusi BCNF*: Buat tabel perantara (`post_comments`, `video_comments`) atau gunakan tabel supertype/subtype pattern.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Dekomposisi BCNF**:
   Diberikan sebuah skema penugasan konsultan: `Consultant_Project (consultant_id, project_id, role, hourly_rate)`. Asumsikan aturan bisnis berikut:
   - Satu konsultan dalam satu proyek hanya memiliki satu role: `(consultant_id, project_id) -> role`.
   - Standar rate ditentukan mutlak oleh role: `role -> hourly_rate`.
   
   Identifikasi pelanggaran normalisasi pada skema ini (apakah 2NF, 3NF, atau BCNF), tunjukkan anomali yang muncul, dan tuliskan DDL SQL dekomposisinya yang lossless!

2. **Benchmarking IO Cost (EXPLAIN ANALYZE)**:
   Buat dua skema pada database lokal Anda:
   - Skema A: Tabel denormalisasi 10 kolom dengan data redundan sebesar 500.000 baris.
   - Skema B: Tabel 3NF terdekomposisi (3 tabel) dengan jumlah data setara.
   
   Jalankan kueri pembaruan (UPDATE) pada satu entitas data yang tersebar di 50.000 baris. Periksa metrik `Execution Time` dan `Buffers: shared hit/read` menggunakan `EXPLAIN (ANALYZE, BUFFERS)`. Amati perbedaan Write Amplification antara kedua model tersebut.
