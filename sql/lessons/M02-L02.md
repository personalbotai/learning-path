## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Perintah `UPDATE` adalah bagian dari *Data Manipulation Language* (DML) yang bertugas memodifikasi status (*state*) dari satu atau beberapa baris data (*tuples/records*) yang sudah ada di dalam tabel. Berbeda dari sistem penyimpanan berbasis file sederhana yang menimpa *byte* secara linear, eksekusi `UPDATE` pada *Relational Database Management System* (RDBMS) modern merupakan operasi kompleks yang melibatkan konkurensi, keutuhan referensial, transaksi ACID (*Atomicity, Consistency, Isolation, Durability*), dan manipulasi memori.

Di tingkat arsitektural, mesin database (seperti PostgreSQL, MySQL InnoDB, atau Oracle) memproses `UPDATE` melalui serangkaian lapisan:
1. **Query Parser & Rewriter**: Memvalidasi sintaks dan hak akses pengguna terhadap tabel serta kolom terkait.
2. **Optimizer/Planner**: Menentukan jalur akses fisik paling efisien menuju baris yang ditargetkan (misalnya melalui *Index Scan* vs. *Sequential/Full Table Scan*).
3. **Transaction & Lock Manager**: Memasang *Row-Level Exclusive Lock* (X-Lock) pada baris target untuk mencegah *race condition* (seperti *lost updates*).
4. **Storage Engine**: Mengubah nilai kolom target dan memperbarui indeks yang relevan.

Pendekatan fisik eksekusi `UPDATE` sangat bervariasi bergantung pada implementasi *Multi-Version Concurrency Control* (MVCC) dari masing-masing storage engine:
* **Append-Only / Copy-on-Write (e.g., PostgreSQL)**: Secara fisik, `UPDATE` sebenarnya adalah kombinasi dari operasi `DELETE` (menandai *tuple* lama sebagai *dead/expired*) diikuti oleh `INSERT` (*tuple* baru dibuat dengan nilai yang dimutasi).
* **In-Place Update with Undo Log (e.g., MySQL InnoDB, Oracle)**: Nilai baru langsung dituliskan ke dalam halaman data (*data page*) pada indeks clustered jika ukurannya memadai, sedangkan versi data lama disalin ke dalam *Undo Tablespace* (Undo Log) untuk memfasilitasi pembacaan konkuren non-blocking (*consistent read*) dan *rollback*.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh skrip DDL dan skenario `UPDATE` pada domain perbankan/fintech yang membutuhkan presisi tinggi.

```sql
-- 1. Setup Skema & Data Dummy
CREATE TABLE accounts (
    account_id INT PRIMARY KEY,
    owner_name VARCHAR(100) NOT NULL,
    balance DECIMAL(15, 2) NOT NULL CHECK (balance >= 0),
    tier VARCHAR(20) DEFAULT 'STANDARD',
    version INT DEFAULT 1, -- Untuk Optimistic Locking
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO accounts (account_id, owner_name, balance, tier) VALUES
(1, 'Alice', 15000000.00, 'STANDARD'),
(2, 'Bob', 500000.00, 'STANDARD'),
(3, 'Charlie', 75000000.00, 'VIP');

-- ==========================================================
-- KASUS A: Pembaruan Terkondisi Tunggal dengan Validasi State
-- ==========================================================
-- Menerapkan transfer balance dengan menjaga data integrity:
UPDATE accounts
SET 
    balance = balance - 2000000.00,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE account_id = 1 
  AND balance >= 2000000.00; -- Guard clause untuk mencegah race condition saldo negatif

-- ==========================================================
-- KASUS B: Pembaruan Massal dengan CASE Expression (Batch Update)
-- ==========================================================
-- Menaikkan tier pelanggan secara dinamis berdasarkan ambang saldo:
UPDATE accounts
SET 
    tier = CASE 
        WHEN balance >= 50000000.00 THEN 'VIP'
        WHEN balance >= 10000000.00 THEN 'PREMIUM'
        ELSE 'STANDARD'
    END,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE tier <> 'VIP'; -- Memfilter tuple yang sudah berada di tier target

-- ==========================================================
-- KASUS C: UPDATE Menggunakan Klausa RETURNING (PostgreSQL Native)
-- ==========================================================
-- Mengambil nilai setelah modifikasi secara atomic tanpa query SELECT terpisah:
UPDATE accounts
SET 
    balance = balance + 100000.00,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE account_id = 2
RETURNING account_id, balance AS new_balance, version;
```

**Analisis Baris Kunci:**
* **`balance = balance - 2000000.00`**: Operasi komputasi berbasis nilai saat ini di disk, menghindari dependensi nilai dari sisi memori aplikasi (*stale data*).
* **`WHERE account_id = 1 AND balance >= 2000000.00`**: Menjamin atomisitas tingkat baris. Jika saldo tidak cukup, engine menghasilkan *zero affected rows* tanpa memicu *error* sintaks, sehingga *application logic* dapat menanganinya dengan elegan.
* **`version = version + 1`**: Pola *Optimistic Concurrency Control* (OCC) untuk mendeteksi apakah proses lain telah memodifikasi data yang sama selama durasi transaksi berlangsung.
* **`RETURNING ...`**: Mencegah *network round-trip* tambahan. Sangat berguna untuk sinkronisasi state ke dalam aplikasi backend secara instan.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Penetapan Kunci (*Row Locking*)**: Engine mencari baris yang memenuhi klausa `WHERE`. Saat baris ditemukan, mesin mengunci baris tersebut menggunakan *Exclusive Lock* (X-Lock). Transaksi lain yang ingin membaca baris ini tidak akan diblokir (berkat MVCC), namun transaksi lain yang ingin memodifikasi atau mengunci (`FOR UPDATE`) baris ini harus menunggu hingga transaksi ini selesai (`COMMIT` atau `ROLLBACK`).
2. **Buffer Pool Modification**: Engine tidak menulis langsung ke disk fisik. Halaman memori (*page*) yang menyimpan baris tersebut dimuat ke dalam *Buffer Pool* (RAM). Perubahan diaplikasikan pada *page* ini di memori, sehingga status *page* berubah menjadi *Dirty Page*.
3. **Pencatatan WAL / Redo Log**: Sebelum perubahan di buffer pool diizinkan untuk di-flush ke disk secara permanen, detail perubahan fisik/logis wajib ditulis terlebih dahulu ke sistem *Write-Ahead Logging* (WAL pada PostgreSQL, *Redo Log* pada MySQL InnoDB) secara sequensial. Ini memenuhi prinsip *Durability*.

#### Alokasi Memori / Resource
* **PostgreSQL (Dead Tuple & HOT Optimization)**: Setiap kali `UPDATE` terjadi, *tuple* lama ditandai dengan `xmax` (Transaction ID transaksi saat ini). Salinan *tuple* baru dibuat di halaman yang sama jika muat, atau di halaman baru. Jika kolom yang di-update diindeks, pointer indeks baru harus dibuat, yang memicu fenomena *Write Amplification*. PostgreSQL mengatasi hal ini sebagian melalui optimasi **HOT (Heap-Only Tuple)**: jika tidak ada kolom indeks yang dimutasi dan ada sisa ruang di halaman yang sama, pembuatan pointer indeks baru di-bypass.
* **MySQL/InnoDB (Undo Tablespace)**: InnoDB memodifikasi record pada *Clustered Index* secara langsung. Versi sebelum modifikasi ditulis ke dalam struktur *Undo Log* pada *Undo Tablespace*. Jika memori habis saat memproses data volume besar, engine akan mengeksekusi *disk spills* yang menurunkan throughput I/O secara signifikan.

#### Trade-offs
* **Frekuensi Pembaruan vs Overhead Indeks**: Mengupdate kolom yang merupakan bagian dari *B-Tree Index* memaksa engine membongkar dan menata ulang *node-node* B-Tree. Semakin banyak indeks pada tabel, semakin tinggi *write latency* dari sebuah pernyataan `UPDATE`.
* **Lock Granularity**: Jika kueri `UPDATE` tidak menggunakan kolom terindeks pada klausa `WHERE`, database engine terpaksa beralih ke *Full Table Scan*. Pada beberapa engine (seperti SQL Server), jika jumlah baris yang dikunci melampaui batas ambang tertentu, database akan melakukan *Lock Escalation*—menaikkan status kunci dari level baris (*row lock*) menjadi kunci tabel penuh (*table-level lock*), menghentikan seluruh operasi tulis konkuren lainnya.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan Explicit Transactions (`BEGIN ... COMMIT`)**: Selalu bungkus eksekusi `UPDATE` kritis di dalam transaksi terkelola, terutama saat memperbarui beberapa tabel secara relasional.
* **Verifikasi Menggunakan `SELECT` Terlebih Dahulu**: Sebelum mengeksekusi `UPDATE ... WHERE <kondisi>` di level production, jalankan kueri `SELECT ... WHERE <kondisi>` atau `EXPLAIN` untuk memvalidasi jumlah baris target dan jalur eksekusi indeks yang dipilih.
* **Batch Large Updates**: Hindari memodifikasi jutaan baris dalam satu perintah SQL. Lakukan secara bertahap (*chunking/batching*) menggunakan limitasi Primary Key (misal: 5.000 baris per iterasi) untuk menghindari saturasi WAL/Redo Log dan *locking table contention*.

#### Don'ts
* **Lupa Menyertakan Klausa `WHERE`**: Merupakan bencana operasional paling fatal di industri. `UPDATE accounts SET balance = 0;` akan menimpa seluruh baris data dalam tabel tanpa peringatan.
* **Update Menggunakan Data Eksternal Tanpa Sanitasi / Casting**: Menyematkan nilai numerik atau string mentah dari controller API langsung ke dalam sintaks SQL tanpa *Prepared Statements* (parameterized query) membuka celah fatal terhadap serangan *SQL Injection*.
* **Mengabaikan Dampak Cascade Update**: Menggunakan foreign key dengan aturan `ON UPDATE CASCADE` pada tabel bervolume tinggi dapat memicu gelombang modifikasi yang tidak terduga ke tabel-tabel anak (*child tables*), memicu *table-wide locking cascade*.

#### Edge Cases
* **Deadlock Konkuren**: Terjadi ketika Transaksi A mengupdate Baris 1 lalu mencoba mengupdate Baris 2, sementara Transaksi B mengupdate Baris 2 lalu mencoba mengupdate Baris 1. **Solusi:** Selalu susun urutan eksekusi update baris secara konsisten di kode aplikasi (misalnya: urutkan pembaruan berdasarkan `account_id ASC`).
* **Lost Updates**: Dua transaksi membaca nilai saldo yang sama ($100), kemudian keduanya secara bersamaan mengurangi saldo sebesar $20 lalu menulis kembali hasilnya ($80), padahal saldo akhir seharusnya $60. **Solusi:** Gunakan pembaruan atomic `balance = balance - 20` atau gunakan mekanisme penguncian *Pessimistic Locking* (`SELECT ... FOR UPDATE`).

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Deadlock Secara Sadar**:
   Buka dua sesi terminal terpisah (menggunakan terminal CLI Postgres atau MySQL). Pada Sesi 1, mulai transaksi dan update baris A. Pada Sesi 2, mulai transaksi dan update baris B. Tanpa melakukan `COMMIT`, coba update baris B di Sesi 1, dan baris A di Sesi 2. Analisis bagaimana engine mendeteksi deadlock dan mekanisme apa yang dilakukan engine terhadap salah satu transaksi yang menjadi korban (*victim transaction*).
2. **Investigasi Write Amplification (PostgreSQL Case)**:
   Buat sebuah tabel dengan 100.000 baris. Buat indeks pada kolom `updated_val`. Jalankan update berulang sebanyak 10 kali pada kolom tersebut. Amati pertumbuhan ukuran tabel dan indeks menggunakan kueri `pg_stat_user_tables` serta fungsi `pg_relation_size()`. Ulangi pengujian pada tabel yang kolom target pembaruannya **tidak** memiliki indeks, lalu bandingkan rasio *Dead Tuples* dan efisiensi *HOT update*-nya.
