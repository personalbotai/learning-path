## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa basis data relasional (RDBMS), manipulasi penghapusan data tidak hanya sekadar "membuat baris menghilang". Dua perintah fundamental—`DELETE` dan `TRUNCATE`—memiliki klasifikasi arsitektural yang berbeda secara mendasar:

*   **`DELETE` (Data Manipulation Language - DML):** Dirancang untuk operasi berbasis baris (*row-by-row operations*) yang granular. `DELETE` mengeksekusi *predicate evaluation* (klausa `WHERE`), memeriksa batasan integritas referensial (Foreign Keys), memicu *row-level triggers*, dan menulis perubahan setiap baris ke dalam log transaksi (*Write-Ahead Logging* / WAL atau Redo/Undo Log).
*   **`TRUNCATE` (Data Definition Language - DDL):** Dirancang untuk deallokasi penyimpanan massal pada tingkat tabel atau partisi. `TRUNCATE` memperlakukan tabel sebagai satu kesatuan struktur data: alih-alih memindai dan menghapus baris demi baris, ia membebaskan halaman data (*data pages/extents*) yang dialokasikan ke tabel tersebut pada lapisan *storage engine* dan memperbarui katalog metadata sistem.

```
+-------------------------------------------------------------------------+
|                               DELETE (DML)                              |
| Engine: [Scan Row] -> [Eval WHERE] -> [Check FK/Trigger] -> [Write Log] |
| Storage: Menandai tuple sebagai "dead" / Update Undo -> Baris dihapus   |
+-------------------------------------------------------------------------+
                                    vs
+-------------------------------------------------------------------------+
|                              TRUNCATE (DDL)                             |
| Engine: [Acquire Exclusive Lock] -> [Bypass Rows/Triggers]              |
| Storage: Deallokasi B-Tree Extents / Swap Relfilenode -> Reset Metadata |
+-------------------------------------------------------------------------+
```

Perbedaan arsitektur ini memengaruhi latensi, penggunaan I/O disk, pembengkakan log transaksi (*log bloat*), konkurensi (locking), dan kemampuan pemulihan (*rollback*).

### 2. Implementasi & Contoh Kasus Nyata

Contoh skenario di bawah ini menggunakan sintaks standar (kompatibel dengan PostgreSQL dan MySQL/InnoDB) untuk menunjukkan perbedaan perilaku operasional kedua perintah.

```sql
-- 1. SETUP TABEL PENGUJIAN
CREATE TABLE staging_events (
    id BIGSERIAL PRIMARY KEY,
    event_payload TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- Mengisi data tiruan (mock data)
INSERT INTO staging_events (event_payload)
SELECT 'event_data_' || seq
FROM generate_series(1, 100000) AS seq;

-- =========================================================================
-- KASUS A: Penggunaan DELETE (Granular, Transaksional, Row-oriented)
-- =========================================================================
BEGIN;

-- Menghapus subset baris secara selektif
DELETE FROM staging_events 
WHERE created_at < CURRENT_TIMESTAMP - INTERVAL '1 day';

-- Memeriksa sequence setelah DELETE
-- Nilai auto-increment/sequence TIDAK di-reset
SELECT last_value FROM staging_events_id_seq; 

COMMIT;

-- =========================================================================
-- KASUS B: Penggunaan TRUNCATE (Reset Penyimpanan Cepat)
-- =========================================================================
-- Skenario: Pipeline ETL membersihkan staging table sebelum batch baru
BEGIN;

-- Mengosongkan tabel seketika dan me-reset sequence generator
TRUNCATE TABLE staging_events RESTART IDENTITY;

-- Verifikasi: Tabel kosong dan sequence kembali ke nilai awal (1)
SELECT COUNT(*) FROM staging_events; -- Output: 0

COMMIT;
```

#### Variasi & Skrip Mitigasi Produksi: Batched DELETE
Ketika harus menghapus jutaan baris menggunakan `DELETE` tanpa mengunci seluruh tabel atau membuat log transaksi meledak:

```sql
-- Pola Chunked Deletion (MySQL/PostgreSQL procedural pattern)
-- Menghapus data tua secara inkremental untuk mencegah lock contention
DO $$
DECLARE
    deleted_rows INT;
BEGIN
    LOOP
        -- Hapus dalam batch kecil (misal: 5.000 baris)
        DELETE FROM staging_events
        WHERE id IN (
            SELECT id FROM staging_events
            WHERE created_at < NOW() - INTERVAL '30 days'
            LIMIT 5000
        );
        
        GET DIAGNOSTICS deleted_rows = ROW_COUNT;
        
        -- Berhenti jika tidak ada lagi baris yang perlu dihapus
        EXIT WHEN deleted_rows = 0;
        
        -- Berikan jeda waktu sejenak agar background worker (Vacuum/Purge) 
        -- dan thread replikasi dapat mengejar
        PERFORM pg_sleep(0.05);
    END LOOP;
END $$;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
*   **`DELETE`**: *Query Planner* membentuk *execution plan* (misalnya `Seq Scan` atau `Index Scan`). Setiap baris diambil ke dalam memori (*buffer pool*), diperiksa kondisinya, kemudian ditandai untuk dihapus. Jika ada *trigger* `BEFORE/AFTER DELETE`, konteks eksekusi beralih memproses fungsi *trigger* untuk setiap baris, yang menghasilkan *overhead context switching* yang masif pada volume data besar.
*   **`TRUNCATE`**: Melewati *Execution Engine* pemrosesan baris secara total. Pada PostgreSQL, mesin mengeksekusi pemotongan dengan membuat relasi berkas baru di disk (*relfilenode swap*) dan menjadwalkan penghapusan berkas lama saat transaksi *commit*. Pada MySQL (InnoDB), halaman dialokasikan ulang, dan struktur indeks B+Tree diinisialisasi ulang ke kondisi kosong.

#### Alokasi Memori, Resource & Disk
*   **Log Transaksi (WAL / Redo-Undo Log):**
    *   `DELETE`: Mencatat setiap perubahan baris secara individual ke dalam WAL/Redo Log. Menghapus 10 juta baris menghasilkan gigabytes catatan log, membebani I/O disk dan meningkatkan *replication lag* pada *replica nodes*.
    *   `TRUNCATE`: Menggunakan *minimal logging*. Hanya mencatat perubahan status alokasi halaman atau operasi DDL ke log transaksi. Ukuran log yang dihasilkan sangat kecil (skala kilobyte).
*   **Reklamasi Ruang Disk (Space Reclamation):**
    *   `DELETE` **tidak mengembalikan ruang disk ke sistem operasi secara instan**. Pada PostgreSQL (MVCC), baris hanya ditandai sebagai *dead tuple* dan memerlukan proses `VACUUM` untuk menandai ruang tersebut agar dapat digunakan kembali oleh data baru. Pada InnoDB, halaman yang kosong tetap berada dalam *tablespace file* (`.ibd`), kecuali dijalankan `OPTIMIZE TABLE`.
    *   `TRUNCATE` membebaskan ruang disk (atau menginisialisasi ulang ukuran berkas) seketika dan menurunkan *High-Water Mark* (HWM) pada *storage engine*.

#### Mekanisme Penguncian (Locking)
*   **`DELETE`**: Mengambil *Intention Exclusive (IX)* lock pada tingkat tabel, dan *Exclusive (X)* lock pada tingkat baris (*row-level*). Transaksi lain masih dapat membaca (*concurrent read*) atau memodifikasi baris lain di tabel yang sama.
*   **`TRUNCATE`**: Membutuhkan kunci paling restriktif: `ACCESS EXCLUSIVE` (PostgreSQL) atau *exclusive table lock* (MySQL). Perintah ini memblokir **seluruh operasi baca dan tulis** konkuren hingga transaksi selesai.

#### Trade-offs Matrix
| Karakteristik | `DELETE` | `TRUNCATE` |
| :--- | :--- | :--- |
| **Kategori** | DML | DDL |
| **Filter (`WHERE`)** | Ya | Tidak (semua baris) |
| **Kecepatan** | Lambat (berbanding lurus dengan jumlah baris: $O(N)$) | Instan ($O(1)$) |
| **Beban WAL/Redo**| Sangat Tinggi | Sangat Rendah |
| **Reset Identity** | Tidak | Ya (opsional di PostgreSQL, otomatis di MySQL) |
| **Triggers** | Menjalankan *Row-level Triggers* | Mengabaikan *Row-level Triggers* |
| **Lock Level** | Row-level Lock (X) | Table-level Lock (Access Exclusive) |

### 4. Best Practices & Common Pitfalls

#### Do's
*   **Gunakan `TRUNCATE` untuk Reset Data:** Terapkan pada tabel penampung sementara (*staging tables*, *ETL buffers*, *session caches*) di mana performa adalah prioritas utama dan data lama tidak lagi relevan.
*   **Lakukan Batching pada `DELETE` Skala Besar:** Jika harus menghapus jutaan baris dari tabel produksi yang aktif, pecah transaksi menjadi beberapa iterasi kecil (lihat bagian 2). Ini mencegah *lock escalation*, mengontrol ukuran log transaksi, dan meminimalkan *replication lag*.
*   **Pertimbangkan Partition Pruning:** Untuk data berbasis deret waktu (*time-series*), gunakan *table partitioning*. Menghapus data lama dengan perintah `ALTER TABLE ... DROP PARTITION` jauh lebih cepat dan lebih aman daripada `DELETE` maupun `TRUNCATE`.

#### Don'ts
*   **JANGAN gunakan `DELETE FROM table;` tanpa klausa `WHERE`:** Mengosongkan tabel jutaan baris menggunakan `DELETE` tanpa filter adalah anti-pattern ekstrem yang menyebabkan lonjakan I/O, transaksi tertahan lama (*long-running transaction*), dan kehabisan ruang disk akibat WAL/Redo log.
*   **JANGAN berasumsi `TRUNCATE` selalu dapat di-rollback di semua RDBMS:** Di PostgreSQL dan MS SQL Server, `TRUNCATE` bersifat transaksional dan dapat di-*rollback* di dalam blok `BEGIN ... ROLLBACK`. Namun, di **MySQL**, `TRUNCATE` menyebabkan *implicit commit*, sehingga operasi tersebut **tidak dapat dibatalkan** meskipun berada di dalam blok `START TRANSACTION`.

#### Edge Cases
*   **Foreign Key Constraints:** `TRUNCATE` akan langsung gagal (*fail fast*) jika tabel tersebut direferensikan oleh *Foreign Key constraint* dari tabel lain, meskipun tabel anak tersebut kosong (kecuali di Postgres menggunakan klausa `TRUNCATE ... CASCADE`). Sebaliknya, `DELETE` akan memvalidasi dependensi per baris dan mengeksekusi aturan `ON DELETE CASCADE` atau `ON DELETE SET NULL`.
*   **Indeks Auto-Increment/Identity Desynchronization:** Jika baris terakhir dihapus menggunakan `DELETE`, angka *auto-increment* berikutnya tidak akan mundur. Penyerang atau anomali sistem yang memicu insert-delete berulang dapat menghabiskan jangkauan tipe data ID (`INT` 4-byte habis di ~2.1 miliar). Gunakan `BIGINT` atau reset menggunakan `TRUNCATE` jika daur ulang ID memang diinginkan.

1.  **Analisis Log Transaksi & Ukuran Berkas:**
    Buat tabel dengan 500.000 baris. Periksa ukuran tabel fisik di disk dan ukuran berkas log transaksi (WAL/Redo). Lakukan `DELETE` pada separuh data, lalu periksa apakah ukuran tabel di disk menyusut. Bandingkan hasilnya setelah Anda mengeksekusi `TRUNCATE` pada tabel pengujian kedua. Mengapa ukuran disk fisik berbeda drastis pasca-`DELETE`?
2.  **Eksperimen Deadlock & Konkurensi:**
    Buka dua sesi terminal terpisah pada database Anda:
    *   *Sesi 1:* Mulai transaksi dengan `BEGIN`, lalu jalankan query baca lambat (`SELECT ... FROM large_table`).
    *   *Sesi 2:* Coba jalankan `TRUNCATE TABLE large_table`.
    *   *Sesi 3:* Buka sesi ketiga dan jalankan `SELECT * FROM large_table WHERE id = 1`.
    Amati bagaimana *lock queue* terbentuk: mengapa *Sesi 3* ikut terblokir meskipun *Sesi 2* belum selesai dieksekusi?
3.  **Transaksional DDL (Cross-Engine Validation):**
    Tulis skrip pembuktian untuk memverifikasi apakah engine target Anda (misal MySQL vs PostgreSQL) mendukung pembatalan (`ROLLBACK`) perintah `TRUNCATE` di dalam blok transaksi aktif. Catat perbedaan perilaku katalog metadata di kedua sistem tersebut.
