### 1. Konsep & Arsitektur Mendalam

Dalam aljabar relasional dan *database internals*, fungsi agregasi statistik seperti `AVG()`, `MIN()`, dan `MAX()` digolongkan sebagai operator reduksi skalar (*scalar reduction operators*). Operator ini memetakan sebuah multiset (kumpulan baris nilai) menjadi sebuah nilai skalar tunggal. 

Secara teoretis, fungsi-fungsi ini diimplementasikan menggunakan pendekatan **Fold/Reduce State Machine**:

$$\text{State}_{n} = f(\text{State}_{n-1}, \text{Input}_n)$$

Namun, karakteristik komputasi dan optimasi arsitektural antara `AVG` dan `MIN`/`MAX` sangat berbeda:

```
          +-------------------------------------------------------------+
          |             QUERY EXECUTION ENGINE (AGGREGATION)            |
          +-------------------------------------------------------------+
                                         |
         +-------------------------------+-------------------------------+
         |                                                               |
  [ Algebraic Aggregate ]                                     [ Distributive Aggregate ]
         AVG(x)                                                      MIN(x) / MAX(x)
  State: {sum, count}                                         State: {current_extremum}
  Requires 2 accumulators.                                    Requires 1 accumulator.
  Cannot leverage B-Tree directly                             B-Tree Index Scan:
  (requires full set evaluation).                             Direct seek to Leftmost/Rightmost leaf (O(1)).
```

#### A. `AVG()`: Algebraic Aggregate
`AVG()` bukanlah fungsi distributif murni, melainkan **algebraic aggregate**. Nilai rata-rata tidak bisa digabungkan langsung dari sub-rata-rata tanpa mengetahui bobotnya:
$$\text{AVG}(S_1 \cup S_2) \neq \text{AVG}(S_1) + \text{AVG}(S_2)$$

Query engine memecah evaluasi `AVG(x)` menjadi dua fungsi primitif distributif:
$$\text{AVG}(x) = \frac{\sum x}{\text{COUNT}(x)}$$

Di balik layar, *execution engine* mengalokasikan *internal state transition structure*:
```c
// Representasi konseptual akumulator AVG di engine C/C++
typedef struct AvgState {
    int128_t sum;     // Akumulator nilai (tipe diperluas untuk mencegah overflow)
    uint64_t count;   // Jumlah baris valid (non-null)
} AvgState;
```

#### B. `MIN()` & `MAX()`: Distributive Aggregates
`MIN()` dan `MAX()` adalah fungsi **distributif** dan **idempoten**. 
$$\min(S_1 \cup S_2) = \min(\min(S_1), \min(S_2))$$

Sifat ini memungkinkan RDBMS melakukan partisi data secara paralel (MapReduce internal) secara trivial tanpa melacak metadata sekunder. Lebih penting lagi, fungsi ini memungkinkan optimasi struktural ekstrem menggunakan indeks B-Tree: pencarian nilai minimum ekuivalen dengan mencari *leaf node* paling kiri (*leftmost leaf*), sedangkan nilai maksimum berada pada *leaf node* paling kanan (*rightmost leaf*).

#### C. ANSI SQL Null Semantics
Sesuai standar ISO/IEC 9075:
- Semua fungsi agregasi statistik **mengabaikan nilai `NULL`** sebelum kalkulasi dimulai.
- Jika sebuah dataset hanya berisi `NULL` atau tidak memiliki baris (empty set), hasil dari `AVG()`, `MIN()`, dan `MAX()` adalah `NULL` (berbeda dengan `COUNT(*)` yang menghasilkan `0`).

### 2. Implementasi & Contoh Kasus Nyata

Skenario berikut menggunakan schema transaksi e-commerce skala besar untuk menghitung performa penjualan harian, latensi pengiriman, serta variasi penggunaan *Window Functions* dan ekspresi kondisional modern.

```sql
-- 1. Setup Skema Database & Data Dummy
CREATE TABLE order_shipments (
    shipment_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    carrier VARCHAR(50) NOT NULL,
    delivery_fee NUMERIC(10, 2),
    transit_duration_hours NUMERIC(6, 2), -- Mengizinkan NULL untuk paket yang hilang/retur
    shipped_at TIMESTAMPTZ NOT NULL
);

INSERT INTO order_shipments (order_id, carrier, delivery_fee, transit_duration_hours, shipped_at) 
VALUES 
    (101, 'JNE', 15000.00, 24.50, '2023-10-01 08:00:00+00'),
    (102, 'JNE', 12000.00, 48.00, '2023-10-01 09:30:00+00'),
    (103, 'Sicepat', 15000.00, NULL,  '2023-10-01 10:15:00+00'), -- In-transit / Exception
    (104, 'Sicepat', 22000.00, 18.25, '2023-10-01 11:00:00+00'),
    (105, 'JNE', 18000.00, 72.10, '2023-10-02 08:00:00+00'),
    (106, 'Sicepat', 25000.00, 12.00, '2023-10-02 08:30:00+00');

-- 2. Analisis Statistik Dasar per Carrier
-- Menggunakan FILTER clause (ANSI SQL standard yang didukung PostgreSQL/modern engines)
SELECT 
    carrier,
    COUNT(*) AS total_shipments,
    
    -- MIN/MAX mengabaikan NULL
    MIN(transit_duration_hours) AS fastest_delivery_hrs,
    MAX(transit_duration_hours) AS slowest_delivery_hrs,
    
    -- AVG hanya membagi nilai akumulasi dengan baris non-NULL
    ROUND(AVG(transit_duration_hours), 2) AS pure_avg_duration,
    
    -- Perbandingan: Mengubah NULL menjadi 0 merusak metrik statistik rata-rata
    ROUND(AVG(COALESCE(transit_duration_hours, 0)), 2) AS biased_avg_duration,
    
    -- Statistik bersyarat via FILTER (lebih efisien daripada agregasi CASE-WHEN)
    ROUND(AVG(delivery_fee) FILTER (WHERE transit_duration_hours <= 24.0), 2) AS avg_fee_for_fast_shipping
FROM order_shipments
GROUP BY carrier;

-- 3. Advanced Pattern: Window Aggregations untuk Outlier Detection
-- Menghitung gap antara performa order saat ini terhadap batas ekstrem global
SELECT 
    order_id,
    carrier,
    transit_duration_hours,
    MIN(transit_duration_hours) OVER(PARTITION BY carrier) AS carrier_min_duration,
    MAX(transit_duration_hours) OVER(PARTITION BY carrier) AS carrier_max_duration,
    ROUND(AVG(transit_duration_hours) OVER(PARTITION BY carrier), 2) AS carrier_avg_duration,
    -- Normalisasi Min-Max (Skor 0.0 - 1.0)
    ROUND(
        (transit_duration_hours - MIN(transit_duration_hours) OVER(PARTITION BY carrier)) /
        NULLIF(
            MAX(transit_duration_hours) OVER(PARTITION BY carrier) - 
            MIN(transit_duration_hours) OVER(PARTITION BY carrier), 
            0
        ), 
        4
    ) AS min_max_normalized_score
FROM order_shipments
WHERE transit_duration_hours IS NOT NULL;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Runtime: Aggregate Operators
Query planner memilih satu dari dua strategi eksekusi agregasi fisik:

1. **`HashAggregate`**:
   - Engine menginisialisasi Hash Table di memori (*work_mem* di Postgres atau *Sort/Hash Area* di Oracle/MySQL).
   - *Key*: Nilai kolom `GROUP BY`.
   - *Value*: Tuple pointer ke struktur akumulator (cth: `min_val`, `max_val`, `sum`, `count`).
   - Kompleksitas waktu: $O(N)$ scanning baris, $O(1)$ amortized look-up hash.

2. **`StreamAggregate` (Sort-Aggregate)**:
   - Digunakan jika input sudah terurut (melalui `INDEX` scan atau operator `SORT` eksplisit).
   - Engine membaca stream secara sekuensial. Ketika nilai kolom group berubah, state di-emit ke output dan state di-reset.
   - Mengkonsumsi memori sangat kecil ($O(1)$ *memory space*) karena tidak perlu menampung seluruh state grup di memori.

```
+-------------------------------------------------------------------------+
|                  MIN/MAX B-TREE INDEX OPTIMIZATION                      |
+-------------------------------------------------------------------------+
| Query: SELECT MIN(val), MAX(val) FROM metrics;                          |
| Execution Plan: Result                                                  |
|   InitPlan 1 (returns $0)                                               |
|     ->  Limit (cost=0.42..0.45 rows=1)                                  |
|           ->  Index Only Scan using idx_metrics_val on metrics (Forward)|
|   InitPlan 2 (returns $1)                                               |
|     ->  Limit (cost=0.42..0.45 rows=1)                                  |
|           ->  Index Only Scan Backward using idx_metrics_val (Backward) |
+-------------------------------------------------------------------------+
```
Jika ada indeks B-Tree pada kolom yang dicari nilai `MIN()` atau `MAX()`-nya, query engine tidak perlu memindai seluruh tabel (*Full Table Scan*). Engine melakukan **Index Fast Full Scan / Index Seek** langsung melompat ke node daun paling ujung kiri (untuk `MIN`) atau ujung kanan (untuk `MAX`). Operasi ini selesai dalam kompleksitas $O(\log B)$, di mana $B$ adalah kedalaman pohon B-Tree (umumnya 3–4 I/O operasi disk).

#### B. Alokasi Memori & Trade-offs Data Type
- **Accumulator Overflow**: Pada fungsi `AVG(integer_column)`, jika dieksekusi naif, akumulator $\sum x$ rentan mengalami *arithmetic overflow*. Engine seperti PostgreSQL secara otomatis mempromosikan accumulator `SUM(int4)` ke tipe data `int8` (BIGINT) atau `NUMERIC`, lalu membaginya di akhir fase reduksi.
- **Floating-point Inaccuracy**: Tipe data `FLOAT` atau `DOUBLE PRECISION` menggunakan representasi IEEE 754. Penjumlahan berulang dalam `AVG()` dapat mengalami akumulasi *rounding error* (*cancellation error*). Untuk kalkulasi finansial, selalu gunakan `NUMERIC` / `DECIMAL`.

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Buat Indeks Komposit untuk MIN/MAX pada Kondisi Filtering:**
   Jika menjalankan query `SELECT MAX(created_at) FROM logs WHERE tenant_id = 42;`, buatlah indeks komposit:
   ```sql
   CREATE INDEX idx_logs_tenant_created ON logs (tenant_id, created_at DESC);
   ```
   Ini memungkinkan query engine melakukan *Index Seek* langsung ke baris target tanpa filtering manual.
2. **Ketahui Tipe Data Hasil:**
   Memanggil `AVG()` pada kolom integer sering kali menghasilkan tipe data `NUMERIC` atau `FLOAT` tergantung RDBMS. Pastikan parsing di layer aplikasi (Go, Java, Rust) siap menangani serialisasi tipe floating/string decimal.

#### Don'ts:
1. **Jangan Sembarangan Menggunakan `COALESCE(val, 0)` di Dalam `AVG()`:**
   Secara statistik, $NULL$ merepresentasikan *missing information*, bukan nilai $0$. 
   - Set $\{10, 20, NULL\} \rightarrow \text{AVG} = 15$ (Sample size = 2).
   - Set $\{10, 20, 0\} \rightarrow \text{AVG} = 10$ (Sample size = 3).
   Kecuali ada kebutuhan domain bisnis spesifik, memasukkan `0` membiaskan mean secara artifisial.
2. **Jangan Menjalankan `MIN()` dan `MAX()` Terpisah dalam Query Berbeda:**
   Hindari menjalankan dua query sekuensial jika membutuhkan keduanya. Jalankan:
   ```sql
   -- Baik: Satu kali pemindaian atau dual index probe dalam 1 round-trip
   SELECT MIN(price), MAX(price) FROM products;
   ```

#### Edge Cases:
- **Tabel Kosong (Empty Set Aggregation):**
  ```sql
  SELECT AVG(score), MIN(score), MAX(score) FROM students WHERE 1 = 0;
  -- Hasil: 1 baris berisi NULL, NULL, NULL.
  ```
  Tetapi jika ada `GROUP BY`:
  ```sql
  SELECT class_id, AVG(score) FROM students WHERE 1 = 0 GROUP BY class_id;
  -- Hasil: 0 baris (Empty result set).
  ```
- **String Collation pada MIN/MAX:**
  Eksekusi `MIN(string_col)` sangat bergantung pada konfigurasi *Collation* (`LC_COLLATE`) database. Nilai `'a'` bisa dianggap lebih kecil atau lebih besar dari `'A'` tergantung apakah collation yang digunakan bersifat case-sensitive atau berbasis ICU library.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Query Plan (B-Tree Seek vs Table Scan):**
   Buat sebuah tabel dengan 1.000.000 baris acak. Jalankan perintah:
   ```sql
   EXPLAIN ANALYZE SELECT MIN(val), MAX(val) FROM test_table;
   ```
   Bandingkan eksekusi dan *execution cost* sebelum dan sesudah Anda membuat index pada kolom `val`. Analisis bagaimana representasi node plan berubah (misal: perpindahan dari `Seq Scan` + `Aggregate` ke `Result` + `InitPlan`).

2. **Deteksi Anomali Truncated Moving Average:**
   Dengan memanfaatkan tabel `order_shipments` di atas, tulis query untuk menghitung **Moving Average (MA)** durasi transit 3 transaksi terakhir berdasarkan tanggal transaksi:
   ```sql
   AVG(transit_duration_hours) OVER (
       PARTITION BY carrier 
       ORDER BY shipped_at 
       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
   )
   ```
   Apa yang terjadi jika salah satu dari 3 baris tersebut memiliki nilai `NULL`? Bagaimana cara *window frame* ini memperlakukan baris tersebut dalam pembagian penyebutnya (*denominator*)? Buktikan hipotesis Anda menggunakan data riil.
