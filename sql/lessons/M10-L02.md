## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem data modern, penyimpanan dan pemrosesan data dibagi berdasarkan pola beban kerja (workload): **OLTP** (Online Transaction Processing) dan **OLAP** (Online Analytical Processing). Evolusi arsitektur data melahirkan tiga pilar utama: Cloud SQL, Data Warehouse, dan Data Lakehouse.

1.  **Cloud SQL (Managed RDBMS untuk OLTP)**
    *   **Konsep:** Layanan database relasional terkelola (seperti Amazon RDS, Google Cloud SQL, Azure SQL) yang menjalankan engine tradisional seperti PostgreSQL atau MySQL.
    *   **Arsitektur:** Berbasis *Row-oriented storage* (penyimpanan berbasis baris) menggunakan struktur data B-Tree. Dioptimalkan untuk operasi baca/tulis latensi rendah, transaksi ACID tingkat tinggi, dan konkurensi masif pada data berukuran kecil per transaksi.
    *   **Keterbatasan:** Tidak efisien untuk agregasi data berskala Petabyte karena harus membaca seluruh baris (row) ke dalam memori meskipun hanya satu kolom yang dibutuhkan.

2.  **Data Warehouse (OLAP Murni)**
    *   **Konsep:** Sistem terpusat untuk analitik dan Business Intelligence (BI) berskala besar (contoh: Google BigQuery, Snowflake, Amazon Redshift).
    *   **Arsitektur:** Menggunakan *Columnar storage* (penyimpanan berbasis kolom) dan arsitektur **MPP (Massively Parallel Processing)**. Data didistribusikan ke ratusan node komputasi. Pemisahan komputasi dan penyimpanan (*Compute/Storage Decoupling*) memungkinkan penskalaan independen.
    *   **Keterbatasan:** Biaya penyimpanan relatif mahal, kaku terhadap data tidak terstruktur (unstructured data), dan rentan terhadap *vendor lock-in*.

3.  **Data Lakehouse (Konvergensi Data Lake & Warehouse)**
    *   **Konsep:** Menggabungkan fleksibilitas dan biaya rendah dari Data Lake (penyimpanan objek seperti S3/GCS) dengan manajemen data dan transaksi ACID dari Data Warehouse (contoh: Databricks, Apache Iceberg, Delta Lake, Apache Hudi).
    *   **Arsitektur:** Data mentah disimpan dalam format file terbuka (seperti Parquet atau ORC) di *object storage*. Di atasnya, terdapat *Metadata Layer* (seperti Iceberg/Delta) yang melacak versi file, skema, dan transaksi. *Query engine* (seperti Trino, Spark, atau DuckDB) membaca metadata ini untuk mengeksekusi query SQL seolah-olah membaca tabel relasional.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah perbandingan implementasi SQL pada ketiga arsitektur tersebut untuk menangani kasus yang sama: Manajemen Data Transaksi E-Commerce.

**A. Cloud SQL (PostgreSQL) - Fokus pada Integritas & Partisi**
```sql
-- Membuat tabel transaksi dengan partisi deklaratif untuk optimasi OLTP
CREATE TABLE orders (
    order_id UUID PRIMARY KEY,
    user_id BIGINT NOT NULL,
    total_amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) PARTITION BY RANGE (created_at);

-- Membuat partisi bulanan
CREATE TABLE orders_2023_10 PARTITION OF orders
    FOR VALUES FROM ('2023-10-01') TO ('2023-11-01');

-- Index pada user_id menggunakan B-Tree untuk pencarian point-lookup yang cepat
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

**B. Data Warehouse (BigQuery/Snowflake) - Fokus pada Analitik & Kolumnar**
```sql
-- Analitik kompleks menggunakan Window Functions dan penanganan tipe data semi-structured (JSON/Array)
WITH MonthlyUserStats AS (
    SELECT 
        user_id,
        DATE_TRUNC(created_at, MONTH) AS order_month,
        SUM(total_amount) AS monthly_spend,
        -- Menghitung running total per user tanpa self-join (sangat efisien di MPP)
        SUM(SUM(total_amount)) OVER (
            PARTITION BY user_id 
            ORDER BY DATE_TRUNC(created_at, MONTH)
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS lifetime_spend
    FROM `data_warehouse.sales.orders`
    WHERE created_at >= '2023-01-01'
    GROUP BY 1, 2
)
SELECT * FROM MonthlyUserStats 
ORDER BY monthly_spend DESC 
LIMIT 100;
```

**C. Data Lakehouse (Apache Iceberg / Delta Lake) - Fokus pada ACID di Object Storage & Time Travel**
```sql
-- 1. UPSERT (Merge) data dari staging ke tabel utama di Object Storage (S3/GCS)
MERGE INTO lakehouse.sales.orders AS target
USING lakehouse.staging.daily_orders AS source
ON target.order_id = source.order_id
WHEN MATCHED AND source.status = 'CANCELLED' THEN 
    UPDATE SET status = 'CANCELLED', updated_at = CURRENT_TIMESTAMP
WHEN NOT MATCHED THEN 
    INSERT (order_id, user_id, total_amount, status, created_at)
    VALUES (source.order_id, source.user_id, source.total_amount, source.status, source.created_at);

-- 2. Time Travel Query: Melihat state data pada waktu tertentu (fitur khas Lakehouse)
SELECT count(*) 
FROM lakehouse.sales.orders TIMESTAMP AS OF '2023-10-15 10:00:00';
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime:**
  - **Cloud SQL:** Menggunakan *Volcano Iterator Model* (memproses data baris demi baris). Sangat bergantung pada *Buffer Pool* di RAM untuk menghindari disk I/O.
  - **Data Warehouse:** Menggunakan *Vectorized Execution*. Data diproses dalam *batch* kolom (misal 10.000 nilai sekaligus) yang muat dalam cache CPU (L1/L2 cache), memanfaatkan instruksi SIMD (Single Instruction, Multiple Data).
  - **Lakehouse:** *Query engine* (seperti Spark/Trino) pertama-tama membaca *Manifest Files* (metadata) untuk melakukan *Data Skipping* (mengabaikan file Parquet yang tidak relevan berdasarkan statistik min/max). Setelah itu, *worker nodes* menarik file yang tersisa dari S3/GCS secara paralel.

- **Alokasi Memori / Resource:**
  - **Cloud SQL:** Memori dialokasikan secara statis (misal `shared_buffers` di Postgres). Jika query analitik besar dijalankan, memori akan *spill to disk* (menulis ke temp files), menyebabkan penurunan performa drastis.
  - **Warehouse/Lakehouse:** Memori dikelola secara dinamis di seluruh klaster. Jika satu node kehabisan memori saat melakukan *Distributed Hash Join*, data akan di-shuffle ke node lain atau di-spill ke SSD lokal berkecepatan tinggi.

- **Trade-offs:**
  - **Cloud SQL:** Latensi sub-milidetik, tetapi tidak bisa *scale-out* untuk penulisan (hanya *scale-up* atau *read replicas*).
  - **Data Warehouse:** Performa analitik instan (out-of-the-box), tetapi biaya komputasi (per-query atau per-hour) sangat mahal.
  - **Lakehouse:** Biaya penyimpanan sangat murah (S3) dan tidak ada *vendor lock-in*, tetapi setup awal lebih kompleks dan latensi query sedikit lebih tinggi dibanding Data Warehouse murni karena overhead membaca dari *object storage*.

### 4. Best Practices & Common Pitfalls

- **Do's:**
  - **Gunakan Read Replica untuk Cloud SQL:** Jika Anda harus menjalankan query analitik ringan di RDBMS, arahkan query tersebut ke *Read Replica* agar tidak membebani *Primary Node* yang melayani transaksi user.
  - **Partisi & Clustering (Warehouse/Lakehouse):** Selalu partisi data berdasarkan kolom yang sering digunakan untuk filter (misal: `tanggal`, `region`). Ini memungkinkan *Partition Pruning* (memangkas data yang dibaca).
  - **Gunakan Format Kolumnar:** Simpan data analitik dalam format Parquet atau ORC yang mendukung kompresi tinggi (seperti Snappy atau Zstd).

- **Don'ts:**
  - **`SELECT *` di Data Warehouse:** Karena arsitektur kolumnar, `SELECT *` akan memaksa engine membaca seluruh kolom. Di BigQuery, ini berarti Anda akan ditagih biaya maksimal untuk query tersebut. Selalu sebutkan kolom secara spesifik.
  - **Menggunakan Lakehouse untuk OLTP:** Jangan gunakan Delta Lake atau Iceberg untuk aplikasi yang membutuhkan ribuan transaksi per detik (TPS). Mereka didesain untuk *batch* atau *micro-batch streaming*, bukan *single-row point lookups*.

- **Edge Cases:**
  - **The Small File Problem (Lakehouse):** Jika pipeline streaming Anda menulis file Parquet berukuran kecil (misal 10KB) setiap detik ke S3, metadata akan membengkak dan performa query akan hancur. **Solusi:** Lakukan operasi *Compaction* (seperti `OPTIMIZE` di Delta/Iceberg) secara berkala untuk menggabungkan file kecil menjadi file besar (idealnya 128MB - 1GB).

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Biaya Kolumnar:** Buat akun Google Cloud (gratis tier BigQuery). Buat tabel publik berukuran besar (misal dataset Wikipedia). Bandingkan jumlah byte yang diproses antara `SELECT * FROM table` dengan `SELECT title, views FROM table`.
2. **Implementasi Lakehouse Lokal:** Instal **DuckDB** di mesin lokal Anda. Buat skrip Python/SQL untuk membaca file CSV, lalu simpan sebagai file Parquet. Jalankan query analitik langsung ke file Parquet tersebut menggunakan DuckDB dan amati perbedaan kecepatan eksekusinya.
3. **Eksplorasi Time Travel:** Gunakan Apache Iceberg (bisa via Docker dengan Spark) untuk membuat tabel. Lakukan 3 kali operasi `UPDATE` pada satu baris data. Gunakan sintaks `FOR SYSTEM_VERSION AS OF` atau `TIMESTAMP AS OF` untuk melakukan query ke versi data sebelum di-update.
