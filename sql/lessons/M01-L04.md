### 1. Konsep & Arsitektur Mendalam

Dalam sistem manajemen basis data relasional (RDBMS), pemfilteran data menggunakan klausa `WHERE` beroperasi di atas aljabar relasional dan logika formal. Namun, tidak seperti bahasa pemrograman imperatif yang umumnya menerapkan *Two-Valued Logic* (Boolean: `TRUE` atau `FALSE`), SQL mengimplementasikan **Three-Valued Logic (3VL)**. Di dalam 3VL, sebuah predikat logika dapat bernilai:
1. `TRUE`
2. `FALSE`
3. `UNKNOWN` (hasil evaluasi ekspresi yang melibatkan `NULL`)

Klausa `WHERE` hanya meloloskan baris (tuples) yang hasil evaluasi predikat keseluruhannya bernilai mutlak `TRUE`. Baris yang bernilai `FALSE` atau `UNKNOWN` akan diabaikan.

```
       Tabel Kebenaran SQL (Three-Valued Logic)
+---------+---------+---------+---------+---------+
|    P    |    Q    | P AND Q | P OR Q  |  NOT P  |
+---------+---------+---------+---------+---------+
| TRUE    | TRUE    | TRUE    | TRUE    | FALSE   |
| TRUE    | FALSE   | FALSE   | TRUE    | FALSE   |
| TRUE    | UNKNOWN | UNKNOWN | TRUE    | FALSE   |
| FALSE   | FALSE   | FALSE   | FALSE   | TRUE    |
| FALSE   | UNKNOWN | FALSE   | UNKNOWN | TRUE    |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |
+---------+---------+---------+---------+---------+
```

#### Operator Precedence (Hierarki Presedensi)
Ketika beberapa predikat dikombinasikan tanpa tanda kurung eksplisit, SQL Engine mengevaluasi operator dengan urutan presedensi matematis:
1. **`NOT`** (Presedensi tertinggi)
2. **`AND`** (Konjungsi / *Conjunction*)
3. **`OR`**  (Disjungsi / *Disjunction*, Presedensi terendah)

Ekspresi `A OR B AND C` secara internal diuraikan oleh SQL Parser menjadi `A OR (B AND C)`. Ketidaktahuan terhadap hierarki ini menjadi salah satu sumber bug logika paling kritis dalam query analitik maupun transaksional.

#### Aljabar Boolean & Normalisasi pada Query Optimizer
Sebelum eksekusi, SQL Query Optimizer mentransformasikan predikat pada *Abstract Syntax Tree* (AST) ke dalam bentuk standar:
- **Conjunctive Normal Form (CNF)**: Sekumpulan klausa yang dihubungkan dengan `AND`, misalnya `(A OR B) AND (C OR D)`. Engine menyukai CNF karena setiap klausa yang bernilai `FALSE` dapat langsung memicu *early rejection*.
- **Disjunctive Normal Form (DNF)**: Sekumpulan klausa yang dihubungkan dengan `OR`, misalnya `(A AND B) OR (C AND D)`. DNF sering kali mempersulit penggunaan indeks B-Tree tunggal.

Hukum De Morgan juga diterapkan secara otomatis oleh optimizer untuk penyederhanaan:
- `NOT (A AND B)` $\equiv$ `(NOT A) OR (NOT B)`
- `NOT (A OR B)`  $\equiv$ `(NOT A) AND (NOT B)`

### 2. Implementasi & Contoh Kasus Nyata

Skenario berikut menggunakan PostgreSQL/MySQL modern untuk memproses filter fraud detection dan status pesanan pada sistem *e-commerce*.

```sql
-- 1. Setup Skema Database & Data Dummy
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    total_amount NUMERIC(10, 2) NOT NULL,
    status VARCHAR(20) NOT NULL, -- 'PENDING', 'PAID', 'CANCELLED', 'FLAGGED'
    is_risk_country BOOLEAN NOT NULL,
    discount_code VARCHAR(50) -- Nullable
);

INSERT INTO orders (order_id, customer_id, total_amount, status, is_risk_country, discount_code) VALUES
(101, 1, 500000.00, 'PAID', FALSE, 'PROMO10'),
(102, 2, 1200000.00, 'PENDING', TRUE, NULL),
(103, 3, 2500000.00, 'PAID', TRUE, 'WHALE20'),
(104, 4, 150000.00, 'CANCELLED', FALSE, NULL),
(105, 5, 800000.00, 'FLAGGED', FALSE, NULL),
(106, 6, 3000000.00, 'PENDING', FALSE, 'VIP');

-- 2. Query Kompleks: Identifikasi Transaksi High-Risk untuk Audit
-- Kriteria:
-- a. Nilai transaksi > 1.000.000 DAN berasal dari negara berisiko, ATAU
-- b. Status 'FLAGGED', TETAPI BUKAN yang memiliki discount_code khusus ('VIP')
SELECT 
    order_id, 
    customer_id, 
    total_amount, 
    status, 
    discount_code
FROM 
    orders
WHERE 
    (
        (total_amount > 1000000.00 AND is_risk_country = TRUE)
        OR 
        status = 'FLAGGED'
    )
    AND NOT (discount_code = 'VIP' AND discount_code IS NOT NULL);
```

#### Penjelasan Logika Predikat:
- `(total_amount > 1000000.00 AND is_risk_country = TRUE)`: Memfilter pesanan bernilai tinggi dari negara berisiko (Order `102` dan `103`).
- `OR status = 'FLAGGED'`: Menambahkan baris dengan status *FLAGGED* ke dalam set kandidat (Order `105`).
- Tanda kurung luar `(...)` membatasi cakupan `OR` sebelum dievaluasi terhadap kondisi berikutnya.
- `AND NOT (...)`: Mengeksklusikan transaksi jika kode diskonnya bernilai mutlak `'VIP'`. Baris dengan `discount_code IS NULL` tidak dieksklusikan karena `NULL = 'VIP'` bernilai `UNKNOWN`, dan `NOT (UNKNOWN)` tetaplah `UNKNOWN`, yang mana jika digabungkan dengan `AND` membutuhkan penanganan nilai *null-safe*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Short-Circuit Evaluation**: Standar SQL ANSI sebenarnya **tidak menjamin** urutan evaluasi dari kiri ke kanan (*short-circuit*) seperti pada C/C++ atau Java. Query optimizer bebas mengevaluasi predikat mana yang paling murah terlebih dahulu (*Cost-Based Optimization*). Jika predikat `B` berupa subquery yang berat dan predikat `A` berupa perbandingan integer, optimizer mengevaluasi `A` lebih dahulu. Jika `A = FALSE` dalam operator `AND`, engine mengabaikan `B`.
- **Bitmap Index Scan & Index Merge**: 
  - Pada operator `AND`, engine dapat menggunakan *Compound Index* (misal: `CREATE INDEX idx_amt_risk ON orders(total_amount, is_risk_country)`) dalam satu kali lintasan B-Tree Scan.
  - Pada operator `OR`, satu indeks majemuk tidak dapat dipakai secara optimal. Engine modern (seperti PostgreSQL/MySQL) melakukan **Bitmap Index Scan / Index Merge**: menjalankan index scan secara independen untuk tiap cabang `OR`, membuat representasi bit array di memori atas baris yang cocok, lalu menjalankan bitwise `OR` sebelum membaca blok heap data dari disk.

```
       Visualisasi Index Merge (OR Execution)
 Predicate A (total_amount > 1M) -> [1, 0, 1, 0, 0, 1] (Bitmap A)
                                           |
                                      BITWISE OR
                                           v
 Predicate B (status = 'FLAGGED') -> [0, 0, 0, 0, 1, 0] (Bitmap B)
                                           |
                                           v
 Resulting Rows to Fetch Heap    -> [1, 0, 1, 0, 1, 1]
```

#### Alokasi Memori / Resource
- Jika kondisi `OR` melibatkan kolom yang tidak terindeks bersama, optimizer terpaksa melakukan **Seq Scan (Full Table Scan)**, memicu I/O disk tinggi dan memenuhi buffer cache database dengan data yang tidak relevan.
- Kompleksitas kombinasi predikat meningkatkan ukuran memori yang dibutuhkan optimizer saat menghitung permutasi eksekusi pohon rencana query (*Execution Plan Tree*).

#### Trade-offs
| Pendekatan | Keuntungan | Kerugian |
| :--- | :--- | :--- |
| **`AND` (Conjunction)** | Menghasilkan filter yang sangat selektif; sangat optimal untuk B-Tree indexing. | Mengharuskan pemenuhan banyak batasan secara ketat. |
| **`OR` (Disjunction)** | Fleksibel untuk mencakup multi-kondisi dalam satu query. | Sering kali mematikan optimasi B-Tree standar; sering memaksa penggunaan Bitmap Scans yang memakan CPU/RAM. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Tanda Kurung Eksplisit**: Jangan pernah mengandalkan presedensi implisit saat menggabungkan `AND` dan `OR`. Tuliskan `(A AND B) OR C` atau `A AND (B OR C)` secara jelas untuk memastikan determinisme logika dan mempermudah pembacaan kode oleh tim.
- **Konversi Rantai `OR` Menjadi `IN`**: Jika menguji satu kolom terhadap banyak nilai konstan, gunakan `status IN ('PAID', 'PENDING')` daripada `status = 'PAID' OR status = 'PENDING'`. Optimizer dapat memproses predikat `IN` sebagai *Index Range Scan* secara efisien.
- **Optimasi `OR` Menggunakan `UNION ALL`**: Jika penggabungan via `OR` menghasilkan *Execution Plan* yang lambat karena membatalkan indeks, pisahkan query menjadi dua branch indeks dan gabungkan dengan `UNION ALL`:
  ```sql
  -- Lebih ramah indeks pada volume data puluhan juta baris
  SELECT * FROM orders WHERE customer_id = 100
  UNION ALL
  SELECT * FROM orders WHERE total_amount > 5000000.00 AND customer_id <> 100;
  ```

#### Don'ts
- **Menghindari Perangkap `NOT IN` dengan Nilai `NULL`**: Ini adalah jebakan paling berbahaya dalam SQL.
  ```sql
  -- JIKA discount_codes memiliki minimal 1 nilai NULL:
  -- Query ini AKAN SELALU MENGEMBALIKAN 0 BARIS (Empty Set)!
  SELECT * FROM orders 
  WHERE discount_code NOT IN ('PROMO10', NULL);
  ```
  *Alasan Arsitektural*: `x NOT IN ('A', NULL)` diekspansikan menjadi `x <> 'A' AND x <> NULL`. Karena `x <> NULL` menghasilkan `UNKNOWN`, maka ekspresi `TRUE AND UNKNOWN` bernilai `UNKNOWN`. Sesuai aturan 3VL, baris tidak pernah diloloskan.
  *Solusi*: Gunakan `NOT EXISTS` atau filter `IS NOT NULL`.

#### Edge Cases
- **Hukum De Morgan pada Negasi Kompleks**:
  Menulis `WHERE NOT (status = 'CANCELLED' OR status = 'FLAGGED')` secara fungsional identik dengan `WHERE status <> 'CANCELLED' AND status <> 'FLAGGED'`. Namun, bentuk kedua umumnya memberi peluang lebih tinggi bagi optimasi indeks range scan pada mesin basis data legasi.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Query Plan**: Buat tabel dengan 100.000 baris data dummy. Buat indeks terpisah pada kolom `A` dan indeks terpisah pada kolom `B`. Jalankan query:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM your_table WHERE A = 10 OR B = 20;
   ```
   Amati apakah engine database Anda memilih `BitmapOr / Index Merge`, atau melakukan `Seq Scan`. Bandingkan waktu eksekusinya jika query diubah menggunakan `UNION ALL`.
2. **Eksplorasi Three-Valued Logic**: Jalankan query berikut di RDBMS Anda tanpa membuat tabel:
   ```sql
   SELECT 
       CASE WHEN NULL OR TRUE THEN 'Lolos' ELSE 'Gagal' END AS test_or,
       CASE WHEN NULL AND FALSE THEN 'Lolos' ELSE 'Gagal' END AS test_and;
   ```
   Analisis mengapa `NULL OR TRUE` menghasilkan `'Lolos'` (`TRUE`), sedangkan `NULL AND FALSE` menghasilkan `'Gagal'` (`FALSE`) meskipun sama-sama mengandung operand `NULL`.
