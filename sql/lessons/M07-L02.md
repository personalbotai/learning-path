## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Klausa `PARTITION BY` adalah sub-elemen dari klausa `OVER()` dalam fungsi jendela (*window functions*) SQL. Secara fundamental, `PARTITION BY` memecah *result set* yang telah difilter ke dalam subset logis—disebut *partitions* atau jendela data—tanpa menggabungkan (*collapsing*) baris-baris data tersebut ke dalam satu baris tunggal seperti yang terjadi pada `GROUP BY`.

```
           +-------------------------------------------------------+
           |                    GROUP BY                           |
           | Input: N rows  ---> Aggregation ---> Output: K rows   |
           |                     (K <= N, identitas baris hilang)  |
           +-------------------------------------------------------+

           +-------------------------------------------------------+
           |              WINDOW + PARTITION BY                    |
           | Input: N rows  ---> Partitioning -> Output: N rows    |
           |                     & Calc          (Setiap baris     |
           |                                      tetap utuh)      |
           +-------------------------------------------------------+
```

#### Urutan Eksekusi Logis (*Logical Query Processing*)
Fungsi jendela dieksekusi sangat larut dalam *pipeline* pemrosesan query SQL:
1. `FROM` & `JOIN`
2. `WHERE`
3. `GROUP BY`
4. `HAVING`
5. **`SELECT` (termasuk evaluasi Window Function & `PARTITION BY`)**
6. `DISTINCT`
7. `ORDER BY`
8. `LIMIT` / `OFFSET`

Karena dieksekusi pada tahap `SELECT`, window function dapat mengakses kolom individual sekaligus agregasi grup yang dihitung pada tahap `GROUP BY`, tetapi **tidak bisa** langsung difilter di dalam klausa `WHERE` atau `HAVING` pada level query yang sama (harus dibungkus dalam CTE atau Subquery).

#### Mekanisme Pemartisian
Ketika sebuah query memuat klausa `OVER (PARTITION BY col_a ORDER BY col_b)`:
1. Engine memecah *working set* ke dalam kelompok-kelompok diskrit berdasarkan *hash* atau urutan nilai dari `col_a`.
2. Setiap partisi diperlakukan sebagai batas isolasi komputasi: akumulator fungsi (misalnya `SUM()`, `AVG()`, `ROW_NUMBER()`) akan di-*reset* ke kondisi awal setiap kali boundary partisi berpindah ke nilai `col_a` berikutnya.

### 2. Implementasi & Contoh Kasus Nyata

Skenario berikut menggunakan PostgreSQL modern untuk melacak transaksi e-commerce: mencari kontribusi persentase penjualan tiap produk terhadap total kategori, serta mendeteksi pesanan berulang menggunakan *ranking*.

```sql
-- 1. Setup Skema & Sample Data
CREATE TABLE orders (
    order_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INT NOT NULL,
    category VARCHAR(50) NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    ordered_at TIMESTAMPTZ NOT NULL
);

INSERT INTO orders (customer_id, category, amount, ordered_at) VALUES
(101, 'Electronics', 1200.00, '2023-10-01 08:30:00+00'),
(102, 'Electronics',  300.00, '2023-10-01 09:15:00+00'),
(101, 'Electronics',  800.00, '2023-10-02 11:00:00+00'),
(103, 'Home',         150.00, '2023-10-01 10:00:00+00'),
(104, 'Home',         450.00, '2023-10-02 14:20:00+00'),
(102, 'Home',         200.00, '2023-10-03 16:45:00+00');

-- 2. Query Kompleks: Agregasi Relatif & Ranking per Partisi
WITH PartitionedMetrics AS (
    SELECT
        order_id,
        customer_id,
        category,
        amount,
        ordered_at,
        
        -- Komputasi akumulasi total dalam partisi kategori yang sama
        SUM(amount) OVER (
            PARTITION BY category
        ) AS total_category_sales,

        -- Running total per kategori secara kronologis
        -- Frame default: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        SUM(amount) OVER (
            PARTITION BY category 
            ORDER BY ordered_at
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS running_category_sales,

        -- Ranking urutan belanja per pelanggan (Customer History)
        ROW_NUMBER() OVER (
            PARTITION BY customer_id 
            ORDER BY ordered_at ASC
        ) AS customer_order_sequence,

        -- Mengambil nilai transaksi sebelumnya milik pelanggan yang sama
        LAG(amount, 1, 0.00) OVER (
            PARTITION BY customer_id 
            ORDER BY ordered_at ASC
        ) AS previous_order_amount
    FROM orders
)
SELECT
    order_id,
    customer_id,
    category,
    amount,
    customer_order_sequence,
    previous_order_amount,
    running_category_sales,
    total_category_sales,
    -- Menghitung rasio kontribusi transaksi terhadap kategori
    ROUND((amount / total_category_sales) * 100, 2) AS category_contribution_pct
FROM PartitionedMetrics
ORDER BY category, ordered_at;
```

#### Penjelasan Komponen Kunci:
- **`PARTITION BY category`**: Memastikan `total_category_sales` hanya menjumlahkan transaksi dalam kategori yang relevan (`Electronics` tidak tercampur dengan `Home`).
- **`PARTITION BY customer_id ORDER BY ordered_at`**: Konteks partisi dialihkan ke `customer_id`. Artinya, mesin basis data dapat mengevaluasi beberapa definisi partisi yang berbeda dalam satu lintasan *SELECT* yang sama.
- **`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`**: Penentuan batas eksplisit *sliding window* dari baris awal partisi hingga baris saat ini.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
Ketika query optimizer menerima klausa `PARTITION BY`:
1. **Sort Phase**: Optimizer menyisipkan simpul eksekusi `Sort` sebelum simpul `WindowAgg`. Data **wajib diurutkan** berdasarkan kolom-kolom pada `PARTITION BY`, diikuti oleh kolom pada `ORDER BY` jendela.
   ```text
   QUERY PLAN:
   ->  WindowAgg  (Cost: ... Rows: ... Width: ...)
         ->  Sort  (Key: category, ordered_at)
               Sort Method: quicksort  Memory: 25kB
               ->  Seq Scan on orders
   ```
2. **Streaming Evaluation (WindowAgg)**: Node `WindowAgg` membaca baris data yang sudah terurut secara sekuensial. Selama nilai kolom partisi sama dengan baris sebelumnya, akumulator internal fungsi jendela diperbarui. Begitu nilai kunci partisi berubah (*boundary crossing*), node memicu operasi *flush*, me-reset *state*, dan memulai partisi baru.

#### Alokasi Memori & Disk Spill
- Pemrosesan partisi sangat bergantung pada alokasi memori lokal per sesi (misalnya `work_mem` di PostgreSQL atau sort buffer di MySQL/Oracle).
- Jika volume data yang akan dipartisi melebihi alokasi memori kerja, engine akan beralih dari algoritma pemilahan in-memory (*Quicksort*) ke pemilahan berbasis disk (**External Merge Sort**).
- *Spill-to-disk* menyebabkan pembacaan dan penulisan berkas sementara (*temp files*), yang mendegradasi performa I/O secara signifikan.

#### Trade-offs
- **Kompleksitas Komputasi**: Window function dengan `PARTITION BY` memiliki kompleksitas dasar $\mathcal{O}(N \log N)$ akibat fase sorting, dibandingkan pembacaan sekuensial $\mathcal{O}(N)$ biasa.
- **Multi-Partition Overhead**: Menggunakan beberapa window function dengan `PARTITION BY` yang menggunakan kolom berbeda (misalnya partisi satu berbasis `category`, partisi lainnya berbasis `customer_id`) memaksa engine melakukan **multiple sort steps** secara beruntun, meningkatkan pemakaian CPU dan memori secara drastis.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Manfaatkan Index Scans**: Buat indeks komposit yang mencakup pola partisi dan pengurutan jendela:
  ```sql
  CREATE INDEX idx_orders_cat_date ON orders(category, ordered_at);
  ```
  Ini mengeliminasi node `Sort` yang mahal; engine dapat langsung melakukan *Index Scan* masuk ke simpul `WindowAgg`.
- **Eksplisit terhadap Frame (`ROWS` vs `RANGE`)**: Selalu tentukan frame spesifik secara eksplisit jika menggunakan `ORDER BY` di dalam window:
  ```sql
  -- Baik & Deterministik:
  SUM(amount) OVER (PARTITION BY category ORDER BY ordered_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
  ```
- **Reuse Definisi Window**: Gunakan klausul `WINDOW` bernama (*named window*) jika konfigurasi partisi digunakan berulang kali:
  ```sql
  SELECT 
      SUM(amount) OVER w,
      AVG(amount) OVER w
  FROM orders
  WINDOW w AS (PARTITION BY category ORDER BY ordered_at);
  ```

#### Don'ts
- **Hindari Implicit Frame Bottleneck**: Jika Anda mendefinisikan `ORDER BY` tanpa frame clause, ANSI SQL menetapkan default ke:
  `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`
  `RANGE` membutuhkan pelacakan baris dengan nilai duplikat (*ties check*) yang membutuhkan struktur memori tambahan dibanding `ROWS` yang hanya menghitung posisi fisik baris.
- **Jangan Menggunakan Window Function untuk Filter Langsung**:
  ```sql
  -- ERROR: window functions are not allowed in WHERE
  SELECT * FROM orders WHERE ROW_NUMBER() OVER (PARTITION BY category ORDER BY amount DESC) = 1;
  ```
  Gunakan **CTE** (*Common Table Expression*) atau *derived table*.

#### Edge Cases
- **Partisi Bernilai NULL**: Semua nilai `NULL` pada kolom `PARTITION BY` akan dikelompokkan ke dalam **satu partisi tunggal**. Pastikan logika fungsi agregasi Anda memperhitungkan kemungkinan ini agar tidak terjadi ketimpangan ukuran partisi (*data skew*).
- **Empty Partition / Singular Partition**: Jika seluruh tabel menghasilkan satu nilai unik pada kolom pemartisi, seluruh tabel menjadi satu partisi raksasa, menghilangkan keuntungan paralelisasi engine analitik.

### 5. Tantangan Eksplorasi Mandiri

1. **Deduplikasi Skala Besar Tanpa Self-Join**:
   Buat tabel sementara berisi 100.000 data log web server (`user_id`, `ip_address`, `visited_at`). Tulis query menggunakan `ROW_NUMBER() OVER (PARTITION BY ...)` untuk menghapus seluruh entri duplikat dari `user_id` yang mengakses sistem dalam selang waktu tertentu, hanya menyisakan log yang paling pertama terekam.
2. **Gap and Islands Problem**:
   Diberikan tabel absensi karyawan harian, gunakan kombinasi `PARTITION BY`, `ROW_NUMBER()`, dan manipulasi tanggal untuk mengidentifikasi rentang hari kerja beruntun (*consecutive working days*) terpanjang untuk masing-masing departemen. Analisis output `EXPLAIN ANALYZE` pada PostgreSQL untuk mengidentifikasi apakah terjadi *external merge sort* pada disk.
