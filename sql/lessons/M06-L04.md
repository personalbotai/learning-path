### 1. Konsep & Arsitektur Mendalam

*Common Table Expression* (CTE) adalah konstruksi sintaksis SQL standar (diperkenalkan pada SQL:1999) yang mendefinisikan *result set* sementara yang diberi nama, bersifat modular, dan masa hidupnya (*lifetime*) terbatas hanya pada siklus eksekusi satu kueri utama (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, atau `MERGE`). CTE diinisialisasi menggunakan klausa `WITH`.

```
        +-------------------------------------------------------+
        |                 Kueri Utama (Outer Query)             |
        |                                                       |
        |   WITH Cte_A AS ( ... ),                              |
        |        Cte_B AS ( ... referensi Cte_A ... )           |
        |   SELECT * FROM Cte_B JOIN Cte_A ON ...               |
        +-------------------------------------------------------+
                                  |
               Parsing & Ast Generation (Logical Plan)
                                  |
                                  v
              Query Optimizer (Inlining vs Materialization)
                     /                          \
                    v                            v
       [ Inline Expansion ]             [ Temporary Spool ]
       Subtree digabung ke kueri        Materialisasi ke memory/disk
       induk, predicate pushdown        Dieksekusi sekali, di-scan ulang
       berjalan optimal.                (Cache-like behavior).
```

Secara arsitektural, CTE menyelesaikan masalah keterbacaan (*readability*) dan perawatan (*maintainability*) dari *derived tables* (subquery bersarang/nested subqueries). Jika subquery membentuk pohon ketergantungan *inside-out* (dibaca dari lapisan terdalam ke terluar), CTE menyusun kueri secara imperatif-deklaratif dari *top-to-bottom*, merepresentasikan graf asiklik terarah (*Directed Acyclic Graph* / DAG) dari dependensi relasional.

Pada level *parser* dan *query planner*:
1. **Scope Binding:** Nama CTE didaftarkan ke dalam *catalog namespace* sementara yang hanya valid untuk *scope* kueri tersebut.
2. **AST Transformation:** Parser membentuk node terpisah untuk setiap definisi CTE dalam *Abstract Syntax Tree* (AST).
3. **Optimasi Dependensi:** Query Optimizer mengevaluasi ketergantungan antar-CTE. Sebuah CTE dapat mereferensikan CTE lain yang didefinisikan sebelumnya dalam klausa `WITH` yang sama, memungkinkan dekomposisi kalkulasi pipeline yang kompleks menjadi tahapan-tahapan diskret.

### 2. Implementasi & Contoh Kasus Nyata

Contoh kasus berikut merepresentasikan sistem analitik e-commerce: Mengidentifikasi metrik performa pelanggan (*High-Value Customers*) dengan menghitung agregasi pesanan, memfilter ambang batas tertentu, lalu menggabungkannya dengan profil pelanggan dan detail transaksi terakhir.

```sql
-- DDL & Sample Data Setup (PostgreSQL / modern ANSI-SQL dialect)
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100),
    tier VARCHAR(20)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT REFERENCES customers(customer_id),
    order_date DATE,
    total_amount NUMERIC(12, 2),
    status VARCHAR(20)
);

-- Eksekusi Pipeline Query Menggunakan Multi-CTE
WITH 
-- 1. CTE Pertama: Agregasi metrik finansial per pelanggan (hanya order selesai)
customer_aggregates AS (
    SELECT 
        o.customer_id,
        COUNT(o.order_id) AS total_orders,
        SUM(o.total_amount) AS lifetime_spent,
        MAX(o.order_date) AS last_order_date
    FROM orders o
    WHERE o.status = 'COMPLETED'
    GROUP BY o.customer_id
),

-- 2. CTE Kedua: Menentukan segmen pelanggan bernilai tinggi (bergantung pada customer_aggregates)
high_value_customers AS (
    SELECT 
        customer_id,
        lifetime_spent,
        total_orders,
        last_order_date
    FROM customer_aggregates
    WHERE lifetime_spent >= 10000000.00 -- Threshold: >= 10 juta IDR
),

-- 3. CTE Ketiga: Mengambil detail order terakhir untuk validasi recency
latest_order_details AS (
    SELECT 
        o.customer_id,
        o.order_id AS latest_order_id,
        o.total_amount AS latest_order_amount
    FROM orders o
    INNER JOIN high_value_customers hvc 
        ON o.customer_id = hvc.customer_id 
       AND o.order_date = hvc.last_order_date
)

-- Kueri Utama: Menggabungkan hasil CTE dengan dimensi profil pelanggan
SELECT 
    c.customer_id,
    c.name,
    c.tier,
    hvc.lifetime_spent,
    hvc.total_orders,
    lod.latest_order_id,
    lod.latest_order_amount
FROM high_value_customers hvc
JOIN customers c ON c.customer_id = hvc.customer_id
LEFT JOIN latest_order_details lod ON lod.customer_id = hvc.customer_id
ORDER BY hvc.lifetime_spent DESC;
```

**Penjelasan Alur Eksekusi:**
- `customer_aggregates`: Mengurangi kardinalitas tabel transaksi mentah melalui agregasi `GROUP BY`.
- `high_value_customers`: Menerapkan filter predikat (*filtering stage*) terhadap hasil CTE pertama.
- `latest_order_details`: Melakukan *self-join constraint* secara efisien karena hanya mengevaluasi subset data pelanggan yang telah difilter oleh `high_value_customers`.
- Kueri Utama: Menyatukan domain dimensi (*dimension table*) dengan metrik analitik yang telah diproses.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Inlining vs Materialization
Perilaku *runtime* CTE sangat bergantung pada *cost-based optimizer* (CBO) dari mesin basis data yang digunakan:
- **Inlining (Subquery Folding):** Optimizer memperlakukan CTE layaknya *derived table* atau *inline view*. Teks kueri CTE di-*expand* langsung ke dalam kueri utama. Dengan mekanisme ini, optimizer bebas melakukan *Predicate Pushdown* (mendorong klausa `WHERE` kueri induk masuk ke dalam CTE) serta menyusun ulang urutan *Join* (*join reordering*).
- **Materialization (Optimization Fence):** RDBMS mengeksekusi CTE secara terpisah satu kali, kemudian menulis hasilnya ke struktur data *ephemeral* di memori (*Tuplestore* atau *Spool* buffer). Kueri induk kemudian membaca dari *buffer* tersebut.

> **Evolusi PostgreSQL Engine:**
> - **Sebelum PG 12:** Semua CTE bersifat *materialization fence* secara absolut. Optimizer tidak dapat mendorong predikat luar ke dalam CTE, sering kali memicu *performance degradation* fatal (misal: *sequential scan* pada jutaan baris data padahal kueri induk hanya meminta satu ID).
> - **PG 12 ke Atas:** CTE di-*inline* secara *default* jika memenuhi kriteria: bukan rekursif, bebas dari *side-effects* (seperti `INSERT/UPDATE/DELETE`), dan hanya direferensikan sekali dalam kueri induk. Developer dapat mengontrolnya secara deterministik via sintaks:
>   `WITH cte AS MATERIALIZED (...)` atau `WITH cte AS NOT MATERIALIZED (...)`.

#### Alokasi Memori / Resource
- Jika CTE di-materialisasi, hasil evaluasi disimpan dalam alokasi memori lokal per-proses/koneksi (seperti `work_mem` di PostgreSQL atau *tempdb* buffer pool di SQL Server).
- Jika volume baris hasil evaluasi melampaui ambang batas memori lokal, mesin akan melakukan *spill-to-disk* ke *temporary tablespace*, menyebabkan latensi I/O tinggi.
- Mesin berbasis *Volcano Iterator Model* memproses *inlined* CTE secara *pipelined* baris-demi-baris (`tuple-at-a-time` via fungsi `next()`), mengeliminasi overhead alokasi struktur data perantara.

#### Trade-offs
| Pendekatan | Keuntungan | Kerugian |
| :--- | :--- | :--- |
| **Materialized CTE** | Menghindari re-komputasi jika CTE dibaca berulang kali (> 1 kali) dalam kueri utama. | Mengabaikan indeks luar; memblokir *predicate pushdown*; alokasi RAM/Disk untuk *spooling*. |
| **Inlined CTE** | Akses ke indeks tabel dasar dipertahankan; optimasi join & filter maksimal. | Jika direferensikan berkali-kali, kueri CTE akan dieksekusi ulang sebanyak pemanggilan. |

### 4. Best Practices & Common Pitfalls

- **Do's:**
  - Gunakan CTE sebagai instrumen dokumentasi kode logika bisnis yang kompleks agar pembaca memahami aliran transformasi data secara terstruktur.
  - Tambahkan deklarasi eksplisit `WITH cte AS MATERIALIZED (...)` (khususnya di PostgreSQL 12+) jika CTE memproses kueri agregasi yang sangat berat dan direferensikan lebih dari satu kali pada klausa kueri induk.
  - Terapkan filter seketat mungkin di dalam *body* CTE untuk meminimalkan ukuran data sebelum diproses oleh CTE berikutnya atau kueri induk.

- **Don'ts:**
  - Jangan berasumsi bahwa CTE membuat temporary index. CTE **tidak** memiliki indeks sekunder. Mengabaikan ukuran data materialisasi pada CTE dapat memicu operasi `Nested Loop` lambat pada kueri utama.
  - Jangan gunakan CTE untuk operasi sederhana satu baris yang dapat diselesaikan dengan ekspresi JOIN standar; *layering* CTE yang berlebihan tanpa alasan menambah beban parsing kueri.
  - Hindari menganggap CTE setara dengan `CREATE TEMPORARY TABLE`. CTE tidak memiliki statistik distribusi kolom (*catalog statistics*) tersendiri; CBO mengestimasi biayanya berdasarkan tabel dasar atau fungsi heuristik.

- **Edge Cases & Pitfalls:**
  - **Optimization Fence Trap:** Di beberapa database (atau PG pre-12), kueri seperti:
    ```sql
    WITH data AS (SELECT * FROM massive_log)
    SELECT * FROM data WHERE id = 100;
    ```
    dapat memicu *full scan* pada `massive_log` sebelum filter `id = 100` diterapkan.
  - **Multiple References Overhead:** Pada mesin yang selalu men-inline CTE (seperti MySQL 8.0 tanpa *derived table materialization optimization* khusus), jika sebuah CTE dipanggil 3 kali dalam `UNION ALL`, subquery tersebut dieksekusi 3 kali dari nol.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan (Optimizer Inspection):**
   Eksekusi kueri berikut pada database PostgreSQL Anda menggunakan `EXPLAIN ANALYZE`:
   ```sql
   EXPLAIN ANALYZE
   WITH raw_orders AS (
       SELECT * FROM orders
   )
   SELECT * FROM raw_orders WHERE order_id = 42;
   ```
   Bandingkan hasilnya jika Anda mengubahnya secara paksa menjadi:
   `WITH raw_orders AS MATERIALIZED (...)`. Perhatikan perbedaan pada biaya (`cost`), estimasi baris, dan tipe scan (*Index Scan* vs *Seq Scan* / *CTE Scan*).

2. **Benchmarking CTE Re-use:**
   Buat tabel dengan 1.000.000 data acak. Buat kueri yang menghitung nilai `AVG()`, `MAX()`, dan `MIN()` dalam satu CTE, lalu gabungkan (*self-join*) CTE tersebut sebanyak dua kali pada kueri utama. Periksa apakah mesin database Anda mengeksekusinya satu kali (materialisasi) atau dua kali (inlining berulang).

3. **Data Mutation CTE Handling:**
   Teliti kemampuan dialek PostgreSQL di mana CTE dapat menjalankan `DELETE` atau `UPDATE` yang mengembalikan data (`RETURNING`), lalu gunakan CTE tersebut sebagai sumber input bagi perintah `INSERT` di kueri utama dalam satu transaksi atomik. Eksplorasi batasan konsistensi *snapshot* isolasinya.
