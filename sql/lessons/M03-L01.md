## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Fungsi Agregasi (*Aggregate Functions*) dalam SQL adalah operasi matematis yang memetakan multiset nilai (*bag of values*) dari sekumpulan baris menjadi sebuah nilai skalar tunggal. Berbeda dengan operasi proyeksi skalar biasa (misal: `SELECT price * 0.1`), agregasi memerlukan pemrosesan vertikal melintasi banyak *tuple* (baris) pada *record set*.

Dua fungsi agregasi paling fundamental dalam spesifikasi ANSI SQL adalah `COUNT` dan `SUM`.

```
                  Input: N Rows                      Output: 1 Value
┌─────────────────────────────────────────────────┐
│ Row 1: amount = 100                             │
│ Row 2: amount = NULL                            │  ───>  SUM(amount)   ───>  350
│ Row 3: amount = 250                             │  ───>  COUNT(amount) ───>  2
└─────────────────────────────────────────────────┘  ───>  COUNT(*)      ───>  3
```

#### A. Semantik Evaluasi `COUNT`
- **`COUNT(*)`**: Menghitung kardinalitas total dari baris yang memenuhi predikat evaluasi tabel, tanpa memedulikan apakah nilai pada kolom individual bernilai `NULL` atau tidak. RDBMS memperlakukan `*` di sini sebagai representasi utuh dari eksistensi baris (*row-level counter*).
- **`COUNT(expression)` / `COUNT(column)`**: Mengevaluasi ekspresi per baris dan hanya menginkrementasi akumulator jika hasil ekspresi **bukan `NULL`** (*non-null value*).
- **`COUNT(DISTINCT column)`**: Memerlukan evaluasi deduplikasi (*hash set* atau *B-Tree lookup*) sebelum menginkrementasi nilai counter untuk setiap nilai unik non-`NULL`.

#### B. Semantik Evaluasi `SUM`
- **`SUM(expression)`**: Melakukan akumulasi matematis terhadap seluruh ekspresi numerik non-`NULL`. 
- **Penanganan `NULL` & Three-Valued Logic (3VL)**: Sesuai standar ANSI SQL, jika sekumpulan data input bernilai kosong atau seluruh baris yang dievaluasi bernilai `NULL`, operasi `SUM` akan mengembalikan `NULL`, **bukan `0`**. Ini merupakan perbedaan struktural mendasar dengan `COUNT`, yang akan selalu mengembalikan angka `0` jika tidak ada baris yang cocok.

### 2. Implementasi & Contoh Kasus Nyata

Berikut skema tabel transaksi keuangan dan contoh penggunaan analitis menggunakan SQL standar modern (kompatibel dengan PostgreSQL, MySQL 8+, SQLite 3):

```sql
-- DDL Skema Transaksi Finansial
CREATE TABLE transactions (
    id BIGINT PRIMARY KEY,
    account_id INT NOT NULL,
    amount DECIMAL(12, 2), -- Bernilai NULL jika transaksi dibatalkan sebelum processing
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

-- DML Seed Data
INSERT INTO transactions (id, account_id, amount, status, created_at) VALUES
(1, 101, 1500.00, 'COMPLETED', '2024-01-01 10:00:00'),
(2, 101,  750.50, 'COMPLETED', '2024-01-02 11:30:00'),
(3, 101,    NULL, 'ABORTED',   '2024-01-02 12:00:00'),
(4, 102,  200.00, 'COMPLETED', '2024-01-03 09:15:00'),
(5, 103,    NULL, 'PENDING',   '2024-01-03 14:00:00');

-- 1. Evaluasi Perbedaan COUNT(*), COUNT(col), dan SUM(col)
SELECT 
    COUNT(*) AS total_rows,                  -- Output: 5 (semua baris)
    COUNT(amount) AS valid_amount_count,     -- Output: 3 (mengabaikan 2 baris NULL)
    SUM(amount) AS gross_volume,             -- Output: 2450.50 (1500 + 750.50 + 200)
    -- Praktik aman: konversi NULL ke 0 untuk integrasi aplikasi hilir
    COALESCE(SUM(amount), 0.00) AS safe_volume
FROM transactions;

-- 2. Agregasi Kondisional Tingkat Lanjut (Conditional Aggregation)
-- Menggunakan SUM(CASE ...) atau FILTER clause (standar ANSI SQL modern / PostgreSQL)
SELECT 
    COUNT(*) AS total_tx,
    -- Menghitung spesifik transaksi sukses via SUM of flags
    SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS completed_tx_count,
    -- Akumulasi finansial hanya untuk yang berstatus COMPLETED
    COALESCE(SUM(CASE WHEN status = 'COMPLETED' THEN amount ELSE 0 END), 0.00) AS total_settled_amount
FROM transactions;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
Pemrosesan fungsi agregasi pada *query engine* (seperti PostgreSQL, MySQL InnoDB) mengikuti **Volcano Iterator Model** atau **Vectorized Execution**:

1. **Volcano Iterator**: Operator agregasi bertindak sebagai node `Aggregate` pada query tree. Node ini memanggil method `.next()` secara rekursif pada node child (misal: `Seq Scan` atau `Index Scan`).
2. **State Transition Loop**:
   Mesin memiliki dua register internal:
   - `state_value` (akumulator)
   - `sfunc` (fungsi transisi status)
   
   Untuk `SUM(amount)`:
   ```c
   // Pseudocode representasi C level di DBMS (PostgreSQL backend)
   Datum current_state = NULL;
   bool is_null = true;

   while ((tuple = ExecScanFetch(child_node)) != NULL) {
       Datum val = GetAttributeByName(tuple, "amount", &is_attr_null);
       if (!is_attr_null) {
           if (is_null) {
               current_state = val;
               is_null = false;
           } else {
               current_state = numeric_add(current_state, val);
           }
       }
   }
   return is_null ? DirectFunctionCall(NULL) : current_state;
   ```

#### Alokasi Memori / Resource
- **State Register**: Agregasi sederhana (`SUM`, `COUNT`) tanpa klausa `GROUP BY` hanya membutuhkan memori $O(1)$ karena akumulasi dilakukan secara streaming tanpa perlu menyimpan baris mentah di memori (`WorkMem` / buffer pool).
- **Tipe Data Akumulator (Numeric Precision)**: Pada fungsi `SUM`, DBMS mempromosikan tipe data akumulator untuk mencegah *arithmetic overflow*. Misalnya, kolom bertipe integer 32-bit (`INT`) sering kali diakumulasikan ke register 64-bit (`BIGINT`), sedangkan kolom float/decimal diakumulasikan ke tipe arbitrary-precision (`NUMERIC`/`DECIMAL`).

#### Trade-offs: Table Scan vs MVCC (Multi-Version Concurrency Control)
- Banyak pengembang berasumsi `COUNT(*)` membaca *metadata* internal tabel secara instan $O(1)$. Hal ini hanya berlaku pada storage engine non-transaksional usang (seperti MySQL MyISAM).
- Pada engine transaksional modern dengan MVCC (seperti InnoDB atau PostgreSQL HEAP), setiap baris harus diuji visibilitas transaksinya (*transaction visibility map* / snapshot visibility check). Akibatnya, `COUNT(*)` tanpa index coverage harus melakukan pembacaan berbiaya $O(N)$ melalui Sequential Scan.
- **Index-Only Scan**: Jika terdapat secondary index, optimasi engine akan memilih memindai struktur leaf node B-Tree daripada membaca tabel heap utuh, mereduksi I/O disk secara signifikan.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `COUNT(*)` sebagai default counter**: RDBMS Query Planner modern telah dioptimasi secara spesifik untuk menganggap `COUNT(*)` sebagai penghitungan baris murni, memilih indeks terkecil yang tersedia untuk menghemat I/O.
- **Bungkus `SUM()` dengan `COALESCE()`**: Selalu gunakan `COALESCE(SUM(col), 0)` pada lapisan query database jika logika bisnis mengharuskan representasi nilai nol dari himpunan baris yang berpotensi kosong, guna menghindari `NullPointerException` atau `nil pointer dereference` di aplikasi client.
- **Gunakan tipe `DECIMAL` / `NUMERIC` untuk mata uang**: Jangan gunakan `SUM()` pada kolom bertipe floating-point (`FLOAT`/`DOUBLE`) untuk operasi moneter karena akumulasi *rounding error* berbasis IEEE 754.

#### Don'ts
- **Hindari `COUNT(column)` jika tujuannya menghitung baris**: Menulis `COUNT(id)` memaksa engine memeriksa keberadaan nilai non-NULL pada kolom tersebut di setiap baris, mendatangkan overhead kecil dibanding `COUNT(*)` tanpa adanya keuntungan fungsional.
- **Jangan gunakan idiom usang `COUNT(1)`**: Anggapan bahwa `COUNT(1)` lebih cepat dibanding `COUNT(*)` adalah mitos. Parser SQL menginterpretasikan `1` sebagai konstanta literal skalar yang dicek ketiadaan NULL-nya, sedangkan `*` langsung diarahkan ke counter semantik internal engine.

#### Edge Cases
```sql
-- KASUS 1: Query terhadap himpunan kosong
SELECT 
    COUNT(amount) AS empty_count, -- Mengembalikan: 0
    SUM(amount)   AS empty_sum    -- Mengembalikan: NULL (PERHATIKAN INI!)
FROM transactions 
WHERE id = 999999; -- Record tidak ditemukan

-- KASUS 2: Numeric Overflow pada SUM
-- Jika kolom bertipe SMALLINT dijumlahkan melampaui batas 32,767
-- Beberapa engine (seperti strict-mode MySQL atau manual cast) memicu error:
SELECT SUM(small_number_col::INT) FROM large_table; -- Mitigation: Explicit Type Casting
```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan**: Buat tabel dengan 500.000 baris acak. Jalankan perintah `EXPLAIN ANALYZE` (PostgreSQL) atau `EXPLAIN FORMAT=TREE` (MySQL) untuk membandingkan eksekusi:
   - `SELECT COUNT(*) FROM your_table;` tanpa index.
   - Buat secondary index pada kolom terkecil, lalu ulangi query di atas. Analisis perbedaan cost dan struktur node yang dipilih oleh Optimizer.
2. **Pola "Pivot/Transpose" Finansial**: Tanpa menggunakan klausa `GROUP BY`, tulis sebuah query menggunakan `SUM(CASE ...)` yang menghasilkan satu baris berisi 3 metrik total terpisah: `total_pemasukan`, `total_pengeluaran`, dan `saldo_netto` (pemasukan dikurang pengeluaran).
3. **Simulasi Dampak MVCC**: Buka dua sesi terminal database transaksional simultan. Pada Sesi A, lakukan `DELETE` baris data tanpa `COMMIT`. Di Sesi B, jalankan `COUNT(*)`. Mengapa Sesi B tetap harus melakukan pemindaian baris secara mendalam alih-alih mengandalkan cache statistik tabel?
