## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam SQL, *subquery* (kueri bersarang) dapat mengembalikan satu baris (*single-row*) atau banyak baris (*multi-row*). Ketika sebuah *subquery* mengembalikan lebih dari satu baris, operator perbandingan standar seperti `=`, `>`, atau `<` akan menghasilkan *runtime error* (misal: `Subquery returns more than 1 row`). 

Untuk menangani himpunan data (*set of values*) yang dikembalikan oleh *multi-row subquery*, SQL menyediakan tiga operator himpunan logis:
1. **`IN`**: Mengevaluasi ke `TRUE` jika nilai yang dicari cocok dengan **salah satu** nilai dalam himpunan hasil *subquery*. Secara logis ekuivalen dengan `= ANY`.
2. **`ANY` (atau `SOME`)**: Membandingkan nilai skalar dengan setiap nilai yang dikembalikan oleh *subquery*. Mengevaluasi ke `TRUE` jika perbandingan bernilai benar untuk **setidaknya satu** baris (beroperasi seperti logika `OR`).
3. **`ALL`**: Membandingkan nilai skalar dengan setiap nilai yang dikembalikan oleh *subquery*. Mengevaluasi ke `TRUE` hanya jika perbandingan bernilai benar untuk **semua** baris (beroperasi seperti logika `AND`).

Secara arsitektur, operator ini memungkinkan developer untuk menulis deklarasi filter berbasis himpunan dinamis tanpa harus melakukan eksplisit `JOIN`, meskipun di balik layar, *Query Optimizer* modern sering kali menulis ulang (rewrite) kueri ini menjadi bentuk *Join* untuk efisiensi eksekusi.

### 2. Implementasi & Contoh Kasus Nyata

Misalkan kita memiliki dua tabel: `karyawan` (id, nama, gaji, departemen_id) dan `departemen` (id, nama_dept, lokasi).

```sql
-- 1. Menggunakan IN: 
-- Mencari karyawan yang bekerja di departemen yang berlokasi di 'Jakarta'
SELECT nama, gaji, departemen_id
FROM karyawan
WHERE departemen_id IN (
    SELECT id 
    FROM departemen 
    WHERE lokasi = 'Jakarta'
);

-- 2. Menggunakan ANY:
-- Mencari karyawan yang gajinya LEBIH BESAR dari setidaknya satu karyawan di departemen IT (id = 1)
-- (Artinya: Gajinya lebih besar dari gaji minimum di departemen IT)
SELECT nama, gaji
FROM karyawan
WHERE gaji > ANY (
    SELECT gaji 
    FROM karyawan 
    WHERE departemen_id = 1
)
AND departemen_id != 1; -- Mengecualikan karyawan IT itu sendiri

-- 3. Menggunakan ALL:
-- Mencari karyawan yang gajinya LEBIH BESAR dari SEMUA karyawan di departemen Sales (id = 2)
-- (Artinya: Gajinya lebih besar dari gaji maksimum di departemen Sales)
SELECT nama, gaji
FROM karyawan
WHERE gaji > ALL (
    SELECT gaji 
    FROM karyawan 
    WHERE departemen_id = 2
);
```

**Penjelasan Variasi:**
- `> ANY` ekuivalen dengan `> MIN(kolom)`.
- `< ANY` ekuivalen dengan `< MAX(kolom)`.
- `> ALL` ekuivalen dengan `> MAX(kolom)`.
- `< ALL` ekuivalen dengan `< MIN(kolom)`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  *Query Optimizer* (seperti di PostgreSQL atau MySQL) jarang mengeksekusi *subquery* secara naif (menjalankan *subquery* lalu melakukan iterasi *outer query*). Untuk operator `IN`, *optimizer* biasanya mengubahnya menjadi operasi **Semi-Join**. Semi-Join mengembalikan baris dari tabel luar hanya sekali, meskipun ada banyak kecocokan di tabel dalam, sehingga menghindari duplikasi data.
  Untuk `NOT IN`, *optimizer* menggunakan **Anti-Join**.
- **Alokasi Memori / Resource**: 
  Jika *subquery* tidak berkorelasi (*uncorrelated*), *Execution Engine* akan melakukan **Materialization**. Hasil *subquery* dieksekusi sekali, disimpan dalam *temporary hash table* di memori (jika kecil) atau di disk (jika besar). *Outer query* kemudian melakukan *hash probe* terhadap tabel memori ini, yang memberikan kompleksitas waktu pencarian O(1).
- **Trade-offs**: 
  Menggunakan `IN` dengan *subquery* yang mengembalikan jutaan baris dapat menyebabkan *memory bottleneck* saat proses materialisasi. Dalam kasus himpunan data masif, menggunakan `EXISTS` (yang mendukung *short-circuit evaluation*) seringkali lebih efisien daripada `IN`.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `EXISTS` alih-alih `IN` jika *subquery* mengembalikan dataset yang sangat besar, karena `EXISTS` akan berhenti mencari (*short-circuit*) segera setelah menemukan satu kecocokan.
  - Pastikan kolom yang digunakan dalam klausa `IN`, `ANY`, atau `ALL` memiliki indeks (B-Tree index) untuk mempercepat proses *lookup* atau *Semi-Join*.
- **Don'ts**:
  - **BAHAYA KRITIS (The NULL Trap)**: Jangan pernah menggunakan `NOT IN` jika *subquery* berpotensi mengembalikan nilai `NULL`. Jika ada satu saja nilai `NULL` dalam hasil *subquery*, maka seluruh evaluasi `NOT IN` akan menghasilkan `UNKNOWN` (dianggap *False*), dan kueri luar tidak akan mengembalikan baris sama sekali. Selalu gunakan `NOT EXISTS` sebagai alternatif yang aman terhadap `NULL`.
- **Edge Cases**:
  - Jika *subquery* mengembalikan himpunan kosong (0 baris):
    - `IN` dan `ANY` akan selalu mengevaluasi ke `FALSE`.
    - `ALL` akan selalu mengevaluasi ke `TRUE` (ini adalah konsep matematika *vacuous truth*).

### 5. Tantangan Eksplorasi Mandiri

1. Buatlah sebuah kueri `NOT IN` di mana *subquery*-nya secara sengaja mengembalikan satu nilai `NULL`. Amati hasilnya, lalu tulis ulang kueri tersebut menggunakan `NOT EXISTS` untuk melihat perbedaan perilakunya.
2. Gunakan perintah `EXPLAIN ANALYZE` (atau `EXPLAIN` di MySQL) pada kueri yang menggunakan `= ANY` dan kueri yang menggunakan `IN`. Bandingkan *Execution Plan* keduanya—apakah *database engine* memperlakukan keduanya secara identik?
3. Tulis sebuah kueri untuk mencari karyawan dengan gaji tertinggi di seluruh perusahaan **tanpa** menggunakan fungsi agregasi `MAX()`, `ORDER BY`, atau `LIMIT`, melainkan hanya menggunakan operator `ALL` atau `ANY`.
