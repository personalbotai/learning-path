## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Operasi himpunan (*Set Operations*) dalam SQL berakar langsung pada teori Aljabar Relasional (*Relational Algebra*) Edgar F. Codd. Berbeda dengan operasi *JOIN* yang menggabungkan relasi secara horizontal (menambah kolom dari tabel berbeda berdasarkan predikat relasional), operasi himpunan menggabungkan relasi secara **vertikal** (menumpuk baris data dari dua atau lebih aliran tupel (*tuple streams*)).

Terdapat tiga operasi himpunan fundamental dalam standar SQL (ISO/IEC 9075):
1. **`UNION`**: Menghasilkan gabungan himpunan $A \cup B$.
2. **`INTERSECT`**: Menghasilkan irisan himpunan $A \cap B$.
3. **`EXCEPT`** (atau `MINUS` pada dialek Oracle): Menghasilkan selisih himpunan $A \setminus B$.

```
UNION:               INTERSECT:          EXCEPT:
+-------+-------+    +-------+-------+   +-------+-------+
|   A   | A ∩ B |    |       | A ∩ B |   | A \ B |       |
|       |   B   |    |       |       |   |       |       |
+-------+-------+    +-------+-------+   +-------+-------+
Semua baris unik     Hanya baris yang    Hanya baris di A
dari A dan B.        ada di A DAN B.     yang TIDAK ada di B.
```

#### Semantik Himpunan (*Set*) vs. Multihimpunan (*Bag/Multiset*)
Secara default, aljabar relasional murni bekerja pada *Set* (tidak mengizinkan duplikasi). Namun, implementasi database SQL komersial dan open-source beroperasi pada level *Bag/Multiset* untuk alasan efisiensi eksekusi. Oleh karena itu, SQL membedakan dua varian:
- **`DISTINCT` (default implisit)**: Menghapus duplikasi baris pasca-penggabungan.
- **`ALL` (eksplisit)**: Mempertahankan multiplisitas baris tanpa evaluasi kesamaan (*duplicate elimination*).

#### Aturan Integritas Skema (*Union Compatibility*)
Dua relasi dapat dioperasikan secara himpunan jika dan hanya jika memenuhi syarat kompatibilitas skema:
1. **Derajat Arity Sama**: Jumlah kolom (*projected expressions*) pada setiap klausa `SELECT` harus identik ($n_A = n_B$).
2. **Kompatibilitas Tipe Data**: Tipe data pada posisi ordinal yang bersesuaian ($pos_1 \leftrightarrow pos_1, pos_2 \leftrightarrow pos_2$) harus memiliki domain tipe yang sama atau dapat dikonversi secara implisit (*implicit type coercion*) oleh parser/compiler database.
3. **Metadata Label**: Nama kolom pada *result set* akhir ditentukan secara deterministik oleh ekspresi pada branch `SELECT` **pertama**.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sistem multi-channel e-commerce melakukan konsolidasi basis data pelanggan dari transaksi sistem retail fisik (*POS - Point of Sale*) dan platform digital (*Web/App*).

```sql
-- DDL & Sample Data Setup
CREATE TABLE retail_customers (
    customer_id INT,
    email VARCHAR(100),
    registered_at DATE
);

CREATE TABLE online_customers (
    user_id INT,
    email VARCHAR(100),
    created_at DATE
);

INSERT INTO retail_customers VALUES 
(1, 'andi@example.com', '2023-01-15'),
(2, 'budi@example.com', '2023-02-20'),
(3, 'citra@example.com', '2023-03-10');

INSERT INTO online_customers VALUES 
(101, 'budi@example.com', '2023-02-22'),
(102, 'citra@example.com', '2023-04-01'),
(103, 'dewi@example.com', '2023-05-12');
```

#### Kasus 1: Konsolidasi Omnichannel Tanpa Duplikasi (`UNION`)
Mengambil seluruh email pelanggan unik di seluruh platform.

```sql
SELECT email FROM retail_customers
UNION
SELECT email FROM online_customers;
-- Output: andi@example.com, budi@example.com, citra@example.com, dewi@example.com
```

#### Kasus 2: Audit Total Transaksi/Interaksi Pelanggan (`UNION ALL`)
Mengumpulkan semua jejak log registrasi tanpa membuang duplikasi untuk keperluan audit volume stream.

```sql
SELECT email, registered_at AS activity_date, 'RETAIL' AS source 
FROM retail_customers
UNION ALL
SELECT email, created_at AS activity_date, 'ONLINE' AS source 
FROM online_customers;
-- Menghasilkan 6 baris data lengkap tanpa overhead dedup
```

#### Kasus 3: Identifikasi Cross-Channel Shoppers (`INTERSECT`)
Mencari pelanggan yang aktif berbelanja baik di toko fisik maupun platform online.

```sql
SELECT email FROM retail_customers
INTERSECT
SELECT email FROM online_customers;
-- Output: budi@example.com, citra@example.com
```

#### Kasus 4: Retensi Offline-Only Customers (`EXCEPT`)
Mencari pelanggan fisik yang belum terdaftar sama sekali di ekosistem online untuk target kampanye digitalisasi.

```sql
SELECT email FROM retail_customers
EXCEPT
SELECT email FROM online_customers;
-- Output: andi@example.com
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
Ketika SQL query planner memproses query himpunan, ia membentuk pohon eksekusi (*execution plan*) berbasis salah satu dari dua strategi utama:

1. **Sort-Based Strategy (Unique/Merge)**
   - Engine mengeksekusi kedua child node (`Seq Scan`, `Index Scan`, dll).
   - Melakukan operasi `Sort` pada kedua dataset berdasarkan seluruh proyeksi kolom.
   - Menggunakan operator **`Unique`** (untuk `UNION`) atau **`MergeSetOp`** (untuk `INTERSECT`/`EXCEPT`). Operator membaca stream baris terurut secara linear ($O(N)$ setelah sorting) dan membandingkan baris yang bersebelahan.

2. **Hash-Based Strategy (HashAggregate / HashSetOp)**
   - Dataset cabang pertama dimasukkan ke dalam *In-Memory Hash Table*.
   - Hash key dibangun dari kombinasi seluruh kolom yang diproyeksikan.
   - Cabang kedua di-scan, menguji setiap baris terhadap hash table:
     - Untuk `UNION`: Menambahkan baris ke hash table jika hash key belum ada.
     - Untuk `INTERSECT`: Memancarkan baris jika hash key ditemukan di hash table, lalu menandainya agar tidak dievaluasi dua kali.
     - Untuk `EXCEPT`: Menandai/menghapus entri hash table jika ditemukan kecocokan dari cabang kedua, lalu mengembalikan entri yang tersisa.

```
Query: SELECT col FROM A UNION SELECT col FROM B;

                      [ Aggregate / Unique ] (Deduplikasi)
                                |
                         [ Append Node ]
                        /               \
            [ Scan Engine: A ]    [ Scan Engine: B ]
```

#### Alokasi Memori & Disk Spilling
- Engine mengalokasikan buffer memori kerja per operasi (misalnya `work_mem` pada PostgreSQL, `sort_buffer_size` pada MySQL).
- **In-Memory**: Jika hash table atau dataset sorting muat di memori kerja, deduplikasi terjadi secara instan via RAM.
- **Disk Spilling**: Jika ukuran intermediate dataset melebihi batas buffer:
  - Sort-based akan melakukan *External Merge Sort* (menulis partisi sementara ke disk/temp files).
  - Hash-based beralih ke *Hybrid Hash Partitioning* yang mengekspor batch hash buckets ke disk, memicu lonjakan I/O latency.
- **Keuntungan Ekstrem `UNION ALL`**: Operator `UNION ALL` direpresentasikan murni oleh node **`Append`**. Engine streaming membaca cabang A hingga habis, lalu menyambung langsung ke cabang B. Tidak membutuhkan Hash Table, tidak membutuhkan sorting, dan alokasi memori adalah $O(1)$ untuk buffer streaming.

#### Evaluasi NULL (Trinary Logic Bypass)
Berbeda dengan predikat perbandingan biasa seperti `=` (di mana `NULL = NULL` menghasilkan evaluasi `UNKNOWN`), pada operasi himpunan berlaku spesifikasi ANSI SQL: **Dua nilai `NULL` dianggap identik (*indistinguishable*)**. 
Oleh karena itu, baris `(1, NULL)` dari tabel A dan `(1, NULL)` dari tabel B akan dianggap duplikat oleh `UNION`, `INTERSECT`, maupun `EXCEPT`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Default ke `UNION ALL`**: Gunakan `UNION ALL` kecuali jika logika bisnis secara eksplisit mengharuskan eliminasi nilai kembar. Deduplikasi via sorting/hashing adalah operasi komputasi mahal ($O(N \log N)$ atau $O(N)$ space).
- **Gunakan Tipe Data yang Seragam**: Hindari konversi tipe data implisit antarcabang. Jika Tabel A bertipe `INT` dan Tabel B bertipe `NUMERIC`, lakukan casting eksplisit (`CAST(col AS NUMERIC)`) guna mencegah dynamic type coercion yang menonaktifkan optimasi indeks.
- **Enkapsulasi `ORDER BY` Global**: Letakkan `ORDER BY` hanya pada baris paling akhir dari seluruh query gabungan, menggunakan nama kolom dari `SELECT` pertama.

#### Don'ts
- **Menghindari `SELECT *`**: Jangan pernah menggunakan `SELECT *` dalam operasi himpunan. Perubahan skema (penambahan atau reordering kolom via migration) di salah satu tabel akan merusak *arity matching* atau menghasilkan pemetaan kolom silang yang keliru (*cross-data mapping*).
- **Jangan Mengabaikan Precedence Operator**: Secara standar ISO/IEC SQL, operator **`INTERSECT` memiliki prioritas preseden lebih tinggi daripada `UNION` dan `EXCEPT`**.
  ```sql
  -- Evaluasi: A UNION (B INTERSECT C) BUKAN (A UNION B) INTERSECT C
  SELECT id FROM A
  UNION
  SELECT id FROM B
  INTERSECT
  SELECT id FROM C;
  ```
  Selalu gunakan tanda kurung eksplisit `()` untuk menegakkan *deterministic order of operations*.

#### Edge Cases
- **Pemberian Alias / Column Labels**: Alias kolom pada `SELECT` kedua atau seterusnya akan diabaikan oleh engine.
  ```sql
  SELECT user_id AS primary_key FROM retail_customers
  UNION ALL
  SELECT client_id AS customer_identity FROM online_customers;
  -- Result set hanya akan memiliki header kolom: "primary_key"
  ```
- **Limit/Pagination**: Penggunaan `LIMIT` tanpa kurung pada cabang query akan membatasi cabang individual atau seluruh hasil tergantung dialek RDBMS.
  ```sql
  -- Standard ANSI: Terapkan LIMIT secara global di tingkat paling luar
  (SELECT email FROM retail_customers)
  UNION ALL
  (SELECT email FROM online_customers)
  ORDER BY email ASC
  LIMIT 20 OFFSET 0;
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Execution Plan**: Buat dua tabel dummy berisi masing-masing 500.000 baris. Jalankan query gabungan menggunakan `UNION` versus `UNION ALL`. Gunakan profiling engine (`EXPLAIN ANALYZE` pada PostgreSQL atau `EXPLAIN FORMAT=TREE` pada MySQL). Bandingkan metrik *Execution Time*, *Memory Usage*, dan ada tidaknya node `Sort` / `HashAggregate`.
2. **Emulasi Operasi Himpunan**: Rancang sebuah query menggunakan `LEFT JOIN` dan predikat `WHERE ... IS NULL` yang menghasilkan *output* set data yang identik secara fungsional dengan operator `EXCEPT`. Uji performa keduanya pada kolom yang bernilai `NULL` untuk melihat konsistensi logika pembanding engine.
