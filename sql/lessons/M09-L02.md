## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Database Trigger adalah mekanisme *event-driven* deklaratif yang dieksekusi secara implisit oleh query execution engine ketika operasi DML (`INSERT`, `UPDATE`, `DELETE`, atau `TRUNCATE`) atau DDL tertentu terjadi pada sebuah tabel atau view. Trigger memungkinkan penegakan integritas data, otomatisasi audit trail, serta sinkronisasi derivatif data langsung pada *data tier* tanpa mengandalkan aplikasi klien.

Secara arsitektural, trigger beroperasi di dalam batasan transaksi (transaction boundary) yang sama dengan query yang memicunya. Jika operasi pemicu dibatalkan (*abort/rollback*), seluruh mutasi data yang dilakukan oleh trigger juga ikut dibatalkan secara atomik.

```
[Client Application] 
       │ 
       ▼ (1. Mengirim SQL Mutation: INSERT/UPDATE/DELETE)
[Query Parser & Optimizer]
       │
       ▼ (2. Rencana Eksekusi / Plan Tree)
[Execution Engine]
       ├──> (3. BEFORE Trigger) ──> Validasi / Transformasi Tuple di Memori
       │         │
       │         ▼
       ├──> (4. Mutasi Disk/Buffer Pool) ──> Penulisan Tuple & Index
       │         │
       │         ▼
       └──> (5. AFTER Trigger)  ──> Audit Log / Perhitungan Agregat / Cascading
                 │
                 ▼
       [Commit / WAL Flush] ──> Sukses, atau Rollback jika ada Exception
```

#### Taksonomi Trigger

1. **Waktu Eksekusi (Timing)**:
   - `BEFORE`: Dieksekusi sebelum data fisik dimutasi ke buffer cache/storage engine. Lazim digunakan untuk sanitasi data, pengisian nilai otomatis (seperti hashing atau timestamping), atau validasi kondisional yang dapat membatalkan transaksi sebelum I/O disk terjadi.
   - `AFTER`: Dieksekusi setelah penulisan data lokal selesai, namun masih dalam transaksi yang sama. Ideal untuk logging audit, memperbarui tabel statistik/materialized, atau mengirim notifikasi via logical channels.
   - `INSTEAD OF`: Khusus digunakan pada database *Views*. Menggantikan query DML standar yang secara inheren tidak dapat diperbarui (*non-updatable view*) dengan logika prosedural kustom.

2. **Granularitas (Granularity)**:
   - `FOR EACH ROW`: Trigger dieksekusi satu kali untuk setiap baris (*tuple*) yang terpengaruh. Memiliki akses ke pseudo-record `OLD` (state sebelum mutasi) dan `NEW` (state setelah mutasi).
   - `FOR EACH STATEMENT`: Trigger dieksekusi tepat satu kali per operasi SQL, terlepas dari apakah query tersebut memodifikasi 0 atau 1.000.000 baris. Menggunakan *Transition Tables* (`OLD TABLE`, `NEW TABLE`) untuk evaluasi bulk data dengan overhead CPU yang jauh lebih rendah.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan sistem inventaris dengan audit trail otomatis dan validasi stok menggunakan dialek **PostgreSQL** (PL/pgSQL).

```sql
-- 1. Setup Skema Tabel
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    stock INT NOT NULL CHECK (stock >= 0),
    price NUMERIC(15, 2) NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE inventory_audit_logs (
    id BIGSERIAL PRIMARY KEY,
    product_id BIGINT NOT NULL,
    operation VARCHAR(10) NOT NULL,
    old_stock INT,
    new_stock INT,
    changed_by VARCHAR(100) DEFAULT CURRENT_USER,
    changed_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 2. Fungsi Trigger: Validasi & Sanitasi Otomatis (BEFORE UPDATE)
CREATE OR REPLACE FUNCTION trg_fn_products_before_update()
RETURNS TRIGGER 
LANGUAGE plpgsql
AS $$
BEGIN
    -- Validasi: Cegah penurunan harga lebih dari 50% dalam satu mutasi
    IF NEW.price < (OLD.price * 0.50) THEN
        RAISE EXCEPTION 'Anomali Harga: Penurunan harga melebihi batas 50%% dari harga lama (Lama: %, Baru: %)', 
            OLD.price, NEW.price
            USING ERRCODE = 'check_violation';
    END IF;

    -- Otomatisasi: Update timestamp ke waktu presisi transaksi saat ini
    NEW.updated_at = CLOCK_TIMESTAMP();

    -- Mengembalikan baris NEW yang telah dimodifikasi ke executor engine
    RETURN NEW;
END;
$$;

-- 3. Fungsi Trigger: Pencatatan Audit Trail (AFTER UPDATE)
CREATE OR REPLACE FUNCTION trg_fn_products_after_update()
RETURNS TRIGGER 
LANGUAGE plpgsql
AS $$
BEGIN
    -- Audit hanya dicatat jika ada perbedaan stok riil
    IF OLD.stock IS DISTINCT FROM NEW.stock THEN
        INSERT INTO inventory_audit_logs (
            product_id, 
            operation, 
            old_stock, 
            new_stock
        ) VALUES (
            NEW.id, 
            TG_OP, 
            OLD.stock, 
            NEW.stock
        );
    END IF;

    RETURN NULL; -- Nilai return diabaikan pada AFTER row trigger
END;
$$;

-- 4. Pendaftaran Trigger ke Tabel
CREATE TRIGGER trg_products_sanitize_and_validate
    BEFORE UPDATE ON products
    FOR EACH ROW
    EXECUTE FUNCTION trg_fn_products_before_update();

CREATE TRIGGER trg_products_audit_stock
    AFTER UPDATE ON products
    FOR EACH ROW
    EXECUTE FUNCTION trg_fn_products_after_update();
```

#### Pengujian Eksekusi

```sql
-- Inisialisasi Data
INSERT INTO products (name, stock, price) VALUES ('Server Rack 42U', 20, 15000000.00);

-- Update Valid (Mengurangi stok)
UPDATE products SET stock = 18 WHERE id = 1;

-- Cek Log Hasil Audit
SELECT product_id, operation, old_stock, new_stock, changed_at FROM inventory_audit_logs;

-- Uji Kasus Invalid: Percobaan menurunkan harga > 50% (Akan gagal dan rollback)
-- Error: Anomali Harga: Penurunan harga melebihi batas 50%...
UPDATE products SET price = 5000000.00 WHERE id = 1;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine
1. **Query Tree Re-writing**: Pada fase rewrite, query engine mendeteksi apakah tabel target memiliki *Trigger List*. Trigger di-cache dalam representasi memori metadata katalog (`pg_trigger` pada PostgreSQL atau `sys.triggers` pada SQL Server).
2. **Context Switching & PL/SQL Engine**: Saat executor mencapai baris yang terpengaruh, query engine menangguhkan eksekusi C-level SQL standar dan melakukan *context switch* ke procedural virtual machine (misalnya runtime PL/pgSQL).
3. **Cascading & Recursion Depth**: Jika trigger memanggil mutasi pada tabel lain yang juga memiliki trigger, engine mengelola *call stack* internal. RDBMS menerapkan batas kedalaman rekursi (misal `max_stack_depth` di PostgreSQL atau opsi `nested triggers` di SQL Server) untuk mencegah *infinite loop* stack overflow.

#### Alokasi Memori & Disk I/O
- **Tuple Buffer**: Pseudo-record `NEW` dan `OLD` tidak disimpan di disk, melainkan berupa pointer ke struktur tuple memori (`HeapTupleData` di RAM). Namun, memodifikasi `NEW` pada trigger `BEFORE` memaksa database membuat salinan fisik tuple baru di memory pool sebelum commit.
- **Write Amplification**: Setiap `INSERT` pada trigger `AFTER` menghasilkan overhead tambahan berupa penulisan log transaksi (*Write-Ahead Logging* / WAL) dan mutasi B-Tree index pada tabel audit.
- **MVCC Dead Tuples**: Pada database berbasis MVCC, modifikasi berulang yang dipicu oleh trigger dapat menghasilkan *dead tuples* dalam jumlah signifikan, mempercepat kebutuhan background worker vacuuming.

#### Trade-offs

| Keuntungan | Konsekuensi Kinerja (Trade-off) |
| :--- | :--- |
| **Integritas Absolut**: Data terjamin konsisten terlepas dari bahasa/framework aplikasi pemanggil. | **Latensi Transaksi Tinggi**: Eksekusi SQL memakan waktu lebih lama karena harus mengeksekusi procedural code sinkron. |
| **Mengurangi Network Roundtrip**: Logika multi-tabel dieksekusi in-memory di host DB yang sama. | **Lock Contention**: Trigger memperpanjang waktu kepemilikan row-lock atau table-lock, meningkatkan potensi deadlock. |
| **Invisible Audit**: Aplikasi tidak perlu mengetahui implementasi logging. | **Hidden Complexity**: Logika bisnis menjadi tersembunyi (*opaque*); menyulitkan debugging, profiling, dan tracing. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Pendekatan Set-Based Jika Memungkinkan**: Jika memproses pembaruan massal (bulk update), pertimbangkan trigger berorientasi *STATEMENT* dengan klausa *transition tables* (`REFERENCING NEW TABLE AS ...`) untuk menghindari overhead transisi row-by-row.
- **Evaluasi Kondisi dengan `WHEN` Clause**:
  Gunakan klausa deklaratif `WHEN` pada definisi trigger agar fungsi trigger tidak dipanggil sama sekali jika kondisinya tidak terpenuhi:
  ```sql
  CREATE TRIGGER trg_audit_stock_filtered
      AFTER UPDATE ON products
      FOR EACH ROW
      WHEN (OLD.stock IS DISTINCT FROM NEW.stock) -- Engine memfilter tanpa switch ke PL/pgSQL
      EXECUTE FUNCTION trg_fn_products_after_update();
  ```
- **Jaga Fungsi Tetap Bersih dan Cepat**: Eksekusi operasi I/O minimum di dalam trigger. Hindari perhitungan rumit yang dapat didelegasikan ke async worker di luar database.

#### Don'ts
- **Dilarang Melakukan External I/O**: Jangan memanggil Webhook/HTTP API atau prosedur soket eksternal dari dalam trigger. Jika jaringan terhambat atau timeout, transaksi database akan menggantung (*hang*) dan mengunci baris data secara masif.
- **Hindari Trigger Mutasi Dua Arah (Circular Mutating)**: Menulis trigger di Tabel A yang mengubah Tabel B, di mana Tabel B memiliki trigger yang mengubah Tabel A. Hal ini menyebabkan crash runtime atau kegagalan isolasi transaksi.
- **Hindari Mengganti Constraints Standar**: Jangan gunakan trigger hanya untuk validasi yang bisa diselesaikan dengan `CHECK`, `NOT NULL`, `UNIQUE`, atau `FOREIGN KEY`. Constraint internal database dikompilasi ke level mesin yang jauh lebih optimal dibanding PL/SQL trigger.

#### Edge Cases
- **Operasi Bulk I/O (`COPY` / `BULK INSERT`)**: Sebagian database menonaktifkan trigger baris secara *default* saat mengimpor data massal melalui utilitas streaming demi throughput, atau sebaliknya: sistem akan kehabisan memori jika ada 5 juta baris yang memicu 5 juta pemanggilan fungsi PL/pgSQL.
- **Penanganan NULL (`IS DISTINCT FROM`)**: Dalam SQL, ekspresi `IF (OLD.val != NEW.val)` bernilai `UNKNOWN` jika salah satu nilainya `NULL`, menyebabkan kondisi dilewati. Selalu gunakan `IS DISTINCT FROM` untuk membandingkan nilai yang nullable.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Soft-Delete Cascade via Trigger**:
   Buat dua tabel: `tenants` dan `tenant_users`. Implementasikan trigger `INSTEAD OF DELETE` atau `BEFORE DELETE` pada `tenants` sehingga alih-alih menghapus baris dari storage, sistem mengubah kolom status `deleted_at = CURRENT_TIMESTAMP` dan secara otomatis memperbarui seluruh baris terkait di `tenant_users` menjadi terhapus secara logis.
2. **Pendeteksi Deadlock Trigger Bersarang**:
   Simulasikan skenario di mana dua transaksi bersamaan memicu pembaruan pada dua tabel (`accounts_a` dan `accounts_b`) dalam urutan terbalik di dalam trigger. Amati bagaimana database melempar error deadlock detection (`40P01` di PG) dan selidiki cara restrukturisasi query agar thread safe.
