## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur komputasi modern, data tidak terstruktur (teks, audio, gambar) direpresentasikan secara matematis sebagai **vektor embedding** (serangkaian angka *floating-point* berdimensi tinggi, misalnya 768 atau 1536 dimensi). Model machine learning seperti BERT, OpenAI `text-embedding-3`, atau Cohere memetakan kedekatan semantik data ke dalam ruang vektor (*vector space*): konsep yang maknanya mirip akan memiliki jarak koordinat yang berdekatan.

```
       [Dimensi Y]
           ▲
           │         (Panci) •  • (Wajan)  <- Cluster: Peralatan Dapur
           │
           │
           │  (Kucing) •
           │          \
           │           • (Anjing)  <- Cluster: Hewan Peliharaan
───────────┼────────────────────────► [Dimensi X]
           │
```

#### Mengapa SQL dan Relational Database Membutuhkan Dukungan Vektor?
Awalnya, pencarian kemiripan vektor membutuhkan database khusus (*standalone vector databases* seperti Pinecone atau Milvus). Namun, pendekatan ini menimbulkan masalah arsitektur baru:
1. **Dual-system synchronization:** Mengakibatkan inkonsistensi data antara database transaksional (RDBMS) dan database vektor.
2. **Kompleksitas ACID & Security:** Standalone vector DB umumnya memiliki kontrol akses (RBAC), backup/restore, dan integritas referensial yang lebih lemah dibanding RDBMS kelas industri.

Ekstensi seperti `pgvector` pada PostgreSQL mentransformasi RDBMS menjadi mesin pencari vektor hibrida. Anda dapat mengeksekusi pencarian kemiripan vektor (*vector similarity search*) sembari memanfaatkan kapabilitas relasional: filter `WHERE`, relasi `JOIN`, transaksi `ACID`, dan kontrol konkurensi `MVCC` dalam satu kueri atomic.

#### RAG (Retrieval-Augmented Generation) Architecture
LLM memiliki dua kelemahan mendasar: batas jendela konteks (*context window*) dan risiko halusinasi (*knowledge cutoff* / ketiadaan data privat). RAG memecahkan masalah ini dengan skema tiga langkah:
1. **Retrieve:** Kueri dari user diubah menjadi embedding, lalu dicari $k$ dokumen yang paling relevan secara semantik di database vektor.
2. **Augment:** Potongan teks (*chunks*) dari dokumen hasil pencarian disuntikkan ke dalam *prompt* LLM sebagai konteks rujukan.
3. **Generate:** LLM menghasilkan jawaban yang berpijak secara faktual pada konteks tersebut.

```
+------------+       Embedding        +-----------------------+
| User Query | ---------------------> | Vector Database (SQL) |
+------------+                        +-----------------------+
      |                                           |
      |                               Top-k Semantic Chunks
      v                                           v
+-------------------------------------------------------------+
| Prompt Template: Context + User Query                       |
+-------------------------------------------------------------+
      |
      v
+------------+
|    LLM     | ---------------------> Final Synthesized Answer
+------------+
```

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan sistem penyimpanan basis pengetahuan RAG enterprise menggunakan **PostgreSQL** dan ekstensi **`pgvector`**.

```sql
-- 1. Inisialisasi ekstensi pgvector
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Definisi Schema Dokumen RAG Enterprise
-- Menggunakan dimensi 1536 (standar OpenAI text-embedding-3-small)
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    category VARCHAR(64) NOT NULL,
    metadata JSONB DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    document_id BIGINT REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index INT NOT NULL,
    chunk_content TEXT NOT NULL,
    -- Definisi kolom vektor 1536 dimensi (32-bit floating point)
    embedding vector(1536) NOT NULL,
    CONSTRAINT uq_doc_chunk UNIQUE(document_id, chunk_index)
);

-- 3. Membuat Indeks Pencarian Vektor: HNSW (Hierarchical Navigable Small World)
-- Menggunakan metrik Cosine Distance (vector_cosine_ops)
CREATE INDEX idx_document_chunks_embedding_hnsw 
ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Indeks komplementer untuk Hybrid Filtering
CREATE INDEX idx_documents_category ON documents(category);
CREATE INDEX idx_documents_metadata_gin ON documents USING gin(metadata);

-- 4. Simulasi Seed Data
INSERT INTO documents (id, title, category, metadata) VALUES 
(1, 'SOP Keamanan Jaringan', 'IT_OPS', '{"access_level": "internal", "version": 2}'),
(2, 'Kebijakan Cuti Karyawan', 'HR', '{"access_level": "public", "version": 1}');

-- Insert chunk dengan dummy vektor 1536 dimensi (direpresentasikan singkat di sini)
-- Operator '...' menggambarkan float[] dengan 1536 elemen
INSERT INTO document_chunks (document_id, chunk_index, chunk_content, embedding) VALUES
(1, 0, 'Autentikasi SSH wajib menggunakan public-key ed25519 dan port non-standar.', array_fill(0.0125, ARRAY[1536])::vector),
(1, 1, 'Firewall harus memblokir seluruh koneksi ingress secara default.', array_fill(0.0210, ARRAY[1536])::vector),
(2, 0, 'Karyawan tetap berhak atas 12 hari cuti tahunan setelah 1 tahun masa kerja.', array_fill(0.0899, ARRAY[1536])::vector);

-- 5. Kueri RAG: Hybrid Search (Semantic + Relational Filtering)
-- Mengambil 2 chunk teks paling relevan untuk departemen IT_OPS
-- Metrik: Cosine Distance (<=>), Semakin kecil nilainya, semakin mirip
EXPLAIN ANALYZE
SELECT 
    d.title,
    d.category,
    dc.chunk_index,
    dc.chunk_content,
    1 - (dc.embedding <=> array_fill(0.0120, ARRAY[1536])::vector) AS cosine_similarity
FROM document_chunks dc
JOIN documents d ON dc.document_id = d.id
WHERE d.category = 'IT_OPS'
  AND (d.metadata->>'access_level') IN ('internal', 'public')
ORDER BY dc.embedding <=> array_fill(0.0120, ARRAY[1536])::vector ASC
LIMIT 2;
```

#### Penjelasan Operasi Penting:
* **Operator Jarak:**
  * `<=>` : Cosine Distance ($1 - \text{Cosine Similarity}$). Bernilai `0` jika identik, `2` jika berlawanan arah.
  * `<->` : Euclidean / L2 Distance. Mengukur jarak absolut garis lurus antar titik.
  * `<#>` : Negative Inner Product. Sangat efisien jika vektor sudah dinormalisasi ($||x|| = 1$).
* **Struktur HNSW:** Menentukan parameter `m` (maksimum koneksi dua arah per node, default 16) dan `ef_construction` (kedalaman evaluasi saat *build index*, default 64). Nilai lebih tinggi meningkatkan *recall* dengan kompromi kecepatan *build* dan konsumsi RAM.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Algoritma Indexing: IVFFlat vs HNSW
Pencarian eksak (Exact k-NN via *Sequential Scan*) memiliki kompleksitas $O(N \cdot D)$ di mana $N$ adalah jumlah baris dan $D$ adalah dimensi. Pada $N > 100.000$, kueri menjadi sangat lambat. Mesin vektor menggunakan algoritma **Approximate Nearest Neighbor (ANN)**:

```
[IVFFlat: Voronoi Partitioning]          [HNSW: Multi-Layer Proximity Graph]
       .  *  .  |  .  *  .                     Layer 2:  O ───────────► O
       .  Centroid 1  .                        Layer 1:  O ────► O ────► O
   -------------+-------------                 Layer 0:  O ─► O ─► O ─► O ─► O
       .  *  .  |  .  *  .                     (Skip-list probabilistic multidimensi)
       .  Centroid 2  .
```

1. **IVFFlat (Inverted File Flat):**
   * Membagi ruang vektor menjadi beberapa klaster berbasis partisi Voronoi menggunakan $k$-means *clustering*.
   * Mengelompokkan vektor ke dalam *inverted lists* (titik-titik di sekitar *centroid*).
   * Kueri hanya memindai vektor dalam daftar klaster terdekat (`probes`).
   * **Karakteristik:** Memori rendah, kecepatan pembentukan indeks tinggi, namun *recall* rentan terdegradasi jika data baru tidak terdistribusi merata dengan centroid lama.

2. **HNSW (Hierarchical Navigable Small World):**
   * Membangun graf multi-layer yang terinspirasi dari struktur data *Skip-List*.
   * Layer teratas memiliki lompatan jarak jauh (koneksi jarang) untuk *routing* cepat, layer dasar (Layer 0) menyimpan seluruh data dengan koneksi rapat.
   * Pencarian dimulai dari layer teratas dan turun bertahap (*greedy routing*).
   * **Karakteristik:** Latensi kueri sangat rendah ($O(\log N)$), *recall* sangat tinggi (>98%), namun konsumsi memori (RAM) sangat masif.

#### Alokasi Memori dan Resource
Tiap vektor dimensi 1536 dengan presisi `float4` (32-bit) membutuhkan:
$$\text{Ukuran} = 1536 \times 4\text{ bytes} = 6.144\text{ bytes} \approx 6\text{ KB per record}$$
Untuk 1 juta baris data chunk:
* **Ukuran Raw Data:** $\approx 6\text{ GB}$.
* **Ukuran Index HNSW:** Menambahkan *overhead* pointers graf sebesar $\approx 1.5\times$ hingga $2\times$ dari data vektor murni ($\approx 9\text{ GB - } 12\text{ GB}$).
* Jika HNSW index tidak muat di dalam `shared_buffers` atau cache RAM OS (*page cache*), operasi I/O disk acak (*random disk reads*) akan melonjak dan meningkatkan latensi dari level sub-milidetik ke puluhan milidetik.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Normalisasi Vektor:** Jika model embedding menghasilkan vektor ternormalisasi (misal panjang unit = 1), gunakan **Inner Product (`<#>`)** alih-alih Cosine (`<=>`). Operasi dot-product secara matematis identik dengan cosine pada unit vector, tetapi mengeliminasi pembagian *magnitude* (menghindari operasi `sqrt`), menghemat siklus CPU.
* **Warm up Index di RAM:** Gunakan `pg_prewarm` untuk memastikan indeks HNSW dimuat sepenuhnya ke RAM sebelum melayani *traffic* produksi.
  ```sql
  SELECT pg_prewarm('idx_document_chunks_embedding_hnsw');
  ```
* **Tuning `hnsw.ef_search`:** Secara runtime, ubah kedalaman traversal HNSW sesuai trade-off yang diinginkan:
  ```sql
  SET hnsw.ef_search = 100; -- Default 40. Nilai tinggi = recall lebih baik, latensi naik.
  ```

#### Don'ts
* **Membangun IVFFlat Sebelum Data Terkumpul:** IVFFlat mengharuskan data sampel ada di tabel untuk menghitung centroid yang akurat. Jika membuat indeks IVFFlat pada tabel kosong kemudian mengisinya dengan jutaan baris, centroid menjadi bias, menyebabkan *recall drop* drastis.
* **Over-chunking vs Under-chunking:** Membagi dokumen terlalu kecil (misal: 50 karakter) menghilangkan konteks semantik. Membagi dokumen terlalu besar (misal: 4000 token) mengaburkan sinyal pencarian (vektor menjadi terlalu representatif secara general sehingga kemiripan lokal hilang).
* **Menyimpan Blob Besar di Tabel Indeks Vektor:** Pisahkan teks konten chunk yang sangat panjang atau metadata biner ke tabel terpisah jika memungkinkan, atau pastikan PostgreSQL memindahkannya ke sistem penyimpanan TOAST secara efisien agar *page buffer* utama tetap padat (*cache-friendly*).

#### Edge Cases
* **Zero Vectors:** Vektor dengan nilai nol di semua koordinat (`[0.0, 0.0, ...]`) akan memicu error `division by zero` saat dievaluasi menggunakan Cosine Similarity. Selalu validasi data sebelum `INSERT`.
* **Kombinasi Filter Sangat Selektif + ANN Index:** PostgreSQL Planner terkadang memilih *Seq Scan* dibanding *HNSW Index Scan* jika filter atribut relasional (`WHERE category = '...'`) menghasilkan estimasi selektivitas yang sangat kecil. Solusinya: gunakan *Iterative Index Scan* (`pgvector 0.7.0+`) yang secara cerdas menavigasi graf sembari mengevaluasi filter predikat.

### 5. Tantangan Eksplorasi Mandiri

1. **Reranking & Multi-Stage Retrieval:**
   Rancang skema kueri di mana Anda mengambil $k = 50$ dokumen awal menggunakan Cosine Distance via indeks HNSW, lalu gunakan *scoring function* khusus (kombinasi nilai cosine similarity, recency/umur dokumen berdasarkan `created_at`, dan popularitas dokumen) untuk menyaringnya menjadi Top-5 dokumen final langsung dalam level SQL query.

2. **Analisis Memory vs Recall:**
   Buat tabel dengan 10.000 vektor sintetis berdimensi 768. Buat dua indeks: satu IVFFlat (`lists = 100`) dan satu HNSW (`m = 16, ef_construction = 64`). Bandingkan:
   * Ukuran fisik indeks pada disk menggunakan `pg_relation_size()`.
   * Perbedaan output Top-10 teratas antara kueri tanpa indeks (*Exact Scan* sebagai ground truth) melawan IVFFlat dan HNSW untuk mengukur *Recall Rate* ($Recall = \frac{|\text{Retrieved} \cap \text{Ground Truth}|}{|\text{Ground Truth}|}$).
