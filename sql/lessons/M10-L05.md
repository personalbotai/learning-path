### 1. Konsep & Arsitektur Mendalam

Ledakan adopsi *Large Language Models* (LLM) memperkenalkan kebutuhan penyimpanan dan pencarian representasi semantik dalam bentuk array floating-point berdimensi tinggi (*embeddings*). Pendekatan tradisional memisahkan data relasional (PostgreSQL/SQLite) dengan *Vector Database* khusus (seperti Pinecone, Milvus, Qdrant). Namun, arsitektur *dual-database* ini memicu kompleksitas sinkronisasi data, tantangan konsistensi eventual (ACID terdistribusi), serta latensi jaringan ganda.

Ekstensi seperti **`pgvector`** (untuk PostgreSQL) dan **`sqlite-vec`** (arsitektur modular C untuk SQLite) menyelesaikan problem ini dengan menjadikan tipe data vektor sebagai warga kelas satu (*first-class citizen*) di dalam mesin basis data relasional.

```

|                                                             |
```

#### Metrik Jarak Matematis
Dalam pencarian kemiripan vektor (*Vector Similarity Search*), kedekatan semantik dihitung menggunakan metrik aljabar linier:
1. **L2 Distance / Euclidean Distance ($\|\mathbf{u} - \mathbf{v}\|$):** Menghitung jarak absolut antara dua titik. Menggunakan operator `<->` di `pgvector`.
2. **Inner Product / Dot Product ($\mathbf{u} \cdot \mathbf{v}$):** Mengukur magnitudo dan arah. Sangat cepat pada vektor yang sudah dinormalisasi (*unit vectors*). Menggunakan operator `<#>`.
3. **Cosine Distance ($1 - \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|}$):** Mengukur perbedaan sudut tanpa mempedulikan panjang vektor. Menggunakan operator `<=>`.

#### Algoritma Indexing: IVFFlat vs HNSW
Pencarian *exact nearest neighbor* (k-NN) membutuhkan pemindaian sekuensial penuh (*Sequential Scan*) berbiaya $O(N \cdot d)$ di mana $N$ adalah jumlah baris dan $d$ adalah dimensi. Untuk skala besar, digunakan *Approximate Nearest Neighbor* (ANN):

- **IVFFlat (Inverted File Flat):** Membagi ruang vektor ke dalam klaster-klaster menggunakan k-means (*Voronoi cells*). Pencarian hanya memeriksa subset klaster terdekat.
  - *Pros:* Waktu *build* cepat, konsumsi memori/disk relatif rendah.
  - *Cons:* Mengharuskan data sudah terisi saat index dibuat (agar penentuan centroid optimal); memiliki *recall* yang lebih rendah dibanding HNSW.
- **HNSW (Hierarchical Navigable Small World):** Membangun grafik multi-layer di mana layer paling atas memiliki lompatan jaringan yang panjang (*skip-list property*), dan layer bawah memiliki konektivitas granular.
  - *Pros:* *Recall* sangat tinggi, latensi query ultra-rendah ($O(\log N)$).
  - *Cons:* Konsumsi RAM sangat tinggi, waktu pembuatan indeks (*build time*) signifikan lebih lambat.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi hybrid-search (menggabungkan filtering relasional dengan pencarian kemiripan vektor) pada PostgreSQL menggunakan `pgvector`.

#### PostgreSQL + pgvector

```sql
-- 1. Mengaktifkan ekstensi pgvector di PostgreSQL
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Buat tabel dokumen dengan embedding 1536-dimensi (standar OpenAI text-embedding-3-small)
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    tenant_id UUID NOT NULL,
    category VARCHAR(64) NOT NULL,
    content TEXT NOT NULL,
    -- Definisi kolom vektor dengan 1536 dimensi
    embedding VECTOR(1536) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 3. B-Tree Index untuk metadata filtering
CREATE INDEX idx_documents_tenant_cat ON documents(tenant_id, category);

-- 4. Membuat HNSW Index pada kolom embedding
-- m: jumlah maksimum edge per node (khas: 16-64).
-- ef_construction: ukuran dynamic candidate list saat build (khas: 64-200).
CREATE INDEX idx_documents_embedding_hnsw ON documents 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 128);

-- 5. Query Hybrid: Pre-filtering relational + Vector Similarity
-- Mengatur ef_search per-koneksi: trade-off antara akurasi vs latency
SET hnsw.ef_search = 100;

EXPLAIN ANALYZE
SELECT 
    id, 
    content, 
    -- Menghitung skor kemiripan kosinus (1 - Cosine Distance)
    1 - (embedding <=> '[0.012, -0.043, ..., 0.089]'::vector) AS similarity_score
FROM documents
WHERE tenant_id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'
  AND category = 'finance'
ORDER BY embedding <=> '[0.012, -0.043, ..., 0.089]'::vector ASC
LIMIT 5;
```

#### SQLite + sqlite-vec (Alternatif Edge / Embedded)

Untuk skenario edge seperti desktop app atau local inference, `sqlite-vec` (penerus `sqlite-vss`) menggunakan Virtual Table:

```sql
-- Load ekstensi runtime (tergantung platform, misal: .load ./vec0)
-- CREATE VIRTUAL TABLE menggunakan modul vec0
CREATE VIRTUAL TABLE document_vectors USING vec0(
    document_id INTEGER PRIMARY KEY,
    embedding float[768] distance_metric=cosine
);

-- Query pencarian top-K
SELECT 
    document_id,
    distance
FROM document_vectors
WHERE embedding MATCH '[0.021, 0.081, ..., -0.014]'
  AND k = 5;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & SIMD Acceleration
Saat membandingkan vektor di tingkat CPU, operasi produk dot dan jarak Euclidean diiterasi ribuan kali per tuple. `pgvector` dan `sqlite-vec` mengimplementasikan kompilasi berbasis **SIMD (Single Instruction, Multiple Data)** seperti **AVX2**, **AVX-512** pada arsitektur x86_64, serta **ARM NEON**.
- Instruksi seperti `_mm256_fmadd_ps` melakukan operasi perkalian dan penjumlahan akumulatif (FMA) 8 elemen *float32* sekaligus dalam satu siklus clock CPU.
- Tanpa SIMD, perhitungan jarak 1536-dimensi memerlukan $1536 \times 2$ instruksi register CPU skalar per baris.

#### Alokasi Memori & Page Layout
- Di PostgreSQL, nilai `VECTOR` disimpan sebagai tipe data `varlena` (tipe data panjang variabel). Nilai vektor disimpan secara inline di dalam heap page jika ukurannya $\le 2\text{ KB}$. Jika melebihi batas TOAST (seperti vektor dimensi 1536 yang memakan $\approx 6\text{ KB}$ raw data), data akan dipecah dan dipindahkan ke tabel **TOAST**, yang dapat memicu overhead I/O tambahan saat *sequential scan*.
- Indeks HNSW tidak disimpan di TOAST melainkan di buffer terpisah yang terdistribusi ke dalam halaman-halaman indeks PostgreSQL biasa (8 KB page standard). Indeks ini harus muat sepenuhnya di dalam `shared_buffers` atau OS page cache RAM. Jika ukuran file indeks HNSW melebihi alokasi RAM, traversal graf akan mengalami bottleneck *disk random read* yang melumpuhkan performa transaksi.

#### Trade-offs: Algoritma vs Biaya Komputasi
| Parameter | Sequential Scan (Flat) | IVFFlat | HNSW |
| :--- | :--- | :--- | :--- |
| **Recall / Akurasi** | 100% (Exact) | 80% - 95% (Approximate) | 95% - 99.9% (Approximate) |
| **Kecepatan Query** | Sangat Lambat ($O(N)$) | Cepat (Tergantung `probes`) | Sangat Cepat ($O(\log N)$) |
| **Waktu Build** | Tidak ada | Relatif Cepat | Sangat Lambat (CPU-intensive) |
| **Konsumsi RAM/Disk** | Minimum | Rendah ($O(N)$) | Sangat Tinggi (Struktur Graf) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Normalisasi Vektor Secara Eksternal:** Jika menggunakan Cosine Similarity, normalisasikan vektor ke *unit length* ($\|v\| = 1$) di level aplikasi (misal menggunakan Python/Go) sebelum disimpan. Gunakan metrik **Inner Product (`<#>`)** alih-alih Cosine (`<=>`). Operasi Inner Product pada vektor yang ternormalisasi setara secara matematis dengan Cosine Distance, tetapi mengeliminasi operasi pembagian dan akar kuadrat ($\sqrt{\sum x^2}$) per komparasi di CPU.
- **Konfigurasi Memory Maintenance yang Agresif:** Saat membuat indeks HNSW, naikkan alokasi memori kerja untuk proses tersebut:
  ```sql
  SET maintenance_work_mem = '2GB';
  SET max_parallel_maintenance_workers = 4;
  ```
- **Filter Berbobot dengan Index Gabungan:** Untuk PostgreSQL 16+, pertahankan B-Tree pada kolom penapis relasional (`tenant_id`, `status`) agar query engine dapat mengeksekusi *Iterative Index Scans* untuk memangkas pencarian HNSW lebih awal.

#### Don'ts
- **Membangun IVFFlat pada Tabel Kosong:** IVFFlat memerlukan data sampel representatif untuk mengalkulasi *k-means centroids*. Membangun IVFFlat saat tabel kosong atau hanya berisi sedikit data akan membuat centroid terkonsentrasi tidak merata, menghasilkan *recall* yang hancur saat data bertambah masif.
- **Mengabaikan TOAST Overhead:** Jangan lakukan `SELECT *` saat memproses vektor berdimensi tinggi. Membaca kolom vektor yang tersimpan di TOAST tabel secara berulang akan menyebabkan *cache thrashing* pada sistem buffer PostgreSQL.

#### Edge Cases
- **Zero Vector:** Masuknya vektor dengan semua elemen nol ($[0.0, 0.0, ...]$) akan menghasilkan nilai `NaN` (*Not a Number*) saat dihitung menggunakan *Cosine Similarity* karena terjadinya pembagian dengan nol ($\|\mathbf{0}\| = 0$). Lakukan validasi `CHECK (embedding <=> '[0,0,...]' != 0)` atau cegah di API gateway.
- **Efek "Curse of Dimensionality" pada IVFFlat:** Pada vektor dimensi $>2000$, pembagian ruang sel Voronoi menjadi tidak efektif karena jarak antar titik menjadi nyaris seragam (*distance concentration effect*). Gunakan HNSW untuk dimensi sangat tinggi.

### 5. Tantangan Eksplorasi Mandiri

1. **Benchmarking Metrik Jarak:**
   Buat sebuah tabel dengan 100.000 baris data dummy vektor acak berdimensi 768. Bandingkan latensi eksekusi dan throughput I/O antara metrik jarak Euclidean (`<->`), Inner Product (`<#>`), dan Cosine (`<=>`) saat dilakukan *sequential scan* (`SET enable_indexscan = OFF;`).
2. **Eksperimen Tuning Parameter HNSW:**
   Buat indeks HNSW dengan parameter $(m=8, ef\_construction=64)$ dan indeks lain dengan $(m=32, ef\_construction=256)$. Ukur perbedaan ukuran disk (`pg_relation_size`), durasi pembuatan indeks, serta ukur persentase perbedaan hasil (Recall Drop) pada top-10 result dengan membandingkannya terhadap Sequential Exact Search.
3. **Optimasi Hybrid Query Execution Plan:**
   Buat query yang mencari 10 vektor terdekat dengan klausa `WHERE tenant_id = '...'`. Amati output `EXPLAIN (ANALYZE, BUFFERS)`. Identifikasi kapan query planner memilih *Bitmap Index Scan* vs *HNSW Index Scan*, dan uji bagaimana perubahan nilai `hnsw.ef_search` mempengaruhi pergerakan *Buffer Shared Hit* vs *Read*.
