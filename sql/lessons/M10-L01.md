## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur data modern, beban kerja (*workload*) pemrosesan basis data dibagi menjadi tiga paradigma utama: **OLTP** (*Online Transaction Processing*), **OLAP** (*Online Analytical Processing*), dan konvergensi keduanya, **HTAP** (*Hybrid Transactional/Analytical Processing*). Pemisahan ini lahir karena pertentangan mendasar antara kebutuhan latensi transaksi rendah vs *throughput* agregasi data bervolume besar.

```
       [ Client Applications ]                     [ BI / Data Analysts ]
                  │                                           ▲
       (Writes / Point Reads)                        (Complex Queries)
                  │                                           │
                  ▼                                           │
        ┌──────────────────┐     ETL / CDC         ┌──────────────────┐
        │   OLTP Engine    │ ════════════════════> │   OLAP Engine    │
        │ (Row-Store: B-Tree)                      │(Columnar: Parquet)
        └──────────────────┘                       └──────────────────┘
                  ▲                                           ▲
                  │                                           │
                  └───────────────┬───────────────────────────┘
                                  │
                          [ HTAP Systems ]
                  (Dual Engine: In-Memory / Vectorized)
                  (e.g., TiDB, AlloyDB, ClickHouse chDB)
```

#### OLTP (Online Transaction Processing)
- **Tujuan**: Menangani operasi atomik tingkat baris (*point reads/writes*) secara konkuren dengan latensi rendah (<10ms).
- **Karakteristik Data**: Data ternormalisasi (3NF) untuk mencegah redundansi, ukuran data per transaksi kecil, didominasi instruksi `INSERT`, `UPDATE`, `DELETE`, dan `SELECT` berbasis *primary key*.
- **Penyimpanan (Row-Oriented)**: Menggunakan struktur berbasis baris (contoh: *B-Tree index* pada PostgreSQL Heap Table atau MySQL InnoDB Clustered Index). Seluruh nilai atribut dari sebuah baris disimpan berurutan secara fisik di disk/buffer page.

#### OLAP (Online Analytical Processing)
- **Tujuan**: Menjalankan kueri analitik kompleks yang memindai jutaan hingga miliaran baris (*deep scans*, *aggregations*, *joins*) untuk kebutuhan agregasi dan *business intelligence*.
- **Karakteristik Data**: Denormalisasi (Star/Snowflake Schema), data bersifat historis, *immutable* atau *append-only*, didominasi instruksi `SELECT ... GROUP BY`, `AVG`, `SUM`.
- **Penyimpanan (Column-Oriented)**: Data disimpan per kolom (contoh: ClickHouse, DuckDB, AWS Redshift, Apache Parquet). Blok memori hanya berisi entri dari kolom yang sama, memungkinkan kompresi ekstrem (Dictionary, Run-Length Encoding) dan eksekusi SIMD (*Single Instruction, Multiple Data*).

#### HTAP (Hybrid Transactional/Analytical Processing)
- **Tujuan**: Menghilangkan latensi pipeline ETL tradisional dengan mengeksekusi analitik langsung pada data transaksional terkini secara *real-time* tanpa mengorbankan performa OLTP.
- **Arsitektur**: Menggunakan dual-format storage engine (misalnya TiDB dengan TiKV untuk row-store + TiFlash untuk columnar-store melalui Raft learner) atau log-structured multi-version engines dengan in-memory vectorized execution.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah perbandingan skema dan perilaku eksekusi kueri pada OLTP (PostgreSQL) vs OLAP (ClickHouse / DuckDB) untuk domain *e-commerce*.

#### Kasus A: Skema OLTP (Row-Oriented, Ternormalisasi)
Optimal untuk integritas relasional dan penulisan konkuren berbasis transaksi ACID:

```sql
-- DDL OLTP: Mengutamakan relasi dan constraint integritas
CREATE TABLE customers (
    customer_id BIGSERIAL PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(customer_id),
    order_date DATE NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(32) NOT NULL
);

-- Transaksi OLTP khas: Menulis satu baris pesanan secara atomik
BEGIN;
INSERT INTO orders (customer_id, order_date, total_amount, status)
VALUES (4291, CURRENT_DATE, 1500000.00, 'PROCESSING');
COMMIT;

-- Kueri Operasional OLTP: Eksekusi berbasis Index Scan (O(log N))
SELECT order_id, total_amount, status 
FROM orders 
WHERE customer_id = 4291 
ORDER BY order_date DESC 
LIMIT 5;
```

#### Kasus B: Skema OLAP (Column-Oriented, Denormalisasi)
Optimal untuk pemindaian agregasi besar (*bulk scan*) melintasi rentang waktu luas:

```sql
-- DDL OLAP (Dialek ClickHouse): Engine berbasis Kolom
CREATE TABLE analytics.fact_orders (
    order_id UInt64,
    customer_id UInt64,
    order_date Date,
    total_amount Decimal64(2),
    status LowCardinality(String),
    customer_country LowCardinality(String)
) 
ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (order_date, customer_country, customer_id);

-- Kueri Analitik OLAP: Agregasi jutaan data secara paralel
-- Engine hanya membaca kolom: 'order_date', 'customer_country', dan 'total_amount'
SELECT 
    order_date,
    customer_country,
    COUNT(order_id) AS total_orders,
    SUM(total_amount) AS revenue,
    AVG(total_amount) AS aov
FROM analytics.fact_orders
WHERE order_date BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY order_date, customer_country
ORDER BY revenue DESC;
```

#### Kasus C: Pendekatan HTAP (Contoh Virtual Columnar / Dynamic Routing)
Pada engine HTAP seperti TiDB/AlloyDB, SQL Optimizer menentukan eksekusi berdasarkan profil kueri:

```sql
-- Query Optimizer secara dinamis membaca dari Row-Store (TiKV) jika cost rendah:
SELECT * FROM orders WHERE order_id = 9812401;

-- Query yang sama dialihkan otomatis ke Column-Engine (TiFlash) tanpa campur tangan aplikasi:
SELECT 
    status, 
    COUNT(*) AS volume, 
    SUM(total_amount) AS total_metric
FROM orders
WHERE order_date >= '2024-01-01'
GROUP BY status;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Row-Store (OLTP)**: Mengadopsi *Volcano Iterator Model* (metode `next()`). Setiap baris diproses secara independen melewati serangkaian operator relasional. Pemrosesan per-baris ini menghasilkan *instruction cache misses* yang tinggi pada CPU saat menangani jutaan baris data, tetapi sangat cepat untuk mengambil *tuple* lengkap dalam satu *page*.
- **Column-Store (OLAP)**: Menggunakan *Vectorized Execution* (Block-oriented processing). Tuple dikelompokkan ke dalam *vectors* (biasanya array 1024-4096 nilai per kolom). CPU mengeksekusi instruksi perulangan sederhana yang dapat dioptimasi oleh *compiler* menggunakan register SIMD (AVX-512). Hal ini mengurangi *virtual function calls* hingga 90%.

#### Alokasi Memori / Resource
- **I/O Disk & Buffer Cache**:
  - Kueri OLAP yang meminta `SUM(total_amount)` pada Row-Store harus memuat seluruh blok data yang berisi kolom `customer_id`, `email`, `address`, dll., ke dalam *buffer pool*. Ini membuang *memory bandwidth* untuk data yang tidak dihitung.
  - Column-Store hanya memuat *chunk* disk milik kolom `total_amount`. Kolom lain sama sekali tidak diakses dari disk.
- **Rasio Kompresi**:
  - Data dalam kolom memiliki tipe data serupa dan sering kali berisi data berulang. Column-store mampu menerapkan *PFOR-DELTA*, *Bit-Packing*, dan *Dictionary Encoding*, menghasilkan rasio kompresi 5x-10x lebih tinggi dibanding Row-Store.

```
Penyimpanan Row-Store (Page 8KB - Baris demi Baris):
[ID:1 | User:A | Val:100][ID:2 | User:B | Val:200][ID:3 | User:C | Val:300]
--> Untuk menghitung rata-rata 'Val', semua 'User' dan 'ID' tetap harus masuk RAM.

Penyimpanan Column-Store (Chunk Kolom Terpisah):
Page 1 (ID)  : [1, 2, 3]
Page 2 (User): [A, B, C]
Page 3 (Val) : [100, 200, 300] --> Hanya Page 3 yang dibaca ke RAM (I/O Minimal).
```

#### Trade-offs
| Parameter | OLTP | OLAP | HTAP |
| :--- | :--- | :--- | :--- |
| **Storage Layout** | Row-oriented | Column-oriented | Dual (Row + Column) |
| **Write Cost** | Murah (O(1) append/in-place edit) | Sangat mahal (Batch/Append-only) | Moderat (Replikasi asinkron internal) |
| **Read Profile** | Index-driven point lookups | Massive sequential scans | Campuran fleksibel |
| **Latensi Kueri** | Sub-milidetik hingga milidetik | Detik hingga menit | Puluhan milidetik |
| **CPU Overhead** | Terikat Concurrency/Locking | Terikat Memory/Vector Compute | Tinggi (Resource governance kompleks) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Read-Replica atau ELT Pipeline**: Jangan jalankan kueri analitik berat langsung di database OLTP produksi. Buat *CDC pipeline* (Change Data Capture) via Debezium/Kafka ke data warehouse OLAP.
- **Terapkan Batch Insertion di OLAP**: Tulis data ke OLAP dalam ukuran besar (kelipatan 10.000 hingga 100.000 baris). Penulisan baris per baris (*micro-writes*) akan menghancurkan performa LSM-tree atau merge-tree pada OLAP.
- **Normalisasi di OLTP, Denormalisasi di OLAP**: Kurangi operasi `JOIN` di OLAP engine dengan mempersiapkan *wide-tables* atau star schema untuk memanfaatkan efisiensi columnar scan.

#### Don'ts
- **Membuat Index Berlebih di OLTP**: Setiap indeks memperlambat throughput `INSERT` dan `UPDATE` karena write-amplification pada struktur B-Tree.
- **Menggunakan `SELECT *` pada OLAP Engine**: Ini merusak keunggulan utama arsitektur columnar, karena memaksa engine memuat seluruh kolom dari disk ke memori.
- **Mengandalkan HTAP untuk Analitik Skala Petabyte**: HTAP optimal untuk *operational intelligence* (analitik data beberapa jam/hari terakhir). Untuk analitik data historis skala sangat masif, OLAP murni (Snowflake, BigQuery, ClickHouse) tetap menjadi pilihan yang lebih stabil dan hemat biaya.

#### Edge Cases
- **Transaksionalitas pada HTAP**: Dalam sistem HTAP terdistribusi, replikasi data dari row-store ke columnar-store sering kali terjadi secara *asynchronous* (via Raft/Log shipping). Kueri analitik pada column-store mungkin mengalami *replication lag* beberapa milidetik hingga detik (eventual consistency), kecuali Anda mengaktifkan mode *strong consistency* (Read Index) yang akan meningkatkan latensi.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Profil I/O**: Menggunakan PostgreSQL, buat tabel dengan 10 kolom dan 1.000.000 baris dummy. Jalankan `EXPLAIN (ANALYZE, BUFFERS) SELECT AVG(col_10) FROM table;`. Amati berapa banyak *shared hit/read blocks* yang dikonsumsi, lalu bandingkan rasio efisiensi I/O tersebut jika kueri yang sama dieksekusi pada engine kolom seperti DuckDB terhadap file Parquet dari data yang sama.
2. **Simulasi Write Amplification**: Coba lakukan *single-row insertion* sebanyak 10.000 kali secara berurutan menggunakan loop transaksi tunggal pada database OLAP (misalnya ClickHouse atau DuckDB) dan catat *throughput*-nya. Bandingkan ketika 10.000 baris tersebut dimasukkan dalam satu perintah *batch insert* (`INSERT INTO table VALUES (...), (...);`). Identifikasi mengapa perbedaannya bisa mencapai ribuan kali lipat.
