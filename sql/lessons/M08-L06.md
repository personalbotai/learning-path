## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

**SARGable** merupakan akronim dari *Search ARGument ABLE*. Dalam perancangan query basis data relasional, sebuah predikat (kondisi pada klausa `WHERE`, `JOIN ON`, atau `HAVING`) dikatakan SARGable jika *Query Optimizer* dapat memanfaatkan struktur indeks—khususnya B+Tree—secara langsung untuk melakukan operasi **Index Seek** (pencarian biner $O(\log N)$ dari *root node* ke *leaf node*), alih-alih terdegradasi menjadi **Full Index Scan** atau **Sequential/Table Scan** ($O(N)$).

```
Struktur B+Tree Index (Tergantung pada Nilai Mentah Kolom):
                 [ Root: 50 ]
                /            \
       [ Branch: 25 ]      [ Branch: 75 ]
        /          \        /          \
   [Leaf: 10..24]  ...   ...      [Leaf: 75..99]
        ▲
        │
   Index Seek: Langsung melompat ke Leaf Node target melalui komparasi kunci.
   Anti-Pattern: Evaluasi f(kolom) memaksa engine membaca seluruh Leaf Node (Scan).
```

#### Cara Kerja Cost-Based Optimizer (CBO) & Parsing Predikat
Ketika sebuah query dieksekusi, alur kerja di dalam Relational Database Management System (RDBMS) melewati beberapa tahapan:
1. **Parser & Analyzer**: Mengubah teks SQL menjadi *Abstract Syntax Tree* (AST) dan memvalidasi skema.
2. **Query Rewriter**: Menerapkan transformasi logis ekuivalen (misal: *constant folding*).
3. **Query Optimizer (CBO)**: Menghitung estimasi *cost* (I/O, CPU, memori) berdasarkan statistik tabel (*histogram*, *data density*, *cardinality*).
4. **Execution Engine**: Menjalankan *physical operator* yang dipilih oleh CBO.

B+Tree mengurutkan data berdasarkan nilai literal mentah dari kolom yang diindeks. Ketika sebuah predikat ditulis dalam format:
$$\text{kolom} \quad \mathbf{operator} \quad \text{konstanta}$$
*Optimizer* dapat memetakan konstanta tersebut secara langsung ke algoritma pencarian biner pada indeks B+Tree. 

Namun, jika predikat diubah menjadi:
$$f(\text{kolom}) \quad \mathbf{operator} \quad \text{konstanta}$$
RDBMS secara matematis tidak dapat mengasumsikan sifat fungsi $f(x)$ (apakah fungsi tersebut injektif, monotonik naik, deterministik, atau membalik urutan). Tanpa manipulasi algebra simbolik, *execution engine* tidak dapat mencari inversi fungsi $f^{-1}(\text{konstanta})$. Akibatnya, RDBMS terpaksa mengeksekusi fungsi $f(x)$ pada **setiap baris data** yang ada di tabel melalui *Table Scan* atau *Index Scan*, menyebabkan lonjakan drastis pada penggunaan CPU dan disk I/O.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah skema tabel analitik transaksi e-commerce dan perbandingan langsung antara query non-SARGable (*Anti-Pattern*) dengan bentuk SARGable yang optimal.

```sql
-- Skema Pengujian (PostgreSQL 14+)
DROP TABLE IF EXISTS orders CASCADE;

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date TIMESTAMP NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    tracking_code VARCHAR(50) NOT NULL
);

-- Pembuatan Indeks B+Tree Standar
CREATE INDEX idx_orders_order_date ON orders(order_date);
CREATE INDEX idx_orders_total_amount ON orders(total_amount);
CREATE INDEX idx_orders_tracking_code ON orders(tracking_code);

-- Dummy Data: 1.000.000 Baris Data
INSERT INTO orders (customer_id, order_date, total_amount, status, tracking_code)
SELECT 
    (random() * 10000)::INT,
    NOW() - (random() * interval '365 days'),
    (random() * 1000)::NUMERIC(12,2),
    (ARRAY['PENDING', 'PAID', 'SHIPPED', 'CANCELLED'])[floor(random() * 4 + 1)],
    'TRK-' || lpad(i::text, 8, '0')
FROM generate_series(1, 1000000) AS i;

-- Wajib jalankan ANALYZE untuk memperbarui statistik histogram pada CBO
ANALYZE orders;
```

#### Kasus 1: Manipulasi Fungsi pada Kolom Temporal (Tanggal/Waktu)

```sql
-- ANTI-PATTERN (Non-SARGable)
-- Fungsi DATE() membungkus kolom 'order_date'. 
-- Efek: Seq Scan, evaluasi DATE() dilakukan 1.000.000 kali.
EXPLAIN ANALYZE
SELECT id, total_amount 
FROM orders 
WHERE DATE(order_date) = '2023-11-15';

-- REFAKTORISASI OPTIMAL (SARGable)
-- Kolom 'order_date' berdiri sendiri; konstanta diubah menjadi rentang eksplisit.
-- Efek: Index Scan/Bitmap Index Scan menggunakan idx_orders_order_date.
EXPLAIN ANALYZE
SELECT id, total_amount 
FROM orders 
WHERE order_date >= '2023-11-15 00:00:00' 
  AND order_date <  '2023-11-16 00:00:00';
```

#### Kasus 2: Operasi Aritmatika pada Kolom Terindeks

```sql
-- ANTI-PATTERN (Non-SARGable)
-- Operasi aljabar (+, -, *, /) berada di sisi kolom.
EXPLAIN ANALYZE
SELECT id, total_amount 
FROM orders 
WHERE total_amount * 1.11 > 500.00;

-- REFAKTORISASI OPTIMAL (SARGable)
-- Pindahkan kalkulasi aritmatika ke sisi konstanta (Constant Folding oleh engine).
EXPLAIN ANALYZE
SELECT id, total_amount 
FROM orders 
WHERE total_amount > 500.00 / 1.11;
```

#### Kasus 3: Pencarian String Menggunakan Wildcard Awalan (*Leading Wildcard*)

```sql
-- ANTI-PATTERN (Non-SARGable)
-- Karakter wildcard '%' di awal string membuat traversal B-Tree mustahil.
EXPLAIN ANALYZE
SELECT id, tracking_code 
FROM orders 
WHERE tracking_code LIKE '%00001234';

-- REFAKTORISASI OPTIMAL (SARGable)
-- B+Tree dapat mencari prefix secara biner jika wildcard berada di akhir.
EXPLAIN ANALYZE
SELECT id, tracking_code 
FROM orders 
WHERE tracking_code LIKE 'TRK-00001234%';

-- SOLUSI ARSITEKTUR JIKA TETAP BUTUH SUBSTRING / SUFFIX:
-- 1. Buat index reverse:
CREATE INDEX idx_orders_reverse_tracking ON orders(reverse(tracking_code));
-- Query pencarian akhiran secara SARGable via functional index:
SELECT id, tracking_code 
FROM orders 
WHERE reverse(tracking_code) LIKE reverse('%1234');

-- 2. Atau buat Trigram Index (GIN) untuk arbitrary substring matching:
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_orders_tracking_trgm ON orders USING gin(tracking_code gin_trgm_ops);
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Filter vs. Access Predicate
Di level engine (seperti Storage Engine InnoDB MySQL atau Buffer Manager PostgreSQL):
- **Access Predicate (Index Cond)**: Digunakan langsung untuk navigasi pointer pada B+Tree. Engine mengisolasi *leaf page* yang relevan menggunakan perbandingan kunci langsung. Baris yang tidak relevan tidak pernah dimuat dari disk/cache.
- **Filter (Residual Filter)**: Ketika kondisi predikat bernilai non-SARGable, engine harus memuat *page* baris data ke memori, membaca *tuple*, mengeksekusi operasi komputasi di CPU per baris, dan membuang tuple jika kondisi bernilai `FALSE`.

```
Query SARGable:
Index Scan [order_date >= ... AND order_date < ...] -> Hanya mengambil tuple valid

Query Non-SARGable:
Seq Scan on orders -> Membaca 1.000.000 tuple -> CPU Filter: (DATE(order_date) = '...') -> Menghapus 999.xxx tuple
```

#### Alokasi Memori & Disk I/O (Buffer Pool thrashing)
- Pada query non-SARGable, engine terpaksa membaca seluruh *data pages* dari tabel ke dalam **Buffer Pool (Shared Buffers)**.
- Hal ini menyebabkan fenomena **Buffer Pool Cache Thrashing**, di mana data halaman lain yang sering diakses (hot data) terdepak keluar (*evicted*) dari RAM hanya untuk memproses satu query yang memindai tabel secara menyeluruh.
- I/O Amplification meningkat dari beberapa *kilobyte* (beberapa page index + data page) menjadi puluhan *megabyte* atau *gigabyte* (seluruh ukuran tabel pada disk).

#### Trade-offs
| Solusi | Keuntungan | Kerugian |
| :--- | :--- | :--- |
| **Isolasi Predikat Manual** (Refactoring SQL) | Nol overhead penyimpanan; performa optimal di skema yang ada. | Membutuhkan disiplin penulisan kode di layer aplikasi / ORM. |
| **Generated Columns / Expression Indexes** (`CREATE INDEX ON orders(DATE(order_date))`) | Membantu query non-SARGable agar tetap dapat di-*seek*. | Overhead write/insert I/O; menambah konsumsi disk; indeks sangat spesifik dan kaku. |
| **GIN / GiST Indexes** (Full-Text/Trigram) | Memungkinkan pencarian fleksibel (`%substring%`). | Ukuran index jauh lebih besar dibanding B-Tree; latensi mutasi (INSERT/UPDATE) tinggi. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Isolasi Kolom Terindeks**: Pastikan kolom terindeks berdiri sendiri secara murni pada salah satu sisi operator relasional ($=, <, >, \le, \ge, \text{BETWEEN}, \text{IN}$).
- **Eksplisitkan Tipe Data**: Samakan tipe data parameter query dengan tipe data kolom skema untuk mencegah konversi implisit (*implicit type casting*). Contoh: Jangan membandingkan kolom `VARCHAR` dengan parameter numerik tanpa tanda kutip.
- **Gunakan Rentang Waktu Terbuka-Tertutup**: Gunakan pola interval setengah-terbuka:
  ```sql
  WHERE created_at >= '2023-01-01' AND created_at < '2023-02-01'
  ```
  Hindari `BETWEEN` untuk timestamp presisi mikrodetik/milidetik, karena `BETWEEN` bersifat inklusif (`<=`), yang berisiko menangkap data pada timestamp batas `2023-02-01 00:00:00.000`.

#### Don'ts
- **Menghindari Fungsi Wrapper**: Jangan gunakan fungsi bawaan skalar seperti `UPPER()`, `LOWER()`, `SUBSTR()`, `COALESCE()`, `ISNULL()` langsung pada kolom yang diindeks tanpa Functional/Expression Index.
- **Hindari Implicit Casting**:
  ```sql
  -- Kolom phone adalah VARCHAR
  -- ANTI-PATTERN: Memaksa DB mengonversi setiap baris phone menjadi integer (CAST(phone AS INT))
  WHERE phone = 08123456789; 

  -- BEST PRACTICE
  WHERE phone = '08123456789';
  ```
- **Hindari Predikat Negasi**: Operator `!=`, `<>`, `NOT IN`, `NOT LIKE` umumnya membatalkan operasi Index Seek karena B-Tree dirancang untuk memetakan keberadaan data, bukan ketiadaan data (kecuali dioptimalkan CBO dengan anti-join atau indeks parsial).

#### Edge Cases di Industri
- **Pencarian Case-Insensitive**: Penggunaan `ILIKE '%term%'` (PostgreSQL) atau `WHERE LOWER(username) = 'john'` sering menjadi penyebab utama degradasi server produksi. Solusi terbaik adalah memanfaatkan tipe data `CITEXT` atau functional index `CREATE INDEX idx_user_lower ON users (LOWER(username))`.
- **Kombinasi Kondisi OR**:
  ```sql
  WHERE indexed_col_1 = 'val' OR unindexed_col_2 = 'val'
  ```
  Keberadaan kolom tanpa indeks pada klausa `OR` secara otomatis membatalkan penggunaan indeks pada `indexed_col_1`. Gunakan teknik `UNION ALL` jika optimasi `BitmapOr` tidak dieksekusi oleh CBO.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Dampak Implicit Casting pada Foreign Key**:
   Buat tabel `accounts` dengan kolom `account_number VARCHAR(20)` dan isi 500.000 data. Buat indeks B+Tree pada kolom tersebut. Jalankan `EXPLAIN ANALYZE SELECT * FROM accounts WHERE account_number = 123456;` (sebagai integer) dan bandingkan dengan `WHERE account_number = '123456';`. Amati perubahan *Node Type* pada execution plan (`Seq Scan` vs `Index Scan`) dan jelaskan alasannya dari sudut pandang precedensi tipe data SQL engine.

2. **Refaktorisasi Predikat `COALESCE` / `NULL-safe`**:
   Diberikan query laporan analitik lambat berikut:
   ```sql
   SELECT * FROM employees 
   WHERE COALESCE(commission_pct, 0) < 0.05;
   ```
   Ubahlah query tersebut agar SARGable terhadap indeks B+Tree pada kolom `commission_pct` tanpa mengubah semantik logika penanganan nilai `NULL`! (Petunjuk: Manfaatkan ekspresi percabangan kondisi diskrit dengan operator `OR` atau `IS NULL`). Jalankan `EXPLAIN` untuk memvalidasi pemanfaatan indeks.
