## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sistem Manajemen Basis Data Relasional modern seperti PostgreSQL menggunakan arsitektur **MVCC (Multi-Version Concurrency Control)** untuk menjamin isolasi transaksi tanpa mengunci pembaca (*readers don't block writers, writers don't block readers*). Konsekuensi arsitektural dari MVCC adalah: operasi `UPDATE` tidak menimpa data di tempat (*in-place*), dan operasi `DELETE` tidak langsung menghapus data dari disk. 

Sebaliknya, baris lama ditandai sebagai tidak valid secara logika (*dead tuple*), dan baris baru disisipkan sebagai versi baru (*live tuple*). Akumulasi *dead tuples* ini menyebabkan fenomena yang disebut **Table Bloat**, yang memboroskan kapasitas disk dan mendegradasi performa I/O secara drastis.

```
+---------------------------------------------------------------+
| Heap Page (8KB Default)                                       |
| +-----------------------------------------------------------+ |
| | PageHeader | Line Pointers (ItemId)                      | |
| +-----------------------------------------------------------+ |
| | [Free Space]                                              | |
| +-----------------------------------------------------------+ |
| | Tuple 2 (Live, xmin: 105, xmax: 0)                        | |
| +-----------------------------------------------------------+ |
| | Tuple 1 (Dead, xmin: 100, xmax: 105) <- Target VACUUM     | |
| +-----------------------------------------------------------+ |
+---------------------------------------------------------------+
```

Untuk menjaga kestabilan dan keandalan sistem jangka panjang, tiga pilar pemeliharaan (*maintenance*) wajib dijalankan:

1. **VACUUM**:
   - **Lazy VACUUM (Standard)**: Menandai ruang yang sebelumnya ditempati oleh *dead tuples* di dalam halaman data (*data pages/heap*) agar dapat digunakan kembali oleh transaksi baru. Operasi ini **tidak** mengembalikan *space* ke sistem operasi (kecuali jika ada halaman kosong di bagian akhir tabel/file) dan tidak memblokir pembacaan maupun penulisan tabel.
   - **VACUUM FULL**: Menulis ulang (*rewrite*) seluruh isi tabel ke file baru di disk tanpa menyertakan *dead tuples*. Mengembalikan ruang kosong sepenuhnya ke OS, namun membutuhkan *Exclusive Lock* (`ACCESS EXCLUSIVE`) yang memblokir semua operasi DML/DQL.
   - **Freeze (Anti-Wraparound)**: Menangani batas limit 32-bit *Transaction ID* (XID). Jika tidak di-*freeze*, XID akan mengalami *wraparound* yang berisiko merusak visibilitas data historis secara katastropik.

2. **ANALYZE**:
   - Query Planner (Cost-Based Optimizer / CBO) menentukan rencana eksekusi optimal (misal: *Index Scan* vs *Sequential Scan*, *Hash Join* vs *Nested Loop*) berdasarkan statistik distribusi data.
   - Perintah `ANALYZE` mengambil sampel acak (*probabilistic sampling*) dari tabel untuk mengkalkulasi metrik seperti jumlah baris unik (*n_distinct*), nilai paling umum (*MCV - Most Common Values*), dan histogram persebaran nilai ke katalog sistem `pg_statistic`.

3. **Backup Strategy**:
   - **Logical Backup (`pg_dump`, `pg_dumpall`)**: Mengekstrak skema dan data menjadi skrip SQL atau file arsip terkompresi. Bagus untuk granularitas tinggi (per tabel/skema) dan portabilitas antar versi mayor, namun lambat untuk basis data berukuran terabyte.
   - **Physical Backup & Point-in-Time Recovery (PITR)**: Menyalin blok file data mentah pada tingkat disk yang dikombinasikan dengan arsip **Write-Ahead Logging (WAL)**. Pendekatan ini wajib diterapkan di lingkungan enterprise untuk meminimalkan *Recovery Time Objective* (RTO) dan *Recovery Point Objective* (RPO).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi script pemeliharaan, inspeksi metrik bloat, dan konfigurasi optimasi otomatis:

```sql
-- ============================================================================
-- 1. INSPEKSI STATUS DEAD TUPLES & WAKTU ANALYZE TERAKHIR
-- ============================================================================
SELECT 
    schemaname,
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    ROUND((n_dead_tup::NUMERIC / NULLIF(n_live_tup + n_dead_tup, 0)) * 100, 2) AS dead_tuple_ratio_pct,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- ============================================================================
-- 2. EKSEKUSI MANUAL DENGAN VERBOSE MONITORING
-- ============================================================================
-- Mengosongkan dead tuples sekaligus memperbarui statistik optimizer tanpa lock tabel
VACUUM (VERBOSE, ANALYZE) customer_orders;

-- Rekomendasi: Gunakan VACUUM (PARALLEL 4) pada indeks berukuran besar (PostgreSQL 13+)
VACUUM (PARALLEL 4, ANALYZE) large_financial_transactions;

-- ============================================================================
-- 3. TUNING AUTOVACUUM PER TABEL (UNTUK TABEL TINGGI TRANSAKSI)
-- ============================================================================
-- Formula Autovacuum Trigger: 
-- autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor * pg_class.reltuples)
-- Default scale factor (0.2 / 20%) terlalu lambat untuk tabel dengan ratusan juta baris.

ALTER TABLE high_frequency_ledger SET (
    -- Picu autovacuum jika 5% data berubah, bukan 20% default
    autovacuum_vacuum_scale_factor = 0.05,
    -- Ambang batas dasar dead tuples
    autovacuum_vacuum_threshold = 1000,
    -- Analisa statistik optimizer lebih agresif
    autovacuum_analyze_scale_factor = 0.02,
    -- Batasi delay throttling jika prosesor server mumpuni
    autovacuum_vacuum_cost_delay = 2
);

-- ============================================================================
-- 4. INSPEKSI STATISTIK OPTIMIZER HASIL ANALYZE
-- ============================================================================
SELECT 
    attname AS column_name,
    n_distinct,
    correlation, -- Tingkat keterurutan data di disk vs indeks logis
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE tablename = 'customer_orders'
  AND attname = 'status';
```

#### Eksekusi Backup dan Restore (Bash Engine Layer)

```bash
#!/usr/bin/env bash
set -euo pipefail

# 1. LOGICAL BACKUP (Custom Archive Format, Kompresi Paralel)
# -Fc : Format custom pg_dump (efisien, bisa dibaca pg_restore)
# -j 4: Dump menggunakan 4 worker CPU paralel
export PGDATABASE="ecommerce_prod"
pg_dump -h 127.0.0.1 -U postgres -j 4 -Fd -f /backups/dump_$(date +%Y%m%d_%H%M%S)

# Restore Parsial/Spesifik dari Direktori Dump
pg_restore -h 127.0.0.1 -U postgres -d ecommerce_staging -j 4 -t customer_orders /backups/dump_20260329_000000

# 2. PHYSICAL BACKUP (Untuk Standby Node / Disaster Recovery PITR)
# -D : Direktori output
# -Fp: Format plain block
# -Xs: Stream WAL secara simultan selama backup berjalan
# -R : Buat file sinyal replikasi (standby.signal) otomatis
pg_basebackup -h 127.0.0.1 -U replicator -D /var/lib/postgresql/data_backup -Fp -Xs -P -R -v
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Visibility Map (VM) & Free Space Map (FSM)**:
   - Setiap tabel memiliki file *fork* terpisah: `_vm` dan `_fsm`.
   - **Visibility Map**: Melacak halaman mana yang hanya berisi *live tuples* dan sudah terlihat oleh semua transaksi aktif. `VACUUM` memanfaatkan VM untuk melompati (*skip*) halaman yang tidak memiliki *dead tuples*, secara masif mempercepat proses pembersihan. VM juga memungkinkan fitur **Index-Only Scans**, di mana *query engine* tidak perlu membaca halaman *heap* jika bit VM bernilai 1.
   - **Free Space Map**: Menyimpan metadata ketersediaan ruang kosong per halaman (dalam resolusi per-256 byte). Saat `INSERT` atau `UPDATE` membutuhkan ruang, Postgres tidak memindai tabel dari awal, melainkan langsung meminta alokasi ke FSM.

2. **Cost-Based Vacuum Throttling**:
   - `VACUUM` dirancang agar tidak memonopoli I/O disk. Postgres memiliki algoritma akumulasi beban:
     - Halaman ditemukan di `shared_buffers`: Biaya = `vacuum_cost_page_hit` (default: 1)
     - Halaman ditemukan di OS Page Cache: Biaya = `vacuum_cost_page_miss` (default: 2)
     - Halaman harus dibaca dari Disk fisik: Biaya = `vacuum_cost_page_dirty` (default: 20)
   - Saat total kalkulasi biaya mencapai batas `vacuum_cost_limit` (default: 200), *worker* akan tertidur (*sleep*) selama `vacuum_cost_delay` (default: 2ms).

3. **Transaction ID Wraparound**:
   - XID direpresentasikan dalam bilangan bulat 32-bit *unsigned* (~4,29 miliar transaksi). PostgreSQL menggunakan *modulo comparison logic* untuk menentukan apakah transaksi terjadi di masa lalu atau masa depan.
   - Jika transaksi mencapai selisih $2^{31}$ (sekitar 2 miliar transaksi) tanpa pemeliharaan, *engine* akan terancam tidak bisa membedakan transaksi lama dan baru.
   - `VACUUM FREEZE` mengganti nilai `xmin` pada header *tuple* dengan flag khusus `HEAP_XMIN_FROZEN`. Flag ini secara konseptual memberitahu *engine*: *"Tuple ini terjadi di masa lampau yang tak terhingga dan selalu terlihat oleh transaksi apa pun"*.

#### Alokasi Memori / Resource
- Operasi `VACUUM` dibatasi oleh parameter alokasi memori `maintenance_work_mem` (default sering kali 64MB). 
- Ruang memori ini digunakan untuk menyimpan daftar pointer ID *dead tuples* yang ditemukan di halaman data sebelum *worker* beralih membersihkan *pointer* tersebut dari indeks B-Tree. Jika `maintenance_work_mem` penuh sebelum satu *pass* selesai, `VACUUM` terpaksa mengosongkan indeks terlebih dahulu, menyebabkan pemindaian indeks berulang kali (*multiple index scan passes*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Tuning autovacuum per-tabel**: Turunkan `autovacuum_vacuum_scale_factor` untuk tabel masif (misal: 0.01 - 0.05 pada tabel miliaran baris). Nilai default 0.20 berarti tabel 100 juta baris harus menumpuk 20 juta *dead tuples* sebelum autovacuum aktif.
- **Tingkatkan `maintenance_work_mem`**: Alokasikan 1GB - 2GB pada mesin produksi selama periode pemeliharaan terjadwal agar indeks dapat dibersihkan dalam satu siklus (*single pass*).
- **Gunakan Tool Pihak Ketiga untuk Repack**: Gunakan ekstensi seperti `pg_repack` daripada `VACUUM FULL`. `pg_repack` mereorganisasi tabel dan menghilangkan bloat tanpa mengunci tabel secara eksklusif.

#### Don'ts
- **JANGAN Mematikan `autovacuum` Secara Global**: Mematikan `autovacuum = off` adalah resep bencana. Hal ini akan menyebabkan tabel meledak ukurannya secara eksponensial dan memicu *emergency shutdown* akibat bahaya *wraparound*.
- **JANGAN Mengandalkan `pg_dump` untuk Database Terabyte**: `pg_dump` mengekstrak data baris-demi-baris via koneksi SQL normal. Waktu restore basis data 2TB via logical dump bisa memakan waktu belasan jam, melanggar batas RTO pada sebagian besar SLA produksi. Gunakan kombinasi `pg_basebackup` + WAL Archiving (seperti pgBackRest atau Barman).

#### Edge Cases
- **Long-Running Transactions & Uncommitted Locks**: Transaksi yang berjalan sangat lama (misal: reporting query atau uncommitted write transaction) memegang *snapshot horizon* lama (`xmin horizon`). `VACUUM` **tidak dapat menghapus dead tuple apa pun** yang terhapus setelah *snapshot* transaksi tersebut dimulai. Hal ini menyebabkan bloat tetap terjadi meskipun autovacuum berjalan terus-menerus.
- **Abandoned Replication Slots**: Slot replikasi yang tidak aktif (*inactive replication slot*) akan menahan pembersihan WAL dan memblokir *vacuuming* pada tabel catalog/heap, yang berisiko menghabiskan kapasitas disk server hingga 100%.

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi dan Analisis Table Bloat**:
   - Buat satu tabel dummy berisi 1.000.000 baris. 
   - Lakukan operasi `UPDATE` terhadap seluruh baris sebanyak 3 kali berturut-turut.
   - Amati perubahan ukuran tabel menggunakan fungsi `pg_total_relation_size()`. 
   - Bandingkan perbedaan penggunaan ruang disk setelah menjalankan `VACUUM` standar vs `VACUUM FULL`.

2. **Dampak ANALYZE terhadap Query Plan**:
   - Matikan autovacuum sementara pada sesi lokal tabel dummy.
   - Masukkan 500.000 baris data dengan distribusi nilai yang sangat condong (*skewed*, misal 99% bernilai status `'COMPLETED'`, 1% bernilai `'PENDING'`).
   - Buat indeks pada kolom status. Jalankan `EXPLAIN ANALYZE` pada query `WHERE status = 'PENDING'`. 
   - Jalankan `ANALYZE` pada tabel tersebut, lalu ulangi perintah `EXPLAIN ANALYZE`. Amati bagaimana *cost estimation* dan strategi scan (*Seq Scan* vs *Bitmap Index Scan*) berubah secara drastis setelah statistik terupdate.
