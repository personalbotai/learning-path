### 1. Konsep & Arsitektur Mendalam

**Scalar Subquery** adalah sebuah subquery (kueri bersarang) yang secara matematis dan relasional dibatasi untuk mengembalikan **tepat satu nilai atomik tunggal**: satu baris (*single row*) dan satu kolom (*single column*). Di dalam tipe data SQL, hasilnya diposisikan layaknya literal konstan atau ekspresi tunggal (*expression*).

Fitur ini dirancang untuk menyederhanakan deklarasi kebutuhan data di mana nilai perbandingan atau nilai proyeksi bergantung pada kalkulasi dinamis tabel lain tanpa harus selalu menulis blok `JOIN` atau *procedural script* yang ekspansif.

#### Arsitektur Evaluasi: Non-Correlated vs. Correlated

Secara arsitektural di dalam *query engine* (seperti PostgreSQL, MySQL, Oracle), penempatan scalar subquery diproses ke dalam dua paradigma eksekusi:

1. **Non-Correlated Scalar Subquery**:
   - Subquery sama sekali tidak memiliki dependensi terhadap kolom pada kueri utama (*outer query*).
   - *Query Optimizer* mengevaluasi subquery ini satu kali saja di awal eksekusi. Pada Postgres, node ini direpresentasikan sebagai **`InitPlan`**.
   - Hasil tunggal tersebut disimpan di memori (*materialized/cached*) dan disuntikkan secara konstan ke *plan tree* utama. Kompleksitas eksekusi evaluasi subquery: $\mathcal{O}(1)$ terhadap $N$ baris *outer query*.

2. **Correlated Scalar Subquery**:
   - Subquery mereferensikan satu atau lebih kolom dari kueri utama.
   - Evaluasi subquery terikat langsung dengan *lifecycle* iterasi baris *outer query*. Pada *execution plan*, ini direpresentasikan sebagai **`SubPlan`** yang dieksekusi menggunakan pendekatan *Nested Loop*.
   - Jika optimizer gagal melakukan *subquery unnesting* (meratakan subquery menjadi operasi *join*), subquery akan dieksekusi berulang sebanyak $N$ baris yang lolos filter sebelumnya. Kompleksitasnya melonjak menjadi $\mathcal{O}(N \times M)$, di mana $M$ adalah waktu akses data subquery.

```
+-------------------------------------------------------------+
| Outer Query Execution Engine                                |
|                                                             |
|   Baris 1 ──> [ Eksekusi Subquery dengan Param Baris 1 ] ──> Nilai A
|   Baris 2 ──> [ Eksekusi Subquery dengan Param Baris 2 ] ──> Nilai B
|   Baris N ──> [ Eksekusi Subquery dengan Param Baris N ] ──> Nilai N
|                                                             |
| * Riset Optimizer modern: CBO mencoba mentransformasi        |
|   pola ini menjadi HASH JOIN / MERGE JOIN via Decorrelation |
+-------------------------------------------------------------+
```

### 2. Implementasi & Contoh Kasus Nyata

Skenario berikut menggunakan skema e-commerce dengan tabel `orders` dan `customers`.

```sql
-- Skema Basis Data
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    segment VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT REFERENCES customers(customer_id),
    total_amount NUMERIC(12, 2) NOT NULL,
    order_date DATE NOT NULL
);

-- Injeksi Sampel Data
INSERT INTO customers (customer_id, name, segment) VALUES
(1, 'Alice Corp', 'Enterprise'),
(2, 'Bob Retail', 'SMB'),
(3, 'Charlie Ind', 'Enterprise');

INSERT INTO orders (order_id, customer_id, total_amount, order_date) VALUES
(101, 1, 15000.00, '2024-01-15'),
(102, 1, 35000.00, '2024-02-10'),
(103, 2, 500.00,   '2024-02-12'),
(104, 3, 12000.00, '2024-03-01'),
(105, 2, 1500.00,  '2024-03-05');
```

#### Kasus A: Scalar Subquery di Klausa `WHERE` (Non-Correlated)
Mencari transaksi yang nilainya di atas rata-rata nilai transaksi global pelanggan Enterprise.

```sql
SELECT 
    order_id, 
    customer_id, 
    total_amount
FROM orders
WHERE total_amount > (
    -- Subquery menghasilkan TEPAT SATU baris dan SATU kolom (InitPlan)
    SELECT AVG(o.total_amount)
    FROM orders o
    JOIN customers c ON o.customer_id = c.customer_id
    WHERE c.segment = 'Enterprise'
);
```

#### Kasus B: Correlated Scalar Subquery di Klausa `SELECT` (Proyeksi)
Mengambil detail pesanan bersamaan dengan total akumulasi belanja pelanggan yang bersangkutan secara *inline*.

```sql
SELECT 
    o.order_id,
    o.customer_id,
    o.total_amount,
    -- Correlated Subquery: mereferensikan o.customer_id dari outer query
    (
        SELECT COALESCE(SUM(sub_o.total_amount), 0)
        FROM orders sub_o
        WHERE sub_o.customer_id = o.customer_id
    ) AS lifetime_customer_spend
FROM orders o
ORDER BY o.order_id;
```

#### Kasus C: Correlated Scalar Subquery di Klausa `WHERE`
Memfilter pesanan yang nilainya merupakan nilai transaksi terbesar yang pernah dibuat oleh pelanggan tersebut.

```sql
SELECT 
    o.order_id,
    o.customer_id,
    o.total_amount
FROM orders o
WHERE o.total_amount = (
    -- Menghitung nilai maksimum lokal per pelanggan
    SELECT MAX(sub_o.total_amount)
    FROM orders sub_o
    WHERE sub_o.customer_id = o.customer_id
);
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Validasi Kardinalitas Run-Time**: Engine basis data tidak selalu bisa memvalidasi secara statis apakah subquery akan menghasilkan $\le 1$ baris. Validasi dilakukan saat eksekusi:
  - **0 baris returned**: Engine secara otomatis mengonversinya menjadi nilai `NULL`.
  - **1 baris returned**: Nilai atomik diekstraksi ke register memori ekspresi.
  - **>1 baris returned**: Engine menghentikan transaksi dan melemparkan *runtime exception* (misal pada PostgreSQL: `ERROR: more than one row returned by a subquery used as an expression`).
- **Plan Types**:
  - *Non-Correlated*: Terdaftar sebagai `InitPlan`. Dijalankan satu kali di level *root executor*, hasilnya disimpan dalam *shared parameter state*.
  - *Correlated*: Terdaftar sebagai `SubPlan`. Executor akan mengeksekusi subquery berkali-kali melalui node `Nested Loop`, mensubstitusi parameter baris outer ke *inner plan* pada setiap iterasi tuple.

#### Alokasi Memori / Resource
- Engine modern (seperti PostgreSQL 13+) menggunakan fitur **Memoize** pada node `SubPlan`. Engine mengalokasikan *hash table* sementara di memori (`work_mem`).
- Jika outer query membawa `customer_id = 1` berulang kali, hasil komputasi subquery untuk `customer_id = 1` diambil dari *cache memory*, menghindari *heap scan* atau *index scan* ulang pada tabel anak.
- Jika ukuran *cache* melampaui alokasi memori, engine melakukan eviksi (LRU) atau *spill to disk*, yang memicu penurunan performa I/O secara drastis.

#### Trade-offs: Subquery vs. JOIN / Window Functions
| Pendekatan | Kelebihan | Kelemahan |
| :--- | :--- | :--- |
| **Scalar Subquery di SELECT** | Sederhana, menjaga kardinalitas outer query (tidak memicu duplikasi baris seperti pada *improper JOIN*). | Menghasilkan $\mathcal{O}(N)$ *lookups* jika optimizer gagal melakukan *decorrelation* dan caching tidak muat di memori. |
| **Window Function (`OVER (...)`)** | Mengkalkulasi metrik agregat dalam satu *single pass* scanning via *WindowAgg node*. | Terbatas pada tabel yang sudah terhubung dalam konteks query yang sama atau harus di-JOIN terlebih dahulu. |
| **LEFT JOIN + GROUP BY** | Sangat ramah optimizer (*Hash Join* / *Merge Join*), efisien untuk skala data besar. | Kode lebih panjang; risiko *cardinality explosion* jika agregasi salah dikonstruksi. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Fungsi Agregasi**: Saat menulis scalar subquery, pastikan output selalu skalar dengan menggunakan fungsi agregasi (`MAX()`, `MIN()`, `COUNT()`, `AVG()`) atau konstrain tegas dengan klausa `LIMIT 1` jika deterministik.
- **Dukung dengan Indeks**: Jika menggunakan *correlated scalar subquery*, pastikan kolom referensi di tabel dalam (*inner table*) memiliki indeks:
  ```sql
  -- Wajib ada jika subquery melakukan filtering WHERE inner.customer_id = outer.customer_id
  CREATE INDEX idx_orders_customer_id ON orders(customer_id);
  ```
- **Audit dengan EXPLAIN ANALYZE**: Periksa apakah kueri menghasilkan node `SubPlan` yang memiliki nilai `loops` setara dengan jumlah baris outer query. Jika ya, refactor ke `LEFT JOIN` atau *Window Function*.

#### Don'ts
- **Hindari Multi-Level Scalar Subqueries di SELECT**: Menulis lebih dari satu scalar subquery di `SELECT` (misal mencari total order, rata-rata order, dan order terakhir dalam 3 subquery terpisah) adalah *antipattern*. Ini memaksa engine membaca tabel target berkali-kali. Gunakan `LEFT JOIN LATERAL` atau agregasi tunggal.
- **Jangan Bergantung pada Asumsi Non-Deterministic**: Menulis subquery tanpa `ORDER BY` namun menggunakan `LIMIT 1` untuk memaksa bentuk skalar dapat menyebabkan inkonsistensi data antar eksekusi.

#### Edge Cases
- **The Silent NULL Trap**: 
  Jika scalar subquery di klausa `WHERE` menghasilkan 0 baris, subquery menghasilkan `NULL`.
  ```sql
  SELECT * FROM orders 
  WHERE total_amount > (SELECT total_amount FROM orders WHERE order_id = 999999);
  -- Subquery = NULL. Evaluasi: total_amount > NULL bernilai UNKNOWN (False).
  -- Kueri mengembalikan 0 baris tanpa melempar error!
  ```
  *Mitigasi*: Gunakan fungsi `COALESCE` di dalam atau di luar subquery jika nilai fallback diperlukan.

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Antipattern Performance**:
   Diberikan query dengan performa buruk berikut:
   ```sql
   SELECT 
       c.customer_id,
       c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS total_orders,
       (SELECT MAX(o.total_amount) FROM orders o WHERE o.customer_id = c.customer_id) AS max_spent
   FROM customers c;
   ```
   *Tantangan*: Ubah query di atas menjadi bentuk yang lebih optimal menggunakan `LEFT JOIN` dengan agregasi, atau menggunakan `CROSS JOIN LATERAL` / `LEFT JOIN LATERAL`. Gunakan `EXPLAIN ANALYZE` pada dataset lokal Anda untuk membandingkan metrik `shared hit blocks` dan `execution time`.

2. **Deteksi Runtime Failure**:
   Tulis kueri yang menggunakan scalar subquery di klausa `WHERE` dengan operator `=`, tetapi sengaja didesain untuk memicu error kardinalitas (*more than one row returned*). Modifikasi kueri tersebut secara bertahap menggunakan:
   - Operator berbasis set (`IN` / `ANY`).
   - Pendekatan analitik berbasis `LIMIT 1` dengan `ORDER BY` deterministik.
   Amati bagaimana *Query Execution Plan* berubah pada masing-masing perbaikan.
