### 1. Konsep & Arsitektur Mendalam

Paradigma aplikasi web tradisional bertumpu pada arsitektur *Thin Client*: browser berperan sebagai lapisan presentasi pasif yang sepenuhnya bergantung pada REST/GraphQL API dan latensi jaringan untuk memanipulasi basis data di server. Paradigma ini memperkenalkan masalah latensi round-trip (RTT), kegagalan parsial saat *offline*, dan arsitektur *optimistic UI* yang kompleks dan rentan terhadap inkonsistensi *race condition*.

**Local-First Architecture** membalik model ini:
1. Data disimpan dan dimanipulasi secara lokal di sisi klien (*client-side storage*) sebagai sumber kebenaran primer (*source of truth*).
2. UI membaca dan menulis secara instan (0ms perceived latency) langsung ke mesin database lokal.
3. Sinkronisasi jaringan berjalan di latar belakang secara asinkron (*eventual consistency*) menggunakan mekanisme *conflict resolution* (seperti CRDTs - *Conflict-free Replicated Data Types* atau *operational transformation*).

```
[ Traditional Web App ]
Browser UI ---> Network (100-300ms) ---> Server API ---> Cloud Database

[ Local-First App ]
Browser UI ---> SQLite WASM + OPFS (<1ms)
                     |
            (Background Worker)
                     | (Sync Engine / CRDT)
                     v
             Cloud Sync Gateway ---> Server Database
```

Untuk merealisasikannya, browser membutuhkan mesin SQL relasional yang tangguh, deterministik, dan berkinerja tinggi, bukan sekadar *Key-Value store* primitif seperti `IndexedDB` atau `localStorage`. Di sinilah **SQLite WASM** masuk.

#### Kompilasi SQLite ke WebAssembly & Virtual File System (VFS)
SQLite dirancang dengan modularitas tinggi melalui lapisan **OS Interface / VFS (Virtual File System)**. Mesin SQL SQLite (parser, optimizer, B-Tree engine, pager) tidak pernah mengakses OS primitives (`open()`, `read()`, `write()`, `fsync()`) secara langsung; melainkan mendelegasikannya ke modul VFS yang terpasang.

Ketika SQLite C code-base dikompilasi menggunakan LLVM/Emscripten menjadi biner WebAssembly (`sqlite3.wasm`):
- Pager dan B-Tree engine berjalan di dalam lingkungan **WASM Linear Memory**.
- Lapisan VFS C dijembatani ke JavaScript API untuk mengakses sistem berkas web modern: **Origin Private File System (OPFS)**.
- OPFS menyediakan metode `createWritable()` atau antarmuka berkecepatan tinggi `FileSystemSyncAccessHandle` yang memungkinkan operasi I/O sinkron, *in-place modification*, dan manipulasi biner langsung pada level blok penyimpanan privat browser tanpa overhead serialisasi Base64/JSON.

### 2. Implementasi & Contoh Kasus Nyata

Implementasi modern memerlukan isolasi eksekusi database di dalam **Web Worker** agar query analitis/intensif tidak memblokir UI thread (Main Thread). Eksekusi OPFS sinkron juga **wajib** dijalankan di Worker thread.

Berikut implementasi berbasis JavaScript modern menggunakan pustaka resmi `@sqlite.org/sqlite-wasm`.

#### A. Konfigurasi Worker Database (`worker.js`)

```javascript
import { sqlite3Worker1Promiser } from '@sqlite.org/sqlite-wasm';

// Inisialisasi promiser interface resmi dari SQLite WASM
let promiser;

async function initDB() {
  return new Promise((resolve) => {
    promiser = sqlite3Worker1Promiser({
      onready: () => resolve(promiser)
    });
  });
}

self.onmessage = async (event) => {
  const { action, payload, id } = event.data;

  try {
    if (action === 'INIT') {
      await initDB();

      // Buka database dengan OPFS VFS backend (persistensi disk nyata di browser)
      const openResponse = await promiser('open', {
        filename: 'app_production.sqlite3',
        vfs: 'opfs'
      });

      // Optimasi pragmas runtime SQLite WASM
      await promiser('exec', {
        dbId: openResponse.dbId,
        sql: `
          PRAGMA journal_mode = WAL;
          PRAGMA synchronous = NORMAL;
          PRAGMA cache_size = -64000; -- Alokasikan cache memori 64MB
          PRAGMA foreign_keys = ON;
        `
      });

      // Skema tabel lokal & inisialisasi
      await promiser('exec', {
        dbId: openResponse.dbId,
        sql: `
          CREATE TABLE IF NOT EXISTS sync_queue (
            id TEXT PRIMARY KEY,
            payload JSON NOT NULL,
            action TEXT NOT NULL,
            synced INTEGER DEFAULT 0,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
          );

          CREATE TABLE IF NOT EXISTS documents (
            id TEXT PRIMARY KEY,
            title TEXT NOT NULL,
            content TEXT NOT NULL,
            version INTEGER NOT NULL DEFAULT 1,
            is_deleted INTEGER DEFAULT 0,
            updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
          );

          CREATE INDEX IF NOT EXISTS idx_documents_updated ON documents(updated_at);
        `
      });

      self.postMessage({ id, status: 'OK', result: { dbId: openResponse.dbId } });
    }

    if (action === 'EXEC_TRANSACTION') {
      const { dbId, docId, title, content } = payload;

      // Atomic Mutation: Tulis Dokumen + Log Queue Mutasi Sinkronisasi Lokal
      await promiser('exec', {
        dbId: dbId,
        sql: `
          BEGIN TRANSACTION;

          INSERT INTO documents (id, title, content, version, updated_at)
          VALUES ($id, $title, $content, 1, CURRENT_TIMESTAMP)
          ON CONFLICT(id) DO UPDATE SET
            title = excluded.title,
            content = excluded.content,
            version = documents.version + 1,
            updated_at = CURRENT_TIMESTAMP;

          INSERT INTO sync_queue (id, payload, action)
          VALUES (
            hex(randomblob(16)),
            json_object('id', $id, 'title', $title, 'content', $content),
            'UPSERT'
          );

          COMMIT;
        `,
        bind: {
          $id: docId,
          $title: title,
          $content: content
        }
      });

      self.postMessage({ id, status: 'OK', result: { success: true } });
    }

    if (action === 'QUERY_ACTIVE_DOCS') {
      const { dbId } = payload;
      const rows = [];

      await promiser('exec', {
        dbId: dbId,
        sql: `SELECT id, title, content, version, updated_at 
              FROM documents 
              WHERE is_deleted = 0 
              ORDER BY updated_at DESC;`,
        rowMode: 'object',
        callback: (res) => {
          if (res.row) {
            rows.push(res.row);
          }
        }
      });

      self.postMessage({ id, status: 'OK', result: rows });
    }
  } catch (err) {
    self.postMessage({ id, status: 'ERROR', error: err.message });
  }
};
```

#### B. Main Thread Client Interaction (`app.js`)

```javascript
// Memerlukan header HTTP pada Web Server:
// Cross-Origin-Opener-Policy: same-origin
// Cross-Origin-Embedder-Policy: require-corp

const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' });

let requestId = 0;
const pendingRequests = new Map();

worker.onmessage = (e) => {
  const { id, status, result, error } = e.data;
  if (pendingRequests.has(id)) {
    const { resolve, reject } = pendingRequests.get(id);
    pendingRequests.delete(id);
    if (status === 'OK') resolve(result);
    else reject(new Error(error));
  }
};

function dispatchWorker(action, payload = {}) {
  return new Promise((resolve, reject) => {
    const id = ++requestId;
    pendingRequests.set(id, { resolve, reject });
    worker.postMessage({ action, payload, id });
  });
}

(async () => {
  console.log("Inisialisasi SQLite WASM + OPFS...");
  const initRes = await dispatchWorker('INIT');
  const dbId = initRes.dbId;

  console.log("Menyimpan transaksi lokal...");
  await dispatchWorker('EXEC_TRANSACTION', {
    dbId,
    docId: 'doc_alpha_99',
    title: 'Arsitektur Edge Computing',
    content: 'Penyimpanan lokal dengan persistensi berbasis B-Tree di OPFS'
  });

  console.log("Query data lokal:");
  const docs = await dispatchWorker('QUERY_ACTIVE_DOCS', { dbId });
  console.table(docs);
})();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **WASM Linear Memory Bridge**: WebAssembly mengoperasikan ruang alamat memori array biner kontinu (*Linear Memory*). Ketika kueri SQL dieksekusi, string SQL di-marshal dari lingkungan V8/JavaScript engine ke alamat linear memory WASM menggunakan Emscripten memory allocators (`malloc`/`free`).
2. **Virtual Machine (VDBE)**: SQLite mengkompilasi string SQL menjadi instruksi *byte-code* untuk Virtual Database Engine (VDBE). VDBE mengeksekusi instruksi ini sepenuhnya di dalam runtime WASM dengan kecepatan komputasi mendekati *native C*.
3. **OPFS VFS Adapter**: 
   - Pada browser modern, SQLite memanfaatkan `FileSystemSyncAccessHandle` milik Web Storage API.
   - Pager module pada SQLite mengirimkan *read/write page requests* berukuran tertentu (default 4096 bytes). VFS WASM menerjemahkan request ini langsung ke *read/write offset* pada file biner di OPFS.

#### Alokasi Memori / Resource
- **WebAssembly Pages**: Memori dialokasikan dalam kelipatan 64KB *pages*. SQLite WASM mengalokasikan pool statis untuk VDBE execution stacks dan B-Tree internal nodes.
- **SharedArrayBuffer & Atomics**: Untuk implementasi multi-threading (akses konkuren beberapa tab browser ke database yang sama), browser menggunakan `SharedArrayBuffer` dan instruksi `Atomics` untuk sinkronisasi thread-level locks (mutexes) di VFS.
- **Cache Size Allocation**: Penggunaan `PRAGMA cache_size = -64000;` memaksa SQLite mengonsumsi hingga 64MB dari batas kuota WASM memory heap murni untuk *in-memory B-Tree page buffer cache*, mengurangi panggilan I/O ke OPFS.

#### Trade-offs
| Aspek | SQLite WASM + OPFS | IndexedDB Murni | Server-Side RDBMS via API |
| :--- | :--- | :--- | :--- |
| **Kueri Kompleks (JOIN/Aggregates)** | Sangat Cepat (Engine Relasional C) | Sangat Lambat (Manual filtering di JS) | Cepat (Tergantung resource server) |
| **Latensi Eksekusi** | Ultra Rendah (<2ms lokal) | Menengah (overhead serialisasi IDB) | Bergantung jaringan (50ms - 500ms) |
| **Payload Ukuran Aplikasi** | Tambahan ~1-2 MB (.wasm binary) | 0 KB (Native Browser API) | 0 KB (Hanya HTTP Client) |
| **Kebutuhan Header Khusus** | Butuh COOP/COEP jika pakai SharedArrayBuffer | Tidak ada | Tidak ada |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Web Worker Secara Eksklusif**: File access handle sinkron pada OPFS (`FileSystemSyncAccessHandle`) diblokir oleh browser jika dipanggil pada UI/Main Thread demi mencegah *frame drops*.
- **Konfigurasikan COOP/COEP Headers**: Pastikan web server menyajikan berkas HTML dengan header HTTP berikut:
  ```http
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  ```
  Ini mengaktifkan `SharedArrayBuffer` yang krusial untuk mekanisme locking VFS multithread SQLite.
- **Batch Mutasi dalam Transaksi Eksplisit**: Jangan mengeksekusi multiple *INSERT/UPDATE* satu per satu. Bungkus dalam `BEGIN TRANSACTION` dan `COMMIT` untuk meminimalkan *I/O sync locks* pada OPFS.

#### Don'ts
- **Jangan Simpan Objek Blobs/Images Berukuran Raksasa di Kolom SQLite**: Simpan berkas biner besar langsung di OPFS sebagai file terpisah atau Cache Storage API; cukup simpan path file atau pointer hash string di SQLite guna mencegah *database page fragmentation*.
- **Hindari Memory Leaks di SQLite Promiser**: Selalu bersihkan cursor atau batasi *unbounded queries*. SQLite WASM yang menumpuk B-tree pages pada heap memory dapat memicu OOM (*Out Of Memory*) fatal yang meng-crash tab browser.

#### Edge Cases
- **Quota Exceeded Handling**: Ketika penyimpanan browser perangkat klien (terutama pada iOS Safari) menyentuh batasan kuota storage, penulisan block B-Tree pada OPFS akan melempar *QuotaExceededError*. Aplikasi wajib menangani kueri `navigator.storage.estimate()` dan menangani fallback jika storage persisten ditolak oleh OS.
- **Tab Konkurensi Tanpa Shared Locks**: Jika dua tab browser membuka database OPFS yang sama menggunakan VFS yang tidak mendukung multi-threading lock, salah satu tab akan mengalami kegagalan *I/O Lock error*. Pastikan menggunakan model *Worker-per-application architecture* atau SharedWorker jika mendukung.

### 5. Tantangan Eksplorasi Mandiri

1. **Rancang Skema CRDT Sederhana pada SQLite**:
   Tambahkan kolom vector clock atau HLC (*Hybrid Logical Clock*) `node_id TEXT, hlc_timestamp TEXT` ke dalam tabel `documents`. Tulis skrip trigger SQL yang otomatis mengisi tabel log perubahan setiap kali ada operasi `INSERT` atau `UPDATE` untuk kebutuhan audit delta-syncing.
2. **Benchmarking OPFS vs. IndexedDB**:
   Buat skrip pengujian untuk memasukkan (insert) 20.000 data relasional kompleks ke dalam SQLite WASM (OPFS) versus IndexedDB murni. Ukur:
   - Waktu kompilasi dan eksekusi transaksi.
   - Waktu agregasi kueri (contoh: filtering bersyarat kompleks dengan `GROUP BY`).
   - Ukuran byte storage aktual yang dikonsumsi browser.
