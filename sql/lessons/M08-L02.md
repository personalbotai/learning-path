## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam sistem basis data relasional (RDBMS), properti **Isolation** dari akronim ACID (*Atomicity, Consistency, Isolation, Durability*) bertugas menjamin bahwa eksekusi transaksi yang berjalan bersamaan (*concurrent*) menghasilkan status akhir sistem yang sama seperti jika transaksi-transaksi tersebut dieksekusi secara serial (satu per satu).

Tanpa mekanisme isolasi yang tepat, sistem rentan terhadap anomali konkurensi:
1. **Dirty Read**: Transaksi A membaca data yang diubah oleh Transaksi B, padahal Transaksi B belum melakukan `COMMIT` dan kemudian melakukan `ROLLBACK`.
2. **Non-Repeatable (Fuzzy) Read**: Transaksi A membaca sebuah baris, lalu Transaksi B mengubah baris tersebut dan melakukan `COMMIT`. Saat Transaksi A membaca ulang baris tersebut, nilainya telah berubah.
3. **Phantom Read**: Transaksi A mengeksekusi query dengan rentang kondisi tertentu (misal: `WHERE age > 30`). Transaksi B menyisipkan (`INSERT`) baris baru yang memenuhi kondisi tersebut dan `COMMIT`. Saat Transaksi A mengulang query, muncul baris baru ("hantu").
4. **Serialization Anomaly / Write Skew**: Dua transaksi membaca dataset yang tumpang tindih secara bersamaan, mengevaluasi aturan bisnis yang valid, lalu menulis pembaruan pada data yang saling terpisah, namun gabungan dari kedua pembaruan tersebut melanggar batasan integritas data.

Untuk menyeimbangkan antara performa throughput dan konsistensi, standar ANSI/ISO SQL-92 menetapkan 4 Level Isolasi Transaksi:

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
| :--- | :---: | :---: | :---: |
| **Read Uncommitted** | Mungkin | Mungkin | Mungkin |
| **Read Committed** (Default PostgreSQL/Oracle) | Tidak | Mungkin | Mungkin |
| **Repeatable Read** (Default MySQL InnoDB) | Tidak | Tidak | Mungkin* |
| **Serializable** | Tidak | Tidak | Tidak |

*\*Catatan: MySQL InnoDB dan PostgreSQL mengeliminasi Phantom Read pada level Repeatable Read melalui implementasi MVCC dan Gap Locking.*

#### Dua Paradigma Kontrol Konkurensi

##### 1. Pessimistic Concurrency Control (Locking)
Pendekatan ini berasumsi bahwa konflik sering terjadi. DBMS menggunakan mekanisme penguncian (*Locking*) berbasis **Two-Phase Locking (2PL)**:
- **Shared Lock (S-Lock)**: Didapatkan saat operasi baca (`SELECT`). Banyak transaksi dapat memegang S-Lock pada baris yang sama.
- **Exclusive Lock (X-Lock)**: Didapatkan saat operasi modifikasi data (`INSERT`, `UPDATE`, `DELETE`, atau `SELECT ... FOR UPDATE`). Hanya satu transaksi yang dapat memegang X-Lock, dan memblokir S-Lock maupun X-Lock lainnya.
- **Intent Locks (IS / IX)**: Penguncian tingkat tabel untuk mengindikasikan bahwa transaksi bermaksud mengambil S atau X lock pada level baris, menghindari pemindaian penuh saat pemeriksaan lock tabel.

*Kelemahan murni 2PL:* Operasi baca memblokir operasi tulis, dan operasi tulis memblokir operasi baca. Hal ini memicu penurunan throughput konkurensi secara drastis (*contention*) dan rentan menghasilkan **Deadlock**.

##### 2. Multi-Version Concurrency Control (MVCC)
MVCC memecahkan paradigma saling blokir tersebut dengan prinsip: **"Readers do not block writers, and writers do not block readers."**

Alih-alih menimpa data langsung di tempat (*in-place overwrite*), MVCC mempertahankan beberapa versi historis dari sebuah baris data (*tuple*). Ketika transaksi membaca data, engine basis data memberikan "snapshot" logis dari data tersebut sesuai dengan *timestamp* atau *Transaction ID (XID)* transaksi yang bersangkutan.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sistem Dompet Digital (*E-Wallet*). Dua proses mencoba menarik saldo secara bersamaan dari akun yang sama (kondisi *Race Condition* / *Lost Update*).

Berikut simulasi penanganan menggunakan isolasi bawaan dan *Explicit Row Locking*:

```sql
-- Setup Skema & Data Awal
CREATE TABLE wallets (
    wallet_id INT PRIMARY KEY,
    user_id INT NOT NULL,
    balance NUMERIC(15, 2) NOT NULL CHECK (balance >= 0)
);

INSERT INTO wallets (wallet_id, user_id, balance) 
VALUES (1, 101, 500000.00);
```

#### Simulasi Anti-Pattern: Lost Update (Read Committed Default)
Jika dua sesi mengeksekusi script ini secara paralel tanpa lock:

```sql
-- SESI 1                              -- SESI 2
BEGIN;                                 BEGIN;
SELECT balance                         SELECT balance 
FROM wallets                           FROM wallets 
WHERE wallet_id = 1;                   WHERE wallet_id = 1;
-- Hasil: 500.000                      -- Hasil: 500.000

-- Aplikasi menghitung:                -- Aplikasi menghitung:
-- 500.000 - 200.000 = 300.000         -- 500.000 - 400.000 = 100.000

UPDATE wallets                         
SET balance = 300000.00                
WHERE wallet_id = 1;                   
                                       UPDATE wallets 
                                       SET balance = 100000.00 
                                       WHERE wallet_id = 1; 
                                       -- Terblokir menunggu Sesi 1 COMMIT
COMMIT;
                                       -- Sesi 2 lanjut & menimpa saldo!
                                       COMMIT;
-- HASIL AKHIR: Saldo 100.000 (Seharusnya transaksi Sesi 2 gagal karena saldo tidak cukup!)
```

#### Solusi 1: Pessimistic Locking (`SELECT FOR UPDATE`)
Gunakan Exclusive Lock pada level baris agar pembacaan dan pembaruan terisolasi secara deterministik.

```sql
-- Eksekusi aman dalam level READ COMMITTED
BEGIN;

-- Mengakuisisi Exclusive Lock (X-Lock) pada baris wallet_id = 1.
-- Transaksi lain yang memanggil FOR UPDATE / UPDATE pada baris ini akan masuk antrean (blocked).
SELECT balance 
FROM wallets 
WHERE wallet_id = 1 
FOR UPDATE;

-- Lakukan validasi di layer aplikasi: balance >= nominal_tarik
-- Eksekusi pembaruan
UPDATE wallets 
SET balance = balance - 200000.00 
WHERE wallet_id = 1;

COMMIT; -- Lock dilepas otomatis saat COMMIT/ROLLBACK
```

#### Solusi 2: Optimistic Check / Atomic Update
Memanfaatkan row-level atomic write tanpa `SELECT FOR UPDATE` eksplisit:

```sql
BEGIN;

-- Mutasi atomik dengan kondisi pra-syarat
UPDATE wallets 
SET balance = balance - 200000.00 
WHERE wallet_id = 1 AND balance >= 200000.00;

-- Periksa 'rows affected' di aplikasi.
-- Jika affected rows == 0, rollback dan throw Exception: Insufficient Funds.
COMMIT;
```

#### Solusi 3: Menggunakan Isolation Level `REPEATABLE READ` atau `SERIALIZABLE`

```sql
-- Ubah isolation level pada level transaksi
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM wallets WHERE wallet_id = 1;

-- Jika Sesi lain mengubah baris wallet_id = 1 dan COMMIT sebelum baris di bawah ini dieksekusi:
UPDATE wallets 
SET balance = balance - 200000.00 
WHERE wallet_id = 1;
-- PostgreSQL akan melempar error: 
-- ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)

COMMIT;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Arsitektur MVCC: PostgreSQL vs. MySQL InnoDB

Cara penyimpanan versi data berbeda signifikan antar storage engine:

```
[PostgreSQL: Append-Only Heap]
Heap Page:
+-------------------------------------------------------------+
| Tuple V1 (xmin: 100, xmax: 105) -> [balance: 500k] (Dead)  |
| Tuple V2 (xmin: 105, xmax: 0)   -> [balance: 300k] (Live)  |
+-------------------------------------------------------------+

[MySQL InnoDB: Rollback Segment / Undo Log]
Clustered Index Page:
+-------------------------------------------------------------+
| Current Row -> [balance: 300k] (DB_TRX_ID: 105)             |
|                DB_ROLL_PTR --------------------+            |
+------------------------------------------------|------------+
                                                 |
                                                 v
Undo Tablespace (Undo Log Chain):
[ Undo Record V1: balance: 500k (DB_TRX_ID: 100) ]
```

##### 1. PostgreSQL (Append-Only Tuples)
Setiap record (tuple) di disk memiliki metadata internal di headernya:
- `xmin`: ID transaksi (*XID*) yang membuat/menyisipkan tuple tersebut.
- `xmax`: ID transaksi yang menghapus atau memperbarui tuple tersebut (operasi `UPDATE` direpresentasikan sebagai `DELETE` versi lama + `INSERT` versi baru).

Ketika sebuah query dijalankan:
- Query mengambil snapshot dari *active transactions list*.
- Tuple berstatus **terlihat (visible)** jika `xmin` sudah berstatus `COMMITTED` sebelum snapshot dibuat, dan `xmax` bernilai 0 atau belum committed.
- **Dampak**: Versi lama dari tuple tetap berada di file tabel (*Heap*) sebagai *dead tuple*. Basis data membutuhkan proses **VACUUM** latar belakang secara berkala untuk membersihkan dead tuple dan mencegah *table bloat*.

##### 2. MySQL (InnoDB Undo Logs)
- InnoDB memodifikasi data langsung pada indeks kluster (*in-place update* pada buffer pool/disk).
- Versi data lama disalin ke struktur data khusus bernama **Undo Log**.
- Setiap baris memiliki pointer tersembunyi `DB_ROLL_PTR` yang menunjuk ke rantai versi (*undo chain*) dan `DB_TRX_ID` yang mencatat transaksi terakhir pembuat perubahan.
- Saat transaksi lama membutuhkan snapshot data sebelum modifikasi, engine menelusuri rantai pointer undo log ke belakang untuk merekonstruksi citra baris data yang konsisten.
- Pembersihan (*purge*) pada Undo Log dilakukan otomatis oleh thread InnoDB ketika tidak ada lagi transaksi aktif yang membutuhkan snapshot versi lama tersebut.

#### Lock Manager & Alokasi Resource
RDBMS mengelola lock menggunakan struktur data **Hash Table** di *Shared Memory*:
- Kunci hash dibentuk dari: `(DatabaseID, TableID, PageID, TupleOffset)`.
- Ketika transaksi meminta lock pada tuple yang sedang di-lock eksklusif oleh transaksi lain, transaksi tersebut dialihkan ke status `WAITING` pada antrean (*wait queue*) semafor sistem operasi.
- Engine mengaktifkan algoritma **Deadlock Detection** (berjalan pada interval tertentu, misal `deadlock_timeout` di Postgres atau `innodb_deadlock_detect` di MySQL). Algoritma ini membangun **Directed Wait-For Graph (WFG)**. Jika terdeteksi siklus tertutup ($T1 \to T2 \to T1$), basis data akan menghentikan paksa (*abort/rollback*) salah satu transaksi (umumnya transaksi dengan biaya rollback terkecil) dan melempar error konkurensi ke aplikasi.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Pertahankan transaksi sesingkat mungkin**: Ambil koneksi dari pool, proses manipulasi data, lalu segera `COMMIT` atau `ROLLBACK`. Jangan biarkan transaksi terbuka saat menunggu komputasi CPU yang berat atau respons I/O jaringan.
- **Urutkan akuisisi lock secara konsisten**: Jika Transaksi A memperbarui tabel `A` lalu tabel `B`, pastikan Transaksi B juga memperbarui tabel `A` lalu tabel `B`. Mengubah data dengan urutan terbalik di beberapa modul adalah penyebab utama deadlock.
- **Implementasikan Mekanisme Retry pada Error Serialisasi**: Di level `REPEATABLE READ` atau `SERIALIZABLE`, tangani error state `40001` (*serialization_failure*) atau `40P01` (*deadlock_detected*) dengan retry terprogram menggunakan pola *exponential backoff*.

```python
# Pola penanganan Retry Transaksi (Pseudo-code)
MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    try:
        with db.transaction(isolation_level="REPEATABLE_READ"):
            execute_business_logic()
            break
    except SerializationFailureException:
        if attempt == MAX_RETRIES - 1:
            raise
        sleep(2 ** attempt * 0.1)
```

#### Don'ts
- **JANGAN memanggil External API / I/O lambat di dalam blok transaksi**:
  ```sql
  BEGIN;
  SELECT ... FOR UPDATE; -- Mengunci baris
  -- JANGAN: HTTP Call ke Payment Gateway selama 3 detik di sini!
  -- Transaksi lain akan terblokir dan thread pool basis data akan cepat habis.
  UPDATE ...;
  COMMIT;
  ```
- **Hindari penggunaan isolation level `SERIALIZABLE` secara global**: Tingkat isolasi ini memerlukan overhead tracking dependensi yang sangat mahal (*predicate locks / SSI*). Gunakan `READ COMMITTED` sebagai basis, dan tingkatkan isolasi secara selektif per transaksi bila mutlak diperlukan.
- **Hindari pembaruan tanpa index**: `UPDATE ... WHERE non_indexed_column = x` pada transaksi dengan isolation level tinggi dapat memaksa engine melakukan lock pada SELURUH baris tabel (*table-wide lock* atau scanning lock), melumpuhkan seluruh konkurensi sistem.

#### Edge Cases
- **Long-Running Queries memicu Table Bloat / Undo Spikes**: 
  - Pada PostgreSQL: Query `SELECT` yang berjalan berjam-jam menahan batas `xmin`, mencegah `VACUUM` membersihkan dead tuple di seluruh database.
  - Pada MySQL: Undo tablespace akan membengkak drastis karena sistem tidak dapat melakukan *purge* pada undo log chain.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Metadata MVCC (PostgreSQL)**:
   Buat tabel pengujian dengan 1 baris data. Jalankan query internal:
   ```sql
   SELECT xmin, xmax, * FROM your_table;
   ```
   Lakukan `UPDATE` pada baris tersebut tanpa menghapusnya, lalu query kembali field `xmin` dan `xmax`. Analisis bagaimana nilai tersebut berubah. Gunakan ekstensi `pageinspect` (`heap_page_items`) untuk melihat bagaimana tuple lama tetap tersimpan di disk sebelum di-`VACUUM`.

2. **Rekayasa Deadlock Manual**:
   Buka dua jendela terminal terpisah ke database Anda.
   - Sesi 1: `BEGIN; UPDATE table_a SET col = 1 WHERE id = 1;`
   - Sesi 2: `BEGIN; UPDATE table_b SET col = 2 WHERE id = 2;`
   - Sesi 1: `UPDATE table_b SET col = 1 WHERE id = 2;` (Sesi 1 akan terblokir/menunggu)
   - Sesi 2: `UPDATE table_a SET col = 2 WHERE id = 1;`
   Amati pesan error yang dikeluarkan oleh database engine dan periksa log file database untuk melihat analisis Directed Graph dari deadlock tersebut.
