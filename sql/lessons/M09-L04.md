## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Keamanan database modern mengadopsi pendekatan *Defense in Depth* (pertahanan berlapis). Dalam konteks SQL dan RDBMS, tiga pilar utama untuk melindungi data sensitif (seperti PII - *Personally Identifiable Information* atau PCI - *Payment Card Industry*) adalah **Enkripsi**, **Data Masking**, dan **RBAC (Role-Based Access Control)**.

1.  **Enkripsi (Encryption):**
    *   **TDE (Transparent Data Encryption):** Mengenkripsi data *at rest* (di level disk/file fisik). Database engine secara otomatis mendekripsi data saat dimuat ke memori (Buffer Pool). Ini melindungi dari pencurian fisik media penyimpanan.
    *   **Column-Level Encryption:** Mengenkripsi data pada level kolom tertentu menggunakan fungsi kriptografi. Data tetap terenkripsi di dalam memori dan hanya didekripsi saat *query* dieksekusi dengan kunci yang tepat.
    *   **Hashing:** Digunakan untuk kredensial (password). Berbeda dengan enkripsi yang *reversible* (bisa dikembalikan), hashing bersifat *one-way*.
2.  **Data Masking (Dynamic Data Masking / DDM):**
    Fitur ini menyembunyikan data sensitif di lapisan presentasi (hasil *query*) tanpa mengubah data asli di dalam *storage*. Tujuan utamanya adalah mencegah *exposure* data sensitif kepada pengguna yang tidak memiliki hak akses penuh (misalnya: *Customer Service* hanya melihat 4 digit terakhir kartu kredit).
3.  **RBAC (Role-Based Access Control):**
    Mekanisme otorisasi yang memisahkan *User* (pengguna/aplikasi) dari *Privileges* (hak akses). Alih-alih memberikan hak akses langsung ke *User*, hak akses diberikan ke sebuah *Role* (peran), dan *User* di- *assign* ke *Role* tersebut. Ini menyederhanakan manajemen akses dan menegakkan *Principle of Least Privilege* (PoLP).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi komprehensif menggunakan dialek **PostgreSQL** (untuk RBAC & Kriptografi) dan **SQL Server (T-SQL)** (karena memiliki dukungan DDM native yang menjadi standar industri).

```sql
-- ==========================================
-- 1. RBAC (Role-Based Access Control) - PostgreSQL
-- ==========================================

-- Membuat Role (Grup)
CREATE ROLE data_analyst;
CREATE ROLE app_service;

-- Memberikan hak akses spesifik ke Role
GRANT CONNECT ON DATABASE e_commerce TO data_analyst;
GRANT USAGE ON SCHEMA public TO data_analyst;
GRANT SELECT ON TABLE users, orders TO data_analyst; -- Analyst hanya bisa baca

GRANT SELECT, INSERT, UPDATE ON TABLE users, orders TO app_service; -- App bisa modifikasi

-- Membuat User (Login) dan memasukkannya ke dalam Role
CREATE USER alice WITH PASSWORD 'StrongP@ssw0rd!';
GRANT data_analyst TO alice;

CREATE USER backend_api WITH PASSWORD 'ApiS3cr3t!';
GRANT app_service TO backend_api;

-- ==========================================
-- 2. Enkripsi Kolom & Hashing - PostgreSQL (menggunakan ekstensi pgcrypto)
-- ==========================================
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE secure_users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    password_hash TEXT NOT NULL,
    credit_card_enc BYTEA NOT NULL -- Disimpan dalam format biner (Ciphertext)
);

-- Insert data: Hashing password (Bcrypt) & Enkripsi Symmetric (AES) untuk CC
INSERT INTO secure_users (username, password_hash, credit_card_enc)
VALUES (
    'bob_user',
    crypt('MySecretPassword', gen_salt('bf', 10)), -- Hashing dengan Blowfish (Bcrypt) cost 10
    pgp_sym_encrypt('4111222233334444', 'MasterKey123') -- Enkripsi AES
);

-- Verifikasi Login & Dekripsi Data
SELECT 
    username,
    pgp_sym_decrypt(credit_card_enc, 'MasterKey123') AS decrypted_cc
FROM secure_users
WHERE username = 'bob_user' 
  AND password_hash = crypt('MySecretPassword', password_hash); -- Validasi hash

-- ==========================================
-- 3. Dynamic Data Masking (DDM) - SQL Server (T-SQL)
-- ==========================================
CREATE TABLE customers (
    id INT IDENTITY PRIMARY KEY,
    first_name VARCHAR(50),
    email VARCHAR(100) MASKED WITH (FUNCTION = 'email()'), -- Masking format email
    credit_card VARCHAR(19) MASKED WITH (FUNCTION = 'partial(0, "XXXX-XXXX-XXXX-", 4)') -- Tampil: XXXX-XXXX-XXXX-4444
);

INSERT INTO customers (first_name, email, credit_card)
VALUES ('Charlie', 'charlie@example.com', '4111-2222-3333-4444');

-- User tanpa hak 'UNMASK' akan melihat:
-- first_name | email             | credit_card
-- Charlie    | cXXX@XXXX.com     | XXXX-XXXX-XXXX-4444

-- Memberikan hak akses agar user tertentu bisa melihat data asli
GRANT UNMASK TO data_analyst;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime:**
  - **RBAC:** Pengecekan otorisasi terjadi pada fase *Parse & Bind* di dalam *Query Execution Pipeline*. Sebelum *Query Optimizer* membuat *Execution Plan*, *engine* memvalidasi apakah *session user* memiliki *privilege* di *System Catalog* (misal: `pg_class`, `pg_roles` di Postgres). Jika gagal, eksekusi dihentikan seketika (Error 403/Permission Denied).
  - **Data Masking:** *Query Optimizer* memodifikasi *Execution Plan*. Saat data diambil dari *storage* ke memori, data masih asli. Namun, sebelum dikirim ke *client* (fase *Projection*), *engine* menerapkan fungsi *string manipulation* (masking) secara *on-the-fly* berdasarkan konteks *user session*.
- **Alokasi Memori / Resource:**
  - **Enkripsi Kolom:** Sangat membebani CPU (*CPU-bound*). Setiap baris yang di- *scan* dan di- *decrypt* memerlukan siklus CPU untuk operasi kriptografi. Data terenkripsi (Ciphertext) juga memakan ruang penyimpanan (dan memori di *Buffer Pool*) lebih besar daripada *Plaintext* karena adanya *padding* dan *metadata* enkripsi (seperti *Initialization Vector* / IV).
- **Trade-offs:**
  - **Keamanan vs Performa:** Mengenkripsi kolom yang sering di- *query* (terutama di klausa `WHERE`) akan mematikan fungsi *Index* (karena *Index* tidak bisa membaca *Ciphertext* acak), memaksa database melakukan *Full Table Scan* yang sangat lambat.
  - **Masking vs Enkripsi:** Masking **bukan** enkripsi. Data asli masih berada di memori database. Jika seorang *attacker* mendapatkan akses *dump* memori atau akses *sysadmin*, masking tidak akan melindungi data tersebut.

### 4. Best Practices & Common Pitfalls

- **Do's:**
  - **Terapkan Principle of Least Privilege (PoLP):** Berikan hak akses seminimal mungkin. Aplikasi hanya boleh melakukan `SELECT`, `INSERT`, `UPDATE`, jangan pernah berikan hak `DROP` atau `ALTER` ke *user* aplikasi.
  - **Gunakan Role, Bukan User:** Jangan pernah melakukan `GRANT` langsung ke *User*. Buatlah *Role* (misal: `read_only_role`, `etl_role`), lalu masukkan *User* ke *Role* tersebut. Ini mempermudah audit dan *onboarding/offboarding* karyawan.
  - **Gunakan Row-Level Security (RLS):** Jika aplikasi bersifat *multi-tenant* (SaaS), gunakan RLS agar *User A* tidak bisa melihat baris data milik *User B* di level database engine.
- **Don'ts:**
  - **Jangan Menyimpan Kunci Enkripsi di Database yang Sama:** Menyimpan *Master Key* di tabel yang sama dengan data terenkripsi sama saja dengan mengunci pintu rumah tapi menaruh kuncinya di gagang pintu. Gunakan KMS (*Key Management Service*) eksternal (AWS KMS, HashiCorp Vault).
  - **Jangan Menggunakan MD5 atau SHA1 untuk Password:** Algoritma ini sudah usang dan rentan terhadap *Rainbow Table attacks*. Gunakan **Bcrypt, Scrypt, atau Argon2** yang memiliki mekanisme *Salting* dan *Work Factor* (memperlambat proses hashing secara sengaja).
- **Edge Cases:**
  - **Connection Pooling & RBAC:** Aplikasi modern sering menggunakan *Connection Pooler* (seperti PgBouncer) dengan satu *database user* (misal: `app_user`). Dalam kasus ini, RBAC tradisional sulit diterapkan per-pengguna aplikasi. Solusinya adalah menggunakan *Session Variables* (misal: `SET LOCAL app.current_user_id = 123;`) yang dikombinasikan dengan *Row-Level Security* (RLS).

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Multi-Tenant dengan RLS:** Buatlah tabel `invoices` dengan kolom `tenant_id`. Aktifkan *Row-Level Security* (RLS) di PostgreSQL dan buat *Policy* agar *user* hanya bisa melakukan `SELECT` pada *invoice* yang memiliki `tenant_id` miliknya sendiri.
2. **Audit & Privilege Escalation:** Buat skenario di mana sebuah *Role* memiliki hak `EXECUTE` pada sebuah *Stored Procedure* yang berjalan dengan hak akses `SECURITY DEFINER` (mengeksekusi dengan hak pembuat fungsi, bukan pemanggil). Analisis bagaimana ini bisa menjadi celah keamanan (*Privilege Escalation*) jika input tidak divalidasi.
3. **Performance Impact Analysis:** Buat tabel dengan 1 juta baris. Bandingkan waktu eksekusi (menggunakan `EXPLAIN ANALYZE`) antara mencari data menggunakan kolom *plaintext* yang di- *index*, dengan mencari data menggunakan kolom yang dienkripsi secara simetris (di mana dekripsi harus dilakukan di klausa `WHERE`).
