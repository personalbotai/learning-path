## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Kotlin dirancang dengan prinsip *100% Java Interoperability*. Artinya, kode Kotlin dan Java dapat hidup berdampingan dalam satu proyek, dikompilasi bersama (*bi-directional interoperability*), dan saling memanggil tanpa *overhead wrapper* runtime khusus. Keduanya dikompilasi menjadi Java Bytecode standar yang dieksekusi di atas Java Virtual Machine (JVM).

```
+--------------------+      +--------------------+
|    Source Java     |      |   Source Kotlin    |
|    (*.java)        |      |      (*.kt)        |
+--------------------+      +--------------------+
          \                          /
     javac \                        / kotlinc
            v                      v
        +------------------------------+
        |     JVM Bytecode (*.class)   |
        |   (Metadata, Mangling, etc.) |
        +------------------------------+
                       |
                       v
        +------------------------------+
        |         JVM Runtime          |
        +------------------------------+
```

Namun, karena Kotlin memiliki fitur sistem tipe yang lebih ekspresif daripada Java (seperti *first-class null safety*, *default parameter values*, *properties*, *extension functions*, dan visibilitas `internal`), compiler Kotlin (`kotlinc`) menggunakan serangkaian konvensi, metadata, dan bytecode synthesis untuk menjembatani perbedaan tersebut:

1. **Platform Types (`T!`)**: Java tidak memaksakan *null safety* pada tingkat bahasa. Ketika tipe Java dibaca oleh Kotlin tanpa anotasi nullability (`@Nullable`/`@NotNull`), Kotlin memperlakukannya sebagai *Platform Type* (dinotasikan sebagai `T!`). Tipe ini memberi kebebasan bagi developer untuk memperlakukannya sebagai *nullable* (`T?`) atau *non-null* (`T`), memindahkan tanggung jawab pengecekan runtime sepenuhnya ke developer.
2. **Property vs Getter/Setter**: Java mengekspos state melalui konvensi JavaBean (*getters/setters*). Kotlin secara otomatis memetakan `getX()` dan `setX()` milik Java menjadi properti Kotlin `x`, dan sebaliknya, properti Kotlin dikompilasi menjadi *private field* dengan *public getter/setter* sintetis di bytecode.
3. **Top-Level Functions & Facades**: Java mewajibkan semua kode berada di dalam kelas. Kotlin mengizinkan *top-level function*. Compiler menyelesaikan inkonsistensi ini dengan membungkus fungsi-fungsi top-level ke dalam sebuah *Facade Class* bernama `<NamaFile>Kt.class`.
4. **Interoperability Annotations**: Kotlin menyediakan anotasi khusus (`@JvmStatic`, `@JvmOverloads`, `@JvmField`, `@JvmName`, `@Throws`) untuk menginstruksikan compiler agar memodifikasi bentuk bytecode yang dihasilkan agar lebih natural (*idiomatic*) ketika diakses dari Java.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Modul pemrosesan transaksi keuangan yang mengintegrasikan *legacy Java service* dengan *modern Kotlin engine*.

#### Bagian A: Kode Java yang Dipanggil dari Kotlin
File: `LegacyPaymentGateway.java`
```java
package com.engine.interop;

import java.io.IOException;
import org.jetbrains.annotations.NotNull;
import org.jetbrains.annotations.Nullable;

public class LegacyPaymentGateway {
    private final String merchantId;

    public LegacyPaymentGateway(String merchantId) {
        this.merchantId = merchantId;
    }

    public String getMerchantId() {
        return merchantId;
    }

    // Explicit Nullability Annotation
    public @Nullable String processPayment(@NotNull String transactionId, double amount) throws IOException {
        if (amount <= 0) {
            throw new IOException("Invalid amount");
        }
        return "SUCCESS_AUTH_" + transactionId;
    }

    // Java SAM (Single Abstract Method) Interface
    public interface PaymentCallback {
        void onComplete(String status);
    }

    public void registerCallback(PaymentCallback callback) {
        callback.onComplete("REGISTERED");
    }
}
```

#### Bagian B: Kode Kotlin Mengonsumsi Java & Mengekspos API untuk Java
File: `PaymentProcessor.kt`
```kotlin
@file:JvmName("PaymentUtils") // Mengubah nama facade class untuk Java

package com.engine.interop

import java.io.IOException

// 1. Memanggil Java dari Kotlin
fun executeTransaction(gateway: LegacyPaymentGateway, txId: String, amount: Double) {
    // Properti Java diakses langsung dengan sintaks properti Kotlin (bukan gateway.getMerchantId())
    println("Using Merchant: ${gateway.merchantId}")

    try {
        // Platform Type ditangani: Kotlin mengenali anotasi @Nullable dan @NotNull dari Java
        val authCode: String? = gateway.processPayment(txId, amount)
        println("Auth Code: ${authCode?.lowercase() ?: "REJECTED"}")
    } catch (e: IOException) {
        // Kotlin tidak memiliki checked exception, namun tetap bisa menangkap IOException
        println("Failed: ${e.message}")
    }

    // SAM Conversion otomatis dari Lambda Kotlin ke Interface Java
    gateway.registerCallback { status ->
        println("Callback received: $status")
    }
}

// 2. Mengekspos Kode Kotlin agar Idiomatik di Java
class PaymentConfig @JvmOverloads constructor(
    // @JvmField mencegah pembuatan getter/setter, diekspos sebagai public field murni
    @JvmField val timeoutMs: Long = 5000L,
    val environment: String = "PRODUCTION"
) {
    companion object {
        // @JvmStatic menghasilkan method static asli pada level kelas PaymentConfig
        @JvmStatic
        fun defaultLiveConfig(): PaymentConfig = PaymentConfig()
    }

    // @Throws memberitahu compiler Java bahwa method ini melempar checked exception
    @Throws(IOException::class)
    fun validate() {
        if (timeoutMs < 1000L) {
            throw IOException("Timeout too short!")
        }
    }
}
```

#### Bagian C: Kode Java Mengonsumsi Kotlin
File: `Application.java`
```java
package com.engine.interop;

import java.io.IOException;

public class Application {
    public static void main(String[] args) {
        // 1. Memanggil top-level function via JvmName Facade
        LegacyPaymentGateway gateway = new LegacyPaymentGateway("MCH-9901");
        PaymentUtils.executeTransaction(gateway, "TX-12345", 250.0);

        // 2. Memanggil static method via @JvmStatic
        PaymentConfig config = PaymentConfig.defaultLiveConfig();

        // 3. Mengakses public field langsung via @JvmField
        System.out.println("Timeout: " + config.timeoutMs);

        // 4. Menggunakan konstruktor overloading berkat @JvmOverloads
        PaymentConfig customConfig = new PaymentConfig(10000L); // Default parameter environment dipakai

        // 5. Menangani @Throws; Java mewajibkan try-catch karena ini Checked Exception
        try {
            customConfig.validate();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **@JvmStatic**: Secara bawaan, fungsi di dalam `companion object` dikompilasi sebagai method instance pada singleton companion (`PaymentConfig.Companion.defaultLiveConfig()`). Anotasi `@JvmStatic` menginstruksikan `kotlinc` untuk membuat **metode delegasi statis sintetis** pada kelas pembungkus (`PaymentConfig.class`) yang meneruskan panggilan ke instance Companion:
  ```java
  // Representasi dekompilasi PaymentConfig.class
  public static final PaymentConfig defaultLiveConfig() {
      return Companion.defaultLiveConfig();
  }
  ```
- **Name Mangling untuk Visibilitas `internal`**: Identifier dengan visibilitas `internal` di-mangle di tingkat bytecode (misal: `doInternal$module_name()`) untuk mencegah pemanggilan yang tidak disengaja oleh klien Java. Di Java, fungsi ini tetap terlihat sebagai fungsi `public` dengan nama yang telah di-mangle.
- **Checked Exceptions via `@Throws`**: Kotlin tidak memiliki konsep checked exception. Semua eksepsi adalah unchecked. Anotasi `@Throws(IOException::class)` menambahkan atribut bytecode `Exceptions` pada method signature class file, yang dibaca oleh compiler Java (`javac`) saat validasi kompilasi.

#### Alokasi Memori / Resource
- **SAM Conversion**: Saat memanggil method Java yang menerima Functional Interface (SAM), compiler Kotlin menggunakan instruksi bytecode `invokedynamic` (pada Kotlin modern/JVM 1.8+) alih-alih selalu mengalokasikan instance kelas anonim baru, sehingga menekan overhead memori di heap untuk lambda yang bersifat *stateless*.
- **@JvmField**: Menghemat overhead pemanggilan method (*method invocation frame*) pada stack trace JVM dengan mengeliminasi method getter/setter sintetis dan mengizinkan instruksi `getfield`/`putfield` langsung.

#### Trade-offs
- Anotasi interoperabilitas menambahkan sedikit kompleksitas sintaksis pada kode dasar Kotlin murni.
- Kompilasi silang (*mixed Kotlin-Java compilation*) dalam satu modul memerlukan eksekusi bertahap (*Kotlin compile phase* menghasilkan stub Java terlebih dahulu sebelum `javac` memproses kode Java), yang sedikit meningkatkan waktu build dibanding proyek monolingual.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Selalu deklarasikan nullability eksplisit di Java**: Gunakan `@Nullable` dan `@NonNull` (JetBrains, AndroidX, atau Checker Framework) pada API Java agar Kotlin tidak memetakannya menjadi *Platform Type* yang rawan crash.
- **Terapkan `@file:JvmName` dan `@file:JvmMultifileClass`**: Menghindari ekspos nama file default (`...Kt`) ke konsumen Java untuk API publik modul.
- **Gunakan `@JvmOverloads` untuk fungsi/konstruktor dengan default arguments**: Ini memungkinkan developer Java menggunakan fitur *optional parameter* tanpa harus membuat overload secara manual di Kotlin.

#### Don'ts
- **Jangan abaikan Platform Types (`T!`)**: Menangani tipe dari Java tanpa validasi `?` atau pengecekan null dapat memicu `NullPointerException` runtime seketika pada instruksi bytecode `Intrinsics.checkNotNullParameter`.
- **Jangan lupa meletakkan `@Throws` jika method Kotlin melempar exception yang ingin di-handle Java**: Java mewajibkan penanganan checked exception. Tanpa `@Throws`, Java menganggap method Kotlin tidak melempar checked exception, sehingga Java tidak mengizinkan developer menulis blok `catch (IOException e)` di sekitarnya.

#### Edge Cases
- **Akses Properti dengan Prefiks `is`**: Properti Kotlin `var isEnabled: Boolean` dikompilasi menjadi `isEnabled()` dan `setEnabled()` di Java, bukan `getIsEnabled()`. Jika nama properti dimulai dengan `is`, Kotlin mempertahankan penamaan getter tersebut di Java.
- **Kata Kunci Java sebagai Identifier di Kotlin**: Jika Java memiliki method bernama sama dengan reserved keyword Kotlin (misal: `in`, `is`, `object`), gunakan tanda backtick (`` ` ``) di Kotlin untuk memanggilnya:
  ```kotlin
  val stream = `in`.read()
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Dekompilasi Bytecode**:
   Buat kelas Kotlin dengan `companion object` yang memiliki satu fungsi biasa dan satu fungsi beranotasi `@JvmStatic`. Dekompilasi file `.class` yang dihasilkan menggunakan IntelliJ IDEA (`Tools -> Kotlin -> Show Kotlin Bytecode -> Decompile`) dan bandingkan perbedaan struktur method yang dibuat oleh compiler.
2. **Platform Types Investigation**:
   Buat class Java dengan method yang me-return `null` tanpa anotasi nullability. Panggil method tersebut di Kotlin dan tetapkan hasilnya ke variabel bertipe non-nullable (`val res: String = javaClass.getValue()`). Analisis pada baris kode mana `NullPointerException` dilempar dan mengapa bytecode `Intrinsics` bertanggung jawab atas exception tersebut.
