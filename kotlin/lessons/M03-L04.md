### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa perangkat lunak, transformasi data dari struktur datar (*flat*) menjadi struktur berhierarki atau tersegmentasi merupakan operasi rutin. Kotlin Standard Library menyediakan abstraksi tingkat tinggi untuk kebutuhan ini melalui operasi **Grouping**, **Partitioning**, dan **Chunking**.

Secara konseptual dan arsitektural:

1. **Grouping (`groupBy` vs `groupingBy`)**:
   - `groupBy`: Membagi elemen koleksi ke dalam *N-bucket* dinamis berbasis nilai kunci yang diekstrak oleh lambda selector. Operasi ini bersifat *eager* dan menghasilkan `Map<K, List<V>>`.
   - `groupingBy`: Diperkenalkan di Kotlin 1.1 untuk memecahkan inefisiensi alokasi memori pada agregasi. Alih-alih langsung membuat `Map` berisi `List` sementara, fungsi ini mengembalikan antarmuka `Grouping<T, K>`. Ini adalah representasi *lazy/deferred* yang memungkinkan operasi seperti `eachCount()`, `fold()`, `reduce()`, atau `aggregate()` dieksekusi dalam satu *pass* langsung ke akumulator akhir.

2. **Partitioning (`partition`)**:
   - Spesialisasi biner dari grouping. Memisahkan koleksi menjadi dua subset eksklusif berdasarkan predikat Boolean `(T) -> Boolean`.
   - Menghasilkan `Pair<List<T>, List<T>>`, di mana komponen `.first` berisi elemen yang memenuhi syarat (`true`), dan `.second` berisi sisanya (`false`).

3. **Chunking (`chunked`)**:
   - Segmentasi linier non-overlapping dengan ukuran partisi tetap (*fixed-size batches*). Elemen terakhir dapat memiliki ukuran lebih kecil jika total elemen tidak habis dibagi ukuran chunk ($N \pmod{\text{size}} \neq 0$).
   - Di balik layar, `chunked` merupakan turunan khusus dari konsep sliding window (`windowed(size, step = size, partialWindows = true)`).

```
Flat Collection: [A1, B1, A2, A3, B2, C1]
                     │
     ┌───────────────┼───────────────┬────────────────┐
     ▼               ▼               ▼                ▼
[groupBy]      [groupingBy]     [partition]       [chunked(2)]
Map:           Grouping (Lazy)  Pair:             List of Lists:
A -> [A1,A2,A3] ──> fold()       First:  [A-elem]  [[A1, B1],
B -> [B1, B2]   ──> eachCount()  Second: [Others]   [A2, A3],
C -> [C1]       (Tanpa alokasi                      [B2, C1]]
                 List per key)
```

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Pemrosesan transaksi e-commerce skala tinggi. Kita perlu:
1. Memvalidasi transaksi (partisi transaksi valid vs fraud/invalid).
2. Menghitung metrik analitik tanpa alokasi memori berlebih via `groupingBy`.
3. Memecah transaksi valid ke dalam *batch* berukuran 50 untuk bulk-insert ke database via `chunked`.

```kotlin
package com.architect.collections

import java.math.BigDecimal

enum class PaymentStatus { SUCCESS, FAILED, PENDING }

data class Transaction(
    val id: String,
    val merchantId: String,
    val amount: BigDecimal,
    val status: PaymentStatus,
    val isFlaggedFraud: Boolean
)

fun main() {
    val transactions = listOf(
        Transaction("TX-001", "M-100", BigDecimal("150.00"), PaymentStatus.SUCCESS, false),
        Transaction("TX-002", "M-200", BigDecimal("500.00"), PaymentStatus.SUCCESS, true),
        Transaction("TX-003", "M-100", BigDecimal("200.00"), PaymentStatus.SUCCESS, false),
        Transaction("TX-004", "M-300", BigDecimal("75.50"), PaymentStatus.FAILED, false),
        Transaction("TX-005", "M-200", BigDecimal("120.00"), PaymentStatus.SUCCESS, false),
        Transaction("TX-006", "M-100", BigDecimal("990.00"), PaymentStatus.PENDING, false)
    )

    // 1. PARTITION: Memisahkan transaksi valid dan transaksi mencurigakan (Fraud)
    // Mengembalikan Pair<List<Transaction>, List<Transaction>> dalam single-pass.
    val (flaggedTransactions, cleanTransactions) = transactions.partition { it.isFlaggedFraud }
    println("Flagged Transactions: ${flaggedTransactions.map { it.id }}")

    // 2. GROUPINGBY + AGGREGATE (Optimal): Total omzet per merchant untuk transaksi sukses
    // Menghindari alokasi intermediate List<Transaction> untuk setiap merchant.
    val revenuePerMerchant: Map<String, BigDecimal> = cleanTransactions
        .asSequence()
        .filter { it.status == PaymentStatus.SUCCESS }
        .groupingBy { it.merchantId }
        .fold(BigDecimal.ZERO) { accumulator, tx ->
            accumulator.add(tx.amount)
        }
    println("Revenue per Merchant: $revenuePerMerchant")

    // 3. GROUPBY (Standard): Pengelompokan ID transaksi berdasarkan PaymentStatus
    val txIdsByStatus: Map<PaymentStatus, List<String>> = cleanTransactions.groupBy(
        keySelector = { it.status },
        valueTransform = { it.id } // Transformasi langsung elemen tanpa perlu .mapValues { ... }
    )
    println("Transactions by Status: $txIdsByStatus")

    // 4. CHUNKED: Batching transaksi valid untuk I/O write (misal: JDBC batch insert max 2 items)
    val batchSize = 2
    cleanTransactions.chunked(batchSize) { batch ->
        // Lambda transform opsional: batch diproses langsung sebelum chunk berikutnya dialokasikan
        persistToDatabase(batch)
    }
}

fun persistToDatabase(batch: List<Transaction>) {
    println("Executing batch insert for IDs: ${batch.map { it.id }}")
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **`groupBy`**:
  Menginisialisasi `LinkedHashMap<K, ArrayList<V>>()`. Iterasi dilakukan sekali melintasi koleksi sumber. Pada setiap elemen, fungsi menghitung nilai hash dari key via `keySelector(element)`. Jika key belum ada di map, alokasikan instance `ArrayList<V>` baru, lalu masukkan elemen tersebut. Kompleksitas waktu: $\mathcal{O}(N)$ rata-rata, dengan overhead hashing.
- **`groupingBy`**:
  Tidak menghasilkan struktur data apapun saat dipanggil. Fungsi ini hanya membuat instance *anonymous object* yang mengimplementasikan interface `Grouping<T, K>`. Saat fungsi terminal (seperti `aggregate` atau `eachCount`) dipanggil, Kotlin menggunakan `LinkedHashMap<K, R>` sebagai map akumulator. Khusus `eachCount()`, akumulator menggunakan kelas utilitas internal `kotlin.jvm.internal.Ref.IntRef` untuk memutasi angka *counter* tanpa overhead unboxing/boxing primitif berulang pada Java Heap.
- **`partition`**:
  Menginisialisasi dua instance `ArrayList` independen: `first = ArrayList<T>()` dan `second = ArrayList<T>()`. Loop `for-each` tunggal mengevaluasi predikat. Elemen langsung dimasukkan via referensi ke salah satu list, kemudian dibungkus ke dalam objek `Pair(first, second)`.
- **`chunked`**:
  Menggunakan iterator internal yang membungkus sub-array berukuran $N$. Jika transform lambda tidak disediakan, setiap chunk dialokasikan sebagai `ArrayList<T>(size)` baru yang kemudian dikumpulkan ke dalam `ArrayList<List<T>>`.

#### Alokasi Memori / Resource
| Operasi | Jumlah Alokasi Objek | Overhead Memori |
| :--- | :--- | :--- |
| `groupBy` | 1 `Map` + $K$ `ArrayList` + Boxing Key/Value | **Tinggi** (Menyimpan seluruh referensi elemen dalam struktur bercabang) |
| `groupingBy().eachCount()` | 1 `Map` + $K$ `IntRef` | **Rendah** (Hanya menyimpan key dan state agregasi) |
| `partition` | 1 `Pair` + 2 `ArrayList` | **Moderat** (Menduplikasi referensi elemen ke 2 list) |
| `chunked(N)` | 1 Outer `List` + $\lceil M/N \rceil$ Inner `List` | **Moderat-Tinggi** tergantung ukuran chunk |

#### Trade-offs
- Menggunakan `groupBy` diikuti dengan agregasi (`.groupBy().mapValues { it.value.size }`) adalah *anti-pattern* di Kotlin. Operasi ini mengalokasikan $K$ buah `ArrayList` sementara beserta *wrapper bucket*-nya hanya untuk membaca properti `.size`, lalu membuangnya ke Garbage Collector. Gunakan `groupingBy().eachCount()` yang memangkas alokasi tersebut hingga 90%.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `groupingBy` untuk operasi analitik/reduksi**: Selalu pilih `groupingBy().fold()`, `reduce()`, atau `eachCount()` ketimbang kombinasi `groupBy { }.map { }`.
- **Manfaatkan argumen transform bawaan**: Gunakan overload `groupBy(keySelector, valueTransform)` dan `chunked(size) { transform }` untuk menghindari iterasi ganda via operasi rantai `.map()`.
- **Definisikan batch size yang realistis pada `chunked`**: Sesuaikan ukuran chunk dengan batasan protokol jaringan atau database, misalnya *parameter limit* SQLite (maksimal 999 parameter) atau query batch size PostgreSQL (optimal 500–2000 baris).

#### Don'ts
- **Jangan gunakan `partition` jika hanya membutuhkan satu subset data**: Memanggil `partition` saat Anda hanya peduli pada elemen `true` adalah pemborosan memori karena list `second` tetap dialokasikan. Gunakan fungsi `filter` standar.
- **Hindari key nullable pada `groupBy` tanpa null-safety plan**: `groupBy` memperbolehkan `null` sebagai key (disimpan sebagai `Map<K?, List<T>>`). Namun, ini dapat memicu NPE tersembunyi pada consumer API hilir yang mengasumsikan map keys bersifat non-null.

#### Edge Cases
- **Koleksi Kosong**: `groupBy` dan `groupingBy` menghasilkan `emptyMap()`, `partition` menghasilkan `Pair(emptyList(), emptyList())`, dan `chunked` menghasilkan `emptyList()`. Tidak ada *exception* dilempar.
- **Nilai Chunk Size $\le 0$**: Memanggil `chunked(0)` atau `chunked(-1)` akan melempar runtime exception: `IllegalArgumentException: size must be greater than zero.`

1. **Custom Aggregate Engine**:
   Tulis ekstensi fungsi `fun <T, K> Grouping<T, K>.averageBy(selector: (T) -> Double): Map<K, Double>` menggunakan fungsi dasar `Grouping.aggregate` secara langsung. Hindari alokasi list perantara dan hitung rata-rata secara akumulatif dalam satu kali jalan (*single pass*).

2. **Windowing vs Chunking**:
   Pelajari fungsi `windowed(size, step)`. Implementasikan algoritma *moving average* (rata-rata bergerak) untuk data *time-series* saham dengan window size = 5 dan step = 1. Analisis perbedaan perilakunya dibanding `chunked(5)`.
