## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam domain ilmu komputer dan pemrograman fungsional, **Algebraic Data Types (ADT)** adalah sistem tipe komposit yang dibentuk dari kombinasi tipe data lain. ADT umumnya terbagi menjadi dua kategori utama:
1. **Product Types**: Tipe data yang nilainya merupakan kombinasi (*cartesian product*) dari field-field pembentuknya. Di Kotlin, ini direpresentasikan oleh `data class` atau `Tuple` (misal: `class Pair(val a: Int, val b: String)` dapat menampung kemungkinan sebanyak domain `Int` $\times$ domain `String`).
2. **Sum Types (Tagged Union / Disjoint Union)**: Tipe data yang nilainya hanya bisa berupa *salah satu* dari sekumpulan kemungkinan tipe yang telah didefinisikan secara eksplisit. Di Kotlin, Sum Types diimplementasikan melalui `sealed class` dan `sealed interface`.

```
                  Algebraic Data Types (ADT)
                         /          \
                        /            \
          Product Types                Sum Types
      (data class, Tuple)       (enum, sealed hierarchy)
      Nilai: A AND B             Nilai: A OR B
                                      |
                      +---------------+---------------+
                      |                               |
                 enum class               sealed class / interface
            (Instance tunggal,            (Bisa berupa object singleton
             state seragam)                maupun class ber-payload dinamis)
```

#### Evolusi: Dari `enum` ke `sealed class` dan `sealed interface`
Secara historis, `enum class` adalah bentuk Sum Type paling sederhana. Namun, setiap konstanta enum merepresentasikan instance tunggal (*singleton*) yang berbagi bentuk struktur data dan constructor yang persis sama. Enum tidak dapat menyimpan state yang bervariasi antar variannya.

`sealed class` memecahkan limitasi ini dengan membatasi hierarki pewarisan di tingkat compiler. Sejak Kotlin 1.5, cakupan pendefinisian subclass diperluas: semua subclass turunan dari sealed hierarchy harus berada di dalam **package yang sama** dan **kompilasi modul yang sama** (*compilation unit*).

Kehadiran `sealed interface` (diperkenalkan pada Kotlin 1.5) menutup celah keterbatasan pewarisan tunggal (*single inheritance*) pada JVM:
- Class turunan dapat mengimplementasikan beberapa `sealed interface` sekaligus (mendukung *multiple sum-type memberships*).
- Menghindari *memory & class footprint* yang diakibatkan oleh alokasi `java.lang.Object` superclass dari `sealed class`.
- Mendukung integrasi idiomatik dengan `value class` (inline classes) yang tidak dapat mewarisi class biasa, namun dapat mengimplementasikan interface.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah pemodelan arsitektur mutasi state untuk *Payment Processing Engine* yang menangani berbagai skenario transaksi menggunakan kombinasi `sealed interface`, `data class`, dan `data object`.

```kotlin
package com.engine.payment

import java.math.BigDecimal
import java.time.Instant
import java.util.UUID

// 1. Root Marker Sealed Interface
sealed interface PaymentResult {
    val transactionId: UUID
    val timestamp: Instant
}

// 2. Secondary Hierarchy untuk Domain Separation
sealed interface TerminalState : PaymentResult

// 3. Variant Concrete Implementations
// State: Transaksi Sukses dengan Payload Finansial
data class PaymentSuccess(
    override val transactionId: UUID,
    override val timestamp: Instant,
    val amount: BigDecimal,
    val approvalCode: String
) : TerminalState

// State: Transaksi Gagal dengan Error Metadata
data class PaymentFailed(
    override val transactionId: UUID,
    override val timestamp: Instant,
    val errorCode: String,
    val reason: String,
    val isRetryable: Boolean
) : TerminalState

// State: Transaksi Butuh Aksi Lanjutan (3D Secure / MFA)
data class ActionRequired(
    override val transactionId: UUID,
    override val timestamp: Instant,
    val redirectUrl: String,
    val sessionToken: String
) : PaymentResult

// State: Dibatalkan oleh Pengguna (Tidak butuh payload unik -> gunakan 'data object')
data class PaymentCancelled(
    override val transactionId: UUID,
    override val timestamp: Instant
) : TerminalState


// 4. Exhaustive State Evaluator
class PaymentProcessor {

    fun handlePaymentOutcome(result: PaymentResult): String = when (result) {
        // Compiler mengecek semua branch secara exhaustive.
        // Tidak memerlukan 'else' branch!
        is PaymentSuccess -> {
            "Payment ${result.transactionId} SUCCEEDED: ${result.approvalCode} " +
            "Amount: ${result.amount}"
        }
        is PaymentFailed -> {
            if (result.isRetryable) {
                "Payment ${result.transactionId} RETRYABLE ERROR: [${result.errorCode}] ${result.reason}"
            } else {
                "Payment ${result.transactionId} FATAL ERROR: [${result.errorCode}] ${result.reason}"
            }
        }
        is ActionRequired -> {
            "Payment ${result.transactionId} REDIRECT: ${result.redirectUrl}"
        }
        is PaymentCancelled -> {
            "Payment ${result.transactionId} CANCELLED by user."
        }
    }

    // Mengurangi cakupan hanya untuk sub-tipe tertentu
    fun archiveTransaction(terminalState: TerminalState) {
        when (terminalState) {
            is PaymentSuccess -> println("Archiving success receipt: ${terminalState.approvalCode}")
            is PaymentFailed  -> println("Archiving failure audit: ${terminalState.errorCode}")
            is PaymentCancelled -> println("Archiving cancellation log")
        }
    }
}

fun main() {
    val processor = PaymentProcessor()
    val txId = UUID.randomUUID()
    val now = Instant.now()

    val outcomes: List<PaymentResult> = listOf(
        PaymentSuccess(txId, now, BigDecimal("150000.00"), "APP-99812"),
        ActionRequired(UUID.randomUUID(), now, "https://bank.com/auth/3ds", "SEC-TOKEN-42"),
        PaymentFailed(UUID.randomUUID(), now, "ERR_INSUFFICIENT_FUNDS", "Saldo tidak cukup", false),
        PaymentCancelled(UUID.randomUUID(), now)
    )

    outcomes.forEach { outcome ->
        println(processor.handlePaymentOutcome(outcome))
        if (outcome is TerminalState) {
            processor.archiveTransaction(outcome)
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Modifier Accessibility**:
   Pada dekompilasi bytecode Kotlin ke Java, sebuah `sealed class` diterjemahkan menjadi abstract class dengan constructor berstatus `private` atau `protected` (package-private):
   ```java
   public abstract class BaseSealedClass {
       private BaseSealedClass() {}
       public /*synthetic*/ BaseSealedClass(DefaultConstructorMarker $constructor_marker) {
           this();
       }
   }
   ```
   Hal ini secara fisik mencegah class di luar compilation unit untuk memperluas (*extends*) class tersebut, karena constructor tidak bisa diakses dari file bytecode lain di luar context kompilasi.

2. **JVM Permitted Subclasses (Java 17+ Target)**:
   Jika target JVM diset ke level 17 atau lebih tinggi (`-jvm-target=17`), compiler `kotlinc` memanfaatkan fitur resmi JVM Sealed Classes. Bytecode class header akan mengikutsertakan atribut `PermittedSubclasses`:
   ```bytecode
   public abstract sealed interface com/engine/payment/PaymentResult
       permits com/engine/payment/PaymentSuccess, 
               com/engine/payment/PaymentFailed, 
               com/engine/payment/ActionRequired, 
               com/engine/payment/PaymentCancelled, 
               com/engine/payment/TerminalState
   ```
   JVM runtime secara native memverifikasi constraint ini saat class-loading, meningkatkan performa type-checking dan refleksi.

3. **Verifikasi Exhaustiveness di `when`**:
   Kotlin compiler membaca metadata `@kotlin.Metadata` pada sealed interface/class untuk mendapatkan daftar seluruh subclass sah. Evaluasi `when` di level bytecode ditransformasikan menjadi deretan instruksi `instanceof` bertingkat (*type check sequence*) atau *tableswitch/lookupswitch* bila memungkinkan:
   ```bytecode
   INSTANCEOF com/engine/payment/PaymentSuccess
   IFNE L1
   INSTANCEOF com/engine/payment/PaymentFailed
   IFNE L2
   ...
   ```
   Jika developer tidak menyertakan semua branch dan tidak menyediakan `else`, compiler akan melempar kesalahan kompilasi: *`'when' expression must be exhaustive`*.

#### Alokasi Memori / Resource
- Subclass berjenis `data object` hanya dibuat sekali di runtime heap (singleton pattern statis di JVM), menghemat alokasi memori secara masif jika state tersebut di-dispatch jutaan kali (seperti state `Idle` atau `Cancelled`).
- Penggunaan `sealed interface` tidak membebankan *superclass overhead* sehingga representasi objek di JVM murni hanya membawa memory layout dari class konkret masing-masing, memotong overhead hierarki objek.

#### Trade-offs
- **Binary Compatibility**: Menambahkan subclass baru ke dalam `sealed hierarchy` merupakan *breaking change* bagi modul consumer downstream, karena ekspresi `when` consumer yang sebelumnya exhaustive akan mendadak gagal dikompilasi (*compile-time failure*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `data object` alih-alih `object` biasa** untuk varian tanpa payload (Kotlin 1.9+). `data object` secara otomatis meng-override method `toString()`, `equals()`, dan `hashCode()` dengan representasi nama class yang jelas, sangat esensial untuk logging dan debugging state.
- **Biarkan `when` bersifat natural exhaustive**: Hindari menaruh `else` branch pada `when` expression yang mengevaluasi sealed types. Tujuan utama sealed types adalah **memaksa compiler berteriak** ketika Anda menambahkan varian baru di masa depan.
- **Gunakan `sealed interface` sebagai default**: Utamakan `sealed interface` daripada `sealed class` kecuali Anda benar-benar perlu menurunkan property/fungsi concrete dengan *backing field* atau logic reusable.

#### Don'ts
- **Anti-pattern Defensive `else`**:
  ```kotlin
  // SANGAT TIDAK DIREKOMENDASIKAN
  when (result) {
      is PaymentSuccess -> handleSuccess()
      is PaymentFailed  -> handleFailed()
      else -> logUnknown() // BAHAYA: Menutupi bug jika ada ActionRequired baru ditambahkan!
  }
  ```
- **Menyimpan State Mutabel dalam Sealed Hierarchy**: Semua subclass dalam sealed type idealnya bersifat *immutable* (`val`). Jika state diubah secara in-place di runtime, prinsip prediktabilitas ADT menjadi rusak.

#### Edge Cases
- **Polymorphic Serialization (JSON)**:
  Library seperti `kotlinx.serialization` membutuhkan anotasi `@Serializable` dan `@JsonClassDiscriminator` pada sealed class/interface untuk melakukan mapping polymorphic data dari JSON ke specific subtype. Pastikan serial discriminator disepakati (misal: field `"type": "PaymentSuccess"`).
- **Subclass di File yang Berbeda**:
  Sejak Kotlin 1.5, Anda dapat mendistribusikan subclass ke file yang berbeda asalkan berada dalam package yang sama dan source set yang sama. Namun, memecah subclass ke terlalu banyak file acak dapat menurunkan readability pembacaan domain ADT.

### 5. Tantangan Eksplorasi Mandiri

1. **State Machine Parser Matematika (AST)**:
   Rancang sebuah *Abstract Syntax Tree* (AST) untuk ekspresi matematika sederhana menggunakan `sealed interface Expr`. Definisikan varian `Const(val value: Double)`, `Add(val left: Expr, val right: Expr)`, `Multiply(val left: Expr, val right: Expr)`, dan `Negate(val expr: Expr)`. Buat fungsi evaluasi rekursif: `fun eval(e: Expr): Double` yang menghitung total matematisnya tanpa `else`.
2. **Inspeksi Bytecode Javap**:
   Kompilasi sealed class dengan `kotlinc`, kemudian jalankan perintah `javap -c -p NamaClassSealed.class` di terminal Anda. Identifikasi akses visibility dari constructor-nya dan buktikan bagaimana compiler memblokir inisialisasi dari luar modul.
