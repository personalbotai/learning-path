## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sistem visibilitas (*visibility modifiers*) dan pengorganisasian kode (*packages*) dalam Kotlin dirancang untuk memperbaiki ambiguitas dan kelemahan enkapsulasi yang ada pada Java, dengan tetap mempertahankan interoperabilitas 100% pada tingkat JVM bytecode.

```
+-----------------------------------------------------------------------------------+
| KOTLIN VISIBILITY SCOPE                                                           |
|                                                                                   |
|  +-------------------+  +-----------------------+  +---------------------------+  |
|  |    Top-Level      |  |     Class Member      |  |      Compilation Unit     |  |
|  | (File Scope)      |  |                       |  |       (Module Scope)      |  |
|  +-------------------+  +-----------------------+  +---------------------------+  |
|  | - public (default)|  | - public (default)    |  | - internal                |  |
|  | - private         |  | - private             |  |   (Terlihat dalam satu    |  |
|  | - internal        |  | - protected           |  |    Gradle/Maven Module)   |  |
|  |                   |  | - internal            |  |                           |  |
|  +-------------------+  +-----------------------+  +---------------------------+  |
+-----------------------------------------------------------------------------------+
```

#### Paket (Packages) & Decoupling Direktori
Berbeda dengan Java yang mewajibkan struktur folder fisik merefleksikan hierarki *package* secara ketat, Kotlin memisahkan deklarasi paket dari sistem berkas fisik. Sebuah file beralamat di `src/main/kotlin/legacy/Utils.kt` dapat mendeklarasikan `package com.enterprise.core.telemetry`. Walaupun konvensi merekomendasikan keselarasan antara direktori fisik dan paket, pemisahan logis ini memberikan fleksibilitas pada *refactoring* dan *multi-platform architecture* (Kotlin Multiplatform).

Paket di Kotlin juga menjadi *namespace* bagi deklarasi **Top-Level** (fungsi, konstanta, kelas, dan antarmuka di luar deklarasi `class`). Ini mengeliminasi kebutuhan pembuatan *utility class* statis palsu seperti `DateUtils` atau `MathHelper` ala Java.

#### Matriks Visibilitas: Filosofi & Perbedaan dari Java

1. **Default Visibility adalah `public`**: Berbeda dengan Java yang menggunakan *default* *package-private* (tanpa modifier), Kotlin mengadopsi *default* `public`. Filosofi Kotlin menganggap pembatasan harus dinyatakan secara eksplisit dan disengaja.
2. **`private`**:
   - *Class Member*: Hanya dapat diakses di dalam tubuh kelas tersebut, termasuk *companion object* dan *inner class*.
   - *Top-Level*: Terisolasi murni di dalam satu file fisik Kotlin (`.kt`). Dua file dalam satu paket yang sama **tidak dapat** melihat deklarasi *top-level* `private` satu sama lain.
3. **`protected`**:
   - Hanya valid untuk *class member* (ilegal pada level *top-level*).
   - Berbeda drastis dengan Java: Anggota bertipe `protected` di Kotlin **hanya** dapat diakses oleh kelas itu sendiri dan subkelasnya. Kotlin **menutup** akses dari kelas lain meskipun berada dalam satu paket yang sama (Java mengizinkan akses satu paket untuk `protected`).
4. **`internal`**:
   - Modifier struktural modularitas Kotlin. Deklarasi hanya terlihat di dalam modul kompilasi yang sama (*Gradle source set*, target Maven, atau IntelliJ module). Fitur ini mengatasi kebocoran implementasi internal SDK/library yang sebelumnya sering terekspos karena Java hanya mengenal pembatasan paket.

### 2. Implementasi & Contoh Kasus Nyata

Struktur modular berikut mendemonstrasikan sistem orkestrasi transaksi keuangan dengan enkapsulasi berlapis.

#### Berkas 1: `CryptoEngine.kt`
```kotlin
package com.enterprise.payment.security

import java.security.SecureRandom
import java.util.Base64

// Top-level private: Hanya visible dalam berkas 'CryptoEngine.kt'
private val secureRandom = SecureRandom()
private const val IV_SIZE = 16

// Top-level internal: Terlihat di seluruh modul payment-core, 
// tetapi tersembunyi dari modul consumer luar (e.g. app-module)
internal class CryptoEngine(private val masterKeyAlias: String) {

    // Member internal: API implementasi untuk service internal
    internal fun encrypt(plainBytes: ByteArray): ByteArray {
        val iv = generateIv()
        // Menggunakan simposium enkripsi simulasi
        return iv + plainBytes.map { it xor 0x5A }.toByteArray()
    }

    // Member private: Hanya untuk internal mesin ini
    private fun generateIv(): ByteArray {
        val iv = ByteArray(IV_SIZE)
        secureRandom.nextBytes(iv)
        return iv
    }
}

// Top-level internal factory function
internal fun createDefaultCryptoEngine(): CryptoEngine {
    return CryptoEngine(masterKeyAlias = "KEY_VAULT_PROD_01")
}
```

#### Berkas 2: `TransactionProcessor.kt`
```kotlin
package com.enterprise.payment.core

// Penggunaan import alias untuk menghindari naming collision
import com.enterprise.payment.security.CryptoEngine
import com.enterprise.payment.security.createDefaultCryptoEngine
import java.time.Instant

// Public class: API terbuka yang diekspos keluar library/modul
abstract class BaseTransactionProcessor(
    // Protected property: Hanya bisa diakses oleh subkelas turunan
    protected val engineType: String
) {
    // Protected abstract function: Subkelas wajib mengimplementasikan
    protected abstract fun validateProcessorState(): Boolean

    // Public method: Titik masuk consumer eksternal
    fun verifyIntegrity(): Boolean {
        return validateProcessorState()
    }
}

class CardTransactionProcessor internal constructor(
    // Injeksi CryptoEngine (internal class) di constructor internal
    private val cryptoEngine: CryptoEngine = createDefaultCryptoEngine()
) : BaseTransactionProcessor(engineType = "HSM-HARDWARE-V2") {

    // Override harus mempertahankan visibilitas protected atau dinaikkan (public)
    // Tidak boleh diturunkan menjadi private.
    override fun validateProcessorState(): Boolean {
        return engineType.isNotBlank()
    }

    // Public API untuk memproses transaksi
    fun processPayment(cardPayload: String): String {
        require(validateProcessorState()) { "Processor is invalid state" }
        
        val encryptedData = cryptoEngine.encrypt(cardPayload.toByteArray(Charsets.UTF_8))
        return "TX-${Instant.now().epochSecond}-${encryptedData.size}"
    }
}
```

#### Berkas 3: Penggunaan Eksternal (`Main.kt`)
```kotlin
package com.enterprise.payment

import com.enterprise.payment.core.CardTransactionProcessor

fun main() {
    // Akses publik yang valid
    val processor = CardTransactionProcessor()
    val txHash = processor.processPayment("4111222233334444|12/26|123")
    println("Transaction executed: $txHash")

    // KOMPILASI ERROR jika uncomment:
    // processor.validateProcessorState() -> ERROR: Cannot access 'validateProcessorState': it is protected in 'CardTransactionProcessor'
    // CryptoEngine() -> ERROR: Cannot access 'CryptoEngine': it is internal in 'com.enterprise.payment.security' (jika beda modul)
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime pada Level Bytecode
Arsitektur JVM tidak memiliki konsep asli untuk *Kotlin-specific features* seperti `internal` dan *top-level private*. Kotlin Compiler (`kotlinc`) melakukan translasi mekanis melalui transformasi bytecode:

1. **Transformasi `internal` & Name Mangling:**
   JVM hanya mengenal modifier `public`, `protected`, `private`, dan *package-private*. Karena JVM tidak memiliki konsep *module isolation*, Kotlin mengompilasi member `internal` menjadi `public` pada bytecode JVM.
   Untuk mencegah kode Java eksternal atau kelas lain memanggil fungsi `internal` secara tidak sengaja, `kotlinc` menerapkan **Name Mangling**:
   
   ```
   // Deklarasi Kotlin:
   internal fun processData() { ... }

   // Dekompilasi Bytecode Java:
   public final void processData$module_name() { ... }
   ```
   Karakter `$` menandakan nama termutilasi (*mangled*). Kode Kotlin dari modul yang sama mengetahui konvensi ini dan dapat memanggilnya secara transparan, namun kompiler Java akan memandangnya sebagai metode bernama aneh yang sulit diakses secara langsung.

2. **Top-Level `private`:**
   Deklarasi *top-level* dikompilasi menjadi kelas pembungkus statis (*file-facade*), misal `CryptoEngineKt.class`. 
   Fungsi dan variabel *top-level* `private` dikompilasi menjadi metode dan field `private static` di dalam `CryptoEngineKt.class`. Karena sifat visibilitas JVM `private` mengikat pada file class pembungkus, file Kotlin lain (yang dikompilasi menjadi file class terpisah) secara teknis terblokir dari mengaksesnya pada tingkat runtime.

3. **Metadata Annotation (`@Metadata`):**
   Kotlin menyematkan anotasi `@Metadata` pada setiap file `.class`. Anotasi biner ini menyimpan informasi AST (Abstract Syntax Tree), seperti visibilitas murni Kotlin (`isInternal`, `isProtectedKotlin`), yang dibaca oleh `kotlinc` saat melakukan analisis kompilasi dependensi.

#### Alokasi Memori / Resource
- **Zero Runtime Overhead:** Visibility modifier adalah abstraksi waktu kompilasi (*compile-time enforcement*). Tidak ada alokasi memori heap tambahan atau instansiasi *lookup table* untuk mengevaluasi hak akses saat aplikasi berjalan.
- **Accessor Synthetics:** Jika sebuah `private` member dalam suatu kelas diakses oleh *nested class* (sebelum Java 11 Nestmates), kompiler membuat *synthetic method* `access$000` dengan scope package-private, yang menimbulkan *minor footprint* berupa beberapa byte instruksi tambahan pada JVM *method area* (*Metaspace*).

#### Trade-offs: `internal` vs Keamanan Penuh
`internal` bukanlah mekanisme keamanan kriptografis (*sandboxing*). Karena di level JVM method tersebut dikompilasi menjadi `public`, runtime manapun dapat membypass batasan ini menggunakan Java Reflection (`Method.setAccessible(true)`) atau dengan memanggil nama fungsi yang termutilasi secara manual dari bahasa Java (`engine.processData$core_release()`).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Terapkan Modul Terisolasi dengan `internal`**: Gunakan `internal` untuk menyembunyikan kelas infrastruktur jaringan, DTO database, dan utilitas enkripsi dalam library atau modul fitur, hanya ekspos Interface dan Factory Publik.
- **Top-Level `private` untuk Scope Lokalisasi**: Letakkan ekstensi khusus atau konstanta *regex* parsing sebagai `private` top-level di dalam file parser itu sendiri untuk menjaga polusi namespace global.
- **Manfaatkan `@PublishedApi` secara Sadar**: Jika fungsi `inline public` memerlukan akses ke fungsi/properti `internal`, tandai deklarasi internal tersebut dengan `@PublishedApi internal`. Ini memberi sinyal eksplisit bahwa secara biner, fungsi internal tersebut menjadi bagian dari kontrak publik karena kode akan di-inlining ke modul pemanggil.

#### Don'ts
- **Jangan Mengandalkan `protected` untuk Keamanan Satu Paket**: Mengasumsikan `protected` di Kotlin dapat dibaca oleh file lain di paket yang sama (seperti di Java). Jika butuh visibilitas satu paket/modul, gunakan `internal`.
- **Hindari Polusi Global Namespace**: Jangan membiarkan fungsi pembantu umum (`fun String.clean(): String`) berada di top-level dengan visibilitas `public` di root package. Ini akan muncul di auto-complete seluruh proyek.

#### Edge Cases
- **Java Interoperability Leakage:**
  Saat membuat library Kotlin untuk dikonsumsi pengguna Java, `internal` modifiers akan tampak sebagai `public` (dengan nama mangled).
  *Solusi*: Gunakan anotasi `@JvmSynthetic` pada fungsi internal jika ingin metode tersebut diabaikan total oleh kompiler Java:
  ```kotlin
  @JvmSynthetic
  internal fun internalOnlyLogic() { ... }
  ```
- **Overriding Member Visibility:**
  Kotlin mengizinkan penaikan visibilitas saat melakukan *override*, tetapi melarang penurunannya:
  ```kotlin
  open class Parent {
      protected open fun run() {}
  }
  class Child : Parent() {
      // VALID: Menaikkan visibilitas
      public override fun run() {} 
      
      // ILLEGAL: Kompilasi error jika menurunkan ke private
      // private override fun run() {}
  }
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Bytecode Dekompilasi**:
   Buat sebuah file `SecuredVault.kt` berisi class dengan visibilitas `internal` dan method `internal`. Kompilasi menggunakan `kotlinc`, lalu jalankan utilitas terminal JVM:
   ```bash
   javap -p -c SecuredVault.class
   ```
   Analisis bagaimana nama metode diubah (*mangled*) dan bagaimana modifier `public` diterapkan oleh JVM.

2. **Eksploitasi Interop Java-Kotlin**:
   Buat file Java di direktori proyek yang sama, lalu coba panggil deklarasi Kotlin bertanda `internal` tersebut. Buktikan bahwa Java dapat mengeksekusinya jika Anda memanggil nama *mangled*-nya secara manual. Gunakan `@JvmName` dan amati apakah modifier dan nama mangling berubah.

3. **Eksplorasi Aturan Inline & PublishedApi**:
   Buat fungsi `internal fun executeSecretAlgorithm()` dan fungsi `public inline fun executePublicPipeline()`. Coba panggil fungsi internal dari dalam fungsi *inline public* tersebut tanpa menambahkan `@PublishedApi`. Amati pesan kesalahan kompilasi yang dihasilkan oleh `kotlinc` dan pahami alasan mengapa aturan inlining mengharuskan stabilitas biner pada level visibilitas.
