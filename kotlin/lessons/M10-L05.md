### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem backend Kotlin, terdapat dua paradigma dominan: **Ktor** (asynchronous, un-opinionated, lightweight framework yang dibangun dari nol untuk Coroutines) dan **Spring Boot** (opinionated enterprise framework berbasis dependency injection container yang kini mengadopsi first-class support untuk Kotlin Coroutines).

```
+-------------------------------------------------------------------------+
|                              Ktor Server                                |
|  Routing DSL -> Pipeline Phases (Setup -> Monitoring -> Call)           |
|  Engine: Netty / CIO (Coroutine I/O) -> Coroutine Dispatcher            |
|  Footprint: Minimalis (~30MB base), No Reflection Runtime               |
+-------------------------------------------------------------------------+
                                    VS
+-------------------------------------------------------------------------+
|                        Spring Boot 3 + WebFlux                          |
|  DispatcherHandler -> Suspend Controller -> Invocation Handler (Proxy)  |
|  Engine: Reactor Netty -> Reactive Streams Bridge -> Coroutines         |
|  Footprint: Enterprise-grade (~150MB+ base), Reflection & Bean Graph    |
+-------------------------------------------------------------------------+
```

#### Arsitektur Ktor Server
Ktor dirancang dengan filosofi modular berbasis pipeline. Inti dari Ktor bukanlah sekadar router HTTP, melainkan serangkaian interceptor pipeline terurut:
* **Pipeline Phases**: Setiap request melewati fase deterministik: `Setup`, `Monitoring`, `Plugins`, `Call`, dan `Fallback`.
* **Coroutines-Native**: Tidak memerlukan adapter reactive streams. Ktor mengeksekusi request langsung di dalam Coroutine context yang dikelola oleh *Application Engine* (seperti Netty atau engine native Ktor yaitu CIO/Coroutine I/O).
* **Ekstensibilitas via Plugins**: Fitur seperti autentikasi, serialisasi data, dan kompresi diimplementasikan sebagai *Plugin* terpisah yang diinjeksi ke fase pipeline spesifik tanpa overhead refleksi runtime.

#### Arsitektur Spring Boot dengan Kotlin
Spring Framework 5/6 mengintegrasikan Kotlin secara mendalam melalui extensions dan custom method resolvers:
* **Spring WebFlux Integration**: Pada layer arsitektur non-blocking, Spring memanfaatkan Project Reactor (`Mono`/`Flux`). Kotlin Coroutines diintegrasikan menggunakan jembatan adapter: fungsi `suspend` diubah secara internal menjadi publisher `Mono<T>` oleh `CoroutinesUtils`.
* **Inversion of Control (IoC) & Metaprogramming**: Spring tetap bertumpu pada `ApplicationContext`. Ia melakukan inspeksi metadata class via reflection atau compile-time processing (AOT pada GraalVM), membungkus target service menggunakan CGLIB/JDK dynamic proxies untuk menangani aspek transaksional (`@Transactional`) dan keamanan.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Pembangunan endpoint non-blocking untuk mengambil data agregasi profil pengguna dan memproses payload secara asinkron.

#### A. Implementasi Ktor Server (Modern Ktor 3.x)

```kotlin
package com.example.ktor

import io.ktor.http.*
import io.ktor.serialization.kotlinx.json.*
import io.ktor.server.application.*
import io.ktor.server.engine.*
import io.ktor.server.netty.*
import io.ktor.server.plugins.contentnegotiation.*
import io.ktor.server.response.*
import io.ktor.server.routing.*
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext
import kotlinx.serialization.Serializable
import kotlinx.serialization.json.Json

@Serializable
data class UserProfile(val id: String, val username: String, val role: String)

// Simulasi operasi database blocking yang diisolasi ke dispatcher terpisah
suspend fun queryDatabase(userId: String): UserProfile = withContext(Dispatchers.IO) {
    // Simulasi I/O latency
    Thread.sleep(50) // Hanya contoh mock blocking I/O legacy
    UserProfile(id = userId, username = "octocat", role = "ADMIN")
}

fun Application.module() {
    // 1. Install Content Negotiation menggunakan kotlinx.serialization (Zero Reflection)
    install(ContentNegotiation) {
        json(Json {
            prettyPrint = false
            isLenient = true
            ignoreUnknownKeys = true
        })
    }

    // 2. Deklarasi Pipeline Routing
    routing {
        route("/api/v1/users") {
            get("/{id}") {
                val userId = call.parameters["id"]
                    ?: return@get call.respond(HttpStatusCode.BadRequest, "Missing User ID")

                // Langsung memanfaatkan coroutine suspension point
                val profile = queryDatabase(userId)
                call.respond(HttpStatusCode.OK, profile)
            }
        }
    }
}

fun main() {
    embeddedServer(Netty, port = 8080, host = "0.0.0.0", module = Application::module)
        .start(wait = true)
}
```

#### B. Implementasi Spring Boot 3.x (WebFlux + Coroutines)

```kotlin
package com.example.spring

import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext
import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.runApplication
import org.springframework.http.HttpStatus
import org.springframework.http.ResponseEntity
import org.springframework.stereotype.Service
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.PathVariable
import org.springframework.web.bind.annotation.RequestMapping
import org.springframework.web.bind.annotation.RestController

data class UserProfile(val id: String, val username: String, val role: String)

@Service
class UserService {
    suspend fun getProfile(userId: String): UserProfile = withContext(Dispatchers.IO) {
        Thread.sleep(50) // Mock blocking I/O legacy
        UserProfile(id = userId, username = "spring_user", role = "USER")
    }
}

@RestController
@RequestMapping("/api/v1/users")
class UserController(private val userService: UserService) {

    // Spring mendeteksi keyword 'suspend' dan mendelegasikannya ke Reactor Bridge
    @GetMapping("/{id}")
    suspend fun getUserById(@PathVariable id: String): ResponseEntity<UserProfile> {
        val profile = userService.getProfile(id)
        return ResponseEntity.ok(profile)
    }
}

@SpringBootApplication
class Application

fun main(args: Array<String>) {
    runApplication<Application>(*args)
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
* **Ktor Server**:
  * Request HTTP diterima oleh Netty EventLoop, dikonversi menjadi instance `ApplicationCall`.
  * Request disalurkan melalui `Pipeline` bertipe asynchronous. Setiap interceptor dieksekusi dalam Coroutine context milik request tersebut.
  * Ketika mencapai suspension point (misal: panggilan IO network), thread EventLoop terbebas untuk menangani ribuan paket request lain tanpa menunggu respons database selesai.
* **Spring Boot (WebFlux Integration)**:
  * Controller dengan modifier `suspend` di-*wrap* saat startup oleh Spring.
  * Di balik layar, Spring membungkus eksekusi fungsi menggunakan `org.springframework.core.CoroutinesUtils.invokeSuspendingFunction(...)`.
  * Objek `Continuation` disuntikkan secara dinamis ke parameter terakhir method, mentransformasikan `suspend fun` menjadi representasi non-blocking `Mono` milik reactive core Project Reactor.

#### Alokasi Memori / Resource
* **Startup footprint & Metaspace**:
  * **Ktor**: Hanya memuat class yang dipanggil langsung oleh kode kita. Tidak memerlukan classpath scanning skala besar. Cold start runtime sangat singkat (< 1 detik), konsumsi Metaspace memori JVM rendah.
  * **Spring Boot**: Melakukan pemindaian anotasi (`@Component`, `@Autowired`, dll.), menginisialisasi reflection cache, dan membangun tree dependensi dependency injection. Startup time lebih lama, konsumsi Metaspace jauh lebih tinggi (~100-200MB lebih besar daripada Ktor pada baseline aplikasi).

#### Trade-offs: Kapan Memilih Ktor vs Spring Boot
| Aspek | Ktor Server | Spring Boot |
| :--- | :--- | :--- |
| **Gaya Desain** | Un-opinionated, Library-centric | Opinionated, Framework-centric |
| **Dependency Injection** | Manual / Eksternal (Koin, Kodein) | Built-in IoC Container (Otomatis) |
| **Ekosistem Enterprise** | Perlu konfigurasi manual (JPA, Security) | Ready-to-use (Spring Data, Spring Security) |
| **Cold Start / Resources**| Sangat ideal untuk Serverless/Edge/Microservices | Ideal untuk Complex Enterprise Monolith/Microservices |

### 4. Best Practices & Common Pitfalls

#### Do's
* **Isolasi Dispatcher Secara Ketat**: Selalu delegasikan operasi I/O blocking (seperti JDBC driver tradisional) ke `withContext(Dispatchers.IO)`. Membiarkan operasi blocking berjalan di thread default Netty/Ktor akan menyebabkan *thread starvation* total pada seluruh service.
* **Manfaatkan Serialisasi Compile-Time**: Gunakan `kotlinx.serialization` alih-alih reflection-based serializers (seperti standard Jackson ObjectMapper) untuk memaksimalkan performa parsing JSON di kedua framework.

#### Don'ts
* **Jangan Mencampur Reactive Monad dan Coroutines Sembarangan**: Di Spring WebFlux, hindari pemanggilan chaining `.subscribe()` manual di dalam `suspend fun`. Gunakan extension method resmi Spring seperti `.awaitSingle()`, `.awaitFirstOrNull()`, atau manipulasi stream langsung via `Flow<T>`.
* **Hindari `runBlocking` di Route/Controller**: Jangan pernah menggunakan `runBlocking` di dalam blok rute Ktor atau endpoint Spring Boot untuk menunggu hasil synchronous; ini merusak konsep thread pooling asinkron dan berisiko tinggi memicu deadlock.

#### Edge Cases & Pitfalls
* **Coroutine Context & ThreadLocal Propagation (MDC Tracing)**:
  Tracing request menggunakan library logging tradisional (SLF4J MDC) berbasis pada Java `ThreadLocal`. Karena Coroutines dapat berpindah thread di tengah eksekusi setelah suspension point, context logging bisa hilang atau bocor ke request lain.
  
  *Solusi*: Gunakan `MDCContext` dari modul `kotlinx-coroutines-slf4j`:
  ```kotlin
  import kotlinx.coroutines.slf4j.MDCContext
  import org.slf4j.MDC

  MDC.put("traceId", UUID.randomUUID().toString())
  withContext(MDCContext()) {
      // traceId akan selalu terjaga lintas suspension points & thread switches
      logger.info("Handling sensitive transaction")
  }
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Benchmarking & Thread-Starvation Simulation**:
   Bangun service sederhana dengan endpoint yang memanggil thread blocking `Thread.sleep(100)` langsung di dalam rute Ktor (tanpa `Dispatchers.IO`). Gunakan benchmarking tool seperti `wrk` atau `k6` dengan 100 concurrent connections. Amati throughput latency-nya. Kemudian bungkus operasi tersebut dengan `withContext(Dispatchers.IO)` dan amati perbedaan performa throughput serta resource utilization-nya.

2. **Implementasi Custom Interceptor/Plugin**:
   Buat custom Ktor Plugin bernama `ExecutionTimerPlugin` yang mengukur durasi setiap fase pipeline dari `RequestReceived` hingga respons terkirim secara utuh. Tulis header respons kustom `X-Response-Time-Ms` yang mengekspos metrik runtime tersebut ke client.
