## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

*Type-Safe Builders* di Kotlin memungkinkan pembuatan *Domain-Specific Language* (DSL) internal yang deklaratif, aman secara tipe data (*compile-time safety*), dan terbaca layaknya bahasa alami atau format konfigurasi (seperti JSON/YAML/HTML), namun tetap berjalan di atas ekosistem *statically typed* JVM.

Konsep ini dirancang untuk memecahkan kelemahan pola Builder tradisional di Java:
1. **Verbosity**: Memerlukan *method chaining* panjang (`.setX().setY()`).
2. **Lack of Hierarchy**: Sulit merepresentasikan struktur data bersarang (*nested trees*) tanpa kode yang kaku.
3. **Runtime Error**: Hilangnya konteks hierarki sering kali menyebabkan kegagalan validasi baru terdeteksi saat *runtime*.

#### Fondasi Arsitektur DSL Kotlin
Kotlin DSL bukan fitur tunggal dari compiler, melainkan sintesis dari beberapa fitur bahasa:

1. **Function Literals with Receiver (`T.() -> Unit`)**:
   Lambda di mana *scope* eksekusi memiliki instance target (`this`) tanpa harus menyebutkannya secara eksplisit. Fitur ini mengubah paradigma pemanggilan fungsi dari *argument-passing* menjadi *contextual mutation*.
2. **Scope Control via `@DslMarker`**:
   Mekanisme anotasi compiler untuk mencegah *scope leakage* (kebocoran konteks antar builder bersarang). Compiler menganalisis hierarki pemanggilan dan melarang akses implisit ke receiver luar jika memiliki marker yang sama.
3. **Operator Overloading & Infix Notation**:
   Memberikan sintaks gramatikal natural, seperti membebaskan kode dari tanda kurung dan titik (`"Content-Type" to "application/json"` atau `invoke()` convention).

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Perancangan DSL untuk konfigurasi HTTP Request Pipeline yang aman dari *scope leakage*.

```kotlin
// 1. Definisikan DSL Marker Annotation untuk isolasi scope
@DslMarker
@Target(AnnotationTarget.CLASS, AnnotationTarget.TYPE)
annotation class HttpRequestDsl

// 2. Immutable Output Models
data class Request(
    val url: String,
    val method: String,
    val headers: Map<String, String>,
    val body: String?
)

// 3. Mutable Builders
@HttpRequestDsl
class HeadersBuilder {
    private val headers = mutableMapOf<String, String>()

    infix fun String.to(value: String) {
        headers[this] = value
    }

    fun build(): Map<String, String> = headers.toMap()
}

@HttpRequestDsl
class RequestBuilder {
    var url: String = ""
    var method: String = "GET"
    private var headers: Map<String, String> = emptyMap()
    private var bodyContent: String? = null

    // Nested Builder dengan Receiver Lambda
    fun headers(block: HeadersBuilder.() -> Unit) {
        headers = HeadersBuilder().apply(block).build()
    }

    fun body(block: () -> String) {
        bodyContent = block()
    }

    fun build(): Request {
        require(url.isNotBlank()) { "URL cannot be blank" }
        return Request(url, method, headers, bodyContent)
    }
}

// 4. Entry-point Function
inline fun httpRequest(block: RequestBuilder.() -> Unit): Request {
    return RequestBuilder().apply(block).build()
}

// 5. Penggunaan DSL
fun main() {
    val clientRequest = httpRequest {
        url = "https://api.internal.infra/v1/deploy"
        method = "POST"

        headers {
            "Authorization" to "Bearer token-xyz-99"
            "Accept" to "application/json"
            
            // Scope Leakage dicegah:
            // url = "https://malicious.com" // COMPILE ERROR: @HttpRequestDsl melarang akses receiver luar
        }

        body {
            """{"service": "auth-service", "replicas": 3}"""
        }
    }

    println(clientRequest)
}
```

#### Penjelasan Komponen Kunci
- `HeadersBuilder.() -> Unit`: Parameter ini adalah lambda dengan receiver. Di dalam blok eksekusi, fungsi `infix fun String.to(value: String)` dapat langsung dipanggil karena `HeadersBuilder` bertindak sebagai `this`.
- `@HttpRequestDsl`: Mencegah instans `RequestBuilder` diakses dari dalam blok `headers { ... }` tanpa kualifikasi eksplisit `this@httpRequest`.
- `inline fun httpRequest(...)`: Menginstruksikan compiler untuk menyalin bytecode isi lambda secara langsung di *call-site*, mengeliminasi overhead alokasi objek lambda saat runtime.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Bytecode
Secara representasi bytecode JVM, *Lambda with Receiver* diubah menjadi objek turunan antarmuka fungsional bawaan `kotlin.jvm.functions.Function1` atau `Function2`.

Kode Kotlin:
```kotlin
fun headers(block: HeadersBuilder.() -> Unit)
```
Diterjemahkan oleh compiler (`kotlinc`) ke dalam representasi signature Java/JVM:
```java
public final void headers(Function1<? super HeadersBuilder, Unit> block) {
    HeadersBuilder builder = new HeadersBuilder();
    block.invoke(builder); // Receiver diteruskan sebagai argumen pertama
    this.headers = builder.build();
}
```
Ketika dieksekusi, JVM tidak mengenal konsep `this` implisit milik Kotlin. Compiler mengubah setiap akses properti atau fungsi implisit di dalam lambda menjadi pemanggilan metode pada instance parameter pertama tersebut (`builder.method()`).

#### Scope Enforcement via Metadata
Anotasi `@DslMarker` tidak memiliki efek performa runtime (`AnnotationRetention.BINARY`). Pada fase analisis semantik (*frontend compilation*), compiler Kotlin memeriksa *lexical scope stack*. Jika dua receiver implisit pada *stack* memiliki kelas yang diannotasikan dengan `@DslMarker` yang sama, compiler secara otomatis membatalkan resolusi nama untuk receiver yang lebih luar dan melempar *compile-time error*.

#### Alokasi Memori & Resource
- **Builder Overhead**: DSL instansiasi memisahkan status builder yang *mutable* dan model data yang *immutable*. Objek *builder* (`RequestBuilder`, `HeadersBuilder`) berumur pendek (*short-lived*).
- **GC Eden Space**: Objek builder yang dibuat dalam DSL dialokasikan di *Eden Space* (Generational GC). Objek ini segera eligible untuk dibersihkan saat Minor GC setelah proses `.build()` selesai, sehingga dampaknya minimal terhadap *throughput* memori.
- **Inlining**: Penggunaan kata kunci `inline` pada fungsi root DSL meniadakan pembuatan instance anonim `new Function1()`, sehingga hanya menyisakan overhead alokasi dari kelas builder itu sendiri.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `@DslMarker`**: Selalu buat satu anotasi ber-marker DSL spesifik untuk domain terkait ketika membuat konfigurasi bersarang lebih dari satu tingkat.
- **Pertahankan Immutability Pasca-Build**: Gunakan kelas builder *mutable* hanya untuk merakit konfigurasi, lalu hasilkan data class *immutable* (`val`) saat metode `build()` dieksekusi.
- **Optimasi dengan `inline`**: Berikan kata kunci `inline` pada fungsi DSL entry-point guna menghindari penalti alokasi objek lambda di HotPath.

#### Don'ts
- **Hindari Side Effects**: Jangan menyisipkan operasi I/O (network calls, database queries) di dalam siklus perakitan blok DSL. Evaluasi DSL harus bersifat murni mutasi state konfigurasi.
- **Jangan Menggunakan DSL untuk Alur Linear**: Jika konfigurasi hanya membutuhkan 1–2 parameter primitif, penggunaan DSL adalah *over-engineering*. Gunakan *default arguments* pada constructor biasa.
- **Hindari Implicit State Leakage**: Hindari exposing koleksi *mutable* secara langsung ke luar blok builder; gunakan encapsulation.

#### Edge Cases
- **Variabel Shadowing**: Perhatikan benturan nama antara variabel lokal di luar blok DSL dengan properti milik receiver builder. Selalu gunakan nama yang deskriptif atau manfaatkan `this@Label` untuk referensi eksplisit jika terjadi ambiguitas.
- **Exception in Builder**: Pastikan validasi invariant dilakukan di akhir (pada fase `build()`), bukan parsial di tengah mutasi DSL, agar stacktrace error menunjukkan validitas state secara menyeluruh (*fail-fast with full context*).

### 5. Tantangan Eksplorasi Mandiri

1. **SQL Query Builder DSL**: Rancang DSL bertipe aman untuk menyusun *query* SQL `SELECT`, mencakup klausa `FROM`, `WHERE`, serta operator perbandingan infix (`eq`, `greaterThan`). Pastikan nested clause `AND`/`OR` tervalidasi dengan aman.
2. **Decompilation Inspection**: Tulis satu blok DSL sederhana dengan dan tanpa kata kunci `inline`. Dekompilasi bytecode ke Java via IntelliJ IDEA (`Tools -> Kotlin -> Show Kotlin Bytecode -> Decompile`) dan bandingkan perbedaan alokasi instance `FunctionX`.
3. **Multi-Receiver Resolution Challenge**: Buat dua DSL marker yang berbeda (`@DatabaseDsl` dan `@NetworkDsl`). Gabungkan keduanya dalam satu fungsi eksekusi untuk menganalisis bagaimana compiler mengelola resolusi receiver ganda ketika marker-nya tidak identik.
