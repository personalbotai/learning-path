### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur perangkat lunak berbasis JVM, *Interface* merepresentasikan kontrak murni (*pure contract*) yang mendefinisikan kapabilitas tanpa memaksakan hierarki kepemilikan data (*stateless contract*). Berbeda dengan *Abstract Class* yang dapat mengikat siklus hidup objek ke dalam hierarki pohon pewarisan tunggal (*single inheritance tree*) dan memiliki *state* (backing fields), interface di Kotlin dirancang untuk mendukung **komposisi perilaku (*behavioral composition*)**.

Kotlin mengizinkan implementasi banyak interface sekaligus (*multiple interface implementation*). Pendekatan ini menyelesaikan kelemahan fundamental dari *multiple class inheritance* di C++ (seperti *Diamond Problem*, di mana terjadi ambiguitas alokasi memori atas state kelas induk ganda) dengan menerapkan dua aturan inti:
1. **Tidak ada Backing Field**: Interface dapat mendeklarasikan properti, tetapi properti tersebut dilarang mengalokasikan memori untuk *backing field* (`field`). Properti pada interface bersifat abstrak atau berupa *custom getter/setter* prosedural murni.
2. **Eksplisit Conflict Resolution**: Jika dua atau lebih interface menyediakan implementasi konkret default (*default implementation*) untuk signature fungsi yang identik, kompilator menolak kompilasi hingga kelas turunan secara eksplisit menentukan implementasi mana yang dipanggil menggunakan sintaks `super<InterfaceName>.method()`.

Di tingkat arsitektur, interface berfungsi memutus kopling (*decoupling*) antar lapisan (misalnya port-and-adapter pada Hexagonal Architecture) dan memungkinkan penerapan *Interface Segregation Principle* (ISP) dari SOLID secara granular.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Pipeline pemrosesan data keuangan yang harus mendukung *Audit Logging*, *Metrics Collection*, dan *Transaction Execution*. Terdapat potensi konflik method `log()` antara sistem audit dan sistem metrik.

```kotlin
package com.engine.payment

import java.time.Instant
import java.util.UUID

// Interface 1: Kontrak untuk kemampuan audit compliance
interface Auditable {
    val auditId: UUID
        get() = UUID.randomUUID() // Default property via custom getter, no backing field

    fun log(message: String) {
        println("[AUDIT - ${Instant.now()}] ID: $auditId | $message")
    }
}

// Interface 2: Kontrak untuk monitoring sistem APM (Application Performance Monitoring)
interface MetricEmitter {
    val metricNamespace: String

    fun log(message: String) {
        println("[METRIC - $metricNamespace] System Event: $message")
    }

    fun recordLatency(durationMs: Long)
}

// Interface 3: Kontrak domain operasi
interface PaymentProcessor {
    fun process(orderId: String, amount: Double): PaymentResult
}

data class PaymentResult(val isSuccess: Boolean, val transactionRef: String)

// Kelas konkret yang mengimplementasikan multiple interfaces
class VisaPaymentProcessor(
    override val metricNamespace: String = "payment.gateway.visa"
) : PaymentProcessor, Auditable, MetricEmitter {

    // Resolusi eksplisit terhadap Diamond Problem pada method log()
    override fun log(message: String) {
        // Mendelegasikan pemanggilan secara teratur ke kedua interface supertype
        super<Auditable>.log(message)
        super<MetricEmitter>.log(message)
    }

    override fun recordLatency(durationMs: Long) {
        println("[METRIC - $metricNamespace] Latency recorded: ${durationMs}ms")
    }

    override fun process(orderId: String, amount: Double): PaymentResult {
        val startTime = System.currentTimeMillis()
        
        // Memanggil resolved method
        log("Memulai transaksi untuk Order ID: $orderId, Nilai: $$amount")

        // Simulasi operasi I/O
        val isSuccess = amount > 0 && amount <= 50000.0
        val latency = System.currentTimeMillis() - startTime
        
        recordLatency(latency)

        return if (isSuccess) {
            val ref = "TXN-${UUID.randomUUID()}"
            log("Transaksi Sukses. Ref: $ref")
            PaymentResult(true, ref)
        } else {
            log("Transaksi Ditolak. Nilai tidak valid atau limit terlampaui.")
            PaymentResult(false, "REJECTED")
        }
    }
}

fun main() {
    val processor = VisaPaymentProcessor()
    
    // Polimorfisme: objek dapat diperlakukan sebagai instansi Auditable, MetricEmitter, atau PaymentProcessor
    val result = processor.process("ORD-99881", 1250.50)
    println("Hasil Akhir: $result")
}
```

#### Penjelasan Komponen Kunci:
1. `override fun log(...)`: Kelas `VisaPaymentProcessor` wajib meng-override method `log` karena kedua interface induk memiliki signature fungsi yang sama persis (`() -> Unit`).
2. `super<Auditable>.log(...)`: Mengarahkan dispatch eksekusi ke implementasi default milik `Auditable`.
3. Property `auditId`: Menggunakan custom getter. Kompilator tidak mengalokasikan slot memori instansi untuk `auditId` di dalam interface; nilainya dievaluasi setiap kali dipanggil, kecuali dioverride dengan `val auditId: UUID = ...` pada kelas konkret.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Pada level bytecode JVM, representasi interface Kotlin bergantung pada target kompilasi:
- **Java 8+ Default Methods**: Secara default pada target bytecode JVM modern, fungsi default di interface Kotlin dikompilasi langsung menjadi JVM *interface default methods* menggunakan modifier `default` pada class file interface.
- **Legacy Compatibility Mode (`DefaultImpls`)**: Jika flag kompilasi kompatibilitas lama digunakan (`-Xjvm-default=disable`), kompilator Kotlin menciptakan *nested static class* bernama `InterfaceName$DefaultImpls`. Semua logika concrete method ditempatkan di sana sebagai method statis yang menerima referensi `this` (`$this: InterfaceName`) sebagai parameter pertama.
- **Instruksi Pemanggilan**: Pemanggilan method interface pada JVM menggunakan opcode `invokeinterface`, bukan `invokevirtual` (seperti pada concrete/abstract class). 
  - `invokevirtual` menyelesaikan dispatch menggunakan *vtable* (Virtual Method Table) terindeks cepat.
  - `invokeinterface` secara historis harus memindai *itable* (Interface Table) karena kelas yang tidak berelasi dapat mengimplementasikan interface yang sama pada offset method yang berbeda. Meskipun demikian, JIT Compiler HotSpot modern mengoptimalkannya menggunakan *Inline Caching* (Monomorphic & Megamorphic calls) sehingga perbedaan latensinya sangat tipis saat *warm-up* selesai.

#### Alokasi Memori / Resource
- Interface murni tidak menambahkan metadata object header baru selain referensi tipe interface pada metadata class loader.
- Tidak ada alokasi heap memori untuk variabel instansi pada interface.
- Setiap state yang dioverride di kelas implementasi (`override val x: Int = 10`) dialokasikan pada memory layout instansi kelas anak di JVM Heap, mematuhi alignment memori standar JVM (biasanya kelipatan 8 byte).

#### Trade-offs
- **Kelebihan**: Fleksibilitas arsitektural total. Memungkinkan *ad-hoc polymorphism* dan modularitas tinggi tanpa terikat problem pewarisan kaku.
- **Kekurangan**: Terlalu banyak memecah interface (over-abstraction) memicu *indirection overhead*. Megamorphic call sites (ketika satu pemanggilan interface memiliki >2 tipe implementasi konkret di runtime) menggagalkan optimasi *monomorphic inline caching* pada JIT, memaksa JVM melakukan full itable dynamic lookup.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Terapkan Interface Segregation**: Pecah interface besar menjadi antarmuka-antarmuka kecil yang fokus pada satu kapabilitas (misal: `Readable`, `Closeable`, `Flushable`).
- **Gunakan Functional Interfaces (SAM)**: Jika interface hanya memiliki satu method abstrak tunggal, tandai dengan `fun interface`. Hal ini memungkinkan interoperabilitas lambda tanpa overhead instansiasi anonymous inner class (`SAM conversion`).
- **Manfaatkan Delegation via `by`**: Gunakan native delegation Kotlin jika ingin mengombinasikan logika implementasi interface tanpa pewarisan:
  ```kotlin
  class LoggingProcessor(
      private val base: PaymentProcessor,
      private val logger: Auditable
  ) : PaymentProcessor by base, Auditable by logger
  ```

#### Don'ts
- **Menyimpan State Tersembunyi via Setter**: Jangan mencoba menyimulasikan stateful field di interface menggunakan backing storage global/static/ThreadLocal yang rapuh. Jika membutuhkan state terikat instansi, gunakan `abstract class`.
- **Interface Pollution**: Mengotori interface domain dengan dependensi infrastruktur atau framework-specific logic.

#### Edge Cases
- **Signature Collision dengan Return Type Berbeda**: Jika dua interface memiliki method dengan nama dan parameter sama persis, tetapi return type berbeda dan tidak kompatibel secara kovarian (misal: `fun getData(): String` vs `fun getData(): Int`), kelas implementasi **tidak dapat dikompilasi**. Satu-satunya solusi adalah merefaktor nama method di salah satu interface.
- **Nullability Clashes**: `fun handle(data: String)` dan `fun handle(data: String?)` dianggap sebagai dua method overload berbeda di Kotlin, tetapi dapat menyebabkan ambiguitas di platform Java runtime akibat type erasure jika generic terlibat.

### 5. Tantangan Eksplorasi Mandiri

1. **Dekomposisi Bytecode**: 
   Kompilasi interface Kotlin dengan default method menggunakan `kotlinc`. Buka terminal, jalankan `javap -c -p MyInterface.class` dan `javap -c -p MyClass.class`. Analisis apakah method default diterjemahkan sebagai Java 8 `default` method langsung atau menciptakan class `DefaultImpls`.
2. **Kovariansi Return Type pada Diamond Resolution**: 
   Buat interface `DataSourceA { fun fetch(): Collection<String> }` dan `DataSourceB { fun fetch(): List<String> }`. Implementasikan keduanya dalam satu kelas `Repository`. Amati bagaimana kompilator Kotlin menangani inferensi subtipe return type tersebut tanpa menimbulkan error resolusi tipe.
