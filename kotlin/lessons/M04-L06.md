### 1. Konsep & Arsitektur Mendalam

Secara *default*, sistem tipe Generics pada Kotlin (dan Java) bersifat **Invariant**. Artinya, jika tipe `Sub` adalah turunan dari `Super`, kelas generic `Container<Sub>` sama sekali **bukan** turunan dari `Container<Super>`, dan sebaliknya. Keduanya tidak memiliki hubungan subtipe.

Ketentuan invariant ini dirancang oleh perancang bahasa untuk mencegah *Heap Pollution* dan *Runtime Type Violation*. Bayangkan jika `MutableList<String>` dianggap sebagai subtipe dari `MutableList<Any>`. Kita dapat meng-assign list string tersebut ke variabel bertipe `MutableList<Any>`, lalu memasukkan objek `Int` ke dalamnya. Ketika elemen tersebut dibaca kembali sebagai `String`, runtime JVM akan melemparkan `ClassCastException`.

```
                  Type Hierarchy (Sub <: Super)
               
          [ Invariance ]              [ Covariance: out ]          [ Contravariance: in ]
     Container<Sub>   Container<Super>       Producer<Sub>                Consumer<Super>
           │                 │                    │                              │
           ✕ (Tidak ada relasi)                   ▼                              ▼
     Container<Sub> ≠ Container<Super>       Producer<Super>                Consumer<Sub>
                                          (Subtipe dipertahankan)       (Subtipe dibalikkan)
```

Untuk memfasilitasi abstraksi polimorfik yang aman, Kotlin mengadopsi konsep variansi:

#### A. Covariance (`out`)
- **Prinsip**: Mempertahankan relasi subtipe (`Sub <: Super` $\implies$ `Class<Sub> <: Class<Super>`).
- **Aturan**: Type parameter hanya boleh diproduksi (**output/read-only**), tidak boleh dikonsumsi (**input/write**).
- **Analogi Java**: Berkorespondensi dengan *Use-site wildcard* `? extends T`.
- **Peran**: *Producer*.

#### B. Contravariance (`in`)
- **Prinsip**: Membalikkan relasi subtipe (`Sub <: Super` $\implies$ `Class<Super> <: Class<Sub>`).
- **Aturan**: Type parameter hanya boleh dikonsumsi (**input/write-only**), tidak boleh diproduksi (**output/read**).
- **Analogi Java**: Berkorespondensi dengan *Use-site wildcard* `? super T`.
- **Peran**: *Consumer*.

#### C. Declaration-Site vs Use-Site Variance
Java hanya mendukung *Use-site variance* (Wildcards di setiap deklarasi parameter method: `List<? extends T>`). Kotlin memperkenalkan **Declaration-Site Variance**, memungkinkan pendefinisian aturan variansi langsung pada level deklarasi class/interface (`interface List<out E>`), sehingga call-site terbebas dari boilerplate wildcard. Namun, Kotlin tetap mendukung *Use-site variance* (disebut **Type Projections**) ketika bekerja dengan kelas invariant seperti `Array<T>`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan arsitektur *Event-Driven Pipeline* yang memanfaatkan Invariance, Covariance, dan Contravariance secara komprehensif.

```kotlin
// Domain Model Hierarchy
open class SystemEvent(val timestamp: Long = System.currentTimeMillis())
class SecurityAlertEvent(val severity: String, timestamp: Long = System.currentTimeMillis()) : SystemEvent(timestamp)
class UserLoginEvent(val userId: String, timestamp: Long = System.currentTimeMillis()) : SystemEvent(timestamp)

// 1. COVARIANCE (out): Producer Role
// Hanya boleh me-return T, tidak boleh menerima T sebagai argumen method publik
interface EventSource<out T : SystemEvent> {
    fun fetchNextEvent(): T
    // fun invalidConsume(event: T) // ERROR: Type parameter T is declared as 'out' but occurs in 'in' position
}

// 2. CONTRAVARIANCE (in): Consumer Role
// Hanya boleh menerima T sebagai argumen, tidak boleh mengembalikan T (kecuali sebagai Any?)
interface EventSink<in T : SystemEvent> {
    fun consume(event: T)
    // fun invalidProduce(): T // ERROR: Type parameter T is declared as 'in' but occurs in 'out' position
}

// 3. INVARIANCE: Read & Write (Default)
class EventBuffer<T : SystemEvent>(private val capacity: Int) {
    private val buffer = ArrayDeque<T>(capacity)

    fun push(item: T) {
        if (buffer.size >= capacity) buffer.removeFirst()
        buffer.addLast(item)
    }

    fun poll(): T? = buffer.removeFirstOrNull()
}

// Implementasi Konkret
class SecurityAlertSource : EventSource<SecurityAlertEvent> {
    override fun fetchNextEvent(): SecurityAlertEvent = SecurityAlertEvent("CRITICAL")
}

class GeneralEventSink : EventSink<SystemEvent> {
    override fun consume(event: SystemEvent) {
        println("Auditing event recorded at: ${event.timestamp}")
    }
}

// Demo Variansi & Use-Site Projection
fun main() {
    // Demo Covariance: SecurityAlertEvent <: SystemEvent
    // Sehingga: EventSource<SecurityAlertEvent> <: EventSource<SystemEvent>
    val alertSource: EventSource<SecurityAlertEvent> = SecurityAlertSource()
    val generalSource: EventSource<SystemEvent> = alertSource // Valid karena 'out'
    val event: SystemEvent = generalSource.fetchNextEvent()
    println("Extracted event timestamp: ${event.timestamp}")

    // Demo Contravariance: SecurityAlertEvent <: SystemEvent
    // Sehingga: EventSink<SystemEvent> <: EventSink<SecurityAlertEvent> (Relasi Dibalik)
    val generalSink: EventSink<SystemEvent> = GeneralEventSink()
    val alertSink: EventSink<SecurityAlertEvent> = generalSink // Valid karena 'in'
    alertSink.consume(SecurityAlertEvent("LOW"))

    // Demo Use-Site Variance (Type Projection) pada kelas Invariant
    val sourceBuffer = EventBuffer<SecurityAlertEvent>(5)
    sourceBuffer.push(SecurityAlertEvent("HIGH"))

    val destinationBuffer = EventBuffer<SystemEvent>(10)

    // Salin elemen dari source ke destination
    copyEvents(source = sourceBuffer, destination = destinationBuffer)
}

// Use-site projection: source bertindak sebagai producer (out), destination sebagai consumer (in)
fun <E : SystemEvent> copyEvents(
    source: EventBuffer<out E>,      // Out-projection (Java: ? extends E)
    destination: EventBuffer<in E>   // In-projection (Java: ? super E)
) {
    var item = source.poll()
    while (item != null) {
        destination.push(item)
        item = source.poll()
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Type Erasure**: JVM tidak memiliki konsep variansi Kotlin pada level eksekusi native bytecode. Seluruh informasi generic parameter dihapus (*erased*) menjadi `java.lang.Object` atau *upper bound*-nya (misal `SystemEvent`).
- **Signature Attribute**: Compiler Kotlin menyisipkan metadata generic pada pool class metadata bytecode (`Signature` attribute) sehingga interoperabilitas dengan Java tetap terjaga.

#### Pemetaan ke Java Bytecode
Ketika compiler Kotlin mengompilasi deklarasi variansi ke bytecode Java:
1. `interface EventSource<out T>` dikompilasi menjadi bytecode Java standard:
   ```java
   public interface EventSource<T> {
       T fetchNextEvent();
   }
   ```
   Namun, setiap kali interface ini digunakan sebagai tipe parameter method di tempat lain, compiler otomatis menambahkan wildcard Java: `EventSource<? extends SystemEvent>`.
2. `interface EventSink<in T>` menghasilkan method signature Java dengan wildcard super saat digunakan: `EventSink<? super SystemEvent>`.

#### Bridge Methods
Jika terjadi penurunan tipe konkret pada kelas turunan yang menerapkan spesialisasi tipe primitif atau penyempitan tipe balik (covariant return type), compiler Kotlin menggenerate **Synthetic Bridge Methods** di level bytecode untuk menjamin integritas kontrak polymorphism virtual method table (vtable) pada JVM.

#### Alokasi Memori & Overhead
- Variansi adalah abstraksi murni **compile-time**. Tidak ada alokasi memori tambahan (*zero runtime memory overhead*) dibandingkan generics biasa.
- Tidak ada runtime check (`instanceof` / `checkcast`) tambahan yang disuntikkan secara otomatis hanya karena penggunaan `in` atau `out`, kecuali saat downcasting eksplisit atau penggunaan unchecked cast.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Prinsip PECS (Producer-Extends, Consumer-Super)**:
  - Gunakan `out` jika class Anda memproduksi nilai bertipe `T` dan menyediakannya ke caller.
  - Gunakan `in` jika class Anda bertindak sebagai consumer yang menerima input bertipe `T`.
- **Prioritaskan Declaration-Site Variance**: Jika sebuah interface memang secara desain adalah producer (contoh: generator, stream read-only), pasang modifier `out` langsung di interface-nya. Ini membuat call-site bersih dari proyeksi tipe.
- **Gunakan UnsafeVariance Secara Selektif**: Kotlin menyediakan `@UnsafeVariance` hanya untuk kasus esensial di mana parameter `out` secara teknis muncul di posisi `in` tetapi tidak melanggar keamanan memori (misalnya method `contains(element: @UnsafeVariance E)` pada `Collection<out E>`).

#### Don'ts
- **Jangan Menggunakan `out` pada Mutable State**:
  ```kotlin
  // KESALAHAN FATAL:
  class Box<out T>(var item: T) // COMPILE ERROR: 'var' menghasilkan getter (out) DAN setter (in)
  ```
  Modifier `var` secara otomatis membuat setter yang menempatkan `T` pada posisi `in`. Jika kelas harus mutable, ia **wajib Invariant**.
- **Jangan Memaksakan Variansi pada Kelas Konkret Final**: Menambahkan `out` atau `in` pada class yang tidak memiliki hierarki atau bukan interface/abstract class seringkali tidak berguna dan membingungkan pemanggil kode.

#### Edge Cases
- **Constructor Parameters vs Methods**: Posisi constructor parameter **bukan** merupakan posisi `in` atau `out` selama parameter tersebut tidak dideklarasikan sebagai `val` atau `var`.
  ```kotlin
  class Factory<out T>(initialWorker: T) { // Valid! Constructor aman.
      private val worker: T = initialWorker // Valid! Private visibility tidak mengekspos T
  }
  ```
- **Visibility Restrictions**: Posisi variansi (`in`/`out`) hanya diperiksa pada level visibilitas publik atau internal. Method bertaraf `private` bebas menggunakan `T` di posisi manapun karena ruang lingkupnya terkapsulasi penuh.

### 5. Tantangan Eksplorasi Mandiri

1. **Transformasi Pipeline Dua Arah**:
   Rancang sebuah interface `Transformer<in Source, out Target>` yang memiliki method `fun transform(input: Source): Target`. 
   - Buktikan bahwa Anda dapat meng-assign `Transformer<Any, String>` ke variabel bertipe `Transformer<Int, CharSequence>`.
   - Analisis secara matematis dan logis mengapa relasi subtipe tersebut valid dan aman dari runtime exception!

2. **Dekomposisi Bytecode `@UnsafeVariance`**:
   Buka file bytecode dari class standard library Kotlin: `kotlin.collections.List`.
   - Analisis method `indexOf(element: @UnsafeVariance E): Int`.
   - Lakukan decompile ke Java (`Tools -> Kotlin -> Show Kotlin Bytecode -> Decompile`).
   - Amati bagaimana JVM menangani type signature method tersebut dan jelaskan mengapa compiler membutuhkan anotasi supresi tersebut agar lolos kompilasi.
