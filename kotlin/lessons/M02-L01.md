### 1. Konsep & Arsitektur Mendalam

Dalam runtime berbasis JVM, sebuah kelas merepresentasikan blueprint untuk alokasi memori objek di *heap*. Pada Java konvensional, inisialisasi status objek sering kali membutuhkan banyak *boilerplate*: deklarasi field privat, parameter konstruktor redundan, assignment manual `this.field = field`, hingga *constructor overloading* berjenjang (telescoping constructors). 

Kotlin merevolusi paradigma ini melalui pemisahan tegas antara **Primary Constructor**, **Secondary Constructor**, dan **Initialization (`init`) Blocks**, yang didukung langsung pada level sintaksis dan dikompilasi secara efisien ke dalam bytecode JVM.

```
+-----------------------------------------------------------+
|                   Class Header                            |
|  class Order(val id: String, customerId: String)          | <--- Primary Constructor
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                   Class Body Execution                    |
|  1. Property Initializer: val isPriority = ...            |
|  2. init { ... } Block 1 (Akses customerId & id)          | <--- Interleaved Execution
|  3. Property Initializer: val timestamp = Instant.now()   |      (Berurutan dari atas
|  4. init { ... } Block 2                                  |       ke bawah)
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|              Secondary Constructor (Opsional)             |
|  constructor(json: JsonNode) : this(...) { ... }          | <--- Delegasi Wajib ke Primary
+-----------------------------------------------------------+
```

#### Primary Constructor
Primary constructor adalah bagian dari *class header*. Berbeda dengan metode biasa, primary constructor tidak memiliki body kode eksekusi langsung. Tanggung jawab utamanya adalah:
1. Mendefinisikan parameter input kelas.
2. Mendeklarasikan sekaligus menginisialisasi *properties* (jika menggunakan kata kunci `val` atau `var`).
3. Menjadi *canonical constructor* (titik tunggal kebenaran instansiasi) yang wajib dipanggil oleh semua secondary constructor.

Jika sebuah parameter tidak diberi prefiks `val` atau `var`, parameter tersebut berstatus **regular parameter**. Parameter ini hanya dapat diakses di dalam deklarasi properti tubuh kelas dan blok `init`, serta tidak akan disimpan sebagai *field* kelas kecuali jika dirujuk oleh deklarasi properti tubuh.

#### Initialization (`init`) Blocks
Karena primary constructor tidak memiliki body, Kotlin menyediakan blok `init`. Blok ini dieksekusi tepat saat instansiasi kelas berlangsung. Sebuah kelas dapat memiliki nol, satu, atau lebih blok `init`. Compiler akan mengeksekusi inisialisasi properti di tubuh kelas dan blok `init` secara strictly sequential: **dari atas ke bawah sesuai urutan deklarasi teks (*textual order*)**.

#### Secondary Constructors
Secondary constructor dideklarasikan di dalam tubuh kelas menggunakan kata kunci `constructor`. Fitur ini utamanya ditujukan untuk interoperabilitas dengan framework Java lama atau skenario ketika instansiasi memerlukan parameter alternatif tanpa default values. Setiap secondary constructor **wajib mendelegasikan pemanggilannya** secara langsung atau tidak langsung ke primary constructor menggunakan sintaks `: this(...)`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem pemrosesan mutasi perbankan (*ledger transaction*) yang menerapkan pola-pola konstruktor Kotlin modern, validasi input, delegasi, dan pemisahan *scoped parameters*.

```kotlin
package com.engine.ledger

import java.math.BigDecimal
import java.time.Instant
import java.util.UUID

class LedgerTransaction(
    // 1. Property langsung via Primary Constructor
    val transactionId: UUID = UUID.randomUUID(),
    val accountId: String,
    val amount: BigDecimal,
    // 2. Regular Parameter (bukan property): hanya ada saat inisialisasi
    rawMetadata: Map<String, String> = emptyMap()
) {
    // Properti tubuh kelas yang diinisialisasi sebelum blok init kedua
    val createdAt: Instant = Instant.now()
    val sanitizedMetadata: Map<String, String>

    // Blok init pertama: Validasi invariants bisnis dasar
    init {
        require(accountId.isNotBlank()) { "accountId tidak boleh kosong/blank." }
        require(amount.compareTo(BigDecimal.ZERO) != 0) { 
            "Nilai transaksi tidak boleh 0." 
        }
    }

    // Blok init kedua: Transformasi data dari regular parameter
    init {
        // Membersihkan whitespace dari metadata keys & values
        sanitizedMetadata = rawMetadata
            .filter { it.key.isNotBlank() }
            .map { (k, v) -> k.trim().lowercase() to v.trim() }
            .toMap()
    }

    // Properti turunan yang bergantung pada state yang telah divalidasi
    val isDebit: Boolean = amount < BigDecimal.ZERO

    /**
     * Secondary Constructor: Mendukung integrasi sistem legacy berbasis string payload.
     * Wajib mendelegasikan secara eksplisit ke Primary Constructor.
     */
    constructor(legacyPayload: String) : this(
        accountId = legacyPayload.substringBefore(":"),
        amount = BigDecimal(legacyPayload.substringAfter(":")),
        rawMetadata = mapOf("source" to "legacy_csv")
    ) {
        // Body secondary constructor dieksekusi SETELAH semua blok init selesai
        println("INFO: LedgerTransaction dibuat via Secondary Constructor untuk: $accountId")
    }

    fun printSummary() {
        println("Tx: $transactionId | Acc: $accountId | Amount: $amount | Debit: $isDebit")
    }
}

fun main() {
    // 1. Instansiasi via Primary Constructor dengan Default Argument
    val tx1 = LedgerTransaction(
        accountId = "ACC-9901",
        amount = BigDecimal("-150000.50"),
        rawMetadata = mapOf("Category " to " Utilities ")
    )
    tx1.printSummary()
    println("Sanitized: ${tx1.sanitizedMetadata}")

    // 2. Instansiasi via Secondary Constructor
    val tx2 = LedgerTransaction("ACC-8821:5000000.00")
    tx2.printSummary()

    // 3. Uji Validasi (Melempar IllegalArgumentException)
    try {
        LedgerTransaction(accountId = "", amount = BigDecimal.TEN)
    } catch (e: IllegalArgumentException) {
        println("Gagal membuat transaksi: ${e.message}")
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (JVM Desugaring)
Di balik layar, Kotlin compiler (`kotlinc`) tidak mempertahankan konsep "primary constructor" dan "init block" sebagai entitas terpisah pada target bytecode JVM. Seluruh komponen ini digabung (*merged*) ke dalam satu fungsi internal Java constructor standard: `<init>(...)`.

Jika kita melakukan *decompilation* dari Kotlin bytecode ke Java code (ekuivalen):

```java
// Hasil dekompilasi bytecode LedgerTransaction
public final class LedgerTransaction {
    @NotNull private final UUID transactionId;
    @NotNull private final String accountId;
    @NotNull private final BigDecimal amount;
    @NotNull private final Instant createdAt;
    @NotNull private final Map<String, String> sanitizedMetadata;
    private final boolean isDebit;

    // Primary Constructor + init blocks digabung ke dalam <init>
    public LedgerTransaction(@NotNull UUID transactionId, @NotNull String accountId, 
                             @NotNull BigDecimal amount, @NotNull Map rawMetadata) {
        super();
        this.transactionId = transactionId;
        this.accountId = accountId;
        this.amount = amount;

        // Inisialisasi properti tubuh kelas
        this.createdAt = Instant.now();

        // Kode dari init block #1
        if (StringsKt.isBlank(this.accountId)) {
            throw new IllegalArgumentException("accountId tidak boleh kosong/blank.");
        }
        if (this.amount.compareTo(BigDecimal.ZERO) == 0) {
            throw new IllegalArgumentException("Nilai transaksi tidak boleh 0.");
        }

        // Kode dari init block #2
        this.sanitizedMetadata = ...; // Transformasi map

        // Properti isDebit
        this.isDebit = this.amount.compareTo(BigDecimal.ZERO) < 0;
    }

    // Secondary Constructor menjadi overload <init> terpisah
    public LedgerTransaction(@NotNull String legacyPayload) {
        // Delegasi ke primary constructor
        this(..., ..., ..., ...);
        // Body secondary constructor dijalankan di sini
        System.out.println("INFO: LedgerTransaction dibuat via Secondary Constructor...");
    }
}
```

#### Alokasi Memori / Resource
1. **Regular Parameter vs Property**: `rawMetadata` tidak dideklarasikan sebagai `val`/`var`. Karena hanya dipakai dalam assignment di dalam `init`, compiler mendeteksi bahwa nilai ini tidak perlu persistensi jangka panjang. Akibatnya, `rawMetadata` hanya dialokasikan di dalam **Stack Frame** fungsi `<init>` selama konstruksi berlangsung dan **tidak pernah mengonsumsi memori di Heap** sebagai field kelas.
2. **Execution Flow Constraints**: Karena semua blok `init` disisipkan ke dalam method `<init>`, JVM menjamin *thread-safety* parsial pada tingkat inisialisasi: referensi `this` baru akan terekspos sepenuhnya ke thread pemanggil setelah seluruh blok `init` dan inisialisasi field tuntas dieksekusi.

#### Trade-offs: Secondary Constructors vs Default Arguments
- Penggunaan **Default Arguments** pada primary constructor menghasilkan synthetic classes/method masks di bytecode (menggunakan bitmask untuk mendeteksi argumen mana yang di-pass). Ini sangat fleksibel dan idiomatik di Kotlin.
- Penggunaan **Secondary Constructors** memproduksi `<init>` bytecode overload eksplisit. Pendekatan ini berguna untuk interoperabilitas Java murni, tetapi menambah ukuran *method footprint* pada metadata file `.class`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Default Arguments daripada Secondary Constructors**: Hampir semua kebutuhan constructor overloading pada Java dapat digantikan secara elegan dengan primary constructor yang memiliki *default parameter values*.
- **Gunakan `require()` atau `check()` untuk State Invariant**: Letakkan validasi parameter di blok `init` paling awal untuk menerapkan prinsip *Fail-Fast*.
- **Pilih Regular Parameters untuk Data Transien**: Jika sebuah parameter konstruktor hanya dibutuhkan untuk menghitung properti lain atau validasi, jangan beri kata kunci `val`/`var`.

#### Don'ts
- **Hindari Operasi I/O atau Blocking di dalam `init` Block**: Blok `init` dijalankan secara sinkron selama pemesanan memori objek. Melakukan database call, HTTP request, atau file reading di dalam `init` akan memperlambat alokasi memori, menyulitkan unit testing, dan berisiko membekukan thread (terutama UI thread).
- **Hindari Logika Kompleks di Secondary Constructor**: Secondary constructor sebaiknya murni melakukan mapping data input menuju Primary Constructor. Jangan tempatkan mutasi state kompleks di tubuh secondary constructor.

#### Edge Cases & Pitfalls: *Leaking `this` before Initialization*
Sebuah jebakan fatal pada Kotlin terjadi ketika memanggil method open/virtual dari dalam konstruktor atau blok `init` saat kelas diwarisi (`open class`).

```kotlin
// BAHAYA: Leaking partially-initialized object
open class BaseAccount(val initialBalance: Double) {
    init {
        // Bahaya! Memanggil virtual method dari konstruktor parent
        setupAccount() 
    }

    open fun setupAccount() {
        println("Base setup with balance: $initialBalance")
    }
}

class PremiumAccount(initialBalance: Double, val bonusTier: String) : BaseAccount(initialBalance) {
    // Properti ini BELUM diinisialisasi saat BaseAccount.init berjalan
    val multiplier: Double = if (bonusTier == "GOLD") 1.5 else 1.0

    override fun setupAccount() {
        // NPE atau Null Logic Hazard! multiplier masih bernilai default tipe data primitif (0.0)
        println("Premium setup. Multiplier: $multiplier") 
    }
}
```
*Mengapa ini terjadi?* Superclass constructor selalu dieksekusi sebelum subclass constructor. Saat `BaseAccount` menjalankan `init`, memory footprint `multiplier` milik `PremiumAccount` belum dialokasikan nilainya oleh compiler (masih `0.0`), menghasilkan *bug* state yang sulit dilacak.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Urutan Eksekusi (*Initialization Order*)**:
   Buat sebuah kelas dengan minimal dua properti tubuh dan dua blok `init` yang saling bersilangan posisinya secara vertikal. Akses properti A dari dalam blok `init` pertama, kemudian pindahkan deklarasi properti A ke bawah blok `init` pertama tersebut. Amati dan jelaskan mengapa compiler Kotlin menghasilkan error `"Variable cannot be initialized before declaration"` meskipun keduanya berada dalam lingkup tubuh kelas yang sama.

2. **Dekomposisi Bytecode dengan `javap`**:
   Kompilasi kelas `LedgerTransaction` di atas menggunakan perintah `kotlinc LedgerTransaction.kt`. Jalankan command `javap -c -p LedgerTransaction.class` pada terminal Anda. Telusuri instruksi `invokespecial` yang memanggil `java/lang/Object."<init>"` dan temukan di mana tepatnya instruksi pemanggilan `require()` disisipkan di dalam instruksi bytecode JVM tersebut.
