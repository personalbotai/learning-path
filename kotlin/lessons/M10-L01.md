### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem JVM tradisional, testing suite standar industri umumnya bertumpu pada **JUnit 5** dan **Mockito**. Namun, saat dihadapkan pada karakteristik idiomatik Kotlin—seperti *classes are final by default*, *coroutines & suspend functions*, *extension functions*, *inline value classes*, serta *named & default arguments*—kombinasi tersebut sering kali membutuhkan workaround (misalnya plugin `mockito-inline`, *argument captor wrapper*, atau anotasi `open` yang merusak integritas desain domain).

Di sinilah **Kotest** dan **MockK** hadir sebagai perkakas standar pengujian modern yang dirancang natively untuk Kotlin.

```
+-------------------------------------------------------------------+
|                        Kotest Engine                              |
|  [Test Specs: BehaviorSpec, FunSpec, StringSpec, etc.]            |
|  [Lifecycle Hooks: beforeTest, afterEach, prepareSpec]            |
|  [Assertion Engine: Matchers, Non-deterministic assertions]       |
+---------------------------------+---------------------------------+
                                  | Mengontrol Eksekusi
                                  v
+---------------------------------+---------------------------------+
|                       System Under Test (SUT)                     |
+---------------------------------+---------------------------------+
                                  | Berinteraksi via Injeksi
                                  v
+---------------------------------+---------------------------------+
|                        MockK Subsystem                            |
|  [Proxy / Byte Buddy Transformer] -> Menangani 'final' & 'suspend' |
|  [Kotlin Metadata Reader]         -> Mendukung Default/Named Args |
|  [Continuation Interceptor]       -> Stubbing Suspend Functions   |
+-------------------------------------------------------------------+
```

#### Arsitektur Kotest
Kotest memisahkan framework testing menjadi tiga komponen modular:
1. **Kotest Framework (Engine):** Menyediakan variasi gaya penulisan pengujian (*Testing Styles/Specs*) seperti `BehaviorSpec` (BDD: Given-When-Then), `StringSpec`, `FunSpec`, hingga `AnnotationSpec`. Kotest terintegrasi secara mendalam dengan coroutine engine melalui `TestCoroutineDispatcher`.
2. **Kotest Assertions:** Mesin assertion yang *type-safe*, ekspresif, dan kaya fitur (seperti inspeksi koleksi kompleks, *data class diffing*, dan *soft assertions*).
3. **Kotest Property-based Testing:** Generator data berbasis properti matematika untuk memverifikasi invarian logika bisnis pada ribuan kombinasi input acak.

#### Arsitektur MockK
MockK dirancang khusus untuk membedah *bytecode* Kotlin. Arsitektur MockK dibangun di atas **Byte Buddy** dan Java Instrumentation API:
- **Final Class & Method Handling:** Tidak seperti Mockito standar yang memerlukan sub-classing (yang gagal karena class di Kotlin *final* secara default), MockK memanipulasi *bytecode* target saat runtime langsung melalui agent-based instrumentation tanpa perlu membuka modifikasi class (`open`).
- **Continuation Handling (Coroutines):** Saat fungsi `suspend` dikompilasi, Kotlin Compiler mengubah tanda tangan fungsinya menggunakan *Continuation Passing Style* (CPS), menambahkan parameter tersembunyi `kotlin.coroutines.Continuation`. MockK mengidentifikasi CPS ini secara internal dan menyediakan DSL `coEvery` serta `coVerify` untuk mengintersepsi objek `Continuation` tersebut secara transparan.
- **Support untuk Fitur Bahasa:** Mendukung *mocking* untuk `object` (singleton), *companion objects*, *extension functions*, dan *inline value classes* yang mengalami *name mangling* di level bytecode JVM.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Sebuah sistem *Payment Processing* di mana `PaymentService` bergantung pada `PaymentGatewayClient` (remote I/O via coroutine) dan `TransactionRepository` (database persistence).

#### Dependensi (Gradle Kotlin DSL)
```kotlin
testImplementation("io.kotest:kotest-runner-junit5:5.8.0")
testImplementation("io.kotest:kotest-assertions-core:5.8.0")
testImplementation("io.mockk:mockk:1.13.10")
```

#### Kode Produksi
```kotlin
package com.alvayon.payment

import java.util.UUID

@JvmInline
value class TransactionId(val value: UUID)

enum class PaymentStatus { SUCCESS, FAILED, INSUFFICIENT_FUNDS }

data class PaymentRequest(val accountId: String, val amountCents: Long)
data class PaymentResult(val id: TransactionId, val status: PaymentStatus, val rawResponseCode: String)

interface PaymentGatewayClient {
    suspend fun charge(accountId: String, amountCents: Long): GatewayResponse
}

data class GatewayResponse(val isSuccess: Boolean, val code: String)

interface TransactionRepository {
    fun save(paymentResult: PaymentResult)
    fun exists(transactionId: TransactionId): Boolean
}

class PaymentService(
    private val gatewayClient: PaymentGatewayClient,
    private val repository: TransactionRepository
) {
    suspend fun processPayment(request: PaymentRequest): PaymentResult {
        require(request.amountCents > 0) { "Amount must be strictly positive" }

        val gatewayResponse = gatewayClient.charge(request.accountId, request.amountCents)
        
        val status = if (gatewayResponse.isSuccess) {
            PaymentStatus.SUCCESS
        } else {
            when (gatewayResponse.code) {
                "ERR_FUNDS" -> PaymentStatus.INSUFFICIENT_FUNDS
                else -> PaymentStatus.FAILED
            }
        }

        val result = PaymentResult(
            id = TransactionId(UUID.randomUUID()),
            status = status,
            rawResponseCode = gatewayResponse.code
        )

        repository.save(result)
        return result
    }
}
```

#### Test Suite Menggunakan Kotest & MockK
```kotlin
package com.alvayon.payment

import io.kotest.assertions.throwables.shouldThrow
import io.kotest.core.spec.style.BehaviorSpec
import io.kotest.matchers.shouldBe
import io.kotest.matchers.types.shouldBeInstanceOf
import io.mockk.clearAllMocks
import io.mockk.coEvery
import io.mockk.coVerify
import io.mockk.confirmVerified
import io.mockk.every
import io.mockk.just
import io.mockk.mockk
import io.mockk.runs
import io.mockk.slot
import io.mockk.verify

class PaymentServiceTest : BehaviorSpec({

    // Instansiasi mock dependensi
    val gatewayClient = mockk<PaymentGatewayClient>()
    val repository = mockk<TransactionRepository>()

    // SUT (System Under Test)
    val service = PaymentService(gatewayClient, repository)

    // Reset rekaman panggilan dan state mock setiap kali lifecycle container/leaf dieksekusi
    afterContainer {
        clearAllMocks()
    }

    Given("Sebuah permintaan pembayaran (PaymentRequest) valid") {
        val request = PaymentRequest(accountId = "ACC-12345", amountCents = 150_000)

        When("Gateway merespons dengan transaksi sukses") {
            // Stubbing suspend function menggunakan coEvery
            coEvery { 
                gatewayClient.charge(request.accountId, request.amountCents) 
            } returns GatewayResponse(isSuccess = true, code = "TX_OK_200")

            // Slot untuk menangkap parameter yang dikirim ke repository
            val resultSlot = slot<PaymentResult>()
            every { repository.save(capture(resultSlot)) } just runs

            val outcome = service.processPayment(request)

            Then("Outcome harus bertransisi ke status SUCCESS") {
                outcome.status shouldBe PaymentStatus.SUCCESS
                outcome.rawResponseCode shouldBe "TX_OK_200"
                outcome.id.shouldBeInstanceOf<TransactionId>()
            }

            Then("Repository harus menyimpan hasil transaksi dengan data yang akurat") {
                // Verifikasi suspend interaction
                coVerify(exactly = 1) { 
                    gatewayClient.charge("ACC-12345", 150_000) 
                }

                // Verifikasi synchronous interaction
                verify(exactly = 1) { 
                    repository.save(any()) 
                }

                // Validasi data yang ditangkap di dalam slot
                resultSlot.captured.status shouldBe PaymentStatus.SUCCESS
                resultSlot.captured.rawResponseCode shouldBe "TX_OK_200"
            }

            Then("Tidak boleh ada interaksi liar pada dependensi lain") {
                confirmVerified(gatewayClient, repository)
            }
        }

        When("Gateway mendeteksi dana tidak mencukupi") {
            coEvery { 
                gatewayClient.charge(any(), any()) 
            } returns GatewayResponse(isSuccess = false, code = "ERR_FUNDS")

            every { repository.save(any()) } just runs

            val outcome = service.processPayment(request)

            Then("Outcome status harus INSUFFICIENT_FUNDS") {
                outcome.status shouldBe PaymentStatus.INSUFFICIENT_FUNDS
            }
        }
    }

    Given("Sebuah permintaan pembayaran dengan nominal tidak valid") {
        val invalidRequest = PaymentRequest(accountId = "ACC-99999", amountCents = 0)

        When("Service mengeksekusi request") {
            Then("Harus melempar IllegalArgumentException sebelum memanggil Gateway") {
                val exception = shouldThrow<IllegalArgumentException> {
                    service.processPayment(invalidRequest)
                }
                
                exception.message shouldBe "Amount must be strictly positive"

                // Memastikan tidak ada network call yang terbuang sia-sia
                coVerify(exactly = 0) { gatewayClient.charge(any(), any()) }
                verify(exactly = 0) { repository.save(any()) }
            }
        }
    }
})
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Coroutine Suspension Interception
Pada level JVM Bytecode, sebuah fungsi suspend diubah:
```kotlin
// Asal Kotlin
suspend fun charge(accountId: String, amountCents: Long): GatewayResponse

// Representasi Bytecode Dekompilasi (Java Signature)
Object charge(String accountId, long amountCents, Continuation<? super GatewayResponse> $completion);
```
Saat runtime:
1. `coEvery { ... }` membungkus lambda pencocokan ke dalam blok yang secara internal mengekstraksi parameter `$completion` (`Continuation`).
2. MockK mendaftarkan signature method dinamis ini ke dalam registry pemanggilannya.
3. Saat method dipanggil dari coroutine, MockK memotong alur eksekusi, memverifikasi `Continuation.context`, lalu mengembalikan nilai return value secara langsung atau menjadwalkan `resumeWith` pada dispatcher coroutine aktif, sehingga framework pengetesan tidak mengalami blocking pada thread pool utama.

#### Alokasi Memori & Transformasi Kelas
- **Class Subclassing vs Transformation:** MockK menggunakan **Byte Buddy Attach API**. Jika mock dibuat, MockK tidak selalu membuat proxy via Java Reflection dynamic proxy (`java.lang.reflect.Proxy`), melainkan dapat meredefinisi struktur *in-memory* byte array kelas terkait di metaspace melalui modul class-redefinition agent.
- **Lifecycle Invocation Graph:** Setiap interaksi dengan objek mock dicatat di memori sebagai *tree-like data structure* yang memetakan daftar argumen, hash signature thread pemanggil, dan call-count metrics. Jika mock dibuat dalam skala besar pada ratusan file test tanpa dibersihkan via `clearAllMocks()` / `unmockkAll()`, rekaman ini menetap di static context memory sehingga memicu resiko `OutOfMemoryError: Metaspace / Java Heap Space`.

#### Trade-offs MockK vs Real Components
| Fitur | MockK / Kotest | Java Native Tools (JUnit5 + Mockito) |
| :--- | :--- | :--- |
| **Parsing Metadata Kotlin** | Sangat Tinggi (Mendukung inline class, default params, reflection metadata) | Rendah (Kerap menganggap class final, default argumen menjadi mangled method) |
| **Kecepatan Inisialisasi** | Sedikit lebih lambat saat startup (karena beban instrumentasi Byte Buddy khusus) | Sedikit lebih cepat di JVM primitif |
| **Eksekusi Asinkron** | Native via coroutine dispatcher interceptor | Membutuhkan adapter (seperti `runBlocking` boilerplate berlebih) |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Gunakan Scope Lifecycle yang Tepat:** Manfaatkan lifecycle hook Kotest seperti `afterContainer`, `afterEach`, atau `afterSpec` untuk mengeksekusi `clearMocks()` atau `clearAllMocks()`. Ini memastikan test-case bersifat independen (*isolated execution*).
2. **Prioritaskan Verification yang Ketat Menggunakan `confirmVerified()`:** Setelah melakukan `verify` atau `coVerify`, gunakan `confirmVerified(mockA, mockB)` untuk memastikan tidak ada pemanggilan fungsi yang tidak terdokumentasi/tak terduga yang lolos dari assertions.
3. **Gunakan `relaxed = true` Secara Selektif:** Penggunaan `mockk<Dependency>(relaxed = true)` memang menghindari boilerplate stubbing untuk fungsi void/unit, namun dapat menutupi bug logika karena dependensi akan mengembalikan nilai default (seperti `0`, `""`, atau `false`) secara implisit.

#### Don'ts
1. **Jangan Mocking Data Classes / Value Objects:** Jangan pernah melakukan `mockk<PaymentRequest>()` atau `mockk<TransactionId>()`. Instansiasikan data class secara langsung. Mocking data holder adalah anti-pattern yang memperlambat runtime dan mengaburkan data state.
2. **Jangan Menggunakan `runBlocking` di Kotest Spec:** Kotest mendukung coroutines out-of-the-box. Hindari membungkus eksekusi test di dalam `runBlocking { ... }`. Biarkan Kotest mengelola execution scope melalui coroutine-based specs.
3. **Hindari Verifikasi Implementasi Internal yang Berlebihan:** Menguji tiap baris interaksi privat menyebabkan unit test menjadi *brittle* (mudah patah ketika struktur kode direfaktor meskipun kontrak input-output fungsionalnya tidak berubah).

#### Edge Cases
- **Inline Value Classes:** Kotlin melakukan *name-mangling* pada method yang menerima `value class` (contoh: fungsi `fun get(id: TransactionId)` diubah namanya di bytecode menjadi `get-u1283h(UUID id)`). Gunakan versi MockK terbaru (1.13+) agar resolver metadata membaca signature asli.
- **Mocking Object Singletons:** MockK menyediakan `mockkObject(MySingleton)`. Ingatlah bahwa singleton bersifat global per ClassLoader! Anda **wajib** mengeksekusi `unmockkObject(MySingleton)` di blok `finally` atau hook `afterSpec`, jika tidak modifikasi tersebut akan bocor (*leak*) dan merusak kestabilan suite test lain yang berjalan paralel.

### 5. Tantangan Eksplorasi Mandiri

1. **Mocking Static & Extension Function:**
   Implementasikan sebuah extension function `fun PaymentResult.toReceiptJson(): String` yang memanggil library eksternal. Buatlah unit test menggunakan MockK (`mockkStatic`) untuk memastikan extension function tersebut dapat di-stub dan verifikasi bahwa stub dilepas kembali secara aman tanpa efek samping ke test suite lain.
2. **Pengujian Reaktif / Flow dengan Kotest:**
   Ubah `PaymentGatewayClient` agar mengembalikan stream asinkron `Flow<PaymentStatusUpdate>`. Tulis test spec di Kotest menggunakan modul `kotest-assertions-turbine` untuk memvalidasi emisi data stream tersebut tanpa menggunakan *thread sleep*.
