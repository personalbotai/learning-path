### 1. Konsep & Arsitektur Mendalam

Pengujian unit (*unit testing*) pada kode asinkron tradisional menghadapi dua masalah mendasar: **non-determinisme** dan **eksekusi berbasis waktu nyata (wall-clock time)**. Penggunaan `Thread.sleep()` menghasilkan tes yang lambat dan rentan *flaky*. Library `kotlinx-coroutines-test` dan **Turbine** (dari Cash App) diciptakan untuk memecahkan masalah ini melalui abstraksi waktu virtual (*virtual time*) dan konsumsi event berbasis saluran reaktif (*reactive channel*).

```
+-------------------------------------------------------------------------+
|                               runTest                                   |
|  +-------------------------------------------------------------------+  |
|  |                       TestScope / TestScheduler                   |  |
|  |  [ Virtual Clock: currentTime = 0ms ]                             |  |
|  |  [ Priority Queue: Scheduled Runnables (ordered by target time) ] |  |
|  +----------------------------------+--------------------------------+  |
|                                     |                                   |
|          +--------------------------+--------------------------+        |
|          v                                                     v        |
|  +----------------------------+     +-------------------------------+   |
|  |   StandardTestDispatcher   |     |   UnconfinedTestDispatcher    |   |
|  | - Menunda task ke queue    |     | - Mengeksekusi eager (langsung|   |
|  | - Butuh advanceUntilIdle() |     |   sampai titik suspensi)      |   |
|  +----------------------------+     +-------------------------------+   |
|                                                                         |
|  +-------------------------------------------------------------------+  |
|  |                           Turbine                                 |  |
|  |  Flow.test { ... }                                                |  |
|  |    Flow -> [ Collect Coroutine ] -> [ Channel<Event<T>> ]         |  |
|  |    Assertion API: awaitItem(), awaitError(), awaitComplete()      |  |
|  +-------------------------------------------------------------------+  |
+-------------------------------------------------------------------------+
```

#### Komponen Utama Arsitektur Pengujian Coroutine

1. **`TestCoroutineScheduler` & Virtual Time**:
   Inti dari eksekusi asinkron deterministik. Scheduler ini menyimpan *priority queue* internal dari runnable tasks yang dijadwalkan berdasarkan *virtual timestamp*. Ketika coroutine memanggil `delay(10_000)`, coroutine tidak memblokir thread nyata selama 10 detik. Scheduler hanya memajukan pointer `currentTime` internal ke `+10_000ms` dan segera mengeksekusi kelanjutan (*continuation*) coroutine secara instan di thread pengujian.

2. **Dua Varian `TestDispatcher`**:
   - **`StandardTestDispatcher`**: Dispatcher default di dalam `runTest`. Ia tidak langsung mengeksekusi coroutine baru. Coroutine dimasukkan ke antrean scheduler. Kita memiliki kontrol penuh untuk mengeksekusi tugas tersebut menggunakan `advanceUntilIdle()` atau `advanceTimeBy()`. Dispatcher ini ideal untuk menguji urutan eksekusi (*ordering*) dan kondisi balapan (*race conditions*).
   - **`UnconfinedTestDispatcher`**: Coroutine yang diluncurkan langsung dieksekusi secara agresif (*eagerly*) hingga mencapai titik penangguhan (*suspension point*) pertama. Dispatcher ini menyederhanakan penulisan tes untuk kasus-kasus umum yang tidak memerlukan verifikasi detail mengenai penjadwalan tingkat rendah.

3. **Masalah Pengujian Flow Tradisional**:
   Menguji `Flow` secara manual menggunakan `toList()` atau meluncurkan kolektor manual (`launch { flow.collect() }`) berisiko menyebabkan:
   - Tes menggantung selamanya (*hanging*) jika Flow bersifat tak hingga (*infinite flow* seperti `StateFlow` atau `SharedFlow`).
   - Kehilangan emisi karena penggabungan nilai (*conflation*).
   - *Race condition* antara thread penghasil (*producer*) dan pengumpul (*consumer*).

4. **Arsitektur Turbine**:
   Turbine mengonversi setiap emisi `Flow` menjadi aliran kejadian diskrit (`Event<T>`) melalui `Channel` internal yang aman terhadap thread (*thread-safe*). Setiap kali flow mengemisi data, melempar error, atau selesai (*complete*), Turbine memasukkan event tersebut ke dalam queue internal. API seperti `awaitItem()` mengambil event tersebut secara berurutan dan menghentikan pengujian jika event berikutnya tidak sesuai dengan ekspektasi atau jika *timeout* terlampaui.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mendemonstrasikan pengujian `SearchViewModel` yang menggunakan `StateFlow`, operasi `debounce`, dan pemanggilan data layer.

#### Dependencies (Gradle Kotlin DSL)
```kotlin
testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.8.0")
testImplementation("app.cash.turbine:turbine:1.1.0")
testImplementation("junit:junit:4.13.2")
```

#### Kode Produksi
```kotlin
package com.example.search

import kotlinx.coroutines.CoroutineDispatcher
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.flow.*

sealed interface SearchUiState {
    data object Idle : SearchUiState
    data object Loading : SearchUiState
    data class Success(val results: List<String>) : SearchUiState
    data class Error(val message: String) : SearchUiState
}

class SearchRepository(private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO) {
    suspend fun search(query: String): List<String> {
        // Simulasi query network
        return listOf("$query result 1", "$query result 2")
    }
}

class SearchViewModel(
    private val repository: SearchRepository,
    private val defaultDispatcher: CoroutineDispatcher = Dispatchers.Default
) {
    private val _query = MutableStateFlow("")
    
    val uiState: StateFlow<SearchUiState> = _query
        .debounce(300L)
        .filter { it.isNotBlank() }
        .distinctUntilChanged()
        .flatMapLatest { query ->
            flow {
                emit(SearchUiState.Loading)
                try {
                    val result = repository.search(query)
                    emit(SearchUiState.Success(result))
                } catch (e: Exception) {
                    emit(SearchUiState.Error(e.message ?: "Unknown Error"))
                }
            }
        }
        .flowOn(defaultDispatcher)
        .stateIn(
            scope = kotlinx.coroutines.CoroutineScope(defaultDispatcher),
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = SearchUiState.Idle
        )

    fun onQueryChanged(newQuery: String) {
        _query.value = newQuery
    }
}
```

#### Unit Test dengan TestDispatcher & Turbine
```kotlin
package com.example.search

import app.cash.turbine.test
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.test.*
import org.junit.After
import org.junit.Assert.assertEquals
import org.junit.Before
import org.junit.Test

@OptIn(ExperimentalCoroutinesApi::class)
class SearchViewModelTest {

    private val testScheduler = TestCoroutineScheduler()
    private val testDispatcher = StandardTestDispatcher(testScheduler)
    
    // Stub / Fake Repository
    private val repository = SearchRepository(ioDispatcher = testDispatcher)
    private lateinit var viewModel: SearchViewModel

    @Before
    fun setUp() {
        // Mengganti Dispatchers.Main jika ada ketergantungan UI
        Dispatchers.setMain(testDispatcher)
        viewModel = SearchViewModel(
            repository = repository,
            defaultDispatcher = testDispatcher
        )
    }

    @After
    fun tearDown() {
        Dispatchers.resetMain()
    }

    @Test
    fun `when query is submitted, verify debounce and state transitions with Turbine`() = runTest(testDispatcher) {
        viewModel.uiState.test {
            // State awal StateFlow
            assertEquals(SearchUiState.Idle, awaitItem())

            // Input query pertama
            viewModel.onQueryChanged("Kot")
            // Majukan waktu kurang dari ambang batas debounce (300ms)
            advanceTimeBy(200)
            
            // Verifikasi belum ada emisi baru karena debounce masih berjalan
            expectNoEvents()

            // Input query baru sebelum 300ms tercapai (menimpa query sebelumnya)
            viewModel.onQueryChanged("Kotlin")
            
            // Majukan waktu melewati sisa debounce
            advanceTimeBy(300)
            
            // Event Loading harus keluar pertama kali
            assertEquals(SearchUiState.Loading, awaitItem())

            // Eksekusi semua background task yang tertunda (pemanggilan repo)
            advanceUntilIdle()

            // Event Success diterima
            val successItem = awaitItem() as SearchUiState.Success
            assertEquals(listOf("Kotlin result 1", "Kotlin result 2"), successItem.results)

            // Batalkan pengumpulan Flow agar coroutine StateFlow berhenti
            cancelAndIgnoreRemainingEvents()
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### 1. Mekanisme Eksekusi `runTest` & Virtual Time
Saat `runTest` dijalankan:
- Dibuat sebuah `TestScope` yang memegang referensi ke `TestCoroutineScheduler`.
- Scheduler mengintersepsi semua pemanggilan `delay()` pada coroutine turunan. Compiler Kotlin mentranslasikan `delay()` menjadi penangguhan coroutine (`suspendCancellableCoroutine`). Scheduler tidak membuat kernel OS memanggil timer sistem, melainkan mendaftarkan `CancellableContinuation` tersebut ke dalam struktur data internal `PriorityQueue<ScheduledTask>` miliknya, di mana pembanding kuncinya (*comparator*) adalah `virtualTimeTarget = currentTime + delayMillis`.
- Fungsi `advanceTimeBy(ms)` mengambil tugas-tugas dari queue yang memiliki target $\le currentTime + ms$, memajukan nilai `currentTime`, lalu mengeksekusi `continuation.resume(Unit)`. Semuanya berjalan pada thread pengujian tunggal tanpa context switching thread nyata.

#### 2. Turbine Event Interception
Di balik method ekstensi `Flow.test(timeout, validate)`:
- Turbine membuat coroutine pengumpul (*collector coroutine*) terpisah yang berjalan di bawah `CoroutineStart.UNDISPATCHED` untuk menjamin pendaftaran collector secara instan sebelum kode blok pengujian berjalan.
- Kolektor tersebut menjalankan `flow.collect { item -> channel.send(Event.Item(item)) }`.
- Error yang tidak tertangkap ditransformasikan menjadi `Event.Error(throwable)`, dan penyelesaian flow menjadi `Event.Complete`.
- Struktur datanya menggunakan **rendezvous channel atau buffered channel** dari `kotlinx.coroutines.channels.Channel`.
- Ketika pengembang memanggil `awaitItem()`, Turbine mengeksekusi `channel.receive()`. Jika channel kosong, ia menunda eksekusi sampai scheduler mengalirkan nilai dari producer. Jika waktu melampaui timeout (default 1 detik virtual time), assertion fail dilempar secara deterministik.
- Fungsi `cancelAndIgnoreRemainingEvents()` membatalkan Coroutine pengumpul melalui `Job.cancel()` guna mencegah *leak* coroutine tak hingga pada `StateFlow`.

#### 3. Analisis Trade-offs

| Fitur | `StandardTestDispatcher` | `UnconfinedTestDispatcher` |
| :--- | :--- | :--- |
| **Pola Eksekusi** | Antrean eksplisit (*Queued*). Butuh intervensi manual scheduler. | Eksekusi langsung (*Eager*) sampai titik suspensi pertama. |
| **Kelebihan** | Kontrol presisi tinggi atas *concurrency* & *race conditions*. | Boilerplate minimal; tidak perlu banyak memanggil `advanceUntilIdle()`. |
| **Kekurangan** | Menulis tes membutuhkan pemahaman mendalam tentang siklus penjadwalan. | Dapat menyembunyikan bug *race condition* yang muncul di runtime produksi. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Selalu Gunakan Dependency Injection untuk Dispatchers**: Jangan pernah mengodekan `Dispatchers.IO`, `Dispatchers.Default`, atau `Dispatchers.Main` secara langsung (hardcoded) di layer domain/data/presentation. Selalu teruskan dispatcher melalui konstruktor kelas sehingga dapat ditimpa dengan `TestDispatcher`.
- **Gunakan `cancelAndIgnoreRemainingEvents()`**: Pada `StateFlow` atau `SharedFlow` yang tidak pernah berhenti (*infinite stream*), akhiri blok Turbine dengan `cancelAndIgnoreRemainingEvents()` untuk membersihkan listener tanpa menimbulkan `AssertionError` akibat emisi yang belum terkonsumsi.
- **Isolasi Dispatchers.Main**: Selalu gunakan kombinasi `Dispatchers.setMain(testDispatcher)` di `@Before` dan `Dispatchers.resetMain()` di `@After` untuk mencegah kebocoran state statis antar-pengujian unit.

#### Don'ts
- **Jangan Menggunakan `Thread.sleep()`**: `Thread.sleep()` akan membekukan thread eksekutor pengujian sehingga `TestScheduler` tidak dapat memproses antrean tugas virtual time, memicu deadlock atau false timeout.
- **Jangan Mengabaikan Unconsumed Events**: Turbine secara default memvalidasi bahwa tidak ada event tertinggal di akhir blok `test { }` jika menggunakan `expectNoEvents()` atau jika flow selesai. Mengabaikan sisa item sering kali menutupi bug logika di mana data ganda (*duplicate emissions*) diproduksi tanpa sengaja.

#### Edge Cases & Conflation Trap
`StateFlow` dirancang secara *conflated* (hanya menyimpan nilai terakhir). Jika produser mengemisi dua data berturut-turut tanpa suspensi sebelum collector sempat berjalan:
```kotlin
// Produksi
_state.value = 1
_state.value = 2

// Konsumsi Turbine
flow.test {
    // Pada StandardTestDispatcher, jika tidak ada pergeseran scheduler di antara mutasi,
    // nilai 1 dilewati (conflated) dan awaitItem() langsung menerima 2.
    assertEquals(2, awaitItem()) 
}
```
Jika aplikasi menuntut setiap perubahan status terkirim tanpa diskonflasi, ubah tipe streaming menjadi `Channel` atau `SharedFlow(replay = 0, extraBufferCapacity = ...)` tergantung kebutuhan fungsionalitas.

### 5. Tantangan Eksplorasi Mandiri

1. **Pengujian Race Condition pada Refresh Token**:
   Buatlah sebuah implementasi `AuthRepository` yang memiliki fungsi konkurensi: melakukan pemanggilan API secara paralel ketika token kedaluwarsa. Gunakan `StandardTestDispatcher` untuk mengorkestrasi penundaan eksekusi secara granular (`advanceTimeBy`) dan buktikan bahwa refresh token hanya dipanggil tepat satu kali meskipun ada 5 request HTTP paralel yang memicu error 401 secara bersamaan.

2. **Deteksi Emisi Terconflate dengan Turbine**:
   Implementasikan pengujian untuk skenario download progress:
   - Buat Flow yang mengemisi progress 0% sampai 100% dengan interval simulasi `delay(10)`.
   - Gunakan `StandardTestDispatcher`.
   - Modifikasi laju virtual time (`advanceTimeBy(50)`) dan catat event apa saja yang berhasil ditangkap oleh Turbine versus event yang hilang akibat mekanisme *conflation* pada pemanggilan operator `.conflate()`.
