## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa perangkat lunak berorientasi objek, pengembang sering kali terjebak dalam dilema antara **Type Safety** dan **Performance**:
1. **Primitive Obsession**: Menggunakan tipe primitif (`String`, `Long`, `Int`) secara langsung untuk merepresentasikan entitas domain (misal: `userId: Long`, `orderId: Long`). Pendekatan ini sangat hemat alokasi memori, namun rawan *human error*—kompiler tidak akan memprotes jika nilai `userId` dan `orderId` tertukar secara tidak sengaja.
2. **Standard Wrapper Class**: Membungkus tipe primitif ke dalam class biasa (misal: `data class UserId(val value: Long)`). Pendekatan ini menjamin *type safety*, namun membebani memori karena setiap *instance* membutuhkan alokasi objek baru di *heap* beserta *pointer overhead*, *garbage collection (GC) pressure*, dan hilangnya *CPU cache locality*.

```
Standard Wrapper Class (Heap Overhead):
[ Pointer to Class Metadata (8-16 bytes) | Mark Word (8-16 bytes) | Actual Value (8 bytes) ] -> Heap Allocation

Value Class / Inline Class (Zero-Cost Abstraction):
[ Actual Value (8 bytes) ] -> Disimpan langsung di Call Stack / CPU Register (Unboxed)
```

Untuk mengatasi dilema ini, Kotlin menghadirkan **Value Classes** (didefinisikan dengan `@JvmInline value class`). 

#### Arsitektur di Balik Layar
Value Class adalah mekanisme abstraksi berbiaya nol (*zero-cost abstraction*). Pada saat kompilasi (*compile-time*), tipe data diperlakukan sebagai kelas yang sepenuhnya berbeda untuk menjamin kepatuhan tipe secara statis. Namun, ketika *bytecode* Java digenerasikan, Kotlin compiler menghapus (*erases*) pembungkus tersebut dan menggantinya langsung dengan tipe data dasarnya (*underlying type*).

Fitur ini dirancang selaras dengan evolusi Java Virtual Machine masa depan melalui **Project Valhalla** (JEP 401), yang bertujuan mengintegrasikan *primitive-like performance* ke dalam sistem objek JVM.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem pembayaran e-commerce berkinerja tinggi yang memproses jutaan transaksi per detik tanpa risiko kesalahan parameter (*parameter confusion*) dan tanpa biaya alokasi objek berlebih.

```kotlin
package com.payment.engine

// 1. Definisi Value Classes dengan anotasi @JvmInline
@JvmInline
value class AccountId(val rawId: String) {
    init {
        require(rawId.isNotBlank()) { "AccountId tidak boleh kosong." }
    }
}

@JvmInline
value class Currency(val code: String) {
    init {
        require(code.length == 3) { "Kode mata uang harus 3 karakter ISO (contoh: IDR, USD)." }
    }
}

@JvmInline
value class Money(val amountInCents: Long) {
    init {
        require(amountInCents >= 0) { "Jumlah uang tidak boleh negatif." }
    }

    // Value class dapat memiliki properti dan fungsi terhitung
    val formatted: String
        get() = "${amountInCents / 100}.${(amountInCents % 100).toString().padStart(2, '0')}"

    operator fun plus(other: Money): Money = Money(this.amountInCents + other.amountInCents)
    operator fun minus(other: Money): Money {
        val result = this.amountInCents - other.amountInCents
        require(result >= 0) { "Saldo tidak mencukupi." }
        return Money(result)
    }
}

// 2. Business Logic menggunakan strongly-typed domain model
class PaymentEngine {
    // Pada tingkat bytecode JVM, fungsi ini dikompilasi menjadi:
    // public final void processTransaction-<hash>(String sender, String receiver, long money, String currency)
    fun processTransaction(
        sender: AccountId,
        receiver: AccountId,
        money: Money,
        currency: Currency
    ) {
        println("Processing transfer: ${money.formatted} ${currency.code} dari ${sender.rawId} ke ${receiver.rawId}")
        // Transaksi diproses langsung menggunakan tipe primitif di tingkat CPU register
    }
}

fun main() {
    val sender = AccountId("ACC-001")
    val receiver = AccountId("ACC-002")
    val initialAmount = Money(150_000L) // Rp 1500.00
    val additionalFee = Money(2_500L)    // Rp 25.00
    val total = initialAmount + additionalFee
    val idr = Currency("IDR")

    val engine = PaymentEngine()

    // Aman secara compile-time:
    // engine.processTransaction(receiver, sender, idr, total) -> Gagal kompilasi! Type mismatch.
    engine.processTransaction(sender, receiver, total, idr)
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Name Mangling
Karena tipe data dibungkus ulang menjadi tipe dasarnya, JVM berpotensi mengalami tabrakan tanda tangan method (*signature clash*). Pertimbangkan dua fungsi berikut:

```kotlin
fun submit(id: AccountId) { ... }
fun submit(id: String) { ... }
```

Jika Kotlin hanya menghapus bungkusnya, kedua fungsi akan memiliki signature JVM yang identik: `submit(Ljava/lang/String;)V`. 
Untuk mengatasinya, compiler Kotlin menggunakan teknik **Name Mangling**. Nama fungsi yang menerima value class diubah secara internal dengan menyematkan hash unik:
```
submit-T8jKm3A(java.lang.String id)
submit(java.lang.String id)
```

#### Alokasi Memori: Kapan Terjadi Boxing vs Unboxing?
Meskipun disebut *zero-cost*, Value Class tidak selalu bebas alokasi. Kotlin compiler akan melakukan **Boxing** (mengalokasikan objek pembungkus di Heap) dalam kondisi berikut:

1. **Sebagai Generik**: Ketika value class digunakan dalam generic collection (`List<Money>`). Karena Java Generic bertipe terhapus (*type erasure*) dan memerlukan `java.lang.Object`, JVM terpaksa melakukan boxing terhadap value class tersebut.
2. **Sebagai Interface**: Jika value class mengimplementasikan sebuah interface dan dioperasikan melalui referensi interface tersebut (`val payable: IPayable = Money(100)`).
3. **Sebagai Nilai Nullable**: `val m: Money? = null` atau `val m: Money? = Money(100)`. JVM primitive tidak mengenal konsep `null`, sehingga diperlukan alokasi wrapper untuk menandai status `null`.

#### Trade-offs
- **Keuntungan**: Mengeliminasi alokasi *Object Header* (umumnya 12-16 bytes per instance pada JVM 64-bit), memutus *pointer chasing*, dan memaksimalkan penggunaan L1/L2 data cache pada CPU.
- **Kerugian**: Pemanggilan dari kode Java menjadi kikuk (*cumbersome*) karena harus memanggil nama fungsi hasil mangling atau mengakses method yang di-box secara eksplisit. Value class juga tidak dapat memiliki identitas referensial (`===` dilarang).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan untuk Identifier**: Terapkan pada ID domain (`CustomerId`, `TransactionId`, `Sku`) untuk mencegah *parameter accidental swapping*.
- **Gunakan untuk Domain Units & Primitives**: Implementasikan untuk tipe data yang memiliki unit satuan eksplisit (`Kilograms`, `Milliseconds`, `Cents`).
- **Gunakan Interface untuk Ekstensibilitas Polimorfik**: Value class diperbolehkan mengimplementasikan interface jika memerlukan abstraksi perilaku (namun sadari implikasi *boxing*-nya).

#### Don'ts
- **Jangan Gunakan pada Hot Loop Generic Collection**: Menempatkan jutaan `value class` di dalam `ArrayList<ValueClass>` meniadakan efisiensi performa karena setiap entri akan di-*box* ke Heap. Jika performa absolut pada koleksi diperlukan, pertahankan penggunaan *primitive array* dasar (`LongArray`, `IntArray`).
- **Jangan Menambahkan Mutable State**: Value class harus bersifat murni (*pure value*). State internal tidak boleh bermutasi.
- **Hindari Integrasi Java Mentah Tanpa `@JvmName`**: Jika method dengan parameter value class harus diakses oleh modul Java, gunakan `@JvmName("safeMethodName")` untuk meredam *mangled name*.

#### Edge Cases
- **Validasi `init` Block yang Kompleks**: Blok `init` tetap dieksekusi saat inisialisasi unboxed, tetapi jika inisialisasi melibatkan operasi I/O atau komputasi berat, overhead komputasi tetap berjalan meskipun alokasi heap nihil.
- **Kesetaraan Struktural vs Referensial**: Operator referensi identitas (`===`) ditolak secara absolut oleh compiler pada value class. Operasi equality (`==`) selalu didelegasikan ke `equals` bawaan dari underlying type.

1. **Investigasi Bytecode JVM**:

2. **Benchmarking Alokasi Memori dengan JMH (Java Microbenchmark Harness)**:
   Buat microbenchmark sederhana untuk membandingkan pemrosesan 10.000.000 iterasi kalkulasi aritmatika:
   - Kasus A: Menggunakan `data class Price(val value: Long)`
   - Kasus B: Menggunakan `@JvmInline value class Price(val value: Long)`
   - Kasus C: Menggunakan `Long` primitif murni.
   Ukur metrik *Allocation Rate* (MB/sec) dan *Garbage Collection Pause* dari ketiga skenario tersebut. Amati apakah Kasus B identik dengan Kasus C.
