## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, ekosistem JVM bergantung pada pustaka berbasis *runtime reflection* seperti Jackson atau Gson untuk serialisasi data. Pendekatan ini memiliki penalti performa yang signifikan: inspeksi metadata kelas dilakukan secara dinamis, *field access* melewati lapisan keamanan JVM, dan optimasi JIT (*Just-In-Time*) terhambat akibat alokasi memori yang sulit diprediksi. Selain itu, refleksi JVM tidak kompatibel dengan paradigma Kotlin Multiplatform (KMP) yang menargetkan JavaScript, Native (LLVM), dan Wasm.

`kotlinx.serialization` menyelesaikan masalah ini dengan memindahkan beban kerja dari *runtime reflection* ke *compile-time code generation*.

```
   Source Code (.kt)
   [@Serializable data class]
            │
            ▼
┌────────────────────────┐
│ Kotlin Compiler Plugin │ ──► Menghasilkan `$serializer` companion class
└────────────────────────┘     & implementasi `KSerializer<T>` statis
            │
            ▼
     Bytecode (.class)
            │
            ▼
┌────────────────────────┐
│ Runtime Library        │ ──► Menggabungkan Schema (KSerializer) dengan 
│ (kotlinx-serialization)│     Format Enkoder/Dekoder (JSON, ProtoBuf, CBOR)
└────────────────────────┘
```

Arsitektur `kotlinx.serialization` terbagi menjadi dua komponen utama:

1. **Compiler Plugin**:
   Saat fase kompilasi Kotlin berlangsung, *compiler plugin* mendeteksi anotasi `@Serializable`. Plugin ini menginjeksi:
   - Kelas statis tersembunyi bernama `$serializer` yang mengimplementasikan antarmuka `KSerializer<T>`.
   - Metadata struktur skema (`SerialDescriptor`) yang merekam daftar *properties*, tipe data, indeks, dan anotasi terkait secara presisi.
   - Fungsi penunjang internal seperti `write$Self` dan *synthetic constructor* yang mengelola inisialisasi *default value* berbasis *bitmask*.

2. **Runtime Core & Format Decoupling**:
   `kotlinx.serialization` memisahkan secara tegas antara definisi model data dan representasi kabel (*wire format*). Inti pustaka menyediakan abstraksi:
   - `Encoder` / `Decoder`: Kontrak antarmuka primitif level rendah untuk membaca dan menulis data stream (`encodeInt`, `decodeString`, dll.).
   - `KSerializer<T>`: Jembatan yang mengetahui cara memetakan *instance* `T` ke serangkaian instruksi pada `Encoder` / `Decoder`.
   - Format engine (seperti modul `kotlinx-serialization-json`): Bertanggung jawab mem-parsing teks mentah menjadi token/AST (*Abstract Syntax Tree*) dan mengumpankannya ke `Decoder`.

Pemisahan ini memungkinkan model data yang sama diserialisasi ke JSON, Protocol Buffers, atau CBOR tanpa modifikasi kode kelas sedikit pun.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern untuk memproses respons API sistem pembayaran yang mencakup:
- Polimorfisme berbasis kelas bersegel (*sealed hierarchy*).
- *Custom serializer* untuk tipe data pihak ketiga (misalnya `java.time.Instant`).
- Konfigurasi `Json` engine yang tangguh untuk lingkungan produksi.

```kotlin
package com.example.serialization

import kotlinx.serialization.*
import kotlinx.serialization.descriptors.*
import kotlinx.serialization.encoding.*
import kotlinx.serialization.json.*
import java.time.Instant
import java.time.format.DateTimeParseException

// 1. Custom Serializer untuk tipe eksternal yang tidak memiliki @Serializable
object InstantIsoSerializer : KSerializer<Instant> {
    override val descriptor: SerialDescriptor = 
        PrimitiveSerialDescriptor("java.time.Instant", PrimitiveKind.STRING)

    override fun serialize(encoder: Encoder, value: Instant) {
        encoder.encodeString(value.toString())
    }

    override fun deserialize(decoder: Decoder): Instant {
        val raw = decoder.decodeString()
        return try {
            Instant.parse(raw)
        } catch (e: DateTimeParseException) {
            throw SerializationException("Gagal mem-parsing ISO-8601 Instant: $raw", e)
        }
    }
}

// 2. Polimorfisme Tipe Data Transaksi Pembayaran
@Serializable
sealed interface PaymentMethod {
    val provider: String
}

@Serializable
@SerialName("CREDIT_CARD") // Diskriminator eksplisit menggantikan FQCN
data class CreditCard(
    override val provider: String,
    @SerialName("masked_pan") val maskedPan: String,
    val expiry: String
) : PaymentMethod

@Serializable
@SerialName("E_WALLET")
data class EWallet(
    override val provider: String,
    @SerialName("account_id") val accountId: String
) : PaymentMethod

// 3. Root Domain Model
@Serializable
data class Transaction(
    val id: String,
    val amountCents: Long,
    val status: TransactionStatus,
    val paymentMethod: PaymentMethod,
    @Serializable(with = InstantIsoSerializer::class)
    val createdAt: Instant,
    // Mengabaikan field internal dari serialization payload
    @Transient
    val internalTraceId: String = "TRACE-DEFAULT"
)

@Serializable
enum class TransactionStatus {
    PENDING,
    SUCCESS,
    FAILED
}

// 4. Inisialisasi Json Runtime Singleton Terkonfigurasi
val AppJson = Json {
    ignoreUnknownKeys = true        // Toleransi terhadap evolusi schema API hulu
    coerceInputValues = true        // Fallback ke default value jika JSON bernilai null untuk non-nullable
    encodeDefaults = true           // Selalu sertakan field default pada saat serialisasi
    classDiscriminator = "type"     // Menentukan field diskriminator polimorfik (default: "type")
    prettyPrint = false             // Matikan pretty print untuk efisiensi throughput memori
}

fun main() {
    val rawJson = """
    {
        "id": "tx_998124",
        "amountCents": 150000,
        "status": "SUCCESS",
        "paymentMethod": {
            "type": "CREDIT_CARD",
            "provider": "VISA",
            "masked_pan": "4111-XXXX-XXXX-1111",
            "expiry": "12/28"
        },
        "createdAt": "2024-02-15T08:30:00Z",
        "metadata_unused": "akan diabaikan karena ignoreUnknownKeys = true"
    }
    """.trimIndent()

    // Deserialisasi
    val transaction: Transaction = AppJson.decodeFromString(rawJson)
    println("Berhasil deserialisasi transaksi ID: ${transaction.id}")
    println("Tipe pembayaran: ${transaction.paymentMethod::class.simpleName}")

    // Serialisasi kembali ke format JSON
    val serializedJson = AppJson.encodeToString(transaction)
    println("JSON Hasil Serialisasi:\n$serializedJson")
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Di balik layar, Kotlin compiler plugin menyuntikkan konstruktor sintetik khusus dan metode pelacak pada setiap kelas `@Serializable`.

Misalkan terdapat kelas sederhana:
```kotlin
@Serializable
data class User(val id: Int, val name: String = "Unknown")
```

Compiler mengompilasi konstruktor sintetis berikut:
```java
// Bytecode Java Decompiled Representation
public User(int seen0, int id, String name, SerializationConstructorMarker marker) {
    if ((seen0 & 1) == 0) { // Bitmask 1 mewakili property index 0 (id)
        throw new MissingFieldException("id");
    }
    this.id = id;
    if ((seen0 & 2) == 0) { // Bitmask 2 mewakili property index 1 (name)
        this.name = "Unknown"; // Menggunakan nilai default jika bit tidak aktif
    } else {
        this.name = name;
    }
}
```
Mekanisme ini menggunakan teknik **Bitmasking (`seen0`, `seen1`, ...)** untuk melacak properti mana saja yang ada di payload JSON. Tiap satu integer tipe `Int` (32 bit) mampu melacak keberadaan hingga 32 properti. Jika sebuah kelas memiliki 40 properti, compiler menghasilkan dua variabel penanda: `seen0` dan `seen1`.

#### Alokasi Memori / Resource
- **Zero-Reflection**: Saat parsing, runtime memanggil `decodeElementIndex(descriptor)` secara linear. Ia mencocokkan hash string dari nama kunci JSON atau indeksnya langsung melalui switch-case terkompilasi, menghindari pemanggilan `Field.setAccessible()` atau `Method.invoke()` yang mengalokasikan memori pada metadata heap JVM.
- **Streaming Parser**: Mesin JSON membaca karakter per karakter dari *underlying buffer* (`CharArrayBuffer`). String hanya dialokasikan ketika nilainya benar-benar diekstrak ke properti domain class, tidak membuat representasi perantara seperti DOM Nodes (`Map<String, Any>`) kecuali menggunakan tipe eksplisit `JsonElement`.

#### Trade-offs
- **Dampak Ukuran Bytecode**: Karena logika serialisasi/deserialisasi di-*generate* untuk setiap kelas, ukuran file `.class` (dan APK/JAR akhir) akan sedikit membengkak dibandingkan solusi reflektif murni.
- **Fleksibilitas Dinamis Rendah**: Mengubah representasi skema secara dinamis pada saat *runtime* (tanpa mendefinisikan *custom serializer*) jauh lebih kompleks dibanding Jackson yang mengizinkan manipulasi runtime type-binding melalui `TypeReference`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Instance `Json` Tunggal (Singleton)**: Objek konfigurasi `Json { ... }` bersifat *thread-safe* dan melakukan *caching* internal terhadap `KSerializer` dan `SerialDescriptor`. Instansiasi berulang `Json` pada setiap HTTP request akan memicu pemborosan memori dan penalti re-evaluasi skema.
- **Isolasi Kontrak Eksternal dengan `@SerialName`**: Jangan mengandalkan nama properti Kotlin untuk skema payload publik. Gunakan `@SerialName("snake_case_key")` agar Anda bebas me-refactor nama variabel Kotlin tanpa memutus integrasi API.
- **Gunakan `sealed hierarchy` untuk Union Types**: Manfaatkan `sealed class` atau `sealed interface` untuk data polimorfik. Compiler akan otomatis membuat skema diskriminator tertutup yang valid saat kompilasi.

#### Don'ts
- **Jangan Mengasumsikan Default Arguments Otomatis Aman**:
  Secara default, jika sebuah payload JSON memiliki key baru yang tidak terdefinisi di kelas DTO, `kotlinx.serialization` akan melempar `SerializationException`. Selalu setel `ignoreUnknownKeys = true` saat mengonsumsi data dari REST API pihak ketiga.
- **Jangan Gunakan `@Contextual` Tanpa Mendaftarkan Module**:
  Menggunakan anotasi `@Contextual` pada properti memerlukan *runtime mapping* melalui `SerializersModule`. Kegagalan registrasi modul pada instans `Json` akan menyebabkan *runtime crash* (`SerializationException: Serializer for class '...' has not been found`).

#### Edge Cases
- **Penanganan Nilai `null` vs Field Tidak Ada (Missing Keys)**:
  Jika properti didefinisikan sebagai `val status: String = "ACTIVE"`, payload `{}` akan menghasilkan `"ACTIVE"`. Namun, payload `{"status": null}` akan memicu kegagalan deserialisasi karena field tersebut non-nullable. Untuk memaksa runtime mengabaikan `null` dan beralih ke *default value*, aktifkan konfigurasi:
  ```kotlin
  val json = Json { coerceInputValues = true }
  ```
- **Properti Generic Tanpa Reified Type**:
  Deserialisasi tipe generik `T` secara langsung akan gagal tanpa `KSerializer<T>` eksplisit atau kata kunci `inline` dengan `reified T`:
  ```kotlin
  // Benar:
  inline fun <reified T> parseResponse(raw: String): T = AppJson.decodeFromString(raw)

  // Salah (akan gagal kompilasi):
  fun <T> parseResponseWrong(raw: String): T = AppJson.decodeFromString(raw)
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Custom Flattening Serializer**:
   Buatlah sebuah `KSerializer<Address>` khusus untuk kelas:
   ```kotlin
   data class UserProfile(val id: String, val address: Address)
   data class Address(val street: String, val city: String)
   ```
   Deserialisasikan JSON berikut langsung ke objek `UserProfile` tanpa mengubah struktur kelas Kotlin:
   ```json
   {
     "id": "usr_101",
     "street": "Sudirman Kav 5",
     "city": "Jakarta"
   }
   ```
   *(Hint: Gunakan `JsonObject` decoding manipulatif di dalam implementasi kustom `KSerializer` atau manfaatkan `buildClassSerialDescriptor`)*.

2. **Analisis Bytecode Bitmask**:
   Kompilasikan sebuah kelas `@Serializable` yang memiliki 35 properti opsional (memiliki default value). Lakukan *decompile* file `.class` yang dihasilkan menggunakan `javap -c` atau decompiler bawaan IntelliJ IDEA. Analisis bagaimana compiler menambahkan field penanda `seen0` dan `seen1` untuk mengoperasikan seleksi kondisional per bit.
