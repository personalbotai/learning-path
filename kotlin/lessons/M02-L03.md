### 1. Konsep & Arsitektur Mendalam

Secara filosofis, Kotlin menganut prinsip desain dari buku *Effective Java* (Item 19: *Design and document for inheritance or else prohibit it*). Berbeda dengan Java di mana class dan method bersifat terbuka (`open`/non-final) secara default, di Kotlin seluruh class, fungsi, dan properti bersifat **`final` secara default**. 

Pendekatan ini dirancang untuk mencegah *Fragile Base Class Problem*—sebuah kondisi di mana perubahan internal pada superclass secara tidak sengaja merusak fungsionalitas subclass yang melakukan override tanpa sengaja atau tanpa pemahaman kontrak yang jelas.

```
                  +-------------------+
                  |    kotlin.Any     |  <-- Root hierarchy (bukan java.lang.Object langsung)
                  +-------------------+
                            |
           +----------------+----------------+
           |                                 |
+----------------------+          +----------------------+
|   open class Base    |          |   class Standalone   | (implicit: final)
+----------------------+          +----------------------+
           |
+----------------------+
| class Derived : Base | (explicit: final, override base members)
+----------------------+
```

#### Keyword `open` dan `override`
- **`open`**: Memberitahu compiler bahwa class dapat di-extend, atau method/property dapat di-override. Tanpa modifier `open`, compiler akan menolak pewarisan pada compile-time.
- **`override`**: Anotasi penegasan wajib (*mandatory modifier*) saat subclass mengimplementasikan atau mengubah tingkah laku member dari superclass. Desain ini mengeliminasi bug *accidental overloading/shadowing*. Member yang di-override secara implisit berstatus `open` terhadap turunan berikutnya, kecuali secara eksplisit ditandai sebagai `final override`.

#### Semantik `kotlin.Any`
Setiap class di Kotlin secara implisit menurunkan `kotlin.Any`. Namun, `kotlin.Any` **bukanlah** `java.lang.Object`. 
- `kotlin.Any` hanya mengekspos tiga kontrak dasar: `equals()`, `hashCode()`, dan `toString()`.
- Method seperti `wait()`, `notify()`, `getClass()`, dan `clone()` yang ada di Java Object sengaja dieliminasi dari interface publik `kotlin.Any` demi abstraksi multiplatform (Kotlin/Native, Kotlin/JS, Kotlin/Wasm). 
- Di target JVM, compiler memetakan `kotlin.Any` langsung ke `java.lang.Object` pada level bytecode.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi arsitektur pemrosesan transaksi pembayaran (*Payment Gateway Engine*) yang menggunakan hierarki class secara aman.

```kotlin
// 1. Root class didefinisikan sebagai open agar bisa diturunkan
open class PaymentProcessor(
    val processorId: String,
    open val timeoutSeconds: Int = 30 // Property 'open' dapat di-override
) {
    init {
        // PERINGATAN: Membaca open property di sini berisiko (lihat Section 4)
        println("Initializing PaymentProcessor: id=$processorId, timeout=$timeoutSeconds")
    }

    // Fungsi terbuka untuk modifikasi algoritma
    open fun processPayment(transactionId: String, amountCents: Long): Boolean {
        println("Base verification for transaction $transactionId")
        return amountCents > 0
    }

    // Fungsi final: Kontrak inti yang TIDAK BOLEH diubah oleh subclass
    fun auditLog(transactionId: String, status: String) {
        println("[AUDIT] Tx: $transactionId | Status: $status | Processor: $processorId")
    }

    // Override Any.toString()
    override fun toString(): String {
        return "PaymentProcessor(id='$processorId', timeout=$timeoutSeconds)"
    }
}

// 2. Subclass melakukan pewarisan dengan memanggil primary constructor superclass
open class CreditCardProcessor(
    processorId: String,
    override val timeoutSeconds: Int = 60, // Override property
    val merchantAccount: String
) : PaymentProcessor(processorId, timeoutSeconds) {

    // Override function base class
    override fun processPayment(transactionId: String, amountCents: Long): Boolean {
        // Memanggil logika validasi dasar dari superclass
        val baseValid = super.processPayment(transactionId, amountCents)
        if (!baseValid) return false

        println("Authorizing $amountCents via Credit Card Network for Merchant: $merchantAccount")
        return true
    }

    // Menutup kemampuan override untuk subclass di bawahnya
    final override fun toString(): String {
        return "CreditCardProcessor(merchant='$merchantAccount', parent=${super.toString()})"
    }
}

// 3. Subclass turunan kedua
class HighSecurityCreditCardProcessor(
    processorId: String,
    merchantAccount: String
) : CreditCardProcessor(processorId, 120, merchantAccount) {

    override fun processPayment(transactionId: String, amountCents: Long): Boolean {
        println("Triggering 3D-Secure MFA...")
        return super.processPayment(transactionId, amountCents)
    }

    // COMPILER ERROR jika di-uncomment, karena toString() sudah 'final override' di CreditCardProcessor
    // override fun toString(): String = "HighSecurity"
}

fun main() {
    val processor: PaymentProcessor = HighSecurityCreditCardProcessor(
        processorId = "STRIPE-EU",
        merchantAccount = "ACC-9921"
    )

    val isSuccess = processor.processPayment("TX-8801", 50000)
    processor.auditLog("TX-8801", if (isSuccess) "SUCCESS" else "FAILED")
    println(processor.toString())
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (JVM Bytecode)
1. **Instruksi `invokevirtual` & Virtual Method Table (vtable):**
   - Class tanpa modifier `open` dikompilasi menjadi Java Class dengan flag bytecode `ACC_FINAL`. Compiler JVM / JIT dapat melakukan optimasi inline (*monomorphic call-site optimization*) karena tidak ada subclass.
   - Method yang ditandai `open` atau `override` dikompilasi tanpa flag `final`, sehingga pemanggilan method dieksekusi via `invokevirtual`. JVM akan membaca pointer method dari *Virtual Method Table* (vtable) milik instance saat runtime (*dynamic dispatch*).
2. **Representasi `kotlin.Any`:**
   - Di level JVM bytecode, tipe `kotlin.Any` diubah langsung (*erased/mapped*) menjadi signature `Ljava/lang/Object;`.
   - Method `Any.equals(other: Any?)` dikompilasi menjadi bytecode `public boolean equals(java.lang.Object)`.

#### Alokasi Memori & Urutan Inisialisasi
Saat instance `HighSecurityCreditCardProcessor` dialokasikan di Heap:
1. Blok memori dialokasikan untuk seluruh instance variabel dari `Any` (overhead object header 12/16 bytes) -> `PaymentProcessor` -> `CreditCardProcessor` -> `HighSecurityCreditCardProcessor`.
2. Konstruktor superclass dieksekusi **terlebih dahulu** secara hierarkis ke atas (*bottom-up delegation, top-down execution*):
   - Konstruktor `java.lang.Object` berjalan.
   - Konstruktor `PaymentProcessor` berjalan (dan mengeksekusi blok `init`).
   - Konstruktor `CreditCardProcessor` berjalan.
   - Konstruktor `HighSecurityCreditCardProcessor` berjalan.

#### Trade-offs
- **Compile-time safety vs Extensibility:** Pendekatan `final by default` mencegah mutasi tak terduga, tetapi library author harus secara eksplisit mendesain titik ekstensi menggunakan `open`. Framework yang bergantung pada bytecode generation/proxying runtime (seperti Spring CGLIB atau Mockito tempo dulu) memerlukan compiler plugin khusus (`kotlin-spring` atau `all-open`) untuk membuka class secara otomatis.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Prinsip Komposisi daripada Inheritansi:** Utamakan delegasi interface (*Interface Delegation* via keyword `by`) dibanding membuat hierarki class yang dalam (> 2 level inheritance).
- **Tutup override dengan `final override`:** Jika class Anda ditandai `open` tetapi suatu method override tidak aman untuk diubah lagi oleh subclass selanjutnya, kunci method tersebut dengan `final override`.
- **Implementasikan `equals` dan `hashCode` secara berpasangan:** Jika meng-override `equals()`, selalu override `hashCode()`. Keduanya diturunkan dari `Any`. Inkonsistensi menyebabkan kegagalan pencarian data pada struktur `HashMap` atau `HashSet`.

#### Don'ts
- **JANGAN PERNAH mengakses member `open` di dalam blok `init` atau constructor superclass!**
  Ini adalah salah satu bug paling berbahaya di Kotlin.

#### Edge Cases: The "Leaking `this` Before Initialization" Bug
Perhatikan skenario berbahaya berikut:

```kotlin
open class Base {
    open val size: Int = 10

    init {
        // Berbahaya: mengakses open property dari dalam init superclass
        println("Base init -> size: $size") 
    }
}

class Sub : Base() {
    override val size: Int = 20
}

fun main() {
    Sub() // OUTPUT: Base init -> size: 0
}
```

**Mengapa hasilnya `0` dan bukan `10` atau `20`?**
1. Konstruktor `Base` dipanggil sebelum konstruktor `Sub`.
2. Pada saat blok `init` di `Base` dieksekusi, field backing `size` milik `Sub` **belum diinisialisasi** (masih berupa default byte/integer zero value di Heap).
3. Karena `size` bersifat `open`, Kotlin menggunakan dynamic dispatch (pemanggilan *getter* polimorfik) yang merujuk pada getter milik `Sub`.
4. Hasilnya: getter mengembalikan nilai default variabel yang belum matang (`0`), bukan `10` dan bukan `20`. Jika tipenya adalah Non-Nullable Reference (misalnya `String`), ini akan melempar `NullPointerException` seketika pada tipe data yang dikira aman dari null!

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Bytecode:** 
   Tulis sebuah class `open class Shape` dengan method `open fun draw()` dan subclass `class Circle : Shape()`. Buka IntelliJ IDEA, akses menu `Tools -> Kotlin -> Show Kotlin Bytecode`, lalu klik tombol `Decompile` to Java. Analisis bagaimana keyword `open`, `override`, dan struktur konstruktor dipetakan ke dalam sintaks Java murni.
2. **Simulasi NullPointerException pada Non-Null Type:** 
   Buktikan bug "Leaking this" dengan membuat class `Base` yang memanggil `open val name: String` di dalam fungsi yang dipanggil oleh `init`. Buat subclass `Derived` yang meng-override `name = "Production"`. Buat kondisi yang menghasilkan crash `NullPointerException` saat runtime meskipun tipe datanya adalah non-nullable `String`.
