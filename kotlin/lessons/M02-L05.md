### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur perangkat lunak berbasis OOP, objek sering kali berfungsi murni sebagai penampung data (*Data Transfer Objects*, *Value Objects*, atau *State Payloads*). Di ekosistem Java konvensional, pembuatan kelas semacam ini membutuhkan kode *boilerplate* yang repetitif: `getter`, `setter`, `equals()`, `hashCode()`, dan `toString()`.

Kotlin mengatasi redundansi ini melalui **Data Classes** (ditandai dengan *modifier* `data`). Ketika sebuah *class* dideklarasikan sebagai `data class`, Kotlin Compiler (`kotlinc`) secara otomatis menginferensi dan menginjeksi sejumlah metode sintetis (*synthetic methods*) ke dalam *bytecode* pada saat kompilasi. Metode-metode tersebut diturunkan secara eksklusif dari properti yang dideklarasikan di dalam **primary constructor**.

```
                         +-----------------------+
                         | data class User(...)  |
                         +-----------------------+
                                     |
                               kotlinc Phase
                                     v
       +-----------------------------------------------------------+
       | - equals(other: Any?): Boolean (Structural Equality)       |
       | - hashCode(): Int (Consistent with equals)                |
       | - toString(): String ("User(id=..., name=...)")           |
       | - copy(...): User (Immutable modification via copy-on-read)|
       | - component1(), component2(), ... (Positional mapping)    |
       +-----------------------------------------------------------+
```

#### Aturan Arsitektural Data Class
1. **Primary Constructor Minimum**: Harus memiliki minimal satu parameter.
2. **Eksplisit Val/Var**: Semua parameter pada *primary constructor* wajib dideklarasikan dengan `val` atau `var` (sangat direkomendasikan `val` untuk menjamin prinsip *immutability*).
3. **Pembatasan Pewarisan**: *Data class* tidak dapat berstatus `abstract`, `open`, `sealed`, atau `inner`. Namun, *data class* dapat mengimplementasikan *interface* dan mewarisi kelas non-data lainnya (open class biasa).
4. **Isolasi Properti Luar**: Properti yang dideklarasikan di dalam *class body* (di luar *primary constructor*) **dikecualikan** dari kalkulasi otomatis `equals()`, `hashCode()`, `toString()`, dan `copy()`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh implementasi *immutable state management* pada domain pemrosesan transaksi keuangan:

```kotlin
import java.math.BigDecimal
import java.time.Instant
import java.util.UUID

// Value Object untuk melacak mutasi balance perbankan
data class TransactionRecord(
    val transactionId: UUID,
    val sourceAccountId: String,
    val destinationAccountId: String,
    val amount: BigDecimal,
    val isProcessed: Boolean = false,
    val metadata: Map<String, String> = emptyMap()
) {
    // Properti class body: TIDAK masuk ke equals, hashCode, copy, atau componentN
    val createdAt: Instant = Instant.now()
}

fun main() {
    val initialTx = TransactionRecord(
        transactionId = UUID.randomUUID(),
        sourceAccountId = "ACC-ID-8801",
        destinationAccountId = "ACC-ID-9942",
        amount = BigDecimal("1500000.00")
    )

    // 1. Immutable State Transition menggunakan copy()
    // copy() mengalokasikan instance baru tanpa memutasi instance lama
    val processedTx = initialTx.copy(
        isProcessed = true,
        metadata = mapOf("gateway" to "MIDTRANS_SNAP", "settledAt" to Instant.now().toString())
    )

    // 2. Destructuring Declaration didukung oleh compiler via componentN()
    val (id, source, destination, amount) = processedTx
    println("Dispatching Tx: $id | From: $source -> To: $destination | Val: Rp$amount")

    // 3. Structural Equality (equals & hashCode)
    val duplicateCheckTx = initialTx.copy()
    println("Structural check: ${initialTx == duplicateCheckTx}") // Output: true
    println("Referential check: ${initialTx === duplicateCheckTx}") // Output: false

    // Bukti bahwa properti body diabaikan oleh equals
    // Meskipun initialTx.createdAt dan duplicateCheckTx.createdAt berbeda (alokasi instan berbeda),
    // compiler tetap menghasilkan true karena keduanya identik di primary constructor.
    println("Equals ignore body: ${initialTx.equals(duplicateCheckTx)}") // Output: true
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Bytecode Compiler
Jika *bytecode* hasil kompilasi didekompilasi kembali ke format Java (`javap -c` atau IntelliJ Decompiler), compiler menghasilkan instruksi berikut:

1. **Destructuring via `componentN()`**:
   Untuk setiap parameter ke-$n$ di *primary constructor*, compiler menghasilkan metode sintetis `public final Type componentN()`.
   ```java
   // Decompiled Java representation
   public final UUID component1() { return this.transactionId; }
   public final String component2() { return this.sourceAccountId; }
   // dst...
   ```
   Ketika menulis kode `val (id, source) = tx`, compiler menerjemahkannya secara langsung menjadi:
   ```java
   UUID id = tx.component1();
   String source = tx.component2();
   ```
   Ini adalah pemetaan **posisional**, bukan pemetaan berbasis nama properti.

2. **Metode `copy()` dan `$default` Synthetic Bridge**:
   Compiler tidak hanya membuat metode `copy(...)`, melainkan menyertakan *synthetic bridge method* `copy$default(...)` yang menerima *bitmask* integer.
   ```java
   public static TransactionRecord copy$default(
       TransactionRecord obj, 
       UUID id, 
       String src, 
       String dest, 
       BigDecimal amt, 
       boolean proc, 
       Map meta, 
       int mask, 
       Object dummy
   ) {
       // Bitwise check: Jika bit ke-n adalah 0 (tidak disediakan argumen baru),
       // ambil properti asli dari objek sumber.
       if ((mask & 1) != 0) id = obj.transactionId;
       if ((mask & 2) != 0) src = obj.sourceAccountId;
       // ...
       return obj.copy(id, src, dest, amt, proc, meta);
   }
   ```
   Bitmasking ini memungkinkan pemanggilan `copy()` hanya dengan menimpa nilai parameter tertentu (*named arguments*) secara efisien tanpa membuat *overload explosion*.

#### Alokasi Memori & Shallow Copying
Metode `copy()` pada Kotlin melakukan **shallow copy**, bukan *deep copy*.
- Variabel primitif disalin nilainya (*value-copied*).
- Objek bertipe referensi (*reference types* seperti `Map`, `List`, atau objek kustom) disalin alamat memorinya (pointer). Instance baru merujuk pada objek heap yang sama dengan instance lama.
- Jika tipe data referensi di dalam *data class* bersifat *mutable* (misalnya `ArrayList`), memodifikasi list pada objek hasil salinan akan merusak data pada objek asli.

#### Trade-offs
- **Bytecode Overhead**: Mendeklarasikan *data class* dengan parameter sangat banyak (misal: 25+ fields) akan menghasilkan ukuran kelas `.class` yang membengkak karena kombinasi metode `componentN()`, `copy$default()`, kalkulasi kompleks `hashCode()`, dan representasi string.
- **Inheritance Rigidity**: Tidak dapat menjadi *base class* (dilarang menggunakan `open data class`) untuk mencegah *Liskov Substitution Principle (LSP) violation* pada saat mengevaluasi `equals()` dan *slicing* data pada pewarisan.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Jadikan Semua Properti `val`**: Selalu buat properti *primary constructor* bersifat *read-only*. Paradigma *data class* dirancang secara optimal untuk mendukung komputasi fungsional dan model konkurensi berbasis *immutability*.
- **Terapkan `copy()` untuk State Mutation**: Ubah *state* aplikasi dengan mengembalikan instance baru hasil `copy()`, menjaga prediktabilitas alur data (seperti pada pola Redux/MVI).

#### Don'ts
- **Menghindari Penggunaan `Array` di Primary Constructor**: 
  Array di JVM mengevaluasi kesetaraan berdasarkan identitas referensial (`===`), bukan konten struktural (`contentEquals`). Jika Anda memasukkan `Array` ke dalam *data class*, dua *instance* dengan isi data array yang identik akan menghasilkan `equals() == false`. Gunakan `List` atau koleksi generik lainnya.
- **Jangan Mengandalkan Destructuring untuk Struktur yang Sering Berubah**:
  Karena `componentN` bekerja berdasarkan urutan posisi parameter, mengubah urutan deklarasi properti di *primary constructor* akan merusak logika *destructuring* di *call site* tanpa adanya peringatan *compile-time error* (jika tipenya kompatibel).

#### Edge Cases & Pitfalls Tersembunyi

*Pitfall 1: Kesalahan Posisi pada Destructuring*
```kotlin
data class Coordinate(val latitude: Double, val longitude: Double)

val loc = Coordinate(latitude = -6.2088, longitude = 106.8456)

// Bahaya: Developer mengubah constructor Coordinate menjadi (val longitude: Double, val latitude: Double)
// Call site berikut TIDAK error saat kompilasi, namun menghasilkan bug logika fatal:
val (lat, long) = loc // 'lat' secara diam-diam menerima properti pertama (latitude/longitude)
```

*Pitfall 2: Masalah Array Equality*
```kotlin
data class SecurityPayload(val rawBytes: ByteArray)

val p1 = SecurityPayload(byteArrayOf(1, 2, 3))
val p2 = SecurityPayload(byteArrayOf(1, 2, 3))

// Meskipun isi byte array identik:
println(p1 == p2) // HASIL: false! Array equals mengecek referensi memori JVM.

// Solusi jika array mutlak dibutuhkan:
// Override equals() & hashCode() secara manual menggunakan Arrays.equals() / contentHashCode()
```

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Dekompilasi Bitmask**:
   Kompilasi sebuah `data class` yang memiliki 33 parameter (semuanya bernilai *default*). Lakukan dekompilasi menggunakan `javap -c` atau fitur *Show Kotlin Bytecode -> Decompile* di IntelliJ IDEA. Analisis mengapa compiler menghasilkan `int mask0`, `int mask1`, dan seterusnya pada metode sintetis `copy$default`.
2. **Array Deep Equality Override**:
   Buat sebuah `data class` yang menerima `ByteArray` dan properti `version: Int`. Lakukan *override* manual pada fungsi `equals()` dan `hashCode()` sehingga dua objek independen dengan urutan *byte* yang sama dievaluasi sebagai `true` dalam pembandingan struktural (`==`). Buktikan bahwa fungsi `copy()` tetap mempertahankan integritas perilaku tersebut.
