## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam reaktif pemrograman Kotlin Coroutines, **Cold Stream** (`Flow` standar) bersifat *lazy*—kode di dalam blok pembangun flow tidak akan dieksekusi sampai ada terminal operator (seperti `collect()`), dan setiap *collector* baru akan memicu eksekusi pipeline dari awal secara independen. 

Sebaliknya, **Hot Stream** (`SharedFlow` dan `StateFlow`) memiliki siklus hidup yang independen dari keberadaan *collector/subscriber*. Produser data dapat memancarkan (*emit*) nilai ke dalam stream terlepas dari apakah ada konsumen yang mendengarkan atau tidak. Karakteristik utamanya adalah **Multicasting**: satu emisi nilai didistribusikan secara bersamaan ke nol, satu, atau banyak *collector*.

```
                +-------------------+
                |   Producer/Emit   |
                +---------+---------+
                          |
                          v
         +---------------------------------+
         |       Hot Stream Buffer         |
         | (SharedFlowImpl/StateFlowImpl)  |
         +---+-------------+-------------+-+
             |             |             |
             v             v             v
       +-----------+ +-----------+ +-----------+
       |Collector A| |Collector B| |Collector C|
       +-----------+ +-----------+ +-----------+
```

#### SharedFlow: Broadcasting Engine
`SharedFlow` dirancang untuk memancarkan *event* atau data berulang ke banyak konsumen. Arsitekturnya dikonfigurasi melalui tiga parameter utama:
- `replay`: Jumlah nilai historis terakhir yang disimpan dalam *buffer cache* dan langsung dikirimkan ke setiap *collector* baru.
- `extraBufferCapacity`: Kapasitas buffer tambahan di luar `replay` untuk menangani disparitas kecepatan antara emitter dan collector (backpressure).
- `onBufferOverflow`: Strategi mitigasi jika buffer penuh:
  - `BufferOverflow.SUSPEND`: Emitter ditangguhkan (*suspend*) hingga buffer memiliki ruang.
  - `BufferOverflow.DROP_OLDEST`: Menghapus data tertua di buffer untuk memberi ruang bagi data baru.
  - `BufferOverflow.DROP_LATEST`: Membuang data yang sedang dipancarkan, mempertahankan isi buffer yang ada.

#### StateFlow: State Machine Terkonflasi
`StateFlow` adalah spesialisasi murni dari `SharedFlow` (`replay = 1`, `onBufferOverflow = BufferOverflow.DROP_OLDEST`) yang didesain khusus untuk mengelola *State* (keadaan aplikasi/UI).
Karakteristik arsitekturalnya:
1. **Always Holds a Value**: Harus selalu memiliki nilai awal (`initialValue`).
2. **Conflation**: Hanya menyimpan nilai terkini. Jika emitter memproduksi state baru sebelum konsumen lambat selesai memproses state lama, konsumen akan melompati state lama dan langsung menerima state terbaru.
3. **Equality Check Optimization**: Menggunakan pengecekan struktural `Any.equals()`. Jika emitter memancarkan nilai baru yang secara logis identik dengan nilai sebelumnya (`oldValue == newValue`), emisi tersebut **tidak akan diteruskan** ke downstream untuk mencegah re-komputasi/re-rendering yang tidak perlu.

### 2. Implementasi & Contoh Kasus Nyata

Contoh implementasi arsitektur State Management dan Event Notification pada aplikasi trading/saham:

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// Domain Models
data class PortfolioState(
    val balance: Double = 0.0,
    val openPositions: List<String> = emptyList(),
    val isLoading: Boolean = false
)

sealed interface TradeEvent {
    data class OrderExecuted(val ticker: String, val price: Double) : TradeEvent
    data class ExecutionFailed(val reason: String) : TradeEvent
}

// State Holder / ViewModel / Controller Layer
class TradingSessionManager(
    private val coroutineScope: CoroutineScope
) {
    // 1. StateFlow: Merepresentasikan UI State saat ini
    private val _portfolioState = MutableStateFlow(PortfolioState(isLoading = true))
    val portfolioState: StateFlow<PortfolioState> = _portfolioState.asStateFlow()

    // 2. SharedFlow: Merepresentasikan One-off Event (Snackbar/Toast/Notification)
    private val _tradeEvents = MutableSharedFlow<TradeEvent>(
        replay = 0,
        extraBufferCapacity = 64,
        onBufferOverflow = BufferOverflow.DROP_OLDEST
    )
    val tradeEvents: SharedFlow<TradeEvent> = _tradeEvents.asSharedFlow()

    fun updateBalance(amount: Double) {
        // Atomic state modification menggunakan update {}
        _portfolioState.update { currentState ->
            currentState.copy(
                balance = currentState.balance + amount,
                isLoading = false
            )
        }
    }

    suspend fun executeOrder(ticker: String, price: Double) {
        if (_portfolioState.value.balance >= price) {
            _portfolioState.update { it.copy(
                balance = it.balance - price,
                openPositions = it.openPositions + ticker
            ) }
            // Emit one-off event ke SharedFlow
            _tradeEvents.emit(TradeEvent.OrderExecuted(ticker, price))
        } else {
            _tradeEvents.emit(TradeEvent.ExecutionFailed("Insufficient balance for $ticker"))
        }
    }
}

// Simulation & Consumption
fun main() = runBlocking {
    val sessionScope = CoroutineScope(Dispatchers.Default + Job())
    val manager = TradingSessionManager(sessionScope)

    // Collector 1: UI State Renderer (StateFlow)
    val stateJob = launch {
        manager.portfolioState.collect { state ->
            println("[UI Render] Balance: $${state.balance} | Positions: ${state.openPositions} | Loading: ${state.isLoading}")
        }
    }

    // Collector 2: Notification System (SharedFlow)
    val eventJob = launch {
        manager.tradeEvents.collect { event ->
            when (event) {
                is TradeEvent.OrderExecuted -> println("[ALERT] Sukses: Membeli ${event.ticker} pada harga $${event.price}")
                is TradeEvent.ExecutionFailed -> println("[ERROR ALERT] Gagal: ${event.reason}")
            }
        }
    }

    // Simulasi alur kerja
    delay(50) // Memberikan waktu collector untuk subscribe
    manager.updateBalance(1000.0)
    
    // Testing Equality-check StateFlow: Nilai sama tidak memicu koleksi berulang
    manager.updateBalance(0.0) 

    manager.executeOrder("BTC", 450.0)
    manager.executeOrder("ETH", 700.0) // Harus gagal karena saldo tersisa 550.0

    delay(200)
    stateJob.cancel()
    eventJob.cancel()
    sessionScope.cancel()
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Subscription Slots (`AbstractSharedFlowSlot`)**: Baik `SharedFlowImpl` maupun `StateFlowImpl` menggunakan array internal dari *slots* (`StateFlowSlot` atau `SharedFlowSlot`). Setiap kali ada coroutine memanggil `collect`, slot kosong dicari atau dialokasikan melalui mekanisme `allocateSlot()`. Jika array penuh, ukurannya diperbesar secara dinamis (faktor 2x).
- **Sinkronisasi Thread-Safe**:
  - `SharedFlowImpl` memproteksi modifikasi daftar *collector* dan *head/tail pointer buffer* menggunakan monitor lock (`synchronized(this)` via JVM intrinsics) yang dirancang sangat cepat (minim *contention time*).
  - `StateFlowImpl` menggunakan implementasi *Lock-Free/CAS (Compare-And-Swap)* via `kotlinx.atomicfu` / `AtomicRef`. State internal disimpan sebagai *volatile reference*. Modifikasi dengan helper `.update { }` berjalan dalam infinite loop dengan pengecekan `compareAndSet(cur, next)` hingga modifikasi berhasil secara atomik tanpa menghentikan thread sistem.

#### Alokasi Memori & Resource
- **Buffer Retention**: Pada `SharedFlow`, jika emitter bekerja jauh lebih cepat daripada collector dengan `BufferOverflow.SUSPEND`, nilai yang belum diproses akan tertahan di buffer `Object[]`. Jika buffer tidak dibatasi (`extraBufferCapacity = 0` default, tanpa konfigurasi drop), penangguhan emisi dapat menahan memori objek berukuran besar, menunda proses pembersihan Garbage Collector (GC).
- **Slot Recycling**: Ketika coroutine kolektor dibatalkan (`JobCancelledException`), slot yang bersangkutan dibersihkan dan ditandai sebagai `FREE`. Memori `collector continuation` langsung di-null-kan untuk mencegah kebocoran memori coroutine.

#### Trade-offs
| Parameter | `StateFlow` | `SharedFlow` |
| :--- | :--- | :--- |
| **Model Emisi** | Conflated (Nilai terabaikan jika lambat diproses) | Bounded/Lossless (Tergantung Buffer Strategy) |
| **Pengecekan Kesetaraan** | Ya (`old.equals(new)` menghentikan pengiriman) | Tidak (Semua `emit()` dipancarkan) |
| **Inisialisasi Nilai** | Mandatori (`initialValue`) | Opsional (`replay` cache kosong di awal) |
| **Replay Capacity** | Konstan: `1` | Dikonfigurasi: `0..n` |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `.update { }` bukan assignment langsung**: Saat melakukan modifikasi nilai pada `MutableStateFlow`, jangan gunakan `_state.value = _state.value.copy(...)` pada lingkungan multithreaded. Selalu gunakan `_state.update { it.copy(...) }` untuk mencegah *race condition* (lost updates).
- **Enkapsulasi State**: Selalu gunakan pola *backing property*. Jangan pernah mengekspos `MutableStateFlow` atau `MutableSharedFlow` ke luar kelas. Konversikan menggunakan `.asStateFlow()` atau `.asSharedFlow()`.
- **Gunakan `SharingStarted.WhileSubscribed(5000)`**: Saat mengonversi Cold Flow menjadi Hot Flow menggunakan operator `.stateIn()` / `.shareIn()`, gunakan `SharingStarted.WhileSubscribed(stopTimeoutMillis = 5000)` guna menghemat resource saat tidak ada subscriber aktif (misalnya rotasi layar pada client app).

#### Don'ts
- **Memodifikasi Properti Mutable Object secara In-Place**:
  ```kotlin
  // CRITICAL BUG: StateFlow TIDAK akan memancarkan nilai baru!
  val _state = MutableStateFlow(ArrayList<String>())
  _state.value.add("New Item")
  _state.value = _state.value // equals() bernilai TRUE, collector diabaikan!
  ```
  `StateFlow` mendeteksi perubahan berdasarkan kesetaraan objek. Selalu gunakan *immutable data structure* (`List` baru via `.copy()`).
- **Menggunakan StateFlow untuk Single-Time Event**: Jangan gunakan `StateFlow` untuk navigasi atau dialog error. Jika subscriber reconnect (misal konfigurasi ulang view), nilai terakhir akan diputar ulang (*replayed*), menyebabkan dialog muncul kembali atau navigasi tereksekusi dua kali.

#### Edge Cases
- **SharedFlow Emit Tanpa Subscriber**: Pada `SharedFlow` dengan konfigurasi default `replay = 0`, pemanggilan `emit()` sebelum ada collector yang aktif akan menyebabkan data terbuang begitu saja secara senyap (*dropped silently*).

### 5. Tantangan Eksplorasi Mandiri

1. **Membuktikan Conflation pada StateFlow**:
   Buat coroutine producer yang memancarkan angka `1..100` ke dalam `MutableStateFlow` tanpa delay. Pada coroutine consumer, tambahkan `delay(50)` di dalam blok `collect`. Amati berapa banyak emisi yang dilewati (*skipped*) dan jelaskan mengapa nilai akhir selalu `100`.
2. **Simulasi Race Condition vs Atomic Update**:
   Buat dua coroutine yang secara bersamaan melakukan pemanggilan `updateBalance(1.0)` sebanyak 1000 kali. Uji kasus ini menggunakan assignment langsung `_state.value = _state.value.copy(balance = _state.value.balance + 1)` versus `_state.update { ... }`. Cetak saldo akhir dan verifikasi terjadinya kondisi *thread-safety divergence*.
