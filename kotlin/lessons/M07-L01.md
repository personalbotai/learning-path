### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem asynchronous Kotlin, **Kotlin Flow** dirancang sebagai abstraksi stream asinkron berbasis *pull-based* (cold stream). Sebelum adanya Flow, penanganan data stream asinkron didominasi oleh library eksternal seperti RxJava/Project Reactor atau menggunakan Kotlin `Channel`. Namun, Channel bersifat *hot stream* (mengonsumsi resource dan memproduksi nilai terlepas dari ada atau tidaknya *consumer*), sedangkan RxJava memperkenalkan kompleksitas API dan alokasi memori yang masif.

```
       [ Cold Flow ]                             [ Collector ]
             |                                         |
             | <-------- 1. collect() dipanggil -------|
             |                                         |
             | --- 2. emit(data) [Suspends] ---------> |
             |                                         | (Memproses data)
             | <--- 3. Lanjut resume ------------------|
             |                                         |
             x (Selesai/Cancelled)                     v
```

#### Karakteristik Utama Cold Stream
1. **Eksekusi Pasif (Lazy Evaluation):** Blok kode di dalam builder `flow { ... }` tidak akan pernah dieksekusi sampai ada terminal operator (seperti `collect()`, `toList()`, `first()`) yang dipanggil.
2. **Independensi Subscriber:** Setiap pemanggilan `collect()` mengeksekusi ulang blok kode *builder* dari awal secara independen, terisolasi untuk tiap kolektor.
3. **Native Suspension:** Berbeda dengan reactive stream tradisional yang membutuhkan protokol backpressure kompleks (seperti `request(n)`), Flow menggunakan mekanisme **suspending function** bawaan Kotlin Coroutines. Jika *collector* berjalan lambat, pemanggil `emit()` akan tersuspensi (*suspend*) secara otomatis pada call-stack coroutine yang sama.

#### Arsitektur Inti: Dua Interface Sederhana
Flow dibangun di atas dua interface fundamental:

```kotlin
public interface Flow<out T> {
    public suspend fun collect(collector: FlowCollector<T>)
}

public fun interface FlowCollector<in T> {
    public suspend fun emit(value: T)
}
```

Secara esensial, pemanggilan `flow.collect(collector)` adalah *inversion of control*: Flow mengeksekusi blok kode miliknya sendiri dan melewatkan instance `FlowCollector` tempat nilai dikirimkan via `emit()`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan simulasi pemantauan status transaksi gateway perbankan menggunakan berbagai flow builder (`flow`, `flowOf`, `asFlow`), serta konsumsinya dengan penanganan pembatalan (*cancellation*).

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// Domain Model
sealed class TransactionStatus {
    data class Processing(val step: Int) : TransactionStatus()
    data class Success(val transactionId: String) : TransactionStatus()
    data class Failed(val reason: String) : TransactionStatus()
}

// 1. Menggunakan Standard flow { } Builder
fun trackTransaction(txId: String): Flow<TransactionStatus> = flow {
    println("[Producer] Memulai audit transaksi: $txId di thread: ${Thread.currentThread().name}")
    
    emit(TransactionStatus.Processing(step = 1))
    delay(300) // Simulasi I/O / Network latency

    emit(TransactionStatus.Processing(step = 2))
    delay(300)

    // Simulasi hasil akhir
    if (txId.startsWith("TX_ERR")) {
        emit(TransactionStatus.Failed("Saldo tidak mencukupi"))
    } else {
        emit(TransactionStatus.Success(txId))
    }
}

suspend fun main() = coroutineScope {
    // 2. Menggunakan flowOf dan asFlow Builder sederhana
    val staticFlow: Flow<String> = flowOf("Config-A", "Config-B", "Config-C")
    val listFlow: Flow<Int> = listOf(100, 200, 300).asFlow()

    println("=== Test 1: Cold Verification (Belum ada log producer) ===")
    val transactionFlow = trackTransaction("TX_99812")
    println("Flow object dibuat: $transactionFlow") // Belum ada emisi

    println("\n=== Test 2: Collecting Data (First Consumer) ===")
    transactionFlow.collect { status ->
        println("[Consumer 1] Status diterima: $status")
    }

    println("\n=== Test 3: Multiple Collectors Re-execution ===")
    // Membuktikan sifat cold: blok builder dieksekusi ulang
    transactionFlow.collect { status ->
        if (status is TransactionStatus.Success) {
            println("[Consumer 2] Transaksi diverifikasi berhasil: ${status.transactionId}")
        }
    }

    println("\n=== Test 4: Fast Collector vs Suspension ===")
    listFlow
        .map { it * 2 }
        .collect { value ->
            println("[ListFlow] Value: $value")
        }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Continuation-Passing Style (CPS)
- Saat `flow { ... }` dipanggil, runtime hanya membuat instance anonymous class implementasi `Flow` yang menyimpan referensi lambda tersebut (`block: suspend FlowCollector<T>.() -> Unit`).
- Saat `collect(collector)` dieksekusi, compiler meneruskan *continuation* dari coroutine pemanggil langsung ke lambda flow builder.
- **Backpressure Alami Tanpa Buffer:**
  Tidak ada antrean (*buffer queue*) implisit. Ketika `emit(value)` dipanggil, eksekusi producer berhenti seketika (*suspends*) hingga lambda pada *collector* selesai mengeksekusi iterasi tersebut dan memanggil `resume` pada *continuation* milik `emit`. Produksi dan konsumsi berjalan strictly synchronous secara logis, kecuali operator eksplisit seperti `buffer()` digunakan.

#### Context Preservation & Exception Transparency
Runtime Kotlin Flow menerapkan invariant ketat:
1. **Context Preservation:** Flow builder dilarang keras mengubah CoroutineContext downstream menggunakan `withContext(Dispatchers.IO) { emit(...) }`. Runtime Flow menyisipkan class `SafeCollector`. Jika `SafeCollector` mendeteksi context saat `emit()` berbeda dengan context saat `collect()` dimulai, ia langsung melemparkan exception:
   `java.lang.IllegalStateException: Flow invariant is violated`.
   *Solusinya:* Gunakan operator `.flowOn(Dispatchers.IO)`.

```
[flow builder Context] <--- (Dikelola via .flowOn())
          |
   [SafeCollector] ---- Validasi Thread / Context Invariant
          |
[collect() Context]   <--- (Ditentukan oleh scope pemanggil collect)
```

2. **Alokasi Memori & Resource:**
   Berbeda dari Reactive Stream yang membuat *wrapper node* untuk setiap operator dalam *pipeline chain*, Flow meminimalkan alokasi. Builder `flow { }` hanya mengalokasikan satu instance FlowCollector aman (`SafeCollector`) dan sebuah *state machine continuation*. Jika stream tidak pernah di-*collect*, alokasi memori mendekati nol (hanya wrapper object lambda).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `flowOn()` untuk Offloading Context:** Selalu gunakan `flowOn(Dispatchers.IO)` jika builder melakukan operasi blocking I/O, alih-alih mencoba membungkus emisi ke dalam `withContext`.
- **Manfaatkan Cooperative Cancellation:** Gunakan `currentCoroutineContext().ensureActive()` jika melakukan iterasi CPU-bound yang intensif di dalam blok `flow { }` agar emisi dapat segera dibatalkan ketika collector scope di-*cancel*.

#### Don'ts
- **Dilarang Mengubah Context di Dalam `emit`:**
  ```kotlin
  // CRASH (IllegalStateException)
  flow {
      withContext(Dispatchers.IO) {
          emit(fetchData()) 
      }
  }
  
  // BENAR
  flow {
      emit(fetchData())
  }.flowOn(Dispatchers.IO)
  ```
- **Menelan `CancellationException`:** Hindari menggunakan `catch (t: Throwable)` umum di dalam builder tanpa melempar ulang (`rethrow`) jika instance-nya adalah `CancellationException`. Jika tertelan, structured concurrency akan rusak dan flow tidak dapat dihentikan oleh parent scope.

#### Edge Cases
- **Leakage Resource pada Early Exit:**
  Jika collector berhenti di tengah jalan (misal menggunakan operator `take(1)`), runtime melempar `AbortFlowException` internal untuk menghentikan flow producer. Pastikan resource tertutup dengan membungkus kode di builder menggunakan blok `try { ... } finally { closeResource() }`.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Manual Tanpa Builder:**
   Buat implementasi custom dari interface `Flow<T>` dan `FlowCollector<T>` secara langsung (tanpa memakai DSL `flow { }`). Amati bagaimana `collect()` memicu eksekusi logika Anda dan bagaimana mekanisme penanganan suspension berjalan tanpa bantuan abstraksi `kotlinx.coroutines`.
2. **Verifikasi Pelanggaran SafeCollector:**
   Tulis kode yang sengaja memanggil `emit()` dari dalam `GlobalScope.launch { ... }` atau `withContext` di dalam `flow { }`. Jalankan program, amati stack trace `IllegalStateException` yang dihasilkan, lalu telusuri *internal code* Kotlin coroutines pada kelas `SafeCollector.kt` untuk melihat cara runtime mendeteksi perbedaan context tersebut.
