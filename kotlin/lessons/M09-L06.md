## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, Gradle mengandalkan Groovy DSL sebagai bahasa konfigurasi deklaratif. Fleksibilitas Groovy yang berbasis *dynamic typing* sering kali menjadi bumerang pada proyek skala besar: ketiadaan validasi *compile-time*, keterbatasan integrasi IDE (*code navigation*, *refactoring*, dan *auto-completion* yang lambat atau tidak akurat), serta tingginya potensi *runtime error* pada fase konfigurasi build.

**Gradle Kotlin DSL (`build.gradle.kts`)** hadir untuk memecahkan masalah ini dengan memperkenalkan *static typing* ke dalam sistem automasi build. Script build diperlakukan layaknya kode Kotlin kelas satu: divalidasi oleh kompiler Kotlin (`kotlinc`), memiliki dokumentasi tipe yang eksplisit, dan didukung penuh oleh tooling IntelliJ IDEA/Android Studio.

Di sisi lain, pengelolaan dependensi pada proyek *multi-module* sebelumnya sangat terfragmentasi. Developer sering menggunakan *Groovy extra properties* (`ext`), *buildSrc* dengan `object` Kotlin statis, atau menduplikasi deklarasi *string coordinates* (`"group:artifact:version"`). Solusi `buildSrc` memiliki kelemahan arsitektural fatal: setiap kali ada perubahan nilai string pada file di dalam `buildSrc`, Gradle akan menginvaliasi seluruh *build cache* dan mengompilasi ulang seluruh *build script* dari awal.

**Gradle Version Catalogs (`libs.versions.toml`)** diperkenalkan (stabil sejak Gradle 7.4) sebagai standardisasi arsitektural untuk sentralisasi dependensi:
1. **Pemisahan Konfigurasi dan Deklarasi**: Data versi dan dependensi didefinisikan secara deklaratif dalam format TOML (*Tom's Obvious Minimal Language*).
2. **Type-Safe Accessors Generation**: Gradle membaca file TOML pada fase inisialisasi awal dan secara otomatis menghasilkan ekstensi kode (*synthetic extension properties*) berkategori tipe aman (`libs.ktor.core`, `libs.plugins.kotlin.jvm`).
3. **Cache Stability**: Mengubah versi library di dalam file TOML **tidak** menginvaliasi kompilasi class script build logic, melainkan hanya memperbarui *value* saat dependency resolution berlangsung.

```
                      +-----------------------------+
                      |   gradle/libs.versions.toml |
                      +--------------+--------------+
                                     |
                                     v (Initialization Phase)
            +------------------------------------------------+
            |  Gradle Core generates Type-Safe Accessors     |
            |  Synthetic extension classes: `LibrariesForLibs`|
            +------------------------+-----------------------+
                                     |
                                     v (Configuration Phase)
           +-------------------------+-------------------------+
           |                                                   |
           v                                                   v
+-----------------------+                           +-----------------------+
| :app:build.gradle.kts |                           | :core:build.gradle.kts|
|  implementation(      |                           |  implementation(      |
|    libs.ktor.core     |                           |    libs.ktor.core     |
|  )                    |                           |  )                    |
+-----------------------+                           +-----------------------+
```

### 2. Implementasi & Contoh Kasus Nyata

Struktur modular proyek modern menggunakan Version Catalog default (`gradle/libs.versions.toml`) dan Kotlin DSL.

#### 1. Definisi Katalog Dependensi: `gradle/libs.versions.toml`
```toml
[versions]
kotlin = "1.9.23"
ktor = "2.3.9"
coroutines = "1.8.0"
logback = "1.5.3"
junit = "5.10.2"

[libraries]
# Format: alias = { module = "group:name", version.ref = "version_key" }
kotlinx-coroutines-core = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-core", version.ref = "coroutines" }
ktor-server-core = { module = "io.ktor:ktor-server-core-jvm", version.ref = "ktor" }
ktor-server-netty = { module = "io.ktor:ktor-server-netty-jvm", version.ref = "ktor" }
logback-classic = { module = "ch.qos.logback:logback-classic", version.ref = "logback" }

# Testing dependencies
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }

[bundles]
# Mengelompokkan library yang selalu digunakan bersamaan
ktor-server = ["ktor-server-core", "ktor-server-netty", "logback-classic"]

[plugins]
kotlin-jvm = { id = "org.jetbrains.kotlin.jvm", version.ref = "kotlin" }
kotlin-serialization = { id = "org.jetbrains.kotlin.plugin.serialization", version.ref = "kotlin" }
```

#### 2. Root Project Settings: `settings.gradle.kts`
```kotlin
rootProject.name = "enterprise-service"

// Gradle secara otomatis membaca "gradle/libs.versions.toml".
// Konfigurasi manual di bawah hanya diperlukan jika ingin mengubah nama atau lokasi catalog.
dependencyResolutionManagement {
    repositories {
        mavenCentral()
    }
    versionCatalogs {
        create("libs") {
            from(files("gradle/libs.versions.toml"))
        }
    }
}

include(":server")
include(":core")
```

#### 3. Module Build Script: `server/build.gradle.kts`
```kotlin
plugins {
    // Menggunakan type-safe plugin accessor dari Version Catalog
    alias(libs.plugins.kotlin.jvm)
    alias(libs.plugins.kotlin.serialization)
    application
}

application {
    mainClass.set("com.enterprise.service.ApplicationKt")
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

dependencies {
    // Implementasi project module internal
    implementation(project(":core"))

    // Menggunakan bundle: menyelesaikan ktor-core, ktor-netty, logback secara kolektif
    implementation(libs.bundles.ktor.server)
    implementation(libs.kotlinx.coroutines.core)

    // Scope testing
    testImplementation(libs.junit.jupiter)
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

// Konfigurasi Task secara Lazy (Task Configuration Avoidance API)
tasks.named<Test>("test") {
    useJUnitPlatform()
    
    // Alokasi resource JVM test runner
    maxHeapSize = "1g"
    testLogging {
        events("passed", "skipped", "failed")
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Dua Lintasan Evaluasi (Two-Pass Compilation)
Script `.gradle.kts` tidak dieksekusi secara interpretatif murni. Gradle menggunakan pipeline khusus:
1. **Pass 1 (`buildscript` & `plugins` blocks)**: Gradle mengekstrak blok deklaratif `plugins { ... }`. Kode ini dikompilasi ke memori untuk mengekstrak classpath dependensi *build engine*.
2. **Classloader Isolation**: Berdasarkan plugin yang diimpor, Gradle membuat `ClassLoader` baru bertingkat hierarkis (*Root ClassLoader -> Script Plugin ClassLoader*).
3. **Pass 2 (Script Body Execution)**: Sisa script build lainnya dikompilasi ke JVM bytecode (menghasilkan class yang meng-extend interface `KotlinBuildScript`). Bytecode ini disimpan di dalam folder direktori `.gradle/caches/<gradle-version>/kotlin-dsl/`.
4. **Accessors Generation**: Gradle melakukan introspeksi skema TOML dan mengompilasi sebuah JAR in-memory yang memuat kelas ekstensi *accessor* (misal: `LibrariesForLibs`). Inilah yang memungkinkan IDE mengenali `libs.kotlinx.coroutines.core` tanpa error resolusi dependensi.

#### Alokasi Memori / Resource
* **Kotlin Daemon Engine**: Eksekusi script Kotlin DSL memicu *daemon* compiler Kotlin internal di background. Hal ini membutuhkan heap overhead ekstra (umumnya berkisar 512MB - 1GB) di luar *Gradle Daemon* itu sendiri.
* **Metadata Caching**: Kelas-kelas yang dihasilkan dari kompilasi skrip DSL disimpan dalam cache. Pada eksekusi berulang (*warm build*), tidak terjadi kompilasi skrip ulang kecuali hash konten file `.gradle.kts` berubah.

#### Trade-offs: Kotlin DSL vs Groovy DSL
* **Cold Build Penalty**: Waktu kompilasi awal (*first-run / cold build*) Kotlin DSL lebih lambat dibanding Groovy karena `kotlinc` harus memverifikasi *type safety*, melakukan resolusi simbol ekstensi, dan menghasilkan bytecode.
* **Warm Build Performance**: Hampir setara, terutama bila memanfaatkan Gradle **Configuration Cache**.
* **Maintainability Gain**: Menghilangkan *typo error*, memvalidasi API compatibility library saat konfigurasi, dan mempermudah migrasi API library skala enterprise.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan API `alias()` untuk plugins**: Selalu gunakan `alias(libs.plugins.xyz)` daripada `id("xyz").version("...")`. Hal ini mencegah desinkronisasi versi plugin dengan runtime library.
* **Gunakan Task Configuration Avoidance**: Selalu gunakan `tasks.register("myTask")` atau `tasks.named("compileKotlin")`. Hindari `tasks.create()` karena `tasks.create()` memaksa instansiasi dan konfigurasi task secara instan pada fasa konfigurasi, yang mendegradasi performa build.
* **Kelompokkan Modul dengan `bundles`**: Manfaatkan blok `[bundles]` pada TOML untuk dependensi yang kohesif (contoh: Ktor server engines, Jetpack Compose, Jackson modules).

#### Don'ts
* **Jangan Taruh Logic Kompleks di `build.gradle.kts`**: File DSL harus tetap *declarative*. Jika membutuhkan custom logic, class transformasi file, atau dynamic task injection, tempatkan di dalam *Convention Plugins* menggunakan `build-logic` (Composite Builds), bukan menumpuk fungsi Kotlin murni di dalam `build.gradle.kts`.
* **Hindari String-based Dependency Notation**: Hindari `implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.8.0")` langsung di module. Hal ini merusak prinsip *single source of truth* versi.
* **Jangan Inisialisasi Logika Eksekusi di Configuration Phase**: Menulis logika seperti membaca database, network calls, atau file I/O langsung di top-level script `.gradle.kts` akan memperlambat semua siklus build, termasuk saat hanya menjalankan `./gradlew help`.

#### Edge Cases
* **Akses Version Catalog di Precompiled Script Plugins**: Jika Anda membuat *convention plugin* di `build-logic`, Version Catalog `libs` tidak secara otomatis ter-generate di Classpath `build-logic` tanpa menginjeksikan dependency katalog secara eksplisit:
  ```kotlin
  // build-logic/build.gradle.kts
  dependencies {
      compileOnly(files(libs.javaClass.superclass.protectionDomain.codeSource.location))
  }
  ```
  Atau dengan mendefinisikannya sebagai `dependencyResolutionManagement` extension di level composite build.

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Multi-Module Migration**: Ambil proyek Kotlin yang masih menggunakan string dependency hardcoded atau Groovy DSL. Migrasikan seluruhnya ke `build.gradle.kts` dan satukan seluruh manajemen versinya ke dalam `gradle/libs.versions.toml`. Pastikan tidak ada satupun versi yang dideklarasikan manual di dalam build script modul.
2. **Investigasi Build Impact Menggunakan Build Scan**:
   Jalankan build dengan flag `--scan` (misal: `./gradlew assemble --scan`). Bandingkan durasi *Configuration Phase* antara skrip yang menggunakan eager task configuration (`tasks.create(...)`) versus yang menggunakan task avoidance (`tasks.register(...)`). Amati bagaimana class loader cache berperilaku saat Anda mengubah satu karakter di file `.toml` versus mengubah file `.gradle.kts`.
