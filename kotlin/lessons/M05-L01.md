### 1. Konsep & Arsitektur Mendalam

Di Kotlin, fungsi diperlakukan sebagai **first-class citizens**. Artinya, fungsi dapat disimpan dalam variabel, disimpan dalam struktur data, dioperasikan sebagai argumen, dan dikembalikan dari fungsi lain.

#### Function Types (Tipe Fungsi)
Kotlin menggunakan notasi khusus untuk mendefinisikan tipe fungsi, dengan sintaksis dasar:
```text
(ParameterTypes) -> ReturnType
```
Contohnya, `(Int, String) -> Boolean` merepresentasikan fungsi yang menerima dua argumen (`Int` dan `String`) dan mengembalikan sebuah `Boolean`. 

Kotlin juga mendukung:
- **Unit Return**: Jika tidak mengembalikan nilai, tipe pengembalian harus didefinisikan secara eksplisit sebagai `Unit` (misal: `() -> Unit`).
- **Nullable Function Types**: `((Int) -> String)?` menunjukkan variabel fungsi tersebut dapat bernilai `null`.
- **Lambda with Receiver**: `T.(Param) -> ReturnType`. Di sini, fungsi dieksekusi di dalam konteks instance tipe `T`, sehingga instance tersebut menjadi `this` implisit di dalam badan fungsi.

#### Higher-Order Functions (HOF)
Higher-Order Function adalah fungsi yang memenuhi setidaknya satu dari kriteria berikut:
1. Menerima satu atau lebih fungsi sebagai parameter.
2. Mengembalikan sebuah fungsi.

HOF memungkinkan abstraksi logika kontrol (*control flow*), memisahkan *business logic* dari *execution strategy* (seperti transaksi database, *error handling*, atau *retry mechanism*).

#### Representasi di Balik Layar: `FunctionN` Interfaces
Karena JVM versi lama (Java 6/7) tidak memiliki konsep native *function pointers*, Kotlin compiler (`kotlinc`) memetakan setiap tipe fungsi ke interface generik bawaan:
- `kotlin.jvm.functions.Function0<R>` (0 parameter)
- `kotlin.jvm.functions.Function1<P1, R>` (1 parameter)
- ... hingga `kotlin.jvm.functions.Function22<P1, ..., P22, R>`
- Untuk fungsi dengan aritas > 22, Kotlin menggunakan `kotlin.jvm.functions.FunctionN`.

Setiap fungsi lambda yang Anda tulis akan dikompilasi menjadi class anonim yang mengimplementasikan interface `FunctionX` tersebut dengan metode `invoke(...)`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi *Resilient Execution Pipeline* yang menggunakan Higher-Order Function, lambda with receiver, dan custom type aliases untuk menangani transaksi operasi database/jaringan.

```kotlin
package com.architect.resilience

import java.time.Instant

// 1. Deklarasi Typealias untuk readability
typealias ErrorHandler = (Throwable, Int) -> Unit
typealias Predicate<T> = (T) -> Boolean

// Context object untuk Lambda with Receiver
class TransactionContext(val transactionId: String) {
    val startedAt: Instant = Instant.now()
    fun log(message: String) = println("[$transactionId] $message")
}

// 2. Higher-Order Function: Eksekusi blok fungsi dengan retry & interceptor
fun <T> executeWithRetry(
    maxAttempts: Int = 3,
    onFailure: ErrorHandler? = null,
    validationPredicate: Predicate<T>? = null,
    block: TransactionContext.() -> T // Function Type with Receiver
): Result<T> {
    var attempts = 0
    val context = TransactionContext(transactionId = "TXN-${System.currentTimeMillis()}")

    while (attempts < maxAttempts) {
        attempts++
        try {
            context.log("Percobaan ke-$attempts dieksekusi.")
            
            // Eksekusi fungsi lambda menggunakan context sebagai receiver
            val result = context.block()

            // Validasi hasil jika predicate disediakan
            if (validationPredicate != null && !validationPredicate(result)) {
                throw IllegalStateException("Hasil tidak memenuhi kriteria validasi.")
            }

            return Result.success(result)
        } catch (e: Throwable) {
            context.log("Gagal: ${e.message}")
            onFailure?.invoke(e, attempts) // Safe-call invocation untuk nullable function

            if (attempts >= maxAttempts) {
                return Result.failure(e)
            }
        }
    }

    return Result.failure(IllegalStateException("Operasi dihentikan."))
}

data class Order(val id: String, val amount: Double)

fun main() {
    // 3. Penggunaan idiomatik: Trailing Lambda Syntax
    val result: Result<Order> = executeWithRetry(
        maxAttempts = 3,
        onFailure = { error, attempt ->
            System.err.println("Gagal pada percobaan $attempt: ${error.localizedMessage}")
        },
        validationPredicate = { order -> order.amount > 0.0 }
    ) {
        // Didalam scope ini, 'this' mengarah ke TransactionContext
        log("Mengambil data order dari sistem eksternal...")
        
        // Mensimulasikan logika bisnis
        Order(id = "ORD-9982", amount = 150_000.0)
    }

    result.fold(
        onSuccess = { println("Transaksi Berhasil: Order ID ${it.id} seharga Rp${it.amount}") },
        onFailure = { println("Transaksi Gagal Total: ${it.message}") }
    )
}
```

#### Penjelasan Komponen Kunci:
1. **`block: TransactionContext.() -> T`**: Parameter ini mengizinkan pemanggil mengakses metode `log(...)` secara langsung di dalam kurung kurawal tanpa harus mendefinisikan parameter eksplisit.
2. **Trailing Lambda**: Argumen terakhir (`block`) ditempatkan di luar tanda kurung fungsi `executeWithRetry(...) { ... }`, menjaga keterbacaan kode menyerupai *native language features*.
3. **Safe Calling `onFailure?.invoke(...)`**: Karena tipe fungsi bersifat nullable, pemanggilannya harus menggunakan operator `?.invoke(...)`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Perhatikan kode berikut:
```kotlin
fun applyOperation(x: Int, op: (Int) -> Int): Int = op(x)
```
Di level bytecode JVM, fungsi di atas dikompilasi setara dengan Java bytecode:
```java
public static final int applyOperation(int x, Function1<? super Integer, Integer> op) {
    return ((Number) op.invoke(Integer.valueOf(x))).intValue();
}
```

#### Alokasi Memori & Closures
1. **Non-Capturing Lambdas**:
   Jika lambda **tidak mengakses** variabel lokal di luar scopenya:
   ```kotlin
   val res = applyOperation(5) { it * 2 }
   ```
   Kotlin compiler mengoptimalkannya dengan membuat **singleton instance** (`static final instance`) dari kelas turunan `Function1`. Tidak ada alokasi objek baru pada pemanggilan berulang.

2. **Capturing Lambdas (Closure)**:
   Jika lambda **mengakses** variabel dari scope luarnya:
   ```kotlin
   val factor = 2
   val res = applyOperation(5) { it * factor }
   ```
   Kotlin akan mengalokasikan instance baru (`new Function1(...)`) ke dalam **Heap memory** setiap kali baris tersebut dieksekusi. Objek `factor` dilewatkan ke konstruktor instance tersebut.
   
3. **Boxing & Unboxing Overhead**:
   Tipe primitif seperti `Int` dikonversi menjadi `java.lang.Integer` karena tipe generik Java tidak mendukung tipe primitif (`Function1<Integer, Integer>`). Hal ini memicu auto-boxing yang membebani Garbage Collector (GC).

#### Trade-offs
- **Abstraksi vs GC Pressure**: Penggunaan HOF standar memberikan abstraksi tingkat tinggi, tetapi capturing lambda di dalam loop ketat (*tight loop*) dapat memicu alokasi memori ribuan instance per detik yang menyebabkan *GC pauses*. 
- **Solusi**: Kasus performa kritis diatasi dengan kata kunci `inline` (memindahkan badan bytecode lambda langsung ke call site tanpa membuat instansi objek).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Manfaatkan Trailing Lambda**: Posisikan parameter fungsi selalu di urutan paling belakang jika fungsi tersebut hanya memiliki satu parameter fungsi.
- **Gunakan `typealias`**: Jika tanda tangan fungsi kompleks (contoh: `(Map<String, List<Int>>, (Throwable) -> Unit) -> Flow<Result<String>>`), bungkus dalam `typealias` untuk menjaga *maintainability*.
- **Pahami Functional Interfaces (SAM)**: Gunakan `fun interface` saat mendefinisikan kontrak interface yang membutuhkan interoperabilitas Java SAM.

#### Don'ts
- **Hindari Callback Hell**: Jangan menumpuk HOF terlalu dalam secara anonim; ekstrak menjadi fungsi privat terpisah atau gunakan Coroutines jika mengelola operasi asinkron.
- **Jangan Mengabaikan State Capture**: Hindari meng-capture variabel mutable luar (`var`) di dalam lambda yang dieksekusi secara asinkron (dapat memicu race conditions) atau objek besar seperti `Activity` / `ServiceContext` (dapat memicu memory leaks).

#### Edge Cases
- **Non-local Return vs Labelled Return**:
  Lambda biasa **tidak bisa** melakukan non-local `return` langsung ke pemanggil fungsi luar.
  ```kotlin
  fun test() {
      listOf(1, 2, 3).forEach {
          if (it == 2) return // Error jika forEach bukan inline function!
          if (it == 2) return@forEach // Benar: Labelled return (setara continue)
      }
  }
  ```
- **Nullability Ambiguity**:
  - `(Int) -> String?` $\rightarrow$ Fungsi menerima `Int` dan mengembalikan nilai nullable `String`.
  - `((Int) -> String)?` $\rightarrow$ Variabel fungsi itu sendiri bernilai nullable (dapat bernilai `null` alih-alih instance fungsi).
