### 1. Konsep & Arsitektur Mendalam

Kotlin dirancang dengan prinsip *100% Java Interoperability*. Namun, terdapat perbedaan fundamental antara model objek dan fitur bahasa di Kotlin dengan Java Virtual Machine (JVM) standar:
- Java mengenal *static methods* dan *static fields* yang menempel langsung pada *class object*. Kotlin tidak memiliki keyword `static`, melainkan menggunakan konsep `object` declaration dan `companion object` (instansiasi singleton terselubung).
- Kotlin mendukung *default parameter values*, sedangkan Java hanya mengenal *method overloading*.
- Di Kotlin, *property* secara otomatis menghasilkan *backing field* beserta getter/setter (enkapsulasi default), sedangkan Java mengizinkan manipulasi *public field* secara telanjang.

Untuk menjembatani perbedaan semantik ini tanpa memaksa developer Java menulis boilerplate code yang janggal (seperti `MyClass.Companion.getInstance().doSomething()`), Kotlin menyediakan *interop annotations*:

1. **`@JvmStatic`**: Memerintahkan compiler (`kotlinc`) untuk membuat metode/properti statis sungguhan di kelas kontainer JVM, di samping metode instans di dalam kelas singleton companion/object.
2. **`@JvmOverloads`**: Menginstruksikan compiler untuk menghasilkan variasi overloaded konstruktor atau fungsi di bytecode Java untuk setiap parameter yang memiliki nilai default.
3. **`@JvmField`**: Menginstruksikan compiler agar tidak menghasilkan getter/setter dan mengekspos *backing field* Kotlin sebagai `public final` atau `public` field murni di level Java bytecode.

Fitur-fitur ini bekerja sepenuhnya pada tahap kompilasi (*compile-time metadata manipulation*) untuk membentuk struktur bytecode (class file signature) yang ramah terhadap Java client, pustaka refleksi, dan framework JVM seperti Spring, Jackson, atau Android Framework.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh komprehensif yang menggabungkan ketiga anotasi dalam skenario arsitektur riil: integrasi service configuration dan DTO antara Kotlin dan Java.

#### Kode Kotlin (`NetworkClient.kt`)
```kotlin
package com.roadmaps.interop

data class ClientConfig @JvmOverloads constructor(
    @JvmField val baseUrl: String,
    @JvmField val timeoutMs: Long = 5000L,
    @JvmField val retryCount: Int = 3
)

class NetworkClient private constructor(val config: ClientConfig) {

    companion object {
        private const val DEFAULT_USER_AGENT = "Kotlin-Engine/1.0"

        // Mengizinkan Java memanggil langsung: NetworkClient.createDefault();
        // Bukan: NetworkClient.Companion.createDefault();
        @JvmStatic
        fun createDefault(): NetworkClient {
            return NetworkClient(ClientConfig("https://api.internal.net"))
        }

        // Menghasilkan overload di Java:
        // 1. connect(String host)
        // 2. connect(String host, int port)
        // 3. connect(String host, int port, boolean useTls)
        @JvmStatic
        @JvmOverloads
        fun connect(
            host: String,
            port: Int = 443,
            useTls: Boolean = true
        ): String {
            val scheme = if (useTls) "https" else "http"
            return "Connected to $scheme://$host:$port via $DEFAULT_USER_AGENT"
        }
    }
}
```

#### Cara Java Mengonsumsinya (`App.java`)
```java
package com.roadmaps.interop;

public class App {
    public static void main(String[] args) {
        // 1. Konsumsi @JvmField: Akses langsung tanpa getter
        ClientConfig config = new ClientConfig("https://example.com");
        System.out.println("Base URL: " + config.baseUrl); // Direct field access
        System.out.println("Timeout: " + config.timeoutMs);

        // 2. Konsumsi @JvmStatic: Pemanggilan layaknya Java static method
        NetworkClient client = NetworkClient.createDefault();

        // 3. Konsumsi @JvmOverloads: Pemanggilan parameter default via multiple signatures
        String conn1 = NetworkClient.connect("service.local");
        String conn2 = NetworkClient.connect("service.local", 8080);
        String conn3 = NetworkClient.connect("service.local", 80, false);

        System.out.println(conn1);
        System.out.println(conn2);
        System.out.println(conn3);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Bytecode Inspection
Jika kita mendekompilasi file `.class` hasil kompilasi Kotlin ke dalam representasi bytecode dan Java decompiled view:

##### A. `@JvmStatic`
Kotlin mengompilasi Companion Object menjadi *inner class* statis bernama `Companion`.
- **Tanpa `@JvmStatic`**: Metode hanya ada di dalam `NetworkClient$Companion.class`. Java harus memanggil `NetworkClient.Companion.createDefault()`.
- **Dengan `@JvmStatic`**: Compiler menghasilkan delegator statis di kelas terluar (`NetworkClient.class`):
```java
// Bytecode decompiled dari NetworkClient.class
public static final NetworkClient createDefault() {
    return Companion.createDefault();
}
```
Metode target tetap ada di dalam `Companion`, namun JVM menambahkan instruksi `invokestatic` di kelas utama yang meneruskan eksekusi ke instans `Companion`.

##### B. `@JvmOverloads`
Kotlin menangani default parameter di runtime melalui metode sintetis berbendera `$default`:
`connect$default(String, int, boolean, int mask, Object marker)`. Bitwise mask mengevaluasi argumen mana yang diisi dan mana yang harus menggunakan nilai default.
Dengan menambahkan `@JvmOverloads`, compiler men-generate synthetic bridge methods di Java bytecode:
```java
// Hasil decompiled @JvmOverloads:
public static final String connect(String host, int port) {
    return connect(host, port, true);
}

public static final String connect(String host) {
    return connect(host, 443, true);
}
```
Setiap kombinasi diisi dari kiri ke kanan secara berurutan, memanggil metode penuh dengan menyuntikkan nilai konstan yang ditentukan di deklarasi Kotlin.

##### C. `@JvmField`
- **Tanpa `@JvmField`**: Properti `val baseUrl: String` menghasilkan private field `private final String baseUrl` dan public accessor method `public final String getBaseUrl()`.
- **Dengan `@JvmField`**: Modifiers field diubah menjadi `public final String baseUrl;`. Getter dan Setter sama sekali tidak di-generate ke dalam bytecode pool, memangkas overhead pemanggilan metode (`invokevirtual` menjadi `getfield`).

#### Alokasi Memori / Resource
- `@JvmStatic` dan `@JvmOverloads` sedikit meningkatkan ukuran file binary (`.class`) karena adanya metode forwarding sintetik.
- `@JvmField` mengeliminasi *method table references* untuk getter/setter, mengurangi memory footprint dari class definition di Metaspace JVM.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `@JvmField` pada *constants* publik jika tidak bisa menggunakan `const val` (misalnya instans non-primitif: regex, collections yang immutable).
  - Terapkan `@JvmOverloads` pada konstruktor `Custom View` di Android jika view tersebut didefinisikan di Kotlin tetapi di-inflate oleh Java / XML LayoutInflater.
  - Gunakan `@JvmStatic` pada method Factory atau Utility agar interoperabilitas dengan framework berbasis refleksi (seperti JUnit `@MethodSource`, Spring Beans) berjalan mulus tanpa konfigurasi khusus.

- **Don'ts**:
  - Jangan gunakan `@JvmField` jika properti membutuhkan validasi internal (enkapsulasi) atau jika properti tersebut adalah bagian dari interface.
  - Jangan gunakan `@JvmOverloads` pada fungsi yang parameternya sering berubah urutan di internal lifecycle, karena signature overloading Java di-generate secara kaku dari kiri ke kanan.
  - Jangan menambahkan `@JvmOverloads` pada method polymorphic/abstract di interface.

- **Edge Cases**:
  - **Inkompatibilitas `@JvmField`**: Anotasi ini tidak bisa diterapkan pada properti `private`, `protected`, `open`, `override`, atau properti dengan *custom getter/setter*.
  - **Overload Collision**: Jika method di Java sudah memiliki nama dan tipe parameter yang sama persis dengan salah satu hasil proyeksi `@JvmOverloads`, compiler akan mengeluarkan error `Platform declaration clash`.

### 5. Tantangan Eksplorasi Mandiri

1. **Bytecode Reverse-Engineering**:
   Tulis kelas Kotlin dengan satu fungsi yang memiliki 4 parameter dengan nilai default: `fun test(a: Int = 1, b: String = "x", c: Boolean = false, d: Double = 0.0)`. Tambahkan `@JvmOverloads`. Kompilasi menggunakan `kotlinc`, lalu jalankan `javap -c -p NamaKelas.class`. Analisis bagaimana bitmask passed argument dihitung dalam eksekusi JVM.
2. **Framework Reflection Interop**:
   Buat custom data class untuk serialisasi Jackson ObjectMapper di Java. Eksplorasi apa yang terjadi pada deserialisasi saat konstruktor menggunakan `@JvmOverloads` versus tanpa `@JvmOverloads` ketika Jackson berupaya memetakan JSON payload yang tidak lengkap.
3. **`@JvmField` vs `const val`**:
   Buktikan perbedaan bytecode antara `const val TIMEOUT = 1000L` dan `@JvmField val TIMEOUT = 1000L`. Kapan compiler melakukan inlining primitive secara langsung (compile-time constant) dan kapan compiler mempertahankan memory address referencing?
