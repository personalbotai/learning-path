## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa aplikasi Kotlin Multiplatform (KMP), tantangan terbesar bukan terletak pada eksekusi kalkulasi logis, melainkan pada sinkronisasi *state* lintas platform (Android Runtime/ART vs. iOS Native/Objective-C Runtime via Swift ARC). Arsitektur State Management di KMP harus menyelesaikan dua masalah fundamental:
1. **Unidirectional Data Flow (UDF)** yang deterministik dan *thread-safe*.
2. **Interoperabilitas Reaktif** yang mulus antara Kotlin Coroutines (`StateFlow`) dan paradigma UI deklaratif modern (Jetpack Compose di Android/Desktop dan SwiftUI di iOS).

```
                      +-------------------+
                      |   UI View Layer   |
                      | (Compose/SwiftUI) |
                      +---------+---------+
                                |
                   User Action  |  Observes State /
                    (Intent)    |  Receives Effects
                                v
                      +-------------------+
                      |   BaseViewModel   |
                      |  / MVI Container  |
                      +---------+---------+
                                |
                  Dispatches to | Reducer produces
                                v
                      +-------------------+
                      |   Pure Reducer/   |
                      | Execution Engine  |
                      +-------------------+
```

#### MVVM vs. MVI di KMP

*   **Model-View-ViewModel (MVVM)**: ViewModel mengekspos beberapa stream reaktif terfragmentasi (misalnya `isLoading: StateFlow<Boolean>`, `data: StateFlow<List<T>>`). Di KMP, pendekatan ini memicu *state inconsistency* di layer Swift jika dua stream mengalami *race condition* akibat bridging asynchronous yang berbeda, serta menyulitkan proses debugging karena tidak ada representasi tunggal dari kondisi UI pada suatu titik waktu (*point-in-time snapshot*).
*   **Model-View-Intent (MVI)**: Memaksakan prinsip Single Source of Truth (SSOT). ViewModel mengekspos tepat **satu** `StateFlow<UiState>` yang immutable. UI hanya dapat mengirim `Intent` (sinyal intensi), dan efek samping sesaat (*one-off side effects* seperti navigasi, dialog, atau toast) dialirkan melalui `Channel` sebagai `UiEffect`.

MVI secara natural lebih superior untuk KMP karena:
- Mereduksi *surface area* interop ke platform native. iOS cukup mengamati satu stream `StateFlow` dan satu stream `UiEffect`.
- State bersifat atomik; *reducer* menjamin transisi state terjadi secara sekuensial dan prediktif tanpa *race conditions*.

### 2. Implementasi & Contoh Kasus Nyata

Mulai Lifecycle 2.8.0, Jetpack ViewModel (`androidx.lifecycle.ViewModel`) telah resmi menjadi komponen multiplatform. Berikut adalah implementasi *production-ready* Core MVI Engine beserta implementasi fitur nyata (Manajemen Profil Pengguna).

#### Core MVI Architecture (Common Code)

```kotlin
// commonMain/kotlin/core/mvi/MviArchitecture.kt
package core.mvi

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.channels.Channel
import kotlinx.coroutines.flow.MutableSharedFlow
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.asSharedFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.receiveAsFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

interface UiState
interface UiIntent
interface UiEffect

abstract class BaseMviViewModel<S : UiState, I : UiIntent, E : UiEffect>(
    initialState: S
) : ViewModel() {

    private val _uiState = MutableStateFlow(initialState)
    val uiState = _uiState.asStateFlow()

    // Channel menjamin delivery 1-to-1 untuk one-off events
    private val _uiEffect = Channel<E>(capacity = Channel.BUFFERED)
    val uiEffect = _uiEffect.receiveAsFlow()

    fun sendIntent(intent: I) {
        viewModelScope.launch {
            handleIntent(intent)
        }
    }

    protected abstract suspend fun handleIntent(intent: I)

    // Thread-safe state mutation via CAS (Compare-And-Swap)
    protected fun setState(reducer: S.() -> S) {
        _uiState.update { currentState -> currentState.reducer() }
    }

    protected fun sendEffect(effect: E) {
        viewModelScope.launch {
            _uiEffect.send(effect)
        }
    }
}
```

#### Implementasi Kasus Nyata: User Profile Feature

```kotlin
// commonMain/kotlin/feature/profile/ProfileContract.kt
package feature.profile

import core.mvi.UiEffect
import core.mvi.UiIntent
import core.mvi.UiState

data class UserProfile(val id: String, val username: String, val email: String)

// 1. Immutable State
data class ProfileState(
    val isLoading: Boolean = false,
    val profile: UserProfile? = null,
    val errorMessage: String? = null
) : UiState

// 2. Intents
sealed interface ProfileIntent : UiIntent {
    data object LoadProfile : ProfileIntent
    data class UpdateUsername(val newName: String) : ProfileIntent
}

// 3. One-off Effects
sealed interface ProfileEffect : UiEffect {
    data class ShowToast(val message: String) : ProfileEffect
    data object NavigateToLogin : ProfileEffect
}
```

```kotlin
// commonMain/kotlin/feature/profile/ProfileViewModel.kt
package feature.profile

import core.mvi.BaseMviViewModel
import kotlinx.coroutines.delay

class ProfileViewModel(
    private val userRepository: UserRepository // Injected dependency
) : BaseMviViewModel<ProfileState, ProfileIntent, ProfileEffect>(
    initialState = ProfileState()
) {

    override suspend fun handleIntent(intent: ProfileIntent) {
        when (intent) {
            is ProfileIntent.LoadProfile -> executeLoadProfile()
            is ProfileIntent.UpdateUsername -> executeUpdateUsername(intent.newName)
        }
    }

    private suspend fun executeLoadProfile() {
        setState { copy(isLoading = true, errorMessage = null) }
        try {
            val user = userRepository.fetchUser()
            setState { copy(isLoading = false, profile = user) }
        } catch (e: Exception) {
            setState { copy(isLoading = false, errorMessage = e.message) }
            sendEffect(ProfileEffect.ShowToast(e.message ?: "Failed to load profile"))
        }
    }

    private suspend fun executeUpdateUsername(newName: String) {
        if (newName.isBlank()) {
            sendEffect(ProfileEffect.ShowToast("Username cannot be empty"))
            return
        }
        
        setState { copy(isLoading = true) }
        try {
            val updated = userRepository.updateName(newName)
            setState { copy(isLoading = false, profile = updated) }
            sendEffect(ProfileEffect.ShowToast("Profile successfully updated"))
        } catch (e: Exception) {
            setState { copy(isLoading = false) }
            sendEffect(ProfileEffect.ShowToast("Update failed: ${e.message}"))
        }
    }
}

// Stub Repository Interface
interface UserRepository {
    suspend fun fetchUser(): UserProfile
    suspend fun updateName(name: String): UserProfile
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Thread-Safety StateFlow Mutex vs. CAS**: 
   Di balik layar, fungsi `MutableStateFlow.update { }` tidak menggunakan lock berbasis primitif platform (seperti `pthread_mutex` atau Java `synchronized`). Ia mengeksekusi *optimistic loop* menggunakan instruksi CPU atomic **Compare-And-Swap (CAS)** via Atomic Reference. Jika dua thread memanggil `setState` secara konkuren, loop akan mengulang evaluasi lambda hingga mutasi berhasil ditulis tanpa menahan lock thread (*lock-free*).
2. **Channel Buffering**:
   `Channel<E>(Channel.BUFFERED)` menggunakan circular array buffer dengan kapasitas default (64 slot). Pola ini melindungi UI dari *backpressure*: jika SwiftUI View sedang melakukan transisi animasi (belum siap me-render effect), effect tidak hilang (berbeda dengan `SharedFlow` berkonfigurasi `extraBufferCapacity = 0` yang membuang emisi jika tidak ada *active collector*).
3. **Bridge ABI iOS (SKIE vs. Vanilla Obj-C Export)**:
   Kotlin/Native mengkompilasi class Kotlin menjadi Objective-C header.
   - Tanpa tooling tambahan, `StateFlow` diekspor sebagai interface generik biasa yang kehilangan tipe konkret akibat *type erasure* Objective-C. Swift terpaksa menggunakan wrapper completion-handler yang kompleks.
   - Library modern seperti **SKIE** (*Swift Kotlin Interface Enhancer*) memodifikasi output binary Kotlin/Native pada tahap link-time. SKIE membungkus `StateFlow` dan `Channel` menjadi Swift `AsyncSequence` atau native SwiftUI `@Published` wrapper, memungkinkan konsumsi `for await state in viewModel.uiState` langsung di runtime Swift Concurrency.

#### Alokasi Memori / Resource
- **Immutability Overhead**: MVI menggunakan pola `copy()` pada Kotlin data class. Setiap perubahan menghasilkan instansiasi objek baru di heap. Di Kotlin/Native, memory manager baru (sejak Kotlin 1.9.20+) menggunakan *thread-local allocations* yang sangat cepat dengan *tracing garbage collector* yang berjalan paralel di background. Alokasi jangka pendek (*short-lived objects*) dari mutasi state memiliki ongkos GC yang relatif kecil, sebanding dengan kejelasan alur logika aplikasi.
- **Scope Cancellation Cascading**: Saat lifecycle di Android (Activity/Fragment) berakhir atau UIViewController di iOS di-*dealloc*, hierarki coroutine diikat langsung ke `viewModelScope`. Pembatalan konteks memicu `CancellationException` yang membatalkan seluruh *child jobs* dan menutup `Channel`, mencegah memory leak pada closure yang menangkap referensi platform.

#### Trade-offs
| Aspek | MVVM Tradisional | MVI UDF Terpusat |
| :--- | :--- | :--- |
| **Boilerplate** | Rendah (cukup ekspos flow langsung). | Tinggi (harus membuat State, Intent, Effect contract). |
| **State Predictability** | Rentan desinkronisasi antar-komponen. | Deterministik, mudah dibuatkan *Time-Travel Debugging*. |
| **Interop Overhead** | Sangat kompleks (banyak stream harus di-bind di iOS). | Sederhana (hanya 1 state stream dan 1 effect channel). |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `_uiState.update { }`**: Selalu mutasikan state menggunakan method `.update { }` untuk menjamin konsistensi konkuren, jangan pernah menggunakan assign langsung `_uiState.value = _uiState.value.copy(...)`.
- **Bedakan State vs. Effect**: Simpan informasi persisten pada `UiState` (misal: isi input form, daftar item, status loading). Gunakan `UiEffect` secara eksklusif untuk aksi yang hanya boleh dieksekusi tepat satu kali (*fire-and-forget*), seperti navigasi atau modal alert.
- **Konsumsi Flow dengan Lifecycle-Aware Collector**: 
  - Di Android: Gunakan `collectAsStateWithLifecycle()` dari Compose runtime.
  - Di iOS: Gunakan wrapper yang mengikat observasi ke lifecycle SwiftUI (`.task` modifier).

#### Don'ts
- **Mengekspos `MutableStateFlow`**: Jangan pernah membuka instance `MutableStateFlow` ke publik (`public val uiState: MutableStateFlow`). Platform UI native (terutama Swift) berpotensi memutasi nilai state di luar pipeline ViewModel, melanggar prinsip UDF.
- **Blocking Calls di Reducer/Intent**: Hindari menjalankan blocking IO langsung di thread utama ViewModel. Pastikan repository menangani context switching ke `Dispatchers.IO` secara mandiri.
- **Menyimpan Referensi Platform di ViewModel**: Jangan pernah menaruh objek Context Android, UIView iOS, atau Compose Composable di dalam `MviViewModel`. ViewModel harus berstatus *Platform-Agnostic* (pure Kotlin).

#### Edge Cases
- **Swift Cancellation Token Drop**: Pada iOS, jika Task Swift dibatalkan secara tiba-tiba saat coroutine jembatan Kotlin masih berjalan, pastikan adapter mengalirkan sinyal pembatalan ke Kotlin `Job` agar tidak terjadi *orphan background processes*.
- **Rapid-fire Intent Triggering**: Ketika pengguna menekan tombol secara berulang (*double-tap/spam*), Intent dapat membanjiri antrean coroutine. Gunakan operator transformatif seperti `debounce()`, atau terapkan guard flag langsung pada state (misalnya periksa `if (uiState.value.isLoading) return` sebelum mengeksekusi use-case).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Side-Effect Replay Guard**: 
   Modifikasi arsitektur `BaseMviViewModel` di atas untuk menangani skenario di mana konfigurasi Android berubah (orientasi layar berubah). Buktikan bahwa `UiEffect` yang terkirim saat transisi konfigurasi tidak dieksekusi ulang secara ganda, sedangkan `UiState` tetap terjaga utuh tanpa re-fetch data jaringan.
2. **Swift Concurrency Custom Bridge**: 
   Tulis ekstensi Swift (SwiftUI) tanpa library pihak ketiga (tanpa SKIE) yang mengonsumsi Kotlin `CommonFlow` / `StateFlow` memanfaatkan paradigma `AsyncStream` dan protocol `ObservableObject`, lalu verifikasi penanganan memory leak saat view di-dismiss melalui Instruments Memory Leaks Profiler.
