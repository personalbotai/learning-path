## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam paradigma *Structured Concurrency*, kegagalan (exception) pada sebuah coroutine tidak terisolasi secara default. Desain ini bertujuan untuk mencegah *leaked background tasks*—situasi di mana suatu operasi gagal, namun operasi anak atau saudaranya tetap berjalan tanpa ada yang mengonsumsi hasilnya, membuang resource CPU dan memori.

Secara umum, coroutine menangani exception melalui dua mekanisme propagation tergantung *builder* yang digunakan:
1. **Fire-and-forget (`launch`)**: Exception dianggap tidak tertangani (*uncaught*) dan langsung dipropagasikan ke atas hierarki pohon coroutine menuju parent, membatalkan parent serta seluruh sibling coroutine lainnya, hingga mencapai root coroutine scope.
2. **Deferred value (`async`)**: Exception ditahan (*encapsulated*) di dalam objek `Deferred<T>` dan baru akan dilemparkan kembali (*re-thrown*) ketika fungsi `.await()` dipanggil. Namun, perlu dicatat bahwa jika `async` dibuat di dalam root `coroutineScope` biasa (bukan root scope terisolasi), kegagalannya tetap membatalkan parent scope sebelum `await()` sempat dipanggil.

```
            [Job (Standard)]                     [SupervisorJob]
                 Parent                               Parent
                /      \                             /      \
           Child 1    Child 2                   Child 1    Child 2
          (Fails!)       |                     (Fails!)       |
             |           v                        |           v
     Cancels Parent -> Cancels Child 2     Does NOT cancel   Continues
                                               Parent        Running
```

#### Job vs. SupervisorJob
- **`Job` Standar**: Bersifat dua arah (*bidirectional cancellation*). Jika sebuah child coroutine melempar exception selain `CancellationException`, child tersebut membatalkan parent-nya. Parent kemudian membatalkan seluruh child lainnya, lalu melemparkan exception ke handler global atau thread context.
- **`SupervisorJob`**: Mengubah aliran propagasi menjadi satu arah (*unidirectional*). Pembatalan hanya mengalir ke bawah dari parent ke child. Jika salah satu child gagal dan melempar exception, `SupervisorJob` tidak akan membatalkan dirinya sendiri maupun child-child lainnya. Masing-masing child bertanggung jawab penuh menangani exception-nya sendiri.

#### CoroutineExceptionHandler (CEH)
`CoroutineExceptionHandler` adalah elemen opsional pada `CoroutineContext` yang berfungsi sebagai blok `catch` global terakhir untuk coroutine yang diluncurkan via `launch`. CEH **hanya efektif** jika dipasang pada:
- Root coroutine (coroutine yang dibuat langsung dari sebuah `CoroutineScope`).
- Coroutine langsung di bawah `SupervisorJob` atau `supervisorScope`.

Memasang CEH pada child coroutine di dalam `Job` standar adalah operasi yang sia-sia (*no-op*), karena exception akan didelegasikan langsung ke parent tanpa mengeksekusi handler child tersebut.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengilustrasikan sistem agregator data e-commerce: mengambil data Profil Pengguna (kritis) serta data Rekomendasi & Notifikasi (non-kritis). Jika servis rekomendasi down, sistem tidak boleh mematikan pemrosesan profil pengguna.

```kotlin
import kotlinx.coroutines.*
import java.io.IOException

// 1. Definisikan CoroutineExceptionHandler untuk uncaught exceptions
val globalExceptionHandler = CoroutineExceptionHandler { context, throwable ->
    val coroutineName = context[CoroutineName]?.name ?: "Unknown"
    println("[ALERT] Exception tertangkap di $coroutineName: ${throwable.message}")
}

fun main() = runBlocking {
    println("--- Skenario 1: Kegagalan dengan Job Biasa ---")
    runStandardJobFailure()

    println("\n--- Skenario 2: Isolasi dengan supervisorScope & CEH ---")
    runSupervisorSuccess()
}

suspend fun runStandardJobFailure() {
    try {
        coroutineScope {
            launch(CoroutineName("Worker-1")) {
                delay(100)
                println("Worker-1 selesai.")
            }
            launch(CoroutineName("Worker-2-Faulty")) {
                delay(50)
                throw IOException("Koneksi database Worker-2 terputus!")
            }
        }
    } catch (e: Exception) {
        println("Parent coroutineScope menangkap: ${e.message}")
        // Worker-1 otomatis dibatalkan sebelum selesai karena Worker-2 gagal.
    }
}

suspend fun runSupervisorSuccess() {
    // supervisorScope memastikan kegagalan pada satu child tidak membatalkan sibling lainnya
    supervisorScope {
        // Child 1: Layanan Rekomendasi (Non-kritis, gagal)
        // CEH harus dipasang langsung pada root child di supervisorScope
        val childExceptionHandler = CoroutineExceptionHandler { _, throwable ->
            println("[Handled] Rekomendasi gagal dimuat: ${throwable.message}")
        }

        val recommendationJob = launch(CoroutineName("RecommendationService") + childExceptionHandler) {
            println("Memulai fetch rekomendasi...")
            throw IOException("Service Rekomendasi Timeout (504)")
        }

        // Child 2: Layanan Profil Pengguna (Kritis, harus tetap berjalan)
        val userProfileDeferred = async(CoroutineName("UserProfileService")) {
            println("Memulai fetch user profile...")
            delay(200) // Simulasi I/O
            "Data Profil: { id: 101, name: 'Alice' }"
        }

        // Child 3: Memantau penyelesaian
        recommendationJob.join()

        try {
            val profile = userProfileDeferred.await()
            println("Hasil profil berhasil didapatkan: $profile")
        } catch (e: Exception) {
            println("User profile gagal didapatkan: ${e.message}")
        }
    }
    println("supervisorScope selesai dieksekusi secara elegan.")
}
```

#### Analisis Alur Eksekusi:
1. Pada `runStandardJobFailure()`, kegagalan `Worker-2` membatalkan `coroutineScope`. `Worker-1` yang sedang `delay(100)` menerima sinyal cancel (`JobCancellationException`) dan langsung berhenti tanpa mencetak log selesai.
2. Pada `runSupervisorSuccess()`, `supervisorScope` memutus rantai propagasi pembatalan. `RecommendationService` melempar `IOException`, yang langsung ditangani oleh `childExceptionHandler` tanpa merembet ke parent. Hasilnya, `UserProfileService` tetap menyelesaikan eksekusinya dan data profil berhasil dikembalikan via `.await()`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & State Machine: Siklus Pembatalan Parent-Child
Di tingkat runtime, setiap coroutine memiliki `JobSupport` yang mengelola siklus hidup melalui state internal: `NEW`, `ACTIVE`, `COMPLETING`, `COMPLETING_WAITING_CHILDREN`, `CANCELLING`, dan `CANCELLED`.

```
                    +--------------+
                    |    ACTIVE    |
                    +--------------+
                      /          \
     (Child Fails / Exception)   (Normal Completion)
                    /              \
                   v                v
      +------------------+    +----------------------------+
      |    CANCELLING    |    | COMPLETING_WAITING_CHILDEN |
      +------------------+    +----------------------------+
                   \                /
             (All children finalized)
                     \            /
                      v          v
                    +--------------+
                    |  CANCELLED / |
                    |  COMPLETED   |
                    +--------------+
```

1. Ketika child melempar exception, child masuk ke state `CANCELLING`.
2. Child memanggil internal method `parent.childCancelled(cause)`.
3. Pada **`Job` standar**: Method `childCancelled()` mengembalikan nilai `true`. Parent segera membatalkan dirinya sendiri, memanggil `cancelChildren()`, dan beralih ke state `CANCELLING`. Parent mengumpulkan semua exception dari child-child yang dibatalkan ke dalam struktur data terkompresi (*exception aggregation*) dan memasukkannya ke `Throwable.addSuppressed()`.
4. Pada **`SupervisorJobImpl`**: Method `childCancelled()` di-override untuk selalu mengembalikan nilai `false`. Parent menolak untuk dibatalkan dan tidak menyebarkan pembatalan ke sibling coroutine lainnya.

#### Alokasi Memori & Resource Management
`CoroutineExceptionHandler` disimpan sebagai referensi di dalam array atau hash map `CoroutineContext` (yang direpresentasikan oleh class `CombinedContext` atau `Element`). Ketika exception tidak tertangani oleh handler context lokal:
- Runtime akan mencari handler di context parent secara rekursif hingga menemukan root.
- Jika root tidak memiliki handler, runtime memanggil `Thread.currentThread().uncaughtExceptionHandler`, yang pada Android dapat memicu *Application Not Responding* (ANR) atau *crash log*, sedangkan di JVM standar akan mencetak stack trace ke `System.err`.

#### Trade-offs: `SupervisorJob()` vs `supervisorScope`
- `SupervisorJob()` biasa membutuhkan pembatalan manual (`job.cancel()`). Jika di-pass ke `CoroutineScope(SupervisorJob())`, developer harus mengontrol lifecycle scope tersebut agar tidak memicu memory leak.
- `supervisorScope` adalah suspend function yang mengenkapsulasi coroutine scope secara temporer. Scope ini otomatis menunggu semua child selesai sebelum kembali (*structured*), mengeliminasi risiko coroutine bocor tanpa lifecycle yang jelas.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Tangkap Exception Spesifik**: Tangkap hanya exception yang diekspektasi (misal: `IOException`, `HttpException`). Biarkan `CancellationException` melewatinya.
- **Gunakan `supervisorScope` untuk Operasi Paralel Independen**: Jika memiliki sejumlah task yang independen (misal: query batch ke microservices terpisah), bungkus dengan `supervisorScope` agar kegagalan parsial dapat ditangani gracefully.
- **Pasang CEH di Root Coroutine**: Pasang `CoroutineExceptionHandler` pada `CoroutineScope` utama atau langsung pada pemanggilan `launch` di level paling atas.

#### Don'ts
- **Jangan Menelan `CancellationException`**:
  ```kotlin
  // ANTI-PATTERN: Merusak mekanisme kooperatif cancellation coroutine
  try {
      delay(1000)
  } catch (e: Exception) { // Termasuk CancellationException!
      // Menelan exception tanpa melempar ulang
      logger.error("Terjadi error", e)
  }
  ```
  Jika terpaksa menangkap `Exception`, selalu re-throw jika instance tersebut adalah `CancellationException`:
  ```kotlin
  // IDIOMATIC PATTERN
  try {
      delay(1000)
  } catch (e: CancellationException) {
      throw e // Wajib di-throw ulang agar cancellation hierarchy bekerja
  } catch (e: Exception) {
      logger.error("Error valid tertangkap", e)
  }
  ```

- **Jangan Melewatkan `SupervisorJob` sebagai Argumen Parent Scope Biasa**:
  ```kotlin
  // JEBAKAN UMUM:
  val scope = CoroutineScope(Job())
  scope.launch(SupervisorJob()) { // TIDAK BEKERJA SEPERTI SUPERVISOR!
      // SupervisorJob di sini menjadi child dari scope.Job, 
      // tetapi child di bawah launch ini tetap menggunakan Job default.
      launch { throw RuntimeException() } // Tetap membatalkan scope!
  }
  ```
  Gunakan fungsi `supervisorScope { ... }` untuk membuat batas supervisi baru, bukan sekadar menyisipkan `SupervisorJob()` di dalam parameter `launch`.

#### Edge Cases
- **Exception di `async` tanpa `await()`**: Jika `async` adalah root coroutine yang terpasang pada `SupervisorJob`, exception tidak akan dilempar sampai `.await()` dipanggil. Jika `.await()` tidak pernah dipanggil, exception akan hilang tanpa jejak (*silent failure*), mempersulit proses debugging.

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Partial Batch Processor**:
   Buat sebuah fungsi `suspend fun processBatch(items: List<Int>): List<Result<String>>` menggunakan `supervisorScope`. Buat simulasi di mana setiap item genap memicu exception dan item ganjil sukses. Kembalikan representasi `Result.success` atau `Result.failure` untuk tiap item tanpa membatalkan pemrosesan item lainnya.

2. **Dekomposisi Exception Aggregation**:
   Buat skenario di mana dua child coroutine melempar exception berbeda secara hampir bersamaan di dalam `coroutineScope` biasa (bukan supervisor). Tangkap exception di parent dan inspeksi properti `exception.suppressed`. Amati exception mana yang menjadi *root cause* dan exception mana yang masuk ke dalam *suppressed list*.
