### 1. Konsep & Arsitektur Mendalam

Mempublikasikan pustaka Kotlin Multiplatform (KMP) secara fundamental berbeda dari pustaka JVM tunggal. Pustaka JVM hanya menghasilkan satu file `.jar` dan satu file metadata Maven (`.pom`). Sebaliknya, KMP menghasilkan matriks biner yang heterogen:
- File `.jar` untuk JVM/Android.
- File `.klib` (Kotlin Library) untuk target Native (iOS, macOS, Linux, Windows) dan Web (JS, Wasm).
- File `.module` (*Gradle Module Metadata*).

```
                      +-----------------------------+
                      |   Root Publication (.pom)   |
                      | Gradle Module Metadata      |
                      |       (.module)             |
                      +--------------+--------------+
                                     |
      +------------------------------+-----------------------------+
      |                              |                             |
+-----v-------+               +------v------+               +------v------+
| JVM Target  |               | iOS (Arm64) |               | JS Target   |
| .jar + .pom |               | .klib + .pom|               | .klib + .pom|
+-------------+               +-------------+               +-------------+
```

#### Gradle Module Metadata (GMM) & Variant-Aware Resolution
Sistem Maven standar berbasis `pom.xml` tidak memahami konsep arsitektur CPU, varian native, atau target kompilasi silang (*cross-compilation*). Gradle menyelesaikan limitasi ini melalui **Gradle Module Metadata** (`.module` format JSON).

Ketika sebuah *consumer* (proyek aplikasi) mendefinisikan dependensi ke pustaka KMP:
1. Gradle client membaca file `.module` pada root koordinat pustaka (misal `com.example:mylib:1.0.0`).
2. Mesin resolusi dependensi mengevaluasi *Attributes* dari target consumer (misal: `org.jetbrains.kotlin.platform.type=native`, `org.jetbrains.kotlin.native.target=ios_arm64`).
3. Gradle mengalihkan resolusi ke sub-modul yang sesuai secara deterministik (misal `com.example:mylib-iosarm64:1.0.0`).
4. Jika pustaka dikonsumsi oleh proyek non-Gradle (seperti pure Maven), fallback POM tradisional digunakan (biasanya merujuk ke target JVM).

#### Tantangan Multi-Host CI/CD
Tantangan terbesar KMP CI/CD adalah batasan sistem operasi:
- **macOS Runner:** Wajib untuk mengompilasi target Apple (`iosArm64`, `iosSimulatorArm64`, `macosX64`, `macosArm64`) karena memerlukan Xcode toolchain dan Apple SDK proprietary.
- **Linux Runner:** Jauh lebih murah dan cepat untuk membangun target JVM, Android, JS, dan Linux native.

Arsitektur CI modern mengadopsi strategi **Single Host Runner (macOS)** untuk kesederhanaan orkestrasi jika beban proyek masih moderat, atau **Composite/Matrix Multi-Host Publishing** dengan runner Linux dan macOS yang memisahkan kompilasi artefak dan menyatukannya pada tahap *staging repository* sebelum rilis final.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah konfigurasi produksi menggunakan Gradle Kotlin DSL (`build.gradle.kts`) dengan plugin resmi `maven-publish` dan `signing`, dikombinasikan dengan alur kerja GitHub Actions.

#### Konfigurasi `build.gradle.kts` (Library Core)

```kotlin
plugins {
    alias(libs.plugins.kotlin.multiplatform)
    id("maven-publish")
    id("signing")
    alias(libs.plugins.dokka) // Wajib untuk Maven Central (Javadoc JAR)
}

kotlin {
    jvm()
    
    // Target Apple
    iosX64()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            // common dependencies
        }
    }
}

// Generate Dokka Javadoc Jar untuk memenuhi kualifikasi Sonatype/Maven Central
val javadocJar by tasks.registering(Jar::class) {
    archiveClassifier.set("javadoc")
    from(tasks.dokkaHtml)
}

publishing {
    publications.withType<MavenPublication> {
        artifact(javadocJar)

        pom {
            name.set("KMP Cryptography Core")
            description.set("Algoritma kriptografi multiplatform berbasis Kotlin.")
            url.set("https://github.com/example/kmp-crypto")

            licenses {
                license {
                    name.set("The Apache License, Version 2.0")
                    url.set("http://www.apache.org/licenses/LICENSE-2.0.txt")
                }
            }
            developers {
                developer {
                    id.set("engineercore")
                    name.set("Principal Engineer")
                    email.set("dev@example.com")
                }
            }
            scm {
                connection.set("scm:git:git://github.com/example/kmp-crypto.git")
                developerConnection.set("scm:git:ssh://github.com/example/kmp-crypto.git")
                url.set("https://github.com/example/kmp-crypto")
            }
        }
    }
}

signing {
    val signingKey = System.getenv("GPG_SIGNING_KEY")
    val signingPassword = System.getenv("GPG_SIGNING_PASSWORD")
    
    if (!signingKey.isNullOrBlank() && !signingPassword.isNullOrBlank()) {
        useInMemoryPgpKeys(signingKey, signingPassword)
        sign(publishing.publications)
    }
}
```

#### GitHub Actions Workflow (`.github/workflows/publish.yml`)

Pipeline berikut mengeksekusi validasi dan publikasi ke Sonatype Central Portal melalui runner macOS.

```yaml
name: Publish Multiplatform Library

on:
  push:
    tags:
      - 'v*'

jobs:
  publish:
    runs-on: macos-14 # Apple Silicon Runner (M1/M2) untuk kompilasi cepat
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '17'

      - name: Setup Gradle
        uses: gradle/actions/setup-gradle@v3
        with:
          cache-read-only: false

      - name: Validate Gradle Wrapper
        uses: gradle/wrapper-validation-action@v2

      - name: Run Checks & Host Unit Tests
        run: ./gradlew allTests

      - name: Publish to Maven Central Portal
        env:
          ORG_GRADLE_PROJECT_mavenCentralUsername: ${{ secrets.SONATYPE_USERNAME }}
          ORG_GRADLE_PROJECT_mavenCentralPassword: ${{ secrets.SONATYPE_PASSWORD }}
          GPG_SIGNING_KEY: ${{ secrets.GPG_SIGNING_KEY }}
          GPG_SIGNING_PASSWORD: ${{ secrets.GPG_SIGNING_PASSWORD }}
        run: |
          ./gradlew publishAllPublicationsToMavenCentralRepository \
            --no-configuration-cache \
            --stacktrace
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Kompiler (Konan & Metadata)
- Saat task `publish` dijalankan pada target Apple, Gradle memicu **Kotlin/Native Compiler (`kotlinc-native` / Konan)**. Konan menurunkan Kotlin IR (Intermediate Representation) ke bitcode LLVM, menghasilkan file `.klib`.
- File `.klib` secara fisik adalah file ZIP yang berisi:
  - IR dalam format protobuf.
  - Manifest yang mendefinisikan ABI version dan platform targets.
  - Komponen C-interop bindings (bila ada dependensi ke Objective-C/C runtime).
- Publikasi root (`publishKotlinMultiplatformPublicationToMavenRepository`) menghasilkan artefak abstrak tanpa biner platform. Modul ini murni berisi file `.module` dan `.pom` yang berperan sebagai "pointer" ke biner spesifik arsitektur target.

#### Alokasi Memori & Resource CI Runner
- **LLVM Backend Footprint:** Konan mengonsumsi memori masif saat melakukan fase optimasi LTO (Link Time Optimization). Runner dengan RAM 7GB standar sering kali mengalami *Out-Of-Memory (OOM) Killer* jika kompilasi dilakukan secara paralel.
- **Konan Toolchain Download:** Konan mengunduh *native dependencies* (Clang, sysroot Xcode) ke direktori `~/.konan`. Pada ephemeral CI runner tanpa persistent cache, proses ini memakan transfer data sebesar 1.5GB–3GB pada setiap run, meningkatkan waktu pipeline secara signifikan.

#### Trade-offs: Single Runner vs Matrix Builds
| Aspek | Single Runner (macOS) | Matrix Builds (Linux + macOS) |
| :--- | :--- | :--- |
| **Biaya Runner** | Mahal (macOS runner GitHub berbiaya hingga 10x Linux). | Hemat (Hanya target Apple yang masuk ke macOS). |
| **Kompleksitas State** | Rendah. Satu runner mempublikasikan seluruh varian sekaligus. | Tinggi. Membutuhkan agregasi artefak via shared storage sebelum publish. |
| **Race Condition** | Nol. Pengunggahan metadata root sinkron. | Tinggi. Runner Linux dan macOS berisiko saling menimpa metadata root jika tidak diorkestrasi via *Staging Repository*. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan In-Memory GPG Signing:** Jangan simpan private key dalam bentuk file di filesystem CI. Konversikan private key GPG ASCII-armored ke base64, simpan di Secret CI, dan muat langsung ke memori melalui `useInMemoryPgpKeys()`.
- **Implementasikan Cache untuk `~/.konan`:** Tambahkan path `~/.konan` ke dalam cache step CI untuk menghemat 2–4 menit waktu build pada setiap eksekusi.
- **Wajibkan Task `publishToMavenLocal` pada Pull Request:** Validasi kelengkapan POM, JavaDoc, dan penandatanganan GPG pada environment PR tanpa mempublikasikannya ke server publik.

#### Don'ts
- **Jangan Mempublikasikan Release Build Menggunakan Flag `-Pversion` Manual:** Gunakan Git Tags sebagai sumber kebenaran tunggal (*single source of truth*) untuk versi rilis. Library yang dibangun dengan flag manual rentan terhadap inkonsistensi metadata.
- **Hindari Kompilasi Framework pada Library:** Jangan mencampuradukkan pembuatan biner library (`.klib`) dengan distribusi biner aplikasi (`.xcframework`). Konfigurasi library cukup mendefinisikan arsitektur target, bukan packaging akhir aplikasi, kecuali pustaka didistribusikan via CocoaPods/SPM murni biner.

#### Edge Cases
- **Duplicate Root Publication pada Matrix Execution:** Jika runner Linux menjalankan `publish` dan runner macOS juga menjalankan `publish`, kedua runner akan mencoba mengunggah modul root (`:mylib`) ke Sonatype. Maven Central akan menolak unggahan kedua dengan status `400 Bad Request` atau `409 Conflict`.
  - *Mitigasi:* Jalankan task `publish<Target>PublicationTo...` secara spesifik di tiap runner, dan isolasi publishing modul root hanya ke satu runner tertentu via konfigurasi Gradle flag `-DexcludeRoot=true`.

### 5. Tantangan Eksplorasi Mandiri

1. **Konfigurasi Matrix Multi-Host Publishing:** Modifikasi alur kerja CI untuk membagi pekerjaan menjadi dua runner: Linux (untuk `jvm`, `js`, `wasmJs`) dan macOS (hanya untuk `iosX64`, `iosArm64`, `iosSimulatorArm64`). Gunakan task `publishToMavenLocal` di setiap node, unggah artefak sebagai GitHub Artifact, lalu buat job agregasi khusus yang mengunggah seluruh artefak ke Maven Central tanpa memicu *duplicate root publication*.
2. **Otomatisasi SPM (Swift Package Manager) Release:** Buat task kustom pada Gradle yang membungkus output biner `.xcframework` dari target iOS, menghasilkan file `.zip`, menghitung checksum SHA-256 menggunakan biner CLI host, dan secara otomatis memperbarui file manifest `Package.swift` pada repositori distribusi terpisah.
