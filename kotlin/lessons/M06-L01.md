### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem JVM tradisional, konkurensi dibangun di atas model pemetaan thread **1:1** dengan sistem operasi (*Operating System Threads* via POSIX threads / pthreads). Setiap kali sebuah instance `java.lang.Thread` diinisialisasi, sistem operasi mengalokasikan stack memori khusus (biasanya berkisar antara 512 KB hingga 1 MB per thread tergantung konfigurasi JVM melalui flag `-Xss`) dan mendaftarkannya ke dalam penjadwal kernel (*kernel scheduler*).

```
Model 1:1 (Threads)                  Model M:N (Coroutines)
[ JVM Thread 1 ] <-> [ OS Thread 1 ]   [ Coroutine 1 ] \
[ JVM Thread 2 ] <-> [ OS Thread 2 ]   [ Coroutine 2 ] -- [ OS Worker Thread 1 ]
[ JVM Thread 3 ] <-> [ OS Thread 3 ]   [ Coroutine 3 ] /
(Tiap thread = 1MB Stack Memory)       [ Coroutine 4 ] \_ [ OS Worker Thread 2 ]
                                       (Coroutines berbagi Thread Pool)
```

Terdapat dua batasan arsitektural utama pada pendekatan berbasis thread murni:

1. **Konsumsi Memori (Memory Footprint)**: Jika sebuah aplikasi web melayani 10.000 request bersamaan secara blocking, alokasi memori murni untuk thread stack mencapai $\approx 10.000 \times 1\text{ MB} \approx 10\text{ GB}$, belum termasuk alokasi heap untuk objek aplikasi.
2. **Biaya Context Switch**: Ketika thread mengalami blocking (misalnya menunggu respon database atau disk I/O), kernel OS harus menginterupsi eksekusi, menyimpan register CPU, membersihkan pipeline instruction, dan memuat context thread berikutnya (*CPU register saving, cache trashing, TLB cache invalidation*). Operasi ini memakan ratusan hingga ribuan siklus clock CPU.

Kotlin menyelesaikan tantangan ini melalui **Lightweight Coroutines** berbasis model **M:N** (*multiplexing*). Sebanyak $M$ coroutine dapat dijalankan secara kooperatif di atas $N$ thread OS (di mana $N$ umumnya sebanding dengan jumlah inti CPU logic).

Alih-alih menahan (*blocking*) OS thread saat menunggu proses I/O selesai, coroutine **menangguhkan (*suspends*)** eksekusinya sendiri secara kooperatif. OS thread yang dibebaskan dapat langsung mengeksekusi coroutine lain. Ketika operasi asinkron selesai, coroutine tersebut dapat dilanjutkan kembali (*resumed*) pada thread yang sama atau thread yang berbeda tanpa intervensi kernel scheduler.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengilustrasikan perbedaan perilaku dan konsumsi resource antara pembuatan 100.000 native thread vs 100.000 lightweight coroutine, dilanjutkan dengan implementasi asynchronous I/O batch fetch yang aman.

```kotlin
package com.roadmap.concurrency

import kotlinx.coroutines.*
import java.util.concurrent.atomic.AtomicInteger
import kotlin.system.measureTimeMillis

// Simulasi pemanggilan remote API
suspend fun fetchUserData(userId: Int): String {
    // delay() menangguhkan coroutine tanpa memblokir thread di baliknya
    delay(500L) 
    return "UserPayload(id=$userId)"
}

fun runCoroutineBenchmark(totalTasks: Int) = runBlocking {
    val counter = AtomicInteger(0)
    
    val executionTime = measureTimeMillis {
        // Menggunakan CoroutineScope terkelola (Structured Concurrency)
        coroutineScope {
            repeat(totalTasks) { id ->
                launch(Dispatchers.Default) {
                    val data = fetchUserData(id)
                    if (data.isNotEmpty()) {
                        counter.incrementAndGet()
                    }
                }
            }
        }
    }
    
    println("[COROUTINE] Berhasil memproses ${counter.get()} task dalam ${executionTime}ms")
}

fun runThreadBenchmark(totalTasks: Int) {
    val counter = AtomicInteger(0)
    val threads = mutableListOf<Thread>()

    val executionTime = measureTimeMillis {
        try {
            repeat(totalTasks) { id ->
                val thread = Thread {
                    try {
                        // Thread.sleep() memblokir OS thread secara penuh
                        Thread.sleep(500L)
                        counter.incrementAndGet()
                    } catch (e: InterruptedException) {
                        Thread.currentThread().interrupt()
                    }
                }
                threads.add(thread)
                thread.start()
            }
            
            // Tunggu semua thread selesai
            for (thread in threads) {
                thread.join()
            }
        } catch (oom: OutOfMemoryError) {
            System.err.println("[THREAD] Gagal mengalokasikan native thread: ${oom.message}")
            return
        }
    }
    
    println("[THREAD] Berhasil memproses ${counter.get()} task dalam ${executionTime}ms")
}

fun main() {
    val taskCount = 50_000

    println("=== 1. Menjalankan Uji Beban Coroutines ($taskCount tasks) ===")
    runCoroutineBenchmark(taskCount)

    println("\n=== 2. Menjalankan Uji Beban OS Threads ($taskCount tasks) ===")
    // PERINGATAN: Nilai di atas ~10.000 pada mesin konvensional berpotensi memicu:
    // java.lang.OutOfMemoryError: unable to create native thread
    runThreadBenchmark(taskCount)
}
```

#### Penjelasan Komponen Kunci:
- `suspend fun`: Kata kunci penanda ke compiler bahwa fungsi ini memiliki *suspension point* dan membutuhkan `Continuation` context.
- `delay()` vs `Thread.sleep()`: `delay()` mendaftarkan task scheduler non-blocking lalu melepas thread kembali ke pool. `Thread.sleep()` memerintahkan kernel OS untuk menahan thread pada status `BLOCKED`, mencegah utilisasi thread tersebut untuk komputasi lain.
- `coroutineScope`: Membentuk boundary konkurensi terstruktur (*structured concurrency*), menjamin bahwa parent scope tidak akan selesai sampai seluruh 50.000 child coroutine menyelesaikan eksekusinya.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Continuation-Passing Style (CPS)
Kotlin tidak memerlukan modifikasi pada level JVM bytecode specification untuk mendukung coroutine. Kotlin compiler menerapkan transformasi bernama **Continuation-Passing Style (CPS)** bersama dengan implementasi **State Machine**.

Saat compiler menemukan fungsi bertanda `suspend`:
1. Parameter tambahan bertipe `Continuation<T>` diinjeksi ke parameter terakhir fungsi.
2. Tipe kembalian diubah menjadi `Any?` untuk mengakomodasi nilai asli fungsi atau sentinel value `COROUTINE_SUSPENDED`.

Setiap suspension point dikompilasi menjadi satu state di dalam blok switch-case state machine:

```text
// Representasi konseptual hasil dekompilasi compiler Kotlin ke Java Bytecode
public static final Object fetchUserData(int userId, Continuation $completion) {
    UserDataStateMachine sm = ($completion instanceof UserDataStateMachine) 
        ? (UserDataStateMachine) $completion 
        : new UserDataStateMachine($completion);

    switch (sm.label) {
        case 0:
            sm.label = 1;
            // delay() mengembalikan COROUTINE_SUSPENDED jika proses belum instan selesai
            if (DelayKt.delay(500L, sm) == COROUTINE_SUSPENDED) {
                return COROUTINE_SUSPENDED; // Thread dilepaskan di sini
            }
            break;
        case 1:
            // Lanjutan eksekusi setelah resumed
            break;
    }
    return "UserPayload(id=" + userId + ")";
}
```

#### Alokasi Memori / Resource
- **Stackless vs Stackful**: OS Thread bersifat *stackful*; setiap thread membawa stack frame sendiri untuk melacak rantai eksekusi lokal. Coroutine Kotlin bersifat *stackless*; saat coroutine disuspensi, frame eksekusinya disimpan ke dalam objek `Continuation` pada **JVM Heap**. Ukuran instance `Continuation` hanya beberapa puluh hingga ratusan byte.
- **Dispatchers**: `Dispatchers.Default` dan `Dispatchers.IO` ditenagai oleh custom work-stealing thread pool internal Kotlin (`CoroutineScheduler`). Worker thread mengambil runnable tasks dari global queue atau mencuri task dari local queue worker thread lain saat idle, meminimalkan thread creation overhead.

#### Trade-offs
| Metrik / Karakteristik | Native OS Thread | Kotlin Coroutine |
| :--- | :--- | :--- |
| **Footprint Memori per Unit** | $\approx 512\text{ KB} - 1\text{ MB}$ | $\approx 400\text{ Byte} - 2\text{ KB}$ |
| **Batas Skalabilitas Konkurensi** | Ribuan thread per instance | Jutaan coroutine per instance |
| **Overhead Context Switch** | Kernel trap, register flush, TLB invalidation | Pemanggilan method JVM biasa (polymorphic dispatch) |
| **Debugging & Profiling** | Standard OS & Profiler tooling (`jstack`) | Perlu tooling khusus (`kotlinx-coroutines-debug`) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Dispatcher Sesuai Beban Komputasi**:
  - Gunakan `Dispatchers.Default` untuk tugas terikat CPU (*CPU-bound*) seperti hashing, kompresi, atau parsing payload besar (ukuran pool = jumlah CPU cores).
  - Gunakan `Dispatchers.IO` untuk tugas terikat I/O (*I/O-bound*) seperti pemanggilan HTTP, RPC, atau akses DB (ukuran pool elastis, default max 64 atau jumlah core).
- **Pertahankan Cooperative Cancellation**: Selalu periksa status aktif coroutine secara berkala saat menjalankan loop CPU-bound yang intensif menggunakan `yield()` atau properti `isActive`.

#### Don'ts
- **Memanggil Blocking Call di Coroutine Tanpa Dispatcher Khusus**:
  ```kotlin
  // SALAH: Memblokir worker thread Dispatchers.Default
  launch(Dispatchers.Default) {
      val response = blockingHttpClient.get() // Bahaya: Starvation pada thread pool!
  }

  // BENAR: Offload ke Dispatchers.IO
  launch(Dispatchers.IO) {
      val response = blockingHttpClient.get()
  }
  ```
- **Menggunakan `GlobalScope`**: Mengabaikan siklus hidup aplikasi dan menghilangkan kapabilitas *structured concurrency*. Gunakan lifecycle-aware scope atau `coroutineScope {}`.

#### Edge Cases
- **Thread Local Leakage**: Hati-hati saat menggunakan `ThreadLocal` di dalam coroutine. Karena satu coroutine dapat disuspensi di Worker Thread A dan di-resume di Worker Thread B, data `ThreadLocal` bisa berpindah secara inkonsisten atau bocor (*leak*). Gunakan `asContextElement()` dari pustaka kotlinx-coroutines untuk menyinkronkan context across suspension points.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Bytecode State Machine**:
   Tulis fungsi `suspend fun doubleDelay(): Int` yang memanggil `delay(100)` sebanyak dua kali secara berurutan. Kompilasi dan decompile class tersebut menjadi Java Bytecode via IntelliJ IDEA (`Tools -> Kotlin -> Show Kotlin Bytecode -> Decompile`). Temukan bagaimana compiler menghasilkan field `label` dan blok switch-case yang mengatur suspension point tersebut.

2. **Deteksi Thread Starvation**:
   Buat sebuah scenario menggunakan `runBlocking` dengan dispatcher yang dibatasi pada single thread (`Executors.newSingleThreadExecutor().asCoroutineDispatcher()`). Luncurkan 5 coroutine; pada coroutine pertama panggil `Thread.sleep(3000)`, dan pada 4 coroutine lainnya panggil `delay(100)`. Amati waktu total eksekusinya dan catat mengapa `Thread.sleep` menyebabkan *thread starvation* total bagi coroutine lainnya.
