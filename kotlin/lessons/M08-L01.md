## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Kotlin Multiplatform (KMP) tidak menggunakan pendekatan *Write Once, Run Anywhere* (seperti Java atau Flutter), melainkan *Share Business Logic, Keep Native UI*. Arsitektur KMP didesain agar developer dapat membagikan kode inti (domain, data, network) di berbagai platform (Android, iOS, Desktop, Web) sambil tetap mempertahankan akses langsung ke API spesifik platform (Native API) tanpa *overhead* jembatan (bridge) yang berat.

Struktur dasar KMP membagi kode ke dalam **Source Sets**:
- `commonMain`: Berisi kode murni Kotlin yang agnostik terhadap platform. Tidak bisa mengakses API JVM, iOS, atau JS.
- `androidMain`, `iosMain`, `desktopMain`: Berisi kode spesifik platform. Dapat mengakses API native (misal: `java.util.*` di Android, atau `Foundation` di iOS).

**Mekanisme `expect` dan `actual`**
Ketika kode di `commonMain` membutuhkan fungsionalitas yang implementasinya bergantung pada platform (misalnya: mendapatkan versi OS, enkripsi native, atau *key-value storage*), KMP menyediakan mekanisme `expect` dan `actual`.
- **`expect`**: Deklarasi (kontrak) di `commonMain` yang memberi tahu kompilator, *"Saya butuh fungsi/kelas ini, implementasinya akan disediakan nanti oleh masing-masing platform."*
- **`actual`**: Implementasi nyata di source set platform (`androidMain`, `iosMain`) yang memenuhi kontrak `expect`.

Berbeda dengan *Interface* (OOP), `expect`/`actual` bukanlah polimorfisme *runtime*. Ini adalah fitur **compile-time**. Kompilator Kotlin akan secara statis menautkan pemanggilan `expect` ke `actual` yang sesuai saat melakukan kompilasi untuk target tertentu.

### 2. Implementasi & Contoh Kasus Nyata

Kasus: Kita ingin membuat fungsi untuk menghasilkan UUID (Universally Unique Identifier) dan mendapatkan informasi sistem operasi, yang mana API-nya berbeda antara Android (JVM) dan iOS (Native).

```kotlin
// 1. File: src/commonMain/kotlin/PlatformUtils.kt
// Deklarasi expect di Common module
expect class Platform() {
    val osName: String
    val version: String
}

// Fungsi expect untuk generate UUID
expect fun generateUUID(): String

// Fungsi biasa di common yang menggunakan deklarasi expect
fun getSystemReport(): String {
    val platform = Platform()
    return "System: ${platform.osName} ${platform.version} | Session ID: ${generateUUID()}"
}
```

```kotlin
// 2. File: src/androidMain/kotlin/PlatformUtils.actual.kt
// Implementasi actual untuk Android (JVM)
import android.os.Build
import java.util.UUID

actual class Platform actual constructor() {
    actual val osName: String = "Android"
    actual val version: String = "${Build.VERSION.SDK_INT}"
}

actual fun generateUUID(): String {
    // Menggunakan API bawaan Java/Android
    return UUID.randomUUID().toString()
}
```

```kotlin
// 3. File: src/iosMain/kotlin/PlatformUtils.actual.kt
// Implementasi actual untuk iOS (Kotlin/Native)
import platform.UIKit.UIDevice
import platform.Foundation.NSUUID

actual class Platform actual constructor() {
    actual val osName: String = UIDevice.currentDevice.systemName()
    actual val version: String = UIDevice.currentDevice.systemVersion
}

actual fun generateUUID(): String {
    // Menggunakan API Foundation dari Apple
    return NSUUID().UUIDString()
}
```

**Penjelasan Kode:**
- `expect class Platform()` mendefinisikan *blueprint*. Perhatikan bahwa `actual class` harus menggunakan keyword `actual` baik pada nama kelas maupun pada *constructor*-nya (`actual constructor()`).
- Di `iosMain`, Kotlin/Native menyediakan *interoperability* dua arah dengan Objective-C/Swift, sehingga kita bisa langsung mengimpor `platform.UIKit.*` dan `platform.Foundation.*`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Mekanisme `expect`/`actual` diselesaikan pada tahap kompilasi (Compile-Time Resolution). Saat kompilator Kotlin memproses target Android, ia akan menggabungkan `commonMain` dan `androidMain`, lalu membuang deklarasi `expect` dan menggantinya langsung dengan implementasi `actual`. Tidak ada *Virtual Dispatch* (seperti pada pemanggilan Interface via *vtable*), sehingga eksekusinya secepat pemanggilan fungsi statis/langsung.
- **Kotlin IR (Intermediate Representation)**:
  Kompilator Kotlin (K2) mengubah kode sumber menjadi Kotlin IR. Pada tahap ini, *frontend compiler* memvalidasi bahwa setiap `expect` memiliki `actual` yang cocok (signature, tipe data, visibilitas harus identik). Jika ada satu target platform yang tidak memiliki `actual`, kompilasi akan gagal (*Compile Error*). Setelah divalidasi, *backend compiler* (Kotlin/JVM, Kotlin/Native LLVM, Kotlin/JS) akan menghasilkan *bytecode* atau *machine code* spesifik.
- **Alokasi Memori / Resource**:
  Karena ini adalah resolusi statis, tidak ada *overhead* memori tambahan untuk menyimpan referensi objek polimorfik. Objek `Platform` di Android akan dialokasikan di JVM Heap, sedangkan di iOS akan dialokasikan menggunakan *Native Memory* yang dikelola oleh Kotlin/Native GC.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `expect`/`actual` hanya untuk **thin wrappers** (pembungkus tipis) di atas API spesifik platform.
  - Pertimbangkan menggunakan **Interfaces dan Dependency Injection (DI)** (seperti Koin) sebagai alternatif `expect`/`actual` jika implementasinya membutuhkan banyak dependensi eksternal atau logika yang kompleks. Interface lebih fleksibel untuk *mocking* saat *Unit Testing*.
  - Gunakan `typealias` pada `actual` jika platform sudah memiliki kelas yang persis sama dengan kontrak `expect` (misal: `actual typealias ConcurrentHashMap = java.util.concurrent.ConcurrentHashMap`).

- **Don'ts**:
  - Jangan menaruh **Business Logic** di dalam blok `actual`. Logika bisnis harus tetap berada di `commonMain`.
  - Jangan mendefinisikan *default arguments* di dalam `actual`. Aturan Kotlin mengharuskan *default arguments* hanya dideklarasikan di bagian `expect`.

- **Edge Cases**:
  - **Visibilitas**: Jika `expect` bersifat `internal`, maka `actual` juga harus `internal` atau lebih longgar (`public`). Namun, sangat disarankan untuk menjaga modifier visibilitas agar identik.
  - **Evolusi API**: Jika Anda menambahkan fungsi baru di `expect`, Anda **wajib** mengimplementasikannya di *semua* target platform. Jika Anda memiliki 5 target (Android, iOS, Desktop, Web, Wasm), Anda harus menulis 5 `actual` baru. Ini bisa menjadi *bottleneck* pemeliharaan.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Key-Value Storage**: Buatlah sebuah `expect class Settings` di `commonMain` yang memiliki fungsi `putString(key, value)` dan `getString(key)`. Implementasikan `actual`-nya menggunakan `SharedPreferences` (atau DataStore) di Android dan `NSUserDefaults` di iOS.
2. **Eksperimen Default Arguments**: Cobalah membuat fungsi `expect fun logMessage(message: String, level: String = "INFO")`. Lalu cobalah menaruh nilai default yang sama di fungsi `actual`-nya. Amati pesan *error* yang diberikan oleh kompilator Kotlin dan pahami mengapa Kotlin melarang hal tersebut.
