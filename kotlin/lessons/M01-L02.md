### 1. Konsep & Arsitektur Mendalam

Kotlin mendesain sistem variabel dan tipenya dengan prinsip utama: **Null Safety**, **Immutability by Default**, dan **Ergonomi melalui Type Inference**.

```
       +---------------------------------------------+
       |                  Any / Any?                 |
       +---------------------------------------------+
                              ^
                              |
       +----------------------+----------------------+
       |                                             |
+---------------+                             +---------------+
| Primitives*   |                             | Object Types  |
| (Int, Double, |                             | (String, List,|
|  Boolean, etc)|                             |  CustomClass) |
+---------------+                             +---------------+
       ^                                             ^
       |                                             |
       +----------------------+----------------------+
                              |
       +---------------------------------------------+
       |                   Nothing                   |
       +---------------------------------------------+
  *Di JVM: Direpresentasikan sebagai primitif primitif native jika non-nullable.
```

#### Mutabilitas: `val` vs `var`
- **`val` (Value / Read-Only):** Menginisialisasi referensi yang tidak dapat diubah (*read-only reference*). Setelah di-assign, referensi ini tidak dapat dialokasikan ulang ke objek lain. Namun, `val` **bukan** berarti *deep immutability*. Objek yang ditunjuk oleh `val` tetap dapat memiliki *internal state* yang mutabel.
- **`var` (Variable / Mutable):** Mendeklarasikan referensi yang dapat di-reassign ke objek lain selama tipe datanya sama atau merupakan subtipenya.

#### Sistem Tipe Data & Type Inference
Kotlin tidak mengekspos tipe primitif secara langsung di tingkat bahasa sintaksis; tidak ada *keyword* `int`, `double`, atau `boolean` seperti pada Java. Seluruh tipe data dasar direpresentasikan sebagai kelas objek tingkat tinggi (`Int`, `Double`, `Boolean`, `Char`). 

Meski demikian, arsitektur *compiler* (kotlinc) melakukan optimasi otomatis ke Java Virtual Machine (JVM). Jika sebuah variabel bertipe `Int` bersifat non-nullable, compiler akan merendahkannya (*lowering*) menjadi primitif `int` native JVM untuk memaksimalkan performa eksekusi dan meminimalkan jejak memori.

**Type Inference Engine:**
Kotlin mengadopsi variasi dari algoritma inferensi tipe berbasis aliran lokal (*local type inference*). Compiler menganalisis ekspresi di sisi kanan tanda penugasan (`=`) untuk menentukan tipe data variabel secara statis pada fase kompilasi. Dengan demikian, Kotlin tetap merupakan bahasa yang *statically-typed* (bukan dinamis): tipe data dikunci pada saat kompilasi (*compile-time*) tanpa penalti performa saat aplikasi berjalan (*run-time*).

### 2. Implementasi & Contoh Kasus Nyata

```kotlin
fun main() {
    // 1. Type Inference & Explicit Types
    val inferredInt = 42           // Compiler menginferensi tipe sebagai Int
    val explicitLong: Long = 42L   // Eksplisit Long
    
    // Perhatikan: Kotlin TIDAK mendukung implicit widening conversion
    // val invalidLong: Long = inferredInt // COMPILE ERROR: Type mismatch
    val validLong: Long = inferredInt.toLong() // Konversi eksplisit diperlukan

    // 2. Perbedaan val vs var
    var transactionCount = 0
    transactionCount += 1 // Legal: var dapat di-reassign

    val maxTransactionLimit = 100
    // maxTransactionLimit = 101 // COMPILE ERROR: Val cannot be reassigned

    // 3. Referensi Read-Only vs State Mutabel (Shallow Immutability)
    val serverConfig = SystemConfig(host = "10.0.0.1", port = 8080)
    // serverConfig = SystemConfig("10.0.0.2", 9000) // COMPILE ERROR: Referensi terkunci

    val activeEndpoints = mutableListOf("/api/v1/users", "/api/v1/auth")
    // activeEndpoints = mutableListOf() // COMPILE ERROR: Variabel val menolak reassignment
    activeEndpoints.add("/api/v1/orders") // LEGAL: Objek yang ditunjuk tetap mutabel!

    // 4. Primitive vs Boxing Triggers
    val primitiveInt: Int = 1000        // Menjadi primitive 'int' di JVM bytecode
    val boxedInt: Int? = 1000          // Menjadi object 'java.lang.Integer' (Boxing)
    val genericList: List<Int> = listOf(1, 2, 3) // Elemen mengalami autoboxing ke Integer

    println("Config: ${serverConfig.host}, Endpoints: ${activeEndpoints.size}")
    println("Int equality: ${primitiveInt == boxedInt}") // Structural equality: true
}

data class SystemConfig(val host: String, val port: Int)
```

**Penjelasan Alur Kode:**
- `inferredInt.toLong()`: Karena integritas tipe statis yang ketat, Kotlin mencegah *implicit widening* (misal: `Int` ke `Long`) untuk menghindari bug tersembunyi seperti *overflow truncation*.
- `activeEndpoints.add(...)`: Menunjukkan bahwa deklarasi `val` hanya menjamin kestabilan *pointer/referensi* pada *stack*, bukan konten objek yang berada di dalam *heap*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Bytecode Translation)
Ketika kotlinc mengompilasi kode ke JVM Bytecode:
1. **`val` di tingkat lokal** dikompilasi menjadi alokasi variabel lokal tanpa adanya instruksi `*store` lanjutan setelah inisialisasi awal.
2. **`val` di tingkat kelas (properti)** secara default dikompilasi menjadi *private field* dengan *modifier* `final` disertai *public getter*, tanpa adanya *setter*.
3. **`var` di tingkat kelas** dikompilasi menjadi *private field* non-final disertai sepasang *getter* dan *setter*.

Contoh translasi konseptual ke Java:
```kotlin
// Kotlin
class UserSession {
    val sessionId: String = "UUID-01"
    var pingCount: Int = 0
}
```
Diterjemahkan JVM compiler menjadi:
```java
// Java Equivalent
public final class UserSession {
   @NotNull
   private final String sessionId = "UUID-01";
   private int pingCount = 0;

   @NotNull
   public final String getSessionId() { return this.sessionId; }

   public final int getPingCount() { return this.pingCount; }
   public final void setPingCount(int value) { this.pingCount = value; }
}
```

#### Alokasi Memori: Stack vs Heap (Autoboxing)
- **`Int` non-nullable:** Dipetakan ke tipe primitif JVM `int`. Disimpan langsung di dalam *Stack Frame* saat bertindak sebagai variabel lokal thread. Operasi aritmatika menggunakan instruksi CPU native (`iadd`, `imul`), tanpa *overhead* pointer traversal.
- **`Int?` (Nullable):** JVM tidak memiliki konsep *nullable primitive*. Maka, Kotlin membungkus nilainya (*autoboxing*) ke objek `java.lang.Integer`. Objek ini dialokasikan di **Heap**, sedangkan variabel di Stack hanya menyimpan alamat memorinya (referensi 4 atau 8 byte tergantung *Compressed OOPs*).

```
Stack Frame (Lokal)                        Heap Memory
+-----------------------+              +-----------------------+
| primitiveInt: 1000    | (direct val) |                       |
| boxedInt: 0x7FFF001   |------------->| java.lang.Integer     |
+-----------------------+              |   - value: 1000       |
                                       +-----------------------+
```

#### Trade-offs
- Penggunaan `Int?` atau koleksi generik seperti `List<Int>` menimbulkan beban dereferensi pointer, *cache miss* pada L1/L2 CPU cache, serta memperberat kerja *Garbage Collector* (GC) akibat pembuatan jutaan objek pembungkus pendek.
- `val` mempermudah eksekusi aman multi-threading (*concurrency*), meminimalisir *race conditions* karena referensi tidak dapat diganti secara mutabel oleh thread lain di luar kontrol sinkronisasi.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `val` secara default.** Ubah ke `var` hanya jika algoritma memang mutlak membutuhkan mutasi nilai (*state reassignment*).
- **Gunakan tipe primitif spesifik untuk array berkinerja tinggi:** Alih-alih memakai `Array<Int>` (yang menghasilkan array `java.lang.Integer[]` ter-box), gunakan `IntArray` (yang dipetakan langsung ke `int[]` di tingkat JVM).
- **Deklarasikan tipe secara eksplisit pada *Public API* / fungsi tingkat atas.** Type inference sangat baik untuk variabel lokal di dalam tubuh fungsi, namun tipe eksplisit pada *public interface* mencegah *breaking changes* kontraktual yang tidak disengaja.

#### Don'ts
- **Jangan mengasumsikan `val` adalah konstanta waktu kompilasi (*compile-time constant*).** `val` hanya menjamin *read-only access*. Gunakan `const val` untuk nilai primitif atau `String` yang harus digantikan langsung (*inlined*) saat kompilasi.
- **Hindari *boxing loop variables* secara tidak sadar:**
  ```kotlin
  // Buruk: Mengakibatkan jutaan alokasi objek Integer di heap
  var counter: Int? = 0
  for (i in 0 until 1_000_000) {
      counter = counter!! + 1
  }
  ```

#### Edge Cases & Pitfalls
- **Custom Getter pada `val` Properti:** `val` tidak menjamin data bersifat statis jika Anda mendefinisikan *custom getter*. Nilainya dapat berubah tiap kali diakses:
  ```kotlin
  val currentTimestamp: Long
      get() = System.currentTimeMillis() // Legal, namun menghasilkan nilai berbeda setiap pemanggilan!
  ```
- **Variable Shadowing:** Deklarasi ulang variabel dengan nama yang sama di scope yang lebih dalam (*nested scope*) dapat menyembunyikan referensi terluar dan memicu bug logika:
  ```kotlin
  val total = 100
  run {
      val total = 200 // Shadowing: membingungkan pembaca kode
      println(total)  // Mencetak 200
  }
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Bytecode Autoboxing:**
   - Buat file Kotlin dengan fungsi yang menjumlahkan elemen dalam `IntArray` vs `Array<Int>`.
   - Lakukan kompilasi manual menggunakan terminal: `kotlinc PerformanceTest.kt -include-runtime -d PerformanceTest.jar`
   - Buka bytecode menggunakan perintah `javap -c PerformanceTestKt` atau tools *Show Kotlin Bytecode -> Decompile* di IntelliJ IDEA. 
   - Analisis di mana instruksi `java/lang/Integer.valueOf` (boxing) dan `java/lang/Integer.intValue` (unboxing) disisipkan.

2. **Deteksi Shallow vs Deep Copy:**
   - Rancang sebuah `data class Engine(var rpm: Int)` dan `data class Car(val engine: Engine)`.
   - Instansiasi `val car1 = Car(Engine(1000))`, lalu buat `val car2 = car1.copy()`.
   - Ubah `car1.engine.rpm = 3000`. Analisis apa yang terjadi pada nilai `car2.engine.rpm` dan jelaskan pengaruh referensi memori (*memory pointer*) terhadap sifat immutability pada `val`.
