### 1. Konsep & Arsitektur Mendalam

Secara *default*, operasi pada Kotlin Collections (`List`, `Set`, `Map`) dievaluasi secara **Eager** (rakus/langsung). Setiap kali fungsi transformasi seperti `map` atau `filter` dipanggil, runtime akan langsung mengiterasi seluruh elemen dan mengalokasikan koleksi penampung baru (*intermediate collection*) di heap memory. 

Untuk himpunan data kecil, alokasi ini tidak signifikan. Namun, ketika berhadapan dengan data berskala besar (ratusan ribu hingga jutaan entitas, streaming file, atau infinite dataset), evaluasi eager memicu degradasi performa:
1. **Tekanan pada Garbage Collector (GC):** Setiap *chaining method* menciptakan objek list baru yang berumur pendek (*short-lived objects*).
2. **Komputasi Redundan:** Elemen yang seharusnya gugur pada tahap akhir tetap diproses pada tahap awal karena pemrosesan dilakukan per-tahapan (*step-by-step processing*).

```
Eager (Collection):
[Data 1, Data 2, Data 3] ---> filter() ---> [Intermediate List] ---> map() ---> [Result List]
(Horizontal Processing: Setiap langkah menyelesaikan SELURUH elemen sebelum langkah berikutnya)

Lazy (Sequence):
Data 1 ---> filter() ---> map() ---> Result
Data 2 ---> filter() (gugur, stop)
Data 3 ---> filter() ---> map() ---> Result
(Vertical Processing: Setiap elemen mengalir melalui SELURUH pipeline satu per satu)
```

**Kotlin `Sequence`** menerapkan pola evaluasi **Lazy** (tertunda). Komputasi tidak langsung dieksekusi saat fungsi dideklarasikan, melainkan ditangguhkan sampai sebuah **Terminal Operation** (seperti `toList()`, `first()`, `count()`, atau `forEach()`) dipanggil. 

Pipeline `Sequence` terdiri dari dua jenis operasi:
* **Intermediate Operations (Stateless / Stateful):** Mengembalikan instans `Sequence` baru yang membungkus (*decorates*) urutan sebelumnya. Operasi ini bersifat pasif.
  * *Stateless* (contoh: `map`, `filter`): Tidak memerlukan informasi elemen lain.
  * *Stateful* (contoh: `sorted`, `distinct`): Membutuhkan buffering sebagian atau seluruh elemen di memori.
* **Terminal Operations:** Memicu konsumsi data melalui mekanisme *pull-based* (penarikan per elemen).

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan pemrosesan log file server berukuran masif (Multi-Gigabyte) untuk menemukan 3 transaksi gagal pertama dengan status error tertentu tanpa memuat seluruh file ke dalam RAM.

```kotlin
import java.io.File

data class LogEntry(
    val timestamp: String,
    val severity: String,
    val message: String,
    val responseTimeMs: Long
)

fun parseLogLine(line: String): LogEntry? {
    // Format simulasi: TIMESTAMP|SEVERITY|MESSAGE|RESPONSE_TIME
    val parts = line.split("|")
    if (parts.size < 4) return null
    return LogEntry(
        timestamp = parts[0],
        severity = parts[1],
        message = parts[2],
        responseTimeMs = parts[3].toLongOrNull() ?: 0L
    )
}

fun main() {
    val logFile = File("access_large.log")

    // useLines() membaca file baris demi baris menggunakan BufferedReader
    // dan mengembalikan Sequence<String> yang otomatis menutup resource I/O (AutoCloseable).
    val slowCriticalErrors: List<String> = logFile.useLines { linesSequence ->
        linesSequence
            .mapNotNull { line -> parseLogLine(line) } // Intermediate (Stateless)
            .filter { entry -> entry.severity == "CRITICAL" } // Intermediate (Stateless)
            .filter { entry -> entry.responseTimeMs > 2000L } // Intermediate (Stateless)
            .map { entry -> "[${entry.timestamp}] ALERT: ${entry.message} (${entry.responseTimeMs}ms)" } // Intermediate
            .take(3) // Intermediate (Short-circuiting limiter)
            .toList() // Terminal Operation: Memicu pemrosesan stream
    }

    slowCriticalErrors.forEach(::println)

    // Contoh: Infinite Sequence dengan state machine generator
    val fibonacciSequence: Sequence<Long> = sequence {
        var terms = Pair(0L, 1L)
        while (true) {
            yield(terms.first) // Menghentikan eksekusi sementara dan mengembalikan nilai (coroutine suspension)
            terms = Pair(terms.second, terms.first + terms.second)
        }
    }

    // Hanya menghitung hingga elemen ke-10 lalu berhenti total
    val first10Fib = fibonacciSequence.take(10).toList()
    println("Fibonacci: $first10Fib")
}
```

#### Penjelasan Operasi Kunci:
1. `File.useLines()`: Berbeda dengan `File.readLines()` yang mengembalikan `List<String>` (langsung membaca seluruh file ke RAM dan memicu `OutOfMemoryError` pada file besar), fungsi ini memetakan stream I/O langsung ke `Sequence`.
2. `take(3)`: Bertindak sebagai mekanisme *short-circuit*. Segera setelah kondisi ke-3 terpenuhi, iterator berhenti menarik data ke bawah, memutus pembacaan baris file berikutnya secara instan.
3. `sequence { yield(...) }`: Menggunakan builder berbasis Kotlin Coroutines suspension untuk membangun sequence tak terbatas (*infinite sequence*) dengan alokasi heap minimal.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Pola Dekorasi Iterator
Saat Anda menulis rantai operasi:
```kotlin
sequence.filter { it % 2 == 0 }.map { it * 2 }
```
Compiler dan runtime **tidak menjalankan filter atau map saat itu juga**. Sebaliknya, compiler menginisialisasi rantai objek wrapper:
1. Pemanggilan `.filter { ... }` membungkus target sequence ke dalam instance `FilteringSequence(this, predicate)`.
2. Pemanggilan `.map { ... }` membungkus `FilteringSequence` tersebut ke dalam `TransformingSequence(this, transform)`.

Kedua kelas ini mengimplementasikan antarmuka `Sequence<T>`, yang intinya hanya memiliki satu method abstrak:
```kotlin
public interface Sequence<out T> {
    public operator fun iterator(): Iterator<T>
}
```

Ketika Terminal Operation (misal: `toList()`) dipanggil:
1. `toList()` meminta iterator terluar: `TransformingSequence.iterator()`.
2. Iterator tersebut meminta elemen dari iterator di dalamnya: `FilteringSequence.iterator()`.
3. `FilteringSequence` mengiterasi source sampai predikat menghasilkan `true`, lalu melempar elemen tersebut ke `TransformingSequence`.
4. `TransformingSequence` menjalankan fungsi transform dan menyerahkan nilai akhir ke accumulator milik `toList()`.

Ini adalah representasi klasik dari **Pull-based Stream Pipeline**.

#### Alokasi Memori / Resource
* **Standard Iterable Chaining:** Jika terdapat 4 operasi chaining pada `List` dengan 1.000.000 elemen, runtime akan mengalokasikan 4 instans `ArrayList` perantara di memori. Ukuran heap melonjak drastis, memicu *stop-the-world* GC pause.
* **Sequence Chaining:** Memori tambahan yang dialokasikan adalah konstan ($O(1)$) untuk intermediate stateless pipeline. Elemen diproses dan dibuang/ditampung satu persatu. Tidak ada array penyangga sementara.

#### Trade-offs & Performance Penalty
Sequence **bukan** pengganti permanen untuk Collections:
* **Overhead Instansiasi Iterator:** Sequence membungkus komputasi dalam kelas `Iterator` baru dengan *megamorphic virtual method calls* (`hasNext()`, `next()`).
* **Cache Locality:** Array flat (`ArrayList`) sangat ramah terhadap CPU L1/L2 data cache karena alokasi memori kontigu. Navigasi melalui beberapa rantai iterator pada sequence menyebabkan *indirect jumps* yang mengurangi efisiensi JIT compiler dalam melakukan *inlining* dan vektorisasi CPU SIMD.
* **Ambruk pada Koleksi Kecil:** Untuk dataset kecil (misalnya di bawah 100 elemen), overhead alokasi objek sequence dan virtual calls jauh lebih lambat daripada alokasi satu atau dua `ArrayList` sementara.

### 4. Best Practices & Common Pitfalls

#### Do's:
- **Gunakan untuk Chained Operations Besar:** Gunakan `asSequence()` jika data berukuran besar ($> 1.000$ elemen) dan memiliki rantai operasi transformasi lebih dari satu (misal: `filter` + `map` + `drop`).
- **Gunakan untuk Short-Circuit Operations:** Sangat direkomendasikan jika target pencarian berada di awal dataset (contoh: `find`, `first`, `any`, `take`).
- **Manfaatkan I/O Streaming:** Selalu gunakan `useLines()` alih-alih `readLines()` ketika membaca file teks yang tidak diketahui batas ukurannya.

#### Don'ts:
- **Jangan gunakan Sequence untuk operasi tunggal:** Operasi `list.asSequence().filter { ... }.toList()` hanya menambah overhead objek wrapper tanpa memberikan keuntungan alokasi memori apapun dibanding langsung memanggil `list.filter { ... }`.
- **Hindari re-iterasi Sequence yang bersumber dari One-Shot Source:** Sequence yang membaca stream (seperti file I/O atau socket network) hanya dapat diiterasi **satu kali**. Mengiterasinya untuk kedua kali akan menghasilkan `IllegalStateException` atau kegagalan stream tertutup.
- **Hati-hati dengan Sub-Sequence Tanpa Terminal:** Menghasilkan Sequence dari method internal tanpa mendokumentasikannya dapat menjebak pemanggil method untuk mengeksekusi pipeline lambat berkali-kali.

#### Edge Cases & Stateful Traps:
Hati-hati dengan operasi stateful seperti `.sorted()` atau `.sortedWith()`.
```kotlin
// BAHAYA: sorted() membatalkan efisiensi lazy memory!
val result = hugeSequence
    .filter { it.isValid }
    .sortedBy { it.id } // Runtime HARUS mengumpulkan SELURUH elemen ke memori internal untuk sorting!
    .take(5)
    .toList()
```
Operasi `sorted()` bertindak sebagai **barrier**: Ia memblokir konsumsi lazy dan harus memuat seluruh sisa elemen sequence ke dalam buffer internal sebelum elemen pertama dapat dialirkan ke operasi berikutnya (`take(5)`).

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Profiling Memori:** Buat sebuah program yang memuat 10.000.000 integer. Terapkan pipeline 3 kali filter dan 1 kali map. Bandingkan profil alokasi memori (heap size) dan durasi eksekusi antara pendekatan `List` vs `Sequence` menggunakan Java Flight Recorder (JFR) atau profiler bawaan IDE (IntelliJ Profiler).
2. **Implementasi Custom Chunking/Batching Sequence:** Menggunakan fungsi builder `sequence { ... }`, buat sebuah extension function `fun <T> Sequence<T>.batch(batchSize: Int): Sequence<List<T>>` yang mengelompokkan elemen stream menjadi list-list kecil berukuran `batchSize` secara on-the-fly tanpa menahan seluruh elemen sequence di dalam memori.
3. **Deteksi Stateful Trap:** Buat pengujian untuk membuktikan bahwa urutan penempatan intermediate operation berpengaruh drastis terhadap performa. Bandingkan eksekusi:
   * Sequence: `.sortedBy { ... }.take(10)` vs `.take(100).sortedBy { ... }.take(10)`
   Amati mengapa penempatan `take()` sebelum barrier stateful mengubah kompleksitas waktu secara radikal.
