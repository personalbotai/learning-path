### 1. Konsep & Arsitektur Mendalam

*Static Code Analysis* adalah metode evaluasi kode sumber tanpa mengeksekusi program. Di ekosistem Kotlin, dua instrumen standar industri yang saling melengkapi adalah **Ktlint** dan **Detekt**. Keduanya beroperasi pada level abstraksi yang berbeda untuk menjamin konsistensi gaya (*formatting*) dan kesehatan arsitektural (*code smell & bug detection*).

```
                      +-----------------------------+
                      |      Kotlin Source Code     |
                      +--------------+--------------+
                                     |
                       Kotlin Compiler Frontend (PSI)
                                     |
               +---------------------+---------------------+
               |                                           |
               v                                           v
      +-----------------+                         +-----------------+
      |     Ktlint      |                         |     Detekt      |
      +-----------------+                         +-----------------+
      | - Style Linter  |                         | - Smell Linter  |
      | - AST Parsing   |                         | - PSI + Binding |
      | - Auto-format   |                         | - Metric & Cost |
      +-----------------+                         +-----------------+
               |                                           |
               v                                           v
      Formatting Cleanliness                      Architectural Safety
```

#### Ktlint: Anti-Bikeshedding Formatter
Ktlint dirancang dengan filosofi *zero-configuration* (walaupun mendukung `.editorconfig`). Tujuannya adalah mengeliminasi perdebatan gaya penulisan kode (*bikeshedding*).
- **Mekanisme**: Ktlint mem-parsing kode Kotlin menjadi AST (*Abstract Syntax Tree*) menggunakan parser bawaan compiler Kotlin (`kotlin-compiler-embeddable`).
- **Fokus**: Indentasi, spasi, penamaan variabel (dasar), impor yang tidak terpakai, dan pemecahan baris. Ktlint menyediakan mekanisme *linter* sekaligus *formatter* otomatis (`ktlintFormat`).

#### Detekt: Code Smell & Complexity Analyzer
Detekt berfokus pada deteksi masalah semantik, kompleksitas kode, dan potensi celah performa/keamanan.
- **Mekanisme**: Detekt memanfaatkan Kotlin **PSI (Program Structure Interface)**. Berbeda dengan AST biasa, PSI adalah pohon sintaksis kaya hierarki yang mempertahankan relasi semantik antarelemen kode.
- **Detekt dengan Type Resolution**: Mode analisis penuh di mana Detekt mengakses *Classpath* proyek dan mengkompilasi sebagian kode untuk menghasilkan `BindingContext`. Ini memungkinkan analisis lintas modul, verifikasi tipe aktual variabel, serta penurunan *false positive*.
- **Fokus**: Metrik kompleksitas (*Cyclomatic Complexity*, *Cognitive Complexity*, *Halstead*), penanganan error buruk (*swallowed exceptions*), penggunaan fitur bahasa yang sub-optimal (misal: penggunaan operator yang memicu alokasi tersembunyi), dan implementasi *custom rule* berbasis aturan arsitektural internal tim.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah integrasi modern Detekt dan Ktlint menggunakan Gradle Kotlin DSL (`build.gradle.kts`), serta pembuatan *Custom Detekt Rule* untuk mencegah eksekusi operasi blocking di dalam Coroutine Dispatcher yang salah.

#### 1. Konfigurasi Gradle (`build.gradle.kts`)

```kotlin
plugins {
    kotlin("jvm") version "1.9.22"
    id("io.gitlab.arturbosch.detekt") version "1.23.5"
    id("org.jlleitschuh.gradle.ktlint") version "12.1.0"
}

detekt {
    toolVersion = "1.23.5"
    buildUponDefaultConfig = true
    allRules = false // true: paksa mengaktifkan aturan eksperimental
    config.setFrom(files("$rootDir/config/detekt/detekt.yml"))
    baseline = file("$rootDir/config/detekt/baseline.xml")
}

// Konfigurasi Type Resolution untuk Detekt
tasks.withType<io.gitlab.arturbosch.detekt.Detekt>().configureEach {
    jvmTarget = "21"
    reports {
        xml.required.set(true)
        html.required.set(true)
        sarif.required.set(true) // Berguna untuk GitHub Code Scanning
    }
    // Mengaktifkan Type Resolution dengan menyuplai classpath dan source
    classpath.setFrom(project.configurations.getByName("compileClasspath"))
}

ktlint {
    version.set("1.2.1")
    debug.set(false)
    verbose.set(true)
    android.set(false)
    outputToConsole.set(true)
    ignoreFailures.set(false)
    filter {
        exclude("**/generated/**")
    }
}
```

#### 2. Implementasi Custom Detekt Rule: Larangan Memanggil `Thread.sleep()`

Aturan ini mendeteksi pemanggilan fungsi blocking `Thread.sleep()` di dalam kode Kotlin dan menyarankan penggunaan coroutine `delay()`.

```kotlin
package com.rules.detekt

import io.gitlab.arturbosch.detekt.api.CodeSmell
import io.gitlab.arturbosch.detekt.api.Config
import io.gitlab.arturbosch.detekt.api.Debt
import io.gitlab.arturbosch.detekt.api.Entity
import io.gitlab.arturbosch.detekt.api.Issue
import io.gitlab.arturbosch.detekt.api.Rule
import io.gitlab.arturbosch.detekt.api.Severity
import org.jetbrains.kotlin.psi.KtCallExpression
import org.jetbrains.kotlin.psi.KtDotQualifiedExpression
import org.jetbrains.kotlin.resolve.BindingContext

class AvoidThreadSleepRule(config: Config = Config.empty) : Rule(config) {

    override val issue = Issue(
        id = "AvoidThreadSleep",
        severity = Severity.Performance,
        description = "Jangan menggunakan Thread.sleep(). Gunakan non-blocking delay() jika dalam coroutine.",
        debt = Debt.FIVE_MINS
    )

    override fun visitDotQualifiedExpression(expression: KtDotQualifiedExpression) {
        super.visitDotQualifiedExpression(expression)

        val receiver = expression.receiverExpression.text
        val selector = expression.selectorExpression

        // Deteksi pemanggilan statis: Thread.sleep(...)
        if (receiver == "Thread" && selector is KtCallExpression) {
            val calleeName = selector.calleeExpression?.text
            if (calleeName == "sleep") {
                report(
                    CodeSmell(
                        issue = issue,
                        entity = Entity.from(expression),
                        message = "Deteksi pemanggilan `Thread.sleep()`. Operasi ini memblokir thread thread worker, gunakan `delay()` atau Dispatchers.IO."
                    )
                )
            }
        }
    }
}
```

#### 3. Provider untuk Mendaftarkan Custom Rule

```kotlin
package com.rules.detekt

import io.gitlab.arturbosch.detekt.api.RuleSet
import io.gitlab.arturbosch.detekt.api.RuleSetProvider

class CustomRuleSetProvider : RuleSetProvider {
    override val ruleSetId: String = "enterprise-rules"

    override fun instance(config: io.gitlab.arturbosch.detekt.api.Config): RuleSet {
        return RuleSet(
            ruleSetId,
            listOf(
                AvoidThreadSleepRule(config)
            )
        )
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: PSI Traversal via Visitor Pattern
Baik Detekt maupun Ktlint tidak mengevaluasi *bytecode* JVM (`.class`), melainkan beroperasi langsung pada fase pemrosesan sintaksis compiler Kotlin.

```
Source File (.kt)
       │
       ▼
[Kotlin Core Environment]
       │
       ├─ Lexer/Tokenizer (Token Stream: IDENTIFIER, LBRACE, etc.)
       │
       ▼
[Kotlin Parser] ──► Mengonstruksi AST
       │
       ▼
[Program Structure Interface (PSI)] ──► Hirarki Node Semantik (KtFile, KtNamedFunction)
       │
       ├─► [Ktlint Visitor]: Menghitung whitespace & urutan token lexer
       │
       └─► [Detekt Visitor]: Mengevaluasi kompleksitas branch & node expressions
```

1. **Inisialisasi Compiler Engine**: Detekt membungkus `KotlinCoreEnvironment` untuk menginisialisasi lingkungan parser tanpa perlu menghasilkan file *binary*.
2. **Visitor Pattern**: Detekt mengimplementasikan `KtTreeVisitorVoid` (bagian dari Kotlin Compiler API). Detekt melakukan traversing (penelusuran) pohon PSI secara mendalam (*depth-first search*). Setiap kali parser menemukan node tertentu (misalnya `KtClass`, `KtNamedFunction`, atau `KtTryExpression`), callback yang bersesuaian pada `Rule` akan dieksekusi.
3. **Type Resolution via BindingContext**: Jika diaktifkan, Detekt mengeksekusi analisis frontend Kotlin compiler secara utuh. Compiler menghasilkan `BindingContext`, sebuah *lookup table* raksasa yang memetakan elemen PSI ke tipe data compile-time (`KotlinType`), referensi *descriptor*, dan *scope* simbolis. Hal ini memungkinkan Detekt memastikan apakah suatu metode `.get()` milik `java.util.Map` atau struktur data buatan sendiri.

#### Alokasi Memori & Resource
- **Overhead Tanpa Type Resolution**: Detekt hanya memuat model PSI dari file teks ke memori. Penggunaan memori berkisar antara 200MB - 500MB untuk repositori menengah.
- **Overhead Dengan Type Resolution**: Membutuhkan alokasi memori heap JVM signifikan (1.5GB - 4GB+). Compiler harus menyelesaikan seluruh *classpath*, dependensi biner JAR eksternal, dan membentuk `BindingContext`. Hal ini menuntut pipeline CI/CD mengalokasikan parameter JVM yang memadai: `-Xmx4g -XX:+UseG1GC`.

#### Trade-offs
| Parameter | Ktlint | Detekt (Syntactic Only) | Detekt (Type Resolution) |
| :--- | :--- | :--- | :--- |
| **Kecepatan Analisis** | Sangat Cepat (< 5s) | Cepat (~10-20s) | Lambat (bisa setara durasi kompilasi) |
| **Kebutuhan Memori** | Rendah (~256MB) | Rendah (~512MB) | Tinggi (2GB - 8GB) |
| **Akurasi Semantik** | Sangat Rendah | Menengah (Batas file lokal) | Sangat Tinggi (Lintas modul/dependensi) |
| **Auto-Fix** | Ya (Sangat baik) | Sangat Terbatas | Tidak (Hanya pelaporan) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Manfaatkan `.editorconfig` Sebagai Sumber Kebenaran Tunggal**: Ktlint mendukung pembacaan konfigurasi indentasi, panjang baris (`max_line_length`), dan trailing comma dari `.editorconfig`. Integrasikan ini langsung agar konsisten dengan format bawaan IntelliJ IDEA.
- **Integrasikan Pre-commit Hook**: Pasang Ktlint pada Git Hook lokal via tool seperti `Husky` atau script shell `pre-commit`. Format otomatis harus terjadi di mesin developer sebelum kode dikirim ke upstream remote.
- **Gunakan Baseline untuk Legacy Code**: Jangan mencoba memperbaiki puluhan ribu pelanggaran aturan Detekt sekaligus pada kode lawas (*code debt*). Gunakan fitur `detektBaseline`. Ini mengunci pelanggaran lama ke dalam file XML, sehingga tim dapat fokus menerapkan standar baru secara ketat hanya pada baris kode yang baru ditulis atau diubah.

#### Don'ts
- **Menonaktifkan Aturan Secara Brutal Melalui `@Suppress`**:
  ```kotlin
  // JANGAN: Menyembunyikan masalah tanpa alasan arsitektural yang jelas
  @Suppress("TooGenericExceptionCaught", "ComplexMethod", "NestedBlockDepth")
  fun handleOrder() { /* 100 baris logika kacau */ }
  ```
  Jika `@Suppress` benar-benar terpaksa digunakan, sertakan justifikasi teknis dan batasi scope penekanan sekecil mungkin (pada variabel/ekspresi lokal, bukan pada level *class* atau *file*).
- **Mencampuradukkan Peran Linter**: Jangan gunakan Detekt untuk mengatur indentasi/spasi (meskipun Detekt memiliki modul *formatting* yang mengemas Ktlint). Gunakan *official* Ktlint Gradle Plugin untuk formatting dan serahkan analisis semantik kompleksitas murni kepada Detekt.

#### Edge Cases
- **False Positives pada Jetpack Compose**: Fungsi `@Composable` sering kali melanggar aturan konvensional Detekt. Fungsi Compose sering kali diawali huruf kapital (melanggar `FunctionNaming`), tidak mengembalikan nilai secara eksplisit (melanggar `MagicNumber` pada alur UI), atau memiliki parameter yang banyak (melanggar `LongParameterList`).
  *Mitigasi*: Konfigurasikan `detekt.yml` untuk mengabaikan fungsi dengan anotasi `@Composable`:
  ```yaml
  naming:
    FunctionNaming:
      ignoreAnnotated: ['Composable']
  complexity:
    LongParameterList:
      ignoreAnnotatedParameter: ['Composable']
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Audit Cyclomatic vs Cognitive Complexity**:
   Ubah konfigurasi Detekt (`detekt.yml`) pada proyek Anda untuk mengaktifkan aturan `CognitiveComplexMethod` dengan batas ambang (*threshold*) 10. Ambil salah satu method kompleks dalam codebase Anda, analisis bagaimana struktur kontrol bercabang (*branching* dan *nested loops*) menaikkan skor kognitif tersebut, lalu lakukan refactoring menggunakan teknik *early returns* atau *polymorphic dispatch*.
2. **Pembuatan Custom Rule Berbasis Anotasi Domain**:
   Tulis sebuah custom rule Detekt bernama `MandatoryRepositoryAnnotationRule`. Rule ini harus mengecek apakah setiap kelas yang memiliki nama berakhiran `Repository` (misal: `UserRepository`) memiliki custom annotation internal `@ThreadSafe`. Jika kelas tersebut berakhiran `Repository` namun tidak memiliki anotasi tersebut, lemparkan `CodeSmell`. Uji rule tersebut menggunakan library pengetesan Detekt: `detekt-test`.
