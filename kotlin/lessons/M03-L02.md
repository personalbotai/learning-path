## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Pemrosesan koleksi secara fungsional di Kotlin berpusat pada transformasi data immutabel: alih-alih memodifikasi struktur data secara *in-place* melalui iterasi imperatif (`for`/`while`), kita memproyeksikan data ke bentuk baru menggunakan fungsi tingkat tinggi (*higher-order functions*). Kotlin Standard Library menyediakan operator deklaratif seperti `map`, `filter`, `flatMap`, `reduce`, dan `fold` sebagai *extension functions* pada interface `Iterable<T>`.

Secara arsitektural, terdapat dua paradigma evaluasi operasi koleksi di Kotlin:
1. **Eager Evaluation (Standard Collections):** Setiap pemanggilan operator pada `List`, `Set`, atau `Map` langsung dieksekusi secara instan. Tiap tahapan pipeline menghasilkan koleksi *intermediary* (sementara) baru di heap memory.
2. **Lazy Evaluation (`Sequence<T>`):** Pemrosesan ditunda hingga sebuah *terminal operation* dipanggil. Data diproses elemen demi elemen (*vertical evaluation*), meminimalkan alokasi koleksi perantara.

Masing-masing operator memiliki peran komputasi spesifik:
- **`filter`**: Memproyeksikan subset elemen yang memenuhi predikat `(T) -> Boolean`. Ukuran output $\le$ ukuran input ($N \to M$ di mana $M \le N$).
- **`map`**: Mentransformasikan setiap elemen bertipe `T` menjadi tipe `R` melalui fungsi transformasi `(T) -> R`. Ukuran output selalu sama dengan input ($N \to N$).
- **`flatMap`**: Menggabungkan dua operasi: pemetaan elemen `T` menjadi koleksi baru `Iterable<R>`, diikuti dengan perataan (*flattening*) hasil menjadi satu list dimensi tunggal `List<R>` ($N \to M$).
- **`fold` & `reduce`**: Mengakumulasikan seluruh koleksi menjadi satu nilai skalar/objek tunggal. `fold` menerima nilai awal (*initial accumulator*), sedangkan `reduce` menggunakan elemen pertama koleksi sebagai nilai awal dan melempar pengecualian jika koleksi kosong.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Memproses riwayat transaksi perbankan untuk mengekstrak total pengeluaran per kategori, memfilter transaksi mencurigakan, dan mengagregasi ringkasan data finansial.

```kotlin
data class Transaction(
    val id: String,
    val tags: List<String>,
    val amount: Double,
    val isFlagged: Boolean
)

data class AccountSummary(
    val totalProcessedAmount: Double,
    val transactionCount: Int
)

fun main() {
    val transactions = listOf(
        Transaction("TX-001", listOf("groceries", "food"), 150.0, isFlagged = false),
        Transaction("TX-002", listOf("electronics", "tech"), 1200.0, isFlagged = true),
        Transaction("TX-003", listOf("utilities"), 80.0, isFlagged = false),
        Transaction("TX-004", listOf("food", "dining"), 45.0, isFlagged = false)
    )

    // 1. FILTER: Ambil hanya transaksi yang valid (tidak diflag)
    val validTransactions: List<Transaction> = transactions.filter { !it.isFlagged }

    // 2. MAP: Ambil nominal transaksi yang valid
    val amounts: List<Double> = validTransactions.map { it.amount }

    // 3. FLATMAP: Ekstrak seluruh tag unik dari transaksi valid
    val uniqueTags: Set<String> = validTransactions
        .flatMap { it.tags }
        .toSet()

    // 4. REDUCE: Hitung total transaksi (Aman hanya jika koleksi dipastikan tidak kosong)
    val totalAmountReduced: Double = amounts.reduce { acc, amount -> acc + amount }

    // 5. FOLD: Agregasi kompleks ke tipe data baru (AccountSummary) dengan initial value aman
    val summary: AccountSummary = transactions
        .filter { !it.isFlagged }
        .fold(AccountSummary(totalProcessedAmount = 0.0, transactionCount = 0)) { acc, tx ->
            acc.copy(
                totalProcessedAmount = acc.totalProcessedAmount + tx.amount,
                transactionCount = acc.transactionCount + 1
            )
        }

    println("Unique Tags: $uniqueTags")
    println("Total via Reduce: $$totalAmountReduced")
    println("Summary via Fold: $summary")
}
```

#### Penjelasan Komponen Kunci:
- `flatMap { it.tags }`: Mengubah `Transaction` menjadi `List<String>`, lalu membongkar dan menggabungkannya ke dalam satu `List<String>` datar alih-alih `List<List<String>>`.
- `reduce { acc, amount -> ... }`: Tipe akumulator dan tipe elemen *harus identik* (`Double`). Jika `amounts` kosong, runtime akan melempar `UnsupportedOperationException`.
- `fold(initial) { acc, tx -> ... }`: Mengizinkan tipe akumulator (`AccountSummary`) berbeda dari tipe elemen koleksi (`Transaction`). Aman digunakan pada koleksi kosong (akan mengembalikan *initial value*).

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Sebagian besar operator transformasi pada `Iterable` diimplementasikan sebagai `inline` function di Kotlin Standard Library:

```kotlin
// Simplifikasi implementasi map pada Kotlin Standard Library
public inline fun <T, R> Iterable<T>.map(transform: (T) -> R): List<R> {
    return mapTo(ArrayList<R>(collectionSizeOrDefault(10)), transform)
}
```

Karena dideklarasikan sebagai `inline`, compiler Kotlin tidak membuat instance objek anonim `Function1` (`Function<T, R>`) di heap untuk lambda yang diberikan. Sebagai gantinya, bytecode dari fungsi `transform` disisipkan langsung ke call-site di dalam loop `for` standar.

#### Alokasi Memori & Resource
- **Koleksi Menengah (Intermediate Collections):**
  Rantai pemanggilan eager:
  ```kotlin
  list.filter { ... }.map { ... }
  ```
  Menghasilkan *alokasi memori berulang*. `filter` mengalokasikan instance `ArrayList` baru di heap. Kemudian `map` mengalokasikan instance `ArrayList` kedua. Pada data berukuran besar, alokasi objek sementara ini memicu tekanan GC (*Garbage Collection pressure*) yang signifikan.
- **Pre-allocation Optimization:**
  Fungsi internal `mapTo` mengestimasi kapasitas awal `ArrayList` menggunakan `collectionSizeOrDefault(10)`. Ini meminimalkan *array resizing* (penyalinan array internal saat kapasitas terlampaui), namun tidak mengeliminasi alokasi list itu sendiri.

#### Trade-offs: Collections vs. Sequences
| Karakteristik | `Iterable<T>` (Eager) | `Sequence<T>` (Lazy) |
| :--- | :--- | :--- |
| **Model Evaluasi** | Horizontal (seluruh elemen per tahap) | Vertikal (satu elemen melalui seluruh tahap) |
| **Alokasi Intermediary**| Ya (satu koleksi baru per langkah) | Nol (state disimpan dalam iterator state machine) |
| **Inlining** | Fungsi di-*inline* secara langsung | Fungsi **tidak** di-*inline* (overhead closure object) |
| **Performa Data Kecil**| Sangat cepat (overhead loop minimal) | Lebih lambat karena overhead instansiasi sequence |
| **Performa Data Besar**| Lambat (tekanan alokasi heap & GC) | Jauh lebih cepat dan hemat memori |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `fold` daripada `reduce` secara default:** `fold` secara eksplisit mendefinisikan *initial state* dan kebal terhadap crash akibat koleksi kosong.
- **Manfaatkan `asSequence()` untuk pipeline panjang pada dataset besar:** Jika pipeline memiliki $\ge 3$ rantai transformasi dan data berukuran ribuan elemen, ubah menjadi Sequence terlebih dahulu:
  ```kotlin
  transactions.asSequence()
      .filter { !it.isFlagged }
      .map { it.amount }
      .toList()
  ```
- **Gunakan fungsi agregasi terdedikasi bila tersedia:** Hindari `reduce { a, b -> a + b }` jika dapat menggunakan `sumOf { it.amount }` atau `sum()` yang lebih teroptimasi tanpa boxing primitif tambahan.

#### Don'ts
- **Hindari `reduce` pada koleksi yang berpotensi kosong:**
  ```kotlin
  // CRASH jika list kosong: java.lang.UnsupportedOperationException: Empty collection can't be reduced.
  val total = emptyList<Double>().reduce { acc, v -> acc + v }
  
  // SOLUSI: Gunakan reduceOrNull atau fold
  val safeTotal = emptyList<Double>().reduceOrNull { acc, v -> acc + v } ?: 0.0
  ```
- **Jangan gunakan `flatMap` jika hanya ingin meratakan struktur tanpa pemetaan:** Gunakan `flatten()` secara langsung jika koleksi sudah berbentuk nested (`List<List<T>>`).
- **Hindari operasi mutasi di dalam lambda:** Menulis kode seperti `filter { list.add(it); true }` melanggar prinsip *pure functions*, menyebabkan *side-effects*, dan merusak keamanan thread (*thread safety*).

#### Edge Cases
- **Operasi Objek Akumulator Immutabel pada `fold`:**
  Membuat objek baru pada setiap iterasi `fold` (seperti `acc.copy(...)` pada dataset berjuta-juta) dapat menimbulkan lonjakan alokasi objek sementara. Untuk performa ekstrem, gunakan mutasi lokal terisolasi (*in-place accumulator*) di dalam builder atau loop imperatif.

### 5. Tantangan Eksplorasi Mandiri

1. **Dekonstruksi Bytecode**: Tulis fungsi sederhana dengan rantai `.filter { ... }.map { ... }`. Buka via IntelliJ IDEA (`Tools -> Kotlin -> Show Kotlin Bytecode`), lakukan *Decompile to Java*, lalu analisis bagaimana kompilator menyisipkan kode lambda inline tersebut ke dalam loop reguler tanpa instansiasi class anonim.
2. **Benchmark Heap Allocations**: Buat list berisi $1.000.000$ integer. Jalankan transformasi:
   - Menggunakan standard `Iterable` (`map`, `filter`).
   - Menggunakan `asSequence()`.
   Ukur penggunaan memory heap menggunakan profiler (atau `Runtime.getRuntime()`) dan catat perbedaan konsumsi alokasi memorinya.
3. **Implementasi `fold` Custom**: Tanpa menggunakan fungsi bawaan library, buatlah generic extension function `fun <T, R> Iterable<T>.customFold(initial: R, operation: (acc: R, T) -> R): R` dengan penandaan keyword `inline` yang tepat. Buktikan fungsi Anda menangani list kosong tanpa melempar exception.
