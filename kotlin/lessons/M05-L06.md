### 1. Konsep & Arsitektur Mendalam

Dalam paradigma pemrograman fungsional murni, fungsi adalah *first-class citizen* dengan aritas (jumlah parameter) matematika yang kaku. Di ekosistem Kotlin—meskipun bukan bahasa fungsional murni—kita dapat mengadopsi dua teknik dekomposisi fungsi tingkat lanjut: **Currying** dan **Partial Application**. Keduanya sering disalahartikan sebagai konsep yang sama, padahal memiliki semantik arsitektur yang berbeda secara fundamental.

```
Fungsi Asal:        f(a, b, c) -> R
---------------------------------------------------------------------------------
Currying:           f(a) -> (f(b) -> (f(c) -> R))      // Arity n diubah jadi n fungsi ber-arity 1
Partial Application: f_partial(b, c) = f(konstantaA, b, c) // Mengikat k argumen, menyisakan (n-k) arity
```

#### Currying
Currying (dinamai dari matematikawan Haskell Curry) adalah proses transformasi fungsi yang menerima *multiple arguments* $f: (A \times B) \to C$ menjadi rantai fungsi bertingkat (*higher-order functions*) di mana setiap fungsi hanya menerima **tepat satu argumen**: $f_{curried}: A \to (B \to C)$.

Alasan teknis di balik Currying:
1. **Fungsional Komposisi Teoretis:** Memungkinkan fungsi multi-argumen kompatibel secara langsung dengan pipeline operasi unari seperti `map`, `filter`, dan operator komposisi `compose` atau `andThen`.
2. **Penundaan Evaluasi (Deferred Execution):** Anda dapat mengonsumsi argumen satu per satu seiring data tersedia di berbagai lapisan arsitektur tanpa harus mengeksekusi komputasi utama.

#### Partial Application
Partial Application adalah teknik mengambil fungsi dengan aritas $N$, memasok nilai konkret untuk $K$ parameter ($K < N$), dan menghasilkan fungsi baru dengan aritas $N - K$. 

Berbeda dengan Currying yang memaksa setiap langkah hanya menerima satu argumen, Partial Application berfokus pada **spesialisasi fungsi**: mengubah fungsi generik menjadi fungsi spesifik dengan mengikat (*binding*) dependensi atau konfigurasi tetap terlebih dahulu.

Di Kotlin, fitur ini tidak disediakan secara natif melalui *keyword* khusus (seperti operator `_` pada Scala), melainkan diabstraksikan melalui **Higher-Order Functions**, **Extension Functions**, dan **Lambda Expressions**.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi generik utilitas Currying & Partial Application, diikuti dengan skenario nyata: sistem kalkulasi pajak dan diskon faktur berbasis konfigurasi regional.

```kotlin
package functional.currying

// ==========================================
// 1. GENERIC UTILITIES
// ==========================================

// Currying untuk 2 dan 3 argumen
fun <P1, P2, R> ((P1, P2) -> R).curry(): (P1) -> (P2) -> R =
    { p1 -> { p2 -> this(p1, p2) } }

fun <P1, P2, P3, R> ((P1, P2, P3) -> R).curry(): (P1) -> (P2) -> (P3) -> R =
    { p1 -> { p2 -> { p3 -> this(p1, p2, p3) } } }

// Uncurrying: Mengembalikan fungsi rantai ke fungsi multi-argumen
fun <P1, P2, R> ((P1) -> (P2) -> R).uncurry(): (P1, P2) -> R =
    { p1, p2 -> this(p1)(p2) }

// Partial Application: Mengikat argumen pertama
fun <P1, P2, R> ((P1, P2) -> R).partial(p1: P1): (P2) -> R =
    { p2 -> this(p1, p2) }

fun <P1, P2, P3, R> ((P1, P2, P3) -> R).partial(p1: P1): (P2, P3) -> R =
    { p2, p3 -> this(p1, p2, p3) }

fun <P1, P2, P3, R> ((P1, P2, P3) -> R).partial(p1: P1, p2: P2): (P3) -> R =
    { p3 -> this(p1, p2, p3) }


// ==========================================
// 2. KASUS NYATA: Domain Engine Penagihan
// ==========================================

data class TaxRate(val countryCode: String, val vatPercentage: Double)
data class DiscountTier(val tierName: String, val multiplier: Double)
data class InvoiceItem(val sku: String, val basePrice: Double, val quantity: Int)

object BillingEngine {
    // Fungsi inti: Arity-3 (TaxRate, DiscountTier, InvoiceItem) -> Double
    val calculateFinalPrice: (TaxRate, DiscountTier, InvoiceItem) -> Double = 
        { tax, discount, item ->
            val subtotal = item.basePrice * item.quantity
            val discounted = subtotal * (1.0 - discount.multiplier)
            val totalWithVat = discounted * (1.0 + (tax.vatPercentage / 100.0))
            // Pembulatan 2 desimal
            Math.round(totalWithVat * 100.0) / 100.0
        }
}

fun main() {
    // Data Context
    val idTax = TaxRate(countryCode = "ID", vatPercentage = 11.0)
    val vipDiscount = DiscountTier(tierName = "VIP", multiplier = 0.15) // Diskon 15%
    val laptop = InvoiceItem(sku = "LPT-001", basePrice = 10_000_000.0, quantity = 1)
    val mouse = InvoiceItem(sku = "MOU-002", basePrice = 250_000.0, quantity = 2)

    // --- Menggunakan Partial Application ---
    // Spesialisasi fungsi kalkulasi khusus untuk Region Indonesia
    val calculateIndoPrice = BillingEngine.calculateFinalPrice.partial(idTax)
    
    // Spesialisasi lanjutan khusus untuk member VIP di Indonesia (Arity-1)
    val calculateIndoVipPrice = calculateIndoPrice.partial(vipDiscount)

    println("Partial Application Result:")
    println("Laptop VIP Price (ID): IDR ${calculateIndoVipPrice(laptop)}")
    println("Mouse VIP Price (ID): IDR ${calculateIndoVipPrice(mouse)}")

    // --- Menggunakan Currying ---
    val curriedCalculation = BillingEngine.calculateFinalPrice.curry()
    
    // Konfigurasi rantai eksekusi
    val idTaxApplied = curriedCalculation(idTax)
    val vipApplied = idTaxApplied(vipDiscount)
    
    val finalPriceLaptop = vipApplied(laptop)
    println("\nCurrying Result:")
    println("Curried Laptop Price: IDR $finalPriceLaptop")

    // Pemanfaatan dalam koleksi fungsional
    val cart = listOf(laptop, mouse)
    val processedTotals = cart.map(vipApplied) // vipApplied berfungsi sebagai (InvoiceItem) -> Double
    println("\nBatch Processed via map(): $processedTotals")
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (JVM Mechanics)
Di platform JVM, fungsi Kotlin tidak direpresentasikan sebagai penunjuk fungsi (*function pointer*) primitif tingkat rendah, melainkan sebagai instansiasi antarmuka bawaan standard library: `kotlin.jvm.functions.FunctionN<P1, ..., PN, R>`.

Ketika fungsi curried dieksekusi:
```kotlin
val f: (A) -> (B) -> C = { a -> { b -> compute(a, b) } }
```
Compiler Kotlin melakukan transformasi sintaksis berikut:
1. `f` adalah objek bertipe `Function1<A, Function1<B, C>>`.
2. Saat `f(a)` dipanggil, runtime memanggil metode virtual `Function1.invoke(a)`.
3. Pemanggilan `f(a)` mengalokasikan dan mengembalikan instansi anonim baru dari `Function1<B, C>`, yang menyimpan variabel `a` di dalam *field* instansi tersebut (variabel *captured*).
4. Saat `f(a)(b)` dipanggil, metode `invoke(b)` pada objek kedua dipanggil, yang kemudian mengakses *captured field* `a` dan parameter `b` untuk menghasilkan `C`.

Bytecode yang dihasilkan melibatkan serangkaian instruksi `CHECKCAST`, `INVOKEVIRTUAL`, dan pembuatan objek closure via alokasi `NEW`:
```bytecode
NEW functional/currying/BillingEngine$curry$1$1
DUP
ALOAD_1 // memuat 'a'
INVOKESPECIAL functional/currying/BillingEngine$curry$1$1.<init> (Ljava/lang/Object;)V
ARETURN // mengembalikan Function1 baru
```

#### Alokasi Memori & Resource
- **Heap Allocation Overhead:** Setiap tingkatan (*step*) dari fungsi curried atau partially applied yang tidak di-*inline* akan mengalokasikan objek baru bertipe `Lambda` (`FunctionX`) di heap.
- **Variable Boxing:** Jika parameter berupa tipe data primitif Kotlin (`Int`, `Double`, `Boolean`), antarmuka generik `FunctionN<P1, R>` memaksa terjadinya **autoboxing** ke objek wrapper Java (`java.lang.Integer`, `java.lang.Double`). Komputasi numerik intensif akan membebani Garbage Collector (GC).

#### Trade-offs
| Aspek | Currying & Partial Application | Fungsi Konvensional / Default Args |
| :--- | :--- | :--- |
| **Fleksibilitas Komposisi** | Sangat Tinggi (Pipeline modular, point-free style) | Rendah (Kaku pada deklarasi awal aritas) |
| **Konsumsi Memori** | Tinggi (Objek closure bertingkat di heap) | Minimal (Frame dialokasikan di thread stack) |
| **Performa Eksekusi** | Lebih lambat (Multiple indirection via `invoke()`, boxing) | Cepat (Direct invocation / inline JIT) |
| **Keterbacaan Debugger** | Stacktrace dalam, penamaan kelas `$lambda$1` | Stacktrace linier dan mudah dilacak |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Gunakan untuk Konfigurasi & Injeksi Dependensi Fungsional:** Gunakan Partial Application untuk mengikat modul konfigurasi database, HTTP client, atau environment token sebelum menyalurkan fungsi pemrosesan bisnis ke lapisan *controller*.
2. **Kombinasikan dengan Pipeline Stream:** Gunakan fungsi yang sudah ter-*curry* secara parsial sebagai argumen langsung untuk operasi `map`, `filter`, dan `reduce` pada `Sequence` atau `List`.
3. **Optimalkan dengan Nilai Konstan:** Lakukan partial application sedini mungkin (di luar loop) agar GC tidak tertekan oleh pembuatan instansi lambda berulang di dalam iterasi loop.

#### Don'ts
1. **Jangan Over-Engineer Kebutuhan Sederhana:** Jika Anda hanya butuh nilai bawaan, gunakan fitur idiomatik Kotlin: **Default Arguments** (`fun compute(a: Int, b: Int = 10)`). Jangan ubah semua fungsi menjadi bentuk Currying hanya demi gaya fungsional murni.
2. **Hindari di Hot-Path (Critical Loop Performance):** Hindari memanggil `.curry()` atau rantai curried function di dalam perulangan jutaan data transaksi per detik karena alokasi closure dan overhead *dynamic dispatch* method `invoke()`.
3. **Jangan Menyalahgunakan Currying untuk Arity Tinggi:** Rantai pemanggilan seperti `fn(a)(b)(c)(d)(e)` menurunkan *readability* kode secara drastis dibanding model DTO/Builder pattern.

#### Common Pitfall & Edge Cases
- **Capturing Mutable State (State Mutation Bug):**
  ```kotlin
  var discount = 0.10
  val applyDiscount = originalPriceFunction.partial(discount)
  
  discount = 0.25 // Perubahan ini TIDAK berpengaruh jika Partial Application meng-copy by-value (primitif)
  // Namun jika meng-capture objek mutable:
  val config = MutableConfig(rate = 0.10)
  val calc = priceFunc.partial(config)
  config.rate = 0.50 // Berbahaya: Efek samping tak terduga terjadi jika lambda membaca referensi state!
  ```
  *Mitigasi:* Pastikan data yang di-capture oleh closure bersifat immutable (`val` dan immutable data class).
- **Stack Overflow pada Recursive Currying:** Jangan membuat rantai currying berbasis rekursi tanpa mengimplementasikan teknik `Tailrec` atau `Trampoline`.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Operator Overloading untuk Partial Application:**
   Buatlah implementasi extension operator `rem` (`%`) atau `invoke` pada fungsi arity-2 dan arity-3 di Kotlin, sehingga Partial Application dapat dipanggil menggunakan sintaks yang sangat ringkas, contohnya:
   ```kotlin
   val add = { a: Int, b: Int -> a + b }
   val addFive = add % 5 // Mengembalikan fungsi (Int) -> Int
   println(addFive(10))  // Output: 15
   ```
   *Eksplorasi:* Analisis batasan sintaksis Kotlin dalam mengabstraksikan operator kustom tersebut untuk jumlah parameter arbitrer.

2. **Dekomposisi Bytecode dengan `javap`:**
   Tulis file Kotlin minimalis yang meng-curry fungsi penjumlahan dua nilai `Int`. Kompilasi menggunakan `kotlinc` dan dekompilasi bytecode-nya menggunakan perintah:
   ```bash
   javap -c -p NamaFileKt.class
   ```
   *Eksplorasi:* Identifikasi berapa banyak objek `Function1` yang dialokasikan, amati instruksi `INVOKESTATIC java/lang/Integer.valueOf (I)Ljava/lang/Integer;` (boxing), dan hitung estimasi *overhead* siklus CPU dibandingkan pemanggilan fungsi top-level non-curried secara langsung.
