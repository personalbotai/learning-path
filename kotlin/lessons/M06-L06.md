### 1. Konsep & Arsitektur Mendalam

Pembatalan (cancellation) pada Kotlin Coroutines bersifat **kooperatif (cooperative)**. Artinya, coroutine runtime tidak secara paksa menghentikan eksekusi thread seperti yang dilakukan oleh metode usang `Thread.stop()` di Java (yang berisiko merusak integritas *state* memori dan memicu *deadlock*). Sebaliknya, sebuah coroutine harus secara aktif memeriksa status pembatalannya dan menyerahkan kendali kembali ke runtime.

#### State Machine pada `Job`
Setiap coroutine direpresentasikan oleh sebuah `Job` yang mengontrol siklus hidupnya. Transisi state pembatalan berjalan sebagai berikut:

```
[ New ] ──> [ Active ] ──(cancel)──> [ Cancelling ] ──> [ Cancelled ]
                 │                          │
              (finish)                  (cleanup)
                 ▼                          ▼
           [ Completing ] ─────────> [ Completed ]
```

1. **Active**: Coroutine sedang berjalan atau siap berjalan.
2. **Cancelling**: Fungsi `job.cancel()` dipanggil. State ini memberi kesempatan bagi coroutine untuk mengeksekusi blok pembersihan (*cleanup/finally*).
3. **Cancelled**: Coroutine telah selesai membersihkan resource dan berhenti secara permanen. Transisi ini dianggap sebagai penyelesaian normal dari perspektif parent coroutine jika penyebabnya adalah `CancellationException`.

#### Mekanisme Propagasi: `CancellationException`
Pembatalan diimplementasikan secara internal menggunakan sebuah exception khusus: `kotlinx.coroutines.CancellationException`.
- Ketika `Job.cancel()` dipanggil, runtime menyuntikkan `CancellationException` ke dalam coroutine target.
- Fungsi *suspending* standar dari library `kotlinx.coroutines` (seperti `delay()`, `yield()`, `await()`) memeriksa status `Job` secara berkala. Jika `Job` berada dalam status *Cancelling*, fungsi suspensi tersebut tidak akan melanjutkan eksekusinya melainkan langsung melempar `CancellationException`.
- Berbeda dari exception biasa, `CancellationException` ditangani secara khusus oleh runtime: exception ini **tidak** membatalkan *parent coroutine* dan **tidak** mencetak crash stack trace ke console/log unhandled exception.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi komprehensif yang mencakup komputasi CPU-bound yang kooperatif, penanganan cleanup yang aman, dan timeout.

```kotlin
import kotlinx.coroutines.*
import java.io.Closeable

// Simulasi Resource yang harus ditutup secara deterministik
class DatabaseConnection : Closeable {
    fun query(step: Int) = "Data chunk #$step"
    override fun close() {
        println("[Resource] Koneksi database berhasil ditutup.")
    }
}

fun main() = runBlocking {
    println("=== 1. Cooperative Cancellation pada CPU-bound Task ===")
    val cpuJob = launch(Dispatchers.Default) {
        var count = 0
        val startTime = System.currentTimeMillis()
        
        // Pola 1: Menggunakan isActive sebagai guard loop
        while (isActive) {
            // Simulasi komputasi intensif
            if (System.currentTimeMillis() >= startTime + (count * 100)) {
                println("Komputasi tahap: ${count++} pada ${Thread.currentThread().name}")
            }
            
            // Pola 2 (Alternatif): ensureActive() atau yield()
            // ensureActive() // Melempar CancellationException seketika jika job dibatalkan
        }
        
        println("Loop selesai secara elegan karena isActive bernilai false.")
    }

    delay(250) // Biarkan berjalan sebentar
    println("Membatalkan cpuJob...")
    cpuJob.cancelAndJoin()

    println("\n=== 2. Safe Cleanup dengan NonCancellable ===")
    val resourceJob = launch(Dispatchers.IO) {
        val db = DatabaseConnection()
        try {
            var step = 1
            while (true) {
                ensureActive() // Titik periksa kooperatif
                println(db.query(step++))
                delay(100) // Suspend point yang responsif terhadap cancellation
            }
        } catch (e: CancellationException) {
            println("[Worker] Menerima sinyal pembatalan: ${e.message}")
            throw e // Sangat penting: jangan telan CancellationException!
        } finally {
            // Blok cleanup standar
            println("[Cleanup] Memulai prosedur pelepasan resource...")
            
            // KASUS KRITIS: Jika butuh suspend function di dalam finally,
            // bungkus dengan withContext(NonCancellable).
            withContext(NonCancellable) {
                delay(50) // Simulasi I/O network saat cleanup (misal: graceful shutdown packet)
                db.close()
                println("[Cleanup] Prosedur selesai di context NonCancellable.")
            }
        }
    }

    delay(250)
    resourceJob.cancel(CancellationException("Permintaan timeout dari sistem"))
    resourceJob.join()

    println("\n=== 3. Timeout Handling ===")
    // withTimeout melempar TimeoutCancellationException jika batas waktu terlewati
    try {
        withTimeout(150) {
            repeat(10) { i ->
                println("Proses timeout step $i...")
                delay(50)
            }
        }
    } catch (e: TimeoutCancellationException) {
        println("Tertangkap TimeoutCancellationException: Eksekusi melebihi batas waktu!")
    }

    // withTimeoutOrNull mengembalikan null secara aman tanpa melempar exception
    val result: String? = withTimeoutOrNull(100) {
        delay(200) // Melebihi timeout
        "Data Berhasil Diambil"
    }
    println("Hasil withTimeoutOrNull: $result") // Output: null
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Continuation Invalidation**: Saat `cancel()` dipanggil, target `JobSupport` (implementasi default dari `Job`) mengubah bit-flag state internalnya menjadi `Cancelling`. Ia memanggil daftar *cancellation handlers* terdaftar dan menyebarkan `CancellationException` ke seluruh *child jobs*.
2. **Resume With Exception**: Jika coroutine sedang berada dalam status *suspended* pada dispatcher (misalnya sedang menunggu `delay` atau I/O), fungsi suspensi tersebut menginterupsi antrean normal. Runtime me-resume Continuation target menggunakan `Result.failure(CancellationException)`.
3. **Dispatch Phase Check**: Sebelum coroutine yang di-resume mulai mengeksekusi instruksi berikutnya di thread pool, `DispatchedTask` memvalidasi status `Job`. Jika `job.isCancelled` bernilai true, dispatcher langsung melempar `CancellationException` tanpa mengeksekusi sisa blok instruksi reguler.

#### Alokasi Memori & Context Switch
- **NonCancellable Context**: Objek `NonCancellable` adalah implementasi `Job` singleton yang berstatus permanen `isActive = true`. Ketika membungkus kode dengan `withContext(NonCancellable)`, child continuation baru dibuat dengan mengabaikan status pembatalan parent scope-nya. Ini mencegah *immediate fast-path cancellation* saat menjalankan instruksi pembersihan.

#### Trade-offs: Cooperative vs Preemptive
| Parameter | Cooperative Cancellation (Kotlin) | Preemptive Cancellation (OS/Native Threads) |
| :--- | :--- | :--- |
| **Safety** | Sangat Tinggi. State memori tidak tertinggal dalam kondisi korup. | Sangat Rendah. Resource locking rentan macet (*deadlock*). |
| **CPU-Bound Latency**| Bergantung pada disiplin programmer menyisipkan check point (`isActive`/`yield`). | Instan, thread dihentikan langsung oleh OS/VM scheduler. |
| **Overhead** | Minimal. Hanya periksa nilai boolean flag atau try-catch exception ringan. | Berat. Melibatkan interupsi kernel level dan context switching sinyal OS. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Periksa Status Secara Berkala**: Sisipkan `ensureActive()` atau `yield()` di dalam loop pemrosesan data biner, kompresi, atau kalkulasi matematika yang memakan CPU.
- **Rethrow `CancellationException`**: Jika Anda menangkap `Throwable` atau `Exception`, selalu lempar kembali `CancellationException` agar alur pembatalan coroutine tidak terputus.
  ```kotlin
  try {
      doWork()
  } catch (e: Exception) {
      if (e is CancellationException) throw e
      logger.error("Operasi gagal", e)
  }
  ```
- **Gunakan `withTimeoutOrNull` untuk Operasi Spekulatif**: Lebih idiomatik dibanding membungkus `withTimeout` dengan blok `try-catch` jika ketiadaan hasil bernilai wajar dalam domain logika aplikasi.

#### Don'ts
- **Jangan Telan Exception Tanpa Seleksi (Swallowing Exception)**:
  ```kotlin
  // ANTI-PATTERN: Membunuh cooperative cancellation!
  try {
      while (true) { delay(100) }
  } catch (e: Exception) {
      // Tidak melempar kembali CancellationException
      // Coroutine akan menolak dibatalkan dan terus memakan alokasi thread
  }
  ```
- **Jangan Jalankan Operasi Suspending di `finally` tanpa `NonCancellable`**: Fungsi suspending apa pun di dalam `finally` yang dipanggil saat job dibatalkan akan langsung melempar `CancellationException` seketika itu juga, membatalkan sisa proses cleanup di bawahnya.

#### Edge Cases
- **Resource Leak pada `withTimeout`**: Jika resource dibuka langsung di dalam blok `withTimeout`, timeout dapat terpicu tepat sebelum referensi resource disimpan ke variabel pointer, menyebabkan memory/file-descriptor leak. 
  *Solusi*: Buat atau buka resource di luar blok `withTimeout`, lalu tutup di dalam blok `finally`.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Titik Lemah Tanpa Cooperative Check**: Buat program coroutine sederhana yang mengeksekusi `while(true)` murni (hanya increment variabel `Long`) tanpa `yield()` atau `isActive`. Panggil `.cancelAndJoin()` dari thread utama. Amati mengapa program Anda *hang* dan gagal berhenti.
2. **Simulasi Network File Downloader dengan Cancel Rollback**: Bangun simulasi download file berbasis chunk (misalnya 10 bagian). Setiap chunk ditulis ke file temporary. Implementasikan pembatalan di tengah jalan sehingga file temporary tersebut otomatis dihapus melalui blok `finally` yang dibungkus oleh `withContext(NonCancellable)`.
3. **Analisis Perbedaan `yield()` vs `delay(1)`**: Telusuri bytecode atau source code Kotlin standard library untuk mengetahui perbedaan alokasi objek dan scheduling behavior antara `yield()` dan `delay(1)` saat digunakan sebagai cancellation check point.
