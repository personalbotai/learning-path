## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem asynchronous Kotlin, **Coroutine Builders** adalah fungsi ekstensi dari `CoroutineScope` (atau fungsi standalone) yang bertindak sebagai pintu masuk untuk menginisiasi, mengonfigurasi, dan menjadwalkan eksekusi sebuah coroutine. Coroutine tidak dapat berjalan di ruang hampa; ia memerlukan batasan siklus hidup (*lifecycle boundary*), penanganan error (*failure propagation*), serta konteks eksekusi (*dispatcher*). Di sinilah coroutine builder berperan menghubungkan blok kode *suspendable* dengan model **Structured Concurrency**.

Tiga coroutine builder fundamental dalam Kotlin Coroutines adalah:

```
                  ┌───────────────────────────────┐
                  │       CoroutineScope          │
                  └───────────────┬───────────────┘
                                  │
         ┌────────────────────────┼────────────────────────┐
         ▼                        ▼                        ▼
    [ launch ]                [ async ]              [ runBlocking ]
  Fire-and-forget         Deferred Result         Thread-Blocking Bridge
  Returns: Job            Returns: Deferred<T>    Returns: T
  Error: Uncaught/Context Error: Thrown on await  Error: Thrown directly
```

#### A. `launch` (Fire-and-Forget)
- **Tujuan**: Digunakan saat operasi asinkron tidak perlu mengembalikan nilai langsung ke pemanggilnya.
- **Return Type**: Mengembalikan instance `Job`. Objek ini merepresentasikan pegangan (*handle*) terhadap siklus hidup coroutine tersebut (bisa dibatalkan via `job.cancel()`, atau ditunggu penyelesaiannya via `job.join()`).
- **Error Handling**: Setiap *unhandled exception* di dalam `launch` akan langsung diteruskan ke atas hierarki *Structured Concurrency* (ke parent `Job` atau `CoroutineExceptionHandler`), berpotensi membatalkan parent jika tidak diisolasi menggunakan `supervisorScope`.

#### B. `async` (Async-Await / Compute Deferred Result)
- **Tujuan**: Digunakan saat operasi asinkron menghasilkan sebuah nilai komputasi atau data I/O yang dibutuhkan di masa mendatang.
- **Return Type**: Mengembalikan `Deferred<T>`, sebuah turunan dari `Job` yang membawa nilai hasil bertipe `T`.
- **Mekanisme**: Memanggil fungsi suspending `.await()` pada `Deferred<T>` akan menangguhkan coroutine pemanggil hingga komputasi selesai. Jika terjadi kegagalan di dalam `async`, exception akan dienkapsulasi di dalam objek `Deferred` dan dilempar ulang (*re-thrown*) saat `.await()` dieksekusi. Namun, dalam cakupan standard scope, exception tersebut juga tetap membatalkan parent job jika tidak ditangani dengan tepat.

#### C. `runBlocking` (The Synchronous Bridge)
- **Tujuan**: Menjembatani dunia sekuensial-blocking reguler (seperti fungsi `main()` standar atau testing unit) dengan dunia suspending.
- **Mekanisme**: `runBlocking` bukan ekstensi dari `CoroutineScope`. Fungsi ini menginterupsi dan memblokir *thread* fisik tempat ia dipanggil sampai seluruh coroutine di dalam cakupannya selesai dieksekusi.
- **Batasan Arsitektur**: Dilarang keras digunakan di dalam kode produksi reaktif, endpoint non-blocking (seperti Ktor/Spring WebFlux), atau Android UI thread, karena menegasikan keunggulan non-blocking IO dan dapat memicu *thread starvation* atau *deadlock*.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Membangun agregator data pengguna (*User Dashboard Aggregator*) yang mengambil profil dan transaksi secara paralel menggunakan `async`, mengirim metrik/analitik secara independen via `launch`, dan dieksekusi dalam runner berbasis `runBlocking`.

```kotlin
import kotlinx.coroutines.*
import kotlin.system.measureTimeMillis

data class UserProfile(val id: String, val name: String)
data class UserTransaction(val transactionId: String, val amount: Double)
data class DashboardData(val profile: UserProfile, val transactions: List<UserTransaction>)

// Simulasi layanan eksternal (I/O Bound)
suspend fun fetchUserProfile(userId: String): UserProfile {
    delay(1000L) // Mensimulasikan network latency non-blocking
    return UserProfile(userId, "Alex Pratama")
}

suspend fun fetchUserTransactions(userId: String): List<UserTransaction> {
    delay(1200L) // Mensimulasikan latency query database non-blocking
    return listOf(
        UserTransaction("TX-101", 250_000.0),
        UserTransaction("TX-102", 750_000.0)
    )
}

suspend fun trackAnalyticsEvent(event: String) {
    delay(300L)
    println("[ANALYTICS] Event '$event' recorded on thread: ${Thread.currentThread().name}")
}

// Fungsi agregasi menggunakan CoroutineScope custom
suspend fun loadDashboard(userId: String): DashboardData = coroutineScope {
    println("Fetching dashboard on thread: ${Thread.currentThread().name}")

    // 1. Eksekusi asynchronous konkuren menggunakan 'async'
    val profileDeferred: Deferred<UserProfile> = async(Dispatchers.IO) {
        fetchUserProfile(userId)
    }

    val transactionsDeferred: Deferred<List<UserTransaction>> = async(Dispatchers.IO) {
        fetchUserTransactions(userId)
    }

    // 2. Fire-and-forget logging/telemetry menggunakan 'launch'
    // Menggunakan Job independen di dalam scope ini
    val analyticsJob: Job = launch(Dispatchers.Default) {
        trackAnalyticsEvent("DASHBOARD_FETCH_INITIATED")
    }

    // 3. Menunggu hasil deferred secara paralel (await)
    // Total latency ~ 1200ms (bukan serial 1000ms + 1200ms = 2200ms)
    val profile = profileDeferred.await()
    val transactions = transactionsDeferred.await()

    // Kita tidak perlu await analyticsJob kecuali ingin menjamin telemetry selesai sebelum return.
    // Structured Concurrency menjamin coroutineScope tidak keluar sebelum analyticsJob selesai!

    DashboardData(profile, transactions)
}

fun main() {
    // 4. 'runBlocking' digunakan sebagai entry point aplikasi konsol / JVM main
    println("Application booting on: ${Thread.currentThread().name}")

    val totalTime = measureTimeMillis {
        runBlocking {
            val dashboard = loadDashboard("USR-8821")
            println("Dashboard successfully loaded: $dashboard")
        }
    }

    println("Total operational latency: ${totalTime}ms")
    println("Execution completed back on thread: ${Thread.currentThread().name}")
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime:
1. **State Machine Injection**: Kompiler Kotlin (`kotlinc`) mentransformasi setiap fungsi `suspend` dan lambda builder menjadi sebuah class turunan dari `ContinuationImpl`. Tiap titik suspensi (`delay`, `await`, `join`) menjadi sebuah label dalam *state machine switch-case*.
2. **`runBlocking` & EventLoop**: Saat `runBlocking` dipanggil, runtime menginisialisasi instance dari `BlockingCoroutine<T>` yang mengimplementasikan event loop lokal berbasis `EventLoopImplBase`. Thread yang memanggil akan masuk ke dalam loop `while (!isCompleted) { parkNanos(processNextEvent()) }`. Thread fisik di-*park* (menggunakan `LockSupport.park()`) saat tidak ada event yang siap dieksekusi, dan di-*unpark* kembali ketika continuation dari coroutine anak selesai.
3. **`launch` vs `async` Execution**:
   - `launch` menginstansiasi `StandaloneCoroutine`, yang mewarisi `AbstractCoroutine<Unit>`. Ketika terjadi exception yang tidak tertangkap, metode `handleJobException()` langsung dipanggil untuk meneruskan error ke parent hierarchy.
   - `async` menginstansiasi `DeferredCoroutine<T>`, yang mewarisi `AbstractCoroutine<T>` dan mengimplementasikan `Deferred<T>`. Hasil komputasi (baik value sukses ataupun exception) disimpan pada field state internal objek coroutine tersebut. Exception baru di-unwrap dan dilempar ke thread caller saat method `awaitInternal()` dipanggil.

```
+--------------------------------------------------------------+
|                    Kompilasi Bytecode                        |
|                                                              |
|  async { fetch() }  --->  new DeferredCoroutine(context)    |
|                           stateMachine.resumeWith(result)    |
|                           Deferred.await() --> cek state:    |
|                             - Success: return T              |
|                             - Failure: rethrow Throwable     |
+--------------------------------------------------------------+
```

#### Alokasi Memori / Resource:
- Berbeda dengan OS thread yang memerlukan alokasi memori default stack berkisar antara 512KB hingga 1MB (tergantung OS dan JVM flag `-Xss`), coroutine instance hanyalah objek heap biasa berukuran beberapa puluh byte hingga beberapa kilobyte (berisi context, references, dan frame state variables).
- Memanggil 100.000 `launch` hanya memakan beberapa ratus megabyte memory di JVM heap, sedangkan membuat 100.000 OS Thread via `java.lang.Thread` akan langsung memicu `java.lang.OutOfMemoryError: unable to create new native thread`.

#### Trade-offs:
- **`runBlocking` vs Suspending Methods**: `runBlocking` mengorbankan sifat non-blocking dari thread JVM demi kenyamanan interfacing dengan kode legacy/sinkron. Satu thread yang terblokir tidak dapat melayani request lain.
- **Parallel Decomposition (`async`) vs Throughput**: Menggunakan terlalu banyak `async` paralel untuk tugas-tugas yang terlampau granular (komputasi sub-milidetik) menimbulkan *overhead scheduling* pada thread pool dispatcher yang justru dapat memperlambat throughput dibanding komputasi sekuensial.

### 4. Best Practices & Common Pitfalls

#### Do's:
- **Gunakan `coroutineScope` / `supervisorScope` untuk membungkus `async`**: Selalu batasi masa hidup `async` dalam scope lokal terstruktur. Jika salah satu `async` gagal, scope pembungkus akan membatalkan task paralel lainnya secara otomatis (*fail-fast*).
- **Gunakan `launch` untuk logging/auditing fire-and-forget**: Pasangkan dengan `NonCancellable` atau scope terpisah jika proses auditing tidak boleh dibatalkan saat coroutine utama terkena cancel.
- **Pilihlah Dispatcher yang Sesuai**: Inject `CoroutineDispatcher` (misal: `Dispatchers.IO` untuk disk/network, `Dispatchers.Default` untuk operasi CPU-bound intensif) daripada melakukan hardcode di dalam builder.

#### Don'ts:
- **JANGAN PERNAH gunakan `runBlocking` di dalam coroutine atau suspend function**: Memanggil `runBlocking` di dalam suspend function adalah *anti-pattern* fatal yang dapat menyebabkan *thread pool exhaustion* atau deadlock. Suspend function seharusnya langsung memanggil suspend function lain atau menggunakan builder seperti `coroutineScope`.
- **JANGAN abaikan return value `async` tanpa memanggil `.await()`**: Jika Anda meluncurkan `async` dan tidak pernah memanggil `.await()`, exception apa pun yang terjadi di dalamnya mungkin tidak tertangkap secara lokal, membingungkan proses debugging jika tidak ada ExceptionHandler global. Gunakan `launch` jika memang tidak memerlukan return value.

#### Edge Cases (The Async Exception Swallow Trap):
Jika `async` dipanggil langsung dari `GlobalScope` atau scope tanpa parent yang menangani exception, lalu `.await()` tidak dipanggil, exception dapat "hilang" (swallowed) sampai `.await()` dieksekusi. Namun di dalam structured scope standar:
```kotlin
// BAHAYA: Exception dalam async akan membatalkan parent scope MESKIPUN await() belum dipanggil!
coroutineScope {
    val deferred = async { 
        throw IllegalStateException("Fatal Failure") 
    }
    // Jika ada kode lambat di sini, scope AKAN runtuh sebelum await() tercapai
    delay(500)
    deferred.await()
}
```
*Solusi*: Gunakan `supervisorScope` jika Anda ingin kegagalan pada satu `Deferred` tidak secara otomatis mematikan sibling coroutine lainnya sebelum Anda sempat mengevaluasi hasil `.await()`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Exception Behavior `async` vs `supervisorScope`**: 
   Buatlah program yang menjalankan dua tugas via `async` di dalam sebuah `supervisorScope`. Buat salah satu tugas melempar `RuntimeException` setelah 200ms, sementara tugas kedua membutuhkan waktu 1000ms. Buktikan bahwa tugas kedua tetap berjalan sampai selesai, dan tangani exception tersebut dengan membungkus pemanggilan `.await()` dalam blok `try-catch`.
2. **Simulasi Thread Starvation dengan `runBlocking`**: 
   Buat custom single-thread dispatcher (`Executors.newSingleThreadExecutor().asCoroutineDispatcher()`). Jalankan coroutine dengan `launch` pada dispatcher tersebut, lalu di dalamnya panggil `runBlocking` yang mencoba melakukan `launch` kembali ke dispatcher yang sama. Amati apa yang terjadi (Deadlock) dan jelaskan mengapa itu terjadi berdasarkan konsep Event Loop.
