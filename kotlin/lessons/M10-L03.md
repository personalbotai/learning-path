## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara arsitektural, coroutine sering dipromosikan sebagai *"lightweight threads"*, namun karakteristik siklus hidupnya di JVM bergantung sepenuhnya pada alokasi objek heap dan rantai referensi Garbage Collector (GC). **Coroutine Leak** terjadi ketika sebuah coroutine terus berjalan atau tertahan dalam status suspended di memori tanpa batas waktu, padahal hasil komputasinya sudah tidak lagi dibutuhkan oleh aplikasi.

#### Akar Masalah: Mengapa Coroutine Bisa Bocor?
Dalam arsitektur JVM, sebuah objek dapat di-garbage collect hanya jika objek tersebut *unreachable* dari GC Roots (seperti local variable pada active thread stack, static reference, atau thread aktif itu sendiri).

Ketika sebuah coroutine dijalankan:
1. Runtime membuat serangkaian objek: `Job`, `CoroutineContext`, dan instance `Continuation`.
2. Setiap lambda suspensi (*suspending lambda*) mengompilasi closure yang menangkap (*captures*) variabel di sekitarnya, termasuk referensi ke objek pemanggil (`this`), listener, konteks UI, atau repository.
3. Objek `Continuation` ini dijadwalkan ke dalam `CoroutineDispatcher` (seperti `Dispatchers.Default` atau `Dispatchers.IO`), yang pada dasarnya dikelola oleh thread pool aktif (`Executor` / `ForkJoinPool`).
4. Thread pool aktif bertindak sebagai **GC Root**. Selama coroutine belum selesai (*completed*) atau dibatalkan (*cancelled*), rantai referensi berikut terbentuk:
   $$\text{GC Root (Thread/Dispatcher)} \rightarrow \text{Continuation} \rightarrow \text{Captured Context (e.g., ViewModel/Activity/Heavy Service)}$$
5. Akibatnya, seluruh graph objek yang tertangkap tidak dapat direklamasi oleh GC, memicu memory leak masif.

#### Structured Concurrency & Kegagalannya
Kotlin memperkenalkan **Structured Concurrency** untuk mencegah masalah ini dengan memaksakan relasi parent-child antar-`Job`. Ketika parent job dibatalkan, semua child job ikut dibatalkan. Namun, kebocoran tetap kerap terjadi akibat:
- **Scope Misalignment:** Penggunaan `GlobalScope`, scope kustom tanpa binding siklus hidup (*unbounded lifecycle*), atau inject scope singleton ke objek berumur pendek.
- **Uncooperative Cancellation:** Coroutine terjebak dalam loop CPU-bound tanpa mengecek status pembatalan (`isActive` / `ensureActive()`).
- **Swallowed Exceptions:** Menangkap dan menelan `CancellationException` tanpa melemparnya kembali, memutus rantai pembatalan struktural.
- **Hanging Resources:** Menunggu emisi dari unclosed `Channel`, `StateFlow`, atau callback API pihak ketiga yang tidak pernah menyelesaikan suspensi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah demonstrasi skenario umum kebocoran coroutine akibat scope singleton dan cara refactoring menggunakan idiomatisasi Structured Concurrency dengan lifecycle teardown yang aman.

```kotlin
package com.architecture.concurrency.leakprevention

import kotlinx.coroutines.*
import java.io.Closeable
import java.util.concurrent.atomic.AtomicInteger

// -------------------------------------------------------------
// KASUS BURUK: Memori bocor karena referensi tertahan di background
// -------------------------------------------------------------
class LeakyWorker(
    private val heavyPayload: ByteArray = ByteArray(10 * 1024 * 1024) // 10 MB payload
) {
    // BAHAYA: Menggunakan GlobalScope atau Dispatcher tanpa batas siklus hidup
    fun startUnsafeJob() {
        @OptIn(DelicateCoroutinesApi::class)
        GlobalScope.launch(Dispatchers.Default) {
            while (true) {
                // Suspended coroutine menahan reference ke instance LeakyWorker ('this')
                println("Working with payload size: ${heavyPayload.size}")
                delay(1000)
            }
        }
    }
}

// -------------------------------------------------------------
// KASUS SOLUTIF: Lifecycle-aware & cooperative cancellation
// -------------------------------------------------------------
class SafeWorker(
    private val heavyPayload: ByteArray = ByteArray(10 * 1024 * 1024)
) : Closeable {

    // 1. Buat Job lokal yang dapat dibatalkan bersama instance-nya
    private val workerJob = SupervisorJob()
    
    // 2. CoroutineScope terikat pada siklus hidup Worker
    private val scope = CoroutineScope(Dispatchers.Default + workerJob)

    fun startSafeJob() {
        scope.launch {
            try {
                // Menjalankan tugas komputasi secara kooperatif
                doIntensiveWork()
            } catch (e: CancellationException) {
                // WAJIB: CancellationException harus dibiarkan me-unwind state coroutine
                println("Worker cancelled successfully. Membersihkan resource...")
                throw e
            } finally {
                // Tempat pembersihan resource non-coroutine jika ada
                cleanUpResources()
            }
        }
    }

    private suspend fun doIntensiveWork() {
        var counter = 0
        while (true) {
            // Memastikan coroutine merespons sinyal pembatalan secara instan
            coroutineContext.ensureActive()

            // Simulasi proses
            counter++
            delay(500) // Delay kooperatif terhadap pembatalan
            println("Safe task running tick: $counter, payload active")
        }
    }

    private fun cleanUpResources() {
        println("Resource pembersihan selesai.")
    }

    // Dipanggil ketika lifecycle owner dihancurkan (misal: onDestroy / DI tearDown)
    override fun close() {
        // Membatalkan job dan seluruh child coroutine di dalamnya
        workerJob.cancel()
    }
}

// -------------------------------------------------------------
// Driver Program
// -------------------------------------------------------------
fun main() = runBlocking {
    println("--- Memulai Safe Worker ---")
    val worker = SafeWorker()
    worker.startSafeJob()

    delay(1600) // Biarkan berjalan sesaat

    println("--- Menghancurkan Safe Worker ---")
    worker.close() // Mentransisikan job ke Cancelled, memutus referensi ke GC Root

    delay(1000) // Verifikasi tidak ada lagi log dari coroutine
    println("Program selesai tanpa leak.")
}
```

#### Penjelasan Komponen Kunci:
1. **`SupervisorJob()`**: Memungkinkan kegagalan pada satu child coroutine tidak membatalkan coroutine lainnya, namun pembatalan pada `workerJob.cancel()` akan menyapu bersih seluruh eksekusi di bawah scope tersebut.
2. **`coroutineContext.ensureActive()`**: Memeriksa properti `isActive` dari context. Jika job sudah dibatalkan, fungsi ini segera melempar `CancellationException`, mencegah pemborosan resource CPU pada operasi intensif non-suspending.
3. **`Closeable` Pattern**: Menjamin adanya kontrak eksplisit untuk melepaskan resource coroutine saat objek induk dimusnahkan.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: State Machine Transformation
Saat fungsi suspend dikompilasi, Kotlin Compiler mengubah blok kode menjadi **State Machine** melalui CPS (*Continuation Passing Style*).

```
suspend fun example() {
    val data = loadFromDb() // suspension point 1
    process(data)           // suspension point 2
}
```

Di-decompile menjadi kelas internal turunan `ContinuationImpl`:
```java
// Bytecode Java Pseudo-Code
final class ExampleContinuation extends ContinuationImpl {
    Object result;
    int label;
    Object L$0; // Variabel lokal "data" disimpan di field objek heap!

    public final Object invokeSuspend(Object result) {
        this.result = result;
        this.label |= Integer.MIN_VALUE;
        return example(this);
    }
}
```

Jika coroutine tersuspensi di *suspension point 1*, variabel lokal dan referensi objek instance pemanggil (`this$0`) disimpan sebagai field langsung (`L$0`, `L$1`, dst.) pada instance `ExampleContinuation`. Objek ini tidak akan dibuang oleh GC sampai fungsi resume kembali dan state machine mencapai label final.

#### Alokasi Memori / Resource
1. **Dispatcher Queue References:** Ketika coroutine berpindah dispatcher (misalnya `withContext(Dispatchers.IO)`), instance `Continuation` dibungkus ke dalam `DispatchedContinuation` yang didaftarkan ke antrean scheduler thread (`Worker` thread pada `ForkJoinPool`). Selama antrean ini memegang referensi ke runnable/continuation, entire invocation frame tertahan di memory.
2. **L$ Variable Nullability (Field Clearing):** Kotlin compiler modern mengoptimasi memori dengan cara melakukan nullification terhadap field lokal (`L$0 = null`) segera setelah variabel tersebut tidak lagi digunakan di antara titik suspensi berikutnya. Namun, compiler **tidak** otomatis me-nullkan referensi `this$0` (outer class) sampai seluruh coroutine selesai!

#### Trade-offs: Cooperative Cancellation vs Throughput
- **Overhead `ensureActive()`**: Memanggil pengecekan status pembatalan berulang kali di dalam loop ketat (*tight loop*) menambahkan instruksi branching ekstra. Namun, tanpa ini, coroutine yang dibatalkan akan menjadi *zombie process* yang memakan core CPU.
- **Scope Granularity**: Membuat `CoroutineScope` terpisah per komponen membutuhkan overhead alokasi objek `Job` dan hash map context. Namun, alternatifnya (menggunakan scope global bersama) membuka celah kebocoran cascade ketika salah satu flow tertahan.

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Gunakan Scope yang Terikat Lifecycle:** Selalu ikat coroutine ke lifecycle runtime host (misal: `viewModelScope` di Android, `lifecycleScope`, atau implementasi `AutoCloseable`/`Closeable` pada service backend).
2. **Hormati `CancellationException`:** Jika menangkap `Exception` generik, lempar kembali `CancellationException`.
   ```kotlin
   try {
       doSuspendWork()
   } catch (e: Exception) {
       if (e is CancellationException) throw e // WAJIB!
       logger.error("Error non-cancellation", e)
   }
   ```
3. **Bersihkan Non-Cancellable Work di Finally Block:**
   Gunakan `withContext(NonCancellable)` secara bijak hanya untuk operasi penutupan resource di dalam blok `finally`.

#### Don'ts:
1. **Dilarang Menelan Exception Secara Buta:**
   ```kotlin
   // SANGAT BURUK: Coroutine tidak akan pernah bisa di-cancel
   try {
       delay(Long.MAX_VALUE)
   } catch (t: Throwable) {
       // Menelan CancellationException secara diam-diam
   }
   ```
2. **Jangan Menggunakan `GlobalScope`:** `GlobalScope` tidak memiliki context parent-child dengan komponen Anda, sehingga coroutine yang di-launch akan hidup selama proses JVM hidup.
3. **Hindari Long-lived Coroutine yang Mengamati Short-lived State:** Menghubungkan listener UI atau objek berumur pendek ke coroutine yang berjalan di scope berumur panjang tanpa mekanisme unregister/cancellation.

#### Edge Cases:
- **Deadlock pada Unbuffered Channels:** Mengirim data ke `Channel` unbuffered (`rendezvous`) di mana tidak ada consumer yang membaca akan menahan sender coroutine dalam suspensi abadi.
- **`withContext(NonCancellable)` Overuse:** Menjalankan operasi I/O yang panjang di dalam `NonCancellable` mematikan kapabilitas structured concurrency secara total untuk scope tersebut. Gunakan hanya untuk rollback atomik/close stream.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Heap Dump Leak:**
   Modifikasi kelas `LeakyWorker` di atas untuk mengalokasikan 100 instance secara bersamaan di `main()`. Lakukan heap dump menggunakan tool seperti `jcmd <pid> GC.dump /path/to/dump.hprof` atau profiler bawaan IDE Anda (IntelliJ Profiler). Temukan jalur terpendek dari GC Root (`Shortest Path to GC Roots`) menuju array `heavyPayload`. Identifikasi objek internal coroutine mana yang menahan payload tersebut.
2. **Implementasi `CancellableComputationRunner`:**
   Buat sebuah kelas wrapper engine komputasi matematis berat (misal: menghitung bilangan prima secara terus-menerus tanpa fungsi `suspend` bawaan seperti `delay`). Rancang sistem agar perhitungan tersebut dapat dihentikan dalam waktu kurang dari 50 milidetik setelah client memanggil `.cancel()`, tanpa menyebabkan CPU throttling yang tidak perlu. (Petunjuk: Padukan loop murni dengan `yield()` atau `ensureActive()`).
