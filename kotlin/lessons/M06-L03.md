## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem *asynchronous* tradisional (seperti *raw threads* atau *callbacks*), masalah terbesar yang sering muncul adalah **"Orphaned Tasks"** atau tugas yang terus berjalan di *background* meskipun komponen pemanggilnya sudah dihancurkan (misalnya, *Activity* ditutup atau *HTTP Request* dibatalkan). Hal ini menyebabkan *memory leak* dan pemborosan *resource* CPU.

Kotlin menyelesaikan masalah ini melalui paradigma **Structured Concurrency**. Prinsip utamanya adalah: **Tidak ada coroutine yang boleh diluncurkan tanpa batasan siklus hidup (lifecycle) yang jelas.**

Tiga pilar utama dalam arsitektur ini:
1. **CoroutineScope**: Bertindak sebagai "arena" atau batas siklus hidup. Setiap coroutine harus diluncurkan di dalam sebuah *scope*. *Scope* ini menyimpan `CoroutineContext` yang berisi elemen-elemen seperti *Dispatcher* dan *Job*.
2. **Job**: Representasi *handle* dari sebuah coroutine. `Job` bertanggung jawab atas *state machine* (New, Active, Completing, Completed, Cancelling, Cancelled) dan membentuk hierarki *parent-child* (pohon eksekusi).
3. **Structured Concurrency**: Aturan main yang mengikat `CoroutineScope` dan `Job`. Aturan ini menjamin:
   - *Parent* tidak akan selesai (berstatus *Completed*) sebelum semua *child* coroutine-nya selesai.
   - Pembatalan (*Cancellation*) pada *parent* akan membatalkan semua *child* secara otomatis.
   - *Exception* (selain `CancellationException`) pada *child* akan membatalkan *parent* dan seluruh *child* lainnya (kecuali menggunakan `SupervisorJob`).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi yang mendemonstrasikan hierarki *parent-child*, pembatalan, dan perbedaan antara `Job` biasa dengan `SupervisorJob`.

```kotlin
import kotlinx.coroutines.*

// Simulasi komponen arsitektur (misal: ViewModel di Android atau Controller di Backend)
class UserDashboardComponent {
    // 1. Membuat Custom Scope dengan SupervisorJob
    // SupervisorJob mencegah kegagalan satu child membatalkan child lainnya.
    private val componentJob = SupervisorJob()
    private val exceptionHandler = CoroutineExceptionHandler { _, exception ->
        println("[ExceptionHandler] Caught: ${exception.message}")
    }
    
    // Scope menggabungkan Job, Dispatcher, dan Exception Handler
    val scope = CoroutineScope(Dispatchers.Default + componentJob + exceptionHandler)

    fun loadDashboardData() {
        // Meluncurkan Parent Coroutine
        scope.launch {
            println("[Parent] Memulai proses pemuatan data...")

            // Child 1: Mengambil profil user
            val profileJob = launch {
                println("[Child 1] Fetching profile...")
                delay(1000) // Simulasi I/O
                println("[Child 1] Profile loaded.")
            }

            // Child 2: Mengambil data transaksi (Simulasi Error)
            val transactionJob = launch {
                println("[Child 2] Fetching transactions...")
                delay(500)
                throw RuntimeException("Gagal mengambil transaksi!") // Akan ditangkap oleh exceptionHandler
            }

            // Child 3: Mengambil notifikasi
            val notifJob = launch {
                println("[Child 3] Fetching notifications...")
                delay(1500)
                println("[Child 3] Notifications loaded.")
            }

            // Menunggu semua child selesai (meskipun ada yang error, Child 3 tetap berjalan karena SupervisorJob di root)
            joinAll(profileJob, transactionJob, notifJob)
            println("[Parent] Semua tugas selesai (atau dibatalkan).")
        }
    }

    fun clear() {
        println("[Component] Membersihkan resource, membatalkan semua coroutine...")
        // Membatalkan scope akan membatalkan componentJob dan semua child-nya
        scope.cancel() 
    }
}

fun main() = runBlocking {
    val dashboard = UserDashboardComponent()
    dashboard.loadDashboardData()
    
    delay(2000) // Biarkan berjalan sebentar
    dashboard.clear() // Simulasi komponen dihancurkan
    delay(500) // Waktu untuk melihat log pembatalan
}
```

**Penjelasan Kode:**
- `SupervisorJob()`: Digunakan di tingkat *scope* agar jika `Child 2` *crash*, `Child 1` dan `Child 3` tidak ikut dibatalkan. Jika kita menggunakan `Job()` biasa, *exception* di `Child 2` akan meruntuhkan seluruh *scope*.
- `scope.cancel()`: Saat komponen dihancurkan, kita memanggil `cancel()`. Ini akan mengirimkan `CancellationException` ke bawah hierarki pohon `Job`, menghentikan semua coroutine yang sedang *suspend* (seperti pada `delay`).

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Saat coroutine baru dibuat via `launch` atau `async`, *runtime* Kotlin memeriksa `CoroutineContext` dari *scope*. Jika ada `Job` di dalam konteks tersebut, coroutine baru akan membuat `Job` miliknya sendiri dan mendaftarkannya sebagai *child* dari `Job` milik *scope*. Hubungan ini disimpan dalam struktur data internal (biasanya *lock-free list*) di dalam instance `JobSupport`.
- **Alokasi Memori / Resource**: 
  `Job` sangat ringan (*lightweight*). Namun, hierarki *parent-child* menahan referensi objek. Ketika sebuah *child* selesai, ia akan menghapus dirinya dari daftar *children* milik *parent*-nya. Hal ini penting untuk mencegah *memory leak* pada *parent* coroutine yang berumur panjang (seperti *application scope*).
- **Trade-offs**: 
  Menggunakan `coroutineScope { ... }` (fungsi *scoping* bawaan) untuk memecah tugas paralel sangat aman karena ia akan memblokir (secara *suspend*) sampai semua *child* selesai. Namun, *trade-off*-nya adalah jika satu *child* gagal, seluruh blok `coroutineScope` langsung gagal. Jika Anda butuh ketahanan parsial, Anda harus menggunakan `supervisorScope { ... }`.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Selalu gunakan `coroutineScope` atau `supervisorScope` saat melakukan dekomposisi tugas paralel di dalam sebuah fungsi *suspend*.
  - Batalkan `CoroutineScope` saat siklus hidup komponen pemiliknya berakhir (misal: `ViewModel.onCleared()` atau saat *TCP connection* ditutup).
  - Gunakan `SupervisorJob` **hanya** pada *root scope* (seperti di kelas UI atau *Application*), bukan sebagai argumen langsung ke `launch(SupervisorJob())` karena itu memutus hierarki *Structured Concurrency*.

- **Don'ts**:
  - **JANGAN** menggunakan `GlobalScope`. `GlobalScope` tidak terikat pada *lifecycle* apa pun dan beroperasi seperti *daemon thread*. Ini adalah sumber utama *memory leak*.
  - **JANGAN** menangkap (`catch`) `CancellationException` secara diam-diam. Jika Anda menangkap `Exception` secara umum, pastikan untuk me-rethrow `CancellationException`, atau coroutine Anda tidak akan bisa dibatalkan dengan benar.
    ```kotlin
    // BAD
    try { delay(1000) } catch (e: Exception) { /* diam saja */ }
    
    // GOOD
    try { delay(1000) } catch (e: Exception) {
        if (e is CancellationException) throw e
        // handle error lainnya
    }
    ```

- **Edge Cases**:
  - Jika Anda meneruskan instance `Job` baru ke dalam `launch(Job())`, coroutine tersebut akan kehilangan hubungan *parent-child* dengan *scope* pemanggilnya. Pembatalan *scope* tidak akan membatalkan coroutine tersebut.

### 5. Tantangan Eksplorasi Mandiri

1. **Eksperimen Hierarki Job**: Buat sebuah program dengan `coroutineScope`. Luncurkan 3 *child* coroutine menggunakan `launch`. Di dalam *child* ke-2, lemparkan `IllegalArgumentException`. Amati apa yang terjadi pada *child* ke-1 dan ke-3. Ubah `coroutineScope` menjadi `supervisorScope` dan amati perbedaannya.
2. **Custom Timeout Scope**: Buat sebuah fungsi ekstensi `CoroutineScope.launchWithTimeout(timeMillis: Long, block: suspend CoroutineScope.() -> Unit): Job`. Fungsi ini harus meluncurkan coroutine yang otomatis membatalkan dirinya sendiri (dan *child*-nya) jika eksekusi `block` melebihi `timeMillis`, tanpa menggunakan fungsi bawaan `withTimeout`. *(Petunjuk: Gunakan `launch` tambahan yang melakukan `delay` lalu memanggil `cancel()` pada Job utama).*
