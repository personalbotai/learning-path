## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur monolitik tradisional (seperti LAMP stack), PHP dieksekusi sebagai modul Apache (`mod_php`). Pendekatan ini menyatukan *web server* dan *PHP runtime* ke dalam satu proses memori, yang menyebabkan inefisiensi masif: setiap kali Apache melayani aset statis (CSS, JS, gambar), *overhead* runtime PHP tetap dialokasikan dalam memori.

Di era *cloud-native* dan *containerization*, pola standar industri memisahkan peran ini secara modular:
1. **Nginx** bertindak sebagai *reverse proxy*, terminator TLS, dan server file statis yang *event-driven* (berbasis `epoll`).
2. **PHP-FPM (FastCGI Process Manager)** bertindak sebagai *application server* independen yang mengeksekusi skrip PHP melalui protokol biner **FastCGI**.

```
Client (Browser)
      │
      ▼ [HTTP/HTTPS :80/:443]
┌──────────────┐
│  Container   │ ──(Static Files: .css, .js)──► Dilayani langsung dari disk
│    Nginx     │
└──────┬───────┘
       │ [FastCGI Protocol via TCP Port 9000 atau Shared UNIX Socket]
       ▼
┌──────────────┐
│  Container   │
│   PHP-FPM    │ ──► [Master Process (PID 1)]
│(Alpine Linux)│       ├── Worker 1 (Forked) ──► Zend Engine Execution
└──────────────┘       ├── Worker 2 (Forked) ──► Zend Engine Execution
                       └── Worker N ...
```

#### Arsitektur PHP-FPM
PHP-FPM beroperasi menggunakan model *pre-forking*:
- **Master Process**: Berjalan pada *user privileged* (atau non-root yang didelegasikan), mengelola siklus hidup *worker*, mendengarkan sinyal OS (`SIGTERM`, `SIGUSR2` untuk reload), dan membuka *socket*.
- **Worker Processes**: Mengisolasi eksekusi kode PHP per *request*. Setiap *worker* menjalankan Zend Engine, mengeksekusi *byte-code* (Opcode), lalu membersihkan konteks memori request (`request_shutdown`).

Mode manajemen proses PHP-FPM:
- `static`: Jumlah worker tetap sejak awal (`pm.max_children`). Ideal untuk container produksi karena penggunaan memori terprediksi.
- `dynamic`: Worker bertambah/berkurang sesuai beban (`pm.start_servers`, `pm.min_spare_servers`, dll.). Cocok untuk VM konvensional, kurang optimal di container Kubernetes yang mengandalkan HPA (*Horizontal Pod Autoscaler*).
- `ondemand`: Worker di-spawn hanya ketika ada request masuk. Menghemat memori tetapi menimbulkan *latency cold-start*.

#### Mengapa Alpine Linux?
Alpine Linux memanfaatkan **musl libc** (sebagai pengganti GNU C Library/`glibc`) dan **BusyBox**. 
- **Ukuran Image**: Image berbasis Alpine umumnya berukuran 10–30 MB, berbanding terbalik dengan image berbasis Debian/Ubuntu yang berkisar antara 150–400 MB.
- **Attack Surface**: Jumlah binary dan dependensi minimal memangkas potensi Common Vulnerabilities and Exposures (CVE).
- **Konsekuensi Arsitektur**: Kompilasi *extension* C/C++ pada Alpine sering membutuhkan *toolchain* native (`gcc`, `make`, `autoconf`) karena pre-compiled binary dari ekosistem `glibc` tidak kompatibel secara ABI (*Application Binary Interface*).

### 2. Implementasi & Contoh Kasus Nyata

Struktur direktori proyek:
```text
.
├── docker-compose.yml
├── docker/
│   ├── nginx/
│   │   └── default.conf
│   └── php/
│       ├── Dockerfile
│       ├── opcache.ini
│       └── php-fpm.conf
└── src/
    └── public/
        └── index.php
```

#### a. `docker/php/Dockerfile` (Multi-stage & Production-ready)
```dockerfile
# Stage 1: Build stage untuk dependensi Composer dan Extension kompilasi
FROM php:8.3-fpm-alpine AS base

# Install dependensi sistem dasar & library C runtime
RUN apk add --no-cache \
    libpng \
    libjpeg-turbo \
    libwebp \
    freetype \
    libzip \
    icu-libs \
    linux-headers

# Stage 2: Builder
FROM base AS builder

# Install build-dependencies sementara untuk kompilasi extension
RUN apk add --no-cache --virtual .build-deps \
    $PHPIZE_DEPS \
    libpng-dev \
    libjpeg-turbo-dev \
    libwebp-dev \
    freetype-dev \
    libzip-dev \
    icu-dev

# Konfigurasi dan compile extension
RUN docker-php-ext-configure gd --with-freetype --with-jpeg --with-webp \
    && docker-php-ext-install -j$(nproc) \
        pdo_mysql \
        gd \
        intl \
        zip \
        opcache

# Stage 3: Runtime Image Final
FROM base AS final

# Salin extension yang sudah terkompilasi dari builder
COPY --from=builder /usr/local/lib/php/extensions/ /usr/local/lib/php/extensions/
COPY --from=builder /usr/local/etc/php/conf.d/ /usr/local/etc/php/conf.d/

# Konfigurasi OPcache & Security INI
COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/docker-php-ext-opcache.ini
COPY docker/php/php-fpm.conf /usr/local/etc/php-fpm.d/zz-docker.conf

WORKDIR /var/www/html

# Gunakan user non-privileged default bawaan image alpine: www-data (UID/GID 82)
USER www-data

# Forward port FastCGI
EXPOSE 9000

CMD ["php-fpm", "-F"]
```

#### b. `docker/php/opcache.ini`
```ini
[opcache]
opcache.enable=1
opcache.enable_cli=0
opcache.memory_consumption=128
opcache.interned_strings_buffer=16
opcache.max_accelerated_files=10000
; Di container produksi, hindari revalidasi disk untuk latency minimum
opcache.validate_timestamps=0
opcache.save_comments=1
opcache.fast_shutdown=1
```

#### c. `docker/php/php-fpm.conf`
```ini
[global]
daemonize = no
error_log = /proc/self/fd/2

[www]
listen = 9000
listen.owner = www-data
listen.group = www-data
; Static pool: Prediktabilitas utilisasi RAM dalam container
pm = static
pm.max_children = 20
pm.max_requests = 1000
pm.status_path = /status

clear_env = no
catch_workers_output = yes
decorate_workers_output = no
```

#### d. `docker/nginx/default.conf`
```nginx
server {
    listen 80;
    server_name localhost;
    root /var/www/html/public;
    index index.php index.html;

    # Logging ke stdout/stderr
    access_log /dev/stdout;
    error_log /dev/stderr warn;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    # Teruskan eksekusi PHP ke container PHP-FPM
    location ~ \.php$ {
        fastcgi_split_path_info ^(.+\.php)(/.+)$;
        # Resolving service name via Docker embedded DNS (127.0.0.11)
        fastcgi_pass php:9000;
        fastcgi_index index.php;
        
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param PATH_INFO $fastcgi_path_info;
        
        # Buffer tuning untuk transmisi payload FastCGI
        fastcgi_buffer_size 16k;
        fastcgi_buffers 4 16k;
        fastcgi_read_timeout 60s;
    }

    location ~ /\.ht {
        deny all;
    }
}
```

#### e. `docker-compose.yml`
```yaml
services:
  php:
    build:
      context: .
      dockerfile: docker/php/Dockerfile
    volumes:
      - ./src:/var/www/html:cached
    networks:
      - app-tier
    restart: unless-stopped

  nginx:
    image: nginx:1.25-alpine
    ports:
      - "8080:80"
    volumes:
      - ./src:/var/www/html:ro
      - ./docker/nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - php
    networks:
      - app-tier
    restart: unless-stopped

networks:
  app-tier:
    driver: bridge
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Protokol FastCGI
FastCGI adalah protokol biner berbasis rekaman (*record-oriented binary protocol*). Berbeda dengan HTTP berbasis teks:
1. Nginx mem-parsing HTTP request dari klien dan menyusun *FastCGI frame* (`FCGI_BEGIN_REQUEST`, `FCGI_PARAMS`, `FCGI_STDIN`).
2. Melalui socket TCP (`php:9000`), Nginx mentransmisikan data environment (`SCRIPT_FILENAME`, HTTP headers) dalam bentuk *key-value pairs*.
3. Master FPM mendelegasikan *file descriptor* socket ke salah satu *worker* yang sedang *idle*.
4. Worker membaca `SCRIPT_FILENAME`, memanggil OPcache. Jika terjadi *cache hit*, worker langsung mengeksekusi Opcode di Zend VM. Jika *cache miss*, proses *Lexing*, *Parsing*, dan *Compilation* dijalankan sebelum eksekusi.
5. Worker mengirim respons (`FCGI_STDOUT`) kembali ke Nginx, diakhiri dengan frame `FCGI_END_REQUEST`.

#### Alokasi Memori: musl libc vs. glibc
- **Memory Allocator**: `glibc` menggunakan `ptmalloc3` (sangat optimal untuk multithreading paralel performa tinggi), sedangkan `musl` menggunakan implementasi alokator memori yang jauh lebih ringkas (*scudo-based* di versi modern / varian *dlmalloc* di versi lama). Implikasinya: PHP-FPM di Alpine menggunakan *virtual memory footprint* yang jauh lebih kecil saat idle, namun pada kasus konkurensi alokasi dinamis ekstrem, `musl` berpotensi memiliki fragmentasi memori sedikit lebih tinggi dibanding `glibc`.
- **Thread Stack Size**: Default thread stack di `musl` jauh lebih kecil (biasanya 128KB vs 8MB–10MB di glibc). Skrip PHP dengan rekursi yang sangat dalam bisa mengalami *Segmentation Fault* (`SIGSEGV`) lebih cepat di Alpine.

#### Trade-offs: TCP vs UNIX Domain Socket (UDS)
| Aspek | TCP Socket (`php:9000`) | UNIX Domain Socket (`unix:/var/run/php-fpm.sock`) |
| :--- | :--- | :--- |
| **Beban Kernel** | Memerlukan traversal *network stack*, checksumming, loopback routing. | Zero-copy via kernel buffer memory langsung antar-proses. |
| **Throughput** | Lebih rendah (~10-15% latency penalty). | Latensi mikrosekon lebih cepat. |
| **Modularitas Container** | Nginx dan PHP dapat dipisah ke beda container/node. | Nginx & PHP harus berbagi volume disk yang sama (*shared volume*). |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Logging ke `/proc/self/fd/2`**: Di container, proses tidak boleh menulis log ke file statis internal (`/var/log/php-fpm.log`). Output log harus diteruskan ke standard output/error agar driver log Docker/Kubernetes dapat mengumpulkannya.
- **Konfigurasi `pm.max_children` Terhitung**: Jangan biarkan FPM kehabisan memori.
  $$\text{pm.max\_children} = \frac{\text{Batas RAM Container} - \text{Headroom OS (misal 50MB)}}{\text{Rata-rata Konsumsi RAM per Worker PHP (misal 30MB)}}$$
- **Multi-stage Dockerfile**: Bersihkan build tools (`gcc`, `make`, `dev-libs`) dari runtime final image untuk mencegah bloating dan eksploitasi binary kompilasi.

#### Don'ts
- **Menyatukan Nginx & PHP-FPM dengan Supervisord**: Melanggar paradigma *single-responsibility container*. Hal ini mempersulit agregasi healthcheck, pemisahan auto-scaling (Nginx CPU-bound vs PHP Memory/CPU-bound), dan manajemen PID 1.
- **Membiarkan `opcache.validate_timestamps=1` di Produksi**: Hal ini memaksa worker memeriksa modifikasi disk via *stat system calls* pada setiap hit, yang menurunkan throughput IOPS container secara signifikan.

#### Edge Cases: Penanganan PID 1 dan Sinyal OS
- **Zombie / Orphan Processes**: Ketika PHP-FPM berjalan sebagai PID 1 di dalam container tanpa *init system*, proses `fork()` yang mengalami *crash* dapat berubah menjadi zombie process jika Master FPM gagal me-reap sinyal `SIGCHLD`. Gunakan binary `--init` (seperti `tini` bawaan Docker) jika Anda mengeksekusi command kompleks sebelum spawning FPM.
- **Permissions Mismatch**: UID/GID `www-data` di Alpine bernilai `82:82`, sedangkan di Debian/Ubuntu bernilai `33:33`. Saat menggunakan *bind-mounts* volume dari Host OS ke Alpine, file sering kali gagal diakses (`EACCES: Permission Denied`) karena ketimpangan UID mapping host dan container.

### 5. Tantangan Eksplorasi Mandiri

1. **Benchmarking IPC: TCP vs. Shared UNIX Socket**: Modifikasi konfigurasi `docker-compose.yml` di atas untuk menggunakan *shared volume socket* (`/var/run/php-fpm/php-fpm.sock`). Lakukan load-testing menggunakan tool seperti `wrk` atau `k6` dengan 1.000 concurrent connection. Analisis perbedaan throughput (RPS) dan latensi p99 antar keduanya.
2. **Kalkulasi Matematis Dynamic vs Static Pool**: Buka endpoint `/status` PHP-FPM melalui browser (pastikan Nginx mem-forward path tersebut). Simulasikan memory leak sederhana pada PHP dengan skrip alokasi array besar, amati kapan master FPM membunuh worker (`pm.max_requests`), lalu amati dampaknya terhadap resident memory (`RSS`) container via `docker stats`.
