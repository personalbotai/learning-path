## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Pada masa awal PHP (PHP 4 dan 5 awal), mekanisme pelaporan masalah didominasi oleh sistem *Error Reporting* prosedural (`E_NOTICE`, `E_WARNING`, `E_ERROR`). Error ini tidak menghentikan eksekusi secara elegan (kecuali level *fatal*) dan tidak memicu *stack unwinding* seperti sistem berorientasi objek modern. 

Sejak PHP 7.0 dan disempurnakan di PHP 8.x, arsitektur penanganan kesalahan dirombak secara fundamental melalui pengenalan antarmuka internal `Throwable`.

```
                  interface Throwable
                         /   \
                        /     \
      interface Exception     interface Error (PHP 7+)
             |                        |
    +--------+--------+      +--------+--------+
    |                 |      |                 |
RuntimeException  LogicExc   TypeError    ParseError ...
```

#### Bitmasking pada Error Levels
PHP merepresentasikan level error menggunakan *integer bitmask*. Setiap level error adalah konstanta berbasis pangkat dua ($2^n$):
- `E_ERROR` (1): Kesalahan fatal runtime; eksekusi skrip dihentikan seketika.
- `E_WARNING` (2): Peringatan runtime; eksekusi tetap berjalan.
- `E_PARSE` (4): Kesalahan sintaks kompilasi.
- `E_NOTICE` (8): Pemberitahuan runtime terkait potensi bug (misal: mengakses indeks array yang tidak terdefinisi).
- `E_DEPRECATED` (8192): Pemberitahuan fitur yang akan dihapus di versi PHP berikutnya.

Operasi seperti `error_reporting(E_ALL & ~E_NOTICE)` menggunakan operasi *bitwise AND* dan *bitwise NOT* untuk memfilter mask mana yang diizinkan masuk ke pipeline pelaporan runtime.

#### Taksonomi `Throwable`
1. **`\Exception`**: Basis untuk masalah yang umumnya dapat dipulihkan (*recoverable*) secara terprogram. Digunakan untuk logika domain aplikasi (misal: `HttpException`, `ModelNotFoundException`).
2. **`\Error`**: Basis untuk kesalahan sistemik atau kegagalan engine PHP yang sebelumnya merupakan *fatal error*. Contoh: `TypeError` (kesalahan type hinting), `ParseError` (kesalahan sintaks dari `eval()`), `ArithmeticError` (pembagian dengan nol/bit-shift negatif), dan `AssertionError`.

Aplikasi modern tidak boleh membiarkan *traditional error* beroperasi secara paralel dengan *exceptions*. Arsitektur modern mengonversi seluruh peringatan (*warnings/notices*) menjadi instans `\ErrorException` menggunakan custom error handler, sehingga seluruh siklus kegagalan dapat ditangani seragam melalui blok `try-catch-finally`.

### 2. Implementasi & Contoh Kasus Nyata

Di bawah ini adalah implementasi penanganan error tingkat produksi dengan standarisasi modern PHP 8.2+: mengonversi native error menjadi `ErrorException`, membuat taksonomi domain exception kustom, serta mendefinisikan *uncaught exception pipeline*.

```php
<?php

declare(strict_types=1);

namespace App\Core\Exceptions;

use ErrorException;
use Throwable;

// --- 1. Custom Domain Exceptions ---

interface DomainExceptionInterface extends Throwable {}

abstract class AppException extends \Exception implements DomainExceptionInterface
{
    public function __construct(
        string $message = "",
        int $code = 0,
        ?Throwable $previous = null,
        protected array $context = []
    ) {
        parent::__construct($message, $code, $previous);
    }

    public function getContext(): array
    {
        return $this->context;
    }
}

final class PaymentFailedException extends AppException
{
    public static function insufficientFunds(string $accountId, float $balance, float $amount): self
    {
        return new self(
            message: "Akun {$accountId} tidak memiliki saldo yang cukup.",
            code: 4002,
            context: [
                'account_id' => $accountId,
                'current_balance' => $balance,
                'attempted_amount' => $amount,
            ]
        );
    }
}

// --- 2. Error & Exception Infrastructure ---

final class ErrorBootstrapper
{
    public static function register(): void
    {
        // Pastikan PHP melaporkan seluruh anomali
        error_reporting(E_ALL);

        // Ubah Warning/Notice PHP native menjadi ErrorException
        set_error_handler(static function (
            int $severity,
            string $message,
            string $file,
            int $line
        ): bool {
            // Evaluasi error_reporting saat ini (menghormati operator @)
            if (!(error_reporting() & $severity)) {
                return false;
            }

            throw new ErrorException($message, 0, $severity, $file, $line);
        });

        // Global uncaught exception handler
        set_exception_handler(static function (Throwable $e): void {
            self::logAndRender($e);
        });

        // Tangkap fatal error yang mem-bypass handler standar (misal: Out of Memory)
        register_shutdown_function(static function (): void {
            $error = error_get_last();
            if ($error !== null && in_array($error['type'], [E_ERROR, E_PARSE, E_CORE_ERROR, E_COMPILE_ERROR], true)) {
                self::logAndRender(new ErrorException(
                    $error['message'],
                    0,
                    $error['type'],
                    $error['file'],
                    $error['line']
                ));
            }
        });
    }

    private static function logAndRender(Throwable $e): void
    {
        $context = ($e instanceof AppException) ? $e->getContext() : [];

        // Dalam produksi: output dialihkan ke structured logger (Monolog, STDERR, OpenTelemetry)
        $payload = [
            'type'    => get_class($e),
            'message' => $e->getMessage(),
            'code'    => $e->getCode(),
            'file'    => $e->getFile(),
            'line'    => $e->getLine(),
            'context' => $context,
            'trace'   => $e->getTrace(),
        ];

        http_response_code(500);
        header('Content-Type: application/json');
        echo json_encode(['error' => 'Internal Server Failure', 'details' => $payload], JSON_PRETTY_PRINT);
        exit(1);
    }
}

// --- 3. Eksekusi Runtime & Domain Simulation ---

ErrorBootstrapper::register();

class PaymentGateway
{
    public function charge(string $accountId, float $amount): void
    {
        $currentBalance = 150.0;

        if ($amount > $currentBalance) {
            throw PaymentFailedException::insufficientFunds($accountId, $currentBalance, $amount);
        }
    }
}

// Simulasi Alur Penanganan
try {
    $gateway = new PaymentGateway();
    $gateway->charge(accountId: "ACC-9921", amount: 500.0);
} catch (PaymentFailedException $e) {
    // Penanganan terkontrol: Catat log spesifik dan lempar upstream jika perlu
    error_log("Domain Error Caught: " . $e->getMessage() . " Context: " . json_encode($e->getContext()));
    
    // Melempar kembali atau wrapping dengan preserve trace ($previous)
    throw new \RuntimeException("Transaksi Pembayaran Dibatalkan", 500, $e);
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Zend VM)
1. **Instruksi VM**: Ketika keyword `throw` dieksekusi, Zend Engine memancarkan opcode `ZEND_THROW`.
2. **EG(exception)**: Zend VM meletakkan objek exception tersebut ke dalam pointer global executor: `EG(exception)`.
3. **Stack Unwinding**:
   - VM segera menghentikan eksekusi opcode linier berikutnya.
   - Engine membaca tabel struktur internal `zend_try_catch_element` yang diasosiasikan dengan frame fungsi saat ini.
   - Jika frame tersebut memiliki blok `catch` yang cocok (`instanceof` zend class entry), program counter dialihkan ke label catch tersebut.
   - Jika tidak cocok, engine memicu proses **Stack Unwinding**: menghancurkan variabel lokal frame saat ini (menurunkan `refcount` zval untuk memicu destruktor objek), lalu kembali turun satu level ke frame pemanggil (*caller frame*).
   - Jika mencapai root frame tanpa ada `catch`, PHP memanggil handler yang didaftarkan di `EG(user_exception_handler)` (via `set_exception_handler`).

#### Alokasi Memori / Resource
- **Backtrace Construction**: Pembuatan objek exception (`new Exception()`) membutuhkan resource yang cukup mahal. Saat instansiasi, Zend VM memanggil `zend_fetch_debug_backtrace()` untuk mengambil snapshot seluruh Call Stack saat ini (setiap frame, argument file, baris, dan parameter fungsi).
- Jika hirarki exception terlalu dalam atau dieksekusi dalam perulangan ribuan kali (*tight loops*), pemanggilan berulang ini akan memicu alokasi memori heap masif dan latensi CPU untuk membentuk array trace tersebut.

#### Trade-offs: Exception vs Result Pattern
- **Exception**: Sangat ideal untuk *exceptional cases* (kasus luar biasa yang menyimpang dari jalannya proses normal). Exception mahal dari sisi komputasi saat dilempar, tetapi tidak memiliki overhead performa pada jalur sukses (*happy path*).
- **Result Object**: Menghindari alokasi stack unwinding yang lambat, namun membutuhkan evaluasi eksplisit pada return type di setiap pemanggil, meningkatkan verbositas kode.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Exception Chaining**: Saat menangkap exception lalu melempar exception tingkat domain, selalu teruskan exception lama ke parameter `$previous`:
  ```php
  throw new OrderProcessingException("Gagal memproses order", 0, $previousException);
  ```
- **Buat Hierarchy Domain yang Terukur**: Pisahkan antara *Client/Validation Exceptions* (4xx HTTP) dan *System/Infrastructure Exceptions* (5xx HTTP) menggunakan interface marker (seperti `DomainExceptionInterface`).
- **Gunakan Named Constructors**: Buat *static factory method* pada custom exception (`PaymentFailedException::insufficientFunds(...)`) agar pesan kesalahan konsisten dan parameter konteks terikat secara kontraktual.

#### Don'ts
- **Dilarang Menelan (Swallow) Exception Tanpa Aksi**:
  ```php
  // ANTI-PATTERN: Silent failure menyembunyikan root cause bug sistemik
  try {
      $db->execute();
  } catch (\Throwable $e) {}
  ```
- **Hindari Menggunakan Operator `@` (Error Control Operator)**: Operator `@` mematikan pelaporan error sementara pada ekspresi tertentu dengan mengubah mask `error_reporting` secara dinamis menjadi `0`. Hal ini memperlambat eksekusi opcode dan menyembunyikan fatal error di lingkungan debugging.
- **Jangan Lempar `\Exception` Generic**: Melempar langsung `new \Exception("Gagal")` memaksa pemanggil untuk menangkap `\Exception` root, yang berisiko menangkap exception lain yang seharusnya tidak ditangani di layer tersebut.

#### Edge Cases
- **OOM (Out Of Memory) dan Timeouts**: Alokasi `memory_limit` yang habis memicu fatal error di level core PHP. `try-catch` **tidak** bisa menangkap kondisi ini. 
  - *Solusi*: Gunakan `register_shutdown_function()` untuk mendeteksi `E_ERROR`, dan pastikan aplikasi menyisakan "memory reserve" di awal (misal mengalokasikan string dummy 500KB yang di-`unset()` saat shutdown) agar shutdown handler memiliki cukup memori untuk memformat dan mencatat log error.

### 5. Tantangan Eksplorasi Mandiri

1. **Memory Reservation Recovery Pattern**:
   Buat sebuah skrip yang mendeklarasikan reserved memory buffer `$GLOBALS['__reserve'] = str_repeat(' ', 1024 * 512);`. Simulasikan kondisi kehabisan memori menggunakan loop tak terhingga yang mengisi array. Pada `register_shutdown_function`, bebaskan buffer tersebut (`unset($GLOBALS['__reserve'])`), tangkap kondisi out-of-memory menggunakan `error_get_last()`, dan kirimkan format JSON error ke konsol tanpa memicu OOM kedua.
2. **Context-Rich Structured Exception Logger**:
   Rancang sebuah Custom Exception hierarchy yang mengimplementasikan metode `toLogArray(): array`. Buat sebuah middleware/handler yang mampu membedah exception yang memiliki rantai keterhubungan mendalam (*nested exceptions/chained via `$previous`*) lalu mencetak pohon silsilah error secara terstruktur beserta metadata konteks masing-masing tingkat.
