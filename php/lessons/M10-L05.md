## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, PHP beroperasi dengan model **Shared-Nothing Architecture** melalui PHP-FPM (FastCGI Process Manager). Dalam model ini, setiap *request* HTTP yang masuk akan memicu siklus hidup penuh: *Booting* (memuat file, inisialisasi framework, koneksi database) -> *Eksekusi* -> *Terminasi* (memori dibersihkan). Model ini sangat aman dari kebocoran memori (memory leak), namun memiliki *overhead* performa yang masif, terutama pada framework modern yang berat.

Untuk mencapai *High Performance*, paradigma bergeser ke **Long-Running Process** (Application Server). Aplikasi di-*boot* hanya sekali, dan tetap berada di memori (RAM) untuk melayani ribuan *request* secara berurutan atau konkuren.

Tiga pemain utama dalam ekosistem ini memiliki pendekatan arsitektur yang berbeda:

1.  **Swoole**: Sebuah *extension* PHP yang ditulis dalam C/C++. Swoole menggantikan web server tradisional (Nginx/Apache) dengan menyediakan *Event-Loop* asinkron dan *Coroutines* (green threads) langsung di level *runtime* PHP. Swoole memungkinkan PHP berjalan secara *non-blocking* I/O mirip dengan Node.js atau Go.
2.  **RoadRunner**: Application server yang ditulis dalam Golang. RoadRunner bertindak sebagai *load balancer* dan web server yang mengelola sekumpulan (pool) *worker* PHP CLI. Komunikasi antara Go dan PHP dilakukan melalui protokol RPC/IPC yang sangat cepat bernama **Goridge**.
3.  **FrankenPHP**: Application server modern berbasis Caddy (Golang). Berbeda dengan RoadRunner yang menggunakan RPC, FrankenPHP menanamkan (embed) *runtime* PHP langsung ke dalam *binary* Go menggunakan **CGO**. Ini menghilangkan *overhead* komunikasi antar-proses dan mendukung fitur modern secara native seperti HTTP/3, Early Hints, dan integrasi Mercure.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah perbandingan implementasi *Long-Running Process*. Kita akan melihat bagaimana paradigma kode berubah dari skrip prosedural biasa menjadi sebuah *Worker Loop*.

#### Contoh 1: Worker Loop pada FrankenPHP / RoadRunner
```php
<?php
// worker.php
require __DIR__ . '/vendor/autoload.php';

// 1. BOOTSTRAPPING (Dijalankan HANYA SEKALI)
// Inisialisasi framework, koneksi DB, load konfigurasi
$app = new Framework\Application();
$app->bootstrap();

// 2. WORKER LOOP (Menunggu dan memproses request)
// Pada FrankenPHP, fungsi frankenphp_handle_request akan memblokir 
// sampai ada request masuk.
$handler = function () use ($app) {
    // Tangkap request dari superglobals (yang sudah di-inject oleh server)
    $request = Framework\Http\Request::createFromGlobals();
    
    // Proses request
    $response = $app->handle($request);
    $response->send();

    // PENTING: Bersihkan state (memory) setelah request selesai
    $app->terminate($request, $response);
};

// Loop ini menjaga proses PHP tetap hidup
for ($requests = 0; $requests < 500; $requests++) {
    // FrankenPHP API
    if (function_exists('frankenphp_handle_request')) {
        $preventWorkerExit = frankenphp_handle_request($handler);
        if (!$preventWorkerExit) break;
    }
}
```

#### Contoh 2: Asynchronous Server dengan Swoole
```php
<?php
// swoole_server.php
use Swoole\Http\Server;
use Swoole\Http\Request;
use Swoole\Http\Response;

// Inisialisasi Server pada port 9501
$server = new Server("0.0.0.0", 9501);

// Konfigurasi jumlah worker dan coroutine
$server->set([
    'worker_num' => 4,
    'enable_coroutine' => true
]);

// Event listener saat request masuk
$server->on("request", function (Request $request, Response $response) {
    // Di dalam sini, kita berada dalam Coroutine context.
    // Operasi I/O (seperti query DB menggunakan Swoole PDO) tidak akan memblokir worker.
    
    // Jangan gunakan $_GET/$_POST global! Gunakan object $request dari Swoole.
    $name = $request->get['name'] ?? 'World';
    
    $response->header("Content-Type", "text/plain");
    $response->end("Hello, {$name}! Powered by Swoole Coroutines.\n");
});

echo "Swoole server running on http://127.0.0.1:9501\n";
$server->start();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**:
  - Pada **FPM**, Nginx menerima HTTP request, meneruskannya via FastCGI ke FPM master, yang kemudian menugaskan *worker* untuk mengeksekusi file `.php` dari awal hingga akhir.
  - Pada **RoadRunner/FrankenPHP**, Go *binary* menerima HTTP request. Go kemudian mengirimkan data request (headers, body) ke *worker* PHP yang sedang *idle* di dalam *loop*. Setelah PHP mengembalikan response, *worker* kembali ke status *idle* tanpa dimatikan.
  - Pada **Swoole**, *Event Loop* (berbasis `epoll` di Linux) mengatur antrean request. Jika ada operasi I/O (misal: query database), Swoole secara otomatis menangguhkan (suspend) *coroutine* saat ini dan mengerjakan request lain, lalu melanjutkannya (resume) saat data dari database siap.

- **Alokasi Memori / Resource**:
  - Karena proses PHP tidak mati, variabel global (`global $var`), *static properties* (`public static $instance`), dan *Singleton pattern* akan **bertahan (persist)** antar request.
  - Jika Anda menambahkan data ke dalam array statis di setiap request tanpa menghapusnya, RAM akan terus membengkak hingga terjadi *Out of Memory* (OOM) dan *worker* *crash*.
  - *Garbage Collector* (GC) PHP didesain untuk siklus hidup pendek. Pada *long-running process*, GC mungkin tidak cukup agresif. Seringkali *worker* diatur untuk *restart* otomatis setelah memproses N request (misal: 500 request) untuk mencegah kebocoran memori (dikenal sebagai *Max Requests limit*).

- **Trade-offs**:
  - **Keuntungan**: Latensi turun drastis (hingga 10x lebih cepat) karena tidak ada *overhead bootstrapping* framework. Kemampuan menangani koneksi konkuren (WebSockets, SSE) menjadi mungkin di PHP.
  - **Kerugian**: Kompleksitas kode meningkat tajam. Developer harus sangat berhati-hati terhadap *state leakage* (kebocoran state). *Debugging* lebih sulit karena error pada satu request bisa merusak state untuk request berikutnya.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Laravel Octane** jika Anda menggunakan Laravel. Octane mengabstraksi kompleksitas Swoole, RoadRunner, dan FrankenPHP, serta menangani pembersihan *state* secara otomatis.
  - **Reset State**: Selalu bersihkan *Service Container*, *Singletons*, dan variabel statis di akhir setiap request.
  - **Gunakan Connection Pooling**: Karena *worker* hidup terus, koneksi database juga tetap terbuka. Gunakan *connection pool* atau pastikan untuk menangani error "MySQL server has gone away" dengan melakukan *reconnect*.

- **Don'ts**:
  - **JANGAN gunakan `exit()` atau `die()`**. Memanggil fungsi ini akan langsung membunuh *worker process*, menyebabkan request gagal dan memaksa server melakukan *respawn worker* (menghilangkan keuntungan performa).
  - **JANGAN gunakan Superglobals** (`$_GET`, `$_POST`, `$_SESSION`). Data ini mungkin tidak di-reset dengan benar antar request oleh application server. Selalu gunakan *Request Object* yang disediakan oleh framework/server.

- **Edge Cases**:
  - **Third-Party Packages**: Banyak *library* PHP lawas diasumsikan berjalan di lingkungan FPM. Mereka mungkin menggunakan variabel statis untuk *caching* internal yang akan bocor di lingkungan *long-running*. Anda mungkin perlu melakukan *fork* atau mencari alternatif *library* yang *coroutine/worker-safe*.
  - **File Uploads**: Penanganan memori untuk *multipart/form-data* yang besar harus diperhatikan agar tidak menghabiskan RAM *worker*.

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Memory Leak**: Buatlah sebuah *worker script* sederhana menggunakan FrankenPHP atau RoadRunner. Buat sebuah kelas dengan *static array*, lalu *push* string acak sebesar 1MB ke dalam array tersebut pada setiap request. Gunakan `wrk` atau `ab` untuk menembak server dan pantau penggunaan RAM menggunakan `htop` hingga *worker crash*.
2. **Benchmark Komparatif**: Setup aplikasi Laravel standar. Jalankan menggunakan Nginx + PHP-FPM, lalu jalankan aplikasi yang sama menggunakan Laravel Octane (FrankenPHP). Gunakan *load testing tool* seperti `k6` dan bandingkan metrik *Requests per Second* (RPS) dan *Tail Latency* (p95/p99).
3. **Eksplorasi Swoole Coroutine**: Tulis skrip Swoole yang melakukan 3 HTTP request ke API eksternal (misal: mengambil data cuaca, kurs mata uang, dan berita). Gunakan `Swoole\Coroutine\Http\Client` dan `Swoole\Coroutine\WaitGroup` untuk menjalankan ketiganya secara paralel (*concurrently*), lalu ukur total waktu eksekusinya dibandingkan dengan `file_get_contents` biasa.
