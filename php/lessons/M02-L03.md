### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur perangkat lunak berbasis OOP, **Interface** mendefinisikan sebuah *kontrak perilaku (behavioral contract)* tanpa mengekspos detail implementasi internal ataupun status (*state*). Berbeda dengan *Abstract Class* yang dapat membagikan implementasi parsial dan *state* (melalui properti), Interface murni berperan sebagai cetak biru fungsionalitas publik.

#### Alasan Keberadaan & Prinsip Arsitektur
Interface adalah pondasi utama dalam penerapan dua pilar SOLID:
1. **Interface Segregation Principle (ISP)**: Klien tidak boleh dipaksa bergantung pada antarmuka (*interface*) yang tidak digunakannya.
2. **Dependency Inversion Principle (DIP)**: Modul tingkat tinggi (*high-level modules*) tidak boleh bergantung pada modul tingkat rendah (*low-level modules*). Keduanya harus bergantung pada abstraksi (*interface*).

Secara arsitektural (misalnya pada *Hexagonal / Ports and Adapters Architecture*), interface bertindak sebagai *Port*. Domain inti aplikasi Anda hanya mengetahui kontrak (*Port*), sedangkan teknologi pihak ketiga (database, payment gateway, mailer) bertindak sebagai *Adapter* yang mengimplementasikan kontrak tersebut.

```
       [ High-Level Domain Service ]
                     │
                     ▼ (Bergantung pada kontrak)
        <<interface: PaymentGateway>>
                     ▲
         ┌───────────┴───────────┐
         │                       │
[ StripeAdapter ]      [ MidtransAdapter ]
 (Low-Level Driver)      (Low-Level Driver)
```

#### Mekanisme Subtipe: LSP dan Varians
Dalam PHP 8+, Interface memberlakukan validasi ketat terhadap **Liskov Substitution Principle (LSP)** melalui mekanisme varians tipe:
- **Parameter Contravariance**: Implementasi method dapat menerima tipe parameter yang lebih luas (kurang spesifik) daripada yang didefinisikan di interface.
- **Return Type Covariance**: Implementasi method dapat mengembalikan tipe yang lebih sempit (lebih spesifik) daripada yang didefinisikan di interface.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: **Sistem Pemrosesan Transaksi Multi-Gateway**. Sistem harus mampu mengeksekusi pembayaran melalui berbagai vendor (misal: Stripe dan Midtrans) secara *interchangeable* tanpa merusak modul checkout.

```php
<?php

declare(strict_types=1);

namespace App\Payments;

// 1. Value Object & Data Transfer Object (DTO) untuk Integritas Tipe Data
readonly class PaymentRequest
{
    public function __construct(
        public string $transactionId,
        public int $amountInCents,
        public string $currency,
        public array $metadata = []
    ) {}
}

enum PaymentStatus: string
{
    case SUCCESS = 'success';
    case PENDING = 'pending';
    case FAILED = 'failed';
}

readonly class PaymentResponse
{
    public function __construct(
        public PaymentStatus $status,
        public string $providerTransactionId,
        public ?string $errorMessage = null
    ) {}
}

// 2. Kontrak (Interface)
interface PaymentGatewayInterface
{
    /**
     * Memproses tagihan pembayaran.
     * Mengembalikan PaymentResponse terlepas dari vendor yang digunakan.
     *
     * @throws PaymentGatewayException Jika terjadi kesalahan fatal jaringan/protokol.
     */
    public function charge(PaymentRequest $request): PaymentResponse;

    /**
     * Mendukung pembatalan / pengembalian dana.
     */
    public function refund(string $providerTransactionId, int $amountInCents): bool;
}

class PaymentGatewayException extends \RuntimeException {}

// 3. Implementasi 1: Stripe Adapter
final class StripePaymentGateway implements PaymentGatewayInterface
{
    public function __construct(
        private string $secretKey,
        private string $apiVersion = '2023-10-16'
    ) {}

    public function charge(PaymentRequest $request): PaymentResponse
    {
        // Simulasi komunikasi jaringan / SDK Stripe
        // $stripePayload = ['amount' => $request->amountInCents, 'currency' => $request->currency];
        
        $isSuccess = true; // Simulasi hasil response HTTP 200

        if (!$isSuccess) {
            return new PaymentResponse(
                status: PaymentStatus::FAILED,
                providerTransactionId: '',
                errorMessage: 'Stripe charge declined: Card had insufficient funds.'
            );
        }

        return new PaymentResponse(
            status: PaymentStatus::SUCCESS,
            providerTransactionId: 'ch_stripe_' . bin2hex(random_bytes(8))
        );
    }

    public function refund(string $providerTransactionId, int $amountInCents): bool
    {
        // Eksekusi logic refund Stripe
        return true;
    }
}

// 4. Implementasi 2: Midtrans Adapter
final class MidtransPaymentGateway implements PaymentGatewayInterface
{
    public function __construct(
        private string $serverKey,
        private bool $isProduction = false
    ) {}

    public function charge(PaymentRequest $request): PaymentResponse
    {
        // Simulasi komunikasi API Snap Midtrans
        // Format parameter internal Midtrans dapat berbeda, namun output dinormalisasi
        
        return new PaymentResponse(
            status: PaymentStatus::SUCCESS,
            providerTransactionId: 'midtrans-' . bin2hex(random_bytes(6))
        );
    }

    public function refund(string $providerTransactionId, int $amountInCents): bool
    {
        // Midtrans Direct Refund API logic
        return true;
    }
}

// 5. High-Level Consumer (Decoupled Domain Service)
final class CheckoutService
{
    // Menginjeksi abstraksi, bukan konkrit implementasi
    public function __construct(
        private PaymentGatewayInterface $gateway
    ) {}

    public function processOrder(string $orderId, int $totalAmount): PaymentResponse
    {
        $request = new PaymentRequest(
            transactionId: $orderId,
            amountInCents: $totalAmount,
            currency: 'IDR'
        );

        // Eksekusi polymorphically tanpa tahu apakah ini Stripe, Midtrans, atau Mock
        return $this->gateway->charge($request);
    }
}

// --- Driver Execution / Polymorphism Demo ---

$stripeGateway = new StripePaymentGateway(secretKey: 'sk_test_xxx');
$checkoutWithStripe = new CheckoutService($stripeGateway);
$res1 = $checkoutWithStripe->processOrder('ORD-001', 15000000);
echo "Stripe Ref: " . $res1->providerTransactionId . "\n";

$midtransGateway = new MidtransPaymentGateway(serverKey: 'SB-Mid-xxx');
$checkoutWithMidtrans = new CheckoutService($midtransGateway);
$res2 = $checkoutWithMidtrans->processOrder('ORD-002', 25000000);
echo "Midtrans Ref: " . $res2->providerTransactionId . "\n";
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Zend Engine Internals)
Di dalam Zend Engine (C-Level runtime PHP):
1. **Representasi Struktur Data**: Interface direpresentasikan oleh `zend_class_entry` di memory engine, sama halnya dengan class normal. Namun, field `ce_flags` memiliki bitmask `ZEND_ACC_INTERFACE`.
2. **Penyimpanan Opcodes**: Method pada interface tidak memiliki bytecode atau pointer instruksi opcode (`zend_op_array`). Method tersebut hanya menyimpan metadata definisi signature di dalam tabel `function_table`.
3. **Fase Linking (Interface Inheritance)**: Ketika class `Foo` mengimplementasikan `BarInterface`, Zend Engine mengeksekusi `zend_do_implement_interface()`. Engine akan mengiterasi setiap method di interface dan mencocokkannya dengan `function_table` class konkrit.
   - Pengecekan kompatibilitas signature (tipe parameter, return type, visibility) dilakukan di fase kompilasi jika kedua class berada dalam file yang sama, atau saat runtime linking jika menggunakan autoloader.
   - Jika terdapat inkonsistensi signature, Zend Engine melempar `Fatal Error` (`Compile Error`).

#### Alokasi Memori / Resource
- Ketika class mengimplementasikan interface, array internal `interfaces` pada `zend_class_entry` dialokasikan untuk menampung pointer ke `zend_class_entry` dari interface tersebut.
- **Dispatching Overhead**: Pemanggilan polymorphic method (`$this->gateway->charge()`) di-compile menjadi instruksi opcode `ZEND_INIT_METHOD_CALL` dan `ZEND_DO_FCALL`. PHP menggunakan **Polymorphic Inline Cache (PIC)**: engine menyimpan cache offset pemanggilan method pada `zend_op` untuk menghindari traversal berulang ke hash table method saat dipanggil dalam perulangan intensif.

#### Trade-offs
- **Abstraksi vs Direct Call**: Ada sedikit *lookup indirection overhead* dibandingkan memanggil method final class secara langsung tanpa interface (meskipun terhitung negligible dalam skenario web I/O-bound).
- **Maintenance Cost**: Mengubah signature method pada interface akan memaksa refactoring ke seluruh class yang mengimplementasikannya (*breaking change cascading*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Interface Segregation**: Pecah interface besar menjadi interface granular. Gunakan interface kecil (1–3 method), mirip dengan filosofi PSR (`Psr\Log\LoggerInterface`, `Stringable`).
- **Gunakan Type Hint Interface pada Dependency Injection**: Selalu minta antarmuka pada constructor service, bukan kelas konkrit, untuk memudahkan unit testing melalui *mocking*.
- **Gunakan Interface Segregation dengan Interface Inheritance**: Gabungkan interface kecil jika dibutuhkan melalui ekstensi:
  ```php
  interface ReadableStream { public function read(): string; }
  interface WritableStream { public function write(string $data): void; }
  interface DuplexStream extends ReadableStream, WritableStream {}
  ```

#### Don'ts
- **Leaky Abstractions**: Jangan mengekspos detail vendor ke dalam kontrak.
  *Buruk:* `public function charge(StripeCustomerObject $customer);`
  *Baik:* `public function charge(PaymentRequest $request);`
- **Jangan Menggunakan Interface untuk Menyimpan Status Konstan yang Erat Kaitannya dengan Implementasi**: Hindari menaruh konstanta spesifik implementasi di dalam interface.
- **Menghindari God Interfaces**: Interface dengan belasan method adalah tanda bahwa abstraksi Anda memecah prinsip Single Responsibility.

#### Edge Cases
1. **Name Collision pada Multiple Interfaces**: Jika class mengimplementasikan dua interface yang memiliki nama method yang sama persis:
   ```php
   interface A { public function run(): void; }
   interface B { public function run(): void; }
   class Worker implements A, B {
       public function run(): void {} // Valid, selama signature (argumen, tipe) identik!
   }
   ```
   Jika tipe parameter atau return type bertentangan (misal `A::run(): void` dan `B::run(): int`), PHP akan melempar **Fatal Compile Error** karena konflik resolusi varians tipe yang tidak dapat dipertemukan.
2. **Interface Constants Inheritance**: Di PHP 8.1+, class konkrit dapat menimpa (*override*) konstanta interface, asalkan tipenya kompatibel, namun interface tidak dapat menimpa konstanta dari interface induk yang di-*extend*.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Pattern Strategy & Fallback Engine**:
   Buat antarmuka `NotificationSenderInterface` dengan method `send(string $to, string $message): bool`. Buat 2 implementasi: `SmsSender` dan `EmailSender`. Kemudian, buat implementasi ketiga bernama `FallbackNotificationSender` yang menerima array dari `NotificationSenderInterface[]`. Jika implementasi pertama gagal (`false`/throw exception), ia harus secara otomatis beralih memanggil implementasi berikutnya (*circuit-breaker / fallback behavior*).
2. **Eksplorasi Return Type Covariance**:
   Buat interface `RepositoryInterface` dengan method `find(int $id): ?object`. Buat class `UserRepository` yang mengimplementasikannya, tetapi ubah return type-nya menjadi `?UserEntity`. Jalankan script untuk membuktikan bagaimana Zend Engine memproses validasi *Covariance* secara legal tanpa error.
