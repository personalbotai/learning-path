### 1. Konsep & Arsitektur Mendalam

PHP secara tradisional beroperasi di bawah model *share-nothing architecture* melalui PHP-FPM, di mana siklus hidup (lifecycle) proses terikat langsung dengan siklus hidup *HTTP request*. Setiap alokasi memori, koneksi I/O, dan konteks eksekusi dihancurkan begitu respon terkirim ke klien.

Ketika sistem menghadapi komputasi berat (misalnya pemrosesan media, ekspor CSV jutaan baris, interaksi API eksternal yang lambat), mempertahankan model sinkronus akan memblokir *thread* FPM, menghabiskan *worker pool*, dan menyebabkan HTTP 504 Gateway Timeout. Solusinya adalah memisahkan eksekusi sinkronus (penerimaan instruksi) dari eksekusi asinkronus (pemrosesan data) menggunakan **Message Queue**.

```
[Client] 
   │ (HTTP POST)
   ▼
[Nginx / PHP-FPM] ──(Publish Job)──► [Message Broker]
   │ (HTTP 202 Accepted)               │ (AMQP / Redis Protocol)
   ▼                                   ▼
[Response to Client]             [Long-Running PHP CLI Workers]
                                       │ (Process Data)
                                       ▼
                                 [Database / Storage]
```

#### Komparasi Arsitektural: RabbitMQ vs Redis

| Parameter | RabbitMQ (AMQP 0-9-1) | Redis (List / Streams) |
| :--- | :--- | :--- |
| **Model Arsitektur** | *Smart Broker / Dumb Consumer* (Broker mengatur perutean, status pengiriman, dan *redelivery*). | *Dumb Broker / Smart Consumer* (Consumer harus mengelola *polling*, *acknowledgement*, dan partisi sendiri). |
| **Penyimpanan Data** | Berbasis disk dengan *memory paging*. Sangat andal untuk garansi pengiriman (*durability*). | Berbasis *In-Memory* dengan opsi persistensi (RDB/AOF). Fokus pada throughput ekstrim dengan latensi sub-milidetik. |
| **Mekanisme Routing** | Kompleks melalui **Exchanges** (*Direct, Fanout, Topic, Headers*) dan *Bindings*. | Terbatas. *List* hanya mendukung *point-to-point* (`LPUSH`/`BRPOP`). *Streams* mendukung *Consumer Groups*. |
| **Garansi Pengiriman** | Mendukung *At-least-once*, *At-most-once*, transaksional, dan *Publisher Confirms*. | Bergantung implementasi: *At-most-once* (List) atau *At-least-once* (Streams dengan `XACK`). |

#### Anatomi AMQP 0-9-1 pada RabbitMQ
1. **Producer**: Aplikasi pengirim pesan.
2. **Exchange**: Komponen penerima pesan dari Producer yang bertugas merutekan pesan ke antrean berdasarkan *Routing Key*.
3. **Queue**: *Buffer* memori/disk yang menampung pesan sampai dikonsumsi.
4. **Consumer**: *Daemon process* CLI yang mengambil dan memproses pesan dari antrean.
5. **Channel**: Kanal virtual di dalam satu koneksi TCP tunggal. Multiplexing koneksi TCP sangat krusial untuk efisiensi resource jaringan.

### 2. Implementasi & Contoh Kasus Nyata

Implementasi ini menggunakan pustaka standar industri `php-amqplib/php-amqplib` untuk membuat *worker* RabbitMQ yang *production-ready* dengan fitur:
- Penanganan sinyal POSIX untuk *graceful shutdown*.
- Pembatasan *prefetch count* (QoS).
- Mekanisme *Manual Acknowledgement* (ACK / NACK) dengan *Dead Letter Exchange* (DLX).

#### Worker Implementation (`worker.php`)

```php
<?php

declare(strict_types=1);

namespace App\Queue;

require_once __DIR__ . '/vendor/autoload.php';

use PhpAmqpLib\Connection\AMQPStreamConnection;
use PhpAmqpLib\Message\AMQPMessage;
use PhpAmqpLib\Wire\AMQPTable;
use Throwable;

// 1. Setup Signal Handler untuk Graceful Shutdown (POSIX)
$shouldStop = false;
pcntl_async_signals(true);

$signalHandler = function (int $signo) use (&$shouldStop): void {
    echo "\n[Signal] Menerima sinyal terminasi ({$signo}). Menyiapkan graceful shutdown...\n";
    $shouldStop = true;
};

pcntl_signal(SIGTERM, $signalHandler);
pcntl_signal(SIGINT, $signalHandler);

// 2. Inisialisasi Koneksi TCP dan Multiplexed Channel
$connection = new AMQPStreamConnection('localhost', 5672, 'guest', 'guest');
$channel = $connection->channel();

// 3. Konfigurasi Dead Letter Exchange (DLX) untuk pesan gagal/poison pills
$deadLetterExchange = 'dlx.orders';
$deadLetterQueue = 'orders_failed_queue';

$channel->exchange_declare($deadLetterExchange, 'direct', false, true, false);
$channel->queue_declare($deadLetterQueue, false, true, false, false);
$channel->queue_bind($deadLetterQueue, $deadLetterExchange, 'orders.failed');

// 4. Konfigurasi Work Queue Utama yang terikat ke DLX
$mainExchange = 'app.orders';
$mainQueue = 'orders_processing_queue';

$channel->exchange_declare($mainExchange, 'direct', false, true, false);

$queueArgs = new AMQPTable([
    'x-dead-letter-exchange' => $deadLetterExchange,
    'x-dead-letter-routing-key' => 'orders.failed',
]);

$channel->queue_declare(
    queue: $mainQueue,
    passive: false,
    durable: true,      // Queue persisten terhadap restart broker
    exclusive: false,
    auto_delete: false,
    arguments: $queueArgs
);

$channel->queue_bind($mainQueue, $mainExchange, 'order.created');

// 5. Quality of Service (QoS): Batasi worker hanya mengambil 1 pesan sekaligus
// Mencegah worker menelan ribuan task ke memory internal sebelum selesai diproses
$channel->basic_qos(prefetch_size: 0, prefetch_count: 1, a_global: false);

echo " [*] Menunggu pesan di {$mainQueue}. Tekan CTRL+C untuk keluar.\n";

// 6. Callback Penanganan Job
$callback = function (AMQPMessage $message) use (&$shouldStop): void {
    $payload = json_decode($message->getBody(), true);

    echo " [x] Memproses Order ID: " . ($payload['order_id'] ?? 'Unknown') . "\n";

    try {
        if (!isset($payload['order_id']) || $payload['order_id'] <= 0) {
            throw new \InvalidArgumentException("Invalid Order ID Payload");
        }

        // Simulasi latensi pemrosesan (e.g., charge kartu kredit, generate invoice)
        usleep(500000); // 500ms

        // ACK: Konfirmasi sukses proses, hapus dari queue
        $message->ack();
        echo " [v] Sukses diproses.\n";
    } catch (Throwable $e) {
        echo " [!] Gagal memproses: {$e->getMessage()}. Melempar ke DLX.\n";
        
        // NACK: Tolak pesan dan JANGAN kembalikan ke antrean utama (requeue = false)
        // Pesan otomatis dialihkan oleh RabbitMQ ke Dead Letter Exchange
        $message->nack(requeue: false);
    }
};

$channel->basic_consume(
    queue: $mainQueue,
    consumer_tag: '',
    no_local: false,
    no_ack: false,       // Wajib false agar manual ACK berlaku
    exclusive: false,
    nowait: false,
    callback: $callback
);

// 7. Event Loop Non-blocking terkontrol
while ($channel->is_consuming()) {
    try {
        // Timeout 3 detik agar loop mengecek variabel $shouldStop secara berkala
        $channel->wait(null, false, 3.0);
    } catch (\PhpAmqpLib\Exception\AMQPTimeoutException $e) {
        // Timeout normal ketika antrean kosong, lanjutkan evaluasi loop
    }

    if ($shouldStop) {
        echo " [*] Menghentikan konsumsi pesan baru...\n";
        break;
    }
}

// Cleanup resources
$channel->close();
$connection->close();
echo " [*] Worker berhenti dengan aman.\n";
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Long-Running CLI vs FPM
*   **Persistent Process:** PHP CLI di atas tidak mati setelah menangani pesan. Kode berjalan di satu proses OS tunggal.
*   **Socket I/O & Heartbeats:** Komunikasi AMQP bergantung pada soket jaringan *stream*. RabbitMQ mengirim paket *heartbeat* secara periodik untuk memvalidasi apakah koneksi klien masih hidup. Jika worker menjalankan fungsi komputasi sinkronus yang memblokir eksekusi lebih lama dari nilai *heartbeat interval* tanpa memanggil `$channel->wait()`, broker akan menganggap worker mati dan memutus koneksi TCP secara sepihak (*Connection Reset*).

#### Alokasi Memori dan Resource Leakage
*   **Zend Engine Memory Management:**
    Zend Engine mengalokasikan memori menggunakan *emalloc()* (engine allocator) yang didesain untuk *request boundary*. Pada CLI jangka panjang, siklus dereferensi variabel harus dikelola secara ketat.
*   **Cyclic References & Garbage Collection:**
    Objek yang memiliki relasi sirkular (misal: `$a->child = $b; $b->parent = $a;`) tidak langsung dihapus dari memori saat di-`unset()`. Penumpukan siklus ini mengharuskan eksekusi periodik `gc_collect_cycles()`, jika tidak, `memory_get_usage()` akan naik terus-menerus (*memory bloat*).
*   **PDO Ghost Connection:**
    Objek koneksi database yang dibuat di luar loop akan mengalami *timeout* dari sisi server MySQL/PostgreSQL (`wait_timeout`). Ketika pesan berikutnya datang setelah antrean sepi berjam-jam, PDO akan melemparkan galat `MySQL server has gone away` karena koneksi TCP telah ditutup secara diam-diam oleh DB server.

```
       Memory Consumption Pattern (Long-running Worker)
MB
▲
│        /│      /│      /│  <-- Leak tanpa Garbage Collection / Unset
│       / │     / │     / │
│      /  │    /  │    /  │
├─────/───┴───/───┴───/───┴───  Baseline yang sehat (Clean State)
└────────────────────────────► Time
```

#### Trade-offs: Redis Worker vs RabbitMQ Worker
*   **Redis Worker (`BRPOP`/Streams):**
    *   *Kelebihan:* Setup sangat murah, *footprint* memori broker rendah, throughput sangat tinggi (mencapai 100k+ ops/detik).
    *   *Kekurangan:* Minim kapabilitas perutean logis. Jika Redis kehabisan memori (*OOM*), sistem bisa *crash* atau menjatuhkan kunci pesan berdasarkan *eviction policy* (misal `volatile-lru`).
*   **RabbitMQ Worker:**
    *   *Kelebihan:* Mekanisme garansi data superior. Pengaturan *prefetch*, penanganan NACK terdistribusi via DLX, dan proteksi konsumsi berlebih pada worker.
    *   *Kekurangan:* Membutuhkan resource Erlang VM yang lebih tinggi, arsitektur konfigurasi pertukaran (Exchange) lebih kompleks.

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Gunakan Process Supervisor:** Jalankan *daemon* worker menggunakan alat orkestrasi seperti **Systemd** atau **Supervisor**. Biarkan Supervisor me-restart worker jika mati karena batas memori terlampaui.
2. **Definisikan Hard Memory Limit:** Evaluasi penggunaan memori secara manual di setiap iterasi loop:
   ```php
   if (memory_get_usage(true) > 128 * 1024 * 1024) { // 128MB
       exit(0); // Biarkan supervisor melakukan restart dengan state yang bersih
   }
   ```
3. **Reset State Eksternal:** Selalu tutup koneksi basis data atau gunakan mekanisme *reconnect* sebelum memproses pesan baru jika ada potensi *idle timeout*.
4. **Idempoten:** Desain logika konsumen agar bersifat *idempotent*. Jika jaringan putus tepat setelah worker memproses tugas tetapi sebelum ACK terkirim, broker akan mengirimkan ulang pesan yang sama ke worker lain.

#### Don'ts
1. **Hindari State Statis Global:** Jangan gunakan variabel `static` atau Singleton yang menyimpan data transaksi di dalam *loop consumer*. Data dari *job* A akan berisiko merembes ke kalkulasi *job* B.
2. **Jangan Menggunakan `prefetch_count: 0` (Unbounded):** Nilai `0` berarti RabbitMQ akan membanjiri worker dengan seluruh pesan yang ada di queue ke dalam memori proses PHP, yang dapat memicu `Fatal error: Allowed memory size exhausted`.
3. **Jangan Melakukan Requeue Tanpa Batas:** Menggunakan `$message->nack(requeue: true)` ketika menghadapi eror logika kode akan memicu *infinite loop* (poison pill) dengan penggunaan CPU mencapai 100%.

#### Edge Cases
*   **Signal Handling saat Blocking I/O:** Fungsi seperti `sleep()` atau eksekusi fungsi C extension yang memblokir I/O soket dapat menunda penangkapan sinyal OS (`SIGTERM`). Gunakan `usleep()` dengan iterasi kecil atau gunakan timeout terukur pada `$channel->wait()`.
*   **JSON Serialization Payload:** Selalu validasi bahwa struktur data yang di-unserialize dari antrean benar-benar sesuai skema. Hindari penggunaan native PHP `unserialize()` untuk payload antrean karena membuka celah keamanan *Object Injection* / RCE.

### 5. Tantangan Eksplorasi Mandiri

1. **Dead Letter Delay Queue Pattern:**
   Rancang arsitektur menggunakan RabbitMQ di mana pesan yang gagal diproses tidak langsung masuk ke antrean *dead-letter*, melainkan diarahkan ke antrean transisi dengan TTL (*Time-To-Live*) dan tanpa *consumer*, yang setelah masa TTL-nya habis akan mengarahkan pesan kembali ke antrean utama (mekanisme *Exponential Backoff Retry* murni berbasis AMQP).
2. **Redis Streams vs Redis List Worker:**
   Implementasikan skrip worker PHP sederhana yang memanfaatkan fitur **Redis Streams** (`XREADGROUP`, `XACK`, dan `XPENDING`) menggunakan ekstensi `ext-redis`. Analisis bagaimana Streams menyelesaikan permasalahan hilangnya pesan ketika proses worker mati secara mendadak (`SIGKILL`) di tengah pemrosesan, sebuah kelemahan utama dari pola `BRPOP` konvensional.
