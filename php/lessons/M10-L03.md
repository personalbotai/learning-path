### 1. Konsep & Arsitektur Mendalam

Secara tradisional, siklus eksekusi PHP pada Zend Engine terdiri dari empat tahap utama: **Lexing (Scanning)**, **Parsing (AST generation)**, **Compilation (Opcode generation)**, dan **Execution (Zend VM Interpretation)**. Pada setiap request tanpa optimasi, siklus ini diulang terus-menerus sehingga menyebabkan pemborosan CPU cycle yang masif untuk parsing kode sumber yang sama.

```
[PHP Source Code] 
       │
       ▼ (Lexing & Parsing)
[Abstract Syntax Tree (AST)]
       │
       ▼ (Compilation)
[Zend Opcodes] ◄─────────────── OPcache (Menyimpan bytecode di Shared Memory)
       │
       ├──► [Zend Virtual Machine (Interpreter Loop)] ──► [Machine Code (CPU)]
       │
       ▼ (JIT Compilation - PHP 8.0+)
[Native Machine Code (x86-64/ARM64)] ─────────────► Langsung dieksekusi CPU
```

#### OPcache: Bytecode Caching & Optimization Passes
OPcache mengeliminasi fase *Lexing*, *Parsing*, dan *Compilation* dengan menyimpan array struktur `zend_op_array` di Shared Memory (SHM). Ketika sebuah skrip diminta kembali:
1. Zend Engine memeriksa apakah opcodes skrip tersebut sudah teralokasi di SHM.
2. Jika ada (*cache hit*), Zend Engine langsung melompati tahap kompilasi dan mengirim pointer `zend_op_array` ke executor Zend VM.
3. OPcache juga menjalankan serangkaian *optimization passes* (Level 1 hingga 14 pada SSA optimizer): Dead Code Elimination (DCE), Constant Folding, Jump Elimination, dan Type Inference lokal.

#### JIT (Just-In-Time) Compiler
Diperkenalkan pada PHP 8.0, JIT bekerja bukan dengan mengubah PHP langsung menjadi binary mandiri, melainkan bertindak sebagai ekstensi dari OPcache. JIT menerjemahkan Zend Opcodes menjadi instruksi mesin asli (*native machine instructions*) secara dinamis menggunakan library **DynASM**.

Zend VM standar bekerja menggunakan loop raksasa berbasis pointer fungsi atau *direct-threaded code*:
```c
// Representasi konseptual Zend VM Interpreter Loop
while (1) {
    opline->handler(ZEND_OPCODE_ARGS_PASSTHRU);
    opline++;
}
```
Setiap eksekusi opcode membutuhkan overhead dispatch, type check, dan register indirection. JIT mengeliminasi interpretasi ini dengan:
- **Function JIT**: Mengompilasi seluruh fungsi menjadi instruksi mesin saat dipanggil.
- **Tracing JIT**: Mengidentifikasi *hot code paths* (loop atau instruksi yang sering dieksekusi berulang kali menggunakan counter linier), mencatat tipe data yang digunakan pada runtime, kemudian mengompilasi jalur eksekusi tersebut menjadi *linear native assembly block*. Jika ada tipe data yang menyimpang dari asumsi (*type guard failed*), CPU akan melakukan *de-optimization bail-out* kembali ke interpreter Zend VM.

### 2. Implementasi & Contoh Kasus Nyata

#### 2.1 Konfigurasi Produksi `php.ini` (High-Throughput Web App)
Konfigurasi berikut dioptimalkan untuk arsitektur server-side modern (PHP-FPM/Nginx atau container orchestration) tanpa pembacaan file ulang saat runtime.

```ini
[opcache]
zend_extension=opcache.so

; Aktifkan OPcache untuk CLI (opsional, bagus untuk testing/benchmarking) dan Web
opcache.enable=1
opcache.enable_cli=1

; Ukuran shared memory untuk opcode (dalam MB). Sesuaikan dengan codebase size.
opcache.memory_consumption=256

; Memori untuk interned strings (string literal seperti nama fungsi, class, string konstan)
opcache.interned_strings_buffer=16

; Jumlah maksimal skrip yang bisa di-cache (bilangan prima lebih optimal)
opcache.max_accelerated_files=20000

; Nonaktifkan revalidasi file di production. Sekali cache terbentuk, abaikan modifikasi file.
opcache.validate_timestamps=0
opcache.revalidate_freq=0

; Pertahankan komentar untuk anotasi framework/library (Doctrine, PHPUnit, Swagger)
opcache.save_comments=1

; Pengaktifan Zero-Copy untuk fast shutdown
opcache.fast_shutdown=1

; Preloading script (PHP 7.4+)
opcache.preload=/var/www/html/preload.php
opcache.preload_user=www-data

; JIT Configuration (PHP 8.0+)
; CRTO: C=CPU-specific, R=Register allocation, T=Trigger (1: Trace, 5: Function), O=Optimization Level
; 1255 = Tracing JIT dengan profil agresif
opcache.jit=1255
opcache.jit_buffer_size=64M
```

#### 2.2 Inspeksi Status Runtime OPcache & JIT
Skrip diagnostik untuk memverifikasi alokasi SHM, status compiler JIT, dan hit-rate.

```php
<?php
declare(strict_types=1);

final class RuntimeDiagnostics
{
    public static function inspect(): void
    {
        if (!function_exists('opcache_get_status')) {
            echo "[-] Ekstensi OPcache tidak terpasang.\n";
            return;
        }

        $status = opcache_get_status(false);
        if ($status === false) {
            echo "[-] OPcache dinonaktifkan via konfigurasi.\n";
            return;
        }

        $mem = $status['memory_usage'];
        $usedMb = round($mem['used_memory'] / 1024 / 1024, 2);
        $freeMb = round($mem['free_memory'] / 1024 / 1024, 2);
        $wastedMb = round($mem['wasted_memory'] / 1024 / 1024, 2);
        $hitRate = round($status['opcache_statistics']['opcache_hit_rate'], 2);

        echo "=== [OPcache Diagnostic] ===\n";
        echo "Memory: Used {$usedMb}MB | Free {$freeMb}MB | Wasted {$wastedMb}MB\n";
        echo "Hit Rate: {$hitRate}%\n";
        echo "Cached Scripts: " . $status['opcache_statistics']['num_cached_scripts'] . "\n";

        echo "\n=== [JIT Diagnostic] ===\n";
        if (isset($status['jit'])) {
            $jit = $status['jit'];
            echo "Enabled    : " . ($jit['enabled'] ? 'YES' : 'NO') . "\n";
            echo "On         : " . ($jit['on'] ? 'YES' : 'NO') . "\n";
            echo "Buffer Size: " . round($jit['buffer_size'] / 1024 / 1024, 2) . " MB\n";
            echo "Buffer Free: " . round($jit['buffer_free'] / 1024 / 1024, 2) . " MB\n";
        } else {
            echo "JIT tidak didukung pada versi build PHP ini.\n";
        }
    }
}

RuntimeDiagnostics::inspect();
```

#### 2.3 CPU-Bound Microbenchmark (JIT Impact Demo)
JIT memberikan peningkatan masif pada algoritma matematis/CPU-bound, bukan pada I/O-bound (Database Query / Network Call).

```php
<?php
declare(strict_types=1);

// Menghitung Mandelbrot set untuk membuktikan efisiensi kompilasi register JIT
function mandelbrot(int $width, int $height, int $maxIter): int
{
    $totalIterations = 0;
    for ($y = 0; $y < $height; $y++) {
        $ci = ($y * 2.0 / $height) - 1.0;
        for ($x = 0; $x < $width; $x++) {
            $cr = ($x * 3.0 / $width) - 2.1;
            $zr = 0.0;
            $zi = 0.0;
            $iter = 0;

            while ($zr * $zr + $zi * $zi < 4.0 && $iter < $maxIter) {
                $newZr = $zr * $zr - $zi * $zi + $cr;
                $zi = 2.0 * $zr * $zi + $ci;
                $zr = $newZr;
                $iter++;
            }
            $totalIterations += $iter;
        }
    }
    return $totalIterations;
}

$start = microtime(true);
$result = mandelbrot(1000, 1000, 256);
$elapsed = microtime(true) - $start;

printf("Total iterasi: %d | Waktu eksekusi: %.4f detik\n", $result, $elapsed);
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Opcodes ke Instruksi Mesin**: Saat kode dijalankan, Tracing JIT memonitor perulangan via counter. Jika loop melampaui ambang batas (*hot spot*), DynASM membaca representasi SSA (*Static Single Assignment*) dari opcode tersebut, memetakan tipe variabel PHP yang terlacak (misal: `double` atau `long`), kemudian memancarkan *native machine code* (seperti `movsd`, `mulsd`, `addsd` pada x86-64) langsung ke dalam memori eksekusi.
2. **Type Guards**: PHP adalah bahasa dinamis. Saat native code dieksekusi, JIT memasang instruksi guard:
   ```assembly
   cmp    BYTE PTR [rax+0x8], 0x4   ; Cek apakah zval type adalah IS_LONG
   jne    deoptimize_bailout       ; Jika tipe berubah, bail-out kembali ke Zend VM!
   ```
   Jika tipe variabel berubah secara dinamis, instruksi mesin lompat keluar (*side-exit*) kembali ke Zend VM handler. Terlalu banyak side-exit akan menghancurkan performa alur instruksi mesin akibat *branch misprediction*.

#### Alokasi Memori / Resource
- **SHM Allocation**: OPcache memetakan memori virtual via `mmap(MAP_SHARED | MAP_ANONYMOUS)`. Alokasi ini diakses oleh seluruh child process PHP-FPM secara concurrent (*read-only* setelah inisialisasi).
- **JIT Buffer Memory**: JIT membutuhkan memori yang memiliki permission Read, Write, dan Execute. Sistem operasi modern menerapkan proteksi W^X (*Write XOR Execute*). DynASM mengalokasikan buffer via `mmap` dan menggunakan `mprotect()` atau runtime switching (*dual-mapping*) untuk menulis bytecode mesin sebelum menandainya sebagai `PROT_READ | PROT_EXEC`.
- **Wasted Memory**: Terjadi ketika skrip berubah tetapi `opcache.validate_timestamps=1`. Skrip yang di-compile ulang dialokasikan di blok SHM baru; memori lama ditandai sebagai *wasted*. OPcache hanya melakukan *full restart* saat `wasted_memory` melewati ambang batas persentase tertentu.

#### Trade-offs
- **CPU-bound vs I/O-bound**: JIT hanya mempercepat CPU arithmetic loops dan array manipulation. Untuk aplikasi web standar (Laravel/Symfony) yang terikat pada Database I/O, Serialization JSON, atau Network Socket, dampak performa JIT umumnya marjinal (<5%), namun dapat memakan memori tambahan (JIT Buffer) dan meningkatkan latensi warm-up.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Preloading**: Preload framework core ke shared memory saat start engine via `opcache.preload`. Skrip yang dimuat ini tidak akan pernah di-revalidate dan scope class-nya tersedia secara global untuk semua request tanpa mekanisme autoloading SPL.
- **Tuning `max_accelerated_files`**: Pastikan nilai ini **lebih besar** daripada jumlah total file PHP proyek (termasuk folder `vendor/`). Jalankan perintah `find . -type f -name '*.php' | wc -l` untuk mengetahui kebutuhan minimum.
- **Terapkan Atomic Cache Clearing saat Deploy**: Saat merilis kode baru dengan `validate_timestamps=0`, trigger reload pada PHP-FPM (`kill -USR2 <pid>`) atau gunakan fungsi `opcache_reset()` via web context. Jangan restart container secara brutal untuk menghindari *request drop*.

#### Don'ts
- **Jangan Set `validate_timestamps=1` di Server Produksi**: Engine akan melakukan syscall `stat()` pada disk untuk setiap file yang diminta demi memeriksa apakah `mtime` berubah. Ini membunuh throughput disk I/O.
- **Jangan Alokasikan `jit_buffer_size` Terlalu Besar**: Nilai yang terlalu tinggi (misal: >512MB) menyebabkan pemborosan Virtual Memory Address Space dan meningkatkan beban CPU saat membersihkan buffer cache. Mulai dengan `64M` atau `128M`.
- **Jangan Mengubah Tipe Data Variabel dalam Hot Loop**: Praktik ini memaksa JIT memicu *guard failure*, mengabaikan *trace compilation*, dan mengembalikan eksekusi ke interpreter lambat Zend VM.

#### Edge Cases
- **Symlink Zero-Downtime Deployment**: Menggunakan symlink swap (contoh: rilis Capistrano/Deployer dari `/current` ke `/releases/v2`) sering membingungkan OPcache karena `realpath_cache` Linux meng-cache path lama. Set `opcache.revalidate_path=1` atau bersihkan `realpath_cache()` bersamaan dengan `opcache_reset()` pada *deploy hook*.

### 5. Tantangan Eksplorasi Mandiri

1. **JIT Mode Decoding Challenge**:
   Konfigurasi `opcache.jit` menggunakan kombinasi 4-digit bilangan integer (`CRTO`). Analisis dokumentasi internal PHP, lalu jelaskan perbedaan mendasar karakteristik eksekusi antara mode `opcache.jit=1205` dan `opcache.jit=1255`.
2. **Benchmark Profiling Mandiri**:
   Buat sebuah skrip yang menjalankan komputasi hashing kompleks (atau enkripsi RC4/AES murni di level userland PHP) dan sebuah skrip HTTP endpoint yang mengambil data dari database lokal. Bandingkan latensi dan *Throughput per Second (TPS)* kedua skrip tersebut dalam 3 kondisi:
   - Tanpa OPcache.
   - Dengan OPcache (JIT Off).
   - Dengan OPcache + Tracing JIT (`jit=1255`, `jit_buffer_size=64M`).
   Jelaskan mengapa perbedaan performa JIT pada kedua jenis beban tersebut sangat timpang.
