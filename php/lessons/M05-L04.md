## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Database Migration dan Seeding adalah implementasi dari prinsip **Evolutionary Database Design** dan **Infrastructure as Code (IaC)** pada lapisan persistensi data. Pendekatan ini memandang skema database bukan sebagai entitas statis, melainkan sebagai mesin status (*state machine*) yang bertransisi secara deterministik melalui serangkaian mutasi inkremental.

```
       Linear Migration History (Forward / Rollback)
State 0 ---------> State 1 ---------> State 2 ---------> State 3
(Init)   v1_users  (Users)   v2_posts  (Posts)   v3_tags   (Current)
         <---------          <---------          <---------
          Rollback            Rollback            Rollback
```

#### Mengapa Pola Ini Dibutuhkan?
1. **Pemberantasan Schema Drift**: Menghilangkan inkonsistensi skema antara lingkungan lokal, *staging*, dan *production* yang sering terjadi saat perubahan skema diaplikasikan secara manual via GUI atau raw SQL tak terlacak.
2. **Reproducibility & Temporal Travel**: Memungkinkan tim teknis merekonstruksi skema database pada titik waktu (*commit*) mana pun secara otomatis, menyederhanakan proses *bisecting bug* dan otomatisasi pengujian di pipeline CI/CD.
3. **Pemisahan DDL (Struktur) dan DML (Data)**: Migrasi bertanggung jawab atas *Data Definition Language* (DDL), sementara Seeder bertanggung jawab atas *Data Manipulation Language* (DML) untuk data rujukan (master data) maupun data sintesis (mocking/testing).

#### Arsitektur Inti
Sistem migrasi di ekosistem modern (seperti Laravel Migrations atau Doctrine Migrations) dibangun di atas tiga komponen utama:
* **Migration Repository (Metadata Tracker)**: Tabel database khusus (biasanya bernama `migrations`) yang menyimpan log eksekusi: nama berkas migrasi dan *batch number*. Komponen ini menentukan *delta* antara status skema saat ini dan status yang didefinisikan pada kode sumber.
* **Schema Blueprint & Grammar Compiler**: Abstraksi tingkat tinggi (Object-Oriented) yang menerjemahkan definisi kolom agnostik menjadi sintaks SQL spesifik sesuai dialek RDBMS target (MySQL, PostgreSQL, SQLite, dsb.).
* **State Transition Engine**: Orkestrator yang membaca dependensi urutan berkas (berbasis *timestamp*), membuka koneksi, mengelola *lock*, mengeksekusi DDL, dan memperbarui tabel metadata.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi migrasi modern menggunakan PHP 8.2+ dengan pendekatan anonim (*anonymous migration*), serta seeder berbasis *bulk operation* dengan optimasi memori.

#### File Migrasi: Pembuatan & Mutasi Relasional
```php
<?php

declare(strict_types=1);

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    /**
     * Jalankan mutasi skema (State N -> State N+1).
     */
    public function up(): void
    {
        Schema::create('orders', function (Blueprint $table): void {
            $table->ulid('id')->primary();
            // Foreign key dengan constraint eksplisit dan cascade behavior
            $table->foreignId('user_id')
                  ->constrained('users')
                  ->cascadeOnUpdate()
                  ->restrictOnDelete();
                  
            $table->string('reference_number', 64)->unique();
            $table->decimal('total_amount', 14, 2)->default(0.00);
            
            // Kolom status menggunakan native string dengan index
            $table->string('status', 32)->index();
            
            // JSON column untuk metadata dinamis
            $table->json('payload')->nullable();
            
            // Timestamps presisi mikrodetik untuk data transaksional
            $table->timestamps(6);
        });

        // Contoh modifikasi tabel terpisah: Composite Index untuk optimasi query
        Schema::table('orders', function (Blueprint $table): void {
            $table->index(['user_id', 'status', 'created_at'], 'idx_orders_user_status_created');
        });
    }

    /**
     * Batalkan mutasi skema (State N+1 -> State N).
     */
    public function down(): void
    {
        // Penghapusan tabel harus memperhatikan urutan dependency foreign key
        Schema::dropIfExists('orders');
    }
};
```

#### File Seeder: Idempotent & Memory-Conscious Data Population
```php
<?php

declare(strict_types=1);

namespace Database\Seeders;

use Illuminate\Database\Seeder;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Str;

final class SystemSettingSeeder extends Seeder
{
    /**
     * Jalankan seeding data.
     * Menggunakan pendekatan Idempotent (upsert) dan Bulk Insert.
     */
    public function run(): void
    {
        $settings = [
            [
                'key'        => 'app.maintenance_mode',
                'value'      => json_encode(false),
                'updated_at' => now(),
            ],
            [
                'key'        => 'billing.currency',
                'value'      => json_encode('IDR'),
                'updated_at' => now(),
            ],
            [
                'key'        => 'inventory.auto_reserve',
                'value'      => json_encode(true),
                'updated_at' => now(),
            ],
        ];

        // Idempotency: Menghindari duplikasi saat seeder dijalankan berulang kali
        DB::table('system_settings')->upsert(
            values: $settings,
            uniqueBy: ['key'],
            update: ['value', 'updated_at']
        );

        // Seeding Data Sintesis Berskala Besar (Chunking pattern)
        $this->seedSimulatedAudits(chunkSize: 1000, totalRecords: 5000);
    }

    private function seedSimulatedAudits(int $chunkSize, int $totalRecords): void
    {
        // Matikan query logging untuk mencegah memory exhaustion
        DB::disableQueryLog();

        $batches = (int) ceil($totalRecords / $chunkSize);

        for ($i = 0; $i < $batches; $i++) {
            $records = [];
            for ($j = 0; $j < $chunkSize; $j++) {
                $records[] = [
                    'id'         => (string) Str::ulid(),
                    'action'     => 'SYSTEM_BOOTSTRAP',
                    'created_at' => now()->toDateTimeString(),
                ];
            }

            // Raw batch insert langsung ke database engine (bypass ORM)
            DB::table('audit_logs')->insert($records);
            
            // Bebaskan referensi memory secara eksplisit
            unset($records);
        }
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Flow
1. **Discovery & Lexicographical Sorting**: Mesin migrasi memindai direktori `database/migrations/*.php`. Nama berkas diawali format waktu ISO (`YYYY_MM_DD_HHMMSS_action.php`). String ini diurutkan secara leksikografis untuk menyusun *Directed Acyclic Graph* (DAG) dari tahapan skema.
2. **Atomic Synchronization & Concurrency Locks**: Sebelum mengeksekusi operasi DDL, runner modern mengunci *mutex* (melalui skema *table locking* atau *advisory locks* seperti `pg_advisory_lock` pada PostgreSQL). Hal ini mencegah beberapa instans aplikasi (misal, kontainer Kubernetes yang melakukan *rolling update*) menjalankan migrasi yang sama secara paralel.
3. **Execution & Batch Registration**: Migrasi dieksekusi di dalam runner. Jika berhasil, nama berkas dicatat ke tabel `migrations` dengan nomor *batch* inkremental (`MAX(batch) + 1`).

#### DDL & Transaksi Database (Behavior Kritis Antar RDBMS)
* **PostgreSQL**: Mendukung **Transactional DDL**. Jika sebuah migrasi gagal di tengah jalan (misalnya penambahan kolom berhasil, tetapi indeks gagal dibuat), seluruh perintah dalam method `up()` akan di-*rollback* secara atomik oleh engine database.
* **MySQL / MariaDB**: Menerapkan **Implicit Commit** pada hampir seluruh instruksi DDL (`ALTER`, `CREATE`, `DROP`). 
  > *Implikasi*: Jika migrasi Anda memiliki 3 pernyataan `Schema::table` dan pernyataan ke-3 gagal, 2 perubahan pertama **sudah persisten di disk** dan tidak dapat di-rollback via transaksi SQL. Tabel metadata tidak akan mencatat berkas tersebut, meninggalkan skema database dalam status *corrupt* (*dirty state*).

#### Alokasi Memori pada Seeding
Menggunakan ORM (seperti Eloquent) saat seeding ribuan data menyebabkan **Memory Leak**:
* Setiap instans model yang dibuat di-hydrate ke memori lengkap dengan *dirty tracking state*, *casts*, dan *relations*.
* Event dispatcher dan *Query Log* mencatat seluruh string SQL ke dalam array memori PHP.
* Solusi arsitektural: Gunakan raw query builder (`DB::table(...)`), lakukan *bulk insertion* secara terukur (*chunking*), dan nonaktifkan logger internal (`DB::disableQueryLog()`).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Terapkan Expand and Contract Pattern**: Jangan pernah menghapus atau mengubah nama kolom secara langsung di production. Buat kolom baru (*Expand*), sinkronkan data melalui kode aplikasi, lalu hapus kolom lama pada deployment fase berikutnya (*Contract*).
- **Gunakan Foreign Key Types yang Identik**: Pastikan tipe data kolom referensi dan *primary key* memiliki kesamaan absolut (misalnya `BIGINT UNSIGNED` harus berpasangan dengan `BIGINT UNSIGNED`).
- **Gunakan Named Index**: Selalu berikan nama eksplisit pada *constraint* dan indeks (`$table->index(['org_id', 'status'], 'idx_org_status')`). RDBMS memiliki algoritma penamaan otomatis yang berbeda-beda; jika auto-generated name berubah antar versi, migrasi rollback akan gagal menemukan indeks tersebut.

#### Don'ts
- **DILARANG Menggunakan Model ORM di dalam Migration**:
  ```php
  // BURUK:
  public function up(): void {
      Schema::table('users', fn($t) => $t->string('role')->default('user'));
      User::whereNull('role')->update(['role' => 'user']); // JANGAN DILAKUKAN
  }
  ```
  *Alasan*: Model `User` mencerminkan kode aplikasi saat ini (*current state*). Tiga bulan kemudian, jika model `User` memiliki *global scope*, event, atau properti yang bergantung pada kolom baru lainnya, migrasi lama ini akan *fatal error* saat dijalankan dari nol di database kosong. Gunakan raw `DB::table('users')` di dalam migrasi jika migrasi data tidak dapat dihindari.
- **Jangan Menggabungkan Seed Data Produksi dengan Data Testing**: Bedakan antara *Reference/Seed Data* (misal: daftar negara, hak akses, mata uang) dan *Dummy/Mock Data* (misal: data transaksi simulasi).

#### Edge Cases
* **Zero-Downtime Table Rewrite**: Pada MySQL versi lama (atau mutasi tertentu di MySQL 8.0 seperti modifikasi tipe data), `ALTER TABLE` memicu pembuatan tabel salinan sementara secara internal (*copy table*), menyebabkan penguncian tabel penuh (*table metadata lock*). Gunakan *online schema change tools* (seperti `pt-online-schema-change` atau GitHub's `gh-ost`) untuk tabel berukuran gigabyte/terabyte.
* **Orphan Records saat Rollback**: Jika `down()` method menghapus tabel secara membabi buta tanpa menonaktifkan *Foreign Key Checks*, PostgreSQL atau MySQL dengan `strict mode` akan melempar constraint violation error.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Zero-Downtime Column Rename**:
   Rancang serangkaian berkas migrasi (minimal 2 berkas) yang mengubah nama kolom `phone` menjadi `contact_number` pada tabel transaksi berkonsistensi tinggi tanpa menimbulkan kegagalan query (*zero error*) pada aplikasi versi lama yang masih berjalan saat deployment berlangsung.
2. **Reverse-Engineering Runner Migrasi**:
   Buatlah sebuah *script* PHP CLI murni (`runner.php`) tanpa framework yang:
   - Membuat koneksi PDO ke MySQL atau SQLite.
   - Menginisialisasi tabel metadata `__schema_log` jika belum ada.
   - Membaca file-file SQL di folder `/migrations`, mengeksekusi berkas yang belum tercatat secara transaksional, dan mencatat eksekusinya ke tabel `__schema_log`.
