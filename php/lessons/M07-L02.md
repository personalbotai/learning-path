## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam ekosistem PHP modern, manajemen dependensi bergantung sepenuhnya pada Composer dan spesifikasi **Semantic Versioning (SemVer 2.0.0)**. SemVer mendefinisikan kontrak formal evolusi kode melalui format:

$$\text{MAJOR}.\text{MINOR}.\text{PATCH}[-\text{PRERELEASE}][+\text{BUILD}]$$

- **MAJOR ($X.0.0$)**: Terjadi perubahan yang memutus kompatibilitas ke belakang (*Breaking Changes / Backward Incompatibility - BC Break*).
- **MINOR ($x.Y.0$)**: Penambahan fungsionalitas baru yang tetap *backward-compatible*.
- **PATCH ($x.y.Z$)**: Perbaikan *bug* internal yang tetap *backward-compatible*.

```
  SemVer 0.x (Fase Inkubasi):
  0.1.0 ──────► 0.2.0 (Bisa membawa BC Break sewaktu-waktu!)
  
  SemVer 1.x+ (Fase Stabil):
  1.2.0 ──────► 1.3.0 (Fitur baru, aman diupdate)
    │
    ▼
  1.2.1 (Fix bug, aman diupdate)
    │
    ▼
  2.0.0 (BC Break, butuh refactor manual)
```

#### Operator Batasan Composer (*Constraint Operators*)

Composer menerjemahkan operator versi menjadi rentang (*range*) matematis:

1. **Tilde Operator (`~`)**: 
   - `~1.2.3` ekuivalen dengan `>=1.2.3 <1.3.0` (mengunci Minor).
   - `~1.2` ekuivalen dengan `>=1.2.0 <2.0.0` (mengunci Major karena presisi hanya sampai Minor).
2. **Caret Operator (`^`)**: 
   - Mengizinkan pembaruan selama tidak merusak digit non-nol paling kiri (*left-most non-zero digit*).
   - `^1.2.3` ekuivalen dengan `>=1.2.3 <2.0.0`.
   - **Perilaku Khusus Versi Nol (`0.x`)**: Pada fase pra-rilis (`0.x.x`), rilis minor dianggap membawa *breaking changes*. Maka, `^0.2.3` ekuivalen dengan `>=0.2.3 <0.3.0`, bukan `<1.0.0`.
3. **Hyphen Range (`1.0.0 - 2.1.0`)**: Ekuivalen dengan `>=1.0.0 <=2.1.0`.
4. **Wildcard (`1.2.*`)**: Ekuivalen dengan `>=1.2.0 <1.3.0`.

#### Masalah Resolusi Dependensi: *Diamond Dependency Problem*

Ketika dependensi berbentuk *Directed Acyclic Graph* (DAG), konflik sering terjadi akibat dependensi transitif.

```
       [Aplikasi Anda]
        /           \
   membutuhkan    membutuhkan
      v1.0            v1.0
      /                 \
     ▼                   ▼
[Paket Alpha]      [Paket Beta]
     │                   │
  membutuhkan         membutuhkan
    ^1.2.0              ^2.0.0
     │                   │
     └─────► [Paket Omega] ◄────┘
             (SAT Conflict!)
```

PHP tidak mendukung isolasi multi-versi paket di dalam satu runtime (hanya ada satu *symbol namespace table* untuk setiap FQCN / *Fully Qualified Class Name*). Jika Paket Alpha membutuhkan `Omega v1` dan Paket Beta membutuhkan `Omega v2`, PHP engine tidak dapat memuat kedua *class* bernama sama ke dalam memori eksekusi secara bersamaan. Composer bertugas menyelesaikan dilema ini sebelum kode dieksekusi.

### 2. Implementasi & Contoh Kasus Nyata

Contoh konfigurasi `composer.json` tingkat lanjut untuk memitigasi konflik resolusi, mengunci dependensi platform, dan memanfaatkan operator constraint:

```json
{
    "name": "acme/payment-gateway",
    "description": "Enterprise Core Payment Engine",
    "type": "project",
    "license": "MIT",
    "config": {
        "platform": {
            "php": "8.2.18"
        },
        "sort-packages": true,
        "optimize-autoloader": true
    },
    "require": {
        "php": ">=8.2.0",
        "ext-pdo": "*",
        "ext-sodium": "*",
        "guzzlehttp/guzzle": "^7.8.1",
        "psr/log": "^3.0",
        "symfony/console": "~6.4.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^10.5"
    },
    "conflict": {
        "monolog/monolog": "<3.0.0"
    },
    "replace": {
        "acme/legacy-payment-interface": "self.version"
    },
    "minimum-stability": "stable",
    "prefer-stable": true
}
```

#### Menangani Resolusi dan Diagnostik Konflik

Ketika menghadapi *solver error*, kita mengidentifikasi akar penyebab pohon dependensi secara programatis menggunakan Composer CLI:

```bash
# 1. Analisis mengapa paket tertentu terpasang
composer why psr/log

# Output:
# acme/payment-gateway  requires  psr/log (^3.0)
# guzzlehttp/guzzle     requires  psr/log (^1.0 || ^2.0 || ^3.0)

# 2. Diagnosa mengapa versi baru tidak dapat di-install
composer why-not monolog/monolog 2.9.0

# Output:
# acme/payment-gateway  conflicts  monolog/monolog (<3.0.0)

# 3. Simulasi instalasi tanpa mengubah lockfile (Dry Run)
composer update --dry-run
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Resolusi Menggunakan SAT Solver (Boolean Satisfiability)

Composer memodelkan pemilihan paket sebagai masalah **Boolean Satisfiability (SAT)**, mengadaptasi algoritma berbasis solver **libzypp** (turunan dari MiniSAT dengan optimasi CDCL / *Conflict-Driven Clause Learning*).

1. **Pembuatan Pool Dependensi**:
   Composer mengambil metadata versi dari semua paket yang diminta beserta dependensi transitifnya dari Packagist (via *lazy loading* metadata v2 berformat JSON terkompresi). Setiap kombinasi nama paket dan versinya diubah menjadi variabel *boolean* diskret ($X_{package, version}$).
   
2. **Transformasi ke Bentuk Conjunctive Normal Form (CNF)**:
   Aturan resolusi dikonversi menjadi klausa logika AND dari OR:
   - Jika Aplikasi butuh `guzzlehttp/guzzle: ^7.8`, maka dibuat aturan:
     $$(Guzzle_{7.8.0} \lor Guzzle_{7.8.1} \lor Guzzle_{7.9.0})$$
   - Jika `Guzzle 7.8.1` membutuhkan `psr/http-client: ^1.0`, maka dibentuk implikasi logika:
     $$Guzzle_{7.8.1} \implies (Client_{1.0.0} \lor Client_{1.0.1})$$
     Diubah menjadi klausa CNF:
     $$(\neg Guzzle_{7.8.1} \lor Client_{1.0.0} \lor Client_{1.0.1})$$

3. **Branch-and-Bound / Backtracking Search**:
   Solver mencoba menetapkan nilai `true`/`false` ke setiap variabel. Jika ditemukan konflik (misalnya dependensi `A` membutuhkan `C:1.0` tetapi `B` membutuhkan `C:2.0`, sedangkan aturan paket membatasi hanya boleh ada satu versi $C$ yang aktif: $\neg C_{1.0} \lor \neg C_{2.0}$), solver melakukan *backtracking*, menganalisis himpunan klausa penyebab benturan, dan memutus cabang eksplorasi (*clause learning*).

```
[Fetch Metadata] ──► [Build Pool] ──► [Generate CNF Clauses]
                                               │
                                               ▼
[Install Manifest] ◄── [composer.lock] ◄── [CDCL SAT Solver]
```

#### Alokasi Memori dan Resource

- **Penyimpanan Graph di RAM**: Composer v1 menyimpan seluruh repositori Packagist dalam array PHP besar yang menyebabkan lonjakan memori (sering menyentuh batas `memory_limit`). Composer v2 merekonstruksi ini: metadata diunduh secara *on-demand* paralel menggunakan `curl_multi`, dan *Pool Optimizer* membuang kandidat paket yang tidak mungkin valid sebelum diserahkan ke SAT solver, memangkas penggunaan memori secara eksponensial.
- **`composer.lock` Content Hash**: Field `content-hash` di dalam lockfile dihitung dari hash SHA1/MD5 properti relasional `composer.json` (`require`, `require-dev`, `conflict`, `replace`, dll). Ini memastikan integritas status: jika `composer.json` dimodifikasi tanpa menjalankan `composer update`, Composer akan mendeteksi perbedaan hash ini saat proses verifikasi.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Komit `composer.lock` di Aplikasi, Abaikan di Library**: 
  - Pada proyek tingkat aplikasi (Web App, API, CLI Tool), komit `composer.lock` ke Git untuk menjamin *deterministic builds* identik di staging dan production.
  - Pada *open-source library*, abaikan (`.gitignore`) `composer.lock` agar testing CI menjalankan matriks versi terendah (`--prefer-lowest`) dan tertinggi (`--prefer-stable`) yang diizinkan oleh `composer.json`.
- **Konfigurasikan Target Platform**: 
  Selalu sematkan blok `config.platform.php` di `composer.json`. Ini mencegah developer yang menggunakan PHP 8.3 lokal secara tidak sengaja mengunduh paket dengan dependensi bahasa yang tidak kompatibel dengan server production yang masih menjalankan PHP 8.2.
- **Eksekusi Deterministik di CI/CD**:
  ```bash
  composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction --no-progress
  ```

#### Don'ts
- **Dilarang Menjalankan `composer update` di Server Produksi**:
  `composer update` menjalankan SAT solver dari awal dan menghitung ulang seluruh dependensi, membuka risiko terpasangnya *transitive minor/patch updates* yang belum diuji secara lokal. Selalu gunakan `composer install`.
- **Hindari Operator Wildcard Terbuka**:
  Jangan pernah menulis `"vendor/package": "*"` atau `"vendor/package": ">=1.0"`. Hal ini merusak stabilitas dan memperlambat proses SAT solver karena memperluas *search space* klausa.

#### Edge Cases & Pitfalls
- **The Aliasing Trap (Branch Aliases)**:
  Saat bekerja dengan cabang dev (`dev-main` atau `dev-feature`), paket sering kali gagal teresolusi jika dependensi lain bergantung pada tag SemVer tertentu. Gunakan alias langsung:
  ```json
  "require": {
      "acme/package": "dev-main as 2.1.x-dev"
  }
  ```
- **Transient Dependency Vulnerabilities**:
  Terkadang versi patch dependensi transitif memperkenalkan bug kritis (*breaking regression*). Jika dependensi tingkat atas tidak kunjung merilis perbaikan batasan versi, gunakan blok `conflict` di `composer.json` *root* Anda untuk secara paksa mencegah solver memilih versi yang bermasalah tersebut tanpa perlu melakukan *forking*.

### 5. Tantangan Eksplorasi Mandiri

1. **Simulasi Kegagalan Resolusi Satuan (Manual Conflict Resolution)**:
   Buat direktori baru dan inisialisasi Composer. Coba instal `symfony/console:^5.0` bersamaan dengan paket yang membutuhkan `symfony/console:^6.0` (misalnya versi terbaru dari `laravel/zero-framework`). Analisis pesan galat yang dikeluarkan SAT solver. Gunakan flag `-vvv` pada perintah instalasi untuk membaca jejak langkah perumusan klausa oleh solver.
2. **Investigasi Resolusi Lowest-Dependencies**:
   Pada suatu proyek library atau framework sederhana, jalankan `composer update --prefer-lowest`. Amati bagaimana Composer memilih batas bawah dari setiap operator rentang (`^` dan `~`). Identifikasi apakah paket Anda masih berjalan mulus atau melempar fatal error akibat *type mismatch* yang hanya muncul di rilis minor tertua dependensi Anda.
