### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur perangkat lunak modern, terutama saat menerapkan *Domain-Driven Design* (DDD), pemisahan antara logika bisnis (domain) dan infrastruktur (database) adalah hal yang krusial. Di sinilah kombinasi **Repository Pattern** dan **Data Mapper** berperan.

*   **Data Mapper**: Pola arsitektur di mana objek domain (Entity) sama sekali tidak mengetahui keberadaan database. Mapper bertugas sebagai penerjemah (mediator) dua arah antara baris data relasional (SQL) dan objek murni PHP (*Plain Old PHP Object* / POPO). Berbeda dengan *Active Record* (seperti Eloquent di Laravel) di mana model mewarisi metode database (`$user->save()`), pada Data Mapper, entitas tetap murni dan terisolasi.
*   **Repository Pattern**: Bertindak sebagai koleksi objek domain di dalam memori. Lapisan aplikasi tidak berinteraksi dengan SQL atau PDO, melainkan meminta data ke Repository (`$repository->findById(1)`). Repository kemudian menggunakan Data Mapper untuk melakukan *hydration* (mengubah data mentah menjadi objek).

**Mengapa arsitektur ini penting?**
1.  **Single Responsibility Principle (SRP)**: Entitas hanya peduli pada aturan bisnis, bukan cara menyimpan dirinya sendiri.
2.  **Testability**: Repository direpresentasikan melalui *Interface*, sehingga sangat mudah di-*mock* saat *Unit Testing* tanpa menyentuh database asli.
3.  **Database Agnosticism**: Anda dapat bermigrasi dari MySQL ke MongoDB hanya dengan membuat implementasi Repository baru, tanpa mengubah satu baris pun kode pada logika bisnis.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan PHP 8.2+ yang memanfaatkan *Constructor Property Promotion*, *Readonly Classes*, dan *Type Hinting* yang ketat.

```php
<?php

declare(strict_types=1);

// 1. Domain Entity (Murni, tidak ada dependensi ke database)
class User
{
    public function __construct(
        private ?int $id,
        private string $email,
        private string $name,
        private DateTimeImmutable $createdAt
    ) {}

    // Getters & Domain Logic (Setters dihindari untuk menjaga immutability/enkapsulasi)
    public function getId(): ?int { return $this->id; }
    public function getEmail(): string { return $this->email; }
    public function getName(): string { return $this->name; }
    
    public function changeName(string $newName): void
    {
        if (empty(trim($newName))) {
            throw new InvalidArgumentException("Nama tidak boleh kosong.");
        }
        $this->name = $newName;
    }
}

// 2. Data Mapper (Bertugas melakukan Hydration dan Extraction)
class UserMapper
{
    /**
     * Hydration: Mengubah array dari database menjadi Objek Domain
     */
    public function toEntity(array $row): User
    {
        return new User(
            id: (int) $row['id'],
            email: $row['email'],
            name: $row['name'],
            createdAt: new DateTimeImmutable($row['created_at'])
        );
    }

    /**
     * Extraction: Mengubah Objek Domain menjadi array untuk database
     */
    public function toDatabase(User $user): array
    {
        return [
            'id' => $user->getId(),
            'email' => $user->getEmail(),
            'name' => $user->getName(),
            // Format tanggal sesuai kebutuhan SQL
            'created_at' => (new DateTimeImmutable())->format('Y-m-d H:i:s') 
        ];
    }
}

// 3. Repository Interface (Kontrak untuk Domain Layer)
interface UserRepositoryInterface
{
    public function findById(int $id): ?User;
    public function save(User $user): void;
    public function delete(User $user): void;
}

// 4. Infrastructure Layer: Implementasi PDO dari Repository
readonly class PdoUserRepository implements UserRepositoryInterface
{
    public function __construct(
        private PDO $pdo,
        private UserMapper $mapper
    ) {}

    public function findById(int $id): ?User
    {
        $stmt = $this->pdo->prepare("SELECT * FROM users WHERE id = :id LIMIT 1");
        $stmt->execute(['id' => $id]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if (!$row) {
            return null;
        }

        return $this->mapper->toEntity($row);
    }

    public function save(User $user): void
    {
        $data = $this->mapper->toDatabase($user);

        if ($user->getId() === null) {
            // Insert
            $stmt = $this->pdo->prepare(
                "INSERT INTO users (email, name, created_at) VALUES (:email, :name, :created_at)"
            );
            unset($data['id']); // ID auto-increment
            $stmt->execute($data);
            
            // Catatan: Di dunia nyata, kita menggunakan Reflection untuk set ID ke entitas setelah insert
        } else {
            // Update
            $stmt = $this->pdo->prepare(
                "UPDATE users SET email = :email, name = :name WHERE id = :id"
            );
            unset($data['created_at']); // Jangan update created_at
            $stmt->execute($data);
        }
    }

    public function delete(User $user): void
    {
        if ($user->getId() === null) return;
        
        $stmt = $this->pdo->prepare("DELETE FROM users WHERE id = :id");
        $stmt->execute(['id' => $user->getId()]);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Pada arsitektur *Active Record*, pemanggilan `$user->save()` langsung memicu eksekusi SQL dari dalam objek itu sendiri. Pada *Data Mapper*, objek `User` murni berada di *user-space memory*. Saat `$repository->save($user)` dipanggil, eksekusi berpindah ke *Infrastructure Layer*. Repository mengekstrak state dari objek, mengompilasinya menjadi *prepared statement* PDO, dan mengirimkannya ke *database engine* melalui *C-level driver* PHP (pdo_mysql).
- **Alokasi Memori / Resource (Hydration Cost)**:
  Proses *Hydration* (pemetaan dari array ke objek) memakan CPU dan memori. Jika Anda melakukan `SELECT * FROM users` yang mengembalikan 10.000 baris, Data Mapper akan menginstansiasi 10.000 objek `User` di memori (Zval structures di Zend Engine). Ini jauh lebih mahal (overhead) dibandingkan mengembalikan array asosiatif biasa. Oleh karena itu, ORM berbasis Data Mapper (seperti Doctrine) menggunakan teknik *Lazy Loading* dan *Proxy Objects* untuk menunda instansiasi relasi antar tabel sampai benar-benar diakses.
- **Trade-offs**:
  *Keuntungan*: Kode sangat bersih, mudah diuji, dan domain logic terlindungi.
  *Kerugian*: *Boilerplate code* yang tinggi. Anda harus menulis Entity, Mapper, Interface, dan Implementation. Kurang cocok untuk aplikasi CRUD sederhana yang butuh *time-to-market* cepat.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Gunakan Dependency Injection (DI)**: Selalu injeksikan *Interface* Repository ke dalam *Service/Controller*, bukan implementasi konkretnya (`PdoUserRepository`).
  - **Gunakan Reflection API untuk Mapper Kompleks**: Jika entitas Anda memiliki properti *private* tanpa *setter* (untuk enkapsulasi ketat), gunakan `ReflectionClass` di dalam Data Mapper untuk mengisi nilai properti tanpa melanggar visibilitas objek.
- **Don'ts**:
  - **Membocorkan Exception Database**: Jangan biarkan `PDOException` keluar dari Repository. Tangkap exception tersebut di dalam Repository dan lemparkan sebagai *Domain Exception* kustom (misal: `UserNotFoundException` atau `DuplicateEmailException`).
  - **Membuat "God Repository"**: Jangan menambahkan metode spesifik tanpa batas seperti `findByEmailAndStatusAndDate()`. Gunakan pola *Specification* atau *Criteria* jika query menjadi terlalu dinamis.
- **Edge Cases**:
  - **N+1 Query Problem**: Saat memuat entitas yang memiliki relasi (misal: `User` memiliki banyak `Post`), mengambil data dari database secara naif akan memicu 1 query untuk User dan N query untuk setiap Post. Implementasikan *Eager Loading* di tingkat Repository/Mapper untuk mengatasi ini.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Reflection Mapper**: Modifikasi kelas `UserMapper` di atas agar tidak menggunakan *constructor* saat *hydration*, melainkan menggunakan `ReflectionClass` PHP untuk menginjeksi data langsung ke properti *private* `User`. Ini mensimulasikan cara kerja Doctrine ORM.
2. **Caching Decorator**: Buat kelas `CachedUserRepository` yang mengimplementasikan `UserRepositoryInterface`. Kelas ini harus membungkus (wrap) `PdoUserRepository` dan menggunakan Redis/Memcached untuk menyimpan hasil `findById` sebelum melakukan query ke database (Pola *Decorator*).
3. **Unit of Work Pattern**: Pelajari dan buat kerangka sederhana pola *Unit of Work* untuk melacak objek mana yang *dirty* (berubah), *new* (baru), atau *deleted* (dihapus), sehingga Anda hanya perlu memanggil `$unitOfWork->commit()` satu kali untuk mengeksekusi semua perubahan dalam satu transaksi database.
