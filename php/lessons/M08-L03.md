### 1. Konsep & Arsitektur Mendalam

Pest PHP adalah testing framework dengan fokus utama pada *Developer Experience* (DX) yang mengadopsi paradigma fungsional dan deklaratif (mirip dengan Jest di ekosistem JavaScript). Alih-alih memaksakan struktur berbasis kelas (*Object-Oriented Testing*) seperti yang diusung oleh PHPUnit standar, Pest menyederhanakan deklarasi pengujian menggunakan fungsi global (seperti `test()`, `it()`, `describe()`, dan `expect()`).

Secara arsitektural, Pest **bukanlah** pengganti PHPUnit dari nol, melainkan sebuah lapisan abstraksi tingkat tinggi (*high-level DSL layer*) yang berjalan di atas PHPUnit. Pest memanfaatkan core engine PHPUnit (`PHPUnit\Framework\TestCase`, *test runner*, *assertion library*, dan *runner lifecycle*) namun mengubah cara developer berinteraksi dengannya:

```
+-------------------------------------------------------------+
|                        Pest Test DSL                        |
|        (test(), it(), expect(), arch(), higher-order)       |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                     Pest Compiler / Core                    |
|   - Closure Binding: $closure->bindTo($testCase)            |
|   - Test Suite & Factory (Pest\TestSuite, Pest\PendingCalls)|
|   - Architecture Plugin Engine (PHPStan parser wrapper)     |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                       PHPUnit Engine                        |
|   (PHPUnit\Framework\TestCase, Runner, Assertions, Hooks)   |
+-------------------------------------------------------------+
```

Alasan evolusi ini terjadi di ekosistem PHP:
1. **Reduksi Boilerplate**: Pada PHPUnit konvensional, penulisan pengujian memerlukan boilerplate kelas, deklarasi *method visibility*, anotasi/PHP Attributes (`#[Test]`), dan penamaan metode yang sering kali kaku (`test_it_can_calculate_discount()`).
2. **Keterbacaan Berorientasi Perilaku (BDD)**: Pest memfasilitasi *Behavior-Driven Development* secara *native*. Spesifikasi perilaku ditulis layaknya dokumen deskriptif menggunakan perpaduan blok `describe()` dan `it()`.
3. **Pondasi Ekosistem Modern**: Pest menyediakan *first-class support* untuk *Architecture Testing* (memastikan layer arsitektur seperti DDD atau Clean Architecture tidak dilanggar secara statis), *Mutation Testing*, *Type Coverage*, dan eksekusi paralel melalui integrasi ParaTest langsung di core CLI-nya.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi modern pengujian sistem kalkulasi diskon dan validasi batas arsitektur menggunakan Pest PHP.

#### File: `src/DiscountService.php`
```php
<?php

declare(strict_types=1);

namespace App\Services;

use InvalidArgumentException;

final class DiscountService
{
    /**
     * Hitung total akhir setelah diskon.
     *
     * @param float $subtotal
     * @param float $percentage Nilai persentase (0 - 100)
     * @return float
     */
    public function applyDiscount(float $subtotal, float $percentage): float
    {
        if ($subtotal < 0) {
            throw new InvalidArgumentException('Subtotal tidak boleh negatif.');
        }

        if ($percentage < 0 || $percentage > 100) {
            throw new InvalidArgumentException('Persentase diskon harus berada di antara 0 dan 100.');
        }

        $discountAmount = $subtotal * ($percentage / 100);

        return round($subtotal - $discountAmount, 2);
    }
}
```

#### File: `tests/Unit/DiscountServiceTest.php`
```php
<?php

declare(strict_types=1);

use App\Services\DiscountService;

// Setup instance per-scope menggunakan beforeEach
beforeEach(function () {
    $this->service = new DiscountService();
});

describe('DiscountService::applyDiscount', function () {
    it('menghitung potongan harga dengan benar', function (float $subtotal, float $discount, float $expected) {
        $result = $this->service->applyDiscount($subtotal, $discount);

        expect($result)
            ->toBeFloat()
            ->toBe($expected);
    })->with([
        'diskon 10% dari 100.000' => [100000.0, 10.0, 90000.0],
        'diskon 0% (tidak ada diskon)' => [50000.0, 0.0, 50000.0],
        'diskon 100% (gratis)' => [75000.0, 100.0, 0.0],
        'diskon dengan angka desimal' => [100.0, 33.333, 66.67],
    ]);

    it('melempar exception saat subtotal negatif', function () {
        expect(fn () => $this->service->applyDiscount(-1000.0, 10.0))
            ->toThrow(InvalidArgumentException::class, 'Subtotal tidak boleh negatif.');
    });

    it('melempar exception saat persentase di luar batas (0-100)', function (float $invalidPercentage) {
        expect(fn () => $this->service->applyDiscount(10000.0, $invalidPercentage))
            ->toThrow(InvalidArgumentException::class, 'Persentase diskon harus berada di antara 0 dan 100.');
    })->with([
        'kurang dari nol' => [-0.01],
        'lebih dari 100'  => [100.01],
    ]);
});
```

#### File: `tests/Architecture/ArchTest.php`
```php
<?php

declare(strict_types=1);

// Architecture Testing: Memastikan integritas struktur kode
arch('Domain Services harus final dan tidak memiliki dependencies ke HTTP Controller')
    ->expect('App\Services')
    ->toBeFinal()
    ->not->toUse('App\Http\Controllers');

arch('Tidak boleh meninggalkan debugging functions di seluruh codebase')
    ->expect(['dd', 'dump', 'var_dump', 'print_r', 'ray'])
    ->not->toBeUsed();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Pendaftaran DSL ke AST / Object Graph**:
   Ketika file tes dijalankan via CLI Pest, fungsi global `test()` atau `it()` tidak langsung mengeksekusi assertion. Fungsi-fungsi ini mengeksekusi factory internal (`Pest\TestSuite::getInstance()->tests->set(...)`) yang membuat instance objek `TestCall`.
2. **Dynamic TestCase Synthesis & Closure Binding**:
   Pest secara dinamis merepresentasikan setiap blok pengujian ke dalam kelas turunan `PHPUnit\Framework\TestCase`. Di tingkat runtime Zend Engine, closure tes yang ditulis developer dibungkus dan di-*bind* menggunakan:
   ```php
   $closure->bindTo($testCaseInstance, get_class($testCaseInstance));
   ```
   Mekanisme inilah yang membuat pseudovariabel `$this` di dalam closure tes memiliki akses langsung ke seluruh method, assertion lama, dan lifecycle hook dari instance `TestCase` PHPUnit yang bersangkutan.
3. **Higher-Order Proxy**:
   Fitur Higher-Order Testing (`$this->expect(...)->toBe(...)`) memanfaatkan PHP `__get` dan `__call` magic methods. Setiap method chain mengembalikan objek proxy (`Pest\Expectation`) yang menunda eksekusi atau meneruskan assertions ke driver assertion underlying (seperti Sebastians Bergmann's `PHPUnit\Framework\Assert`).
4. **Architecture Testing via Static Analysis**:
   Plugin `arch()` tidak mengeksekusi kode aplikasi Anda ke memory. Di balik layar, Pest menggunakan engine **PHPStan** untuk membaca file via Abstract Syntax Tree (AST), melakukan pengecekan referensi *class reflection*, *token stream*, dan dependensi dependensi namespace secara statis.

#### Alokasi Memori / Resource
- **State Capture & Memory Leaks**: Karena tes ditulis dalam bentuk Closure, closure tersebut berpotensi menahan referensi konteks leksikal variabel di sekitarnya. Jika developer mengoper variabel besar via konstruksi `use ($largePayload)`, memori tersebut tidak akan di-garbage collect oleh Zend Engine (Zend GC) sampai seluruh siklus test runner selesai, memicu *out of memory* (OOM) pada test suite berskala ribuan tes.
- **Process Isolation**: Pada mode paralel (`pest --parallel`), Pest memisahkan alokasi memori ke proses-proses worker yang berbeda menggunakan sub-process pooling (berbasis IPC/Sockets). Ini mengeliminasi kontaminasi state memori global, namun meningkatkan overhead I/O startup process.

#### Trade-offs
- **Stack Trace Complexity**: Lapisan proksi dan penanganan exception Pest menyisipkan banyak frame internal ke dalam call-stack. Ketika terjadi error yang tak terduga (misal segfault atau fatal error), penelusuran stack trace native memerlukan filter agar tidak tertutup jejak runner Pest.
- **Slight Execution Overhead**: Dynamic closure binding dan abstraction layer menambahkan overhead komputasi CPU mikro per-test dibandingkan PHPUnit kelas murni, meskipun hal ini diimbangi oleh eksekusi paralel multi-core yang sangat optimal.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Datasets untuk Combinatorial Testing**: Manfaatkan `->with([...])` untuk memisahkan logika validasi data dari struktur tes, menghindari duplikasi blok kode pengujian yang identik.
- **Terapkan Architecture Testing di CI/CD**: Gunakan `arch()` untuk menjaga aturan enkapsulasi kode (misal: "Value Objects harus immutable", "Models tidak boleh dipanggil dari View").
- **Manfaatkan Konfigurasi `Pest.php` Terpusat**: Tentukan binding namespace dan custom traits secara konsisten di `tests/Pest.php`:
  ```php
  uses(TestCase::class)->in('Feature');
  uses(DatabaseTransactions::class)->in('Feature');
  ```

#### Don'ts
- **Menyimpan State di Global/Static Variable**: Jangan pernah mengandalkan modifikasi state static di dalam closure tes tanpa membersihkannya di `afterEach()`.
- **Mencampuradukkan Assertion Style**: Hindari mencampur `$this->assertEquals()` milik PHPUnit dengan `expect()->toBe()` milik Pest secara acak. Gunakan `expect()` API secara konsisten demi menjaga keterbacaan deklaratif.
- **Over-Mocking pada Unit Tests**: Jangan membuat mock untuk data primitives atau Value Objects murni. Mocking harus dikhususkan untuk dependensi infrastruktur eksternal (API Client, Payment Gateway, Database Driver).

#### Edge Cases
- **Variabel `$this` pada Arrow Functions (`fn () => ...`)**:
  Arrow functions di PHP secara otomatis melakukan *by-value binding* terhadap scope parent saat deklarasi. Hati-hati saat menggunakan `$this->something` di dalam arrow functions jika Anda memodifikasi `$this` secara dinamis via lifecycle hooks (`beforeEach`), karena perilaku lexical binding-nya lebih kaku dibanding *anonymous function* reguler (`function () { ... }`).
- **Parallel Testing Race Conditions**: Saat mengeksekusi database transactions di parallel worker, pastikan konfigurasi worker menggunakan database terisolasi (misal: database suffix `test_db_1`, `test_db_2`) untuk menghindari *deadlock* transaksi ACID.

### 5. Tantangan Eksplorasi Mandiri

1. **Custom Expectation Creation**: Buatlah custom expectation method Pest menggunakan `expect()->extend('toBeValidUuid', function () { ... })` yang memvalidasi format string UUID v4 menggunakan Regular Expression atau library RAMSEY/UUID. Pastikan ada penanganan pesan error yang informatif saat asersi bernilai false.
2. **Domain Architecture Rule Enforcement**: Buatlah satu suite Architecture Test (`tests/Architecture/DomainTest.php`) yang menegakkan aturan:
   - Semua kelas di namespace `App\Domain\ValueObjects` harus berstatus `final`.
   - Semua kelas di namespace `App\Domain\Exceptions` harus meng-extend native `\Exception` atau `\DomainException`.
   - Modul `Domain` tidak boleh bergantung sama sekali pada modul `Infrastructure`.
