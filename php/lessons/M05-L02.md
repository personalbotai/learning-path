### 1. Konsep & Arsitektur Mendalam

*SQL Injection* (SQLi) terjadi ketika data yang tidak dipercaya (*untrusted user input*) disisipkan langsung ke dalam string query SQL tanpa isolasi struktural. Akibatnya, Database Management System (DBMS) menginterpretasikan data tersebut sebagai instruksi sintaksis (*code execution*), bukan nilai skalar (*literal data*). Kerentanan ini memanipulasi *Abstract Syntax Tree* (AST) parser database, memungkinkan bypass autentikasi, eksfiltrasi data, hingga eksekusi perintah remote via fungsi basis data tertentu.

Secara historis, developer memitigasi SQLi menggunakan fungsi sanitasi string seperti `addslashes()` atau `mysqli_real_escape_string()`. Pendekatan ini rapuh secara arsitektural karena:
1. **Kegagalan Encoding Karakter Multi-byte:** Celah seperti *GBK/Big5 character set bypass* dapat menelan byte *escape* (`\`), mengubah byte berikutnya menjadi delimiter SQL valid.
2. **Konteks Non-String:** Sanitasi string tidak berpengaruh pada klausa numerik (misal: `SELECT * FROM users WHERE id = $id`), di mana nilai tidak dibungkus tanda kutip tunggal.
3. **Kompleksitas Parser:** Meniru logika parsing DBMS pada level aplikasi (PHP) rentan terhadap inkonsistensi perlakuan karakter spesial (*parser differential*).

```
[ Pendekatan Rentan (String Concatenation) ]
PHP: "SELECT * FROM users WHERE user = '" . $input . "'"
$input = "admin' --"
DBMS Parser: Parse + Compile String Utuh -> AST Berubah (Bypass Logic)

[ Pendekatan Prepared Statements ]
Fase 1 (Prepare): PHP mengirim Template SQL -> DBMS Parse & Compile ke Executable Query Plan (AST Terkunci)
Fase 2 (Execute): PHP mengirim Parameter Murni -> DBMS Mengisi Slot Data (Tidak Mempengaruhi AST)
```

Solusi deterministik untuk masalah ini adalah **Prepared Statements** (Parameterization). Arsitektur ini memisahkan siklus hidup query menjadi dua fase terisolasi:
1. **Fase Preparasi (*Prepare*):** Query SQL dikirim ke DBMS dengan penanda khusus (*placeholders*, `?` atau `:named`). DBMS melakukan tokenisasi, parsing sintaksis, optimasi, dan menghasilkan *Query Execution Plan*. Pada tahap ini, struktur logika query dikunci ke dalam AST permanen.
2. **Fase Eksekusi (*Execute*):** Aplikasi mengirimkan nilai literal parameter secara terpisah melalui protokol komunikasi biner DBMS. Karena query plan telah dikompilasi, DBMS secara absolut memperlakukan nilai tersebut murni sebagai data, tidak peduli karakter berbahaya apa pun yang terkandung di dalamnya (`'`, `"`, `--`, `/*`, atau byte biner `NULL`).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan PHP Data Objects (PDO) di PHP 8.2+. PDO dipilih karena menyediakan antarmuka terpadu, mendukung *named parameters*, serta memiliki penanganan konfigurasi keamanan yang lebih konsisten dibandingkan ekstensi `mysqli`.

```php
<?php

declare(strict_types=1);

namespace App\Infrastructure\Database;

use PDO;
use PDOException;
use InvalidArgumentException;

final class DatabaseConnection
{
    private static ?PDO $instance = null;

    public static function getConnection(): PDO
    {
        if (self::$instance === null) {
            $dsn = 'mysql:host=127.0.0.1;dbname=production_db;charset=utf8mb4;port=3306';
            $options = [
                // Menginstruksikan driver untuk melempar PDOException ketika terjadi kegagalan
                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
                // Mengubah fetch mode default menjadi associative array
                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
                // NONAKTIFKAN emulasi prepared statement demi keamanan & performa protokol biner native
                PDO::ATTR_EMULATE_PREPARES   => false,
                // Menjaga integritas tipe data: int & float tidak dikonversi menjadi string
                PDO::ATTR_STRINGIFY_FETCHES  => false,
            ];

            try {
                self::$instance = new PDO($dsn, 'db_user', 'super_secret_password', $options);
            } catch (PDOException $e) {
                // Jangan ekspos kredensial atau detail koneksi ke log publik/output
                throw new PDOException("Koneksi database gagal: " . $e->getMessage(), (int)$e->getCode());
            }
        }

        return self::$instance;
    }
}

final class UserRepository
{
    public function __construct(private readonly PDO $pdo) {}

    /**
     * Contoh 1: Named Placeholders Standar
     */
    public function findByEmailAndStatus(string $email, string $status): ?array
    {
        $sql = 'SELECT id, email, password_hash, status, created_at 
                FROM users 
                WHERE email = :email AND status = :status 
                LIMIT 1';

        $stmt = $this->pdo->prepare($sql);
        
        // Eksekusi dengan mengirimkan asosiasi nilai
        $stmt->execute([
            'email'  => $email,
            'status' => $status,
        ]);

        $result = $stmt->fetch();
        return $result ?: null;
    }

    /**
     * Contoh 2: Menangani Array Dinamis pada Klausa IN (?)
     * Parameter binding tidak bisa mem-bind array langsung ke satu placeholder.
     */
    public function findUsersByIds(array $ids): array
    {
        if (empty($ids)) {
            return [];
        }

        // Validasi tipe data untuk memastikan integritas
        $validatedIds = array_map(fn($id) => (int)$id, $ids);

        // Buat placeholder terhitung: ?, ?, ?
        $placeholders = implode(',', array_fill(0, count($validatedIds), '?'));
        
        $sql = "SELECT id, email, status FROM users WHERE id IN ($placeholders)";
        $stmt = $this->pdo->prepare($sql);
        
        // Eksekusi menggunakan parameter posisi
        $stmt->execute($validatedIds);

        return $stmt->fetchAll();
    }

    /**
     * Contoh 3: Mitigasi Injeksi pada Identifier Dinamis (ORDER BY / Column)
     * Prepared statement HANYA memvalidasi nilai literal, BUKAN identifier (nama tabel/kolom).
     * Solusi: Strict Whitelisting.
     */
    public function getSortedUsers(string $sortBy, string $direction = 'ASC'): array
    {
        // 1. Definisikan whitelist identifier yang sah
        $allowedColumns = ['id', 'email', 'created_at'];
        $directionUpper = strtoupper($direction);

        if (!in_array($sortBy, $allowedColumns, true)) {
            throw new InvalidArgumentException("Kolom sorting tidak valid: {$sortBy}");
        }

        // 2. Strict enum check untuk arah sorting
        $sortDirection = match ($directionUpper) {
            'ASC', 'DESC' => $directionUpper,
            default       => throw new InvalidArgumentException("Arah sorting tidak valid: {$direction}")
        };

        // Identifiers dimasukkan via interpolasi yang sudah divalidasi ketat
        $sql = "SELECT id, email, created_at FROM users ORDER BY {$sortBy} {$sortDirection} LIMIT 50";
        
        $stmt = $this->pdo->prepare($sql);
        $stmt->execute();

        return $stmt->fetchAll();
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Native vs. Emulated Prepares
Secara default, PDO MySQL mengaktifkan `PDO::ATTR_EMULATE_PREPARES => true`. Perbedaan mendasar di layer transport dan runtime:

1. **Emulated Prepares (`ATTR_EMULATE_PREPARES = true`):**
   * PHP tidak mengirim sinyal prepare ke DBMS.
   * Runtime PHP secara internal mem-parsing query, meng-escape karakter variabel via fungsi internal C `mysql_real_escape_string`, menggabungkan string parameter ke dalam template SQL, lalu mengirim query utuh menggunakan **Text Protocol** (`COM_QUERY`).
   * **Risiko:** Apabila konfigurasi charset koneksi di level database dan klien desinkron, parsing internal PHP berpotensi dilewati oleh exploit manipulasi set karakter multi-byte.

2. **Native Prepares (`ATTR_EMULATE_PREPARES = false`):**
   * PHP berkomunikasi dengan DBMS menggunakan **Binary Protocol** via dua langkah terpisah:
     1. Client mengirim frame paket `COM_STMT_PREPARE` berisi string query template.
     2. DBMS memvalidasi sintaksis, mengalokasikan Statement ID (uint32) di memori, dan mengembalikan paket metadata statement ke PHP.
     3. Client mengirim paket `COM_STMT_EXECUTE` yang membawa Statement ID beserta buffer payload parameter biner (data dikirim tanpa pembungkus quote string).
   * DBMS mengeksekusi parameter terhadap Query Plan yang sudah di-cache tanpa melalui proses lexing/parsing ulang.

```
PHP Runtime                       Network (MySQL Protocol)                 MySQL Engine
    |                                        |                                  |
    |---- 1. prepare($sql) ----------------->| === [COM_STMT_PREPARE] ========> | (Lexer & Parser)
    |                                        |                                  | (Build Plan & AST)
    |<--- Statement Handler (ID: 1) ---------|<=== [Stmt Prepared OK] ==========| (Alokasi Memori)
    |                                        |                                  |
    |---- 2. execute([$val]) --------------->| === [COM_STMT_EXECUTE (ID: 1)] =>| (Inject Value ke Leaf Node)
    |                                        |     (Payload: Type & Raw Bytes)  | (Execute Plan Langsung)
    |<--- Result Set Data -------------------| <== [Binary Resultset] ==========|
```

#### Alokasi Memori / Resource
* **Database Server:** Menggunakan Native Prepares mengonsumsi memori pada server (`max_prepared_stmt_count`) untuk menyimpan pointer AST dan execution context selama koneksi tetap terbuka. Jika aplikasi membuat jutaan variasi query unik tanpa menutup statement, server dapat mengalami kehabisan memori (*out of prepared statement handlers*).
* **PHP Engine:** Nilai parameter di dalam PHP di-wrap ke struktur C `zval`. Ketika `execute()` dipanggil, tipe zval (`IS_LONG`, `IS_STRING`, `IS_DOUBLE`) dipetakan ke tipe biner internal MySQL (misal: `MYSQL_TYPE_LONG`, `MYSQL_TYPE_VAR_STRING`).

#### Trade-offs
* **Performa Native Prepares:**
  * *Single Execution:* Lebih lambat karena membutuhkan 2 *network round-trips* (`COM_STMT_PREPARE` + `COM_STMT_EXECUTE`).
  * *Batch Execution (Looping):* Jauh lebih cepat karena satu query template di-prepare sekali, lalu di-execute berkali-kali hanya dengan mengirimkan payload biner baru tanpa overhead parsing ulang SQL.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Wajib Matikan Emulasi:** Selalu konfigurasikan `PDO::ATTR_EMULATE_PREPARES => false` pada inisialisasi koneksi PDO untuk memaksa pemisahan parsing di DBMS.
- **Tentukan Charset secara Eksplisit di DSN:** Sertakan `charset=utf8mb4` di DSN string. Jangan mengeksekusi `SET NAMES utf8mb4` secara terpisah via `exec()`, karena driver PHP PDO tidak menyadari perubahan *character set state* tersebut.
- **Terapkan Strict Whitelisting pada Identifier:** Karena *table name*, *column name*, dan *direction* (ASC/DESC) tidak bisa dijadikan parameter prepared statement, gunakan `in_array()` dengan *strict type comparison* (`true`) atau PHP 8 `match` expressions.
- **Batasi Hak Akses Database (Principle of Least Privilege):** Akun database aplikasi tidak boleh memiliki privilege DDL (`DROP`, `ALTER`) atau akses administratif (`FILE`, `SUPER`).

#### Don'ts
- **DILARANG MENGGABUNGKAN String Konkatenasi dengan Placeholders:**
  ```php
  // FATAL: Masih rentan SQL Injection
  $stmt = $pdo->prepare("SELECT * FROM users WHERE status = 'active' AND name = '" . $_GET['name'] . "' AND id = ?");
  ```
- **Jangan Mengandalkan Regular Expression untuk Sanitasi SQL:** Parser database jauh lebih permisif dan kompleks daripada rule regex buatan developer.
- **Jangan Percaya Data dari Database Sendiri (Second-Order SQLi):** Data yang diambil dari tabel A kemudian digunakan untuk mengonstruksi query teks mentah ke tabel B tetap berpotensi menimbulkan eksekusi SQLi.

#### Edge Cases
* **Kueri Dinamis Kompleks (Banyak Filter Opsional):** Hindari konkatenasi string mentah saat membuat filtering form dinamis. Bangun array kondisi dan array parameter secara paralel:
  ```php
  $conditions = [];
  $params = [];

  if (!empty($filters['role'])) {
      $conditions[] = 'role = :role';
      $params['role'] = $filters['role'];
  }
  if (!empty($filters['min_age'])) {
      $conditions[] = 'age >= :min_age';
      $params['min_age'] = $filters['min_age'];
  }

  $sql = "SELECT * FROM users";
  if ($conditions) {
      $sql .= " WHERE " . implode(' AND ', $conditions);
  }

  $stmt = $pdo->prepare($sql);
  $stmt->execute($params);
  ```
* **Klausa `LIMIT ?, ?`:** Pada beberapa versi MySQL/MariaDB dengan emulasi dinonaktifkan, PDO dapat mengikat parameter `LIMIT` sebagai string (`'10'`), memicu sintaks eror pada engine. Gunakan `$stmt->bindValue(':limit', (int)$limit, PDO::PARAM_INT)` untuk memvalidasi tipe data secara ketat.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Paket Jaringan Rendah (Network Inspection):**
   Gunakan tools seperti *Wireshark* atau utilitas *tcpdump* pada port MySQL (default: 3306). Buat skrip PHP sederhana yang menjalankan query dengan `PDO::ATTR_EMULATE_PREPARES => true` lalu bandingkan paketnya dengan `PDO::ATTR_EMULATE_PREPARES => false`. Identifikasi paket `COM_QUERY` vs perpaduan `COM_STMT_PREPARE` dan `COM_STMT_EXECUTE`.

2. **Rancang Dynamic Criteria Builder Abstraction:**
   Implementasikan sebuah class PHP sederhana `QueryCriteriaBuilder` yang mampu menerima struktur query bersyarat dinamis (misal kombinasi filter AND/OR dinamis) dan menghasilkan string template SQL ber-placeholder beserta mapping associative array parameternya secara otomatis, tanpa sekali pun mengekspos variabel mentah ke dalam string query.

3. **Eksploitasi & Mitigasi Second-Order Injection:**
   Bangun simulasi sederhana: buat sebuah alur pendaftaran user di mana nama user diinputkan payload (misal: `admin' --`). Simpan data tersebut secara aman menggunakan *prepared statements* ke database. Kemudian, buat script terpisah yang mengambil data user tersebut dan menggunakannya dalam query kedua tanpa prepared statement. Amati bagaimana eksploitasi berhasil tereksekusi pada query kedua dan ubah kodenya hingga kebal terhadap serangan.
