## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, PHP didesain sebagai bahasa dinamis (*dynamically typed*), di mana tipe data tidak terikat pada variabel, melainkan pada nilai (*value*) yang dikandungnya. Variabel hanyalah sebuah pointer atau label yang merujuk pada nilai tertentu di memori. 

```
Variabel ($x) ---> Pointer ---> [ Container: zval (Type Tag + Raw Data) ]
```

Dalam sistem dinamis murni, PHP menggunakan mekanisme **Type Juggling** (konversi tipe implisit / *implicit coercion*). Ketika sebuah operasi melibatkan dua tipe data yang tidak kompatibel (misalnya string `"100"` dan integer `50` pada operasi penjumlahan), Zend Engine secara otomatis mengonversi tipe salah satu atau kedua operan pada saat *runtime* agar operasi dapat dilanjutkan tanpa melempar pengecualian (*exception*). Pendekatan ini mempermudah pemrosesan data HTTP (seperti formulir web atau query string di mana seluruh payload awalnya bertipe string), tetapi menimbulkan konsekuensi fatal berupa *behavior* yang ambigu dan celah keamanan logika (*type confusion vulnerabilities*).

Mulai PHP 7.0, PHP memperkenalkan deklarasi tipe skalar (*scalar type hints*) serta direktif `declare(strict_types=1);`. Ini menandai pergeseran arsitektural menuju *gradual typing*.

Perbedaan filosofis dan teknis kedua mode ini adalah:
1. **Coercive Mode (Default / `strict_types=0`)**: Ketika argumen fungsi atau nilai kembalian (*return value*) tidak sesuai dengan tipe yang dideklarasikan, engine akan mencoba mengonversi nilai tersebut secara agresif ke target tipe jika memungkinkan (misalnya `float` menjadi `int`, string angka menjadi `int`).
2. **Strict Mode (`strict_types=1`)**: Engine menolak konversi implisit. Jika terdapat ketidakcocokan tipe antara argumen yang dikirim dan tipe parameter target, Zend Engine langsung melempar `TypeError`. **Satu-satunya pengecualian pelebaran tipe (*widening conversion*) yang diizinkan dalam strict mode adalah passing tipe `int` ke parameter `float`.**

> **Penting Mengenai Ruang Lingkup (Scope):** Direktif `declare(strict_types=1);` bersifat **per-file basis** dan dievaluasi pada saat kompilasi (*compile-time*). Aturan *strict types* berlaku pada file **pemanggil (*caller*)**, bukan file **penerima (*callee*)**. Jika file A (`strict_types=1`) memanggil fungsi di file B (`strict_types=0`), pemanggilan tersebut tetap tunduk pada aturan ketat file A.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengilustrasikan perbedaan fatal antara konversi implisit (type juggling) dan penegakan *strict typing* dalam kalkulasi finansial.

```php
<?php

declare(strict_types=1);

namespace App\Billing;

use TypeError;
use InvalidArgumentException;

class InvoiceCalculator
{
    /**
     * Menghitung total harga dengan persentase diskon.
     * Menggunakan tipe skalar strict: float, int.
     */
    public function calculateFinalAmount(float $basePrice, float $discountPercentage, int $quantity): float
    {
        if ($discountPercentage < 0.0 || $discountPercentage > 100.0) {
            throw new InvalidArgumentException("Diskon harus berada pada rentang 0.0 - 100.0");
        }

        $subtotal = $basePrice * $quantity;
        $discountAmount = $subtotal * ($discountPercentage / 100.0);

        return $subtotal - $discountAmount;
    }
}

// ==========================================
// SIMULASI RUNTIME
// ==========================================

$calculator = new InvoiceCalculator();

// Kasus 1: Valid Execution (int ke float diizinkan secara otomatis oleh strict mode)
$total = $calculator->calculateFinalAmount(150000.0, 10, 2); // 10 (int) divalidasi ke 10.0 (float)
echo "Total Valid: " . $total . PHP_EOL; // 270000

// Kasus 2: Type Juggling Trap (String numerik yang lolos dari payload request/JSON)
$rawUserInput = [
    'price'    => "150000.50",
    'discount' => "10.5",
    'quantity' => "2_items" // String non-standar
];

try {
    // Di bawah strict_types=1, baris ini LANGSUNG melempar TypeError tanpa kompromi
    // Jika strict_types=0, string "150000.50" akan dipaksa menjadi float 150000.50,
    // dan "2_items" di PHP < 8.0 dipaksa menjadi int 2 (dengan Notice).
    $calculator->calculateFinalAmount(
        $rawUserInput['price'], // Error: string diberikan, float diharapkan
        $rawUserInput['discount'],
        $rawUserInput['quantity']
    );
} catch (TypeError $e) {
    echo "Tertangkap oleh Strict Types: " . $e->getMessage() . PHP_EOL;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Struktur `zval`
Di dalam C source code Zend Engine (terletak di `Zend/zend_types.h`), setiap variabel PHP direpresentasikan oleh sebuah struktur data C berukuran 16-byte (pada arsitektur 64-bit) bernama **`zval`** (*Zend Value*).

```c
struct _zval_struct {
    zend_value        value; // 8 byte: Union data (int, double, pointer ke string/objek)
    union {
        struct {
            zend_uchar    type;         // 1 byte: IS_UNDEF, IS_NULL, IS_LONG, IS_DOUBLE, IS_STRING, dll.
            zend_uchar    type_flags;   // 1 byte: flag konstanta, referensi, dll.
            zend_uchar    u0;
            zend_uchar    extra;
        } v;
        uint32_t type_info;             // 4 byte: representasi bitmask terpadu
    } u1;
    union {
        uint32_t     next;             // Hash collision chain
        uint32_t     cache_slot;
        ...
    } u2;
};
```

* **Ketika Type Juggling terjadi (`strict_types=0`)**: Zend Engine memanggil fungsi utilitas internal seperti `convert_to_long_base()` atau `convert_to_double()`. Fungsi ini membaca flag `u1.v.type`, mengekstrak data dari `value`, mengalokasikan data baru jika diperlukan, lalu memperbarui tag tipe `zval` tersebut.
* **Ketika Strict Types aktif (`strict_types=1`)**: Compiler PHP memancarkan *opcode* `INIT_FCALL` dan memeriksa `arg_info` pada *function signature*. Di runtime, VM mengeksekusi instruksi `ZEND_CHECK_ARG_TYPE`. Jika nilai pada `zval.u1.v.type` tidak identik dengan ekspektasi parameter (kecuali konversi aman `IS_LONG` ke `IS_DOUBLE`), Zend Engine segera memanggil `zend_type_error()` tanpa menjalankan fungsi konversi.

#### Alokasi Memori: Copy-on-Write (COW)
PHP menggunakan strategi optimasi memori **Copy-on-Write (COW)** untuk variabel skalar kompleks (seperti string berukuran besar) dan array:
1. Saat Anda meng-assign variabel: `$b = $a;`, Zend Engine tidak menyalin isi buffer memori dari `$a`.
2. Mesin hanya mereferensikan `$b` ke struktur pointer data yang sama dengan `$a` dan menaikkan nilai `refcount` di dalam header memori struktur (`zend_refcounted_h`).
3. Alokasi memori baru (*deep copy*) hanya di-trigger tepat saat salah satu variabel tersebut mengalami mutasi (*write*).

#### Trade-offs
* **Strict Types**: Membutuhkan sanitasi tipe data secara manual pada *entry-point* aplikasi (misal: parsing request DTO), tetapi menghasilkan eksekusi opcode yang lebih deterministik dan memfasilitasi optimalisasi *Just-In-Time* (JIT) compiler di PHP 8+.
* **Type Juggling**: Menghilangkan *boilerplate parsing* data formulir, namun menimbulkan *overhead* berupa pemanggilan fungsi mutasi struktur `zval` berkali-kali di runtime dan menghasilkan potensi bug logika laten.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Letakkan `declare(strict_types=1);` di baris pertama**: Jadikan ini sebagai standar absolut di setiap file PHP tanpa pengecualian (otomatisasikan via PHP-CS-Fixer / PHP_CodeSniffer).
* **Gunakan Strict Comparison (`===` dan `!==`)**: Hindari operator `==` dan `!=`. Operator *loose comparison* memaksa Zend Engine melakukan konversi tipe implisit antar operan sebelum evaluasi.
* **Gunakan Explicit Casting saat mengolah data eksternal**: Validasi dan cast tipe secara manual pada batas sistem (*boundary layer*, misalnya Controller/Repository):
  ```php
  $id = filter_var($request->get('id'), FILTER_VALIDATE_INT);
  if ($id === false) {
      throw new BadRequestHttpException("ID harus berupa integer valid");
  }
  ```

#### Don'ts
* **Jangan mengandalkan `empty()` untuk validasi skalar presisi**: Nilai `"0"` (string berisi nol), `0` (integer), `false`, dan `[]` (array kosong) semuanya dievaluasi sebagai `true` oleh fungsi `empty()`. Hal ini sering merusak logika verifikasi kuantitas barang atau status numerik.
* **Jangan menganggap `strict_types` menular (*infectious*)**: Jika library pihak ketiga tidak menggunakan `declare(strict_types=1)`, pemanggilan internal di dalam library tersebut tetap menggunakan mode koersif.

#### Edge Cases & Perubahan Paradigma PHP 8.0
Sebelum PHP 8.0, perbandingan string dengan integer pada operator `==` mengubah string menjadi angka terlebih dahulu:
```php
// PHP 7.x
0 == "foobar"; // TRUE! Karena string "foobar" dikonversi paksa ke integer 0

// PHP 8.0+ (Sane string to number comparisons)
0 == "foobar"; // FALSE. Jika string adalah non-numeric, angka dikonversi ke string: "0" == "foobar"
0 == "0";      // TRUE. Tetap dibandingkan sebagai integer karena string numerik valid
```

1. **Investigasi File Scope Strict Types**:
   Buat dua file terpisah: `Math.php` (tanpa `declare(strict_types=1)`) yang memiliki fungsi `function add(int $a, int $b): int`, dan `index.php` (dengan `declare(strict_types=1)`). Panggil fungsi `add("5", "10")` dari `index.php`. Amati hasilnya dan jelaskan alur validasi Zend Engine yang terjadi. Lakukan skenario sebaliknya!

2. **Dekomposisi Struktur Variabel dengan Zend Debugger**:
   Pasang ekstensi *Xdebug* pada environment lokal Anda. Gunakan fungsi bawaan `xdebug_debug_zval()` pada sebuah variabel sebelum dan sesudah proses mutasi untuk melihat transisi nilai `refcount` dan membuktikan arsitektur *Copy-on-Write (COW)* secara langsung:
   ```php
   $x = "Testing COW Engine";
   $y = $x;
   // Amati nilai refcount
   $y .= " Modified";
   // Amati pemisahan buffer memori dan refcount baru
   ```
