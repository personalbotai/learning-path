## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam *Unit Testing*, prinsip utama adalah menguji satu unit kode (biasanya sebuah *class* atau *method*) secara terisolasi. Namun, dalam arsitektur perangkat lunak dunia nyata, sebuah *class* hampir selalu memiliki ketergantungan (*dependencies*) terhadap komponen lain seperti *Database*, *External API*, atau *File System*. 

Untuk mempertahankan isolasi, kita menggunakan **Test Doubles**—sebuah istilah generik (diperkenalkan oleh Gerard Meszaros) untuk objek yang menggantikan objek asli (produksi) untuk tujuan pengujian.

Terdapat 5 jenis *Test Doubles* dengan tujuan arsitektural yang berbeda:
1. **Dummy**: Objek yang dilempar ke dalam *method* tetapi tidak pernah digunakan (hanya untuk memenuhi *type-hint*).
2. **Fake**: Implementasi yang benar-benar berfungsi, tetapi mengambil "jalan pintas" yang membuatnya tidak cocok untuk produksi (contoh: *In-Memory Database*).
3. **Stub**: Objek yang menyediakan jawaban yang sudah diprogram sebelumnya (*canned answers*) terhadap panggilan *method* selama pengujian. Digunakan untuk **State Verification**.
4. **Spy**: Sebuah *Stub* yang juga merekam informasi tentang bagaimana ia dipanggil (berapa kali, argumen apa yang digunakan).
5. **Mock**: Objek yang diprogram dengan **ekspektasi** (aturan tentang panggilan apa yang harus diterimanya). Jika ekspektasi tidak terpenuhi, pengujian akan gagal. Digunakan untuk **Behavior Verification**.

Dalam ekosistem PHP (terutama PHPUnit), batas antara *Stub* dan *Mock* sering kali kabur karena keduanya dibuat menggunakan *API* yang sama, namun secara konseptual, *Stub* digunakan untuk *Query* (mengembalikan data), sedangkan *Mock* digunakan untuk *Command* (memverifikasi aksi/efek samping).

### 2. Implementasi & Contoh Kasus Nyata

Mari kita lihat implementasi modern menggunakan PHP 8.2+ dan PHPUnit 10+. Kita memiliki `UserService` yang bergantung pada `UserRepository` (untuk mengambil data) dan `EmailService` (untuk mengirim notifikasi).

```php
<?php
declare(strict_types=1);

namespace App\Services;

use App\Repositories\UserRepositoryInterface;
use App\Services\EmailServiceInterface;
use InvalidArgumentException;

readonly class UserService
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private EmailServiceInterface $emailService
    ) {}

    public function registerUser(string $email, string $password): bool
    {
        if ($this->userRepository->findByEmail($email) !== null) {
            throw new InvalidArgumentException('Email already exists');
        }

        // Logika penyimpanan user (disederhanakan)
        $userId = $this->userRepository->save(['email' => $email, 'password' => $password]);

        if ($userId) {
            // Kita ingin memverifikasi bahwa email benar-benar dikirim (Behavior Verification)
            $this->emailService->sendWelcomeEmail($email);
            return true;
        }

        return false;
    }
}
```

**Kode Pengujian (Test Case):**

```php
<?php
declare(strict_types=1);

namespace Tests\Unit;

use App\Services\UserService;
use App\Repositories\UserRepositoryInterface;
use App\Services\EmailServiceInterface;
use PHPUnit\Framework\TestCase;
use InvalidArgumentException;

class UserServiceTest extends TestCase
{
    public function test_register_user_successfully(): void
    {
        // 1. Membuat STUB untuk UserRepository (State Verification)
        // Kita hanya peduli apa yang dikembalikan, bukan berapa kali dipanggil.
        $userRepoStub = $this->createStub(UserRepositoryInterface::class);
        $userRepoStub->method('findByEmail')->willReturn(null); // User belum ada
        $userRepoStub->method('save')->willReturn(1); // Berhasil simpan, return ID 1

        // 2. Membuat MOCK untuk EmailService (Behavior Verification)
        // Kita EKSPEKTASI method ini dipanggil TEPAT SATU KALI dengan argumen spesifik.
        $emailServiceMock = $this->createMock(EmailServiceInterface::class);
        $emailServiceMock->expects($this->once())
                         ->method('sendWelcomeEmail')
                         ->with($this->equalTo('test@example.com'));

        // 3. Instansiasi System Under Test (SUT)
        $userService = new UserService($userRepoStub, $emailServiceMock);

        // 4. Eksekusi & Assert
        $result = $userService->registerUser('test@example.com', 'secret123');
        $this->assertTrue($result);
    }

    public function test_register_fails_if_email_exists(): void
    {
        $userRepoStub = $this->createStub(UserRepositoryInterface::class);
        // Stub mengembalikan array, mensimulasikan user sudah ada
        $userRepoStub->method('findByEmail')->willReturn(['id' => 1, 'email' => 'test@example.com']);

        // Dummy/Mock untuk email service, karena kita tahu ini tidak akan pernah dipanggil
        $emailServiceDummy = $this->createMock(EmailServiceInterface::class);
        $emailServiceDummy->expects($this->never())->method('sendWelcomeEmail');

        $userService = new UserService($userRepoStub, $emailServiceDummy);

        $this->expectException(InvalidArgumentException::class);
        $userService->registerUser('test@example.com', 'secret123');
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: Saat Anda memanggil `$this->createMock(InterfaceName::class)`, PHPUnit menggunakan **Reflection API** (`ReflectionClass`) untuk membaca struktur *interface* atau *class* target. PHPUnit kemudian secara dinamis menghasilkan (*generate*) kode PHP baru berupa *class* anonim (atau *class* dengan nama unik) yang mengimplementasikan/meng-*extend* target tersebut. *Method-method* di- *override* untuk mencegat (*intercept*) panggilan dan mengarahkannya ke *InvocationMocker* internal PHPUnit.
- **Alokasi Memori / Resource**: Karena *mock class* di- *generate* secara dinamis menggunakan `eval()` atau mekanisme pemuatan *file* dinamis di *runtime*, proses ini memakan memori dan siklus CPU yang signifikan. OPcache PHP tidak dapat mengoptimalkan *class* yang di- *generate* secara dinamis ini dengan efisien. *Test suite* dengan ribuan *mocks* akan berjalan jauh lebih lambat dibandingkan *test suite* yang menggunakan *Fakes* (implementasi manual).
- **Trade-offs**: *Mocking* memberikan isolasi absolut dan kecepatan penulisan *test*, tetapi mengorbankan keyakinan integrasi. Jika *interface* dari *dependency* berubah, *mock* mungkin masih lulus (*false positive*), padahal kode produksi akan gagal karena *mock* tidak mencerminkan perilaku asli dari *dependency* tersebut.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Mock Interfaces, Not Classes**: Selalu usahakan melakukan *mocking* terhadap *Interface*. Ini memaksa Anda menerapkan *Dependency Inversion Principle* (SOLID).
  - **Gunakan Stub untuk Query, Mock untuk Command**: Jika *method* hanya mengembalikan data (misal: `getUser()`), gunakan *Stub*. Jika *method* mengubah *state* atau memicu efek samping (misal: `sendEmail()`, `deleteUser()`), gunakan *Mock* dengan `expects()`.
  - **Hanya Mock Dependency Langsung**: Jangan melakukan *mocking* terhadap objek yang berada di luar batas arsitektur Anda secara langsung (misal: jangan *mock* `PDO` atau `GuzzleClient`, buatlah *Repository* atau *Wrapper* dan *mock* *wrapper* tersebut).

- **Don'ts**:
  - **Don't Mock the System Under Test (SUT)**: Jangan pernah melakukan *mocking* terhadap *class* yang sedang Anda uji (kecuali dalam kasus *Partial Mocking* yang sangat jarang dan biasanya mengindikasikan *code smell*).
  - **Over-mocking**: Jangan melakukan *mocking* pada *Value Objects* atau *Data Transfer Objects* (DTO). Instansiasi saja objek aslinya.
  - **Chained Mocking**: Menulis `$mock->method('getA')->willReturn($mockB); $mockB->method('getB')...` adalah tanda pelanggaran *Law of Demeter*. Refaktor kode produksi Anda.

- **Edge Cases**:
  - **Final Classes/Methods**: Secara *default*, PHPUnit tidak bisa melakukan *mocking* terhadap *class* atau *method* yang ditandai dengan `final` karena PHP tidak mengizinkan *class* turunan untuk meng-*override* mereka. Solusinya adalah menggunakan *library* seperti `dg/bypass-finals` yang memanipulasi *opcode* PHP di memori untuk menghapus *keyword* `final` selama pengujian.

### 5. Tantangan Eksplorasi Mandiri

1. **Buat Custom Spy**: Tanpa menggunakan PHPUnit `createMock()`, buatlah sebuah *class* PHP manual yang mengimplementasikan `EmailServiceInterface` dan bertindak sebagai *Spy* (menyimpan jumlah panggilan dan argumen ke dalam *array* internal, lalu buat *method* `assertCalledWith()` Anda sendiri).
2. **Eksplorasi Mockery**: Pelajari *library* `Mockery` (standar de-facto di ekosistem Laravel). Tulis ulang *test case* di atas menggunakan sintaks `Mockery::mock()` dan bandingkan keterbacaannya dengan PHPUnit.
3. **Bypass Finals**: Buat sebuah `final class` di PHP. Coba lakukan *mocking* dengan PHPUnit murni (akan gagal). Kemudian, instal dan konfigurasikan `dg/bypass-finals` di `bootstrap.php` PHPUnit Anda, dan amati bagaimana *mocking* tiba-tiba berhasil. Analisis bagaimana *library* tersebut bekerja di level *stream wrapper*.
