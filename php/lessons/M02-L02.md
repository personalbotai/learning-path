### 1. Konsep & Arsitektur Mendalam

Dalam rekayasa perangkat lunak berorientasi objek (OOP), **Inheritance**, **Abstract Class**, dan **Polymorphism** adalah mekanisme fundamental untuk mereduksi duplikasi logika, mengabstraksi kompleksitas domain, dan menerapkan *dependency inversion*.

```
┌─────────────────────────────────────────────────────────┐
│                    PaymentGateway                       │  <-- Abstract Class (Contract & Skeleton)
│  - currency: string                                     │
│  + process(amount: float): TransactionResult            │  <-- Template Method
│  # executePayment(amount: float): ProviderResponse (*)  │  <-- Abstract Method
└────────────────────────────┬────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
┌───────────────────────┐         ┌───────────────────────┐
│     StripeGateway     │         │    MidtransGateway    │  <-- Concrete Subclasses
│ + executePayment(...) │         │ + executePayment(...) │
└───────────────────────┘         └───────────────────────┘
```

#### Inheritance (Pewarisan)
PHP mengadopsi model *single inheritance*. Sebuah *subclass* mewarisi state (properties) dan behavior (methods) dari sebuah *superclass* via kata kunci `extends`. Pewarisan membentuk relasi "IS-A" yang sangat terikat secara struktural. 

Pewarisan berlebihan menimbulkan masalah klasik: **The Fragile Base Class Problem**, di mana perubahan kecil pada kelas induk dapat merusak fungsionalitas di seluruh hierarki turunan.

#### Abstract Class
Kelas abstrak adalah cetak biru tak lengkap yang tidak dapat diinstansiasi secara langsung (`new BaseClass()` akan melempar fatal error). 
* Berbeda dari `Interface` yang murni berfungsi sebagai kontrak publik tanpa membawa implementasi state/metode konkret (sebelum PHP 8, interface sama sekali nihil implementasi), `Abstract Class` dapat memiliki properti dengan visibilitas berbeda (`private`, `protected`, `public`) serta metode konkret sebagai logika dasar yang dibagikan.
* Berfungsi sempurna sebagai implementasi arsitektur **Template Method Pattern**, di mana alur kontrol tingkat tinggi dieksekusi di kelas induk, sementara langkah-langkah spesifik didelegasikan ke *subclass* melalui metode abstrak.

#### Polymorphism & Dynamic Dispatch
Polimorfisme (khususnya *Subtype Polymorphism*) memungkinkan sistem memperlakukan objek dari kelas turunan seolah-olah mereka adalah objek dari kelas dasar atau interface yang sama. 
* Di runtime, pemanggilan metode `$gateway->process($amount)` tidak ditentukan secara statis di fase kompilasi. Sebaliknya, PHP menggunakan **Dynamic Method Dispatch** untuk memeriksa tipe konkret objek di memori saat eksekusi dan memanggil implementasi metode yang sesuai.
* Hal ini menggaransi prinsip **Liskov Substitution Principle (LSP)**: *Subtype harus dapat menggantikan Base Type tanpa merusak integritas atau fungsionalitas program.*

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus berikut mengimplementasikan sistem pemrosesan pembayaran terpusat yang aman, terstandarisasi, dan tahan audit menggunakan PHP 8.2+.

```php
<?php

declare(strict_types=1);

namespace App\Payments;

use InvalidArgumentException;
use RuntimeException;

// Result DTO: Representasi data keluaran yang immutable
final readonly class TransactionResult
{
    public function __construct(
        public bool $isSuccess,
        public string $transactionId,
        public float $amount,
        public string $currency,
        public ?string $errorMessage = null
    ) {}
}

// 1. Abstract Base Class: Mendefinisikan Template Method & Hooking Mechanism
abstract class PaymentGateway
{
    // Constructor Promotion & Property Invariance
    public function __construct(
        protected readonly string $currency,
        protected readonly int $timeoutSeconds = 30
    ) {}

    /**
     * Template Method (Final): Menjamin konsistensi pipeline transaksi.
     * Tidak boleh di-override oleh child class.
     */
    final public function process(float $amount): TransactionResult
    {
        // Pre-processing assertion
        if ($amount <= 0) {
            throw new InvalidArgumentException("Nilai transaksi harus lebih besar dari 0.");
        }

        $this->logActivity("Inisiasi transaksi sebesar {$amount} {$this->currency}");

        try {
            // Primitive Operation yang didelegasikan ke child classes
            $rawResponse = $this->executePayment($amount);
            
            $result = $this->normalizeResponse($rawResponse, $amount);
            
            $this->logActivity("Transaksi {$result->transactionId} berhasil.");
            return $result;
        } catch (\Throwable $e) {
            $this->logActivity("Transaksi gagal: " . $e->getMessage());
            
            return new TransactionResult(
                isSuccess: false,
                transactionId: 'FAILED',
                amount: $amount,
                currency: $this->currency,
                errorMessage: $e->getMessage()
            );
        }
    }

    /**
     * Abstract Method: Wajib diimplementasikan oleh Subclass.
     * Mengembalikan response raw spesifik provider.
     */
    abstract protected function executePayment(float $amount): mixed;

    /**
     * Abstract Method: Normalisasi payload vendor ke schema domain standar kita.
     */
    abstract protected function normalizeResponse(mixed $response, float $amount): TransactionResult;

    /**
     * Concrete Method yang dapat digunakan langsung oleh semua subclass.
     */
    protected function logActivity(string $message): void
    {
        // Pada aplikasi nyata, gunakan PSR-3 Logger
        echo sprintf("[%s] [%s]: %s\n", date('Y-m-d H:i:s'), static::class, $message);
    }
}

// 2. Concrete Implementation A: Stripe Engine
final class StripeGateway extends PaymentGateway
{
    public function __construct(
        string $currency,
        private readonly string $stripeSecretKey
    ) {
        parent::__construct($currency);
    }

    protected function executePayment(float $amount): mixed
    {
        // Simulasi HTTP Call ke API Stripe
        return [
            'id' => 'ch_' . bin2hex(random_bytes(8)),
            'status' => 'succeeded',
            'amount_captured' => (int) ($amount * 100)
        ];
    }

    protected function normalizeResponse(mixed $response, float $amount): TransactionResult
    {
        if (!is_array($response) || $response['status'] !== 'succeeded') {
            throw new RuntimeException("Stripe API menolak authorization.");
        }

        return new TransactionResult(
            isSuccess: true,
            transactionId: $response['id'],
            amount: $amount,
            currency: $this->currency
        );
    }
}

// 3. Concrete Implementation B: Midtrans Engine
final class MidtransGateway extends PaymentGateway
{
    public function __construct(
        string $currency,
        private readonly string $serverKey
    ) {
        parent::__construct($currency);
    }

    protected function executePayment(float $amount): mixed
    {
        // Simulasi integrasi Snap Token / Core API Midtrans
        return (object) [
            'transaction_id' => 'midtrans-' . bin2hex(random_bytes(6)),
            'transaction_status' => 'settlement',
            'gross_amount' => (string) $amount
        ];
    }

    protected function normalizeResponse(mixed $response, float $amount): TransactionResult
    {
        if (!is_object($response) || $response->transaction_status !== 'settlement') {
            throw new RuntimeException("Midtrans payment tidak berhasil diselesaikan.");
        }

        return new TransactionResult(
            isSuccess: true,
            transactionId: $response->transaction_id,
            amount: $amount,
            currency: $this->currency
        );
    }
}

// 4. Client Consumer: Menerapkan Polymorphism
class CheckoutService
{
    // Type-hinting terhadap Abstract Base Class, bukan concrete implementation
    public function __construct(
        private PaymentGateway $gateway
    ) {}

    public function handleOrderCheckout(string $orderId, float $total): void
    {
        echo "Memproses pesanan #{$orderId}...\n";
        
        // Polymorphic Call: Mengeksekusi pipeline tanpa peduli provider apa yang aktif
        $result = $this->gateway->process($total);

        if ($result->isSuccess) {
            echo "Pembayaran Berhasil! Tx ID: {$result->transactionId}\n";
        } else {
            echo "Pembayaran Gagal: {$result->errorMessage}\n";
        }
    }
}

// === RUNTIME EXECUTION ===
$stripe = new StripeGateway(currency: 'USD', stripeSecretKey: 'sk_test_123');
$midtrans = new MidtransGateway(currency: 'IDR', serverKey: 'SB-Mid-456');

// Dynamic Polymorphism: Menukar adapter runtime tanpa mengubah kode CheckoutService
$checkoutA = new CheckoutService($stripe);
$checkoutA->handleOrderCheckout(orderId: "ORD-001", total: 49.99);

echo "\n--------------------------------------------------\n\n";

$checkoutB = new CheckoutService($midtrans);
$checkoutB->handleOrderCheckout(orderId: "ORD-002", total: 750000.00);
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Zend Engine)
1. **Kompilasi ke Opcode & Class Linking**:
   Ketika berkas dieksekusi, Zend Engine mengurai hierarki class. Abstract class dan concrete class dikompilasi menjadi struktur internal C yang disebut `zend_class_entry`.
   * Pada saat link hierarki inheritance (`ZEND_DECLARE_INHERITED_CLASS`), Zend Engine menyalin referensi pointer metode dari `zend_class_entry.function_table` milik kelas induk ke tabel fungsi milik *subclass*.
   * Jika kelas anak tidak mengimplementasikan metode dengan flag `ZEND_ACC_ABSTRACT`, Zend Engine melempar fatal error saat fase kompilasi: `"Class ... contains 1 abstract method and must therefore be declared abstract or implement the remaining methods"`.
2. **Virtual Method Table (vtable) & Dynamic Dispatch**:
   Saat mengeksekusi polymorphic call `$this->gateway->process()`, Zend Engine membaca pointer handler fungsi dari instance objek aktif (`zend_object`). Zend Engine mencari opcode `ZEND_INIT_METHOD_CALL` dan mendispatch ke alamat fungsi yang sesuai pada `function_table` kelas konkret di memori.
3. **Late Static Binding (LSB)**:
   Metode statis atau konstanta yang diakses via `static::` versus `self::` dievaluasi secara dinamis. Kata kunci `self::` di-resolve pada fase kompilasi (menunjuk ke kelas tempat kode ditulis), sementara `static::` membaca referensi `called_scope` dari frame eksekusi runtime (`zend_execute_data`).

#### Alokasi Memori & Resource
* **Struktur Objek (`zend_object`)**: 
  Semua properti kelas induk yang diwarisi disalin ke dalam tabel properti objek turunan. Subclass mengalokasikan array contiguous memori untuk menampung *internal property table*. Semakin dalam hierarki inheritance dan semakin banyak properti yang diwariskan, alokasi memori heap untuk instansiasi setiap objek membengkak.
* **Inheritance Resolution Cost**: 
  Inheritance resolution dieksekusi sekali per proses pada runtime standar PHP. Namun, bila **OPcache** aktif, inheritance resolution ini di-cache di Shared Memory (SHM) menggunakan struktur *immutable class entries*, mereduksi penalti I/O dan lookup linking saat melayani HTTP request berulang.

#### Trade-offs
* **Deep Inheritance vs. Flat Composition**: 
  Pewarisan lebih dari 2–3 level menghasilkan *coupling* yang sangat kuat. Perubahan signature pada base class memaksa verifikasi menyeluruh terhadap kompatibilitas Liskov (`type contravariance` pada parameter dan `covariance` pada return types).
* **Dynamic Dispatch Overhead**:
  Walaupun lookup hash table pada `zend_function` sangat teroptimasi via hash masks di Zend Engine, terdapat mikro-overhead kalkulasi dibandingkan pemanggilan static method murni atau pemanggilan direct closure.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan Keyword `final` Secara Agresif**: Tandai concrete method atau seluruh concrete class sebagai `final` kecuali Anda secara eksplisit merancang kelas tersebut untuk diekstensi lebih jauh. Ini mencegah sub-classing tak terkontrol.
* **Terapkan Liskov Substitution Principle (LSP)**:
  * Parameter type pada sub-class harus identik atau lebih luas (Contravariance).
  * Return type pada sub-class harus identik atau lebih spesifik (Covariance).
* **Gunakan Template Method Pattern pada Base Class**: Gunakan `final public function` untuk template method agar child class tidak dapat merusak urutan flow orkestrasi internal.

#### Don'ts
* **Jangan Jadikan Inheritance Sebagai Alat Code-Reuse Semata**: Jika relasinya bukan hubungan esensial "IS-A", gunakan teknik **Composition over Inheritance** (Inject objek pembantu melalui Constructor, jangan `extend`).
* **Hindari Memanggil Constructor Parent Secara Implisit**: Jangan pernah lupa memanggil `parent::__construct(...)` jika child class mendefinisikan constructor-nya sendiri; kegagalan memanggilnya akan membiarkan state kelas induk tidak terinisialisasi (*uninitialized properties*).
* **Hindari Penggunaan `protected` Properti Tanpa Validasi**: Memberikan akses `protected` mentah membuka risiko modifikasi state secara acak oleh subclass. Buat properti berstatus `private` atau `protected readonly`, dan sediakan mutator/accessor terproteksi jika dibutuhkan.

#### Edge Cases
* **Late Static Binding Masalah Rekursi / Scope**:
  Hati-hati saat menggunakan `new static()` di dalam abstract factory method. Jika child class mengubah parameter konstruktornya tanpa signature compatibility, pemanggilan `new static()` akan menyebabkan runtime `ArgumentCountError`.
* **Private vs. Protected Method Overriding**:
  Mendefinisikan metode privat dengan nama yang sama di child class **bukanlah** overriding. PHP memperlakukan metode tersebut sebagai dua entry terpisah di `function_table`, sehingga polimorfisme tidak berlaku pada level `private`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Type Variance Violation**:
   Buat sebuah abstract class `Repository` dengan method `abstract public function find(int|string $id): object`. Buat subclass `UserRepository` yang mengubah signature method tersebut menjadi `public function find(int $id): User`. Amati apa yang terjadi pada PHP 8.2+. Mengapa compiler mengizinkan atau menolak perubahan tipe parameter dan tipe kembalian tersebut? Jelaskan hubungannya dengan aturan *Covariance* dan *Contravariance*.
2. **Refactoring Anti-Pattern "Deep Hierarchy"**:
   Ambil basis kode di mana `SpecialAdminController extends AdminController extends BaseController extends AbstractController`. Refaktorisasi hierarki 4 tingkat tersebut menjadi arsitektur berbasis komposisi (Action-Domain-Responder atau Controller ramping dengan dependency injection) tanpa memutus fungsionalitas dependensi yang dibutuhkan sub-class.
3. **Analisis Memory Zend Engine**:
   Gunakan fungsi `memory_get_usage()` untuk membandingkan alokasi memori 10.000 objek yang mewarisi 5 level class dengan 20 `protected` properti, dibandingkan dengan 10.000 objek dari *flat standalone class* yang memanfaatkan komposisi via referensi DTO tunggal. Bandingkan jejak memori keduanya di runtime.
