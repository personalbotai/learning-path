### 1. Konsep & Arsitektur Mendalam

Logging adalah instrumen observabilitas paling mendasar dalam siklus hidup aplikasi. Tanpa standardisasi, setiap library atau framework akan mengimplementasikan logger proprietary masing-masing, menyebabkan *tight coupling* dan fragmentasi ekosistem. Untuk mengatasi masalah ini, PHP-FIG (Framework Interop Group) merumuskan **PSR-3 (Logger Interface)**.

```
+-----------------------------------------------------------+
|                   Application Layer                       |
|           (Depends on Psr\Log\LoggerInterface)            |
+-----------------------------------------------------------+
                             |
                             v
+-----------------------------------------------------------+
|                  Monolog\Logger (Core)                    |
+-----------------------------------------------------------+
         |                                    |
         v (Enrich)                           v (Handle)
+-------------------+                +----------------------+
|    Processors     |                |   Handlers (Stack)   |
| - Introspection   |                | - FingersCrossed     |
| - MemoryUsage     |                | - StreamHandler      |
| - UidProcessor    |                +----------------------+
+-------------------+                           |
                                                v (Format)
                                     +----------------------+
                                     |      Formatters      |
                                     | - JsonFormatter      |
                                     | - LineFormatter      |
                                     +----------------------+
```

#### Standardisasi PSR-3
PSR-3 mendefinisikan sebuah kontrak tunggal: `Psr\Log\LoggerInterface`. Interface ini mengekspos 8 level keparahan log yang diturunkan langsung dari standar **RFC 5424**:
1. **Emergency**: Sistem tidak dapat digunakan sama sekali (*system is down*).
2. **Alert**: Tindakan harus segera diambil (misal: seluruh database down, korupsi data primer).
3. **Critical**: Kondisi kritis (misal: komponen penting aplikasi mati, unhandled exception utama).
4. **Error**: Kesalahan runtime yang tidak memerlukan aksi langsung namun harus dimonitor.
5. **Warning**: Peristiwa aneh yang berpotensi memicu error (misal: penggunaan API deprecated).
6. **Notice**: Peristiwa normal namun bernilai signifikan.
7. **Info**: Peristiwa operasional biasa (misal: *user login*, *transaction initiated*).
8. **Debug**: Informasi detail untuk keperluan pelacakan bug teknis (*flow tracing*).

Kunci utama PSR-3 adalah **Message & Context Separation**. Pesan log harus berupa string atau objek yang mengimplementasikan `__toString()`, dan dapat memanfaatkan sintaks placeholder `{key}`. Variabel dinamis tidak boleh langsung digabungkan melalui konkatenasi string, melainkan dilewatkan melalui array `$context`. Ini memungkinkan pemrosesan log downstream (seperti parser JSON) membaca konteks sebagai metadata terstruktur.

#### Arsitektur Monolog (v3.x)
Monolog merupakan implementasi *de facto* dari PSR-3. Arsitektur Monolog dibangun di atas tiga pilar utama:
1. **Handlers**: Komponen yang menerima log record dan menentukan ke mana log tersebut diarahkan (file, standard I/O, socket, service remote seperti Sentry/Elasticsearch). Handler tersusun dalam struktur **Stack (LIFO)**. Sebuah handler dapat menghentikan propagasi log ke handler berikutnya (*bubbling*).
2. **Processors**: Komponen middleware yang meng-enrich (*memperkaya*) metadata log record sebelum diteruskan ke handler (misalnya: menambahkan memory usage, Git commit hash, request UUID, atau IP client).
3. **Formatters**: Komponen yang mengubah objek/array log record menjadi representasi string atau format target (misalnya: plaintext via `LineFormatter`, atau JSON via `JsonFormatter`) sebelum handler mengeksekusi I/O write.

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi production-ready Monolog 3.x menggunakan PSR-3, memanfaatkan konfigurasi pipeline modern: JSON formatting, context enrichment, dan *fail-safe logging*.

```php
<?php

declare(strict_types=1);

namespace App\Infrastructure\Logging;

use Monolog\Logger;
use Monolog\Level;
use Monolog\Handler\StreamHandler;
use Monolog\Handler\FingersCrossedHandler;
use Monolog\Formatter\JsonFormatter;
use Monolog\Processor\MemoryUsageProcessor;
use Monolog\Processor\IntrospectionProcessor;
use Psr\Log\LoggerInterface;

final class LoggerFactory
{
    /**
     * Membangun instance PSR-3 Logger dengan arsitektur multi-handler.
     */
    public static function create(string $channelName, string $logPath): LoggerInterface
    {
        $logger = new Logger($channelName);

        // 1. Processors: Memperkaya konteks secara otomatis
        $logger->pushProcessor(new MemoryUsageProcessor());
        $logger->pushProcessor(new IntrospectionProcessor(
            level: Level::Error,
            skipClassesPartials: ['Monolog\\', 'App\\Infrastructure\\Logging\\']
        ));

        // Processor kustom untuk Trace Context (Distributed Tracing / Correlation ID)
        $logger->pushProcessor(function (\Monolog\LogRecord $record): \Monolog\LogRecord {
            $correlationId = $_SERVER['HTTP_X_CORRELATION_ID'] ?? bin2hex(random_bytes(8));
            return $record->with(extra: array_merge($record->extra, [
                'correlation_id' => $correlationId,
                'php_version'    => PHP_VERSION,
            ]));
        });

        // 2. Formatter: Standardisasi JSON untuk kompatibilitas ELK/Loki/CloudWatch
        $jsonFormatter = new JsonFormatter(
            batchMode: JsonFormatter::BATCH_MODE_JSON,
            appendNewline: true
        );

        // 3. Low-Level Handler: Output ke stream (File / stdout)
        $fileStream = new StreamHandler($logPath, Level::Debug);
        $fileStream->setFormatter($jsonFormatter);

        // 4. FingersCrossedHandler: Buffering log debug/info di memory,
        // HANYA flush ke file jika terjadi level ERROR atau lebih tinggi.
        // Sangat menghemat disk I/O di environment production.
        $fingersCrossedHandler = new FingersCrossedHandler(
            handler: $fileStream,
            activationStrategy: Level::Error,
            bufferSize: 100,
            bubble: true
        );

        $logger->pushHandler($fingersCrossedHandler);

        return $logger;
    }
}

// ===============================================================
// Penggunaan dalam Domain Service
// ===============================================================

final class OrderProcessingService
{
    public function __construct(
        private readonly LoggerInterface $logger // Injeksi via interface, decoupling total
    ) {}

    public function processOrder(string $orderId, float $amount, string $userId): void
    {
        // Debug record akan di-buffer di memory oleh FingersCrossedHandler
        $this->logger->debug('Memulai validasi order state', [
            'order_id' => $orderId,
            'user_id'  => $userId,
        ]);

        try {
            if ($amount <= 0) {
                throw new \InvalidArgumentException('Nilai transaksi order tidak valid.');
            }

            // Simulasi proses bisnis berhasil
            $this->logger->info('Order berhasil diproses untuk {orderId}', [
                'orderId' => $orderId,
                'amount'  => $amount,
                'status'  => 'COMPLETED',
            ]);
        } catch (\Throwable $e) {
            // Ketika level ERROR terpicu, seluruh log debug sebelumnya
            // yang tersimpan dalam buffer akan ikut dituliskan ke file.
            $this->logger->error('Gagal memproses transaksi {orderId}: {reason}', [
                'orderId'   => $orderId,
                'reason'    => $e->getMessage(),
                'exception' => $e, // Monolog otomatis melakukan extract trace & class
            ]);

            throw $e;
        }
    }
}

// Inisialisasi dan Eksekusi
$logger = LoggerFactory::create('checkout-service', __DIR__ . '/app.log');
$service = new OrderProcessingService($logger);

try {
    $service->processOrder('ORD-9901', -25000.0, 'USR-441');
} catch (\Throwable) {
    // Exception ditangani di layer terluar
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Monolog 3 `LogRecord` Pipeline
Di PHP 8.1+, Monolog v3 beralih menggunakan *readonly class* `Monolog\LogRecord` menggantikan format array asosiatif warisan Monolog v1/v2:
1. Ketika `$logger->error($message, $context)` dipanggil, Monolog menginstansiasi objek immutabel `LogRecord`.
2. Logging pipeline bersifat sekuensial synchronous: record dialirkan melalui array `$processors`. Setiap processor mengembalikan salinan (`clone/with`) objek `LogRecord` baru dengan metadata tambahan pada properti `$extra`.
3. Handler dievaluasi dalam model **LIFO (Last-In, First-Out)**. Handler yang terakhir di-*push* akan dieksekusi pertama kali. Jika handler mengembalikan `$bubble = false`, rantai eksekusi terputus dan handler di bawahnya diabaikan.

```
Log Call -> [Record Object] -> Processors -> Handlers Stack (LIFO) -> Formatter -> I/O Stream
```

#### Alokasi Memori / Resource: Stream Handling & Buffering
- **File Descriptors**: `StreamHandler` membuka PHP stream resource menggunakan `fopen($stream, 'a')`. Di PHP standard runtime, resource ini tetap terbuka dalam memori proses selama siklus request HTTP atau siklus iterasi worker CLI berlangsung (long-running process).
- **Concurrency & Locking**: Secara default, `StreamHandler` Monolog tidak melakukan locking file (`LOCK_EX`) otomatis untuk mencegah *performance degradation*. Pada skenario multi-worker (seperti PHP-FPM pool dengan ratusan child processes yang menulis ke satu file log mentah yang sama), operasi write atomic dibatasi oleh limit buffer OS (`PIPE_BUF` di sistem POSIX, biasanya 4096 bytes). Jika panjang baris log melebihi ukuran ini, *race condition* dapat menyebabkan log terpotong (*interleaved output*).
- **FingersCrossedHandler Memory Footprint**: Handler ini menyimpan instansiasi `LogRecord` di dalam array memory buffer internal. Jika `bufferSize` diatur terlalu besar (misal 50.000 log) pada worker yang memproses data masif, alokasi heap memori Zend Engine akan melonjak secara eksponensial sebelum sempat dibersihkan oleh Garbage Collector.

#### Trade-offs
| Pendekatan | Kelebihan | Kelemahan |
| :--- | :--- | :--- |
| **Direct File Logging (`StreamHandler`)** | Sederhana, zero-dependency infrastruktur luar. | Memblokir I/O thread PHP, rawan contention saat konkurensi tinggi. |
| **In-Memory Buffering (`FingersCrossed`)** | Sangat cepat (zero I/O write) saat operasi sukses tanpa error. | Jika aplikasi crash fatal (misal `SIGKILL` dari OOM), log di buffer hilang total. |
| **Stdout to Agent (Loki/Vector/Fluentd)** | Non-blocking di level container, format seragam via stdout. | Bergantung pada availability background agent di host machine. |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Context Array untuk Nilai Dinamis**: Tulis `$logger->info('Payment for order {id} processed', ['id' => $id])`. Parser log terpusat dapat mengindeks `id` sebagai metadata yang bisa di-query tanpa merusak regex parser string.
- **Pass Exception Object Utuh**: Selalu sertakan key `'exception' => $e` di dalam context array. Monolog memiliki normalizer bawaan yang mengekstrak full stack-trace, class name, error code, hingga previous exception secara mendalam tanpa perlu melakukan manual casting `(string) $e`.
- **Gunakan Format JSON di Production**: Format JSON mentah memudahkan ingestion oleh agregator log industri (Elasticsearch, OpenSearch, Datadog, Grafana Loki).

#### Don'ts
- **Jangan Gunakan Konkatenasi String / `sprintf`**: Menulis `$logger->info("User " . $user->id . " logged in")` merusak kapabilitas agregasi pattern log (log management tool akan menganggap setiap log sebagai tipe event yang berbeda).
- **Jangan Log Data Sensitif (PII / Secrets)**: Jangan memasukkan *credit card number*, *plaintext password*, *bearer token*, atau data identitas pribadi (PII) ke dalam message atau context tanpa proses masking / redacting via Processor.
- **Jangan Menginisialisasi Ulang Logger di Dalam Loop**: Menginisialisasi handler dan processor berulang kali di dalam loop iterasi masif dapat menyebabkan kebocoran memory (*memory leaks*) dan limit exhaustion pada file descriptor OS.

#### Edge Cases
- **Circular References dalam Context**: Jika Anda memasukkan Entity object (misal ORM Doctrine entity) yang memiliki relasi dua arah (*bidirectional relationship*) ke dalam `$context`, serializer bawaan Monolog dapat mengalami *infinite recursion* yang memicu `Fatal Error: Maximum execution time exceeded` atau `Memory Exhaustion`.
  *Solusi*: Ekstrak representasi primitif (misal `$entity->getId()`) daripada memasukkan objek domain model mentah ke context.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Redacting Processor**: Buat sebuah Monolog `ProcessorInterface` kustom yang secara rekursif menelusuri array context dan melakukan enkripsi atau masking (`***MASKED***`) pada key sensitif seperti `password`, `token`, `authorization`, dan `credit_card`.
2. **Custom PSR-3 Interpolator**: Bangun kelas minimalis dari nol yang mengimplementasikan `Psr\Log\LoggerInterface` (bukan Monolog). Tulis algoritma penggantian placeholder `{key}` menggunakan regular expression atau `strtr`, sembari memastikan nilai objek non-stringable dalam context ditangani dengan aman tanpa melempar PHP Fatal Error.
3. **Audit File Descriptor CLI**: Jalankan script PHP CLI long-running (worker loop) yang mencatat log dengan `StreamHandler`. Gunakan utilitas sistem operasi `lsof -p <PID>` (di Linux/macOS) untuk memverifikasi apakah file descriptor log ditutup dengan benar saat script di-terminate via signal `SIGINT` atau `SIGTERM`.
