### 1. Konsep & Arsitektur Mendalam

JSON Web Token (JWT) yang didefinisikan dalam **RFC 7519** adalah standar terbuka ringkas (*compact*) dan mandiri (*self-contained*) untuk mentransmisikan informasi secara aman antarpihak sebagai objek JSON. Dalam arsitektur modern, JWT sering dipasangkan dengan skema HTTP Authentication **Bearer Token** (RFC 6750).

#### Anatomi JWT
Sebuah token JWT terdiri dari tiga bagian string yang dipisahkan oleh karakter titik (`.`):
```text
Header.Payload.Signature
```
Setiap komponen di-*encode* menggunakan format **Base64URL** (bukan Base64 standar; karakter `+` diganti `-`, `/` diganti `_`, dan *padding* `=` dihilangkan agar URL-safe):

1. **Header**: Metadata tentang algoritma kriptografi (`alg`, misal: `HS256`, `RS256`, `EdDSA`) dan tipe token (`typ: "JWT"`).
2. **Payload**: Berisi klaim (*claims*) data. Terbagi menjadi:
   - *Registered Claims*: Klaim standar yang direkomendasikan seperti `iss` (issuer), `sub` (subject), `aud` (audience), `exp` (expiration time), `nbf` (not before), dan `iat` (issued at).
   - *Public Claims*: Klaim yang didefinisikan bebas namun harus menghindari collision (biasanya berbentuk IANA JSON Web Token Registry atau URI).
   - *Private Claims*: Data custom kesepakatan antara server dan klien (misal: `user_id`, `role`).
3. **Signature**: Verifikasi integritas. Dibuat dengan mengambil *header* dan *payload* yang telah di-Base64URL-encode, digabungkan dengan delimiter titik, lalu di-hash menggunakan *secret key* (HMAC simetrik) atau *private key* (Asimetrik seperti RSA/ECDSA).

```text
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  secret
)
```

#### Alur Bearer Authentication
Berbeda dengan Session-based auth konvensional yang bersifat *stateful* (state disimpan di server memory/Redis/DB dan ID disimpan di Cookie), JWT umumnya diimplementasikan secara *stateless*:
1. Klien mengirim kredensial (username/password) ke server via endpoint login.
2. Server memvalidasi kredensial ke database. Jika valid, server mengonstruksi payload, menandatanganinya secara kriptografis, dan mengembalikan token string ke klien.
3. Klien menyimpan token (misalnya di Secure Memory, HttpOnly Cookie, atau Storage) dan melampirkannya pada setiap *request* berikutnya di HTTP Header:
   ```http
   Authorization: Bearer <token_jwt>
   ```
4. Server membaca header tersebut, memverifikasi tanda tangan kriptografis secara lokal tanpa perlu query state/database session, memvalidasi klaim waktu (`exp`, `nbf`), lalu mengekstrak identitas pengguna dari klaim `sub`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi *low-level* berbasis native PHP 8.2+ untuk memahami mekanisme internal penandatanganan dan verifikasi HMAC-SHA256 (tanpa *third-party library*), diikuti oleh Middleware ekstraksi Bearer auth.

```php
<?php

declare(strict_types=1);

namespace App\Security;

use RuntimeException;
use InvalidArgumentException;

final class SimpleJwtService
{
    public function __construct(
        private readonly string $secretKey,
        private readonly string $issuer = 'https://api.domain.com'
    ) {
        if (strlen($this->secretKey) < 32) {
            throw new InvalidArgumentException('Secret key must be at least 256 bits (32 bytes).');
        }
    }

    /**
     * Membuat JWT token baru.
     *
     * @param array<string, mixed> $customClaims
     */
    public function generateToken(string $userId, array $customClaims = [], int $ttl = 3600): string
    {
        $now = time();

        $header = [
            'typ' => 'JWT',
            'alg' => 'HS256'
        ];

        $payload = array_merge($customClaims, [
            'iss' => $this->issuer,
            'sub' => $userId,
            'iat' => $now,
            'nbf' => $now,
            'exp' => $now + $ttl,
        ]);

        $encodedHeader  = $this->base64UrlEncode((string) json_encode($header, JSON_THROW_ON_ERROR));
        $encodedPayload = $this->base64UrlEncode((string) json_encode($payload, JSON_THROW_ON_ERROR));

        $signature = hash_hmac(
            'sha256',
            "{$encodedHeader}.{$encodedPayload}",
            $this->secretKey,
            true
        );

        $encodedSignature = $this->base64UrlEncode($signature);

        return "{$encodedHeader}.{$encodedPayload}.{$encodedSignature}";
    }

    /**
     * Memverifikasi token dan mengembalikan decoded payload jika valid.
     *
     * @return array<string, mixed>
     */
    public function verifyAndDecode(string $token): array
    {
        $parts = explode('.', $token);

        if (count($parts) !== 3) {
            throw new InvalidArgumentException('Format token tidak valid.');
        }

        [$encodedHeader, $encodedPayload, $encodedSignature] = $parts;

        // 1. Verifikasi Header
        $header = json_decode($this->base64UrlDecode($encodedHeader), true, 512, JSON_THROW_ON_ERROR);
        if (($header['alg'] ?? null) !== 'HS256' || ($header['typ'] ?? null) !== 'JWT') {
            throw new RuntimeException('Algoritma atau tipe token tidak didukung.');
        }

        // 2. Verifikasi Signature menggunakan Constant-Time Comparison
        $expectedSignature = hash_hmac(
            'sha256',
            "{$encodedHeader}.{$encodedPayload}",
            $this->secretKey,
            true
        );

        $actualSignature = $this->base64UrlDecode($encodedSignature);

        if (!hash_equals($expectedSignature, $actualSignature)) {
            throw new RuntimeException('Signature tidak valid! Token telah dimanipulasi.');
        }

        // 3. Verifikasi Claims Waktu
        $payload = json_decode($this->base64UrlDecode($encodedPayload), true, 512, JSON_THROW_ON_ERROR);
        $currentTime = time();

        if (isset($payload['exp']) && $currentTime >= $payload['exp']) {
            throw new RuntimeException('Token telah kedaluwarsa.');
        }

        if (isset($payload['nbf']) && $currentTime < $payload['nbf']) {
            throw new RuntimeException('Token belum aktif digunakan.');
        }

        return $payload;
    }

    private function base64UrlEncode(string $data): string
    {
        return rtrim(strtr(base64_encode($data), '+/', '-_'), '=');
    }

    private function base64UrlDecode(string $data): string
    {
        $remainder = strlen($data) % 4;
        if ($remainder) {
            $data .= str_repeat('=', 4 - $remainder);
        }
        return base64_decode(strtr($data, '-_', '+/')) ?: '';
    }
}
```

#### Middleware Handler untuk Bearer Token

```php
<?php

declare(strict_types=1);

namespace App\Http\Middleware;

use App\Security\SimpleJwtService;
use Exception;

final class BearerAuthMiddleware
{
    public function __construct(private readonly SimpleJwtService $jwtService) {}

    public function handle(): void
    {
        $authHeader = $_SERVER['HTTP_AUTHORIZATION'] ?? '';

        // Tangani kasus modul Apache/FPM yang tidak meneruskan Header HTTP Authorization
        if ($authHeader === '' && function_exists('apache_request_headers')) {
            $headers = apache_request_headers();
            $authHeader = $headers['Authorization'] ?? $headers['authorization'] ?? '';
        }

        if (!preg_match('/^Bearer\s+(.+)$/i', $authHeader, $matches)) {
            $this->abort(401, 'Bearer token tidak ditemukan dalam request.');
        }

        $token = $matches[1];

        try {
            $claims = $this->jwtService->verifyAndDecode($token);
            
            // Masukkan data user terautentikasi ke context aplikasi/request global
            $_SERVER['AUTH_USER_ID'] = $claims['sub'];
            $_SERVER['AUTH_CLAIMS']  = $claims;

        } catch (Exception $e) {
            $this->abort(401, 'Autentikasi Gagal: ' . $e->getMessage());
        }
    }

    private function abort(int $code, string $message): never
    {
        http_response_code($code);
        header('Content-Type: application/json');
        echo json_encode(['error' => $message]);
        exit;
    }
}

// Inisialisasi dan Eksekusi
$secretKey = 'b15a6b0c3f4e1d2c3b4a596877889900aabbccddeeff00112233445566778899';
$jwtService = new SimpleJwtService($secretKey);

// Simulasi Request
$token = $jwtService->generateToken(userId: 'usr_987654', customClaims: ['role' => 'admin']);
$_SERVER['HTTP_AUTHORIZATION'] = "Bearer {$token}";

$middleware = new BearerAuthMiddleware($jwtService);
$middleware->handle();

echo "User terautentikasi: " . $_SERVER['AUTH_USER_ID'];
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Kriptografi
- `hash_hmac()` mendelegasikan hashing ke engine OpenSSL atau engine hash internal PHP yang di-compile ke C binary. Pada tingkat kernel/CPU, fungsi hashing simetris (seperti SHA-256) memanfaatkan instruksi akselerasi hardware seperti Intel SHA Extensions.
- **Timing Attack Mitigation**: Baris `hash_equals($expectedSignature, $actualSignature)` wajib digunakan dibanding `===`. Operator perbandingan string biasa (`===`) menghentikan evaluasi byte seketika saat ditemukan byte yang tidak cocok (short-circuiting). Hal ini mengekspos celah waktu (dihitung dalam nanodetik) yang memungkinkan penyerang menebak signature byte-per-byte. `hash_equals` mengoperasikan verifikasi *constant time*.

#### Alokasi Memori & Siklus Hidup PHP
- PHP menganut model eksekusi *Share-Nothing Architecture*. Setiap request HTTP yang masuk ke PHP-FPM mengalokasikan pool memori terpisah (Zend Memory Manager / ZMM).
- Karena JWT stateless, verifikasi token tidak memicu round-trip I/O ke Redis atau database relasional. Verifikasi signature sepenuhnya adalah operasi *CPU-bound* di dalam ruang memori eksekusi worker PHP-FPM, mengurangi latency koneksi jaringan per-request.

#### Trade-offs: Stateless vs State Invalidation
- **Keuntungan**: Skalabilitas horisontal optimal. Node server API di belakang Load Balancer tidak perlu berbagi shared session store untuk sekadar memverifikasi status login.
- **Kelemahan**: Invalidation problem. Sekali JWT terbit, token sah sampai masa `exp` habis. Jika token bocor, server tidak bisa langsung membatalkannya (revoke) secara native tanpa mengorbankan sifat stateless-nya (misal: harus membuat denylist di Redis).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Validasi Nilai Algoritma Secara Eksplisit**: Pastikan membatasi algoritma (`alg`) yang diharapkan dalam validator. Jika server dikonfigurasi untuk `HS256`, tolak token yang menyertakan algoritma lain dalam headernya.
- **Gunakan Secret yang Kuat**: Secret untuk HMAC-SHA256 minimal harus berupa string kriptografis acak sebesar 256-bit (32 bytes generated via `random_bytes(32)`).
- **Gunakan Durasi Kedaluwarsa yang Singkat**: Terapkan masa hidup *Access Token* yang pendek (5-15 menit) dan gunakan *Refresh Token* (yang disimpan di database) untuk merotasi access token.
- **Enkripsi Channel Pengiriman**: Wajib gunakan protokol HTTPS/TLS. Payload JWT di-encode, **bukan di-enkripsi**. Siapa pun yang melakukan sniffing paket HTTP dapat membaca payload secara transparan.

#### Don'ts
- **Menyimpan Sensitif PII di Payload**: Jangan letakkan password, hash, nomor kartu kredit, atau data privat sensitif di dalam Payload JWT.
- **Menerima Algoritma `"alg": "none"`**: Beberapa parser library lama rentan terhadap celah kritis di mana penyerang mengubah header menjadi `{"alg": "none"}` dan menghapus signature, menyebabkan parser menganggap token valid tanpa verifikasi.
- **Menyimpan Token di `localStorage` Browser**: Menyimpan Bearer Token di `localStorage` atau `sessionStorage` membuka celah token dicuri via serangan **XSS (Cross-Site Scripting)**. Lebih disarankan menyimpan token di HttpOnly + Secure + SameSite Cookies jika klien adalah web browser.

#### Edge Cases
- **Clock Skew (Perbedaan Waktu Antar Server)**: Perbedaan sinkronisasi clock NTP antar server auth dan server resource dapat menyebabkan token yang baru saja dibuat ditolak karena klaim `nbf` (not before) dianggap belum tercapai, atau klaim `exp` dianggap telah lewat. Solusinya, terapkan toleransi waktu kecil (*leeway*) sebesar 30–60 detik saat membandingkan timestamp.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Leeway Clock Skew**:
   Modifikasi fungsi `verifyAndDecode` pada kelas `SimpleJwtService` di atas agar menerima parameter `$leeway = 60` (dalam detik) untuk mengakomodasi jeda sinkronisasi clock server saat memvalidasi `exp` dan `nbf`.
2. **Asymmetric Key Migration (RS256/EdDSA)**:
   Ubah metode penandatanganan di atas dari pendekatan simetrik (HMAC) menjadi asimetrik (RSA menggunakan `openssl_sign` & `openssl_verify` dengan pasangan Private & Public Key). Analisis mengapa arsitektur microservices lebih menyukai RS256/EdDSA dibandingkan HS256!
3. **Mekanisme Blacklist/Revocation Token**:
   Rancang arsitektur di mana user dapat melakukan `Logout` sebelum masa `exp` berakhir. Buat prototipe integrasi Redis di level Middleware untuk mencatat token yang di-*revoke* (menggunakan TTL otomatis sesuai sisa masa kedaluwarsa token) tanpa membebani performa database utama.
