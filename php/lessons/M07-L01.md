## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum era modern PHP, pengelolaan pustaka pihak ketiga bergantung pada pemanggilan manual menggunakan `require`, `include`, atau skrip kustom yang rentan terhadap masalah *dependency hell*, tabrakan nama (*name collision*), dan degradasi performa I/O akibat pengecekan `include_path`. 

Composer hadir bukan sebagai manajer paket sistem (seperti `apt` atau `brew`), melainkan sebagai **Application-Level Dependency Manager**. Arsitektur pengelolaan dependensi dan pemuatan kode di Composer ditopang oleh tiga pilar utama:

```
+-------------------------------------------------------------+
|                        composer.json                        |
|  (Deklarasi intensi, constraint versi, & metadata PSR-4)    |
+-------------------------------------------------------------+
                               |
                   [ SAT Solver / Resolver ]
                               |
                               v
+-------------------------------------------------------------+
|                        composer.lock                        |
|  (Peta deterministik: commit hash spesifik & content-hash)  |
+-------------------------------------------------------------+
                               |
                 [ composer dump-autoload ]
                               |
                               v
+-------------------------------------------------------------+
|                    vendor/autoload.php                      |
|       (SPL Autoload Register -> Zend Engine VM Hook)        |
+-------------------------------------------------------------+
```

#### A. Deklarasi Intensi vs. Determinisme: `composer.json` vs `composer.lock`
- **`composer.json`**: Berisi *intensi* dan batasan (*constraints*) versi abstrak (misalnya `^8.2`, `~1.4.0`). File ini mendefinisikan apa yang dibutuhkan aplikasi secara fleksibel menggunakan format *Semantic Versioning* (SemVer).
- **`composer.lock`**: Menyimpan status *realisasi konkret* dari pohon dependensi. Berisi URL repositori, commit hash Git yang presisi, dan checksum kriptografis dari setiap pustaka yang terunduh. Terdapat atribut `content-hash` (MD5/SHA dari konfigurasi `composer.json`) yang memvalidasi apakah file `.lock` masih sinkron dengan perubahan pada `.json`.

Resolusi dependensi Composer dijalankan menggunakan algoritma **SAT (Boolean Satisfiability) Solver**. Solver ini memetakan seluruh batasan dependensi ke dalam bentuk *Conjunctive Normal Form* (CNF) untuk menemukan kombinasi versi pustaka yang tidak menimbulkan konflik sebelum mengunduh aset.

#### B. PSR-4 (PHP Standard Recommendation 4)
PSR-4 adalah spesifikasi autoloading yang diresmikan oleh PHP-FIG (Framework Interop Group) untuk menggantikan PSR-0. 

Aturan formal PSR-4 memetakan struktur *Fully Qualified Class Name* (FQCN):
$$\text{\textbackslash NamespacePrefix\textbackslash SubNamespace\textbackslash ClassName}$$

Ke jalur file fisik:
$$\text{/base/directory/SubNamespace/ClassName.php}$$

Perbedaan mendasar dengan PSR-0: Pada PSR-4, **Namespace Prefix tidak ikut diterjemahkan menjadi direktori fisik**. Hanya sub-namespace setelah prefix yang dipetakan secara absolut ke direktori file. Ini menghilangkan keharusan membuat struktur folder bersarang yang redundan (misal: `/src/Vendor/Package/` cukup dipetakan langsung dari root `/src`).

#### C. Integrasi SPL (Standard PHP Library) dengan Zend VM
Di balik layar, autoloading mengeksploitasi fungsi `spl_autoload_register()`. Ketika Zend Engine mengeksekusi bytecode dan menemukan identifier kelas, antarmuka, *trait*, atau *enum* yang belum dialokasikan di tabel simbol memori (`EG(class_table)`), Zend VM memicu interupsi internal:
1. Eksekusi engine ditunda sementara.
2. Zend VM menelusuri rantai fungsi (*autoload queue*) yang didaftarkan oleh `spl_autoload_register()`.
3. Autoloader milik Composer mengevaluasi string FQCN, memetakan path file, dan mengeksekusinya via `include` internal ke dalam konteks runtime.
4. Jika kelas berhasil dimuat ke dalam `EG(class_table)`, instruksi opcode yang tertunda dilanjutkan; jika tidak, engine melempar fatal error `Class not found`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah konfigurasi produksi tipikal yang memisahkan kode domain inti, kode pengujian, dan dependensi dengan kepatuhan PSR-4:

#### Struktur Proyek
```text
my-project/
├── composer.json
├── composer.lock
├── src/
│   ├── Domain/
│   │   └── Payment/
│   │       └── Invoice.php
│   └── Infrastructure/
├── tests/
│   └── Unit/
│       └── InvoiceTest.php
└── public/
    └── index.php
```

#### 1. Definisi `composer.json`
```json
{
    "name": "acme/payment-engine",
    "description": "Sistem pemrosesan invoice deterministik.",
    "type": "project",
    "license": "Proprietary",
    "require": {
        "php": ">=8.2",
        "monolog/monolog": "^3.5"
    },
    "require-dev": {
        "phpunit/phpunit": "^10.4"
    },
    "autoload": {
        "psr-4": {
            "Acme\\Payment\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "Acme\\Payment\\Tests\\": "tests/"
        }
    },
    "config": {
        "optimize-autoloader": true,
        "sort-packages": true,
        "platform": {
            "php": "8.2.13"
        }
    }
}
```

#### 2. Definisi Kelas PHP (`src/Domain/Payment/Invoice.php`)
```php
<?php

declare(strict_types=1);

namespace Acme\Payment\Domain\Payment;

use Monolog\Logger;

final class Invoice
{
    public function __construct(
        private string $id,
        private int $amountInCents,
        private ?Logger $logger = null
    ) {}

    public function process(): void
    {
        $this->logger?->info("Memproses invoice: {$this->id}");
        // Logika domain
    }

    public function getAmount(): int
    {
        return $this->amountInCents;
    }
}
```

#### 3. Entry Point & Konsumsi Autoloader (`public/index.php`)
```php
<?php

declare(strict_types=1);

use Acme\Payment\Domain\Payment\Invoice;
use Monolog\Handler\StreamHandler;
use Monolog\Logger;

// 1. Bootstrapping Autoloader Composer
require_once __DIR__ . '/../vendor/autoload.php';

// 2. Inisialisasi dependensi
$logger = new Logger('payment');
$logger->pushHandler(new StreamHandler('php://stdout', Logger::DEBUG));

// 3. Zend VM menginterupsi pemanggilan ini; autoloader memuat file 'src/Domain/Payment/Invoice.php'
$invoice = new Invoice(
    id: 'INV-2023-001',
    amountInCents: 500000,
    logger: $logger
);

$invoice->process();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Lifecycle Runtime
Saat Composer menghasilkan autoloader (`composer dump-autoload`), ia membangun beberapa file statis di `vendor/composer/`:
- `autoload_psr4.php`: Menyimpan array asosiatif hierarki namespace terhadap path absolut.
- `autoload_classmap.php`: Peta datar satu-ke-satu (*one-to-one dictionary*) antara FQCN dan path file.
- `autoload_real.php`: Menginisialisasi instans `Composer\Autoload\ClassLoader`.

Proses resolusi kelas standar PSR-4:
```
Resolve FQCN 
  -> Potong prefix namespace terdaftar 
  -> Cari panjang kecocokan terpanjang (longest-prefix match)
  -> Konversi separator namespace (\) menjadi DIRECTORY_SEPARATOR (/)
  -> Append ekstensi .php
  -> file_exists() / is_file()
  -> includeFile()
```

#### B. Alokasi Memori, I/O, & Optimasi Autoloader
Pada mode pengembangan (*development mode*), setiap pencarian kelas PSR-4 yang belum dimuat berpotensi menghasilkan *system call* `stat` / `lstat` ke filesystem kernel Linux untuk mengecek keberadaan file. Pada beban ribuan kelas dan traffic tinggi, overhead syscall ini menyebabkan latency I/O yang substansial.

Composer menyediakan beberapa level optimasi:

1. **Level 1: Classmap Generation (`composer dump-autoload -o` / `--optimize`)**
   Composer memindai semua file di bawah aturan PSR-4/PSR-0 dan mengonversinya menjadi array statis raksasa di `autoload_classmap.php`.
   - **Mekanisme**: Pencarian berbasis lookup hash array O(1) di memori, bukan traversal filesystem.
   - **Fallback**: Jika kelas baru tidak ada di classmap, runtime fallback mengecek filesystem secara PSR-4.

2. **Level 2: Authoritative Classmaps (`composer dump-autoload -a` / `--classmap-authoritative`)**
   Mirip Level 1, namun aturan fallback PSR-4 **dinonaktifkan secara permanen**.
   - **Keuntungan**: Jika FQCN tidak ditemukan di classmap, autoloader langsung mengembalikan `false`. Zero disk I/O untuk *missing classes*.
   - **Trade-off**: Evaluasi dinamis atau pemanggilan kelas di luar classmap akan langsung melempar Fatal Error tanpa pengecekan ulang ke disk.

3. **APCu Cache (`--apcu`)**
   Array lookup disimpan di *Shared Memory* menggunakan ekstensi APCu PHP. Sangat efisien jika memori OPcache tidak cukup menampung classmap array yang sangat besar.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Commit `composer.lock` pada Project/Application Repository**: Memastikan seluruh developer, mesin CI/CD, dan server staging/production mengeksekusi commit dependency tree yang 100% identik hingga ke level byte.
- **Definisikan `config.platform.php` di `composer.json`**: Mencegah dependensi ter-update ke versi yang membutuhkan runtime PHP lebih tinggi daripada versi yang aktif di infrastruktur produksi.
- **Gunakan Flag Determinisme di CI/CD Pipeline**:
  ```bash
  composer install --no-dev --prefer-dist --optimize-autoloader --no-progress --no-interaction
  ```

#### Don'ts
- **DILARANG Menjalankan `composer update` di Server Produksi**: Perintah ini menghitung ulang SAT solver secara runtime, berisiko mengunduh versi dependensi baru yang belum teruji, dan dapat membengkakkan konsumsi RAM server seketika (*OOM Killer*).
- **Jangan Commit Direktori `vendor/`**: Menyebabkan *repository bloat*, polusi git history, dan mengaburkan perbedaan kode aplikasi asli.
- **Jangan Menghapus Manual `composer.lock` untuk "Memperbaiki Masalah"**: Ini tindakan antipattern yang menghancurkan determinisme build dan memaksa update liar ke seluruh dependency tree.

#### Edge Cases & Pitfalls Industri
- **Sensitivitas Huruf (Case-Sensitivity Mismatch)**:
  Sistem operasi macOS (secara default APFS/HFS+) dan Windows (NTFS) bersifat *case-insensitive*, sedangkan Linux produksi bersifat *case-sensitive*. Jika nama file Anda `invoice.php` tetapi FQCN-nya `class Invoice`, autoloader di lokal macOS akan memuat file tersebut tanpa error. Namun saat dideploy ke Linux, kernel gagal menemukan file dan melemparkan `Class "Invoice" not found` seketika.
- **Pembersihan Cache Metadata Autoload**:
  Menambahkan file kelas baru secara lokal saat status autoloader berada dalam mode `--classmap-authoritative` tidak akan mendeteksi kelas tersebut sebelum `composer dump-autoload` dijalankan ulang.

### 5. Tantangan Eksplorasi Mandiri

1. **Inspeksi Metrik I/O**: 
   Jalankan `composer dump-autoload` tanpa flag pada proyek yang memiliki lebih dari 30 pustaka, kemudian profil pemanggilan fungsi menggunakan Xdebug atau skrip mikro benchmark `microtime(true)` untuk memuat 200 kelas berbeda. Bandingkan latensinya dengan hasil dari `composer dump-autoload -a`. Berapa persen reduksi waktu eksekusi yang didapatkan?
2. **Rekayasa Kasus `content-hash`**:
   Buka file `composer.json`, ubah deskripsi proyek secara minor tanpa menjalankan composer command. Buka file `composer.lock` dan amati bagian `"content-hash"`. Tulis skrip CLI PHP singkat menggunakan fungsi `hash()` untuk mereproduksi bagaimana Composer menghasilkan nilai hash tersebut dari skema JSON asli.
3. **Analisis File Emisi Autoloader**:
   Jelajahi direktori `vendor/composer/`. Identifikasi file `autoload_static.php` dan jelaskan bagaimana closure scope injection (`\Closure::bind()`) digunakan oleh Composer untuk mem-bypass visibilitas class loader demi mengejar optimasi performa memori.
