## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur *runtime* modern, penanganan kesalahan (*error handling*) menuntut keseimbangan antara dua hal: integritas *resource* (koneksi database, *lock*, *file descriptor*) dan preservasi konteks kegagalan (*root-cause observability*). PHP menyediakan dua mekanisme fundamental untuk memenuhi kebutuhan ini: blok `finally` dan *Exception Chaining*.

```
+-------------------------------------------------------------+
| try Block                                                   |
| (Mengeksekusi operasi rentan kegagalan)                     |
+-------------------------------------------------------------+
         |                                           |
    [Sukses]                                    [Exception]
         v                                           v
+------------------+                    +---------------------+
| Menyiapkan Nilai |                    | catch Block         |
| Return           |                    | (Membungkus ke      |
+------------------+                    |  Domain Exception)  |
         |                              +---------------------+
         |                                           |
         +-------------------+-----------------------+
                             |
                             v
+-------------------------------------------------------------+
| finally Block                                               |
| (Pelepasan Resource / Mutex / Revert State)                 |
| *PASTI DIEKSEKUSI SEBELUM KELUAR DARI STACK FRAME*         |
+-------------------------------------------------------------+
                             |
                             v
+-------------------------------------------------------------+
| Keluar Stack Frame (Return Value atau Propagasi Exception)  |
+-------------------------------------------------------------+
```

#### Blok `finally`
Diperkenalkan pada PHP 5.5, blok `finally` menyelesaikan masalah pelepasan *resource* yang deterministik. Tanpa `finally`, pembersihan *resource* harus diduplikasi di akhir blok `try` dan di dalam setiap blok `catch`.

Blok `finally` menjamin eksekusi instruksi pembersihan, terlepas dari apakah:
1. Tidak ada *exception* yang dilempar.
2. *Exception* dilempar dan tertangkap oleh blok `catch`.
3. *Exception* dilempar tetapi **tidak tertangkap** (akan dipropagasi naik ke pemanggil).
4. Blok `try` atau `catch` mengeksekusi *control flow interrupts* eksplisit seperti `return`, `continue`, atau `break`.

#### Exception Chaining
*Exception Chaining* memungkinkan kita menangkap *exception* tingkat rendah (misalnya `\PDOException` atau `\RedisException`), lalu membungkusnya ke dalam *Domain-Specific Exception* (misalnya `PaymentGatewayUnavailableException`) tanpa menghilangkan jejak kesalahan aslinya (*root cause*). 

Semua kelas turunan `\Throwable` di PHP mendukung parameter `$previous` pada konstruktornya:
```php
public __construct(
    string $message = "",
    int $code = 0,
    ?Throwable $previous = null
)
```
Parameter `$previous` membangun struktur data *Singly-Linked List* di memori, di mana setiap *exception* menyimpan referensi ke penyebab kegagalan sebelumnya. Hal ini sangat krusial pada arsitektur berlapis (*Clean Architecture* atau *Hexagonal Architecture*) agar lapisan domain tidak membocorkan implementasi infrastruktur, namun *observability pipeline* (seperti Sentry, New Relic, atau OpenTelemetry) tetap dapat membaca seluruh *stack trace* sampai ke akar masalah.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi pemrosesan file mutasi rekening bank dengan kontrol transaksi, *file locking*, dan *exception chaining*.

```php
<?php

declare(strict_types=1);

namespace Bank\Infrastructure;

use Throwable;
use RuntimeException;
use InvalidArgumentException;

// Domain Exceptions
class BankTransactionException extends RuntimeException {}
class FileProcessingException extends BankTransactionException {}
class LockAcquisitionException extends BankTransactionException {}

final class MutationProcessor
{
    /**
     * Memproses file mutasi dengan garansi pelepasan resource & exception wrapping.
     *
     * @throws BankTransactionException
     */
    public function process(string $filePath): int
    {
        if (!file_exists($filePath)) {
            throw new InvalidArgumentException("File mutasi tidak ditemukan: {$filePath}");
        }

        $fileHandle = fopen($filePath, 'rb');
        if ($fileHandle === false) {
            throw new FileProcessingException("Gagal membuka stream file: {$filePath}");
        }

        $lockAcquired = false;
        $processedRecords = 0;

        try {
            // Dapatkan exclusive lock (non-blocking)
            $lockAcquired = flock($fileHandle, LOCK_EX | LOCK_NB);
            if (!$lockAcquired) {
                throw new LockAcquisitionException("File sedang diproses oleh proses worker lain.");
            }

            // Simulasi pembacaan baris per baris
            while (($line = fgets($fileHandle)) !== false) {
                $trimmed = trim($line);
                if ($trimmed === '') {
                    continue;
                }

                // Simulasi parsing data yang bisa melempar native Exception
                $this->parseAndPersistRecord($trimmed);
                $processedRecords++;
            }

            return $processedRecords;

        } catch (LockAcquisitionException $e) {
            // Re-throw langsung jika merupakan domain lock exception
            throw $e;

        } catch (Throwable $e) {
            // Exception Chaining: Bungkus technical exception ke domain exception
            // Parameter ke-3 ($e) mempertahankan root cause dan full stack trace
            throw new FileProcessingException(
                message: "Gagal memproses batch mutasi pada baris: " . ($processedRecords + 1),
                code: 500,
                previous: $e
            );

        } finally {
            // Blok ini DIJAMIN dieksekusi:
            // Baik saat sukses (return), caught exception, maupun uncaught exception.
            if ($lockAcquired) {
                flock($fileHandle, LOCK_UN);
            }

            if (is_resource($fileHandle)) {
                fclose($fileHandle);
            }
        }
    }

    private function parseAndPersistRecord(string $rawRecord): void
    {
        // Simulasi error validasi / database runtime
        if (str_contains($rawRecord, 'CORRUPT')) {
            throw new RuntimeException("Checksum integritas baris data tidak valid.");
        }
    }
}

// ==========================================
// Consumer / Runner & Stack Unwinding Logger
// ==========================================

$processor = new MutationProcessor();
$tempFile = tempnam(sys_get_temp_dir(), 'bank_mut_');
file_put_contents($tempFile, "VALID_TRX_1\nCORRUPT_TRX_2\nVALID_TRX_3\n");

try {
    $processor->process($tempFile);
} catch (BankTransactionException $e) {
    echo "[Domain Error]: " . $e->getMessage() . PHP_EOL;

    // Membaca Exception Chain (Traversing the Previous List)
    $rootCause = $e->getPrevious();
    if ($rootCause !== null) {
        echo "[Root Cause]: " . $rootCause::class . " -> " . $rootCause->getMessage() . PHP_EOL;
        echo "[Root Trace]:" . PHP_EOL . $rootCause->getTraceAsString() . PHP_EOL;
    }
} finally {
    if (file_exists($tempFile)) {
        unlink($tempFile);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Zend VM Runtime
Zend Engine (kompiler dan VM runtime PHP) mengelola *exception handling* melalui *exception table* internal yang dipetakan pada *abstract syntax tree* (AST) saat kompilasi menjadi *opcodes*.

1. **Opcode Dispatcher**:
   - Ketika PHP bertemu blok `try-finally`, Zend Engine menghasilkan opcode khusus: `FAST_CALL` dan `FAST_RET`.
   - Pada Zend Engine 3/4 (PHP 7 & 8), saat ada pernyataan `return` di dalam blok `try`, VM tidak langsung keluar dari *stack frame*. VM menyalin nilai balik ke variabel sementara internal (zval), memanggil sub-rutin `finally` melalui `FAST_CALL`, menjalankan instruksi di dalam `finally`, dan setelah opcode `FAST_RET` tercapai, nilai sementara tersebut dikembalikan ke fungsi pemanggil.
   
2. **Stack Unwinding & Exception Tables**:
   - Setiap fungsi memiliki tabel penanganan pengecualian (`zend_op_array->try_catch_array`).
   - Ketika opcode melempar exception (mengisi `EG(exception)` di executor globals), VM menghentikan alur linear dan memulai proses *Stack Unwinding*.
   - Jika ada blok `finally` di scope tersebut, pointer eksekusi VM diarahkan ke awal blok `finally` terlebih dahulu. *Exception* aktif disimpan sementara di `EG(prev_exception)` atau internal buffer agar tidak terhapus.
   - Setelah blok `finally` selesai secara normal, VM melanjutkan propagasi *exception* ke atas jika tidak tertangkap oleh `catch`.

```
Zend VM Stack:
[ Call Frame: process() ]
       |
       +--> Try-Block Start
       |       |
       |     Throws RuntimeException! 
       |       |
       |       v
       |    [Catch Block Matched?] 
       |       |--> Yes: Instansiasi FileProcessingException(previous: $e)
       |       |
       |    [Finally Address Dispatched via FAST_CALL]
       |       |--> Release Lock
       |       |--> Close Resource
       |       v
       |    [FAST_RET / Propagate Exception]
       v
[ Call Frame: Global Caller ] <-- Menangkap FileProcessingException
```

#### Alokasi Memori & Linked List `Throwable`
- Objek `Exception` di PHP adalah *standard object* (`zend_object`). Properti `$previous` adalah referensi pointer zval biasa ke instansi `zend_object` sebelumnya.
- Selama exception pembungkus (*wrapper exception*) masih hidup dalam memori, seluruh *chain* ke bawah akan tetap hidup karena *reference counting* (`gc_refcount`).
- **Trace Allocation Overhead**: Setiap instansi `Throwable` menangkap *backtrace* (`zend_fetch_debug_backtrace`). Chaining berantai 10 lapis berarti 10 salinan metadata *stack trace* (termasuk referensi ke argumen fungsi jika `zend.exception_ignore_args` tidak diaktifkan).

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Gunakan `finally` Khusus untuk Mutasi State/Resource Cleanup**: Gunakan untuk melepaskan mutex, menutup koneksi socket, menghapus file temporary, atau me-reset variabel global/statis.
2. **Selalu Teruskan `$previous` Saat Transformasi Exception**: Saat mengonversi low-level exception (misalnya `PDOException`, `GuzzleHttp\Exception\ClientException`) ke Domain Exception, sertakan instance aslinya sebagai argumen ketiga.
3. **Bungkus Operasi Pembersihan dalam Defensive Logic**: Periksa apakah *resource* valid sebelum melepaskannya di dalam `finally` (misalnya `if (is_resource($file))`).

#### Don'ts:
1. **DILARANG Menaruh `return` di Dalam Blok `finally`**:
   Jika blok `try` melempar *exception*, dan blok `finally` mengeksekusi `return`, PHP akan **secara diam-diam membatalkan *exception* tersebut**. VM akan mengabaikan *exception* dan mengembalikan nilai dari `finally`. Ini adalah *silent failure bug* yang sangat berbahaya.
2. **DILARANG Melempar Exception Baru Tanpa Penanganan dari `finally`**:
   Jika exception terjadi di `try`, lalu exception lain terjadi di `finally`, exception dari `finally` akan menimpa (*discard*) exception asli dari `try`. Konteks error awal hilang seluruhnya dari *unwinding pipeline*.

#### Edge Cases:

*   **Override Nilai Return (Try vs Finally)**:
    ```php
    function test(): string {
        try {
            return "DARI_TRY";
        } finally {
            return "DARI_FINALLY"; // ANTI-PATTERN: Nilai "DARI_TRY" terhapus!
        }
    }
    echo test(); // Menghasilkan: "DARI_FINALLY"
    ```

*   **Fatal Error / Exit di dalam `try`**:
    Jika fungsi `exit()`, `die()`, atau terjadi fatal error out-of-memory (`OOM`) di dalam blok `try`, blok `finally` **TIDAK AKAN** dieksekusi karena *Zend Engine executor* langsung mematikan proses tanpa melakukan *graceful stack unwinding*.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Perilaku Return-Discarding**:
   Buat sebuah fungsi di mana blok `try` melempar `Exception("Error Fatal A")`, namun blok `finally` mengeksekusi `return 42;`. Amati apakah exception tertangkap oleh blok `catch` pemanggil atau justru tertelan sepenuhnya. Jelaskan mengapa hal ini berbahaya dalam sistem finansial!
2. **Implementasikan Recursive Exception Unpacker**:
   Tulis fungsi utilitas bernama `flattenExceptionChain(Throwable $e): array`. Fungsi ini harus melakukan traversal secara rekursif menelusuri `$e->getPrevious()` dan mengembalikan seluruh riwayat class, pesan, file, dan line exception dari yang terluar hingga *root cause* pertama.
3. **Multi-catch dengan Re-wrapping Terseleksi**:
   Buat skenario di mana satu blok `try` berpotensi melempar 3 jenis exception: `DatabaseException`, `ValidationException`, dan `TimeoutException`. Gunakan sintaks *multi-catch* (`catch (DatabaseException | TimeoutException $e)`) untuk membungkusnya ke dalam `InfrastructureException` menggunakan exception chaining, tetapi biarkan `ValidationException` terbebas dan langsung melompat ke pemanggil tanpa di-wrap.
