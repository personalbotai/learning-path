### 1. Konsep & Arsitektur Mendalam

*Integration Testing* memvalidasi orkestrasi antar-komponen aplikasi: HTTP routing, middleware, *dependency injection container*, *business domain service*, hingga ke persistence engine (Database/RDBMS). Berbeda dengan *Unit Testing* yang mengisolasi unit terkecil dengan memotong dependensi menggunakan *mock/stub*, *Integration Testing* justru menguji keabsahan interaksi nyata antar-lapisan tersebut.

```
       [ HTTP Test Request / CLI Invocation ]
                         │
                         ▼
        [ Kernel / Pipeline / Middleware ]
                         │
                         ▼
          [ Application / Domain Layer ]
                         │
                         ▼
             [ Data Access Layer / ORM ]
                         │
                         ▼
           ┌───────────────────────────┐
           │ Real Database Connection  │ <── Transaction Wrapped (BEGIN)
           │ (MySQL / PostgreSQL / etc)│
           └───────────────────────────┘
                         │
                         ▼
            [ Assertions Execution ]
                         │
                         ▼
               [ Auto ROLLBACK ]
```

Dalam ekosistem PHP modern, tantangan terbesar *integration testing* berpusat pada **Database State Isolation** dan **I/O Execution Overhead**:
1. **State Isolation**: Setiap pengujian harus bersifat deterministik dan independen (*hermetic*). Mutasi data yang dilakukan oleh `Test A` tidak boleh memengaruhi pembacaan state oleh `Test B` (*test pollution*).
2. **Database Assertion Strategy**: Assertions tidak hanya mengecek nilai kembalian (*return value* atau *HTTP response payload*), melainkan memverifikasi *side-effect* langsung pada media persistensi—seperti ketersediaan rekaman data (*row existence*), integritas relasi (*foreign key constraints*), *soft-deletes*, hingga mutasi nilai kolom secara presisi.

Mengapa *mocking* pada lapisan database (misalnya melakukan mocking pada interface repository atau PDO) dianggap sebagai *anti-pattern* pada integration test? Karena mock tidak mengeksekusi *type casting* bawaan database, trigger, constraint checking, query syntax validity, maupun race-condition behavior yang sesungguhnya.

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: Sistem Checkout E-Commerce. Saat order dibuat, sistem harus mengurangi stok barang secara atomik, menyimpan data order, mencatat *order items*, dan memastikan kalkulasi total harga tersimpan akurat ke database.

Implementasi menggunakan basis **PHPUnit 10+** dengan integrasi Laravel Testing Framework (standar de facto di ekosistem enterprise PHP).

```php
<?php

declare(strict_types=1);

namespace Tests\Feature\Orders;

use App\Models\Inventory;
use App\Models\Product;
use App\Models\User;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Illuminate\Http\Response;
use Tests\TestCase;

final class OrderCheckoutIntegrationTest extends TestCase
{
    // Menggunakan trait isolasi database via transaksi
    use RefreshDatabase;

    private User $customer;
    private Product $product;
    private Inventory $inventory;

    protected function setUp(): void
    {
        parent::setUp();

        // 1. Arrange: Siapkan state awal database menggunakan Factory
        $this->customer = User::factory()->create();
        
        $this->product = Product::factory()->create([
            'price_in_cents' => 250_000, // Rp 2.500,00
            'is_active' => true,
        ]);

        $this->inventory = Inventory::factory()->create([
            'product_id' => $this->product->id,
            'stock_quantity' => 10,
        ]);
    }

    public function test_user_can_successfully_checkout_and_deduct_inventory(): void
    {
        $payload = [
            'items' => [
                [
                    'product_id' => $this->product->id,
                    'quantity' => 3,
                ],
            ],
        ];

        // 2. Act: Eksekusi endpoint checkout menggunakan authenticated HTTP client
        $response = $this->actingAs($this->customer, 'sanctum')
            ->postJson('/api/v1/orders/checkout', $payload);

        // 3. Assert (HTTP Layer): Verifikasi status code dan skema response
        $response->assertStatus(Response::HTTP_CREATED)
            ->assertJsonPath('status', 'success')
            ->assertJsonStructure([
                'data' => ['order_id', 'total_amount_in_cents', 'status']
            ]);

        $orderId = $response->json('data.order_id');

        // 4. Assert (Database State - Integration Checks):
        
        // Memastikan record 'orders' terbuat dengan data relasi customer yang benar
        $this->assertDatabaseHas('orders', [
            'id' => $orderId,
            'user_id' => $this->customer->id,
            'total_amount_in_cents' => 750_000,
            'status' => 'PENDING_PAYMENT',
        ]);

        // Memastikan record detail pesanan tersimpan di relasi 'order_items'
        $this->assertDatabaseHas('order_items', [
            'order_id' => $orderId,
            'product_id' => $this->product->id,
            'quantity' => 3,
            'unit_price_in_cents' => 250_000,
        ]);

        // Verifikasi mutasi state inventaris: stok terpotong dari 10 menjadi 7
        $this->assertDatabaseHas('inventories', [
            'product_id' => $this->product->id,
            'stock_quantity' => 7,
        ]);

        // Memastikan tidak ada duplikasi record order
        $this->assertDatabaseCount('orders', 1);
        $this->assertDatabaseCount('order_items', 1);
    }

    public function test_checkout_fails_and_rolls_back_when_stock_is_insufficient(): void
    {
        $payload = [
            'items' => [
                [
                    'product_id' => $this->product->id,
                    'quantity' => 11, // Melebihi stok yang tersedia (10)
                ],
            ],
        ];

        $response = $this->actingAs($this->customer, 'sanctum')
            ->postJson('/api/v1/orders/checkout', $payload);

        // Assert HTTP Level
        $response->assertStatus(Response::HTTP_UNPROCESSABLE_ENTITY);

        // Assert Database Integrity: Pastikan tidak ada data sampah akibat transaksi partial
        $this->assertDatabaseCount('orders', 0);
        $this->assertDatabaseCount('order_items', 0);
        
        // Stok harus tetap utuh
        $this->assertDatabaseHas('inventories', [
            'product_id' => $this->product->id,
            'stock_quantity' => 10,
        ]);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Emulasi HTTP Kernel**: Pemanggilan metode seperti `$this->postJson()` **tidak** memicu HTTP server lokal (misalnya Nginx/Swoole/PHP built-in server) melalui transport socket TCP/IP. Alih-alih demikian, pengujian membangun instansi `Symfony\Component\HttpFoundation\Request`, kemudian menyuntikkannya langsung ke dalam `Http\Kernel::handle()`. Semua *middleware*, *request validation*, dan *controller dispatcher* dieksekusi secara in-memory dalam proses CLI PHP yang sama.
2. **Transaction-Level Sandboxing**: Mekanisme `RefreshDatabase` atau `DatabaseTransactions` bekerja dengan cara mengintercept koneksi PDO:
   - Sebelum metode test berjalan (`setUp`), framework mengirimkan perintah `BEGIN TRANSACTION` via PDO ke DBMS.
   - Aplikasi menulis, mengubah, dan membaca data secara normal via koneksi PDO tersebut. Database engine mencatat transaksi ini pada memori engine buffer / Write-Ahead Logging (WAL).
   - Saat test selesai (`tearDown`), framework secara otomatis mengeksekusi `ROLLBACK`. Seluruh mutasi dibatalkan tanpa menyentuh disk persistensi secara permanen.
3. **Database Assertion Engine**: Metode seperti `assertDatabaseHas($table, $data)` mengompilasi query deterministik:
   ```sql
   SELECT COUNT(*) AS aggregate FROM "orders" WHERE "id" = ? AND "user_id" = ? LIMIT 1;
   ```
   Eksekusi dilakukan di atas koneksi transaksi yang masih aktif sebelum rollback terjadi.

#### Alokasi Memori / Resource
- **Stateful Memory Overhead**: PHP adalah bahasa *shared-nothing architecture* di web server, namun dalam skenario PHPUnit, CLI runner hidup sebagai satu proses persisten (*single continuous process*) yang mengeksekusi seluruh test suite secara sekuensial. Jika Model ORM atau Service Container menyimpan instance secara statis tanpa dibersihkan di `tearDown()`, penggunaan memori akan meningkat linear (*memory leak*), menyebabkan *OOM (Out-of-Memory)* pada test suite berukuran ribuan file.

#### Trade-offs: Real DBMS vs. In-Memory SQLite
- **SQLite `:memory:` (Cepat, Risiko Divergensi Tinggi)**:
  - *Kelebihan*: Zero I/O disk footprint; sangat cepat untuk CI pipeline.
  - *Kekurangan*: Arsitektur SQLite berbeda secara fundamental dengan PostgreSQL/MySQL. SQLite memiliki *weak typing*, parsing query yang berbeda, tidak mendukung *locking hints* (`FOR UPDATE`), implementasi fungsi JSON yang berlainan, dan perilaku *foreign keys* yang longgar secara default.
- **Dedicated Real Database via Docker (Akurat, Resource-Intensive)**:
  - Menguji query raw, window functions, trigger, constraint engine yang 100% identik dengan production. Namun, membutuhkan *overhead* koneksi TCP dan I/O disk writing.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Database Factory dengan State Terdefinisi**: Bangun factory yang jelas untuk skenario spesifik (misal: `User::factory()->unverified()->create()`) daripada mendefinisikan array manual di dalam test body.
- **Jalankan Migration Sekali Saja**: Pastikan DDL (*schema creation*) dieksekusi sekali di awal siklus testing (menggunakan caching schema / fast-refreshing), bukan melakukan migrate fresh pada setiap pemanggilan method test.
- **Uji Skenario Race-Conditions & Constraints**: Validasi bahwa constraint unik di level database benar-benar mencegah *duplicate record* saat dua request paralel terjadi (menghindari ketergantungan semata pada *Validation Rule* di level kode PHP).

#### Don'ts
- **Menulis Raw Assertions Berulang**: Hindari mengekstrak record via ORM lalu melakukan manual assert seperti:
  ```php
  // BAD: Objek termutasi di level memori model, bukan verifikasi state database aktual
  $order = Order::find($id);
  $this->assertEquals(750000, $order->total_amount_in_cents);
  
  // GOOD: Memaksa query langsung ke storage engine
  $this->assertDatabaseHas('orders', ['id' => $id, 'total_amount_in_cents' => 750000]);
  ```
- **Melakukan Hard-coded Auto-Increment ID**: Jangan pernah berasumsi record baru akan selalu memiliki `id = 1`. Transaksi yang di-rollback pada PostgreSQL atau MySQL InnoDB tetap menaikkan sequence auto-increment pointer (*gap sequence*). Gunakan dynamic ID dari record yang di-return.

#### Edge Cases
- **Nested Transactions & Truncation Issue**: Jika kode aplikasi yang diuji secara eksplisit memanggil `DB::beginTransaction()` dan `DB::commit()`, hal ini dapat secara tidak sengaja meng-commit transaksi *outer layer* yang disediakan oleh test runner. Pastikan DBMS dan framework mendukung `SAVEPOINT` untuk nested transaction virtualization agar *auto-rollback* test suite tidak rusak.
- **Fulltext & Async Search Indexes**: Database assertions sering gagal jika sistem menggunakan asynchronous indexing engine (seperti Elasticsearch/Meilisearch). Pisahkan pengujian transactional database dengan pengujian search engine indexer.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Mekanisme SAVEPOINT**:
   Buat sebuah service class yang menggunakan `DB::transaction(...)` di dalamnya. Jalankan integration test menggunakan trait `RefreshDatabase` atau `DatabaseTransactions`. Analisis SQL query log (via database profiling log) untuk membuktikan bagaimana PDO menangani *nested transaction* menggunakan sintaks `SAVEPOINT trans2` dan `RELEASE SAVEPOINT trans2` tanpa mematikan rollback pengujian utama.
2. **Parallel Testing Race-Condition**:
   Konfigurasikan pengujian paralel di PHP (menggunakan `paratest` atau `php artisan test --parallel`). Pelajari bagaimana framework mengisolasi skema antar proses pekerja (misalnya pembuatan dynamically scoped schema `db_test_1`, `db_test_2`) untuk mencegah *table lock contention* dan *dirty reads*.
