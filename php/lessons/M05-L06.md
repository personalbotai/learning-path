### 1. Konsep & Arsitektur Mendalam

Redis (*Remote Dictionary Server*) adalah sistem penyimpanan data di dalam memori (*in-memory data structure store*) yang beroperasi sebagai basis data NoSQL berbasis *key-value*, *cache engine*, dan *message broker*. Dalam ekosistem aplikasi web berkinerja tinggi berbasis PHP, Redis memegang peran krusial sebagai lapisan perantara (*caching layer*) antara logika aplikasi dan basis data relasional (seperti PostgreSQL atau MySQL) untuk memangkas latensi pembacaan data disk I/O dari hitungan milidetik (*ms*) menjadi sub-milidetik (*microsecond*).

```
[Klien HTTP]
      │
      ▼
[Nginx / Web Server]
      │
      ▼
[PHP-FPM Worker]  ◄──── (RESP via TCP/Unix Socket) ────► [Redis In-Memory (RAM)]
      │                                                        │
      │ (Cache Miss)                                    (Sub-millisecond)
      ▼
[RDBMS (SSD/Disk)]
```

#### Shared-Nothing Architecture PHP & Redis
PHP mengadopsi model eksekusi *shared-nothing architecture*. Setiap *request* HTTP yang ditangani oleh PHP-FPM (*FastCGI Process Manager*) memicu siklus hidup terisolasi: inisialisasi modul, alokasi memori *request*, eksekusi skrip, destruksi konteks, dan *garbage collection*. 

Konsekuensi dari model ini adalah PHP tidak memiliki memori persisten lintas *request* secara *native*. Di sinilah Redis berperan: Redis menyediakan *shared memory space* eksternal dengan performa ekstrem, memungkinkan berbagai *worker* PHP-FPM berbagi status (*state*), sesi, atau data hasil kalkulasi yang mahal secara konkuren.

#### Protokol & Ekstensi: `ext-redis` vs `Predis`
Komunikasi antara PHP dan Redis berjalan di atas protokol aplikasi lapisan atas yang disebut **RESP** (*REdis Serialization Protocol*), yang biasanya ditransmisikan melalui TCP socket atau Unix Domain Socket (UDS). Di level eksekusi PHP, terdapat dua pendekatan integrasi:

1. **`ext-redis` (PhpRedis)**: Ekstensi berbasis bahasa C yang dikompilasi langsung ke dalam *binary* PHP sebagai modul inti. Ekstensi ini mengeksekusi serialisasi, deserialisasi, dan *socket parsing* pada lapisan C-level, meminimalkan *overhead* Zend Engine (CPU cycle dan alokasi memori Zend).
2. **`Predis`**: Klien murni PHP (*userland client*). Fleksibel dan tidak membutuhkan kompilasi modul pada sistem operasi, namun mengorbankan performa sekitar 2–5x lebih lambat dibanding `ext-redis` karena tingginya *overhead* parsing array dan *string manipulation* di runtime PHP.

Dalam lingkungan produksi skala besar, penggunaan **`ext-redis`** merupakan standar mutlak industri.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan pola **Cache-Aside (Lazy Loading)** menggunakan `ext-redis` dengan koneksi persisten (*persistent connection*), pencegahan *Cache Stampede* menggunakan *randomized TTL (jitter)*, dan serialisasi terkonfigurasi.

```php
<?php

declare(strict_types=1);

namespace App\Infrastructure\Cache;

use Redis;
use RedisException;
use RuntimeException;

final class RedisCacheService
{
    private Redis $redis;

    public function __construct(
        private readonly string $host = '127.0.0.1',
        private readonly int $port = 6379,
        private readonly ?string $auth = null,
        private readonly int $database = 0,
        private readonly float $timeout = 1.5,
        private readonly int $retryInterval = 100
    ) {
        $this->redis = new Redis();
        $this->establishConnection();
    }

    private function establishConnection(): void
    {
        try {
            // Menggunakan pconnect untuk reuse TCP socket lintas siklus PHP-FPM
            // persistent_id membedakan pool koneksi antar konfigurasi
            $connected = $this->redis->pconnect(
                $this->host,
                $this->port,
                $this->timeout,
                'php_redis_pool',
                $this->retryInterval
            );

            if (!$connected) {
                throw new RuntimeException("Gagal membuka koneksi persisten ke Redis.");
            }

            if ($this->auth !== null) {
                $this->redis->auth($this->auth);
            }

            $this->redis->select($this->database);

            // Optimasi engine: Gunakan Igbinary jika tersedia, fallback ke JSON
            if (defined('Redis::SERIALIZER_IGBINARY') && extension_loaded('igbinary')) {
                $this->redis->setOption(Redis::OPT_SERIALIZER, Redis::SERIALIZER_IGBINARY);
            } else {
                $this->redis->setOption(Redis::OPT_SERIALIZER, Redis::SERIALIZER_JSON);
            }

            // Prefix global untuk isolasi namespace cache
            $this->redis->setOption(Redis::OPT_PREFIX, 'app_v1:');
        } catch (RedisException $e) {
            throw new RuntimeException("Redis connection error: " . $e->getMessage(), (int)$e->getCode(), $e);
        }
    }

    /**
     * Cache-Aside Pattern dengan Callback Resolving & TTL Jittering
     *
     * @template T
     * @param string $key
     * @param int $ttl Base TTL dalam detik
     * @param callable(): T $fallback
     * @return T
     */
    public function remember(string $key, int $ttl, callable $fallback): mixed
    {
        try {
            $cachedValue = $this->redis->get($key);

            // Redis deserializer otomatis mengembalikan tipe data asli
            if ($cachedValue !== false) {
                return $cachedValue;
            }
        } catch (RedisException $e) {
            // Log exception ke observability system (e.g., Monolog / OpenTelemetry)
            // Fallback gracefully ke database jika Redis offline
            error_log("Redis read error: " . $e->getMessage());
            return $fallback();
        }

        // Eksekusi kalkulasi/query berat
        $computedValue = $fallback();

        try {
            // Jittering: Tambahkan noise acak (0-15% dari TTL) untuk mitigasi thundering herd
            $jitter = random_int(0, (int) ceil($ttl * 0.15));
            $finalTtl = $ttl + $jitter;

            $this->redis->setex($key, $finalTtl, $computedValue);
        } catch (RedisException $e) {
            error_log("Redis write error: " . $e->getMessage());
        }

        return $computedValue;
    }

    public function invalidate(string $key): bool
    {
        try {
            return (bool) $this->redis->del($key);
        } catch (RedisException $e) {
            error_log("Redis delete error: " . $e->getMessage());
            return false;
        }
    }
}

// ============================================================================
// CONTOH PENGGUNAAN RIIL (Misal: Mengambil Detail Pengguna)
// ============================================================================

$cache = new RedisCacheService(host: '127.0.0.1', port: 6379);

$userId = 42;
$cacheKey = "users:{$userId}:profile";

// Data akan diambil dari database HANYA pada pemanggilan pertama
$userProfile = $cache->remember($cacheKey, 3600, function () use ($userId) {
    // Simulasi Query Berat DB: SELECT * FROM users WHERE id = ?
    return [
        'id' => $userId,
        'username' => 'alex_dev',
        'roles' => ['admin', 'engineer'],
        'computed_at' => microtime(true)
    ];
});

echo "User Loaded: " . json_encode($userProfile) . PHP_EOL;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Single-Threaded Event Loop**: Redis memproses perintah menggunakan mekanisme I/O Multiplexing (*epoll* pada Linux, *kqueue* pada BSD/macOS). Meskipun Redis 6.0+ mendukung multi-threading untuk I/O *socket reading/writing*, pemrosesan eksekusi logika perintah terhadap data in-memory tetap berjalan secara **single-threaded**. Artinya, setiap instruksi bersifat atomik; operasi `GET`, `SET`, atau `INCR` dieksekusi secara serial tanpa risiko *race condition* internal pada memori Redis.
2. **Koneksi Persisten (`pconnect`) vs Ephemeral (`connect`)**:
   - Jika menggunakan `connect()`, setiap eksekusi skrip PHP melakukan *TCP 3-Way Handshake* (`SYN`, `SYN-ACK`, `ACK`), autentikasi, transfer data, dan penutupan koneksi (`FIN`, `ACK`).
   - Dengan `pconnect()`, ekstensi C meregistrasikan *file descriptor* soket jaringan ke dalam memori proses master PHP-FPM. Ketika *request* PHP berakhir, koneksi soket **tidak ditutup**, melainkan diparkir. Request berikutnya yang masuk ke proses worker yang sama langsung menggunakan *file descriptor* tersebut, memangkas *round-trip latency* hingga ~40-60%.

#### Alokasi Memori & Serialisasi
Redis menyimpan data dalam *dynamic memory allocator* tingkat rendah (biasanya **jemalloc**). 
- Di dalam Redis, sebuah *String* tidak hanya menyimpan byte mentah, melainkan dibungkus dalam struktur C bernama `robj` (*Redis Object*) dan `sdshdr` (*Simple Dynamic String*), yang melacak panjang string dan sisa kapasitas buffer secara konstan $O(1)$.
- Format serialisasi dari sisi PHP menentukan efisiensi RAM Redis:
  - **`PHP Native Serializer`**: Lambat dan menghasilkan string panjang (banyak *metadata* penamaan kelas dan tipe PHP).
  - **`JSON`**: Portabel lintas bahasa, tetapi lambat dalam *decoding* dan mengabaikan metadata tipe data biner.
  - **`Igbinary`**: Mengubah representasi memori variabel Zend Engine langsung ke format biner (*binary packing*). Menghemat ukuran penyimpanan di Redis hingga 50-70% dan mengurangi beban siklus CPU PHP-FPM secara drastis saat proses deserialisasi.

#### Trade-offs
- **CPU vs Bandwidth**: Menggunakan kompresi data (misal: Zstandard/Snappy) menghemat *memory footprint* di Redis dan *network bandwidth*, tetapi meningkatkan *CPU consumption* pada worker PHP-FPM.
- **Konsistensi vs Ketersediaan (CAP Theorem)**: Redis dirancang berorientasi pada performa tinggi dan konsistensi pada *single node*, namun replikasi bawaannya (*Master-Replica*) bersifat *asynchronous*. Ada potensi *data loss* mikro jika master mati sebelum replika menerima propagasi data.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Namespace Berhierarki**: Format `domain:subdomain:id` (contoh: `catalog:product:1094:stock`) untuk mempermudah identifikasi *keyspace* dan metrik memory profiler.
- **Terapkan TTL Jittering**: Tambahkan variasi acak pada waktu kadaluarsa data untuk mencegah *Cache Stampede*.
- **Pilih Serializer yang Efisien**: Wajib memasang ekstensi `ext-igbinary` pada PHP-FPM di server produksi sebelum mengintegrasikannya dengan `ext-redis`.
- **Set Up Memory Eviction Policy**: Konfigurasikan `maxmemory` dan `maxmemory-policy` di `redis.conf` (misal: `volatile-lru` atau `allkeys-lru`) untuk mencegah Redis mengalami *Out-Of-Memory (OOM) Crash* saat RAM host penuh.

#### Don'ts
- **DILARANG menggunakan `KEYS *`**: Perintah `KEYS pattern` memblokir *single-threaded event loop* Redis saat memindai jutaan key. Seluruh request dari client lain akan mengalami *freeze/timeout*. Gunakan iterator non-blocking **`SCAN`** sebagai gantinya.
- **Jangan Menggunakan Redis sebagai Persistent Database Utama**: Tanpa konfigurasi *persistence* (RDB/AOF) yang disetel dengan presisi, Redis tidak menjamin durabilitas data secara absolut jika server mengalami mati daya tiba-tiba.
- **Hindari Large Keys (Mega-Hashes/Arrays)**: Menyimpan sebuah *array* PHP berukuran puluhan megabyte ke dalam satu *key* string memicu alokasi memori berlebih (*memory fragmentation*) dan latensi transfer jaringan yang tinggi.

#### Edge Cases
- **Cache Penetration**: Kueri diarahkan ke data yang tidak ada di Redis maupun Database (misal: `id = -99999`). Permintaan berulang akan membebani database.
  - *Solusi*: Cache nilai kosong/null dengan TTL singkat (misal: 30-60 detik), atau gunakan **Bloom Filter** di depan Redis.
- **Cache Breakdown / Thundering Herd**: Sebuah key dengan traffic pembacaan masif (*hotkey*) kadaluarsa secara tiba-tiba, menyebabkan ribuan request secara serentak menghantam database untuk meregenerasi data yang sama.
  - *Solusi*: Terapkan *distributed mutex locking* (via `SET resource_key my_random_value NX PX 5000`) sehingga hanya 1 proses PHP yang mengambil data dari DB dan menulis ulang cache, sementara proses lain menunggu.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Distributed Mutex (Cache Stampede Protector)**:
   Modifikasi method `remember()` pada class `RedisCacheService` di atas. Jika terjadi *cache miss*, gunakan perintah atomik Redis `SET $lockKey $token NX PX 5000` (Not Exists, Expire in 5 seconds) untuk memastikan hanya ada **satu** proses PHP yang meregenerasi cache dari database, sedangkan proses PHP lainnya menunggu (*polling loop*) hingga data tersedia di Redis.
2. **Benchmark Serialization Engine**:
   Buat skrip benchmark mandiri menggunakan PHP CLI untuk menguji serialisasi sebuah array bersarang berisi 10.000 data. Bandingkan performa (waktu eksekusi parsing dan ukuran payload byte yang dihasilkan) antara `Redis::SERIALIZER_PHP`, `Redis::SERIALIZER_JSON`, dan `Redis::SERIALIZER_IGBINARY`.
3. **Migrasi Iterator Non-Blocking**:
   Tulis sebuah class helper berbasis `ext-redis` yang mengimplementasikan method `deleteByPattern(string $pattern): int` menggunakan metode `Redis::scan()` alih-alih `Redis::keys()`, untuk menghapus ribuan key cache secara aman pada *production environment* tanpa memicu lonjakan latensi (*latency spike*).
