### 1. Konsep & Arsitektur Mendalam

Fungsi *cryptographic hash* standar seperti MD5, SHA-1, atau SHA-256 dirancang untuk integritas data: throughput tinggi dan latensi rendah. Karakteristik ini justru menjadi kelemahan fatal ketika digunakan untuk proteksi kredensial. Dengan kapabilitas GPU modern dan *Application-Specific Integrated Circuit* (ASIC), penyerang dapat menghitung miliaran *hash* SHA-256 per detik menggunakan teknik *rainbow table* atau *brute-force dictionary attack*.

Untuk memitigasi vektor serangan ini, industri menggunakan **Password Hashing Functions (PHF)** atau **Key Derivation Functions (KDF)** yang bersifat sengaja lambat (*computationally expensive*) dan menghabiskan memori (*memory-hard*).

```
                      [ Raw Password ]
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
      [ bcrypt ]                        [ Argon2id ]
   (Eksblowfish KDF)              (Winner of PHC 2015)
            │                                 │
  - CPU-bound (S-Boxes)             - Memory-hard + CPU-bound
  - Max input: 72 bytes             - No 72-byte limitation
  - Cost: 2^cost rounds             - Configurable: Memory, Time, Threads
            │                                 │
            └────────────────┬────────────────┘
                             ▼
         [ Modular Crypt Format (MCF) Hash Output ]
   e.g., $argon2id$v=19$m=65536,t=4,p=1$... / $2y$12$...
```

#### bcrypt (Eksblowfish)
Dibuat oleh Niels Provos dan David Mazières pada tahun 1999, bcrypt berbasis pada algoritma cipher blok *Blowfish*. Inti dari bcrypt adalah fase inisialisasi yang dimodifikasi, disebut **Eksblowfish** (*Expensive Key Setup Blowfish*).
- **Work Factor (`cost`)**: Menentukan iterasi komputasi sebesar $2^{\text{cost}}$. Jika *cost* dinaikkan sebesar 1, durasi pemrosesan menjadi dua kali lipat.
- **Limitasi Arsitektural**: Bcrypt memiliki limit panjang input maksimal **72 byte**. Byte ke-73 dan seterusnya akan diabaikan secara diam-diam (*silent truncation*). Selain itu, bcrypt hanya terikat pada komputasi CPU/cache, sehingga rentan terhadap paralelisasi masif via FPGA (*Field-Programmable Gate Array*).

#### Argon2 (Argon2id)
Argon2 memenangkan *Password Hashing Competition* (PHC) pada Juli 2015. Argon2 memiliki tiga varian:
1. **Argon2d**: Mengakses memori berdasarkan urutan data (*data-dependent*). Sangat cepat dan resisten terhadap serangan GPU, namun rentan terhadap serangan *side-channel cache-timing*.
2. **Argon2i**: Mengakses memori tanpa bergantung pada data rahasia (*data-independent*). Tahan terhadap *side-channel attack*, namun lebih mudah diparalelkan pada ASIC.
3. **Argon2id**: Pendekatan hibrida. Iterasi pertama menggunakan strategi Argon2i untuk mencegah serangan *side-channel*, iterasi selanjutnya menggunakan strategi Argon2d untuk mencegah paralelisasi komputasi pada GPU/ASIC. **Argon2id adalah standar emas industri saat ini (rekomendasi OWASP).**

Argon2id memiliki tiga dimensi *tuning*:
- **Memory Cost (`memory_cost`)**: Jumlah memori RAM yang dialokasikan (dalam KiB).
- **Time Cost (`time_cost`)**: Jumlah iterasi eksekusi.
- **Parallelism (`threads`)**: Jumlah *thread* CPU yang dialokasikan untuk pemrosesan paralel.

### 2. Implementasi & Contoh Kasus Nyata

PHP menyediakan *native password abstraction layer* via ekstensi `ext/standard/password.c` (dan terhubung ke `libsodium` / `libargon2`). Abstraksi ini secara otomatis mengelola *cryptographically secure random salt* menggunakan CSPRNG internal (`random_bytes`).

Berikut adalah implementasi *service* autentikasi modern menggunakan PHP 8.2+:

```php
<?php

declare(strict_types=1);

namespace App\Security;

use SensitiveParameter;
use RuntimeException;

final class PasswordManager
{
    // Konfigurasi standar Argon2id berbasis rekomendasi OWASP
    private const ARGON2_OPTIONS = [
        'memory_cost' => 65536, // 64 MiB
        'time_cost'   => 4,     // 4 iterasi
        'threads'     => 1,     // 1 thread (disesuaikan dengan spesifikasi server)
    ];

    // Konfigurasi fallback bcrypt
    private const BCRYPT_OPTIONS = [
        'cost' => 12, // 2^12 = 4096 iterasi
    ];

    /**
     * Hash plain password menggunakan algoritma yang direkomendasikan lingkungan server.
     * Menggunakan atribut #[SensitiveParameter] agar password tidak bocor pada stack trace/error log.
     */
    public function hash(#[SensitiveParameter] string $plainPassword): string
    {
        // Utamakan Argon2id jika didukung oleh kompilasi runtime PHP
        $algorithm = defined('PASSWORD_ARGON2ID') ? PASSWORD_ARGON2ID : PASSWORD_BCRYPT;
        $options   = ($algorithm === PASSWORD_ARGON2ID) ? self::ARGON2_OPTIONS : self::BCRYPT_OPTIONS;

        /**
         * Mitigasi limit 72-byte bcrypt:
         * Jika sistem fallback ke bcrypt, kita validasi agar input tidak melebihi 72 byte,
         * atau pra-hash string via SHA-384/SHA-512 jika arsitektur membutuhkan password panjang.
         */
        if ($algorithm === PASSWORD_BCRYPT && strlen($plainPassword) > 72) {
            throw new RuntimeException('Panjang kata sandi melebihi limit 72 byte untuk bcrypt.');
        }

        $hash = password_hash($plainPassword, $algorithm, $options);

        if ($hash === false) {
            throw new RuntimeException('Gagal menghasilkan cryptographic hash.');
        }

        return $hash;
    }

    /**
     * Verifikasi kesesuaian input plain password dengan hash di database.
     * Eksekusi timing-safe dijamin oleh password_verify().
     */
    public function verify(#[SensitiveParameter] string $plainPassword, string $hashedPassword): bool
    {
        return password_verify($plainPassword, $hashedPassword);
    }

    /**
     * Memeriksa apakah hash perlu dibuat ulang akibat perubahan konfigurasi cost
     * atau migrasi algoritma (misal: migrasi lama dari bcrypt ke Argon2id).
     */
    public function needsRehash(string $hashedPassword): bool
    {
        $algorithm = defined('PASSWORD_ARGON2ID') ? PASSWORD_ARGON2ID : PASSWORD_BCRYPT;
        $options   = ($algorithm === PASSWORD_ARGON2ID) ? self::ARGON2_OPTIONS : self::BCRYPT_OPTIONS;

        return password_needs_rehash($hashedPassword, $algorithm, $options);
    }
}

// ==========================================
// Simulasi Alur Kerja Autentikasi & Re-hash
// ==========================================

$passwordManager = new PasswordManager();
$plainInput = 'K4t4-S@nd1-S4ng4t-R4h4s14!';

// 1. Pendaftaran Akun (Hashing)
$persistedHash = $passwordManager->hash($plainInput);
echo "Hash: " . $persistedHash . PHP_EOL;

// 2. Login Autentikasi
$loginInput = 'K4t4-S@nd1-S4ng4t-R4h4s14!';
if ($passwordManager->verify($loginInput, $persistedHash)) {
    echo "Autentikasi Berhasil." . PHP_EOL;

    // 3. Evaluasi Re-hashing (Transparent Migration)
    if ($passwordManager->needsRehash($persistedHash)) {
        $newHash = $passwordManager->hash($loginInput);
        // DB::table('users')->where('id', $userId)->update(['password' => $newHash]);
        echo "Hash berhasil di-upgrade ke parameter/algoritma terbaru." . PHP_EOL;
    }
} else {
    echo "Autentikasi Gagal: Kredensial tidak valid." . PHP_EOL;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Generasi Salt**: Saat `password_hash()` dieksekusi, Zend Engine memanggil fungsi CSPRNG sistem (`/dev/urandom` pada Linux, `getrandom(2)` pada kernel modern, atau `BCryptGenRandom` di Windows) via utilitas C internal PHP. Salt sepanjang 16 byte (bcrypt) atau lebih (Argon2id) di-generate secara deterministik dari sumber entropi OS.
2. **Modular Crypt Format (MCF)**: Output hash bukan hanya *digest* biner, melainkan representasi ASCII terstruktur yang menyimpan metadata lengkap:
   - Contoh Bcrypt: `$2y$12$e8N8yQW9mC8uL6e5F4d3a.q8P...`
     - `$2y$`: Identifikasi algoritma (Bcrypt fix bug 8-bit wrap-around CVE-2011-2483).
     - `$12$`: Work factor ($2^{12}$).
     - Sisa string: Kombinasi salt (22 karakter base64) dan *digest* akhir (31 karakter base64).
   - Contoh Argon2id: `$argon2id$v=19$m=65536,t=4,p=1$...`
     - Algoritma, versi mesin Argon2 (`v=19`), alokasi RAM (`m`), iterasi (`t`), thread (`p`), salt, dan digest.
3. **Verifikasi Timing-Safe**: `password_verify()` mengekstrak metadata dari string hash yang disimpan, merekonstruksi kalkulasi terhadap kata sandi yang dikirimkan, lalu melakukan perbandingan memori secara *constant-time* (ekuivalen implementasi C pada `timingsafe_bcmp`). Ini memastikan rentang waktu eksekusi tidak bocor untuk dieksploitasi melalui *Timing Side-Channel Attacks*.

#### Alokasi Memori / Resource
- **Bcrypt**: Bekerja hampir murni pada register dan L1/L2 cache prosesor. Alokasi memori hanya berkisar 4 KiB untuk sub-array internal S-box. Hal ini menjadikannya sangat efisien dari perspektif memori server web ber-concurrency tinggi, tetapi sekaligus rentan dipecahkan dengan GPU cluster ber-concurrency masif.
- **Argon2id**: Membutuhkan alokasi memori dinamis di level kernel OS (via `malloc` dalam C *space* `libargon2`). Jika `memory_cost = 65536`, setiap eksekusi fungsi akan mengunci 64 MiB RAM. Jika ada 100 *request* autentikasi bersamaan, server membutuhkan minimal $100 \times 64\text{ MiB} = 6.4\text{ GiB}$ RAM seketika.

#### Trade-offs
| Parameter | Bcrypt | Argon2id |
| :--- | :--- | :--- |
| **Resistensi GPU / ASIC** | Sedang | Sangat Tinggi (*Memory-hard*) |
| **Beban RAM Server** | Minimal (~4 KiB/hash) | Tinggi (Disesuaikan, e.g., 64 MiB/hash) |
| **Maksimum Panjang Input** | 72 byte (*strict limitation*) | $2^{32}-1$ byte (Praktis tanpa limit) |
| **Kompatibilitas Runtime** | Tersedia di semua lingkungan PHP 5.5+ | Membutuhkan build PHP dengan libargon2 atau libsodium |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `password_needs_rehash()`**: Selalu tempatkan fungsi ini tepat setelah verifikasi login berhasil. Mekanisme ini memfasilitasi rotasi *cost* bertahap dan migrasi algoritma dari bcrypt ke Argon2id tanpa memaksa semua pengguna mereset kata sandi mereka.
- **Benchmark Latensi Target**: Ukur beban server untuk menentukan parameter cost. Sasaran latensi hash yang ideal untuk web request adalah **250ms hingga 500ms** per operasi pada hardware produksi.
- **Terapkan Rate Limiting Ketat**: Karena PHF membebani CPU dan RAM, *endpoint* login rentan dijadikan target *Denial of Service* (DoS). Batasi frekuensi *request* menggunakan Redis token-bucket per IP dan per *identifier* user.

#### Don'ts
- **DILARANG Menyediakan Salt Manual**: Opsi parameter `'salt'` pada `password_hash()` telah di-*deprecate* sejak PHP 7.0 dan **dihapus** di PHP 8.0. Memasukkan salt statis atau manual merusak entropi kriptografi yang disediakan OS.
- **DILARANG Melakukan Hash Ganda Mentah**: Jangan memanggil `hash('sha256', $password)` sebelum dioper ke `password_hash()`, kecuali menggunakan HMAC dengan *pepper* yang aman. Hashing ganda tanpa pemahaman mendalam justru dapat mengurangi entropi atau memperkenalkan *collision vulnerabilities*.
- **Hindari Parameter Argon2 Berlebihan di Lingkungan Container Kecil**: Menjalankan Argon2id dengan `memory_cost => 131072` (128 MiB) di container Docker dengan memory-limit 256 MiB akan memicu *Linux Out-of-Memory (OOM) Killer* ketika terjadi sedikit lonjakan *traffic*.

#### Edge Cases
- **Trunkasi 72-Byte Bcrypt**: Password `PasswordPanjangLebihDari72Karakter...[A]` dan `PasswordPanjangLebihDari72Karakter...[B]` akan menghasilkan hash bcrypt yang identik jika 72 karakter pertamanya persis sama. Jika arsitektur sistem Anda mengizinkan frasa sandi (*passphrase*) super panjang tanpa Argon2id, lakukan *pre-hashing* menggunakan *HMAC-SHA-384* (menghasilkan binary digest 48 byte) sebelum dimasukkan ke dalam `password_hash($hmac, PASSWORD_BCRYPT)`.

### 5. Tantangan Eksplorasi Mandiri

1. **Benchmark Cost Factor**:
   Tulis skrip PHP CLI untuk melakukan *profiling* performa eksekusi `password_hash()`. Uji bcrypt dari `cost => 8` hingga `cost => 14`, dan Argon2id dengan berbagai variasi `memory_cost` (32 MiB, 64 MiB, 128 MiB). Catat waktu eksekusi dalam milidetik dan tentukan *sweet spot* yang menghasilkan latensi ~300ms pada mesin pengembangan Anda.

2. **Implementasi HMAC Pepper Pre-Hashing**:
   Rancang sebuah arsitektur pembungkus password (sering disebut *pepper*) di mana kata sandi di-hash menggunakan `hash_hmac('sha384', $password, $secretKey, true)` sebelum diserahkan ke `password_hash(..., PASSWORD_BCRYPT)`. Bagaimana Anda mendesain mekanisme mitigasi limit 72-byte tersebut tanpa merusak backward compatibility terhadap hash legacy yang belum di-pepper?
