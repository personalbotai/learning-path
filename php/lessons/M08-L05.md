## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Kualitas testing dalam ekosistem perangkat lunak sering kali diukur menggunakan metrik kuantitatif seperti **Code Coverage**. Namun, metrik ini memiliki kelemahan fatal: line coverage hanya memvalidasi bahwa suatu baris kode dieksekusi oleh Zend Engine, bukan memvalidasi kebenaran logika atau ketahanan assertion. Untuk mengatasi batasan ini, metodologi **Test-Driven Development (TDD)** dan **Mutation Testing** diterapkan guna menjamin kualitas kode sekaligus kualitas test suite itu sendiri.

```
       [ Line Coverage ]             [ Branch Coverage ]            [ Mutation Testing ]
       "Apakah baris ini             "Apakah cabang if/else         "Jika logika baris ini diubah,
         dieksekusi?"                  semuanya diuji?"              apakah test akan gagal?"
               │                             │                               │
               ▼                             ▼                               ▼
       Metrik Paling Lemah          Metrik Struktural              Standar Emas Ketahanan
```

#### 1. Code Coverage: Line vs. Branch vs. Path
- **Line/Statement Coverage**: Menghitung rasio baris kode yang tersentuh selama eksekusi unit test. Kelemahannya: assertion-free test (test tanpa assertion) dapat menghasilkan 100% line coverage.
- **Branch Coverage**: Mengukur apakah setiap percabangan kontrol alur (kondisi boolean pada `if`, `match`, switch-case) dievaluasi ke state `true` dan `false`.
- **Path Coverage**: Menguji seluruh permutasi jalur eksekusi yang mungkin terjadi dalam suatu fungsi. Pada fungsi kompleks, jalur ini bertambah secara eksponensial ($2^n$).

#### 2. Test-Driven Development (TDD)
TDD membalik siklus konvensional pengembangan perangkat lunak melalui iterasi **Red-Green-Refactor**:
1. **Red**: Tulis unit test untuk fungsionalitas yang belum dibuat. Test harus gagal karena kode belum ada. Ini memvalidasi bahwa test harness bekerja dan assertion mendeteksi ketiadaan fitur.
2. **Green**: Tulis kode implementasi seminimal mungkin agar test lolos. Optimasi performa dan arsitektur dikesampingkan pada tahap ini.
3. **Refactor**: Bersihkan kode implementasi tanpa mengubah perilakunya (behavior-preserving transformation). Hilangkan duplikasi, terapkan design pattern, dan perjelas penamaan. Test suite bertindak sebagai jaring pengaman (safety net).

Secara arsitektural, TDD memaksa dependensi diekspos melalui dependency injection, memperkecil ukuran class (Single Responsibility Principle), serta mengeliminasi coupling ketat ke I/O atau framework globals.

#### 3. Mutation Testing (Infection PHP)
Mutation testing mengevaluasi efektivitas test suite dengan cara menyuntikkan eror sintaksis/semantik buatan (**Mutants**) ke dalam source code, kemudian menjalankan test suite terhadap kode yang telah dimutasi tersebut.

Siklus hidup Mutation Testing:
1. **Parsing**: Infection membaca Abstract Syntax Tree (AST) source code menggunakan `nikic/php-parser`.
2. **Mutasi**: Operator logika diubah (misalnya `>` diganti `>=`, `true` menjadi `false`, `&&` menjadi `||`).
3. **Kompilasi Ulang**: AST yang telah dimutasi dikonversi kembali menjadi file PHP temporer.
4. **Eksekusi Test**: PHPUnit dijalankan secara terisolasi terhadap kode yang dimutasi.
5. **Evaluasi Status Mutant**:
   - **Killed (Bagus)**: Test suite mendeteksi mutasi dan menghasilkan status *fail*.
   - **Escaped (Buruk)**: Test suite tetap berstatus *pass* meskipun logika bisnis telah dirusak. Menandakan missing assertion atau edge-case yang tidak teruji.
   - **Uncovered**: Mutasi berada pada baris kode yang sama sekali tidak tersentuh unit test.
   - **Timed Out / Fatal Error**: Mutan menyebabkan infinite loop atau memory leak.

Metrik utama yang dihasilkan adalah **Mutation Score Indicator (MSI)**:
$$\text{MSI} = \frac{\text{Killed} + \text{Timed Out} + \text{Error}}{\text{Total Mutants}} \times 100\%$$

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Implementasi kalkulator diskon berjenjang (*Tiered Discount Engine*) dengan pendekatan TDD dan validasi Mutation Testing.

#### Langkah 1: Phase RED (Tulis Test Terlebih Dahulu)

```php
<?php

declare(strict_types=1);

namespace Tests\Unit\Billing;

use App\Billing\DiscountCalculator;
use App\Billing\Money;
use PHPUnit\Framework\TestCase;

final class DiscountCalculatorTest extends TestCase
{
    private DiscountCalculator $calculator;

    protected function setUp(): void
    {
        $this->calculator = new DiscountCalculator();
    }

    public function testShouldReturnZeroDiscountWhenOrderIsBelowThreshold(): void
    {
        $amount = new Money(99_00); // 99.00 IDR/USD
        $discount = $this->calculator->calculateTieredDiscount($amount);

        self::assertSame(0, $discount->cents);
    }

    public function testShouldApplyTenPercentDiscountWhenOrderEqualsOrExceedsOneHundred(): void
    {
        $amount = new Money(100_00);
        $discount = $this->calculator->calculateTieredDiscount($amount);

        self::assertSame(10_00, $discount->cents);
    }

    public function testShouldApplyTwentyPercentDiscountWhenOrderExceedsFiveHundred(): void
    {
        $amount = new Money(500_01);
        $discount = $this->calculator->calculateTieredDiscount($amount);

        self::assertSame(100_00, $discount->cents); // 20% of 500.01 rounded down to 100.00
    }
}
```

#### Langkah 2: Phase GREEN & REFACTOR (Implementasi Minimum & Bersih)

```php
<?php

declare(strict_types=1);

namespace App\Billing;

final readonly class Money
{
    public function __construct(public int $cents)
    {
        if ($this->cents < 0) {
            throw new \InvalidArgumentException('Nilai moneter tidak boleh negatif.');
        }
    }
}

final readonly class DiscountCalculator
{
    private const int TIER_ONE_THRESHOLD = 100_00;
    private const int TIER_TWO_THRESHOLD = 500_00;

    public function calculateTieredDiscount(Money $orderTotal): Money
    {
        // Mutasi target: Mengubah '>=' menjadi '>', pembulatan, atau batas angka
        return match (true) {
            $orderTotal->cents > self::TIER_TWO_THRESHOLD => new Money((int) floor($orderTotal->cents * 0.20)),
            $orderTotal->cents >= self::TIER_ONE_THRESHOLD => new Money((int) floor($orderTotal->cents * 0.10)),
            default => new Money(0),
        };
    }
}
```

#### Langkah 3: Konfigurasi Mutation Testing (`infection.json5`)

Infection dikonfigurasi pada root direktori project:

```json
{
    "$schema": "vendor/infection/infection/resources/schema.json",
    "source": {
        "directories": [
            "src/Billing"
        ]
    },
    "logs": {
        "text": "infection.log",
        "html": "infection-report.html"
    },
    "mutators": {
        "@default": true,
        "GreaterThanOrEqualTo": true,
        "LogicalAnd": true
    },
    "minMsi": 100,
    "minCoveredMsi": 100
}
```

Jalankan perintah mutasi:
```bash
vendor/bin/infection --threads=4
```

Jika pada unit test di atas kita lupa menguji kondisi tepat di `500_00`, Infection akan menghasilkan mutan:
- Kode Asli: `$orderTotal->cents > self::TIER_TWO_THRESHOLD`
- Mutan: `$orderTotal->cents >= self::TIER_TWO_THRESHOLD`

Jika input `500_00` tidak di-assert, mutan ini akan berstatus **Escaped** (karena `500_00` masuk ke tier 10% di kode asli, namun masuk ke 20% di kode mutan tanpa ada test yang gagal). Kita dipaksa menambahkan unit test edge-case:

```php
public function testShouldApplyTenPercentAtExactTierTwoBoundary(): void
{
    $amount = new Money(500_00);
    $discount = $this->calculator->calculateTieredDiscount($amount);

    self::assertSame(50_00, $discount->cents);
}
```
Dengan test tambahan ini, mutan `GreaterThanOrEqualTo` akan **Killed**.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Driver (PCOV vs Xdebug)
Untuk mengumpulkan *Code Coverage*, engine PHP membutuhkan profiler yang mencatat eksekusi opcode.

```
PHP Source Code ──> Compilation (Zend Compiler) ──> Op_array (Oplines)
                                                          │
                                         ┌────────────────┴────────────────┐
                                         ▼                                 ▼
                                  [ Xdebug Hook ]                   [ PCOV Driver ]
                            Intercept zend_execute_ex          Bitmask allocation per
                            Heavy memory & tracing overhead    op_array file (Lightweight)
```

1. **Xdebug**: Bekerja dengan cara meng-override pointer fungsi C internal engine: `zend_execute_ex` dan `zend_execute_internal`. Setiap kali instruksi `opline` dieksekusi, Xdebug mencatat file path, line number, status cabang (branch), serta konteks call-stack. Hal ini menyebabkan degradation performa runtime sebesar **200% - 1000%**.
2. **PCOV**: Ekstensi C yang dirancang khusus hanya untuk line & branch coverage. PCOV tidak melakukan stack tracing. Ia mengalokasikan struktur data array bitmask langsung di shared memory yang terikat pada struktur C `zend_op_array`. Begitu interpreter memproses instruksi, PCOV membalik bit pada offset bersangkutan. Overhead performa PCOV sangat rendah, rata-rata hanya bertambah **20% - 40%**.

#### Mekanika Engine Infection (AST Mutation Process)
1. **Analisis Mutabilitas**: Infection menggunakan parser berbasis PHP-Parser untuk membedah kode menjadi node grafis (*AST*).
2. **Mutator Execution**: Interface mutator mendeteksi pola node:
   ```php
   // Contoh konseptual implementasi mutator internal: GreaterThan
   if ($node instanceof \PhpParser\Node\Expr\BinaryOp\Greater) {
       return new \PhpParser\Node\Expr\BinaryOp\GreaterOrEqual($node->left, $node->right);
   }
   ```
3. **Proses Paralel**: Infection menggunakan Symfony Process Component untuk melakukan *forking* worker. Masing-masing mutan diuji dalam sub-process runtime PHP terisolasi:
   - Worker memuat mutan secara dynamically via auto-prepending (`--prepend-file`) atau overriding file fisik sementara di `/tmp`.
   - Menggunakan konfigurasi memory PHPUnit yang terisolasi untuk menghindari kontaminasi state memori antar-mutan.

#### Trade-offs
| Aspek | Code Coverage Tradisional (PCOV) | Mutation Testing (Infection) |
| :--- | :--- | :--- |
| **Waktu Eksekusi** | Sangat Cepat (Detik) | Sangat Lambat (Menit hingga Jam) |
| **Konsumsi CPU/Memory**| Rendah (Single process / thread) | Sangat Tinggi (Membutuhkan multi-core saturation) |
| **Output Nilai** | Kuantitatif (Berapa baris disentuh) | Kualitatif (Seberapa tangguh assertion & logika) |
| **Integrasi CI/CD** | Mudah dijalankan di setiap commit | Membutuhkan strategi delta testing (`--git-diff-filter`) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan PCOV di CI untuk kalkulasi Coverage**: Hindari penggunaan Xdebug di pipeline CI/CD jika tujuan utamanya hanyalah mengukur coverage. Gunakan PCOV demi efisiensi resource runner.
- **Eksekusi Infection Berbasis Git Diff**:
  ```bash
  vendor/bin/infection --git-diff-filter=AM --git-diff-base=main
  ```
  Menjalankan mutation testing hanya pada baris dan file yang baru ditambahkan/diubah pada pull request mencegah bottleneck build pipeline.
- **Konfigurasikan Mutator Profiles**: Nonaktifkan mutator yang bersifat non-fungsional atau pedantik pada domain tertentu (misalnya `CastString`, `CastInt` jika type safety di level PHP engine sudah dijamin oleh `declare(strict_types=1)`).
- **Targetkan Mutation Testing pada Pure Domain Logic**: Tempatkan Infection pada Core Domain Models, Financial Engines, Policy/Permission Guards, bukan pada Framework Glue Code (Controllers, Repositories, Commands).

#### Don'ts
- **Menjadikan 100% Line Coverage sebagai Golden Metric**: Jangan berasumsi bahwa 100% coverage berarti kode bebas bug. Tanpa assertion yang ketat, itu hanyalah ilusi metriks.
- **Menguji Kode Boilerplate/DTO dengan Infection**: Menguji class getter/setter atau read-only Value Object sederhana tanpa logika mutasi hanya membuang CPU time. Ignore direktori tersebut di `infection.json5`.
- **Menulis Unit Test dengan Side Effects**: Mutation test mengeksekusi PHPUnit berulang-ulang ratusan kali. Jika test Anda memodifikasi database real, file fisik, atau state global singleton, eksekusi Infection akan menghasilkan false-positive status mutant (flaky).

#### Edge Cases
- **Infinite Loop Mutants**: Ketika Infection memutasi decrement pada perulangan while/for (`$i--` menjadi `$i++`), sub-process PHPUnit dapat mengalami hang. Selalu tentukan opsi `--test-framework-options="--process-isolation"` atau atur execution timeout Infection (`--timeout=10`).
- **Equivalent Mutants**: Kondisi di mana mutasi kode menghasilkan perilaku logika yang secara matematis identik dengan kode aslinya, sehingga mustahil untuk di-*kill* oleh test runner.
  Contoh:
  ```php
  // Original
  $diff = $a - $b;
  if ($diff <= 0) { ... }

  // Mutant
  $diff = $a - $b;
  if ($diff < 0 || $diff == 0) { ... }
  ```
  Mutan ini tidak bisa dihilangkan karena ekuivalen. Gunakan anotasi `@infection-ignore-all` atau konfigurasi ignore mutator secara spesifik jika menemui equivalent mutant.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Equivalent Mutant**: Buat implementasi algoritma pencarian string sederhana. Jalankan Infection, analisis mutant log yang berstatus *Escaped*. Identifikasi apakah mutan tersebut lolos karena test Anda kurang assertion, atau apakah itu merupakan *Equivalent Mutant*.
2. **PCOV vs Xdebug Benchmark**: Siapkan test suite dengan minimal 50 unit test. Eksekusi `phpunit --coverage-text` menggunakan Xdebug driver, lalu ubah ke PCOV driver. Ukur perbedaan waktu eksekusi dan memori puncaknya (*peak memory usage*).
3. **Zero-Coverage Mutation Trap**: Buat sebuah method dengan 3 jalur `if-else` kompleks. Tulis unit test yang memanggil method tersebut tanpa satu pun `self::assert*` (assertion-free). Amati bahwa Code Coverage PHPUnit menunjukkan angka 100%, namun Mutation Score Infection menunjukkan angka 0%. Implementasikan assertion yang tepat hingga MSI mencapai 100%.
