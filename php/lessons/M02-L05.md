## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum PHP 8.1, paradigma *immutability* (kekekalan status objek) dalam PHP memerlukan *boilerplate* yang masif. Developer terpaksa membungkus properti dalam visibilitas `private` atau `protected`, menghilangkan *setter*, dan mengekspos data melalui metode *getter*. Selain meningkatkan beban penulisan kode, pendekatan ini menghasilkan *overhead* pemanggilan fungsi (*function call overhead*) pada level Zend Virtual Machine (Zend VM) hanya untuk membaca nilai.

```
Pendekatan Klasik:
[Client] ---> CALL getAmount() ---> [Zend VM: Stack Frame Push] ---> Return Value ---> [Stack Pop]

Pendekatan Readonly (PHP 8.1+):
[Client] ---> FETCH_OBJ_R amount ---> Langsung baca zval dari properties_table
```

Fitur **Readonly Properties** (diperkenalkan di PHP 8.1) dan **Readonly Classes** (PHP 8.2) memindahkan jaminan *immutability* dari konvensi level kode/metode ke penegakan native level mesin runtime (*engine-level constraint*).

#### Aturan & Karakteristik Arsitektur
1. **Explicit Type Requirement**: Properti `readonly` **wajib** memiliki deklarasi tipe eksplisit. Tipe `mixed` diizinkan di PHP 8.2+, namun properti tanpa tipe (*untyped*) sama sekali dilarang karena engine memanfaatkan status `uninitialized` untuk melacak mutasi.
2. **Write-Once Initialization**: Properti hanya dapat diinisialisasi tepat satu kali. Inisialisasi harus terjadi di dalam *scope* kelas tempat properti tersebut dideklarasikan (atau via *Constructor Property Promotion*).
3. **Pewarisan Kelas Readonly**: Jika sebuah *class* dideklarasikan sebagai `readonly class`, seluruh turunannya (*child classes*) **wajib** dideklarasikan sebagai `readonly class`.
4. **Shallow Immutability**: Properti `readonly` hanya menjamin bahwa *pointer* atau *zval* dari properti itu sendiri tidak berubah. Jika properti tersebut memegang referensi ke sebuah *object* mutable (misalnya instance `DateTime` non-immutable), isi internal dari object tersebut masih dapat dimutasi.

### 2. Implementasi & Contoh Kasus Nyata

Penerapan paling ideal dari `readonly class` adalah pada representasi **Data Transfer Object (DTO)**, **Value Objects (Domain-Driven Design)**, dan **Command Objects** di mana integritas data mutlak tidak boleh berubah setelah instansiasi.

```php
<?php

declare(strict_types=1);

namespace App\Domain\Payment;

use DateTimeImmutable;
use InvalidArgumentException;

/**
 * Value Object: Money
 * Menggunakan Readonly Class untuk menjamin nilai moneter tidak pernah termutasi.
 */
readonly class Money
{
    public function __construct(
        public int $amountInCents,
        public string $currency
    ) {
        if ($this->amountInCents < 0) {
            throw new InvalidArgumentException("Nominal uang tidak boleh negatif.");
        }

        if (strlen($this->currency) !== 3) {
            throw new InvalidArgumentException("Mata uang harus 3 karakter ISO (e.g. IDR, USD).");
        }
    }

    public function add(Money $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException("Tidak dapat menjumlahkan mata uang yang berbeda.");
        }

        // Return instance baru alih-alih memutasi state internal
        return new self($this->amountInCents + $other->amountInCents, $this->currency);
    }
}

/**
 * DTO: PaymentTransaction
 * Menunjukkan integrasi Readonly Class dan Immutable Wither Pattern (PHP 8.3+)
 */
readonly class PaymentTransaction
{
    public function __construct(
        public string $transactionId,
        public Money $money,
        public string $status,
        public DateTimeImmutable $createdAt
    ) {}

    /**
     * Wither pattern menggunakan fasilitas clone di PHP 8.3
     * Di PHP 8.3+, readonly properties diizinkan untuk diinisialisasi ulang di dalam __clone()
     */
    public function withStatus(string $newStatus): self
    {
        $clone = clone $this;
        $clone->status = $newStatus; // Valid hanya di PHP 8.3+
        return $clone;
    }
}

// --- Driver Code ---
$price = new Money(500000, 'IDR');
$tax = new Money(55000, 'IDR');
$total = $price->add($tax);

$transaction = new PaymentTransaction(
    transactionId: 'TXN-99824',
    money: $total,
    status: 'PENDING',
    createdAt: new DateTimeImmutable()
);

echo "Status Awal: {$transaction->status}\n"; // PENDING
echo "Total Bayar: {$transaction->money->amountInCents} {$transaction->money->currency}\n";

// Mutasi tidak langsung melalui kloning (Wither Pattern)
$paidTransaction = $transaction->withStatus('SETTLED');
echo "Status Baru: {$paidTransaction->status}\n"; // SETTLED

// Eksperimen mutasi ilegal:
try {
    // Fatal Error: Cannot modify readonly property App\Domain\Payment\PaymentTransaction::$status
    $transaction->status = 'FAILED';
} catch (\Error $e) {
    echo "Tertangkap di runtime: " . $e->getMessage() . "\n";
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Zend Engine)
Pada struktur internal Zend Engine (`zend_compile.h`), setiap entitas properti kelas direpresentasikan oleh struktur C `zend_property_info`. 

```c
struct _zend_property_info {
    uint32_t offset;
    uint32_t flags; // Bitmask flags
    zend_string *name;
    zend_type type;
    zend_class_entry *ce;
};
```

Ketika parser menemukan kata kunci `readonly`, compiler PHP menambahkan bit flag `ZEND_ACC_READONLY` ke dalam *member* `flags`.

Saat instruksi penugasan properti dieksekusi (Opcode: `ZEND_ASSIGN_OBJ` atau `FETCH_OBJ_W`), Zend VM menjalankan alur verifikasi berikut:
1. Engine membaca `zend_property_info` dari properti yang ditargetkan.
2. Memeriksa bitmask: jika `flags & ZEND_ACC_READONLY` bernilai *true*, engine memeriksa status isi memorinya.
3. Melalui `properties_table` pada `zend_object`, engine memeriksa apakah tipe `zval` properti tersebut adalah `IS_UNDEF` (*uninitialized*).
4. **Kondisi 1:** Jika bertipe `IS_UNDEF` dan konteks pemanggilan berada dalam scope kelas (atau `__clone` pada PHP 8.3+), penugasan diizinkan (*write granted*). Engine menyimpan nilai baru dan status properti berubah dari `IS_UNDEF` ke tipe data target (misal `IS_STRING`, `IS_LONG`).
5. **Kondisi 2:** Jika properti **bukan** `IS_UNDEF`, VM membatalkan eksekusi dan langsung melemparkan exception native: `Error: Cannot modify readonly property`.

#### Alokasi Memori & Resource
- **Getter vs Direct Access:** Akses langsung ke properti `public readonly` mengubah opcode dari pemanggilan fungsi berjenjang (`ZEND_INIT_METHOD_CALL` + `ZEND_DO_FCALL`) menjadi satu opcode pembacaan memori murni (`ZEND_FETCH_OBJ_R`). Ini mengeliminasi pembuatan *Call Stack Frame* (`zend_execute_data`) baru di memori C stack, menghasilkan penurunan latensi eksekusi dan konsumsi memori siklus eksekusi CPU yang signifikan pada aplikasi dengan volume DTO tinggi.
- **Dynamic Properties Overhead:** Pada `readonly class`, engine mengunci penambahan properti dinamis di runtime secara permanen (`ZEND_ACC_NO_DYNAMIC_PROPERTIES`). Zend VM tidak perlu mengalokasikan memori untuk *Hash Table* `properties` tambahan pada struktur internal `zend_object` untuk menyimpan properti tak terduga.

#### Trade-offs
- **Ketiadaan Lazy Loading Murni:** Menggunakan `readonly` membatasi teknik *proxy initialization* atau *ghost objects* (sering dipakai ORM seperti Doctrine), karena properti tidak dapat diisi bertahap di luar constructor/scope kelas tanpa menggunakan Reflection API secara agresif.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Readonly Class untuk seluruh DTO, Command, dan Event:** Jadikan entitas pembawa pesan (*messaging/transport payload*) *immutable by default*.
- **Kombinasikan dengan Constructor Promotion:** Pangkas penulisan kelas dari puluhan baris menjadi beberapa baris yang bersih dan aman secara tipe.
- **Manfaatkan PHP 8.3 Re-initialization in Clone:** Gunakan pola `$clone = clone $this; $clone->prop = $val; return $clone;` untuk membangun fungsionalitas mutasi non-destruktif (*wither methods*).

#### Don'ts
- **Jangan Mengira Readonly = Deep Immutability:** Jangan menyimpan instance mutable (seperti standard `\DateTime`, `stdClass`, atau array berisi object reference) di dalam properti readonly jika tujuannya mencegah perubahan data di seluruh siklus hidup objek. Gunakan `\DateTimeImmutable`.
- **Jangan Berikan Nilai Default di Deklarasi Properti (kecuali Constructor Promotion):** 
  ```php
  // FATAL ERROR di PHP: Readonly property cannot have a default value
  public readonly string $status = 'ACTIVE';
  ```
  Menentukan nilai default di deklarasi membuat properti dianggap sudah terinisialisasi sejak kompilasi, sehingga konstruktor tidak akan bisa mengisinya lagi.

#### Edge Cases
- **Reflection Bypass:** Reflection API (`ReflectionProperty::setValue()`) memiliki kemampuan membypass proteksi readonly jika dipanggil dari luar scope, namun sejak PHP 8.1, memodifikasi properti readonly yang **sudah diinisialisasi** via Reflection tetap akan memicu fatal `Error`, kecuali scope di-*unset* terlebih dahulu (sangat tidak direkomendasikan).
- **Unserialize:** Proses deserialisasi (`unserialize()`) berjalan pada level C engine internal yang mengalokasikan object dan mengisi `properties_table` secara langsung tanpa melewati `__construct()`, sehingga `unserialize()` tetap bekerja normal pada `readonly class`.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Shallow Immutability:**
   Buat sebuah `readonly class UserProfile` yang memiliki properti `public DateTime $createdAt`. Coba ubah waktu menggunakan metode `$userProfile->createdAt->modify('+1 day')`. Amati apakah engine melempar error. Kemudian, refactor kode tersebut agar benar-benar *deeply immutable*.
2. **Kompilasi Opcodes:**
   Instal ekstensi VLD (*Vulcan Logic Dumper*) atau gunakan perintah CLI `php -d opcache.enable_cli=1 -d opcache.opt_debug_level=0x10000 script.php` untuk membandingkan urutan opcode antara pembacaan data via *method getter* konvensional vs *public readonly property access*. Buktikan berkurangnya opcode `DO_FCALL`.
3. **Behavioral Test PHP 8.2 vs 8.3 pada Cloning:**
   Tulis kelas dengan properti `readonly`, lalu coba timpa nilai properti tersebut di dalam metode magic `__clone()`. Jalankan script tersebut di runtime PHP 8.2 (yang akan melempar fatal error) dan bandingkan perilakunya saat dijalankan di PHP 8.3+. Analisis mengapa arsitektur PHP 8.3 memutuskan untuk merelaksasi batasan ini.
