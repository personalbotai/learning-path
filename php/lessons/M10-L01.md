## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Perjalanan arsitektur perangkat lunak dalam ekosistem PHP berevolusi dari skrip prosedural datar menuju **MVC (Model-View-Controller)**, kemudian bertransformasi ke **Clean Architecture (Hexagonal / Ports & Adapters)**, hingga mengadopsi **Domain-Driven Design (DDD)** untuk mengelola kompleksitas domain bisnis skala enterprise.

```
       TRADITIONAL MVC                           CLEAN ARCHITECTURE + DDD
+----------------------------+             +-----------------------------------+
| Controller (Framework)    |             | Infrastructure (HTTP, DB, Queue)  |
+--------------+-------------+             +-----------------+-----------------+
               |                                             | (Implements)
               v                                             v
+--------------+-------------+             +-----------------+-----------------+
| Model (ActiveRecord / ORM) |             | Application / Use Cases (DTO, Bus)|
+--------------+-------------+             +-----------------+-----------------+
               |                                             | (Coordinates)
               v                                             v
+--------------+-------------+             +-----------------+-----------------+
| Database Engine (MySQL)    |             | Domain Core (Entities, VOs, Events|
+----------------------------+             +-----------------------------------+
(Tinggi coupling framework & DB)           (Domain murni, zero external dependency)
```

#### MVC dan Masalah *Fat Model, Anemic Domain*
MVC memisahkan presentasi, alur kontrol, dan data. Namun, pada framework PHP modern (seperti default Laravel atau Symfony terdahulu), Model kerap diimplementasikan menggunakan pola **Active Record** (misal: `Illuminate\Database\Eloquent\Model`). 
Masalah muncul ketika aplikasi membesar:
1. **Anemic Domain Model**: Model hanya menjadi representasi tabel basis data (kumpulan *getter/setter* tanpa logika proteksi *invariant* bisnis).
2. **Coupling Runtime & I/O**: Menginstansiasi model langsung mengikat aplikasi ke database runtime connection, menyulitkan *unit testing* murni tanpa *database booting*.
3. **Fat Controller**: Logika orkestrasi, validasi, dan bisnis bertumpuk di *controller* karena model hanya bertindak sebagai *query builder*.

#### Clean Architecture & Inversion of Control (IoC)
Clean Architecture membalik dependensi menggunakan **Dependency Inversion Principle (DIP)**:
- **Domain Layer (Core)**: Berisi entitas bisnis murni dan aturan bisnis tingkat tinggi. Lapisan ini tidak boleh memiliki dependensi terhadap *library*, framework, atau driver database apa pun (`ext-pdo`, Laravel, Symfony).
- **Application Layer**: Mengatur skenario use case sistem, menerima DTO (*Data Transfer Object*), mengorkestrasi *domain entities*, dan memanggil interface repository.
- **Infrastructure Layer**: Berisi implementasi detail teknis (Doctrine ORM, Eloquent, Redis, Mailer, AWS S3).
- **Boundary Control**: Aliran kendali melintasi batas arsitektur menggunakan **Ports** (PHP `interface`) dan **Adapters** (kelas implementor di Infrastructure).

#### Domain-Driven Design (DDD) Taktikal
DDD menyediakan instrumen konkret untuk memodelkan Domain Core:
- **Value Object (VO)**: Objek yang diidentifikasi oleh nilainya, bukan identitasnya (contoh: `Money`, `EmailAddress`). Bersifat *immutable* dan memvalidasi dirinya sendiri saat instansiasi.
- **Entity**: Objek yang memiliki identitas unik (`UserId`, `OrderId`) yang bertahan sepanjang waktu, meskipun atribut lainnya berubah.
- **Aggregate Root**: Kumpulan entitas dan value object yang diperlakukan sebagai satu kesatuan konsistensi data. Perubahan state internal di luar batasan agregat mutlak dilarang.
- **Domain Service**: Logika bisnis murni yang melibatkan lebih dari satu agregat dan tidak cocok ditempatkan di dalam satu entitas.
- **Domain Event**: Penanda kejadian penting yang telah terjadi di dalam domain (contoh: `OrderPlacedDomainEvent`).

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: **Transfer Saldo Antar Akun Dompet Digital** dengan aturan bisnis:
1. Akun tidak boleh mentransfer dana melebihi saldo yang tersedia.
2. Transfer mata uang yang berbeda ditolak (hanya mendukung IDR).
3. Nilai transfer harus positif dan di atas batas minimum.

#### 1. Domain Layer: Value Object & Entity (Pure PHP 8.2+)

```php
<?php

declare(strict_types=1);

namespace Domain\Wallet\ValueObject;

use InvalidArgumentException;

// Value Object bersifat immutable (readonly class)
final readonly class Money
{
    public function __construct(
        public int $amountInCents,
        public string $currency = 'IDR'
    ) {
        if ($this->amountInCents <= 0) {
            throw new InvalidArgumentException("Jumlah uang harus bernilai positif.");
        }

        if ($this->currency !== 'IDR') {
            throw new InvalidArgumentException("Hanya mata uang IDR yang didukung.");
        }
    }

    public function add(Money $other): self
    {
        $this->ensureSameCurrency($other);
        return new self($this->amountInCents + $other->amountInCents, $this->currency);
    }

    public function subtract(Money $other): self
    {
        $this->ensureSameCurrency($other);
        if ($other->amountInCents > $this->amountInCents) {
            throw new InvalidArgumentException("Saldo tidak mencukupi untuk pengurangan.");
        }
        return new self($this->amountInCents - $other->amountInCents, $this->currency);
    }

    private function ensureSameCurrency(Money $other): void
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException("Mata uang tidak cocok.");
        }
    }
}
```

```php
<?php

declare(strict_types=1);

namespace Domain\Wallet\Entity;

use Domain\Wallet\ValueObject\Money;
use Domain\Wallet\Exception\InsufficientBalanceException;

// Aggregate Root
final class Account
{
    public function __construct(
        private readonly string $id,
        private Money $balance
    ) {}

    public function getId(): string
    {
        return $this->id;
    }

    public function getBalance(): Money
    {
        return $this->balance;
    }

    public function debit(Money $amount): void
    {
        try {
            $this->balance = $this->balance->subtract($amount);
        } catch (\InvalidArgumentException $e) {
            throw new InsufficientBalanceException("Akun [{$this->id}] gagal didebit: " . $e->getMessage());
        }
    }

    public function credit(Money $amount): void
    {
        $this->balance = $this->balance->add($amount);
    }
}
```

#### 2. Domain & Application Layer: Port & Use Case

```php
<?php

declare(strict_types=1);

namespace Domain\Wallet\Repository;

use Domain\Wallet\Entity\Account;

// PORT: Interface didefinisikan oleh kebutuhan Domain/Application
interface AccountRepositoryInterface
{
    public function findById(string $id): ?Account;
    public function save(Account $account): void;
}
```

```php
<?php

declare(strict_types=1);

namespace Application\Wallet\UseCase;

use Application\Wallet\DTO\TransferRequest;
use Domain\Wallet\Repository\AccountRepositoryInterface;
use Domain\Wallet\ValueObject\Money;
use Domain\Wallet\Exception\AccountNotFoundException;

final readonly class TransferMoneyUseCase
{
    public function __construct(
        private AccountRepositoryInterface $accountRepository
    ) {}

    public function execute(TransferRequest $request): void
    {
        $source = $this->accountRepository->findById($request->sourceAccountId);
        if (!$source) {
            throw new AccountNotFoundException("Akun pengirim tidak ditemukan.");
        }

        $destination = $this->accountRepository->findById($request->destinationAccountId);
        if (!$destination) {
            throw new AccountNotFoundException("Akun tujuan tidak ditemukan.");
        }

        $transferAmount = new Money($request->amountInCents, $request->currency);

        // Orkestrasi mutasi state domain invariants
        $source->debit($transferAmount);
        $destination->credit($transferAmount);

        // Simpan state agregat melalui Port
        $this->accountRepository->save($source);
        $this->accountRepository->save($destination);
    }
}
```

#### 3. Infrastructure Layer: Adapter Implementasi

```php
<?php

declare(strict_types=1);

namespace Infrastructure\Persistence;

use Domain\Wallet\Entity\Account;
use Domain\Wallet\ValueObject\Money;
use Domain\Wallet\Repository\AccountRepositoryInterface;
use PDO;

// ADAPTER: Detail database relational di luar core domain
final readonly class PdoAccountRepository implements AccountRepositoryInterface
{
    public function __construct(private PDO $pdo) {}

    public function findById(string $id): ?Account
    {
        $stmt = $this->pdo->prepare('SELECT id, balance_cents, currency FROM accounts WHERE id = :id FOR UPDATE');
        $stmt->execute(['id' => $id]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if (!$row) {
            return null;
        }

        return new Account(
            id: (string)$row['id'],
            balance: new Money((int)$row['balance_cents'], (string)$row['currency'])
        );
    }

    public function save(Account $account): void
    {
        $stmt = $this->pdo->prepare(
            'UPDATE accounts SET balance_cents = :balance WHERE id = :id'
        );
        $stmt->execute([
            'balance' => $account->getBalance()->amountInCents,
            'id' => $account->getId(),
        ]);
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime Engine (Zend VM)
1. **Model Instansiasi Bersarang**: Berbeda dengan Active Record yang langsung memetakan kolom basis data ke *dynamic properties* di memori (`stdClass` atau array internal), Clean Architecture membangun *object graph* (`Account` -> mengalokasikan instance `Money` -> memuat validasi skalar).
2. **Kompilasi OpCache & Preloading**:
   - Pola DDD memecah arsitektur menjadi ribuan file kelas kecil (*high file granularity*).
   - Di PHP-FPM konvensional, I/O *disk lookup* dan parsing AST (*Abstract Syntax Tree*) untuk ratusan file per *request* memicu latensi tinggi.
   - **Solusi**: OpCache Preloading (`opcache.preload`) wajib diaktifkan. Saat PHP engine melakukan *cold start* (CLI/Server initialization), compiler membaca dan mengompilasi seluruh interface, DTO, dan domain classes langsung ke memori bersama (*shared memory segment* SHM). Pointer `zend_class_entry` menjadi permanen di seluruh *worker process*, meniadakan *autoloading overhead* via Composer.

#### Alokasi Memori / Resource (`zval` & Immutability)
- Pada PHP 8.2+, penandaan `readonly class` mengunci struktur memori `zend_class_entry`. Zend VM menandai flag `ZEND_ACC_READONLY_CLASS`.
- Modifikasi properti setelah konstruktor dilarang di tingkat mesin VM (`zend_throw_error`), mencegah *side effect mutation* lintas context.
- Objek `Money` baru dialokasikan setiap kali operasi matematika (`add`, `subtract`) dilakukan. Hal ini menghasilkan alokasi `zval` baru di memori heap engine. Namun, karena model eksekusi *shared-nothing* PHP, *garbage collector* (Zend GC) secara otomatis membersihkan seluruh heap alokasi ini secara serentak pada fase `RSHUTDOWN` (Request Shutdown) tanpa memicu fragmentasi memori jangka panjang.

#### Trade-offs
| Metrik | Tradisional MVC (ActiveRecord) | Clean Architecture + DDD |
| :--- | :--- | :--- |
| **Throughput (RPS)** | Lebih tinggi secara *default* (overhead layer sedikit). | Sedikit lebih rendah jika tanpa persistent worker (RoadRunner/Swoole). |
| **Bootstrapping Cost** | Cepat di awal, melambat seiring bertambahnya event listener & hook. | Memerlukan DI container compilation untuk resolve dependensi interface. |
| **Maintainability** | Buruk di skala enterprise (mudah *spaghetti code*). | Sangat tinggi, isolasi domain logic 100% terlindungi. |
| **Testability** | Bergantung pada database mock/in-memory DB (`sqlite`). | Sangat cepat (Pure Unit Test tanpa bootstrap DB/Framework). |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Definisikan Ubiquitous Language**: Nama kelas dan metode harus merefleksikan istilah bisnis nyata. Gunakan `$account->debit($amount)` bukan `$account->setBalance($account->getBalance() - $amount)`.
- **Enforce Invariant di Konstruktor**: Buat entitas tidak mungkin berada dalam kondisi data tidak valid (*invalid state*). Validasi tipe dan batas logika harus selesai saat objek diinstansiasi.
- **Isolasi Framework**: Jaga agar folder `src/Domain` tidak pernah mengimpor namespace seperti `Illuminate\*`, `Symfony\*`, atau atribut bawaan ORM yang merusak batas portabilitas.

#### Don'ts
- **Mengekspos Internal State Agregat**: Hindari menambahkan *setter* publik. Modifikasi state hanya boleh dilakukan melalui metode fungsional domain.
- **Primitive Obsession**: Menggunakan skalar murni (`int`, `string`) untuk data yang memiliki aturan bisnis. Contoh: Jangan gunakan `string $email`, gunakan Value Object `EmailAddress $email`.
- **Query Database di dalam Domain Model**: Entitas domain tidak boleh memanggil I/O (Repository atau DB facade) dari dalam tubuhnya sendiri.

#### Edge Cases
- **Database Transaction Boundary (Atomisitas Multi-Agregat)**:
  - Domain layer tidak boleh mengetahui transaksi basis data (`BEGIN`, `COMMIT`, `ROLLBACK`).
  - *Mitigasi*: Implementasikan pola **Unit of Work** di lapisan Infrastructure, atau tangani transaksi di Application Layer via decorator/middleware transaksional sebelum use case dieksekusi.
- **Leaky Abstraction melalui ORM**:
  - Penggunaan lazy-loading ORM (seperti Doctrine Proxies) pada domain entity dapat secara diam-diam memicu I/O query di dalam perulangan loop.
  - *Mitigasi*: Petakan (*mapping*) data mentah database ke domain entity secara eksplisit menggunakan Mapper murni di Infrastructure Layer.

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Anemic Model ke Rich Domain Model**:
   Ambil satu controller berbasis Active Record di proyek Anda (misal: pendaftaran pengguna atau checkout pesanan). Pisahkan seluruh logika bisnis validasi limit, diskon, atau kalkulasi harga ke dalam Domain Entity dan Value Object murni yang bebas dari dependensi framework.
2. **Implementasi Domain Events**:
   Rancang sistem *Domain Events* internal di PHP: Buat agregat `Order` yang mampu mencatat event `OrderCreated` ke dalam array internalnya, kemudian dispatch event tersebut ke infrastruktur *Message Broker* (seperti RabbitMQ atau In-Memory Event Dispatcher) setelah Use Case selesai menyimpan agregat tersebut.
3. **Analisis Profiling Memori (Blackfire / Xdebug)**:
   Bandingkan alokasi memori antara pembuatan 10.000 data menggunakan Eloquent Model vs 10.000 Domain Entity murni dengan Value Object di CLI. Analisis perbedaan waktu siklus CPU dan lonjakan alokasi heap `zval`.
