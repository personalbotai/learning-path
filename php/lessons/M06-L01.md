### 1. Konsep & Arsitektur Mendalam

Keamanan aplikasi web berbasis PHP berpusat pada pemahaman batas kepercayaan (*trust boundary*) antara server dan klien. Dua vektor serangan paling klasik pada layer presentasi dan transport data adalah **Cross-Site Scripting (XSS)** dan **Cross-Site Request Forgery (CSRF)**, dengan **Content Security Policy (CSP)** sebagai mekanisme pertahanan berlapis (*defense-in-depth*).

```
[ Browser / Client Engine ]
       │
       ├── (1) XSS: Penyerang menyusupkan skrip ke dalam DOM/Parser Context
       │            └── Solusi: Context-Aware Escaping + CSP Nonce/Hash
       │
       ├── (2) CSRF: Penyerang memaksa browser mengirim authenticated request
       │             └── Solusi: Synchronizer Token Pattern + SameSite Cookies
       ▼
[ PHP Runtime Server ] ── Engine memvalidasi Token & meng-encode Payload sebelum render
```

#### A. Cross-Site Scripting (XSS)
XSS terjadi ketika runtime browser mengeksekusi payload karakter tak terpercaya sebagai instruksi kode (JavaScript/HTML). Penyebab utamanya adalah kegagalan membedakan mana **data** dan mana **kode**.
*   **Reflected XSS:** Payload disisipkan melalui HTTP request (query string/header) dan langsung direfleksikan kembali ke dalam respons HTTP tanpa persistensi.
*   **Stored XSS:** Payload disimpan di layer persistensi (database, filesystem) dan dieksekusi setiap kali pengguna lain me-render data tersebut.
*   **DOM-based XSS:** Kerentanan murni di sisi klien, ketika sink JavaScript berbahaya (misal: `innerHTML`, `document.write`) memproses source tak terpercaya (`location.hash`, `window.name`).

#### B. Cross-Site Request Forgery (CSRF)
CSRF mengeksploitasi mekanisme bawaan browser: **Ambient Credentials**. Saat browser mengirimkan request ke suatu origin, browser secara otomatis menyertakan kredensial origin tersebut (cookies sesi, HTTP Basic Auth headers), terlepas dari origin mana yang menginisiasi request tersebut (misalnya melalui tag `<img>` atau form tersembunyi di situs penyerang). Server PHP yang naif hanya mengecek keberadaan session cookie tanpa memverifikasi intensi autentik dari pengguna.

#### C. Content Security Policy (CSP)
CSP adalah HTTP response header (`Content-Security-Policy`) yang membatasi kapabilitas eksekusi resource di browser. CSP secara deklaratif membatasi origin sumber daya eksternal (skrip, gambar, stylesheet) dan mematikan eksekusi inline script tak berizin melalui mekanisme kriptografis (*nonce* atau *sha256 hash*), secara efektif memitigasi dampak dari celah XSS yang tidak sengaja lolos.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern komponen perlindungan XSS, CSRF engine (Synchronizer Token Pattern), dan generator CSP berbasis Nonce menggunakan PHP 8.2+.

```php
<?php
declare(strict_types=1);

namespace App\Security;

final class SecurityManager
{
    private const CSRF_TOKEN_KEY = '_csrf_token';

    public function __construct()
    {
        if (session_status() === PHP_SESSION_NONE) {
            // Hardened session configuration
            session_start([
                'cookie_httponly' => true,
                'cookie_secure'   => true, // Wajib HTTPS
                'cookie_samesite' => 'Lax', // Mitigasi CSRF level transport
                'use_strict_mode' => true,
            ]);
        }
    }

    /**
     * Menghasilkan CSP Header dengan Nonce Kriptografis
     */
    public function applyContentSecurityPolicy(): string
    {
        // Generate random 128-bit base64-encoded nonce
        $nonce = base64_encode(random_bytes(16));

        // Policy ketat: Disable unsafe-inline, kunci form-action dan object
        $policy = [
            "default-src 'self'",
            "script-src 'self' 'nonce-{$nonce}'",
            "style-src 'self' 'nonce-{$nonce}'",
            "img-src 'self' data:",
            "object-src 'none'",
            "base-uri 'self'",
            "form-action 'self'",
            "frame-ancestors 'none'", // Mitigasi Clickjacking
        ];

        header('Content-Security-Policy: ' . implode('; ', $policy));
        return $nonce;
    }

    /**
     * Menghasilkan atau mengambil token CSRF yang terikat pada sesi
     */
    public function getCsrfToken(): string
    {
        if (empty($_SESSION[self::CSRF_TOKEN_KEY])) {
            $_SESSION[self::CSRF_TOKEN_KEY] = bin2hex(random_bytes(32));
        }
        return $_SESSION[self::CSRF_TOKEN_KEY];
    }

    /**
     * Memvalidasi CSRF token menggunakan constant-time string comparison
     */
    public function validateCsrfToken(?string $submittedToken): bool
    {
        $sessionToken = $_SESSION[self::CSRF_TOKEN_KEY] ?? '';
        
        if (empty($sessionToken) || empty($submittedToken)) {
            return false;
        }

        // Mencegah timing attack pada evaluasi string byte-per-byte
        return hash_equals($sessionToken, $submittedToken);
    }

    /**
     * Kontekstual Escaping untuk Konteks HTML Body dan Atribut
     */
    public static function escapeHtml(string $untrustedData): string
    {
        return htmlspecialchars(
            $untrustedData,
            ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5,
            'UTF-8'
        );
    }

    /**
     * Kontekstual Escaping untuk Konteks JavaScript/JSON
     */
    public static function escapeJs(mixed $data): string
    {
        return json_encode(
            $data,
            JSON_HEX_TAG | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_HEX_AMP | JSON_THROW_ON_ERROR
        );
    }
}

// ==========================================
// Integrasi Alur Kerja Aplikasi (Contoh Penggunaan)
// ==========================================

$security = new SecurityManager();
$nonce = $security->applyContentSecurityPolicy();

// Proses State-Changing Request (POST)
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $submittedToken = $_POST['csrf_token'] ?? null;
    
    if (!$security->validateCsrfToken($submittedToken)) {
        http_response_code(403);
        die('CSRF Validation Failed: Permintaan tidak sah.');
    }

    // Pemrosesan transaksi...
    $feedback = "Transfer dana berhasil dieksekusi.";
}

$userComment = "<script>alert('Pwned!');</script>Halo <b>Dunia</b>!";
?>
<!DOCTYPE html>
<html lang="id">
<head>
    <meta charset="UTF-8">
    <title>Aplikasi Aman</title>
</head>
<body>
    <h1>Komentar Pengguna</h1>
    <!-- Output Escaping yang Benar: Tag berbahaya dinetralisir -->
    <div id="comment">
        <?= SecurityManager::escapeHtml($userComment); ?>
    </div>

    <!-- Form Dilindungi Token CSRF -->
    <form method="POST" action="">
        <input type="hidden" name="csrf_token" value="<?= $security->getCsrfToken(); ?>">
        <label for="amount">Nominal:</label>
        <input type="number" id="amount" name="amount" required>
        <button type="submit">Transfer</button>
    </form>

    <!-- Script Inline Aman Hanya Jika Memiliki Nonce Valid -->
    <script nonce="<?= $nonce; ?>">
        const serverData = <?= SecurityManager::escapeJs(['user' => $userComment]); ?>;
        console.log("Data aman di-load:", serverData);
    </script>

    <!-- Skrip di bawah ini akan DIBLOKIR browser secara otomatis oleh CSP -->
    <script>
        console.log("Skrip ilegal tanpa nonce ini tidak akan dieksekusi.");
    </script>
</body>
</html>
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Tokenizer Browser vs HTML Escaping
Ketika string masuk ke HTML Lexer/Tokenizer milik browser (seperti Blink atau Gecko), parsing beroperasi sebagai *State Machine*. 
*   Karakter `<` mengubah state dari `Data State` menjadi `Tag Open State`.
*   Jika string berisi `&lt;` (hasil dari `htmlspecialchars`), lexer tetap bertahan pada `Data State` dan memancarkan token karakter murni, bukan token tag. Akibatnya, JavaScript parser tidak pernah dipanggil.
*   Untuk konteks JavaScript (`<script>`), HTML entity escaping tidak berlaku karena parser berada di `Script Data State`. Di sini, serialisasi wajib menggunakan fungsi seperti `json_encode` dengan flag `JSON_HEX_*` agar karakter pemutus seperti `</script>` tidak memotong konteks parsing secara prematur.

#### B. Cryptographic Nonce & CSP Evaluation
1.  **Eksekusi & Runtime:** Pada level kernel HTTP, PHP menyisipkan header `Content-Security-Policy` ke dalam buffer respons fastCGI (`php-fpm`).
2.  Browser menerima header sebelum merender body dokumen.
3.  Browser membaca atribut `nonce="[token]"` pada tag skrip, lalu melakukan perbandingan langsung dengan nilai yang ada pada header CSP.
4.  Jika ada injeksi HTML dinamis (misal melalui stored XSS tanpa filter) yang menyertakan tag `<script>` tanpa atribut `nonce` yang cocok, browser memutus pipeline eksekusi JavaScript sebelum memasuki compilation phase di V8/SpiderMonkey.

#### C. Constant-Time Comparison (`hash_equals`)
Evaluasi standar string `==` pada C-level (Zend Engine) bekerja dengan membandingkan karakter secara sekuensial dan keluar lebih awal (*early exit*) begitu ditemukan perbedaan:
```c
// Analogi cara kerja '==' di C
while (n--) {
    if (*s1++ != *s2++) return 0; // Rentan Side-Channel Attack (Timing)
}
```
Penyerang dapat mengukur latensi HTTP dalam satuan mikrodetik untuk menebak CSRF token byte demi byte. `hash_equals()` mengeksekusi operasi bitwise XOR konstan untuk seluruh panjang string terlepas dari posisi ketidakcocokan, mencegah leakage informasi berbasis waktu eksekusi CPU.

### 4. Best Practices & Common Pitfalls

#### Do's
*   **Gunakan Flag Konfigurasi Lengkap pada `htmlspecialchars`:** Selalu deklarasikan `ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML5` dengan encoding eksplisit `UTF-8`. `ENT_QUOTES` memastikan baik single quote (`'`) maupun double quote (`"`) diubah menjadi entitas aman guna mencegah eksploitasi pada atribut HTML.
*   **Implementasikan Defense-in-Depth untuk CSRF:** Gabungkan atribut cookie `SameSite=Lax` atau `SameSite=Strict` dengan Synchronizer Token Pattern (atau mekanisme *Double Submit Cookie* terenkripsi untuk stateless API).
*   **Regenerasi Token CSRF secara Berkala:** Regenerasi token setelah perubahan level autentikasi (seperti pasca-login) untuk mencegah serangan *Session Fixation*.

#### Don'ts
*   **Jangan Percaya `strip_tags()` untuk Sanitasi Input:** `strip_tags()` rentan terhadap payload malformed atau broken tags (contoh: `<img src=x onerror=alert(1)>` dalam kombinasi karakter aneh) yang mungkin tetap diproses oleh browser yang pemaaf (*quirks parsing*).
*   **Hindari Sanitasi pada Input:** Jangan mengubah data saat masuk ke database (*sanitization on input*), karena Anda merusak integritas data dan tidak pernah tahu konteks di mana data tersebut akan di-render di masa depan (HTML, PDF, Email CLI, REST API). Lakukan pembersihan via **Contextual Escaping on Output**.
*   **Hindari Direct Array CSRF Check:** Jangan lakukan `if ($_POST['token'] == $_SESSION['token'])`. Selalu gunakan `hash_equals()`.

#### Edge Cases
*   **Mutated XSS (mXSS):** Terjadi ketika library pembersih DOM di JavaScript mengira sebuah snippet aman, namun serialisasi ulang oleh browser me-render ulang elemen bersarang menjadi berbahaya.
*   **Nested Context XSS:** Data yang masuk ke dalam event handler inline (seperti `onclick="myFunction('<?= $untrusted; ?>')"`). Konteks ini memerlukan **dua lapisan escaping**: Escaping JavaScript terlebih dahulu, kemudian di-escape untuk konteks atribut HTML. Mengabaikan salah satunya akan membuka celah bypass.

### 5. Tantangan Eksplorasi Mandiri

1.  **Analisis Bypass Konteks Atribut:**
    Buat skrip PHP sederhana yang me-render input pengguna di dalam tag atribut: `<input type="text" name="user" value="<?= $input ?>">` (tanpa tanda kutip membungkus nilai atribut). Buktikan mengapa `htmlspecialchars($input)` standar masih bisa di-bypass oleh serangan XSS jika tidak dikonfigurasi dengan benar atau jika atribut tidak dibungkus tanda kutip. Bagaimana cara memperbaikinya?
2.  **State-Changing GET Request:**
    Telusuri mengapa mitigasi CSRF `SameSite=Lax` tidak melindungi aplikasi jika sistem mengizinkan endpoint mutasi data (misalnya: `/account/delete?id=12`) dieksekusi via metode HTTP `GET`. Ubah alur routing tersebut agar tunduk secara ketat pada spesifikasi RFC 7231 mengenai Safe Methods.
