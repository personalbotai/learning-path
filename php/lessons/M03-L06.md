## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum PHP 8.0, melampirkan metadata atau status sementara ke sebuah *object* tanpa memodifikasi definisi kelas aslinya adalah masalah klasik yang rawan menyebabkan kebocoran memori (*memory leak*). 

Dalam arsitektur *request-response* tradisional (PHP-FPM), siklus hidup proses sangat pendek; seluruh alokasi memori di-*flush* saat *request* berakhir (`RSHUTDOWN`). Namun, dengan dominasi arsitektur modern seperti *worker daemon* (RoadRunner, Swoole, Laravel Octane, queue consumers), memori bersifat persisten antar-*request*. Jika referensi terhadap suatu objek tertahan di memori global/statis, *Garbage Collector* (GC) tidak dapat membebaskan objek tersebut.

#### Masalah dengan `SplObjectStorage` dan Array Biasa
Secara historis, developer menggunakan `SplObjectStorage` atau array berbasis `spl_object_id($obj)` untuk memetakan objek ke metadata:
- Menggunakan `SplObjectStorage` mempertahankan **strong reference** terhadap objek target. Akibatnya, objek tersebut tidak akan pernah dihancurkan selama `SplObjectStorage` masih ada dalam memori.
- Menggunakan `spl_object_id($obj)` sebagai *key* integer pada array biasa berbahaya. Begitu objek dihancurkan, Zend Engine dapat mendaur ulang ID tersebut untuk objek baru yang dialokasikan kemudian (*ID collision*), memicu *stale data bug*.

#### Kehadiran `WeakReference` dan `WeakMap`
- **`WeakReference` (PHP 7.4)**: Memungkinkan kode merujuk ke suatu objek tanpa meningkatkan *reference count* (`refcount`) objek tersebut. Jika referensi kuat terakhir hilang, objek dihancurkan, dan panggilan `WeakReference::get()` mengembalikan `null`.
- **`WeakMap` (PHP 8.0)**: Koleksi *key-value* di mana **key harus berupa objek**, dan referensi ke *key* tersebut bersifat lemah (*weak*). Ketika objek kunci tidak lagi memiliki *strong reference* di tempat lain di aplikasi, objek tersebut dihancurkan, dan entri terkait di dalam `WeakMap` akan **otomatis terhapus**.

```
[Strong Reference Pattern]
Container (Cache) ──(Strong Ref)──> Objek Entitas (refcount = 1)
                                      ▲
Variabel Lokal ──────(Strong Ref)─────┘ (refcount = 2)
*Jika Variabel Lokal di-unset, refcount = 1 -> Objek TETAP HIDUP di Cache (Memory Leak)*

[WeakMap Pattern]
WeakMap (Metadata) - - (Weak Ref) - -> Objek Entitas (refcount = 1)
                                         ▲
Variabel Lokal ───────(Strong Ref)───────┘
*Jika Variabel Lokal di-unset, refcount = 0 -> Objek MATI -> Entri di WeakMap Otomatis DIHAPUS*
```

### 2. Implementasi & Contoh Kasus Nyata

Studi kasus: **Identity Map & Change Tracking pada ORM / Unit of Work** di lingkungan *long-running daemon*. Kita ingin melacak *state* asli (*snapshot*) dari entitas untuk mendeteksi perubahan (*dirty checking*) tanpa mencegah entitas tersebut di-*garbage collect*.

```php
<?php

declare(strict_types=1);

final class User
{
    public function __construct(
        public int $id,
        public string $name,
        public string $email
    ) {}
}

/**
 * Pelacak state entitas berbasis WeakMap.
 * Aman untuk worker yang berjalan tanpa batas waktu (daemon).
 */
final class EntityChangeTracker
{
    /**
     * WeakMap yang memetakan objek ke representasi snapshot datanya.
     * @var WeakMap<object, array<string, mixed>>
     */
    private \WeakMap $snapshots;

    public function __construct()
    {
        $this->snapshots = new \WeakMap();
    }

    public function track(object $entity): void
    {
        // Menyimpan deep snapshot dari properti publik saat ini
        $this->snapshots[$entity] = $this->extractPayload($entity);
    }

    public function isDirty(object $entity): bool
    {
        if (!isset($this->snapshots[$entity])) {
            throw new \InvalidArgumentException("Entitas tidak terdaftar dalam tracker.");
        }

        $currentPayload = $this->extractPayload($entity);
        return $currentPayload !== $this->snapshots[$entity];
    }

    public function countTracked(): int
    {
        return count($this->snapshots);
    }

    private function extractPayload(object $entity): array
    {
        return get_object_vars($entity);
    }
}

// ==========================================
// Simulasi Eksekusi & Lifecycle Memori
// ==========================================

$tracker = new EntityChangeTracker();

// 1. Inisialisasi entitas
$userA = new User(1, 'Alice', 'alice@domain.com');
$userB = new User(2, 'Bob', 'bob@domain.com');

// 2. Daftarkan ke Tracker
$tracker->track($userA);
$tracker->track($userB);

echo "Total objek terlacak: " . $tracker->countTracked() . PHP_EOL; // Output: 2

// 3. Modifikasi state
$userA->name = 'Alice In Wonderland';
echo "Apakah User A dirty? " . ($tracker->isDirty($userA) ? 'Ya' : 'Tidak') . PHP_EOL; // Output: Ya
echo "Apakah User B dirty? " . ($tracker->isDirty($userB) ? 'Ya' : 'Tidak') . PHP_EOL; // Output: Tidak

// 4. Hapus referensi kuat terhadap $userA
unset($userA);

// $userA langsung dihancurkan oleh Zend Engine; entri di WeakMap terhapus secara otomatis!
echo "Total objek terlacak setelah userA di-unset: " . $tracker->countTracked() . PHP_EOL; // Output: 1
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Zend Object Hooks**: Struktur C `zend_object` di dalam Zend Engine memiliki penangan khusus untuk *weak references*. Setiap kali sebuah objek diinisialisasi, `zend_object` dapat dikaitkan dengan struktur `zend_weakref`.
2. **Lifecycle Pembersihan**:
   - Ketika `refcount` dari sebuah `zend_object` mencapai `0`, fungsi destruksi `zend_objects_store_del()` dipanggil.
   - Sebelum memori C dari objek dibebaskan (`efree`), Zend Engine memeriksa apakah objek memiliki keterikatan dengan *weak reference registry*.
   - Engine mengeksekusi *internal callback* yang menelusuri seluruh instans `WeakMap` yang memegang referensi objek ini sebagai *key*, lalu membuang (*unhash*) *bucket* terkait langsung dari *HashTable* `WeakMap`.

#### Alokasi Memori / Resource
- Nilai (*value*) di dalam `WeakMap` adalah `zval` standar yang tunduk pada aturan memori biasa.
- Namun, **kunci (*key*) di dalam `WeakMap` tidak menaikkan nilai `refcount` pada struktur `zend_object` target**.
- Hal ini mencegah pembentukan **Cyclic References**. Pada array biasa, jika Objek A menyimpan referensi ke Objek B, dan Objek B menyimpan referensi kembali ke Objek A melalui array penampung, `refcount` kedua objek tidak pernah menjadi `0`, memaksa siklus diserahkan ke Zend Cyclic Garbage Collector (`gc_collect_cycles()`) yang lambat dan memakan *CPU cycles*.

#### Trade-offs
- **Overhead Mutasi**: Operasi *write* dan *delete* pada `WeakMap` sedikit lebih mahal dibandingkan array PHP primitif (HashTable murni) karena melibatkan pendaftaran dan deregistrasi penangan referensi pada Zend Engine.
- **Batasan Kunci**: `WeakMap` hanya menerima instans `object` sebagai kunci. Tidak mendukung `string`, `int`, atau `null`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan untuk Caching Ephemeral**: Sangat ideal untuk menyimpan hasil komputasi berat (*memoization*) dari sebuah objek yang umur simpannya harus identik dengan umur objek tersebut.
- **Audit Kode Long-Running Task**: Pada runtime seperti RoadRunner atau Swoole, ubah singleton cache yang menyimpan *state* per-objek dari `array` ke `WeakMap` untuk mencegah kebocoran memori tersembunyi.
- **Manfaatkan Iterable Interface**: `WeakMap` mengimplementasikan `IteratorAggregate`, `Countable`, dan `ArrayAccess`. Perlakukan seperti array asosiatif berorientasi objek.

#### Don'ts
- **Jangan Memasukkan Nilai yang Memegang Referensi Kuat ke Kunci**: 
  ```php
  // ANTI-PATTERN: Memory Leak dalam WeakMap
  $map = new \WeakMap();
  $obj = new \stdClass();
  
  // closure menangkap $obj secara strong reference
  $map[$obj] = function() use ($obj) { 
      return $obj; 
  };
  unset($obj); 
  // BAHAYA: $obj tidak akan hancur karena value di WeakMap 
  // memegang strong reference kembali ke key-nya sendiri!
  ```
- **Jangan Gunakan untuk Data Persisten Antar-Request**: `WeakMap` bukan pengganti Redis atau cache terdistribusi. Jika semua referensi skrip ke objek hilang, datanya seketika hilang.

#### Edge Cases
- **Iterasi dan Modifikasi Konkuren**: Menghapus referensi luar objek saat sedang mengiterasi `WeakMap` dapat memicu *undefined behavior* pada *internal bucket pointer*. Hindari mutasi skop saat loop `foreach ($weakMap as $k => $v)` berlangsung.
- **Serialization**: `WeakMap` tidak dapat di-serialize secara native melalui `serialize()`. Mencobanya akan menghasilkan `Exception: Serialization of 'WeakMap' is not allowed`.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Kebocoran Memori (Benchmarking)**:
   Buat skrip PHP CLI yang melakukan iterasi 1.000.000 kali. Di setiap iterasi, buat objek dummy dan simpan metadatanya.
   - Bandingkan konsumsi memori puncak (`memory_get_peak_usage(true)`) antara penggunaan `SplObjectStorage`, `array` biasa, dan `WeakMap`.
   - Amati bagaimana `gc_mem_caches()` dan destruktor berinteraksi.

2. **Deteksi Circular Dependency Closure**:
   Implementasikan kelas `Memoizer` menggunakan `WeakMap`. Pastikan Anda merancang mekanisme proteksi agar jika *closure* yang dimemoize memegang referensi ke objek target (baik eksplisit via `use` maupun implisit via `$this`), sistem memberikan peringatan (*warning*) atau secara otomatis mengonversi *binding* menjadi `WeakReference`.
