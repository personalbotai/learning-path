## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

#### Mengapa Bukan `var_dump()` dan `dd()`?
Pendekatan primitif debugging seperti *print debugging* (`var_dump()`, `die()`, atau helper `dd()`) memiliki kelemahan fundamental pada sistem berskala produksi:
1. **Mengubah State & Alur Eksekusi**: Menampilkan output secara paksa merusak header HTTP, output buffer, dan membatalkan siklus hidup framework (misalnya event listener `terminate` di Symfony/Laravel).
2. **Ketiadaan Konteks Eksekusi Temporal**: Anda hanya melihat snapshot data pada satu titik waktu, tanpa kemampuan melangkah maju (*step-over*), masuk (*step-into*), keluar (*step-out*), atau memantau mutasi variabel secara realtime.
3. **Pencemaran Logika**: Berisiko tinggi ter-commit ke repositori dan lolos ke tahap *production*.

#### Arsitektur Xdebug 3 & DBGp Protocol
Xdebug bukan sekadar ekstensi PHP biasa (*userland extension*), melainkan **Zend Engine Extension**. Xdebug beroperasi langsung pada layer inti Zend Virtual Machine (Zend VM), memotong (*hooking*) eksekusi internal engine sebelum dan sesudah opcode dijalankan.

Komunikasi antara PHP Runtime dan IDE (VS Code, PhpStorm) dimediasi oleh protokol standar bernama **DBGp** (Common Debugger Protocol) yang berbasis XML melalui koneksi TCP/IP:

```
+-------------------------------------------------------------+
| Mesin Server / Container                                   |
|                                                             |
|   +-------------------+          +----------------------+   |
|   |  PHP Application  |          |      Xdebug Core     |   |
|   | (Zend Engine VM)  | <------> | (Zend Hook Engine)   |   |
|   +-------------------+          +----------+-----------+   |
+---------------------------------------------|---------------+
                                              |
                                   TCP/IP (Port 9003)
                                   DBGp XML Protocol
                                              |
+---------------------------------------------v---------------+
| Host / Developer Machine                                    |
|   +-----------------------------------------------------+   |
|   | IDE (PhpStorm / VS Code)                            |   |
|   | - Menunggu incoming connection (Listening)          |   |
|   | - Mapping path lokal ke remote path                 |   |
|   +-----------------------------------------------------+   |
+-------------------------------------------------------------+
```

Alur kerjanya:
1. PHP menginisialisasi request. Xdebug membaca konfigurasi `php.ini`.
2. Jika terpicu (via browser cookie, trigger query parameter, atau `xdebug.start_with_request=yes`), Xdebug membuka socket TCP ke `client_host` pada `client_port` (standar Xdebug 3 adalah port **9003**).
3. IDE menerima koneksi dan menegosiasikan kapabilitas melalui DBGp.
4. Ketika Zend VM mencapai baris kode dengan *breakpoint*, Xdebug menunda (*freeze*) eksekusi thread PHP dan mengirimkan metadata *stack frame* ke IDE.

### 2. Implementasi & Contoh Kasus Nyata

#### 1. Konfigurasi `xdebug.ini` (Modern Xdebug 3)
Pastikan file konfigurasi ekstensi memuat direktif yang efisien dan aman untuk lokal:

```ini
; Lokasi zend_extension disesuaikan dengan OS/distro
zend_extension=xdebug.so

; Mode operasional: debug untuk step debugging, develop untuk stack trace yang diperkaya
xdebug.mode=develop,debug

; Memulai debugging hanya saat ada trigger (misal: ekstensi browser Xdebug Helper)
xdebug.start_with_request=trigger
xdebug.trigger_value=PHPSTORM

; Alamat IP host IDE (gunakan host.docker.internal jika dalam Docker container)
xdebug.client_host=host.docker.internal
xdebug.client_port=9003
xdebug.idekey=PHPSTORM

; Menampilkan kedalaman nested error dan trace
xdebug.max_nesting_level=256
```

#### 2. Implementasi Pemecahan Bug Kompleks via Stack Trace
Berikut adalah contoh arsitektur service dengan bug terselubung: mutasi data pada *nested calls* yang menghasilkan `TypeError` ketika menangani payload tidak valid.

```php
<?php

declare(strict_types=1);

namespace App\Billing;

use Throwable;
use RuntimeException;

final class Money
{
    public function __construct(
        public readonly int $amountInCents,
        public readonly string $currency
    ) {}
}

final class DiscountPipeline
{
    /**
     * @param array<string, mixed> $rule
     */
    public function applyRule(Money $money, array $rule): Money
    {
        // Breakpoint potensial di sini untuk inspeksi $rule
        if (!isset($rule['type'])) {
            throw new RuntimeException("Rule structure invalid: missing 'type'");
        }

        return match ($rule['type']) {
            'fixed' => new Money(
                // BUG: Memungkinkan nilai minus jika rule['value'] > $money->amountInCents
                $money->amountInCents - (int) $rule['value'],
                $money->currency
            ),
            default => $money,
        };
    }
}

final class InvoiceService
{
    public function __construct(
        private readonly DiscountPipeline $pipeline
    ) {}

    /**
     * @param array<int, array<string, mixed>> $discounts
     */
    public function calculateFinalAmount(int $baseCents, array $discounts): Money
    {
        $current = new Money($baseCents, 'IDR');

        foreach ($discounts as $step => $discount) {
            // Kita ingin memantau frame stack saat bug terjadi
            $current = $this->pipeline->applyRule($current, $discount);
        }

        if ($current->amountInCents < 0) {
            throw new RuntimeException("Inkonsistensi finansial terdeteksi: Nilai negatif.");
        }

        return $current;
    }
}

// Simulasi Alur Masuk (Controller Layer / Entrypoint)
try {
    $service = new InvoiceService(new DiscountPipeline());

    // Payload yang mengandung anomali data
    $discountsPayload = [
        ['type' => 'fixed', 'value' => 50000],
        ['type' => 'fixed', 'value' => 70000], // Menyebabkan bug negatif jika base amount 100000
    ];

    $result = $service->calculateFinalAmount(100000, $discountsPayload);
    echo "Total: " . $result->amountInCents;
} catch (Throwable $e) {
    // Menampilkan Stack Trace Terperinci
    echo "Exception Caught: " . $e->getMessage() . PHP_EOL;
    echo "Stack Trace:" . PHP_EOL;
    
    // Iterasi Stack Trace Frame secara native
    foreach ($e->getTrace() as $index => $frame) {
        $file = $frame['file'] ?? 'internal';
        $line = $frame['line'] ?? '0';
        $class = $frame['class'] ?? '';
        $type = $frame['type'] ?? '';
        $function = $frame['function'];
        
        echo "#{$index} {$file}({$line}): {$class}{$type}{$function}()" . PHP_EOL;
    }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Zend VM Hooking
Di dalam Zend Engine, fungsi-fungsi dieksekusi melalui pointer fungsi global bernama `zend_execute_ex` (atau `zend_execute`). 

Saat ekstensi Xdebug diinisialisasi:
1. Xdebug menyimpan alamat pointer `zend_execute_ex` bawaan PHP ke dalam variabel internal.
2. Xdebug menimpa (*hijack*) pointer `zend_execute_ex` dengan implementasi miliknya sendiri (`xdebug_execute_ex`).
3. Setiap kali Zend VM memanggil fungsi, metode, atau *include*, ia wajib melewati fungsi wrapper Xdebug. Di sini Xdebug:
   - Mencatat waktu dan alokasi memori saat fungsi dimasuki.
   - Mengambil *opline* (instruksi opcode) yang sedang aktif via `execute_data->opline`.
   - Memeriksa apakah file dan nomor baris dari opline tersebut cocok dengan daftar *active breakpoints*.
   - Jika cocok, eksekusi masuk ke loop `xdebug_debugger_dbgp()` yang menghentikan eksekusi thread dan menunggu instruksi IDE melalui soket.

```
Zend VM -> [zend_execute_ex Hooked by Xdebug]
                 │
                 ├── Memeriksa Breakpoints pada baris aktif
                 ├── Jika ada -> Suspensi Thread & Kirim Event via DBGp
                 └── Lanjutkan ke zend_execute_ex asli
```

#### Alokasi Memori / Resource
* **Zval Inspection**: Saat IDE meminta evaluasi variabel lokal pada stack frame, Xdebug membaca `zend_execute_data->symbol_table` (atau tabel variabel terkompilasi / *CV* - *Compiled Variables*). Xdebug harus mengiterasi zval dan mengonversi struktur C level PHP menjadi format data XML DBGp secara on-the-fly.
* **Overhead Ekstra**: Untuk setiap frame, Xdebug mengalokasikan memori internal C untuk melacak rekursi, argumen fungsi, dan *execution path*.

#### Trade-offs
* **Kinerja Turun Drastis (Performance Penalty)**: Meskipun `xdebug.mode=off` tidak membawa dampak performa yang signifikan, mengaktifkan `xdebug.mode=debug` atau `develop` dapat memperlambat performa eksekusi aplikasi sebesar **200% hingga 2000% (2x - 20x lebih lambat)** tergantung kedalaman arsitektur pemanggilan fungsi.
* **Overhead I/O Jaringan**: Setiap langkah eksekusi (*step-over*) memicu paket TCP bolak-balik antara PHP server dan IDE. Latensi jaringan lokal dapat langsung mempengaruhi responsivitas interaksi debugging.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan Mode Sesuai Kebutuhan**: Pisahkan konfigurasi berdasarkan kebutuhan. Gunakan `xdebug.mode=coverage` hanya saat menjalankan test suite, `xdebug.mode=profile` saat mencari bottleneck, dan `xdebug.mode=debug` untuk step-debugging.
* **Gunakan Conditional Breakpoints**: Daripada menekan *Resume* ratusan kali dalam loop besar, set breakpoint bersyarat pada IDE (contoh: `$step === 4` atau `$discount['value'] > 50000`).
* **Konfigurasi Path Mapping dengan Tepat**: Kesalahan paling umum di lingkungan Docker: path di dalam container (misal `/var/www/html`) harus dipetakan secara eksplisit ke direktori host lokal (misal `/Users/dev/project`) pada konfigurasi IDE.

#### Don'ts
* **JANGAN PERNAH Memasang Xdebug di Lingkungan Production**:
  1. *Security Vulnerability*: DBGp protocol tidak memiliki mekanisme enkripsi/autentikasi bawaan yang ketat; membuka port debugging berarti membuka akses eksekusi kode arbitrer.
  2. *Resource Exhaustion*: Overhead memori dan CPU akan menghancurkan kapasitas throughput server (*requests per second*).
* **Hindari `xdebug.start_with_request=yes` di Semua Skenario**: Gunakan `xdebug.start_with_request=trigger` agar Anda hanya mengaktifkan engine saat benar-benar mengirimkan header atau cookie debugging.

#### Edge Cases
* **PHP 8.1+ Fibers / Coroutines**: Saat menggunakan framework asinkron seperti Revolt atau Swoole, *call stack* konvensional terpecah antar-fiber. Stack trace Xdebug tradisional mungkin kehilangan jejak konteks eksekusi parent fiber kecuali runtime mendukung integrasi fiber-tracing khusus.
* **Infinite Recursion / Stack Overflow**: Jika loop rekursif menembus batas `xdebug.max_nesting_level`, PHP akan mematikan proses dengan *Fatal Error*. Tingkatkan limit hanya jika Anda memproses struktur pohon (*tree/graph*) yang memang sangat dalam, bukan untuk menutupi bug rekursi tak terbatas.

### 5. Tantangan Eksplorasi Mandiri

1. **Dockerized Debugging Setup**:
   Bangun sebuah konfigurasi Docker Compose dengan image `php:8.3-fpm` dan Nginx. Pasang Xdebug 3 secara manual via `pecl install xdebug`. Konfigurasikan koneksi agar IDE Anda yang berjalan di host machine dapat menangkap breakpoint di dalam container menggunakan variabel lingkungan `host.docker.internal` tanpa menggunakan IP hardcoded.

2. **Deteksi Bottleneck dengan Xdebug Profiling**:
   Ubah mode Xdebug menjadi `xdebug.mode=profile`. Jalankan skrip pemrosesan array berukuran besar (misalnya operasi sorting atau transformasi data dengan puluhan ribu elemen). Buka file *cachegrind* output yang dihasilkan menggunakan tool visualisasi (seperti QCacheGrind, KCacheGrind, atau Webgrind), lalu temukan fungsi mana yang menghabiskan *wall clock time* paling banyak dan berapa kali fungsi tersebut dipanggil.
