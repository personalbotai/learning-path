# 2. Hierarchy of Throwable: Error vs Exception

## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum PHP 7, penanganan error di PHP sangat terfragmentasi. *Exceptions* digunakan untuk error pada logika aplikasi, sementara *Fatal Errors* (seperti memanggil fungsi yang tidak ada atau *type mismatch*) ditangani langsung oleh Zend Engine yang berakibat pada terhentinya eksekusi skrip secara paksa (Halt). Hal ini membuat *graceful degradation* atau *logging* yang komprehensif menjadi sangat sulit.

Sejak PHP 7, arsitektur ini dirombak total dengan diperkenalkannya antarmuka **`Throwable`**. `Throwable` adalah *base interface* untuk semua objek yang dapat dilempar (di-*throw*) menggunakan *statement* `throw`. 

Hierarki ini terbagi menjadi dua cabang utama:
1. **`Exception`**: Merepresentasikan error di level aplikasi (*user-land*). Ini adalah kondisi abnormal yang **diharapkan bisa dipulihkan** (recoverable) oleh program.
2. **`Error`**: Merepresentasikan error internal dari PHP/Zend Engine. Ini adalah kondisi fatal (seperti `TypeError`, `ParseError`, `DivisionByZeroError`) yang sebelumnya akan langsung mematikan skrip. Meskipun sekarang bisa ditangkap (*catchable*), `Error` umumnya **tidak disarankan untuk dipulihkan**, melainkan ditangkap untuk keperluan *logging* dan *clean exit*.

**Penting:** Anda tidak dapat mengimplementasikan interface `Throwable` secara langsung pada kelas buatan Anda. Kelas Anda harus melakukan *extend* terhadap kelas `Exception` atau turunannya.

**Visualisasi Hierarki:**
```text
Throwable (Interface)
├── Error (Zend Engine / Internal)
│   ├── ArithmeticError (misal: DivisionByZeroError)
│   ├── AssertionError
│   ├── CompileError (misal: ParseError)
│   └── TypeError
└── Exception (User-land / Aplikasi)
    ├── LogicException (misal: InvalidArgumentException)
    └── RuntimeException (misal: OutOfBoundsException)
```

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern yang menunjukkan cara membedakan penanganan antara `Exception` (logika bisnis) dan `Error` (kesalahan sistem/engine) dalam sebuah *entry-point* aplikasi (misalnya *Front Controller* atau *Middleware*).

```php
<?php
declare(strict_types=1);

// Mensimulasikan sebuah service yang rentan terhadap berbagai jenis kegagalan
class PaymentProcessor {
    public function process(float $amount, object $gateway): string {
        if ($amount <= 0) {
            // Melempar Exception: Kesalahan logika bisnis (User-land)
            throw new InvalidArgumentException("Jumlah pembayaran harus lebih dari 0.");
        }

        // Jika $gateway tidak memiliki method 'charge', PHP akan melempar Error (Engine-level)
        // Secara spesifik: Error (Call to undefined method)
        return $gateway->charge($amount);
    }
}

// Entry point aplikasi (misal: index.php)
function handleRequest() {
    $processor = new PaymentProcessor();
    $dummyGateway = new stdClass(); // Objek kosong, tidak punya method 'charge'

    try {
        // Skenario 1: Akan memicu InvalidArgumentException (Exception)
        // $processor->process(-50.0, $dummyGateway);

        // Skenario 2: Akan memicu Error dari Zend Engine
        $processor->process(100.0, $dummyGateway);

    } catch (Exception $e) {
        // Menangkap error logika aplikasi. Bisa dipulihkan atau diberi pesan yang user-friendly.
        http_response_code(400);
        echo "Aplikasi Error: " . $e->getMessage() . "\n";
        // Lakukan retry atau fallback logic di sini
        
    } catch (Error $e) {
        // Menangkap error kritikal dari Engine. JANGAN dilanjutkan.
        // Log error ini untuk developer, berikan pesan generik ke user.
        http_response_code(500);
        error_log("CRITICAL ENGINE ERROR: " . $e->getMessage() . " di " . $e->getFile() . ":" . $e->getLine());
        echo "Terjadi kesalahan sistem internal. Tim kami sedang menanganinya.\n";
        exit(1); // Clean exit
        
    } catch (Throwable $t) {
        // Fallback terakhir (Catch-all) jika ada implementasi Throwable lain di masa depan
        error_log("UNKNOWN THROWABLE: " . $t->getMessage());
        exit(1);
    }
}

handleRequest();
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime (Stack Unwinding)**: 
  Ketika `throw` dieksekusi (baik oleh kode Anda atau oleh Zend Engine), PHP menghentikan eksekusi sekuensial saat ini dan memulai proses *Stack Unwinding* (penggulungan *call stack*). Zend Engine akan mencari blok `catch` terdekat yang cocok dengan tipe objek yang dilempar. Jika tidak ditemukan di fungsi saat ini, ia akan naik ke fungsi pemanggil (*caller*), terus hingga mencapai *global scope*. Jika tetap tidak ada yang menangkap, PHP akan memanggil *Global Exception Handler* (jika diatur via `set_exception_handler`), atau berujung pada *Fatal Error* dan skrip dihentikan.
- **Alokasi Memori / Resource**: 
  Selama proses *Stack Unwinding*, variabel lokal yang berada di dalam *scope* yang ditinggalkan akan dihancurkan (Garbage Collection). Jika variabel tersebut adalah objek, *magic method* `__destruct()` akan dipanggil. Ini memastikan tidak ada *memory leak* (seperti koneksi database yang menggantung) meskipun terjadi error fatal, asalkan ditangani dengan benar.
- **Trade-offs**: 
  Melempar `Throwable` (terutama `Exception`) memiliki *overhead* performa karena Zend Engine harus mengumpulkan *Stack Trace* (informasi file, baris, dan fungsi yang dipanggil). Oleh karena itu, `Exception` tidak boleh digunakan untuk *Control Flow* (seperti pengganti `if-else`), melainkan murni untuk kondisi eksepsional.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Tangkap `Throwable` hanya di level tertinggi aplikasi Anda (seperti *Router*, *Middleware*, atau *Job Worker loop*) untuk mencegah aplikasi *crash* secara diam-diam.
  - Selalu urutkan blok `catch` dari yang paling spesifik (misal: `TypeError`) hingga yang paling umum (`Throwable`).
  - Gunakan `Error` murni sebagai sinyal untuk *logging* dan mematikan proses (*graceful shutdown*).
- **Don'ts**:
  - **Jangan pernah** melakukan *swallow exception* (menangkap `Throwable` tanpa melakukan apa-apa di dalam blok `catch`). Ini akan menyembunyikan *bug* kritikal.
  - Jangan mencoba memulihkan (*recover*) aplikasi dari sebuah `Error` (seperti `ParseError` atau `TypeError`). Jika `Error` terjadi, *state* aplikasi kemungkinan besar sudah korup.
- **Edge Cases**:
  - **`OutOfMemoryError`**: Meskipun secara teori bisa ditangkap, pada praktiknya saat error ini dilempar, PHP mungkin tidak memiliki cukup memori tersisa bahkan untuk menjalankan blok `catch` atau menulis log.
  - **`ParseError`**: Hanya bisa ditangkap jika error sintaks terjadi pada file yang di-`include`/`require` atau dieksekusi via `eval()`. Jika error sintaks ada di file utama yang sedang dijalankan, skrip tidak akan pernah mencapai tahap *runtime* (gagal di tahap *compile*).

### 5. Tantangan Eksplorasi Mandiri

1. Buatlah sebuah fungsi yang menggunakan `eval()` untuk mengeksekusi string kode PHP yang sengaja dibuat salah sintaksnya (misal: kurang titik koma). Tangkap `ParseError` yang dihasilkan dan cetak pesan errornya tanpa membuat skrip utama berhenti.
2. Implementasikan fungsi `set_exception_handler()`. Buatlah agar fungsi ini menerima `Throwable` (sehingga bisa menangani baik `Exception` maupun `Error` yang tidak tertangkap oleh blok `try-catch`), lalu simpan *stack trace*-nya ke dalam sebuah file `error.log` berformat JSON.
3. Buatlah hierarki *Custom Exception* Anda sendiri (misal: `DatabaseException` yang meng-extend `RuntimeException`, dan `ConnectionException` yang meng-extend `DatabaseException`). Simulasikan pelemparan error dan tangkap menggunakan urutan `catch` yang benar.
