## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara *default*, Composer mengimplementasikan autoloader berbasis standar **PSR-4** dan **PSR-0**. Pada lingkungan *development*, fleksibilitas adalah prioritas utama: setiap kali Anda menambahkan atau memindahkan file kelas PHP baru, Anda tidak perlu menjalankan perintah apa pun agar kelas tersebut dapat diakses oleh runtime. 

Namun, fleksibilitas ini memiliki konsekuensi performa yang buruk pada lingkungan *production*.

```
[Request Masuk] 
       │
       ▼
spl_autoload_register callback (Composer\Autoload\ClassLoader)
       │
       ├──> 1. Cek internal in-memory array ($classMap)
       │         └── Jika TIDAK DITEMUKAN:
       │
       ├──> 2. Iterasi Prefix PSR-4 / PSR-0 (String matching sub-namespace)
       │
       ├──> 3. Resolusi Path File (Merangkai base directory + namespace path)
       │
       └──> 4. System Call: file_exists() / stream_resolve_include_path() (Disk I/O)
                 └── Jika ADA: require $file;
                 └── Jika TIDAK ADA: Lanjut iterasi prefix berikutnya -> Disk I/O lagi
```

#### Masalah Utama: Overhead Filesystem (I/O Bottleneck)
Pada mode standar:
1. Ketika sebuah kelas diinisialisasi (misal: `new App\Services\PaymentService()`), autoloader memecah namespace, mencocokkan *prefix* vendor/aplikasi, lalu mengkalkulasi path absolut di disk.
2. PHP memicu sistem panggilan (*system calls*) I/O seperti `stat()`, `lstat()`, atau `access()` melalui fungsi pengecekan file seperti `file_exists()`.
3. Dalam arsitektur kontainer modern (Docker dengan *storage driver* seperti `overlay2`) atau sistem jaringan (NFS/AWS EFS), latensi *system call* filesystem jauh lebih lambat dibanding *bare-metal local disk*. Jika satu request memuat 150 kelas, terjadi ratusan *disk check* yang sepenuhnya redundan.

#### Solusi: Strategi Level Optimasi Composer
Composer menyediakan beberapa tingkatan optimasi untuk mengubah resolusi dinamis berbasis *disk scan* menjadi resolusi statis berbasis *in-memory hash-map lookup* ($O(1)$ complexity):

1. **Level 1: Classmap Generation (`-o` / `--optimize`)**
   Composer memindai seluruh direktori proyek dan dependensi yang didefinisikan dalam PSR-4/PSR-0, lalu mengekstrak semua pemetaan `Namespace\Class => /path/to/File.php` ke dalam sebuah array statis (`autoload_classmap.php`). Jika kelas tidak ada di dalam classmap, autoloader akan **jatuh kembali (*fallback*)** ke pemindaian filesystem PSR-4 standar.

2. **Level 2 - Opsi A: Authoritative Classmap (`-a` / `--classmap-authoritative`)**
   Tingkat optimasi tertinggi untuk skenario deterministik. Mengasumsikan bahwa **semua** kelas yang valid sudah terdaftar di dalam classmap saat *build time*. Jika sebuah kelas tidak ditemukan di dalam classmap, Composer langsung mengembalikan nilai `false` tanpa pernah menyentuh filesystem melalui fallback PSR-4.

3. **Level 2 - Opsi B: APCu Cache (`--apcu`)**
   Menggunakan shared memory APCu sebagai cache lookup kelas (*hit* maupun *miss*). Opsi ini menjadi alternatif jika `--classmap-authoritative` tidak dapat digunakan (misalnya aplikasi memuat kelas dinamis baru saat runtime).

### 2. Implementasi & Contoh Kasus Nyata

Optimasi autoloader dapat dikonfigurasi melalui CLI saat proses deployment atau dideklarasikan permanen di dalam berkas konfigurasi `composer.json`.

#### Konfigurasi Produksi pada `composer.json`
Untuk memastikan seluruh deployment tim otomatis menerapkan optimasi tanpa mengandalkan flag CLI manual:

```json
{
    "name": "enterprise/payment-gateway",
    "type": "project",
    "require": {
        "php": "^8.3",
        "ext-apcu": "*",
        "psr/log": "^3.0"
    },
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    },
    "config": {
        "optimize-autoloader": true,
        "classmap-authoritative": true,
        "apcu-autoloader": false,
        "sort-packages": true
    }
}
```

#### Pipeline Build Produksi (Dockerfile)
Implementasi idiomatik dalam multi-stage Docker build untuk aplikasi PHP produksi:

```dockerfile
FROM composer:2.7 AS vendor-builder

WORKDIR /app
COPY composer.json composer.lock ./

# Install dependensi produksi tanpa menjalankan script/autoloader terlebih dahulu
RUN composer install \
    --no-dev \
    --no-interaction \
    --prefer-dist \
    --no-scripts \
    --no-autoloader

COPY . .

# Dump autoloader dengan optimasi tertinggi (Authoritative Classmap)
RUN composer dump-autoload \
    --no-dev \
    --classmap-authoritative

FROM php:8.3-fpm-alpine AS production
WORKDIR /var/www/html

COPY --from=vendor-builder /app/vendor ./vendor
COPY --from=vendor-builder /app/src ./src
COPY --from=vendor-builder /app/public ./public
COPY --from=vendor-builder /app/composer.json ./

USER www-data
```

#### Script Audit & Verifikasi Autoloader
Jalankan script PHP berikut di server untuk memverifikasi apakah autoloader berjalan dalam mode *Authoritative*:

```php
<?php

declare(strict_types=1);

require_once __DIR__ . '/vendor/autoload.php';

// Ambil seluruh registered autoloaders dari SPL stack
$autoloaders = spl_autoload_functions();
$composerLoader = null;

foreach ($autoloaders as $autoloader) {
    if (is_array($autoloader) && $autoloader[0] instanceof \Composer\Autoload\ClassLoader) {
        $composerLoader = $autoloader[0];
        break;
    }
}

if ($composerLoader === null) {
    throw new RuntimeException("Composer ClassLoader tidak terdeteksi.");
}

// Gunakan Reflection untuk membaca private property $classMapAuthoritative
$reflector = new ReflectionClass($composerLoader);
$authoritativeProp = $reflector->getProperty('classMapAuthoritative');
$authoritativeProp->setAccessible(true);

$isAuthoritative = $authoritativeProp->getValue($composerLoader);
$totalClassesInMap = count($composerLoader->getClassMap());

echo "=== Composer Autoloader Status ===" . PHP_EOL;
echo "Authoritative Mode : " . ($isAuthoritative ? "ACTIVE (Optimal)" : "DISABLED (Suboptimal)") . PHP_EOL;
echo "Indexed Classes    : " . $totalClassesInMap . " classes" . PHP_EOL;

// Uji coba resolusi kelas non-existent
$startTime = microtime(true);
$nonExistentClass = 'App\\NonExistent\\' . bin2hex(random_bytes(8));
$resolved = class_exists($nonExistentClass); // Memicu autoloader
$duration = (microtime(true) - $startTime) * 1_000_000;

echo "Miss Check Time    : " . number_format($duration, 2) . " µs" . PHP_EOL;
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Dari Dynamic Scanning ke Array Lookup
Ketika perintah `composer dump-autoload -a` dijalankan, Composer menghasilkan file `vendor/composer/autoload_static.php`. File ini menyimpan array PHP statis yang memuat seluruh dependensi:

```php
// vendor/composer/autoload_static.php (Representasi internal)
namespace Composer\Autoload;

class ComposerStaticInit...
{
    public static $classMap = array (
        'App\\Services\\PaymentService' => __DIR__ . '/../..' . '/src/Services/PaymentService.php',
        'Psr\\Log\\LoggerInterface' => __DIR__ . '/..' . '/psr/log/src/LoggerInterface.php',
        // ... ribuan kelas lainnya
    );
}
```

Saat runtime, method `ClassLoader::findFile($class)` dieksekusi:

```php
// vendor/composer/ClassLoader.php
private function findFileWithExtension($class, $ext)
{
    // 1. Direct Hashmap Lookup - O(1) Time Complexity
    if (isset($this->classMap[$class])) {
        return $this->classMap[$class];
    }

    // 2. Authoritative Cutoff:
    // Jika classMapAuthoritative bernilai true, loop PSR-4 DIBAWAH INI TIDAK DIEKSEKUSI.
    if ($this->classMapAuthoritative) {
        return false;
    }

    // Fallback: PSR-4 Dynamic Directory Scanning (Dilewati sepenuhnya pada mode -a)
    // ... string sub-matching & file_exists checks ...
}
```

#### Alokasi Memori / Resource & OPcache
- **Immutable Shared Memory**: Ketika array classmap dideklarasikan di dalam file PHP (`autoload_static.php`), ekstensi **OPcache** akan mengompilasi array tersebut menjadi *opcodes* dan menyimpannya di *Shared Memory* (SHM). 
- Array `$classMap` tidak dialokasikan ulang di memori proses per-request (Zend Engine heap). Semua worker PHP-FPM membaca struktur data C-level hash table yang sama dari SHM secara *read-only*, menjaga konsumsi RAM per request tetap minimal.

#### Trade-offs: Build Time vs Runtime Latency
| Aspek | Standar (Dev) | Optimized (`-o`) | Authoritative (`-a`) |
| :--- | :--- | :--- | :--- |
| **Kecepatan Build** | Instan (Tidak ada scan) | Sedang (Scan direktori lokal) | Sedang (Scan direktori lokal) |
| **Lookup Hit** | Lambat ($O(N)$ string/IO check) | Sangat Cepat ($O(1)$ Hashmap) | Sangat Cepat ($O(1)$ Hashmap) |
| **Lookup Miss** | Sangat Lambat (Disk traversal) | Sangat Lambat (Disk traversal) | Instan ($O(1)$ kegagalan map) |
| **Fleksibilitas Runtime** | Tinggi (Bisa load file baru) | Menengah (Fallback aktif) | Nol (Strict, file baru diabaikan) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `--classmap-authoritative` secara default di CI/CD**: Jadikan ini langkah final setelah eksekusi `composer install` dan sebelum *container image* di-*tag* untuk rilis.
- **Kombinasikan dengan OPcache Preloading (PHP 7.4+)**: Masukkan file `vendor/autoload.php` ke dalam skrip `opcache.preload`. Hal ini memastikan seluruh hashmap autoloader telah dikompilasi ke memori server saat PHP-FPM booting pertama kali:
  ```ini
  ; php.ini
  opcache.preload=/var/www/html/preload.php
  opcache.preload_user=www-data
  ```
  ```php
  // preload.php
  require_once '/var/www/html/vendor/autoload.php';
  ```

#### Don'ts
- **Jangan gunakan `-a` jika terdapat Runtime Code Generation**: Framework atau library yang mengompilasi kelas langsung ke sistem file saat runtime (misal: *Doctrine Proxies* atau *ProxyManager* tanpa pemanasan cache build) akan gagal fatal dengan error `Fatal error: Uncaught Error: Class "..." not found` karena kelas tersebut belum ada saat `dump-autoload` dijalankan.
- **Jangan gunakan `--apcu` jika sudah mengaktifkan `-a`**: Menambahkan APCu autoloader pada setup yang sudah *authoritative* adalah pemborosan resource. IPC (*Inter-Process Communication*) ke APCu lebih lambat daripada OPcache SHM PHP hashmap internal.

#### Edge Cases
- **Dynamic Class Loading / Framework Plugins**: Beberapa aplikasi memuat plugin dari direktori eksternal secara dinamis di runtime. Jika direktori tersebut tidak dimasukkan ke dalam `autoload` block `composer.json` saat *build*, autoloader authoritative akan memblokir pemuatan kelas tersebut. 
  *Solusi*: Jalankan pemanasan generator (seperti `php bin/console cache:warmup` atau `php artisan optimize`) **sebelum** mengeksekusi `composer dump-autoload -a`.
- **Case Sensitivity Desynchronization**: Jika Anda membangun classmap di lingkungan macOS/Windows (filesystem case-insensitive) lalu mendistribusikannya ke Linux (case-sensitive), kesalahan tipografi pada pemanggilan namespace (misal: `use App\services\PaymentService`) akan tersimpan di classmap dan menyebabkan kegagalan resolusi file di Linux. Selalu lakukan build pada OS target.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi I/O System Calls Menggunakan `strace`**:
   Jalankan PHP CLI dengan pelacakan sistem file pada mode standar vs authoritative:
   ```bash
   # Jalankan autoloader standar, amati jumlah pemanggilan stat/openat
   strace -c -e trace=stat,lstat,openat,access php -r "require 'vendor/autoload.php'; class_exists('App\Services\PaymentService');"

   # Bandingkan dengan mode authoritative
   composer dump-autoload -a
   strace -c -e trace=stat,lstat,openat,access php -r "require 'vendor/autoload.php'; class_exists('App\Services\PaymentService');"
   ```
   *Analisis berapa banyak I/O call yang berhasil dieliminasi.*

2. **Deteksi Kerentanan Dynamic Proxy Generation**:
   Buat kelas baru secara dinamis menggunakan `file_put_contents()` di dalam direktori `src/Generated/DummyClass.php` saat runtime setelah perintah `composer dump-autoload -a` selesai. Jalankan `class_exists('App\Generated\DummyClass')`. Amati kegagalannya, lalu susun strategi build pipeline yang benar untuk mengatasi masalah ini tanpa mematikan mode authoritative.
