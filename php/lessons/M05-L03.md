### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur aplikasi berbasis web dengan PHP, model eksekusi umumnya bersifat *stateless* dan berbasis siklus hidup permintaan (*request-response lifecycle* via PHP-FPM atau Swoole/RoadRunner). Ketika aplikasi PHP memanipulasi entitas data yang saling terkait (seperti pemrosesan pembayaran dan pembaruan stok), konsistensi data tidak boleh terfragmentasi di tengah jalan. Di sinilah konsep **Database Transactions** dan prinsip **ACID** menjadi pilar utama.

```
+-----------------------------------------------------------+
|                   PHP Runtime (Engine)                    |
|  $pdo->beginTransaction() -> Send query -> $pdo->commit() |
+-----------------------------+-----------------------------+
                              | TCP / Unix Socket
                              v
+-----------------------------------------------------------+
|               RDBMS Engine (e.g., InnoDB)                 |
|  - Lock Manager (Row/Table locks)                         |
|  - MVCC (Multi-Version Concurrency Control)               |
|  - WAL: Redo Log (Durability) & Undo Log (Atomicity/Rollback)
+-----------------------------------------------------------+
```

#### Fondasi ACID:
1. **Atomicity (Semua atau Tidak Sama Sekali):** Serangkaian operasi DML (`INSERT`, `UPDATE`, `DELETE`) dieksekusi sebagai satu unit kerja logis. Jika satu operasi gagal, seluruh status basis data harus dikembalikan (*rollback*) ke titik sebelum transaksi dimulai.
2. **Consistency (Integritas Status):** Transaksi membawa data dari satu status valid ke status valid lainnya, mematuhi semua batasan skema (*constraints*, *cascades*, *triggers*).
3. **Isolation (Isolasi Transaksi Konkuren):** Menentukan visibilitas perubahan data antar-transaksi yang berjalan bersamaan. Tingkat isolasi standar ANSI/ISO SQL meliputi:
   - *Read Uncommitted* (rentan *Dirty Read*)
   - *Read Committed* (rentan *Non-repeatable Read*)
   - *Repeatable Read* (default MySQL InnoDB, mitigasi via *MVCC* & *Gap Locks*)
   - *Serializable* (isolasi tertinggi menggunakan penguncian ketat)
4. **Durability (Daya Tahan Permanen):** Setelah `COMMIT` berhasil, modifikasi data dijamin tidak hilang bahkan jika server *crash* seketika, dijamin melalui *Write-Ahead Logging* (WAL).

Di runtime PHP, transaksi dikelola melalui abstraksi layer seperti **PDO (PHP Data Objects)**. Saat `PDO::beginTransaction()` dipanggil, PDO menonaktifkan mode *autocommit* pada sesi koneksi database tersebut (`AUTOCOMMIT=0`), menahan konfirmasi perubahan disk permanen hingga `PDO::commit()` dipicu secara eksplisit.

### 2. Implementasi & Contoh Kasus Nyata

Pola modern yang direkomendasikan adalah membungkus transaksi dalam skema eksekusi *closure-based* (Higher-Order Function) yang menangani pembukaan transaksi, komit, mitigasi rollback, dan *retry* saat terjadi *deadlock*.

Berikut adalah implementasi *Transactional Runner* idiomatik menggunakan PHP 8.2+:

```php
<?php

declare(strict_types=1);

namespace App\Database;

use PDO;
use PDOException;
use Throwable;

final class TransactionManager
{
    public function __construct(private readonly PDO $pdo) {}

    /**
     * Mengeksekusi closure di dalam lingkup transaksi database
     * dengan mekanisme deteksi Deadlock & automatic retry.
     *
     * @template T
     * @param callable(PDO): T $action
     * @param int $maxRetries
     * @return T
     * @throws Throwable
     */
    public function transactional(callable $action, int $maxRetries = 3): mixed
    {
        $attempts = 0;

        beginning:
        $attempts++;

        try {
            $this->pdo->beginTransaction();

            // Eksekusi unit logika bisnis
            $result = $action($this->pdo);

            $this->pdo->commit();

            return $result;
        } catch (Throwable $e) {
            // Selalu rollback saat terjadi unhandled error
            if ($this->pdo->inTransaction()) {
                $this->pdo->rollBack();
            }

            // Error code 1213 = MySQL Deadlock, 40001 = ANSI Serialization Failure
            if ($this->isDeadlock($e) && $attempts < $maxRetries) {
                // Backoff jitter sederhana (dalam mikrodetik)
                usleep(random_int(10000, 50000));
                goto beginning;
            }

            throw $e;
        }
    }

    private function isDeadlock(Throwable $e): bool
    {
        return $e instanceof PDOException && (
            $e->getCode() === '40001' || 
            str_contains($e->getMessage(), '1213')
        );
    }
}

// ==========================================
// CONTOH KASUS PENGGUNAAN: TRANSFER SALDO
// ==========================================

$dsn = 'mysql:host=127.0.0.1;dbname=fintech;charset=utf8mb4';
$pdo = new PDO($dsn, 'db_user', 'db_secret', [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false, // Wajib false untuk prepared statements native
]);

$txManager = new TransactionManager($pdo);

try {
    $senderId = 42;
    $receiverId = 88;
    $transferAmount = 250_000.00;

    $transferReceipt = $txManager->transactional(function (PDO $db) use ($senderId, $receiverId, $transferAmount): string {
        // 1. Kunci baris pengirim secara pesimistik untuk menghindari race-condition
        $stmt = $db->prepare('SELECT balance FROM wallets WHERE user_id = :id FOR UPDATE');
        $stmt->execute(['id' => $senderId]);
        $senderBalance = (float) $stmt->fetchColumn();

        if ($senderBalance < $transferAmount) {
            throw new \UnderflowException("Saldo tidak mencukupi untuk transfer.");
        }

        // 2. Debet akun pengirim
        $debitStmt = $db->prepare('UPDATE wallets SET balance = balance - :amount WHERE user_id = :id');
        $debitStmt->execute(['amount' => $transferAmount, 'id' => $senderId]);

        // 3. Kredit akun penerima
        $creditStmt = $db->prepare('UPDATE wallets SET balance = balance + :amount WHERE user_id = :id');
        $creditStmt->execute(['amount' => $transferAmount, 'id' => $receiverId]);

        // 4. Catat riwayat mutasi
        $logStmt = $db->prepare('INSERT INTO transactions (from_user, to_user, amount, created_at) VALUES (?, ?, ?, NOW())');
        $logStmt->execute([$senderId, $receiverId, $transferAmount]);

        return "TX-" . bin2hex(random_bytes(8));
    });

    echo "Transaksi Sukses. Kode Referensi: {$transferReceipt}\n";

} catch (Throwable $e) {
    echo "Transaksi Dibatalkan: " . $e->getMessage() . "\n";
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Network Boundary:** Saat PHP mengeksekusi `$pdo->beginTransaction()`, PDO mengirim instruksi network packet level protokol (misalnya paket query `START TRANSACTION` atau flag COM_QUERY) ke engine database melalui koneksi socket TCP/IP atau Unix Domain Socket.
2. **State Mesin DB:** Database menandai thread koneksi tersebut berada dalam blok transaksi aktif. Parameter `AUTOCOMMIT` dimatikan secara lokal pada sesi tersebut.
3. **Commit/Rollback:** Ketika `$pdo->commit()` dipanggil, instruksi `COMMIT` dikirim. Database mem-flush *transaction state*. Jika script PHP mati mendadak (*fatal error* atau `die()`) sebelum commit, koneksi socket terputus; server basis data otomatis mendeteksi pemutusan koneksi (*client disconnect*) dan mengeksekusi prosedur internal rollback secara otomatis.

#### Alokasi Memori / Resource
* **Write-Ahead Logging (WAL) & Redo Log:** Saat perintah `UPDATE` berjalan di PHP, DB tidak langsung menulis halaman data ke storage SSD/HDD (karena operasi *random I/O* mahal). Modifikasi disimpan pada *Buffer Pool* (RAM server DB) dan ditulis secara sekuensial ke **Redo Log** (operasi *append-only* cepat). Redo log menjamin **Durability**.
* **Undo Log (Rollback Segments):** Database membuat salinan data sebelum dimodifikasi ke dalam **Undo Log**. Jika PHP mengirim `$pdo->rollBack()`, DB mengambil pointer dari undo log untuk mengembalikan row ke nilai semula (**Atomicity**). Undo log juga digunakan oleh mekanisme **MVCC** (*Multi-Version Concurrency Control*) agar transaksi lain yang membaca data melihat snapshot lama tanpa terblokir.

#### Trade-offs
* **Throughput vs. Data Integrity:** Semakin tinggi level isolasi atau semakin sering menggunakan penguncian eksklusif (`SELECT ... FOR UPDATE`), semakin besar *lock contention*. Latensi *request* PHP akan meningkat drastis karena antrean kunci (*lock wait timeout*).
* **Connection Footprint:** Transaksi yang terbuka mengikat koneksi database secara eksklusif. Di lingkungan PHP-FPM dengan lalu lintas padat, transaksi berdurasi panjang dapat menghabiskan kuota `max_connections` basis data dalam hitungan detik.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Jaga Transaksi Sesingkat Mungkin:** Jalankan operasi non-database (seperti validasi data, hashing password, kalkulasi kompleks di CPU) **sebelum** memanggil `beginTransaction()`.
* **Urutkan Mutasi Entitas Secara Konsisten:** Jika Transaksi A memperbarui tabel `A` lalu `B`, pastikan Transaksi B juga memperbarui `A` lalu `B` (bukan `B` lalu `A`). Hal ini mencegah terjadinya siklus saling tunggu (*Deadlock*).
* **Gunakan Explicit Pessimistic Locking dengan Tepat:** Gunakan `FOR UPDATE` saat membaca data yang nilainya akan digunakan sebagai acuan validasi modifikasi berikutnya di dalam transaksi yang sama.

#### Don'ts
* **JANGAN Panggil External Network Calls (API/HTTP/Email) di Dalam Transaksi:**
  ```php
  // FATAL ANTI-PATTERN!
  $pdo->beginTransaction();
  $pdo->query("UPDATE billing SET status = 'paid' WHERE id = 1");
  
  // Jika gateway pembayaran membutuhkan 5 detik untuk merespons,
  // database row lock akan tertahan selama 5 detik penuh!
  $httpClient->post('https://payment-gateway.com/charge');
  
  $pdo->commit();
  ```
  *Solusi:* Lakukan panggilan HTTP di luar transaksi, atau simpan status "PENDING" dalam transaksi cepat, lalu serahkan eksekusi external service ke Background Job / Queue Worker.
* **JANGAN Mengandalkan Nested Transaction Palsu:** PDO tidak mendukung *nested transaction* murni secara default. Memanggil `beginTransaction()` dua kali berturut-turut pada koneksi yang sama akan melempar `PDOException` ("There is already an active transaction"). Gunakan mekanisme **SAVEPOINT** jika benar-benar membutuhkan sub-transaksi logis.

#### Edge Cases
* **Implicit Commit oleh Pernyataan DDL:** Di MySQL, mengeksekusi perintah skema seperti `CREATE TABLE`, `ALTER TABLE`, atau `DROP TABLE` di tengah-tengah transaksi aktif akan memicu **Implicit Commit** secara otomatis. Status transaksi sebelumnya langsung tersimpan permanen dan tidak dapat di-rollback.
* **PHP Long-Running CLI Scripts / Worker:** Pada daemon CLI (seperti Laravel Horizon, RabbitMQ consumer), jika transaksi tidak di-rollback/commit secara benar akibat `unhandled exception`, koneksi persistent atau koneksi yang di-reuse akan tetap berstatus `inTransaction()`, merusak integritas isolasi job berikutnya.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Manual Savepoint Wrapper:** 
   Rancang modifikasi pada kelas `TransactionManager` di atas agar mendukung *nested transactions* berbasis nama `SAVEPOINT` (menggunakan query mentah `SAVEPOINT savepoint_name`, `RELEASE SAVEPOINT savepoint_name`, dan `ROLLBACK TO SAVEPOINT savepoint_name`). Pastikan rollback level kedua tidak membatalkan operasi level pertama.
2. **Simulasi dan Resolusi Deadlock:**
   Tulis dua script CLI PHP terpisah yang dijalankan bersamaan. 
   - Script 1 memperbarui Akun A lalu mencoba memperbarui Akun B (dengan delay `sleep(2)` di tengahnya).
   - Script 2 memperbarui Akun B lalu mencoba memperbarui Akun A.
   Periksa log database untuk melihat pesan *Deadlock detected*, dan amati bagaimana mekanisme retry pada contoh di atas menangani *graceful recovery*.
