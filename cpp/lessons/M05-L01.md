## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, memori bukan sekadar deretan bita (bytes); memori terikat erat dengan konsep **Object Lifetime** (siklus hidup objek) dan **Ownership** (kepemilikan sumber daya). Ketidakmampuan membedakan antara *raw memory* (alokasi bita murni) dan *object initialization* (pemanggilan konstruktor pada alamat tertentu) adalah akar dari banyak bug fatal seperti *use-after-free*, *double-free*, dan *undefined behavior* (UB).

```
+-------------------------------------------------------------------+
|                        Resource Lifecycle                         |
+-------------------------------------------------------------------+
| 1. Memory Allocation  : Raw bytes direservasi (malloc / ::op new)  |
| 2. Object Construction: Konstruktor dieksekusi di alamat tersebut   |
| 3. Object Destruction : Destruktor membersihkan state internal    |
| 4. Memory Deallocation: Raw bytes dikembalikan ke OS / Heap       |
+-------------------------------------------------------------------+
```

#### Ownership Model: Dari Manual ke RAII
Kepemilikan (*ownership*) mendefinisikan entitas mana yang bertanggung jawab mengelola daur hidup suatu sumber daya (kapan dialokasikan, ditransfer, dan dibebaskan).
1. **Raw Ownership (Legacy C/Early C++)**: Menggunakan pointer mentah (`T*`). Tanggung jawab pembersihan bersifat implisit dan rawan *human error*. Pointer tidak membawa semantik kepemilikan.
2. **Exclusive Ownership (`std::unique_ptr`)**: Memanfaatkan *move semantics* (C++11). Objek hanya boleh dimiliki oleh satu pemilik pada satu waktu. Saat pemilik keluar dari *scope*, destruktor dipanggil secara deterministik via paradigma **RAII** (*Resource Acquisition Is Initialization*).
3. **Shared Ownership (`std::shared_ptr` & `std::weak_ptr`)**: Kepemilikan bersama berbasis *reference counting*. Siklus hidup sumber daya diperpanjang sampai *reference count* mencapai nol.

#### Raw Memory vs. Object Lifetime
Di level bahasa, alokasi memori dan konstruksi objek adalah dua fase terpisah:
- **Raw Memory**: Blok memori tak bertipe (`void*`, `std::byte[]`, atau `char[]`) yang memiliki ukuran (*size*) dan batas keselarasan (*alignment boundary*), tetapi belum berisi objek C++ yang valid.
- **Object**: Memori yang telah melalui fase konstruksi sehingga invarian kelasnya terpenuhi. Mengakses memori sebelum objek dikonstruksi atau setelah didekonstruksi memicu *undefined behavior*.
- **Placement `new`**: Mekanisme C++ untuk memanggil konstruktor pada alamat raw memory yang sudah dialokasikan sebelumnya:
  $$\text{Syntax: } \texttt{new (address) Type(args...);}$$
- **Explicit Destructor**: Karena memori tidak dialokasikan via *new-expression* standar, destruktor harus dipanggil secara eksplisit (`ptr->~Type()`) sebelum memori dasarnya dibebaskan.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi *custom fixed-capacity inline storage* (serupa dengan fondasi internal `std::optional` atau *small buffer optimization*), di mana kita mengelola *raw memory*, *alignment*, dan siklus hidup objek secara manual namun aman dengan semantik kepemilikan RAII.

```cpp
#include <iostream>
#include <new>          // placement new
#include <utility>      // std::move, std::forward
#include <cstddef>      // std::byte, std::size_t
#include <memory>       // std::construct_at, std::destroy_at (C++20)

template <typename T>
class ScopedInlineCell {
public:
    ScopedInlineCell() : m_has_value(false) {}

    // Konstruksi in-place menggunakan perfect forwarding
    template <typename... Args>
    void emplace(Args&&... args) {
        if (m_has_value) {
            reset(); // Bersihkan objek lama jika ada
        }
        
        // C++20 std::construct_at atau placement new tradisional:
        // ::new (static_cast<void*>(m_storage)) T(std::forward<Args>(args)...);
        std::construct_at(reinterpret_cast<T*>(m_storage), std::forward<Args>(args)...);
        m_has_value = true;
    }

    void reset() noexcept {
        if (m_has_value) {
            // Destruksi objek secara eksplisit TANPA membebaskan memori storage
            std::destroy_at(reinterpret_cast<T*>(m_storage));
            m_has_value = false;
        }
    }

    T& get() {
        if (!m_has_value) throw std::logic_error("Cell is empty!");
        return *reinterpret_cast<T*>(m_storage);
    }

    const T& get() const {
        if (!m_has_value) throw std::logic_error("Cell is empty!");
        return *reinterpret_cast<const T*>(m_storage);
    }

    bool has_value() const noexcept { return m_has_value; }

    // RAII Destructor
    ~ScopedInlineCell() {
        reset();
    }

    // Disable copy semantics untuk menyederhanakan kepemilikan (Move-only)
    ScopedInlineCell(const ScopedInlineCell&) = delete;
    ScopedInlineCell& operator=(const ScopedInlineCell&) = delete;

    ScopedInlineCell(ScopedInlineCell&& other) noexcept {
        if (other.m_has_value) {
            emplace(std::move(other.get()));
            other.reset();
        }
    }

    ScopedInlineCell& operator=(ScopedInlineCell&& other) noexcept {
        if (this != &other) {
            reset();
            if (other.m_has_value) {
                emplace(std::move(other.get()));
                other.reset();
            }
        }
        return *this;
    }

private:
    // Alokasi raw memory pada stack dengan alignment yang identik dengan tipe T
    alignas(alignof(T)) std::byte m_storage[sizeof(T)];
    bool m_has_value{false};
};

struct HeavyTracker {
    int id;
    HeavyTracker(int i) : id(i) { std::cout << "Constructed: " << id << "\n"; }
    ~HeavyTracker() { std::cout << "Destructed: " << id << "\n"; }
};

int main() {
    std::cout << "--- Inisialisasi Storage ---\n";
    ScopedInlineCell<HeavyTracker> cell;

    std::cout << "--- Emplace Object 1 ---\n";
    cell.emplace(101);

    std::cout << "--- Emplace Object 2 (Auto destruct 101) ---\n";
    cell.emplace(202);

    std::cout << "--- Explicit Reset ---\n";
    cell.reset();

    std::cout << "--- Re-emplace Object 3 ---\n";
    cell.emplace(303);

    std::cout << "--- Scope Exit (Auto destruct via RAII) ---\n";
    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Ketika mengeksekusi ekspresi `new T(args...)`:
1. Compiler menyisipkan pemanggilan runtime `operator new(sizeof(T))` untuk mengalokasikan blok memori mentah dari heap manager OS (menggunakan `malloc`, `brk`, atau `mmap`).
2. Jika alokasi berhasil, compiler menyisipkan instruksi perakitan (*assembly*) untuk memanggil konstruktor `T::T(args...)` pada alamat penunjuk tersebut.
3. Sebaliknya, pada **Placement `new`**, fase (1) diabaikan sepenuhnya; compiler langsung menjalankan fase (2) pada alamat memori yang disuplai oleh programmer.

#### Alokasi Memori & Hardware Alignment
- Setiap tipe data memiliki kebutuhan *alignment* (`alignof(T)`), yaitu kelipatan alamat memori di mana objek tersebut harus ditempatkan agar CPU dapat melakukan dereferensi memori secara optimal (atau tanpa memicu instruksi fault/hardware trap pada arsitektur tertentu seperti ARM).
- `alignas(alignof(T)) std::byte m_storage[sizeof(T)]` menjamin bahwa offset *byte array* di stack memenuhi alignment yang dibutuhkan `T`. Jika tipe memerlukan 8-byte alignment, alamat memori basis buffer akan diakhiri dengan bit heksadesimal `0x0`, `0x8`, dst.

#### Memory Layout Control Block pada `std::shared_ptr`
Ketika menggunakan *smart pointer*:
- `std::unique_ptr<T>` memiliki ukuran setara dengan pointer mentah `T*` (zero overhead) jika menggunakan *default deleter*.
- `std::shared_ptr<T>` terdiri dari dua raw pointer:
  1. Pointer ke objek terkelola (`T*`).
  2. Pointer ke *Control Block* internal yang berisi:
     - Strong Reference Counter (`std::atomic<long>`)
     - Weak Reference Counter (`std::atomic<long>`)
     - Custom Deleter & Allocator
- `std::make_shared<T>()` menggabungkan alokasi *Control Block* dan alokasi memori `T` ke dalam **satu blok memori kontigu**, mereduksi fragmentasi heap dan meningkatkan performa CPU cache locality.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan RAII secara Mutlak**: Bungkus setiap siklus alokasi/deallokasi raw memory ke dalam struktur kelas yang memanfaatkan destruktor.
- **Gunakan `std::construct_at` dan `std::destroy_at` (C++20)**: Gantikan placement `new` dan pemanggilan manual `~T()` dengan utilitas standar ini untuk konsistensi fungsional dan kompatibilitas *constexpr*.
- **Patuhi Batas Keselarasan (*Alignment*)**: Selalu gunakan `alignas` saat mengalokasikan array byte mentah untuk penampungan objek.
- **Gunakan `std::make_unique` dan `std::make_shared`**: Mencegah *memory leak* akibat urutan evaluasi argumen sebelum C++17 dan mengoptimalkan penempatan control block.

#### Don'ts
- **Dilarang Mencampuradukkan Alokator**: Jangan pernah memasangkan `malloc()` dengan `delete`, atau `new[]` dengan `delete` (bukan array `delete[]`). Hal ini merusak metadata internal heap allocator dan memicu UB seketika.
- **Hindari Memanggil Destruktor Dua Kali**: Memanggil destruktor eksplisit lalu membiarkan RAII mengeksekusi destruktor lagi pada memori yang sama akan memicu *double-free* atau *corrupted state*.
- **Hindari *Strict Aliasing Violation***: Jangan membaca data melalui pointer bertipe sembarang tanpa perantara `std::byte`, `char`, atau `std::bit_cast`.

#### Common Pitfalls
- **Exception pada Konstruksi Parsial**: Jika sebuah kelas mengalokasikan raw memory untuk 10 objek berturut-turut, dan objek ke-4 melempar eksepsi (*exception*) saat dikonstruksi, runtime C++ **tidak** akan otomatis membersihkan objek 1, 2, dan 3. Anda wajib menangkap eksepsi tersebut dan memanggil destruktor hanya untuk objek yang telah selesai dikonstruksi secara eksplisit.
- **Slicing pada Ownership Transfer**: Mentransfer kepemilikan polimorfik tanpa *virtual destructor* pada base class akan mengakibatkan kebocoran memori pada turunan (*derived class*).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Exception-Safe Bulk Construction**:
   Buat fungsi kustom:
   ```cpp
   template <typename T>
   void uninitialized_construct_n(std::byte* buffer, std::size_t n, const T& value);
   ```
   Fungsi ini harus mengonstruksi $N$ buah objek $T$ pada *buffer* mentah. Jika konstruktor ke-$k$ ($k < N$) melempar eksepsi, seluruh $k-1$ objek yang telah terkonstruksi sebelumnya harus didekonstruksi secara terbalik sebelum eksepsi dilempar kembali (*rethrow*), sehingga tidak terjadi kebocoran memori.

2. **Deteksi Cyclic Reference**:
   Buat dua struktur data `NodeA` dan `NodeB` yang saling mereferensikan via `std::shared_ptr`. Amati konsumsi memori dan destruktor yang gagal terpanggil saat kedua *instance* keluar dari *scope*. Perbaiki desain arsitektur kepemilikan tersebut menggunakan `std::weak_ptr`.
