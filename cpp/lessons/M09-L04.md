## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum C++20, *template metaprogramming* mengandalkan paradigma *duck typing*: kompilator mengasumsikan tipe data memiliki operasi tertentu, dan jika tidak ada, proses kompilasi gagal di fase instansiasi terdalam. Untuk membatasi tipe (*type constraint*), C++ terdahulu mengandalkan **SFINAE** (*Substitution Failure Is Not An Error*) via `std::enable_if_t`, tag dispatching, atau trik `void_t`. Pendekatan ini menghasilkan:
1. Pesan galat (*compiler diagnostic*) yang sangat panjang dan sulit dibaca.
2. Waktu kompilasi lambat akibat instansiasi template rekursif hanya untuk validasi tipe.
3. Keterbacaan kode (*code readability*) yang buruk.

**C++20 Concepts** mengubah paradigma ini secara mendasar. Concept adalah predikat waktu-kompilasi (*compile-time predicate*) bernama yang mengevaluasi tipe data terhadap sekumpulan kebutuhan leksikal dan semantik.

```
       SFINAE (Pre-C++20)                    Concepts (C++20)
+-------------------------------+     +-------------------------------+
| Template Instantiation Sinks  |     | First-Class AST Constraint    |
| (Exploits AST SFINAE failure) |     | (Evaluated before instantiate)|
+-------------------------------+     +-------------------------------+
               |                                      |
       Slow substitution                     Fast boolean reduction
  Complex compiler error dumps           Direct, human-readable diagnostics
```

#### Arsitektur Constraints & Overload Resolution

Ketika kompilator memproses fungsi ber-constraint, terdapat tahapan khusus dalam **Overload Resolution**:
1. **Template Argument Deduction**: Kompilator mendeduksi tipe template seperti biasa.
2. **Constraint Checking**: Kompilator memvalidasi apakah tipe memenuhi *associated constraints*. Jika bernilai `false`, fungsi langsung dieliminasi dari daftar kandidat overload resolution *tanpa memicu instansiasi body template*.
3. **Partial Ordering by Constraints (Subsumption)**: Jika ada beberapa kandidat overload template yang sama-sama valid, kompilator membandingkan keketatan constraint (*more constrained* vs *less constrained*) menggunakan aturan **Subsumption**. Konsep $A$ men-*subsume* konsep $B$ jika $A$ secara logis mengimplikasikan $B$ ($A \implies B$). Kandidat yang paling terspesialisasi akan dipilih secara otomatis tanpa memicu ambiguitas kompilasi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi sistem pemrosesan buffer/data stream performa tinggi. Kita membedakan perlakuan antara data numerik skalar primitif, contiguous buffer (memory-mapped), dan struktur serialisasi kustom menggunakan **Concepts** dan **Constrained Overload**.

```cpp
#include <iostream>
#include <concepts>
#include <vector>
#include <span>
#include <cstring>
#include <type_traits>

// 1. Definisi Custom Concepts
template <typename T>
concept TriviallySerializable = std::is_trivially_copyable_v<T> && !std::is_pointer_v<T>;

template <typename T>
concept CustomSerializable = requires(T obj) {
    { obj.serialize() } -> std::same_as<std::vector<uint8_t>>;
    { obj.serialized_size() } -> std::convertible_to<std::size_t>;
};

template <typename T>
concept Serializable = TriviallySerializable<T> || CustomSerializable<T>;

// 2. Definisi Concept untuk Subsumption Hierarchy
template <typename T>
concept ByteStreamSource = requires(T stream) {
    { stream.data() } -> std::convertible_to<const uint8_t*>;
    { stream.size() } -> std::same_as<std::size_t>;
};

// ContiguousMemorySource lebih terspesialisasi daripada ByteStreamSource
template <typename T>
concept ContiguousByteStream = ByteStreamSource<T> && std::contiguous_iterator<typename T::const_iterator>;

// 3. Constrained Overloading Pipeline

// Overload A: Tipe Primitif / Trivial (memcpy-safe)
template <TriviallySerializable T>
void write_payload(const T& data) {
    std::cout << "[Fast-Path] Menulis trivially copyable data, size: " 
              << sizeof(T) << " bytes via memcpy.\n";
}

// Overload B: Tipe dengan serialisasi custom (tidak trivial)
template <CustomSerializable T>
    requires (!TriviallySerializable<T>) // Menghindari ambiguitas eksplisit jika kedua kondisi terpenuhi
void write_payload(const T& data) {
    std::cout << "[Custom-Path] Menggunakan serializer kustom, payload size: " 
              << data.serialized_size() << " bytes.\n";
    auto bytes = data.serialize();
    // Proses payload byte stream...
}

// Overload C: Menggunakan Subsumption (Stream umum vs Contiguous Stream)
template <ByteStreamSource S>
void dispatch_stream(const S& stream) {
    std::cout << "[Generic-Stream] Membaca stream secara chunk-by-chunk. Total: " 
              << stream.size() << " bytes.\n";
}

// Overload D: Men-subsume Overload C karena ContiguousByteStream mengimplikasikan ByteStreamSource
template <ContiguousByteStream S>
void dispatch_stream(const S& stream) {
    std::cout << "[Contiguous-Stream] Direct DMA / Zero-Copy transfer! Total: " 
              << stream.size() << " bytes.\n";
}

// Terse syntax (C++20 auto concept)
void inspect_data(const Serializable auto& item) {
    std::cout << "[Inspector] Tipe data tervalidasi sebagai Serializable.\n";
}

// Dummy structs untuk testing
struct NetworkPacket {
    std::vector<uint8_t> payload{0xDE, 0xAD, 0xBE, 0xEF};
    
    std::vector<uint8_t> serialize() const { return payload; }
    std::size_t serialized_size() const { return payload.size(); }
};

int main() {
    uint32_t raw_id = 0x12345678;
    NetworkPacket packet;

    // Overload selection berbasis tipe
    write_payload(raw_id);   // Memilih Overload A (TriviallySerializable)
    write_payload(packet);   // Memilih Overload B (CustomSerializable)
    
    inspect_data(raw_id);
    inspect_data(packet);

    // Pengujian Subsumption: std::vector memenuhi ContiguousByteStream
    struct SimpleStream {
        const uint8_t* data() const { return nullptr; }
        std::size_t size() const { return 0; }
    };

    SimpleStream non_contiguous;
    std::vector<uint8_t> contiguous_vec(1024, 0xFF);

    dispatch_stream(non_contiguous); // Memilih Overload C (ByteStreamSource)
    dispatch_stream(contiguous_vec); // Memilih Overload D (ContiguousByteStream - most constrained)

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Compiler Frontend
1. **Normal Form Reduction**: Saat mengevaluasi `requires`, kompilator mengubah ekspresi logika constraint ke dalam bentuk *Conjunctive Normal Form* (CNF) atau *Disjunctive Normal Form* (DNF). Ini dipecah menjadi **Atomic Constraints**.
2. **Subsumption Algorithm**: Kompilator memetakan atomic constraints dari dua kandidat fungsi overload:
   - Jika Constraint $A$ dinormalisasi menjadi elemen $P \land Q$, dan Constraint $B$ menjadi $P$, maka $A$ men-*subsume* $B$.
   - Syarat mutlak: kompilator harus mengidentifikasi atomic constraint sebagai ekspresi identik secara leksikal dan struktural (*identical expression tree*), bukan sekadar nilai runtime yang bernilai sama.
3. **Short-Circuit Evaluation**: Constraint dievaluasi dari kiri ke kanan. Jika suku pertama bernilai `false`, kompilator langsung menghentikan evaluasi tanpa memeriksa ekspresi berikutnya (mencegah error sintaksis pada cabang yang invalid).

#### Alokasi Memori / Resource
- **Zero Runtime Overhead**: Concepts murni abstraksi fase kompilasi (*compile-time construct*). Tidak ada *virtual dispatch*, tidak ada overhead *instruction pointer*, dan tidak ada jejak struktur metadata concept yang tersisa di biner ELF/PE.
- **Code Bloat Mitigation**: Berbeda dengan SFINAE yang sering kali menginstansiasi template parsial sebelum membatalkan substitusi, constraint dihentikan di level deklarasi, mereduksi alokasi memori internal kompilator (*AST node allocation*).

#### Trade-offs
| Aspek | C++20 Concepts | SFINAE (`std::enable_if`) | Tag Dispatching |
| :--- | :--- | :--- | :--- |
| **Parsing Latency** | Lebih Cepat (Dievaluasi di frontend) | Sangat Lambat (Banyak template instantiation) | Cepat |
| **Error Diagnostics** | Presisi tinggi (Kompilator menyebut klausul mana yang gagal) | Kriptik (Bisa menghasilkan error cascade ratusan baris) | Terfokus pada overload mismatch |
| **Refactoring** | Mudah (Modular dan reusable) | Rapuh (Perubahan signature merusak SFINAE) | Kaku (Membutuhkan wrapping tipe) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Standard Concepts**: Sebelum menulis konsep sendiri, gunakan pustaka bawaan `<concepts>` seperti `std::integral`, `std::floating_point`, `std::same_as`, `std::movable`, dll.
- **Dekomposisi Menjadi Atomic**: Pecah requirement besar menjadi concept-concept kecil yang atomik (`HasId`, `Encrypted`, `Transmittable`) agar kompilator dapat melakukan subsumption secara presisi.
- **Prioritaskan Terse Syntax**: Gunakan sintaks `void process(MyConcept auto x)` untuk kode yang lebih ringkas jika fungsi tidak memerlukan relasi antar-argumen tipe yang kompleks.

#### Don'ts
- **Hindari Ad-hoc Boolean pada Requires Clause**:
  ```cpp
  // SALAH: Menggunakan predikat boolean arbitrary merusak subsumption
  template <typename T> requires (sizeof(T) > 4)
  void execute(T);

  // BENAR: Bungkus dalam named concept
  template <typename T>
  concept LargeType = sizeof(T) > 4;

  template <LargeType T>
  void execute(T);
  ```
  Kompilator menganggap dua ekspresi `(sizeof(T) > 4)` di dua tempat berbeda sebagai atomik yang independen jika tidak dibungkus dalam *concept* bernama yang sama.

#### Edge Cases & Pitfalls
- **The "Requires Requires" Trap**:
  ```cpp
  // JEBAKAN SINTAKSIS:
  template <typename T>
  requires requires (T x) { x.run(); } // Sintaks valid tapi rawan salah paham!
  void start(T);
  ```
  Klausul pertama adalah *requires-clause* (kondisi), klausul kedua adalah *requires-expression* (evaluasi fitur tipe). Solusinya: bungkus selalu *requires-expression* ke dalam `concept`.
- **Ekspresi Non-dependent Terjebak Evaluasi Dini**: Jika suatu requirement di dalam concept tidak bergantung secara langsung pada parameter template tipe (`type-dependent`), kompilator dapat mengevaluasinya secara statis saat deklarasi, bukan saat instansiasi.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Subsumption Custom Smart Pointer**:
   Buat dua concept: `PointerLike<T>` (tipe yang bisa di-*dereference* via operator `*` dan `->`) dan `SmartPointer<T>` (memenuhi `PointerLike<T>` DAN memiliki method `.get()` yang mengembalikan raw pointer). Buat dua overload fungsi `release_resource` dan pastikan `SmartPointer` dipilih tanpa ambiguitas saat diberikan `std::unique_ptr`.
2. **Reverse Polish Concept Checker**:
   Rancang concept `ArithmeticStack<T>` yang memvalidasi bahwa sebuah tipe container memiliki method `push(val)`, `pop()`, dan elemen yang dikandungnya memenuhi `std::integral` atau `std::floating_point`. Verifikasi dengan `std::stack<int>` (berhasil) dan `std::stack<std::string>` (harus gagal di compile-time dengan pesan yang jelas).
