## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, manajemen siklus hidup objek (object lifecycle) dan sumber daya (resources seperti heap memory, file descriptors, socket, thread handle) diatur secara deterministik melalui idiom **RAII (Resource Acquisition Is Initialization)**. Ketika suatu objek membungkus *raw resource*, compiler membutuhkan instruksi eksplisit tentang bagaimana menduplikasi, memindahkan, atau memusnahkan objek tersebut.

Secara default, jika sebuah *class* tidak mendefinisikan operasi replikasi, compiler akan menggenerasi secara implisit:
1. **Destructor**
2. **Copy Constructor**
3. **Copy Assignment Operator (`operator=`)**

Implementasi default dari compiler menggunakan **Shallow Copy** (member-wise copy). Jika suatu atribut bertipe *primitive value* (seperti `int` atau `double`), nilainya disalin langsung bit-per-bit. Namun, jika atribut berupa *raw pointer* ke heap memory, yang tersalin hanyalah alamat memorinya (*pointer address*), bukan data yang ditunjuk. Hal ini menyebabkan dua objek menunjuk ke blok memori yang sama (*aliasing*), memicu bug fatal: **Double Free** saat destructor kedua objek dieksekusi, serta **Dangling Pointer**.

```
[Shallow Copy]
Objek A: [ dataPtr ] ──┐
                       ├──> Heap: [ Block: 0xDEADBEEF ]
Objek B: [ dataPtr ] ──┘     (Akan di-free 2x -> Undefined Behavior/Crash)

[Deep Copy]
Objek A: [ dataPtr ] ──> Heap: [ Block A: 0xDEADBEEF ]
Objek B: [ dataPtr ] ──> Heap: [ Block B: 0xCAFEFACE ] (Alokasi Baru)
```

Untuk mengatasi ini, diperkenalkan aturan arsitektural manajemen resource:

#### Rule of Three (C++03)
Jika sebuah kelas membutuhkan implementasi kustom dari salah satu fungsi berikut, kelas tersebut hampir pasti membutuhkan **ketiganya**:
1. **Destructor** (untuk dealokasi resource)
2. **Copy Constructor** (untuk alokasi baru dan deep copy saat inisialisasi)
3. **Copy Assignment Operator** (untuk dealokasi resource lama, alokasi baru, dan deep copy saat penugasan)

#### Rule of Five (C++11 ke atas)
Dengan diperkenalkannya *Rvalue Reference* dan *Move Semantics* pada C++11, Rule of Three diperluas untuk menghindari deep copy yang mahal ketika objek sumber adalah temporary (rvalue). Jika kelas Anda mengelola resource manual, definisikan ke-5 fungsi khusus (*Special Member Functions*):
1. **Destructor**
2. **Copy Constructor**
3. **Copy Assignment Operator**
4. **Move Constructor**
5. **Move Assignment Operator**

#### Rule of Zero
Desain modern C++ menganjurkan **Rule of Zero**: jangan menulis salah satu dari kelima fungsi di atas secara manual. Gunakan abstraksi STL tingkat tinggi yang sudah mengelola RAII sendiri (seperti `std::vector`, `std::string`, `std::unique_ptr`, `std::shared_ptr`). Kelas Anda cukup mengandalkan fungsi yang digenerasi otomatis oleh compiler.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi *generic buffer* berbasis Rule of Five menggunakan idiom industri modern yang paling aman dari segi *exception safety*: **Copy-and-Swap Idiom**.

```cpp
#include <iostream>
#include <utility>
#include <algorithm>
#include <cstddef>

class SafeBuffer {
private:
    std::size_t m_size;
    int* m_data;

public:
    // 1. Constructor Standar
    explicit SafeBuffer(std::size_t size = 0)
        : m_size(size), m_data(size ? new int[size]() : nullptr) {
        std::cout << "[CTOR] Alokasi " << m_size << " elemen di " << m_data << "\n";
    }

    // 2. Destructor
    ~SafeBuffer() noexcept {
        std::cout << "[DTOR] Dealokasi memori di " << m_data << "\n";
        delete[] m_data;
    }

    // 3. Copy Constructor (Deep Copy)
    SafeBuffer(const SafeBuffer& other)
        : m_size(other.m_size), m_data(other.m_size ? new int[other.m_size] : nullptr) {
        std::cout << "[COPY CTOR] Deep copying " << m_size << " elemen\n";
        std::copy(other.m_data, other.m_data + m_size, m_data);
    }

    // 4. Move Constructor (Resource Theft)
    // Wajib noexcept agar STL containers (seperti std::vector) menggunakannya saat reallokasi
    SafeBuffer(SafeBuffer&& other) noexcept
        : m_size(other.m_size), m_data(other.m_data) {
        std::cout << "[MOVE CTOR] Mencuri resource dari " << other.m_data << "\n";
        // Netralkan pointer sumber agar tidak ter-dealokasi di DTOR objek asal
        other.m_size = 0;
        other.m_data = nullptr;
    }

    // Fungsi swap non-throwing (ADL-friendly)
    friend void swap(SafeBuffer& first, SafeBuffer& second) noexcept {
        using std::swap;
        swap(first.m_size, second.m_size);
        swap(first.m_data, second.m_data);
    }

    // 5. Unified Assignment Operator (Copy-and-Swap Idiom)
    // Parameter di-pass by value:
    // - Jika rvalue diteruskan -> Move Constructor dipanggil
    // - Jika lvalue diteruskan -> Copy Constructor dipanggil
    SafeBuffer& operator=(SafeBuffer other) noexcept {
        std::cout << "[ASSIGNMENT] Swap state via copy-and-swap\n";
        swap(*this, other);
        return *this;
        // Objek 'other' yang memegang resource lama otomatis di-delete saat keluar scope
    }

    // Utilitas inspeksi
    std::size_t size() const noexcept { return m_size; }
    int* data() noexcept { return m_data; }
};

int main() {
    std::cout << "--- Inisialisasi Objek Asal ---\n";
    SafeBuffer buf1(5);
    buf1.data()[0] = 42;

    std::cout << "\n--- Uji Copy Constructor ---\n";
    SafeBuffer buf2 = buf1; // Memanggil Copy Constructor

    std::cout << "\n--- Uji Move Constructor ---\n";
    SafeBuffer buf3 = std::move(buf1); // Memanggil Move Constructor

    std::cout << "\n--- Uji Assignment Operator (Copy) ---\n";
    SafeBuffer buf4(2);
    buf4 = buf2; // Memanggil Copy-and-Swap (Copy path)

    std::cout << "\n--- Uji Assignment Operator (Move) ---\n";
    buf4 = std::move(buf3); // Memanggil Copy-and-Swap (Move path)

    std::cout << "\n--- Keluar dari Scope Main ---\n";
    return 0;
}
```

#### Penjelasan Komponen Kritis:
* **`noexcept` pada Move Operations**: Menandakan operasi pemindahan dijamin tidak melempar eksepsi. Tanpa penanda ini, container seperti `std::vector` akan menolak menggunakan move constructor saat melakukan `resize()`/`push_back()` dan mundur menggunakan *copy* demi menjaga *Strong Exception Guarantee*.
* **Unified `operator=(SafeBuffer other)`**: Menerima argumen *by-value*. Ini mengeliminasi duplikasi kode antara *Copy Assignment* dan *Move Assignment*, sekaligus menangani *self-assignment* (`a = a`) secara aman tanpa perlu `if (this != &other)`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
* **Copy Elision & RVO (Return Value Optimization)**: Sejak C++17, compiler **wajib** melakukan *guaranteed copy elision* pada nilai kembalian fungsi PRvalue (*Pure Rvalue*). Objek dibangun langsung pada ruang memori pemanggil (*caller stack frame*), melewati eksekusi copy atau move constructor seluruhnya:
  ```cpp
  SafeBuffer createBuffer() {
      return SafeBuffer(100); // Tidak ada copy/move yang dieksekusi di runtime
  }
  ```
* **Trivial vs Non-Trivial Special Members**: Jika sebuah tipe hanya berisi primitif tanpa destructor custom, compiler menganggapnya *Trivially Copyable*. Operasi copy akan dioptimasi menjadi instruksi CPU level rendah setara `memcpy()` atau register SIMD. Begitu destructor atau copy constructor kustom dideklarasikan, kelas menjadi *non-trivial*, memaksa compiler mengeksekusi *function prologue/epilogue* di setiap siklus copy.

#### Alokasi Memori & Pointer Aliasing
Pada arsitektur memori:
* Alokasi heap (`new[]`) membutuhkan overhead metadata alokator (*chunk header* untuk tracking ukuran blok yang dialokasikan, biasanya 8-16 bytes sebelum pointer yang dikembalikan).
* **Deep copy** memicu panggilan syscall alokator (`brk`/`mmap` melalui `malloc`). Jika dilakukan berulang kali, deep copy menyebabkan fragmentasi heap memory dan degradasi *cache locality*.
* **Move constructor** hanya menyalin pointer (8 byte pada sistem 64-bit) dan field ukuran, memodifikasi 2 word memory di stack, menjadikannya operasi dengan kompleksitas $\mathcal{O}(1)$ tanpa alokasi heap baru.

#### Trade-offs
| Pendekatan | Kelebihan | Kekurangan |
| :--- | :--- | :--- |
| **Manual Rule of Five** | Kontrol absolut atas alokasi level rendah (cocok untuk library/driver). | Rawan kebocoran memori (*leak*), exception safety kompleks, boilerplate tinggi. |
| **Copy-and-Swap** | Kuat terhadap eksepsi (*Strong Exception Guarantee*), kode ringkas. | Memiliki sedikit overhead konstruksi rvalue temporer pada assignment. |
| **Rule of Zero (STL/Smart Pointers)** | Kode bebas bug alokasi, dioptimasi otomatis oleh compiler, zero boilerplate. | Menyerahkan kontrol alokasi granular ke abstraksi library. |

### 4. Best Practices & Common Pitfalls

#### Do's
* **Prioritaskan Rule of Zero**: Gunakan `std::vector<int>` daripada `int*` atau `std::unique_ptr<T[]>` jika Anda hanya butuh dynamic array dengan lifecycle terikat objek.
* **Tandai Move Constructor & Move Assignment dengan `noexcept`**: Ini adalah prasyarat mutlak untuk efisiensi ekosistem STL.
* **Terapkan Copy-and-Swap**: Membantu mencapai *Strong Exception Guarantee* (jika alokasi gagal di tengah jalan, state objek lama tidak termodifikasi/rusak).

#### Don'ts
* **Jangan mengabaikan Self-Assignment pada assignment operator manual**:
  ```cpp
  // BAHAYA: Mengakibatkan undefined behavior jika 'this == &other'
  SafeBuffer& operator=(const SafeBuffer& other) {
      delete[] m_data; // Jika 'a = a', memory milik 'other' juga ikut terhapus di sini!
      m_data = new int[other.m_size]; // M_data membaca pointer yang sudah di-free!
      return *this;
  }
  ```
* **Jangan melempar eksepsi dari Destructor**: Destructor yang melempar exception saat terjadi *stack unwinding* akan langsung memicu `std::terminate()`.

#### Edge Cases
* **Exception di Tengah Alokasi**: Jika copy constructor menyalin banyak anggota dinamis dan anggota kedua melempar `std::bad_alloc`, anggota pertama akan bocor (*memory leak*) kecuali di-*wrap* dengan benar menggunakan RAII lokal atau blok `try-catch` fungsi (function-try-block).
* **Partial Move State**: Setelah sebuah objek di-*move*, objek tersebut berada dalam kondisi *"valid but unspecified state"*. Pastikan destructor objek asal tetap aman dieksekusi setelah dipindahkan (misalnya dengan mengeset pointer ke `nullptr`).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Generic Matrix dengan RAII**:
   Bangun kelas `Matrix` 2D berukuran dinamis ($M \times N$) tanpa menggunakan STL container. Terapkan **Rule of Five** secara lengkap. Buktikan melalui unit test atau assert bahwa operasi pemindahan (`std::move`) tidak mengalokasikan memori baru di heap.
2. **Investigasi Assembly Terhadap RVO**:
   Kompilasi sebuah program yang mengembalikan objek dengan Rule of Five menggunakan flag `-fno-elide-constructors` pada GCC/Clang, lalu bandingkan output log pemanggilan constructor-nya dengan kompilasi normal (C++17 default). Analisis perbedaan instruksi assembly-nya menggunakan [Compiler Explorer (godbolt.org)](https://godbolt.org).
3. **Refactoring ke Rule of Zero**:
   Ambil implementasi `SafeBuffer` di atas, lalu ubah arsitekturnya menjadi **Rule of Zero** menggunakan `std::unique_ptr<int[]>`. Amati bagaimana compiler secara otomatis melarang copy semantik yang tidak valid dan mempertahankan move semantik tanpa sebaris pun kode boiler-plate manual.
