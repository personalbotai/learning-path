### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur C++, tipe data bentukan pengguna didefinisikan menggunakan *keyword* `struct` atau `class`. Secara teknis dan menurut standar ISO C++, perbedaan sintaksis antara keduanya sangat minimal:

1. **Default Access Specifier**: Anggota (data member dan fungsi) dalam `struct` secara default bersifat `public`, sedangkan dalam `class` bersifat `private`.
2. **Default Inheritance Specifier**: Turunan (inheritance) dari sebuah `struct` secara default bersifat `public`, sedangkan `class` secara default bersifat `private`.

Di luar dua aturan di atas, kompiler memperlakukan `struct` dan `class` secara identik. Namun, dalam rekayasa perangkat lunak modern (termasuk rekomendasi *C++ Core Guidelines*), keduanya memiliki konvensi arsitektural yang berbeda secara filosofis:

```
+-------------------------------------------------------------------------+
|                              TIPE DATA                                  |
+------------------------------------+------------------------------------+
|               STRUCT               |               CLASS                |
|  Passive Data Structure / DTO      |   Active Domain Entity             |
|  - Tanpa Invariant Kompleks        |   - Menegakkan Class Invariant     |
|  - Akses Langsung (Public)         |   - State Terenkapsulasi (Private) |
|  - Trivial / Standard-Layout Data  |   - Validasi via Interface Publik  |
+------------------------------------+------------------------------------+
```

#### Memahami *Class Invariant*
*Class Invariant* (invarian kelas) adalah sekumpulan kondisi atau relasi logis antar data member yang **harus selalu bernilai benar (valid)** sepanjang siklus hidup objek tersebut:
- Dimulai tepat setelah proses konstruksi selesai (akhir dari *constructor*).
- Sebelum dan sesudah setiap pemanggilan fungsi anggota publik (*public member function*).
- Tepat sebelum destruksi objek dieksekusi.

Tanpa penegakan invarian, data berada dalam risiko korupsi internal (*invalid state*). Objek yang mengizinkan *state* tidak konsisten menciptakan fenomena *zombie object*—objek yang berhasil dibuat tetapi tidak berfungsi dengan benar dan rawan menghasilkan *undefined behavior* saat dieksekusi pada pipeline logika selanjutnya.

Enkapsulasi (`private` access) bukan sekadar menyembunyikan data untuk estetika, melainkan mekanisme untuk **mengisolasi batas invarian** (*invariant boundary*). Jika data member berstatus `public`, sembarang fungsi luar dapat merusak relasi logis internal tanpa validasi.

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi domain objek `DateRange` yang mengilustrasikan pemisahan antara `struct` (sebagai data murni/DTO tanpa invarian) dan `class` (yang menegakkan invarian bahwa `start_date` harus selalu $\le$ `end_date`).

```cpp
#include <iostream>
#include <chrono>
#include <stdexcept>
#include <format>
#include <compare>

// 1. STRUCT: Passive Data Record (No invariant, public access)
// Digunakan hanya sebagai agregat data tanpa logika validasi
struct DateRecord {
    std::chrono::year_month_day date;
    std::string metadata;
};

// 2. CLASS: Mengenkapsulasi state dan menegakkan Invariant
// Invariant: start_time <= end_time harus selalu benar.
class DateRange {
private:
    std::chrono::year_month_day start_;
    std::chrono::year_month_day end_;

    // Helper validasi internal untuk menegakkan invariant
    [[nodiscard]] static constexpr bool is_valid(
        const std::chrono::year_month_day& s, 
        const std::chrono::year_month_day& e) noexcept {
        return s.ok() && e.ok() && (s <= e);
    }

public:
    // Constructor: Menjamin objek hanya tercipta jika invariant terpenuhi.
    // Jika gagal, throw exception. Mengeliminasi konsep "zombie object".
    DateRange(std::chrono::year_month_day start, std::chrono::year_month_day end)
        : start_{start}, end_{end} {
        if (!is_valid(start_, end_)) {
            throw std::invalid_argument(
                "Invariant Violation: 'start' harus valid dan <= 'end'"
            );
        }
    }

    // Modern C++20: Defaulted three-way comparison operator (Spaceship)
    auto operator<=>(const DateRange&) const = default;

    // Getter memberikan read-only access (const-correctness)
    [[nodiscard]] constexpr std::chrono::year_month_day start() const noexcept { 
        return start_; 
    }
    
    [[nodiscard]] constexpr std::chrono::year_month_day end() const noexcept { 
        return end_; 
    }

    // Mutator: Invariant harus dicek sebelum mutasi commit ke internal state
    void update_range(std::chrono::year_month_day new_start, 
                      std::chrono::year_month_day new_end) {
        if (!is_valid(new_start, new_end)) {
            throw std::invalid_argument("Invariant Violation pada update_range");
        }
        // Strong Exception Safety: state hanya diubah bila validasi sukses
        start_ = new_start;
        end_ = new_end;
    }

    [[nodiscard]] std::chrono::days duration() const noexcept {
        const auto sys_start = std::chrono::sys_days{start_};
        const auto sys_end = std::chrono::sys_days{end_};
        return sys_end - sys_start;
    }
};

int main() {
    using namespace std::chrono;

    try {
        // Pembuatan struct pasif
        DateRecord record{ 2026y / March / 15d, "Deployment Target" };
        std::cout << "Log Struct: " << record.metadata << "\n";

        // Pembuatan class dengan penegakan invariant sukses
        DateRange valid_range{ 2026y / January / 1d, 2026y / December / 31d };
        std::cout << std::format("Durasi: {} hari\n", valid_range.duration().count());

        // Mencoba melanggar class invariant
        std::cout << "Mencoba membuat range tidak valid...\n";
        DateRange invalid_range{ 2026y / December / 31d, 2026y / January / 1d };

    } catch (const std::invalid_argument& ex) {
        std::cerr << "Caught Exception: " << ex.what() << "\n";
    }

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Metode Sebagai Fungsi Bebas**: Di tingkat instruksi mesin, *member function* tidak disimpan di dalam memori objek. Kompiler mentransformasikan pemanggilan `obj.update_range(a, b)` menjadi fungsi non-anggota biasa dengan pointer implisit:
  $$\text{DateRange\_update\_range}(\&obj, a, b)$$
  Parameter pertama adalah register yang memuat pointer `this` (biasanya register `RDI` atau `RCX` pada arsitektur x86-64 System V / MSVC ABI).

#### Alokasi Memori & Padding
Bentuk *struct* dan *class* tunduk pada aturan *alignment* tipe data primitif yang menyusunnya. Kompiler menyisipkan *padding bytes* untuk menyelaraskan alamat memori ke kelipatan ukuran word CPU (misalnya 4 atau 8 byte):

```cpp
struct BadLayout {
    uint8_t a;  // 1 byte
    // [Padding: 7 bytes disisipkan di sini oleh compiler]
    uint64_t b; // 8 bytes (harus berada pada memory address kelipatan 8)
    uint32_t c; // 4 bytes
    // [Tail Padding: 4 bytes untuk menutup kelipatan 8 dari total struct]
}; // Total ukuran = 24 bytes

struct GoodLayout {
    uint64_t b; // 8 bytes
    uint32_t c; // 4 bytes
    uint8_t a;  // 1 byte
    // [Tail Padding: 3 bytes disisipkan]
}; // Total ukuran = 16 bytes (Menghemat 33% memory footprint)
```

Gunakan *compiler attribute* atau susun data member secara menurun berdasarkan ukurannya untuk meminimalkan *cache line pollution*.

#### Standar Tata Letak (Standard Layout)
Sebuah tipe data dianggap **Standard-Layout** jika:
- Tidak memiliki fungsi virtual atau virtual base class.
- Memiliki kontrol akses (`public`/`private`/`protected`) yang sama untuk semua non-static data member.
- Menempatkan semua non-static data member pada kelas yang sama dalam hierarki inheritance.

Jika kondisi ini terpenuhi, tata letak memori C++ kompatibel dengan representasi memori bahasa C murni (*C ABI layout*), memungkinkan transmisi data melintasi batasan modul via `memcpy` tanpa risiko *undefined behavior*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan RAII (Resource Acquisition Is Initialization)**: Inisialisasi dan verifikasi invarian seluruhnya di dalam *constructor*. Jika invariant gagal, gagalkan pembuatan objek dengan melempar *exception*.
- **Inisialisasi Menggunakan Member Initializer List**: Hindari inisialisasi di dalam badan konstruktor. Member initializer list menginisialisasi variabel langsung di tempat alokasi memori, bukan membuat nilai *default* lalu menimpanya (*assignment*).
- **Berikan Qualifier `[[nodiscard]]`**: Pasang atribut ini pada fungsi getter untuk mencegah bug di mana developer memanggil accessor tanpa menggunakan nilainya.
- **Konsep Const-Correctness**: Tandai semua *member function* yang tidak mengubah state internal dengan keyword `const`.

#### Don'ts
- **Hindari Two-Phase Initialization**: Pola di mana objek dibuat kosong lalu dipanggil `obj.init(...)` adalah pemicu bug utama dalam C++. Pola ini melahirkan *zombie state* di antara selang waktu pembuatan dan inisialisasi.
- **Jangan Me-return Non-const Reference ke Private State**:
  ```cpp
  // ANTI-PATTERN: Merusak invarian secara tidak langsung
  class Account {
      int balance_{0};
  public:
      int& get_balance() { return balance_; } // BENCANA: Pihak luar bisa menulis balance_ = -9999
  };
  ```
- **Hindari Public Data Member pada Objek Ber-invariant**: Begitu data member dibuka ke publik, Anda kehilangan kendali atas invariant kelas secara permanen.

#### Edge Cases
- **Pengecualian dalam Constructor (Throwing Constructors)**: Jika *constructor* melempar exception di tengah jalan, destruktor dari objek tersebut **tidak akan pernah dipanggil**. Namun, destruktor dari data member yang sudah selesai dibangun sebelum exception dilempar *tetap akan dieksekusi* secara otomatis. Pastikan resource mentah dibungkus dengan smart pointer sebelum memasuki badan konstruktor.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Padding dengan ABI Inspection**:
   Buatlah sebuah `struct` yang memiliki tipe data campur: `char`, `double`, `int16_t`, `bool`, dan `void*`. Gunakan operator `sizeof()`, `alignof()`, dan macro `offsetof()` (dari header `<cstddef>`) untuk memetakan alamat memori tiap member secara presisi. Tata ulang urutannya hingga menghasilkan ukuran memori paling minimum.

2. **Refactoring Zombie Object**:
   Temukan pola *two-phase initialization* atau implementasikan kelas `BoundedBuffer` yang menerima kapasitas maksimum integer $(N > 0)$. Terapkan proteksi invariant penuh sehingga objek buffer tidak pernah bisa berada dalam status `capacity <= 0`, baik saat instansiasi maupun saat operasi *resizing*. Jelaskan bagaimana penanganan alokasi memori buffer jika terjadi error di tengah proses konstruksi.
