## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Secara historis, C++ memiliki dua paradigma utama dalam penanganan error: **Exceptions** (pengecualian) dan **Error Codes** (kode error via *return value* atau *out-parameter*). Keduanya memiliki kelemahan fundamental:
- *Exceptions* memicu *stack unwinding* yang sangat mahal secara performa, memecah *control flow*, dan melanggar prinsip *zero-overhead abstraction* pada *sad path* (jalur error).
- *Error codes* membuat *signature* fungsi menjadi kotor (membutuhkan pointer/referensi untuk mengembalikan nilai asli) dan mudah diabaikan oleh developer.

Untuk mengatasi ini, C++ modern mengadopsi konsep tipe data aljabar (*algebraic data types* / *sum types*) yang terinspirasi dari bahasa fungsional (seperti Haskell) dan Rust.

1. **`std::optional<T>` (C++17)**: Merepresentasikan sebuah nilai yang **mungkin ada atau tidak ada**. Secara semantik, ini digunakan ketika ketiadaan nilai bukanlah sebuah "error" yang butuh penjelasan, melainkan sebuah state yang valid (misal: mencari elemen dalam *hash map* yang ternyata tidak ada).
2. **`std::expected<T, E>` (C++23)**: Merepresentasikan sebuah nilai sukses bertipe `T`, atau sebuah nilai error bertipe `E`. Ini adalah implementasi standar dari pola `Result` atau `Either`. `std::expected` memaksa developer untuk menangani error secara eksplisit di level *type system* tanpa *overhead* dari exceptions.

Keduanya kini mendukung **Monadic Operations** (seperti `and_then`, `transform`, `or_else`) di C++23, memungkinkan *chaining* operasi secara elegan tanpa blok `if-else` yang bersarang (*pyramid of doom*).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi modern menggunakan C++23 yang mendemonstrasikan *parsing* data dengan `std::optional` dan validasi bisnis dengan `std::expected`.

```cpp
#include <iostream>
#include <string>
#include <optional>
#include <expected>
#include <charconv>

// Enum untuk mendefinisikan jenis error secara spesifik
enum class ParseError {
    InvalidFormat,
    OutOfRange,
    EmptyInput
};

// Fungsi 1: Menggunakan std::optional karena ketiadaan domain adalah state yang valid
std::optional<std::string> extract_domain(const std::string& email) {
    auto pos = email.find('@');
    if (pos == std::string::npos || pos == email.length() - 1) {
        return std::nullopt; // Tidak ada domain
    }
    return email.substr(pos + 1);
}

// Fungsi 2: Menggunakan std::expected karena kegagalan parsing butuh alasan spesifik
std::expected<int, ParseError> parse_port(const std::string& port_str) {
    if (port_str.empty()) {
        return std::unexpected(ParseError::EmptyInput);
    }

    int port = 0;
    auto [ptr, ec] = std::from_chars(port_str.data(), port_str.data() + port_str.size(), port);
    
    if (ec == std::errc::invalid_argument) {
        return std::unexpected(ParseError::InvalidFormat);
    }
    if (ec == std::errc::result_out_of_range || port < 1 || port > 65535) {
        return std::unexpected(ParseError::OutOfRange);
    }

    return port; // Implicit conversion ke std::expected<int, ParseError>
}

// Fungsi 3: Demonstrasi Monadic Operations (C++23)
std::expected<std::string, ParseError> process_network_config(const std::string& input) {
    return parse_port(input)
        // transform: dieksekusi jika parse_port SUKSES. Mengubah T menjadi tipe lain.
        .transform([](int port) {
            return "Port configured to: " + std::to_string(port);
        })
        // or_else: dieksekusi jika parse_port GAGAL. Bisa digunakan untuk fallback/recovery.
        .or_else([](ParseError err) -> std::expected<std::string, ParseError> {
            if (err == ParseError::EmptyInput) {
                return "Default Port: 8080"; // Fallback sukses
            }
            return std::unexpected(err); // Teruskan error lainnya
        });
}

int main() {
    // Test std::optional
    auto domain = extract_domain("user@cpp.org");
    // Menggunakan value_or untuk memberikan nilai default jika nullopt
    std::cout << "Domain: " << domain.value_or("unknown") << "\n";

    // Test std::expected dengan Monadic Chaining
    auto result1 = process_network_config("80");
    if (result1.has_value()) {
        std::cout << "Success: " << *result1 << "\n";
    }

    auto result2 = process_network_config("999999"); // OutOfRange
    if (!result2.has_value()) {
        std::cout << "Failed with error code: " << static_cast<int>(result2.error()) << "\n";
    }

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Baik `std::optional` maupun `std::expected` tidak menggunakan *heap allocation* (kecuali tipe `T` atau `E` di dalamnya mengalokasikan memori, seperti `std::string`). Keduanya dieksekusi murni di *stack* dan di-resolve pada saat *compile-time*. Tidak ada *stack unwinding* atau intervensi OS/Runtime seperti pada C++ Exceptions, sehingga *control flow* sangat *predictable* dan ramah terhadap *branch predictor* CPU.
- **Alokasi Memori / Resource**:
  Secara internal, `std::expected<T, E>` diimplementasikan sebagai *Tagged Union* (mirip `std::variant`). Strukturnya kira-kira berisi `union { T val; E err; }` ditambah sebuah `bool has_value`. 
  *Perhatian pada Padding:* Ukuran `std::optional<int>` (4 bytes untuk int + 1 byte untuk bool) biasanya akan menjadi **8 bytes** karena *memory alignment*. Ini adalah *trade-off* ruang memori demi kecepatan akses.
- **Trade-offs**:
  Dibandingkan dengan *Exceptions*, `std::expected` menambah ukuran memori dari *return type* (karena harus memuat ukuran maksimum antara `T` dan `E` ditambah *flag*). Pada *happy path* (selalu sukses), *Exceptions* memiliki *zero-size overhead* di *return type*, namun `std::expected` jauh lebih cepat pada *sad path* (saat error terjadi).

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `std::optional` jika "tidak ada hasil" adalah hal yang wajar dan pemanggil fungsi tidak peduli *mengapa* hasilnya tidak ada.
  - Gunakan `std::expected` jika kegagalan memiliki berbagai alasan yang harus direspons secara berbeda oleh pemanggil fungsi.
  - Manfaatkan operasi monadik (`and_then`, `transform`, `or_else`) di C++23 untuk menghindari blok `if (!result.has_value())` yang berulang-ulang.
- **Don'ts**:
  - **JANGAN** menggunakan `.value()` tanpa mengecek `.has_value()` terlebih dahulu. Jika kosong, ini akan melempar exception `std::bad_optional_access` atau `std::bad_expected_access`, yang justru mengembalikan Anda ke masalah performa exception. Gunakan `operator*` atau `operator->` jika Anda sudah yakin (via `if`), atau gunakan `.value_or()`.
  - Jangan gunakan `std::expected` untuk *fatal errors* (seperti kehabisan memori atau *out-of-bounds array access*). Biarkan program *crash* atau gunakan exception untuk *unrecoverable errors*.
- **Edge Cases**:
  - **References**: `std::optional<T&>` dan `std::expected<T&, E>` **tidak diizinkan** dalam standar C++ saat ini karena ambiguitas semantik *assignment*. Jika Anda perlu mengembalikan referensi, gunakan `std::optional<std::reference_wrapper<T>>` atau cukup gunakan *pointer* biasa (`T*`).
