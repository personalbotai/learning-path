### 1. Konsep & Arsitektur Mendalam

Secara formal, C++ tidak memiliki kata kunci `interface` seperti Java atau C#. Sebagai gantinya, C++ mengimplementasikan konsep *interface* menggunakan **Abstract Base Class (ABC)**—kelas yang memiliki setidaknya satu *pure virtual function* (`virtual void foo() = 0;`).

```
                +-------------------------+
                |    <<interface>>        |
                |       ILogger           |
                +-------------------------+
                | + log(string_view) = 0  |
                | + ~ILogger() = default  |
                +-------------------------+
                             ^
                             | (implements)
        +--------------------+--------------------+
        |                                         |
+-----------------------+               +-----------------------+
|     ConsoleLogger     |               |      FileLogger       |
+-----------------------+               +-----------------------+
| + log(string_view)    |               | + log(string_view)    |
| - m_colorCode: int    |               | - m_fileStream: ofst. |
+-----------------------+               +-----------------------+
```

#### Alasan Keberadaan & Problem yang Diselesaikan
Tanpa interface abstrak, modul perangkat lunak mengalami *tight coupling* (keterikatan kuat pada kelas konkret). Jika Kelas A secara langsung memanggil instansiasi Kelas B, modifikasi pada Kelas B atau penggantian dengan Kelas C akan merusak Kelas A.

Interface abstrak memfasilitasi dua prinsip inti SOLID:
1. **Dependency Inversion Principle (DIP)**: Modul tingkat tinggi tidak boleh bergantung pada modul tingkat rendah. Keduanya harus bergantung pada abstraksi.
2. **Liskov Substitution Principle (LSP)**: Objek turunan harus dapat menggantikan objek dasar tanpa merusak invariant atau kebenaran logis program.

#### Dynamic Polymorphism (Subtype Polymorphism)
C++ mengimplementasikan polimorfisme dinamis melalui *late binding* (resolusi alamat fungsi pada saat *runtime*). Ketika sebuah metode dipanggil melalui pointer atau referensi bertipe interface, program menavigasi struktur internal objek konkret untuk menentukan implementasi fungsi yang sesuai, melepaskan keterikatan kompilasi ke kode biner tertentu.

### 2. Implementasi & Contoh Kasus Nyata

Kasus berikut mendemonstrasikan sistem pengiriman notifikasi (*notification pipeline*) yang menggunakan dynamic polymorphism berbasis *Dependency Injection* menggunakan Modern C++ (C++17/20).

```cpp
#include <iostream>
#include <memory>
#include <string_view>
#include <vector>

// 1. Interface Definisi (Murni Abstrak)
class INotificationService {
public:
    // Destructor virtual WAJIB ada untuk polymorphic base class
    virtual ~INotificationService() = default;

    // Pure virtual function mendefinisikan kontrak interface
    virtual void send(std::string_view recipient, std::string_view message) = 0;
    
    // Interface murni sebaiknya menghapus operasi copy/move untuk mencegah slicing
    INotificationService() = default;
    INotificationService(const INotificationService&) = delete;
    INotificationService& operator=(const INotificationService&) = delete;
    INotificationService(INotificationService&&) = delete;
    INotificationService& operator=(INotificationService&&) = delete;
};

// 2. Implementasi Konkret A
class EmailService final : public INotificationService {
public:
    explicit EmailService(std::string smtpServer) 
        : m_smtpServer(std::move(smtpServer)) {}

    void send(std::string_view recipient, std::string_view message) override {
        std::cout << "[SMTP: " << m_smtpServer << "] Mengirim Email ke " 
                  << recipient << " | Isi: " << message << '\n';
    }

private:
    std::string m_smtpServer;
};

// 3. Implementasi Konkret B
class PushNotificationService final : public INotificationService {
public:
    explicit PushNotificationService(std::string appId) 
        : m_appId(std::move(appId)) {}

    void send(std::string_view recipient, std::string_view message) override {
        std::cout << "[AppID: " << m_appId << "] Mengirim Push Notification ke Device " 
                  << recipient << " | Isi: " << message << '\n';
    }

private:
    std::string m_appId;
};

// 4. Modul Konsumen Tingkat Tinggi (Tergantung Abstraksi)
class AlertSystem {
public:
    // Dependency Injection melalui pointer abstract
    void registerService(std::unique_ptr<INotificationService> service) {
        m_services.push_back(std::move(service));
    }

    void broadcast(std::string_view target, std::string_view alertMessage) const {
        for (const auto& service : m_services) {
            // Polymorphic dispatch terjadi di sini
            service->send(target, alertMessage);
        }
    }

private:
    std::vector<std::unique_ptr<INotificationService>> m_services;
};

int main() {
    AlertSystem alertSystem;

    // Injeksi dependensi konkrete dibungkus dalam abstraksi INotificationService
    alertSystem.registerService(std::make_unique<EmailService>("smtp.internal.corp"));
    alertSystem.registerService(std::make_unique<PushNotificationService>("APP-XYZ-99"));

    // Menjalankan operasi tanpa mengetahui tipe konkret di baliknya
    alertSystem.broadcast("User_Admin", "Kritis: Penggunaan RAM melebihi 90%!");

    return 0;
}
```

#### Penjelasan Komponen Kunci:
- **`virtual ~INotificationService() = default;`**: Menjamin bahwa ketika objek dihapus lewat pointer base (`std::unique_ptr<INotificationService>`), destructor kelas turunan (`EmailService`) terpanggil dengan benar.
- **`override` Keyword**: Memberikan instruksi kepada compiler untuk memverifikasi kesamaan signature dengan basis fungsi di ABC; kegagalan signature memicu error saat kompilasi.
- **`final` Specifier**: Mengoptimalkan compiler agar dapat melakukan *devirtualization* jika instansi diketahui secara lokal dan mencegah subclassing lebih lanjut.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Dynamic Dispatch: Vtable & Vptr
Ketika kelas memiliki setidaknya satu fungsi `virtual`, compiler menginjeksi mekanisme khusus ke dalam binary:

```
Object InMemory Layout (EmailService Instance):
+-----------------------+
|  __vptr               | ------>  Vtable (EmailService) [Read-Only Data]
+-----------------------+          +-----------------------------------------+
|  m_smtpServer (data)  |          | [0]: EmailService::~EmailService()      |
+-----------------------+          | [1]: EmailService::send(str_view, ...)  |
                                   +-----------------------------------------+
```

1. **Vtable (Virtual Method Table)**: Struktur array statis yang dibuat oleh compiler per-kelas pada segment memori read-only (`.rodata`). Berisi pointer langsung ke alamat instruksi fungsi virtual yang telah di-override.
2. **Vptr (Virtual Table Pointer)**: Setiap instansiasi kelas menyematkan pointer tersembunyi berukuran 8 byte (pada arsitektur 64-bit) di offset `0` objek, menunjuk ke Vtable kelasnya.

#### Eksekusi Saat Runtime
Pemanggilan `service->send(...)` diterjemahkan oleh compiler menjadi instruksi assembly indireksi:
```assembly
mov rax, QWORD PTR [rdi]        ; Ambil pointer vtable dari objek (vptr)
mov rax, QWORD PTR [rax + 8]    ; Ambil alamat fungsi send() pada offset index vtable
call rax                        ; Panggil fungsi secara tak langsung (indirect call)
```

#### Memory & Performance Trade-offs
- **Overhead Ukuran Objek**: Setiap instansi bertambah sebesar `sizeof(void*)` (8 byte pada 64-bit) karena injeksi `vptr`.
- **Latency Eksekusi**: Terjadi *double indirection* (mengambil `vptr`, kemudian mengambil entry fungsi di vtable).
- **CPU Cache Miss**: Alamat fungsi yang dipanggil ditentukan saat runtime, sehingga instruksi berpotensi tidak berada di CPU L1 Instruction Cache.
- **Inhibition of Inlining**: Compiler tidak dapat melakukan inline ekspansi terhadap `virtual function call`, membatasi optimasi loop dan dead-code elimination (kecuali compiler berhasil melakukan *speculative devirtualization*).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Virtual Destructor di Basis**: Selalu sediakan `virtual ~Interface() = default;` pada interface atau deklarasikan destructor sebagai `protected non-virtual` jika kelas basis tidak dimaksudkan untuk dihapus secara polymorphic.
- **Terapkan Keyword `override`**: Wajib pada setiap fungsi turunan untuk menangkap bug kesalahan tipe parameter atau *const-qualification mismatch*.
- **Pass By Reference/Pointer**: Selalu lewatkan interface sebagai `const Interface&`, `Interface*`, atau smart pointer (`std::unique_ptr<Interface>`).

#### Don'ts
- **Dilarang Object Slicing**: Jangan pernah menerima interface atau polymorphic base class *by-value*.
  ```cpp
  // CRITICAL BUG: Object Slicing
  void process(INotificationService service); // Error kompilasi jika ABC murni, 
                                              // atau data terpotong jika class non-pure base!
  ```
- **Dilarang Memanggil Virtual Function di Constructor / Destructor**: Pada saat eksekusi constructor base class, vptr masih mengarah ke vtable milik *base class*, bukan *derived class*. Dynamic dispatch tidak bekerja di sini (resolusi dilakukan statis ke implementasi lokal, atau crash murni via `__cxa_pure_virtual`).

#### Edge Cases: Multiple Inheritance & Pointer Adjustment
Jika kelas turunan mengimplementasikan lebih dari satu interface:
```cpp
class Device : public ISerializable, public ILoggable { ... };
```
Objek `Device` akan memiliki **dua** vptr:
1. `vptr_ISerializable` pada offset `0`
2. `vptr_ILoggable` pada offset `8` (atau setelah data `ISerializable`)

Ketika pointer `Device*` di-cast secara implisit ke `ILoggable*`, compiler melakukan **Pointer Adjustment (Thunk / `this` fixup)** dengan menambahkan offset memori tertentu:
$$\text{Addr}(ILoggable) = \text{Addr}(Device) + \text{sizeof}(ISerializable)$$
Jika menggunakan `reinterpret_cast` alih-alih `static_cast` pada skenario ini, pointer akan menunjuk ke vptr yang salah dan langsung memicu *undefined behavior* / *segmentation fault*.

### 5. Tantangan Eksplorasi Mandiri

1. **Eksplorasi Memory Alignment & Vptr Injection**:
   Tulis program kecil yang mencetak `sizeof()` dari:
   - Kelas kosong (`class Empty {}`)
   - Kelas dengan fungsi biasa (`class NonVirt { void foo(); }`)
   - Kelas dengan fungsi virtual (`class Virt { virtual void foo(); }`)
   Jelaskan mengapa ukurannya berbeda drastis pada sistem 64-bit Anda.

2. **Analisis Pure Virtual Crash**:
   Ciptakan skenario di mana sebuah pure virtual function secara tidak sengaja dipanggil dari rantai constructor via indirect call (misal: constructor memanggil fungsi non-virtual `init()`, dan `init()` memanggil pure virtual method). Amati pesan kesalahan runtime yang dihasilkan compiler (seperti `pure virtual method called` atau `__cxa_pure_virtual`).

3. **Benchmarking Devirtualization**:
   Gunakan flag compiler `-O3` dan bandingkan performa pemanggilan fungsi melalui *interface pointer* vs pemanggilan fungsi kelas konkret via `template` (Static Polymorphism / CRTP) sebanyak $10^8$ iterasi loop. Analisis assembly yang dihasilkan menggunakan Compiler Explorer (godbolt.org).
