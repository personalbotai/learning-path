## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, siklus hidup sebuah entitas memori diatur secara ketat oleh dua konsep fundamental: **Initialization** (inisialisasi) dan **Object Lifetime** (masa hidup objek). Berbeda dengan bahasa berbasis *Garbage Collector* (GC) seperti Java atau Go, C++ memberikan kontrol deterministik atas kapan memori dialokasikan, kapan konstruktor dipanggil, dan kapan destruktor membersihkan sumber daya.

#### Object Lifetime: Alokasi vs Inisialisasi
Masa hidup sebuah objek bukanlah sinonim dari durasi alokasi memorinya. Masa hidup objek adalah jendela waktu di mana objek tersebut dianggap *valid* oleh runtime C++:
1. **Masa hidup dimulai** saat proses inisialisasi (eksekusi konstruktor) selesai secara sukses tanpa melempar eksepsi.
2. **Masa hidup berakhir** saat pemanggilan destruktor dimulai.

Jika sebuah konstruktor melempar eksepsi di tengah jalan, masa hidup objek tersebut **tidak pernah dimulai**. Konsekuensinya, destruktor objek tersebut tidak akan pernah dipanggil oleh runtime—hanya sub-objek (anggota dan *base class*) yang sudah selesai dikonstruksi yang akan dibersihkan via *stack unwinding*.

```
[ Alokasi Memori ] 
       │
       ▼
[ Konstruksi/Inisialisasi ] ──(Gagal/Exception)──> [ Unwinding Sub-objek & Deallokasi ]
       │ (Sukses)
       ▼
┌─────────────────────────┐
│   OBJECT LIFETIME       │ <── Objek berada dalam state valid & operasional
└─────────────────────────┘
       │
       ▼
[ Destruksi (Destructor)  ]
       │
       ▼
[ Deallokasi Memori       ]
```

#### Taksonomi Storage Duration
C++ mendefinisikan 4 jenis *storage duration* yang menentukan kapan memori dialokasikan dan dideallokasikan:
* **Automatic**: Objek lokal di dalam fungsi atau blok scope (`{}`). Dialokasikan di stack, dihancurkan secara LIFO (Last-In, First-Out) saat eksekusi keluar dari scope penampung.
* **Static**: Variabel global, `namespace` scope, atau ditandai `static`. Dialokasikan di segmen data BSS/Data sebelum `main()` berjalan dan dihancurkan setelah `main()` selesai.
* **Thread-local**: Dideklarasikan dengan `thread_local`. Terikat pada siklus hidup *thread* yang membuatnya.
* **Dynamic**: Dialokasikan manual via `new` / `malloc` di area heap. Masa hidupnya sepenuhnya dikendalikan oleh programmer sampai `delete` atau `free` dipanggil.

#### Ragam Bentuk Inisialisasi
C++ memiliki sejarah sintaks inisialisasi yang kompleks:
* **Default Initialization**: `int x;` atau `MyClass obj;`. Untuk tipe primitif di stack, nilainya adalah *indeterminate* (sampah memori).
* **Value Initialization**: `int x{};` atau `int x = int();`. Tipe primitif dijamin bernilai nol (*zero-initialized*).
* **Direct vs Copy Initialization**: `MyClass a(b);` (direct) vs `MyClass a = b;` (copy).
* **Direct-list-initialization / Uniform Initialization (C++11)**: Menggunakan kurung kurawal `{}` (e.g., `int x{42};`). Bentuk ini mencegah **narrowing conversions** (misal: mengonversi `double` ke `int` tanpa sengaja) dan memecahkan ambiguitas parsing compiler (**Most Vexing Parse**).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah demonstrasi deterministik dari siklus hidup objek, bahaya *uninitialized value*, urutan destruksi LIFO, dan implementasi modern *aggregate initialization* (C++20).

```cpp
#include <iostream>
#include <string>
#include <string_view>

class Tracker {
public:
    explicit Tracker(std::string_view name) : m_name(name) {
        std::cout << "[Constructed] " << m_name << " at " << this << '\n';
    }

    ~Tracker() {
        std::cout << "[Destructed ] " << m_name << " at " << this << '\n';
    }

    // Disable copy untuk memastikan trace merefleksikan lifetime murni
    Tracker(const Tracker&) = delete;
    Tracker& operator=(const Tracker&) = delete;

private:
    std::string m_name;
};

// C++20 Aggregate Initialization
struct ServerConfig {
    std::string host{"127.0.0.1"};
    uint16_t port{8080};
    bool use_tls{false};
    size_t max_connections{1000};
};

void run_lifecycle_demonstration() {
    std::cout << "--- Memulai Scope run_lifecycle_demonstration ---\n";
    
    Tracker first{"Object A (Stack First)"};
    Tracker second{"Object B (Stack Second)"};

    {
        std::cout << "  -- Memasuki Inner Scope --\n";
        Tracker inner{"Object C (Inner Scope)"};
        
        // C++20 Designated Initializers: Jelas, eksplisit, dan aman
        ServerConfig config{
            .host = "api.internal.net",
            .port = 443,
            .use_tls = true
            // max_connections fallback ke default value: 1000
        };
        
        std::cout << "  Config Server: " << config.host << ":" << config.port 
                  << " (TLS: " << (config.use_tls ? "ON" : "OFF") << ")\n";
        std::cout << "  -- Keluar Inner Scope --\n";
    } // inner dihancurkan di sini

    std::cout << "--- Mengakhiri run_lifecycle_demonstration ---\n";
} // second, lalu first dihancurkan di sini (LIFO order)

int main() {
    // 1. Primitive Uninitialized (UB Hazard) vs Value Initialized
    int garbage_val; // Indeterminate value (BACA: BISA CRASH/SECURITY LEAK)
    int safe_val{};  // Zero-initialized (safe_val == 0)

    // 2. Uniform Initialization mencegah Narrowing
    long double high_precision = 3.14159265358979323846L;
    // int truncated{high_precision}; // COMPILE ERROR: Narrowing conversion!
    int explicit_truncated = static_cast<int>(high_precision); // OK: Sengaja

    (void)garbage_val;
    (void)safe_val;
    (void)explicit_truncated;

    // 3. Demonstrasi Lifetime & Destructor Order
    run_lifecycle_demonstration();

    return 0;
}
```

#### Komponen Kunci Kode:
1. `Tracker::Tracker` dan `Tracker::~Tracker`: Mencatat visualisasi masa hidup objek dan alamat memorinya di stack.
2. `ServerConfig`: Menunjukkan *Aggregate Initialization* dengan *Designated Initializers* (C++20). Pola ini menggantikan pola *Builder* yang berat untuk konfigurasi murni data POD (*Plain Old Data*).
3. Evaluasi *Scope Exit*: Perhatikan bahwa objek di dalam inner block dihancurkan tepat sebelum tanda kurung kurawal tutup `}` dari blok tersebut dieksekusi.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Pemanggilan Konstruktor & Destruktor
Secara level instruksi (assembly), objek pada stack tidak dialokasikan satu per satu dengan instruksi terpisah. Kompiler menghitung total ukuran kebutuhan stack untuk sebuah fungsi, lalu memindahkan penunjuk stack (*stack pointer*) sekaligus di prolog fungsi:

```assembly
# x86-64 SysV ABI
sub rsp, 64       # Mengalokasikan seluruh frame stack fungsi secara instan
lea rdi, [rbp-32] # Memuat alamat 'first' ke register argumen pertama (this pointer)
call Tracker::Tracker(std::string_view)
```

Saat alur program keluar dari blok:
* Kompiler menyisipkan instruksi `call Tracker::~Tracker()` secara implisit tepat sebelum instruksi jump atau return.
* Jika fungsi keluar akibat eksepsi (*abnormal termination*), **Exception Handling Tables** (format DWARF pada Linux atau SEH pada Windows) memetakan *instruction pointer* (`RIP`) saat ini ke tabel *Landing Pad*. Runtime C++ membaca tabel ini dan mengeksekusi destruktor dari objek-objek yang sudah valid secara mundur (*Stack Unwinding*).

#### Alokasi Memori: Static vs Automatic
* Objek `static` disimpan di segmen data:
  * Variabel static dengan inisialisasi nol masuk ke segmen `.bss`.
  * Variabel static dengan inisialisasi nilai tetap masuk ke segmen `.data`.
  * Objek static dengan konstruktor non-trivial ditangani menggunakan fungsi wrapper internal compiler (seperti `__cxx_global_var_init`) yang didaftarkan ke array fungsi inisialisasi `.init_array`.
* Objek `automatic` berada di segmen *Stack*. Tidak ada overhead alokasi dinamis; alokasi dan dealokasi memori berbiaya zero-runtime-cost (hanya manipulasi register `RSP`).

#### Trade-offs: List Initialization `{}` vs Direct Initialization `()`
Penggunaan uniform initialization `{}` memiliki satu ambiguitas kritis: **prioritas mutlak `std::initializer_list`**.
```cpp
std::vector<int> v1(10, 2); // 10 elemen, masing-masing bernilai 2
std::vector<int> v2{10, 2}; // 2 elemen, bernilai 10 dan 2!
```
Jika sebuah kelas memiliki konstruktor yang menerima `std::initializer_list<T>`, kompiler akan memprioritaskan pemanggilan konstruktor tersebut di atas konstruktor lain yang cocok ketika kurung kurawal `{}` digunakan.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Selalu Inisialisasi Variabel Primitif**: Jangan pernah membiarkan tipe dasar (`int`, `float`, *pointer*) berstatus uninitialized. Gunakan `{}` untuk memastikan *zero-initialization* jika nilainya belum diketahui saat deklarasi:
  ```cpp
  int* ptr{nullptr};
  uint32_t counter{0};
  ```
* **Manfaatkan RAII (Resource Acquisition Is Initialization)**: Ikat siklus hidup sumber daya (file descriptor, socket, mutex, heap memory) ke dalam masa hidup objek lokal stack via class wrapper seperti `std::unique_ptr` atau `std::lock_guard`.
* **Gunakan Member Initializer List**: Inisialisasi variabel anggota kelas pada konstruktor via *initializer list*, bukan di dalam *body* konstruktor, untuk menghindari konstruksi ganda (*default construction* diikuti *assignment*).

#### Don'ts
* **The "Most Vexing Parse"**:
  ```cpp
  class DatabaseClient { ... };
  // PITFALL: Baris berikut BUKAN inisialisasi objek, melainkan deklarasi fungsi 
  // bernama 'client' yang tidak menerima parameter dan me-return DatabaseClient!
  DatabaseClient client(); 

  // FIX:
  DatabaseClient client{}; // Uniform initialization
  // atau
  DatabaseClient client;   // Default initialization
  ```
* **Static Initialization Order Fiasco**: Objek `static` non-lokal yang berada di unit translasi (file `.cpp`) berbeda memiliki urutan inisialisasi yang **tidak terdefinisi** (*undefined*). Jika objek statis di `file_a.cpp` menggunakan objek statis di `file_b.cpp` dalam konstruktornya, ini dapat memicu *crash* karena mengakses memori yang belum diinisialisasi.
* **Membocorkan Pointer yang Mengikat Objek Temporary**:
  ```cpp
  const std::string& str = std::string("temporary"); // Legal: Lifetime diperpanjang ke ref
  const char* raw = std::string("temporary").c_str(); // FATAL BUG: Dangling pointer!
  // Objek std::string temporary dihancurkan di akhir full-expression baris ini.
  // 'raw' sekarang menunjuk ke memori yang sudah hangus (Dangling).
  ```

1. **Analisis Assembly via Compiler Explorer**:
   Salin kode kelas `Tracker` di atas ke [Godbolt Compiler Explorer](https://godbolt.org/) menggunakan compiler `x86-64 GCC -O0` lalu bandingkan dengan `-O2`. Identifikasi baris assembly instruksi `call` konstruktor dan destruktor, lalu amati bagaimana compiler mengoptimalkan destruktor yang bersifat *trivial*.

2. **Memecahkan Static Initialization Order Fiasco**:
   Buat dua class independen: `Logger` dan `NetworkManager`. Buat instance `static Logger g_logger;` di satu file `.cpp` dan `static NetworkManager g_network;` di file `.cpp` lain, di mana konstruktor `NetworkManager` langsung memanggil metode `g_logger.log()`. 
   * Uji gejalanya saat kompilasi acak.
   * Perbaiki masalah ini secara definitif menggunakan teknik **Construct-On-First-Use Idiom** (pola Meyer's Singleton berbasis lokal `static` reference).
