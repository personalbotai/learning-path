## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

#### Masalah Pembuatan Thread secara Ad-Hoc
Di C++, memanggil `std::thread t(func)` secara naif untuk setiap unit pekerjaan (*task*) adalah anti-pattern dalam sistem berskala produksi. Setiap pembuatan thread level OS (`pthread_create` di POSIX atau `CreateThread` di Windows) memiliki overhead signifikan:
1. **Alokasi Sumber Daya Kernel**: Pembuatan struktur data kernel (Task Control Block/Thread Environment Block).
2. **Alokasi Virtual Memory**: Setiap thread membutuhkan call stack sendiri (biasanya 1 MB hingga 8 MB secara default).
3. **Context Switch Overhead**: Terlalu banyak thread aktif melebihi jumlah logical core CPU menyebabkan thrashing—CPU menghabiskan lebih banyak siklus waktu untuk menyimpan dan memulihkan register/stack pointers daripada mengeksekusi instruksi aplikasi.

#### Arsitektur Thread Pool
Thread Pool menyelesaikan masalah ini dengan mendaur ulang sejumlah *worker threads* yang telah dialokasikan di awal (*pre-allocated*). Pola arsitekturnya mengadopsi pola **Producer-Consumer multi-threaded**:

```
[Producers: Main / Business Logic]
        |
        | enqueue(Task) -> std::packaged_task / std::function
        v
+------------------------------------------+
| Thread-Safe Task Queue                   |
| (std::queue<Task> + Mutex + Cond_Var)    |
+------------------------------------------+
        |                 |               |
        | pop()           | pop()         | pop()
        v                 v               v
 [Worker Thread 1] [Worker Thread 2] [Worker Thread N]
 (pinned/reused)   (pinned/reused)   (pinned/reused)
```

Komponen utama:
- **Task Queue**: Antrean *FIFO* thread-safe yang menyimpan tugas eksekusi (biasanya diabstraksi sebagai callable objects `std::function<void()>`).
- **Worker Threads**: Kumpulan `std::thread` atau `std::jthread` (C++20) yang menunggu sinyal dari *Condition Variable* ketika antrean tidak kosong.
- **Synchronization Primitives**: `std::mutex` menjaga integritas antrean dari modifikasi serentak; `std::condition_variable` mengatur sleep/wake-up worker threads untuk menghindari busy-waiting (100% CPU utilization).

---

#### Anatomi Deadlock dan Kondisi Coffman
Deadlock adalah kondisi di mana dua atau lebih eksekusi thread terhenti permanen karena masing-masing saling menunggu sumber daya yang dipegang oleh thread lain. Deadlock secara matematis hanya dapat terjadi jika **keempat kondisi Coffman** terpenuhi secara simultan:

1. **Mutual Exclusion**: Sumber daya bersifat non-shareable; hanya satu thread yang dapat memegang resource (misal: `std::mutex`).
2. **Hold and Wait**: Sebuah thread sedang memegang minimal satu resource dan meminta resource baru yang sedang ditahan oleh thread lain.
3. **No Preemption**: Resource tidak bisa dipaksa lepas dari thread; hanya pemilik yang bisa melepaskannya secara sukarela.
4. **Circular Wait**: Terdapat rantai tertutup thread $\{T_1, T_2, ..., T_n\}$ sedemikian rupa sehingga $T_1$ menunggu resource milik $T_2$, $T_2$ menunggu $T_3$, ..., dan $T_n$ menunggu resource milik $T_1$.

**Solusi Modern C++**: Mencegah *Circular Wait* dan *Hold and Wait* menggunakan `std::scoped_lock` (C++17) yang menerapkan algoritma *deadlock-avoidance* (seperti algoritma *resource hierarchy* atau *two-phase locking / back-off* tanpa busy-wait).

---

#### Concurrency Pitfalls Tingkat Lanjut

- **Livelock**: Kondisi ketika state dari thread terus berubah merespons thread lain, tetapi tidak ada progres logis yang tercapai (misal: kedua thread saling melepaskan resource saat tabrakan dan mencoba kembali di siklus waktu yang identik).
- **Starvation**: Sebuah thread tidak pernah mendapatkan akses ke resource yang dibutuhkan karena thread lain memiliki prioritas tidak seimbang atau antrean tidak adil (*unfair scheduling*).
- **False Sharing**: Dua thread yang berjalan di core CPU berbeda memodifikasi variabel independen yang secara fisik berada dalam **satu Cache Line CPU yang sama** (biasanya 64 byte). CPU cache coherence protocol (MESI/MOESI) mematikan (*invalidate*) cache line tersebut bolak-balik antar-core, merusak throughput concurrency secara drastis.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi **Modern C++17 Thread Pool** yang fleksibel. Desain ini menggunakan `std::future` untuk mengembalikan nilai secara asinkron dan menerima callable object arbitrer dengan variadic templates.

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <future>
#include <functional>
#include <type_traits>

class ThreadPool {
public:
    explicit ThreadPool(size_t num_threads = std::thread::hardware_concurrency()) 
        : stop(false) 
    {
        workers.reserve(num_threads);
        for (size_t i = 0; i < num_threads; ++i) {
            workers.emplace_back([this]() {
                this->worker_loop();
            });
        }
    }

    // Submit task arbitrer dan dapatkan std::future hasil return-nya
    template <typename F, typename... Args>
    auto enqueue(F&& f, Args&&... args) 
        -> std::future<std::invoke_result_t<F, Args...>> 
    {
        using return_type = std::invoke_result_t<F, Args...>;

        // Bungkus task ke packaged_task yang dibagikan via shared_ptr
        // Memungkinkan task disalin ke std::function<void()>
        auto task = std::make_shared<std::packaged_task<return_type()>>(
            [func = std::forward<F>(f), 
             capture_args = std::make_tuple(std::forward<Args>(args)...)]() mutable {
                return std::apply(std::move(func), std::move(capture_args));
            }
        );

        std::future<return_type> res = task->get_future();
        {
            std::unique_lock<std::mutex> lock(queue_mutex);
            if (stop) {
                throw std::runtime_error("enqueue dipanggil pada ThreadPool yang telah berhenti!");
            }

            tasks.emplace([task]() {
                (*task)();
            });
        }
        cv.notify_one();
        return res;
    }

    ~ThreadPool() {
        {
            std::unique_lock<std::mutex> lock(queue_mutex);
            stop = true;
        }
        cv.notify_all();
        for (std::thread& worker : workers) {
            if (worker.joinable()) {
                worker.join();
            }
        }
    }

    // Mencegah Copy dan Move semantics
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;
    ThreadPool(ThreadPool&&) = delete;
    ThreadPool& operator=(ThreadPool&&) = delete;

private:
    std::vector<std::thread> workers;
    std::queue<std::function<void()>> tasks;

    std::mutex queue_mutex;
    std::condition_variable cv;
    bool stop;

    void worker_loop() {
        while (true) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lock(this->queue_mutex);
                this->cv.wait(lock, [this]() {
                    return this->stop || !this->tasks.empty();
                });

                if (this->stop && this->tasks.empty()) {
                    return; // Terminasi worker
                }

                task = std::move(this->tasks.front());
                this->tasks.pop();
            }
            // Jalankan task di luar critical section queue_mutex!
            task();
        }
    }
};

// Simulasi Transfer Bank: Demonstrasi Pencegahan Deadlock
struct Account {
    int id;
    int balance;
    std::mutex mtx;

    Account(int id, int balance) : id(id), balance(balance) {}
};

// Solusi Deadlock: Menggunakan std::scoped_lock (C++17)
void safe_transfer(Account& from, Account& to, int amount) {
    if (&from == &to) return; // Menghindari self-locking

    // std::scoped_lock mengunci banyak mutex secara atomik menggunakan 
    // algoritma pencegahan deadlock (mirip std::lock)
    std::scoped_lock lock(from.mtx, to.mtx);

    if (from.balance >= amount) {
        from.balance -= amount;
        to.balance += amount;
        std::cout << "[Tx Success] Transfer " << amount 
                  << " dari ID:" << from.id << " ke ID:" << to.id << "\n";
    }
}

int main() {
    ThreadPool pool(4);
    Account acc1(101, 1000);
    Account acc2(102, 1000);

    std::vector<std::future<void>> futures;

    // Menjalankan transaksi bolak-balik secara konkruen
    for (int i = 0; i < 5; ++i) {
        futures.push_back(pool.enqueue(safe_transfer, std::ref(acc1), std::ref(acc2), 50));
        futures.push_back(pool.enqueue(safe_transfer, std::ref(acc2), std::ref(acc1), 30));
    }

    // Mengambil hasil komputasi fungsi dengan return value
    auto future_calc = pool.enqueue([](int a, int b) {
        std::this_thread::sleep_for(std::chrono::milliseconds(50));
        return a * b;
    }, 6, 7);

    std::cout << "Hasil Kalkulasi Paralel: " << future_calc.get() << "\n";

    for (auto& f : futures) {
        f.get();
    }

    std::cout << "Final Saldo 101: " << acc1.balance 
              << ", Final Saldo 102: " << acc2.balance << "\n";

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Condition Variable Spurious Wakeups
Di dalam loop worker, perhatikan idiom berikut:
```cpp
this->cv.wait(lock, [this]() {
    return this->stop || !this->tasks.empty();
});
```
Fungsi `wait` tidak boleh dieksekusi menggunakan kondisi *if* sederhana. Di level OS/POSIX kernel, thread dapat terbangun tanpa ada panggilan `signal` atau `broadcast`—fenomena ini disebut **Spurious Wakeup**. Predikat lambda bertindak sebagai loop `while (!predicate()) { wait(); }` internal yang memastikan thread hanya melanjutkan eksekusi jika invarian sistem terpenuhi.

#### Alokasi Memori / Resource: Task Erasure Overhead
Tipe callable object diabstraksi menggunakan `std::function<void()>`. Di balik layar:
- `std::function` menggunakan teknik **Type Erasure**.
- Objek yang di-bind bersama capture-nya (seperti closure objek lambda) disimpan di dalamnya.
- Jika ukuran closure melampaui buffer internal implementasi Standard Library (ambang batas *Small Buffer Optimization* / SBO, biasanya sekitar 16–32 byte), `std::function` akan memicu **alokasi heap (`operator new`)**.
- Jika performa alokasi menjadi *bottleneck* absolut, antrean harus diganti menjadi *ring buffer lock-free* dengan ukuran task yang tetap (*fixed-size callable memory buffer*).

#### False Sharing dan Cache Coherence (L1/L2/L3)
Ketika thread mengeksekusi operasi paralel pada data berdampingan:
```cpp
struct BadCounters {
    uint64_t a; // Core 0 sering menulis ke 'a'
    uint64_t b; // Core 1 sering menulis ke 'b'
}; // Keduanya berada dalam 1 cache line 64-byte
```
Meskipun core 0 dan core 1 mengakses field yang berbeda, protokol hardware (seperti MESI) harus menandai baris cache L1/L2 core lain sebagai *Invalidated* setiap kali salah satu variabel dimodifikasi. Data harus dimuat ulang dari L3 cache atau RAM, menyebabkan lonjakan latensi memori drastis. 

Solusinya adalah memastikan alignment terhadap cache-line:
```cpp
struct alignas(hardware_destructive_interference_size) GoodCounter {
    uint64_t val;
};
```

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan RAII Lock Wrappers**: Selalu gunakan `std::scoped_lock` (multi-mutex, C++17) atau `std::unique_lock` / `std::lock_guard` (single-mutex). Mutex tidak boleh dilepas secara manual via `.unlock()` karena rawan kebocoran lock jika terjadi exception.
- **Minimalkan Critical Section Scope**: Kunci mutex hanya saat memodifikasi data bersama. Jangan pernah memanggil operasi I/O (seperti `std::cout`, query database, atau panggilan network) di dalam mutex lock jika tidak mutlak diperlukan.
- **Ketahui Kapasitas Hardware**: Tentukan pool size default berdasarkan `std::thread::hardware_concurrency()`. Menetapkan ratusan worker pada CPU 4 core hanya akan memicu degradasi performa akibat *scheduler thrashing*.

#### Don'ts
- **Hindari Nested Locking Manual**: 
  ```cpp
  // RAWAN DEADLOCK!
  // Thread 1:
  mtx_a.lock(); mtx_b.lock();
  // Thread 2:
  mtx_b.lock(); mtx_a.lock();
  ```
- **Hindari Detached Threads**: Jangan gunakan `t.detach()` kecuali untuk daemon proses yang dijamin *self-contained*. Detached thread menyulitkan shutdown yang bersih dan dapat menyebabkan *undefined behavior* jika mengakses objek statik/global yang telah dihancurkan oleh main thread runtime.
- **Jangan Memegang Mutex saat Memanggil External Callbacks**: Ini membuka peluang *inversion of control* di mana thread luar mencoba mengakuisisi lock yang sama dari konteks callback, memicu deadlock tak terduga (*alien method deadlock*).

#### Edge Cases
- **Destruction Race pada Thread Pool**: Destruktor Thread Pool harus secara eksplisit memberi sinyal `stop = true`, menyiarkan notifikasi (`notify_all()`), dan melakukan `.join()` pada **seluruh** worker thread. Membiarkan objek thread dihancurkan saat statusnya masih `.joinable()` akan langsung memicu pemanggilan `std::terminate()`.
- **Exception dalam Worker Loop**: Jika sebuah task melemparkan unhandled exception di luar `std::packaged_task`, seluruh aplikasi akan crash. Setiap task callable harus dieksekusi dalam blok *try-catch* jika tidak dibungkus oleh abstraksi future.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Prioritized Task Queue**:
   Modifikasi antrean pada `ThreadPool` di atas dari `std::queue` standar menjadi `std::priority_queue`. Rancang struct `PriorityTask` yang memungkinkan pengguna mengirim task dengan label prioritas (High, Medium, Low), dan buktikan bahwa worker mengeksekusi task prioritas tinggi terlebih dahulu meskipun di-enqueue belakangan.

2. **Deteksi dan Simulasi False Sharing Benchmark**:
   Buat program benchmark yang menggunakan 2 thread. Thread 1 menginkrementasi array index `[0]`, thread 2 menginkrementasi index `[1]`. Bandingkan waktu eksekusinya dengan skenario kedua di mana index `[0]` dan index `[1]` dipisahkan padding sebesar `alignas(64)`. Ukur perbedaan throughput menggunakan *Google Benchmark* atau `std::chrono::high_resolution_clock`.

3. **Work-Stealing Algorithm (Advanced)**:
   Pelajari arsitektur *Work-Stealing Thread Pool* (seperti yang digunakan di Go Runtime, TBB, atau Tokio di Rust). Alih-alih memiliki satu global queue terpusat yang rentan terhadap perebutan mutex (*mutex contention*), rancang arsitektur di mana setiap worker thread memiliki antrean lokal sendiri (menggunakan `std::deque`), dan hanya mencuri (*steal*) task dari antrean worker lain saat antrean miliknya kosong.
