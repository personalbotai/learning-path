### 1. Konsep & Arsitektur Mendalam

Sejak C++ diperkenalkan pada era 1980-an, model kompilasinya diwarisi langsung dari bahasa C: **Textual Inclusion** via preprocessor directive `#include`. Dalam model ini, preprocessor secara naif menyalin isi header file ke dalam Translation Unit (TU) target. Konsekuensinya:
1. **Compilation Overhead O(N × M)**: Jika $N$ buah translation unit mengikutsertakan header yang sama sebanyak $M$ kali, compiler mem-parsing AST (*Abstract Syntax Tree*) header tersebut berulang kali sebanyak $N \times M$. Solusi parsial seperti *Precompiled Headers* (PCH) bersifat monolitik, rapuh terhadap urutan include, dan tidak portabel antar-compiler.
2. **Macro Leakage & ODR Hazards**: Makro yang didefinisikan dalam sebuah header bocor ke seluruh TU yang menyertakannya, menyebabkan polusi namespace, modifikasi token tak terduga, dan potensi pelanggaran *One Definition Rule* (ODR).

```
Model Tradisional:
[header.h] ---> (Preprocessed Copy) ---> [TU_1.cpp] => Compiler Parsing AST
            ---> (Preprocessed Copy) ---> [TU_2.cpp] => Compiler Parsing AST

Model C++20 Modules:
[engine.ixx] ---> [Compiler Frontend] ---> [Binary Module Interface (.pcm / .ifc)]
                                                   |
              +------------------------------------+
              v
[TU_consumer.cpp] (On-demand AST deserialization, O(1) parsing overhead)
```

#### Paradigma C++20 Modules
C++20 Modules merevolusi sistem ini dengan memperkenalkan batasan isolasi semantik:
- **Binary Module Interface (BMI)**: Compiler mem-parsing file interface modul (`.cppm` / `.ixx`) sekali saja, lalu menyimpannya dalam format biner perantara (misalnya `.pcm` di Clang, `.ifc` di MSVC). File konsumen modul hanya memuat representasi semantik biner ini (*deserialization*), bukan teks mentah.
- **Hygiene & Macro Isolation**: Simbol makro di dalam modul **tidak** diekspor secara default ke konsumen, dan makro di luar modul tidak dapat memodifikasi logika internal modul.
- **Dependency Graph Statis**: Hubungan dependensi antar-modul bersifat eksplisit (`import module_name;`), memungkinkan sistem build membentuk Directed Acyclic Graph (DAG) yang deterministik sebelum fase kompilasi TU dimulai.

#### Arsitektur Build System & CI
Pada model `#include`, sistem build dapat mengompilasi semua file `.cpp` secara paralel karena dependensi header dicek secara implisit saat kompilasi. 
Pada C++20 Modules, tercipta **Dependensi Urutan Kompilasi**: Jika `main.cpp` mengimpor `telemetry`, maka BMI dari `telemetry` harus dikompilasi terlebih dahulu.

Untuk mengatasi ini, komite ISO C++ merancang **P1689R5** (*Format for describing graph of dependencies*). Build system modern (CMake $\ge$ 3.28 bersama Ninja $\ge$ 1.11) melakukan fase *Dynamic Dependency Scanning* dua tahap:
1. **Scanning Step**: Toolchain memindai semua file modul untuk mengekstraksi relasi `import` dan `export module`.
2. **DAG Generation & Compilation**: Ninja menyusun ulang urutan build berdasarkan DAG yang dihasilkan dan mengeksekusi kompilasi BMI, lalu implementasi, dan terakhir *linking*.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan sistem sub-komponen telemetry modular menggunakan C++20 Modules dan konfigurasi CMake modern berstandar industri.

#### Struktur Proyek
```text
telemetry_system/
├── CMakeLists.txt
├── src/
│   ├── telemetry.cppm          // Primary Module Interface
│   ├── telemetry_core.cppm     // Internal Module Partition
│   ├── telemetry_impl.cpp      // Module Implementation Unit
│   └── main.cpp                // Consumer TU
```

#### File: `src/telemetry_core.cppm` (Module Partition)
```cpp
// Menandai file ini sebagai modul internal partition :core
module; // Global Module Fragment (untuk menyertakan header C legacy jika mutlak diperlukan)
#include <cstdint>

export module telemetry:core;

namespace Telemetry::Internal {
    // Tipe data ini diekspor ke partisi lain dari modul yang sama
    export struct MetricPayload {
        std::uint64_t timestamp;
        double value;
        const char* tag;
    };

    export double Normalize(double raw_val) noexcept {
        return raw_val > 0.0 ? raw_val : 0.0;
    }
}
```

#### File: `src/telemetry.cppm` (Primary Module Interface Unit)
```cpp
export module telemetry;

// Mengimpor dan mengekspor ulang partisi :core
export import :core;

import <string_view>; // Standard library module unit (C++23) atau header unit (C++20)
import <vector>;

export namespace Telemetry {
    class MetricsPipeline {
    public:
        void Record(std::string_view tag, double value);
        [[nodiscard]] std::size_t Count() const noexcept;
        void Flush();

    private:
        std::vector<Internal::MetricPayload> buffer_;
    };
}
```

#### File: `src/telemetry_impl.cpp` (Module Implementation Unit)
```cpp
// Unit implementasi: Memisahkan deklarasi dari implementasi agar modifikasi
// pada logic tidak memicu recompilation cascade pada konsumen modul telemetry.
module telemetry;

import <iostream>;
import <chrono>;

namespace Telemetry {
    void MetricsPipeline::Record(std::string_view tag, double value) {
        auto now = std::chrono::system_clock::now().time_since_epoch();
        auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(now).count();

        buffer_.push_back(Internal::MetricPayload{
            .timestamp = static_cast<std::uint64_t>(ms),
            .value = Internal::Normalize(value),
            .tag = tag.data()
        });
    }

    std::size_t MetricsPipeline::Count() const noexcept {
        return buffer_.size();
    }

    void MetricsPipeline::Flush() {
        for (const auto& metric : buffer_) {
            std::cout << "[" << metric.timestamp << "] " 
                      << metric.tag << " : " << metric.value << '\n';
        }
        buffer_.clear();
    }
}
```

#### File: `src/main.cpp` (Consumer)
```cpp
import telemetry;
import <iostream>;

int main() {
    Telemetry::MetricsPipeline pipeline;
    pipeline.Record("cpu_usage", 42.5);
    pipeline.Record("memory_rss_mb", -12.0); // Akan dinormalisasi ke 0.0

    std::cout << "Recorded metrics count: " << pipeline.Count() << '\n';
    pipeline.Flush();

    return 0;
}
```

#### File: `CMakeLists.txt` (CMake 3.28+ C++20 Module Native Support)
```cmake
cmake_minimum_required(VERSION 3.28)
project(Cpp20ModulesArchitecture CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# Export compile commands untuk Language Server Protocol (Clangd)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

add_library(telemetry_engine)

# Konfigurasi C++20 File Sets untuk modules
target_sources(telemetry_engine
    PUBLIC
        FILE_SET CXX_MODULES FILES
            src/telemetry_core.cppm
            src/telemetry.cppm
    PRIVATE
        src/telemetry_impl.cpp
)

add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE telemetry_engine)
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Dynamic Dependency Scanning & P1689R5
Pada eksekusi `cmake --build .`, Ninja tidak bisa langsung mengeksekusi compiler worker thread secara random. Generator menjalankan *scanner phase*:
1. Compiler dipanggil dengan flag pemindai dependensi modul (misal: `-M` atau `-fscan-sources` pada Clang).
2. Compiler membaca struktur token tanpa mem-parsing seluruh semantic TU, lalu mengeluarkan file JSON berformat P1689R5:
   ```json
   {
     "rules": [{
       "primary-output": "telemetry.pcm",
       "provides": [{"logical-name": "telemetry"}],
       "requires": [{"logical-name": "telemetry:core"}]
     }]
   }
   ```
3. Ninja membaca output JSON ini dan secara runtime menyisipkan *edges* dependensi baru ke dalam build graph:
   $$\text{telemetry:core.pcm} \longrightarrow \text{telemetry.pcm} \longrightarrow \text{telemetry\_impl.o} \land \text{main.o}$$

#### Alokasi Memori & Disk Footprint: AST Deserialization vs Macro Preprocessing
- **Macro-based `#include`**: Compiler menduplikasi token stream ke RAM. Untuk `#include <vector>` di 10 TU berbeda, compiler mengalokasikan dan membuang jutaan node AST identik di memori.
- **BMI Generation**: Frontend compiler serialisasi representasi AST (termasuk symbol table, template instantiation tree dasar, visibility linkage) ke disk dalam bentuk bitstream terindeks.
- **Consumption (`import`)**: Compiler menggunakan teknik *Demand-Driven Deserialization*. Simbol yang tidak digunakan dari modul tidak pernah dinaikkan ke memori heap compiler; compiler hanya membaca offset byte spesifik dari BMI menggunakan *memory-mapped files* (`mmap`).

#### Trade-offs: Throughput vs Rigidity
- **Clean Build vs Incremental Build**: Clean build C++20 modules seringkali lebih lambat dibandingkan model `#include` tanpa PCH karena serialisasi graf dependensi memangkas paralelisasi murni di fase awal. Sebaliknya, incremental build menjadi eksponensial lebih cepat karena perubahan internal pada file `telemetry_impl.cpp` sama sekali tidak memicu kompilasi ulang `main.cpp`.
- **BMI Brittleness**: File BMI terikat erat secara biner dengan:
  - Versi compiler mikro (patch level).
  - Flags compiler (`-O3`, `-DDEBUG`, target CPU ISA). Perbedaan sekecil apa pun membatalkan kompatibilitas BMI.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Pisahkan Interface (`.cppm`) dan Implementasi (`.cpp`)**: Gunakan *Module Implementation Units* untuk menyembunyikan definisi fungsi non-inline/non-template. Ini mencegah modifikasi logika fungsi internal merusak checksum BMI, sehingga TU konsumen tidak perlu di-compile ulang.
- **Manfaatkan Global Module Fragment untuk Legacy Headers**: Jika terpaksa menyertakan third-party library berbasis C/C++ tua yang mengandalkan macro, letakkan secara ketat di antara deklarasi `module;` dan `export module <name>;`.
  ```cpp
  module;
  #include <openssl/ssl.h> // Makro OpenSSL terkarantina di sini
  export module crypto_service;
  ```
- **Gunakan CMake `FILE_SET CXX_MODULES`**: Jangan mencoba memanipulasi flag kompilator manual (`-fmodules-ts`, `/experimental:module`). Gunakan abstraksi formal CMake 3.28+.

#### Don'ts
- **Circular Imports**: Modul A tidak boleh mengimpor Modul B jika Modul B mengimpor Modul A (baik secara langsung maupun transitif via partisi). Sistem build akan mendeteksi siklus ini pada fase scan dan menghentikan build seketika (*deadlock prevention*).
- **Mengekspor Entitas Internal Tanpa Namespace**: Selalu bungkus kode dalam `namespace`. Modul mengontrol *visibility* (apakah suatu simbol terlihat oleh TU lain), tetapi **tidak** mengubah *linkage resolution* atau mencegah tabrakan nama simbol global.
- **Mendistribusikan Library C++ dalam Format BMI Mentah**: Jangan pernah mendistribusikan library komersial hanya sebagai file `.pcm` atau `.ifc`. Distribusikan sebagai source code modules lengkap dengan build tool configuration, karena BMI tidak memiliki ABI/AST portability guarantee antar-kompiler.

#### Edge Cases: Global Fragment Macro Injection
Jika Anda menaruh `#include` di dalam scope modul utama:
```cpp
// SALAH:
export module logger;
#include <windows.h> // FATAL: Mengotori global module linkage!

// BENAR:
module;
#include <windows.h> // Terisolasi dalam Global Module Fragment
export module logger;
```
Menyertakan header di luar Global Module Fragment akan menyebabkan isi header tersebut dievaluasi di dalam ownership modul bersangkutan, mengakibatkan ODR violations instan ketika modul lain menyertakan header yang sama via `#include`.

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Legacy Codebase**:
   Ambil program C++ multi-file berbasis `#include` guard tradisional yang Anda miliki. Ubah arsitekturnya menjadi arsitektur Modular C++20:
   - Pecah menjadi 1 Primary Interface Unit (`.cppm`) dan minimal 2 Partitions (`:network`, `:parser`).
   - Ukur perbedaan durasi *incremental build* saat Anda hanya mengubah badan fungsi di unit implementasi (`.cpp`). Gunakan flag `ninja -t trace` atau `/Bt` pada MSVC.
2. **CI Pipeline dengan C++20 Dependency Scanning**:
   Rancang pipeline GitHub Actions menggunakan runner `ubuntu-24.04` dengan `clang-18`, `cmake >= 3.28`, dan `ninja-build`.
   - Konfigurasikan cache untuk compiler ccache/sccache. Analisis: Mengapa caching BMI di CI lebih rumit dibanding caching `.o` tradisional? Tulis skrip CI yang mampu memvalidasi kegagalan parsing dependensi sirkular secara otomatis.
