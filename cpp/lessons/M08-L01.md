## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum standarisasi C++11, penulisan program multithreading di C++ sangat bergantung pada API native sistem operasi: POSIX Threads (`pthread`) di ekosistem UNIX/Linux atau Win32 Threads di lingkungan Windows. Hal ini menghasilkan basis kode yang non-portabel dan rentan terhadap inkonsistensi memory model.

C++11 memperkenalkan standardisasi multithreading dengan menambahkan model memori sadar-konkurensi (*concurrency-aware memory model*) dan membungkus abstraksi thread tingkat sistem operasi ke dalam kelas `std::thread` (didefinisikan dalam header `<thread>`).

```
+-------------------------------------------------------------------+
|                        User Space (C++)                          |
|  [ std::thread obj ] ------> State: Joinable / Non-Joinable       |
|          |                                                        |
|  (libstdc++ / libc++) Mengalokasikan heap invoker & argument tuple |
+----------|--------------------------------------------------------+
           | pthread_create() / CreateThread()
+----------v--------------------------------------------------------+
|                        Kernel Space (OS)                          |
|  [ Task / Thread Descriptor (TCB) ]                               |
|  ├── User Stack (default: ~8MB Linux, ~1MB Win32)                 |
|  ├── Register Context (RIP, RSP, RAX, dll.)                       |
|  └── Scheduled by OS Preemptive Scheduler                         |
+-------------------------------------------------------------------+
```

#### Pemetaan 1:1 (One-to-One Threading Model)
Di balik layar, mayoritas implementasi `std::thread` pada sistem operasi modern mengadopsi model *1:1 mapping*. Artinya, satu objek `std::thread` yang aktif berkorespondensi langsung dengan satu entitas penjadwalan kernel (Kernel-level Thread atau lightweight process via `clone(2)` di Linux dengan flag `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND`).

#### State Machine: Joinable vs Non-Joinable
Sebuah objek `std::thread` berada dalam salah satu dari dua status representasional:
1. **Joinable**: Thread terikat (*attached*) ke konteks eksekusi aktif di level OS. Status ini bernilai `true` sejak konstruksi berhasil sampai thread tersebut di-`join()` atau di-`detach()`. Thread yang fungsinya telah selesai dieksekusi namun belum di-`join` tetap berstatus **joinable**.
2. **Non-Joinable**: Thread tidak terikat ke konteks eksekusi sistem. Kondisi ini terjadi jika:
   - Dikonstruksi tanpa fungsi target (konstruktor default: `std::thread t;`).
   - Objek telah dipindahkan kepemilikannya (*moved-from*).
   - Method `.join()` telah selesai dieksekusi.
   - Method `.detach()` telah dipanggil.

#### Aturan Invarian `std::terminate`
Invarian terpenting dalam `std::thread` adalah: **Destruktor `~std::thread()` akan memanggil `std::terminate()` jika objek dihancurkan saat masih berstatus *joinable***. Desain ini sengaja dipilih oleh komite standarisasi C++ untuk menghindari dua skenario buruk yang tersembunyi:
- **Auto-join implisit**: Berpotensi menyebabkan deadlock yang tidak terduga saat stack unwinding (misalnya ketika terjadi exception).
- **Auto-detach implisit**: Mengakibatkan *lifetime bug* yang parah (akses memory liar/dangling pointer) karena thread anak terus berjalan mengakses variabel lokal yang telah hancur bersama stack induknya.

### 2. Implementasi & Contoh Kasus Nyata

Kode di bawah mendemonstrasikan variasi mekanisme invoking (fungsi biasa, lambda capture, passing by reference menggunakan `std::ref`, dan move semantics), siklus hidup `join()`, bahaya `detach()`, serta idiom RAII thread wrapper.

```cpp
#include <iostream>
#include <thread>
#include <vector>
#include <string>
#include <chrono>
#include <memory>
#include <utility>

// 1. Thread function biasa dengan argument passing
void calculateHash(int taskId, const std::string& input, std::string& outResult) {
    // Simulasi komputasi intensif
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    outResult = "HASH_" + std::to_string(taskId) + "_" + input;
}

// 2. Idiom RAII: Thread Guard untuk keamanan Exception
class ScopedThread {
    std::thread t;
public:
    explicit ScopedThread(std::thread t_) : t(std::move(t_)) {
        if (!t.joinable()) {
            throw std::logic_error("Thread tidak memiliki target eksekusi!");
        }
    }

    ~ScopedThread() {
        if (t.joinable()) {
            t.join(); // Memastikan join terpanggil sebelum stack frame lepas
        }
    }

    ScopedThread(const ScopedThread&) = delete;
    ScopedThread& operator=(const ScopedThread&) = delete;
    ScopedThread(ScopedThread&&) noexcept = default;
    ScopedThread& operator=(ScopedThread&&) noexcept = default;
};

// 3. Worker untuk demonstrasi detach
void backgroundDaemon(int maxIterations) {
    for (int i = 0; i < maxIterations; ++i) {
        // PERINGATAN: Jangan mengakses referensi ke objek lokal di thread pembuat!
        std::this_thread::sleep_for(std::chrono::milliseconds(20));
    }
}

int main() {
    std::cout << "[Main] ID: " << std::this_thread::get_id() << '\n';

    // --- KASUS A: Passing By-Value dan By-Reference ---
    std::string dataPayload = "MasterData";
    std::string resultPayload;
    
    // std::ref MUTLAK digunakan jika parameter target adalah referensi non-const.
    // std::thread secara default meng-copy/decay semua argumen ke internal storage.
    std::thread worker1(calculateHash, 101, dataPayload, std::ref(resultPayload));
    
    // Menunggu eksekusi worker1 selesai (blocking call)
    if (worker1.joinable()) {
        worker1.join();
        std::cout << "[Worker1 Result]: " << resultPayload << '\n';
    }

    // --- KASUS B: Move-Only Types dan Lambda Execution ---
    auto dynamicData = std::make_unique<std::vector<int>>(1000, 42);

    // Menggunakan move semantics untuk mentransfer resource unik ke lambda internal thread
    std::thread worker2([data = std::move(dynamicData)]() mutable {
        std::cout << "[Worker2] Ukuran data yang dipindahkan: " << data->size() << '\n';
        // dynamicData hancur saat lambda selesai dieksekusi di thread ini
    });
    worker2.join();

    // --- KASUS C: Penggunaan RAII Thread Guard ---
    try {
        ScopedThread safeWorker(std::thread([]() {
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
            // Simulasi lemparan exception
            // throw std::runtime_error("Kesalahan internal thread");
        }));
        
        // Operasi lokal yang berpotensi melempar exception di Main
        // ScopedThread akan menjamin join() terpanggil saat stack unwinding.
    } catch (const std::exception& e) {
        std::cerr << "[Exception Ditangani]: " << e.what() << '\n';
    }

    // --- KASUS D: Detach (Fire-and-Forget) ---
    // Detach melepaskan kepemilikan thread handle dari C++.
    // Thread OS berjalan mandiri di background dan resource-nya direclaim OS saat mati.
    std::thread workerDaemon(backgroundDaemon, 5);
    workerDaemon.detach();

    // Verifikasi non-joinable setelah detach
    if (!workerDaemon.joinable()) {
        std::cout << "[Daemon] Worker berhasil di-detach dan berjalan mandiri.\n";
    }

    // Beri waktu sejenak agar daemon tidak langsung terpotong saat proses keluar
    std::this_thread::sleep_for(std::chrono::milliseconds(120));
    std::cout << "[Main] Selesai.\n";
    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Penerusan Argumen (*Argument Decay*)**: 
   Konstruktor template `std::thread` menggunakan parameter pack `Args&&...`. Namun, implementasi standar (seperti `libstdc++`) tidak langsung menjalankan fungsi pada stack pemanggil. Argumen di-decay (konversi array-ke-pointer, pembuangan `const` dan referensi) lalu disimpan ke dalam sebuah heap-allocated tuple (`_Invoker` frame).
   
   Jika Anda membutuhkan passing by-reference, `std::ref()` / `std::cref()` wajib digunakan untuk membungkus argumen ke dalam `std::reference_wrapper<T>`, menghindari kompilasi error akibat copy-constructibility check.
   
2. **Kompilasi & Pemanggilan OS**:
   Ketika runtime library C++ mengeksekusi konstruktor:
   - Alokasi blok internal kontrol state thread di heap.
   - Library memanggil wrapper native (misal: `pthread_create`). Pointer ke trampoline function milik library C++ diteruskan bersama payload argumen.
   - Trampoline function mengekstrak tuple, memanggil fungsi target pengguna, menangkap exception level thread, dan memicu pembersihan saat fungsi selesai.

3. **Operasi `join()` vs `detach()`**:
   - **`join()`**: Memanggil fungsi blocking OS native (seperti `pthread_join` atau `WaitForSingleObject`). Thread pemanggil masuk ke state `WAITING`/`BLOCKED`, melepaskan CPU time slice hingga OS scheduler menerima notifikasi termination dari thread target. Setelah sinkronisasi ini, state objek C++ diubah menjadi *non-joinable*, dan internal storage dibersihkan.
   - **`detach()`**: Memanggil `pthread_detach` atau menutup handle kernel (`CloseHandle`). Koneksi antara objek C++ dan kernel thread diputus. Objek `std::thread` segera menjadi *non-joinable*. OS akan otomatis membebaskan Thread Control Block (TCB) dan call stack thread tersebut seketika setelah fungsinya selesai dieksekusi.

#### Alokasi Memori / Resource
- **Thread Stack**: OS mengalokasikan stack independen untuk setiap thread (default Linux sekitar 8 MB via `ulimit -s`, Windows 1 MB). Penggunaan ratusan/ribuan thread berbasis `std::thread` dapat dengan cepat menghabiskan *virtual address space* dan menyebabkan *OOM (Out Of Memory)*.
- **Heap Overhead**: Pembuatan `std::thread` hampir selalu memicu alokasi heap dinamis kecil untuk menyimpan metadata pemanggilan (*call wrapper/state*), kecuali dioptimasi ketat oleh implementasi compiler tertentu.

#### Trade-offs
- **Hardware Concurrency vs Overhead**: Mengalokasikan thread melebihi core logis CPU (`std::thread::hardware_concurrency()`) memicu fenomena **CPU Throttling & Cache Invalidation**. Biaya *Context Switching* antar-kernel thread mencakup: swap register set, flush branch predictor, dan invalidasi Translation Lookaside Buffer (TLB) memori virtual.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Prioritaskan RAII Pattern**: Bungkus `std::thread` menggunakan idiom RAII (seperti kelas `ScopedThread` di atas) atau langsung gunakan `std::jthread` jika Anda memakai target **C++20**. `std::jthread` secara otomatis memanggil request cooperative cancelation dan melakukan `.join()` pada destruktornya.
- **Validasi `joinable()`**: Selalu gunakan pengecekan `.joinable()` sebelum memanggil `.join()` atau `.detach()`, terutama dalam alur kondisional bercabang.
- **Batasi Pembuatan Thread Berdasarkan Core**: Gunakan `std::thread::hardware_concurrency()` sebagai referensi batas maksimum thread komputasi (*CPU-bound*) guna menghindari *oversubscription*.

#### Don'ts
- **DILARANG melempar Uncaught Exception ke luar batas Thread**: Jika thread fungsi anak melempar exception yang tidak tertangkap di dalam blok function bodynya, runtime C++ akan memanggil `std::terminate()`. Exception **tidak bisa** merambat secara otomatis melintasi batas thread ke thread induk.
- **Hindari Mengakses Variabel Stack Induk pada Detached Thread**:
  ```cpp
  void initTask() {
      int localBuffer[64];
      std::thread t([&]() {
          // BENCANA: Begitu initTask() return, localBuffer hancur.
          // t.detach() akan membaca stack frame yang sudah invalid -> Undefined Behavior!
          localBuffer[0] = 123; 
      });
      t.detach();
  }
  ```
- **Hindari Re-joining**: Memanggil `.join()` dua kali pada objek thread yang sama akan melempar exception `std::system_error` (*Invalid argument* / `EINVAL`).

#### Edge Cases
- **Exit saat `main()` berakhir**: Jika thread di-`detach()`, lalu eksekusi fungsi `main()` selesai (`return 0`), runtime C library akan memanggil destruktor objek statis dan mengeksekusi `exit(3)`. Thread yang ter-detach akan dibunuh seketika oleh OS di tengah jalan tanpa pembersihan stack (destruktor objek lokal di detached thread **tidak akan dipanggil**).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Move-Aware Thread Guard**:
   Rancang sebuah kelas `JThreadReplica` (menggunakan C++14/17) yang mereplikasi fungsionalitas dasar `std::jthread` (C++20). Pastikan kelas ini:
   - Bersifat Move-Constructible dan Move-Assignable.
   - Non-Copyable.
   - Memanggil `join()` pada destruktor jika thread masih joinable.
   - Ujilah kelas ini di dalam fungsi yang melempar exception (`std::runtime_error`) dan pastikan proses aplikasi tidak crash (`std::terminate()` tidak terpanggil).

2. **Deteksi Overhead Context Switching**:
   Buat benchmark sederhana yang membandingkan:
   - Eksekusi $100.000$ kalkulasi matematika sekuensial pada satu thread.
   - Eksekusi pekerjaan yang sama tetapi dipecah ke dalam $1.000$ instance `std::thread` yang dibuat dan di-join secara ad-hoc.
   Analisis bagaimana alokasi memory/stack OS dan context switching mempengaruhi runtime secara drastis melalui *profiler* (misalnya `perf` di Linux atau Concurrency Visualizer di Windows).
