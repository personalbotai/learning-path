## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum C++20, *generic programming* berbasis Template mengandalkan prinsip *duck typing* statis: jika sintaksis ekspresi di dalam fungsi template valid untuk tipe argumen yang di-oper, kompilasi berhasil. Masalah timbul ketika tipe tidak cocok: kompilator mencoba melakukan substitusi hingga meledak jauh di kedalaman *call stack* internal pustaka dengan pesan galat (error trace) ratusan baris.

Teknik lama untuk memitigasi ini menggunakan **SFINAE** (*Substitution Failure Is Not An Error*) via `std::enable_if_t` dan *tag dispatching*. Namun, SFINAE memiliki kelemahan arsitektural:
1. Membebani waktu kompilasi (*compile-time overhead*) karena instansiasi template yang masif.
2. Mengotori tanda tangan fungsi (*function signature*).
3. Sulit dibaca dan minim semantik deklaratif.

```
       C++98/03                  C++11/14/17                   C++20
[Unconstrained T] ---> [SFINAE / std::enable_if] ---> [Concepts + Constraints]
(Duck typing liar)     (Verbose, slow compile)        (First-class semantic contract)
```

#### Evolusi: Concepts & Constraints (C++20)
*Concepts* adalah predikat waktu-kompilasi (*compile-time predicates*) yang mengevaluasi apakah suatu tipe memenuhi sekumpulan kebutuhan semantik dan sintaktis. Kompilator mengevaluasi *constraint* ini sebelum melakukan instansiasi tubuh template. 

Jika tipe gagal memenuhi *concept*, substitusi dihentikan seketika pada antarmuka fungsi, menghasilkan pesan kesalahan yang presisi. Selain itu, Concepts memperkenalkan aturan **Subsumption**: jika fungsi di-overload dengan dua *concept* yang berbeda tingkatan hierarkinya, kompilator secara deterministik memilih fungsi dengan *constraint* yang paling terspesialisasi tanpa memicu ambiguitas SFINAE.

#### Paradigma Baru: Ranges & Views
Pustaka standar algoritma klasik (`<algorithm>`) bekerja dengan pasangan iterator terpisah `[begin, end)`. Ini membatasi komposabilitas: kita tidak bisa merangkai (*pipe*) operasi tanpa membuat alokasi memori kontainer sementara.

`std::ranges` merombak arsitektur ini melalui tiga pilar:
1. **Range Abstraction**: Sebuah *range* adalah entitas tunggal yang merepresentasikan rentang elemen, didefinisikan oleh iterator awal (*begin*) dan batas akhir (*sentinel*). Tipe *sentinel* tidak harus sama dengan tipe iterator, memungkinkan representasi *infinite ranges* atau *null-terminated ranges*.
2. **Views (`std::views`)**: Abstraksi *range* non-owning, berbobot sangat ringan ($O(1)$ untuk penyalinan/pemindahan), dan dievaluasi secara malas (*lazy evaluation*). Komputasi baru dieksekusi saat elemen diakses via dereferensiasi iterator.
3. **Projections**: Kemampuan untuk meneruskan *callable* (seperti pointer-to-member atau lambda) ke algoritma guna mengekstrak atau mentransformasi data sebelum diproses oleh predikat atau komparator, mengeliminasi kebutuhan pembuatan transformasi data perantara.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem pemrosesan telemetri finansial yang menggabungkan custom *concept*, *range views pipeline*, dan *projections*:

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <concepts>
#include <ranges>
#include <algorithm>
#include <chrono>

// 1. Definisi Custom Concept
template <typename T>
concept FinancialMetric = requires(T m) {
    { m.id } -> std::convertible_to<std::string>;
    { m.timestamp } -> std::convertible_to<std::chrono::system_clock::time_point>;
    { m.value } -> std::floating_point;
    { m.is_valid() } -> std::same_as<bool>;
};

struct Metric {
    std::string id;
    std::chrono::system_clock::time_point timestamp;
    double value;
    bool valid;

    bool is_valid() const { return valid; }
};

// 2. Fungsi Template Ter-konstrain menggunakan Sintaks 'requires'
template <typename R>
    requires std::ranges::input_range<R> && 
             FinancialMetric<std::ranges::range_value_t<R>>
void process_telemetry(const R& range, double threshold) {
    // Pipeline komposisi Ranges:
    // Filter data tidak valid -> Filter di atas threshold -> Ambil top 3 -> Transformasi
    auto pipeline = range 
        | std::views::filter(&Metric::is_valid)
        | std::views::filter([threshold](const Metric& m) { return m.value >= threshold; })
        | std::views::take(3)
        | std::views::transform([](const Metric& m) {
            return std::format("ALERT: Asset {} spiked to ${:.2f}", m.id, m.value);
        });

    for (const auto& alert : pipeline) {
        std::cout << alert << '\n';
    }
}

int main() {
    using namespace std::chrono;
    auto now = system_clock::now();

    std::vector<Metric> stream = {
        {"BTC-USD", now, 64250.50, true},
        {"ETH-USD", now, 3450.20, false}, // Invalid, diabaikan
        {"SOL-USD", now, 145.80, true},
        {"BTC-USD", now + 1s, 64900.00, true},
        {"DOT-USD", now, 7.20, true},
        {"BTC-USD", now + 2s, 65100.00, true}
    };

    // 3. Algoritma Ranges dengan Projection
    // Urutkan stream secara descending berdasarkan 'value' tanpa lambda komparator eksplisit
    std::ranges::sort(stream, std::greater<double>{}, &Metric::value);

    // Eksekusi pipeline
    std::cout << "--- High Value Transactions Pipeline ---\n";
    process_telemetry(stream, 100.0);

    return 0;
}
```

#### Bedah Kode:
* **`concept FinancialMetric`**: Menggunakan ekspresi `requires`. Menguji bahwa tipe memiliki member yang relevan dan memastikan *return type* dari pemanggilan method/akses member memenuhi syarat kovertibilitas secara statis.
* **`range | views::filter | ...`**: Operator bitwise OR (`|`) di-overload untuk menyediakan antarmuka chaining fungsional. Tidak ada perulangan yang langsung dieksekusi di baris deklarasi `auto pipeline`.
* **`&Metric::value` (Projection)**: `std::ranges::sort` menerima parameter ketiga berupa proyeksi. Komparator `std::greater<double>` tidak membandingkan objek `Metric`, melainkan langsung membandingkan hasil proyeksi `Metric::value`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Lazy Evaluation Engine)
Ketika baris pipeline didefinisikan:
```cpp
auto pipeline = range | std::views::filter(...) | std::views::transform(...);
```
Kompilator **tidak menghasilkan satu baris pun instruksi traversal loop**. Pipeline tersebut adalah objek komposit yang membungkus tipe *iterator adaptors*.
* Struktur `filter_view` menyimpan referensi ke range asal dan predikat filter.
* Ketika pemanggilan `pipeline.begin()` dilakukan, di sinilah pencarian elemen pertama yang memenuhi kriteria *filter* dimulai secara langsung.
* Setiap kali operator `++` pada iterator dipanggil, iterator bergerak melintasi kontainer dasar secara *lazy*, menguji predikat dan langsung meneruskannya ke adaptor berikutnya (*transform*) tanpa menyimpan data perantara ke dalam memori.

#### Compiler & AST: Constraint Normalization & Subsumption
Pada fase kompilasi:
1. **Normalisasi**: Kompilator memecah ekspresi `requires` menjadi *Atomic Constraints* bertipe boolean.
2. **Subsumption Analysis**: Jika ada dua overload:
   ```cpp
   template <std::ranges::input_range R> void fn(R&&);           // Overload A
   template <std::ranges::random_access_range R> void fn(R&&);   // Overload B
   ```
   Karena `random_access_range` menurunkan/mensyaratkan `derived_from<..., input_range_tag>` secara logis, Kompilator menentukan bahwa **Overload B lebih terspesialisasi (subsumes A)**. Hal ini dilakukan murni pada tingkat parsing struktur logika proposisional oleh kompilator tanpa perlu instansiasi SFINAE buatan.

#### Alokasi Memori & Inlining
* **Zero Allocation**: `views` tidak mengalokasikan heap. View hanya menyimpan pointer/referensi ke kontainer dasar ditambah fungsi lambda (jika *stateful*). Ukurannya pada memori stack biasanya setara dengan 1-3 *machine pointers*.
* **Aggressive Inlining**: Melalui optimasi `-O2` atau `-O3`, *nested iterator dereferencing* dieliminasi secara total oleh kompilator modern (GCC/Clang). Hasil akhir assembly dari perulangan berbasis pipeline view seringkali identik (*zero-cost abstraction*) dengan perulangan `for` manual satu tingkat yang ditulis dengan tangan.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Semantic Constraints**: Buat concept berdasarkan kapabilitas semantik tipe, bukan sekadar nama fungsinya. Preferensikan concept standar (`std::integral`, `std::ranges::contiguous_range`) sebelum merancang custom concept.
- **Manfaatkan Projections**: Gunakan proyeksi pada `std::ranges::sort`, `find`, `lower_bound`, dll., alih-alih membuat lambda kustom hanya untuk mengakses struct field.
- **Constrain Menggunakan Auto**: Sederhanakan fungsi template singkat dengan constrained auto:
  ```cpp
  void log_metric(const FinancialMetric auto& m); // Terbaca jelas dan instan
  ```

#### Don'ts
- **Dangling Views pada Objek Temporary**: Ini adalah sumber *Undefined Behavior* paling umum pada C++ Ranges.
  ```cpp
  // CRITICAL BUG: vector temporer dihancurkan di akhir baris statement.
  // 'bad_view' menyimpan referensi ke memori yang sudah di-deallokasi (dangling iterator).
  auto bad_view = get_temporary_vector() | std::views::filter(predicate);
  for (auto x : bad_view) { /* Crash / Read garbage */ }
  ```
- **Hindari Menggunakan View Penuh Efek Samping (Side Effects)**: Karena view dievaluasi secara malas dan berulang setiap kali di-iterasi, memasukkan modifikasi state ke dalam lambda `views::transform` atau `views::filter` akan menyebabkan evaluasi ganda yang non-deterministik.

#### Edge Cases
- **`std::views::filter` Merusak `const`-correctness Cache Iterator**:
  `std::views::filter` melakukan *caching* internal untuk posisi `.begin()` agar operasi amortisasi tetap $O(1)$. Konsekuensinya, memanggil `.begin()` pada non-const filter view dapat memodifikasi state internal view tersebut. Mengoper `const auto& filter_view` ke fungsi lain sering kali memicu error kompilasi karena method `.begin()` tidak memiliki kualifikasi `const`. Solusi: Lewatkan views via *pass-by-value*, karena views dirancang sangat murah untuk disalin.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Subsumption Engine Mandiri**:
   Buat dua concept: `Shape` (memiliki method `area() -> double`) dan `RenderableShape` (memenuhi `Shape` DAN memiliki method `draw() -> void`). Buat dua overload fungsi `render(Shape auto s)` dan `render(RenderableShape auto s)`. Amati bagaimana kompilator memprioritaskan overload yang lebih spesifik tanpa memicu *ambiguous call error*.
2. **Reverse Pipeline Analysis**:
   Rancang pipeline ranges yang membaca data dari `std::string` yang sangat panjang (berisi teks log yang dipisahkan baris baru `\n`), memfilter baris yang hanya mengandung substring `[ERROR]`, memotong spasi di awal string secara malas, dan menghitung total kemunculan kata kunci tanpa menduplikasi string ke dalam vektor perantara. Gunakan profiling memori untuk membuktikan alokasi memori adalah $O(1)$.
