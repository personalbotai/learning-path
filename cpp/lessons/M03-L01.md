### 1. Konsep & Arsitektur Mendalam

Dalam paradigma C++, manajemen *lifecycle* objek terikat erat pada konsep penjaminan invarian (*class invariants*). Objek tidak hanya sekadar blok memori pasif; ia memiliki siklus hidup terdefinisi: inisialisasi, mutasi, dan terminasi.

```
       Alokasi Memori (Stack / Heap)
                    │
                    ▼
┌───────────────────────────────────────┐
│ 1. Base Class Constructors            │
│ 2. Member Initializer List (In-place) │ ◄── Construction Phase
│ 3. Constructor Body Execution         │
└───────────────────────────────────────┘
                    │
           [ Object is Alive ]
                    │
┌───────────────────────────────────────┐
│ 1. Destructor Body Execution          │
│ 2. Member Destructors (Reverse order) │ ◄── Destruction Phase (RAII)
│ 3. Base Class Destructors             │
└───────────────────────────────────────┘
                    │
                    ▼
       Devaluasi / Deallokasi Memori
```

#### Constructor & Member Initializer List
Constructor bertugas membangun state awal objek yang valid. Secara arsitektural, inisialisasi anggota kelas (*member initialization*) **harus terjadi sebelum** blok kode tubuh constructor (`{ ... }`) dieksekusi.

Jika Anda tidak menggunakan *Member Initializer List*, compiler secara implisit memanggil *default constructor* untuk semua tipe non-primitif, baru kemudian mengeksekusi ekspresi assignment di dalam tubuh constructor. Hal ini menimbulkan penalti performa (konstruksi ganda) dan mustahil dilakukan untuk:
1. Variabel referensi (`T&`).
2. Variabel konstan (`const T`).
3. Anggota kelas yang tidak memiliki *default constructor*.

Urutan evaluasi dalam *Initializer List* diatur secara mutlak oleh **urutan deklarasi atribut di dalam definisi kelas**, bukan urutan penulisan pada *initializer list* itu sendiri. Mengabaikan aturan ini dapat menyebabkan *undefined behavior* akibat mengakses memori yang belum diinisialisasi.

#### Destructor & Filosofi RAII
Destructor adalah inti dari idiom **RAII (Resource Acquisition Is Initialization)**. Destructor menjamin bahwa *resource* (alokasi heap, *file handle*, *mutex lock*, *socket*) dilepas secara deterministik segera setelah masa hidup objek berakhir (*out of scope*), baik melalui alur eksekusi normal maupun akibat propagasi *exception* (*stack unwinding*).

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi manajer *buffer* dinamis yang mendemonstrasikan constructor berparameter, delegating constructor, *member initializer list*, penanganan kegagalan inisialisasi, dan destructor.

```cpp
#include <iostream>
#include <cstddef>
#include <utility>
#include <algorithm>
#include <stdexcept>

class NativeBuffer {
private:
    std::size_t m_capacity;
    std::size_t m_size;
    int* m_data; // Raw resource

public:
    // 1. Delegating Constructor
    NativeBuffer() : NativeBuffer(8) {
        std::cout << "[LOG] Default constructor: Delegated to NativeBuffer(8)\n";
    }

    // 2. Explicit Parameterized Constructor dengan Initializer List
    explicit NativeBuffer(std::size_t capacity)
        : m_capacity(capacity),
          m_size(0),
          m_data(capacity > 0 ? new int[capacity] : nullptr) 
    {
        if (capacity == 0) {
            throw std::invalid_argument("Capacity harus lebih besar dari 0");
        }
        std::fill_n(m_data, m_capacity, 0);
        std::cout << "[LOG] Buffer dialokasikan dengan kapasitas: " << m_capacity << "\n";
    }

    // 3. Destructor (RAII Cleanup)
    ~NativeBuffer() noexcept {
        delete[] m_data;
        std::cout << "[LOG] Destructor dieksekusi. Memori dibebaskan.\n";
    }

    // Mencegah Copy implisit untuk menjaga stabilitas resource (Rule of Three/Five)
    NativeBuffer(const NativeBuffer&) = delete;
    NativeBuffer& operator=(const NativeBuffer&) = delete;

    void push(int value) {
        if (m_size >= m_capacity) {
            throw std::overflow_error("Buffer kapasitas penuh!");
        }
        m_data[m_size++] = value;
    }

    [[nodiscard]] std::size_t size() const noexcept { return m_size; }
    [[nodiscard]] std::size_t capacity() const noexcept { return m_capacity; }
    
    [[nodiscard]] int at(std::size_t index) const {
        if (index >= m_size) throw std::out_of_range("Index out of bounds");
        return m_data[index];
    }
};

int main() {
    try {
        std::cout << "--- Lifecycle Scope Dimulai ---\n";
        NativeBuffer buf(4);
        buf.push(10);
        buf.push(20);

        std::cout << "Element 0: " << buf.at(0) << "\n";
        std::cout << "Element 1: " << buf.at(1) << "\n";
        std::cout << "--- Lifecycle Scope Akan Berakhir ---\n";
    } // buf keluar dari scope di sini, destructor dipanggil secara deterministik
    catch (const std::exception& ex) {
        std::cerr << "Error: " << ex.what() << "\n";
    }

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Prologue & Epilogue Constructor**:
   Ketika sebuah objek ditumpuk di stack, compiler mengalokasikan ruang memori sesuai `sizeof(Type)`. Setelah itu, compiler menyuntikkan kode inisialisasi:
   - Menjalankan constructor *base class* (jika ada).
   - Menginisialisasi *vptr* (Virtual Table Pointer) jika kelas memiliki fungsi virtual.
   - Menjalankan *member initializer list* langsung pada *offset* memori masing-masing atribut.
   - Mengeksekusi blok kode di dalam tubuh `{}` constructor.
2. **Reverse Order Destruction**:
   Destruksi dieksekusi dengan urutan yang berkebalikan persis (*strictly reverse*) dari konstruksi. Ini menjamin dependensi aman: jika anggota `B` bergantung pada `A` saat konstruksi, `B` akan dihancurkan terlebih dahulu sebelum `A` dihancurkan.

#### Alokasi Memori / Resource
Perhatikan perbedaan antara *Assignment* vs *Direct Initialization*:
```cpp
// Direct Initialization (via Initializer List)
// Assembly: langsung memanggil Type::Type(args) pada offset objek
MyClass::MyClass(std::string s) : m_str(std::move(s)) {} 

// Assignment di Body
// Assembly: memanggil std::string::string() default, 
// kemudian std::string::operator=(std::move(s)) -> 2x kerja!
MyClass::MyClass(std::string s) { 
    m_str = std::move(s); 
}
```

#### Polimorfisme & Virtual Destructor
Jika kelas memiliki fungsi virtual dan akan digunakan secara polimorfis via pointer basis (`Base* ptr = new Derived()`), maka destructor `Base` **wajib** dideklarasikan `virtual`.
- Tanpa `virtual ~Base()`: Operasi `delete ptr;` hanya akan mengeksekusi destructor milik `Base`. Destructor `Derived` terlewati sepenuhnya (*Resource Leak* / *Undefined Behavior*).
- Dengan `virtual`: Pemanggilan destructor diarahkan lewat *vtable* (Virtual Method Table), memastikan destructor `Derived` dipanggil sebelum `Base`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan keyword `explicit`** pada constructor dengan satu argumen (atau yang dapat dipanggil dengan satu argumen) untuk mencegah konversi tipe implisit yang tidak disengaja (*implicit conversion bug*).
- **Inisialisasi semua variabel primitif** via *in-class member initializers* (C++11) atau *initializer list* untuk menghindari *garbage values*.
- **Tandai Destructor sebagai `noexcept`**. Secara default sejak C++11, destructor bersifat `noexcept(true)`. Jangan pernah membiarkan *exception* keluar dari destructor; jika destruksi gagal saat *stack unwinding*, runtime akan langsung memanggil `std::terminate()`.

#### Don'ts
- **Jangan memanggil Virtual Functions di dalam Constructor atau Destructor**. 
  Saat constructor kelas basis dieksekusi, *vptr* masih menunjuk ke *vtable* basis (bagian *derived* belum terbentuk). Virtual call tidak akan mencapai implementasi *override* derived class (*dynamic binding* tidak aktif).
- **Jangan mengandalkan urutan Initializer List**:
  ```cpp
  class Faulty {
      int a;
      int b;
  public:
      // BUG: 'b' dideklarasikan setelah 'a', namun 'a' mencoba memakai 'b'.
      // Urutan inisialisasi: 'a' DULU baru 'b', sehingga 'b' masih uninitialized garbage!
      Faulty(int val) : b(val), a(b + 1) {} 
  };
  ```

#### Edge Cases: Exception dalam Constructor
Jika constructor melempar *exception*, **destructor dari objek tersebut TIDAK AKAN PERNAH dipanggil** karena runtime menganggap objek tersebut tidak pernah selesai dibangun.
- **Solusi**: Semua atribut resource harus dibungkus dengan tipe RAII (seperti `std::unique_ptr` alih-alih raw pointer). Atribut yang berhasil dibangun *sebelum* exception meledak akan dihancurkan secara otomatis, namun raw pointer yang dialokasikan di dalam blok tubuh constructor akan bocor (*leak*).

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Assembly via Compiler Explorer (Godbolt)**:
   Buat struct dengan atribut `std::string`. Bandingkan kode assembly keluaran compiler (pada level `-O0` dan `-O2`) antara inisialisasi menggunakan *member initializer list* versus inisialisasi di dalam *constructor body*. Amati instruksi `call` ke constructor dan assignment operator yang dihasilkan.
2. **Simulasi Memory Leak pada Pewarisan Polimorfis**:
   Buat kelas basis `Shape` tanpa `virtual ~Shape()` dan kelas turunan `Circle` yang mengalokasikan array di heap. Lakukan alokasi `Shape* s = new Circle(); delete s;`. Gunakan tools seperti *AddressSanitizer* (`-fsanitize=address`) atau *Valgrind* untuk mengamati kebocoran memori yang terjadi, kemudian perbaiki dengan `virtual destructor`.
