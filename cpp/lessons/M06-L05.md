## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Di dalam C++ Standard Template Library (STL), terdapat pemisahan tanggung jawab (*separation of concerns*) yang fundamental:
1. **Container**: Bertanggung jawab mengelola topologi data, keterurutan (*order*), dan invarian struktur (misalnya: *contiguous array* pada `std::vector`, *red-black tree* pada `std::map`, atau *doubly-linked list* pada `std::list`).
2. **Allocator**: Bertanggung jawab murni atas siklus hidup memori fisik: reservasi memori mentah (*allocation*), inisialisasi objek di atas memori tersebut (*construction*), penghancuran objek (*destruction*), serta pengembalian memori mentah ke sistem (*deallocation*).

```
+-------------------------------------------------------------+
|                       STL Container                         |
|   (vector, list, map -> Mengelola struktur data & iterasi)  |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                    std::allocator_traits                    |
|       (Interface seragam: allocate, construct, deallocate)  |
+-------------------------------------------------------------+
                              |
        +---------------------+---------------------+
        v                                           v
+-----------------------+               +-----------------------+
|    std::allocator     |               |   std::pmr::...       |
| (Default: global heap |               | (Polymorphic Memory   |
|   via ::operator new) |               |  Resource: C++17)     |
+-----------------------+               +-----------------------+
```

#### Masalah Default Allocator (`std::allocator<T>`)
Secara *default*, semua kontainer STL menggunakan `std::allocator<T>`. Di balik layar, allocator ini memanggil `::operator new` dan `::operator delete`, yang biasanya berujung pada pemanggilan *system-level heap allocator* (seperti `ptmalloc`, `jemalloc`, atau Win32 Heap).

Kelemahan pendekatan ini untuk sistem performa tinggi (*low-latency*, *game engine*, *high-frequency trading*):
- **Overhead System Call & Thread Contention**: Global heap harus *thread-safe*, sehingga alokasi sering kali memicu *mutex lock* atau manipulasi struktur *free list* global.
- **Fragmentasi Memori**: Container berbasis simpul (*node-based*) seperti `std::map`, `std::set`, atau `std::list` mengalokasikan memori terpisah untuk setiap elemen beserta *pointer overhead* (`sizeof(Node)` > `sizeof(T)`). Ini menghancurkan *cache locality* (L1/L2/L3 cache misses).
- **Type Incompatibility**: Pada C++ standard sebelum C++17, instansiasi kontainer dengan alokator kustom yang berbeda akan menghasilkan **tipe data yang sama sekali berbeda**. `std::vector<int, AllocatorA>` tidak bisa di-passing ke fungsi yang menerima `std::vector<int, AllocatorB>`.

#### Revolusi C++17: Polymorphic Memory Resources (PMR)
Untuk mengatasi masalah rigiditas tipe, C++17 memperkenalkan namespace `std::pmr`. Arsitekturnya memisahkan tipe allocator dari tipe memori fisik menggunakan *dynamic polymorphism* (`std::pmr::memory_resource`). 

Kontainer seperti `std::pmr::vector<T>` hanyalah alias dari `std::vector<T, std::pmr::polymorphic_allocator<T>>`. Memori dasarnya dapat ditukar saat *runtime* tanpa mengubah tipe kontainer:
- **`std::pmr::monotonic_buffer_resource`**: Alokasi sekuensial yang sangat cepat tanpa deallokasi individual (hanya dealokasi total di akhir siklus hidup arena). Sangat ideal untuk operasi per-*frame* atau *request-scoped*.
- **`std::pmr::unsynchronized_pool_resource`**: Memory pool untuk objek-objek berukuran serupa, memitigasi fragmentasi tanpa overhead thread-safety.
- **`std::pmr::synchronized_pool_resource`**: Varian *thread-safe* dari pool resource.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan bagaimana mengeliminasi alokasi heap dinamis dalam *hot-path loop* menggunakan `std::pmr` dan alokasi berbasis *stack-buffer* (Arena Allocation).

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <array>
#include <memory_resource>
#include <chrono>

// Custom tracker untuk mendeteksi kapan heap global disentuh
class HeapTrackerResource : public std::pmr::memory_resource {
public:
    explicit HeapTrackerResource(std::pmr::memory_resource* upstream = std::pmr::get_default_resource())
        : upstream_resource(upstream) {}

protected:
    void* do_allocate(std::size_t bytes, std::size_t alignment) override {
        std::cout << "[ALLOC] " << bytes << " bytes (alignment: " << alignment << ") dialokasikan.\n";
        return upstream_resource->allocate(bytes, alignment);
    }

    void do_deallocate(void* p, std::size_t bytes, std::size_t alignment) override {
        std::cout << "[DEALLOC] " << bytes << " bytes dibebaskan.\n";
        upstream_resource->deallocate(p, bytes, alignment);
    }

    bool do_is_equal(const std::pmr::memory_resource& other) const noexcept override {
        return this == &other;
    }

private:
    std::pmr::memory_resource* upstream_resource;
};

struct OrderPacket {
    uint64_t order_id;
    double price;
    uint32_t quantity;
};

int main() {
    std::cout << "=== 1. Standar Heap Allocator via std::pmr ===\n";
    HeapTrackerResource tracker;
    
    {
        // Menggunakan polymorphic_allocator yang mengarah ke custom tracker
        std::pmr::vector<OrderPacket> orders(&tracker);
        orders.reserve(3); // Meminta alokasi
        orders.push_back({1001, 150.25, 10});
        orders.push_back({1002, 150.50, 5});
    } // orders keluar scope, dealokasi terjadi di sini

    std::cout << "\n=== 2. Monotonic Buffer (Stack Arena Allocation) ===\n";
    // Buffer memori lokal di stack: 1024 byte, TIDAK ADA system call new/malloc
    std::array<std::byte, 1024> stack_memory;

    {
        // Hubungkan stack buffer ke monotonic resource. Jika buffer habis, fallback ke tracker
        std::pmr::monotonic_buffer_resource mem_pool(
            stack_memory.data(), 
            stack_memory.size(), 
            &tracker // upstream jika stack_memory penuh
        );

        // Vector menggunakan buffer stack lokal secara transparan
        std::pmr::vector<OrderPacket> fast_orders(&mem_pool);
        fast_orders.reserve(10); // Alokasi terjadi seketika (hanya pointer bump di stack_memory)

        for (uint64_t i = 0; i < 5; ++i) {
            fast_orders.push_back({2000 + i, 99.0 + i, 100});
        }

        std::cout << "Berhasil memproses " << fast_orders.size() 
                  << " orders tanpa menyentuh Global Heap.\n";
        
        // Simpulkan: Tidak ada output [ALLOC] dari Tracker untuk alokasi di dalam kapasitas stack_memory
    }

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Setiap kontainer STL tidak pernah memanggil `new` atau `malloc` secara langsung. Konstruksi elemen berjalan melalui dua tahap via perantara `std::allocator_traits<Alloc>`:

1. **Tahap Alokasi**: 
   ```cpp
   T* ptr = std::allocator_traits<Alloc>::allocate(alloc, count);
   ```
   Langkah ini hanya memesan *raw memory* berukuran `count * sizeof(T)` tanpa memanggil konstruktor objek `T`.
2. **Tahap Konstruksi (Placement new)**:
   ```cpp
   std::allocator_traits<Alloc>::construct(alloc, ptr + index, std::forward<Args>(args)...);
   ```
   Secara internal memanggil `::new (static_cast<void*>(p)) T(args...)`, mengeksekusi konstruktor tepat di alamat memori mentah yang sudah dipesan.

#### Strategi Alokasi Memori Container STL
- **Contiguous Containers (`std::vector`, `std::basic_string`)**:
  - Menggunakan strategi *geometric reallocation*. Ketika `size() == capacity()`, kontainer mengalokasikan blok memori baru berukuran $\approx 1.5 \times$ (MSVC) atau $2.0 \times$ (GCC `libstdc++`/Clang `libc++`) dari kapasitas lama.
  - Elemen dipindahkan (*move-construct*) jika `noexcept` terpenuhi, lalu blok lama dideallokasi. Hal ini menjamin kompleksitas *amortized* $\mathcal{O}(1)$ untuk `push_back`.
- **Node-Based Containers (`std::map`, `std::list`, `std::unordered_map`)**:
  - Setiap simpul adalah alokasi independen (`allocate(1)` untuk tipe node internal seperti `std::_List_node<T>`).
  - Fragmentasi sangat parah jika menggunakan alokator bawaan, karena metadata allocator OS sering kali menambahkan *header overhead* (umumnya 8–16 byte) untuk setiap simpul kecil.

#### Trade-offs
| Strategi Alokasi | Keuntungan | Kerugian |
| :--- | :--- | :--- |
| **Default `std::allocator`** | Bebas ukuran tak terbatas, diatur OS otomatis. | Latensi tinggi, thread lock, fragmentasi memori besar pada *node-based*. |
| **Stack-backed Monotonic (`pmr`)** | Super cepat ($\mathcal{O}(1)$ pointer bump), nol alokasi heap, *cache-friendly*. | Ukuran terbatas, tidak bisa membebaskan elemen individual (hanya bisa reset masal). |
| **PMR Pool Resource** | Menghilangkan fragmentasi ukuran seragam, minim overhead per-node. | Konsumsi memori awal lebih besar (*pre-allocated slabs*), jejak memori menetap jika tidak di-purge. |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Selalu Panggil `reserve()` pada Contiguous Containers**: Hindari alokasi ulang berulang kali yang memicu copy/move konstan dan fragmentasi memori.
2. **Gunakan PMR untuk Hot Paths**: Gunakan `std::pmr::monotonic_buffer_resource` pada fungsi pemrosesan per-frame, per-tick, atau parsing data jaringan.
3. **Pastikan Move Constructor Ditandai `noexcept`**: `std::vector` hanya akan menggunakan operasi *move* saat realokasi jika konstruktor pemindahan bertipe `noexcept`. Jika tidak, vector akan melakukan *copy* (lebih lambat) untuk menjamin *strong exception safety guarantee*.

#### Don'ts
1. **Jangan Membocorkan PMR Memory Resource Out of Scope**: Container PMR memegang *pointer mentah* ke memory resource-nya.
   ```cpp
   // FATAL BUG: Undefined Behavior
   std::pmr::vector<int> get_data() {
       std::array<std::byte, 512> buffer;
       std::pmr::monotonic_buffer_resource local_res(buffer.data(), buffer.size());
       std::pmr::vector<int> vec(&local_res);
       vec.push_back(42);
       return vec; // ERROR! local_res mati saat keluar scope, vec memegang pointer dangling!
   }
   ```
2. **Jangan Menggunakan `std::list` / `std::map` Default Jika Performa Memori Prioritas**: Beralihlah ke flat structure seperti `boost::container::flat_map` atau `std::vector` terurut (*cache locality* jauh lebih superior dibanding pencarian pointer melintasi heap).

#### Edge Cases
- **Allocator Propagation pada Operasi Move/Copy**: Ketika melakukan *copy/move assignment* pada kontainer dengan alokator kustom, pastikan memahami properti `propagate_on_container_copy_assignment` dan `propagate_on_container_move_assignment`. Jika dua kontainer PMR memiliki memory resource yang berbeda, operasi **move assignment** tidak dapat memindahkan pointer secara $\mathcal{O}(1)$, melainkan harus melakukan **deep copy** fallback karena memori fisik tidak bisa saling ditukar kepemilikannya.
