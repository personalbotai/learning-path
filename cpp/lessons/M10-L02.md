## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, performa tinggi bukanlah kebetulan, melainkan hasil dari desain arsitektur yang selaras dengan cara kerja perangkat keras (CPU dan Memori) serta pemahaman mendalam tentang *compiler*. Aturan emas dalam optimasi adalah: **"Jangan menebak, ukurlah" (Don't guess, measure)**. 

Optimasi tanpa *profiling* (pengukuran) sering kali berujung pada *premature optimization* yang merusak keterbacaan kode tanpa memberikan dampak signifikan. Proses optimasi yang terukur mengikuti siklus ilmiah:
1. **Measure (Ukur)**: Gunakan *profiler* untuk menemukan *bottleneck* (titik krisis).
2. **Analyze (Analisis)**: Pahami mengapa bagian tersebut lambat (apakah *CPU-bound*, *Memory-bound*, atau *I/O-bound*?).
3. **Optimize (Optimasi)**: Terapkan perbaikan (algoritma, struktur data, atau *micro-optimization*).
4. **Verify (Verifikasi)**: Ukur kembali untuk memastikan performa benar-benar meningkat dan regresi tidak terjadi.

Di C++, *compiler* modern (GCC, Clang, MSVC) sangat agresif dalam melakukan optimasi (seperti *loop unrolling*, *inlining*, *vectorization*). Tugas *engineer* bukanlah menulis kode *assembly* secara manual, melainkan menulis kode C++ yang idiomatik dan terstruktur sedemikian rupa sehingga *compiler* dapat menghasilkan instruksi mesin yang optimal, serta memastikan data diakses dengan cara yang ramah terhadap *cache* CPU (*Cache Locality*).

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh penggunaan **Google Benchmark** untuk mengukur dampak *Cache Locality* (Data-Oriented Design). Kita membandingkan iterasi matriks secara *Row-Major* (ramah cache) vs *Column-Major* (tidak ramah cache).

```cpp
#include <benchmark/benchmark.h>
#include <vector>

constexpr int SIZE = 1000;

// Setup matriks 1000x1000
std::vector<std::vector<int>> generate_matrix() {
    return std::vector<std::vector<int>>(SIZE, std::vector<int>(SIZE, 1));
}

// 1. Iterasi Row-Major (Cache Friendly)
static void BM_RowMajor(benchmark::State& state) {
    auto matrix = generate_matrix();
    for (auto _ : state) {
        long long sum = 0;
        for (int i = 0; i < SIZE; ++i) {
            for (int j = 0; j < SIZE; ++j) {
                sum += matrix[i][j];
            }
        }
        // Mencegah compiler menghapus loop karena 'sum' tidak digunakan
        benchmark::DoNotOptimize(sum);
    }
}
BENCHMARK(BM_RowMajor);

// 2. Iterasi Column-Major (Cache Unfriendly)
static void BM_ColumnMajor(benchmark::State& state) {
    auto matrix = generate_matrix();
    for (auto _ : state) {
        long long sum = 0;
        for (int i = 0; i < SIZE; ++i) {
            for (int j = 0; j < SIZE; ++j) {
                // Perhatikan indeks dibalik: matrix[j][i]
                sum += matrix[j][i];
            }
        }
        benchmark::DoNotOptimize(sum);
    }
}
BENCHMARK(BM_ColumnMajor);

BENCHMARK_MAIN();

/* 
Instruksi Kompilasi:
g++ -O3 -std=c++17 benchmark_test.cpp -lbenchmark -lpthread -o bench
*/
```

**Penjelasan Kode:**
- `benchmark::State& state`: Mengatur *loop* internal *framework* untuk menjalankan iterasi berulang kali hingga mendapatkan data statistik yang valid.
- `benchmark::DoNotOptimize(sum)`: Ini adalah trik krusial. Tanpa ini, *compiler* dengan flag `-O3` akan menyadari bahwa nilai `sum` tidak pernah dicetak atau digunakan di luar fungsi, sehingga *compiler* akan menghapus seluruh *loop* (Dead Code Elimination). Waktu eksekusi akan menjadi 0 ns.
- Pada `BM_RowMajor`, data diakses berurutan di memori. Pada `BM_ColumnMajor`, akses memori melompat-lompat sejauh ukuran baris, menyebabkan *Cache Miss* yang masif.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  CPU modern menggunakan teknik *Pipelining* dan *Branch Prediction*. Jika kode memiliki banyak percabangan `if-else` yang tidak terprediksi di dalam *loop* ketat, CPU akan sering salah menebak (*branch misprediction*). Ini memaksa CPU membuang instruksi yang sudah diproses di *pipeline* (*pipeline flush*), membuang siklus berharga (bisa 10-20 siklus per kesalahan).
- **Alokasi Memori / Resource**: 
  Memori utama (RAM) itu lambat. CPU memiliki *Cache* (L1, L2, L3) yang sangat cepat. Saat CPU meminta 1 byte data, ia tidak mengambil 1 byte dari RAM, melainkan mengambil satu blok data (biasanya 64 bytes, disebut **Cache Line**). Jika data Anda berdekatan di memori (seperti `std::vector`), akses berikutnya akan langsung diambil dari L1 Cache (*Cache Hit*). Jika data tersebar (seperti *linked list* atau iterasi *column-major*), CPU harus menunggu RAM (*Cache Miss*), yang bisa 100x lebih lambat dari L1 Cache.
- **Trade-offs**: 
  Menggunakan *Link-Time Optimization* (LTO) via flag `-flto` memungkinkan *compiler* melakukan *inlining* lintas file translasi (.cpp). Trade-off-nya adalah waktu kompilasi (*compile-time*) dan penggunaan memori saat kompilasi akan meningkat drastis, demi mendapatkan performa *runtime* yang maksimal.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Selalu kompilasi dengan flag optimasi (`-O2` atau `-O3`, dan `-DNDEBUG`) saat melakukan *profiling* atau rilis. Mengukur performa pada mode *Debug* (`-O0`) adalah hal yang sia-sia.
  - Gunakan *profiler* eksternal seperti `perf` (Linux), Valgrind/Callgrind, atau Intel VTune untuk melihat *bottleneck* di level instruksi dan *cache miss*.
  - Utamakan struktur data yang *contiguous* (bersebelahan di memori) seperti `std::vector` atau `std::array` dibandingkan `std::list` atau `std::map`.
- **Don'ts**:
  - Jangan melakukan alokasi memori dinamis (`new`, `malloc`, `std::vector::push_back` tanpa `reserve`) di dalam *loop* yang kritis terhadap performa (*hot path*).
  - Jangan menulis *custom sorting* atau algoritma manual jika `std::sort` atau algoritma dari `<algorithm>` sudah tersedia. Implementasi STL biasanya sudah sangat teroptimasi.
- **Edge Cases**:
  - **False Sharing**: Dalam *multithreading*, jika dua *thread* memodifikasi variabel berbeda yang kebetulan berada di *Cache Line* yang sama (64 bytes), CPU akan terus-menerus melakukan invalidasi *cache* antar *core*, membuat performa *multithreading* lebih lambat daripada *single-thread*. Gunakan `alignas(64)` untuk memisahkan data antar *thread*.

### 5. Tantangan Eksplorasi Mandiri

1. **AoS vs SoA**: Buatlah program yang mensimulasikan pergerakan 1.000.000 partikel (X, Y, Z, Velocity). Implementasikan dalam bentuk *Array of Structs* (AoS) dan *Struct of Arrays* (SoA). Gunakan Google Benchmark untuk membuktikan mana yang lebih cepat dan jelaskan mengapa dari perspektif *Cache Line*.
2. **Branchless Programming**: Tulis sebuah fungsi untuk menghitung jumlah elemen ganjil dalam array acak. Implementasikan versi pertama dengan `if (arr[i] % 2 != 0)` dan versi kedua tanpa percabangan (misal: `sum += (arr[i] & 1)`). Bandingkan performanya menggunakan *profiler*.
3. **Compiler Explorer Analysis**: Buka [Godbolt Compiler Explorer](https://godbolt.org/), tulis fungsi matematika sederhana, lalu bandingkan *assembly output* antara flag `-O1`, `-O3`, dan `-O3 -march=native -ffast-math`. Amati bagaimana *compiler* menggunakan instruksi SIMD (Vectorization) pada flag tertinggi.
