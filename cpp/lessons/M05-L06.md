## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, kebebasan mengelola memori secara manual melalui *raw pointer*, alokasi dinamis, dan manipulasi *lifetime* objek membuka celah kesalahan fatal: *buffer overflow*, *use-after-free* (UAF), *double-free*, serta *undefined behavior* (UB). Secara historis, kakas dinamis berbasis interpretasi biner seperti Valgrind/Memcheck menjadi standar industri. Namun, pendekatan emulasi instruksi CPU Valgrind menimbulkan *overhead* performa ekstrem (10x hingga 50x lebih lambat), membuatnya tidak layak dijalankan pada *test suite* skala besar atau *stress-testing* performa tinggi.

Keluarga **LLVM/GCC Sanitizers** menyelesaikan masalah ini melalui pendekatan **Compiler Instrumentation** yang dipadukan dengan **Runtime Library**. Sanitizer menginjeksi kode verifikasi langsung ke dalam representasi perantara (Intermediate Representation/IR) saat kompilasi, menghasilkan *overhead* yang jauh lebih rendah (hanya 1.5x hingga 3x).

#### Taksonomi Sanitizer Utama
1. **AddressSanitizer (ASan):** Mendeteksi *out-of-bounds access* (pada *heap*, *stack*, dan *global memory*), *use-after-free*, *use-after-return*, dan *double-free*.
2. **LeakSanitizer (LSan):** Mendeteksi kebocoran memori (*memory leak*). Terintegrasi secara bawaan di dalam ASan pada platform x86_64.
3. **UndefinedBehaviorSanitizer (UBSan):** Memeriksa pelanggaran standar bahasa C++ seperti *signed integer overflow*, pergeseran *bit* di luar batas (*invalid bit shifts*), dereferensi *null pointer*, dan alokasi array berukuran negatif.
4. **ThreadSanitizer (TSan):** Mendeteksi *data races* antarthread dan potensi *deadlock*.
5. **MemorySanitizer (MSan):** Mendeteksi pembacaan nilai dari memori yang belum diinisialisasi (*uninitialized reads*).

```
   Kode Sumber C++
         │
         ▼
┌──────────────────┐
│ Compiler Clang/  │ ──► [Injeksi Kode Cek: Shadow Memory & Redzones]
│ GCC Frontend/IR  │
└──────────────────┘
         │
         ▼
┌──────────────────┐
│  Linker + ASan   │ ──► [Intersepsi: malloc, free, new, delete, memcpy]
│ Runtime Library  │
└──────────────────┘
         │
         ▼
  Executable Biner (Dapat dijalankan langsung di CPU tanpa VM)
```

Sanitizer bekerja secara deterministik. Begitu memori yang tidak valid disentuh, proses langsung dihentikan (*crash fast*) dan laporan diagnostik mendalam dicetak ke `stderr` lengkap dengan *call stack* resolusi simbolis.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh program C++ modern yang merepresentasikan tiga bug memori laten yang sering lolos dari *code review* konvensional: **Heap Use-After-Free**, **Stack Buffer Overflow**, dan **Memory Leak**.

#### File: `memory_bugs.cpp`
```cpp
#include <iostream>
#include <vector>
#include <string>
#include <memory>

// Kasus 1: Stack Buffer Overflow via pointer arithmetic
void triggerStackOverflow() {
    std::cout << "[Run] Memicu Stack Overflow...\n";
    int stack_array[4] = {10, 20, 30, 40};
    
    // Akses di luar batas indeks array (out-of-bounds write)
    volatile int* ptr = stack_array;
    ptr[4] = 999; // Indeks 4 berada di luar batas (0-3 valid)
}

// Kasus 2: Heap Use-After-Free (UAF) melalui referensi menggantung
void triggerUseAfterFree() {
    std::cout << "[Run] Memicu Use-After-Free...\n";
    
    std::string* dynamic_str = new std::string("Data Sensitif");
    // Simpan pointer mentah
    const char* raw_ptr = dynamic_str->c_str();
    
    // Dealokasi memori
    delete dynamic_str;
    
    // Membaca memori yang sudah di-free (Dangling pointer read)
    std::cout << "Data terbaca: " << raw_ptr[0] << "\n";
}

// Kasus 3: Memory Leak
void triggerMemoryLeak() {
    std::cout << "[Run] Memicu Memory Leak...\n";
    // Alokasi memori mentah tanpa pasangannya (free/delete)
    int* leaked_array = new int[100];
    leaked_array[0] = 42;
    // Pointer hilang saat keluar scope tanpa pembersihan
}

int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "Gunakan argumen: stack | uaf | leak\n";
        return 1;
    }

    std::string mode = argv[1];

    if (mode == "stack") {
        triggerStackOverflow();
    } else if (mode == "uaf") {
        triggerUseAfterFree();
    } else if (mode == "leak") {
        triggerMemoryLeak();
    } else {
        std::cerr << "Mode tidak dikenal!\n";
        return 1;
    }

    return 0;
}
```

#### Kompilasi & Eksekusi

Kompilasi kode di atas menggunakan Clang atau GCC dengan mengaktifkan flag instrumentasi:

```bash
# Flags:
# -fsanitize=address,undefined : Aktifkan ASan dan UBSan secara bersamaan
# -g                            : Sertakan debug symbols untuk stack-trace presisi
# -fno-omit-frame-pointer      : Pastikan stack unwinding akurat
# -O1                           : Optimalisasi minimal agar performa baik namun jejak kode tetap jelas

clang++ -std=c++20 -fsanitize=address,undefined -g -fno-omit-frame-pointer -O1 memory_bugs.cpp -o bug_detector
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

AddressSanitizer bekerja berdasarkan arsitektur **Shadow Memory** dan **Redzones**.

#### 1. Shadow Memory Mapping
Setiap byte memori virtual pada aplikasi (*application memory*) dipetakan ke lokasi khusus yang disebut *shadow memory*. Skala pemetaannya adalah **8 banding 1**: 8 byte memori aplikasi direpresentasikan oleh 1 byte memori bayangan (*shadow byte*).

$$ShadowAddr = \left(\frac{AppAddr}{8}\right) + Offset$$

Pada arsitektur Linux x86_64 64-bit, `Offset` statis umumnya adalah `0x7fff8000` (atau `0x10007fff8000`).
Nilai dari *shadow byte* merefleksikan status dari 8 byte aplikasi yang diawasinya:
* Nilai `0`: Semua 8 byte memori valid untuk dibaca dan ditulis.
* Nilai `1` sampai `7`: Hanya $k$ byte pertama yang valid untuk diakses (misalnya jika alokasi tidak genap kelipatan 8 byte).
* Nilai negatif (misal `0xFD`, `0xFA`): Wilayah teracuni (*poisoned*), akses ke alamat ini ilegal.

```
Application Memory (8-byte aligned)
[ Byte 0 ][ Byte 1 ][ Byte 2 ][ Byte 3 ][ Byte 4 ][ Byte 5 ][ Byte 6 ][ Byte 7 ]
       │
       ▼ (Dipetakan ke 1 byte)
Shadow Memory Byte: [ 0x00 ] (Artinya: Semua 8 byte aman untuk diakses)
```

#### 2. Redzones dan Poisoning
Saat compiler mengalokasikan variabel pada *stack* atau *heap* (melalui modul runtime ASan yang meng-*override* `malloc`/`operator new`):
1. **Penyisipan Redzone:** Memori dialokasikan ekstra dengan membungkus blok asli menggunakan *redzone* (area terlarang) di awal dan akhir buffer.
2. **Poisoning:** Runtime ASan menandai shadow byte milik *redzone* dengan nilai khusus (misalnya: `0xFA` untuk heap redzone, `0xF1` untuk stack redzone).
3. **Quarantine:** Ketika `free()` atau `delete` dipanggil, memori tidak langsung dikembalikan ke OS atau *allocator pool*. Blok tersebut dimasukkan ke dalam antrean karantina (*quarantine queue*) dan shadow bytes diubah menjadi `0xFD` (Heap-freed). Operasi akses apapun ke alamat ini akan memicu *heap-use-after-free*.

#### 3. Runtime Check Insertion
Untuk setiap operasi *load* atau *store* memori tak langsung pada kode C++, kompiler secara otomatis menginjeksi instruksi assembly untuk memverifikasi shadow byte:

```cpp
// Kode asli C++:
*address = 42;

// Kode yang ditransformasikan oleh Kompiler (ASan instrumentation):
byte* shadow_address = (address >> 3) + Offset;
if (*shadow_address != 0) {
    if (HardMemoryCheckFailed(shadow_address, address)) {
        __asan_report_store(address); // Menghentikan eksekusi dan mencetak trace
    }
}
*address = 42; // Eksekusi asli hanya berjalan jika validasi lolos
```

#### Trade-offs
* **CPU Overhead:** Terjadi pelambatan sekitar **1.5x - 2x** akibat injeksi instruksi verifikasi bit sebelum setiap instruksi dereferensi pointer.
* **Memory Overhead:** Penggunaan RAM membengkak **2x - 3x**. Ini disebabkan oleh reservasi ruang tabel *shadow memory* dan alokasi padding *redzone* pada setiap blok variabel.

### 4. Best Practices & Common Pitfalls

#### Do's
* **Jalankan di CI/CD Pipeline:** Selalu jalankan *Unit Test* dan *Integration Test* dengan binary yang dikompilasi menggunakan `-fsanitize=address,undefined`. Ini menangkap 90%+ degradasi memori sebelum kode masuk ke *branch production*.
* **Gunakan Flag `-fno-omit-frame-pointer`:** Memastikan struktur *frame pointer* (`%rbp`) tidak dibuang untuk optimasi, sehingga *backtrace* yang diproduksi oleh sanitizer akurat hingga ke nomor baris.
* **Gunakan ASan Suppression Files:** Jika menggunakan pustaka pihak ketiga (*third-party*) berformat *closed-source* yang menghasilkan *false positive*, buat berkas supresi menggunakan env `ASAN_OPTIONS=suppressions=suppr.txt`.

#### Don'ts
* **JANGAN Pernah Deploy Binary Ber-Sanitizer ke Lingkungan Production:**
  Sanitizer dirancang untuk **Crash-Fast**. Satu *out-of-bounds read* sepele yang biasanya tidak fatal akan langsung mematikan aplikasi seketika (*Denial of Service*), di samping beban konsumsi memori dan CPU yang tinggi.
* **JANGAN Menggabungkan Sanitizer yang Saling Eksklusif:**
  AddressSanitizer (ASan) dan ThreadSanitizer (TSan) **tidak dapat** dikompilasi bersamaan ke dalam satu binary. Keduanya mendefinisikan layout *shadow memory* dan interseptor yang bentrok secara fundamental. Gunakan build target terpisah untuk ASan dan TSan.

#### Edge Cases
* **Custom Memory Allocator (Arena, Memory Pool):**
  ASan secara bawaan hanya mengintersepsi allocator standar sistem (`malloc`, `free`, `mmap`). Jika Anda membangun *Arena Allocator* kustom, ASan akan melihatnya sebagai satu alokasi *heap* raksasa yang legal, sehingga kegagalan memori internal di dalam arena tidak akan terdeteksi.
  *Solusi:* Gunakan *macro* manual bawaan ASan (`sanitizer/asan_interface.h`):
  ```cpp
  #include <sanitizer/asan_interface.h>

  // Racuni memori yang belum dialokasikan dari Arena
  ASAN_POISON_MEMORY_REGION(arena_ptr, unallocated_size);

  // Buka racun saat memori dipinjamkan ke modul lain
  ASAN_UNPOISON_MEMORY_REGION(borrowed_ptr, allocated_size);
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Batas UndefinedBehaviorSanitizer (UBSan):**
   Tulis program yang memicu:
   * *Signed Integer Overflow* (misal: `INT_MAX + 1`).
   * *Invalid Shift* (menggeser integer 32-bit sebanyak 35 bit).
   * *Misaligned Pointer Dereference* (meng-*cast* `char*` ke `uint64_t*` pada alamat ganjil).
   Kompilasi dengan flag `-fsanitize=undefined` dan amati bagaimana UBSan melacak pelanggaran ini tanpa menghentikan program jika flag `-fsanitize-recover=undefined` diaktifkan.

2. **Deteksi Data Race Menggunakan ThreadSanitizer (TSan):**
   Buat kode multithreading sederhana menggunakan dua instance `std::jthread` yang menginkrementasi satu variabel `int counter` global tanpa menggunakan `std::mutex` ataupun `std::atomic`. Kompilasi dengan `-fsanitize=thread -g`. Pelajari *data race warning* yang dihasilkan dan bandingkan perbedaan strukturnya dengan keluaran ASan.
