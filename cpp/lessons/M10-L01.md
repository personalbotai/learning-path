## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Standar C++20 membawa perubahan bahasa yang masif (Concepts, Coroutines, Modules, dan Ranges), namun Standard Template Library (STL) pada saat itu belum sepenuhnya memanfaatkan fitur-fitur baru tersebut secara optimal. **C++23 hadir sebagai standardisasi konsolidasi dan penyempurnaan library**, yang menjembatani kapabilitas bahasa C++20 ke dalam interface STL yang ergonomis, efisien, dan ramah performa (*zero-overhead abstraction*).

Migrasi ke C++23 Library berpusat pada empat pilar arsitektur utama:

```
+-----------------------------------------------------------------------+
|                         C++23 Standard Library                        |
+-------------------+--------------------+------------------+-----------+
| Error Handling    | Output I/O Modern  | Range & Coroutine| Kontainer |
| std::expected     | <print>            | std::generator   | flat_map  |
| Monadic Optional  | print / println    | views::zip/chunk | flat_set  |
+-------------------+--------------------+------------------+-----------+
```

#### A. Modern Error Handling: `std::expected<T, E>` & Monadic Operations
Sebelum C++23, penanganan galat bergantung pada:
1. **Exceptions (`throw`/`catch`)**: Memiliki biaya runtime non-deterministik saat terjadi lemparan (*stack unwinding*, alokasi memori dinamis untuk *exception object*, dan tabel *zero-cost exceptions* yang membengkakkan ukuran *binary text section*).
2. **`std::optional<T>` / Out-parameters**: Kehilangan konteks informasi penyebab kegagalan (*root cause error*).

C++23 memperkenalkan **`std::expected<T, E>`** (terinspirasi dari tipe `Result<T, E>` pada Rust atau `Either` pada Functional Programming). Secara arsitektural, `std::expected` adalah *discriminated union* berbasis *stack* yang menyimpan objek `T` jika operasi sukses (*value*) atau objek `E` jika operasi gagal (*unexpected error*). Ditambah dengan **Monadic Operations** pada `std::optional` dan `std::expected` (`.and_then()`, `.transform()`, `.or_else()`), pemrosesan data dapat dikomposisikan secara deklaratif tanpa percabangan manual `if-else` yang rentan *bug*.

#### B. Type-Safe, High-Performance I/O: `<print>`
`std::cout` (bagian dari `<iostream>`) memiliki masalah laten:
* Overhead sinkronisasi dengan C standard I/O (`stdio`).
* Format stateful (`std::setw`, `std::setprecision`) yang mengotori *stream state*.
* Konversi tipe data dinamis dan *multiple virtual dispatch calls* per operator `<<`.
* Menghasilkan ukuran binary yang besar karena ekstensifnya instansiasi template stream.

`std::print` dan `std::println` di `<print>` mengintegrasikan pustaka `{fmt}` langsung ke STL:
* Memvalidasi *format string* pada saat kompilasi (**compile-time format string validation** menggunakan `consteval`).
* Menghindari alokasi memori perantara (menulis langsung ke *native OS file descriptor* / *console buffer*).
* Menyediakan parsing UTF-8 secara *native* lintas platform (termasuk Windows Console API tanpa masalah *codepage*).

#### C. Cache-Friendly Adaptors: `std::flat_map` & `std::flat_set`
Kontainer asosiatif standar (`std::map`, `std::set`) berbasis *red-black node-based trees*. Struktur ini memicu alokasi heap per-elemen dan menyebabkan fragmentasi memori (*pointer chasing*), yang menghancurkan efisiensi CPU L1/L2/L3 *cache line*.
C++23 memperkenalkan kontainer adaptor berbasis vektor berurutan (*contiguous memory*): **`std::flat_map`** dan **`std::flat_set`**. Kontainer ini menyimpan kunci dan nilai dalam struktur array terpisah atau *interleaved* (`std::vector<Key>` dan `std::vector<Value>`), memanfaatkan pencarian biner (*binary search* / `std::lower_bound`) yang sangat ramah terhadap *prefetcher hardware CPU*.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Membaca, memvalidasi konfigurasi server dari file teks, dan memproses data port koneksi menggunakan kapabilitas C++23.

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <vector>
#include <expected>
#include <optional>
#include <print>
#include <ranges>
#include <charconv>
#include <flat_map>

enum class ParseError {
    EmptyInput,
    InvalidFormat,
    OutOfRange
};

// Utilitas konversi enum error ke string representasi
constexpr std::string_view error_to_string(ParseError err) noexcept {
    switch (err) {
        case ParseError::EmptyInput:    return "Input kosong.";
        case ParseError::InvalidFormat: return "Format data bukan integer valid.";
        case ParseError::OutOfRange:    return "Nilai port di luar batas valid (1-65535).";
    }
    return "Unknown error.";
}

// 1. Menggunakan std::expected untuk parsing numerik yang bebas exception
std::expected<uint16_t, ParseError> parse_port(std::string_view sv) noexcept {
    if (sv.empty()) {
        return std::unexpected(ParseError::EmptyInput);
    }

    uint16_t port = 0;
    auto [ptr, ec] = std::from_chars(sv.data(), sv.data() + sv.size(), port);

    if (ec == std::errc::invalid_argument) {
        return std::unexpected(ParseError::InvalidFormat);
    }
    if (ec == std::errc::result_out_of_range || port == 0) {
        return std::unexpected(ParseError::OutOfRange);
    }

    return port;
}

struct Endpoint {
    std::string host;
    uint16_t port;
};

// 2. Monadic chaining pada std::expected
std::expected<Endpoint, ParseError> create_endpoint(std::string_view host, std::string_view raw_port) {
    return parse_port(raw_port)
        .transform([host](uint16_t port) {
            // Transformasi hanya dieksekusi jika parse_port menghasilkan value
            return Endpoint{ .host = std::string(host), .port = port };
        });
}

int main() {
    // 3. Menggunakan std::flat_map untuk konfigurasi internal yang cache-efficient
    std::flat_map<std::string, std::string> raw_config = {
        {"primary", "8080"},
        {"telemetry", "9090"},
        {"malformed", "invalid_port"},
        {"overflow", "99999"}
    };

    // 4. std::println menggantikan std::cout dengan format string compile-time check
    std::println("=== Pipeline Inisialisasi Endpoint Server (C++23) ===");

    for (const auto& [service_name, raw_port] : raw_config) {
        auto result = create_endpoint(service_name, raw_port);

        // Pola pengecekan std::expected secara terstruktur
        if (result.has_value()) {
            const auto& ep = result.value();
            std::println(stdout, "[SUKSES] Service: {:<10} -> URL: {}:{}", 
                         service_name, ep.host, ep.port);
        } else {
            std::println(stderr, "[GAGAL]  Service: {:<10} -> Alasan: {}", 
                         service_name, error_to_string(result.error()));
        }
    }

    // 5. C++23 Range Adaptor (std::views::zip) untuk iterasi multipel range serentak
    std::vector<std::string_view> labels = {"DB_READ", "DB_WRITE", "AUTH"};
    std::vector<uint16_t> assigned_ports = {5432, 5433, 8000};

    std::println("\n=== Dynamic Target Binding via std::views::zip ===");
    for (auto [label, port] : std::views::zip(labels, assigned_ports)) {
        std::println("Target: {:<10} mapped to Internal Port: {}", label, port);
    }

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
* **`std::expected<T, E>` Layout**:
  Di level kompilasi, `std::expected<T, E>` direpresentasikan mirip dengan:
  ```cpp
  template <typename T, typename E>
  class expected {
      union {
          T val_;
          E unexp_;
      };
      bool has_val_; // Flag pembeda (discriminator)
  };
  ```
  Objek ini diisi secara *in-place*. Ketika sebuah fungsi mengembalikan `std::unexpected(E)`, compiler hanya mengatur flag `has_val_ = false` dan mengonstruksi payload `E` ke dalam area union. Tidak ada *context switch* kernel, tidak ada interupsi registri CPU, dan tidak ada pemanggilan fungsi runtime unwinder seperti `_Unwind_RaiseException` (pada platform Linux Itanium ABI). Nilai dapat dikembalikan langsung melalui CPU register (misal `RAX`/`RDX` di x86-64) jika ukurannya mematuhi calling conventions.

* **Format String Validation `<print>`**:
  `std::print` memanfaatkan `consteval` constructor dari `std::format_string`. Pola format dianalisis saat kompilasi. Jika spesifikasi format salah (misalnya menuliskan `"{:d}"` untuk tipe data string pointer), kompilasi akan langsung digagalkan oleh compiler sebelum binary dihasilkan:
  ```cpp
  // Contoh internal mechanism:
  template<class... Args>
  void print(format_string<Args...> fmt, Args&&... args);
  ```
  Di runtime pada Windows, `std::print` langsung memanggil Win32 API `WriteConsoleW`, melewati emulasi CRT (C Runtime) ANSI yang lambat. Pada POSIX (Linux/macOS), fungsi ini mem-bypass stream buffer iostream dan menulis langsung ke *file descriptor* via `write()` atau buffered wrapper yang mengunci *native file lock* secara minimal.

#### Alokasi Memori / Resource
* **`std::flat_map`**:
  Berbeda dengan `std::map` yang membutuhkan `sizeof(Node) = sizeof(Key) + sizeof(Value) + 3*sizeof(Pointer) + sizeof(Color)`, `std::flat_map` menyelaraskan datanya ke dalam dua kontainer kontigu kontinu (default: `std::vector`).
  
  ```
  std::map (Heap fragmented):
  [Node] -> Heap Ptr -> [Node] -> Heap Ptr -> [Node]
  
  std::flat_map (Contiguous memory):
  Keys:   [ Key1 | Key2 | Key3 | Key4 ]   <-- Cache line L1 hit!
  Values: [ Val1 | Val2 | Val3 | Val4 ]
  ```
  Hal ini secara dramatis mengeliminasi alokasi heap individu dan meminimalkan fragmentasi memori RAM.

#### Trade-offs
1. **Binary Size vs Runtime Performance**: Peningkatan penggunaan `std::expected` dengan beragam variasi tipe error `E` dapat meningkatkan ukuran kode (*code bloat*) akibat instansiasi template multipel dibandingkan dengan *single centralized exception handler*.
2. **Modifikasi `std::flat_map`**: Operasi pembacaan/pencarian adalah $\mathcal{O}(\log N)$ dengan performa CPU cache maksimal, namun operasi *insertion* dan *deletion* acak adalah $\mathcal{O}(N)$ karena elemen harus digeser (*memory moving/copying*).

### 4. Best Practices & Common Pitfalls

#### Do's
* **Gunakan `std::expected` untuk *Domain-level Errors***: Gunakan untuk kegagalan validasi, network timeout, atau format parsing yang sering terjadi secara natural dalam alur bisnis logic.
* **Pertahankan Exceptions hanya untuk *Systemic Invariants Failure***: Contoh: Kehabisan memori total (`std::bad_alloc`), korupsi thread pool, disk hardware failure.
* **Gunakan Monadic Chaining secara Komposisional**: Hindari *nested expected* seperti `std::expected<std::expected<T, E>, E>`. Manfaatkan operator `.and_then()` yang secara otomatis memipihkan (*flattening*) hasil operasi.
* **Gunakan `std::println` sebagai Pengganti Default Seluruh `std::cout`**: Menghasilkan *throughput* I/O yang lebih tinggi dan kode yang bersih dari manipulasi `\n` vs `std::endl` (yang secara implisit memicu `flush`).

#### Don'ts
* **Jangan Memanggil `.value()` pada `std::expected` Tanpa Pengecekan**:
  Memanggil `.value()` saat objek memegang status *unexpected* akan melempar exception `std::bad_expected_access<E>`, yang meniadakan tujuan awal arsitektur bebas exception.
* **Hindari `std::flat_map` untuk Workload dengan Insertion Intensif**:
  Jika dataset Anda berukuran besar dan terus menerus menerima mutasi penambahan elemen acak di runtime, `std::flat_map` akan mengalami degradasi drastis akibat alokasi ulang dan penggeseran memori (*memory shifting*).

#### Edge Cases
* **Ukuran Payload `std::expected<T, E>` yang Membengkak**:
  Jika ukuran `sizeof(E)` sangat besar (misal struct error yang menampung stack trace mentah `std::stacktrace`), seluruh instansiasi `std::expected<T, E>` akan menyerap ukuran memori sebesar `max(sizeof(T), sizeof(E)) + alignment`. Jika ini terjadi, isolasi tipe `E` ke dalam pointer tak langsung (`std::unique_ptr<E>`) untuk menjaga efisiensi transfer data di stack/register CPU.

### 5. Tantangan Eksplorasi Mandiri

1. **Refactoring Pipeline Parsial**:
   Ambil basis kode lama yang menggunakan pola:
   ```cpp
   bool try_parse_config(const std::string& path, Config& out_config, std::string& err_msg);
   ```
   Lakukan refactoring menyeluruh menggunakan `std::expected<Config, ConfigError>` beserta implementasi monadic pipeline (`.and_then()`, `.transform()`, dan `.or_else()`).

2. **Benchmark I/O Throughput**:
   Tulis program benchmark (menggunakan *Google Benchmark* atau *timer high-resolution*) yang mencetak 500.000 record terformat ke `/dev/null` (POSIX) atau `NUL` (Windows). Bandingkan latensi dan penggunaan resource antara:
   * `std::cout` + `\n` (dengan `std::ios_base::sync_with_stdio(false)`)
   * C standard library `printf`
   * C++23 `std::println`
   Analisis bagaimana direct write dan pemrosesan kompilasi format memengaruhi kecepatan pemrosesan data output Anda.
