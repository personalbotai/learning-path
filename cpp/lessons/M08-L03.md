## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Di lingkungan multithreading modern, asumsi bahwa instruksi dieksekusi persis sesuai urutan kode program (*program order*) adalah ilusi. Kompiler dan CPU modern secara agresif melakukan *reordering* (pengurutan ulang instruksi), *speculative execution*, dan *store buffering* untuk memaksimalkan instruksi per siklus (IPC). Ketika dua thread mengakses memori bersama tanpa sinkronisasi, terjadi *data race* yang memicu *Undefined Behavior* (UB) menurut standar C++.

Untuk mengatasi ini tanpa overhead *kernel-level locking* (seperti `std::mutex`), C++11 memperkenalkan **C++ Memory Model** yang didukung oleh `std::atomic<T>` dan hierarki **Memory Ordering** (`std::memory_order`). Fitur ini mendefinisikan kontrak formal antara *hardware*, kompiler, dan pemrogram mengenai kapan suatu *write* pada thread A terlihat (*visible*) oleh thread B.

Hubungan sinkronisasi formal dalam C++ Memory Model meliputi:
1. **Sequenced-before**: Hubungan evaluasi ekspresi dalam satu thread tunggal.
2. **Happens-before**: Jika operasi $A$ *happens-before* $B$, maka efek samping $A$ dijamin terlihat oleh $B$, dan $A$ mendahului $B$ secara logis.
3. **Synchronizes-with**: Hubungan antar-thread di mana sebuah *atomic store-release* menjamin bahwa seluruh modifikasi memori sebelum store tersebut akan terlihat oleh thread lain yang melakukan *atomic load-acquire* pada variabel yang sama.

```
       Thread 1 (Producer)                  Thread 2 (Consumer)
   +-------------------------+          +-------------------------+
   | Non-atomic writes:      |          |                         |
   | data = 42;              |          |                         |
   +-------------------------+          |                         |
                | (sequenced-before)    |                         |
                v                       |                         |
   +-------------------------+          |                         |
   | ready.store(release)    | -------->| ready.load(acquire)     |
   +-------------------------+  syncs-  +-------------------------+
                                with                 | (sequenced-before)
                                                     v
                                        +-------------------------+
                                        | Read non-atomic:        |
                                        | assert(data == 42);     |
                                        +-------------------------+
```

Model konsistensi memori dibagi menjadi 3 kategori utama:

1. **Sequential Consistency (`memory_order_seq_cst`)**:
   Model bawaan (*default*). Menjamin adanya urutan global (*single global clock/timeline*) yang disepakati oleh semua thread. Sangat aman, namun mematikan banyak optimasi perangkat keras karena memerlukan *full memory barrier* (seperti instruksi `MFENCE` di x86).
2. **Acquire-Release (`memory_order_acquire`, `memory_order_release`, `memory_order_acq_rel`)**:
   Tidak ada *global ordering*, sinkronisasi terjadi strictly berpasangan (*pairwise*) antar thread pengirim dan penerima.
   - `memory_order_release`: Operasi baca/tulis di program tidak boleh di-*reorder* setelah operasi release ini.
   - `memory_order_acquire`: Operasi baca/tulis di program tidak boleh di-*reorder* sebelum operasi acquire ini.
3. **Relaxed (`memory_order_relaxed`)**:
   Hanya menjamin sifat atomisitas variabel itu sendiri (tidak terjadi *tearing* memori) dan *modification order consistency* pada atomik tersebut. Tidak memberikan jaminan sinkronisasi atau urutan terhadap akses memori lainnya.

### 2. Implementasi & Contoh Kasus Nyata

Contoh implementasi berikut mendemonstrasikan pola idiomatis:
1. Producer-Consumer bebas lock (*lock-free flag*) menggunakan semantik **Acquire-Release**.
2. Modifikasi atomic menggunakan operasi CAS (*Compare-And-Swap*) via `compare_exchange_weak`.

```cpp
#include <iostream>
#include <atomic>
#include <thread>
#include <vector>
#include <cassert>
#include <string>

struct Payload {
    int id;
    char buffer[64];
};

class LockFreeChannel {
private:
    Payload payload_{};
    std::atomic<bool> has_data_{false};

public:
    // PRODUCER: Menulis payload lalu merilis flag
    void produce(int id, const std::string& msg) {
        payload_.id = id;
        snprintf(payload_.buffer, sizeof(payload_.buffer), "%s", msg.c_str());

        // memory_order_release: Menjamin penulisan ke payload_ selesai
        // dan terlihat sebelum flag has_data_ bernilai true di thread lain.
        has_data_.store(true, std::memory_order_release);
    }

    // CONSUMER: Menunggu flag terbit lalu membaca payload
    Payload consume() {
        // memory_order_acquire: Mencegah CPU membaca payload_ 
        // sebelum has_data_ terbaca bernilai true.
        while (!has_data_.load(std::memory_order_acquire)) {
            #if defined(__x86_64__) || defined(_M_X64)
                __builtin_ia32_pause(); // Mencegah pipeline stall pada spin loop
            #endif
        }
        return payload_;
    }
};

// Implementasi Lock-Free Counter dengan CAS Loop
class AtomicCounter {
private:
    std::atomic<uint64_t> count_{0};

public:
    void add_saturating(uint64_t val, uint64_t max_limit) {
        uint64_t current = count_.load(std::memory_order_relaxed);

        // compare_exchange_weak ideal untuk loop CAS karena toleran terhadap 
        // spurious failure pada arsitektur LL/SC (ARM/RISC-V)
        while (current < max_limit && 
               !count_.compare_exchange_weak(current, 
                                             std::min(current + val, max_limit),
                                             std::memory_order_release, 
                                             std::memory_order_relaxed)) {
            // current di-update otomatis dengan nilai terbaru jika CAS gagal
        }
    }

    uint64_t get() const {
        return count_.load(std::memory_order_relaxed);
    }
};

int main() {
    LockFreeChannel channel;

    std::thread consumer_thread([&channel]() {
        Payload p = channel.consume();
        std::cout << "[Consumer] Diterima ID: " << p.id 
                  << ", Pesan: " << p.buffer << "\n";
    });

    std::thread producer_thread([&channel]() {
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
        channel.produce(404, "Kernel Data Packet");
    });

    producer_thread.join();
    consumer_thread.join();

    // Uji Saturating Counter
    AtomicCounter counter;
    std::vector<std::thread> workers;
    for (int i = 0; i < 4; ++i) {
        workers.emplace_back([&counter]() {
            for (int j = 0; j < 1000; ++j) {
                counter.add_saturating(1, 2500);
            }
        });
    }

    for (auto& w : workers) {
        w.join();
    }

    std::cout << "[Counter] Final Count (Max 2500): " << counter.get() << "\n";
    assert(counter.get() == 2500);

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Hardware Memory Models
Arsitektur CPU mengimplementasikan konsistensi perangkat keras yang berbeda:
- **x86/x64 (Strong Ordering / TSO - Total Store Order)**:
  Perangkat keras sudah menjamin operasi *Read-Read*, *Write-Write*, dan *Read-Write* tidak pernah di-*reorder*. Satu-satunya *reordering* yang diizinkan CPU adalah *Store-Load* (bacaan mendahului penulisan sebelumnya yang tertahan di *Store Buffer*).
  - Akibatnya: Pada x86, `memory_order_acquire` dan `memory_order_release` adalah operasi **gratis** (zero runtime barrier overhead) di level assembler. Keduanya hanya menginstruksikan kompiler agar tidak memindahkan register/instruksi secara lokal.
  - Namun, `memory_order_seq_cst` pada operasi *store* di x86 memerlukan instruksi pengurasan *Store Buffer* seperti `LOCK XADD` atau `MFENCE`, yang memblokir eksekusi thread lokal hingga seluruh core mengakui *write* tersebut via bus snoop.
- **ARM / RISC-V / POWER (Weakly Ordered Memory)**:
  CPU bebas melakukan pengurutan ulang hampir semua urutan instruksi memori.
  - `memory_order_release` memancarkan instruksi barrier fisik (misal: `DMB ISHST` pada ARMv7, atau instruksi store khusus `STLR` pada ARMv8-A).
  - `memory_order_acquire` memancarkan instruksi pembatas baca (misal: `LDAR` pada ARMv8-A atau `DMB ISHLD`).

#### Alokasi Memori / Resource: Cache Coherency
Atomic diimplementasikan di atas protokol koherensi cache (seperti **MESI** atau **MOESI**):
1. **Cache Line Ownership**: Memori diakses per cache line (umumnya 64 byte). Untuk menulis ke variabel atomik, core CPU harus mendapatkan status *Exclusive* (E) atau *Modified* (M) atas cache line tersebut dengan mengirim sinyal *Read For Ownership* (RFO) ke interconnect/bus.
2. **Lockless Guarantee**: `std::atomic<T>::is_lock_free()` mengembalikan `true` jika operasi dieksekusi via instruksi tunggal CPU (seperti `CMPXCHG8B/16B` di x86). Jika tipe data terlalu besar (misal struct berukuran 128 byte pada arsitektur tertentu), kompiler akan membungkus manipulasi data menggunakan fallback lock internal (membuatnya tidak lock-free).

#### Trade-offs: Latensi vs Throughput
- `memory_order_seq_cst` memberikan kemudahan verifikasi kebenaran kode, tetapi mematikan teknik Out-of-Order execution core, menguras *Store Buffer*, dan mematikan speculatively issued loads.
- `memory_order_relaxed` menawarkan performa mendekati non-atomic (tanpa interupsi pipeline CPU), tetapi rawan *logic race* jika digunakan untuk koordinasi multithreading karena tidak ada garansi propagasi dependensi data.

### 4. Best Practices & Common Pitfalls

#### Do's
- Gunakan `compare_exchange_weak` di dalam loop (seperti algoritma retry CAS). Gunakan `compare_exchange_strong` hanya jika kegagalan CAS tidak ditangani di dalam loop (misal algoritma single-shot).
- Selalu periksa `std::atomic<T>::is_always_lock_free` pada tahap kompilasi (`static_assert`) untuk memastikan tipe data Anda tidak diam-diam menggunakan mutex internal.
- Gunakan `memory_order_relaxed` untuk statistik terisolasi atau metrik instrumentasi (seperti *profiler packet counter*) yang tidak mengatur kendali alur (*control flow*) thread lain.

#### Don'ts
- **Jangan gunakan `volatile` untuk multithreading**: Di C++, `volatile` tidak memberikan semantik atomisitas ataupun memory barrier hardware (hanya mencegah kompiler mengeliminasi read/write yang redundan).
- **Hindari False Sharing**: Jangan menempatkan dua variabel atomik yang sering diakses oleh thread berbeda dalam satu cache line yang sama. Gunakan `alignas(std::hardware_destructive_interference_size)`:
  ```cpp
  struct ThreadLocalCounters {
      alignas(64) std::atomic<uint64_t> core1_counter;
      alignas(64) std::atomic<uint64_t> core2_counter;
  };
  ```

#### Edge Cases
- **ABA Problem**: Terjadi pada pointer lock-free stack/queue. Thread 1 membaca nilai $A$, terinterupsi. Thread 2 mengubah $A \to B \to A$. Thread 1 melanjutkan CAS dan mengira status tidak berubah padahal data internal linked-list sudah rusak. Solusi: Gunakan *Tagged Pointers* (menyimpan counter versi di samping pointer) atau `std::atomic<std::shared_ptr<T>>` (C++20).
- **Spurious Failure**: Pada arsitektur Load-Linked/Store-Conditional (LL/SC) seperti ARM, interupsi konteks atau eviksi cache dapat menggagalkan validasi write bahkan jika nilai memori tidak berubah. Ini alasan mengapa `compare_exchange_weak` lebih disukai dalam loop.

   - Analisis skenario di mana alokasi/dealokasi memori mentah pada operasi `pop()` dapat memicu dereferensi pointer liar (*dangling pointer*) jika node langsung dihapus menggunakan operator `delete`.
