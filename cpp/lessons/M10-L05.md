## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam komputasi performa tinggi (*high-performance computing*), rekayasa *Data Pipeline* modern di C++ menuntut throughput maksimal, determinisme latensi, dan pemanfaatan perangkat keras secara efisien. Pipeline data pada dasarnya adalah perwujudan pola arsitektur **Staged Event-Driven Architecture (SEDA)** atau **Pipelined Producer-Consumer**, di mana pemrosesan data dipecah menjadi beberapa tahap independen yang dihubungkan melalui *bounded concurrent channels*.

```
[ Ingestion (Producer) ] 
       │ (Ring Buffer / SPSC Queue)
       ▼
[ Parsing & Transformation (Workers) ]
       │ (MPMC / Lock-free Channel)
       ▼
[ Aggregation & Sink (Consumer / I/O) ]
```

#### Alasan Desain Pipeline Modern Berbasis C++
1. **Zero-Allocation Hot Path**: Berbeda dengan bahasa yang mengandalkan *Garbage Collector* (GC) seperti Java atau Go yang rentan terhadap *GC pauses*, C++ memungkinkan pre-alokasi memori pada fase *initialization*. Selama pipeline berjalan (*steady-state*), mutasi data dilakukan secara *in-place* atau via semantik *move* (`std::move`) tanpa alokasi heap baru.
2. **Deterministic Backpressure**: Ketika laju produksi data melebihi laju konsumsi, antrean tak terbatas (*unbounded queues*) akan memicu lonjakan penggunaan memori hingga *Out-Of-Memory* (OOM) kill. Desain pipeline modern menggunakan *bounded buffers* yang menerapkan *backpressure* mekanis secara ketat—produsen dipaksa melambat atau memblokir eksekusi saat buffer penuh.
3. **Pemanfaatan Cache & Topologi Hardware**: Pipeline yang dirancang dengan baik memperhitungkan arsitektur CPU multicore modern. Menghindari *false sharing* antar-thread melalui perataan cache line (`alignas`), pinning thread ke core tertentu (*CPU affinity*), dan eliminasi *lock contention* melalui struktur data *lock-free* atau *fine-grained locked*.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem pipeline pemrosesan telemetri / log biner berlatensi rendah menggunakan fitur **C++20** (`std::jthread`, `std::stop_token`, dan `std::condition_variable`). Sistem ini terdiri dari tiga tahap:
1. **Ingestion**: Membaca/menghasilkan paket telemetri mentah.
2. **Transformation/Filter**: Memvalidasi integritas data dan melakukan kalkulasi analitik.
3. **Sink**: Menulis agregasi statistik ke stream output.

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <thread>
#include <stop_token>
#include <chrono>
#include <optional>
#include <new>

// Ukuran cache line tipikal x86_64
#ifdef __cpp_lib_hardware_interference_size
    using std::hardware_destructive_interference_size;
#else
    constexpr size_t hardware_destructive_interference_size = 64;
#endif

// 1. Model Data yang Dioptimalkan untuk Cache
struct alignas(hardware_destructive_interference_size) TelemetryRecord {
    uint64_t timestamp_ns;
    uint32_t device_id;
    float reading_value;
    bool is_anomaly;
};

// 2. Bounded Thread-Safe Channel dengan Mekanisme Backpressure
template <typename T, size_t Capacity>
class BoundedChannel {
public:
    bool push(T item, std::stop_token stoken) {
        std::unique_lock<std::mutex> lock(mtx_);
        // Backpressure: Tunggu jika antrean penuh kecuali ada sinyal berhenti
        cv_producer_.wait(lock, stoken, [this]() {
            return ring_buffer_.size() < Capacity;
        });

        if (stoken.stop_requested()) {
            return false;
        }

        ring_buffer_.push(std::move(item));
        lock.unlock();
        cv_consumer_.notify_one();
        return true;
    }

    std::optional<T> pop(std::stop_token stoken) {
        std::unique_lock<std::mutex> lock(mtx_);
        // Tunggu hingga data tersedia atau channel dihentikan
        cv_consumer_.wait(lock, stoken, [this]() {
            return !ring_buffer_.empty();
        });

        if (ring_buffer_.empty()) {
            return std::nullopt; // Dihentikan dan kosong
        }

        T item = std::move(ring_buffer_.front());
        ring_buffer_.pop();
        lock.unlock();
        cv_producer_.notify_one();
        return item;
    }

    void drain_and_abort() {
        cv_producer_.notify_all();
        cv_consumer_.notify_all();
    }

private:
    std::queue<T> ring_buffer_;
    std::mutex mtx_;
    std::condition_variable_any cv_producer_;
    std::condition_variable_any cv_consumer_;
};

int main() {
    constexpr size_t QUEUE_CAPACITY = 1024;
    constexpr size_t TOTAL_EVENTS = 50'000;

    BoundedChannel<TelemetryRecord, QUEUE_CAPACITY> raw_stage_channel;
    BoundedChannel<TelemetryRecord, QUEUE_CAPACITY> processed_stage_channel;

    std::cout << "[Pipeline] Memulai eksekusi data pipeline...\n";

    // Tahap 3: Consumer / Sink (Menyimpan / Menampilkan data)
    std::jthread sink_thread([&](std::stop_token stoken) {
        size_t processed_count = 0;
        size_t anomaly_count = 0;

        while (!stoken.stop_requested() || true) {
            auto item = processed_stage_channel.pop(stoken);
            if (!item.has_value()) {
                break; // Antrean kering dan thread dihentikan
            }

            processed_count++;
            if (item->is_anomaly) {
                anomaly_count++;
            }
        }
        std::cout << "[Sink] Pemrosesan selesai. Total: " << processed_count 
                  << " | Anomali: " << anomaly_count << "\n";
    });

    // Tahap 2: Transformasi & Filtering
    std::jthread transform_thread([&](std::stop_token stoken) {
        while (!stoken.stop_requested() || true) {
            auto item = raw_stage_channel.pop(stoken);
            if (!item.has_value()) {
                break;
            }

            // Operasi Transformation / Analytics
            item->is_anomaly = (item->reading_value > 85.0f);

            // Forward ke pipeline tahap berikutnya
            if (!processed_stage_channel.push(std::move(*item), stoken)) {
                break;
            }
        }
        processed_stage_channel.drain_and_abort();
    });

    // Tahap 1: Ingestion / Ingest Worker
    std::jthread ingestion_thread([&](std::stop_token stoken) {
        for (size_t i = 1; i <= TOTAL_EVENTS; ++i) {
            if (stoken.stop_requested()) break;

            TelemetryRecord record{
                .timestamp_ns = static_cast<uint64_t>(i * 100),
                .device_id = static_cast<uint32_t>(i % 64),
                .reading_value = static_cast<float>(i % 100),
                .is_anomaly = false
            };

            if (!raw_stage_channel.push(std::move(record), stoken)) {
                break;
            }
        }
        raw_stage_channel.drain_and_abort();
    });

    // Biarkan pipeline bekerja
    ingestion_thread.join();
    transform_thread.join();
    sink_thread.join();

    std::cout << "[Pipeline] Siklus hidup pipeline berhasil ditutup secara elegan.\n";
    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Condition Variable Spurious Wakeups**: Pada implementasi channel, predikat pada `cv.wait()` dievaluasi dalam loop internal kernel untuk mengantisipasi *spurious wakeups* (kondisi di mana thread bangun dari status sleep meski OS tidak menerima sinyal notifikasi eksplisit).
- **Thread Signaling Mechanics**: `notify_one()` memindahkan setidaknya satu thread dari status *Wait-Set* ke *Contention/Entry-Set* dari mutex terkait pada tingkat penjadwal OS (*futex* di Linux). Pemanggilan `unlock()` sebelum `notify_one()` dilakukan untuk meminimalkan *pessimization* (thread yang dibangunkan langsung membentur mutex yang masih terkunci).

#### Alokasi Memori & Resource
- **False Sharing Prevention**: `alignas(hardware_destructive_interference_size)` memaksa compiler menyelaraskan struct data tepat pada batas kelipatan cache line (umumnya 64 byte pada arsitektur CPU x86 dan ARM modern).
  ```
  CPU Core 0 Cache Line [ Record A (64 bytes) ]
  CPU Core 1 Cache Line [ Record B (64 bytes) ]
  ```
  Tanpa perataan ini, jika Record A dan Record B menempati satu cache line yang sama, modifikasi pada Core 0 akan memicu protokol koherensi cache (seperti MESI) untuk menginvalidasi seluruh baris di Core 1, menghasilkan penalti latensi memori drastis (*cache-line bouncing*).
- **Semantik Move**: `std::move()` mentransfer kepemilikan struktur data internal tanpa menyalin buffer memori mentah, mereduksi kompleksitas transfer data antar-tahap menjadi $O(1)$.

#### Trade-offs Desain
| Aspek | Mutex-Based Bounded Queue | Lock-Free SPSC/MPMC Ring Buffer |
| :--- | :--- | :--- |
| **Kompleksitas Kode** | Rendah, mudah dipelihara & diverifikasi. | Sangat tinggi, rentan *ABA problem*, rumit didebug. |
| **CPU Utilization** | Efisien saat *idle* (thread tidur via blocking OS). | Tinggi jika menggunakan *active spinning*/*busy-wait*. |
| **Latensi P99** | Lebih tinggi saat terjadi konkurensi ekstrem. | Sangat rendah & konsisten (*deterministic*). |
| **Backpressure** | Alami (menggunakan blocking OS-level sleep). | Memerlukan strategi eksplisit (*yield*, *spin*, atau *drop*). |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan RAII & Thread Cooperative Cancellation**: Manfaatkan `std::jthread` dan `std::stop_token` (C++20). Pola ini menjamin pipeline dapat melakukan *graceful shutdown* tanpa ada thread yang terabai (*dangling threads*) atau menimbulkan `std::terminate()`.
- **Pre-alokasikan Kapasitas Buffer**: Tentukan batas atas kapasitas channel sesuai kalkulasi *memory budget*. Terapkan strategi *backpressure* sejak awal arsitektur dibuat.
- **Rancang Pipeline Berorientasi Batch (Bila Memungkinkan)**: Jika throughput menjadi prioritas utama daripada latensi per-pesan, lakukan agregasi operasi antrean secara batch (misal: mengambil 64 elemen sekaligus per operasi lock) untuk mengamortisasi biaya sinkronisasi.

#### Don'ts
- **Hindari Alokasi Dinamis di Jalur Kritis (Hot Path)**: Jangan pernah menggunakan `new`, `std::make_shared`, atau instansiasi objek dinamis berukuran variabel di dalam loop pengolahan data. Hal ini memicu overhead `malloc` lock contention antar-thread.
- **Jangan Mengabaikan Destruksi Buffer Saat Shutdown**: Sering kali pengembang mematikan produsen, tetapi langsung mematikan konsumen tanpa mengosongkan sisa item di antrean (*draining phase*). Hal ini menyebabkan data hilang (*data loss*).

#### Edge Cases
- **Deadlock Saat Shutdown**: Jika *Producer* sedang memblokir diri karena antrean penuh, lalu *Consumer* menerima sinyal berhenti lebih dulu dan keluar dari loop, *Producer* akan tertidur selamanya (*permanent block*). Penggunaan `std::condition_variable_any` dipadukan dengan `std::stop_token` adalah solusi absolut untuk membatalkan proses tunggu (*wait*) secara serentak.

### 5. Tantangan Eksplorasi Mandiri

1. **Transformasi ke Lock-Free SPSC Queue**:
   Rancang ulang `BoundedChannel` menjadi antrean *Single-Producer Single-Consumer* (SPSC) yang sepenuhnya *lock-free* menggunakan `std::atomic<size_t>` dengan konfigurasi memori `std::memory_order_acquire` dan `std::memory_order_release`. Analisis peningkatan throughput yang diperoleh menggunakan benchmark tool.
2. **Implementasi Batching Engine**:
   Modifikasi fungsi `pop()` agar mampu menerima parameter `std::span<T>` atau batch berukuran $N$. Ukur perbandingan latensi P99 dan beban konteks switching sistem menggunakan profiling tool sistem operasi (misalnya `perf` di Linux).
3. **Drop Policy pada Overflow**:
   Tambahkan opsi kebijakan *backpressure* ketiga selain blocking: strategi *Drop-Oldest* (menimpa data terlama saat antrean penuh) yang esensial untuk pipeline telemetri real-time di mana data terkini jauh lebih penting daripada data historis.
