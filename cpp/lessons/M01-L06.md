## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++, manajemen kode skala besar sangat bergantung pada pemisahan antara **antarmuka (interface)** dan **implementasi (implementation)**. Berbeda dengan bahasa modern seperti Java atau Go yang menggunakan sistem *module* secara native (meskipun C++20 mulai mengadopsi *Modules*), C++ tradisional menggunakan model kompilasi berbasis **Translation Unit (TU)**.

*   **Header Files (`.h`, `.hpp`)**: Berfungsi sebagai "kontrak" atau deklarasi. File ini memberi tahu kompilator *apa* yang ada (fungsi, kelas, variabel) beserta tipe datanya, tanpa menyertakan logika detailnya.
*   **Namespaces**: Mekanisme arsitektural untuk mencegah *Name Collision* (bentrokan nama). Dalam proyek besar dengan banyak dependensi, sangat mungkin ada dua fungsi bernama `connect()`. Namespace membungkus entitas ke dalam ruang lingkup (scope) spesifik.
*   **Debugging & Unit Test Mini**: C++ tidak memiliki *garbage collector* atau *runtime reflection* yang aman secara default. Oleh karena itu, memvalidasi logika melalui *Unit Test* dan menggunakan makro *debugging* (seperti `assert`) sangat krusial untuk menangkap *memory corruption* atau *logic error* sedini mungkin pada fase *development*.

### 2. Implementasi & Contoh Kasus Nyata

Kita akan membuat struktur proyek sederhana yang mendemonstrasikan Header, Namespace, dan sebuah *Mini Unit Test Framework* yang dibangun dari nol menggunakan *Preprocessor Macros*.

**File 1: `math_utils.hpp` (Header - Deklarasi)**
```cpp
// Include guard modern untuk mencegah multiple inclusions dalam satu TU
#pragma once 

#include <stdexcept>

// Mendefinisikan namespace untuk mencegah bentrokan nama
namespace CoreMath {
    
    // Deklarasi fungsi
    int add(int a, int b);
    double divide(double a, double b);

    // Konstanta dalam header sebaiknya menggunakan 'inline' (C++17) atau 'constexpr'
    // agar tidak melanggar One Definition Rule (ODR)
    inline constexpr double PI = 3.14159265359;
}
```

**File 2: `math_utils.cpp` (Source - Implementasi)**
```cpp
#include "math_utils.hpp"

// Implementasi fungsi di dalam namespace
namespace CoreMath {
    
    int add(int a, int b) {
        return a + b;
    }

    double divide(double a, double b) {
        if (b == 0.0) {
            throw std::invalid_argument("Division by zero!");
        }
        return a / b;
    }
}
```

**File 3: `main.cpp` (Entry Point & Mini Unit Test)**
```cpp
#include <iostream>
#include <string>
#include "math_utils.hpp"

// ==========================================
// MINI UNIT TEST FRAMEWORK (Under the hood)
// ==========================================
int tests_run = 0;
int tests_passed = 0;

// Makro untuk testing. Menggunakan __FILE__ dan __LINE__ bawaan kompilator
#define EXPECT_EQ(expected, actual) \
    do { \
        tests_run++; \
        auto exp = (expected); \
        auto act = (actual); \
        if (exp == act) { \
            tests_passed++; \
        } else { \
            std::cerr << "[FAILED] " << __FILE__ << ":" << __LINE__ \
                      << " | Expected: " << exp << ", Got: " << act << "\n"; \
        } \
    } while(0)

// ==========================================
// TEST CASES
// ==========================================
void test_addition() {
    // Mengakses fungsi menggunakan Scope Resolution Operator (::)
    EXPECT_EQ(5, CoreMath::add(2, 3));
    EXPECT_EQ(-1, CoreMath::add(2, -3));
}

void test_division() {
    EXPECT_EQ(2.5, CoreMath::divide(5.0, 2.0));
}

int main() {
    std::cout << "Running Tests...\n";
    
    test_addition();
    test_division();

    std::cout << "====================\n";
    std::cout << "Tests Run: " << tests_run << "\n";
    std::cout << "Tests Passed: " << tests_passed << "\n";
    
    return (tests_run == tests_passed) ? 0 : 1;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

*   **Eksekusi & Runtime (Kompilasi Pipeline)**:
    1.  **Preprocessing (`-E`)**: Kompilator membaca `#include "math_utils.hpp"` dan secara harfiah *menyalin-tempel* seluruh isi file header tersebut ke dalam `main.cpp` dan `math_utils.cpp`. Makro `EXPECT_EQ` juga diekspansi menjadi kode C++ asli.
    2.  **Compilation (`-c`)**: Setiap file `.cpp` dikompilasi menjadi *Object File* (`.o` atau `.obj`) secara independen. Ini disebut *Translation Unit* (TU).
    3.  **Linking**: Linker menggabungkan `main.o` dan `math_utils.o`. Linker mencari alamat memori dari fungsi `CoreMath::add` yang dipanggil di `main.o` dan menyambungkannya dengan implementasi fisik di `math_utils.o`.
*   **Name Mangling (Namespace di Level Kompilator)**:
    Di balik layar, CPU dan Linker tidak mengerti konsep "Namespace". Kompilator C++ melakukan *Name Mangling*. Fungsi `CoreMath::add(int, int)` akan diubah namanya menjadi simbol unik yang sulit dibaca (misal: `_ZN8CoreMath3addEii`). Ini memastikan linker tidak bingung jika ada fungsi `add` di namespace lain.
*   **Alokasi Memori / Resource (ODR)**:
    Aturan *One Definition Rule* (ODR) sangat ketat. Jika Anda menulis *implementasi* fungsi (tanpa keyword `inline`) di dalam file `.hpp`, dan file `.hpp` tersebut di-include oleh dua file `.cpp` yang berbeda, Linker akan menemukan dua definisi fungsi yang sama dan menghasilkan error `multiple definition`.

### 4. Best Practices & Common Pitfalls

*   **Do's**:
    *   Selalu gunakan `#pragma once` (atau *Include Guards* klasik `#ifndef ...`) di setiap file header.
    *   Gunakan **Forward Declaration** (`class MyClass;`) di file header jika Anda hanya menggunakan *pointer* atau *reference* dari kelas tersebut, alih-alih melakukan `#include`. Ini mempercepat waktu kompilasi secara drastis.
    *   Gunakan *Anonymous Namespace* (`namespace { ... }`) di dalam file `.cpp` untuk fungsi/variabel *helper* yang hanya boleh diakses oleh file tersebut (menggantikan keyword `static` gaya C).
*   **Don'ts**:
    *   **JANGAN PERNAH** menulis `using namespace std;` di dalam file header (`.hpp`). Ini akan "mencemari" (pollute) *global namespace* dari semua file `.cpp` yang meng-include header tersebut, memicu bentrokan nama yang sulit di-debug.
    *   Jangan menulis implementasi fungsi yang kompleks di dalam header kecuali fungsi tersebut adalah `template` atau secara eksplisit ditandai `inline`.
*   **Edge Cases**:
    *   **Circular Dependency**: File `A.hpp` meng-include `B.hpp`, dan `B.hpp` meng-include `A.hpp`. Kompilator akan *stuck* atau gagal. Solusinya adalah mendesain ulang arsitektur atau menggunakan *Forward Declaration*.

### 5. Tantangan Eksplorasi Mandiri

1.  **Ekspansi Makro Test**: Modifikasi makro `EXPECT_EQ` di atas menjadi `EXPECT_THROWS(expression, exception_type)` untuk memvalidasi bahwa `CoreMath::divide(5.0, 0.0)` benar-benar melempar `std::invalid_argument`.
2.  **Inspeksi Name Mangling**: Kompilasi file `math_utils.cpp` menjadi object file (`g++ -c math_utils.cpp`), lalu gunakan tool CLI `nm math_utils.o` (di Linux/Mac) atau `dumpbin /SYMBOLS math_utils.obj` (di Windows) untuk melihat nama asli fungsi yang telah di-*mangle* oleh kompilator.
3.  **Simulasi ODR Violation**: Pindahkan implementasi fungsi `add` dari `math_utils.cpp` ke `math_utils.hpp` (tanpa keyword `inline`). Buat file `extra.cpp` yang juga meng-include `math_utils.hpp`. Coba kompilasi keduanya bersamaan dan amati pesan error dari Linker.
