### 1. Konsep & Arsitektur Mendalam

**Resource Acquisition Is Initialization (RAII)**—atau sering disebut *Scope-Bound Resource Management*—adalah idiom sentral dalam C++ yang mengikat siklus hidup sebuah *resource* (memori heap, file handle, socket jaringan, mutex lock) ke siklus hidup objek di stack (*automatic storage duration*).

```
   +--------------------------------------------------------+
   | Scope Dimulai                                          |
   |   - Konstruktor dipanggil: Akuisisi Resource           |
   |   - Eksekusi kode bisnis...                            |
   |                                                        |
   |   [Jika Terjadi Exception]                             |
   |        |                                               |
   |        v                                               |
   |   Stack Unwinding Berjalan                             |
   |        |                                               |
   |        +---> Destruktor Terpanggil Otomatis:           |
   |              Resource Dibersihkan (Deterministic)      |
   +--------------------------------------------------------+
```

#### Mengapa RAII Dibutuhkan?
Dalam bahasa seperti C, pembersihan *resource* dilakukan secara manual via fungsi destruktif eksplisit (`free()`, `close()`, `pthread_mutex_unlock()`). Pola ini rentan terhadap kebocoran (*resource leak*) jika terjadi *early return* atau alur kontrol bercabang. 

Dalam C++, dengan adanya fitur *exception*, pembersihan manual hampir mustahil dilakukan secara deterministik tanpa RAII. Ketika sebuah exception dilempar (*throw*), alur eksekusi melompat keluar dari scope normal hingga menemukan blok `catch` yang cocok. Jika *resource* tidak dibungkus dalam objek RAII, kode pembersihan manual di akhir fungsi akan dilewati, menyebabkan *leak*.

#### Tiga Tingkatan Exception Safety Guarantees
Ketika merancang komponen berbasis RAII dan exception, kode Anda harus mematuhi salah satu kontrak jaminan berikut:
1. **Basic Guarantee**: Jika exception terjadi, tidak ada invariant kelas yang rusak, dan tidak ada resource yang bocor. Namun, state objek mungkin berubah.
2. **Strong Guarantee (Commit or Rollback)**: Jika operasi gagal karena exception, state sistem kembali persis seperti sebelum operasi dimulai.
3. **Nothrow/Noexcept Guarantee**: Operasi dijamin tidak akan pernah melempar exception ke luar (`noexcept`). Wajib diterapkan pada *destructor*, *move constructor*, dan *swap*.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi RAII kelas pembungkus *POSIX File Descriptor* yang mengamankan akuisisi resource terhadap kegagalan parsing konfigurasi, mematuhi *Rule of Five*, dan menggaransi *Strong Exception Safety*.

```cpp
#include <iostream>
#include <string>
#include <stdexcept>
#include <system_error>
#include <utility>
#include <fcntl.h>
#include <unistd.h>

class SafeFileDescriptor {
private:
    int fd_{-1};

public:
    // 1. Konstruktor: Mengakuisisi resource
    explicit SafeFileDescriptor(const std::string& filepath, int flags) {
        fd_ = ::open(filepath.c_str(), flags, 0644);
        if (fd_ == -1) {
            // Lempar std::system_error dengan errno saat ini
            throw std::system_error(errno, std::generic_category(), "Gagal membuka file: " + filepath);
        }
        std::cout << "[RAII] Acquired FD: " << fd_ << '\n';
    }

    // 2. Destruktor: Menjamin pelepasan resource (noexcept secara implisit)
    ~SafeFileDescriptor() noexcept {
        if (fd_ != -1) {
            ::close(fd_);
            std::cout << "[RAII] Released FD: " << fd_ << '\n';
        }
    }

    // Non-copyable (Mencegah double close)
    SafeFileDescriptor(const SafeFileDescriptor&) = delete;
    SafeFileDescriptor& operator=(const SafeFileDescriptor&) = delete;

    // 3. Move Semantics: Transfer ownership
    SafeFileDescriptor(SafeFileDescriptor&& other) noexcept : fd_{std::exchange(other.fd_, -1)} {}

    SafeFileDescriptor& operator=(SafeFileDescriptor&& other) noexcept {
        if (this != &other) {
            if (fd_ != -1) {
                ::close(fd_);
            }
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

    [[nodiscard]] int get() const noexcept { return fd_; }
};

// Simulasi logika bisnis yang rentan error
void parsePayload(int fd) {
    std::cout << "-> Memproses payload dari FD: " << fd << '\n';
    // Mensimulasikan deteksi data korup di tengah pembacaan
    throw std::runtime_error("Corrupted payload detected!");
}

void executeTask(const std::string& path) {
    // Alokasi resource terikat pada stack scope fungsi ini
    SafeFileDescriptor file(path, O_RDWR | O_CREAT);

    // Jika parsePayload melempar exception, stack unwinding otomatis 
    // memanggil destruktor 'file' sebelum scope executeTask ditinggalkan.
    parsePayload(file.get());

    std::cout << "Task selesai secara normal.\n";
}

int main() {
    try {
        executeTask("telemetry.log");
    } catch (const std::exception& ex) {
        std::cerr << "[Exception Caught in Main]: " << ex.what() << '\n';
    }

    // Memverifikasi bahwa FD sudah tertutup bahkan saat terjadi exception
    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Zero-Cost Exception Handling
Pada arsitektur modern (x86-64 System V ABI / Itanium ABI), C++ menggunakan model **Table-Driven (Zero-Cost) Exceptions**.
- **Happy Path (Tanpa Exception)**: Tidak ada overhead instruksi tambahan. Tidak ada blok `setjmp`/`longjmp` yang dieksekusi saat memasuki blok `try`. Biaya performa = **0%**.
- **Unhappy Path (Saat `throw`)**: Terjadi *cost penalty* yang sangat masif. Compiler menghasilkan tabel metadata statis di segmen read-only ELF binary (`.eh_frame` dan `.gcc_except_table` / Language Specific Data Area (LSDA)).

Ketika `throw` dieksekusi:
1. Runtime C++ memanggil *Personality Routine* via libunwind.
2. **Phase 1 (Search Phase)**: Runtime menelusuri stack frame ke atas (menggunakan program counter/instruction pointer) untuk mencari blok `catch` yang memiliki tipe data yang kompatibel (*type match*).
3. **Phase 2 (Cleanup Phase)**: Runtime kembali menelusuri stack frame dari titik `throw` ke titik `catch`. Untuk setiap stack frame yang dilewati, runtime mengeksekusi instruksi pembersihan (*cleanup landing pad*) yang berisi panggilan ke destruktor seluruh objek otomatis yang ada di stack frame tersebut. Proses ini disebut **Stack Unwinding**.

```
[Stack Layout Saat Exception]
+-------------------------+
| main()                  | <-- Titik Catch (Phase 1 menemukan tipe cocok)
+-------------------------+
| executeTask()           | <-- Destruktor 'SafeFileDescriptor' dipanggil (Phase 2)
+-------------------------+
| parsePayload() [THROW]  | <-- Exception dialokasikan di thread-safe heap khusus
+-------------------------+
```

#### Alokasi Memori / Resource
Objek exception tidak dialokasikan di stack fungsi yang melemparnya (karena stack tersebut akan segera di-*unwind* dan dihancurkan), juga tidak melalui `malloc` standar (untuk menghindari kegagalan jika terjadi `std::bad_alloc`).
Sebagian besar runtime (seperti `libc++abi` atau `libsupc++`) mengalokasikan exception object pada *Emergency Exception Heap* thread-local yang direservasi di awal inisialisasi aplikasi.

#### Trade-offs
- **Binary Size vs Runtime Performance**: Ukuran binary membengkak sekitar 10–20% karena adanya tabel `.eh_frame`.
- **Deterministic Cleanup vs Unwinding Latency**: RAII memberikan kepastian pelepasan resource deterministik (*deterministic destruction*), namun latency saat exception dilempar jauh lebih lambat (bisa mencapai ribuan siklus CPU) dibandingkan mengembalikan error code (`std::expected` / `std::optional`).

### 4. Best Practices & Common Pitfalls

#### Do's
- **Catch by Const Reference**: Selalu gunakan `catch (const std::exception& e)`. Menangkap dengan *by-value* (`catch (std::exception e)`) memicu masalah **Object Slicing**, di mana subclass exception (seperti `std::runtime_error`) dipotong menjadi base class `std::exception`, menghilangkan informasi custom `what()`.
- **Destruktor Wajib `noexcept`**: Destruktor secara default berstatus `noexcept` sejak C++11. Pertahankan hal ini. Jika sebuah destruktor melempar exception saat stack unwinding sedang berjalan karena exception lain, runtime C++ akan langsung memanggil `std::terminate()`, mematikan aplikasi seketika.
- **Rule of Zero**: Desain kelas Anda menggunakan tipe RAII bawaan STL (`std::unique_ptr`, `std::shared_ptr`, `std::string`, `std::vector`) daripada menulis destructor manual.

#### Don'ts
- **Jangan Gunakan Raw Owning Pointer**: Hindari `new` dan `delete` mentah.
  ```cpp
  // BURUK: Memory leak jika doSomething() melempar exception!
  Widget* w = new Widget();
  doSomething();
  delete w;

  // BAIK: Exception-safe secara default
  auto w = std::make_unique<Widget>();
  doSomething();
  ```
- **Jangan Mengelola Lebih Dari Satu Resource Mentah di Satu Kelas**: Pisahkan kepemilikan resource. Jika sebuah kelas mengalokasikan dua raw pointer di konstruktornya dan pointer kedua gagal dilempar (*throws*), destruktor pointer pertama **tidak akan pernah dipanggil**, menyebabkan leak.

#### Edge Cases: Exception pada Constructor
Jika exception terjadi di dalam konstruktor, destruktor dari objek tersebut **tidak akan pernah dipanggil** karena runtime menganggap objek belum eksis seutuhnya.

```cpp
class NetworkNode {
    int* buffer;
    SafeFileDescriptor logFile; // RAII Member

public:
    NetworkNode(const std::string& path) 
        : buffer(new int[1024]),         // (1) Terlokasi
          logFile(path, O_RDWR)          // (2) JIKA INI MELEMPAR EXCEPTION:
    {
        // Destruktor ~NetworkNode() TIDAK AKAN DIPANGGIL!
        // buffer akan LEAK selamanya jika berupa raw pointer.
        // Namun, destruktor logFile (jika sudah selesai diinisialisasi) 
        // dan sub-objek lain yang sudah selesai akan di-unwind otomatis.
    }

    ~NetworkNode() {
        delete[] buffer; // Tidak akan dieksekusi jika (2) gagal!
    }
};

// SOLUSI: Ganti raw pointer 'int* buffer' dengan 'std::vector<int>'
// atau 'std::unique_ptr<int[]>'.
```

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi `ScopeGuard`**: 
   Rancang sebuah utility class `ScopeGuard` generic (menggunakan lambda/`std::function` atau templated invocable) yang mengeksekusi operasi rollback hanya jika scope keluar akibat exception (`std::uncaught_exceptions()` > 0), meniru perilaku `scope(failure)` pada bahasa D.
2. **Exception Safety Profiling**:
   Buat class matriks dinamis yang melakukan *deep-copy* pada *copy assignment operator* (`operator=`). Uji implementasi Anda dengan teknik *copy-and-swap idiom*. Buktikan bahwa teknik tersebut memberikan *Strong Exception Safety* jika alokasi memori internal tiba-tiba melempar `std::bad_alloc`.
3. **Analisis Binary dengan `objdump`**:
   Kompilasi kode pada Bagian 2 menggunakan GCC/Clang dengan flag `-fno-exceptions`, kemudian bandingkan ukuran binary dan simbol yang dihasilkan dengan kompilasi normal (`-fexceptions`). Amati bagaimana struktur `.eh_frame` menghilang dari tabel segmen ELF.
