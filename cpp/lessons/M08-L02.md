### 1. Konsep & Arsitektur Mendalam

Ketika mengeksekusi aplikasi *multithreaded*, beberapa *thread* sering kali mengakses dan memodifikasi *shared memory* secara bersamaan. Tanpa sinkronisasi, kondisi ini memicu **Data Race** dan perilaku tak terdefinisi (*Undefined Behavior*). Kompiler C++ dan arsitektur CPU modern melakukan *out-of-order execution*, *register caching*, dan *store buffering* yang dapat mengacaukan konsistensi data jika memori tidak diproteksi oleh *memory barrier* atau *synchronization primitives*.

```
[ Thread A ] ----\
                  +--> [ Critical Section: Shared Queue ] <-- (Race Condition tanpa Sinkronisasi!)
[ Thread B ] ----/
```

#### `std::mutex` (Mutual Exclusion)
`std::mutex` adalah primitif sinkronisasi dasar yang menjamin hanya ada satu *thread* yang dapat mengeksekusi blok kode tertentu (*critical section*) pada satu waktu.
- **Mekanisme**: Menggunakan instruksi atomik tingkat CPU (seperti `CMPXCHG` pada x86) yang dipadukan dengan primitif kernel (seperti `futex` di Linux atau `WaitOnAddress`/`SRWLock` di Windows).
- **Sifat**: Bersifat non-rekursif (mengunci mutex yang sudah dikunci oleh *thread* yang sama akan menyebabkan *deadlock* seketika).

#### RAII Wrappers: `std::lock_guard` vs `std::unique_lock`
Memanggil `.lock()` dan `.unlock()` secara manual pada `std::mutex` adalah anti-pattern karena rawan *deadlock* bila terjadi pengecualian (*exception*) atau *early return*. C++ menyelesaikan ini via idiom **RAII** (*Resource Acquisition Is Initialization*).

1. **`std::lock_guard<std::mutex>`**: Wrapper ringan berbasis RAII. Mengunci mutex saat konstruksi dan melepasnya saat destruksi (keluar dari *scope*). Tidak memiliki *overhead* performa dibandingkan pemanggilan manual, tetapi tidak bisa dibuka kuncinya secara manual sebelum destruksi.
2. **`std::unique_lock<std::mutex>`**: Wrapper RAII yang lebih fleksibel. Mendukung *deferred locking*, *timed locking*, serta pemanggilan `.lock()` dan `.unlock()` secara manual di dalam siklus hidupnya. `std::unique_lock` wajib digunakan bersama `std::condition_variable` karena memerlukan kemampuan untuk melepas dan mengakuisisi kembali kunci secara dinamis.

#### `std::condition_variable` (Signaling & Synchronization)
`std::condition_variable` digunakan untuk memblokir satu atau beberapa *thread* sampai *thread* lain memodifikasi kondisi dan memberikan notifikasi (*signaling*). Ini mengeliminasi *busy-waiting* (polling dalam *loop* ketat) yang memboroskan siklus CPU.

- **Hubungan dengan Mutex**: Operasi tunggu (`wait()`) harus menerima `std::unique_lock`. Secara atomik, `wait()` akan:
  1. Melepas mutex yang sedang dipegang.
  2. Menempatkan *thread* ke dalam status tidur (*sleep queue* kernel).
  3. Mengakuisisi kembali mutex sesaat sebelum keluar dari fungsi `wait()`.
- **Spurious Wakeup**: *Thread* dapat terbangun meskipun tidak ada notifikasi yang dikirimkan (karena interupsi kernel atau optimasi arsitektur multi-core). Oleh karena itu, pemanggilan `wait()` **wajib** selalu menyertakan *predicate* (kondisi boolean berulang).

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan **Thread-Safe Bounded Blocking Queue** (pola Producer-Consumer), komponen fundamental dalam arsitektur sistem seperti *thread pool* atau *logging engine*.

```cpp
#include <iostream>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <thread>
#include <vector>
#include <chrono>
#include <optional>

template <typename T>
class BoundedBlockingQueue {
public:
    explicit BoundedBlockingQueue(size_t max_capacity) 
        : capacity_(max_capacity), is_shutdown_(false) {}

    // Produsen memasukkan item ke dalam antrean
    void push(T item) {
        {
            // unique_lock diperlukan karena cv_not_full akan melepas mutex saat menunggu
            std::unique_lock<std::mutex> lock(mutex_);

            // Hindari Spurious Wakeup dengan menyertakan predicate lambda
            cv_not_full_.wait(lock, [this]() {
                return queue_.size() < capacity_ || is_shutdown_;
            });

            if (is_shutdown_) {
                throw std::runtime_error("Queue is shutdown, cannot push.");
            }

            queue_.push(std::move(item));
        } // lock otomatis dilepas di sini saat keluar scope

        // Notifikasi satu consumer bahwa data baru tersedia
        cv_not_empty_.notify_one();
    }

    // Konsumen mengambil data dari antrean
    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(mutex_);

        // Menunggu sampai antrean terisi atau sistem dimatikan
        cv_not_empty_.wait(lock, [this]() {
            return !queue_.empty() || is_shutdown_;
        });

        if (queue_.empty() && is_shutdown_) {
            return std::nullopt; // Mengindikasikan antrean telah ditutup
        }

        T item = std::move(queue_.front());
        queue_.pop();

        // Lepas lock sebelum signaling untuk mengurangi contention pada consumer
        lock.unlock();
        cv_not_full_.notify_one();

        return item;
    }

    // Menghentikan seluruh proses tunggu pada queue
    void shutdown() {
        {
            // lock_guard cukup di sini karena tidak berinteraksi dengan wait()
            std::lock_guard<std::mutex> lock(mutex_);
            is_shutdown_ = true;
        }
        // Bangunkan SEMUA thread yang tertidur di kedua condition variables
        cv_not_empty_.notify_all();
        cv_not_full_.notify_all();
    }

private:
    std::queue<T> queue_;
    const size_t capacity_;
    bool is_shutdown_;

    mutable std::mutex mutex_;
    std::condition_variable cv_not_empty_;
    std::condition_variable cv_not_full_;
};

int main() {
    BoundedBlockingQueue<int> task_queue(5);

    // Jalankan worker thread (Consumer)
    std::thread consumer([&task_queue]() {
        while (auto data = task_queue.pop()) {
            std::cout << "[Consumer] Processed item: " << *data << std::endl;
            std::this_thread::sleep_for(std::chrono::milliseconds(50));
        }
        std::cout << "[Consumer] Exiting gracefully." << std::endl;
    });

    // Jalankan produsen (Producer)
    std::thread producer([&task_queue]() {
        for (int i = 1; i <= 10; ++i) {
            task_queue.push(i);
            std::cout << "[Producer] Pushed item: " << i << std::endl;
            std::this_thread::sleep_for(std::chrono::milliseconds(20));
        }
        task_queue.shutdown();
        std::cout << "[Producer] Shutdown initiated." << std::endl;
    });

    producer.join();
    consumer.join();

    return 0;
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Mekanisme Fast-Path vs Slow-Path (Linux Futex)
Di platform Linux, `std::mutex` dibangun di atas abstraksi **futex** (*Fast Userspace Mutex*).
1. **Fast-path (Userspace)**: Percobaan penguncian pertama dilakukan murni di *userspace* menggunakan instruksi atomik (misalnya `lock cmpxchg`). Jika tidak ada kontensi, eksekusi selesai dalam beberapa *nanosecond* tanpa beralih ke kernel space.
2. **Slow-path (Kernel space)**: Jika mutex sedang dikunci *thread* lain, thread pemanggil mengeksekusi *system call* `sys_futex(FUTEX_WAIT, ...)`. Kernel akan memindahkan *thread* dari *run queue* CPU ke *wait queue* internal, memicu **Context Switch**.
3. **Condition Variable Wait**: Ketika memanggil `cv.wait(lock)`, *thread* mendaftarkan dirinya ke *wait list* milik `condition_variable` di kernel lalu melepaskan futex mutex. Saat `notify_one()` dipanggil, kernel memindahkan satu *thread* dari *CV wait queue* ke *mutex wait queue* (teknik yang dioptimasi sebagai *futex requeue* untuk mencegah *thundering herd*).

#### Alokasi Memori & Resource
- `std::mutex`: Pada Linux x86_64 dengan `libstdc++`, ukuran `std::mutex` adalah 40 byte (identik dengan `pthread_mutex_t`). Objek ini tidak mengalokasikan heap secara dinamis.
- `std::lock_guard`: Hanya menyimpan referensi ke `std::mutex&` (8 byte pada pointer 64-bit). Kompiler biasanya melakukan inlining penuh, sehingga *overhead* memorinya adalah nol (*zero-cost abstraction*).
- `std::unique_lock`: Menyimpan referensi mutex (8 byte) dan status flag kepemilikan boolean (1 byte + alignment padding = 8 byte, total ~16 byte). Memiliki *micro-overhead* tambahan dibanding `lock_guard`.

```
std::unique_lock Memory Layout (16 Bytes Typical)
+-----------------------+-----------------------+
|  std::mutex* (8 Byte) | owns_lock (bool) + Pad|
+-----------------------+-----------------------+
```

#### Trade-offs: Mutex vs Spinlock
- **Mutex Overhead**: Context switch membutuhkan biaya berkisar antara 1 hingga 3 *microsecond* karena penyimpanan register CPU, flush TLB cache, dan penjadwalan ulang scheduler kernel.
- **Kapan Mutex Unggul**: Cocok untuk *critical section* yang panjang atau waktu tunggu tak menentu (thread ditidurkan sehingga menghemat daya CPU).
- **Kapan Spinlock Lebih Unggul**: Jika latensi *critical section* diprediksi jauh lebih singkat daripada biaya context switch (di bawah hitungan puluhan *nanosecond*), namun berisiko memakan 100% core CPU jika terjadi starvation.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan RAII secara eksklusif**: Selalu gunakan `std::lock_guard` atau `std::scoped_lock` (C++17) untuk penguncian sederhana, dan `std::unique_lock` bila membutuhkan kontrol dinamis atau *condition variable*.
- **Gunakan `std::scoped_lock` untuk Multi-Mutex Locking**: Hindari *deadlock* saat harus mengunci lebih dari satu mutex sekaligus.
  ```cpp
  // Menghindari AB-BA Deadlock secara otomatis via algoritma deadlock avoidance
  std::scoped_lock lock(mutex_a, mutex_b);
  ```
- **Selalu Gunakan Predicate pada Condition Variable**: Menghindari *spurious wakeups* dan *lost wakeups*.
  ```cpp
  // BENAR:
  cv.wait(lock, [this]() { return is_ready; });
  ```
- **Kecilkan Durasi Critical Section**: Lakukan komputasi berat, I/O lambat, atau parsing di luar *critical section*. Kunci mutex hanya saat mengakses data mentah bersama.

#### Don'ts
- **DILARANG menggunakan `cv.wait()` tanpa loop predicate**:
  ```cpp
  // SALAH BESAR: Rentan terhadap spurious wakeups
  cv.wait(lock); 
  ```
- **Jangan Memanggil Fungsi Tak Dikenal (Alien Code) di Bawah Kunci**: Jangan pernah mengeksekusi *callback*, fungsi virtual, atau listener pihak ketiga saat memegang mutex. Risiko terjadinya *circular lock dependency* (*deadlock*) sangat tinggi.
- **Jangan Menyalin Objek Mutex**: `std::mutex` menghapus *copy constructor* dan *move constructor* (`= delete`). Mutex tidak dapat dipindahkan ataupun disalin.

#### Edge Cases
- **Destruksi Condition Variable**: Mendestruksi `std::condition_variable` ketika masih ada *thread* yang terblokir di dalam `.wait()` menghasilkan *Undefined Behavior* (biasanya terjadi *memory corruption* atau *SIGSEGV*). Pastikan seluruh *thread* konsumen telah berhenti dan di-`join()` sebelum siklus hidup CV berakhir.
- **Priority Inversion**: Terjadi ketika *thread* prioritas rendah memegang mutex yang dibutuhkan *thread* prioritas tinggi, namun *thread* prioritas menengah menyela eksekusi *thread* prioritas rendah tersebut. Solusi: Gunakan protokol *Priority Inheritance* jika didukung OS target (`pthread_mutexattr_setprotocol`).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Priority Task Scheduler**: Modifikasi antrean *thread-safe* di atas menjadi antrean berbasis prioritas (`std::priority_queue`). Pastikan *thread* dengan pekerjaan berprioritas tinggi selalu diproses lebih dahulu oleh sekumpulan *worker threads*. Tangani skenario ketika beberapa item dengan prioritas sama masuk berurutan (*FIFO stability*).
2. **Benchmark Contention & Profiling**: Buat program yang membandingkan performa antara *fine-grained locking* (menggunakan banyak mutex lokal) versus *coarse-grained locking* (satu mutex tunggal global) pada akses struktur data Tree atau Hash Map bertingkat. Gunakan `perf` di Linux atau *Visual Studio Concurrency Visualizer* untuk mengamati fenomena *lock contention* dan *context switches*.
