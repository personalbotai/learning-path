## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam komputasi performa tinggi dengan C++, operasi penyalinan (*copying*) objek berukuran besar atau pengelola *resource* (seperti `std::vector`, objek RAII) membebani alokasi *heap* dan siklus CPU. Sebelum modernisasi C++, mengembalikan objek *by-value* dari sebuah fungsi kerap kali menghasilkan konstruksi objek sementara (*temporary object*), operasi *copy*, dan destruksi redundan.

Untuk mengatasi ini, compiler memperkenalkan mekanisme optimasi:
1. **RVO (Return Value Optimization)**: Mengeliminasi pembuatan objek sementara ketika fungsi mengembalikan *prvalue* (*nameless temporary*).
2. **NRVO (Named Return Value Optimization)**: Mengeliminasi penyalinan ketika fungsi mengembalikan *lvalue* bernama (*named automatic object*). Objek lokal dikonstruksi langsung pada ruang memori yang disediakan oleh pemanggil (*caller*).

```
Tradisional (Tanpa Elision):
[Callee Stack: Objek Lokal] --(Copy/Move)--> [Temporary Object] --(Copy/Move)--> [Caller Stack: Target Objek]

Dengan Copy Elision / NRVO:
[Caller Stack: Target Objek] <--- Callee mengonstruksi langsung di alamat ini!
```

#### Evolusi Menuju C++17: Guaranteed Copy Elision
Sebelum standar C++17, *copy elision* hanyalah izin optimasi (*compiler optimization omission*). Compiler diizinkan melewati eksekusi *copy/move constructor* meskipun konstruktor tersebut memiliki *side effect*. Namun, tipe data tersebut **wajib** memiliki *copy* atau *move constructor* yang dapat diakses (*accessible*), meskipun tidak pernah dipanggil.

C++17 merevolusi konsep ini dengan mendefinisikan ulang *value categories*:
* **prvalue (*pure rvalue*)**: Bukan lagi sebuah objek, melainkan sebuah evaluasi ekspresi yang menghasilkan inisialisasi objek (*computation rule*).
* **Temporary Materialization**: Objek hanya akan diwujudkan (*materialized*) ketika benar-benar dibutuhkan.

Oleh karena itu, pada C++17, RVO untuk *prvalue* **bukan lagi optimasi**, melainkan aturan bahasa yang dijamin (*Mandatory Copy Elision*). Kita bahkan dapat mengembalikan tipe yang *non-copyable* dan *non-moveable* (seperti `std::mutex` yang dibungkus atau kelas dengan `= delete` pada copy/move) secara *by-value*.

#### Hubungan dengan Move Semantics: "Guaranteed Move" (Implicit Move)
Istilah "Guaranteed Move" sebenarnya merujuk pada aturan resolusi overload saat mengembalikan variabel lokal: jika NRVO gagal dilakukan oleh compiler, standar C++11/C++20 mewajibkan compiler memperlakukan ekspresi `return x;` sebagai *rvalue* secara implisit. Compiler **wajib mencoba memanggil move constructor terlebih dahulu** sebelum jatuh ke *copy constructor*.

### 2. Implementasi & Contoh Kasus Nyata

Kode di bawah mendemonstrasikan perilaku konstruksi objek melintasi RVO, NRVO, dan mekanisme *implicit move*:

```cpp
#include <iostream>
#include <utility>

class TraceableResource {
public:
    TraceableResource() { 
        std::cout << "[Default Ctor]  Objek dibuat di: " << this << '\n'; 
    }
    
    TraceableResource(const TraceableResource& other) { 
        std::cout << "[Copy Ctor]     Salin dari: " << &other << " ke: " << this << '\n'; 
    }
    
    TraceableResource(TraceableResource&& other) noexcept { 
        std::cout << "[Move Ctor]     Pindah dari: " << &other << " ke: " << this << '\n'; 
    }
    
    ~TraceableResource() { 
        std::cout << "[Destructor]    Dihancurkan di: " << this << '\n'; 
    }
};

// 1. Mandatory Elision (C++17 Guaranteed Copy Elision)
TraceableResource createByPrvalue() {
    return TraceableResource(); // Mengembalikan prvalue
}

// 2. NRVO (Named Return Value Optimization) - Bergantung optimasi compiler
TraceableResource createByNRVO() {
    TraceableResource localObj; // Dibuat di caller frame jika NRVO aktif
    // Simulasi mutasi state
    return localObj;
}

// 3. Situasi di mana NRVO Gagal -> Jatuh ke Implicit Move
TraceableResource createConditional(bool flag) {
    TraceableResource objA;
    TraceableResource objB;
    
    // Dua jalur pengembalian dengan entitas berbeda membatalkan NRVO pada mayoritas compiler
    if (flag) {
        return objA; // Implicit Move (objA diperlakukan sebagai rvalue)
    } else {
        return objB; // Implicit Move (objB diperlakukan sebagai rvalue)
    }
}

// Tipe Non-Copyable & Non-Moveable: Hanya valid dikembalikan by-value sejak C++17
class ImmovableResource {
public:
    ImmovableResource() = default;
    ImmovableResource(const ImmovableResource&) = delete;
    ImmovableResource& operator=(const ImmovableResource&) = delete;
    ImmovableResource(ImmovableResource&&) = delete;
    ImmovableResource& operator=(ImmovableResource&&) = delete;
};

ImmovableResource createImmovable() {
    return ImmovableResource(); // Valid di C++17! Tidak ada move/copy yang diperlukan.
}

int main() {
    std::cout << "--- 1. Test Guaranteed Elision (prvalue) ---\n";
    TraceableResource res1 = createByPrvalue();

    std::cout << "\n--- 2. Test NRVO ---\n";
    TraceableResource res2 = createByNRVO();

    std::cout << "\n--- 3. Test Fallback ke Implicit Move ---\n";
    TraceableResource res3 = createConditional(true);

    std::cout << "\n--- 4. Test Immovable Object ---\n";
    ImmovableResource res4 = createImmovable(); // Berhasil dikompilasi di C++17

    std::cout << "\n--- Akhir Eksekusi Scope Main ---\n";
    return 0;
}
```

#### Analisis Output:
1. **`createByPrvalue()`**: Hanya memanggil `[Default Ctor]` langsung pada alamat memori `res1`. Tidak ada jejak *Move* atau *Copy*, terlepas dari opsi optimasi compiler (`-O0` atau `-O3`).
2. **`createByNRVO()`**: Diaktifkan secara default pada build rilis (`-O2` / `-O3`). Hanya memanggil `[Default Ctor]`. Jika dikompilasi dengan `-fno-elide-constructors`, fungsi ini akan memanggil `[Default Ctor]` lalu `[Move Ctor]`.
3. **`createConditional()`**: Karena compiler tidak dapat menentukan secara statis variabel mana (`objA` atau `objB`) yang akan menempati stack pemanggil, compiler mengalokasikan keduanya di frame lokal lalu mengeksekusi `[Move Ctor]` ke `res3`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime ABI (Application Binary Interface)
Di tingkat *low-level* (misal: System V ABI untuk x86-64 atau Microsoft x64 ABI), pengembalian objek berukuran besar (biasanya `sizeof(T) > 16` bytes atau kelas non-trivial) dilakukan melalui mekanisme **Hidden Return Pointer**:

```
Stack Frame Caller               Stack Frame Callee (Fungsi)
+-----------------------+        +--------------------------+
|  Ruang untuk res      | <-----+| RDI = Alamat memori res  | (Pointer tersembunyi dikirim via register RDI/RCX)
+-----------------------+        +--------------------------+
```

1. **Caller** mengalokasikan ruang uninitialized di stack frame miliknya sendiri untuk menampung objek kembalian.
2. Alamat memori tersebut disalurkan ke fungsi **Callee** sebagai argumen tersembunyi pertama (misal via register `rdi` pada Linux x86_64 atau `rcx` pada Windows).
3. **Pada Mandatory Copy Elision / NRVO**: Alih-alih mengalokasikan memori lokal baru di stack Callee, instruksi perakitan Callee langsung mengeksekusi konstruktor objek menggunakan pointer dari register tersebut.
4. Callee mengakhiri eksekusi dan mengembalikan pointer tersebut (biasanya via register `rax`). Objek telah terkonstruksi sempurna di memori Caller tanpa ada pergeseran byte.

#### Alokasi Memori & Materialization
* **Pre-C++17**: Evaluasi `TraceableResource()` menciptakan *temporary object* di stack lokal, lalu memanggil *move constructor* ke stack Caller, kemudian memanggil destruktor *temporary*.
* **Post-C++17**: `TraceableResource()` bukanlah objek fisik melainkan *initializer expression*. Materialisasi ditunda hingga titik inisialisasi target: `TraceableResource res1 = ...`. Memori dialokasikan sekali di target destinasi, lalu diinisialisasi di tempat (*in-place construction*).

#### Trade-offs
* **Deterministic Lifetime vs Optimization**: NRVO adalah elision non-mandatory. Ini berarti destruktor objek lokal yang di-elide tidak dipanggil pada akhir fungsi, melainkan mengikuti siklus hidup objek target di pemanggil. Perbedaan implementasi antar-compiler (GCC, Clang, MSVC) dalam kapabilitas NRVO dapat menyebabkan variasi minor urutan eksekusi konstruktor/destruktor pada kasus kompleks.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Kembalikan objek *by-value***: Tulis kode yang mengembalikan nilai langsung secara natural. Percayakan kepada C++17 untuk *mandatory elision* dan C++20 untuk *implicit move*.
- **Gunakan satu titik return dengan variabel lokal tunggal** jika menginginkan NRVO yang konsisten di berbagai compiler:
  ```cpp
  MyClass buildObject() {
      MyClass result;
      // Operasi pengisian data...
      return result; // Optimal untuk NRVO
  }
  ```

#### Don'ts (Pessimization Anti-Pattern)
- **JANGAN menggunakan `std::move` pada return variabel lokal!**
  ```cpp
  // ANTI-PATTERN: Pessimization
  MyClass getBad() {
      MyClass obj;
      return std::move(obj); // KESALAHAN FATAL!
  }
  ```
  *Mengapa fatal?* `std::move(obj)` menghasilkan ekspresi bertipe *xvalue* (`MyClass&&`). Aturan bahasa melarang penerapan NRVO pada *xvalue*. Akibatnya, Anda **mematikan peluang NRVO (zero-cost)** dan **memaksa** pemanggilan *move constructor*. Jika tipe tersebut tidak mendukung *move*, kode ini bahkan akan memicu *copy constructor*.

#### Edge Cases
1. **Returning Local Parameter**:
   ```cpp
   MyClass process(MyClass param) {
       // NRVO TIDAK BISA diterapkan pada fungsi parameter!
       return param; // Standar C++ menjamin implicit move di sini, bukan copy.
   }
   ```
2. **Ternary Operator**:
   ```cpp
   return condition ? localA : localB; // Menghambat NRVO dan sering kali memicu Copy Constructor, bukan Move!
   ```
   *Solusi*: Gunakan blok `if-else` standar agar compiler dapat menerapkan *implicit move*.
