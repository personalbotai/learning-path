## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam C++ modern, manajemen memori dan performa adalah prioritas utama. Secara historis, pengembang menggunakan `std::string` dan `std::vector` untuk mengelola teks dan kumpulan data dinamis. Namun, passing objek-objek ini (bahkan dengan *const reference*) sering kali memicu overhead yang tidak perlu atau membatasi fleksibilitas API. Untuk mengatasi ini, C++ memperkenalkan konsep **Non-owning Views**.

*   **`std::string` (C++98):** Kontainer dinamis yang *memiliki* (owns) memorinya sendiri. Ia bertanggung jawab atas alokasi, dealokasi, dan mutasi string.
*   **`std::string_view` (C++17):** Abstraksi *read-only* yang ringan (non-owning) terhadap urutan karakter. Ia hanya menyimpan *pointer* ke awal karakter dan *panjang* (size) string. Ia tidak mengalokasikan memori dan sangat murah untuk disalin.
*   **`std::span` (C++20):** Konsep yang sama dengan `string_view`, tetapi digeneralisasi untuk memori yang bersebelahan (*contiguous memory*) seperti array, `std::vector`, atau `std::array`. Berbeda dengan `string_view`, elemen di dalam `std::span` dapat dimodifikasi (jika tidak dideklarasikan sebagai `const`).

**Mengapa fitur ini ada?**
Sebelum C++17, jika Anda menulis fungsi yang menerima `const std::string&`, Anda memaksa pemanggil yang memiliki *C-style string* (`const char*`) untuk melakukan alokasi heap implisit demi membuat objek `std::string` sementara. Dengan `std::string_view` dan `std::span`, API Anda menjadi agnostik terhadap kontainer aslinya, menghindari alokasi memori (Zero-overhead abstraction).

### 2. Implementasi & Contoh Kasus Nyata

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <span>
#include <vector>
#include <array>

// Menggunakan std::string_view: Menerima std::string, const char*, atau char array tanpa alokasi
std::string_view extractDomain(std::string_view email) {
    size_t atPos = email.find('@');
    if (atPos == std::string_view::npos) return "";
    
    // substr pada string_view O(1) karena hanya menggeser pointer dan mengubah size
    return email.substr(atPos + 1);
}

// Menggunakan std::span: Menerima vector, array, atau C-array secara seragam
void multiplyBuffer(std::span<int> buffer, int multiplier) {
    // std::span memungkinkan mutasi elemen (karena bukan std::span<const int>)
    for (int& val : buffer) {
        val *= multiplier;
    }
}

void printBuffer(std::span<const int> buffer) {
    for (const int val : buffer) {
        std::cout << val << " ";
    }
    std::cout << "\n";
}

int main() {
    // --- Contoh std::string & std::string_view ---
    std::string userEmail = "engineer@roadmap.sh";
    const char* c_email = "admin@cpp.org";

    // Tidak ada alokasi heap yang terjadi saat memanggil fungsi ini!
    std::cout << "Domain 1: " << extractDomain(userEmail) << "\n";
    std::cout << "Domain 2: " << extractDomain(c_email) << "\n";

    // --- Contoh std::span ---
    std::vector<int> vecData = {1, 2, 3, 4, 5};
    std::array<int, 3> arrData = {10, 20, 30};
    int c_arrData[] = {100, 200};

    // Satu fungsi (multiplyBuffer) dapat menangani 3 jenis kontainer berbeda
    multiplyBuffer(vecData, 2);
    multiplyBuffer(arrData, 2);
    multiplyBuffer(c_arrData, 2);

    std::cout << "Vector: "; printBuffer(vecData);
    std::cout << "Array: "; printBuffer(arrData);
    std::cout << "C-Array: "; printBuffer(c_arrData);

    // Subspan: Mengambil sebagian dari buffer tanpa mengkopi data
    std::span<int> subVec = std::span{vecData}.subspan(1, 3); // Elemen index 1, panjang 3
    std::cout << "Sub-vector: "; printBuffer(subVec);

    return 0;
}
```

**Penjelasan Kode:**
1.  `extractDomain` mengembalikan `std::string_view`. Operasi `substr` di sini tidak membuat string baru, melainkan hanya mengembalikan `string_view` baru dengan pointer yang digeser dan ukuran yang disesuaikan.
2.  `multiplyBuffer` menerima `std::span<int>`. Kompiler secara otomatis mendeduksi ukuran dan pointer dari `std::vector`, `std::array`, maupun *raw array*, membuat API sangat fleksibel.

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: 
  Objek `std::string_view` dan `std::span` secara internal direpresentasikan sebagai sebuah *struct* sederhana yang berisi dua anggota: sebuah pointer (`T*`) dan sebuah ukuran (`size_t`). Ukurannya di memori biasanya hanya 16 bytes (pada arsitektur 64-bit). Karena sangat kecil, mereka dirancang untuk di-*pass by value* di register CPU, yang jauh lebih cepat daripada *pass by reference* (yang memerlukan dereferensi pointer di level assembly).
- **Alokasi Memori / Resource**:
  - **SSO (Small String Optimization)**: Pada `std::string`, jika string berukuran kecil (biasanya < 15 atau 22 karakter tergantung implementasi STL), data disimpan langsung di dalam *stack footprint* objek `std::string` itu sendiri, menghindari alokasi heap. Jika lebih besar, ia akan memanggil `new` (heap allocation).
  - **Zero Allocation**: `std::string_view` dan `std::span` **tidak pernah** mengalokasikan memori. Mereka hanya "melihat" (view) memori yang sudah dialokasikan oleh entitas lain.
- **Trade-offs**: 
  Kecepatan dan efisiensi memori ditukar dengan **tanggung jawab lifetime**. Karena *views* tidak memiliki data, jika data asli (owner) dihancurkan, *view* akan menunjuk ke memori yang tidak valid (*dangling pointer*).

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Selalu *pass* `std::string_view` dan `std::span` secara **by value** (`void foo(std::string_view sv)`), bukan *by reference* (`void foo(const std::string_view& sv)`).
  - Gunakan `std::string_view` sebagai pengganti `const std::string&` pada parameter fungsi untuk API yang bersifat *read-only*.
  - Gunakan `std::span` sebagai pengganti pointer dan panjang (`void foo(int* ptr, size_t len)`) pada API C-style lama.
- **Don'ts**:
  - **JANGAN** mengembalikan `std::string_view` atau `std::span` dari sebuah fungsi jika data yang ditunjuk adalah variabel lokal (termasuk parameter fungsi yang di-*pass by value*).
  - Jangan berasumsi bahwa `std::string_view` selalu *null-terminated* (`\0` di akhir). Jika Anda perlu mem-passing data dari `string_view` ke API C lama (seperti `printf` atau `atoi`), Anda harus mengubahnya menjadi `std::string` terlebih dahulu.
- **Edge Cases**:
  - **Dangling View dari Temporary Object**:
    ```cpp
    // BAHAYA! std::string("test") adalah objek sementara (temporary).
    // Ia dihancurkan di akhir baris, membuat 'sv' menjadi dangling pointer.
    std::string_view sv = std::string("test") + " data"; 
    std::cout << sv; // Undefined Behavior!
    ```
