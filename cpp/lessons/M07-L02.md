## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum C++20, operasi transformasi dan penyaringan sekuens data (melalui STL Algorithms seperti `std::transform` atau `std::copy_if`) bersifat *eager* (langsung dievaluasi) dan *allocating* (membutuhkan kontainer perantara/alokasi memori tambahan jika dikomposisikan bertingkat). Hal ini menyebabkan inefisiensi memori cache, overhead alokasi heap via `std::vector` sementara, serta sintaks kode yang berbelit-belit (*nested function calls*).

C++20 memperkenalkan pustaka **Ranges** (`std::ranges`), dengan komponen intinya: **Views** (`std::ranges::view` dan namespace `std::views`).

```
                +---------------------------------------+
                |     Underlying Container (Owning)     |
                |        std::vector<int> (Heap)        |
                +-------------------+-------------------+
                                    ^
                                    | (holds pointer / iterator reference)
+-----------------------------------+-----------------------------------+
|                           std::views Pipe                             |
|                                                                       |
|  +---------------------------+       +-----------------------------+  |
|  | std::views::filter (Lazy) | ----> | std::views::transform (Lazy)|  |
|  +---------------------------+       +-----------------------------+  |
+-----------------------------------+-----------------------------------+
                                    |
                                    v
                           Consumer / Loop (Pull)
                     (Evaluasi komputasi terjadi di sini)
```

Secara arsitektur, sebuah *View* memiliki dua karakteristik fundamental:
1. **Non-Owning (Semantik Referensial):** View tidak memiliki (*does not own*) elemen data yang ditunjuknya. View bertindak sebagai *window* atau adaptor tipis atas data yang dimiliki kontainer lain (atau *infinite sequence* yang dihitung secara matematis seperti `std::views::iota`). Operasi *copy*, *move*, dan destruksi dari sebuah View dijamin beroperasi dalam kompleksitas waktu konstan $O(1)$.
2. **Lazy Evaluation (Evaluasi Tertunda):** Tidak ada elemen yang diproses atau ditransformasi ketika View didefinisikan atau disambungkan (*piped*). Transformasi atau penyaringan baru dieksekusi secara *on-demand* ketika iterator dari View tersebut di-*dereference* (`operator*`) atau digeser (`operator++`).

Sebuah tipe `T` memenuhi concept `std::ranges::view` jika memenuhi syarat `std::ranges::range<T>`, serta `std::movable<T>`, `std::default_initializable<T>`, dan memiliki kompleksitas $O(1)$ untuk konstruksi salin, pemindahan, dan destruksi melalui trait `std::ranges::enable_view<T>`.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah contoh pemrosesan data transaksi keuangan modern berformat C++20 menggunakan *range view composition* (`|` operator):

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <ranges>
#include <numeric>
#include <format> // C++20 std::format

struct Transaction {
    int id;
    double amount;
    bool is_cleared;
    std::string category;
};

int main() {
    // Sumber data primer (Owning container - memiliki alokasi memori)
    const std::vector<Transaction> ledger = {
        {101,  150.50, true,  "Infrastructure"},
        {102, 2300.00, false, "Marketing"},
        {103,   45.20, true,  "SaaS"},
        {104,  890.00, true,  "Infrastructure"},
        {105, 1200.00, false, "Infrastructure"},
        {106,  310.00, true,  "Infrastructure"}
    };

    // Pipeline pemrosesan non-owning & lazy:
    // Filter transaksi 'Infrastructure' yang sudah 'is_cleared',
    // ekstrak nominalnya, lalu ambil 2 transaksi pertama.
    auto processed_pipeline = ledger 
        | std::views::filter([](const Transaction& tx) {
            return tx.is_cleared && tx.category == "Infrastructure";
        })
        | std::views::transform([](const Transaction& tx) {
            return tx.amount * 1.11; // Hitung PPN 11% secara instan
        })
        | std::views::take(2);

    // Sampai titik ini: NOL komputasi matematika atau filtering yang terjadi.
    // Memori perantara = 0 byte.
    
    std::cout << "--- Hasil Pipeline Lazy ---\n";
    
    // Komputasi dieksekusi HANYA saat loop meminta elemen berikutnya
    for (double final_amount : processed_pipeline) {
        std::cout << std::format("Tagihan: ${:.2f}\n", final_amount);
    }

    // Materialisasi ke kontainer fisik (Eager evaluation)
    // Di C++20 menggunakan iterator range, C++23 dapat menggunakan std::ranges::to<std::vector>()
    std::vector<double> materialized_results(processed_pipeline.begin(), processed_pipeline.end());

    std::cout << std::format("\nTotal entri termaterialisasi: {}\n", materialized_results.size());

    return 0;
}
```

#### Penjelasan Komponen:
- Operator pipe (`|`) mengimplementasikan *Range Adaptor Closure Object* (RACO). Ekspresi `ledger | std::views::filter(...)` secara semantik setara dengan memanggil `std::views::filter(ledger, ...)`.
- Objek `processed_pipeline` berukuran sangat kecil di stack (biasanya hanya sepasang pointer iterator dasar kontainer induk ditambah fungsi predikat/transformasi).

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Iterator-Sentinel Model:** C++20 ranges memecah dependensi lama di mana batas awal dan akhir harus bertipe iterator yang persis sama (`begin` & `end`). View bekerja dengan skema **Iterator-Sentinel**. Iterator bertugas menghitung dan melangkah, sedangkan Sentinel bertugas memeriksa validitas terminasi (`it != sentinel`).
- **Mekanisme Filter View:** Saat `processed_pipeline.begin()` dipanggil pada `std::views::filter`, runtime **langsung mencari elemen pertama yang cocok** dengan predikat (mencari maju dari elemen 0). Pada setiap `operator++`, iterator secara internal melakukan loop `while (it != end && !predicate(*it))` untuk melompati elemen yang tidak memenuhi kriteria.
- **Mekanisme Transform View:** Operasi dereference `*it` tidak mengambil data mentah dari memori, melainkan langsung mengeksekusi lambda fungsi pengubah `return invoke(func, *current_it);` dan mengembalikan nilai baru secara *on-the-fly*.

#### Alokasi Memori / Resource
- **Zero Heap Allocations:** Seluruh pipeline view bekerja murni di memori stack. Overhead alokasi memori adalah $O(1)$. Tidak ada buffer penampung sementara (beda dengan pendekatan chaining konvensional yang membuat `std::vector` baru di tiap tahap).
- **Cache Locality:** Menghindari *thrashing* cache CPU karena data dibaca langsung dari lokasi kontainer asli secara kontinu (*streaming model*), bukan membaca vektor sementara yang dialokasikan di blok heap terpisah.

#### Trade-offs
- **Recomputation vs Storage Overhead:** Karena data bersifat *lazy* dan tidak dicache di memori, mengulang traversal View berkali-kali (`for` loop berulang) akan menjalankan logika predikat dan fungsi transformasi secara berulang-ulang pada tiap iterasi.
- **Compiler Inlining Pressure:** Penggunaan template berlapis untuk View adaptor meningkatkan beban kompilasi (*compile-time latency*). Optimasi binary yang dihasilkan bergantung penuh pada kemampuan compiler (`inline expansion`) untuk mereduksi rantai iterator menjadi setara *raw assembly loop*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `std::views` untuk Data Pipelining Read-Only/Projeksi:** Ini adalah alternatif superior dibanding membuat kontainer `std::vector` sementara untuk *chaining*.
- **Pastikan Lifetime Kontainer Induk Tetap Hidup:** Karena View bersifat *non-owning*, pastikan kontainer pemilik eksis lebih lama dari View itu sendiri.
- **Kombinasikan dengan Sentinel C++20:** Manfaatkan `std::views::counted` atau `std::views::iota` untuk menyusun abstraksi infinite-range tanpa alokasi tak terhingga.

#### Don'ts
- **JANGAN Mengikat View ke Temporary (Rvalue Lifetime Pitfall):**
  ```cpp
  // CRITICAL BUG: Undefined Behavior / Dangling Reference!
  auto bad_view = get_temporary_vector() | std::views::filter(predicate);
  
  for (auto x : bad_view) { 
      // Vektor temporer hasil `get_temporary_vector()` 
      // SUDAH DIHANCURKAN di akhir baris inisialisasi di atas!
  }
  ```
- **Hindari Operasi Modifikasi Bersarang (*Heavy Stateful Lambdas*):** Predikat di dalam `std::views::filter` harus *pure function* (bebas efek samping). C++ standard library tidak menjamin berapa kali predikat dievaluasi pada satu elemen.

#### Edge Cases
- **Iterasi Ganda pada Non-Cached Sub-expression:**
  Beberapa Views tidak *cacheable*. Misalnya, jika `std::views::filter` melakukan pengecekan yang intensif secara komputasi, mengakses `view.begin()` kedua kali akan mengevaluasi kembali elemen pertama dari awal.
- **Mutabilitas melalui View:**
  Jika kontainer sumber bukan `const`, transformasi dasar view memungkinkan mutasi pada kontainer asli jika lambda mengembalikan referensi non-const (`T&`). Hati-hati terhadap modifikasi tak terduga (*side effects*).

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Assembly (Godbolt):**
   Tulis perulangan manual (`for (auto& item : vec)`) yang melakukan pengecekan `if` dan operasi aritmetika, lalu bandingkan assembly yang dihasilkan dengan pipeline yang menggunakan `std::views::filter | std::views::transform` pada level optimasi `-O3`. Verifikasi apakah compiler (GCC/Clang) dapat menghasilkan kode mesin yang identik (*zero-cost abstraction*).
2. **Infinite Generator Pipeline:**
   Gunakan kombinasi `std::views::iota` (infinite range) yang dipadukan dengan `std::views::filter` untuk mencari bilangan prima, dipotong menggunakan `std::views::take(10)`. Buktikan bahwa alokasi memori tidak bertambah meskipun range input secara matematis tidak terbatas.
3. **Mendeteksi Masalah Borrowing (Dangling Iterator Check):**
   Coba berikan *rvalue container* ke `std::views::all` atau view pipeline secara langsung, lalu periksa apakah compiler Anda membangkitkan `std::ranges::dangling` iterator saat mencoba memanggil `std::ranges::begin()`. Pahami peran `std::ranges::borrowed_range` dalam mencegah masalah ini.
