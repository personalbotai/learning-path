### 1. Konsep & Arsitektur Mendalam

Sebelum C++17, alokator pada C++ Standard Template Library (STL) memiliki kelemahan arsitektural fundamental: **tipe alokator merupakan bagian dari tipe kontainer**.
```cpp
// Pre-C++17: Dua kontainer ini memiliki TIPE YANG BERBEDA secara kompilasi
std::vector<int, std::allocator<int>> v1;
std::vector<int, MyCustomPoolAlloc<int>> v2; 
// v1 = v2; // COMPILE ERROR: Incompatible types!
```
Kondisi ini menyebabkan *template bloat*, masalah *ABI incompatibility*, dan ketidakmampuan mendesain antarmuka (interface) fungsi umum yang dapat menerima kontainer dengan alokator kustom tanpa menggunakan template fungsi secara agresif.

#### Solusi C++17: Polymorphic Memory Resources (`std::pmr`)

C++17 memperkenalkan namespace `std::pmr` (berada di header `<memory_resource>`). Pendekatan ini mengubah paradigma alokasi memori dari *compile-time template policy* menjadi *runtime polymorphism*.

```
+-------------------------------------------------------+
|                    std::pmr::vector<T>                |
|  (alias dari std::vector<T, pmr::polymorphic_allocator<T>>) |
+-------------------------------------------------------+
                           |
                           v  delegasi alokasi via runtime pointer
+-------------------------------------------------------+
|              std::pmr::memory_resource (Abstract)     |
|   + allocate(bytes, alignment)                        |
|   + deallocate(p, bytes, alignment)                   |
|   + is_equal(other)                                   |
+-------------------------------------------------------+
                           |
       +-------------------+-------------------+
       |                   |                   |
       v                   v                   v
+------------------+ +-------------------+ +--------------------+
| monotonic_buffer | | pool_resource     | | new_delete_resource|
| _resource        | | (sync/unsync)     | | (Global Heap)      |
+------------------+ +-------------------+ +--------------------+
```

1. **`std::pmr::memory_resource`**: *Abstract base class* yang mengekspos pure virtual interface: `do_allocate`, `do_deallocate`, dan `do_is_equal`.
2. **`std::pmr::polymorphic_allocator<T>`**: Alokator konkrit yang membungkus pointer ke `std::pmr::memory_resource`. Karena tipenya seragam (`polymorphic_allocator<T>`), semua kontainer `std::pmr` dengan tipe elemen sama memiliki tipe C++ yang sama persis, terlepas dari backend alokasi memorinya.
3. **Allocator Propagation**: `pmr::polymorphic_allocator` otomatis menerapkan aturan propagasi alokator bersarang (*nested allocator propagation*). Jika Anda membuat `std::pmr::vector<std::pmr::string>`, alokator dari `vector` otomatis diwariskan ke setiap elemen `string` di dalamnya.

### 2. Implementasi & Contoh Kasus Nyata

Contoh skenario: Membaca dan memproses payload JSON/teks berkecepatan tinggi dalam siklus *frame/request pipeline* tanpa menyentuh *global heap* (`malloc`/`free`).

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <array>
#include <memory_resource>

void process_frame_data(std::pmr::memory_resource* mem_res) {
    // std::pmr::vector dan std::pmr::string menggunakan polymorphic_allocator
    // yang mereferensikan mem_res tanpa mengubah tipe objek container.
    std::pmr::vector<std::pmr::string> words{mem_res};
    
    // Alokasi memori string dan vector terjadi di buffer stack upstream!
    words.emplace_back("High-Performance");
    words.emplace_back("C++");
    words.emplace_back("Allocator-Aware");
    words.emplace_back("Architecture");

    for (const auto& w : words) {
        std::cout << "Word: " << w << " | Address: " << (void*)w.data() << '\n';
    }
}

int main() {
    // 1. Sediakan static buffer di Stack (misal: 64 KB)
    std::array<std::byte, 65536> stack_buffer;

    // 2. Pasang Monotonic Buffer Resource di atas buffer stack tersebut.
    // Jika stack buffer penuh, fallback ke new_delete_resource (heap).
    std::pmr::monotonic_buffer_resource mem_pool(
        stack_buffer.data(),
        stack_buffer.size(),
        std::pmr::new_delete_resource()
    );

    std::cout << "--- Menjalankan Frame 1 (Zero System Allocations) ---\n";
    process_frame_data(&mem_pool);

    // 3. Reset resource untuk frame berikutnya:
    // Monotonic buffer mendealokasikan SEMUA memori secara instan (O(1)) 
    // hanya dengan me-reset internal offset pointer-nya.
    mem_pool.release();

    std::cout << "\n--- Menjalankan Frame 2 (Memory Reuse) ---\n";
    process_frame_data(&mem_pool);

    return 0;
}
```

#### Penjelasan Kode:
- `std::array<std::byte, 65536> stack_buffer`: Memori dialokasikan langsung pada stack frame `main`, menghindari *kernel transition* atau traversal heap arena.
- `monotonic_buffer_resource`: Mengelola pointer internal yang digeser ke depan (*bump-pointer*). `deallocate()` pada resource ini adalah operasi *no-op*.
- `process_frame_data(&mem_pool)`: Menerima pointer polymorfik. Fungsi ini tidak peduli apakah memori berasal dari stack, shared memory, ataupun heap global.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Virtual Method Dispatch (vtable)**: Berbeda dengan alokator klasik yang di-*inline* secara penuh oleh compiler, alokasi via `polymorphic_allocator` mengeksekusi *indirect call* via vtable pointer:
  $$\text{Vector::push\_back} \longrightarrow \text{polymorphic\_allocator::allocate} \longrightarrow \text{memory\_resource::do\_allocate()}$$
  Meskipun terdapat biaya *virtual dispatch* (~beberapa siklus CPU), biaya ini jauh lebih kecil dibandingkan *system call* atau lock overhead dari general-purpose allocator (`ptmalloc`/`jemalloc`) yang membutuhkan ratusan siklus CPU.

#### Alokasi Memori & Resource Internals
1. **`monotonic_buffer_resource` (Bump Pointer)**:
   - Menyimpan *pointer head*. Ketika `allocate(size, align)` dipanggil:
     $$\text{current\_ptr} = \text{align\_forward}(\text{current\_ptr}, \text{align})$$
     $$\text{result} = \text{current\_ptr}; \quad \text{current\_ptr} += \text{size}$$
   - Sangat ramah terhadap L1/L2 data cache karena alokasi terjadi secara berurutan (*contiguous memory streaming*).
2. **`synchronized_pool_resource` & `unsynchronized_pool_resource`**:
   - Membagi memori ke dalam beberapa *pool* berbasis ukuran chunk tetap (*fixed-size bins*, misal: 8B, 16B, 32B, 64B, dsb.).
   - Setiap pool mengelola *freelist*. Alokasi dan dealokasi individual adalah $O(1)$. Mengeliminasi fragmentasi eksternal memori.

#### Trade-offs
| Fitur | Standar (`std::allocator`) | PMR (`std::pmr`) |
| :--- | :--- | :--- |
| **Type Uniformity** | Buruk (Tipe berubah bila alokator beda) | Sempurna (Tipe seragam) |
| **Inlining Efficiency** | Maksimal (Dapat di-*inline* penuh) | Terbatas (*Indirect call* via vtable) |
| **Heap Fragmentation** | Bergantung pada OS/Glibc malloc | Terisolasi di resource lokal |
| **Footprint Objek** | 0-byte (Stateless via EBO) | Menyimpan 1 pointer resource (8-byte) |

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan PMR untuk Sub-sistem Terisolasi**: Sangat efektif untuk *Game Loop Frame Allocator*, *Per-Request Web Server Context*, dan *Network Packet Parsing*.
- **Gunakan monotonic buffer dengan fallback**: Selalu passing upstream resource (seperti `new_delete_resource()` atau pool resource) ke konstruktor monotonic resource untuk mengantisipasi *overflow* buffer.
- **Manfaatkan Propagasi Otomatis**: Gunakan pasangan PMR secara utuh, seperti `std::pmr::vector<std::pmr::string>`, bukan `std::pmr::vector<std::string>`.

#### Don'ts
- **JANGAN Mencampur Tipe Non-PMR di dalam Kontainer PMR**:
  ```cpp
  // BURUK: std::string menggunakan std::allocator (global heap),
  // bukan memory resource dari vector!
  std::pmr::vector<std::string> bad_vec{mem_res}; 
  
  // BENAR: Keduanya berada di memori polymorfik yang sama
  std::pmr::vector<std::pmr::string> good_vec{mem_res}; 
  ```

#### Edge Cases & Memory Pitfalls
- **The Lifetime Trap (Use-After-Free fatal)**:
  `pmr::polymorphic_allocator` memegang pointer non-owning (`memory_resource*`). Masa hidup kontainer **tidak boleh melebihi** masa hidup resource penyedianya!
  ```cpp
  std::pmr::vector<int>* create_dangling_vector() {
      std::array<std::byte, 1024> local_stack;
      std::pmr::monotonic_buffer_resource local_res(local_stack.data(), local_stack.size());
      
      auto vec = new std::pmr::vector<int>(&local_res);
      vec->push_back(42);
      return vec; // BENCANA: local_res dan local_stack hancur saat return.
                  // vec sekarang mereferensikan dangling memory_resource!
  }
  ```
- **Move Semantics Antar Memory Resource yang Berbeda**:
  Jika memindahkan kontainer PMR (`std::move`):
  - Jika `this->get_allocator() == other.get_allocator()`, terjadi pemindahan pointer internal (*shallow move*, $O(1)$).
  - Jika resource **berbeda**, move assignment **secara implisit melakukan alokasi baru dan copy elements** ($O(N)$), karena memori tidak dapat dipindahtangankan lintas arena alokasi!

### 5. Tantangan Eksplorasi Mandiri

1. **Benchmark Monotonic vs Standard Heap**:
   Tulis program benchmark menggunakan Google Benchmark atau `std::chrono` untuk membandingkan alokasi $100.000$ elemen ke dalam `std::vector<std::string>` vs `std::pmr::vector<std::pmr::string>` (yang disokong oleh `pmr::monotonic_buffer_resource`). Analisis perbedaannya dalam hal cache misses dan runtime execution.
2. **Implementasi Custom `memory_resource`**:
   Buat subclass dari `std::pmr::memory_resource` bernama `logging_memory_resource` yang membungkus upstream allocator. Timpa fungsi `do_allocate` dan `do_deallocate` untuk mencetak alamat pointer, jumlah bytes, serta alignment setiap kali terjadi request alokasi.
3. **Analisis Fallback Behavior**:
   Buat `std::pmr::monotonic_buffer_resource` dengan buffer berukuran hanya $64$ byte menggunakan `std::pmr::null_memory_resource()` sebagai upstream. Uji apa yang terjadi jika Anda memasukkan data melebihi 64 byte ke dalam `std::pmr::vector<int>` (Amati exception `std::bad_alloc` yang dilempar).
