## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dart adalah bahasa dengan pewarisan tunggal (*single inheritance*). Hal ini didesain untuk menghindari *Diamond Problem* yang sering terjadi pada bahasa dengan *multiple inheritance* (seperti C++). Namun, pewarisan tunggal membatasi penggunaan ulang kode (*code reuse*) pada hierarki kelas yang tidak saling terkait. 

Di sinilah **Mixins** masuk. Mixin adalah mekanisme untuk menggunakan kembali kode kelas di berbagai hierarki kelas tanpa harus menjadi bagian dari rantai pewarisan utama. Konsep ini sangat kental dengan prinsip *Composition over Inheritance*.

- **`mixin`**: Keyword untuk mendefinisikan blok kode (state dan behavior) yang dapat disuntikkan ke kelas lain. Mixin tidak dapat diinstansiasi secara langsung.
- **`with`**: Keyword untuk menerapkan satu atau lebih mixin ke dalam sebuah kelas.
- **`on`**: Constraint (batasan) yang mendefinisikan bahwa sebuah mixin hanya dapat digunakan oleh kelas yang mewarisi kelas tertentu. Ini memungkinkan mixin untuk mengakses *member* dari *superclass* tersebut menggunakan keyword `super`.

**Arsitektur Linearization:**
Dart menyelesaikan konflik metode antar mixin menggunakan teknik *Linearization*. Ketika Anda menulis `class A extends B with C, D`, Dart tidak melakukan *multiple inheritance*. Sebaliknya, compiler membuat kelas perantara anonim secara berurutan:
1. `B` adalah *base class*.
2. Dart membuat kelas anonim `B+C` (mewarisi `B`, meng-override dengan `C`).
3. Dart membuat kelas anonim `B+C+D` (mewarisi `B+C`, meng-override dengan `D`).
4. `A` mewarisi `B+C+D`.
Oleh karena itu, mixin yang dideklarasikan paling akhir (paling kanan) memiliki prioritas tertinggi jika terjadi bentrokan nama metode.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem *Entity* pada game sederhana yang mendemonstrasikan penggunaan `mixin`, `with`, dan `on`.

```dart
// 1. Base Class
abstract class Entity {
  String get name;
  void update() => print('[$name] Updating entity state...');
}

// 2. Mixin sederhana tanpa constraint
mixin Logger {
  void logDebug(String message) {
    print('[DEBUG] ${DateTime.now().toIso8601String()}: $message');
  }
}

// 3. Mixin dengan constraint 'on'
// Mixin ini HANYA bisa digunakan oleh kelas yang merupakan turunan dari Entity.
mixin Damageable on Entity {
  int _health = 100;

  int get health => _health;

  void takeDamage(int amount) {
    _health -= amount;
    // Karena ada constraint 'on Entity', kita bisa mengakses properti 'name'
    print('[$name] took $amount damage. Health: $_health');
  }

  // Kita juga bisa meng-override metode dari superclass (Entity)
  @override
  void update() {
    super.update(); // Memanggil update() dari Entity atau Mixin sebelumnya
    if (_health <= 0) {
      print('[$name] is destroyed!');
    }
  }
}

// 4. Implementasi Kelas menggunakan 'with'
// Urutan mixin penting! Logger dieksekusi lebih dulu, lalu Damageable.
class Player extends Entity with Logger, Damageable {
  @override
  final String name;

  Player(this.name);

  void play() {
    logDebug('Player spawned.');
    update(); // Akan memanggil update() dari Damageable, yang memanggil super.update() dari Entity
    takeDamage(40);
    takeDamage(60);
    update();
  }
}

void main() {
  final player = Player('Hero');
  player.play();
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: Di tingkat *byte-code* atau *machine code* (AOT), Dart mengimplementasikan mixin melalui *Mixin Application Classes*. Deklarasi `class Player extends Entity with Logger, Damageable` secara internal dipecah menjadi rantai pewarisan linier. *Virtual Method Table* (vtable) dibangun sedemikian rupa sehingga pemanggilan `super` di dalam `Damageable` tahu persis bahwa ia harus melompat ke implementasi `Entity` (atau mixin lain yang berada di sebelah kirinya dalam deklarasi `with`).
- **Alokasi Memori / Resource**: Mixin tidak menambah *overhead* memori khusus dibandingkan pewarisan biasa. *State* (variabel instance seperti `_health`) yang dideklarasikan di dalam mixin akan dialokasikan secara langsung di dalam *memory layout* dari objek akhir (`Player`). Tidak ada objek terpisah yang dibuat untuk mixin di *heap*.
- **Trade-offs**: 
  - *Kelebihan*: Modularitas tinggi, menghindari duplikasi kode, dan menjaga hierarki pewarisan tetap dangkal (*shallow*).
  - *Kekurangan*: *Traceability* (pelacakan) kode bisa menjadi sulit. Jika sebuah kelas menggunakan 5 mixin dan memanggil metode `init()`, developer harus melacak secara manual dari kanan ke kiri mixin mana yang mengimplementasikan metode tersebut.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - Gunakan `on` constraint secara agresif. Ini memberikan *type-safety* dan mencegah mixin Anda disuntikkan ke kelas yang tidak memiliki konteks yang tepat.
  - Buat mixin sekecil dan sespesifik mungkin (*Single Responsibility Principle*). Contoh: `mixin Draggable`, `mixin Serializable`.
  - Gunakan mixin untuk *behavior* (metode) daripada *state* (variabel) jika memungkinkan, untuk menghindari kompleksitas inisialisasi memori.

- **Don'ts**:
  - Jangan membuat rantai `with` yang terlalu panjang (misal: `with A, B, C, D, E, F`). Ini adalah *code smell* yang mengindikasikan kelas tersebut melakukan terlalu banyak hal (melanggar *God Object anti-pattern*).
  - Jangan mengandalkan urutan mixin untuk logika bisnis yang kritikal tanpa dokumentasi yang jelas, karena mengubah urutan `with A, B` menjadi `with B, A` dapat merusak aplikasi jika ada metode yang saling *override*.

- **Edge Cases**:
  - **Method Collision**: Jika `MixinA` dan `MixinB` memiliki metode `void doWork()`, dan Anda menulis `class C with MixinA, MixinB`, maka pemanggilan `c.doWork()` akan mengeksekusi metode dari `MixinB` (yang paling kanan menang).
  - **Konstruktor**: Mixin **tidak boleh** mendeklarasikan konstruktor. Jika Anda membutuhkan inisialisasi yang memerlukan parameter, Anda harus menggunakan metode inisialisasi terpisah (misal: `void initMixin(int value)`) atau menggunakan *abstract class* biasa.

1. **Sistem Validasi Form**: Buatlah sebuah base class `FormField` dan beberapa mixin seperti `mixin RequiredValidation`, `mixin EmailValidation`, dan `mixin MinLengthValidation`. Gabungkan mixin-mixin tersebut menggunakan `with` pada kelas `EmailField` dan `PasswordField` untuk memvalidasi input string.

Terapkan ketiganya pada sebuah kelas dan amati urutan output di konsol untuk membuktikan bagaimana Dart menyusun rantai *linearization* dari kanan ke kiri.
