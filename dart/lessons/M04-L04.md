### 1. Konsep & Arsitektur Mendalam

Hadirnya Dart 3 menandai pergeseran paradigma besar dalam sistem tipe Dart melalui pengenalan **Pattern Matching**, **Records**, dan **Class Modifiers (terutama `sealed`)**. Sebelum Dart 3, `switch` statement terbatas pada evaluasi kesetaraan primitif (`==`), integer, string, atau enum sederhana. Pengembang terpaksa menggunakan rentetan blok `if-else` dan pengecekan tipe manual (`is`) yang rentan terhadap *runtime error* dan *boilerplate*.

Pattern matching mengubah `switch` dari sekadar struktur kontrol percabangan berbasis nilai menjadi mesin dekonstruksi data deklaratif.

```
                  [Input Data / Object]
                            │
               ┌────────────┴────────────┐
               ▼                         ▼
      [Pattern Matching]         [Destructuring]
      (Validasi Bentuk/Tipe)     (Ekstraksi Properti Instan)
               │                         │
               └────────────┬────────────┘
                            ▼
              [Guard Clause (when)] (Opsional)
                            │
                            ▼
                 [Eksekusi / Hasil Nilai]
```

#### Perbedaan Mendasar: Switch Statements vs. Switch Expressions
1. **Switch Statement**: Menjalankan blok imperatif berdasarkan pencocokan pola. Memerlukan penanganan alur kontrol manual (`break`, `return`, `throw`) dan tidak menghasilkan nilai secara langsung.
2. **Switch Expression**: Konstruksi fungsional di mana seluruh blok `switch` dievaluasi menjadi sebuah nilai (*expression*). Switch expression memiliki sifat:
   - **Exhaustive by Default**: Kompiler memvalidasi bahwa seluruh kemungkinan variasi nilai telah ditangani. Jika ada kasus yang terlewat, kode gagal dikompilasi (*compile-time error*).
   - **Sintaksis Ringkas**: Menggunakan operator fat arrow (`=>`) tanpa memerlukan *break* manual atau resiko *fall-through* yang tidak disengaja.

#### Jenis-Jenis Pattern yang Didukung
- **Type Pattern**: Menguji tipe data dan melakukan *smart-casting* secara otomatis (`case String s`).
- **Object Pattern**: Mendekonstruksi properti objek menggunakan *getters* (`case Point(:final x, :final y)`).
- **Record Pattern**: Mengekstrak nilai dari tupel/record secara posisional maupun *named* (`case (final a, final b)`).
- **Collection Pattern**: Mencocokkan struktur elemen pada `List` atau `Map` (`case [first, ..., last]`).
- **Relational & Logical Pattern**: Memeriksa batasan nilai menggunakan operator (`>`, `<`, `==`, `&&`, `||`).
- **Guards (`when`)**: Menambahkan predikat boolean arbitrary setelah pencocokan struktur berhasil.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi sistem pemrosesan transaksi *payment gateway* yang memanfaatkan `sealed classes`, *switch expressions*, dan *pattern matching* dengan guard clause.

```dart
import 'dart:math';

// 1. Hierarchy Domain menggunakan sealed class untuk menjamin exhaustiveness
sealed class PaymentMethod {}

final class CreditCard extends PaymentMethod {
  final String pan;
  final String cvv;
  final double limit;
  CreditCard(this.pan, this.cvv, this.limit);
}

final class EWallet extends PaymentMethod {
  final String provider;
  final double balance;
  EWallet(this.provider, this.balance);
}

final class CryptoPayment extends PaymentMethod {
  final String walletAddress;
  final double networkFeeGwei;
  CryptoPayment(this.walletAddress, this.networkFeeGwei);
}

// Model transaksi menggunakan Record type
typedef TransactionPayload = (double amount, PaymentMethod method, {bool isSuspicious});

// 2. Evaluasi Transaksi menggunakan Switch Expression & Destructuring
String processTransaction(TransactionPayload transaction) {
  return switch (transaction) {
    // Relational pattern & Guard clause untuk fraud detection
    (_, _, isSuspicious: true) => 
      'REJECTED: Indikasi fraud terdeteksi oleh sistem keamanan.',

    // Object pattern destructuring + relational guard pada CreditCard
    (final amount, CreditCard(:final pan, :final limit), isSuspicious: false) 
        when amount > limit =>
      'REJECTED: Limit kartu $pan tidak mencukupi (Limit: $limit, Amount: $amount).',

    // Object pattern dengan property alias extraction
    (final amount, CreditCard(:final pan), isSuspicious: false) =>
      'APPROVED: Transaksi $amount berhasil didebit dari Kartu $pan.',

    // Logical AND, Relational Pattern, dan Destructuring pada EWallet
    (final amount, EWallet(:final balance, :final provider), isSuspicious: false)
        when balance >= amount =>
      'APPROVED: Saldo $provider cukup. Sisa saldo: ${balance - amount}.',

    (final amount, EWallet(:final provider), isSuspicious: false) =>
      'REJECTED: Saldo $provider tidak mencukupi untuk nominal $amount.',

    // Matching tipe spesifik dengan kalkulasi dinamis
    (final amount, CryptoPayment(:final walletAddress, :final networkFeeGwei), isSuspicious: false)
        when networkFeeGwei > 100 =>
      'DELAYED: Biaya gas network ($networkFeeGwei Gwei) terlalu tinggi untuk $walletAddress.',

    (final amount, CryptoPayment(:final walletAddress), isSuspicious: false) =>
      'APPROVED: Transfer Crypto sebesar $amount dialokasikan ke $walletAddress.',
  };
}

void main() {
  final tx1 = (1500000.0, CreditCard('4111-XXXX-XXXX-1111', '123', 2000000.0), isSuspicious: false);
  final tx2 = (750000.0, EWallet('GoPay', 500000.0), isSuspicious: false);
  final tx3 = (50000.0, EWallet('OVO', 100000.0), isSuspicious: true);

  print(processTransaction(tx1)); // Output: APPROVED: Transaksi 1500000.0 berhasil...
  print(processTransaction(tx2)); // Output: REJECTED: Saldo GoPay tidak mencukupi...
  print(processTransaction(tx3)); // Output: REJECTED: Indikasi fraud terdeteksi...
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Kompilasi & Decision Tree (CFE)
Ketika kode di atas diproses oleh Dart *Common Front End* (CFE), *pattern matching* tidak diterjemahkan menjadi pencocokan berbasis *reflection* (seperti `dart:mirrors` yang dilarang pada Flutter/AOT). CFE mengurai pola-pola tersebut menjadi **Directed Acyclic Graph (DAG)** atau struktur pohon keputusan (*Decision Tree*) optimal.

Misalnya, pola:
```dart
CreditCard(:final pan, :final limit) when amount > limit
```
Akan diuraikan menjadi instruksi bytecode/IR (*Intermediate Representation*) primitif:
1. Pengecekan tipe polimorfik: `if (method is CreditCard)`
2. Pengambilan nilai (*getter access*): `final pan = method.pan; final limit = method.limit;`
3. Evaluasi predikat skalar: `if (amount > limit)`

#### Exhaustiveness Checking & SSA (Static Single Assignment)
Analisis kelengkapan (*exhaustiveness checking*) dihitung menggunakan **Subtype Lattice**. Karena `PaymentMethod` ditandai sebagai `sealed`, CFE mengetahui secara pasti seluruh sub-tipe langsungnya (`CreditCard`, `EWallet`, `CryptoPayment`) berada di dalam unit kompilasi/library yang sama. 
Jika kamu menghapus *case* untuk `CryptoPayment`, compiler membunyikan galat:
> *"The type 'PaymentMethod' is not exhaustively matched by the switch expression."*

Pada tahap *Optimization* (Dart AOT compiler), *field extraction* yang berulang dalam satu pattern memanfaatkan eliminasi redudansi (*Common Subexpression Elimination* - CSE) melalui format SSA. Destructuring tidak mengalokasikan memori untuk objek baru; variabel hasil dekonstruksi hanya bertindak sebagai pointer/referensi lokal pada *stack frame* menuju properti objek asli di *heap*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Class Modifier `sealed` untuk State Management**: Selalu gunakan `sealed` pada representasi state (misalnya BLoC/Cubit state atau UI union types) agar *switch expression* memaksa *exhaustive checking*.
- **Manfaatkan Sintaksis Field-Pun**: Jika nama variabel lokal sama dengan nama *field/getter*, gunakan `:final propertyName` alih-alih `propertyName: final propertyName`.
- **Gunakan Switch Expression untuk Transformasi Data Murni**: Switch expression lebih unggul dibanding statement karena bersifat *pure*, mudah di-inline, dan tidak memiliki resiko *accidental fall-through*.

#### Don'ts
- **Hindari Wildcard (`_`) Sembarangan pada Sealed Hierarchies**: Menambahkan `case _ => ...` pada *switch* yang mengevaluasi `sealed class` akan melumpuhkan fungsi *exhaustiveness checking*. Ketika ada subkelas baru ditambahkan di kemudian hari, compiler tidak akan memperingatkan kamu bahwa subkelas tersebut belum ditangani secara spesifik.
- **Jangan Menaruh Logika Asinkron/Efek Samping Masif di Switch Expression**: Switch expression dirancang untuk menghasilkan nilai secara deterministik. Jangan mengeksekusi I/O berat atau *mutation* objek global di dalam evaluasi baris expression.

#### Edge Cases & Pitfalls
- **Urutan Pattern Sangat Menentukan**: Pola dievaluasi secara sekuensial dari atas ke bawah. Pola yang lebih umum (kurang spesifik) akan menutupi (*shadow*) pola di bawahnya jika posisinya salah:
  ```dart
  // SALAH: Unreachable Case
  case CreditCard() => 'Credit card biasa';
  case CreditCard(:final limit) when limit > 1000000 => 'VIP'; // Error/Dead code!
  ```
- **Map Patterns Tidak Exhaustive**: Tidak seperti Record dan Object types, struktur `Map` dievaluasi secara dinamis pada runtime. Kompiler tidak dapat menjamin keberadaan *key* spesifik pada fase statis.

### 5. Tantangan Eksplorasi Mandiri

1. **Evaluator Abstract Syntax Tree (AST)**: Buatlah sebuah hierarki `sealed class MathExpr` yang memiliki turunan: `Number(double val)`, `Add(MathExpr left, MathExpr right)`, `Multiply(MathExpr left, MathExpr right)`, dan `Divide(MathExpr left, MathExpr right)`. Buat fungsi rekursif `double evaluate(MathExpr expr)` murni menggunakan *switch expression* yang mencakup penanganan kasus *division by zero* menggunakan *guard clause*.
2. **JSON Schema Validator Tanpa Schema Parser**: Dekonstruksi payload `Map<String, dynamic>` arbitrary dari REST API yang kompleks menggunakan kombinasi *Map pattern* dan *List pattern* (contoh: parsing `{ "data": [{ "id": 1, "attrs": { "status": "active" } }] }`) dalam satu *switch statement* tanpa melakukan *nested if* atau manual type-casting `as`.
