## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dalam pengujian perangkat lunak (software testing), kita sering kali perlu mengisolasi *System Under Test* (SUT) dari dependensi eksternalnya (seperti database, API jaringan, atau modul lain). Di sinilah konsep **Test Double** masuk, dan **Mocking** adalah salah satu teknik utamanya.

Di ekosistem Dart, terdapat dua pustaka dominan untuk mocking: **Mockito** dan **Mocktail**.
Sejak Dart memperkenalkan *Sound Null Safety*, arsitektur mocking mengalami perubahan drastis:
1. **Mockito**: Mengandalkan *Code Generation* (`build_runner`). Karena Dart tidak mengizinkan pengembalian nilai `null` pada tipe *non-nullable*, Mockito harus men-generate kelas *override* yang mengembalikan nilai *dummy* yang valid secara statis.
2. **Mocktail**: Diciptakan oleh Felix Angelov (kreator Bloc) sebagai alternatif tanpa *code generation*. Mocktail memanfaatkan fitur bawaan Dart yaitu `noSuchMethod` dan *dynamic interception* untuk merekam interaksi, namun mengharuskan developer mendaftarkan *fallback values* secara manual untuk tipe data kustom.

Secara arsitektur, sebuah objek Mock bertindak sebagai proksi. Saat metode pada Mock dipanggil, alih-alih mengeksekusi logika asli, ia akan:
1. Merekam pemanggilan tersebut (nama metode, argumen yang diberikan).
2. Mengembalikan nilai yang telah diatur sebelumnya (*Stubbing*).

### 2. Implementasi & Contoh Kasus Nyata

Kita akan menggunakan **Mocktail** karena alur kerjanya yang lebih cepat tanpa perlu menjalankan `build_runner`. Skenarionya adalah menguji `UserService` yang bergantung pada `ApiClient`.

```dart
import 'package:test/test.dart';
import 'package:mocktail/mocktail.dart';

// 1. Abstraksi Dependensi
abstract class ApiClient {
  Future<Map<String, dynamic>> fetchUser(String id);
  Future<void> updateUser(String id, User user);
}

// Model Data (JANGAN di-mock, gunakan instansiasi langsung)
class User {
  final String id;
  final String name;
  User(this.id, this.name);
}

// 2. System Under Test (SUT)
class UserService {
  final ApiClient _apiClient;

  UserService(this._apiClient);

  Future<User> getUser(String id) async {
    final data = await _apiClient.fetchUser(id);
    return User(data['id'], data['name']);
  }

  Future<void> saveUser(User user) async {
    await _apiClient.updateUser(user.id, user);
  }
}

// 3. Pembuatan Kelas Mock
class MockApiClient extends Mock implements ApiClient {}

// Karena `updateUser` menerima objek `User` (tipe kustom non-nullable),
// Mocktail membutuhkan fallback value.
class FakeUser extends Fake implements User {}

void main() {
  late UserService userService;
  late MockApiClient mockApiClient;

  setUpAll(() {
    // Registrasi fallback value untuk tipe kustom
    registerFallbackValue(FakeUser());
  });

  setUp(() {
    mockApiClient = MockApiClient();
    userService = UserService(mockApiClient);
  });

  group('UserService Tests', () {
    test('getUser mengembalikan User yang valid dari API', () async {
      // Arrange: Stubbing respons API
      const userId = '123';
      when(() => mockApiClient.fetchUser(userId)).thenAnswer(
        (_) async => {'id': '123', 'name': 'Budi'},
      );

      // Act: Eksekusi SUT
      final result = await userService.getUser(userId);

      // Assert: Verifikasi hasil
      expect(result.id, equals('123'));
      expect(result.name, equals('Budi'));
      
      // Verify: Memastikan metode dipanggil tepat 1 kali dengan argumen yang benar
      verify(() => mockApiClient.fetchUser(userId)).called(1);
    });

    test('saveUser memanggil updateUser pada ApiClient', () async {
      // Arrange
      final user = User('123', 'Budi');
      when(() => mockApiClient.updateUser(any(), any())).thenAnswer(
        (_) async => {}, // Stubbing void/Future<void>
      );

      // Act
      await userService.saveUser(user);

      // Assert & Verify
      // Menggunakan `any()` matcher untuk memverifikasi pemanggilan
      verify(() => mockApiClient.updateUser('123', any(that: isA<User>()))).called(1);
    });
    
    test('getUser melempar exception jika API gagal', () async {
      // Arrange: Stubbing error
      when(() => mockApiClient.fetchUser(any())).thenThrow(Exception('Network Error'));

      // Act & Assert
      expect(() => userService.getUser('999'), throwsA(isA<Exception>()));
    });
  });
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

- **Eksekusi & Runtime**: Kelas `Mock` dari Mocktail/Mockito meng-override metode bawaan Dart yaitu `noSuchMethod(Invocation invocation)`. Karena kelas Mock tidak mengimplementasikan metode dari antarmuka aslinya secara konkret, Dart runtime akan melempar eksekusi ke `noSuchMethod`. Di dalam metode inilah pustaka mocking mengekstrak `invocation.memberName` dan `invocation.positionalArguments`, mencocokkannya dengan aturan `when()` yang telah didefinisikan, dan mengembalikan nilai stub.
- **Alokasi Memori / Resource**: Objek Mock menyimpan *state* internal berupa daftar `List<Invocation>` untuk melacak setiap kali ia dipanggil. Jika objek Mock digunakan ulang di berbagai *test case* tanpa di-reset, memori akan membengkak dan *state* akan bocor (*test pollution*). Oleh karena itu, inisialisasi ulang di dalam `setUp()` atau pemanggilan `reset(mockObject)` sangat krusial.
- **Trade-offs**: 
  - **Mockito**: Aman secara tipe (*type-safe*) secara bawaan, tetapi memperlambat *build time* karena harus menjalankan `dart run build_runner build`.
  - **Mocktail**: Siklus iterasi sangat cepat (tanpa *codegen*), tetapi mengorbankan sedikit kenyamanan karena developer harus mendaftarkan `registerFallbackValue` secara manual untuk setiap tipe data kustom *non-nullable* yang digunakan sebagai argumen dalam metode yang di-mock.

### 4. Best Practices & Common Pitfalls

- **Do's**:
  - **Mock pada batas arsitektur (Boundaries)**: Mock antarmuka eksternal seperti HTTP Client, Repositori, atau akses File System.
  - **Gunakan `setUp` dan `tearDown`**: Selalu inisialisasi ulang SUT dan Mock di dalam `setUp` agar setiap *test case* berjalan secara independen (prinsip *Isolated*).
  - **Gunakan `Fake` untuk Data Class**: Jika metode membutuhkan objek kompleks, buat kelas `Fake` alih-alih me-mock entitas data.
- **Don'ts**:
  - **Jangan Me-mock Data/Model/Entitas**: Objek seperti `User`, `Product`, atau DTO harus diinisialisasi secara nyata. Me-mock data class adalah *anti-pattern* yang membuat tes rapuh.
  - **Jangan Me-mock SUT**: Jangan pernah me-mock kelas yang sedang Anda uji.
  - **Over-verification**: Jangan memverifikasi setiap pemanggilan metode jika itu tidak relevan dengan *behavior* yang sedang diuji. Ini membuat tes menjadi kaku (*brittle tests*).
- **Edge Cases**: 
  - Saat me-mock metode yang mengembalikan `Stream`, gunakan `thenAnswer((_) => Stream.value(data))` atau `Stream.fromIterable([...])`. Jangan gunakan `thenReturn` untuk Stream/Future karena akan dievaluasi terlalu cepat.

### 5. Tantangan Eksplorasi Mandiri

1. Buatlah sebuah kelas `AuthBloc` atau `AuthController` yang bergantung pada `AuthRepository`. Tulis tes menggunakan Mocktail untuk memverifikasi bahwa ketika `login()` dipanggil, state berubah menjadi `Loading`, lalu `Success` jika repository mengembalikan token, dan `Error` jika repository melempar exception.
2. Eksplorasi penggunaan `verifyInOrder([...])` di Mocktail/Mockito untuk memastikan bahwa dua metode pada dependensi dipanggil dalam urutan yang spesifik dan ketat.
3. Cobalah me-mock sebuah metode yang mengembalikan `Stream` dan gunakan matcher `emitsInOrder` pada pengujian Anda untuk memvalidasi aliran data asinkron.
