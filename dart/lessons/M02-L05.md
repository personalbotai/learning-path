### 1. Konsep & Arsitektur Mendalam

Di dalam ekosistem Dart, orientasi objek didesain dengan pendekatan pragmatis: **setiap deklarasi `class` secara otomatis mendefinisikan sebuah *implicit interface* (antarmuka implisit)**. Berbeda dengan bahasa seperti Java, TypeScript, atau C# yang memerlukan kata kunci terpisah seperti `interface`, Dart menganggap semua kelas memiliki kontrak tipe data publik yang setara dengan bentuk strukturnya.

```
       [ Class Declaration ]
             /        \
   (Implementasi)    (Tipe/Kontrak)
         |                 |
     Extends          Implements
         |                 |
 Mewarisi Logika      Mewarisi Kontrak
    & State          (Wajib override semua)
```

#### Abstract Class
Kelas abstrak dideklarasikan menggunakan kata kunci `abstract` (atau di Dart 3+: `abstract class` / `abstract interface class`). Karakteristik utamanya:
1. **Tidak Dapat Diinstansiasi Langsung**: Compiler melarang alokasi memori instance langsung via constructor bawaan (kecuali menggunakan *factory constructor*).
2. **Hybrid Structure**: Dapat menampung *concrete methods* (lengkap dengan implementasi logika dan state/field) serta *abstract methods* (hanya deklarasi signature fungsi).
3. **Pondasi Hirarki**: Ditujukan sebagai *base class* dalam arsitektur pewarisan tunggal (*single inheritance* via `extends`).

#### Implicit Interfaces
Setiap kali kelas didefinisikan di Dart—baik itu kelas konkrit maupun kelas abstrak—Dart runtime dan type system secara otomatis mengekstrak representasi interface publik dari kelas tersebut. Interface implisit ini mencakup:
- Semua instance methods publik.
- Semua instance variables (yang diekspos sebagai implicit *getter* dan *setter*).
- Semua interface lain yang diimplementasikan oleh kelas tersebut.

Ketika kelas lain menggunakan kata kunci `implements`, kelas tersebut **hanya meminjam kontrak tipe data**. Kelas pengimplementasi **tidak mewarisi** sebaris kode logika maupun alokasi variabel memori dari kelas target. Hal ini memungkinkan implementasi *multiple inheritance of interfaces* di Dart tanpa terkena kompleksitas *diamond problem* yang lazim terjadi pada multiple inheritance of implementation.

Sejak Dart 3.0, kontrol arsitektural diperketat dengan penambahan modifier:
- `abstract interface class`: Menegaskan bahwa kelas ini murni merupakan kontrak antarmuka. Tidak bisa diinstansiasi langsung dan tidak bisa di-*extends* di luar library asalnya, melainkan harus di-*implements*.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Pembangunan layer persistensi data (*Repository Pattern*) untuk *Payment Gateway* yang mendukung swapping antara implementasi nyata (Stripe) dan simulasi pengujian (*Mock*).

```dart
// 1. Kontrak murni menggunakan idiom modern Dart 3: 'abstract interface class'
abstract interface class PaymentRepository {
  // Implicit interface mengekspos signature ini
  Future<bool> processPayment(double amount, String currency);
  String get gatewayIdentifier;
}

// 2. Base abstract class untuk berbagi logika dasar logging dan validasi (extends)
abstract class BaseAnalyticsPaymentGateway implements PaymentRepository {
  final String environment;

  BaseAnalyticsPaymentGateway({required this.environment});

  // Concrete method: diwariskan ke subclass
  void logTransaction(String status, double amount) {
    print('[$environment] Log ($gatewayIdentifier): Transaction $status -> $amount');
  }

  // Abstract method turunan dari PaymentRepository tetap harus dipenuhi oleh subclass konkret
}

// 3. Implementasi Produksi: Mewarisi state & method dari BaseAnalyticsPaymentGateway
class StripePaymentGateway extends BaseAnalyticsPaymentGateway {
  final String _apiKey;

  StripePaymentGateway({
    required String apiKey,
    required super.environment,
  }) : _apiKey = apiKey;

  @override
  String get gatewayIdentifier => 'STRIPE_API_V3';

  @override
  Future<bool> processPayment(double amount, String currency) async {
    if (_apiKey.isEmpty) {
      logTransaction('FAILED: Invalid Key', amount);
      return false;
    }
    // Simulasi Network Call
    logTransaction('SUCCESS', amount);
    return true;
  }
}

// 4. Implementasi Testing (Mock): Memanfaatkan Implicit Interface
// Menggunakan 'implements', BUKAN 'extends' -> Bebas dari dependency logging/state
class MockPaymentGateway implements PaymentRepository {
  bool shouldSucceed = true;
  final List<double> processedAmounts = [];

  @override
  String get gatewayIdentifier => 'MOCK_IN_MEMORY';

  @override
  Future<bool> processPayment(double amount, String currency) async {
    processedAmounts.add(amount);
    return shouldSucceed;
  }
}

void main() async {
  // Polimorfisme: Variabel bertipe PaymentRepository dapat menampung implementasi mana pun
  final PaymentRepository liveGateway = StripePaymentGateway(
    apiKey: 'sk_live_12345',
    environment: 'production',
  );

  final PaymentRepository mockGateway = MockPaymentGateway();

  await liveGateway.processPayment(150.0, 'USD');
  await mockGateway.processPayment(99.0, 'USD');
}
```

#### Analisis Alur Eksekusi:
- `PaymentRepository` menjadi acuan *type contract*.
- `StripePaymentGateway` melakukan `extends BaseAnalyticsPaymentGateway`, sehingga mewarisi field `environment` dan logika `logTransaction()`.
- `MockPaymentGateway` melakukan `implements PaymentRepository`. Ia sama sekali tidak mewarisi `environment` atau `logTransaction()`, mengisolasi mock object sepenuhnya dari fungsionalitas base class yang berpotensi memiliki efek samping (*side effects*).

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Virtual Method Table & Inline Caching)
- **VTable (Virtual Method Table) Mapping**: Dart VM mengompilasi method calls menggunakan *polymorphic inline caching* (PIC) dan VTable. Ketika kelas meng-`extends` kelas lain, pointer fungsi pada VTable subclass merujuk langsung ke implementasi superclass kecuali di-*override*. Sebaliknya, ketika kelas meng-`implements` implicit interface, Dart compiler menyusun VTable yang sama sekali baru untuk kelas tersebut; seluruh pointer method harus diarahkan ke implementasi lokal.
- **Tear-offs & Method Dispatch**: Resolusi pemanggilan method melalui tipe interface di AOT (Ahead-of-Time) binary diselesaikan menggunakan *dispatch table* terkompresi. Jika compiler menganalisis bahwa tipe hanya memiliki satu implementasi (*monomorphic call site*), pemanggilan fungsi didevirtualisasi (*devirtualized*) langsung ke alamat fungsi target, memangkas overhead pemanggilan virtual.

#### Alokasi Memori / Resource Layout
```
Memory Layout (Heap):

[ Extends ]
StripePaymentGateway Instance
+-----------------------------------+
| Object Header (Type Args, Flags)  |
| field: environment (from Base)    | -> Pointer memory layout berurutan
| field: _apiKey (from Subclass)    |
+-----------------------------------+

[ Implements ]
MockPaymentGateway Instance
+-----------------------------------+
| Object Header (Type Args, Flags)  |
| field: shouldSucceed (Local)      | -> Layout independen,
| field: processedAmounts (Local)   |    tanpa jejak layout Base/Interface
+-----------------------------------+
```
- Objek hasil `extends` memiliki *memory layout* terpadu: memori dialokasikan untuk menampung field dari kelas dasar ditambah field tambahan dari subclass.
- Objek hasil `implements` hanya mengalokasikan memori untuk field yang didefinisikan langsung oleh kelas itu sendiri. Tidak ada fragmentasi memori atau alokasi *hidden state* dari interface target.

#### Trade-offs
- **`extends`**: Meminimalkan boilerplate kode logika, tetapi mengikat subclass secara rigid ke *internal state* superclass (*tight coupling* / *Fragile Base Class problem*).
- **`implements`**: Menciptakan batasan arsitektur yang bersih (*low coupling*), namun memaksa penulisan ulang seluruh getter, setter, dan method, yang dapat memicu duplikasi kode jika digunakan tidak tepat.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan kata kunci `abstract interface class` (Dart 3+)** jika kelas murni hanya mendefinisikan API signature tanpa implementasi logic default. Ini mengekspresikan intent arsitektur secara eksplisit kepada compiler.
- **Terapkan Interface Segregation Principle (ISP)**: Buat implicit interface yang kecil dan spesifik. Pisahkan interface besar menjadi beberapa interface modular agar kelas yang meng-`implements` tidak dipaksa mengimplementasikan method yang tidak relevan.
- **Manfaatkan `implements` untuk Mocking & Testing**: Saat menulis unit test, selalu gunakan `implements` terhadap implicit interface untuk menghindari pemanggilan logika `init()` atau akses I/O tidak disengaja dari kelas konkrit asli.

#### Don'ts
- **Hindari meng-`implements` kelas konkrit dengan state yang masif**: Jika kelas `A` memiliki 20 field, meng-`implements A` di kelas `B` memaksa kamu mendefinisikan ulang 20 getter/setter tersebut secara manual.
- **Jangan abaikan anotasi `@override`**: Selalu gunakan `@override` ketika mengimplementasikan method dari implicit interface untuk mencegah *silent bug* akibat *signature mismatch* saat interface diperbarui.

#### Edge Cases
- **Field vs Accessor Equivalence**: Dalam implicit interface Dart, variabel adalah getter/setter.
  ```dart
  class Source {
    int count = 0; // Menghasilkan implicit getter & setter
  }

  class Destination implements Source {
    // Valid: Mengimplementasikan field dengan explicit getter & setter
    @override
    int get count => 42;

    @override
    set count(int value) {
      // Custom logic
    }
  }
  ```
  Ini berarti implementor memiliki fleksibilitas penuh untuk mengubah *stored property* menjadi *computed property*.

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Factory Constructor pada Abstract Class**: Buat sebuah `abstract class CacheService` dengan *abstract methods* `get()` dan `set()`. Tambahkan `factory CacheService(String type)` pada kelas abstrak tersebut yang mengembalikan instance konkrit (`MemoryCache` atau `DiskCache`) berdasarkan argumen `type`. Analisis mengapa pola ini tidak melanggar aturan abstraksi Dart.
2. **Interface Modifier Constraint**: Ubah deklarasi kelas menjadi `interface class Repository {}` (tanpa kata kunci `abstract`). Cobalah untuk melakukan `extends` dan `implements` terhadap kelas tersebut di dalam file yang sama versus di file yang berbeda (`import`). Amati respons compiler terkait proteksi inheritance Dart 3.
