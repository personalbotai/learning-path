### 1. Konsep & Arsitektur Mendalam

Dalam paradigma UI deklaratif (seperti Flutter), antarmuka adalah proyeksi langsung dari state aplikasi:

$$\text{UI} = f(\text{State})$$

Tantangan utama rekayasa perangkat lunak pada skala besar bukanlah merender UI, melainkan mengelola mutasi, siklus hidup, dan propagasi dependensi state tersebut. Tiga pilar state management utama dalam ekosistem Dart—**Provider**, **Riverpod**, dan **BLoC**—menyelesaikan masalah ini dengan pendekatan arsitektur yang secara fundamental berbeda.

```
+-----------------------------------------------------------------------------+
|                                ARSITEKTUR                                   |
+-----------------------------------+-----------------------------------------+
| Provider (Tree-Bound)             | [Widget Tree]                           |
| - InheritedElement O(1) Lookup    |    └── InheritedProvider (ChangeNotifier)
| - Mengikuti Lifecycle Widget      |          └── Consumer -> rebuild()          |
+-----------------------------------+-----------------------------------------+
| Riverpod (Graph-Based)            | [ProviderContainer] (Di luar UI Tree)   |
| - Unidirectional Dependency Graph |    Node A ──> Node B ──> Node C         |
| - Compile-time Safe / No BuildCtx |          └── Listeners (Widgets / Svc)      |
+-----------------------------------+-----------------------------------------+
| BLoC (Event-Driven State Machine) | [Sink / Events] ──> [Stream Transformer]|
| - Async CSP (Streams/Pipes)       |                              │          |
| - Transisi State Deterministik    | [State Stream]  <── [Event Handler]     |
+-----------------------------------+-----------------------------------------+
```

#### A. Provider: Tree-Bound Context Injection
Provider membungkus primitif bawaan Flutter, yaitu `InheritedWidget`. 
- **Arsitektur**: Bergantung penuh pada pohon widget (`BuildContext`). Data dialirkan ke bawah (*downward*), dan mutasi dipicu melalui `ChangeNotifier` (pola Observer).
- **Mekanisme Lookup**: Menggunakan registri internal di Flutter Engine: `BuildContext.dependOnInheritedWidgetOfExactType<T>()`. Operasi ini berkecepatan $O(1)$ karena Flutter menyimpan referensi `InheritedElement` dalam peta hash internal (`Map<Type, InheritedElement>`) di setiap node `Element`.
- **Kelemahan Inheren**: Rentan terhadap runtime exception (`ProviderNotFoundException`) jika developer memanggil dependensi di luar subtree yang valid. Provider juga terikat erat dengan siklus hidup widget, menyulitkan orkestrasi dependensi non-UI murni.

#### B. Riverpod: Reactive Dependency Graph
Riverpod merancang ulang Provider dari nol tanpa dependensi pada Flutter widget tree (`BuildContext`).
- **Arsitektur**: Riverpod memodelkan state sebagai **Directed Acyclic Graph (DAG)** di dalam memori murni Dart melalui `ProviderContainer`.
- **Mekanisme**: Setiap provider adalah deklarasi global atomik statis. Provider tidak menyimpan state itu sendiri; provider hanyalah *kunci* (lensa deklaratif) untuk mengakses node dalam `ProviderContainer`.
- **Keunggulan**: Evaluasi dependensi terjadi secara reaktif: jika node A bergantung pada node B, dan B bermutasi, node A otomatis ditandai *dirty* dan dikalkulasi ulang. Terjadi pada level kompilasi (*compile-time safe*), tanpa risiko runtime lookup failure.

#### C. BLoC (Business Logic Component): Event-Driven State Machine
BLoC memisahkan domain logika bisnis murni dari UI menggunakan abstraksi antrean asinkron (Dart Streams).
- **Arsitektur**: Mengimplementasikan *Communicating Sequential Processes (CSP)* parsial dan prinsip *Finite State Machine (FSM)*.
- **Mekanisme**: UI tidak pernah memanggil fungsi/metode secara langsung pada BLoC. UI hanya menembakkan `Event` ke dalam `StreamSink`. BLoC memproses event tersebut melalui event transformer (mengelola *concurrency*, *debounce*, atau *buffer*), menjalankan logika bisnis, lalu mengalirkan immutable `State` baru melalui `Stream`.
- **Keunggulan**: Aliran data strictly unidirectional dan deterministik. Semua mutasi tercatat, terisolasi, serta sangat mudah diuji (*unit test*) karena input hanya berupa stream data dan output berupa stream data.

### 2. Implementasi & Contoh Kasus Nyata

Berikut implementasi murni pada level Dart untuk membedah internal engine dari **Reactive Notifier (Prinsip Riverpod/Signals)** dan **Stream State Machine (Prinsip BLoC)** tanpa ketergantungan pihak ketiga.

#### Implementasi 1: The Reactive Core (Prinsip Riverpod)
Mengimplementasikan graf dependensi reaktif murni menggunakan Observer pattern tingkat lanjut.

```dart
import 'dart:async';

/// Base class Node Reaktif dalam Dependency Graph
abstract class ObservableNode<T> {
  T _value;
  final Set<void Function()> _listeners = {};

  ObservableNode(this._value);

  T get value {
    // Daftarkan dependensi otomatis jika sedang dalam siklus komputasi aktif
    ComputationContext.current?._registerDependency(this);
    return _value;
  }

  void addListener(void Function() listener) => _listeners.add(listener);
  void removeListener(void Function() listener) => _listeners.remove(listener);

  void _notifyListeners() {
    // Mencegah mutasi set saat iterasi
    final List<void Function()> iterationList = List.from(_listeners);
    for (final listener in iterationList) {
      listener();
    }
  }
}

/// Node yang nilainya dapat dimutasi secara eksternal (StateProvider / Notifier)
class StateNode<T> extends ObservableNode<T> {
  StateNode(super.initialValue);

  void set(T newValue) {
    if (_value == newValue) return; // Mencegah siklus komputasi berlebih
    _value = newValue;
    _notifyListeners();
  }
}

/// Konteks penangkap dependensi reaktif secara dinamis
class ComputationContext {
  static ComputedNode<dynamic>? current;
}

/// Node yang nilainya dihitung dari dependensi lain (Provider kombinasi / Computed)
class ComputedNode<T> extends ObservableNode<T> {
  final T Function() _compute;
  final Set<ObservableNode<dynamic>> _dependencies = {};

  ComputedNode(this._compute) : super(_compute()) {
    _evaluate();
  }

  void _registerDependency(ObservableNode<dynamic> dependency) {
    if (_dependencies.add(dependency)) {
      dependency.addListener(_onDependencyChanged);
    }
  }

  void _onDependencyChanged() {
    _evaluate();
  }

  void _evaluate() {
    final previousContext = ComputationContext.current;
    ComputationContext.current = this;
    try {
      final newValue = _compute();
      if (_value != newValue) {
        _value = newValue;
        _notifyListeners();
      }
    } finally {
      ComputationContext.current = previousContext;
    }
  }

  void dispose() {
    for (final dep in _dependencies) {
      dep.removeListener(_onDependencyChanged);
    }
    _dependencies.clear();
    _listeners.clear();
  }
}
```

#### Implementasi 2: The Finite State Machine Core (Prinsip BLoC)
Mengimplementasikan BLoC engine berbasis Dart `StreamController` dengan event transformer terisolasi.

```dart
/// Kontrak Event dan State yang Immutable
abstract class BlocEvent {}
abstract class BlocState {}

// Implementasi Kasus Kasir / Checkout
class CheckoutItemAdded extends BlocEvent {
  final String itemName;
  final double price;
  CheckoutItemAdded(this.itemName, this.price);
}

class CheckoutSubmitted extends BlocEvent {}

class CartState extends BlocState {
  final List<String> items;
  final double totalPrice;
  final bool isSubmitting;

  CartState({
    required this.items,
    required this.totalPrice,
    this.isSubmitting = false,
  });

  CartState copyWith({
    List<String>? items,
    double? totalPrice,
    bool? isSubmitting,
  }) {
    return CartState(
      items: items ?? this.items,
      totalPrice: totalPrice ?? this.totalPrice,
      isSubmitting: isSubmitting ?? this.isSubmitting,
    );
  }
}

/// Core BLoC Engine
abstract class Bloc<E extends BlocEvent, S extends BlocState> {
  final StreamController<E> _eventController = StreamController<E>();
  final StreamController<S> _stateController = StreamController<S>.broadcast();
  
  late S _state;
  S get state => _state;
  Stream<S> get stream => _stateController.stream;

  Bloc(S initialState) {
    _state = initialState;
    // Bind stream processor ke Dart Event Loop
    _eventController.stream.listen(_handleIncomingEvent);
  }

  void add(E event) {
    if (!_eventController.isClosed) {
      _eventController.sink.add(event);
    }
  }

  void _handleIncomingEvent(E event);

  void emit(S newState) {
    if (_stateController.isClosed) return;
    _state = newState;
    _stateController.sink.add(_state);
  }

  Future<void> close() async {
    await _eventController.close();
    await _stateController.close();
  }
}

/// Implementasi Konkret Domain Cart
class CartBloc extends Bloc<BlocEvent, CartState> {
  CartBloc() : super(CartState(items: const [], totalPrice: 0.0));

  @override
  void _handleIncomingEvent(BlocEvent event) async {
    if (event is CheckoutItemAdded) {
      final updatedItems = List<String>.from(state.items)..add(event.itemName);
      final updatedPrice = state.totalPrice + event.price;
      emit(state.copyWith(items: updatedItems, totalPrice: updatedPrice));
    } else if (event is CheckoutSubmitted) {
      emit(state.copyWith(isSubmitting: true));
      
      // Simulasi asinkronus I/O ke Payment Gateway
      await Future.delayed(const Duration(milliseconds: 200));
      
      emit(CartState(items: const [], totalPrice: 0.0, isSubmitting: false));
    }
  }
}

// Eksekusi Simulasi
void main() async {
  print("--- Testing Reactive Graph (Riverpod Principle) ---");
  final price = StateNode<double>(100.0);
  final taxRate = StateNode<double>(0.11); // PPN 11%
  final totalWithTax = ComputedNode<double>(() => price.value + (price.value * taxRate.value));

  print('Initial Total: ${totalWithTax.value}'); // 111.0
  totalWithTax.addListener(() {
    print('Reactive Update: Total berubah menjadi ${totalWithTax.value}');
  });

  price.set(200.0); // Output: Reactive Update: Total berubah menjadi 222.0
  taxRate.set(0.12); // Output: Reactive Update: Total berubah menjadi 224.0

  print("\n--- Testing Event-Driven Stream (BLoC Principle) ---");
  final cartBloc = CartBloc();
  final subscription = cartBloc.stream.listen((state) {
    print('[BLoC] State Mutated: Items: ${state.items.length}, '
          'Total: Rp${state.totalPrice}, Submitting: ${state.isSubmitting}');
  });

  cartBloc.add(CheckoutItemAdded("Mechanical Keyboard", 1500000));
  cartBloc.add(CheckoutItemAdded("Wireless Mouse", 500000));
  cartBloc.add(CheckoutSubmitted());

  await Future.delayed(const Duration(milliseconds: 500));
  await subscription.cancel();
  await cartBloc.close();
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Runtime: Event Loop vs Element Rebuilding
- **Provider (InheritedWidget)**: Saat `ChangeNotifier.notifyListeners()` dipanggil, Provider mengeksekusi metode internal `Element.markNeedsBuild()`. Flutter Engine tidak langsung me-render ulang seketika. Flutter memasukkan element tersebut ke daftar dirty-list pipeline render engine (`BuildOwner`). Re-rendering baru dieksekusi sinkron pada frame rendering berikutnya (*drawFrame phase*).
- **Riverpod**: Berjalan sepenuhnya di luar micro-task UI framework jika tidak sedang terikat widget. State dipertahankan dalam memori heap berupa referensi DAG. Evaluasi node dependensi terjadi secara sinkronus atau melalui microtask queue tergantung apakah menggunakan provider synchronous atau asynchronous (`AsyncNotifier`).
- **BLoC**: Mengandalkan **Dart Event Loop**. Ketika event ditambahkan (`sink.add`), event tersebut dimasukkan ke antrean *Event Queue*. Dispatch event dari BLoC ke UI tidak pernah terjadi dalam tick sinkronus yang sama dengan input UI, melainkan melewati siklus event loop berikutnya. Hal ini mencegah *frame drop* akibat mutasi state berulang dalam frame yang sama (*batching effect*).

#### B. Alokasi Memori & Garbage Collection
- **ChangeNotifier (Provider)**: Menyimpan list listener primitif `List<VoidCallback?>`. Jika lupa memanggil `dispose()`, referensi closure UI context akan terus dipegang oleh notifier, menyebabkan **Context Memory Leak** (seluruh subtree widget tertahan di memori dan tidak bisa di-sweep oleh Dart GC).
- **Riverpod (`autoDispose`)**: Menggunakan referensi counter (`Ref`). Ketika subscriber suatu provider mencapai angka `0`, Riverpod memicu mekanisme penghancuran internal (`ProviderElement.dispose()`). Riverpod modern memanfaatkan `WeakReference` dan `Finalizer` dari `dart:core` untuk mendeteksi kapan objek consumer di-garbage collect sehingga provider caching dapat dibersihkan tanpa intervensi manual.
- **BLoC Stream**: `StreamController` mengalokasikan ring buffer internal untuk menampung event. Subscription yang terbuka (`stream.listen`) memegang referensi kuat terhadap fungsi handler. Jika stream tidak ditutup via `close()`, stream controller akan mengonsumsi alokasi native ports/microtask queue leaks secara permanen.

#### C. Trade-offs Arsitektural

| Dimensi | Provider | Riverpod | BLoC |
| :--- | :--- | :--- | :--- |
| **Ketergantungan UI Context** | Sangat Tinggi (`BuildContext`) | Tidak Ada (Global containerized) | Bebas (Pure Streams, UI agnostic) |
| **Safety Type & Compilation** | Lemah (Crash di runtime jika hilang) | Sangat Tinggi (Compile-time checked) | Sangat Tinggi (Exhaustive Pattern Matching) |
| **Boilerplate Ratio** | Rendah | Sedang | Sangat Tinggi (Event, State, Emitter) |
| **Traceability & Time-travel** | Sulit dilacak | Menengah (via `ProviderObserver`) | Sangat Mudah (Full state audit logging) |
| **Concurrency Control** | Manual (Raw Async Logic) | Terbatas pada Provider Lifecycle | Sangat Kuat (`bloc_concurrency` operators) |

### 4. Best Practices & Common Pitfalls

#### Do's
1. **Gunakan Immutable State Objects**: Wajib menggunakan `freezed`, Dart 3 Records, atau `equatable` pada State BLoC dan Notifier. Dart membandingkan objek berdasarkan kesetaraan referensi identitas (*identity comparison/hashCode*). Jika state dimutasi secara in-place (in-memory update), framework/stream subscriber tidak akan mendeteksi perbedaan tersebut, sehingga UI tidak bereaksi.
2. **Kendalikan Konkurensi Event pada BLoC**: Gunakan event transformer bawaan (seperti `droppable()`, `restartable()`, atau `debounce()`) untuk transaksi jaringan.
   ```dart
   // Contoh: Mencegah spam klik tombol submit dengan 'droppable' transformer
   on<CheckoutSubmitted>(_onCheckoutSubmitted, transformer: droppable());
   ```
3. **Pecah Granularitas Provider/State**: Hindari "God State" (objek raksasa berisi ratusan field). Pisahkan state berdasarkan domain atomik untuk mencegah *unnecessary build cascade* pada ribuan subtree widget.

#### Don'ts
1. **Memanggil Side-Effect Asinkron di Luar Controller**: Jangan pernah mengeksekusi I/O atau HTTP call langsung di dalam constructor `ChangeNotifier` atau `Provider`. Hal ini memicu *unhandled async state transitions* sebelum UI siap mendengarkan.
2. **Menyimpan `BuildContext` di State Layer**: Menyimpan referensi context di luar widget tree (misalnya di dalam Riverpod Notifier atau BLoC) adalah antipattern fatal. Saat context unmounted, operasi tersebut memicu *dangling pointer access* dan crash runtime (`setState() called after dispose()`).
3. **Lupa Memutus Stream Subscription**: Jangan membuat `.listen()` manual di layer widget tanpa meng-cancel subscription tersebut di `dispose()`. Gunakan selalu `StreamBuilder` atau ekstensi konsumsi framework bawaan (`context.watch()`, `ref.watch()`).

#### Edge Cases
- **The Stale State Race Condition**: Ketika dua aksi asinkron dipicu berurutan secara cepat (misal: pencarian kata kunci "A", lalu segera diubah menjadi "AB"). Tanpa transformer `restartable()` di BLoC atau pembatalan token di Riverpod (`ref.onDispose`), response request "A" dapat mendarat *setelah* request "AB", menimpa state pencarian akhir dengan data usang.
- **Recursive State Notification Loops**: Mengubah state di dalam blok build UI (contoh: memanggil `ref.read().set()` atau `bloc.add()` tepat di dalam method `build()`). Hal ini memicu loop tak terbatas karena mutasi state meminta rebuild, yang kemudian memicu mutasi state kembali, hingga terjadi runtime stack overflow.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Custom Debounce Event Transformer**:
   Bangun sebuah custom BLoC Event Transformer murni menggunakan Dart `StreamChannel` dan operator `asyncMap` yang secara otomatis mengabaikan event pencarian jika interval antara dua event kurang dari 400 milidetik (debouncing). Pastikan tidak ada kebocoran memori saat BLoC ditutup di tengah-tengah timer yang sedang berjalan.
2. **Circular Dependency Resolver pada Reactive Graph**:
   Modifikasi class `ComputedNode` pada implementasi Riverpod Core di Bagian 2 untuk mendeteksi dependensi sirkular secara dinamis (contoh: Node A membutuhkan Node B, dan Node B membutuhkan Node A). Buat sistem melempar exception spesifik `CyclicDependencyException` alih-alih menyebabkan `StackOverflowError` saat komputasi berlangsung.
