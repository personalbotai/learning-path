## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum rilis Dart 3, seluruh deklarasi `class` secara implisit mendefinisikan *interface*. Hal ini memunculkan fenomena **Fragile Base Class**: author pustaka tidak memiliki kontrol apakah konsumen API akan menurunkan kelas menggunakan `extends` (pewarisan implementasi) atau `implements` (hanya mengambil skema tipe sebagai kontrak murni). Konsumen yang meng-`implements` kelas konkret berisiko merusak invariansi internal ketika author menambahkan method baru di masa mendatang.

Dart 3 memperkenalkan sistem *Class Modifiers* yang memecah hak akses subtipe pada tingkat kompilasi. Dua konstruksi fundamental dalam perancangan sistem berbasis kontrak dan pewarisan adalah:

1. **`abstract interface class`**:
   - **Karakteristik**: Tidak dapat diinstansiasi langsung (`abstract`). Di luar pustaka (*library*) tempat kelas ini didefinisikan, kelas **hanya boleh di-`implements`**, dan **dilarang keras di-`extends`**.
   - **Tujuan Arsitektural**: Mendefinisikan kontrak tipe murni (*pure API contract*). Mencegah kebocoran implementasi internal atau state bawaan kepada konsumen, serta memfasilitasi pembuatan *mock/stub* murni untuk *unit testing* dan penerapan *Dependency Inversion Principle* (DIP).

2. **`abstract base class`**:
   - **Karakteristik**: Tidak dapat diinstansiasi langsung (`abstract`). Di luar pustakanya, kelas **hanya boleh di-`extends`**, dan **dilarang di-`implements`**.
   - **Tujuan Arsitektural**: Menjamin bahwa seluruh subtipe mewarisi logika dasar, *lifecycle*, dan *state* tertentu. Pola ini mengamankan *Template Method Pattern*, memastikan *backward compatibility* ketika author menambahkan fungsi non-abstrak baru, dan memaksakan bahwa kelas turunan juga harus ditandai sebagai `base`, `final`, atau `sealed` untuk menjaga rantai pewarisan tetap terkontrol.

```
+------------------------------------+---------------------------------------+
| Modifier Combination               | Di luar Library: Extends? | Implements?|
+------------------------------------+---------------------------------------+
| abstract interface class           | NO                        | YES       |
| abstract base class                | YES                       | NO        |
+------------------------------------+---------------------------------------+
```

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan arsitektur persistensi data. Kita memisahkan kontrak driver penyimpanan (`interface`) dari kerangka kerja *repository* yang memiliki mekanisme caching dan validasi terpusat (`base`).

#### File: `lib/storage_core.dart`
```dart
library storage_core;

import 'dart:async';

/// 1. Abstract Interface Class: Kontrak murni driver I/O.
/// Konsumen di luar library ini TIDAK BISA mewarisi logika storage engine,
/// melainkan HARUS menyediakan implementasi konkretnya sendiri.
abstract interface class StorageDriver {
  Future<void> write(String key, String value);
  Future<String?> read(String key);
  Future<void> delete(String key);
}

/// Model Entitas
abstract class Entity {
  String get id;
}

/// 2. Abstract Base Class: Kerangka kerja Repository dengan Template Method Pattern.
/// Konsumen di luar library WAJIB melakukan `extends` agar logika caching 
/// dan audit log tidak dapat di-bypass oleh implementasi liar.
abstract base class BaseRepository<T extends Entity> {
  final StorageDriver _driver;
  final Map<String, T> _memoryCache = {};

  BaseRepository(this._driver);

  // Serializer/Deserializer abstrak yang wajib disediakan oleh subclass
  T deserialize(String raw);
  String serialize(T entity);

  // Template Method: Logika caching dan write-through terlindungi
  Future<void> save(T entity) async {
    _validateEntity(entity);
    final rawData = serialize(entity);
    await _driver.write(entity.id, rawData);
    _memoryCache[entity.id] = entity; // Update cache
  }

  Future<T?> findById(String id) async {
    if (_memoryCache.containsKey(id)) {
      return _memoryCache[id];
    }
    final rawData = await _driver.read(id);
    if (rawData == null) return null;

    final entity = deserialize(rawData);
    _memoryCache[id] = entity;
    return entity;
  }

  // Invariant privat internal yang tidak boleh dirusak
  void _validateEntity(T entity) {
    if (entity.id.trim().isEmpty) {
      throw ArgumentError('Entity ID cannot be empty.');
    }
  }
}
```

#### File: `lib/user_repository.dart` (Konsumen Library)
```dart
import 'dart:async';
import 'storage_core.dart';

// Definisi Model
final class User implements Entity {
  @override
  final String id;
  final String name;

  User(this.id, this.name);
}

// IMPLEMENTASI INTERFACE:
// StorageDriver di-implements untuk mengaitkan ke storage engine pihak ketiga.
final class InMemoryStorageDriver implements StorageDriver {
  final Map<String, String> _db = {};

  @override
  Future<void> write(String key, String value) async => _db[key] = value;

  @override
  Future<String?> read(String key) async => _db[key];

  @override
  Future<void> delete(String key) async => _db.remove(key);
}

// IMPLEMENTASI BASE CLASS:
// Subclass dari base class WAJIB menggunakan modifier `base`, `final`, atau `sealed`.
final class UserRepository extends BaseRepository<User> {
  UserRepository(super.driver);

  @override
  String serialize(User entity) => '${entity.id}|${entity.name}';

  @override
  User deserialize(String raw) {
    final parts = raw.split('|');
    return User(parts[0], parts[1]);
  }
}

void main() async {
  final driver = InMemoryStorageDriver();
  final repo = UserRepository(driver);

  await repo.save(User('usr-001', 'Ada Lovelace'));
  final user = await repo.findById('usr-001');

  print('Loaded User: ${user?.name}'); // Output: Loaded User: Ada Lovelace
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime (Static Enforcement via CFE)
Pembatasan class modifier diterapkan oleh **Dart Common Front End (CFE)** pada fase analisis AST (*Abstract Syntax Tree*) sebelum bytecode kernel (`.dill`) dikompilasi ke kode mesin (AOT) atau dieksekusi di Dart VM (JIT).
- Jika ada kode di luar pustaka memanggil `implements BaseRepository`, CFE langsung melempar *compile-time error*.
- Karena pembatasan ini dipaksakan saat kompilasi, tidak ada *performance penalty* pada runtime untuk pengecekan tipe modifier ini.

#### Mekanisme Dispatch: VTable vs Interface Table
- **Pewarisan Kelas (`base class` / Single Inheritance)**: 
  AOT compiler menyusun memori objek dengan *Virtual Method Table* (vtable) yang terstruktur linear. Ketika sebuah metode dipanggil pada subtipe `BaseRepository`, compiler dapat menggunakan *fixed-offset dynamic dispatch* (panggilan memori bergeser secara konstan), yang sangat efisien dan mudah dioptimalkan melalui *devirtualization* (mengubah virtual call menjadi direct call jika kelas turunan bersifat monomorfik).
- **Implementasi Antarmuka (`interface class` / Structural Subtyping)**: 
  Ketika suatu kelas meng-`implements` interface, kelas tersebut tidak membagi tata letak memori yang sama dengan interface-nya. Kompiler runtime menggunakan mekanisme *Interface Table Dispatch* atau *Inline Caching* untuk memetakan pemanggilan metode ke alamat fungsi konkret.

#### Alokasi Memori
- Menggunakan `base class` mengizinkan subtipe mewarisi *field layout* dari superclass secara berurutan di dalam heap. Instance turunan memuat state `_driver` dan `_memoryCache` secara konsisten pada *memory offset* yang diprediksi oleh compiler.
- `interface class` murni bertindak sebagai *compile-time type signature*; ia tidak menghasilkan metadata alokasi state superclass pada instance yang mengimplementasikannya.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `abstract interface class` untuk Abstraksi I/O dan Dependensi**: Gunakan pada repositori, layanan HTTP, atau sensor. Pola ini mempermudah penggantian implementasi produksi dengan Mock/Fake pada pengujian tanpa memicu *side-effect* dari superclass.
- **Gunakan `abstract base class` untuk Template Method Pattern**: Gunakan saat Anda memiliki *domain logic* yang harus dieksekusi seragam sebelum atau sesudah logika spesifik subclass dijalankan (misal: validasi skema, sinkronisasi state).
- **Terapkan Subtype Modifier secara Konsisten**: Saat mengekstensi `base class`, selalu putuskan apakah kelas anak Anda harus `final` (menghentikan rantai turunan) atau `base` (membuka turunan lebih lanjut).

#### Don'ts
- **Jangan gunakan `abstract class` polos di Library Publik**: Meninggalkan kelas tanpa modifier (`interface` atau `base`) membuka celah konsumen mengekstensi DAN mengimplementasi kelas tersebut secara bebas, membuat penambahan fungsionalitas di masa depan berpotensi merusak (*breaking changes*) basis kode pengguna.
- **Jangan menaruh state konkret di `abstract interface class`**: Walaupun sintaks Dart mengizinkan penulisan field di dalam `interface class`, state tersebut tidak akan diwariskan ke konsumen yang menggunakan kata kunci `implements` (mereka dipaksa mendeklarasikan ulang getter/setter-nya).

#### Edge Cases
- **Batasan Bersifat Pustaka (Library-Scope)**:
  Aturan pelarangan `extends` untuk `interface` dan `implements` untuk `base` **hanya berlaku di luar berkas atau direktori pustaka yang sama**. Di dalam satu berkas pustaka yang sama, Dart compiler mengizinkan kelas meng-`extends` sebuah `interface class` atau meng-`implements` sebuah `base class`.
- **Modifier Subclass Cascading**:
  Meng-`extends` sebuah `base class` menuntut subclass mendeklarasikan salah satu dari tiga modifier: `base`, `final`, atau `sealed`. Subclass tidak dapat dideklarasikan sebagai kelas reguler tanpa modifier.

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Validasi Compiler**: Buat dua file terpisah (`api_engine.dart` dan `main.dart`). Deklarasikan `abstract interface class Engine` dan `abstract base class Pipeline` di dalam `api_engine.dart`. Pada `main.dart`, paksa untuk melakukan:
   - `class CustomEngine extends Engine {}`
   - `class CustomPipeline implements Pipeline {}`
   Amati pesan kesalahan yang dihasilkan oleh analyzer Dart Compiler.
2. **Arsitektur Logger Pipeline**: Rancang sebuah `abstract base class BaseLogger` yang memiliki logika pemformatan timestamp dan penulisan level log (INFO, ERROR). Kemudian, buat `abstract interface class LogOutput` sebagai output target (Console, Remote Server, File). Rangkai keduanya sehingga `BaseLogger` menerima dependensi `LogOutput` melalui Dependency Injection. Pastikan dependensi tidak bisa di-bypass oleh subclass logger!
