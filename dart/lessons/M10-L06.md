### 1. Konsep & Arsitektur Mendalam

*Continuous Integration* (CI) dalam ekosistem Dart bukan sekadar otomasi eksekusi skrip pengujian, melainkan sistem validasi gerbang (*gatekeeping*) deterministik yang memverifikasi integritas tipe, kepatuhan gaya bahasa, serta keabsahan runtime kode sebelum digabungkan (*merge*) ke cabang utama.

Di balik layar, ekosistem Dart dirancang dengan modularitas alat bantu (*tooling*) yang kuat berbasis satu executable: `dart`. Ketika diintegrasikan dengan GitHub Actions, kita mengorkestrasi eksekusi toolchain Dart pada sebuah *ephemeral runner* (lingkungan virtual terisolasi).

```
[Developer Push / PR] 
         │
         ▼
[GitHub Event Trigger] ──> [Runner Provisioning (e.g., Ubuntu)]
                                     │
         ┌───────────────────────────┴───────────────────────────┐
         ▼                                                       ▼
[Cache Restoration]                                     [Toolchain Setup]
(~/.pub-cache based on                                  (dart-lang/setup-dart:
 pubspec.lock hash)                                      resolve SDK, set PATH)
         │                                                       │
         └───────────────────────────┬───────────────────────────┘
                                     │
                                     ▼
                          [dart pub get / check]
                                     │
                                     ▼
                          [Static Analysis Phase]
                     ├─ dart format (--set-exit-if-changed)
                     └─ dart analyze (--fatal-infos)
                                     │
                                     ▼
                          [Dynamic Testing Phase]
                     └─ dart test (spawns Isolate workers)
                                     │
                                     ▼
                         [Coverage & Artifacts]
```

Arsitektur CI Dart pada GitHub Actions melibatkan interaksi antara komponen inti berikut:
1. **GitHub Actions Runner Engine**: Menginstansiasi VM/Container, mengunduh repositori, mengevaluasi *matrix*, dan mengeksekusi step secara sekuensial. Setiap langkah dievaluasi berdasarkan kode status keluar (*exit code*). Nilai `0` menandakan sukses, sedangkan selain `0` akan membatalkan alur kerja (*pipeline abort*).
2. **Analysis Server (DAS)**: Ketika `dart analyze` dieksekusi, Dart meluncurkan *Dart Analysis Server* secara *in-memory*. DAS mem-parsing source code menjadi *Abstract Syntax Tree* (AST), menyusun *element model*, melakukan inferensi tipe (*type inference*), dan mengevaluasi batasan linter berdasarkan konfigurasi `analysis_options.yaml`.
3. **Dart Pub Subsystem**: Mengelola dependensi paket. `pubspec.lock` memetakan dependensi secara presisi (termasuk *content hash*). Pipeline CI yang baik memverifikasi determinisme ini tanpa memperbarui (*upgrade*) dependensi secara liar di server.
4. **Isolate Test Runner**: Runner pengujian Dart menjalankan file tes secara terisolasi menggunakan thread/isolate terpisah. Ini meminimalkan efek samping (*side-effects*) antar unit tes dan memanfaatkan multi-core vCPU yang disediakan runner GitHub.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah konfigurasi workflow GitHub Actions kelas produksi untuk paket atau aplikasi backend Dart (`.github/workflows/dart_ci.yml`), dirancang dengan optimasi *caching*, paralelisasi, dan pembatalan otomatis (*concurrency cancellation*).

```yaml
name: Dart Continuous Integration

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

# Batalkan build yang sedang berjalan jika ada commit baru di PR yang sama
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  validate:
    name: Lint, Analyze & Test
    runs-on: ubuntu-latest

    # Variabel environment untuk mengontrol perilaku CLI Dart
    env:
      PUB_CACHE: ~/.pub-cache

    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Setup Dart SDK
        uses: dart-lang/setup-dart@v1
        with:
          sdk: stable # Menggunakan rilis stabil terbaru

      - name: Cache Pub Dependencies
        id: cache-pub
        uses: actions/cache@v4
        with:
          path: ${{ env.PUB_CACHE }}
          # Kunci cache bergantung pada isi pubspec.lock
          key: ${{ runner.os }}-pub-${{ hashFiles('**/pubspec.lock') }}
          restore-keys: |
            ${{ runner.os }}-pub-

      - name: Install Dependencies
        run: dart pub get

      - name: Verify Code Formatting
        # Gagal jika ada file yang tidak mengikuti aturan dart format
        run: dart format --output=none --set-exit-if-changed .

      - name: Static Code Analysis
        # Jadikan warning dan info sebagai kegagalan (strict mode)
        run: dart analyze --fatal-infos --fatal-warnings

      - name: Run Unit & Integration Tests with Coverage
        # Mengumpulkan data cakupan kode untuk laporan analitik
        run: dart test --coverage=coverage

      - name: Format Coverage Data to LCOV
        # Ubah format internal Dart coverage menjadi format universal LCOV
        run: |
          dart pub global activate coverage
          dart pub global run coverage:format_coverage --lcov --in=coverage --out=coverage/lcov.info --packages=.dart_tool/package_config.json --report-on=lib

      - name: Verify Test Coverage Threshold
        # Skrip guard sederhana: pastikan lcov.info tidak kosong
        run: |
          if [ ! -s coverage/lcov.info ]; then
            echo "Coverage file is empty or missing!"
            exit 1
          fi
```

#### Penjelasan Komponen Kunci:
- **`concurrency.cancel-in-progress: true`**: Mencegah pemborosan kuota *billing* GitHub Actions. Jika seorang developer melakukan *push* tiga commit berturut-turut pada PR yang sama, dua proses lama langsung dihentikan.
- **`--set-exit-if-changed`**: Memaksa `dart format` mengembalikan *exit code 1* jika menemukan whitespace atau lekukan yang tidak standar, bukan memformat file di tempat (karena runner bersifat sekali pakai).
- **`--fatal-infos`**: Mencegah penurunan kualitas kode secara perlahan (*code rot*). Semua hint diagnostik (seperti variabel yang tidak terpakai atau redundansi tipe) dianggap *breaking*.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Saat step dieksekusi, GitHub Actions Runner mengeksekusi shell subprocess (`/usr/bin/bash -e`). Penambahan flag `-e` oleh GitHub berarti instruksi bash akan langsung keluar jika ada perintah yang menghasilkan kode non-nol.
- Aksi `dart-lang/setup-dart` mengunduh arsip SDK Dart resmi yang sudah dikompilasi, mengekstraknya ke direktori agen CI (misal: `/opt/hostedtoolcache/dart-sdk/`), dan mengekspor path tersebut ke sistem `$PATH`.
- Ketika `dart test` dipanggil, runner Dart membangun *temporary kernel snapshot* (`.dart_tool/test/cache/...`) dari kode pengujian Anda melalui C++ frontend compiler (`gen_kernel`), lalu mengeksekusi snapshot tersebut di atas Dart VM native.

#### Alokasi Memori / Resource
- **Pub Cache**: Secara *default*, sistem dependensi Dart menaruh paket pihak ketiga di `~/.pub-cache/hosted/pub.dev/`. Langkah `actions/cache` mengompresi direktori ini menggunakan format *tar/zstandard*. Jika `pubspec.lock` tidak berubah, waktu resolusi jaringan terpotong dari belasan detik menjadi sub-detik karena seluruh *source* diekstrak langsung dari storage GitHub.
- **Isolate Threading**: Pada runner standar GitHub (`ubuntu-latest` yang menyediakan 2 vCPU dan 7GB RAM), `dart test` secara otomatis menyesuaikan *pool isolate worker* dengan jumlah core mesin (`concurrency = 2`).

#### Trade-offs
- **Matrix Testing vs. Waktu CI**: Menguji kode di 3 channel Dart (`stable`, `beta`, `dev`) meningkatkan proteksi terhadap *deprecations*, namun mengalikan konsumsi waktu CI sebesar 3x lipat.
- **Cache Size vs. Download Overhead**: Menyimpan folder `.dart_tool/` (hasil build intermediate) ke cache CI sering kali menyebabkan masalah invalidasi dependensi (*stale compilation artifacts*), sehingga lebih aman hanya mencache `$PUB_CACHE`.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Commit `pubspec.lock` untuk Eksekusi Deterministik**: Jika Anda membangun aplikasi backend, CLI, atau sistem terisolasi, kunci dependensi wajib masuk ke Git. Jangan pernah membiarkan CI menarik versi paket yang berbeda dari versi lokal developer.
- **Gunakan Linter yang Ketat**: Gunakan paket `lints/recommended.yaml` atau `very_good_analysis` di `analysis_options.yaml` untuk standarisasi tinggi.
- **Batasi Waktu Eksekusi (*Timeout*)**: Berikan properti `timeout-minutes: 15` pada level job untuk mencegah pengujian yang *deadlock* menghabiskan kuota runtime secara diam-diam.

#### Don'ts
- **Jangan Gunakan `dart pub upgrade` di CI**: Ini melanggar prinsip determinisme build. Selalu gunakan `dart pub get`.
- **Jangan Abaikan Warning Dart SDK**: Menghilangkan `--fatal-warnings` adalah kesalahan fatal yang sering meloloskan *null safety violations* tersembunyi ke branch utama.
- **Jangan Menguji Kode yang Tidak Terformat**: Membiarkan inkonsistensi formatting lolos ke Git history akan mengacaukan *git blame* dan *code review*.

#### Edge Cases
- **Symlink & Hak Akses File**: Dart pub terkadang membuat *symlink* di lingkungan POSIX. Saat menggunakan `actions/cache`, pastikan runner OS target sama (Linux ke Linux, macOS ke macOS) karena struktur permission file Linux tidak dapat dipulihkan secara 1:1 di Windows runner.
- **Interferensi Git submodules / Private Repositories**: Jika file `pubspec.yaml` merujuk dependensi via Git (`git: url: ...`), langkah `actions/checkout` default tidak memiliki kredensial untuk mengakses repo private kedua. Anda wajib menginjeksi *Personal Access Token* (PAT) atau *Deploy Key*.

### 5. Tantangan Eksplorasi Mandiri

1. **Konfigurasi Multi-Channel Matrix**:
   Ubah berkas `.github/workflows/dart_ci.yml` agar menggunakan konfigurasi `matrix` yang mengeksekusi job secara paralel di dua channel SDK Dart: `stable` dan `beta`. Pastikan pipeline tidak menggagalkan seluruh build jika terjadi kegagalan khusus pada channel `beta` (Gunakan instruksi: `continue-on-error`).

2. **Automated Minimum Coverage Enforcer**:
   Integrasikan CLI tool `lcov` (atau skrip Dart kustom) ke dalam pipeline CI untuk menghitung persentase akhir cakupan kode (*line coverage*). Buat pipeline gagal (*exit 1*) secara otomatis jika total coverage unit test berada di bawah 85%.
