## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Semenjak Dart 3.0 memperkenalkan *pattern matching*, sistem tipe Dart bertransformasi menjadi jauh lebih deklaratif. Namun, pencocokan pola struktural murni (*structural pattern matching*) hanya mampu memvalidasi bentuk data, tipe, dan nilai konstan primitif. Pola struktural tidak dapat secara inheren memvalidasi predikat dinamis atau aturan bisnis berbasis kondisi runtime (seperti `x > 10` atau `string.isNotEmpty`).

Untuk menjembatani keterbatasan ini, Dart menyediakan **Guard Clauses** menggunakan kata kunci `when`.

```
pattern 'when' expression
```

#### Mengapa Guard Clauses Dibutuhkan?
Sebelum Dart 3, logika pencabangan kompleks membutuhkan blok `if-else` bersarang atau struktur `switch` yang verbose dengan evaluasi manual di dalam *body*. Guard clause memungkinkan developer menggabungkan:
1. **Destructuring**: Mengekstrak data dari objek kompleks/koleksi/record.
2. **Type Testing**: Memastikan tipe runtime sesuai (*subtyping check*).
3. **Semantic Filtering**: Menjalankan evaluasi boolean arbitrer terhadap variabel yang baru saja diekstrak secara atomik dalam satu deklarasi kasus (*case*).

```
   [ Data Masuk ]
         │
         ▼
┌──────────────────┐       GAGAL
│ Pattern Match?   ├───────────────────► [ Cek Case Berikutnya ]
│ (Tipe & Bentuk)  │
└────────┬─────────┘
         │ SUKSES (Variable Binding Terbentuk)
         ▼
┌──────────────────┐       FALSE
│ Guard Clause     ├───────────────────► [ Unbind / Discard Binding ]
│ (`when condition`)│                     │
└────────┬─────────┘                     ▼
         │ TRUE                    [ Cek Case Berikutnya ]
         ▼
┌──────────────────┐
│ Eksekusi Cabang  │
│ (Body / Result)  │
└──────────────────┘
```

#### Implikasi Terhadap Exhaustiveness Checking
Dart compiler memiliki fitur *Exhaustiveness Checking* pada `switch` expression atau statement yang beroperasi pada `sealed classes`, `enums`, dan `bool`. Compiler menganalisis seluruh kemungkinan subtipe menggunakan teori himpunan (*set-theoretic approach*).

> **Hukum Kritis:** Guard clause (`when`) **menonaktifkan kemampuan compiler untuk membuktikan *exhaustiveness*** pada *case* tersebut.

Karena kondisi pada `when` dievaluasi pada saat runtime (bisa berupa fungsi arbitrer atau bergantung pada state dinamis), compiler tidak dapat membuktikan secara matematis apakah kondisi boolean tersebut mencakup seluruh kemungkinan semesta data (terkait masalah *Halting Problem* dan keterbatasan analisis statis). Akibatnya, jika seluruh *case* dari tipe tertutup (*sealed*) memiliki guard clause, compiler akan mewajibkan adanya *fallback case* (seperti `case _` atau *case* tanpa guard) untuk mempertahankan jaminan *null-safety* dan *compile-time soundness*.

### 2. Implementasi & Contoh Kasus Nyata

Skenario: Pemrosesan transaksi finansial pada Payment Engine. Kita memiliki variasi status transaksi, validasi limit saldo, dan pendeteksian pola fraud secara real-time.

```dart
// domain/transaction.dart

sealed class TransactionStatus {}

final class Pending extends TransactionStatus {
  final DateTime createdAt;
  Pending(this.createdAt);
}

final class Authorized extends TransactionStatus {
  final String authCode;
  Authorized(this.authCode);
}

final class Failed extends TransactionStatus {
  final int errorCode;
  final String reason;
  Failed(this.errorCode, this.reason);
}

class Transaction {
  final String id;
  final double amount;
  final String currency;
  final TransactionStatus status;
  final bool isFlaggedForReview;

  Transaction({
    required this.id,
    required this.amount,
    required this.currency,
    required this.status,
    this.isFlaggedForReview = false,
  });
}

// engine/settlement_processor.dart

enum ProcessingAction {
  executeImmediately,
  holdForManualReview,
  rejectWithAlert,
  retry,
  archive,
}

ProcessingAction evaluateTransaction(Transaction tx) {
  // Switch expression dengan Pattern Matching, Destructuring, dan Guard Clauses
  return switch (tx) {
    // 1. Ekstraksi amount dan status sekaligus; guard memvalidasi batas nilai fraud
    Transaction(amount: var amt, status: Authorized()) when amt > 500000000 =>
      ProcessingAction.holdForManualReview,

    // 2. Destructuring bersarang dengan validasi multi-kondisi
    Transaction(currency: 'IDR', amount: var amt) when amt <= 0 =>
      ProcessingAction.rejectWithAlert,

    // 3. Guard mengevaluasi properti internal dari state 'Pending'
    Transaction(status: Pending(createdAt: var time))
        when DateTime.now().difference(time).inMinutes > 30 =>
      ProcessingAction.retry,

    // 4. Guard memeriksa status error code spesifik pada subtype Failed
    Transaction(status: Failed(errorCode: var code)) when code >= 500 =>
      ProcessingAction.retry,

    // 5. Normal processing: Pattern cocok tanpa guard clause
    Transaction(status: Authorized(), isFlaggedForReview: false) =>
      ProcessingAction.executeImmediately,

    // 6. Explicit fallback jika ada anomali lain yang tidak tertangkap
    _ => ProcessingAction.archive,
  };
}

void main() {
  final highValueTx = Transaction(
    id: "TX-001",
    amount: 750000000.0,
    currency: "IDR",
    status: Authorized("AUTH-992"),
  );

  final action = evaluateTransaction(highValueTx);
  print('Keputusan Transaksi [${highValueTx.id}]: $action'); 
  // Output: Keputusan Transaksi [TX-001]: ProcessingAction.holdForManualReview
}
```

#### Penjelasan Alur Kode:
- `Transaction(amount: var amt, status: Authorized()) when amt > 500000000`:
  1. Compiler mencocokkan apakah objek bertipe `Transaction`.
  2. Melakukan ekstraksi *field* `amount` dan mengikatnya ke variabel lokal `amt`.
  3. Memvalidasi bahwa *field* `status` bertipe `Authorized`.
  4. Jika semua struktur cocok, blok `when amt > 500000000` dieksekusi. Jika bernilai `true`, cabang dipilih. Jika `false`, evaluasi beralih ke cabang berikutnya tanpa keluar dari evaluasi `switch`.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
Di level compiler Dart (Front-End Compiler / CFE), pola dengan guard clause diubah menjadi representasi AST (*Abstract Syntax Tree*) berupa *PatternSwitchStatement* atau *PatternSwitchExpression* yang diurai menjadi serangkaian *decision trees* (pohon keputusan):

1. **Short-Circuit Verification**: Compiler menghasilkan instruksi pengujian struktural terlebih dahulu (instruksi `is` atau *field getter invocation*).
2. **Lexical Scope Binding**: Jika pengujian struktural berhasil, variabel yang dideklarasikan dalam pattern (misal `var amt`) dialokasikan ke dalam slot frame eksekusi lokal (register/stack).
3. **Predicate Evaluation**: Instruksi melompat ke kode boolean ekspresi `when`. 
4. **Backtracking / Fallthrough**: Jika ekspresi `when` mengembalikan `false`, compiler menghasilkan instruksi lompatan (*jump instruction*) langsung ke label *case* berikutnya. Variabel lokal yang terikat pada pola yang gagal diabaikan atau dibersihkan dari konteks cabang tersebut.

```
IL (Intermediate Language) Konseptual:
---------------------------------------------
v0 = tx.status IS Authorized
IF NOT v0 GOTO label_case_2
v1 = tx.amount
v2 = v1 > 500000000.0        // Evaluasi Guard
IF NOT v2 GOTO label_case_2   // Lompat jika guard false
RETURN ProcessingAction.holdForManualReview

label_case_2:
...
```

#### Alokasi Memori / Resource
- **Zero Heap Allocation**: Variabel yang di-bind melalui pattern destructuring dialokasikan di call stack frame, bukan di heap (kecuali jika variabel tersebut di-capture oleh closure/fungsi anonim di dalam ekspresi `when` atau body *case*).
- **Transient Binding Cost**: Mengekstrak data dan mengevaluasi `when` yang bernilai `false` memiliki biaya CPU mikro (*getter call overhead*). Oleh karena itu, hindari menaruh pemanggilan method berat (seperti parsing JSON, I/O disk) di dalam guard clause.

#### Trade-offs
- **Keterbacaan vs. Analisis Statis**: Guard clause membuat kode sangat ringkas dibanding `if-else` bertingkat, tetapi menghilangkan kepastian *exhaustiveness* statis.
- **Urutan Pola (*Case Ordering*) Sangat Berpengaruh**: Berbeda dengan switch tradisional di mana case non-overlapping dievaluasi independen, guard clauses mengembalikan sifat evaluasi linier (atas ke bawah). Kasus yang lebih spesifik harus diletakkan sebelum kasus yang umum.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Jaga Evaluasi Tetap Murni (Pure Predicates)**: Pastikan ekspresi di dalam `when` tidak memiliki efek samping (*side-effects* seperti mutasi state global, increment counter, atau network call).
- **Struktur Pola Dahulu, Guard Kemudian**: Lakukan penyaringan tipe dan bentuk objek seketat mungkin melalui pattern native sebelum menambahkan guard clause. Ini mengurangi jumlah evaluasi boolean yang tidak perlu.
  ```dart
  // BENAR: Filter tipe via pattern, evaluasi kondisi via when
  case Event(payload: UserData data) when data.age >= 18 => ...
  ```
- **Sediakan Fallback Case**: Selalu sertakan kasus default atau kasus unguarded ketika menggunakan guard clause pada sealed class untuk mencegah `StateError` (*Failed pattern matching without a default case* pada runtime switch expression).

#### Don'ts
- **Hindari Operasi Asinkron**: Kata kunci `when` hanya menerima ekspresi sinkron yang mengembalikan `bool`. Jangan memanggil `Future` atau operasi komputasi berat di dalamnya.
- **Jangan Menggantungkan Logika pada Mutasi di Guard**: Jangan lakukan hal berikut:
  ```dart
  // SALAH: Mutasi state dalam evaluasi guard
  case Order(id: var id) when ++counter > 5 => ...
  ```
  Jika pattern berikutnya cocok, mutasi `counter` telah terjadi dan menciptakan bug yang sangat sulit dilacak (*heisenbug*).

#### Edge Cases
1. **Lemparan Eksepsi (Unhandled Exception) di Guard**: Jika ekspresi di dalam `when` melempar eksepsi (misal: `FormatException` atau `TypeError`), switch **tidak** akan jatuh (*fall through*) ke case berikutnya. Eksepsi akan langsung merambat ke atas call stack dan menghentikan eksekusi thread.
2. **Duplikasi Pola dengan Guard Berlawanan**:
   ```dart
   switch (number) {
     case int n when n >= 0: print('Positif');
     case int n when n < 0:  print('Negatif');
     // Compiler TIDAK menganggap ini exhaustive, meskipun secara matematis lengkap.
     // Switch expression akan gagal kompilasi tanpa case _ fallback!
   }
   ```
