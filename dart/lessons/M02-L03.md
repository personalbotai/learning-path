### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur bahasa Dart, enkapsulasi data dan akses properti didasarkan pada dua pilar utama: **Uniform Access Principle (UAP)** dan **Library-Level Privacy**.

```
+-------------------------------------------------------------------+
|                        DART COMPILATION UNIT                      |
|                                                                   |
|   +-----------------------+           +-----------------------+   |
|   |        Class A        |           |        Class B        |   |
|   |  - _privateField      |<--------->|  Bisa akses Langsung  |   |
|   |  - get publicGetter   |           |  ke _privateField     |   |
|   +-----------------------+           +-----------------------+   |
|               ^                                                   |
+---------------|---------------------------------------------------+
                | (Import Library)
+---------------|---------------------------------------------------+
|               x  DIBLOKIR COMPILER                                |
|   +-----------------------+                                       |
|   |     External File     |                                       |
|   |   Hanya bisa akses    |                                       |
|   |     publicGetter      |                                       |
|   +-----------------------+                                       |
+-------------------------------------------------------------------+
```

#### Uniform Access Principle (UAP)
Di Dart, klien pemanggil tidak perlu tahu apakah suatu properti adalah variabel mentah di memori (*stored field*) atau hasil komputasi fungsi (*computed property*). 
Ketika Anda mendeklarasikan variabel publik:
```dart
int balance = 100;
```
Dart Compiler tidak membiarkan akses *direct memory-read* tanpa proteksi antarmuka. Secara implisit, compiler membangkitkan pasangan *implicit getter* (`int get balance`) dan *implicit setter* (`set balance(int value)`). Ini berarti Anda dapat mengubah *field* biasa menjadi getter/setter kustom di kemudian hari **tanpa merusak API publik (*breaking changes*)** bagi pemanggil kelas tersebut.

#### Library-Level Privacy vs. Class-Level Privacy
Berbeda secara fundamental dari Java, C++, atau C# yang menerapkan *privacy* berbasis batas kelas (`private class Foo`), privasi pada Dart beroperasi di tingkat **Library** (unit file `.dart`, atau multi-file menggunakan direktif `part`/`part of`).

Identifikasi privasi tidak menggunakan kata kunci `private`, melainkan **Prefix Underscore (`_`)**. Simbol apa pun (kelas, fungsi *top-level*, variabel *field*, konstruktor, atau getter/setter) yang diawali dengan `_` hanya dapat diakses dalam library tempat ia didefinisikan. Dua kelas berbeda yang berada dalam satu file yang sama dapat saling mengakses field bertanda `_` milik satu sama lain tanpa batasan.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut menunjukkan implementasi dompet digital (*e-wallet*) dengan validasi mutasi saldo, kalkulasi berbasis status, dan pemisahan field privat menggunakan arsitektur UAP yang aman.

```dart
// file: e_wallet.dart
import 'dart:math' as math;

class CurrencyConverter {
  static double toUSD(double amountIDR) => amountIDR / 15500;
}

class DigitalWallet {
  final String walletId;
  
  // Backing fields privat (hanya bisa diakses di dalam file ini)
  double _balance = 0.0;
  bool _isFrozen = false;
  int _mutationCount = 0;

  DigitalWallet({
    required this.walletId,
    double initialBalance = 0.0,
  }) {
    // Memanfaatkan setter publik untuk validasi saat inisialisasi
    balance = initialBalance;
  }

  // --- GETTERS ---

  /// Getter konvensional untuk membaca backing field _balance
  double get balance => _balance;

  /// Computed Getter: Menghitung nilai tanpa ada field penyimpan langsung
  double get balanceInUSD => CurrencyConverter.toUSD(_balance);

  /// Getter read-only untuk status internal
  bool get isFrozen => _isFrozen;
  int get mutationCount => _mutationCount;

  // --- SETTERS ---

  /// Setter eksplisit: Mengontrol mutasi nilai dengan validasi invariant bisnis
  set balance(double value) {
    if (_isFrozen) {
      throw StateError('Transaksi ditolak: Dompet $walletId sedang dibekukan.');
    }
    if (value.isNaN || value.isInfinite) {
      throw ArgumentError('Nilai saldo tidak valid (NaN/Infinite).');
    }
    if (value < 0.0) {
      throw ArgumentError('Saldo tidak boleh bernilai negatif: $value');
    }

    _balance = value;
    _mutationCount++;
  }

  // Business Action Methods
  void freezeWallet() => _isFrozen = true;
  void unfreezeWallet() => _isFrozen = false;
}

// Simulasi penggunaan dalam context yang sama
void main() {
  final wallet = DigitalWallet(walletId: 'W-9901', initialBalance: 500000);

  // Akses properti transparan (UAP) - syntax field tapi mengeksekusi getter
  print('Saldo Awal: IDR ${wallet.balance}');
  print('Saldo USD: \$${wallet.balanceInUSD.toStringAsFixed(2)}');

  // Memanggil setter dengan validasi
  wallet.balance += 250000;
  print('Saldo Setelah Top-Up: IDR ${wallet.balance}');
  print('Total Mutasi: ${wallet.mutationCount}');

  // Simulasi Pelanggaran Invariant
  try {
    wallet.balance = -1000; // Memicu ArgumentError
  } catch (e) {
    print('Caught Error: $e');
  }

  // Simulasi Modifikasi Saat Beku
  wallet.freezeWallet();
  try {
    wallet.balance += 10000; // Memicu StateError
  } catch (e) {
    print('Caught Error: $e');
  }
}
```

#### Analisis Alur Eksekusi:
1. `wallet.balance += 250000;` dievaluasi oleh Dart VM sebagai:
   `wallet.balance = wallet.balance + 250000;`
   Artinya, VM mengeksekusi *getter* `balance`, melakukan operasi penjumlahan, lalu mengumpankannya ke *setter* `balance=`.
2. Properti `balanceInUSD` berlaku dinamis: tidak memakan alokasi memori tambahan per instans objek karena nilainya selalu dievaluasi *on-the-fly* saat getter dipanggil.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime:
* **Name Mangling:** Di tingkat compiler (Frontend Server / Kernel AST Dart), identifier privat yang diawali underscore (`_`) diberi nama unik (*mangled*) yang menyertakan referensi canonical URI dari library tempat ia dibuat. Misalnya, `_balance` di dalam `package:app/e_wallet.dart` dikonversi menjadi identitas internal seperti `_balance@package:app/e_wallet.dart`. Ini membuat objek dari library eksternal secara fisik mustahil mengakses field tersebut, karena compiler menolak resolusi simbol yang berbeda library ID.
* **Inlining (AOT Optimization):** Ketika mengompilasi ke kode mesin native (*AOT Assembly via `dart2native`*), getter/setter sederhana (yang hanya bertindak sebagai *pass-through* ke backing field) akan dihilangkan *overhead method-call*-nya melalui optimasi **Inlining**. Pemanggilan `wallet.balance` diterjemahkan langsung menjadi instruksi pergeseran offset memori (misalnya `LDR` pada ARM64 atau `MOV` pada x86_64), menyamai performa pembacaan field langsung di C/C++.

#### Alokasi Memori / Resource:
* Dart tidak mengalokasikan slot memori untuk getter komputasi (`balanceInUSD`). Instans kelas hanya menyimpan state nyata: `walletId` (pointer 8-byte), `_balance` (float 8-byte), `_isFrozen` (boolean/int pointer 8-byte), dan `_mutationCount` (int pointer 8-byte).

#### Trade-offs:
* **Transparansi vs Kompleksitas Biaya Algoritmik:** Karena getter dipanggil layaknya properti biasa, konsumen API dapat keliru menganggap bahwa eksekusi properti tersebut berbiaya $O(1)$. Jika Anda menaruh algoritma kompleks, iterasi koleksi besar, atau kalkulasi berat di dalam getter, Anda menyembunyikan beban komputasi di balik sintaks field sederhana.

### 4. Best Practices & Common Pitfalls

#### Do's:
* **Gunakan Self-Encapsulation jika Diperlukan:** Gunakan backing field privat `_foo` yang dipasangkan dengan getter/setter publik `foo` ketika ada logika validasi atau sanitasi data.
* **Mulai dari Field Publik:** Manfaatkan UAP. Jangan menulis getter/setter defensif gaya Java secara membabi-buta jika belum ada logika mutasi yang diperlukan:
  ```dart
  // IDIOMATIK DART:
  class Item {
    String name;
    Item(this.name);
  }
  // Jika nanti butuh validasi, ubah menjadi getter/setter tanpa mengubah kode klien.
  ```
* **Jaga Getter Tetap Idempoten:** Memanggil getter berkali-kali tanpa mutasi state harus mengembalikan hasil yang identik dan tidak boleh memicu efek samping (*side-effects*).

#### Don'ts:
* **Jangan Tulis Boilerplate Java:** Hindari pola redundant berikut:
  ```dart
  // ANTI-PATTERN: Menambah kerumitan file tanpa fungsi nyata
  class BadDesign {
    int _id;
    int get id => _id;
    set id(int value) => _id = value;
  }
  ```
* **Jangan Jalankan Operasi I/O atau Async di Getter:** Getter tidak boleh menjalankan I/O, network call, atau komputasi berbiaya tinggi. Jika butuh operasi async, gunakan method `Future<T> fetchX()`.

#### Edge Cases & Pitfalls:
* **Kebocoran Enkapsulasi di File yang Sama:**
  ```dart
  // file: main.dart
  class SecretVault {
    int _secretKey = 12345;
  }

  void hacker() {
    var vault = SecretVault();
    vault._secretKey = 0; // LEGAL! Berhasil dikompilasi karena ada di library yang sama.
  }
  ```
  *Mitigasi:* Jika sebuah data harus benar-benar diisolasi dari entitas lain, pisahkan kelas tersebut ke dalam file mandiri (*distinct library*).

### 5. Tantangan Eksplorasi Mandiri

1. **Uji Validasi Library Boundary:**
   Buat dua file terpisah: `lib/secure_record.dart` dan `bin/main.dart`. Definisikan field `_hash` pada sebuah kelas di `lib/secure_record.dart`. Cobalah membaca atau memodifikasi `_hash` secara paksa dari `bin/main.dart`. Amati pesan error kompilasi yang dihasilkan oleh Analyzer Dart.
2. **Asymmetric Getter/Setter Types:**
   Dart mendukung tipe data yang berbeda antara *getter* dan *setter* (misalnya: setter menerima tipe `String`, mem-parsingnya, dan menyimpannya ke backing field `DateTime`, sedangkan getter mengembalikan tipe `DateTime`). Rancang sebuah kelas `EventScheduler` yang menerima string ISO 8601 pada setter `set scheduledTime(String dateStr)` namun memiliki getter `DateTime get scheduledTime`. Uji validitas tipe dan kestabilan kodenya!
