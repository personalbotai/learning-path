## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Clean Architecture (yang dipopulerkan oleh Robert C. Martin / Uncle Bob) bertujuan untuk memisahkan kode berdasarkan tanggung jawab bisnis dan infrastruktur. Prinsip utamanya adalah **The Dependency Rule**: dependensi kode sumber hanya boleh mengarah ke dalam, menuju domain logic tingkat tinggi.

```
       +------------------------------------+
       | Data / Presentation / External     |  <-- Frameworks, DB, HTTP, UI
       |   +----------------------------+   |
       |   | Use Cases (Application)    |   |  <-- Business Orchestration
       |   |   +--------------------+   |   |
       |   |   | Entities (Domain)  |   |   |  <-- Enterprise Core Rules
       |   |   +--------------------+   |   |
       |   +----------------------------+   |
       +------------------------------------+
```

#### Struktur Layer Standar Dart:
1. **Domain Layer (Paling Dalam - Zero Dependencies):**
   - **Entities**: Objek bisnis murni (*pure Dart object*), kebal terhadap perubahan API atau skema database.
   - **Use Cases (Interactors)**: Logika alur kerja aplikasi spesifik (contoh: `AuthenticateUser`, `FetchUserProfile`).
   - **Repository Interfaces**: Kontrak abstrak yang mendefinisikan operasi data yang dibutuhkan domain tanpa peduli implementasinya.
2. **Data Layer (Infrastruktur):**
   - **Models / DTOs (Data Transfer Objects)**: Representasi data mentah dari API/DB, mencakup logika serialisasi (`fromJson`, `toJson`) dan pemetaan (*mapping*) ke Domain Entity.
   - **Data Sources**: Klien HTTP mentah, SQLite/Drift, atau memori lokal.
   - **Repository Implementations**: Implementasi konkret dari kontrak Domain. Layer ini mengatur pemilihan data source (misal: *cache-first strategy*).
3. **Presentation Layer:**
   - State management (BLoC, Riverpod, atau Controller), View/UI widgets yang mengonsumsi Use Cases.

#### Dependency Inversion Principle (DIP) & Dependency Injection (DI)
- **Dependency Inversion**: Modul tingkat tinggi (Use Case) tidak boleh bergantung pada modul tingkat rendah (HTTP Client). Keduanya harus bergantung pada abstraksi (Repository Interface).
- **Dependency Injection**: Teknik struktural untuk menyuntikkan ketergantungan objek dari luar (biasanya via konstruktor), alih-alih membiarkan objek tersebut menginstansiasi dependensinya sendiri (`new HttpClient()`).

Di runtime Dart, abstraksi diwujudkan melalui `abstract class` atau `abstract interface class` (Dart 3+). Hal ini memungkinkan *mocking* instan pada pengujian unit (*unit testing*) tanpa menyentuh I/O jaringan atau database aktual.

### 2. Implementasi & Contoh Kasus Nyata

Contoh implementasi *User Profile Engine* berbasis Clean Architecture murni di Dart tanpa ketergantungan library eksternal:

```dart
import 'dart:async';

// ==========================================
// 1. DOMAIN LAYER (Zero external dependencies)
// ==========================================

// Pure Entity
class User {
  final String id;
  final String email;
  final bool isVerified;

  const User({
    required this.id,
    required this.email,
    required this.isVerified,
  });
}

// Custom Domain Failure (Menghindari generic exceptions)
abstract class Failure {
  final String message;
  const Failure(this.message);
}

class ServerFailure extends Failure {
  const ServerFailure(super.message);
}

// Abstraction (Boundary)
abstract interface class UserRepository {
  Future<User> getUserById(String id);
}

// Use Case
class GetUserProfileUseCase {
  final UserRepository _repository;

  // Constructor Injection
  const GetUserProfileUseCase(this._repository);

  Future<User> execute(String userId) async {
    if (userId.trim().isEmpty) {
      throw ArgumentError('UserId tidak boleh kosong');
    }
    return await _repository.getUserById(userId);
  }
}

// ==========================================
// 2. DATA LAYER (Implements Domain contracts)
// ==========================================

// Data Model / DTO (Data Transfer Object)
class UserModel extends User {
  const UserModel({
    required super.id,
    required super.email,
    required super.isVerified,
  });

  factory UserModel.fromJson(Map<String, dynamic> json) {
    return UserModel(
      id: json['id'] as String,
      email: json['email'] as String,
      isVerified: json['is_verified'] as bool? ?? false,
    );
  }

  Map<String, dynamic> toJson() => {
        'id': id,
        'email': email,
        'is_verified': isVerified,
      };

  // Explicit mapper to domain entity jika entitas dan model berbeda bentuk
  User toEntity() => User(id: id, email: email, isVerified: isVerified);
}

// Data Source Contracts
abstract interface class UserRemoteDataSource {
  Future<Map<String, dynamic>> fetchUserRaw(String id);
}

// Data Source Implementation
class UserRemoteDataSourceImpl implements UserRemoteDataSource {
  @override
  Future<Map<String, dynamic>> fetchUserRaw(String id) async {
    // Simulasi respons HTTP I/O
    await Future.delayed(const Duration(milliseconds: 100));
    if (id == 'invalid') {
      throw Exception('500: Internal Server Error');
    }
    return {'id': id, 'email': 'dev@internal.net', 'is_verified': true};
  }
}

// Concrete Repository Implementation
class UserRepositoryImpl implements UserRepository {
  final UserRemoteDataSource _remoteDataSource;

  const UserRepositoryImpl(this._remoteDataSource);

  @override
  Future<User> getUserById(String id) async {
    try {
      final rawData = await _remoteDataSource.fetchUserRaw(id);
      final model = UserModel.fromJson(rawData);
      return model.toEntity();
    } on Exception catch (e) {
      throw ServerFailure('Gagal mengambil profil user: ${e.toString()}');
    }
  }
}

// ==========================================
// 3. DI CONTAINER / COMPOSITION ROOT
// ==========================================

class ServiceLocator {
  static final ServiceLocator _instance = ServiceLocator._internal();
  factory ServiceLocator() => _instance;
  ServiceLocator._internal();

  final Map<Type, dynamic> _registry = {};

  void registerSingleton<T>(T instance) {
    _registry[T] = instance;
  }

  void registerFactory<T>(T Function() factory) {
    _registry[T] = factory;
  }

  T resolve<T>() {
    final entry = _registry[T];
    if (entry == null) {
      throw StateError('Dependency tipe $T belum terdaftar!');
    }
    if (entry is Function) {
      return entry() as T; // Factory: Buat instance baru
    }
    return entry as T; // Singleton: Kembalikan instance yang sama
  }
}

// ==========================================
// 4. ENTRY POINT & EXECUTION
// ==========================================

void main() async {
  final ioc = ServiceLocator();

  // Konfigurasi Injeksi Ketergantungan (Composition Root)
  ioc.registerSingleton<UserRemoteDataSource>(UserRemoteDataSourceImpl());
  ioc.registerSingleton<UserRepository>(
    UserRepositoryImpl(ioc.resolve<UserRemoteDataSource>()),
  );
  ioc.registerFactory<GetUserProfileUseCase>(
    () => GetUserProfileUseCase(ioc.resolve<UserRepository>()),
  );

  // Presenter / Consumer Code
  final useCase = ioc.resolve<GetUserProfileUseCase>();

  try {
    print('Memulai eksekusi UseCase...');
    final user = await useCase.execute('USR-9021');
    print('Domain Output: User ID: ${user.id} | Email: ${user.email} | Verified: ${user.isVerified}');
  } on Failure catch (failure) {
    print('Domain Failure Terdeteksi: ${failure.message}');
  }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Polymorphic Dispatch
- Di Dart, setiap deklarasi kelas secara implisit mendefinisikan sebuah *interface*. Ketika kita mendefinisikan `abstract interface class UserRepository`, Dart membuat struktur metadata antarmuka pada tabel kelas (*class table*).
- Pemanggilan metode pada interface (misal: `_repository.getUserById(userId)`) dieksekusi melalui **Virtual Method Table (vtable) Lookup** atau **Inline Caching**. Dart VM/AOT Compiler menandai pemanggilan ini sebagai antarmuka polimorfik. Saat eksekusi, pointer metode yang tepat diekstrak secara dinamis dari instance konkret (`UserRepositoryImpl`), menghasilkan pemisahan total antara pemanggil dan implementor pada tingkat binary bytecode/mesin.

#### Alokasi Memori / Resource
- **Factory vs Singleton**: 
  - Alokasi Singleton ditahan di dalam map statis (`_registry`) di **Old Generation Space** pada Dart Heap. Referensi ini hidup sepanjang masa hidup aplikasi (dapat menjadi *memory leak* jika mengikat dependensi UI/Context).
  - Use Cases yang didaftarkan sebagai *factory* dialokasikan secara efisien di **Young Generation (Nursery)**. Dart Scavenger Garbage Collector membersihkan objek-objek ringan ini dalam hitungan fraksi mikrodetik setelah Use Case selesai dieksekusi dan keluar dari frame pemanggilan (*call stack*).
- **Data Encapsulation**: DTO (`UserModel`) yang di-mapping ke Entity murni (`toEntity()`) melepaskan pointer referensi memori dari JSON parser (`Map<String, dynamic>`), mengizinkan GC membersihkan hashmap JSON mentah secara instan dari memori heap.

#### Trade-offs
- **Indirection Latency**: Penambahan layer (*layering overhead*) menuntut serialisasi ganda (Raw Map -> DTO -> Domain Entity). Terdapat trade-off berupa alokasi objek tambahan di memori demi tercapainya independensi domain.
- **Binary Size**: Peningkatan jumlah interface abstrak dapat sedikit memperbesar tabel kelas AOT, meskipun fitur *tree-shaking* pada compiler Dart akan menghapus kelas abstrak atau implementasi yang tidak pernah direferensikan pada Composition Root.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Constructor Injection sebagai Standar Utama**: Selalu lewatkan dependensi via konstruktor. Pola ini mendeklarasikan ketergantungan secara eksplisit dan mempermudah unit testing (membuat mock/fake instance tanpa perlu konfigurasi framework DI).
- **Batas Layer yang Ketat**: Entitas Domain harus murni. Hindari dependensi pada library pihak ketiga seperti `http`, `dio`, `sqflite`, atau bahkan framework `flutter` di dalam layer Domain.
- **Failures sebagai Data Type**: Tangani error domain menggunakan *sealed classes* atau model kesalahan khusus (`Failure`), bukan melempar *raw exceptions* liar yang merusak flow eksekusi.

#### Don'ts
- **Service Locator Anti-Pattern di Dalam Kelas**: Hindari memanggil `ServiceLocator().resolve<T>()` di dalam *body* metode Use Case atau Repository. Ini menyembunyikan dependensi kelas, merusak keterbacaan, dan mempersulit isolasi unit test.
- **Menggunakan Model/DTO di Domain Layer**: Jangan jadikan kelas yang memiliki fungsi serialisasi `fromJson` sebagai Entity Domain. Jika struktur API berubah, seluruh lapisan logika bisnis Anda akan dipaksa ikut berubah.
- **God-UseCases**: Menyatukan operasi *Create, Read, Update, Delete* (CRUD) ke dalam satu kelas Use Case yang masif. Satu Use Case idealnya hanya mengeksekusi satu tujuan bisnis (*Single Responsibility Principle*).

#### Edge Cases & Memory Leaks
- **Static DI Leaks**: Memasukkan objek yang memiliki *Lifecycle* terbatas (seperti StreamSubscription atau listener UI) ke dalam *Singleton Container* global akan menyebabkan *memory leak*, karena siklus hidup instance tersebut tidak pernah dibersihkan oleh Garbage Collector. Pastikan Singleton hanya digunakan untuk objek stateless atau infrastruktur global (seperti HTTP Client / Local DB Wrapper).

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Functional Error Handling (Either / Result Pattern)**: Modifikasi `GetUserProfileUseCase` dan `UserRepository` agar tidak melempar `Exception` maupun `Failure` melalui `throw`. Implementasikan tipe generic `Result<L, R>` manual (di mana `L` adalah `Failure` dan `R` adalah data sukses), lalu amati bagaimana kontrol aliran program menjadi lebih deterministik di sisi presentasi.
2. **Auto-Disposal pada Dynamic Scopes**: Perluas fungsionalitas `ServiceLocator` sederhana di atas agar mendukung *scoped lifecycle* (misal: pendaftaran dependensi yang otomatis dibersihkan / di-dispose ketika user logout atau modul tertentu dihancurkan). Jelaskan bagaimana Dart garbage collection memperlakukan referensi tersebut setelah dibersihkan dari *registry map*.
