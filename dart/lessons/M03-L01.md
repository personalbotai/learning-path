## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Sebelum Dart 3, setiap deklarasi `class` secara implisit mendefinisikan *interface*. Fitur ini memberikan fleksibilitas tinggi, namun membawa konsekuensi arsitektural yang berbahaya: library author tidak memiliki kontrol atas bagaimana API mereka dikonsumsi. Siapa pun dapat melakukan `implements` pada class konkret mana pun dari luar library, membocorkan implementasi internal, atau merusak invariant saat library author menambahkan method baru (menyebabkan *breaking change* pada seluruh consumer yang meng-implement class tersebut).

Dart 3 memperkenalkan **Class Modifiers** untuk menegakkan batasan subtipe (*subtyping boundary*) pada level compiler. Modifikasi ini tidak hanya mengubah semantik OOP Dart, tetapi juga memengaruhi cara Dart Common Front End (CFE) dan AOT/JIT Compiler mengoptimalkan dispatch method dan *exhaustiveness checking*.

Modifikator bekerja berdasarkan **Library Boundary** (berlaku di luar file library tempat class dideklarasikan):

| Modifier | Construct | Extend (Luar Library) | Implement (Luar Library) | Mixin (Luar Library) | Exhaustive Check |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `class` (default) | Ya | Ya | Ya | Tidak | Tidak |
| `base` | Ya | **Ya** | **Tidak** | Tidak | Tidak |
| `interface` | Ya | **Tidak** | **Ya** | Tidak | Tidak |
| `final` | Ya | **Tidak** | **Tidak** | Tidak | Tidak |
| `sealed` | **Tidak** (Implisit Abstract) | Dalam library saja | Dalam library saja | Dalam library saja | **Ya** |

#### Mekanisme Subtype Constraint Propagation
Ketika sebuah modifier diterapkan, Dart memberlakukan *modifier propagation rule* untuk mencegah penurunan batasan (*downgrading security*):
- Jika sebuah class mewarisi `base class`, maka subclass tersebut **wajib** dideklarasikan sebagai `base`, `final`, atau `sealed`. Subclass tidak boleh membuka kembali restriksi menjadi class biasa.
- `interface class` mematikan pewarisan kode (*code reuse*) dari luar library, tetapi mengizinkan implementasi struktur tipe.
- `sealed class` secara internal memetakan seluruh subtipe langsung (*direct subtypes*) ke dalam set tertutup (*closed-world set*), memungkinkan CFE membuktikan keabsahan evaluasi logika secara matematis tanpa memerlukan fallback `default` pada pola `switch`.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mendemonstrasikan sistem pemrosesan transaksi pembayaran dan representasi status jaringan (*Network Result*) menggunakan pemisahan modular:

```dart
// File: payment_gateway_core.dart
library payment_gateway_core;

import 'dart:async';

/// 1. INTERFACE: Hanya mendefinisikan kontrak I/O.
/// Consumer di luar library DILARANG melakukan `extends` (mencegah pewarisan internal state).
interface class LogSink {
  void write(String message) {
    print('[DEFAULT LOG]: $message');
  }
}

/// 2. BASE: Membawa state penting dan invariant mesin.
/// Konsumen di luar library WAJIB melakukan `extends` untuk menjamin `super()` terpanggil,
/// dan DILARANG melakukan `implements` murni.
base class TransactionSession {
  final String sessionId;
  final DateTime createdAt;
  bool _isDisposed = false;

  TransactionSession(this.sessionId) : createdAt = DateTime.now();

  void dispose() {
    _isDisposed = true;
  }

  bool get isActive => !_isDisposed;
}

/// 3. FINAL: Keamanan kritis. Tidak boleh ada subclass baru di luar library.
/// Menghentikan seluruh rantai polimorfisme di luar domain ini.
final class SecureKeyStore {
  final String _masterKey;

  SecureKeyStore(this._masterKey);

  bool validateKey(String key) => key == _masterKey;
}

/// 4. SEALED: Representasi state algebra (Algebraic Data Types).
/// Seluruh kemungkinan turunan HARUS berada di library ini.
sealed class PaymentResult {
  const PaymentResult();
}

final class PaymentSuccess extends PaymentResult {
  final String transactionHash;
  final double amount;
  const PaymentSuccess(this.transactionHash, this.amount);
}

final class PaymentFailure extends PaymentResult {
  final String errorCode;
  final Exception exception;
  const PaymentFailure(this.errorCode, this.exception);
}

final class PaymentPending extends PaymentResult {
  final Duration estimatedWait;
  const PaymentPending(this.estimatedWait);
}

/// Handler yang memanfaatkan Exhaustiveness Checking
String resolveStatus(PaymentResult result) {
  // Compiler menjamin tidak ada case yang terlewat.
  // Klausa 'default' tidak diperlukan dan justru menjadi code smell.
  return switch (result) {
    PaymentSuccess(transactionHash: final hash, amount: final amt) =>
      'Success! Hash: $hash, Amount: \$${amt.toStringAsFixed(2)}',
    PaymentFailure(errorCode: final code) =>
      'Failed with error code: $code',
    PaymentPending(estimatedWait: final wait) =>
      'Processing... ETA: ${wait.inSeconds}s',
  };
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime: Devirtualization & Static Dispatch
- **Dart Common Front End (CFE)**: Penegakan class modifier sepenuhnya dilakukan pada fase analisa AST (*Abstract Syntax Tree*) di level CFE sebelum Dart Kernel Intermediate Representation (`.dill`) dihasilkan. Tidak ada dynamic check overhead (seperti pemeriksaan reflection) saat runtime.
- **AOT Devirtualization**: Ketika class ditandai sebagai `final` atau `sealed`, compiler AOT Dart mengetahui batas pasti dari *hierarchy tree*. Jika sebuah pemanggilan method ditujukan pada objek yang tipenya `final` dan tidak memiliki subtipe di dalam library yang sama, compiler melakukan **devirtualization**: pemanggilan melalui *VTable (Virtual Method Table)* diubah menjadi direct branch instruction (pemanggilan fungsi langsung di level assembly), mengeliminasi latensi indirect jump.

#### Exhaustiveness Analysis (Decision Tree Compilation)
Pada `sealed class`, CFE membangun sistem *space-covering logic*. CFE memetakan subtipe konkret ke dalam *disjoint sub-spaces*. 
Ketika konstruksi `switch` mengevaluasi instance `sealed`, compiler memverifikasi apakah gabungan subtipe pada `case` mencakup seluruh himpunan tipe yang dimungkinkan:
$$\bigcup_{i=1}^{n} SubType_i = SealedParent$$
Jika coverage $< 100\%$, CFE gagal memproduksi bytecode dan memunculkan static error: `"The type 'PaymentResult' is not exhaustively matched"`.

#### Alokasi Memori
Modifiers tidak menambah footprint memori per instance objek. Instance dari `sealed class` memiliki header memori objek Dart standar:
- *Object Header* (GC metadata & Class identifier tag): 64-bit pada target modern (x86_64, ARM64).
- *Fields reference payload*.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan `sealed` untuk Domain Modeling**: Gantikan representasi status berbasis `enum` + `data class` manual dengan hierarki `sealed class` untuk mendapatkan kapabilitas *type-safe pattern matching* bersama *exhaustive check*.
- **Terapkan `interface class` untuk Services/Adapters**: Buat dependency injection yang bersih. Ini memaksa consumer menulis implementasi mock/spies sendiri tanpa mengotori instance melalui pewarisan method default secara tidak sengaja.
- **Terapkan `base` untuk Lifecycle Framework Class**: Gunakan ketika kelas dasar memiliki lifecycle yang tidak boleh dilewati (misal: registrasi event listener di constructor, pelepasan memory di `dispose()`).

#### Don'ts
- **Hindari penggunaan `sealed` untuk hierarki yang dinamis**: `sealed class` dirancang untuk tipe tertutup (*closed-world*). Jangan gunakan `sealed` jika library Anda dirancang agar developer lain dapat menambahkan variasi tipe secara eksternal. Gunakan `base class` atau `abstract class` standar untuk skenario extensible plugin.
- **Jangan menggunakan `base` jika hanya ingin mengekspos API kontrak**: Menerapkan `base` memaksa consumer membawa seluruh memori implementasi internal kelas Anda.

#### Edge Cases
- **Modifier Combination Rules**:
  - `abstract base class`: Boleh memiliki abstract member, memaksa pewarisan (`extends`) di luar library, dan subkelas wajib berstatus `base`, `final`, atau `sealed`.
  - `abstract interface class`: Murni bertindak seperti interface Java murni (hanya kontrak), tanpa memperbolehkan `extends` di luar library.
- **Transitivitas Subclassing `base`**: Kegagalan mendeklarasikan turunan dari `base` class dengan modifier (`base`, `final`, atau `sealed`) akan memicu compile error seketika. Anda tidak dapat menyembunyikan modifier `base` setelah hierarki dimulai.

### 5. Tantangan Eksplorasi Mandiri

1. **Analisis Dekompilasi AOT**:
   Buat dua program terpisah:
   - Program A: Memanggil method dari hierarki terbuka (`class` konvensional dengan 1 subclass).
   - Program B: Memanggil method dari hierarki tertutup (`final class` tanpa subclass).
   Kompilasi keduanya menggunakan `dart compile exe --save-debugging-info` dan bandingkan apakah terjadi *inlining* pemanggilan fungsi pada file biner yang dihasilkan.

2. **Refactoring Legacy State**:
   Ambil arsitektur `Bloc` atau state management yang masih menggunakan `abstract class NetworkState` konvensional. Ubah menjadi `sealed class NetworkState` dan ganti rantai `if (state is Loading) ... else if (state is Success)` dengan pattern matching `switch (state)`. Buktikan bahwa compiler Dart akan mendeteksi ketika Anda menghapus penanganan salah satu state tanpa menambahkan blok `default`.
