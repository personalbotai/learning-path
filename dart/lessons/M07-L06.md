### 1. Konsep & Arsitektur Mendalam

Model konkurensi Dart mengadopsi prinsip *Actor Model*. Setiap unit eksekusi disebut **Isolate**, yang memiliki *event loop* serta *heap memory* mandiri. Tidak ada *shared memory* antar-isolate; komunikasi antar-isolate dilakukan secara eksklusif melalui *message passing* via `SendPort` dan `ReceivePort`.

Meskipun fungsi seperti `Isolate.run()` (diperkenalkan pada Dart 2.19) memudahkan eksekusi tugas komputasi berat secara *one-off*, pendekatan ini memiliki kelemahan arsitektural fatal untuk beban kerja berfrekuensi tinggi (*high-throughput*): **Spawn Overhead**.

```
Pendekatan Naif (Isolate.run):
[Task 1] ──> Spawn Isolate ──> Init Heap ──> Exec ──> Teardown ──> GC
[Task 2] ──> Spawn Isolate ──> Init Heap ──> Exec ──> Teardown ──> GC (Overhead CPU & Latensi)

Pendekatan Worker Pool:
             ┌──> Worker Isolate 1 (Idle/Busy) ──┐
[Task Queue] ┼──> Worker Isolate 2 (Idle/Busy) ──┼──> [Aggregated Results]
             └──> Worker Isolate N (Idle/Busy) ──┘
             (Isolate tetap hidup; komunikasi lewat stream pesan)
```

Pembuatan isolate baru membutuhkan alokasi struktur data C++ internal runtime Dart, alokasi heap baru (minimal puluhan hingga ratusan kilobyte), dan registrasi ke OS thread pool. Jika aplikasi memproses ratusan request parsing JSON atau enkripsi per detik, melakukan *spawning* dan *killing* isolate secara serial akan menghabiskan CPU cycles hanya untuk manajemen lifecycle.

**Worker Architecture** dan **Isolate Pool** memecahkan masalah ini dengan:
1. Melakukan inisialisasi sejumlah worker isolate (biasanya $N$ atau $N-1$ sesuai jumlah logical CPU core) saat startup (*warm-up*).
2. Mempertahankan isolate tersebut tetap aktif (*long-lived*) menggunakan *event loop* yang terus mendengarkan `ReceivePort`.
3. Mengatur antrean kerja (*Job Queue*) di Main Isolate dan mendistribusikan muatan kerja (*payload*) ke worker yang berstatus *idle*.
4. Mengembalikan hasil komputasi ke Main Isolate dan menandai worker tersebut siap menerima instruksi berikutnya.

### 2. Implementasi & Contoh Kasus Nyata

Berikut adalah implementasi *generic* thread-safe Worker Pool tanpa dependensi eksternal, yang mengelola *lifecycle*, antrean tugas (*task queuing*), dan eksekusi paralel.

```dart
import 'dart:async';
import 'dart:io';
import 'dart:isolate';

/// Representasi payload tugas yang dikirim ke worker
class _Job<T, R> {
  final R Function(T) task;
  final T data;
  final Completer<R> completer;

  _Job(this.task, this.data, this.completer);
}

/// Pesan inisialisasi dan komunikasi antar isolate
class _WorkerCommand {
  final Function? task;
  final dynamic data;
  final SendPort replyPort;

  _WorkerCommand({this.task, this.data, required this.replyPort});
}

/// Unit Worker yang mengelola Isolate persisten
class _Worker {
  late final Isolate _isolate;
  late final SendPort _sendPort;
  bool isBusy = false;

  Future<void> init() async {
    final initPort = ReceivePort();
    _isolate = await Isolate.spawn(_workerEntryPoint, initPort.sendPort);
    // Port pertama yang diterima adalah SendPort milik worker
    _sendPort = await initPort.first as SendPort;
  }

  Future<R> execute<T, R>(R Function(T) task, T data) async {
    isBusy = true;
    final responsePort = ReceivePort();

    _sendPort.send(_WorkerCommand(
      task: task,
      data: data,
      replyPort: responsePort.sendPort,
    ));

    final result = await responsePort.first;
    responsePort.close();
    isBusy = false;

    if (result is _WorkerError) {
      Error.throwWithStackTrace(result.error, result.stackTrace);
    }
    return result as R;
  }

  void dispose() {
    _isolate.kill(priority: Isolate.immediate);
  }

  // Entry point Isolate (berjalan di heap terpisah)
  static void _workerEntryPoint(SendPort mainSendPort) {
    final commandPort = ReceivePort();
    mainSendPort.send(commandPort.sendPort);

    commandPort.listen((message) {
      if (message is _WorkerCommand) {
        try {
          final computation = message.task!;
          final res = computation(message.data);
          message.replyPort.send(res);
        } catch (e, st) {
          message.replyPort.send(_WorkerError(e, st));
        }
      }
    });
  }
}

class _WorkerError {
  final Object error;
  final StackTrace stackTrace;
  _WorkerError(this.error, this.stackTrace);
}

/// Isolate Pool Orchestrator
class IsolatePool {
  final int poolSize;
  final List<_Worker> _workers = [];
  final List<_Job<dynamic, dynamic>> _queue = [];
  bool _isDisposed = false;

  IsolatePool({int? size})
      : poolSize = size ?? Platform.numberOfProcessors {
    if (poolSize <= 0) throw ArgumentError('Pool size harus > 0');
  }

  Future<void> start() async {
    for (var i = 0; i < poolSize; i++) {
      final worker = _Worker();
      await worker.init();
      _workers.add(worker);
    }
  }

  /// Menjadwalkan tugas untuk diproses oleh worker yang idle
  Future<R> schedule<T, R>(R Function(T) task, T data) {
    if (_isDisposed) {
      throw StateError('IsolatePool sudah dimatikan.');
    }

    final completer = Completer<R>();
    _queue.add(_Job<T, R>(task, data, completer));
    _dispatchNext();
    return completer.future;
  }

  void _dispatchNext() {
    if (_queue.isEmpty) return;

    // Cari worker yang tidak sedang sibuk
    final availableWorker = _workers.where((w) => !w.isBusy).firstOrNull;

    if (availableWorker != null) {
      final job = _queue.removeAt(0);
      
      availableWorker.execute(job.task, job.data).then((result) {
        job.completer.complete(result);
        _dispatchNext(); // Proses antrean tersisa
      }).catchError((err, st) {
        job.completer.completeError(err, st);
        _dispatchNext();
      });
    }
  }

  Future<void> dispose() async {
    _isDisposed = true;
    for (final worker in _workers) {
      worker.dispose();
    }
    _workers.clear();
    for (final job in _queue) {
      job.completer.completeError(StateError('Pool terminated before execution'));
    }
    _queue.clear();
  }
}

// Simulasi Komputasi Berat (CPU-bound)
int heavyComputation(int value) {
  var count = 0;
  for (var i = 0; i < 50000000; i++) {
    count += (i ^ value);
  }
  return count;
}

void main() async {
  print('Inisialisasi Isolate Pool...');
  final pool = IsolatePool(size: 4);
  await pool.start();

  final stopwatch = Stopwatch()..start();

  // Memicu 10 tugas berat serentak ke dalam antrean pool
  final futures = List.generate(10, (index) {
    return pool.schedule<int, int>(heavyComputation, index * 42).then((res) {
      print('Job $index selesai, hasil: $res');
      return res;
    });
  });

  await Future.wait(futures);
  stopwatch.stop();

  print('Semua job selesai dalam: ${stopwatch.elapsedMilliseconds}ms');
  await pool.dispose();
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
- **Thread Affinity**: Dart Runtime memetakan isolate ke OS threads menggunakan `ThreadPool` internal VM. Isolate yang berstatus *idle* tidak memakan CPU cycles karena *underlying thread*-nya dibebaskan atau masuk status *wait* pada *event queue condition variable*.
- **Task Dispatching**: Ketika closure dikirim via `SendPort`, Dart VM tidak mentransfer representasi biner fungsi jika fungsi tersebut adalah *top-level* atau *static method*. Dart hanya mengirimkan *pointer reference* ke *object pool entry* dari fungsi tersebut di dalam snapshot program yang bersifat *read-only*.

#### Alokasi Memori / Resource
- **Message Serialization/Copying**: Port serialization terjadi secara native via modul C++ Dart VM (`dart::RawObject*`). Secara default, pesan yang dikirim lewat `SendPort.send()` disalin secara mendalam (*deep copy*). Objek primitif, String, dan representasi biner disalin byte-by-byte dari heap Isolate A ke Isolate B.
- **TransferableTypedData**: Jika Anda memindahkan data biner berukuran besar (misalnya: citra raw RGB, file buffer ratusan MB), penyalinan memori akan memicu latensi tinggi dan lonjakan heap ganda. Dart menyediakan primitif `TransferableTypedData`. Mekanisme ini memindahkan *ownership* *backing store pointer* secara instan ($O(1)$) antar-heap tanpa alokasi baru, membuat data di isolate pengirim menjadi *inaccessible* (dimutasi/dikosongkan).

```
Default Copy:
Heap A: [Buffer 100MB] ──(Copy 100MB)──> Heap B: [Buffer 100MB Baru] (Memori total: 200MB)

TransferableTypedData:
Heap A: [Pointer Ref]  ──(Move Pointer)──> Heap B: [Buffer 100MB Yang Sama] (Memori total: 100MB)
Heap A: [Void/Invalid]
```

#### Trade-offs
- **Warm-up Latency vs Spawning Latency**: Pool membayar *cost* latensi di awal saat aplikasi boot untuk membuat isolate. Namun, latensi per job menjadi deterministik (hanya tersisa overhead komunikasi pesan).
- **Idle Memory Footprint**: Isolate yang tidak bekerja tetap memakan base heap memori (~30KB-100KB per isolate) tergantung platform runtime.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Fungsi Top-Level atau Static**: Pastikan closure yang diserahkan ke worker tidak menangkap konteks lexical scope luar (*outer scope*). Jika fungsi membawa referensi objek instance dari main isolate, VM akan gagal melakukan serialisasi dan melemparkan exception runtime (`ArgumentError: Invalid argument: closure with free variables`).
- **Batasi Pool Size Sesuai CPU Cores**: Tetapkan worker pool maksimal `Platform.numberOfProcessors`. Menetapkan pool size lebih besar dari jumlah logical core tidak meningkatkan throughput komputasi, melainkan justru memicu *CPU context switching thrashing*.
- **Manfaatkan `TransferableTypedData`**: Bungkus `Uint8List` ke dalam `TransferableTypedData.fromList([...])` untuk muatan data biner besar.

#### Don'ts
- **Menghindari Task Berdurasi Sangat Pendek**: Mengirim tugas komputasi mikro (eksekusi < 1 milidetik) ke pool justru menurunkan performa. Overhead serialisasi pesan dan penjadwalan antrean lebih mahal daripada mengeksekusinya langsung di *event loop* utama.
- **Tidak Mematikan Isolate (`dispose`)**: Isolate yang tidak di-*kill* dan masih mereferensikan `ReceivePort` yang terbuka tidak akan pernah dibersihkan oleh Garbage Collector, memicu *memory leak* permanen pada proses aplikasi.

#### Edge Cases
- **Serialization Limits**: Tipe data seperti `Socket`, `ReceivePort`, atau objek C-pointer dari `dart:ffi` tidak dapat dikirimkan secara langsung melalui port antarisolate.
- **Uncaught Exceptions di Worker**: Exception fatal yang tidak ditangkap (`try-catch`) di dalam *event loop* worker isolate dapat membunuh isolate tersebut secara diam-diam. Worker pool harus selalu mengintegrasikan mekanisme *error listener* (`isolate.addErrorListener()`) untuk merestart worker secara otomatis jika terjadi *crash*.

### 5. Tantangan Eksplorasi Mandiri

1. **Auto-healing Dynamic Pool**: Modifikasi kelas `IsolatePool` di atas agar mampu mendeteksi isolate yang *crash* akibat *unhandled exception* (gunakan `Isolate.addErrorListener`), lalu buat mekanisme *respawn* otomatis untuk menjaga kapasitas worker tetap stabil.
2. **Prioritas Antrean (Priority Queue Worker)**: Ubah struktur FIFO `_queue` pada antrean tugas menjadi antrean berbobot (*priority queue*), di mana setiap tugas memiliki enum `Priority { low, normal, high }` dan tugas dengan prioritas tinggi langsung dieksekusi oleh worker berikutnya yang bebas.
3. **Benchmark Memory Footprint**: Bandingkan konsumsi memori dan latensi throughput antara memproses 1.000 file payload biner (masing-masing 5MB) menggunakan `SendPort.send(uint8list)` biasa versus `TransferableTypedData`. Catat perbedaan puncak heap memori pada Dart DevTools Profiler.
