### 1. Konsep & Arsitektur Mendalam

Dalam arsitektur sistem terdistribusi, komunikasi jaringan bersifat *inherently unreliable*. Kegagalan jaringan tidak hanya berupa koneksi yang putus (*fail-fast*), tetapi juga degradasi latensi (*slow-fail*) dan paket data yang hilang tanpa kabar (*silent drop*). Oleh karena itu, aplikasi Dart production-grade membutuhkan tiga pilar ketahanan I/O: **Timeouts**, **Retries**, dan **Interceptors**.

```
[Client Call]
     │
     ▼
┌────────────────────────────────────────────────────────┐
│ Interceptor Pipeline (Chain of Responsibility)         │
│  ├─ onRequest()       ──> [Mutasi Header / Auth Inject]│
│  │                                                     │
│  ├─ Network Layer     ──> [Socket Connect / TLS]       │
│  │      ▲                       │                      │
│  │   (Retry Logic)        (Timeout Watcher)            │
│  │      │                       ▼                      │
│  ├─ onError()         ──> [Catch 5xx / SocketException]│
│  │                                                     │
│  └─ onResponse()      ──> [Logging / Data Transform]   │
└────────────────────────────────────────────────────────┘
     │
     ▼
[UI / Business Logic Result]
```

#### Timeouts
Di level arsitektur I/O socket, timeout terbagi menjadi beberapa fase:
1. **Connection Timeout**: Durasi maksimal untuk menyelesaikan *TCP three-way handshake* dan *TLS negotiation*.
2. **Send Timeout**: Batas waktu transmisi payload dari buffer lokal ke soket kernel.
3. **Receive Timeout**: Durasi maksimal menunggu paket data pertama dari server (*time to first byte/TTFB*) atau jarak antar-chunk data dalam respons streaming.

Jika timeout tidak dikonfigurasi, sistem operasi default (tergantung OS host) dapat menahan socket terbuka hingga belasan menit (biasanya timeout TCP default Linux berkisar antara 2 menit hingga 2 jam untuk keep-alive probes), menyebabkan *resource exhaustion* (penumpukan file descriptor dan memory leak).

#### Retries & Jitter
Melakukan retry secara naif (misalnya langsung mengulang *request* secara instan berulang kali) dapat memicu fenomena **Thundering Herd Problem** yang melumpuhkan backend yang sedang pulih. Solusi standarnya adalah:
- **Exponential Backoff**: Meningkatkan durasi tunggu secara eksponensial ($t = base \times 2^{attempt}$).
- **Full Jitter**: Menambahkan komponen acak pseudorandom ($t = \text{random}(0, base \times 2^{attempt})$) untuk mendistribusikan beban retry secara merata pada timeline server.
- **Idempotency Guard**: Retry otomatis hanya boleh dieksekusi secara aman pada HTTP methods yang bersifat idempoten (`GET`, `PUT`, `DELETE`, `HEAD`) atau memiliki idempotency key eksplisit pada headers untuk `POST`/`PATCH`.

#### Interceptors
Menggunakan pola desain **Chain of Responsibility**. Setiap interceptor memotong alur eksekusi sebelum payload keluar ke network layer (`onRequest`), setelah respons diterima (`onResponse`), atau saat terjadi anomali (`onError`). Pola ini memisahkan logika *cross-cutting concerns*—seperti logging, metrik tracing distributed (`OpenTelemetry`), injeksi JWT/OAuth2, dan handling token expiration otomatis—dari *business logic*.

### 2. Implementasi & Contoh Kasus Nyata

Contoh berikut mengimplementasikan sistem HTTP Client menggunakan package `dio` (standar industri di ekosistem Dart) yang mencakup **timeouts granular**, **Retry Interceptor dengan Exponential Backoff + Jitter**, serta **Automatic Token Refresh Lock**.

```dart
import 'dart:async';
import 'dart:math';
import 'package:dio/dio.dart';

// 1. Model untuk Token Management
class AuthSession {
  static String? accessToken = 'EXPIRED_TOKEN';
  static Future<String> refreshAccessToken() async {
    // Simulasi network call refresh token
    await Future.delayed(const Duration(milliseconds: 500));
    accessToken = 'NEW_VALID_TOKEN_${DateTime.now().millisecondsSinceEpoch}';
    return accessToken!;
  }
}

// 2. Retry Interceptor dengan Backoff & Full Jitter
class ResilientRetryInterceptor extends Interceptor {
  final Dio dio;
  final int maxRetries;
  final Duration baseDelay;
  final Random _random = Random();

  ResilientRetryInterceptor({
    required this.dio,
    this.maxRetries = 3,
    this.baseDelay = const Duration(milliseconds: 500),
  });

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    final requestOptions = err.requestOptions;
    
    // Cek apakah request boleh di-retry
    if (!_shouldRetry(err, requestOptions)) {
      return handler.next(err);
    }

    final currentAttempt = (requestOptions.extra['retry_attempt'] as int? ?? 0) + 1;

    if (currentAttempt <= maxRetries) {
      requestOptions.extra['retry_attempt'] = currentAttempt;

      // Hitung Exponential Backoff + Full Jitter
      // Delay = rand(0, baseDelay * 2^(attempt - 1))
      final maxDelayMs = baseDelay.inMilliseconds * pow(2, currentAttempt - 1).toInt();
      final jitterDelayMs = _random.nextInt(maxDelayMs + 1);
      final delay = Duration(milliseconds: jitterDelayMs);

      print('[RETRY] Attempt $currentAttempt for ${requestOptions.path} after ${delay.inMilliseconds}ms');
      await Future.delayed(delay);

      try {
        // Clone options dan ulangi fetch
        final response = await dio.fetch(requestOptions);
        return handler.resolve(response);
      } on DioException catch (retryError) {
        // Teruskan error ke lifecycle berikutnya
        return handler.next(retryError);
      }
    }

    return handler.next(err);
  }

  bool _shouldRetry(DioException err, RequestOptions options) {
    // Hanya retry safe method atau status code sementara (Transient Errors)
    final isTransientNetworkError = err.type == DioExceptionType.connectionTimeout ||
        err.type == DioExceptionType.sendTimeout ||
        err.type == DioExceptionType.receiveTimeout ||
        err.type == DioExceptionType.connectionError;

    final is5xxServerError = err.response != null && 
        (err.response!.statusCode! >= 500 && err.response!.statusCode! <= 599);

    final isIdempotentMethod = const ['GET', 'HEAD', 'PUT', 'DELETE'].contains(options.method.toUpperCase());

    return (isTransientNetworkError || is5xxServerError) && isIdempotentMethod;
  }
}

// 3. Auth Interceptor dengan Locking Mechanism
class AuthInterceptor extends QueuedInterceptor {
  final Dio dio;

  AuthInterceptor({required this.dio});

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    if (AuthSession.accessToken != null) {
      options.headers['Authorization'] = 'Bearer ${AuthSession.accessToken}';
    }
    handler.next(options);
  }

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    // Tangani unauthorized error (401)
    if (err.response?.statusCode == 401) {
      try {
        print('[AUTH] Token invalid. Memulai refresh token...');
        // QueuedInterceptor memastikan request lain antre hingga interceptor ini selesai
        final newToken = await AuthSession.refreshAccessToken();

        // Mutasi request lama dengan header baru
        final requestOptions = err.requestOptions;
        requestOptions.headers['Authorization'] = 'Bearer $newToken';

        // Eksekusi ulang request yang sempat gagal
        final response = await dio.fetch(requestOptions);
        return handler.resolve(response);
      } catch (refreshErr) {
        // Jika refresh token juga gagal, force logout logic
        return handler.next(err);
      }
    }
    handler.next(err);
  }
}

// 4. Inisialisasi dan Runner
void main() async {
  final dio = Dio(
    BaseOptions(
      baseUrl: 'https://httpbin.org',
      connectTimeout: const Duration(seconds: 3), // Handshake & TLS
      sendTimeout: const Duration(seconds: 3),    // Upload stream
      receiveTimeout: const Duration(seconds: 3), // Download wait
      headers: {'Accept': 'application/json'},
    ),
  );

  // Pasang interceptors secara berurutan
  dio.interceptors.addAll([
    AuthInterceptor(dio: dio),
    ResilientRetryInterceptor(dio: dio, maxRetries: 3),
    LogInterceptor(responseBody: false), // Logging bawaan
  ]);

  try {
    print('--> Mengirim Request 1 (Simulasi flaky network status 500)...');
    // Endpoint ini akan menghasilkan 500 dan memicu ResilientRetryInterceptor
    await dio.get('/status/500');
  } catch (e) {
    print('<-- Gagal setelah retry limit tercapai.\n');
  }

  try {
    print('--> Mengirim Request 2 (Simulasi auth recovery)...');
    // Memvalidasi apakah header Authorization terinjeksi
    final response = await dio.get('/bearer');
    print('<-- Berhasil: StatusCode ${response.statusCode}');
  } catch (e) {
    print('<-- Gagal Request 2: $e');
  }
}
```

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### Eksekusi & Runtime
1. **Timer & Event Loop Binding**:
   Saat `connectTimeout` atau `receiveTimeout` berjalan, runtime Dart mendaftarkan sebuah `Timer` ke dalam **Event Queue** di isolate pemanggil.
   - Di balik layar, platform engine Dart menggunakan API socket native OS: `epoll` di Linux/Android, `kqueue` di macOS/iOS, atau `I/O Completion Ports (IOCP)` di Windows via abstraction layer `dart:io`.
   - Jika event `FD_READ` atau handshake acknowledgment tidak kembali dari OS kernel sebelum durasi timer tercapai, event callback timer terpicu. Runtime mengeksekusi `socket.destroy()`, membatalkan subscription stream, dan melemparkan `DioExceptionType.connectionTimeout` atau `SocketException`.

2. **Pipeline Stream Transformer**:
   `Dio.interceptors` bekerja sebagai rantai pemrosesan monadic terstruktur menggunakan abstraction `Future`. Setiap interceptor membungkus `Completer<Response>` atau `Completer<RequestOptions>`. 
   - `QueuedInterceptor` menghentikan sementara iterasi pada internal task queue Dio via serial async pipeline (`Lock` primitive) sehingga request paralel berikutnya tidak ditembakkan sebelum refresh token internal resolve.

#### Alokasi Memori / Resource
- **File Descriptors (FD)**: Setiap koneksi HTTP yang menggantung memakan satu socket descriptor di kernel OS. Kegagalan mengatur `receiveTimeout` pada koneksi streaming dapat menyebabkan *socket exhaustion* (mencapai batas `ulimit -n`).
- **Buffer Retention**: Saat koneksi timeout tidak dihentikan secara eksplisit, buffer TCP internal (`SO_RCVBUF` / `SO_SNDBUF`) tetap dialokasikan oleh kernel, dan stream buffer Dart (`Uint8List` chunks) tidak dapat diambil oleh *Garbage Collector* (GC).

#### Trade-offs
- **QueuedInterceptor vs Regular Interceptor**: `QueuedInterceptor` menjamin sinkronisasi dan mencegah *race condition* saat refreshing token, namun menyebabkan bottleneck (head-of-line blocking) pada throughput request lain yang berjalan bersamaan.
- **Aggressive Timeouts vs High-Latency Networks**: Setting timeout yang terlalu ketat (< 2 detik) pada jaringan seluler 3G/Edge akan menghasilkan *false positive aborts*, meningkatkan laju kegagalan secara artifisial.

### 4. Best Practices & Common Pitfalls

#### Do's
- **Gunakan Mutex/Queue Saat Refresh Token**: Saat 5 request bersamaan mendapatkan error `401 Unauthorized`, hanya 1 network call ke endpoint `/auth/refresh` yang boleh dieksekusi. 4 request sisanya harus menunggu token baru diperoleh, lalu mengeksekusi ulang request mereka menggunakan token baru tersebut.
- **Implementasikan Jitter**: Selalu campur randomisasi dalam perhitungan delay retry. Menghilangkan jitter akan membuat ribuan client menembak ulang server secara sinkron, menciptakan pola *traffic spike* yang repetitif.
- **Gunakan Idempotency Keys**: Untuk operasi `POST` pembuatan transaksi moneter/checkout, sertakan UUID unik pada header (`Idempotency-Key: <UUID>`) agar aman dilakukan retry oleh interceptor jika terjadi drop koneksi di tengah jalan.

#### Don'ts
- **Jangan Mengabaikan Request Cancellation**: Jangan biarkan request tetap berjalan jika komponen UI/Widget sudah di-unmount. Gunakan `CancelToken` milik Dio:
  ```dart
  final cancelToken = CancelToken();
  // Di Flutter State:
  @override
  void dispose() {
    cancelToken.cancel("Widget destroyed");
    super.dispose();
  }
  ```
- **Jangan Melakukan Retry pada Client Errors (4xx)**: Status `400 Bad Request`, `403 Forbidden`, atau `422 Unprocessable Entity` bersifat deterministik. Mengulanginya tanpa mengubah payload adalah operasi sia-sia yang membuang bandwidth. Pengecualian: `401` (tangani via refresh token) dan `429` (hormati header `Retry-After`).

#### Edge Cases
- **Half-Open TCP Connections**: Keadaan di mana satu sisi koneksi terputus (misalnya antarmuka Wi-Fi mati mendadak) tanpa mengirimkan paket `FIN` atau `RST`. Tanpa socket timeout dan `SO_KEEPALIVE`, isolate Dart akan menunggu secara tak terbatas pada status reading.
- **Mutasi Payload Bersarang**: Berhati-hatilah saat mengubah `RequestOptions.data` di dalam interceptor. Jika data berupa non-rewindable `Stream`, operasi retry kedua akan crash dengan `StateError: Stream has already been listened to`. Ubah stream menjadi bytes (`Uint8List`) jika request berpotensi di-retry.

### 5. Tantangan Eksplorasi Mandiri

1. **Implementasi Rate Limit Circuit Breaker**:
   Modifikasi `ResilientRetryInterceptor` agar memeriksa status code `429 Too Many Requests`. Baca header `Retry-After` dari respons, parsing nilai sekundernya, dan tunda retry tepat sesuai durasi yang diinstruksikan oleh server sebelum mencoba kembali.

2. **Deteksi Non-Rewindable Stream**:
   Buat custom interceptor yang memvalidasi apakah tipe data pada `RequestOptions.data` adalah upload stream file (`Stream<List<int>>`). Buat mekanisme pertahanan (*guard*) agar interceptor secara otomatis membatalkan (*skip*) proses auto-retry jika stream tersebut tidak dapat diputar ulang (*rewound*), untuk mencegah runtime crash `Stream has already been listened to`.
