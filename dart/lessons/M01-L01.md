## 📖 Materi Lengkap

### 1. Konsep & Arsitektur Mendalam

Dart dirancang oleh Google dengan tujuan unik: memberikan siklus pengembangan secepat mungkin (*sub-second iterative development*) tanpa mengorbankan performa eksekusi tingkat rendah pada tahap produksi. Kunci fleksibilitas ini terletak pada dualitas arsitektur kompilasinya: **Just-In-Time (JIT)** dan **Ahead-Of-Time (AOT)**, yang ditopang oleh **Dart SDK** dan **Dart VM**.

```
                           +------------------------+
                           |  Source Code (.dart)   |
                           +------------------------+
                                       |
                                       v
                     +-----------------------------------+
                     |  Dart CFE (Common Front End)      |
                     |  - Type checking & syntactic pass |
                     |  - Generates Kernel AST (.dill)   |
                     +-----------------------------------+
                                       |
            +--------------------------+--------------------------+
            | (Development Mode)                                  | (Production Mode)
            v                                                     v
+-----------------------+                             +-----------------------+
|        Dart VM        |                             |     AOT Compiler      |
|  - JIT Engine         |                             |  - Global Type Flow   |
|  - Profiler & Deopt   |                             |  - Tree Shaking       |
|  - Stateful Hot Reload|                             |  - Assembly Emission  |
+-----------------------+                             +-----------------------+
            |                                                     |
            v                                                     v
   Native Machine Code                                  Standalone Executable
 (Fast dev cycles / Dynamic)                           (Zero runtime VM / ELF)
```

#### A. Dart SDK
Dart SDK bukan sekadar *compiler*, melainkan ekosistem *toolchain* lengkap yang mencakup:
1. **Core Libraries**: Pustaka fundamental seperti `dart:core`, `dart:async`, `dart:io`, `dart:collection`, dan `dart:isolate`.
2. **Dart CLI (`dart`)**: Antarmuka terpadu untuk formatting (`format`), static analysis (`analyze`), testing (`test`), dan kompilasi (`compile`).
3. **Analysis Server**: *Daemon* berbasis *Language Server Protocol* (LSP) yang memfasilitasi autocompletion, refactoring, dan linter real-time pada IDE/editor.
4. **CFE (Common Front End)**: Komponen modular yang mem-parsing kode Dart dan memvalidasi tipe sebelum menghasilkan representasi *intermediate* berbasis Abstract Syntax Tree (AST) bernama **Kernel AST** (format biner `.dill`).

#### B. Dart VM
Dart VM adalah *process runtime environment* yang menyediakan abstraksi komputasi untuk kode Dart native. Fitur inti Dart VM meliputi:
* **Isolate Model**: Eksekusi konkurensi berbasis *single-threaded event loop per isolate*. Tidak ada *shared memory* antar-isolate, meminimalisir kebutuhan *mutex/lock* pada level aplikasi.
* **Garbage Collector (GC)**: Sistem alokasi memori berkinerja tinggi berbasis *generational GC* (Young Generation/Scavenger dan Old Generation/Mark-Sweep-Compact).
* **Execution Engines**: Memiliki interpreter, baseline compiler, dan optimizing compiler.

#### C. Paradigma Kompilasi: JIT vs AOT

| Karakteristik | Just-In-Time (JIT) | Ahead-Of-Time (AOT) |
| :--- | :--- | :--- |
| **Waktu Kompilasi** | Saat aplikasi berjalan (*runtime*) | Sebelum aplikasi dijalankan (*build-time*) |
| **Target Output** | Dynamic machine code dalam RAM | Self-contained executable (ELF/Mach-O/PE) |
| **Startup Latency** | Relatif lambat (perlu *warm-up* dan parsing) | Sangat cepat (*near-instantaneous*) |
| **Penggunaan Memori** | Lebih tinggi (termasuk Dart VM, CFE, dan Profiler) | Sangat hemat (hanya runtime minimal + stripped code) |
| **Fitur Unggulan** | Stateful Hot Reload & Dynamic Debugging | Deterministic performance & Binary distribution |
| **Penggunaan** | Siklus Development (`dart run`) | Production Deployment (`dart compile exe`) |

### 2. Implementasi & Contoh Kasus Nyata

Mari kita buktikan secara empiris perbedaan karakteristik startup dan kompilasi menggunakan Dart CLI modern.

#### Langkah 1: Siapkan Script Benchmark CPU-bound Sederhana
Buat file `performance_benchmark.dart`:

```dart
import 'dart:io';

// Menggunakan static analysis directive untuk memastikan code cleanliness
void main() {
  final stopwatch = Stopwatch()..start();

  // Simulasi komputasi intensif: Penghitungan bilangan prima
  final totalPrimes = _countPrimesUpTo(2000000);

  stopwatch.stop();
  
  // Ambil metadata environment eksekusi
  final isVm = !const bool.fromEnvironment('dart.library.isolate');
  
  stdout.writeln('--------------------------------------------------');
  stdout.writeln('Hasil Perhitungan Prime : $totalPrimes');
  stdout.writeln('Waktu Eksekusi          : ${stopwatch.elapsedMilliseconds} ms');
  stdout.writeln('Platform OS             : ${Platform.operatingSystem}');
  stdout.writeln('Jumlah Processor        : ${Platform.numberOfProcessors}');
  stdout.writeln('Environment             : ${isVm ? "AOT Native" : "JIT/Dart VM"}');
  stdout.writeln('--------------------------------------------------');
}

/// Algoritma Sieve of Eratosthenes untuk uji alokasi array dan looping cepat
int _countPrimesUpTo(int limit) {
  if (limit < 2) return 0;

  // Alokasi memori linear byte array (List<bool>)
  final isPrime = List<bool>.filled(limit + 1, true);
  isPrime[0] = false;
  isPrime[1] = false;

  for (int p = 2; p * p <= limit; p++) {
    if (isPrime[p]) {
      for (int i = p * p; i <= limit; i += p) {
        isPrime[i] = false;
      }
    }
  }

  int count = 0;
  for (int i = 2; i <= limit; i++) {
    if (isPrime[i]) count++;
  }
  return count;
}
```

#### Langkah 2: Menjalankan dalam Mode JIT (Development)
Perintah ini mengeksekusi Dart VM, mem-parsing via CFE, menghasilkan kernel snapshot, dan melakukan JIT compilation:
```bash
# Mengukur total waktu proses (Startup + VM init + JIT Compilation + Execution)
time dart run performance_benchmark.dart
```

#### Langkah 3: Mengompilasi ke Native Machine Code (AOT)
Perintah ini membakar (*ahead-of-time*) seluruh dependensi, runtime minimal, dan kode ke binary native platform host:
```bash
# Menghasilkan binary mandiri tanpa dependensi Dart SDK luar
dart compile exe performance_benchmark.dart -o benchmark_aot

# Eksekusi binary native secara langsung
time ./benchmark_aot
```

#### Analisis Hasil Eksekusi:
Pada mode **JIT** (`dart run`), CPU harus membayar *tax overhead* untuk inisialisasi CFE, alokasi memori Dart VM profiler, serta kompilasi dinamis bertahap saat algoritma dieksekusi. 

Pada mode **AOT** (`./benchmark_aot`), waktu eksekusi total (terlihat via metrik `real` di perintah `time`) akan turun drastis karena OS langsung memetakan binary ELF/Mach-O ke memori virtual tanpa tahapan kompilasi runtime.

### 3. Cara Kerja di Balik Layar (Under the Hood)

#### A. Eksekusi & Runtime Pipeline

1. **JIT Pipeline (Development / Hot Reload)**:
   - File `.dart` diubah oleh **CFE** menjadi **Kernel Bytecode AST** (disimpan dalam modul `.dill`).
   - Dart VM memuat modul `.dill`. Kode pertama kali dieksekusi menggunakan interpreter ringan atau unoptimizing compiler.
   - Saat metode dipanggil berulang kali (*hot spots*), VM Profiler mengumpulkan type feedback.
   - **Optimizing JIT Compiler** menggunakan data profil tersebut untuk memproduksi instruksi native assembly teroptimasi (*inlining*, *loop unrolling*, *type specialization*).
   - **Hot Reload**: Ketika source code berubah, hanya sub-grafik Kernel AST yang dimodifikasi yang dikirim via IPC ke Dart VM. VM memperbarui penunjuk fungsi (*vtables*) di memori heap secara dinamis tanpa mereset *state* memory isolate.

2. **AOT Pipeline (Production)**:
   - **Global Type Flow Analysis (TFA)**: Compiler menganalisis seluruh dependensi dari `main()` ke ujung graf kode secara utuh (*whole-program analysis*).
   - **Tree Shaking**: Semua kelas, *field*, method, dan library yang tidak pernah dijangkau oleh alur eksekusi statis dihilangkan seluruhnya dari output akhir binary.
   - **Devirtualization**: Jika TFA membuktikan bahwa suatu *polymorphic call* hanya memiliki satu implementasi konkret, *dynamic dispatch table lookup* diubah menjadi direct branch/call native instruction.
   - Compiler memproduksi *assembly* mesin spesifik (x86_64 atau ARM64) lalu membungkusnya dengan *AOT runtime stub* (bertugas menginisialisasi heap awal dan GC dasar).

```
[AOT Compile] -> Whole-Program TFA -> Tree Shaking -> Machine Assembly -> OS Loader -> Execution
```

#### B. Alokasi Memori / Resource (The Isolate Heap Model)
Dart VM mengisolasi memori secara ketat:
* **No Shared Heap**: Setiap isolate memiliki heap memory sendiri. Mutator thread berjalan eksklusif di isolate tersebut. Tidak diperlukan global thread synchronization locks untuk alokasi memori biasa.
* **Nursery/New Generation**: Alokasi objek baru ditempatkan pada space memori berurutan (*bump-pointer allocation*). Ukurannya kecil (biasanya beberapa MB), dibersihkan sangat cepat via *semi-space scavenger GC*.
* **Old Generation**: Objek yang selamat dari beberapa siklus scavenger dipromosikan ke Old Generation yang dikelola oleh concurrent non-blocking *Mark-Sweep-Compact GC*.

#### C. Trade-offs: JIT vs AOT
* **Peak Performance vs Startup**: JIT secara teoritis dapat mencapai *peak throughput* yang lebih optimal daripada AOT pada skenario server long-running, karena JIT mengoptimasi kode berdasarkan profil eksekusi dunia nyata (*dynamic profile-guided optimization*). Namun, JIT memiliki *memory footprint* sangat besar dan *warm-up latency*.
* **Binary Size vs Agility**: AOT menghasilkan *fast start* dan memori kecil, namun mengorbankan fleksibilitas. Dynamic code injection, `dart:mirrors` (reflection), dan `eval()` tidak didukung di AOT.

### 4. Best Practices & Common Pitfalls

#### Do's:
1. **Gunakan Environment Variables Secara Konstan**:
   Gunakan ekspresi `const bool.fromEnvironment('KEY')` untuk *feature-flagging*. AOT compiler dapat mengevaluasi ekspresi ini pada fase kompilasi statis dan menghapus (*dead-code strip*) seluruh cabang blok kode yang tidak aktif.
2. **Optimalkan Type Annotations**:
   Berikan batasan tipe yang konkret. Hindari penggunaan tipe `dynamic` yang berlebihan agar *Type Flow Analysis* (TFA) AOT dapat melakukan *devirtualization* dan devirtualized calls langsung ke alamat instruksi native.
3. **Pilih Target Kompilasi yang Tepat**:
   - `dart compile exe` untuk server/CLI mandiri.
   - `dart compile js` atau `dart compile wasm` untuk deployment Web.
   - `dart compile aot-snapshot` jika ingin mendistribusikan kode native modular yang di-load via custom embedding Dart VM.

#### Don'ts:
1. **Jangan Mengukur Performa Produksi pada `dart run`**:
   Banyak developer mengira performa `dart run main.dart` mencerminkan kecepatan aplikasi final. Padahal, `dart run` menyertakan logging, debugging hooks, de-optimizer, dan overhead kompilasi JIT.
2. **Jangan Mengandalkan Refleksi Runtime (`dart:mirrors`)**:
   Penggunaan `dart:mirrors` memblokir kemampuan AOT untuk melakukan *tree shaking*, dan package ini dinonaktifkan secara default pada build native executable. Gunakan *compile-time code generation* (seperti `build_runner`, `source_gen`) sebagai alternatif.

#### Edge Cases & Pitfalls:
* **Dynamic Invocation Failure di AOT**:
  Jika Anda memanggil method via dynamic reflection string atau dynamic member call yang tidak sengaja ter-tree-shake oleh compiler, aplikasi Anda akan mengalami *runtime NoSuchMethodError* di produksi, meskipun lulus kompilasi:
  ```dart
  dynamic handler = SomeService();
  // Bahaya: jika TFA tidak mendeteksi method 'processData' terpanggil secara statis di tempat lain,
  // method tersebut mungkin telah dibuang dari binary AOT!
  handler.processData(); 
  ```

### 5. Tantangan Eksplorasi Mandiri

1. **Investigasi Binary Stripping & Tree Shaking**:
   Buat sebuah file Dart yang mengimpor library besar (misalnya package `crypto` dari pub.dev atau `dart:convert`). Panggil hanya satu fungsi sederhana. Kompilasi menggunakan `dart compile exe`. Cek ukuran binary yang dihasilkan. Kemudian ubah kode agar memanggil library tersebut secara dinamis melalui interface `Function.apply`. Amati apakah ukuran binary dan waktu kompilasi berubah.
2. **Inspect Kernel Snapshot (.dill)**:
   Gunakan perintah SDK internal untuk mengompilasi program ke Kernel AST:
   ```bash
   dart compile kernel performance_benchmark.dart -o benchmark.dill
   ```
   Analisis struktur biner intermediate tersebut menggunakan Dart dump tool (jika tersedia di SDK repository Anda) atau bandingkan ukuran `.dill` terhadap binary native `.exe` untuk memahami porsi overhead runtime OS vs AST bytecode.
